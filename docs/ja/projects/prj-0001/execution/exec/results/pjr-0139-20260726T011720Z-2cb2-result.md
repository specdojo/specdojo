# Edit Result

## 1. 実施内容

PJR-0139「個票 frontmatter の status 遷移を自動化」に対応した。個票の成熟度 `status` が全件 `draft` のまま放置される問題に対し、遷移基準の明文化と `close` / `reject` による自動更新を実装した。

- 遷移基準を [[pjr-rulebook|プロジェクト登録簿ルールブック]] の `個票 status の遷移基準`（新設 `### 5.6.`）に明記した。`draft`（個票生成直後）→ `ready`（`close` かつ必須節に `_TODO_` なし）→ `deprecated`（`reject`）を表で定義し、`pjr-index` の処理状態を機械的に写像しない点を併記した。あわせて `5.4.` の同期ルールを新基準へ整合させた。
- `src/register.ts` に個票 Frontmatter の `status` 書き換え処理を実装した。`register close` は対象個票を `ready` へ昇格、`register reject` は `deprecated` へ更新する。
- `ready` への昇格は個票本文に記入プレースホルダ `_TODO_` が残っていないことを条件とし、残る場合は昇格せず警告して `draft` を維持する。`_TODO_` 判定は見出し文言に依存せず本文全体を対象とし i18n 非依存とした。
- 個票を持たない項目（個票列が `-`）や個票ファイル不在はエラーにせず、処理状態のみ更新して従来どおり完了する。既に目的の `status` の個票は冪等に扱い内容を変えない。
- `--dry-run` では個票を書き換えず、`Would update ticket status → <status>` の変更予定を一覧行の変更に続けて表示する。
- 既存 draft 個票の扱いは「現状維持（一括更新しない）」と決定した。理由と代替運用は `申し送り` に記載。
- 運用ガイド（`状態遷移とコマンド`）とコマンドリファレンス（`register` 表の close / reject 行）へ遷移仕様を反映した。
- テストを `tests/src/register.test.ts` に追加し、`npm run build` / `npm run lint:ts` / 対象 md の `prettier --write` と `markdownlint` を実行してエラーがないことを確認した（register テスト 27 件 pass）。

## 3. 申し送り

- 既存 draft 個票（15 件）は一括更新せず現状維持とした。必須節が未確定な個票を一括で `ready` へ昇格させると成熟度指標が実態とずれるため。既存の終端項目を `ready` にしたい場合は `register reopen` 後に `register close` する運用で個別対応する。この方針判断は人間の承認対象。
- `pjr-index.schema.yaml` など個票 Frontmatter の status enum を機械検証する schema がある場合、`draft` / `ready` / `deprecated` の 3 値が許容されているか確認が望ましい（本タスクでは plan 未記載のため schema 検証コマンドは未実行。追加検証は runner 判断とする）。
- `exec run --register` は agent が項目を終端化しない設計のため、個票 status 遷移は人間による `register close` / `reject` 実行時にのみ発生する。自動実行経路での昇格は本タスクの対象外。

## 4. 参考資料の活用

本タスクは register コマンド実装と rulebook / ガイド更新を伴うため、正本の役割分担に従って進めた。

- 遷移基準の「どこに書くか」は個票の完了条件（`rulebook に明記`）を優先し、規範は [[pjr-rulebook|プロジェクト登録簿ルールブック]] に定義、運用手順は [[specdojo-register-operation-guide|SpecDojo登録簿運用ガイド]]、コマンド一覧は [[specdojo-command-reference|SpecDojoコマンドリファレンス]] に分離した。rulebook の `5.4.` に既存で「文書成熟度を処理状態に連動させない」とあり、新実装の close/reject 連動と表面的に矛盾するため、rulebook を正として「機械的写像はせず記述が固まっているかを判定して遷移させる」と読み替えられるよう `5.4.` の文言を更新して整合させた。
- 実装は既存の register コマンド構造（`loadItemForUpdate` → `applyItemUpdate` の流れ、`process.stdout.write` による出力、章番号アンカーの i18n 非依存方針）に合わせ、個票パス解決・Frontmatter 書き換えを新規ヘルパーとして追加した。個票 Frontmatter は `specdojo:` 名前空間配下のため `parseSpecdojoDocument` を再利用した。
- `_TODO_` 判定は rulebook の type 別必須節（`todo` なら概要・完了条件・作業内容・対応結果）が本来の対象だが、見出し文言依存を避けるため本文全体の `_TODO_` 有無で近似した。これは必須節の上位集合であり、未確定個票を `ready` へ誤昇格させない安全側の判定である旨を rulebook 本文にも明記した。
