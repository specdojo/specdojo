## 4. 進め方と実践の型の適用

plan の approach 指定はなく、`retrofit` に近い進め方を採った。分割元 [[prj-0001:pjr-es57-register-file-ssot-migration]] と先行分割 [[prj-0001:pjr-rf3b-register-item-frontmatter-schema]] の対応結果を読み、既に実装済みの範囲（個票 Frontmatter スキーマ、CLI の書き込み先の個票化、派生ビューの入力の個票化）を実装コード（`src/register.ts`、`src/register-item.ts`、`src/doc-index.ts`、`lefthook.yml`、`.gitignore`）で確認してから、本項目で未実装だった差分（一覧そのものの生成と出力先、追跡ファイルからの独立、決定性、手編集経路の除去）に絞って変更した。

実践の型の適用は次のとおり。

- 一覧の章構成と列定義は [[specdojo:pjr-rulebook]]（`pjr-index` の本文構成、登録項目一覧の標準列、派生ビューの `status` は `ready`）を正として扱った。生成物 Frontmatter の `status` を `ready` にしたのはこの規範に従った判断で、`ready` 昇格が人間限定であるという共通規約は追跡対象の成果物に対する規則であり、非追跡の生成物には適用されないと解釈した（値は template の `frontmatter_template` 配下にあり、commit 時の昇格ガードの検査対象である文書自身の `status` も変更していない）。
- 生成物の外枠を template に持たせる方針（`.github/instructions/markdown.instructions.md` と既存の `pjr-views-template.md` / `pm-*-template.md` の設計）を踏襲した。列名をコードの定数にしない既存の意図（列名の言語非依存）も維持し、供給元だけを作業ツリーのファイルから template へ移した。
- 行の注入方式は当初、既存の `view-slot` 機構（`<!-- specdojo:view-slot=... -->`）で統一しようとしたが、slot 行をテーブル区切り行の直後に置くと prettier が区切り行とコメントの間に空行を挿入してテーブルが分断されることを実測で確認した（`<!-- prettier-ignore -->` は直後の 1 ノードにしか効かない）。そのため一覧の行注入だけは slot を使わず、章 1 のテーブル区切り行を検出して行を挿入する方式にした。template が有効な Markdown テーブル（列見出しのみ）のままになり、prettier と markdownlint の両方を通る。
- テストは `.github/instructions/vitest.instructions.md` に従い、一時ディレクトリを `mkdtemp` で作って `finally` で削除し、リポジトリの実ファイルを変更しない形にした。決定性の検証は「同一入力から 2 回生成して結果が等しい」という観測可能な振る舞いで固定した。
- 完了条件のうち「一覧を手編集する運用が残っていない」は、`register scaffold` の再定義と文書化で満たした一方、追跡対象の `pjr-index.md` が移行完了まで残る点は完全には満たせない。分割元が本項目（分割 3）を既存項目の移行（分割 4）より前に置いているため、この時点でファイルを削除すると 185 件の値が失われるという制約による。削除の実行条件と残課題は「申し送り」に記載した。
