# Edit Result

## 1. 実施内容

PJR-EQAQ の完了条件（個票 [[prj-0001:pjr-eqaq-register-timestamps|PJR-EQAQ 登録簿日時をregistered_at・completed_atへ移行する]] の `完了条件`）を基準に、登録簿の起票・完了の記録を「暦日」から「瞬間」へ移行した。

### 1.1. スキーマと記述規則

- `register-item-frontmatter.schema.yaml` に `$defs/Timestamp`（UTC・RFC 3339・秒精度 `YYYY-MM-DDTHH:MM:SSZ`）を追加し、`registered_on` / `completed_on` を `registered_at` / `completed_at` へ置き換えた。終端状態（`done` / `decided` / `rejected`）で `completed_at` を必須にする条件付き必須も同じ形で移した。
- `due_on` は瞬間ではなくプロジェクトタイムゾーン上の暦日であるため、`Date` のまま維持した（完了条件の「`due_on` は暦日として維持」に対応）。
- `deliverable-frontmatter.schema.yaml` の登録項目フィールドも同じ `Timestamp` 定義を参照するよう更新した。

### 1.2. 記録と表示の分離

- `src/register-date.ts` に日時ヘルパーを追加した。`formatUtcTimestamp` / `nowUtcTimestamp`（保存書式の生成）、`normalizeRegisterTimestamp`（タイムゾーン付き入力の UTC 正規化）、`registerDateFromTimestamp`（表示暦日の導出）、`timestampFromDateInTimeZone`（暦日＋壁時計時刻から UTC への変換。夏時間の切り替え日を跨ぐ場合はオフセットを再評価して補正）。
- `PjrItem` は日時（`registeredAt` / `completedAt`）だけを保持する型にし、一覧行の表示値は `toDisplayItem(item, timeZone)` で導出する `PjrDisplayItem` へ分離した。これにより「同じ値を2か所へ持たない」構造を保ったまま、表示タイムゾーンを変えても記録が書き換わらない。
- 一覧・派生ビューの生成（`generateDerivedViewFiles`）と `register history` の比較値は、いずれも `run.register_date_timezone` へ変換した暦日を使う。
- 旧一覧（表が正本だった頃の `pjr-index.md`）を読む互換経路 `parsePjrIndex` は、暦日セルへ移行と同じ規則（21:00）を補って日時へ変換する。

### 1.3. register コマンド

- `add` は `registered_at` へ、`close` / `reject` は `completed_at` へ実行時刻（UTC）を自動設定する。`reopen` は `completed_at` を削除する。
- `--registered` / `--completed` はタイムゾーン付き RFC 3339（`...Z` またはオフセット）のみ受け付け、UTC の秒精度へ正規化して保存する。タイムゾーンを含まない値（`2026-08-09`、`2026-08-09T14:08:51`）は解釈が実行環境に依存するため拒否し、受け付ける書式を例示する。

### 1.4. 移行処理と実データの移行

- `src/register-migrate-timestamps.ts` を新設し、`register migrate` の第2段として実行するようにした（第1段は既存の「旧一覧の行 → 個票 Frontmatter」移行）。
- 時刻の決定は次の優先順とした。
  1. Git 履歴から復元する。起票は個票ファイルを追加したコミット、完了は終端状態が連続している最古のコミットの author 時刻を採る。
  2. 復元した時刻の暦日（プロジェクトタイムゾーン）が旧日付と一致しない場合、または復元できない場合は、旧日付に 21:00 を補って UTC へ変換する。
- 2 の一致判定を挟んだのは、個票ファイルの作成が起票より後になっている項目では追加コミットの時刻が起票時刻ではないためである。この判定により、移行前後で一覧に出る暦日が変わらないことを保証する（計画時に全件検証し、変わる場合は書き込み前に失敗する）。
- 実データを移行した結果は次のとおり。対象 181 件、起票日時は Git 履歴から 22 件復元・1 件フォールバック、完了日時は Git 履歴から 15 件復元・164 件フォールバック。完了日時の復元率が低いのは、個票が正本になる前のリビジョンには `item_status` が無く終端状態を判定できないためで、その場合は 21:00 へ退避している。
- 移行後の 181 個票から `registered_on` / `completed_on` は削除済みで、`register build` で再生成した一覧・派生ビューの登録日・完了日は移行前と一致することを確認した（例: PJR-0001 の完了日 `2026-05-17`、PJR-C0B7 の登録日 `2026-08-09` / 完了日 `2026-08-09`）。

## 3. 申し送り

- `npm run lint:md` が生成ビュー（`controls/project-register/generated/pjr-index.md` ほか）で MD049 を報告する。原因は PJR-0053 の概要にある `*CAPITAL_CASE*` がそのまま説明列へ入ることで、本タスクの変更とは無関係な既存の内容起因である。生成物は gitignore 済みで pre-commit の対象（staged files）にも入らないためコミットは妨げないが、登録簿の説明文をビューへ埋め込む際のエスケープ不足として別項目で扱う余地がある。
- 完了日時の Git 復元率が低い（15 / 179）。個票が正本になる前のリビジョンには `item_status` が無く終端状態を判定できないためで、それらは 21:00 へ退避している。より正確な close 時刻が必要になった場合は、旧 `pjr-index.md` の表差分（完了日列の変化）から復元する経路を追加できるが、表示される暦日は現状でも正しいため今回は実装していない。
- `register migrate` は個票ごとに `git log` / `git show` を実行するため、本リポジトリ規模（188 件）で 2 分前後かかる。一度限りの移行コマンドである前提で最適化していない。
- 個票のうち 7 件は旧日付キーを持たないため `registered_at` / `completed_at` のいずれも付かない（スキーマ上も任意）。値を推測しない方針に従い、キーを省略したままにしている。

## 4. 進め方と実践の型の適用

- plan の `進め方` に従い、登録簿の該当行と個票を先に読み、個票の `完了条件` を作業の基準にした。完了条件が 7 項目に分解されていたため、仮説を立てる必要はなく、そのまま受入基準として扱った。
- 一次根拠は [[specdojo:pjr-rulebook|プロジェクト登録簿 作成ルール]] と `register-item-frontmatter.schema.yaml` とし、両者が定める「構造化フィールドの正本は個票 Frontmatter」「一覧は生成物」という原則を崩さない形を設計の制約にした。具体的には、表示用の暦日を個票へ保存せず `toDisplayItem` で導出する形にしたのは、rulebook の禁止事項「構造化フィールドを個票本文や別の正本へ重複管理しない」に抵触しないためである。
- 実装ルールは `.github/instructions/typescript.instructions.md`、テストは `.github/instructions/vitest.instructions.md` に従った。日時変換のような外部依存のない変換処理は mock せず入力と出力で検証し、Git 履歴に依存する移行処理だけは解決関数を注入点にして実プロセス起動なしで検証できるようにした。
- 文書更新は `.github/instructions/markdown.instructions.md`（章番号・見出し前後の空行・表のエスケープ）と rulebook 作成ルールに従った。rulebook には日時と日付の使い分けを `### 3.1.` として追加し、既存の章番号体系を崩していない。
- 移行方式の判断について記録する。完了条件は「Git履歴から可能な範囲で復元し、復元できない時刻は 21:00 を補う」とだけ定めており、復元した時刻が旧日付と食い違う場合の扱いは規定されていなかった。ここは「登録簿の記録として日付そのものが正である」「移行で一覧の見え方を変えない」を優先し、暦日が一致する場合だけ Git 時刻を採用する規則を追加した。この判断は個票の `対応結果` にも移行規則として記録している。
