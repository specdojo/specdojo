# 理解の負債の測定と OpenFisca-Japan 試行計画

## 1. 目的と判定範囲

[[prj-0001:pjr-y5rd-civic-tech-comprehension-debt|PJR-Y5RD の決定]]に従い、「前の担当者の記憶に頼らず、文書から判断と作業を引き継げるか」を測る。理解の負債は単一の点数にせず、回答の充足、着手時間、誤り・推測、引き継ぐ側と支える側の負荷で示す。

OpenFisca-Japan の一つの変更範囲について、復元前の文書を使う A と、kata で復元・人が確認した文書を使う B を各1回実施する。本書は測定方法と利用側への起票案であり、試行結果ではない。この項目では利用側の登録簿への起票、リポジトリの調査・変更、外部 PR の作成を行わない。

[[prj-0001:prj-success-criteria-and-acceptance-criteria|成功基準と受入条件]]の SC-03 は「別の参加者による一つの改善の完了」を求める。文書だけで着手できることはその途中の証拠であり、改善の完了と役割・負荷の確認を別に行う。BV-03 や初期公開全体の合否を本試行の点数だけで決めない。

## 2. 開始前に固定する条件

利用側の `BA` が準備し、`QE` が測定条件を確認、`PO` が範囲と負荷上限を承認する。役割には実名または agent の識別子を割り当てる。兼務は可だが、文書作成者・経験者を新規参加者には数えない。

| 項目           | 固定する内容                                                                                                                                                                                                        |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 対象           | 一つの制度計算・判定のまとまりを候補とし、入出力、境界・例外、テスト、利用者価値を確認できる範囲を利用側で選ぶ。特定の制度・実装パスが存在するとは本書では仮定しない                                                |
| 意味のある変更 | 当事者が必要とする一つの小さな改善。対象・期待する変化・対象外・受入例と境界例を先に合意する。単なる整形・改名は除く。制度上の意図を確定できなければ、仕様と回帰テストの補強を候補として人が選ぶ                    |
| 対象版         | コードの commit、A の文書一覧と版、B に適用する kata の版、調査対象パスを保存。A/B のコード・変更課題・質問・制限時間は同じにし、文書だけを変える                                                                   |
| 評価用正解     | `BA` と経験者が第3章の各問の必要事項・根拠・既知の未決・重大な誤答例を作り、`QE` が開始前に版を固定。参加者へは見せない。コードから確認できる動作と、人が確認した意図を区別する                                     |
| 参加者         | 最小構成は同じモデル・設定の新しい agent セッションを A/B に一つずつ。過去会話・検索記憶・復元作業の出力を共有しない。人で行う場合も対象未経験の別人を各1名とし、経験差を記録する。人と agent の結果は混ぜない      |
| 実施者         | 利用側 `BA` が進行、文書作成者とは別の `QE` が採点し、当事者が価値・制度上の意図、経験者が動作と設計経緯を確認する。確定権限がない人の見解は確定扱いにしない                                                        |
| 上限案         | 文書テストは各30分、改善は文書テスト後の実作業を各90分。人の準備・復元・確認は合計6時間、進行・採点は合計2時間を初回の上限案とする。`PO` と `PM` が参加者別配分、現金・API 費の金額上限、対象期間を試行前に確定する |

対象、協力する当事者・経験者、新規参加者、正解票、費用・時間上限、保存先がそろわなければ開始を保留する。これは利用側の準備作業であり、本計画作成の未完了を意味しない。準備中も時間・費用を記録し、上限超過時は縮小または再承認を先に行う。

## 3. 文書だけによる引き継ぎテスト

### 3.1. 提示する問いと着手課題

文書一覧と変更課題を渡した時刻を開始とし、30分以内に次を回答する。質問票は A/B 共通とし、各回答に文書の ID・節・版と、確定／推測／不明の自己申告を求める。

| 問  | 質問                                         | 評価用正解に含める事項                                                                       |
| --- | -------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Q1  | 誰のどんな困りごとを解くシステム・対象機能か | 対象者、目的、期待価値、対象外                                                               |
| Q2  | なぜ現在の設計・判定方式なのか               | 一つの主要判断、その理由・制約・採らなかった案。経緯が失われていれば、その未確認状態と確認先 |
| Q3  | 何が未決・未確認か、誰がどう決めるか         | 重要な未決事項、影響範囲、判断者、次の確認方法                                               |
| Q4  | 今回どこを変え、何に影響するか               | 要件から機能・入出力・実装箇所への対応、変更範囲と影響先                                     |
| Q5  | 保持すべき制約と境界は何か                   | 対象期間・適用条件・例外等から対象課題に関係するもの。実装と意図の乖離があればその扱い       |
| Q6  | 何を確かめれば改善を完了と判断できるか       | 受入例、境界・回帰テスト、実行方法、レビューと確定の担当                                     |

併せて「変更開始票」を作る。期待価値、対象ファイルまたは文書、変更方針、受入例とテスト方法、未決事項と対処を含める。`QE` が正解票と照合し、この5要素がそろい、着手を妨げる未決・重大な誤解がない最初の提出を有効な着手とする。コード編集そのものはこの段階では求めない。

### 3.2. 参照できる情報と停止条件

- 文書段階では、指定した文書とそこに含まれる凍結済みの参照資料だけを読める。実装・テストコード、生の PR 履歴、外部検索、前任者への質問、別 agent への問い合わせは認めない。実装パスが文書に書かれていることは可。人が使う補助 AI も含め、同じ制約を適用する。
- 根拠がなければ不明とし、確認すべき相手や記録を挙げる。質問したいことは記録するが、内容の回答や採点フィードバックは終了まで渡さない。
- 提出時刻と原文を保存し、採点は終了後に行う。30分で有効な着手に至らなければ打ち切る。禁じた参照・助言があればその回は無効とし、支援後の時間を独立の参考値として残す。
- B では復元時に使ったコード・聞き取り原本をそのまま参加者へ渡さず、根拠と確認状態を記した文書を渡す。正解票と採点メモは A/B とも非公開にする。

### 3.3. 測定と比較

| 指標         | 数え方・記録方法                                                                                                                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 回答の充足 S | 各問0〜2点、計12点。必要事項と根拠・確認状態がそろえば2、一部欠落は1、誤答・未回答・根拠なしの断定は0。真に未確認の事項を正しく特定した回答は2にできるが、既知事項を「不明」と答えても満点にはしない |
| 誤り E       | 回答と変更開始票を検証可能な主張に分け、固定した正解・根拠と矛盾する主張を数える。同じ誤りの反復は1件、出現箇所を併記。価値・制度適用・変更範囲・検証を誤らせるものを重大とする                      |
| 推測 G       | 文書で裏付けられない主張の件数。自己申告した推測と、確定と断定した推測を分ける。根拠と矛盾すれば E とも重複計上し、合算しない。不明の申告・確認の提案は推測に含めない                                |
| 着手時間 T   | 文書の引き渡しから、最初の有効な変更開始票の提出までの分数。回答作成・読解・検索・思考の時間を含む。未達は「30分超・打切り」とし、30分で成功した値や欠測0分にしない                                  |
| 負荷         | 参加者別の準備・復元・確認・読解・改善・レビューの作業分数、問い合わせ件数と支援者の分数。agent は壁時計時間、モデル・設定、利用量と費用も別記。人と agent の時間を足して人の労働時間としない        |

質問ごとの点数と E/G の明細を残し、総点だけで隠さない。正解票の誤りが後から判明したら変更理由と版を残し、同じ基準で A/B の両方を再採点する。実際の不明点を採点者も判定できない場合は保留とする。

初回の文書テストの達成目安は、B の S=12、E=0、確定と断定した推測=0、T が30分以内。自己申告した推測の件数と必要な確認は別に残す。A に対し S の増加、E または G の減少、T の短縮（A が打切りで B が着手した場合を含む）のいずれかがあり、ほかが悪化しなければ「今回の範囲で軽減の兆候」とする。A/B とも達成して指標に差がなければ「引き継ぎ可能、軽減効果は未確認」、指標が相反すれば「効果は混在」、差がなく未達なら「軽減の兆候なし」とする。片側無効・欠測なら比較保留とする。

これは標準の合否閾値ではなく、初回の運用目安として本計画で選んだ値である。少人数・一課題の差から因果関係や一般的な改善率は主張しない。同一人物の再試験しかできなければ学習効果を記録し、改善前後の参考観測に格下げする。

## 4. kata による復元と人による確定

利用側の文書担当者が、A の文書を保存した後に実施する。[[specdojo:ryu-guide|実践の進め方ガイド]]と[[specdojo:schedule-design-guide|Schedule設計ガイド]]の retrofit の順序に従う。

1. **入力を固定する**: 対象 commit の実装・テスト・設定の非機密部分、既存要件、公開記録、承認済み判断を列挙する。成果物カタログを使う場合は `evidence_refs` に読み取り対象を宣言し、ない場合は利用側個票に相対パスを列挙する。対象外・読めない箇所も記録する。
2. **必要な型を選ぶ**: 目的・対象者、課題と方針、要件・業務ルール、機能・検証の対応、判断と未決事項を最小の文書群で覆う。既存の rulebook・sample・recipe を使い、型がなければ bootstrap を先に行う。全種類の文書を作ることを目標にしない。[[prj-0001:pjr-bxym-civic-tech-starter-kata|PJR-BXYM]]の採択内容が利用可能なら取り込む。
3. **現在動作を復元する**: 入出力、適用条件、例外、テスト済み範囲を実装根拠と結ぶ。意図との一致・乖離・実装から確認不能・未調査を区別する。目的、設計理由、制度として正しいかをコードから補完しない。乖離は文書を実装へ無条件に合わせず、別の判断項目へ送る。
4. **確認状態を付ける**: 次の表で主張単位に記録し、対象文書の該当節から参照できるようにする。共通 schema や frontmatter は新設しない。[[prj-0001:pjr-dzmv-restored-content-confirmation-status|PJR-DZMV]]の結論が未採択でも、試行用の本文表で開始できる。
5. **人が確定する**: `BA` が質問をまとめ、当事者・制度に詳しい人に目的と業務上の意図を、経験者に動作と設計経緯を照会する。確認者が根拠を示して訂正または承認し、利用側の判断権者が確定内容・対象範囲・日付を decision に残す。回答不能は未確認のまま、担当・期限・次の調査先を付ける。agent のレビューのみで「当事者が確定」へ上げない。
6. **B を凍結する**: 文書同士の対応と実装根拠を review し、重大な乖離・未確定事項が変更を妨げるなら試行を保留する。残る未決は明記して文書版を固定し、第3章を実施する。確認のための人の負担も費用に含める。

| 主張 ID・文書節          | 復元内容・現在動作／意図の区分 | 根拠の場所・版                                         | 確認状態                               | 確認者・日付・判断記録                       | 残る問い・担当・期限 |
| ------------------------ | ------------------------------ | ------------------------------------------------------ | -------------------------------------- | -------------------------------------------- | -------------------- |
| 記録時に一意の ID を付与 | 一つの主張に分ける             | コードの commit とパス・行、文書 ID と版、聞き取り記録 | 推測／根拠で確認／当事者が確定／未確認 | 氏名・役割と確認範囲。未確認なら未確認と記す | ない場合は「なし」   |

「根拠で確認」には、何を確認したかを必ず添える。実装で動作を確認しても業務上の正しさの確定にはならない。既存の目印を使う場合は推測に `_ASSUMPTION_`、未決に `_UNDECIDED_` を使い、表の ID と対応させる。根拠の版が変われば該当主張を再確認し、前の確定をそのまま流用しない。

## 5. 改善の完了と BV-03 への接続

文書テスト終了後、A/B それぞれの参加者が同じ対象コードを読んで改善案とテストを作り、利用側の通常レビューへ渡す。この段階からコード・開発環境の利用を認め、追加情報・支援の種類と時間を記録する。コードを読んだ後の理解で文書テストの回答を上書きしない。

改善の完了は、合意した受入例と回帰テストを満たす差分があり、当事者と経験者の確認を経て利用側のレビュー担当者が受け入れた時点とする。外部 PR が必要なら利用側で作成し、PR の作成・受入・統合を別々に記録する。PR を出しただけでは改善完了としない。レビュー待ちの経過時間と実作業時間を分け、90分の実作業上限を超えた場合は未達とする。

| 判断          | 本試行から渡す証拠と限界                                                                                                                                                                                 |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 理解の負債    | 第3章の指標、文書で答えられなかった箇所、復元・確認に要した負荷。B が目安未達なら不足箇所と是正案を記録する                                                                                              |
| SC-03 / BV-03 | B の別参加者が未決事項を理解して一つの改善を完了し、事前承認した参加者別上限内で分担・継承できたことを `BA` と `QE` が確認。支援・復元・レビューが特定個人へ集中した場合はその負荷と継続可能性も確認する |
| 保留・未達    | 改善未完了・上限超過は未達、確認者不在・証跡不足・レビュー待ちは保留。文書テストの達成だけで SC-03 を合格にしない                                                                                        |
| 最終判断      | `PO` が証拠から BV-03 を判定する。SC-01・SC-02、AC-01〜AC-04 は正本に沿って別途確認し、CH-01・初期公開の合否を本試行だけで確定しない                                                                     |

## 6. 利用側登録簿への起票案

OpenFisca-Japan を扱う利用側プロジェクト（project-inclusive を候補）の登録簿で、実在する project ID・保存先を確認してから採番する。以下は起票用の案であり、既存項目の ID や担当者の承諾を意味しない。利用側 `PM` が試行日を設定し、各段の期限を逆算する。

| 案                        | 担当案・依存                                  | 作業と完了条件                                                                                                                                                      |
| ------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OFJ-CD-1 準備と A 測定    | `BA`、`PM`、`QE` / 最初                       | 第2章の条件と保存先を `PO` が承認。正解票と A 文書を凍結し、新規参加者で A の文書テスト・改善を実施して原票を保存。無効・未達も結果として保存する                   |
| OFJ-CD-2 復元と確認       | 文書担当、当事者、経験者 / 1 の記録保存後     | 第4章を実施。根拠・確認状態・判断記録・未解消の問いを文書化し、B を凍結。型不足なら bootstrap、実装修正が必要なら別項目に分ける                                     |
| OFJ-CD-3 B 測定と価値判定 | 別の新規参加者、`BA`、`QE`、`PO` / 2 の凍結後 | B のテスト・改善を実施し A/B を比較。外部 PR とレビューを含む完了証拠、費用・負荷、SC-03 の判定、是正担当・期限・再測定条件を記録。権利・公開範囲を確認して報告する |

OFJ-CD-1 と OFJ-CD-3 で改善を実行しても、B のコード入力は A と同じ commit の隔離した作業コピーを使う。A の差分・レビュー回答は B の参加者に見せない。受け入れる実変更は利用側で一本にまとめ、重複 PR を上流へ送らない。

試行開始は準備承認後、日程は協力者と合意して決める。利用側 `BA` が観測結果を prj-0001 の `BA`・`QE` に渡し、PJR-BXYM と PJR-DZMV の検討材料にする。再測定は是正後に別の新規参加者と版で行い、初回結果を消さない。

## 7. 記録先と書式

原本は利用側の文書リポジトリに、リポジトリ相対の `reporting/comprehension-debt/<trial-id>/` を設けて保存する案とする。利用側 `PM` が準備段階で実際の保存先と公開範囲を確定し、三つの起票項目から参照する。個人情報を含む原票は制限された保存先へ分け、公開版には匿名 ID と参照可能な集計を載せる。

| ファイル案       | 記録する内容                                                                                                                                                                |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `protocol.md`    | 試行 ID・日時・役割、承認記録、対象 commit、文書と kata の版・一覧、変更課題、参照条件、参加者別上限、費用上限、採点規約の版                                                |
| `answer-key.md`  | Q1〜Q6 の必要事項・根拠・未決・重大な誤答例、作成・確認者、改訂履歴。参加者のアクセス対象から除外                                                                           |
| `A.md` / `B.md`  | 参加者の経験・モデルと設定、開始・終了・提出時刻、回答原文・根拠・自己申告、変更開始票の各版、禁止参照・支援の有無、Q別得点、E/G の主張別明細、T と打切り・無効理由、採点者 |
| `restoration.md` | 第4章の主張別表、確認・decision の証跡、未調査範囲、A/B 文書の差分への参照                                                                                                  |
| `workload.md`    | 日時、参加者、役割、工程、実作業分数・待ち時間、支援内容、agent の壁時計時間・利用量、現金・API 費と証跡、承認上限との差                                                    |
| `summary.md`     | 下記の比較・判定表、改善差分・テスト・PR とレビュー結果への参照、判定者・日付、公開範囲、是正と再判定の記録                                                                 |

`summary.md` では次の表を使う。記録を作る時点の実値を記入し、実施していない段は「未実施」と理由を明記する。打切り・無効・欠測を成功値に置き換えない。

| 指標・条件               | A        | B        | 差・判断と根拠                               |
