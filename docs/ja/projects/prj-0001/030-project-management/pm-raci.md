# RACI

## 1. 適用方針

初期公開と代表試行に必要な責任境界を示す。列は [[prj-0001:pm-roles|ロール定義]] の Role code を用い、各行の `A` は1ロールとする。AI Agent は `R` または `C` の作業を支援できるが、`A` は担わない。

対象は初期 Launch Track の主要成果物と、価値・費用・進捗・品質・変更・公開の判断である。次は本書に独立した行を置かず、扱いを次のとおりとする。

- CLI・schema・生成・検証の実装: 初期 Launch Track の主要成果物に含まれないため行を置かない。[[prj-0001:pm-organization|組織定義]] の「実現・構造」に従い、内容は各成果物の `A` が承認し、作業は `ARC`・`DEV` が担う。実装成果物を計画した時点で成果物別 RACI に行を追加する。
- 公開準備（権利・個人情報・公開適性の確認）: 確認は「成果物・品質ゲートの確認」、公開の可否は「変更要求の採否、初期公開、継続判断」の行で扱う。

| 記号 | 意味                     |
| ---- | ------------------------ |
| R    | 実作業を担当する         |
| A    | 最終承認または判断を行う |
| C    | 事前に相談・レビューする |
| I    | 結果の共有を受ける       |

## 2. 成果物別 RACI

同じ責任分担の成果物は、Schedule で個別管理したまま本表ではまとめる。

| 成果物                                                       | PO  | PM  | BA  | ARC | DEV | QE  | UX  | OPS |
| ------------------------------------------------------------ | --- | --- | --- | --- | --- | --- | --- | --- |
| 概要、スコープ、ステークホルダー、成功基準、課題とアプローチ | A   | C   | R   | C   | I   | C   | C   | I   |
| プロジェクト憲章                                             | A/R | C   | C   | I   | I   | C   | I   | I   |
| 前提・制約・依存、代替案比較                                 | A   | C   | C   | R   | I   | C   | C   | I   |
| 組織、ロール、メンバー                                       | A   | R   | C   | C   | I   | C   | I   | I   |
| RACI、管理計画、コミュニケーション計画                       | C   | A/R | C   | C   | I   | C   | I   | C   |
| Launch スケジュール戦略定義（`sch-strategy-launch`）         | C   | A   | C   | R   | I   | C   | I   | C   |
| 品質管理計画                                                 | A   | C   | C   | C   | I   | R   | C   | I   |
| Schedule defaults                                            | A   | C   | I   | R   | I   | C   | I   | I   |
| 登録簿の管理ビュー、Schedule                                 | C   | A/R | C   | C   | C   | C   | C   | C   |
| 成果物カタログ                                               | C   | C   | A/R | R   | I   | C   | I   | I   |

Launch スケジュール戦略定義は、トラックの構成と作業順序を `ARC` が作成し、進捗管理に使えるかを `PM` が承認する。

成果物カタログの主担当は、作業ごとに次のとおりとする。

- 成果物の選定、`overview`・`done_criteria` の整理: `BA`
- 依存関係（`depends_on`）、適用する rulebook、配置などの文書構造の定義: `ARC`

## 3. 判断・プロセス別 RACI

| 判断・プロセス                                   | PO  | PM  | BA  | ARC | DEV | QE  | UX  | OPS |
| ------------------------------------------------ | --- | --- | --- | --- | --- | --- | --- | --- |
| 社会課題、期待価値、優先順位の判断               | A   | R   | C   | C   | I   | C   | C   | I   |
| 代表課題・試行成果の設計                         | A   | C   | R   | C   | C   | C   | C   | I   |
| 費用・参加時間上限の判断                         | A   | R   | C   | C   | I   | C   | I   | I   |
| 作業順序、進捗、課題・リスク管理                 | C   | A/R | C   | C   | C   | C   | C   | C   |
| 成果物作成フローの運営（着手順、割り当て、滞留） | C   | A/R | C   | C   | C   | C   | C   | C   |
| 成果物・品質ゲートの確認                         | C   | C   | C   | C   | C   | A/R | C   | I   |
| 変更要求の採否、初期公開、継続判断               | A   | R   | C   | C   | I   | C   | C   | C   |

- 成果物作成フローの運営の `A` は、着手順・割り当て・滞留の解消を判断する。成果物の内容承認は成果物別 RACI の各行の `A` が行い、作成作業の主担当も同表の `R` とする。
- 作業順序、進捗、課題・リスク管理では、`PM` が進捗を Schedule へ、発生済みの責任上の課題、将来の引き継ぎリスク、変更要求、決定を [[prj-0001:pjr-index|プロジェクト登録簿]] へ種別ごとに記録し、担当 Role と次の対応を付ける。記録の方針は [[prj-0001:pm-plan|管理計画]] に従う。
- 成果物・品質ゲートの確認の `A` は、品質確認の網羅と結果の判定を担う。受入・初期公開の可否は「変更要求の採否、初期公開、継続判断」の `PO` が決め、ゲート未達と例外要求は [[prj-0001:pm-quality-management-plan|品質管理計画]] に従って扱う。

## 4. Schedule・実行主体との対応

- Schedule の `owner` は [[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] の「Schedule への担当展開」に従う。WBS の明示 `owner` を先に確認し、未指定の作成作業は主担当の `R` とする。承認・レビュー・外部待ちを別の Task / Milestone に分けた場合は、対応する `A` または `C` を `owner` にできる。
- 照合する Schedule の正本は、各トラックの戦略（例: [[prj-0001:sch-strategy-launch|Launch スケジュール戦略定義]]）とトラック定義（例: [[prj-0001:sch-track-planning]]）とする。
- 初期 Launch Track で使う `owner` は `PO`、`PM`、`BA`、`ARC`、`QE` であり、本表の責任分担と整合させる。
- 実行主体と兼務は [[prj-0001:pm-members|メンバー定義]] で管理し、本書へ個人名や agent 名を記載しない。
- 同じ実行主体が `A` と `R` を兼ねる場合も、判断と作業の証跡を分ける。
- 担当の不一致は `PM` が調べ、原因に応じて修正先を選ぶ。合意済みの責任変更が本表に未反映なら RACI、責任配置は有効でタスクの `owner` が誤っていればタスク定義の正本（戦略・トラック定義）、正本は正しく生成結果が誤っていれば生成処理を直す。生成される登録簿ビューや Schedule は直接編集しない。
- 原因または新しい責任が未決なら、`PM` がプロジェクト登録簿に担当 Role と判断期限を付けて登録し、解決まで担当変更を前提とする作業を保留する。

## 5. 見直し条件

採用 Role code、成果物区分、Schedule の owner、主要判断、参加者、兼務の継続可能性が変わった場合に見直す。特に、実装・体験・公開運用が増えた場合は `DEV`、`UX`、`OPS` の専任化と責任分離を確認する。

見直しでは `PM` が次を行う。

1. 影響する RACI の行と、未完了タスク・依存関係・承認ゲートを特定する。
2. [[prj-0001:pm-organization|組織定義]]、[[prj-0001:pm-roles|ロール定義]]、[[prj-0001:pm-members|メンバー定義]]、Schedule の戦略・トラック定義、[[prj-0001:pm-communication-plan|コミュニケーション計画]] の追従箇所を確認し、更新ごとに担当 Role を決めて追従タスクにする。
3. 未決の責任変更はプロジェクト登録簿へ登録し、決まるまで依存する作業を進めない。
