# PJR-0122 launch trackの振り返り

## 1. メモ

### 1.1. 事実・コメント

- exec run --autoで実行した場合に、夜中に利用制限が来て止まってしまうケースがあった。
- exec run --autoがiterationのタイミングの一番時間のかかるagentに引っ張られて次が実行できない。
- bootstrap-finalizeでplanを作っているが結局planを参照しなかった。
- bootstrap-finalizeでresultに確認のチェックを入れたが、機械的なチェックになってしまった。
- prj-charterの承認でdecisionを起票したが、必要だったか？
- completeとcommit, pushと確定行為を3回もやる必要があるか？
- exec run --autoを作ったが、対話型で考えながら進めることが多かった。routineをworkflowに組み込む必要あり。
- agentが一文書単位で生成していったが、文書間で重複した記述、論点がずれた記述が多く生成された。
- exec run --autoで作った文書を最後のbootstrap-finalizeフェーズで論点をフォーカスし、重複した記述を削除する作業をagentに多数依頼した。
- レビューしても面白くない文章が多く生成された。ロジカルではあるが内容のない文章。
- 最後の段階で、ターゲットをCivicTechに絞ったら文章がよくなり始めた。
- 一方でターゲットをCivicTechに絞っても、当初は論点が矮小化されたため、プロジェクト概要の必要性を3点に明確化したら、以降はagentがいい文章を書くようになった。
- 文書間の整合性取りは人がやるより、agentに依頼したほうが早いし正確。たまに間違いや抜けがあるが人間よりは高品質。
- 1 成果物、1 taskの前提で構築したが、1 taskで複数成果物生成も必要そう。

### 1.2. 対策の方針

1. 生産性：省略できる作業は省略する
2. 品質：横断レビューで重複削除、論点を明確にする章構成
3. 自動化：1 taskで複数成果物（品質にも寄与）、autoの改善とroutine化

### 1.3. 対策案

#### 1.3.1. 生産性

- human task では原則として独立した plan を生成せず、実施内容、確認対象、done criteria、確認結果、残課題を result に集約する。複数の手順や関係者間の調整があり、着手前に進め方を合意する必要がある場合だけ plan を作成する。
- result の確認項目は一律のチェックリストにせず、成果物の done criteria と review 結果から未確認事項だけを抽出する。各項目には、確認した文書または検証結果を根拠として記録する。
- 成果物の承認は、finalize result への承認記録と成果物の `status: ready` への更新で完了とする。複数案からの選択や後続工程を拘束する判断だけを decision として登録する。
- 作業完了後の `complete`、`commit`、`push` を一つの終了操作にまとめる。通常は変更の検証、commit、complete までを一括実行し、push は track または作業単位の区切りでまとめて実行する。
- 各 phase の作業を「必須」「条件付き」「省略可」に分類し、対象ファイルに変更がない maintenance、指摘がない再レビュー、参照されない中間成果物の生成を省略できるようにする。

#### 1.3.2. 品質

- track の開始時に、対象読者、解決する課題、中核メッセージ、各成果物の役割を一枚の構成表にまとめ、すべての task と review から共通参照する。
- 成果物ごとの章構成に「この文書で答える論点」と「他文書へ委ねる論点」を明記し、同じ説明を複数文書へ重複させない。共通情報は正本となる文書を一つ決め、他文書から参照する。
- 関連性の強い成果物を一つの文書群として扱い、個別レビュー後に文書群単位の横断レビューを実施する。横断レビューでは、重複、矛盾、論点の抜け、用語の不一致、参照先の妥当性を確認する。
- 横断レビューは `bootstrap-finalize` に集中させず、文書群の初稿完成時と review 完了時に実施する。後続 task は横断レビューの指摘を入力として受け取り、同じ問題の再発を防ぐ。
- review の観点に「具体的な根拠があるか」「対象読者の判断や行動に役立つか」「一般論だけで終わっていないか」を追加する。論理構造が整っていることだけでは合格としない。
- track の開始時に、想定利用者、利用場面、解決する課題を基準としてターゲットを具体化し、対象と対象外をプロジェクト概要などの上位文書に明記する。広すぎて一般論になる場合は、共通の課題と利用場面を持つ範囲まで絞り込む。
- 絞り込んだターゲットに対して中核となる成果物を先に試作し、「内容が具体化したか」「代表的な課題を扱えているか」「重要な対象を除外していないか」を review する。具体性が不足する場合はさらに絞り、論点が矮小化した場合は必要性または対象範囲を見直してから他の成果物へ展開する。
- 下位文書の横断レビューでは、上位文書で定義したターゲット、利用場面、必要性との整合を確認し、対象読者に結び付かない一般論や、対象範囲の一部だけを扱う記述を差し戻す。

#### 1.3.3. 自動化

- schedule の task が複数の成果物 ID を `targets` として持てるようにし、同時に整合させる必要がある成果物を一つの task で生成・更新・レビューできるようにする。完了条件は対象成果物ごとに判定し、すべてを満たした場合に task を complete とする。
- `exec run --auto --parallel` をラウンド内の全 agent を待つ方式から、agent の終了ごとに次の Ready task を投入する連続 worker pool 方式へ変更する。長時間 task があっても、空いた実行枠で依存関係のない task を継続する。
- auto 実行に実行終了時刻、最大実行時間、最大 task 数を指定できるようにする。上限到達時は新規 task の claim を止め、実行中 task の状態と再開位置を保存して正常終了する。
- rate limit を検知した agent は解除見込み時刻まで候補から一時除外し、別 provider の agent または依存関係のない task に切り替える。代替がない場合は task を再開可能な状態で保留し、auto 全体は停止させない。
- 定時の `exec run --auto`、open な register 項目の確認、横断レビュー対象の抽出を routine として定義する。routine は終了時刻と最大 task 数を必須とし、夜間に無制限に実行しない。
- workflow では、定型変換、整合性検査、既知の観点によるレビューを agent task または routine に割り当て、ターゲット設定、論点の選択、最終承認は human task とする。

### 1.4. 優先して実行するTODO

1. **ターゲットと中核メッセージの確定を track の開始条件にする**
   - 想定利用者、利用場面、解決する課題、対象外、中核メッセージを記載する構成表の template を作成し、track の最初に human task で確定する。
   - 中核成果物を一つ試作してターゲットの粒度を review し、承認されるまで他の成果物を本格生成しない phase gate を schedule に追加する。
   - 完了条件は、構成表と試作成果物が作成され、具体性、代表性、対象範囲の妥当性が review result に記録されていることとする。
2. **文書群単位の横断レビューを workflow に追加する**
   - 関連成果物を文書群に分け、各文書が答える論点、正本とする情報、参照関係を構成表に定義する。
   - 文書群の初稿完成後と個別 review 完了後に、重複、矛盾、論点の抜け、用語、ターゲットとの整合を確認する横断 review task を追加する。
   - 完了条件は、指摘ごとに修正先となる正本文書が決まり、後続 task がその review result を参照していることとする。
3. **一つのtaskで複数成果物を扱えるようにする**
   - schedule、plan、result の `targets` を複数成果物に対応させ、文書群を一つの task で生成、更新、review できるよう schema とコマンドを変更する。
   - 対象成果物ごとに done criteria を保持し、すべての成果物と文書間整合の確認が完了した場合だけ task を complete にする。
   - 完了条件は、複数成果物 task の生成、実行、review、complete を一連のテストで確認できることとする。
4. **human task の plan と完了操作を簡素化する**
   - human task は原則として plan を生成せず、実施内容、確認対象、done criteria、確認結果、残課題を result に記録する仕様へ変更する。
   - 成果物の承認は result への承認記録と `status: ready` への更新で完了させ、複数案の選択などに限って decision を登録する。
   - 検証、commit、complete を一つの終了操作として実行できるようにし、完了条件は human task の開始から確定まで重複操作なしで実行できることとする。
5. **autoを長時間でも停止しにくい実行方式へ変更する**
   - `exec run --auto --parallel` を連続 worker pool 方式に変更し、agent の終了ごとに空いた枠へ次の Ready task を投入する。
   - 終了時刻、最大実行時間、最大 task 数を指定可能にし、上限到達時は再開位置を保存して正常終了する。rate limit を検知した agent は一時除外し、他の agent または task の実行を継続する。
   - 完了条件は、長時間 task、rate limit、実行上限が同時に存在しても、依存関係のない task が進行し、中断後に再開できることをテストで確認できることとする。
