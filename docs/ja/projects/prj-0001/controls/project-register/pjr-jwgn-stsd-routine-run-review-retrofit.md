# PJR-JWGN stsd-routine-run を新しい Kata に合わせる

## 1. 概要

stsd-routine-run を新しい章立てと遷移 ID 入りのラベルに合わせる

## 2. 入力

- 利用者のレビュー: 目的には、状態が対象の何を管理し、何のために使われるか（誰がその状態で何を判断するか）を書く。文書の読み手や使い方（承認する人、実装・テストへの利用）は書かない。章の名前は「目的」のままとする（2026-11-06 indie が決定）
- 利用者のレビュー: 状態の正本・判定の規則・互換の扱いは「適用範囲」ではない。「適用範囲」の後に新しい章「状態の判定」を置いてそこへ書き、「適用範囲」には対象・業務の範囲・到達点だけを残す（2026-11-06 indie が決定）
- 利用者のレビュー: スコープ（AS-IS / TO-BE）は既定を現行とし、「現行実装（AS-IS）」とは書かない。TO-BE の文書と並ぶときだけスコープを書く（2026-11-06 indie が決定）
- 利用者のレビュー: 「状態遷移図」と「遷移の説明」を 1 つの章「状態遷移」にまとめ、図を分けた場合は図ごとに、そのすぐ下へ遷移の表を置く。図の遷移のラベルにも遷移 ID を入れ、`T-<nn>` イベント / 条件 の形にする（2026-11-06 indie が決定）

## 3. 完了条件

- [[prj-0001:stsd-routine-run]] が、PJR-S8EF〜PJR-93NK で直した Kata（[[specdojo:stsd-rulebook]]・[[specdojo:stsd-mermaid-rulebook]]）の必須の章・表・図の規則を満たしている。目的は状態が何を管理し何のために使われるかを書き、文書の読み手や使い方を書いていない。状態の正本と判定の規則は「状態の判定」の章にある。
- 「現行実装（AS-IS）」などのスコープの表記を、TO-BE の文書と並ばない限り書いていない。
- 図の遷移ラベルが `T-<nn> イベント / 条件` で、分けた図ごとにすぐ下へその図の遷移の表がある。図の全遷移が、その図の下の表へ一度ずつ対応している。
- 状態と遷移の中身は、カタログの `evidence_refs` の実装で確かめられる。実装で確かめられないことは推測で埋めず、`_UNDECIDED_` か今後の検討メモで残す。
- 文書は確定前（`status: draft`）のため、PJR-FS9A で直した規則に従い、遷移 ID を図と表の順に `T-01` から欠番なく振り直している。図のラベルと遷移表で同じ ID を使い、旧 ID と新 ID の対応を個票の対応結果に書いている。
- 今後の検討メモの各項目を見直し、実装で決まったものは本文へ反映して消し、残すものは理由を個票の対応結果に書く。
- `stsd-routine-run` 以外の成果物と Kata は変えていない。Kata に直すべき点を見つけた場合は、変えずに個票の対応結果に書き、pipeline では報告の `handoff` にも書く。
- `npm run -s lint:md`・`npm run -s lint:fm`・`npm run -s lint:mermaid` が通っている。

## 5. 対応結果

### 5.1. 判断と反映内容

**部分反映**とした。既存の6状態・11遷移と判定規則は列挙された実装エビデンスに対応するが、章構成、図直下の表、遷移ラベルが新しい Kata に適合していなかったため、状態・遷移の意味を保持して構造を直した。

- [[prj-0001:stsd-routine-run|ステータス定義（定期処理の実行結果）]]: 目的を管理対象・利用者の業務判断に絞り、読み手別の利用説明と不要なスコープ表記を削除した。「状態の判定」を新設し、正本・一意判定・互換の扱い・実行機会の選択・結果集約を配置した。
- 「状態遷移」に二図と各図の直下の遷移表をまとめ、全ラベルに遷移 ID を付けた。図表順で欠番なく振り直し、本文・検討メモの参照も更新した。
- 実装で確認できた例外中断・履歴追記失敗時の記録と欠損ファイルの読み取りを本文へ移し、検討メモには未決の復旧・移行判断を残した。routine 全体の lock 取得失敗では `policy.overlap: skip` の指定によらず状態を更新しないことを明記した。
- 本個票の対応結果以外は対象 STSD だけを編集した。実装、他の成果物、Kata、成果物の `status: draft` と `based_on: []` は維持した。result は後段 reporter が記入する。

### 5.5. 検証の分担

`package.json`・`.specdojo/specdojo.config.json`・`lefthook.yml` と共通規約の適用条件を確認した。変更した2件の Markdown を Prettier で整形した。一時スクリプトで全11遷移の図表一対一対応・連番・状態表示名・到達性・旧 ID 対応と、状態遷移の意味および frontmatter の維持を確認した。履歴リンク検査、登録簿ビュー生成、カタログ検査、staged evidence の検査、差分の空白検査はすべて終了コード0で通った（staged evidence は検査対象0件）。カタログには対象外の既存参照・未作成文書について警告があるが、エラーはない。

登録簿ビュー生成は `npx tsx src/specdojo.ts register build` が sandbox の IPC 制限（`EPERM`）で起動できなかったため、共通規約の代替 `node --import tsx src/specdojo.ts register build` で成功した。生成物は追跡対象の変更に含まれない。

指定の `lint:md`・`lint:fm`・`lint:mermaid` を含む親検証は pipeline の指示に従って executor 内では重複実行せず、親 runner の結果を正とする。No.4 は親 runner の検査結果を確認してから反映する。
