# PJR-D4RJ オーケストレーターに承認を前提として git push を許す

## 1. 背景

オーケストレーターは `git push` を行わない決まりのため、commit のたびに利用者が手で push しており、そのたびに作業が止まる。利用者から、人の確認を前提に `git push` まで許してよいのではないかと提案があった（2026-11-28）。

## 2. 入力

- 利用者の提案：オーケストレーターには git push までは人の確認前提で許してよい（2026-11-28）
- CLAUDE.md とオーケストレーターの本文は git push を行わないと定めている。どちらも保護された文書

## 3. 検討した選択肢

| 選択肢 | 内容                                                                                                                                  | 利点                                                                                               | 懸念                                                                                                                   |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| A      | 今のまま `git push` を許さない                                                                                                        | 公開の操作がすべて人の手に残る                                                                     | push のたびに作業が止まり、利用者の手間が残る                                                                          |
| B      | 範囲を守る push の入口（例: `specdojo git push`）を作り、オーケストレーターにだけ毎回の承認で許す。各環境の `git push` の deny は残す | 範囲の守りが文言でなくコマンドで効き、どの環境の agent でも同じに働く。executor の守りは変わらない | コマンドの実装と、各環境の設定・指示の手直しが要る                                                                     |
| C      | 各環境で、オーケストレーターの `git push` だけを ask（毎回確認）に変える                                                              | 実装が要らない                                                                                     | 環境ごとに書き方が違い、main・force・タグの拒否を道具の側で表しにくい。executor と設定を共有する環境では穴になりやすい |
| D      | 承認なしで push を許す                                                                                                                | 待ちがなくなる                                                                                     | 誤った commit がそのまま remote に出る。人の確認の前提が外れる                                                         |

## 4. 決定内容

選択肢 B を採る（2026-11-28 に決め直した。最初は本文の文言だけで許す形を決めたが、各環境の権限の設定が push を拒んでいること、`specdojo git` が push を通す穴があることが分かったため）。

- 範囲を守る push の入口を specdojo のコマンドとして作る。`project/<id>/develop` と `feature/<project-id>/*` への普通の push だけを通し、`main`・`--force` など履歴を書き換える push・タグの push を拒む。送るブランチと commit の範囲・件数を表示する。exec の executor・reporter の実行中に呼ばれたときは拒む。
- オーケストレーターの設定では、この入口を毎回の承認（ask など）で許す。claude・codex・copilot・opencode の `git push` の deny と、executor の守りは残す。
- `npm` の公開とリリースの公開は人が行う。登録簿の同期ブランチへの push は、今どおり specdojo のコマンドに任せる。
- `CLAUDE.md`・`AGENTS.md`・`.opencode/AGENTS.md`・`.github/copilot-instructions.md`・オーケストレーターの本文の文言は、入口ができてから同じ内容にそろえる。反映までは今の決まりのまま push しない。
- `specdojo git` が `push` を止めずに通す穴は、別の issue で先に塞ぐ。
- 実装は別の todo で行い、feature ブランチ `feature/prj-0001/orchestrator-git-push`（b36caa3900）の文言の案はそこで直す。

## 5. 採択理由

- push の待ちが減り、利用者が手で push する手間がなくなる。
- 毎回の承認を残すため、人の確認の前提は変わらない。公開物（`main`・タグ・npm）と履歴を壊す操作は人の手に残る。
- 同期ブランチは specdojo のコマンドが検査してから push するため、そちらに任せたままにする。
