# PJR-D4RJ オーケストレーターに承認を前提として git push を許す

## 1. 背景

オーケストレーターは `git push` を行わない決まりのため、commit のたびに利用者が手で push しており、そのたびに作業が止まる。利用者から、人の確認を前提に `git push` まで許してよいのではないかと提案があった（2026-11-28）。

## 2. 入力

- 利用者の提案：オーケストレーターには git push までは人の確認前提で許してよい（2026-11-28）
- CLAUDE.md とオーケストレーターの本文は git push を行わないと定めている。どちらも保護された文書

## 3. 検討した選択肢

| 選択肢 | 内容                                                                                        | 利点                                             | 懸念                                                             |
| ------ | ------------------------------------------------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------------------------- |
| A      | 今のまま `git push` を許さない                                                              | 公開の操作がすべて人の手に残る                   | push のたびに作業が止まり、利用者の手間が残る                    |
| B      | `project/<id>/develop` と `feature/<project-id>/*` への普通の push だけを、毎回の承認で許す | 待ちが減る。公開物と履歴を壊す操作は人の手に残る | 承認の確認が形だけになると、意図しない commit を送るおそれがある |
| C      | 承認なしで push を許す                                                                      | 待ちがなくなる                                   | 誤った commit がそのまま remote に出る。人の確認の前提が外れる   |

## 4. 決定内容

選択肢 B を採る。オーケストレーターに、次の範囲の `git push` を、毎回の利用者の承認を前提に許す。

- 許すもの: `project/<id>/develop` と `feature/<project-id>/*` への普通の push。承認を求めるときは、push するブランチ、commit の範囲と件数を示す。
- 許さないもの: `main` への push、`--force` など履歴を書き換える push、タグの push、npm の公開。リリースの公開は人が行う。
- 登録簿の同期ブランチ（`sync/register`・`sync/exec-events`）への push は、今どおり specdojo のコマンドに任せ、`git push` を打たない。
- 反映は `CLAUDE.md` とオーケストレーターの本文（保護された文書）の書き換えで行い、feature ブランチで利用者が内容を確かめてから develop に入れる。反映するまでは今の決まりのまま push しない。

## 5. 採択理由

- push の待ちが減り、利用者が手で push する手間がなくなる。
- 毎回の承認を残すため、人の確認の前提は変わらない。公開物（`main`・タグ・npm）と履歴を壊す操作は人の手に残る。
- 同期ブランチは specdojo のコマンドが検査してから push するため、そちらに任せたままにする。
