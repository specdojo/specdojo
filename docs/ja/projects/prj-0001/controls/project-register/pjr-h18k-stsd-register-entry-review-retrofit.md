# PJR-H18K stsd-register-entry を新しい Kata に合わせる

## 1. 概要

stsd-register-entry を新しい章立てと遷移 ID 入りのラベルに合わせる

## 2. 入力

- 利用者のレビュー: 目的には、状態が対象の何を管理し、何のために使われるか（誰がその状態で何を判断するか）を書く。文書の読み手や使い方（承認する人、実装・テストへの利用）は書かない。章の名前は「目的」のままとする（2026-11-06 indie が決定）
- 利用者のレビュー: 状態の正本・判定の規則・互換の扱いは「適用範囲」ではない。「適用範囲」の後に新しい章「状態の判定」を置いてそこへ書き、「適用範囲」には対象・業務の範囲・到達点だけを残す（2026-11-06 indie が決定）
- 利用者のレビュー: スコープ（AS-IS / TO-BE）は既定を現行とし、「現行実装（AS-IS）」とは書かない。TO-BE の文書と並ぶときだけスコープを書く（2026-11-06 indie が決定）
- 利用者のレビュー: 「状態遷移図」と「遷移の説明」を 1 つの章「状態遷移」にまとめ、図を分けた場合は図ごとに、そのすぐ下へ遷移の表を置く。図の遷移のラベルにも遷移 ID を入れ、`T-<nn>` イベント / 条件 の形にする（2026-11-06 indie が決定）

## 3. 完了条件

- [[prj-0001:stsd-register-entry]] が、PJR-S8EF〜PJR-93NK で直した Kata（[[specdojo:stsd-rulebook]]・[[specdojo:stsd-mermaid-rulebook]]）の必須の章・表・図の規則を満たしている。目的は状態が何を管理し何のために使われるかを書き、文書の読み手や使い方を書いていない。状態の正本と判定の規則は「状態の判定」の章にある。
- 「現行実装（AS-IS）」などのスコープの表記を、TO-BE の文書と並ばない限り書いていない。
- 図の遷移ラベルが `T-<nn> イベント / 条件` で、分けた図ごとにすぐ下へその図の遷移の表がある。図の全遷移が、その図の下の表へ一度ずつ対応している。
- 状態と遷移の中身は、カタログの `evidence_refs` の実装で確かめられる。実装で確かめられないことは推測で埋めず、`_UNDECIDED_` か今後の検討メモで残す。
- 文書は確定前（`status: draft`）のため、PJR-FS9A で直した規則に従い、遷移 ID を図と表の順に `T-01` から欠番なく振り直している。図のラベルと遷移表で同じ ID を使い、旧 ID と新 ID の対応を個票の対応結果に書いている。
- 今後の検討メモの各項目を見直し、実装で決まったものは本文へ反映して消し、残すものは理由を個票の対応結果に書く。
- `stsd-register-entry` 以外の成果物と Kata は変えていない。Kata に直すべき点を見つけた場合は、変えずに個票の対応結果に書き、pipeline では報告の `handoff` にも書く。
- `npm run -s lint:md`・`npm run -s lint:fm`・`npm run -s lint:mermaid` が通っている。

## 5. 対応結果

判断は部分反映とした。[[prj-0001:stsd-register-entry|ステータス定義（登録項目個票）]] の 8 状態・40 遷移と既存の業務判断は保持し、新しい Kata の必須章と図表の配置へ移し替えた。

- 「目的」は登録項目の進み具合・追跡継続の必要性と、owner・権限者の行動判断に絞った。頭書きと適用範囲から不要なスコープ表記を削除し、適用範囲には対象・業務境界・到達点を残した。
- 「状態の判定」を新設し、個票の現在値・監査履歴・派生ビューの役割、欠損値の読み取り、旧 Git 履歴の event 変換を整理した。実装で確認した互換動作を本文へ反映した。
- 「状態遷移」に共通条件、type 別の審査・承認、三図と各直下の遷移表、CLI 制約、検証の判定基準を集約した。全ラベルを `T-<nn> イベント / 条件` とし、図・表・本文参照を同時に更新した。
- 成果物の `status: draft` と `based_on: []` は維持した。実装・Kata・ほかの成果物は変更せず、本個票には対応結果だけを追記した。result の記入と lifecycle 操作は reporter / runner に委ねる。

### 5.3. 検討メモの見直しと未確認範囲

- `M-01` は残した。待機理由の省略、`close` の明示終了先、`note` の着手・待機・審査、任意状態での起票、直接待機再開の理由補完、図表にない活動中の直接変更は実装で確認でき、本文の「現行制約との対応」に整理した。ただし、承認・証跡などの業務条件を強制する方針や未承認経路の採否は実装から決定できない。PO・ARC・QE が判断し、PM が後続 PJR と日程へ接続する。変更候補は CLI 制限・検証の追加、または業務仕様・受入手順の改訂であり、本タスクでは無条件に実装へ合わせない。
- `M-04` は残した。`bdd-register-entry` の実ファイルは見つからず、依存辞書との用語照合ができない。辞書作成後に BA が照合し、許可された依存関係に従って `based_on` を追加する。
- 旧状態値の別名は読み取り処理に定義されていない。旧履歴の変換・欠損値の既定は本文で定義し、未決事項とは扱わない。既存の二つの検討メモに、実装だけで解決して削除できる方針・依存課題はなかった。
- 宣言された実装パスの未読・不存在はない。列挙外の実装、register item/event schema、関連テスト、日時・event 処理の外部委譲先、exec・夜間 queue の責任境界の実装詳細は調査範囲外である。人間の承認・証跡と目的の妥当性もコードからは確認不能で、既存仕様として保持した。
- Kata 自体に修正を要する点は検出していない。整形・追加検査の結果は executor evidence に記録し、必須の `lint:md`・`lint:fm`・`lint:mermaid` を含む親検査の実行結果は runner が追記する。

### 5.4. 検証結果

Prettier 整形、登録簿 build、hook のカタログ検証、履歴リンク検証、差分の空白検査は成功した。カタログ検証には対象外の既存の re-export 参照・未作成文書などの警告があり、終了コードは 0 だった。staged の証跡検査も成功したが、対象は 0 ファイルであり、変更本文の検査済みを意味しない。

図表の個別照合では、六章の順序、Frontmatter の保持、8 状態の到達性、三図それぞれの直下の表との一対一対応、40 遷移の ID 連番・遷移元・遷移先・イベント・条件、旧図との遷移内容の同一性、CLI 対応表の全 ID 網羅を確認した。親 runner に設定された lint・テスト・schema 検査は sandbox では重複実行していない。
