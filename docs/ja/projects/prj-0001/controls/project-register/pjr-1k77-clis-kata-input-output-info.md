# PJR-1K77 CLI 仕様（clis）の入出力を、ファイルに限らない入力情報と出力情報に直す

## 1. 概要

clis の 5 章を「入力と出力の要点」にし、入力情報と出力情報に分けて、ファイル・標準入力・環境変数・対話の入力・API を種類の列で並べる。API は ifx-api を参照する

## 2. 入力

- PJR-025M（indie が決定、2026-11-08）: CLI の中から API を呼び出すこともあるため、読むファイル・作る変えるファイルではなく入力情報・出力情報とする。

## 3. 完了条件

- [[specdojo:clis-rulebook]] の本文要件の 5 章を「入力と出力の要点」にし、小節を「入力情報」と「出力情報」の 2 つにしている。標準出力の要点は出力情報にまとめている。
- 記述ガイドに、次の規則を書いている。
  - 入力情報の表は、種類（ファイル・標準入力・環境変数・対話での入力・API の応答）・対象・役割・正本の参照・ない／壊れている／届かないときの扱い、を持つ。
  - 出力情報の表は、種類（標準出力・標準エラー・作る／変えるファイル・API への送信）・対象・役割・正本の参照、を持つ。
  - 中身は書かず正本を参照する。ファイルはその rulebook か schema、API は外部 I/F の仕様（[[specdojo:ifx-api-rulebook]] に従う文書）を参照し、clis にはどのコマンドがどの API をなぜ呼ぶかと失敗時の扱いだけを書く。
  - API の失敗（つながらない・時間切れ・拒否）を含む入力情報の失敗を、終了コードとエラー表示・利用者の次の手の章の表につなげる。
  - 認証情報（API キーなど）は環境変数などの名前と用途だけを書き、値は書かない。
  - 取得と更新の両方を行う API の呼び出しは、入力情報と出力情報の両方に挙げる。
- 用語の定義・位置づけの図など、ほかの章の「読むファイル」「作るファイル」の記述も入力情報・出力情報に揃えている。
- `clis-sample` を新しい章立てにし、ファイルのほかに環境変数と API（例: 商品マスタを API から取る、売上を API へ送る）の例と、その失敗のエラーの例を載せている。
- `##` 以下の見出しにはすべて連番を付けている。
- 迷った点は executor が決め、決めた内容と理由を個票の対応結果に書いている（PJR-K4PM で人が判断する材料にする）。
- uis の型、ほかの型、カタログを変えていない。
- CHANGELOG.md は変えず、利用者に影響する変更を個票の対応結果の「CHANGELOG に書く事項」の節（番号付きの見出し）に、区分と行の文案で書いている（PJR-EPQ3）。
- `npm run lint:md`・`npm run lint:fm`・`npm run test:unit` が通っている。

### 5.4. 規則と sample の書き方で executor が決めた内容と理由（PJR-K4PM への判断材料）

1. **章立てと小節構成（標準出力の統合）**:
   - 決定: 第 5 章の見出しを「入力と出力の要点」とし、小節を「5.1. 入力情報」と「5.2. 出力情報」の 2 つにした。旧「5.2. 標準出力の表示要点」は「5.2. 出力情報」内の種類の 1 つ（`標準出力`）として統合した。
   - 理由: 完了条件「小節を『入力情報』と『出力情報』の 2 つにしている。標準出力の要点は出力情報にまとめている」に従い、CLI が受け取るものと外へ出すものの二項対立に構造を明確化するため。
2. **入力情報・出力情報の表の列定義**:
   - 決定:
     - 入力情報: `| コマンド | 種類 | 対象 | 役割 | 正本参照 | ない／壊れている／届かないときの扱い | 対応エラー事象 |`
     - 出力情報: `| コマンド | 種類 | 対象 | 役割 | 正本参照 | 備考 |`
   - 理由: 完了条件が求める必須要素（種類・対象・役割・正本の参照・ない／壊れている／届かないときの扱い）を網羅し、複数コマンドを扱う CLI 仕様として「コマンド」列および 6 章のエラー表への連携列（「対応エラー事象」）を備えることで、仕様としての実効性と一覧性を最大化するため。
3. **API 失敗時のエラーカテゴリと終了コード体系**:
   - 決定: `clis-sample` において、終了コード 3 を「外部 API・通信エラー」と定義し、API の失敗（つながらない: 接続失敗、時間切れ: タイムアウト、拒否: 403 認証拒否）を終了コード 3 に、API から 404（商品未登録）が返った場合はユーザー入力エラー（終了コード 1）に分類した。
   - 理由: ネットワーク障害やサービス停止などのインフラ要因（終了コード 3）と、ユーザーの入力コードの誤り（終了コード 1）を明確に区別し、利用者が適切な回復アクション（接続確認や再試行か、コードの再入力か）を選択できるようにするため。
4. **取得と更新を行う API の扱い**:
   - 決定: `sales complete` で実行する本部売上登録 API（`POST /api/v1/sales`）を、出力情報（売上データの送信・状態更新）と入力情報（確定受付番号 `receipt_id` の受領）の両方に明記した。
   - 理由: 完了条件「取得と更新の両方を行う API の呼び出しは、入力情報と出力情報の両方に挙げる」に合致させ、リクエストペイロード送信とレスポンス受領の双方の責務と失敗時の扱いを明示するため。
5. **認証情報の記述方針**:
   - 決定: `KINUYA_API_KEY` のように環境変数名と「本部 API 認証トークン」という用途のみを記載し、実際のトークン値やフォーマット詳細は記載しない方針を徹底した。
   - 理由: セキュリティ保護の原則および完了条件の要求を満たすため。
