# PJR-EPQ3 CHANGELOG は各項目が直接書かず、個票の申し送りからリリースでまとめる

## 1. 背景

各項目が CHANGELOG.md の未公開の節へ直接書くと、並べて流したときに統合で衝突する。各項目は個票の対応結果に「CHANGELOG に書く事項」を書き、リリースの todo が close 済みの項目から集めて CHANGELOG を書く

## 2. 入力

- 2026-11-08 に、型の手入れ 5 件などで CHANGELOG の衝突による停止が 3 回あった。
- 案 A（個票の申し送り）・案 B（断片のファイル）・案 C（今のまま）のうち、A を採る（indie が推奨どおりと決定、2026-11-08）。

## 3. 検討した選択肢

| 選択肢    | 内容                                                                                                | 利点                                                               | 懸念                                                      |
| --------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------- |
| A（採用） | 個票の対応結果に「CHANGELOG に書く事項」を書かせ、リリースの todo が close 済みの項目から集めて書く | 個票は項目ごとのファイルで衝突しない。登録簿の仕組みのままでできる | リリースまで CHANGELOG に出ない。集め漏れを防ぐ手順が要る |
| B         | 項目ごとに断片のファイル（例: `changelog.d/<PJR-ID>.md`）を置き、リリースでまとめる                 | 衝突しない。集める処理を機械にしやすい                             | 新しい置き場所とまとめる仕組みを作る必要がある            |
| C         | 今のまま、衝突したら orchestrator が解く                                                            | 変えることがない                                                   | 並べて流すほど止まる                                      |

## 4. 決定内容

案 A を採る。

- 各項目は CHANGELOG.md を変えない。利用者に影響する変更は、個票の対応結果の `### CHANGELOG に書く事項` の節に、CHANGELOG の区分（追加・変更・不具合修正など）と行の文案を書く。影響がなければ「なし」と書く。
- リリースの todo が、前のリリースの後に close した項目の個票からこの節を集め、CHANGELOG の版の節を書く。
- 未公開の節にすでに書かれた行は、そのまま残す。

## 5. 採択理由

- 個票は項目ごとの正本で、並べて流しても衝突しない。close の記録から、前のリリースの後に close した項目を引ける。
- 断片のファイル（案 B）より、新しい置き場所と仕組みを作らずに済む。

## 6. 承認

| 項目     | 内容                                                                           |
| -------- | ------------------------------------------------------------------------------ |
| 決定者   | indie                                                                          |
| 決定日   | 2026-11-08                                                                     |
| 承認方式 | commit                                                                         |
| 証跡     | この個票の close の commit（オーケストレーターとの対話で「全て推奨で」と回答） |

- 承認方式は `commit` または `PR` を記載する。`PR` の場合は証跡に PR URL と merge SHA を本文テキストで記載する。
- 不可逆・高リスク・framework schema 破壊的変更に該当する決定は `PR` 方式で承認する。

## 7. 影響範囲とフォローアップ

| 項目       | 内容                                                                                                         |
| ---------- | ------------------------------------------------------------------------------------------------------------ |
| 影響範囲   | 以後の登録簿項目の完了条件、運用メモのリリースの手順、配布するオーケストレーターの本文の「完了条件の書き方」 |
