# PJR-PJYJ CLI 仕様（clis）の型と GUI だけにした uis の型を確定する

## 1. 背景

PJR-RMMM で CLI を新しい種類 clis に分け、uis は GUI の画面仕様だけにすると決めた。PJR-VMXK で作った clis の型と、PJR-X3T8 で直した uis の型を人が確かめて確定する。確定した clis の型で、カタログの付け替え（PJR-8J47）と clis の代表の作成を進める。

## 2. 入力

- 型の確定は人が行う（PJR-RZ9Q・PJR-RMMM と同じ扱い）。

## 3. 検討した選択肢

| 選択肢                           | 内容                                                                                  | 利点                                                     | 懸念                                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 両方を確定                       | clis と uis の型をそのまま確定する                                                    | 手戻りがない                                             | clis が入力ファイルに触れず、ifx-cmd（inputs と outputs の両方を書く）と揃わない |
| uis を確定し clis を直す（採用） | uis はワイヤーフレームを含めない今の形で確定し、clis は入力ファイルの規則を足して直す | コマンドが読むファイルと、その誤りでのエラーが仕様に載る | clis の型をもう一度確定する手間がかかる                                          |

## 4. 決定内容

- uis（PJR-X3T8）は確定する。ワイヤーフレーム・レイアウトは含めない今の形とする。
- clis（PJR-VMXK）は直す。本文の「出力と生成ファイルの要点」を「入力と出力のファイルの要点」にし、コマンドが読むファイル（設定・正本・前のコマンドが作ったファイルと、ない・壊れているときの扱い）と作る・変えるファイルを分けて書く。読むファイルの中身は書かず、そのファイルの rulebook か schema を参照する。sample に読むファイルの例を足し、読むファイルの誤りのエラーを終了コードとエラーの章とつなげる。
- ワイヤーフレームとデザインのルールをどこで定めるかは、question として別に起票して後で決める。

## 5. 採択理由

- SpecDojo のコマンドの多くはファイルを読んでから動くため、読むファイルが仕様にないと、利用者は何を用意すれば動くか、どのファイルの誤りでエラーになったかが分からない（indie の指摘、2026-11-08）。
- 確定した ifx-cmd の型は、渡すファイルと作るファイルの両方を書く。
- uis はワイヤーフレームを含めない形で、業務仕様の画面ごとの要求として足りる。
