# PJR-1D1X CLI 仕様（clis）の図を単純にし、自システムの API と外部コマンドの参照先を足す

## 1. 概要

clis の位置づけの図を入力情報・出力情報の仕様への線だけにし、入力と出力の規則に自システムの API と CLI が起動する外部コマンドの参照先を足す

## 2. 入力

- PJR-K4PM（indie が決定、2026-11-08）: 図に ifx-cmd を参照先として結ぶと、clis と ifx-cmd が別物であることがかえって分かりにくくなるため、図は入力情報・出力情報の仕様への線だけにする。

## 3. 完了条件

- [[specdojo:clis-rulebook]] の「成果物としての位置づけ」の図を、次の 4 つの箱と 3 本の線だけにしている。ifx-cmd・ファイル・ifx-api の個別の箱は図から外している。
  - sf → clis
  - clis → コマンドリファレンス（構文・引数の正本参照）
  - clis → 入力情報の仕様（中身の正本参照）
  - clis → 出力情報の仕様（中身の正本参照）
- clis と ifx-cmd の違いを、全体方針と役割分担の文で示している（clis は利用者がシステムを操作する側、ifx-cmd はシステムが外部を呼ぶ側）。
- 入力と出力の要点の記述ガイドに、参照する正本を種類ごとに書いている。
  - ファイル: その rulebook か schema
  - 外部システムの API: [[specdojo:ifx-api-rulebook]] に従う文書
  - 自システムの API: システム設計の索引（[[specdojo:sysd-index-rulebook]] に従う文書）が案内する内部 API の定義。まだない段階では API の名前と用途だけを書く
  - CLI が起動する外部コマンド: [[specdojo:ifx-cmd-rulebook]] に従う文書。渡すものは出力情報、受け取る結果は入力情報に挙げる
- 入力情報・出力情報の「種類」の値に、自システムの API と外部コマンドの起動を足している。種類の名前は executor が決め、理由を個票の対応結果に書いている。
- `clis-sample` に、外部コマンドを起動する例（例: レシートを印刷するコマンドを起動する）を入力情報と出力情報に足し、その失敗のエラーを終了コードとエラーの章の表に足している。
- `##` 以下の見出しにはすべて連番を付けている。
- 迷った点は executor が決め、決めた内容と理由を個票の対応結果に書いている（PJR-25B9 で人が判断する材料にする）。
- uis・ifx-cmd・ifx-api の型と、カタログを変えていない。
- CHANGELOG.md は変えず、利用者に影響する変更を個票の対応結果の「CHANGELOG に書く事項」の節（番号付きの見出し）に、区分と行の文案で書いている（PJR-EPQ3）。
- `npm run lint:md`・`npm run lint:fm`・`npm run lint:mermaid`・`npm run test:unit` が通っている。

   - 1 章（全体方針）および 2.1 節（成果物としての位置づけ）において、clis と `ifx-cmd` の違い・役割分担（clis は利用者がシステムを操作する側、`ifx-cmd` はシステムが外部を呼ぶ側）を明文化した。

### 5.3. スキーマ（schema）変更の要否と理由

- **スキーマ変更なし**: CLI 仕様（clis）は Markdown 形式（`target_format: markdown`）の成果物であり、専用の YAML スキーマを持たない。共通メタ情報スキーマ（`type: ui`）および `rulebook-frontmatter.schema.yaml` に適合しており、スキーマの変更は不要である。

### 5.4. 規則と sample の書き方で executor が決めた内容と理由（PJR-25B9 への判断材料）

1. **成果物位置づけの図における箱と線の構成**:
   - 決定: ノードを `SF`（システム化機能）、`CLIS`（CLI仕様）、`CMDREF`（コマンドリファレンス）、`IOSPEC`（入力情報・出力情報の仕様）の 4 つとし、エッジを `SF --> CLIS`、`CLIS -.-> CMDREF`、`CLIS -.-> IOSPEC` の 3 本とした。
   - 理由: 個票の完了条件「次の 4 つの箱と 3 本の線だけにしている」および先行決定 [[prj-0001:pjr-k4pm-clis-kata-confirm-input-output-info]]（「clis → 入力情報の仕様・出力情報の仕様（中身の正本参照）だけにする」）に合致させるため。「入力情報の仕様」と「出力情報の仕様」を別個の箱に分離すると 5 箱 4 線となり完了条件の指定に反するため、中身の正本参照先として 1 つの箱に集約した。
2. **入出力情報の「種類」の命名と理由**:
   - 決定:
     - 入力情報: `自システム API の応答`, `外部コマンドの実行結果`
     - 出力情報: `自システム API への送信`, `外部コマンドの起動`
   - 理由:
     - 自システム API: 外部 API（`ifx-api`）と明確に区別し、システム設計索引（`sysd-index`）配下の内部 API 定義であることを示すため、`自システム API の応答`（データ受領）および `自システム API への送信`（リクエスト送信）とした。
     - 外部コマンド: コマンド起動時に対象プロセスを呼び出して入力データや引数を渡す行為を外への送り出しとして `外部コマンドの起動` とし、プロセス終了時のステータスコードや出力を受け取る行為を受け取りとして `外部コマンドの実行結果` とすることで、因果関係とデータフローの役割を明確に表現した。
3. **`clis-sample` における外部コマンド起動の具体例選定**:
   - 決定: 店舗会計完了コマンド `sales complete` において、レシートプリンタ制御コマンド `receipt-print` を起動し、レシートテキストを渡して印字結果ステータスを受け取るシナリオを採用した。
   - 理由: 会計確定時の現実的な運用要件に合致し、ファイルの出力（テキスト生成）から外部コマンドへの引き渡し（プロセス起動）、および結果判定（印字成否・接続エラー回復）の連携契約が最も明確に例示できるため。
