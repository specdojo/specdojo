# PJR-DZMV 復元した内容の確認状態を成果物に持たせる方法を検討する

## 1. 概要

復元した仕様の根拠、確認の状態、誰がいつ確かめたかを成果物にどう持たせるかの案を比べ、推奨を出す

## 2. 入力

- PJR-Y5RD の決定（2026-11-23）: kata による理解の負債の解消で、シビックテックを持続可能にすることを中核の位置づけにする

## 3. 完了条件

- 復元した内容の確認状態を、成果物に持たせる方法を検討する（PJR-Y5RD）。少なくとも、根拠（コードの場所・記録・聞き取り）、確認の状態（推測・根拠で確認・当事者が確定）、誰がいつ確かめたかを、文書のどこにどう書くかの案を出す。今の目印（`_ASSUMPTION_`・`_UNDECIDED_`・`_CONTEXT_`）、frontmatter、登録簿の decision のどれで持つかを比べる。
- 案ごとに、書く手間（Sustainable Participation）、grade や検査で機械的に確かめられるか、復元した仕様の更新のしやすさを表で比べ、推奨を書く。採るかどうかは利用者が決める。
- この項目では実装しない。実装が要る場合は、案を個票の対応結果に書く。
- `CHANGELOG.md` は変えない。個票の対応結果に「CHANGELOG に書く事項」の小節を作り、区分と行の文案を書く。影響がなければ「なし」と書く。
- 迷った点は executor が決め、決めた内容と理由を個票の対応結果と報告の `handoff` に書く。
- 保護された設定（`.specdojo/`・`.agents/`・`.claude/`・`.codex/`・`.opencode/`・`package.json` など）は変えない。
- `npm run lint:md`・`npm run lint:fm` を通し、親の検証を通す。

## 5. 対応結果

### 5.1. 検討の前提

本節を検討成果とする。以下は利用者が採否を決めるための提案であり、現行標準への追加や実装、方式の採択は行っていない。

- [[prj-0001:pjr-y5rd-civic-tech-comprehension-debt|PJR-Y5RD]] の「復元・確認状態・人の確定・記録」を対象とする。[[prj-0001:prj-overview|プロジェクト概要]] の Sustainable Participation に従い、初回の記入だけでなく、参加者交代後の更新負担も比較する。手間の評価は設計上の相対評価であり、実測値ではない。
- [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] の目印は、`_ASSUMPTION_` が仮説、`_UNDECIDED_` が意思決定待ち、`_CONTEXT_` が下書きへの指示を示す。`_CONTEXT_` は反映後に削除して result に残すため、恒久的な確認記録には使えない。目印がないことも確認済みの証明にはならない。
- 現行の成果物 frontmatter は文書単位の `status` と `based_on` などを持つが、内容単位の確認状態・確認者・確認日は定義していない。`based_on` は直接の根拠文書への参照であり、検証や当事者の確定を意味しない。`deliverable-frontmatter.schema.yaml` は `unevaluatedProperties: false` のため、独自の確認フィールドをそのまま追加する案は使えない。
- [[specdojo:ryu-guide|実践の進め方ガイド]] の `retrofit` と同様に、実装は現在動作の根拠、既存仕様・決定記録は意図された仕様の根拠として分ける。動作が分かっても「なぜそうするか」まで確定したとは扱わない。

### 5.2. 記録場所の比較

すべての案で、対象の範囲、根拠、確認状態、確認者、確認日を記録する。表の機械検査は、現行で可能なことと、追加実装後に可能になることを分けて記載した。

| 案                                       | 文書のどこにどう書くか                                                                                                                                                                                     | 書く手間・継続負担（Sustainable Participation）                                                                      | grade・機械検査                                                                                                                                    | 復元した仕様の更新                                                                                |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| A: 既存の目印と自由記述                  | 対象段落の先頭に `_ASSUMPTION_:`、判断待ちに `_UNDECIDED_:` を置く。根拠・確認者・日付を同じ段落の通常文に書く。確認後は目印を外し、「根拠で確認」「当事者が確定」を通常文で残す。`_CONTEXT_` は指示に限る | 初回は小。統一した列がなく、確認済み情報の探索や記入漏れの点検に手間がかかる                                         | 現行 lint は `_CONTEXT_` の残存などを扱える。grade は記述と根拠を照合できるが、目印の有無だけで三つの確認状態を判定できない                        | 本文と一緒に直しやすい。一方、目印の削除時に過去の根拠や確認記録を落としやすい                    |
| B: frontmatter に集約                    | `specdojo:` 配下に確認記録の配列を新設する案。要素に本文の対象 ID、根拠の参照・版、状態、確認者、確認日時を持たせる。文書全体の単一状態にはしない                                                          | 初回は中〜大。非技術参加者にも YAML の記入が必要。本文と離れ、二か所を更新する負担がある                             | schema 拡張後は列挙値・必須値・日時形式を検査しやすい。本文との対応検査も別途必要。現行 schema では未対応                                          | 要素単位で差分を追えるが、本文 ID の変更や削除との同期が必要                                      |
| C: 登録簿の decision に集約              | 確認対象ごとに decision を作り、決定内容に対象と状態、採択理由に根拠、承認に人・日付・証跡を書く。成果物の該当箇所から個票へリンクする                                                                     | 大。小さな動作確認まで起票・承認すると参加負荷が高い。重要な判断の履歴には向く                                       | 現行の登録簿検査は個票・イベントの整合を扱うが、仕様の真偽までは扱わない。推測や動作観察は decision の採択と意味が異なるため、状態の代用にできない | 判断の履歴は残るが、現在の仕様を読むたびに別文書をたどる。本文変更との対応が古くなりやすい        |
| D: 本文の確認表＋必要な decision（推奨） | 対象を含む節の末尾に小さな「復元内容の確認」表を置く。現在の確認状態はその表を正本とし、判断が要る事項だけ既存の目印・登録簿につなぐ                                                                       | 中。根拠と確認状況を本文と一緒に読める。同じ根拠・状態・確認者・日付の範囲はまとめ、状態が分かれるときだけ行を分ける | 現行 grade では根拠との対応を読む。追加の本文検査で列・状態・条件付き必須値・対象参照を検査できる。現行 lint に専用検査はない                      | 仕様を直す節で確認表も更新できる。decision は判断の経緯だけを持ち、現在状態の二重管理を避けられる |

D を推奨する。A の手軽さを保ちつつ確認済み情報を残せ、B の本文との距離と C の全件起票の負担を抑えられるためである。最初は復元対象の Markdown に限定して試し、すべての既存成果物への一括移行は求めない。YAML・JSON の成果物は形式別の schema との整合が要るため、試行後の拡張とする。

### 5.3. 推奨案の記録単位と状態

記録単位は文書全体ではなく、独立して確認できる仕様項目・主張とする。既存の要件 ID や規則 ID があれば使い、なければ節と対象文を特定する短い引用で範囲を示す。行番号だけには依存しない。現在動作と意図・理由は別の行にし、同じ段落内でも確かめられた範囲を広げない。

| 記録項目         | 提案する記入内容                                                                                                                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 対象             | 本文内の ID または節・対象文、および現在動作／意図・理由の別。仕様本文そのものは表に重複転記しない                                                                                                      |
| 根拠             | コードはリポジトリ・commit または固定版・パス・シンボル／行範囲、記録は文書 ID または保存先・版／日付・該当箇所、聞き取りは記録の参照・実施日・発言者と対象業務での立場。対象の何を裏付けるかも短く書く |
| 確認状態         | 下表の値。情報がないことを確認済みと解釈しない                                                                                                                                                          |
| 確認者・確認日   | 実際に照合した人の識別名または agent の識別名と確認日（`YYYY-MM-DD`）。当事者の確定では人と立場を示す。根拠の作成日・聞き取り日と、照合した日を区別する                                                 |
| 次の確認・追跡先 | 推測や再確認待ちでは、不足する根拠、次にすること、担当を記入する。確認済みなら「なし」を許容し、判断待ちなら登録簿への参照を置く                                                                        |

| 確認状態     | その状態にできる条件                                                                                                             | 更新する主体                                               |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 推測         | 根拠が不足している、または根拠が主張の一部しか支えない。確認者・確認日は「未実施」とし、次の確認欄に記録者と記録日を残す         | 人・agent が復元時に記録する                               |
| 根拠で確認   | 特定の版のコード・記録・聞き取り記録と主張を照合し、その範囲の一致を説明できる。聞き取り記録があるだけでは当事者の確定にならない | 人・agent が根拠と実際の確認者・日を記録する               |
| 当事者が確定 | 対象業務の当事者・経験者、または判断責任を持つ人が、復元した記述の指定範囲を明示的に確認し、同意した証跡がある                   | 人の明示判断に基づく。agent による転記は可、代理判断は不可 |
| 再確認待ち   | 以前の確認後に対象の意味・根拠の版が変わった、根拠にアクセスできない、または相反する根拠が見つかった                             | 変更を見つけた人・agent が理由・担当・次の確認を記録する   |

「再確認待ち」は古い確認を現在有効と誤読させないための追加案である。確認者・確認日は前回分と明記して残し、新たな照合後に適切な状態へ戻す。直接当事者が確定できた場合に、形式だけの中間状態の記録は求めない。

文書の `status: ready`、grade の `pass`、登録簿の `decided` を、個々の復元内容の確認状態へ自動変換しない。文書の成熟度・品質評価・意思決定と、主張の確認範囲は別に扱う。根拠間の矛盾も、コードや新しい記録を機械的に優先して消さず、現在動作と意図の差として残す。

### 5.4. 記入と更新の例

以下はすべて架空の本文・根拠・人物による記入例であり、実際の確認証跡ではない。対象の節の末尾にこの形の表を置く案とする。

| 対象                                   | 根拠                                                                                                                        | 確認状態     | 確認者・確認日               | 次の確認・追跡先                                                                              |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------ | ---------------------------- | --------------------------------------------------------------------------------------------- |
| BR-01 の上限計算（現在動作）           | 架空 repo `example/fees` の固定版 `v1.2.0`、`src/fee.ts` の `capFee` と `tests/fee.test.ts`。上限の分岐と期待値が本文に一致 | 根拠で確認   | `restore-agent`・2026-11-25  | なし                                                                                          |
| BR-01 の上限を設けた理由（意図・理由） | 設計時の記録が見つからず、現在動作から理由を推定した                                                                        | 推測         | 未実施                       | 記録者 `restore-agent`・2026-11-25。担当 `DEV` が設計時の記録を探し、元担当者に理由を確認する |
| BR-02 の受付対象（意図）               | 架空の保存記録 `interview-20261124.md` の「受付対象」。受付担当の佐藤が本文 BR-02 に同意した発言を記録                      | 当事者が確定 | 佐藤（受付担当）・2026-11-24 | なし                                                                                          |

コードを直して BR-01 の上限の意味が変わったら、本文の変更と同じ差分で該当行を「再確認待ち」にし、前回の確認者・日付、変わった点と担当を残す。新しい版の根拠で照合し直してから状態を戻す。誤字修正など意味と根拠が変わらない変更は再確認を求めない。対象の分割・削除時も、表の対象を同じ差分で追従させ、過去の経緯は Git 履歴からたどる。

当事者が見つからなくても、未確認の意図・理由は推測のまま引き継げるようにし、担当と次の確認を残す。根拠で確認できた範囲はその状態を維持する。業務方針の選択やリスク受容が必要なら、`_UNDECIDED_` と登録簿へつなぎ、人が決める。decision には選択肢・採択理由・人の承認を残し、確認表からその証跡を参照する。動作観察や聞き取り一件ごとの decision は求めない。

### 5.5. grade・検査の役割

採用後の検査追加案では、次の二つを分ける。

- 機械検査: 確認表の列、状態値、対象 ID と確認範囲の組の重複・参照漏れ、日付形式、状態に応じた根拠・確認者・次の確認の記入を検査する。「当事者が確定」に人・立場・同意証跡の参照があることも形式として確認する。復元対象の指定範囲と表を照合し、表のない箇所を確認済みとは数えない。ID がなく引用で対象を示す場合の範囲照合と、外部リポジトリやアクセス制限のある記録の照合は grade と人に委ねる。
- grade と人の確認: 根拠が対象の主張を支えるか、現在動作から意図を推測していないか、当事者の同意がその範囲に及ぶかを読む。形式検査の成功や grade の判定は、根拠の真偽や本人同意の証明を代替しない。

現行の lint・grade に、上記の専用検査や新たな状態遷移機能が既にあるとは扱わない。本項目では比較文書だけを変更し、検査の実装と grade の観点追加は後続案にとどめた。

### 5.6. 判断理由と申し送り

- executor の判断: 比較と推奨をこの個票に集約した。検討だけのタスクで別の標準文書を作ると採択済みの規則と混同し、正本も増えるためである。
- executor の判断: 文書単位の状態では確認済みの範囲を表せないため、内容単位の本文表を推奨した。未確認の理由と現在動作を分け、「再確認待ち」を追加する案にしたのは、更新前の確定を無条件に引き継がないためである。人の確認が得られない部分も可視化して引き継ぎ、全件の当事者確定を日常の記録更新の前提にはしない。
- 次の判断: 利用者が D の採否、内容単位の粒度と再確認待ちの扱いを決める。本項目に採択や実装の承認証跡はない。
- 採用する場合の後続案: OpenFisca-Japan の復元対象から、小さな動作仕様と理由が分からない主張を選び、記入時間、変更時の追従漏れ、引き継いだ人が根拠と確認範囲をたどれるかを試す。負担を確認してから、[[specdojo:document-metadata-standard|ドキュメントメタ情報標準]]、関連 kata の rulebook・recipe・sample、`retrofit` と finalize の手順、本文検査・grade 観点を整合させる todo を起票する。B に切り替える場合のみ schema と表示・検査の拡張も必要となる。
- 検証: 対象 Markdown を Prettier で整形し、履歴リンク検査、カタログ検査、登録簿の生成検査、差分の空白検査を通した。カタログ検査は変更対象外の実装参照や未作成文書について警告を出したが、終了コードは 0。`npm run lint:md`・`npm run lint:fm` を含む親検証の最終結果は runner が記録する。

### 5.7. CHANGELOG に書く事項

なし。方式の比較と推奨のみで、利用者向けの規約・機能・既存成果物の運用は変更していない。
