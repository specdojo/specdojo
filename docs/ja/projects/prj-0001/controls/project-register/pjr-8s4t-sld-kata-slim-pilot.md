# PJR-8S4T sld の rulebook と sample から文書の運用の記述を外し、共通の正本への参照にする（試行）

## 1. 概要

業務仕様までの sample の冗長さを減らす試行として、sld 1 件で運用の記述を共通の正本へ寄せ、同じ判断の言い直しを除く。効果を確かめてから他の rulebook と sample へ広げる

## 2. 入力

- PJR-0T83 の対応策 (2)・(4) の試行である。利用者が 2026-11-17 に、sld 1 件で試してから他の rulebook と sample へ広げる進め方（案 C から B）を選んだ
- orchestrator の調査（2026-11-17）: sld-sample は 40KB（空白を除いて約 10,000 字）で業務仕様までの sample で最も大きい。運用・検証の章が全体の約 28% を占める。保管場所ごとの削除の条件を、保管場所一覧の表・3 区分の判断・場面別の対処・検証手順の 4 か所で書き、CDSD・STSD・CLIS との対応も 1.1 節と 4.1 節に二重にある。冒頭に役割の段落、検証の表に prettier・lint:md の行、末尾に PO の承認と agent の draft 維持の段落がある。表のセルは 1 行 700 字前後ある
- sld-rulebook（24KB）は、BA・ARC・DEV・QE・PM・OPS・PO の役割の表と status・承認の手順を持ち、「関連仕様・実装配置との対応と検証」を必須の章、「確認事項と変更影響」を条件付きの章として求める。status・承認・改訂と廃止の正本はドキュメントメタ情報標準にある

## 3. 完了条件

- sld-rulebook の章の求め方を見直す。文書の品質の検査（prettier・lint など）を業務の検証に入れない。未決事項は論点と影響を書き、管理台帳の区分・担当・判断時期の列は求めない（追跡は登録簿で行う）。必須と条件付きの章を変える場合は理由を個票の対応結果に書く。

## 5. 対応結果

### 5.1. 実施内容

- sld-rulebook: 冒頭の役割の段落、「対象者と確認する内容」の役割の表、全体方針の「確定とライフサイクル」、「未決事項・変更管理・公開判断の要件」の公開承認、Frontmatter 項目の `status: draft` 指定を外した。代わりに全体方針へ「共通の運用」を 1 項目置き、役割は適用先のメンバー定義、`status` の昇格と承認・改訂と廃止・未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] を参照する形にした。保管・共有・寿命・削除可否・復旧の基準（標準6列、区分、場面別の対処、隣接仕様との対応）は残した。
- sld-rulebook の章の求め方: 受入確認から QE の文書品質（prettier・lint）の観点を外し、配置と技術制約の一致・記録と状態の網羅・削除と復旧判断の実効性の 3 観点にした。「確認事項と変更影響」は論点と影響（当面の扱い）だけを求め、管理台帳の区分・担当・判断時期の列は求めない（追跡は登録簿）。削除前の条件は「保管場所一覧」を正とし他章で言い直さないこと、隣接仕様との分担と対応を 1 つの表にまとめること、セルは要点にして手順を場面別の表へ寄せることを本文要件に書いた。禁止事項は共通の行（sample へのリンク、章番号だけの参照、表の空行・メタ説明、agent の `ready` 昇格）を外し、sld 固有の 2 行（削除条件の言い直し、文書の整形・lint を業務の受入確認に含めること）を足した。
- sld-sample: 役割の段落、末尾の承認と agent の段落、検証の表の文書品質の行、管理台帳の区分・担当・追跡先候補の列、PM の登録の段落を外した。3 区分の表の「該当する保管場所」の列（一覧の言い直し）を外して区分ごとの扱いの箇条にした。1.1 節と 4.1 節の CDSD・STSD・CLIS などとの対応を 4.1 節の 1 表にまとめ、4.1 節の「整合確認のポイント」は 4.2 節の検証と重なるため、固有の確認（紙の正本の二か所の欠落なし、受入不可品・撤去品の混在なし）を 4.2 節の網羅の行へ移した。一覧のセルは要点にし、手順は場面別の表に寄せた。
- recipe・template: sld は `recipe: not-needed`・`template: not-needed` で、カタログ template（`dct-data-model-sld-template.yaml`）には運用の記述がないため変更なし。
- 共通の正本への追記: 不要と判断した。ドキュメントメタ情報標準の「成果物の値制約」（`ready` への昇格は人だけが行う）と「文書の改訂・廃止とライフサイクル変更管理」（PO の承認、Role code ごとの責務、未決事項の登録簿への引き継ぎ）で、sld-rulebook から外した記述を賄える。

### 5.2. 章の求め方の変更と理由

- 必須・条件付きの区分は変えていない。章名も変えていない（`sld-specdojo.md` など既存の成果物との対応を保つため）。
- rulebook の第 2 章を「位置づけと用語定義」から「位置づけ」に変え、用語の表を外した。表の 5 語は「保管場所一覧の標準列」の列定義の言い直しで、rulebook 作成標準の「重複になる場合は用語定義を省略する」に当たるため。
- 「概要」の要件から想定読者の `Role code` を外し、「誰がどの判断に使うか」とした。役割の割り当てはメンバー定義が正本のため。隣接仕様との分担は「関連仕様・実装配置との対応と検証」にまとめ、概要で再掲しないこととした（sample の 1.1 節と 4.1 節の二重を防ぐため）。
- 「確認事項と変更影響」を条件付きのままにした理由を rulebook に 1 文で書いた（未決事項も変更予定もない領域で空の章を作らせないため）。

### 5.3. 結論の変更

- 保管場所、置くもの、削除可否、復旧の経路と連絡先は変えていない。
- 外した運用の結論: 公開・`ready` 昇格の前に PO が顧客情報の施錠保管と未決事項の扱いを承認する段落を外した（共通の運用で賄う）。照合・回復契約と日次集計の再生成手順が整うまで、それらに依存する運用を始めない点は「確認事項と変更影響」の本部との契約の行に残した。
- 表現を寄せた箇所: 仮メモの「未転記は翌日へ持ち越す」は 3.1 節の「満たせなければ残して持ち越す」へ、販売記録の控えの「容量不足でも消さず DEV・PO へ相談」は場面別の容量不足の行（`tmp/` と条件を満たした `receipts/` だけを消す、DEV・PO が容量確保）へ寄せた。設定ファイル消失時の「PO の確認まで再開しない」は場面別の行に残した。

### 5.4. 大きさ

測り方は空白（改行を含む）を除いた文字数。表の区切り行（`| --- |`）は除く（調査時の約 10,000 字に合う数え方）。括弧内は区切り行を含む文字数とバイト数。

### 5.5. 他の型へ広げるときの一覧

外す記述:

- 役割の表と役割の段落（Role ごとの作成・確認の責務、業務呼称と `Role code` の対応）。
- `status` の `draft` 維持・`ready` 昇格・PO の承認・agent の禁止、公開の承認条件、改訂と廃止の手順。
- 文書品質の検査（prettier・lint・見出しの末尾ピリオド・wikilink の解決）を業務の検証の表や受入条件に入れること。
- 未決事項の表の管理台帳の区分・担当・判断時期・追跡先候補の列と、PM が台帳へ登録する旨の段落。
- 本文要件の列定義を言い直すだけの用語の表。
- 禁止事項のうち共通規約と同じ行（sample へのリンク、章番号だけの参照、表の空行やメタ説明だけのサンプル、agent の `ready` 昇格）。
- sample 内の同じ判断の言い直し（同じ条件を一覧・区分の表・場面別・検証で繰り返す、同じ隣接仕様の対応を 2 か所に書く）。

残す記述:

- その型固有の判断基準と区分（sld なら保管・共有・寿命・削除可否・復旧）、標準列と章の受入条件、良い例・悪い例、型固有の禁止事項。
- 業務の受入確認の手順と合格条件（実行・照合・模擬で確かめる行）。
- 未決事項の論点と影響（当面の扱い、決まったときに直す行）。
- 判断に要る背景・制約・例外（`_ASSUMPTION_`・`_UNDECIDED_` の根拠を含む）。

参照の形:

- rulebook の全体方針に「共通の運用」を 1 項目だけ置き、役割は「適用先のメンバー定義」、`status`・承認・改訂と廃止・未決事項の引き継ぎは `[[specdojo:document-metadata-standard|ドキュメントメタ情報標準]]` を参照する。文書の整形・lint はリポジトリの検証で扱うと 1 文で書く。
- sample には共通の運用の参照文も書かない（rulebook が担う）。
