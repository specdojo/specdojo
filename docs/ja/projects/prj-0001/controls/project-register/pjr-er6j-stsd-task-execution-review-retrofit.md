# PJR-ER6J stsd-task-execution をレビューの指摘と新しい Kata に合わせる

## 1. 概要

stsd-task-execution を新しい Kata に合わせ、目的・着手と再開・完了の条件・検討メモをレビューの決定どおりに直す

## 2. 入力

- 利用者のレビュー: 目的には、状態が対象の何を管理し、何のために使われるか（誰がその状態で何を判断するか）を書く。文書の読み手や使い方（承認する人、実装・テストへの利用）は書かない。章の名前は「目的」のままとする（2026-11-06 indie が決定）
- 利用者のレビュー: 状態の正本・判定の規則・互換の扱いは「適用範囲」ではない。「適用範囲」の後に新しい章「状態の判定」を置いてそこへ書き、「適用範囲」には対象・業務の範囲・到達点だけを残す（2026-11-06 indie が決定）
- 利用者のレビュー: スコープ（AS-IS / TO-BE）は既定を現行とし、「現行実装（AS-IS）」とは書かない。TO-BE の文書と並ぶときだけスコープを書く（2026-11-06 indie が決定）
- 利用者のレビュー: 「状態遷移図」と「遷移の説明」を 1 つの章「状態遷移」にまとめ、図を分けた場合は図ごとに、そのすぐ下へ遷移の表を置く。図の遷移のラベルにも遷移 ID を入れ、`T-<nn>` イベント / 条件 の形にする（2026-11-06 indie が決定）
- 利用者のレビュー: 着手と再開は、agent が違えば別のロールや別のアクターになるため、ロールやアクターを照合しない実装を正とする。完了は、自動の実行では runner が検証と統合の成功後にだけ complete を記録するため、実装を正とする。bdd-exec-state・bdd-exec-event はこれから作るため、未作成のまま確定してよい（2026-11-06 indie が決定）

## 3. 完了条件

- [[prj-0001:stsd-task-execution]] が、PJR-S8EF〜PJR-93NK で直した Kata（[[specdojo:stsd-rulebook]]・[[specdojo:stsd-mermaid-rulebook]]）の必須の章・表・図の規則を満たしている。目的は状態が何を管理し何のために使われるかを書き、文書の読み手や使い方を書いていない。状態の正本と判定の規則は「状態の判定」の章にある。
- 「現行実装（AS-IS）」などのスコープの表記を、TO-BE の文書と並ばない限り書いていない。
- 図の遷移ラベルが `T-<nn> イベント / 条件` で、分けた図ごとにすぐ下へその図の遷移の表がある。図の全遷移が、その図の下の表へ一度ずつ対応している。
- 状態と遷移の中身は、カタログの `evidence_refs` の実装で確かめられる。実装で確かめられないことは推測で埋めず、`_UNDECIDED_` か今後の検討メモで残す。
- 目的が、入力の決定に沿い、タスク実行の状態がスケジュール帳票のタスクの段階（着手前・実行中・中断中・完了・中止）を管理し、人と AI Agent が次に着手できるタスクの選択、止まった作業の引き継ぎ、後続へ進めるかの判断に使う、という内容になっている。
- 適用範囲の対象をスケジュール帳票のタスクに絞るか、プロジェクト登録簿の項目の状態は [[stsd-register-entry]] の側で扱うと 1 文で書いている（`exec run --register` の状態は登録簿の遷移で追うため）。
- 着手（今の `T-03`）の条件が、ロールが違っても着手できる実装に合っている。再開（今の `T-05`）の条件が、中断したアクターと別のアクターでも再開できる実装に合っている。
- 完了（今の `T-08`）の条件が「担当アクターが完了を報告する」で、補足に、自動の実行では runner が executor の成功・result の確認・親の検証と統合の成功の後にだけ記録し、失敗時は中断になると書いている。
- 今後の検討メモの 4 件（bdd の未作成、ロールの一致、再開のアクター、完了の条件）を消し、未決が残らないため章も消している。根拠の `based_on`（`bdd-exec-state`・`bdd-exec-event`）は未作成のまま残している。
- 文書は確定前（`status: draft`）のため、PJR-FS9A で直した規則に従い、遷移 ID を図と表の順に `T-01` から欠番なく振り直している。図のラベルと遷移表で同じ ID を使い、旧 ID と新 ID の対応を個票の対応結果に書いている。
- `stsd-task-execution` 以外の成果物と Kata は変えていない。Kata に直すべき点を見つけた場合は、変えずに個票の対応結果に書き、pipeline では報告の `handoff` にも書く。
- `npm run -s lint:md`・`npm run -s lint:fm`・`npm run -s lint:mermaid` が通っている。

## 5. 対応結果

### 5.1. 判断と反映内容

判断は「部分反映」。既存の 6 状態・16 遷移は有効であり、状態一覧、依存判定、着手解放、差し戻し、中止、旧イベントの互換規則を維持して、新しい Kata と 2026-11-06 の利用者の決定を反映した。

変更対象は [[prj-0001:stsd-task-execution|ステータス定義（タスク実行）]] と本個票の対応結果のみ。

- 目的を、タスクの段階の管理と、人・AI Agent による次のタスクの選択、引き継ぎ、後続へ進めるかの判断へ変更した。
- 適用範囲をスケジュール帳票のタスクに絞り、正本・判定規則・互換の扱いを「状態の判定」へ移した。スコープ表記を削除した。
- 状態遷移を一章へ統合し、通常系・例外系の図と直下の表を一組ずつ配置した。全矢印へ遷移 ID を付け、図と表の順に欠番なく振り直した。
- 着手のロール一致を必須条件から外した。実装に残る、双方のロール指定時の照合と不一致の明示的な許可は補足に記した。再開は中断したアクターとの一致を不要とした。
- 完了条件を「担当アクターが完了を報告する」に変更し、人間による強制操作の例外を維持した。自動実行での runner の成功確認と失敗時の中断は利用者の決定に基づく補足とし、完了状態の意味も報告された事実に合わせた。
- 解決した検討メモ 4 件と章を削除した。未作成の `bdd-exec-state`・`bdd-exec-event` を指す `based_on` と `status: draft` は維持した。

### 5.2. 実装との照合

列挙された実装エビデンスは両方とも全体を参照した。

| 参照パス             | 確認できた現在動作                                                                                                                                                                                                                             | 照合結果                                                               |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `src/exec/types.ts`  | `ExecState` は `todo`・`doing`・`blocked`・`done`・`cancelled`。`ExecEventType` は状態変更と補足記録の 10 種類で、`ready` は基本状態に含まれない                                                                                               | 状態一覧と一致                                                         |
| `src/exec/events.ts` | イベントの形式を検査して時刻順・同時刻の成立順に再生する。イベントなしは `todo`、補足記録は状態を変えない。先行タスクの `done` とマイルストーン・ゲートの依存充足から `ready` を導出する                                                       | 判定規則・通常系と一致                                                 |
| `src/exec/events.ts` | `canClaimTask` は先行依存と着手前の状態を確認する。ロールは双方の指定があり、不一致許可がない場合に照合する。`canUnblockTask` は中断状態を確認し、アクターを照合しない                                                                         | 旧本文の必須ロール一致・同一アクター再開との乖離を承認済みの動作へ修正 |
| `src/exec/events.ts` | `canCompleteTask`・`canBlockTask`・`canReleaseTask` は状態と操作アクターを確認し、人間の強制操作を許す。`canReopenTask` は人間の要求と後続の状態を確認する。`canCancelTask` は着手前のみ許す。過去の実行中・中断中の `cancel` は `todo` に戻す | 完了条件の乖離を修正し、その他の制約・互換規則を維持                   |

実装から確認不能な意図は、状態を使う業務目的と、自動実行で runner が executor の成功・result の確認・親の検証と統合の成功後にだけ完了を記録し、失敗時に中断する保証である。これらは個票入力の利用者の決定を根拠とし、実装から推測していない。

未反映の仕様乖離はない。ロール照合が常に省略されるわけではない点は、承認された「別ロールでも着手可能」と両立する条件付きの動作として記載した。実装修正の申し送りと Kata の変更提案はない。

未確認範囲は、列挙外の runner・コマンド呼出し側の処理、外部 agent CLI の実行、実際の検証・統合失敗の再現である。`bdd-exec-state.yaml`・`bdd-exec-event.yaml` はカタログ記載先に未作成であり、本文の相互照合はできないが、利用者の決定により本タスクの未決事項とはしない。

### 5.4. 検証と後続処理

図表の 16 遷移・ID の一対一対応、状態一覧の 6 状態との一致、初期点から全状態への到達性、既存の遷移と frontmatter の維持を機械確認した。Prettier 整形、`git diff --check`、履歴リンク検証、登録簿生成、カタログ検証は成功した。カタログ検証では未作成の他成果物と既存の再エクスポート参照に関する警告が出たが、エラーはない。結果は pipeline evidence に記録する。

`lint:md`・`lint:fm`・`lint:mermaid` を含む指定の親検証は runner が実行する。result の記入は reporter に委ね、executor は result とライフサイクル記録を変更しない。
