# PJR-2P7C オーケストレーターの運用メモ（playbook）を正式な型にし、見つけ方を決める

## 1. 背景

オーケストレーターがプロジェクトごとに積み上げる知見（agent の使い分けと止まり方、実行の運び方、close の判断、保護された設定、リリースの手順など）を、prj-0001 では `030-project-management/pm-orchestrator-playbook.md` にまとめている。ただし正式な機能ではない。型（rulebook・template・sample）がなく（frontmatter は `rulebook: none`）、置き場所も決まっていない。配布するオーケストレーターの指示は「プロジェクトの文書にオーケストレーター向けの運用メモがあれば読む」とだけ書き、prj-0001 は `CLAUDE.md` と `AGENTS.md` にパスを直接書いて読ませている。別のプロジェクトでは、同じ知見を一から作ることになる。

## 2. 入力

- 利用者の問い（2026-11-23）: オーケストレーターのプロジェクトごとの知見を playbook にまとめているが、正式な機能か。オーケストレーターの答えは、正式ではない（型・置き場所・見つけ方が決まっていない）

## 3. 検討した選択肢

| 選択肢 | 内容                                                                                                                              | 利点                                                                                       | 欠点                                               |
| ------ | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------- |
| A      | 今のまま、プロジェクトごとの約束事にする                                                                                          | 作業が要らない                                                                             | 別のプロジェクトで見つけられず、書き方もそろわない |
| B      | 運用メモを正式な型にし、雛形の作り方と `specdojo where` での見つけ方を足す。指示の本文は `where` で引いた運用メモを読むようにする | どのプロジェクトでも同じ場所・同じ章立てで知見を残せる。`CLAUDE.md` にパスを書かなくて済む | 型と CLI と指示の本文の作業が要る                  |

オーケストレーターの推奨は B（2026-11-23）。長く効く知見は運用メモ、セッションの引き継ぎは handoff（PJR-5RY7）、待っている判断は `question` に分けると、引き継ぎの置き場所が一通りそろう。型の rulebook には、「知見は本体 → 運用メモ → コマンドの順に残す」（手作業の回避策が運用メモに 2 回以上出たら、コマンドにする項目を起票する）という育て方を書く。
