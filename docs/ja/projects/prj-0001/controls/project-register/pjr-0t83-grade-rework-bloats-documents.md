# PJR-0T83 grade の指摘への手直しで、完了条件の外の指摘まで直し、文書が膨らんで読みにくくなる

## 1. 課題内容

完了条件を満たした後も完了条件の外の観点の major を直し続け、表の列や規則が増えて文書が読みにくくなる。手直しの止め方と大きさ・読みやすさの確かめ方を決める

## 2. 入力

- PJR-CPZH（代替案比較）は 3 回の手直しで本文が 27KB から 75KB に増えた（sample は 20KB）。2 回目の時点でカタログの完了条件 4 件をすべて満たしていたが、完了条件の外の観点（vp-qe-verifiability）の major が同じ趣旨で残り、それに応えるため各セルの根拠の表や集約の規則を足し続けた
- 利用者は 2026-11-17 に、grade の結果以前に内容が分かりにくいと指摘し、運用の問題として起票することを依頼した。担当は BA、期限は 2026-11-30
- 同じ手直しの流れで直した他の文書（PJR-Y5AC など）でも同じことが起きているかは、起票の時点では確かめていなかった
- PJR-Y5AC（品質管理計画）も同じだった。3 回の手直しで 5.4KB から 18.8KB（約 3.5 倍）になり、sample（15.8KB）を超えた（2026-11-17 に orchestrator が確かめた）
- PJR-7WE7 で代替案比較を作り直し、結論を変えずに 75KB から 30KB にした。完了条件に大きさの上限、判定の区分を 5 つまでとすること、完了条件の外の指摘は記録だけに留めることを書き、再 grade で完了条件 4 件がすべて満たされた
- PJR-981V の 2 回目では、直す指摘を major と明らかな誤りに絞り、ほかの minor は章を足すより言い換え・統合を優先するとした。大きさを抑えたまま pass した
- 業務仕様までの sample を orchestrator が調べた（2026-11-17）。冗長さの多くは、役割の段落、承認・公開前確認の章、管理台帳への引き継ぎ、文書の lint を検証の表に入れること、同じ判断の言い直しといった文書の運用の記述だった。運用・検証の章が全体に占める割合は sf-index 36%、cdsd 32%、sf 30%、sld 28%。rulebook がこうした章を必須または条件付きで求め、grade の観点も同じ方向に点を付ける

## 3. 影響範囲

| 観点         | 影響                                                                                                                         |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| スコープ     | grade の指摘の手直しを行う成果物と sample、rulebook が各文書に求める運用の章、grade の観点、手直しの todo の完了条件の書き方 |
| スケジュール | 1 回の手直しで終わらず 3〜4 回の再実行になり、型の確定（140）が遅れる                                                        |

## 4. 対応方針

| 項目     | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 原因     | 次の 3 つが重なっている。(1) 手直しの完了条件に止める基準（大きさ・直す指摘の範囲）がない。(2) 完了条件を満たした後も、ほかの観点の major に応えて章や列を足し続ける。(3) rulebook と grade の観点が、役割・承認・検証などの運用の記述を各文書に求める                                                                                                                                                                                                                   |
| 対応策   | 次の 4 つを行う。(1) 手直しの todo の完了条件に、大きさの上限、直す指摘の範囲（major と明らかな誤り）、範囲の外の指摘は記録だけにすることを書き、運用メモに書き方の決まりとして残す。(2) 運用の記述（役割・status と承認・公開前確認）は、ドキュメントメタ情報標準などの共通の正本へ寄せ、各 rulebook は参照だけにする。(3) grade の観点を、運用の記述がないことを減点しない形に見直す。(4) sld 1 件で rulebook と sample を見直して効果を確かめ、ほかの sample へ広げる |
| 依存事項 | grade の観点の定義（`pm-review-viewpoints.yaml`）、ドキュメントメタ情報標準、各 rulebook、型の確定（140）の進め方                                                                                                                                                                                                                                                                                                                                                        |
| 完了条件 | 次の 4 つを満たす。(1) 手直しの完了条件の決まりが運用メモにある。(2) 運用の記述の正本と rulebook からの参照の形が決まり、sld で試した結果（大きさ、grade の結果、読みやすさの利用者の確認）が個票にある。(3) ほかの rulebook と sample へ広げる todo が起票されている。(4) CPZH と Y5AC で膨らんだ文書の扱い（作り直すか、そのままにするか）が決まっている                                                                                                               |
