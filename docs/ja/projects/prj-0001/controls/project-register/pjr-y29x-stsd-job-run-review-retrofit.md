# PJR-Y29X stsd-job-run を新しい Kata に合わせる

## 1. 概要

stsd-job-run を新しい章立てと遷移 ID 入りのラベルに合わせる

## 2. 入力

- 利用者のレビュー: 目的には、状態が対象の何を管理し、何のために使われるか（誰がその状態で何を判断するか）を書く。文書の読み手や使い方（承認する人、実装・テストへの利用）は書かない。章の名前は「目的」のままとする（2026-11-06 indie が決定）
- 利用者のレビュー: 状態の正本・判定の規則・互換の扱いは「適用範囲」ではない。「適用範囲」の後に新しい章「状態の判定」を置いてそこへ書き、「適用範囲」には対象・業務の範囲・到達点だけを残す（2026-11-06 indie が決定）
- 利用者のレビュー: スコープ（AS-IS / TO-BE）は既定を現行とし、「現行実装（AS-IS）」とは書かない。TO-BE の文書と並ぶときだけスコープを書く（2026-11-06 indie が決定）
- 利用者のレビュー: 「状態遷移図」と「遷移の説明」を 1 つの章「状態遷移」にまとめ、図を分けた場合は図ごとに、そのすぐ下へ遷移の表を置く。図の遷移のラベルにも遷移 ID を入れ、`T-<nn>` イベント / 条件 の形にする（2026-11-06 indie が決定）

## 3. 完了条件

- [[prj-0001:stsd-job-run]] が、PJR-S8EF〜PJR-93NK で直した Kata（[[specdojo:stsd-rulebook]]・[[specdojo:stsd-mermaid-rulebook]]）の必須の章・表・図の規則を満たしている。目的は状態が何を管理し何のために使われるかを書き、文書の読み手や使い方を書いていない。状態の正本と判定の規則は「状態の判定」の章にある。
- 「現行実装（AS-IS）」などのスコープの表記を、TO-BE の文書と並ばない限り書いていない。
- 図の遷移ラベルが `T-<nn> イベント / 条件` で、分けた図ごとにすぐ下へその図の遷移の表がある。図の全遷移が、その図の下の表へ一度ずつ対応している。
- 状態と遷移の中身は、カタログの `evidence_refs` の実装で確かめられる。実装で確かめられないことは推測で埋めず、`_UNDECIDED_` か今後の検討メモで残す。
- 文書は確定前（`status: draft`）のため、PJR-FS9A で直した規則に従い、遷移 ID を図と表の順に `T-01` から欠番なく振り直している。図のラベルと遷移表で同じ ID を使い、旧 ID と新 ID の対応を個票の対応結果に書いている。
- 今後の検討メモの各項目を見直し、実装で決まったものは本文へ反映して消し、残すものは理由を個票の対応結果に書く。
- `stsd-job-run` 以外の成果物と Kata は変えていない。Kata に直すべき点を見つけた場合は、変えずに個票の対応結果に書き、pipeline では報告の `handoff` にも書く。
- `npm run -s lint:md`・`npm run -s lint:fm`・`npm run -s lint:mermaid` が通っている。

## 5. 対応結果

- 判断は部分反映。既存の5状態・7遷移は指定実装と一致し、開始・結果記録と再試行に分ける構造も有効だったため、状態と業務判断を維持して章構成・記法を更新した。
- [[prj-0001:stsd-job-run|ステータス定義（Job Run）]] の目的を実行状況の管理と運用担当の判断に絞った。「適用範囲」から正本・一意判定を新設の「状態の判定」へ移し、互換・欠損記録の扱いを追加した。スコープ表記を削除し、「状態遷移」へ図と表をまとめ、図のラベルに遷移 ID を付けた。
- `src/job/job.ts` を読み、Run の新規作成、失敗・実行中からの試行追加、成功・部分成功・処理不要での既存結果返却、Run と最新試行への同じ結果の保存を確認した。事前判定のスキップでは保存せず、再試行では過去の試行を保持する。レビュー記録は状態を変えず、checkpoint の更新対象は成功・処理不要に限られる。
- `src/job/definition.ts` を読み、`JobRunState` と `JobRunAttempt` の状態値が同じ5値であることを確認した。読み込みは旧値の変換・状態欠損の補完を行わず、不正な状態値を拒否する。空の試行履歴は読み込めるが、結果記録は試行不在を拒否するため、この確認済みの扱いを本文へ反映した。
- 確定前の遷移 ID を図・表の順に `T-01` から再割り当てした結果、既存順と一致した。旧 ID → 新 ID は `T-01` → `T-01`、`T-02` → `T-02`、`T-03` → `T-03`、`T-04` → `T-04`、`T-05` → `T-05`、`T-06` → `T-06`、`T-07` → `T-07`。削除・追加した遷移はない。
- 意図された仕様は既存成果物・本個票・カタログの `done_criteria` と照合し、プロジェクト概要の引き継ぎ・判断責任の原則に整合させた。依存する `prj-0001:bdd-job-run` はカタログの指定先 `bdd-job-run.yaml` を含め未作成のため、辞書との用語・業務条件の一致は確認不能であり、`based_on` は空のままとした。
- 今後の検討メモは3件とも意思決定が残るため維持した。第1項は結果通知の受取・保存と `partial_exit_code` の宣言だけでは呼出元の状態選択規則や業務上の受入条件を確定できない。第2項は実行中の試行が残る動作は確認済みだが、安全な再試行の責任と残留試行の確定方針が未決。第3項は記録済み結果の再更新が可能な一方、結果訂正を業務遷移として認める承認根拠がない。実装で解決済みと判断して削除できる項目はなかった。
- 未反映の乖離は、結果記録が遷移元を制限しない点。意図された開始から結果記録までの図は維持し、BA・PO・ARC による訂正方針の合意後に、文書へ訂正遷移を追加するか実装に制限を設けるかを別タスクで決める。呼出元の結果選択・排他制御、外部コマンドや agent の実行、Git 入力解決とファイル保存障害の実行時動作は指定2ファイルの読解を越えて調査していない。
- 実装エビデンス・他の成果物・Kata・result は変更していない。Kata への修正提案はない。整形と親検証対象外の検査は executor evidence に記録し、`lint:md`・`lint:fm`・`lint:mermaid` を含む親検証の結果は runner が追記する。
