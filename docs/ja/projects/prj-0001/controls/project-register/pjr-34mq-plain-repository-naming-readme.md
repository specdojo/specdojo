# PJR-34MQ リポジトリ構成を平易な名前へ改め README を初めての人に分かる形にする

## 1. 概要

npm の README は、初めて SpecDojo を使う人に向けた導入の説明で、説明のない用語が多い。とくに「Detached Unit」は定義がなく、なぜ別のリポジトリにするのかも書かれていない。リポジトリ構成を平易な名前へ改め、README を初めての人が読んで分かる形にする。

## 2. 決定した名前

| 旧                      | 新                           | 意味                                                     |
| ----------------------- | ---------------------------- | -------------------------------------------------------- |
| Detached Unit           | **別リポジトリ構成**         | プロダクトリポジトリとプロジェクトリポジトリを分ける     |
| Attached Unit           | **同一リポジトリ構成**       | 1 つのリポジトリに両方を置く                             |
| プロダクトリポジトリ    | プロダクトリポジトリ（維持） | プロダクトドキュメント（仕様・設計）を置く               |
| SpecDojo 専用リポジトリ | **プロジェクトリポジトリ**   | プロジェクトドキュメント（登録簿・計画・実行記録）を置く |

道場にちなんだ名前（離れ / 母屋、出稽古 / 内稽古）も検討したが、平易さを優先した。弓道で「離れ」は矢を放つ瞬間を指す用語でもある。

リポジトリの呼び方は文書の分類（プロダクトドキュメント / プロジェクトドキュメント）とそのまま対応する。「プロジェクトリポジトリ」は既存の文書で使われておらず、意味がぶつからない。

「SpecDojo Unit」（1 つのプロダクト文脈を扱う論理的な管理境界）の概念は変えない。構成の名前だけを改める。

### 2.1. 初出で定義すること

| 注意点                                                                   | 書き方                                                                           |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| 一般には「プロジェクトリポジトリ＝アプリ本体のリポジトリ」と読まれやすい | 「プロジェクトドキュメント（登録簿・計画・実行記録）を置くリポジトリ」と定義する |
| 1 つのプロジェクトリポジトリに複数のプロジェクトが入る                   | 「プロジェクトごとにリポジトリを作る」と誤解されないよう書く                     |

## 3. README の分かりにくさ

「使い始める」の節だけで、説明のない用語が次のように出てくる。

| 用語                                                          | 問題                                                           |
| ------------------------------------------------------------- | -------------------------------------------------------------- |
| Detached Unit                                                 | 定義がない。なぜ別のリポジトリにするのかも書かれていない       |
| worktree 用ディレクトリ                                       | 何に使うのか書かれていない                                     |
| kata                                                          | 説明の前に「`node_modules/specdojo` から参照される」と出てくる |
| `current_project`、`projects`、`base_path`、catalog、schedule | 最初の導入には不要な設定の話                                   |
| provider、executor / reporter、規範の本文、rules / skills     | オーケストレーターの節で説明なしに出てくる                     |

## 4. 方針

| 方針                             | 内容                                                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------------------ |
| 先に「なぜ」を書く               | SpecDojo の記録（登録簿や実行の履歴）をプロダクトの Git 履歴と混ぜないため、別のリポジトリに置く |
| 最初の導入に要らない話は後ろへ   | 設定キーの話は「設定を変えたいとき」の節へ移す                                                   |
| 用語は初出で一言説明する         | kata = 成果物を書くための型、provider = 使う AI ツール、など                                     |
| オーケストレーターの節を短くする | 表と起動コマンドだけにし、仕組みの説明はガイドへ移す                                             |

## 5. 完了条件

- README に「Detached Unit」「Attached Unit」「SpecDojo 専用リポジトリ」が残っていない。
- README の「使い始める」を、SpecDojo を知らない人が上から読んで意味が通る。説明のない用語がない。
- 別リポジトリにする理由が README の冒頭近くで分かる。
- プロジェクトリポジトリの定義と、複数のプロジェクトが入ることが書かれている。
- 最初の導入に不要な設定の説明が、導入の手順から外れている。
- 次の文書の用語が追従している：`docs-structure-guide`、`quick-start-guide`、`specdojo-overview-guide`、`specdojo-config-reference`、`directory-layout-reference`。
- 見出しを参照している文書のリンクが切れていない（`別リポジトリ構成（Detached Unit）` の章名など）。
- `npm run -s lint:md` と `npm run docs:build` が通過している。
