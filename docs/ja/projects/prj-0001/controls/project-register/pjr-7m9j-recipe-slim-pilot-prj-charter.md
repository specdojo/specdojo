# PJR-7M9J prj-charter の recipe から文書の運用の記述を外す試行をし、recipe の一覧を作る

## 1. 概要

recipe には簡潔にする手本がないため、rulebook と sample を見直し済みの prj-charter で試行し、外す記述・残す記述・参照の形の一覧を作る。

## 2. 入力

- 利用者の決定（2026-11-18）: recipe は schedule に入れる前に prj-charter で試行する。手本は PJR-8S4T の rulebook と sample の一覧

## 3. 完了条件

- `docs/ja/specdojo/recipes/prj-charter-recipe.md` から、どの成果物にも共通する文書の運用の記述（役割の表と段落、`status` の昇格と承認、公開の承認条件、改訂と廃止の手順、文書品質の検査を手順の合格条件に入れること、未決事項の管理台帳の列と登録の段落など）と、rulebook と同じ判断の言い直しを外す。手本は [[prj-0001:pjr-8s4t-sld-kata-slim-pilot|PJR-8S4T]] の対応結果の「他の型へ広げるときの一覧」と、見直し済みの [[specdojo:prj-charter-rulebook|prj-charter-rulebook]] である。
- recipe に残すのは、その型を作る手順・入力の集め方・判断の順番・つまずきやすい点など、rulebook と sample にない作業の知見とする。判断の基準そのものは rulebook を章タイトルで参照する。
- 大きさは、空白を除いた文字数で今の 7 割以下を目安にし、前後の文字数を個票の対応結果に書く。
- 個票の対応結果に、ほかの recipe へ広げるときの「外す記述・残す記述・参照の形」の一覧を書く。schedule の段の指示にそのまま使える形にする。
- 直すのは recipe だけとする。rulebook・sample・template は変えず、合わせて直すべき点は変更案として個票の対応結果に書く。
- 型の grade は統合の後に orchestrator が流す。executor は grade を実行しない。
- 保護された設定（`lefthook.yml`・`.agents/`・`.claude/`・`.codex/`・`package.json`・`.specdojo/` など）は変えない。変更が要る場合は、変更案を個票の対応結果に書き、報告の `handoff` にも書く。反映は利用者の承認のもと feature ブランチで行う。
- 迷った点は executor が決め、決めた内容と理由を個票の対応結果に書く。pipeline では報告の `handoff` にも書く。
- `CHANGELOG.md` は変えず、個票の対応結果の「CHANGELOG に書く事項」の節に区分と行の文案を書く。影響がなければ「なし」と書く。
- `npm run lint:md`・`npm run lint:fm` と親の検証が通る。

## 5. 対応結果

### 5.1. 実施内容

- `docs/ja/specdojo/recipes/prj-charter-recipe.md` だけを直した。8 章の構成（「深掘り手順」を含む）は recipe 記述標準のまま保った。
- 外した記述:
  - rulebook と同じ判断の言い直し: 承認履歴の版番号と証跡リンクの中身、数値目標を再掲しないこと、成果物カタログ・成功基準文書への委譲、GO / Not GO の判断観点（目的整合・公開適性・予算枠・体制・品質）、表の列（決裁者・実行責任者・協議先・証跡）の指定。
  - 未決事項の管理台帳の列（「論点、期限、担当、対応方針」をそろえる）。追跡は登録簿で行う。
  - 仕上げチェックの構造の検査（「章立てがそろっている」「必須表のカラムが埋まっている」）と、同じ確認の繰り返し（承認の証跡の確認が 2 行、AI Agent の確認がレビュー観点・良い例・仕上げチェックの 3 か所）。
  - 「作成前に集める情報」と「深掘り手順」で、全体の作成手順を言い直していた行（「今回認めること」と「まだ認めないこと」を左右に分ける、など）。
  - 冒頭の「本書では問い、深掘り、具体化、レビュー観点を扱う」（章立てのなぞり）。
- 元の recipe には役割の表と段落、`status` の昇格と承認、公開の承認条件、改訂と廃止の手順、文書品質の検査はなかった。
- 残した・足した記述（rulebook と sample にない作業の知見）:
  - 「作成前に集める情報」に取り出し元の列を足した（概要・登録簿・承認責任者への確認・決定記録）。
  - 判断の順番: 認可対象を最初に決める理由と、冒頭文を最後に書く理由。
  - 聞き方: 「承認の直後に始めてよいこと」を聞く、判断ごとに決裁者と証跡を聞く、金額が出ないときは支出の扱いと確定時期を聞く。
  - つまずきやすい点: 後で作る計画書を直接根拠に入れやすい、登録簿から写すと公開できない識別子が紛れやすい、概要の指標表を写したくなる。
  - 「深掘り手順」は、対応のない主張を探す順序（認可対象から期待効果へ、権限委譲から認可対象へ、未決事項から影響先へ）に書き換えた（recipe 記述標準の「Recipe への適用方法」）。
- 用語は rulebook に合わせ、「PO」を「承認責任者」にした。

### 5.3. 迷った点と決めた内容

- 判断の基準の参照の形: 完了条件は「判断の基準そのものは rulebook を章タイトルで参照する」とするが、[[specdojo:recipe-authoring-standard|Recipe 記述標準]] の「記述ガイド」と「禁止事項」は、recipe 本文に rulebook・sample への参照や照合指示を置くことを禁じる（recipe-guided 実行では recipe だけが読み込まれ、参照が実行できない指示になるため）。標準を優先し、rulebook への参照は書かず、判断の基準を言い直さずに外し、成果物の章名（「承認」「未決事項」など）で示すだけにした。rulebook の章タイトルで参照する形を採るなら、先に Recipe 記述標準を変える必要がある（変更案の 1）。
- 標準の「各章の書き方」が求める「具体化のコツ」として、各節の「書き方」を「コツ」に変え、規則の言い直しではなく聞き方とつまずく点を書いた。
- 「良い例 / 悪い例」の AI Agent の行は、4.4 節と仕上げチェックと同じ確認のため外した。予算枠などほかの行は、判断の差がその表で初めて具体的に分かるため残した。
- 「GO / Not GO の観点」を recipe から外しても、rulebook と sample が持つため作成に支障はないと判断した。

### 5.4. 他の recipe へ広げるときの一覧

schedule の段の指示にそのまま使える形で書く。

外す記述:

- どの成果物にも共通する文書の運用（役割の表と段落、`status` の昇格と承認、公開の承認条件、改訂と廃止の手順、文書品質の検査を手順や仕上げチェックの合格条件に入れること）。
- 未決事項の管理台帳の列（区分・担当・期限・判断時期・対応方針・追跡先）と、台帳へ登録する旨の段落。
- rulebook と同じ判断の言い直し（表の列の指定、必須の観点の列挙、委譲先の文書の指定、承認記録の書き方、禁止事項の言い換え）。
- 仕上げチェックの構造の検査（章立て・必須の列がそろっている、など）。
- recipe 内の同じ確認の繰り返し（レビュー観点・良い例 / 悪い例・仕上げチェックで同じ点を確かめる、深掘り手順が全体の作成手順をなぞる）。
- 冒頭や章の頭で、章立てをなぞる文。

残す記述:

- 章を書く順番と、その順番にする理由。
- 入力の集め方（何をどこから取り出すか、誰に何を聞くか）。
- 書き手が答える問い（各節 2 つ程度）と、つまずきやすい点・聞き方のコツ。
- 対応のない主張を探す深掘りの順序。
- 判断の差が具体的に分かる良い例 / 悪い例（ほかの章と同じ確認は 1 か所にまとめる）。
- 型固有の対応関係（Why・What・How・Trace）を 1 項目で示す「このレシピの使い方」。

参照の形:

- recipe 本文に rulebook・sample への参照（wikilink、照合指示、章タイトルでの参照）を書かない（Recipe 記述標準）。判断の基準は言い直さずに外し、成果物の章名で示す。
- 共通の運用の参照文も recipe には書かない（rulebook の「共通の運用」が担う）。
- 上位成果物（概要・登録簿など）を正とする内容は「写さず参照に置き換える」とコツに書く。
- 大きさの目安: 空白を除いた文字数で 7 割以下。8 章の構成は保つ。

### 5.5. 変更案（この項目では直さない）

1. Recipe 記述標準（`docs/ja/specdojo/standards/recipe-authoring-standard.md`）: 個票の完了条件の「判断の基準は rulebook を章タイトルで参照する」と、本文に rulebook への参照を置かない規則が食い違う。recipe-guided 実行で rulebook を読み込まない限り、今の規則（参照しない）を保つ案を推す。他の recipe へ広げる schedule の指示は、上の一覧の「参照の形」にそろえる。
2. prj-charter-template（`docs/ja/specdojo/templates/prj-charter-template.md`）: 「未決事項」の表の列が `論点`・`期限`・`担当`・`対応方針` で、管理台帳の列が残る。rulebook の「承認と未決事項」（論点・影響・当面の扱い）に合わせ、`論点`・`影響`・`当面の扱い` にする。
3. rulebook と sample は変える点がなかった。
