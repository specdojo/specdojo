# PJR-5RY7 オーケストレーターの引き継ぎ（hand off）を register の新しい種類 handoff で扱う

## 1. 背景

オーケストレーターは、セッションや LLM を切り替えるときに `tmp/orchestrator/handoff-*.md` を書いて引き継いでいる。中身には、登録簿や `exec status` にすでにある状態の書き写し、利用者の返事を待っていること、会話の中だけの文脈（夜の間の承認の範囲、注意点）が混ざっている。git 管理外のため、ほかのマシンや LLM から読めず、判断待ちは会話の中にしか残らない。

## 2. 入力

- 今はセッションや LLM の切り替えのときに `tmp/orchestrator/handoff-*.md` を書いて引き継いでいる。git 管理外で、ほかのマシンや LLM から読めず、判断待ちが会話の中にしか残らない（2026-11-23）
- 利用者の提案（2026-11-23）: hand off を register で登録できるようにし、新しい種類 handoff を足す

## 3. 検討した選択肢

| 選択肢 | 内容                                                                                                                     | 利点                                                                                                                | 欠点                                                                                    |
| ------ | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| A      | 今のまま `tmp` に書く                                                                                                    | 手間がいちばん小さい                                                                                                | git で管理されず、判断待ちが失われやすい。register のブランチ（PJR-2TX0）で同期されない |
| B      | 切り替えのたびに note を起票する                                                                                         | git で管理され、項目へ wikilink でつながる                                                                          | note に終わりの状態がなく、古い引き継ぎが開いたまま積もる。状態の書き写しが残る         |
| C      | 中身を分け、状態はコマンドで組み立て、判断待ちは `question`、残りは入力・playbook・note に入れる                         | 書き写しがなく、判断待ちが失われない                                                                                | 次のセッションの入口（どれを読むか）が決まらない                                        |
| D      | 新しい種類 `handoff` を足し、受け取ったら close する。状態はコマンドで組み立て、判断待ちは `question` として別に起票する | 「開いている handoff = まだ読まれていない引き継ぎ」になり、入口が 1 つに決まる。受け取った主体が close の記録に残る | type・template・`pjr-rulebook`・exec の除外・組み立てのコマンドの作業が要る             |

## 4. 決定内容

D を採る。register に新しい種類 `handoff` を足す。

- 状態は open（受け取り待ち）と done（受け取った）。次のセッションが読んだら、受け取った主体を `--by` にして close する。`exec run --register` と夜の実行の対象にしない（note・epic と同じ）。
- 個票の章は次のとおりとする。

| 章               | 中身                                               | 書き方                                                             |
| ---------------- | -------------------------------------------------- | ------------------------------------------------------------------ |
| 引き継ぎ元と先   | どのセッション・どの LLM から、誰へ                | 手で書く                                                           |
| 有効な承認の範囲 | 夜の間に close してよい条件、使わない agent など   | 手で書く。長く効くものは playbook や個票の入力へ移す               |
| 進行中           | 流している列・run、review・waiting の項目          | コマンドで組み立てる                                               |
| 判断待ち         | 利用者の返事を待っている `question` や項目への参照 | 待っていることは `question` として別に起票し、ここは参照だけにする |
| 注意点           | 会話の中で気づいたこと                             | 手で書く。決まりになるものは playbook へ移す                       |

- 判断待ちを `question` として起票する運用は、型を足す前の 2026-11-23 から始める。
- コマンドは役割で分ける。個票の起票と close は `register add --type handoff`・`register close`（ほかの種類と同じ素の操作）。進行中と判断待ちを組み立てて起票するのは `specdojo orchestrator handoff` とする。register は exec を import しない決まり（ESLint の `no-restricted-imports`）があるため、exec の状態を読む組み立てを register に入れない（利用者の確認、2026-11-23）。

## 5. 採択理由

- note と違って終わりの状態があり、開いている handoff が「まだ読まれていない引き継ぎ」を表すため、次のセッションの入口が 1 つに決まる。
- 判断待ちを handoff の外の `question` にすることで、handoff を close しても待っていることが一緒に閉じない。
- 状態をコマンドで組み立てるため、登録簿や `exec status` と食い違う書き写しがなくなる。
- register のブランチ（PJR-2TX0）に入れば、ほかのマシンや LLM からも同じ手順で引き継げる。
