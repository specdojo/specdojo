# PJR-7WE7 prj-comparison-of-alternatives を読みやすい構成に見直す

## 1. 概要

結論を先に置き、判定の区分と根拠の表を絞って、3 回の手直しで膨らんだ代替案比較を読みやすくする

## 2. 入力

- 利用者が 2026-11-17 に、CPZH の対象の代替案比較は grade の結果以前に内容が分かりにくいと指摘した。grade の指摘への手直しとは目的が違うため、CPZH を close して別の todo で見直すことを選んだ（案 A）
- 3 回の手直しで本文は 27KB から 75KB に増えた。sample は 20KB である。grade の指摘に応えて表の列や規則を足し、削らなかったためである
- orchestrator が示した改善案 7 点（結論の要約を冒頭に置く、判定の区分を 4 つに絞る、集約の規則を短くする、根拠の表を sample と同じ案ごとの形にする、採らない案のセルは判定しない、記録の担当の重複を除く、rulebook が許せば尺度を有利・中間・不利にする）を利用者が了承した
- 各決定の結論（D-01〜D-03 の採否）は変えない

## 3. 完了条件

- [[prj-0001:prj-comparison-of-alternatives|代替案比較]] の先頭（「比較目的と前提条件」の前）に、D-01〜D-03 ごとに採るもの・併用または試行するもの・採らないものをまとめた結論の要約の表がある。
- 判定の区分は [[specdojo:prj-comparison-of-alternatives-rulebook|rulebook]] の例示（採択・一部採択・比較試行・保留・非採択）の範囲で 5 つ以内に絞り、意味を凡例として 1 か所に書いている。
- 「判定の根拠と集約規則」は 5 項目以内の短い箇条にしている。D-01 の重みは使わず、総合評価を決める軸（効果・追跡性・AI 適合）を明記する。
- 比較結果の根拠の表は sample と同じく案ごとに 1 行とし、判定の理由と再評価の条件をそれぞれ 2 文以内で書いている。High・Middle・Low ごとに列を分けない。
- 担当と記録先の記載は、同じ内容を複数の章に書いていない（rulebook の「同じ採否理由や見直し条件を複数箇所へ転載しない」）。
- 各決定の結論（D-01〜D-03 の各案の採否）を変えていない。
- 本文は 30KB 以下である（`wc -c` で確かめ、値を対応結果に書く）。
- 次の点は executor が決め、決めた内容と理由を個票の対応結果に書いている。pipeline では報告の `handoff` にも書く。
  - 採らない案のセルの扱い（rulebook の「同一レイヤー内では全候補に同じ軸」との整合）
  - 尺度の表記（High・Middle・Low を残すか、有利・中間・不利にするか）
  - 直す間の `status` の扱い（確定は人が 140 で行う）
- 再 grade（`grade run --target deliverable`）は orchestrator が流すため、executor は作業内容のその行を open のまま残す。再 grade ではカタログの完了条件 4 件を満たすことを確かめる。完了条件の外の観点の指摘は対応結果に記録するだけでよく、それに合わせて本文を足さない。
- `CHANGELOG.md` は変えない。
- `npm run lint:md`・`npm run lint:fm`・`npm run validate:catalog` と親の検証が通っている。

## 5. 対応結果

- [[prj-0001:prj-comparison-of-alternatives|代替案比較]] を見直した。冒頭に D-01〜D-03 の結論の要約の表と判定の凡例（採択・一部採択・比較試行・保留・非採択の 5 区分）を置き、「判定の根拠と集約規則」を 5 項目にした。D-01 の重みの列と加重の規則を除き、総合評価を効果・追跡性・AI 適合の 3 軸で決めると明記した。
- 根拠の表は High・Middle・Low ごとの列をやめ、案ごとに 1 行で「判定の理由」（2 文以内）と「再評価の条件」の 2 列にした。D-01 の再評価の条件は、旧本文の共通の条件（規制領域、反復頻度、自動検証、小規模向け最小構成）を案ごとに割り当てた。
- 担当と記録先の重複を除いた。「決定と見直し」の管理区分の表から試行結果の行を除いて WP の表を参照し、「技術的実現性と影響」・「リスクとトレードオフ」に重ねて書いていた `PM` の Schedule 登録は「決定と見直し」の 1 か所にまとめた。リスクの「全案・印象で評価する」の行は集約規則の未判定と同じ内容のため除いた。
- 判定の区分を 5 つへ寄せるため、表記だけを置き換えた（採否は変えていない）。正本として採択 → 採択、限定採択（STR-04）・段階採用（TSK-02）→ 一部採択、優先試行（SDD-03）→ 比較試行（優先は理由の列に書いた）、条件付き試行（TSK-05）→ 保留（条件の発生時に試行する）。
- grade の指摘のうち判定を変えないセルを直した。F003: SDD-03 の導入・移行負荷を、対応表を要するという基準に合わせて High から Middle にした。F004: TSK-05 の成熟度を、公式資料で確認していないため Low から未判定にした。どちらも判定（比較試行・保留）は変わらない。F001: SDD-02 の仕様・変更モデルを「仕様・計画・タスク・実装の段階（構成は版依存）」とし、版は WP-01 で固定するとした。
- 本文の大きさは 29,903 バイト（`wc -c`）。見直し前は 75,247 バイトだった。
- executor が決めたこと:
  - 採らない案のセル: rulebook の「同一レイヤー内では全候補に同じ軸・判定境界」に合わせ、比較表では全候補の全セルの判定を残した。根拠の表では、採否を決めた軸と、判定を変えない未判定だけを書く。
  - 尺度の表記: High・Middle・Low を残した。rulebook・recipe・sample が同じ表記を使っており、全セルを書き換えると結論が変わっていないことを照合しにくくなるためである。
  - `status`: 見直しの間は `ready` から `draft` に戻した。`ready` への確定は人が 140 で行う。
- 残っていること: 作業内容の 4（再 grade）は orchestrator が行う。F002 が求める全セルの根拠（根拠資料の該当箇所）は、根拠の表を案ごとに 2 文以内とする完了条件を優先したため書いていない。採否を決めた軸と未判定の確認作業だけを書いた。F001 が求める資料確認日は、宣言された資料で確かめられないため書いていない。
- 再 grade の結果（2026-11-17、orchestrator、`sol-review-executor`、run `grade-7we7-20261117`）: verdict は needs-work、score は 94。完了条件の DC-001〜DC-004 はすべて satisfied。残る major は F002（各セルの根拠と、未判定の採否への扱い）で、根拠の表を案ごとに 2 文以内とする本項目の完了条件の外にあるため、完了条件に従い記録だけに留める。要約の表の D-02 の行の非採択の欄に「06」とあり、「SDD-06」の略記になっている。
