# PJR-RJV2 トレースの表を手で書く文書から生成のビューに変えるかを決める

## 1. 背景

型のトレースの表（`trc-requirements-to-specs`・`trc-requirements-to-tests`）は、どちらも rulebook で派生のビューとされている。対応の正本は、仕様とテストの文書の `relations.satisfies`・`relations.verifies`、テストの「トレース」の表、要求の項目 ID である。

一方で生成するコマンドがないため、rulebook は手で作る手順（母集団を決める・抽出する・照合する・数える）を細かく定めている。手間がかかり、正本と食い違いやすい。全件レビュー（PJR-0BGE）でも trc の sample の段が書式で止まった（T-KATA-REVIEW-ALL-trc-requirements-to-tests-sample-130）。

利用者は、トレースの文書は要るのか、書かなくても検索でトレースできないのかと問うた（2026-11-25）。

## 2. 入力

- 利用者の問い（2026-11-25）: トレースの文書は要るのか、書かなくても検索でトレースできないのか
- 利用者の判断（2026-11-25）: 推奨どおり decision として起票する。担当と期限は未定

## 3. 検討した選択肢

検索で分かるのは、ある要求 ID を指す仕様・テストまでである。次の 4 つは検索だけではできない。いずれも機械的に計算できる。

- 漏れの検出（どのテストにも指されていない要求。母集団との突き合わせが要る）
- 充足の判定（対応先がすべて `ready` か、ケースから参照されているか）
- 宛先のない参照（母集団にない要求を指すテスト）
- ある時点の記録（受入やレビューの根拠）

| 案  | 内容                                                                                                           | 利点                                           | 欠点                               |
| --- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ---------------------------------- |
| 1   | 生成コマンドを作り、trc の型を生成のビューの説明に縮める。人が書くのは優先と直し方だけで、登録簿で扱ってもよい | 漏れの検出が確実になり、手で作る手間がなくなる | コマンドの実装が要る               |
| 2   | trc の型を外し、検索だけにする                                                                                 | すぐ済む                                       | 漏れと充足の判定ができなくなる     |
| 3   | 今のまま手で書く                                                                                               | 変更がない                                     | 手間がかかり、正本と食い違いやすい |

オーケストレーターの推奨は案 1。

## 4. 決定内容

_UNDECIDED_: 案の選択（推奨は案 1）。あわせて、全件レビュー（PJR-0BGE）で残っている trc の sample の段を流すか飛ばすかを決める。
