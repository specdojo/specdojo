# PJR-0WE7 途中で落ちた見張りの診断が「診断中」のまま残り、その止まりが二度と診断されない

## 1. 課題内容

診断の agent の実行中にプロセスが落ちると、診断の記録が running のまま残り、同じ止まりは以後診断されない。朝報告の診断の節も失われる

## 2. 入力

- 2026-11-28 08:12 JST の見張り（orchestrator watch-scan）で PJR-VEHX の診断を起動した後、コンテナの再起動でプロセスが落ちた
- 診断の記録（execution/watch/diagnoses/ の JSON）は status: running のまま残った。起動前に予約して同じ止まりを二度起こさない作りのため、PJR-VEHX は以後診断されない
- 朝報告 watch-scan-20261128.md は描き直された後、第 7 節「agent の診断案」を書く前に落ちたため、節が消えた。--no-diagnosis で流し直して復旧した
- 診断の lock（.launch-lock）は心拍が 30 秒途絶えれば次の起動が外すため、手当ては要らなかった
- 直し方（持ち主のプロセスが動いていない running を interrupted として扱い 1 回だけ起こし直す、先に診断の節を書いておく、など）は executor が決め、理由を個票の対応結果に書く（担当 DEV・期限 2026-12-31 は indie の指示、2026-11-28）

## 3. 影響範囲

| 観点         | 内容                                                                                         |
| ------------ | -------------------------------------------------------------------------------------------- |
| スコープ     | 見張りの診断（`src/exec/watch-diagnosis.ts`）と、その記録・朝報告の第 7 節「agent の診断案」 |
| スケジュール | 影響は小さい。朝に人が確かめる手間が増える                                                   |
| コスト       | 影響は小さい                                                                                 |
| 品質         | 落ちた診断の止まりは以後診断されない。描き直しの途中で落ちると、朝報告から診断の案が消える   |
| 関係者       | 朝報告を読む人と、立ち上げたままのオーケストレーター                                         |

## 4. 対応方針

| 観点     | 内容                                                                                                                                                                        |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 原因     | 起動前に `running` で予約した記録を、持ち主のプロセスが落ちたときに終わりの状態へ書き換える手段がない。報告の本文を書いた後に診断の節を書くため、その間に落ちると節が消える |
| 対応策   | executor が決め、理由を個票の対応結果に書く                                                                                                                                 |
| 依存事項 | なし                                                                                                                                                                        |
| 完了条件 | 下の一覧のとおり                                                                                                                                                            |

- 持ち主のプロセスがもう動いていない `running` の記録は、次の見張りで中断（例: `interrupted`）と分かる状態にする。その止まりは 1 回だけ起こし直せ、1 晩の回数の上限には数える。扱いは executor が決め、理由を個票の対応結果に書く。
- 見張りが途中で落ちても、それまでに記録した診断の案が朝報告から消えない。
- 単体テストまたは統合テストで、中断した記録の扱いと、同じ止まりを二度以上起こし直さないことを確かめている。
- `CHANGELOG.md` は変えない。個票の対応結果に「CHANGELOG に書く事項」の小節を作り、区分と行の文案を書く。
- 保護された設定（`.specdojo/`・`.agents/`・`.claude/`・`.codex/`・`.opencode/`・`package.json` など）は変えない。変更が要る場合は、案を個票の対応結果と報告の `handoff` に書く。
- 作業を終える前に `npm run typecheck`・`npm run lint:ts`・`npm run test:unit` を通し、親の検証を通す。
