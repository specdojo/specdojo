# PJR-0WE7 途中で落ちた見張りの診断が「診断中」のまま残り、その止まりが二度と診断されない

## 1. 課題内容

診断の agent の実行中にプロセスが落ちると、診断の記録が running のまま残り、同じ止まりは以後診断されない。朝報告の診断の節も失われる

## 2. 入力

- 2026-11-28 08:12 JST の見張り（orchestrator watch-scan）で PJR-VEHX の診断を起動した後、コンテナの再起動でプロセスが落ちた
- 診断の記録（execution/watch/diagnoses/ の JSON）は status: running のまま残った。起動前に予約して同じ止まりを二度起こさない作りのため、PJR-VEHX は以後診断されない
- 朝報告 watch-scan-20261128.md は描き直された後、第 7 節「agent の診断案」を書く前に落ちたため、節が消えた。--no-diagnosis で流し直して復旧した
- 診断の lock（.launch-lock）は心拍が 30 秒途絶えれば次の起動が外すため、手当ては要らなかった
- 直し方（持ち主のプロセスが動いていない running を interrupted として扱い 1 回だけ起こし直す、先に診断の節を書いておく、など）は executor が決め、理由を個票の対応結果に書く（担当 DEV・期限 2026-12-31 は indie の指示、2026-11-28）

## 3. 影響範囲

| ------------ | -------------------------------------------------------------------------------------------- |

| スケジュール | 影響は小さい。朝に人が確かめる手間が増える                                                   |

| 関係者       | 朝報告を読む人と、立ち上げたままのオーケストレーター                                         |

## 4. 対応方針

| 観点     | 内容                                                                                                                                                                        |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 原因     | 起動前に `running` で予約した記録を、持ち主のプロセスが落ちたときに終わりの状態へ書き換える手段がない。報告の本文を書いた後に診断の節を書くため、その間に落ちると節が消える |
| 対応策   | executor が決め、理由を個票の対応結果に書く                                                                                                                                 |
| 依存事項 | なし                                                                                                                                                                        |
| 完了条件 | 下の一覧のとおり                                                                                                                                                            |

- 持ち主のプロセスがもう動いていない `running` の記録は、次の見張りで中断（例: `interrupted`）と分かる状態にする。その止まりは 1 回だけ起こし直せ、1 晩の回数の上限には数える。扱いは executor が決め、理由を個票の対応結果に書く。
- 見張りが途中で落ちても、それまでに記録した診断の案が朝報告から消えない。
- 単体テストまたは統合テストで、中断した記録の扱いと、同じ止まりを二度以上起こし直さないことを確かめている。
- `CHANGELOG.md` は変えない。個票の対応結果に「CHANGELOG に書く事項」の小節を作り、区分と行の文案を書く。
- 保護された設定（`.specdojo/`・`.agents/`・`.claude/`・`.codex/`・`.opencode/`・`package.json` など）は変えない。変更が要る場合は、案を個票の対応結果と報告の `handoff` に書く。
- 作業を終える前に `npm run typecheck`・`npm run lint:ts`・`npm run test:unit` を通し、親の検証を通す。

## 5. 対応結果

### 5.1. 実施内容と判断

- `src/exec/watch-diagnosis.ts` で、専用の `.launch-lock` を取得した後に残る `running` を `interrupted` として原子的に保存する。持ち主の終了・心拍の途絶を扱う既存のロックを判断の正本とした。PID の再利用を避け、所有者の情報を持たない既存の JSON も回復できるためである。心拍が生きていてロックを取得できない回は、記録を変更せず報告だけ描画する。ロック自体の寿命や回収処理は変更していない。
- 初回が中断した同じ止まりには、1 回だけ再診断を許す。初回の `<鍵の SHA-256>.json` を残し、再診断を `<鍵の SHA-256>.retry.json` に排他的に予約する。中断を含む両方の記録を、それぞれ起動した晩の上限へ数える。上限で起動できなければ次の晩に再診断できるが、再診断の成功・失敗・時間切れ・中断後に 3 回目は起動しない。初回の成功・失敗・時間切れは従来どおり再診断しない。記録の保持により、再試行を重ねず回数の根拠も失わない。
- `src/exec/watch-scan.ts` は、朝報告の再描画時に既存の第 7 節を引き継ぐ。診断処理も agent の起動前に保存済みの案と今回の予約を描画する。報告の書き込みは一時ファイルからの置き換えとし、起動待ちや書き込み途中でプロセスが落ちても直前の報告を残す。
- `--no-diagnosis` でも中断記録の状態と報告は更新し、起動は行わない。dry-run・全体の見張り停止では記録を変更しない。保護された設定と `CHANGELOG.md` の変更は不要だった。
- 回帰テストを `tests/src/commands/watch-diagnosis.integration.test.ts` と `tests/src/exec/watch-scan.test.ts` に追加した。古い形式の予約と期限切れロック、診断無効時の回復、同晩の上限、翌晩の 1 回限りの再診断、再診断自体の中断、並行起動と生存中のロック、agent 起動前の診断節、見張り本体の再描画直後の診断節保持を対象にした。設計と運用・設定ガイドも更新した。

### 5.2. 検証と申し送り

Prettier による変更ファイルの整形、catalog 検査、履歴リンク検査、実行時 import の依存宣言検査、register build、差分の空白検査は成功した。catalog には既存の参照先不在・re-export 参照などの警告があるが、終了コードは 0。

型検査・TypeScript lint・単体／統合テスト・Markdown/frontmatter lint・全体 schema 検査などは、指定された親 runner の検証で確認する。executor では同じ検査の対象限定版も重複実行しない。親検証の成功と、作業内容の runner 行の更新は reporter・runner に引き継ぐ。result の記入と登録簿の状態遷移も後段で行う。

### 5.3. CHANGELOG に書く事項

- 区分: 修正。
- 文案: 見張りの診断中にプロセスが落ちた記録を中断として回復し、晩ごとの上限内で同じ止まりを 1 回だけ再診断できるようにした。朝報告の再描画や診断中の中断でも、保存済みの診断案を保持する。
