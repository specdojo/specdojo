# PJR-6AQF CLI 仕様（clis）の型に入力ファイルの規則を足す

## 1. 概要

clis の本文の「出力と生成ファイルの要点」を「入力と出力のファイルの要点」にし、コマンドが読むファイルと作る・変えるファイルを分けて書く規則と、sample の例を足す

## 2. 入力

- PJR-PJYJ（indie が決定、2026-11-08）: clis は入力ファイルの規則を足して直す。読むファイルの中身は書かず、そのファイルの rulebook か schema を参照する。

## 3. 完了条件

- [[specdojo:clis-rulebook]] の本文要件の「出力と生成ファイルの要点」を「入力と出力のファイルの要点」にし、記述ガイドに次の規則を書いている。
  - コマンドが読むファイル（設定・正本・前のコマンドが作ったファイル）と、作る・変えるファイルを分けて書く。
  - 読むファイルごとに、ない場合と形式が壊れている場合の扱い（止まるか、既定で進むか）を書く。
  - 読むファイルの中身（項目や形式）は書かず、そのファイルの rulebook か schema を参照する。
  - 読むファイルの誤りで出るエラーは、終了コードとエラー表示・利用者の次の手の章の表につなげる。
- `clis-sample` に、読むファイル（商品マスタなど）の例と、そのファイルがない・壊れているときのエラーの例を足している。
- 確定した ifx-cmd の型（渡すファイルと作るファイル）と、用語と考え方が食い違っていない。
- 迷った点は executor が決め、決めた内容と理由を個票の対応結果に書いている（PJR-025M で人が判断する材料にする）。
- uis の型、ほかの型、カタログを変えていない。
- CHANGELOG.md は変えず、利用者に影響する変更を個票の対応結果の「CHANGELOG に書く事項」の節（番号付きの見出し）に、区分と行の文案で書いている（PJR-EPQ3）。
- `npm run lint:md`・`npm run lint:fm`・`npm run test:unit` が通っている。

## 5. 対応結果

### 5.1. 実施内容

1. **`clis-rulebook` への入力ファイル規則の追加**:
   - 第5章の見出しおよび本文要件を「出力と生成ファイルの要点」から「入力と出力のファイルの要点」へ改訂した。
   - 記述ガイド（6.5節）に、コマンドが読むファイル（設定・正本・前のコマンドが作ったファイル）と作る・変えるファイルを分離して記述する規則を追加した。
   - 読むファイルごとに、ない場合および形式破損時の扱い（エラーで停止するか、既定値で進むか）を明記する規則を策定した。
   - 読むファイルの中身（項目や形式）は仕様書内に書かず、そのファイルの正本（rulebook または schema）を参照する規則（二重管理の防止）を明記した。
   - 読むファイルの誤り（欠損・構文不正・権限不足等）で発生するエラーを、第6章の「終了コードとエラー表示・利用者の次の手」の表につなげる規則を明文化した。
   - 全体方針、用語定義（2.2節）、禁止事項（第7章）、運用ルール（第8章）についても、入力ファイルの概念を取り込んで整合させた。
2. **`clis-sample` への入力ファイル例とエラー例の追加**:
   - 第5章を「入力と出力のファイルの要点」に改訂し、「5.1. 読むファイル（入力ファイル）の要点」小節を新設した。店舗設定ファイル（`config/store-config.yaml`）、商品マスタ（`data/master/products.json`）、一時セッションファイル（`.session/current-tx.json`）の例を追加した。
   - 第6章「終了コードとエラー表示・利用者の次の手」に、商品マスタ未検出（ない場合）、商品マスタ破損（壊れている場合）、および店舗設定ファイル破損の具体的なエラーメッセージ要点、原因、利用者の次の手（回復アクション）を追加した。
3. **ifx-cmd の型との用語・概念の整合確認**:
   - 確定済みの外部コマンド連携仕様（[[specdojo:ifx-cmd-rulebook]]）における「渡すファイル（inputs）と作るファイル（outputs）」の考え方・用語と照合し、人間向けの CLI 仕様として「読むファイル」と「作る・変えるファイル」の概念が矛盾なく対応していることを確認した。
4. **他仕様・カタログへの非影響の確認**:

### 5.3. スキーマ（schema）変更の要否と理由

- **スキーマ変更なし**: CLI 仕様（clis）は Markdown 形式（`target_format: markdown`）の成果物であり、`docs/specdojo/schemas/v1/` に専用の YAML/JSON スキーマは存在しない。Frontmatter は共通の `deliverable-frontmatter.schema.yaml`（`type: ui`）および `rulebook-frontmatter.schema.yaml` に適合しており、スキーマ変更および後方互換性への影響はない。

### 5.4. 規則と sample の書き方で executor が決めた内容と理由（PJR-025M への判断材料）

1. **章立てと小節構成**:
   - 決定: 第5章の見出しを「入力と出力のファイルの要点」とし、小節を「5.1. 読むファイル（入力ファイル）の要点」「5.2. 標準出力の表示要点」「5.3. 作る・変えるファイル（出力・生成ファイル）の要点」の3つに分離した。
   - 理由: 入出力ファイルを1つの表で混在させると、入力特有の属性（ない場合・壊れている場合の挙動、正本スキーマ参照）と出力特有の属性（表示項目、ライフサイクル）で列定義が乖離し可読性が低下するため。「コマンドが読むファイルと、作る・変えるファイルを分けて書く」という完了条件にも合致するため。
2. **中身の重複排除と正本参照**:
   - 決定: 読むファイルの中身（項目や形式）は CLIS 本文には書かず、そのファイルの正本（rulebook または schema）への参照にとどめる規則とした。
   - 理由: PJR-PJYJ の「読むファイルの中身は書かず、そのファイルの rulebook か schema を参照する」という決定に直結しており、仕様の二重管理と陳腐化を排除するため。未作成のスキーマ等はバッククォート等による仮置き参照を許容した。
3. **ない場合と形式破損時の扱いの記述**:
   - 決定: 読むファイルごとに「ない場合の扱い」と「形式不正・破損時の扱い」の両方を明記する列・記述を必須とした。
   - 理由: 設定ファイルのように「ない場合は既定値で進むが、壊れている場合は構文エラーで止まる」ケースと、業務正本マスタのように「ない場合も壊れている場合も即時エラー停止する」ケースで CLI の挙動が異なるため、運用者やテスト担当者が正確に期待値を把握できるようにするため。
4. **終了コード・エラー表示・利用者の次の手との連携**:
   - 決定: 読むファイルの欠損・破損時に発生するエラーを、第6章「終了コードとエラー表示・利用者の次の手」の表のエラー事象・原因・回復手順へ直接対応づける規則とした。sample でも「商品マスタ未検出」「商品マスタ破損」「店舗設定ファイル破損」の具体的なエラーと回復アクションを第6章に追加した。
   - 理由: エラーが発生した際に利用者が何を確認しどう復旧すべきか（バックアップからの復元、マスタ同期コマンドの実行等）を明確にすることで、CLI 仕様の実効性を担保するため。
5. **ifx-cmd との用語・概念の整合性**:
   - 決定: `ifx-cmd` の「渡すファイル（`inputs`）と作るファイル（`outputs`）」の考え方・用語と整合させつつ、CLIS では人間が利用する CLI の特性に合わせて「読むファイル（設定・正本・先行コマンド作成ファイル）」と「作る・変えるファイル（生成ファイル・更新ファイル）」として位置づけた。
   - 理由: システムが外部ツールを呼ぶ契約（ifx-cmd）と、人間がコマンドラインを操作する仕様（clis）の視点の違いを保ちつつ、入出力ファイルに関する責務境界とモデルの一貫性を維持するため。
