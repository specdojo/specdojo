# 代替案比較: SpecDojo

本書は、シビックテックで SpecDojo を継続運用するため、運営・開発戦略、SDD 実装支援、作業状態管理を分けて比較する。

## 1. 比較目的と前提条件

### 1.1. 決定すること

本書では、抽象度の異なる次の三つを順に決定する。

| 決定ID | 比較レイヤー   | 決定すること                                             | 決定しないこと                  |
| ------ | -------------- | -------------------------------------------------------- | ------------------------------- |
| D-01   | 運営・開発戦略 | P-01〜P-03 をどの原則と統制の組合せで解くか              | 個別製品、IDE、Issue 管理ツール |
| D-02   | SDD 実装支援   | 採択戦略の仕様・計画・タスク化を何で支援するか           | プロジェクト全体の運営戦略      |
| D-03   | 作業状態管理   | 人と AI Agent の作業、依存、判断根拠の正本をどこに置くか | 要求・設計文書の内容と開発方式  |

D-01 を先に決め、D-02 と D-03 はその実現を支える候補として評価する。SDD ツールやタスク管理ツールが備えるワークフローを、プロジェクト戦略そのものとはみなさない。

### 1.2. 前段文書から引き継ぐ条件

- 当事者の社会課題と期待価値を、要求・仕様・検証結果へ追跡できること。
- OSS、再利用、AI 支援により、現金支出と参加者の作業負荷を抑えられること。
- 判断、作業、負荷を共有し、特定個人へ依存せず分担・継承できること。
- 人間が判断責任を保持し、特定製品へ過度に固定されないこと。

内部の根拠資料は、初期公開の境界を定める [[prj-0001:prj-scope|プロジェクトスコープ]]、P-01〜P-03 と必要能力を定める [[prj-0001:prj-issues-and-approach|プロジェクト課題と解決アプローチ]]、人間の責任者と外部依存を定める [[prj-0001:prj-assumptions-constraints-dependencies|前提・制約・依存関係]] である。`PO` の承認を要する事項は、前提・制約・依存関係の「制約事項」が正とする [[prj-0001:prj-charter|プロジェクト憲章]] の「権限委譲」に従い、評価軸の表では「憲章「権限委譲」」と略記する。

### 1.3. 外部候補の調査範囲と選定基準

候補は、利用者が例示した製品や現在利用中の方式だけから選ばず、次のカテゴリを先に定めて公式資料を調査する。

| 比較レイヤー | 調査カテゴリ                                                                 | 候補に含める基準                                         |
| ------------ | ---------------------------------------------------------------------------- | -------------------------------------------------------- |
| D-01         | 予測型、適応型、ハイブリッド型、最小統制                                     | 単独でも目的達成への道筋と統制原則を説明できる           |
| D-02         | OSS・ベンダー中立型、プラットフォーム提供型、IDE 統合型、包括的 Agent 開発型 | 仕様から計画・タスク・実装への接続を公式資料で確認できる |
| D-03         | リポジトリ内管理、Git ホスティング統合、汎用 SaaS、Agent ネイティブ          | 状態、依存、履歴、担当または Agent の引継ぎを管理できる  |

各候補は、標準・方法論と製品を区別し、管理対象、データ保管場所、対応環境、既存資産との重複、移行・復旧可能性を確認する。普及度だけで採択せず、成熟度は公式情報と試行結果で継続評価する。

現時点では客観的な市場占有率の比較を行っていないため、本書の「有力候補」は「各カテゴリの差異を評価するための比較候補」を意味し、「市場を代表する唯一の標準」を意味しない。

### 1.4. 外部資料の位置づけ

- 戦略: [PMI Standards](https://www.pmi.org/standards)、[PMBOK Guide のテーラリング資料](https://www.pmi.org/-/media/pmi/documents/public/pdf/pmbok-standards/pmi-tailoring.pdf)、[アジャイルソフトウェア開発宣言](https://agilemanifesto.org/iso/ja/manifesto.html) と [背後にある原則](https://agilemanifesto.org/iso/ja/principles.html)。
- SDD: [GitHub Spec Kit](https://github.github.com/spec-kit/index.html)、[OpenSpec](https://openspec.dev/)、[Kiro Specs](https://kiro.dev/docs/specs/)、[BMAD Method](https://docs.bmad-method.org/)。
- 作業状態管理: [GitHub Issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/learning-about-issues/about-issues)、[Jira](https://www.atlassian.com/software/jira/features/project-management)、[Linear](https://linear.app/docs)、[Beads](https://github.com/gastownhall/beads)。

Spec Kit、OpenSpec、Kiro、BMAD、Beads は標準ではなく、特定カテゴリの実装候補として扱う。Loop Engineering は maker/checker、外部化した状態、検証、停止条件などの実行パターンとして扱い、Spec Kit の拡張機能だけに定義を依存させない。

STR-01〜STR-05 は同じ課題に対する戦略パッケージである。SDD 製品や Issue 管理製品は含めず、採択後に D-02、D-03 で選ぶ。

### 2.2. D-02: SDD 実装支援

| 方式ID | 方式                        | カテゴリ                    | 仕様・変更モデル                                        | 強み                                                           | 主な制約                                               |
| ------ | --------------------------- | --------------------------- | ------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------ |

| SDD-06 | 専用 SDD ツールを採用しない | 最小構成                    | 現行 Markdown と手動手順のみ                            | 新規依存と学習負荷がない                                       | 生成・差分管理・Agent 連携の改善機会を得にくい         |

Spec Kit を SDD の唯一の代表とはせず、OpenSpec を直接比較し、Kiro と BMAD は異なる統合範囲の境界確認に用いる。Spec Kit は公式資料が示す既定プロセスを評価の対象とし、プロセスのカスタマイズで対応付けを省けるかは机上では判定しない。試行で使う版と構成（既定プロセスのまま使うか、どこをカスタマイズするか）は WP-01 で固定して評価記録に残し、その構成に実際に適用される制約で評価を更新する。

### 3.4. 判定の根拠と集約規則

- 尺度: High・Middle・Low は順序尺度で、数値に換算しない。各セルは評価軸の表の判定基準のうち、最初の条件を満たせば High、2番目の条件に当たれば Middle、3番目の条件に当たれば Low とする。条件を確認できない、または High の条件を一部しか確認できない場合は Middle とし、未確認事項を High としない。
- 証拠: 各セルは 「外部資料の位置づけ」の公式資料と前段文書に基づく机上評価であり、試行証拠ではない。比較表の直後の根拠表に、採否を決めるセル（D-01 は High と Low のセル、D-02・D-03 は必須条件の軸のセルと Low のセル）の判定理由を記す。根拠表に理由のない Middle のセルは、判定基準の2番目の条件に当たる、または High の条件を確認できなかったことを示す。試行後は測定結果でセルを更新し、根拠表の記載を差し替える。
- D-01 の重みは各軸が総合評価と採否に与える役割を示し、加重合計は用いない。重み5の軸（効果、追跡性、AI 適合）は総合評価を決める。重み5の軸がすべて High で、どの軸にも Low がない案を `High`、重み5の軸のうち2軸以上が Low の案を `Low`、それ以外を `Middle` とする。重み4の軸（リスク、運用適合、技術実現性、適応性）と重み3の軸（コスト、期間、成熟度）は総合評価を変えず、採否への反映は次の項目に従う。重み4と重み3の差は、Low の軸を採択時のトレードオフとして軽減する優先順位を示す。
- D-01 の採否: 総合 `High` の案を採択する。総合 `Middle` の案は High の軸に当たる要素だけを一部採択し、Low の軸をその案の要素で満たそうとしない（採択案の High の軸で補う）。総合 `Middle` でリスクが Low の案は、一部採択に代えて、適用範囲を境界・検証・停止条件を定義できる作業に限る限定採択とする。リスク以外の重み4の軸と重み3の軸の Low は採否の区分を変えず、採択時のトレードオフとして「リスクとトレードオフ」で扱う。総合 `Low` の案は採択しない。
- D-02 と D-03 は、追跡可能な正本、人間の判断責任、可逆性を必須条件とする。必須条件に当たる軸（D-02 は成果物適合・人間の統制・可逆性、D-03 は正本性・ロックイン）がすべて High の案から正本を一つ選ぶ。正本以外では、Low の軸がない案を、正本に不足する軸を補う範囲で試行または段階採用する。Low の軸がある案は、その不利が特定の状況でだけ問題になり、発生条件を再評価トリガーとして定義できる場合に限り条件付き試行または保留とし、それ以外は採択しない。

## 6. 決定と見直し

- D-01 はツール非依存の仕様駆動ハイブリッド、D-02 は SpecDojo 成果物を正本とする。OpenSpec と Spec Kit は「比較試行の計画と完了条件」に従って比較試行し、DP-01 までは正式採用しない。
- D-03 は Schedule / Register を正本、GitHub Issues / Projects を外部協働の入口とする。Jira、Linear は現段階では採用せず、Beads は Agent 固有の実課題が確認された場合だけ試行する。
- 採択案の最終判断は人間の `PO` が行う。`BA` は利用者価値、`ARC` は方式境界と外部依存、`PM` は計画・リスク、`QE` は検証証拠を確認し、AI Agent は調査、比較、隔離試行を支援する。
- 長期 Agent 作業の依存問題、組織横断の統制要求、または外部候補の重要な変更が生じた場合、該当カテゴリ全体を再評価する。特定製品の自動採用条件とはしない。

本書から生じる管理事項は、種類ごとに [[prj-0001:pjr-index|プロジェクト登録簿]] へ分けて記録する。`PM` は後続作業を Schedule に置き、依存する作業の開始前に完了を確認する。

| 管理区分 | 対象                                                                                       | 記録と担当                                                                                     |
| -------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 試行結果 | WP-06 の判定条件ごとの結果、DP-01 の判断                                                   | `QE` が結果を、`PO` が判断と理由を登録簿へ記録する                                             |
