# 代替案比較: SpecDojo

本書は、シビックテックで SpecDojo を継続運用するため、運営・開発戦略、SDD 実装支援、作業状態管理を分けて比較する。結論は次のとおりで、理由は「比較結果と採択理由」を正とする。

| 決定ID | 採るもの                     | 併用または試行するもの                                     | 採らないもの                 |
| ------ | ---------------------------- | ---------------------------------------------------------- | ---------------------------- |
| D-01   | STR-03 仕様駆動ハイブリッド  | STR-01・STR-02 の一部、STR-04 の実行パターン（作業を限る） | STR-05 最小統制              |
| D-02   | SDD-01 SpecDojo 成果物を正本 | SDD-03 OpenSpec を優先し SDD-02 Spec Kit と比較試行        | SDD-04 Kiro、SDD-05 BMAD、06 |
| D-03   | TSK-01 Schedule / Register   | TSK-02 GitHub Issues を受付に併用。TSK-05・TSK-06 は保留   | TSK-03 Jira、TSK-04 Linear   |

判定の凡例（本書はこの 5 区分だけを使う）:

| 判定     | 意味                                                                 |
| -------- | -------------------------------------------------------------------- |
| 採択     | 戦略または正本として採る                                             |
| 一部採択 | 案の一部の要素、または正本以外の役割だけを採る（正本は二重化しない） |
| 比較試行 | 「比較試行の計画と完了条件」で試行し、DP-01 まで正式採用しない       |
| 保留     | 再評価の条件が生じるまで採否を決めず、生じたら試行または再比較する   |
| 非採択   | 採らない。再評価の条件が生じたらカテゴリごと再比較する               |

## 1. 比較目的と前提条件

### 1.1. 決定すること

| 決定ID | 比較レイヤー   | 決定すること                                      | 決定しないこと                  |
| ------ | -------------- | ------------------------------------------------- | ------------------------------- |
| D-01   | 運営・開発戦略 | P-01〜P-03 をどの原則と統制の組合せで解くか       | 個別製品、IDE、Issue 管理ツール |
| D-02   | SDD 実装支援   | 採択戦略の仕様・計画・タスク化を何で支援するか    | プロジェクト全体の運営戦略      |
| D-03   | 作業状態管理   | 人と Agent の作業、依存、判断根拠の正本の置き場所 | 要求・設計文書の内容と開発方式  |

D-01 を先に決め、D-02・D-03 はその実現を支える候補として評価する。

### 1.2. 前段文書から引き継ぐ条件

社会課題を検証まで追跡できる、OSS・AI 支援で支出と負荷を抑える、特定個人へ依存せず継承できる、人間が判断責任を持ち特定製品へ固定されない、の4点を条件とする。

根拠資料は [[prj-0001:prj-scope|プロジェクトスコープ]]（初期公開の境界）、[[prj-0001:prj-issues-and-approach|プロジェクト課題と解決アプローチ]]（P-01〜P-03、A-01〜A-03）、[[prj-0001:prj-assumptions-constraints-dependencies|前提・制約・依存関係]]（ACD-\*）である。`PO` の承認事項は [[prj-0001:prj-charter|プロジェクト憲章]] の「権限委譲」に従い、表では「憲章」と略記する。

### 1.3. 外部候補の調査範囲と選定基準

候補は既知の製品だけから選ばず、カテゴリを先に定めて公式資料を調査する。

| レイヤー | 調査カテゴリ                                               | 候補に含める基準                               |
| -------- | ---------------------------------------------------------- | ---------------------------------------------- |
| D-01     | 予測型、適応型、ハイブリッド型、最小統制                   | 単独で目的達成への道筋と統制原則を説明できる   |
| D-02     | ベンダー中立型、プラットフォーム型、IDE 統合型、包括 Agent | 仕様から計画・タスク・実装への接続を確認できる |
| D-03     | リポジトリ内、Git ホスティング統合、汎用 SaaS、Agent 型    | 状態、依存、履歴、担当または引継ぎを管理できる |

標準・方法論と製品を区別し、データ保管場所と移行・復旧可能性を確認する。市場占有率は比較しておらず、候補は市場の代表や標準ではない。

### 1.4. 外部資料の位置づけ

- 戦略: [PMI Standards](https://www.pmi.org/standards)、[PMBOK Guide のテーラリング資料](https://www.pmi.org/-/media/pmi/documents/public/pdf/pmbok-standards/pmi-tailoring.pdf)、[アジャイルソフトウェア開発宣言](https://agilemanifesto.org/iso/ja/manifesto.html) と [背後にある原則](https://agilemanifesto.org/iso/ja/principles.html)。

- 作業状態管理: [GitHub Issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/learning-about-issues/about-issues)、[Jira](https://www.atlassian.com/software/jira/features/project-management)、[Linear](https://linear.app/docs)、[Beads](https://github.com/gastownhall/beads)。

## 3. 評価軸と評価基準

各レイヤーの全候補に同じ軸を使い、採択に有利なほど高くする（費用・負荷・依存は小さいほど高い）。

### 3.1. D-01 の評価軸

| 評価軸     | 判定基準（High / Middle / Low）                                            | 課題・制約       |
| ---------- | -------------------------------------------------------------------------- | ---------------- |
| 効果       | P-01〜P-03 の3課題に改善の道筋を示せる / 2課題 / 1課題以下                 | P-01〜P-03       |
| コスト     | 現行体制で導入・維持できる / 手順整備の追加で維持 / 専任・追加体制要       | P-02、ACD-C01    |
| 期間       | 最初の反復で成果を得る / 準備後に初期公開前に得る / 得られない             | 初期公開範囲     |
| リスク     | 乖離・負荷転嫁・責任不明・公開不備を統制 / 1〜2事象欠く / 3以上か責任不明  | P-01〜P-03、憲章 |

| 成熟度     | 公開標準と回復方法がある / 一部の要素に限る / 運用知見と回復方法がない     | ACD-D04          |

最低観点の統合は D-02 と同じで、期間は運用負荷で判定する。

### 3.4. 判定の根拠と集約規則

- 証拠: 各セルは「比較対象案」・P-01〜P-03・公式資料を判定基準と照らした机上評価で、試行後に観察結果で更新する。
- 未判定: 当たる条件を確認できないセルは未判定とし、どの段階にも数えない。どう確定しても判定が変わらない案だけ判定を確定し、比較試行の案は WP-01 の確認後に確定する。
- D-01: 重みは使わず、効果・追跡性・AI 適合の3軸で決める。3軸が High でほかに Low がなければ採択、2軸以上が Low なら非採択、それ以外は High の軸の要素を一部採択し、リスクが Low なら境界・検証・停止条件を定義できる作業に限る。
- D-02・D-03 の正本: 必須の軸（D-02 は成果物適合・人間の統制・可逆性、D-03 は正本性・ロックイン）がすべて High の案から一つ採択する。
- 正本以外: Low がなく、正本が High でない軸（成熟度を除く）で High の案は、D-02 は比較試行（比較対照を一つ加えられる）、D-03 は一部採択とする。Low がある案は、不利が特定の状況に限れば保留、ほかは非採択とする。

| ------ | ---------------------------------------------------- | --------------------------------------------------------- |
| D-01   | 文書体系の拡張で実現できる。`ARC` が反映先を特定する | `QE` が検証手順でエラー 0 件を確認                        |

### 4.5. 比較試行の計画と完了条件

SDD-02 と SDD-03 に同じ小規模な変更要求を隔離環境で与える。作業時間の上限は [[prj-0001:prj-issues-and-approach|プロジェクト課題と解決アプローチ]] の「費用・負荷の上限を決める」に従い、上限が未定または有償利用が要る間は ACD-C02 に従い始めない。

| WP    | 作業                                     | 担当 Role             | 前提            | 完了条件                             |
| ----- | ---------------------------------------- | --------------------- | --------------- | ------------------------------------ |
| WP-01 | 変更要求・版と構成・見積もり・成熟度判定 | `PM`（`BA`・`ARC`）   | 上限の決定      | 見積もりが上限内で計画を登録している |
| WP-02 | 試行環境、対応表、試行生成物の削除規則   | `ARC`                 | WP-01、検証方針 | D-02 の確認方法を適用できる          |
| WP-03 | 同一変更要求の処理と反映案の作成         | `ARC`（Agent が支援） | WP-02           | 反映案を作成している（正本は不変）   |
| WP-04 | 意図保持の確認                           | `BA`                  | WP-03           | 意図との不一致をすべて是正している   |
| WP-05 | 正本への反映                             | `ARC`                 | WP-04           | 是正済みの反映案を反映している       |
| WP-06 | 判定条件の検証と評価記録                 | `QE`                  | WP-05           | 条件ごとの結果を登録簿に記録している |
| DP-01 | 継続利用または撤退の判断                 | `PO`                  | WP-06           | 判断と理由を登録簿に記録している     |

継続利用（SDD-01 を正本とした補助利用）は次をすべて満たす場合に限り、上限内に是正できない未達があれば撤退して試行生成物を削除する。試行を終えるまで、どちらも「採用ツール」や「標準」と呼ばない。

- 重複: ツール側にだけ残る要求・判断が 0 件。
- 追跡: 変更要求から検証までの参照の欠落が 0 件。
- 意図保持: WP-04 の不一致が WP-05 の前にすべて是正済み。
- 再開可能性: ツールの設定・生成物を外しても成果物だけで再開でき、検証エラー 0 件。
- 負荷: 実績の作業時間が WP-01 の上限内。

## 6. 決定と見直し

- 判定は冒頭の要約と「比較結果と採択理由」のとおりで、最終判断は人間の `PO` が行う。`BA` は利用者価値、`ARC` は方式境界、`PM` は計画とリスク、`QE` は検証証拠を確認し、AI Agent は調査と試行を支援する。
- 各案の再評価の条件や外部候補の重要な変更が生じたら該当カテゴリ全体を再評価し、特定製品を自動採用しない。

試行結果は「比較試行の計画と完了条件」の担当が、ほかの管理事項は下表の担当が [[prj-0001:pjr-index|プロジェクト登録簿]] へ記録する。`PM` は後続作業を Schedule に置き、依存する作業の開始前に完了を確認する。

| 管理区分 | 対象                                        | 記録の担当                                            |
| -------- | ------------------------------------------- | ----------------------------------------------------- |
| リスク   | 「リスクとトレードオフ」のリスク            | `PM` が登録し、顕在化したら元の ID を付けて課題へ移す |
| 課題     | 試行の不合格、照合の不一致、依存見落とし    | `PM` が案 ID、是正担当、再確認時期を登録する          |
| 変更要求 | 評価軸・採択方針の変更、再評価の条件の発生  | `PM` が影響と撤退方法を登録し、`PO` が承認する        |
| 未決事項 | 費用・負荷の上限、試行の継続、TSK-05 の開始 | `PM` が期限と判断者 `PO` を登録し、未決の間は始めない |
