# プロジェクトスコープ: SpecDojo

本書は、三つの価値仮説を検証するために、SpecDojo の初期公開へ含める活動、成果物、代表試行の境界を定める。

## 1. 対象業務

対象は、資金と専門人材が限られ、技術・非技術の参加者が協働するシビックテックプロジェクトである。代表試行では、一つの社会課題について次の流れを確認する。

1. 当事者と非技術参加者が、課題、対象者、期待する変化、制約を言語化する。
2. 技術者と AI Agent が、それらを要求・仕様とソリューション候補へつなげる。
3. 選んだ候補を、追加支出と作業時間を記録しながら試行成果まで具体化する。
4. 判断と作業を別の参加者へ引き継ぎ、改善を継続する。

試行成果は、課題に応じてプロトタイプ、既存 OSS の構成、業務手順、データ活用方法などから事前に定める。本番サービスの完成を一律には求めない。

| 利用者                   | 利用場面                             | 期待する結果                             |
| ------------------------ | ------------------------------------ | ---------------------------------------- |
| 当事者・市民・地域・行政 | 課題、期待価値、制約、結果を確認する | 技術知識に依存せず、解く内容を判断できる |
| 開発者・技術協力者       | 要求を仕様と試行成果へ具体化する     | 現場の Why を失わず、技術を適用できる    |
| 継続参加者・AI Agent     | 成果物を再利用し、変更・引き継ぐ     | 費用と負荷を抑えて改善を続けられる       |

### 初期公開に含めるもの

1. 社会課題、期待価値、要求、仕様、判断、検証結果を結ぶ最小成果物セット。
2. 最小セットの rulebook、recipe、sample、template と選択案内。
3. 文書、カタログ、登録簿、実行計画の生成・検証・状態管理・Agent 実行を支援する SpecDojo CLI。
4. 人と AI Agent が同じ正本を参照・検証するための ID、メタデータ、参照ルール。
5. OSS・再利用・AI 支援を活用し、現金支出と作業時間を記録する試行手順。
6. 課題定義から試行成果、引き継ぎまでの代表シナリオと評価記録。
7. README、ライセンス、改善提案の入口など、OSS として試用する公開導線。

## 2. 対象システム

| 対象               | 内容                                                                   | 境界                                             |
| ------------------ | ---------------------------------------------------------------------- | ------------------------------------------------ |
| 文書フレームワーク | 最小成果物、作成支援資料、schema、ID、メタデータ、参照関係             | 個別システムの本番実装は含めない                 |
| SpecDojo CLI       | 文書・カタログ・登録簿・実行計画の生成・検証、状態管理、Agent 実行支援 | 外部 Agent CLI 自体や個別業務の自動化は含めない  |
| 管理データ・生成物 | 成果物カタログ、登録簿、Schedule、Execution、検証結果                  | 正本から生成する派生物は直接編集しない           |
| 代表試行           | 社会課題から試行成果までの一つ以上のシナリオ                           | 本番運用、利用者サポート、サービス保証は含めない |
| 公開導線           | 利用方法、ライセンス、改善提案、公開可能なサンプル                     | 有償サービスや個別団体の内部運用は含めない       |

## 3. 対象期間

- 初期公開: 最小セットと公開導線を整え、代表試行で SC-01〜SC-03 を確認するまで。
- 公開後: 実利用3件を目安に、価値、費用・負荷、継続状況を確認するまで。

## 4. スコープ外

| 対象（Out）                          | 理由                                            |
| ------------------------------------ | ----------------------------------------------- |
| 全ライフサイクル・全文書種別の完成   | 三つの価値仮説に必要な最小セットを優先する      |
| 個別ソリューションの本番開発・運用   | 初期試行は SpecDojo の有効性検証を目的とする    |
| 「無償」を理由とする無制限な労務提供 | 人の時間と継続負担を費用として扱う              |
| 特定手法、技術、AI 製品への最適化    | 利用プロジェクトが技術を選べる共通の型を保つ    |
| 外部サービス・団体システムとの連携   | 初期検証に不要で、運用と情報管理の範囲が広がる  |
| 人間の意思決定責任の代替             | AI Agent は言語化、実行、検証の支援者として扱う |

## 5. 境界の判断基準

追加候補は、次の順で判断する。

1. 課題と技術の接続、低コストな実現、無理のない継続のいずれを検証するか。
2. SC-01〜SC-03 の代表試行に必要か。
3. 既存の成果物、OSS、無償の手段で代替できないか。

検証対象と対応しないものは初期公開後に送る。

## 6. スコープ変更方針

変更提案には、対応する P-ID / SC-ID、利用者価値、現金支出、作業負荷、追加・削除する成果物、公開時期への影響を記録する。`BA` と `ARC` が影響を確認し、`PO` が承認する。初期公開前に追加する場合は、同時に削除または延期する項目を示す。
