# プロジェクト課題と解決アプローチ: SpecDojo

本書は、シビックテックで優先して解く課題と、SpecDojo が備える能力を定める。中心仮説は「目的、判断、次の作業を共通の記録として残せば、参加者が交代しても人と AI Agent が活動を継続できる」である。

## 1. 課題一覧

| 課題ID | 課題                                                                 | 利用者への影響                                 | 優先度 |
| ------ | -------------------------------------------------------------------- | ---------------------------------------------- | ------ |
| P-01   | 社会課題、対象者、判断理由が分散し、活動の目的を共有できない         | 手段が先行し、同じ議論や作り直しが発生する     | High   |
| P-02   | 仕様、決定、未決事項、次の作業が結び付かず、変更・交代時にたどれない | 引き継ぎと変更が止まり、少数の担い手に依存する | High   |
| P-03   | 文書の構造と正本が曖昧で、人と AI Agent が同じ文脈を参照できない     | Agent の結果がばらつき、人間の確認負担が増える | High   |

## 2. 原因（仮説でも可）

| 課題ID | 原因区分 | 内容                                                   | 根拠 / 確認方法                          |
| ------ | -------- | ------------------------------------------------------ | ---------------------------------------- |
| P-01   | 仮説     | Why と判断根拠の記録方法が個人の経験に依存している     | 利用事例で情報の所在と合意過程を確認する |
| P-02   | 仮説     | 成果物間の関係、更新責任、現在状態を示す共通の型がない | 変更・引き継ぎシナリオで確認する         |
| P-03   | 仮説     | ID、メタデータ、正本、完了条件が一貫していない         | 人と Agent の参照先と判断結果を比較する  |

これらは仮説であり、代表利用者による試行と実利用で検証する。

## 3. 解決策候補

| 案ID | 案                             | 概要                                                           | 期待できる効果                       | 対応課題   |
| ---- | ------------------------------ | -------------------------------------------------------------- | ------------------------------------ | ---------- |
| A-01 | Why と判断を先に共有する       | 対象者、課題、期待価値、主要判断を実装より先に残す             | 手段の先行と議論の反復を減らす       | P-01       |
| A-02 | 変更・引き継ぎ可能な正本を作る | 仕様、判断、未決事項、次の作業を ID と参照関係で結ぶ           | 変更と担当交代後も文脈をたどれる     | P-01〜P-03 |
| A-03 | 最小セットから反復して改善する | 必要な成果物とガイドだけで開始し、試行に応じて追加・簡素化する | 記録負荷を抑えながら利用を継続できる | P-02、P-03 |

AI Agent は記録、更新、検証を支援するが、目的、主要判断、公開可否は人間が承認する。具体的な運営戦略と支援ツールは [[prj-0001:prj-comparison-of-alternatives|代替案比較]] で選定する。

## 4. 採用アプローチと理由

A-01 を起点、A-02 を中核、A-03 を導入方針として一体で採用する。利用者課題への直接効果、引き継ぎ可能性、少人数での運用負荷の順に重視する。初期公開では、文書種別の網羅よりも、代表的な一つのシビックテックプロジェクトで次の流れが成立することを優先する。

1. Why と主要判断を記録する。
2. 人と AI Agent が同じ正本を参照して変更する。
3. 後任者が未決事項と次の作業を理解して継続する。

## 5. トレードオフ/リスク

| 区分         | 内容                                           | 対応                                                 | 所有者 |
| ------------ | ---------------------------------------------- | ---------------------------------------------------- | ------ |
| トレードオフ | 初期公開では全文書種別を完成させない           | 代表シナリオに必要な成果物を優先する                 | `PO`   |
| トレードオフ | 特定技術の詳細手順は利用プロジェクト側に委ねる | 共通の判断基準と記録形式に限定する                   | `ARC`  |
| リスク       | 文書作成自体が目的化する                       | 各成果物が P-01〜P-03 と成功基準に寄与するか確認する | `PO`   |
| リスク       | 記録負荷により利用が継続しない                 | 必須項目を絞り、試行で不要な項目を削る               | `BA`   |
| リスク       | Agent の判断が人間の承認を代替する             | 判断者と検証証跡を明記し、人間の承認を完了条件にする | `QE`   |
| リスク       | 公開資料に個人情報や非公開情報が混入する       | 公開前レビューで一般化または除外する                 | `QE`   |

リスクは [[prj-0001:pjr-index|プロジェクト登録簿]] で追跡する。

## 6. 次の検討事項（ToDo）

| ToDo                                         | 完了条件                                             | 責任ロール  |
| -------------------------------------------- | ---------------------------------------------------- | ----------- |
| 代表利用者と対象プロジェクトを決める         | 技術・非技術参加者と引き継ぎ役を含む試行条件が決まる | `PO`, `BA`  |
| 初期公開の最小成果物セットを決める           | 代表シナリオに必要な成果物と参考資料が特定される     | `PO`, `ARC` |
| 変更・引き継ぎシナリオを作る                 | SC-01〜SC-03 の手順、必須情報、証跡が定義される      | `BA`, `QE`  |
| 公開範囲、ライセンス、改善提案の入口を決める | 公開前レビューに必要な条件が確定する                 | `PO`, `BA`  |

## 7. 見直しと変更管理

利用者試行または実利用で課題仮説が反証された場合、対象課題、アプローチ、最小成果物セットを見直す。主要な変更は `PO` が承認し、理由を [[prj-0001:pjr-index|プロジェクト登録簿]] または決定記録に残す。
