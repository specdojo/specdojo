# PJR-HKTJ マスコットなどのアセットを specdojo-assets で管理し、使うものだけを各リポジトリへ書き出す

## 1. 背景

マスコットの原本・生成の設定・ブランドの規則を専用のリポジトリ specdojo-assets で管理し、LP・ドキュメントサイトなどへは exports の定義に従って最適化したファイルだけを書き出して commit する運用にするかを決める

### 1.1. 経緯と前提（2026-10-12）

- 利用者から、LP のマスコット（PJR-FSMC）の画像を作るにあたり、LP 以外でも使う可能性があるため、アセットを `specdojo-assets` という別のリポジトリに分け、使うものだけを指定のリポジトリへ書き出す運用がよいのではという相談があった。prj-0001 側の orchestrator の会話で案を整理し、本項目で引き継ぐ。
- 原本（高解像度の画像、差分、生成のプロンプトや設定、ラフ）は大きく、作り直しが多い。LP が使うのは Web 向けに最適化した少数のファイルだけである。
- 使う場所の候補は、LP、ドキュメントサイト（VitePress）、README、VS Code 拡張のアイコン、SNS の画像である。

### 1.2. 推奨案の構成

```text
specdojo-workspace/
├── specdojo-assets/                 # 原本とブランドの規則（プロダクトリポジトリ）
│   ├── mascot/source/               # 原本（Git LFS）
│   ├── mascot/prompts/              # 生成のプロンプト・設定
│   ├── exports.yaml                 # 何を・どの形式とサイズで・どのリポジトリのどこへ書き出すか
│   └── BRAND.md                     # 色・余白・使ってよい場面・ライセンス
├── specdojo-lp/public/mascot/       # 書き出したファイル（commit する）
└── specdojo/docs/public/mascot/     # 書き出したファイル（commit する）
```

- 書き出しはスクリプトで行い、`exports.yaml` に載せたものだけを、決めた形式とサイズ（WebP・AVIF・PNG、@1x・@2x など）で書き出す。
- 書き出したファイルは使う側のリポジトリで commit する。ビルド時に取得しないため、Cloudflare での LP のビルドは外部に依存せず再現できる。git submodule は使わない。
- 原本は Git LFS で管理する。
- 書き出したファイルを使う側で直接直さない。直す場合は原本と `exports.yaml` を変えて書き出し直す。
- prj-0002 の `repos` に `specdojo-assets` をプロダクトリポジトリとして加え、exec が原本と書き出し先の両方を扱えるようにする。

## 2. 検討した選択肢

| 選択肢    | 内容                                                                                                      | 利点                                                                                                                                    | 懸念                                                                                                |
| --------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| A（推奨） | `specdojo-assets` に原本と規則を置き、`exports.yaml` で使うものだけを各リポジトリへ書き出して commit する | 原本が 1 か所に集まり、どこで使っても同じ絵になる。コードのリポジトリが重くならない。ライセンスとブランドの規則を原本と一緒に管理できる | リポジトリが 1 つ増える。書き出しのスクリプトと定義を用意する必要がある                             |
| B         | `specdojo-lp` の中に原本と書き出しを置く                                                                  | 最も手軽で、追加のリポジトリが要らない                                                                                                  | 他の場所で使うときに LP からコピーすることになり、原本の所在が曖昧になる。LP のリポジトリが重くなる |
| C         | `specdojo-assets` を git submodule として各リポジトリから参照する                                         | 書き出しの手順が要らない                                                                                                                | submodule の扱いが重く、Cloudflare のビルド設定も増える。原本ごと参照するためリポジトリが重くなる   |

## 3. 決定内容

選択肢 A を採る。

- `specdojo-assets` に、マスコットなどの原本・生成の設定・ブランドの規則（`BRAND.md`）を置く。`exports.yaml` に載せたものだけを、決めた形式とサイズで各リポジトリへ書き出し、使う側のリポジトリで commit する。git submodule は使わない。原本は Git LFS で管理する。
- 原本の作り方: AI での生成と、人が描くことの両方を使う。
  - AI で生成したものは、生成のプロンプトと設定を `mascot/prompts/` に残す。
  - 人が描いたものは、作者と利用の許諾の範囲を `BRAND.md` に書く。
  - 原本ごとに、どちらの方法で作ったかと、ライセンスを `BRAND.md` で分かるようにする。
- 書き出し先の範囲: 当面は LP（`specdojo-lp`）だけとする。ドキュメントサイトや README などは、必要になった時点で `exports.yaml` に足す。

## 4. 採択理由

- LP 以外でも使う可能性があり、原本を 1 か所に集めると、どこで使っても同じ絵になる。
- 書き出したファイルを使う側で commit するため、Cloudflare での LP のビルドが外部に依存せず再現できる。コードのリポジトリも重くならない。
- AI での生成と人の手描きを併用するため、作り方とライセンスを原本と一緒に管理できる場所が要る。
- 書き出し先を LP だけから始めると、書き出しのスクリプトと定義を小さく保てる。

## 8. 追記（2026-10-12）

利用者の判断で、原本を Git LFS で管理することをやめ、普通の git で管理する。決定内容と構成の案にある「Git LFS」は、この追記で置き換える。

- 理由: マスコットの原本は、AI で生成した画像も手描きの画像も 1 枚あたり数 MB 程度に収まり、大きなファイルを作る予定がない。LFS は devcontainer への導入と、clone する全員の `git lfs` が要り、GitHub の LFS には容量と転送量の上限もある。書き出したファイルは `specdojo-lp` で普通に commit するため、LP のビルドには影響しない。
- 見直しの目安: 1 ファイルが 10 MB を超えるなど、原本が大きくなる場合は LFS を改めて検討する。PSD など大きくなりやすい作業用のファイルを原本として置くか、書き出した PNG だけを置くかは、[[prj-0002:pjr-f34r-assets-repository-setup]] で決めて `README.md` に書く。
