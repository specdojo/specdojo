## 理解の負債とは

**理解の負債（Comprehension Debt）**とは、つくったものや決めたことの背景・意図・前提を十分に共有、記録、更新しないことで、将来の理解・変更・引き継ぎに余計な労力が必要になる状態です。

- **なぜ決めたのか分からない。** 選択肢や判断理由が、会議やチャットの中に埋もれている。
- **何が正しい仕様なのか分からない。** 文書、実装、運用が少しずつ食い違っている。
- **誰かがいないと進まない。** 知識が個人に集中し、引き継ぎのたびに調べ直している。
- **AIがつくったものを説明できない。** 成果物は増えても、何を確かめ、何を採用したかが追えない。

理解の負債は、単なる「文書の不足」ではありません。**判断の経緯と成果物のつながりが失われること**が問題です。

## 速くつくるだけでは、未来に残らない

AIに「つくって」と頼めば、コードも文書も、以前より速く形になります。

しかし、速くつくることと、理解できる状態を保つことは別です。必要なのは、文書の量を増やすことではなく、**何を目指し、なぜ決め、何をつくり、どう確かめたか**を、後からたどれるようにすることです。

SpecDojoは、会話の中で生まれた気づきや判断を登録し、成果物と実行につなぎ、変更が起きたときにも更新できるようにします。

## SpecDojoの答え：記して、形にして、磨き続ける。

### 1. 記して — 判断を、未来に残す

気づき、問い、問題、選択肢、決定、作業を、**register（登録簿）**に一件ずつ記します。何をするかだけでなく、なぜするか、どうなれば完了かも残します。

### 2. 形にして — 意図を、成果物につなぐ

登録した項目を要求・要件・仕様・設計・実装などの成果物につなぎます。AIエージェントに作業を任せるときも、目的や完了条件を共有し、計画・実行・結果を追える形にします。

### 3. 磨き続ける — 変化しても、理解を失わない

成果物を確かめ、判断と結果を記録し、改善点を次の作業につなぎます。仕様書を一度書いて終わりにせず、変化に合わせて育てます。

**一度きりの文書化から、継続的な理解の維持へ。**

---

## 小さな記録から始められる

最初から大量の仕様書をつくる必要はありません。まずは、目の前の一件を記録するところから始めます。

| 登録するもの       | registerの種類   | 残すこと                 |
| ------------------ | ---------------- | ------------------------ |
| やること           | `todo`           | 背景、完了条件、実行結果 |
| 決めたこと         | `decision`       | 選択肢、判断理由、影響   |
| 起きた問題         | `issue`          | 問題、対応、確認結果     |
| 仕事のまとまり     | `epic`           | 子項目との関係、進捗     |
| まだ答えのない問い | `question`       | 確認したいこと、回答     |
| 将来の懸念         | `risk`           | リスク、対応方針         |
| 変更の要望         | `change-request` | 変更理由、影響、反映結果 |
| 観測・分析の記録   | `note`           | 事実、考察、参照情報     |

一件ごとの記録は、読めるMarkdownファイルです。恒久的なIDでほかの項目やGitの変更履歴から参照でき、特定の画面やAIサービスに閉じ込められません。

**会話は流れても、判断は残せる。**

## 人が理解し、AIが実行する

SpecDojoでは、AIエージェントを単なるコード生成器ではなく、記録・実行・確認を支える協働者として使います。

1. **人が目的を伝える。** 何を実現したいか、何に困っているかを話す。
2. **AIと整理する。** 問い・判断・作業をregisterに残す。
3. **AIが作業を進める。** 完了条件に沿って成果物を更新し、計画と結果を記録する。
4. **人が確かめる。** 結果を検証し、必要なら改善点を次の登録項目にする。

AIに任せることと、人が理解を手放すことは同じではありません。

> **AIがつくる。人が理解する。判断と成果を、次につなぐ。**

※実行・検証・承認の具体的な機能と自動化範囲は、利用するバージョンや設定により異なります。

## 既存の道具と、競うよりつなぐ

SpecDojoは、すべての開発ツールを置き換えることを目指していません。

- **GitHub Issues** は、チームの議論と共有に。SpecDojoのregisterは、判断の理由や完了条件を含む記録に。
- **Claude Code・Codexなどのplanモード** は、目の前の段取りに。registerは、会話やセッションをまたいでもたどれる記録に。
- **Spec Kit・OpenSpec・Kiroなど** は、仕様と実装を進めるための選択肢に。SpecDojoは、その前後も含めた判断・要求・成果物の継続性を重視します。

重要なのはツールを統一することではなく、**ツールが変わっても、何を決めたかが失われないこと**です。

---

## 成果物を育てる、型・技・流

SpecDojoは、作業を記録するだけでなく、成果物を継続的に育てる仕組みを目指しています。

| 考え方         | 役割                                               |
| -------------- | -------------------------------------------------- |
| **型（Kata）** | 規約、作り方、完成例、ひな形で成果物の品質を支える |
| **技（Waza）** | 登録、実行、評価など、作業を進めるための仕組み     |
| **流（Ryu）**  | プロジェクトの状況に合わせて進め方を選ぶ考え方     |

一つの正しい工程を全員に押しつけるのではなく、目的に合う成果物と進め方を選びます。

**Continuous Specification Engineering（継続的仕様エンジニアリング）**

仕様を一度「完成」させるのではなく、要求、判断、成果物、検証の関係を変化に合わせて保ち続ける。その実践を、SpecDojoは支援します。

※Kata・Waza・Ryuに関する個別機能は、実装状況に応じて提供範囲が異なります。

## はじめよう

### 今できること、その先へ

**register** は、一件ずつの記録、判断、作業を扱う入り口です。そこから、**schedule** による計画と実行、**routine + job** による繰り返しの仕事、Kataによる成果物の品質管理へと拡張していきます。

機能の提供状況は更新されるため、最新の利用可能範囲はドキュメントとリリース情報をご確認ください。
