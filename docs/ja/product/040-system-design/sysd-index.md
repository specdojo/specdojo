# SpecDojo システム設計索引（SYSD Index）

本書は、SpecDojo のシステム設計における正本（SSOT: Single Source of Truth）、自動生成物、変更の入口、および関連仕様への導線を 1 箇所に集約するシステム設計索引（SYSD Index）である。設計情報をコード・スキーマ・宣言的定義ファイルへ寄せる運用（Code as Spec）に基づき、各設計要素の詳細は正本へ委ね、本書では正本の所在、非該当領域の理由、ロール別の責務、検証経路、公開前確認条件を定義する。

## 1. 概要（対象範囲・更新責任）

対象範囲は、SpecDojo CLI 本体（`src/`）、JSON Schema 群（`docs/specdojo/schemas/v1/`、`docs/ja/specdojo/schemas/v1/`）、静的ドキュメントサイト生成（`packages/docs-site/`）、VS Code 拡張（`packages/vscode-specdojo/`）、外部 AI エージェント実行基盤、Git / worktree 統合、および反復ジョブ（Job）・定期処理（Routine）・継続品質評価（Grade）である。

### 1.1. ロール別の更新・確認・承認責務

| ロール                           | 責務区分       | 対象と確認・判断内容                                                                                                                    |
| -------------------------------- | -------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| アーキテクト（`ARC`）            | 更新・構造整合 | 本書（`sysd-index`）、システム設計分冊（`sysd-*`）、技術スタック（`tsd-*`）、外部連携契約（`ifx-*`）、機能間依存境界の定義と整合維持    |
| 開発者（`DEV`）                  | 更新・実装検証 | CLI 実装（`src/`）、JSON Schema、状態マイグレーション、自動生成コマンド、単体・統合テストの実装と保守                                   |
| プロジェクトマネージャー（`PM`） | 更新・計画管理 | カタログ（`dct-*`）、スケジュール（`sch-*`）、登録簿（`pjr-*`）、変更タスクの実行計画と未作成文書・廃止文書に伴う依存リスク管理         |

### 1.2. 主要略語

- **SSOT（Single Source of Truth）**: 各設計・実装要素について最優先で更新・参照する唯一の正本。
- **SYSD（System Design）**: システム設計（`sysd-index`、`sysd-cross-cutting-policy`、`sysd-critical-flows`、`sysd-*`）。
- **TSD（Technology Stack Definition）**: 技術スタック定義（`tsd-index`、`tsd-*`）。
- **CDFD / CDSD / STSD**: 概念データフロー図（Conceptual Data Flow Diagram）/ 概念データストア定義（Conceptual Data Store Definition）/ 状態遷移仕様（State Transition Specification）。
- **IFX / CLIS**: 外部インターフェース仕様（External Interface Specification）/ CLI 仕様（Command Line Interface Specification）。
- **NFR / OPD / OPR / DEC**: 非機能要件（Non-Functional Requirements）/ 運用方針・設計（Operations Policy and Design）/ 運用手順（Operations Procedure）/ 決定記録（Decision Record）。
- **PJR / CPM**: プロジェクト登録簿（Project Register）/ クリティカルパス法（Critical Path Method）。

### 6.2. 公開・`status: ready` 昇格前の確認条件

本書を `status: draft` から `status: ready` へ昇格（または外部公開）する際は、以下の確認完了を条件とする。

- **アーキテクト（`ARC`）・開発者（`DEV`）確認**: `SSOT 一覧（表形式）` の全パス・スキーマ・実装モジュールおよび `自動生成物（生成コマンド/生成先/閲覧先）` の全コマンドが実在し、`npm run typecheck`、`npm run check:src-imports`、`npm run validate:schema`、`npm run lint:fm`、`npm run lint:md` がすべて終了コード `0` で通過していること。
- **業務分析担当（`BA`）・プロジェクトマネージャー（`PM`）確認**: `関連ドキュメント導線（C4 / NFR / OPD / DEC 等）` に廃止済み（`deprecated` / trash 移動済み）文書への参照がなく、未作成文書の起票・依存関係がカタログ（`dct-*.yaml`）およびスケジュールと整合していること。
- **運用担当（`OPS`）・品質保証担当（`QE`）確認**: `変更の入口（典型ケース）` の各検証コマンドとテスト対象ケースが実行可能であり、Job・Routine・保護ガード・機密検査の運用導線が追跡可能であること。
- **プロダクトオーナー（`PO`）最終承認**: `未決事項と後続作業への影響` に記載された未作成文書（C4 図、`ifx-index`、`opd-*`、`opr-*`、`nfr-index`）の留保範囲または解消結果を確認し、人間の `PO` が PR レビューを通じて `status: ready` への昇格を承認すること（エージェントによる `status: ready` への変更は行わない）。
