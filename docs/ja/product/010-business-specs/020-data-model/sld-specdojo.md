# 保管場所一覧（SpecDojo）

## 1. 概要

SpecDojo がプロジェクト計画・タスク実行・品質評価・定期処理・情報共有で用いる記録とファイルについて、保管場所ごとの「置くもの」「Git で共有するか」「寿命・管理頻度」「消してよいか（削除可否と条件）」を一覧として定義する。[[prj-0001:prj-overview|プロジェクト概要: SpecDojo]] が掲げる「計画・実行・検査の記録を同じルールで追跡可能にしつつ、並行作業やブランチ統合で生成物の競合を起こさない」という方針を、ディレクトリ配置と運用判断の面から具体化する。

ARC・DEV は保管場所の区分と共有制御（Git 追跡・`.gitignore`・端末ローカル分離・worktree 分離）が実装の配置と一致しているかを確認する。BA は概念データストア定義（CDSD）で定義された管理単位の保管先が漏れなく網羅されているかを確認し、OPS は運用・保守・障害対応時に「消してよい場所」と「残すべき場所」を判断する基準として利用する。QE は受入条件の照合を行い、人間の PO が保管・保持方針を最終承認する。

### 1.1. 対象範囲と隣接仕様との分担

本書は SpecDojo が扱うリポジトリ内領域（`docs/`、`execution/`、`controls/`、派生ビュー `generated/`、`.specdojo/`、`archive/`）、端末側の状態ディレクトリ（`${XDG_STATE_HOME:-~/.local/state}/specdojo/`）、タスク実行用 worktree、および一時ディレクトリを対象とする。

| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| [[cdsd-planning\|概念データストア定義（プロジェクトの立上と計画）]]、[[cdsd-execution\|概念データストア定義（プロジェクト実行）]]、[[cdsd-sharing\|概念データストア定義（活用と共有）]] | CDSD は概念上の管理単位・正本区分・更新責務を定義する。本書はそれらが配置される物理・論理パス、Git 共有の有無、寿命、削除可否を定義する |

補足（旧配置との互換性）:

- 実行記録の旧配置（`execution/exec/{plans,results}/`）: 過去の監査証跡として `削除不可`。新規の実行記録は `execution/runs/` を正本とする。
- 定期処理状態の旧配置（`routines/generated/`）: 端末状態ディレクトリへの移行完了後に整理（削除）可。

## 3. 削除・退避・復旧の判断基準

### 3.1. 削除可否の3区分と運用者の判断基準

運用者（OPS）および開発者（DEV）は、ディスク容量整理・障害復旧・環境再構築にあたり、次の3区分に従って消してよい場所と残すべき場所を判断する。

| 削除可否区分     | 対象となる保管場所                                                                                                                                                                                                                                   | 判断基準と誤削除時の影響                                                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `削除不可`       | `docs/<lang>/product/`、`docs/<lang>/specdojo/`、`docs/specdojo/schemas/`、`docs/<lang>/projects/<id>/` の定義・計画・`controls/`・`execution/`（`generated/` と `.locks/` を除く）、`archive/`、端末側の `routine-state.json`・`routine-runs.jsonl` | 仕様・計画・台帳・実行証跡の正本（SSOT）または端末上の定期実行履歴である。削除すると監査証跡や未同期の定期処理状態が失われるため、日常運用で削除しない   |
| `条件付き削除可` | `execution/exec/.locks/`、端末側の `.locks/routine-run.lock`、`<worktree_base>/<task-name>/`                                                                                                                                                         | 稼働中プロセスの排他制御または未統合の作業領域である。所定の前提条件（プロセス非稼働、ブランチ統合済みまたは破棄合意済み）を確認した場合に限り削除できる |
| `削除可`         | `docs/**/generated/`、`.specdojo/doc-index.json`、リポジトリ／worktree 直下の `tmp/`、OS の `/tmp`、ビルドキャッシュ                                                                                                                                 | 正本からいつでも再生成できる派生ファイル、または単発作業の一時ファイルである。削除しても正本データは失われず、再ビルドで完全に復旧できる                 |

### 3.2. 場面別の対処と禁止操作

| 場面                                                              | 運用者・開発者の確認手順と対処                                                                                                                                                                                                                         | 禁止操作とエスカレーション先                                                                                                                                         |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `generated/` の表示崩れや `.specdojo/doc-index.json` の索引不整合 | 対象の `generated/` 配下（`.gitkeep` を除く）または `.specdojo/doc-index.json` を削除し、`specdojo build`（または `index build` / `catalog build` / `register build` / `exec refresh`）を実行する                                                      | `generated/` 内の Markdown を手編集して正本修正の代わりにしてはならない。再生成でエラーが出る場合は正本 YAML・Markdown を DEV・ARC が確認する                        |
| `exec run` や `routine run` がロック競合で開始できない            | 同一リポジトリ／同一端末で実際に `exec run` または `routine run` のプロセスが稼働中か確認する。稼働プロセスが存在しない（異常終了による孤立ロック）と確認できた場合のみ `.locks/` 配下のロックを削除する                                               | 稼働確認を行わずにロックを強制削除してはならない（並行実行による `runs/` や `routine-state.json` の破損を防ぐため）                                                  |
| `<worktree_base>` 配下にタスクの worktree が残存している          | 1) 実行中の runner がないか確認する。2) `exec status` や `git status` / `git log` で `exec/<task-name>` の変更が統合済みか確認する。3) `--resume` で再開予定の失敗タスクや未レビューの `branch-only` タスクでなければ `git worktree remove` で削除する | 実行中タスク、再開予定（`incomplete` / `failed`）のタスク、未統合の `branch-only` タスクの worktree を無断で `rm -rf` してはならない。判断不能時は PM・PO へ確認する |
| 仕様書や計画文書が廃止・統合により不要になった                    | 直接 `git rm` で履歴ごと消去せず、[[specdojo:document-metadata-standard\|ドキュメントメタ情報標準]] に従い `status: deprecated` と `supersedes` を設定するか、`archive/` へ移動して `links.json` を更新する                                            | 参照元（カタログ・Schedule・既存 `plan.md` / `result.md`・`pjr-*`）を確認せずに正本ファイルを削除してはならない                                                      |
