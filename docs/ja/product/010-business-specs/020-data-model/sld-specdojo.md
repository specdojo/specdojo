# 保管場所一覧（SpecDojo）

## 1. 概要

SpecDojo がプロジェクト計画・タスク実行・品質評価・定期処理・情報共有で用いる記録とファイルについて、保管場所ごとの「置くもの」「Git で共有するか」「寿命・管理頻度」「消してよいか（削除可否と条件）」を一覧として定義する。[[prj-0001:prj-overview|プロジェクト概要: SpecDojo]] が掲げる「計画・実行・検査の記録を同じルールで追跡可能にしつつ、並行作業やブランチ統合で生成物の競合を起こさない」という方針を、ディレクトリ配置と運用判断の面から具体化する。

保管場所の区分と共有制御（Git 追跡・`.gitignore`・端末ローカル分離・worktree 分離）が実装の配置と一致しているか、概念データストア定義（CDSD）で定義された管理単位の保管先が漏れなく網羅されているかを確認する。運用・保守・障害対応時に「消してよい場所」と「残すべき場所」を判断する基準としても利用する。

### 1.1. 対象範囲と隣接仕様との分担

本書は SpecDojo が扱うリポジトリ内領域（`docs/`、`execution/`、`controls/`、派生ビュー `generated/`、`.specdojo/`、`archive/`）、端末側の状態ディレクトリ（`${XDG_STATE_HOME:-~/.local/state}/specdojo/`）、タスク実行用 worktree、および一時ディレクトリを対象とする。

| 隣接仕様・正本                                                                                                                                                                          | 本書（`sld-specdojo`）との分担                                                                                                          |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| [[cdsd-planning\|概念データストア定義（プロジェクトの立上と計画）]]、[[cdsd-execution\|概念データストア定義（プロジェクト実行）]]、[[cdsd-sharing\|概念データストア定義（活用と共有）]] | CDSD は概念上の管理単位・正本区分・更新責務を定義する。本書はそれらが配置される物理・論理パス、Git 共有の有無、寿命、削除可否を定義する |

- 実行記録の旧配置（`execution/exec/{plans,results}/`）: 過去の監査証跡として `削除不可`。新規の実行記録は `execution/runs/` を正本とする。

## 3. 削除・退避・復旧の判断基準

### 3.1. 削除可否の3区分と運用者の判断基準

運用者（OPS）および開発者（DEV）は、ディスク容量整理・障害復旧・環境再構築にあたり、「保管場所一覧」の「削除・処分の可否と条件」列で各保管場所の区分を確認し、次の区分ごとの規則で判断する。

| 削除可否区分     | 区分の判断規則                                                                                                                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `削除不可`       | 日常運用で削除しない。不要化・廃止時は「場面別の対処と禁止操作」の廃止・統合の手順に従う                                                                                                                            |
| `条件付き削除可` | 一覧に記載した前提条件（プロセス非稼働、統合済みまたは破棄合意済み、再開予定なし）をすべて確認できた場合に限り削除する。確認できない場合は残す                                                                      |
| `削除可`         | 削除後に一覧に記載した再生成コマンドで復旧する。同じ親ディレクトリに `削除可` 以外の区分の場所（`generated/` 配下の品質評価の実行時状態や未移行の旧定期処理状態など）が含まれる場合は、それらを除外してから削除する |

### 3.2. 場面別の対処と禁止操作

| 場面                                                              | 運用者・開発者の確認手順と対処                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | 禁止操作とエスカレーション先                                                                                                                                                                                                                                                 |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `generated/` の表示崩れや `.specdojo/doc-index.json` の索引不整合 | 1) `execution/grade/generated/` を対象に含む場合は、稼働中の `grade run` がないこと、および `runs/<run-id>/` に再開予定の run がないことを確認し、該当する `run.lock`・`runs/<run-id>/` を削除対象から除外する。2) `routines/generated/` を対象に含む場合は、移行先の端末側状態ディレクトリに `routine-state.json`・`routine-runs.jsonl` が存在することを確認するまで旧ファイルを除外する。3) 残りの `generated/` 配下（`.gitkeep` を除く）または `.specdojo/doc-index.json` を削除し、`specdojo build`（または `index build` / `catalog build` / `register build` / `exec refresh`）を実行する | `generated/` 内の Markdown を手編集して正本修正の代わりにしてはならない。`generated/` を一括削除して稼働中の `grade run` のロックや再開状態、未移行の定期処理履歴を消してはならない。再生成でエラーが出る場合は正本 YAML・Markdown を DEV・ARC が確認する                    |
| `exec run` や `routine run` がロック競合で開始できない            | 同一リポジトリ／同一端末で実際に `exec run` または `routine run` のプロセスが稼働中か確認する。稼働プロセスが存在しない（異常終了による孤立ロック）と確認できた場合のみ `.locks/` 配下のロックを削除する                                                                                                                                                                                                                                                                                                                                                                                        | 稼働確認を行わずにロックを強制削除してはならない（並行実行による `runs/` や `routine-state.json` の破損を防ぐため）                                                                                                                                                          |
| `<worktree_base>` 配下にタスクの worktree が残存している          | 1) 実行中の runner がないか確認する。2) `exec status` や `git status` / `git log` で `exec/<task-name>` の変更が統合済みか確認する。3) `--resume` で再開予定の失敗・中断タスクでなければ `git worktree remove` で削除する。統合処理の成功後は `branch-only` を含め worktree は撤去済みであり、残るのは `branch-only` の exec branch だけである                                                                                                                                                                                                                                                  | 実行中タスク、再開予定（`incomplete` / `failed`）のタスクの worktree を無断で `rm -rf` してはならない。worktree の削除と同時に未統合の `branch-only` の exec branch を削除してはならない（プロダクト側の PR 作業を終えてから退避・削除する）。判断不能時は PM・PO へ確認する |
| 仕様書や計画文書が廃止・統合により不要になった                    | 直接 `git rm` で履歴ごと消去せず、[[specdojo:document-metadata-standard\|ドキュメントメタ情報標準]] に従い `status: deprecated` と `supersedes` を設定するか、`archive/` へ移動して `links.json` を更新する                                                                                                                                                                                                                                                                                                                                                                                     | 参照元（カタログ・Schedule・既存 `plan.md` / `result.md`・`pjr-*`）を確認せずに正本ファイルを削除してはならない                                                                                                                                                              |

## 5. 確認事項と変更影響

上位の概念データストア定義（`cdsd-planning`、`cdsd-execution`、`cdsd-sharing`）から引き継ぐ未決事項・今後の整備予定と、変更時の影響範囲は次のとおりである。

| 論点・区分                                                 | 現在の判断・影響                                                                                                                                                                                                                                                                   | 担当・判断時期・次の行動                                                                                                                                                                                                                           | 追跡先                                                                                                                                                                                   |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 監視結果・費用作業記録の物理保管先と保持期間（留保）       | `_UNDECIDED_`: [[cdsd-sharing\|概念データストア定義（活用と共有）]] は監視結果と費用・作業記録を定義し、監視結果と報告記録の保管先・保持期間・公開範囲を未決としている。本書は実装が存在する保管場所のみを確定記載し、両記録の行は追加していない                                   | OPS・ARC がリポジトリ内（`reporting/` 等）と端末ローカルの方式を比較し、PO が決定する。期限は報告・監視の運用開始前とし、本書の `status: ready` 昇格判断の時点で未決なら PO が留保の継続可否を判断する。決定後に「保管場所一覧」へ該当行を追加する | [[cdsd-sharing\|概念データストア定義（活用と共有）]] が追跡先とする `prj-0001:cdfd-reporting` の未決事項。期限までに決まらない場合は PM が決定事項（`decision`）として管理台帳へ起票する |
| CDSD 追加候補の正式登録と対応表の更新（計画済み作業）      | 追加候補（タスク実行状態、実行計画と実行結果、実行証跡（Evidence）、タスク実行 worktree、成果物本体、成果物索引、プロジェクト構成、成果物カタログ）は実装上の配置が確定しているため、本書で保管場所を定義済みである。CDSD 側の一覧への登録だけが未了であり、本書の未決事項ではない | 各 CDSD の「概要」の予定どおり、BA が対応する業務データ辞書の作成時に CDSD の一覧へ追加する。ARC は同じ改訂で本書の「概念データストア・実装配置との対応」の記述を正式名称へ更新する                                                                | 計画済み作業のため Schedule の業務データ辞書作成・CDSD 改訂で扱い、管理台帳へは起票しない（二重追跡を防ぐ）。該当タスクが Schedule にない場合は PM が Schedule へ追加する                |
| 保管場所のパス規則・Git 共有設定を変更する場合（変更影響） | `runs/` の階層、`${XDG_STATE_HOME}` のハッシュ規則、`<worktree_base>` の既定パス、または `generated/` の `.gitignore` 設定を変更すると、既存履歴の参照やビルド・排他制御へ波及する                                                                                                 | ARC・DEV が `src/shared/run-records.ts`・`src/routine/storage.ts`・`src/shared/local-state.ts`・`src/exec/worktree.ts` の移行処理（`migrateRoutineStorage` 等）と互換性を設計し、OPS・QE が検証したうえで PO が承認する                            | 変更発生時に PM が変更要求（`change-request`）として管理台帳へ起票する                                                                                                                   |

本書の公開は、上記受入条件の確認完了と未決事項の扱いの確定後に行う。
