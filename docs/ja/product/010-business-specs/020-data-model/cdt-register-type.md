# 分類一覧（登録項目の種別）

登録簿で追跡する登録項目の分類（`item_type`）について、各値が何を追跡し、どの結果で通常の追跡を終えるかの使い分けを定義する。

## 1. 概要

- 業務目的: 担当が交代しても、起票者が選んだ分類から追跡の目的・終了の仕方・承認者を読み取れるようにし、判断や作業を特定個人の記憶に依存させない。
- 対象エンティティ: 登録項目（`register_entry`）。属性の定義は [[prj-0001:bdd-register-entry|業務データ辞書（登録項目個票）]] を正とする。
- 主担当ロール: BA（分類の業務的意味と使い分けの定義）、PO（区分けの方針確認）
- 利用者: DEV（schema enum・CLI の許容値との対応確認）、QE（分類別の終端・承認条件の検証）、登録項目を起票・更新する PM と各 owner
- 適用範囲: 個票 Frontmatter の `item_type` と、起票時に指定する分類（`register add` の `--type`）。状態遷移と分類別の終了承認は [[prj-0001:stsd-register-entry|ステータス定義（登録項目個票）]] を正とし、本書では分類の選び方に必要な範囲だけを示す。

## 2. 分類定義

| 定義項目         | 内容                                                                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 対象エンティティ | 登録項目（`register_entry`）                                                                                                                      |
| 分類定義名       | 分類（`item_type`）                                                                                                                               |
| 種別             | 業務分類                                                                                                                                          |
| 正本参照（SSOT） | `schema_ref: docs/specdojo/schemas/v1/register-item-frontmatter.schema.yaml#/$defs/ItemType`（CLI の検証値は `src/register/item.ts#VALID_TYPES`） |
| 説明             | 何を追跡し、どの結果をもって通常の追跡を終えるかを分ける区分。終端（完了か決定済みか）、終了を承認する人、派生ビューへの振り分けを決める          |

## 3. 値の業務的意味と使い分け

値の一覧と識別子はスキーマ `ItemType` を正本とする。CLI は起票・更新時に `VALID_TYPES` で同じ値を検証し、それ以外の値を拒否する。

| 値               | 分類名   | 業務上の意味と使い分け                                                                                                                                                                      |
| ---------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `todo`           | 作業     | 実施することが決まっている具体的な作業。やるかどうか自体が未定なら `question` か `decision`、仕様・計画の変更要望なら `change-request` を使う。対応を確認して完了で終える                   |
| `epic`           | エピック | 一つの `track` 全体の計画と、着手・完了の判断を担う項目。作業そのものは `derived_from` でつないだ子 `todo` で行う。子の状態からは自動で完了せず、子項目と Schedule を見て人が完了を判断する |
| `question`       | 問い     | 回答や確認が必要な事項。回答が確定したら決定済みで終える。回答によって選択肢から方針を選ぶ必要が出たら `decision`、作業が発生したら `todo` を起票する                                       |
| `risk`           | リスク   | まだ起きていない懸念。起きた時点で `issue` として起票する。リスクオーナーが対応完了か受容を判断して完了で終える                                                                             |
| `issue`          | 課題     | すでに起きている問題。未発生の懸念は `risk` に分ける。課題リードが対応を確認して完了で終える                                                                                                |
| `change-request` | 変更要求 | 承認済みの成果物・仕様・計画を変える要望。新しく決める事項ではなく既存の合意を変える場合に使う。変更承認権限者（PO / CCB）の承認後に完了で終え、承認には PR approve を求める                |
| `decision`       | 判断     | 記録・追跡する意思決定。複数の選択肢から当該領域の意思決定者が決め、決定済みで終える。決定後に必要な作業は `todo` として起票する                                                            |
| `note`           | 記録     | 共有・備忘のために継続更新する記録。審査や終了承認の対象にせず、起票済みのまま更新を続ける。対応・回答・判断が必要になったら、その内容に合う分類で別の項目を起票する                        |

分類を選ぶときは次の順で判断する。

1. 対応や判断を要さず、記録を残すことが目的なら `note`。
2. 答えるべき問いなら `question`、選択肢から決めるべき事項なら `decision`。
3. 問題がすでに起きていれば `issue`、まだ起きていなければ `risk`。
4. 承認済みの内容を変える要望なら `change-request`。
5. 一つの `track` 全体の計画と完了判断なら `epic`、具体的に実施する作業なら `todo`。

## 4. 関連仕様との関係

- 業務データ辞書: [[prj-0001:bdd-register-entry|業務データ辞書（登録項目個票）]] の `item_type` の許容値と区分の説明に対応する。分類名は同辞書の論理名・ラベルに合わせる。
- 状態定義: [[prj-0001:stsd-register-entry|ステータス定義（登録項目個票）]] が、分類別の終端（`decision`・`question` は決定済み、`note` 以外の他分類は完了）、終了承認者、`note` の継続記録を定める。
- 派生ビュー: 登録簿の生成時に、`epic` はエピック別の子項目一覧、`risk`・`issue`・`change-request`・`decision` はそれぞれリスク登録簿・課題ログ・変更要求ログ・決定ログへ振り分けられる。`todo`・`question`・`note` は分類別の専用ビューを持たず、一覧と状態・優先度・担当別ビューで扱う。
- commit 種別: 個票・リポジトリ・プロジェクトで指定がない場合、分類から既定の commit 種別が決まる（`issue` は `fix`、`todo`・`change-request`・`epic` は `feat`、他は `docs`）。
