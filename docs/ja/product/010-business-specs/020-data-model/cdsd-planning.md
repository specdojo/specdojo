# 概念データストア定義（プロジェクトの立上と計画）

## 1. 概要

プロジェクトの立上と計画で扱う概念データストアのうち、登録簿と Schedule について、業務上の役割、内容、粒度、更新責務を一覧で定義する。BA は登録簿と計画済み作業の管理境界の確認に、ARC は正本と派生物の区別を設計の基礎に、QE はデータ検証・整合性確認の対象の識別に利用する。

- 本書は登録簿ライフサイクル、進捗監視・報告の各 CDFD に記載していたデータ正本と type 区分の詳細を移設したものである。
- 登録項目の状態・遷移・日時の記録規則は [[prj-0001:stsd-register-entry|ステータス定義（登録項目個票）]] を正本とし、本書では再定義しない。
- _TODO_: プロジェクト構成、成果物カタログ、Schedule 戦略のデータストアは、対応する業務データ辞書の作成時に追加する。

## 2. 概念データストア一覧

| データストア名           | 対応プロセス                         | 主な内容                                                                           | 更新タイミング                         | 粒度                       | 主な用途                                                       |
| ------------------------ | ------------------------------------ | ---------------------------------------------------------------------------------- | -------------------------------------- | -------------------------- | -------------------------------------------------------------- |
| 登録項目個票             | 登録簿ライフサイクル、定期処理、報告 | type、状態、優先度、担当、期限、登録日時、完了日時、説明、結論、追記型の変更 event | 随時（起票時・状態変更時・内容更新時） | 登録項目毎                 | 計画外事項・判断事項の追跡、審査・承認の証跡、監視と報告の根拠 |
| Schedule・マイルストーン | 計画展開、タスク実行、報告           | 計画済みタスク、依存、担当、マイルストーンと依存 task                              | 変更時（カタログ・戦略・計画の変更時） | タスク毎、マイルストーン毎 | 計画済み作業の実行順序、進捗・達成見込みの判断                 |

## 3. 正本区分と更新責務

| データストア名           | 位置づけ                               | 主な生成・更新       | 利用時の扱い                                                                  | 更新責務                  |
| ------------------------ | -------------------------------------- | -------------------- | ----------------------------------------------------------------------------- | ------------------------- |
| 登録項目個票             | 課題・リスク・変更要求・決定などの正本 | 登録簿ライフサイクル | 一項目一ファイルの Frontmatter と本文を正本とし、報告記録から逆に書き戻さない | 項目 owner、type 別承認者 |
| Schedule・マイルストーン | 計画・状態遷移の正本                   | 計画展開、タスク実行 | 報告・監視では参照のみ行い、変更は計画展開・タスク実行へ委譲する              | PM、task owner            |

登録項目一覧、状態別・優先度別・担当者別ビュー、リスク・課題・変更要求・決定の管理ビューは登録項目個票から再生成する派生物であり、[[prj-0001:cdsd-sharing|概念データストア定義（活用と共有）]] で扱う。実行 event は [[prj-0001:cdsd-execution|概念データストア定義（プロジェクト実行）]] で扱う。

## 4. 登録簿と Schedule の管理区分

登録項目個票へ記録する事項を type で区分し、計画済み作業を扱う Schedule との境界を示す。

| 区分             | 登録する判断                                                                     | 主な次の行動                                                   |
| ---------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `todo`           | 実施が決まった計画外の単発作業で、担当・期限・完了を追跡する必要がある           | 人または AI Agent が対応し、結果を審査する                     |
| `question`       | 回答権限者による回答・確認が必要である                                           | 調査結果と回答者を記録し、決定済みとして終了する               |
| `risk`           | まだ顕在化していない懸念について、対応方針・受容・延期を判断する必要がある       | リスクオーナーが方針を審査する                                 |
| `issue`          | 既に発生した問題について、解消または対応判断を追跡する必要がある                 | 課題リードが対応結果を審査する                                 |
| `change-request` | 成果物、仕様、計画、構成の変更について、実施前の承認が必要である                 | PO / CCB が承認対象差分を審査する                              |
| `decision`       | 選択肢、決定、理由、承認証跡を後から参照できるようにする必要がある               | 意思決定者が内容を確定し、決定済みとして終了する               |
| `note`           | 回答・対応・承認を要求せず、共有・備忘として残す必要がある                       | 起票済みのまま記録を更新し続け、終端させない                   |
| Schedule         | カタログに定義された成果物の作成・レビュー・確定、または依存に基づく計画済み作業 | 計画展開で計画し、タスク実行で実行する。登録簿へ重複登録しない |

登録後に事項が計画済みの成果物作業へ移る場合は、個票へ移管先と結論を残して終了し、実作業は Schedule 側だけで追跡する。
