# ステータス定義（登録項目個票）

## 1. 概要

登録簿で追跡する計画外事項・判断事項（登録項目）について、現行運用（AS-IS）の起票から対応、審査、終了、再開までの状態と遷移を定義する。項目 owner と type 別承認者は現在状態から次の行動と終了判断を、ARC・QE・DEV は状態遷移の設計・検証・実装の基礎として利用する。状態と判断の記録を共通正本に集約して誤終了・判断漏れ・引継ぎ不能を防ぎ、プロジェクトの `BV-03`（無理のない継続）を支える。

- 対象: 登録簿の一項目一ファイルの個票で管理する登録項目（`epic`、`todo`、`question`、`risk`、`issue`、`change-request`、`decision`、`note`）
- スコープ: 現行運用（AS-IS）の起票、担当・対応方針設定、人または AI Agent による対応・調査、審査・終了判断、終了項目の再開
- 状態の正本: 個票 Frontmatter の `item_status`。文書の成熟度を表す `status` とは区別する。登録日時・完了日時・結論はそれぞれ `registered_at`・`completed_at`・`conclusion` で保持する。登録項目一覧や状態別ビューは個票から再生成する派生物である
- 一意判定: `item_status` の単一の値で現在状態を判定する。履歴は個票とは別の追記型 event ファイルで管理し、遷移元・遷移先・実行者・理由を記録する。状態変更後は履歴の最終到達状態と現在状態を一致させる
- 日時の記録: 登録日時と完了日時は UTC・RFC 3339・秒精度で個票へ保持する。一覧の登録日・完了日はプロジェクトの IANA タイムゾーンへ変換した暦日として導出し、期限は同タイムゾーン上の暦日として保持する
- 終了点を置かない理由: 業務上の到達点は完了・決定済み・却下・延期である。いずれも再評価のため再開できる状態として管理を続け、ライフサイクルを閉じない。本書の全図を通して、出力遷移のない継続状態はない
- AI Agent の責任範囲: AI Agent は対応・調査と検証を支援するが項目を終端化しない。完了・決定・却下・延期・再開の判断は人間が担う

`epic` は Frontmatter の `track` で track を担い、具体的な作業は `derived_from` でつないだ子 todo で実施する。自身は `exec run --register` と夜間 queue の対象にしない。子項目と schedule を判断材料に人が close し、子の状態から自動遷移しない。

活動中は起票済み・対応中・待機中・審査待ち、終端は完了・決定済み・却下・延期とする。活動中のどの状態からも、人間が必要な確認・承認を終えれば直接終端へ進める。終端からは再評価の準備状況に応じて活動中の四状態へ直接再開でき、起票済みを経由した二段階の遷移とは扱わない。業務上の承認・証跡条件と CLI が強制する制約は第 4 章で区別する。

### 1.1. type 別の審査・承認と到達できる状態

| type             | 審査・承認者               | 主な終了・継続判断                                 | 既定の証跡       |
| ---------------- | -------------------------- | -------------------------------------------------- | ---------------- |
| `change-request` | 変更承認権限者（PO / CCB） | 承認後に完了、または却下・延期・待機               | PR approve       |
| `decision`       | 当該領域の意思決定者       | 決定済み、または却下・延期・追加確認の待機         | 個票と commit    |
| `risk`           | リスクオーナー             | 対応完了・受容による完了、延期、追加確認の待機     | 個票と commit    |
| `question`       | 回答権限者                 | 回答確定後に決定済み、または追加確認の待機         | 個票と commit    |
| `issue`          | 課題リード                 | 対応確認後に完了、または却下・延期                 | result と commit |
| `epic`           | track の完了を判断する人   | 子項目と schedule を確認して完了、または却下・延期 | 個票と commit    |
| `todo`           | 項目 owner・レビュー担当   | 対応確認後に完了、または延期・待機                 | result と commit |
| `note`           | 審査・承認の対象外         | 審査へ進めず、起票済みのまま記録を更新し続ける     | 個票と commit    |

既定は commit による証跡とする。PR 承認を強制するのは、`develop → main` 昇格、`change-request` 承認、不可逆・高リスク・framework schema 破壊的変更の三ケースである。詳細は [[specdojo:register-operation-guide|登録簿運用ガイド]] と [[specdojo:git-branching-standard|Git ブランチ運用標準]] を正とする。

## 2. 状態一覧

`owner`・`due_on` は省略でき、`due_on` の省略は期限未定、明示的な null は期限なしを示す。業務上の遷移条件と現行制約は第 4 章、未解決の依存と実装差異は第 5 章に示す。

| 値            | 状態名   | 通称   | 意味                                                                        | 成立条件                                                    | 管理場所         |
| ------------- | -------- | ------ | --------------------------------------------------------------------------- | ----------------------------------------------------------- | ---------------- |
| `open`        | 起票済み | 未着手 | 起票または再開され、対応に着手していない項目。`note` では継続更新できる記録 | `item_status` が `open`（未設定・空欄時も読み取りでは同値） | 個票 Frontmatter |
| `in-progress` | 対応中   | -      | 担当者または AI Agent が対応・調査している項目                              | `item_status` が `in-progress`                              | 個票 Frontmatter |
| `waiting`     | 待機中   | 保留   | 外部回答、前提解消、失敗復旧、審査材料の補完を待つ項目                      | `item_status` が `waiting`                                  | 個票 Frontmatter |
| `review`      | 審査待ち | -      | 対応結果について人間の審査・承認を待つ項目                                  | `item_status` が `review`                                   | 個票 Frontmatter |

| `rejected`    | 却下     | -      | 対応・変更を行わないと判断した項目                                          | `item_status` が `rejected`                                 | 個票 Frontmatter |
| `deferred`    | 延期     | -      | 現時点では実施せず、再評価条件の成立を待つ項目                              | `item_status` が `deferred`                                 | 個票 Frontmatter |

## 3. 状態遷移図

業務状態は 8、遷移は 40 で、遷移数 20 と一状態の入出力合計 6 の閾値を超えるため、活動・終了判断・再開の三図に分ける。3.1 と他図の接続状態は活動中の四状態、3.2 と 3.3 の接続状態は全八状態である。同じ状態は同じ表示名と `state_id` を使い、初期点は 3.1 にだけ置く。

## 4. 遷移の説明

### 4.1. 業務上の条件

各行の条件と次の共通条件をすべて満たす場合に pass、一つでも不足する場合に fail とする。CLI が操作を受け付けることだけでは業務上の承認・証跡の充足と判定しない。

- 活動中の遷移・終了判断は `note` 以外を対象とする。`note` は `T-02` の記録更新を続け、対応・回答・判断が必要になったら別項目を起票する。
- 着手・再対応: 対応方針と人または AI Agent の対応経路を記録し、待機を要する外部依存がないことを確認する。担当・期限は未定でもよい。
- 待機: 待機理由を `block_reason`、再開条件を個票本文へ記録し、`conclusion` は変更しない。審査差し戻しでは不足情報と取得責任者も記録する。待機を離れるときは `block_reason` を削除し、元の理由は履歴で保持する。
- 審査提出: 対応結果、実施した検証とその結果、承認対象、証跡候補を確認できる。情報が不足すれば提出せず、補完待ちは待機で扱う。
- 終了判断: 1.1 の人間の承認者、判断内容と理由、既定の証跡を確認できる。完了・決定済みは対応結果・検証結果の確認も必要とし、審査待ちを経由しない場合も省略しない。完了・決定済み・却下では `conclusion` と `completed_at` を記録する。延期では延期理由を `conclusion`、再評価条件を本文へ記録し、完了日時は付与しない。
- 再開: 1.1 の承認者が再評価対象と理由を確認し、承認の証跡を残す。旧結論・延期理由を保存し、再開理由を履歴へ追記し、`completed_at` を削除する。再開先は一つ選ぶ。起票済みは未着手、対応中は着手条件、待機中は待機理由・再開条件、審査待ちは審査提出条件を満たすことを確認する。待機中への直接再開では別途 `block_reason` を記録する。

### 4.2. 現行制約との対応

業務イベントの対応先を以下に示す。`src/register/transition-commands.ts` と `src/register/update.ts` で確認した現在動作であり、業務条件の自動検証を保証するものではない。共通して `item_status` を遷移先へ更新し、待機中以外では `block_reason` を削除する。状態が変わる操作は個票更新と別に event を作成する。

| ------------------------------ | ----------------- | --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

`start`・`wait`・`review` は活動中のどの状態からも受け付け、現在と同じ状態の指定も受け付ける。同じ状態の指定や通常のフィールド更新は業務状態の変化を増やさないため、`note` の継続記録を表す `T-02` を除き自己遷移として列挙しない。活動中から起票済みへ戻す操作、終端から別の終端への直接変更は定義しない。終端の状態変更には再開を先に行う。現行 CLI と業務上の制限が異なる点は `M-01` に残す。

### 4.3. 後続検証へ渡す判定基準

4.1 の各 T-ID と共通条件を許可経路・成立条件・記録結果の判定基準とし、表にない状態変更と条件不足は業務上 fail とする。CLI の許可・拒否と記録変更は 4.2 に従い、拒否時には個票・event が変更されないことを確認する。業務上だけの制約は人間の確認と CLI の検証結果を区別する。

- 活動中の各状態からの四つの終端先と、終端の各状態からの四つの再開先を確認し、完了・決定済みの分岐は type 別に検証する。
- 理由省略・承認証跡不足・直接待機再開の理由補完を、業務条件と CLI 制約の境界として確認する。

`register build` は個票 ID とファイル名の対応・一意性、派生元・依存関係、外部 event の検証を呼び出す整合検査として接続する。コマンドの許可・拒否とフィールド更新は関連テストへ T-ID を対応付ける。register item/event schema と関連テストの定義本体は今回の宣言参照外であり、既存テストの網羅や schema との一致を確認済みとはしない。
