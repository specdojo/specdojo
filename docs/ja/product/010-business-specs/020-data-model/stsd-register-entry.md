# ステータス定義（登録項目個票）

登録簿で追跡する計画外事項・判断事項（登録項目）について、起票から対応、審査、終了、再開までの状態と遷移を定義する。

## 1. 目的

登録項目の対応・判断の進み具合と追跡を続ける必要性を管理し、項目 owner と type 別の権限者が、着手・待機・審査・終了・再開を判断するために使う。判断漏れや誤終了を防ぎ、担当が交代しても対応を継続できるようにする。

## 2. 適用範囲

- 対象: 登録簿の一項目一ファイルの個票で管理する登録項目（`epic`、`todo`、`question`、`risk`、`issue`、`change-request`、`decision`、`note`）
- 業務範囲: 起票、担当・対応方針設定、人または AI Agent による対応・調査、審査・終了判断、終了項目の再開。計画済み作業は Schedule で扱い、登録簿へ重複登録しない
- 到達点: 完了・決定済み・却下・延期。いずれも再評価のため再開できる状態として管理を続け、ライフサイクルを閉じないため終了点は置かない。本書の全図を通して、出力遷移のない継続状態はない

`epic` は `track` の全体計画を扱い、具体的な作業は `derived_from` でつないだ子 todo で実施する。自身は `exec run --register` と夜間 queue の対象にしない。子項目と schedule を判断材料に人が終了を判断し、子の状態から自動遷移しない。

## 3. 状態の判定

- 状態の正本: 個票 Frontmatter の `item_status`。文書の成熟度を表す `status` とは別の状態軸とする。登録項目一覧や状態別ビューは個票から再生成する派生物である
- 一意判定: `item_status` の単一の値を「状態一覧」と照合する。完了日時や結論、子項目の状態から現在状態を導出しない。活動中は起票済み・対応中・待機中・審査待ち、終端は完了・決定済み・却下・延期とする
- 履歴との関係: 監査履歴の正本は個票とは別の追記型 event ファイルであり、現在状態の再計算には使わない。状態変更では個票と event を更新し、履歴の最終到達状態と現在状態を一致させる。event には遷移元・遷移先・実行者・理由を記録する
- 互換の扱い: `item_status` が未設定・空欄などで非空の文字列として読めない場合、読み取りでは起票済みとして扱う。これは現在値の読み取りの既定であり、現在の起票・遷移で八状態以外を認める規則ではない。状態値の別名への読み替えは行わない
- 旧履歴の扱い: Git 履歴から event へ移す際、最初の追加だけを起票とし、再追加は更新へ変換する。遷移元が空の場合は直前の到達状態、なければ個票の現在状態へ接続する。終端から活動中への変更は再開、ほかは遷移先に応じて着手・待機・審査・終了の操作へ対応付ける。これは過去の記録の移行規則であり、新たな業務遷移を許可するものではない

登録日時・完了日時・結論はそれぞれ `registered_at`・`completed_at`・`conclusion` で保持する。日時は UTC・RFC 3339・秒精度とし、一覧の登録日・完了日はプロジェクトの IANA タイムゾーンへ変換した暦日として導出し、期限は同タイムゾーン上の暦日として保持する。旧日付キーの `registered_on`・`completed_on` は移行専用とし、現在状態の判定には使わない。`owner`・`due_on` は省略でき、`due_on` の省略は期限未定、明示的な null は期限なしを示す。

## 5. 状態遷移

業務状態は 8、遷移は 40 で、遷移数 20 と一状態の入出力合計 6 の閾値を超えるため、活動・終了判断・再開の三図に分ける。「起票・記録更新・対応・審査」と他図の接続状態は活動中の四状態、「終了判断」と「再開」の接続状態は全八状態である。同じ状態は同じ表示名と `state_id` を使い、初期点は「起票・記録更新・対応・審査」にだけ置く。

### 5.1. 共通条件と審査・承認

各行の条件と次の共通条件をすべて満たす場合に pass、一つでも不足する場合に fail とする。CLI が操作を受け付けることだけでは業務上の承認・証跡の充足と判定しない。

- `T-03`〜`T-24`: 活動中の遷移・終了判断は `note` 以外を対象とする。`note` は `T-02` の記録更新を続け、対応・回答・判断が必要になったら別項目を起票する。
- `T-03`・`T-06`・`T-29`・`T-32`・`T-35`・`T-38`（着手・再対応）: 対応方針と人または AI Agent の対応経路を記録し、待機を要する外部依存がないことを確認する。担当・期限は未定でもよい。
- `T-04`・`T-05`・`T-08`・`T-30`・`T-33`・`T-36`・`T-39`（待機）: 待機理由を `block_reason`、再開条件を個票本文へ記録し、`conclusion` は変更しない。審査差し戻しでは不足情報と取得責任者も記録する。待機を離れる全遷移では `block_reason` を削除し、元の理由は履歴で保持する。
- `T-07`・`T-31`・`T-34`・`T-37`・`T-40`（審査提出）: 対応結果、実施した検証とその結果、承認対象、証跡候補を確認できる。情報が不足すれば提出せず、補完待ちは待機で扱う。
- `T-09`〜`T-24`（終了判断）: 次の type 別審査・承認表の人間の承認者、判断内容と理由、既定の証跡を確認できる。完了・決定済みは対応結果・検証結果の確認も必要とし、審査待ちを経由しない場合も省略しない。完了・決定済み・却下では `conclusion` と `completed_at` を記録する。延期では延期理由を `conclusion`、再評価条件を本文へ記録し、完了日時は付与しない。
- `T-25`〜`T-40`（再開）: 次の type 別審査・承認表の承認者が再評価対象と理由を確認し、承認の証跡を残す。旧結論・延期理由を保存し、再開理由を履歴へ追記し、`completed_at` を削除する。再開先は一つ選ぶ。起票済みは未着手、対応中は着手条件、待機中は待機理由・再開条件、審査待ちは審査提出条件を満たすことを確認する。待機中への直接再開では別途 `block_reason` を記録する。

CLI で確認できる許可・拒否と記録変更は「現行制約との対応」、業務条件の強制や未承認経路の採否は `M-01` で区別する。AI Agent は対応・調査と検証を支援し、終了・再開（`T-09`〜`T-40`）の判断は人間が担う。

| type             | 審査・承認者               | 主な終了・継続判断                                 | 既定の証跡       |
| ---------------- | -------------------------- | -------------------------------------------------- | ---------------- |
| `change-request` | 変更承認権限者（PO / CCB） | 承認後に完了、または却下・延期・待機               | PR approve       |
| `decision`       | 当該領域の意思決定者       | 決定済み、または却下・延期・追加確認の待機         | 個票と commit    |
| `risk`           | リスクオーナー             | 対応完了・受容による完了、延期、追加確認の待機     | 個票と commit    |
| `question`       | 回答権限者                 | 回答確定後に決定済み、または追加確認の待機         | 個票と commit    |
| `issue`          | 課題リード                 | 対応確認後に完了、または却下・延期                 | result と commit |
| `epic`           | track の完了を判断する人   | 子項目と schedule を確認して完了、または却下・延期 | 個票と commit    |
| `todo`           | 項目 owner・レビュー担当   | 対応確認後に完了、または延期・待機                 | result と commit |
| `note`           | 審査・承認の対象外         | 審査へ進めず、起票済みのまま記録を更新し続ける     | 個票と commit    |

既定は commit による証跡とする。PR 承認を強制するのは、`develop → main` 昇格、`change-request` 承認、不可逆・高リスク・framework schema 破壊的変更の三ケースである。詳細は [[specdojo:register-operation-guide|登録簿運用ガイド]] と [[specdojo:git-branching-standard|Git ブランチ運用標準]] を正とする。

### 5.5. 現行制約との対応

業務イベントの対応先を以下に示す。宣言された実装エビデンスで確認した現在動作であり、承認権限・証跡・結論の必須性は CLI が強制しない。共通して `item_status` を遷移先へ更新し、待機中以外では `block_reason` を削除する。状態が変わる操作は個票更新と別に event を作成する。

| 遷移 ID                        | 対応する操作      | 主な記録の変更                                                                                                                    | 現行の拒否条件・制約                                                                                                                                                         |
| ------------------------------ | ----------------- | --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `T-01`                         | `register add`    | 既定は `item_status: open`、`item_type`、`registered_at`。完了日時の既定は未設定                                                  | 状態値は八状態から検証する。初期状態の指定と業務範囲の差異は `M-01`                                                                                                          |
| `T-02`                         | `register update` | 本文・各フィールドを更新し、`item_status` は保持                                                                                  | 現行 `update` に状態変更オプションはない。活動中・終端とも記録更新できる。待機中以外への待機理由設定は拒否する                                                               |

### 5.6. 後続検証へ渡す判定基準

各図直下の遷移表と「共通条件と審査・承認」を許可経路・成立条件・記録結果の判定基準とし、表にない状態変更と条件不足は業務上 fail とする。CLI の許可・拒否と記録変更は「現行制約との対応」に従い、拒否時には個票・event が変更されないことを確認する。業務上だけの制約は人間の確認と CLI の検証結果を区別する。

- 活動中の各状態からの四つの終端先と、終端の各状態からの四つの再開先を確認し、完了・決定済みの分岐は type 別に検証する。
- 理由省略・承認証跡不足・直接待機再開の理由補完を、業務条件と CLI 制約の境界として確認する。

`register build` は個票 ID とファイル名の対応・一意性、派生元・依存関係、外部 event の検証を呼び出す整合検査として接続する。コマンドの許可・拒否とフィールド更新は関連テストへ T-ID を対応付ける。register item/event schema と関連テストの定義本体は今回の宣言参照外であり、既存テストの網羅や schema との一致を確認済みとはしない。
