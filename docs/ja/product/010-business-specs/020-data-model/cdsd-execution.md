# 概念データストア定義（プロジェクト実行）

## 1. 概要

プロジェクト実行で扱う概念データストアについて、業務上の役割、内容、粒度、正本区分、更新責務と検証の基準を一覧で定義する。人と AI Agent が同じ task を引き継ぐとき、状態・指示・証跡の正本が分かれていないと、別の Agent が同じ task を重ねて実行したり、検証に失敗した成果を完了として扱ったりして、参加者が交代したときに作業を継承できなくなる。本書はその防止のために、追記する記録、そこから再構成する状態、人が確定する記録を分ける。

BA は実行記録の管理単位の確認に、ARC は正本と派生物の区別と技術的な制約を設計の基礎に、DEV は保存単位と変更影響の確認に、QE はデータ検証・整合性確認の対象の識別に利用する。PO は管理境界と用途を最終合意し、`ready` 化と公開を人間として承認する。

- 本書は定期処理、進捗監視・報告の各 CDFD に記載していたデータ正本の詳細を移設したものである。
- 定期処理の実行状態の意味と due 判定・結果記録・次回判定の規則は [[prj-0001:stsd-routine-run|ステータス定義（定期処理の実行結果）]] を正本とし、本書では再定義しない。

### 1.1. 対象と隣接領域

範囲の根拠は成果物カタログ `docs/ja/projects/prj-0001/010-deliverables-catalog/dct-data-model-cdsd.yaml` の `cdsd-execution`（実行 event・実行状態、plan / result、evidence、worktree、定期処理、Job Run）である。

| 区分             | 管理境界と理由                                                                                                                                                                                                                                  |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 本書で定義       | 実行 event、実行状態、実行 plan、実行 result、実行 evidence、task worktree、定期処理定義、routine 実行状態、Job Definition、Job Run 履歴の10単位。task の着手から完了・差し戻しまでと、定期・反復の実行を追う                                   |
| 隣接領域から参照 | Schedule・マイルストーンは [[prj-0001:cdsd-planning\|概念データストア定義（プロジェクトの立上と計画）]]、生成済みの state・Ready・CPM・timeline の一式は [[prj-0001:cdsd-sharing\|概念データストア定義（活用と共有）]] の計画派生情報として扱う |
| 対象外           | 置き場所の物理的な区分・寿命・削除可否は[[prj-0001:sld-specdojo\|保管場所一覧（SpecDojo）]] に、各記録の全項目・型・許容値は schema と型定義に委ねる                                                                                            |

用語は次の意味で使う。task は Schedule または登録簿の項目から生じる実行の単位、run は task を 1 回実行した単位、routine は定期処理定義の単位、Job Definition は入力を変えて繰り返し実行する単位の定義、Job Run はその 1 回の実行である。実行 event は task の状態遷移を記録した 1 件の出来事を指す。

## 2. 概念データストア一覧

| データストア名   | 対応プロセス               | 主な内容                                                                               | 更新タイミング                                      | 粒度                | 主な用途                                                          |
| ---------------- | -------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------- | ------------------- | ----------------------------------------------------------------- |
| 実行 event       | タスク実行、定期処理、報告 | task の着手・完了・差し戻し・保留・解放・取消などの状態遷移、actor、理由、日時、run    | イベント（状態変更時）                              | 状態遷移毎          | 実行状態の再構成、進捗・滞留の監視根拠                            |
| 実行状態         | タスク実行                 | task ごとの現在の状態、着手者、直前の遷移、依存の充足と Ready の判定                   | イベント（状態変更の判定時に実行 event から再構成） | task 毎             | 着手・完了・差し戻しの可否判定、重複着手の防止                    |
| 実行 plan        | タスク実行                 | 対象成果物、owner Role、進め方、参照してよい文書、完了の狙い、展開された grade の指摘  | イベント（run の開始時）                            | run 毎              | executor が作業範囲と完了条件を確認する、後から指示内容を監査する |
| 実行 result      | タスク実行、報告           | 実施内容、変更ファイル、進め方と実践の型の適用、申し送り、検証結果                     | イベント（executor 終了後の報告時）                 | run 毎              | 人が完了・差し戻しを判断する、次の run と報告への引き継ぎ         |
| 実行 evidence    | タスク実行                 | 実行したコマンドと結果、executor の報告、親の検証結果、run の進行状態                  | イベント（各段の終了時）                            | run 毎              | 検証に合格したかの判定根拠、途中で止まった run の再開             |
| task worktree    | タスク実行                 | task 専用の作業ツリーとブランチ、未コミットの成果                                      | イベント（run の開始時・統合時・片付け時）          | task 毎             | 並行する task の成果の隔離、統合前の確認                          |
| 定期処理定義     | 定期処理                   | routine の識別、有効・無効、間隔または cron と時間帯、取りこぼし・重複時の方針、action | 随時（定義変更時）                                  | routine 毎          | 実行機会の選択条件、委譲する action の定義                        |
| routine 実行状態 | 定期処理                   | 直前の試行日時、直前の結果、直前に対象とした予定時刻、複数 action ごとの直前の結果     | イベント（実行試行時・結果反映時）                  | routine 毎          | 次回 due 判定、実行結果の運用確認                                 |
| Job Definition   | 定期処理                   | 入力定義、生成する task、冪等性の規則、checkpoint の規則、事前条件                     | 随時（定義変更時）                                  | Job 毎              | Job Run の生成条件と冪等性の判定                                  |
| Job Run 履歴     | 定期処理、タスク実行       | Job Run の識別、冪等性キー、attempt、Run の状態、解決済みの入力、checkpoint            | イベント（Run 生成時・attempt 終了時）              | Job Run・attempt 毎 | 重複実行の防止、反復位置の引き継ぎ、実行結果の監査                |

実行状態は実行 event から判定のたびに再構成する task 単位の状態である。生成して保存した state・Ready の一式は再生成の時点を持つ別の派生情報であり、着手・完了の判定には使わないため区別する。実行 plan と実行 result は同じ run に属するが、作成者と書き換えの制約が異なるため分ける。

## 3. 正本区分と更新責務

### 3.1. 生成元と利用制約

更新・確認担当は業務上の責務を示す。runner や Agent による自動の記録を用いる場合も、記録内容の責任は担当 Role code に残る。task の owner Role は Schedule・登録簿の項目に割り当てた Role code を指す。

| データストア名   | 正本区分・生成元                                                            | 更新契機・扱いの制約                                                                                                                                                                                 | 更新担当                         | 確認担当 |
| ---------------- | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- | -------- |
| 実行 event       | task の状態遷移の正本。タスク実行の状態変更コマンドが 1 遷移 1 件で追記する | 追記のみとし、既存の event を書き換え・削除しない。同じ名前の記録があれば上書きせず別名で追記する。形式に合わない event は読み飛ばさず、状態の再構成を止めて検証を求める。報告・監視では参照のみ行う | task の owner Role、PM           | QE       |
| 実行状態         | 実行 event と Schedule の依存から再構成する派生情報                         | 直接編集しない。着手・完了・差し戻しの可否は保存済みの生成物ではなく実行 event から都度判定する。訂正が必要な場合は実行 event を追記して状態を変える                                                 | task の owner Role（遷移の追記） | QE       |
| 実行 plan        | run の指示の正本。成果物カタログの完了条件、個票、grade の指摘から生成する  | run の開始後は書き換えない。指示を変える場合は plan を作り直して別の run とする。履歴として蓄積するため、リンクはリネームに追従不要な記法で書く                                                      | PM（生成の実行）                 | ARC、QE  |
| 実行 result      | run の結果記録。plan の Frontmatter から雛形を作り、報告の段で記入する      | executor は記入せず、reporter と runner が実行 evidence を根拠に記入する。完了の判断は人が行い、記入内容から成果物の `status` を変えない                                                             | OPS（runner の起動）             | PO、QE   |
| 実行 evidence    | run の検証結果と進行状態の正本。runner が各段の終了時に記録する             | executor の自己申告より親の検証結果を優先する。秘密情報を伏せてから保存する。途中で止まった run は進行状態から再開し、記録を消して実行し直さない                                                     | OPS                              | QE       |
| task worktree    | 成果を統合する前の作業場所。task の識別から名前を決め、専用のブランチを作る | 1 task に 1 つとし、他の task の成果を混ぜない。統合の段で止まった worktree へ別の変更を merge しない。統合後に片付ける。置き場所の区分は保管場所一覧に従う                                          | OPS                              | ARC、DEV |
| 定期処理定義     | 定期処理の選択条件の正本。人間による定義変更で更新する                      | 不正な定義は実行対象にせず、実行状態から推測で補正しない                                                                                                                                             | PM、OPS                          | QE       |
| routine 実行状態 | 定期処理の実行結果の正本。定期処理が記録する                                | 委譲前に試行を記録し、結果反映で直前結果を記録する。委譲先の記録と照合して確認する                                                                                                                   | OPS                              | QE       |
| Job Definition   | 反復実行単位の定義の正本。人間による定義変更で更新する                      | Run 生成前の検証に合格した定義だけを使う                                                                                                                                                             | Job Definition の owner、PM      | QE       |
| Job Run 履歴     | Job Run・attempt と checkpoint の正本。定期処理とタスク実行が記録する       | 完了済みの同一 Run は変更しない。checkpoint は成功または変化なしで終わった attempt の許可された範囲だけ進める                                                                                        | OPS                              | QE       |

Job Definition の owner は定義に記載した Role code とし、記載がない定義は PM が受ける。

### 3.2. 訂正・不整合時の扱い

| 場面                                             | 確認と次の行動                                                                            | 受け付ける担当・復旧の参照先                                                                     |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 実行 event の形式違反で状態を再構成できない      | 該当 event を特定し、状態の判定を止めたまま検証する。event を消して状態を合わせない       | QE が検出し、task の owner Role と PM が訂正の遷移を追記する。確認は「照合手順と受入条件」に従う |
| 実行状態と生成済みの state・Ready が食い違う     | 実行 event からの再構成を正とし、生成済みの一式を再生成する                               | OPS。生成物の扱いは [[prj-0001:cdsd-sharing\|概念データストア定義（活用と共有）]]                |
| 実行 result と実行 evidence の検証結果が食い違う | 親の検証結果を正とし、result を完了の根拠にしない。人が差し戻すか、同じ task を再実行する | OPS が報告し、PO が判断する                                                                      |
| run が途中で止まり worktree に未統合の成果が残る | 進行状態と worktree の差分を確認して再開する。worktree を消す前に成果の要否を確かめる     | OPS。置き場所と削除可否は[[prj-0001:sld-specdojo\|保管場所一覧（SpecDojo）]]                     |
| 定期処理定義・Job Definition が検証に失敗する    | 実行対象から外し、定義を修正して再検証する                                                | PM、Job Definition の owner。仕様の問い合わせは BA                                               |

## 4. 関連仕様と検証

### 4.1. 管理単位ごとの参照対応

業務データ辞書は未作成のため、ID をコード表記で示す。現在の動作の根拠は実装の型定義とコマンドであり、構造の詳細は本書へ複製しない。

| データストア名                 | 根拠・参照先                                                                                                                                       | 照合する内容と検証対象                                                             |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 実行 event                     | 予定辞書 `bdd-exec-event`。実装 `src/exec/events.ts`                                                                                               | 1 遷移 1 件の粒度、必須の識別・actor・理由・日時、追記のみの扱い                   |
| 実行状態                       | 予定辞書 `bdd-exec-state`。実装 `src/exec/events.ts` の状態の再構成と Ready の判定                                                                 | 状態の値の集合（未着手・作業中・保留・完了・取消）、依存の充足と Ready の一致      |
| 実行 plan、実行 result         | 予定辞書 `bdd-exec-plan-result`。実装 `src/shared/run-records.ts`、`src/exec/plans.ts`、`src/exec/results.ts`                                      | run ごとの配置と plan・result の対、Frontmatter の対象成果物と task の一致         |
| 実行 evidence                  | 予定辞書 `bdd-exec-evidence`。実装 `src/exec/evidence.ts`                                                                                          | run ごとの記録、検証結果の状態の値、親の検証結果の優先                             |
| task worktree                  | 予定辞書 `bdd-worktree-branch`。実装 `src/exec/worktree.ts`                                                                                        | task の識別と worktree・ブランチの名前の対応、1 task に 1 つ                       |
| 定期処理定義、routine 実行状態 | 予定辞書 `bdd-routine-definition`。実装 `src/routine/routine.ts`。状態の意味は [[prj-0001:stsd-routine-run\|ステータス定義（定期処理の実行結果）]] | 定義の必須項目、routine ごとの直前結果と due 判定の対応                            |
| Job Definition、Job Run 履歴   | 予定辞書 `bdd-job-run`。実装 `src/job/job.ts`                                                                                                      | 冪等性キーと Run の識別の対応、checkpoint を進める条件、事前条件による実行の見送り |

### 4.2. 照合手順と受入条件

BA が「対象と隣接領域」の10単位を一覧・更新責務・参照対応と照合し、欠落・重複が0件であることを確認する。ARC・DEV が正本区分と生成元を実装と照合した後、QE が次の確認を行う。コマンドの成功は終了コード 0 とし、未実行の検証を合格として扱わない。

| 対象                                  | 確認手順                                                                                                        | 合格条件                                                                                                                                  | 不一致時                                                                    |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 実行 event、実行状態                  | `specdojo exec validate --schedule-only` で Schedule と実行 event を検証する                                    | 終了コード 0 でエラーが0件。完了済みの task が実行状態で完了として再構成される                                                            | QE が該当 event と task を特定し、task の owner Role が訂正の遷移を追記する |
| 実行 plan、実行 result、実行 evidence | `specdojo exec validate --records-only` で run ごとの記録の配置を検証する                                       | 終了コード 0 で `OK: run record layout validation passed` が出る。各 run に plan・result・evidence の対がそろう（人の作業は result のみ） | OPS が欠けた記録の run を特定し、再開または記録の移し替えを行う             |
| 実行 result と実行 evidence           | 対象の run で result の検証結果と evidence の親の検証結果を手動で照合する                                       | 親の検証結果に失敗・未実行がない run だけが完了の根拠になる                                                                               | OPS が PO へ報告し、PO が差し戻しを判断する                                 |
| task worktree                         | 統合前に worktree の名前・ブランチと task の識別を照合する                                                      | 1 task に 1 つの worktree とブランチが対応し、他の task の変更を含まない                                                                  | OPS が統合を止め、混入した変更を元の task へ戻す                            |
| 定期処理定義                          | `specdojo routine validate` で定義を検証する                                                                    | 終了コード 0 で、出力のエラー件数が0                                                                                                      | PM・OPS が定義を修正して再検証する                                          |
| Job Definition                        | `specdojo job validate` で定義を検証する                                                                        | 終了コード 0 で、出力のエラー件数が0                                                                                                      | Job Definition の owner が修正して再検証し、合格まで Run を生成しない       |
| Job Run 履歴                          | `npm run validate:schema:job-run` で Job Run の記録を schema 検証する。checkpoint の前進を Run の状態と照合する | 終了コード 0。checkpoint が成功または変化なしの attempt でだけ進んでいる                                                                  | OPS が Run と checkpoint を確認し、完了済みの Run を書き換えずに再実行する  |

QE は文書の整形・Markdown・Frontmatter 検査も実施し、上記の確認と区別してコマンド・対象・結果を実行記録に残す。導入済みのコマンドは [[specdojo:cdsd-rulebook|概念データストア定義 作成ルール]] の「検証と受入条件」を参照する。

## 5. 確認事項と変更影響

| 論点・区分                                       | 現在の判断・影響                                                                                                                                         | 担当・判断時期・次の行動                                                                                                                                    | 追跡先                                                               |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 業務データ辞書7件が未作成（課題）                | 10単位の管理境界・正本区分・検証の基準は実装の現在の動作から定めた。項目の業務的な意味は辞書が整うまで確定せず、辞書と食い違えば辞書を正として本書を直す | BA が `bdd-exec-event` ほか7件を作成し、ARC・DEV が本書と照合する。PM が辞書→本書の再確認の順に Schedule へ載せ、PO は本書の `ready` 化の前に範囲を判断する | 成果物カタログ `dct-data-model-cdsd.yaml` の依存                     |
| 生成済みの state・Ready と実行状態の分担（決定） | 判定に使う実行状態は本書、生成済みの一式は活用と共有で扱う。分担を変えると両 CDSD と生成処理の説明に波及する                                             | ARC が分担を変える場合は PM へ変更要求として報告し、PO が承認する                                                                                           | 本書と [[prj-0001:cdsd-sharing\|概念データストア定義（活用と共有）]] |
| 記録の形式や粒度を変える場合（変更要求）         | 実行 event・evidence・Job Run の形式を変えると、状態の再構成、検証コマンド、既存の記録の移行に波及する                                                   | DEV が schema・型・生成処理への影響を特定し、QE が再検証範囲、PM が移行の順序と期限を計画する。PO が実施前に承認する                                        | 登録簿の変更要求                                                     |

公開・`ready` 化の前に BA・ARC・QE が管理境界と受入条件を確認し、OPS が記録の置き場所と復旧の導線を確認する。人間の PO は未決事項、記録に秘密情報や個人情報が含まれないことを確認し、承認・保留・差し戻しを判断する。仕様の問い合わせは BA、記録の不整合・再開の相談は OPS が受ける。
