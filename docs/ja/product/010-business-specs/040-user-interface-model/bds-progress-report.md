# 帳票仕様（週次進捗報告）

## 1. 概要

週次進捗報告は、プロジェクトの 1 ISO 週分の作業の完了・進行・課題・翌週予定を、記録からまとめた報告である。読み手は前週からの変化と残る課題を同じ形式で確かめ、翌週の優先度と担当を判断する。作業と判断を特定の参加者の記憶に頼らず共有する手段として、[[prj-0001:prj-overview|プロジェクト概要]] の `BV-03`（無理のない継続）に対応する。

## 2. 読み手と利用目的

| 読み手                         | 利用目的                                           | 帳票から判断すること                                   |
| ------------------------------ | -------------------------------------------------- | ------------------------------------------------------ |
| プロジェクトマネージャー（PM） | 週ごとの進み具合と停滞を同じ観点で定点観測する     | 停滞・遅延している作業、翌週に割り当て直す担当と期日   |
| プロダクトオーナー（PO）       | 成果物の完成状況と課題を確認する                   | 翌週に優先する成果物、範囲や順序の見直しが要る課題     |
| 各ロールの担当・将来の貢献者   | 自分が関わる作業の状態と、前週に決まったことを知る | 引き継ぐ作業、着手できる作業、確認を求められている事項 |

- 報告は AI Agent が Job から作成する。報告の本文で業務判断を確定しない。
- 個人の作業量の評価や、外部への公開報告には使わない。報告を外部へ公開する場合は、内容を確認したうえで公開の可否を判断する。

## 3. 出力の時期と契機

- 契機: routine `rtn-weekly-report` が毎週金曜 17 時（`Asia/Tokyo`）に Job `job-weekly-report` を起動する。契機と入力の定義は project 設定の `routines_path` 配下の `rtn-weekly-report.yaml` と `jobs_path` 配下の `job-weekly-report.yaml`、扱いの正本は [[specdojo:routine-operation-guide|routine運用ガイド]] と [[sysd-job-execution|Job実行設計]] の「週報作成」とする。
- 対象期間: 起動予定時刻が属する ISO 週（例: `2026-W32`）を 1 期間の名前とする。期間は前週金曜 17 時から当週金曜 17 時まで（いずれも `Asia/Tokyo`）とし、始点を含み終点を含まない。週の計算は routine のタイムゾーンを基準にし、実行端末のローカル時刻に依存しない。
- 終点の理由: 終点を起動時刻にそろえると、作成時点で期間内の記録がすべて揃い、金曜夜と土日の記録は翌週の報告に入る。各記録がどれか 1 件の報告にだけ入り、作成後に内容を補う必要がない。
- 取りこぼし: 端末や外部スケジューラの停止中に過ぎた週も、再開後に 1 週ずつ作る。各週の報告を欠かさないためである。
- 再出力: 同じ週の job run は ISO 週を冪等性キーとし、別の報告を増やさない。失敗した Run の再実行は同じ Run の再試行になる。成功した Run が既にある週は再実行しても新しい Run を作らず、報告も更新されない。
- 手動作成: 終点を過ぎた週に限り、`exec run --job job-weekly-report` に期間を渡して作成する。終点の前には作成しない。成功した Run は終点の後に作り直せず、作成時点までの記録だけの報告がその週の報告として残るためである。
- 重複起動: 同じ project の実行が動作中なら起動を見送り、次の起動機会に委ねる。

本書は定期起動を有効化した後の動作を記述する。現在の有効化の状態は「メモ / 将来課題」の「定期起動の有効化」に記す。

## 4. 出力形式と提供方法

- 形式: Markdown 文書。本文の章立て・ID・ファイル名の規則は [[specdojo:pr-rulebook|進捗報告 作成ルール]] を正本とする。
- 保存先: project の `base_path` を起点とする `reporting/progress-reports/`。保存先ディレクトリは、報告を作る AI Agent が初回の保存時に作る。
- 単位: 1 ISO 週につき 1 件。期間で一意な文書として保存する。
- ファイル名: 進捗報告の rulebook の `pr-<yyyy-mm-dd>-<nn>.md` に従い、日付は期間の終点の日付（当週金曜）、連番は `01` に固定する。例: `2026-W32` の報告は `pr-2026-08-07-01.md`。運用者は ISO 週の金曜の日付から報告を特定する。
- 提供方法: プロジェクトのリポジトリ内の文書として読み手が参照する。メール送付や外部への配信は行わない。

## 5. 対象範囲と元にする記録

対象は 1 project の、対象期間内の記録とする。他の project の記録、対象期間外に完了した作業は含めない。期間より前に着手した未完了のタスクと、期間より前に起票した未解決の課題は、期間末時点の状態として「進行中事項」「リスク・課題」に含める。その状態を確かめるため、期間より前の記録も読む。

| 記録                      | 用途                                     | 正本                                                                 | 欠けるときの扱い                                   |
| ------------------------- | ---------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------- |
| Schedule・exec の完了実績 | 完了事項と進行中事項を特定する           | exec の状態記録（[[specdojo:exec-operation-guide\|exec運用ガイド]]） | 読めない場合は報告を作らずに停止し、推測で補わない |
| 登録簿の状態変化          | 課題・依頼の起票・完了・保留を特定する   | 登録簿の個票と状態変化の記録                                         | 同上                                               |
| Schedule の未完了タスク   | 翌週予定を特定する                       | Schedule の定義と exec の状態記録                                    | 同上                                               |
| 前回の週次進捗報告        | 前週との差分と、持ち越した課題を確かめる | `reporting/progress-reports/` の前回分                               | 初回など前回分がない場合は差分を「前回なし」と記す |

- routine の実行履歴は端末側だけに保存され、Git で共有されないため、報告の元にする記録に使わない。
- 「欠けるときの扱い」の停止は、記録を推測で補わないための本書の要求である。Job がこの停止を失敗として記録するかは「メモ / 将来課題」の「記録欠落時の停止」で確かめる。

下表は各項目の意味と出所を定める。

| 1   | 見出し | 報告期間         | 対象の ISO 週と、その始点・終点の日時                       | job run の入力（期間）               | job run の期間と一致し、始点が前週金曜 17 時・終点が当週金曜 17 時であることを照合する                   |

| 4   | 明細   | 進行中事項       | 期間末時点で着手済み・未完了のタスクと、止まっている理由    | Schedule・exec の完了実績            | 期間末時点で実行中・停止中のタスクの集合と一致することを照合する                                         |
| 5   | 明細   | 登録簿の状態変化 | 期間内に起票・完了・保留となった登録簿項目                  | 登録簿の状態変化                     | 期間内の状態変化の記録と一致することを照合する                                                           |
| 6   | 明細   | リスク・課題     | 影響度と対応方針を付けた未解決のリスク・課題と、登録簿の ID | 登録簿の状態変化、前回の週次進捗報告 | 未完了の登録簿項目と前回の持ち越し課題に対応し、示した登録簿の ID が個票と一致することを照合する         |

「登録簿の状態変化」を報告のどの章に置くかは進捗報告の rulebook が定める。定まるまでの扱いは「メモ / 将来課題」の「登録簿の状態変化の配置」に記す。

## 7. 集計・算出ルール

- 期間への割り当て: 記録の日時を `Asia/Tokyo` に換算し、前週金曜 17 時以降かつ当週金曜 17 時より前のものを数える。ちょうど金曜 17 時の記録は翌週の期間に入れる。終点より後に作成・再出力した場合も、終点以降の記録は含めない。
- 完了の数え方: 期間内に完了へ遷移したタスクを 1 件と数える。期間内に差し戻して再び完了したタスクも 1 件とする。
- 前週との差分: 前回の報告のリスク・課題のうち、今回も未解決のものを持ち越しとして示す。
- 登録簿への移し替え: 持ち越しが 2 回続いたリスク・課題で登録簿に項目がないものは、登録簿へ起票し、次回の報告から登録簿の ID を示す。
- 次期予定の選び方: Schedule の着手予定日または完了予定日が翌週の期間（当週金曜 17 時から翌週金曜 17 時）に入る未完了タスクを選ぶ。
- 進捗率: 割合は表示しない。進捗報告の rulebook が根拠のない進捗率を禁じており、本帳票では分母を定義しないためである。
- 端数処理: 件数のみを扱うため該当しない。

## 8. 例外と注意事項

| 状況                               | 報告の扱い                                                           | 次の手                                                                                                         |
| ---------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 期間内に完了・状態変化がない       | 報告を作り、該当する項目に「該当なし」と書く                         | 停滞の理由を確認し、リスク・課題に記す                                                                         |
| 停止中に複数の週が過ぎた           | 過ぎた週ごとに 1 件ずつ作る                                          | 各週の報告で期間の取り違えがないことを確認する                                                                 |
| 成功した週を再実行した             | 新しい Run を作らず、報告を更新しない                                | 既存の報告を正とする。誤りは「成功した報告の作り直し」が解消するまで、次回の報告のリスク・課題に訂正として記す |
| 終点の前に作成しようとした         | 作成しない                                                           | 終点の後に手動で作成する                                                                                       |
| 実行中の作業があり起動が見送られた | その回は報告を作らず、次の起動機会に作る                             | 報告の有無を確認し、必要なら手動で作成する                                                                     |
| 報告の作成が失敗した               | 報告を作らない。失敗の記録は job run または routine の失敗記録に残る | 失敗の記録を確認し、原因の解消後に同じ週を再実行する                                                           |

## 9. メモ / 将来課題

本書の確定の判断点は T-KATA-WAVE-2-bds-progress-report-140 とする。解消条件に「登録簿で追跡」とある項目は、その判断点までに登録簿へ起票し、個票で期日を追跡する。起票した個票の ID は該当する行の解消条件へ書き足し、それまでは未起票として扱う。それ以外の項目は本書の改訂で解消する。改訂のたびに `npm run lint:md`・`npm run lint:fm`・`npm run validate:schema`・`npm run validate:catalog` を実行し、すべてエラーなしで終わることを確かめる。失敗した場合は指摘箇所を直して再実行し、通るまで確定しない。

| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 上位の索引             | `bds-index` は未作成であり、`part_of` を接続していない                                                                                                              | 索引を作成した時点で `part_of` を接続し、本書の共通事項を索引へ移す                                                                                                                                          |

| ファイル名と期間       | 本書は「出力形式と提供方法」で ISO 週から終点の日付と連番 `01` のファイル名を決めたが、進捗報告の rulebook には ISO 週との対応が書かれていない                      | 判断点までに、この対応を進捗報告の rulebook へ書き足すかを決める。書き足すまでは本書の対応を正とする。登録簿で追跡                                                                                           |
