# システム化機能一覧（全体構成）

本書は、SpecDojo が CLI と runner で実現するシステム化機能の全体構成と一覧を定義する。各機能を業務プロセス領域と CLI コマンド群へ対応付け、機能分割・コンポーネント設計、テスト対象の網羅確認、個別機能仕様（`sf-<term>`）への入口として使う。

## 1. 目的と対象範囲

業務プロセス領域ごとにシステムが担う責務を確定し、業務仕様からの漏れと機能間の責務の重なりを一覧で判断できるようにする。これは [[prj-0001:prj-overview|プロジェクト概要]] の、課題を実行可能な仕様へつなぐこと（`BV-01`）と、作業と判断を分担・継承できること（`BV-03`）に対応する。

| 区分   | 範囲                                                                                                                                                                                |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 対象   | SpecDojo CLI のコマンド群と、runner が自動で行う処理（agent 起動、検証、記録、統合、派生生成）。業務プロセス領域 `P-01`〜`P-14` のうち、システムが記録・検証・生成・起動を担う部分  |
| 対象外 | 人間が行う判断（スコープ・受入の承認、`ready` への昇格、構成変更の承認、非推奨化の判断）、外部 agent 製品と Git・エディタなど外部ツールの内部処理、個別機能の入出力・振る舞いの詳細 |

- 読者: 機能分割とコンポーネント設計を行う ARC、実装範囲を確認する DEV、テスト対象を洗い出す QE、業務仕様との対応を確認する BA。
- 保守と確認の記録: ARC が本書を保守する。BA・QE・DEV の確認結果は grade・review の実行記録に、PO の判断は登録簿の決定記録と `status` の昇格に残す。参照切れや対応漏れを見つけた読者は、登録簿へ起票して ARC へ渡す。
- 公開範囲: 本文は機能名、コマンド名、文書 ID だけで構成し、個人情報、認証情報、非公開の接続先を含めない。SpecDojo の製品文書として文書サイトで公開する文書として扱い、公開する相手と範囲は PO が承認時に確認して確定する。
- 承認: 人間の PO（indie）がシステム化のスコープを承認する。本書の確定は `status` の昇格と同じく人間の判断とする。PO は承認の前に、未決事項が解消しているか、承認範囲から切り出して追跡先が明記されていることを確かめる。

## 2. 機能構成

業務プロセス領域の ID は [[prj-0001:dct-business-model-bps|成果物カタログ（業務モデル／業務プロセス仕様）]] の区分に従う。機能領域は関連する業務プロセス領域をまとめて分け、計画（`P-03`・`P-04`）と可視化（`P-09`・`P-10`）のように責務の異なる処理は別の領域にする。領域の略号は機能 ID の `<AREA>` に使う。

| 機能領域         | 略号    | 業務プロセス領域       | システムの責務                                                                                            | 人間に残す判断                     |
| ---------------- | ------- | ---------------------- | --------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| プロジェクト構成 | `SETUP` | `P-01`・`P-12`         | 導入時の構成・Kata・開発環境を配置し、承認済みの構成変更を反映して利用可能性を検査する                    | 導入条件と構成変更の承認           |
| 登録簿           | `REG`   | `P-02`                 | 登録項目・決定記録の起票、状態遷移、履歴を記録する                                                        | 起票内容と対応方針                 |
| 計画             | `PLAN`  | `P-03`・`P-04`         | 成果物カタログを検証・表示し、カタログと戦略から Schedule と実行計画を展開する                            | 成果物として管理する対象と完了条件 |
| 定期実行         | `ROUT`  | `P-05`・`P-06`         | 定期実行定義とジョブ定義を検証・表示し、期日を判定して起動し、定義に従うジョブの実行を記録する            | 周期・条件・委譲の要否             |
| 実行サイクル     | `EXEC`  | `P-07`・`P-08`・`P-11` | タスクの実行受入から agent 実行、検証、統合、結果記録、評価、完了記録までを行う                           | 業務上の完了承認、評価結果の受入   |
| 可視化・派生生成 | `VIEW`  | `P-09`・`P-10`         | 進捗の集計表示と、文書索引・表示ページなどの派生成果物を生成し閲覧に供する                                | 進捗報告の確定                     |
| 文書の廃棄       | `DEPR`  | `P-13`                 | 非推奨化した文書を現行文書と区別できる場所へ移す                                                          | 非推奨化の判断                     |
| 運転調整         | `ORCH`  | `P-14`                 | 対話型オーケストレーターを、宣言済みリポジトリだけを許可して起動する。`P-14` のほかの処理は他の機能が担う | PDCA の運転判断                    |

業務プロセス領域 `P-01`〜`P-14` はすべていずれかの機能領域に属し、システム化しない領域はない。ジョブの実行（`SF-ROUT-02`）は業務上 `P-07` に属するが、ジョブ定義と同じ入口で扱うため `ROUT` に置く。分担は「機能一覧」の注記に示す。

## 3. システム化機能一覧

CLI 列はトップレベルのコマンド名を示す。サブコマンド・引数・出力の詳細は CLI 仕様（`clis-index` 配下）と [[specdojo:command-reference|CLIコマンドリファレンス]] を正本とし、本書へ転記しない。コンポーネント設計で保つ技術制約は個別仕様と CLI 仕様を正本とし、本書は表の後の注記にある責務の分担とまたがりを設計入力として渡す。

- `P-05` は定期実行定義、`P-06` はジョブ定義を作る領域で、定義の検証・表示はそれぞれ `SF-ROUT-01`（`routine`）と `SF-ROUT-03`（`job`）が担う。`SF-ROUT-01` は定義に基づく期日の判定と起動も担う。
- ジョブ定義に従う Run の具体化と実行は、業務上はタスク実行（`P-07`）の共有の実行サイクルに属する（`bps-task-edit` の、条件付きのジョブ定義に従って成果候補を作る処理）。`exec run --job` を入口として `SF-ROUT-02` が担う。`SF-ROUT-02` の意味を変えないため機能領域は `ROUT` のまま残し、業務プロセス領域を `P-07` へ対応付ける。
- `P-14`（定期起点の PDCA 運転）のうち、`SF-ORCH-01` はオーケストレーターの起動と許可するリポジトリの限定だけを担う。ほかの処理は次の機能に割り当てる。オーケストレーター agent が行う運転の判断と対話は、外部 agent 製品の内部処理と人間の判断として対象外とする。割当ては `Q-01` で `bps-routine-register-schedule-cycle` と照合する。
  - 運転要求の確定（期日と条件の判定）: `SF-ROUT-01`
  - 競合判定（遂行可否の判定）と PDCA 要求の発行（タスク・ジョブの実行受入と起動）: `SF-EXEC-01`・`SF-ROUT-02`
  - 実行状態の追跡: 状態遷移の記録は `SF-REG-01`、集計表示は `SF-VIEW-01`
- `exec` はタスク実行（`SF-EXEC-01`）とジョブ実行（`SF-ROUT-02`）にまたがる。`SF-EXEC-01` はタスク完了（`P-11`）の完了記録を含む。完了可否の判断に使う評価は `SF-EXEC-02` が担い、業務上の完了承認は人間に残す。
- `deliverable` は成果物ファイルの用意（`SF-PLAN-01`）と保管への移動（`SF-DEPR-01`）の 2 機能にまたがる。コマンド群の分割は CLI 仕様で判断し、本書では機能ごとに行を分ける。
- 個別仕様は代表 1 件（`sf-task-execution`）だけを作成する方針（[[prj-0001:pjr-2gd6-business-specs-reps|PJR-2GD6]]）とし、その他の機能は一覧行の要約を正とする。個別仕様のない機能の入出力と制約は、行が参照する BPS と CLI 仕様を正本とする。詳細化が必要になった機能は、成果物カタログへ `sf-<term>` を追加してから作成する。
- 機能の境界を変えた場合の影響先（BPS、機能分割、CLI 仕様・実装・schema・生成処理・運用手順、テスト対象）は、[[specdojo:sf-index-rulebook|システム化機能一覧（全体構成）作成ルール]] の「未決事項」にある再照合の手順で機能 ID から特定する。

### 3.2. 業務領域・テスト対象との照合

全機能 ID を、業務プロセス領域、成果物カタログ上の代表の BPS、テスト対象と照らす。代表の BPS は、機能領域ごとに成果物カタログの `depends_on` に置いた BPS とする（`Q-02` の方針）。`depends_on` は本書の作成前に読む代表を示すもので、網羅の根拠は本表と「機能一覧」の業務プロセス仕様列で辿る各行の BPS とする。検証手段はテスト仕様を作るときの起点とする区分で、既存テストの有無を示さない。実 Git・worktree・CLI 子プロセスを要する振る舞いは統合テスト、それ以外は単体テストで確かめる。

| ------------- | ---------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------- | ---------- | ---------------- | ---------------- |
| `SF-SETUP-01` | `P-01`                 | `bps-init-required`                                       | 導入条件に応じた Kata・稼働構成・開発コンテナ構成の配置                                 | 統合テスト | 一致             | 未（`Q-01`）     |

- 参照の解決と記法は、Frontmatter と参照の文書検査（`npm run lint:fm`）と Markdown lint（`npm run lint:md`）がエラーなく終了することを合格条件とする。
- BPS 本文との照合は、本表の行を作業の単位とし、その行の BPS が作成された時点で BA が行って本表の列を更新する。
