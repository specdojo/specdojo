# システム化機能（タスク実行）

## 1. 目的と概要

実行計画に従う作業を人・AI Agent に割り当て、成果物、検証結果、停止理由を同じ実行に対応付けて残す。PM・Orchestrator が次の着手や回復を判断でき、担当者が交代しても保存済みの成果から継続できることを目的とする。作業範囲と完了条件を保ち、再実行の費用と引き継ぎ負担を減らす。

主な利用者は、実行対象と担当を管理する PM・Orchestrator、作業を担う各タスクの owner、人・AI Agent の実行結果を確認する PO・QE である。ARC・DEV は本書を実行制御、外部 agent、検証、統合の責務境界として使う。

| 区分   | 範囲                                                                                                                                                                    |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 対象   | タスク選択と実行受入、着手記録（claim）、実行計画の引き渡し、agent による編集・レビュー、検証、実行結果の記録、中断・再開、worktree による隔離と統合、進捗上の完了記録  |
| 対象外 | カタログ・schedule の設計、routine の起動時刻の判断、成果物の品質評価そのもの、業務上の完了承認、成果物の `status` を `ready` へ昇格する判断、外部 agent 製品の内部処理 |

schedule task を主対象とする。登録簿項目と Job Run は共通の実行・記録処理を利用するが、それぞれの選択規則と状態管理を schedule task に置き換えない。

### 3.2. 前提条件と事後条件

着手条件と候補なしの場合の扱いは 4.1、実行完了・停止後に確認できる成果と状態は 4.2〜4.5 に定める。隔離実行では既存の利用者変更を保持し、人のタスクで agent を自動起動しない。

## 4. 処理要件・機能振る舞い

### 4.1. 選択・着手・隔離

1. 明示対象または着手可能な候補から、担当・実行区分・mode に合う対象を選ぶ。順位付けは [[br-task-selection-strategy|タスク選択戦略]] を参照し、本機能で判定ロジックを重複定義しない。
2. 状態追跡する schedule 実行では、受入後に runner が claim を記録する。状態を追跡しない単発実行、および worktree の分割操作だけでは暗黙に状態を変えない。
3. 選択した実行方式に従い、カレントの作業場所または隔離 worktree へ計画を渡す。隔離、agent 実行、検証、統合、状態記録を別の責務として扱う。

### 4.2. executor と実行証跡

1. pipeline 実行では executor が成果物の編集またはレビューと必要な検証を担い、reporter が evidence に基づく result の記述を担う。executor に result の直接更新やタスク状態の変更を担わせない。
2. executor の起動前に変更状況を記録し、今回の試行で生じた変更を既存変更から識別できるようにする。実行者、終了状態、試行回数、出力への参照とともに evidence を保存する。
3. executor の異常終了、保護違反、未完了報告、または再開時の対象範囲不足が判定された場合は、その理由を残して停止し、後続の親検証・reporter へ進まない。プロセスの正常終了だけを作業完了とはみなさない。
4. 実行段の状態は task の状態と別に記録する。段の成功、失敗、利用制限による停止を区別し、担当者が停止段を確認できるようにする。

### 4.3. 親検証・reporter

1. executor 成功後、設定された親検証を runner が実行し、対象リポジトリごとの結果を evidence に反映する。executor の申告で親検証結果を置き換えない。
2. reporter は plan と引き渡された evidence から実施内容・変更説明・申し送りを構成する。変更一覧と検証・完了可否の確定は runner 側の事実に基づく。reporter が成果を推測して完了扱いにしない。
3. 親検証に失敗があっても、その結果を含む result を残すため reporter を実行する。記録作成の成功によって検証失敗を解消したことにはしない。
4. reporter の応答形式は検査し、設定された回復処理後も失敗した場合は停止する。応答が成功でも result の描画・保存に失敗した場合、または evidence から完了不可と判定された場合は pipeline 全体を成功にしない。

### 4.4. 統合・完了と状態

隔離実行では、検証済みで許可された変更と当該実行の記録を統合対象とする。他の task・run の記録や一時ファイルを混ぜない。統合先の利用者変更を損なう場合や競合・検査失敗がある場合は、統合成功とせず、worktree と再開に必要な記録を保持する。

状態追跡する schedule の自動実行では、executor の成功、result の確認、親検証と統合の成功後に runner が完了を記録する。失敗時は中断理由を記録する。状態遷移・操作権限は [[prj-0001:stsd-task-execution|ステータス定義（タスク実行）]] を正本とする。登録簿項目と Job Run はそれぞれの状態規約へ結果を返す。

この完了は後続タスクへ進むための作業報告である。[[bps-task-completion|タスク完了]] の業務上の verdict、および成果物の `ready` 昇格を置き換えない。人間の承認が必要な判断は確認者へ引き渡す。

### 4.5. 例外・再開

| 条件                             | 振る舞い・保持する情報                                         | 再開条件・範囲                                                                                               |
| -------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 入力・担当・依存・権限の不成立   | 対象と原因を示し、不成立の条件を無視して着手しない             | 条件を補正して受入から再判定する                                                                             |
| executor の失敗・未完了          | 停止理由と evidence、既存成果を保持する                        | 原因・不足作業を解消し executor から継続する。前試行の状態・証跡・ログを退避し、既存変更と申し送りを引き継ぐ |
| 親検証の不足・失敗               | 検証結果と失敗出力を evidence に残す                           | reporter 再開前に親検証を更新する。成果物の修正が必要なら executor へ戻す                                    |
| reporter だけが失敗              | executor の成果と evidence を保持し、reporter の失敗を区別する | 保存済み evidence から reporter を再開し、executor の編集を繰り返さない                                      |
| 再開前に統合先の変更を取り込んだ | 以前の検証成功だけで現在の変更を保証しない                     | 親検証が設定されていれば成功済みでも再実行する。不足・失敗した結果も更新対象とする                           |
| 外部 agent の利用制限・接続障害  | 設定された停止・待機・代替実行に従い、切替・回復履歴を記録する | 保存済みの実行を識別し、利用可能な条件から継続する                                                           |
| 統合失敗                         | 未統合の成果と失敗理由を保持し、完了を記録しない               | 原因解消後に統合段から再開する                                                                               |

親検証の再利用は、必要な結果がそろい失敗がなく、再検証が必要な変更を取り込んでいない場合に限る。再開時の記録の一致・欠落の確認と具体的な回復手順は exec 運用ガイドへ委ねる。

## 5. 非機能・技術制約

- **追跡・継承**: plan、result、evidence、段の状態を同じ実行へ対応付ける。再開時も実行の識別を保ち、前試行と今回の試行を区別できること。
- **実行資源**: agent の利用可否、実行時間制限、再試行、provider ごとの同時実行枠は稼働構成に従う。並行作業によって同じ対象の着手や共有先の統合を競合させない。数値のサービス水準は第 8 章で確定する。
- **権限・保護**: 実行者に許された成果物・操作の範囲を守る。保護設定の変更提案は人へ引き渡し、agent が保護を解除しない。agent による成果物の `ready` 昇格を認めない。
- **外部依存と記録**: AI provider CLI、検証環境、Git が必要な経路は、それぞれの利用可能性に依存する。認証情報を成果物・ログへ残さず、失敗出力は秘匿処理した調査用記録として扱う。
- **分担**: runner が状態管理・親検証・記録確定・統合を担う。editor から独立した成果物評価と、人間による主要判断の責任をこの処理へ混在させない。

## 7. 検証・受入観点

以下は仕様の受入条件であり、実装で確認済みのテスト結果を示すものではない。QE は実行記録と差分で判定し、PO・PM は機能スコープと人間の判断境界を確認する。

| 観点 ID | 対象条件                                                                    | 合格条件                                                                                                    | 検証レベル |
| ------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------- |
| V-01    | 自動選択に候補がある / ない                                                 | 候補があれば選択戦略の結果と対象が一致する。なければ着手せず正常終了する                                    | 結合       |
| V-02    | 依存・担当・権限が不成立                                                    | 不成立の条件と対象を通知し、許可のない着手を記録しない                                                      | 結合       |
| V-03    | 状態追跡あり / なし、human task                                             | 選択した経路だけが状態を更新し、人の作業では agent を暗黙に起動しない                                       | 結合       |
| V-04    | executor が正常完了                                                         | 変更・検証・実行者・試行が証跡へ対応付き、親検証後に reporter が result を構成する                          | 結合       |
| V-05    | executor が未完了を報告 / 保護違反 / 再開範囲不足                           | 終了コードが正常でも完了不可を検出し、理由を残して親検証・reporter を開始しない                             | 結合       |
| V-06    | 親検証が失敗                                                                | evidence と result に失敗を残し、reporter の成功だけで完了・統合を許可しない                                | 結合       |
| V-07    | reporter の形式不正・起動失敗 / result 保存失敗                             | 失敗した段と原因を確認でき、pipeline は成功とならず executor の成果が残る                                   | 結合       |
| V-08    | reporter から再開、親検証が成功済み / 不足・失敗 / 統合先変更の取り込みあり | 再利用条件を満たす場合だけ既存検証を使う。不足・失敗または取り込み時は更新し、executor の編集を繰り返さない | 結合       |
| V-09    | executor から再開                                                           | 前試行の証跡と既存成果が失われず、既存変更・申し送り・元の対象範囲を引き継ぐ                                | 結合       |
| V-10    | 利用制限・外部接続障害                                                      | 選んだ回復方針に従い、停止段・回復履歴と保存済み実行を対応付けて確認できる                                  | 結合       |
| V-11    | 隔離実行の成功 / 統合競合                                                   | 成功時は許可された成果と記録を統合して進捗を完了にする。失敗時は完了を記録せず回復用 worktree を保持する    | 結合       |
| V-12    | レビューまたは人の確定が残る                                                | agent が成果物を `ready` へ昇格せず、進捗上の完了と業務上の verdict・受入承認を別々に確認できる             | 受入       |
