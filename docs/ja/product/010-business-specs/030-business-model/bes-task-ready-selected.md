# 業務イベント: 実行可能タスクの選択

着手可能なタスクが、1 回の実行の対象として選ばれたという出来事を定義する。上位の業務イベント一覧（`bes-index` / `prj-0001:bes-index`、未作成）において、[[prj-0001:cdfd-overview|概念データフロー図（全体概要）]] のタスク実行（`P-07`）の起点イベント「実行指示された」のうち、実行対象の確定を詳細化する個別仕様（`bes-task-ready-selected`）である。対象範囲と業務承認の前提は 1.1 節に示す。

選択要求・対象の確定・着手宣言が混同されると、PM は何が選ばれたかを追跡できず、task owner と AI Agent は引き受ける対象を共有できない。本書は起点が異なっても選択の事実を同じ単位で理解するために使う。定義を利用できると判断する成功基準は、単発・自動・並列の各場面から発生有無・回数・対象を判定でき、並列では同じ要求の選択を関連付けられることである。

候補の順位付けは [[prj-0001:br-task-selection-strategy|タスク選択戦略]]、選択後の担当解決・着手宣言・隔離準備は `bps-task-selection-preparation` と `bps-parallel-required` に委ねる。状態の意味・遷移は上記の状態定義を正本とする。

## 1. 何が起きたか

- 着手可能（`ready`）なタスクのうち 1 件が、今回の実行の対象として確定した。複数件を一度に要求された場合は、確定した 1 件ごとに 1 回発生する。
- 「選択」は対象の確定だけを指し、着手宣言（`claim`、状態遷移 `T-05`）、担当の解決、作業の開始は含まない。これらは本イベントの後に業務プロセスで扱う。
- 候補の表示や順位の確認だけで、実行の対象を確定しない場合は、本イベントにあたらない。

### 1.1. 適用範囲と承認の未決事項

_ASSUMPTION_: 本書は、[[prj-0001:stsd-task-execution|ステータス定義（タスク実行）]] で発生条件を説明できる schedule 系（スケジュール帳票のタスク）の対象確定に適用する前提で記述する。3 系統が共用する実行サイクル全体への適用は、人間の PO による確定の段での業務承認を要する。register 系・routine 系は適用未判定とし、本書の条件をそのまま適用しない。恒久的な対象外ともせず、executor による承認済みの判断にはしない。

以下および各章の確認・判断の担当割当は未承認の進め方案である。判断結果は本書の該当箇所と本成果物のレビュー結果に記録し、PM が未解決事項や変更要求を登録簿（`pjr-*`）で追跡・報告する。

## 2. いつ

- 選択要求を受けて、対象の依存の充足を再判定し、自動・並列では順位を付けたうえで対象が確定した時点を指す。要求を受けた時点や、着手宣言を記録した時点ではない。
- 依存の充足は選択時点の状態で判定する。`ready` は永続化しない導出状態なので、以前の時点で着手可能だったことは根拠にならない。
- 複数件を同時に要求した場合は、候補ごとに確定した時点がそれぞれの発生時点になる。前回の実行が終わった後に次の候補を選び直すときは、再判定と確定のたびに新しく発生する。

_UNDECIDED_: 自動選択で、選択と着手宣言（`claim`）を業務上同一のイベント境界（発生時点）とみなすかは未決定。確認に必要な `bps-task-selection-preparation` は本タスクの参照範囲に含まれず、人間の PO の業務判断も未了であるため、本書では既存の対象確定と `claim` の区別を維持する。BA と ARC が同プロセス仕様を依存に宣言して、対象確定と着手宣言の業務境界を確認し、人間の PO が実装・テスト設計への引き渡し前に判断する。判断結果は PM が本書とレビュー結果に記録する。

## 3. 誰が／何が

`runner` は、自動実行を調整し、選択戦略と実行能力に従って対象を確定するシステム構成要素を指す。以降は「自動実行システム（runner）」と表記する。Orchestrator は人や自動実行の意図を受けて要求を調整する主体、task owner はタスクを担当するロールを指す。

| 起点区分 | 選択を要求する主体                                      | 対象を確定する主体                                   | 起点の特徴                                               |
| -------- | ------------------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------- |
| 単発     | 人（PM、task owner）または Orchestrator                 | 要求した主体（指名したタスクが着手可能だと確認する） | 対象のタスクが要求時点で決まっている。順位付けは行わない |
| 自動     | 実行主体（人または AI Agent）、または Orchestrator      | 自動実行システム（runner）                           | 要求時点では対象が決まらない。順位が最も高い 1 件を選ぶ  |
| 並列     | 人または Orchestrator（件数の上限を指定して一括で要求） | 自動実行システム（runner）                           | 1 回の要求から複数件が確定する                           |

- 起点区分は要求の形で決める。誰が要求したかでは決めない。同じ Orchestrator からの要求でも、指名なら単発、次の 1 件の要求なら自動として記録する。
- 自動実行システム（runner）、Orchestrator、AI Agent は選択の要求または対象確定を担う主体であり、本イベント定義の業務承認と公開可否の責任は人間の PO が担う。

## 4. 発生条件

- 対象のタスクの基本状態が `todo` で、選択時点で先行依存がすべて充足している（依存なしを含む）。実行中・中断中・完了・中止のタスクは選ばれない。
- 対象のタスクが、要求で指定した範囲（プロジェクト、トラックなど）の中にある。
- 単発では、指名したタスクが上の条件を満たす。満たさない場合、イベントは発生しない。
- 自動では、候補が 1 件以上あり、順位が最も高い 1 件が確定する。候補が 0 件なら発生しない。
- 並列では、指定した上限件数まで、順位の高い順に確定する。実行能力（実行主体の同時実行の上限など）が足りずに見送った候補は、今回は発生しない。後で空きができて確定した時点で発生する。
- 選択後の準備（担当の解決、作業場所の用意など）に失敗しても、選択の事実は取り消さない。失敗の扱いは業務プロセス側で決める。

## 5. 事実データ

項目名は業務上の論理名であり、実装のフィールド名・構造を定義するものではない。

| 項目                       | 業務上の意味                                                                                                                                         | 必要になる条件                                                                                   |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 対象タスク ID              | 今回選択された 1 件を識別する                                                                                                                        | 常に必要                                                                                         |
| 所属トラック・owner ロール | 選択されたタスクの計画上の所属と担当責務を示す                                                                                                       | 常に必要                                                                                         |
| 起点区分                   | 指名・次の 1 件・一括要求のどの形で対象が確定したかを示す                                                                                            | 常に必要                                                                                         |
| 選択の要求者               | 人、AI Agent、Orchestrator のうち実際の要求主体をたどる情報                                                                                          | 常に必要                                                                                         |
| 発生時点                   | 当該対象が確定した時刻                                                                                                                               | 常に必要                                                                                         |
| 適用した選択戦略・順位     | 対象確定に用いた戦略と当該候補の順位                                                                                                                 | 自動・並列                                                                                       |
| 要求の上限件数             | 同じ一括要求で確定する件数の上限                                                                                                                     | 並列                                                                                             |
| 同じ要求で確定した件数     | 当該対象の確定を含め、その発生時点までに同じ一括要求で確定した対象の累計。要求終了時の最終件数ではない                                               | 並列で、その時点の累計を確認できる場合。確認できなければ省略し、0 や後から得た最終件数で補わない |
| 並列選択要求識別子         | 同一の一括要求から生じた複数の選択を関連付ける相関情報（対象タスク ID・実行 1 回の識別子・個別イベントの識別子とは別単位）。正本の対応項目名は未確認 | 並列                                                                                             |

### 5.1. 相関と発生の確認例

以下は発生有無・回数と相関の判定基準（検証規則）を示す業務上の確認例であり、実装・テスト済みの証跡ではない。相関項目と正本モデルの対応確定後に QE がテスト設計へ引き継ぐ。

| 場面                                                              | 確認する事実                                                                                                                                  |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 同じ並列要求でタスク A、次に B が確定し、各時点の累計を確認できる | 2 回発生し、両方の「並列選択要求識別子」が同じ要求を示す。対象タスク ID は A と B、確定した件数は A で 1、B で 2。A の値を後から 2 に変えない |
| 同じ並列要求で対象が確定したが、その時点の累計を確認できない      | 対象ごとに発生し、同じ要求への相関は維持する。「同じ要求で確定した件数」は省略する。確定順を観測できない同時確定もこの扱いとする              |
| 別の並列要求でタスク C が確定                                     | 1 回発生し、前の要求と区別できる「並列選択要求識別子」で関連付けられる。時刻や要求者が同じでも混同しない                                      |
| 並列要求の候補のうち実行能力が足りないものを見送る                | 見送った候補の選択イベントは発生せず（0 回）、確定した対象だけが当該要求の「並列選択要求識別子」に属する                                      |
| 自動要求時に候補がない、または指名タスクが着手不可能              | 選択イベントは発生しない（0 回）                                                                                                              |
| 選択後の担当解決・隔離準備が失敗                                  | 確定時の 1 回のまま残し、既に成立した選択の事実と後続処理の失敗を区別できる                                                                   |

### 5.2. データモデルとの未照合事項

_UNDECIDED_: 「並列選択要求識別子」の正本上の対応項目は未確定である。[[prj-0001:stsd-task-execution|ステータス定義（タスク実行）]] が根拠（`based_on`）に挙げる実行記録モデル（`prj-0001:bdd-exec-event` および `prj-0001:bdd-exec-state`）と対応 schema は本タスクの参照範囲に宣言されておらず、要求単位の項目の有無自体が未確認である。照合先候補は `prj-0001:bdd-exec-event`（実行イベント）とし、実行 1 回の ID での代用や新規項目の必要性は断定しない。この対応が確定するまで、並列のイベントデータを実装・テスト設計への確定入力にはできない。

実装・テスト設計への引き渡し前に、ARC が正本の文書 ID・所在と利用可否を確認し、モデルと対応 schema を参照範囲に宣言して要求単位の識別情報を照合する。同時に、上表の累計件数と省略条件を正本で表せるかを確認する。BA が業務上の単位と対応を整理し、人間の PO が確定の段で判断する。判断結果の記録・追跡は 1.1 節に従う。

相関情報の変更時は、本書と実行記録モデル（`prj-0001:bdd-exec-event`）の対応に加えて、`bps-task-selection-preparation`、`bps-parallel-required`、選択イベントの発行・利用側実装、および上の相関確認例を入力にするテスト設計への影響を確認する。下流の個別成果物 ID・実装契約は、依存と対応先を確認した後に特定する。
