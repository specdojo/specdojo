# 業務イベント: 実行可能タスクの選択

着手可能なタスクが、1 回の実行の対象として選ばれたという出来事を定義する。[[prj-0001:cdfd-overview|概念データフロー図（全体概要）]] のタスク実行（`P-07`）の起点イベント「実行指示された」のうち、schedule 系の対象確定を記述する。現在の依存で発生条件を説明できるのは、[[prj-0001:stsd-task-execution|ステータス定義（タスク実行）]] が扱うスケジュール帳票のタスクである。register 系・routine 系への適用は未判定であり、本書の条件をそのまま適用しない。これは最終的な業務範囲を schedule 系に限定する決定ではない。

選択要求・対象の確定・着手宣言が混同されると、PM は何が選ばれたかを追跡できず、task owner と AI Agent は引き受ける対象を共有できない。本書は起点が異なっても選択の事実を同じ単位で理解するために使う。利用できると判断する基準は、単発・自動・並列の各場面から発生有無・回数・対象を判定でき、並列では同じ要求の選択を関連付けられることである。「事実データ」の照合と業務承認が終わるまで、実装・テスト設計への確定入力にはしない。

候補の順位付けは [[prj-0001:br-task-selection-strategy|タスク選択戦略]]、選択後の担当解決・着手宣言・隔離準備は `bps-task-selection-preparation` と `bps-parallel-required` に委ねる。状態の意味・遷移は上記の状態定義を正本とする。

_ASSUMPTION_: 以下の未決事項は、PM が記録・追跡・報告を調整し、BA が業務境界、ARC が依存とデータの照合を整理して、人間の PO に判断を求める進め方案とする。割当は未承認である。判断結果は本書の該当箇所と本成果物のレビュー結果に記録し、PM が未解決事項と併せて報告する。

## 1. 何が起きたか

- 着手可能（`ready`）なタスクのうち 1 件が、今回の実行の対象として確定した。複数件を一度に要求された場合は、確定した 1 件ごとに 1 回発生する。
- 「選択」は対象の確定だけを指し、着手宣言（`claim`、状態遷移 `T-05`）、担当の解決、作業の開始は含まない。これらは本イベントの後に業務プロセスで扱う。
- 候補の表示や順位の確認だけで、実行の対象を確定しない場合は、本イベントにあたらない。

| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| 承認者の識別 | _UNDECIDED_: 業務定義と公開可否を承認する人間の PO の Member または氏名は、参照範囲から確認できない                                                 | PM が業務レビューの依頼前に人間の PO を特定し、その識別と承認結果をレビュー結果に残す。AI Agent による承認で代替しない                                                                |

本書を完成した業務仕様として扱う条件は、適用範囲・選択と着手宣言の境界・並列の相関情報が根拠と照合され、一覧との接続が確認され、特定した人間の PO が業務妥当性と公開可否を承認していることである。現時点ではこれらを満たしていない。

## 2. いつ

- 選択要求を受けて、対象の依存の充足を再判定し、自動・並列では順位を付けたうえで対象が確定した時点を指す。要求を受けた時点や、着手宣言を記録した時点ではない。
- 依存の充足は選択時点の状態で判定する。`ready` は永続化しない導出状態なので、以前の時点で着手可能だったことは根拠にならない。
- 複数件を同時に要求した場合は、候補ごとに確定した時点がそれぞれの発生時点になる。前回の実行が終わった後に次の候補を選び直すときは、再判定と確定のたびに新しく発生する。

_UNDECIDED_: 自動選択で、選択と着手宣言を業務上同一の発生時点とみなすかは未決定。確認に必要な `bps-task-selection-preparation` がまだなく、人間の PO の業務判断も未了であるため、本書では既存の対象確定と `claim` の区別を維持する。BA と ARC が同プロセス仕様を依存に宣言して、同じ排他区間で連続実行するという既存記述と業務境界を確認する。そのうえで、人間の PO が実装・テスト設計への引き渡し前に判断する。

## 3. 誰が／何が

`runner` は、自動実行を調整し、選択戦略と実行能力に従って対象を確定するシステム構成要素を指す。以降は「自動実行システム（runner）」と表記する。Orchestrator は人や自動実行の意図を受けて要求を調整する主体、task owner はタスクを担当するロールを指す。

| 起点区分 | 選択を要求する主体                                      | 対象を確定する主体                                   | 起点の特徴                                                                 |
| -------- | ------------------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------- |
| 単発     | 人（PM、task owner）または Orchestrator                 | 要求した主体（指名したタスクが着手可能だと確認する） | 対象のタスクが要求時点で決まっている。順位付けは行わない                   |
| 自動     | 実行主体（人または AI Agent）、または Orchestrator      | 自動実行システム（runner）                           | 要求時点では対象が決まらない。順位が最も高い 1 件を選ぶ                    |
| 並列     | 人または Orchestrator（件数の上限を指定して一括で要求） | 自動実行システム（runner）                           | 1 回の要求から複数件が確定する。実行能力が足りない候補は、今回は確定しない |

- 起点区分は要求の形で決める。誰が要求したかでは決めない。同じ Orchestrator からの要求でも、指名なら単発、次の 1 件の要求なら自動として記録する。

## 4. 発生条件

- 対象のタスクの基本状態が `todo` で、選択時点で先行依存がすべて充足している（依存なしを含む）。実行中・中断中・完了・中止のタスクは選ばれない。
- 対象のタスクが、要求で指定した範囲（プロジェクト、トラックなど）の中にある。
- 単発では、指名したタスクが上の条件を満たす。満たさない場合、イベントは発生しない。
- 自動では、候補が 1 件以上あり、順位が最も高い 1 件が確定する。候補が 0 件なら発生しない。
- 並列では、指定した上限件数まで、順位の高い順に確定する。実行能力（実行主体の同時実行の上限など）が足りずに見送った候補は、今回は発生しない。後で空きができて確定した時点で発生する。
- 選択後の準備（担当の解決、作業場所の用意など）に失敗しても、選択の事実は取り消さない。失敗の扱いは業務プロセス側で決める。

## 5. 事実データ

項目名は業務上の論理名であり、実装のフィールド名・構造を定義するものではない。

| 項目                       | 業務上の意味                                                             | 必要になる条件 |
| -------------------------- | ------------------------------------------------------------------------ | -------------- |
| 対象タスク ID              | 今回選択された一件を識別する                                             | 常に必要       |
| 所属トラック・owner ロール | 選択されたタスクの計画上の所属と担当責務を示す                           | 常に必要       |
| 起点区分                   | 指名・次の一件・一括要求のどの形で対象が確定したかを示す                 | 常に必要       |
| 選択の要求者               | 人、AI Agent、Orchestrator のうち実際の要求主体をたどる情報              | 常に必要       |
| 発生時点                   | 当該対象が確定した時刻                                                   | 常に必要       |
| 適用した選択戦略・順位     | 対象確定に用いた戦略と当該候補の順位                                     | 自動・並列     |
| 要求の上限件数             | 同じ一括要求で確定する件数の上限                                         | 並列           |
| 同じ要求で確定した件数     | 一括要求での選択数。集計時点は下記の未決事項                             | 並列           |
| 並列選択要求識別子         | 一つの一括要求に属する選択を関連付ける論理項目。正本の対応項目名は未確認 | 並列           |

### 5.1. 相関と発生の確認例

以下は必要な業務上の確認例であり、実装・テスト済みの証跡ではない。相関項目とモデルの対応が決まった後に QE がテスト設計へ引き継ぐ。

| 場面                                                 | 確認する事実                                                                             |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 同じ並列要求でタスク A と B が確定                   | 二回発生し、両方の並列選択要求識別子が同じ要求を示す。対象タスク ID はそれぞれ A と B    |
| 別の並列要求でタスク C が確定                        | 前の要求と区別できる並列選択要求識別子で関連付けられる。時刻や要求者が同じでも混同しない |
| 並列要求の候補のうち実行能力が足りないものを見送る   | 見送った候補の選択イベントは発生せず、確定した対象だけが当該要求に属する                 |
| 自動要求時に候補がない、または指名タスクが着手不可能 | 選択イベントは発生しない                                                                 |
| 選択後の担当解決・隔離準備が失敗                     | 既に成立した選択の事実と、後続処理の失敗を区別できる                                     |

### 5.2. データモデルとの未照合事項

_UNDECIDED_: 状態定義が根拠として挙げる実行記録モデルのうち、照合先候補は `prj-0001:bdd-exec-event`（実行イベント）である。対応する成果物がまだなく、本タスクの依存にも宣言されていないため、内容は未照合である。ARC が正本の文書 ID・所在と要求単位の識別情報の有無を確認し、必要なモデルを依存に宣言した後に照合する。実行一回の ID が一括要求と同じ単位とは限らないため、既存項目で表せるとも新規フィールドが必要とも断定しない。

_UNDECIDED_: 並列選択要求識別子に対応する正本項目と、確定件数を観測する時点（各対象の確定時点までの件数か、要求終了時の件数か）は未決定。最終件数を途中の発生時点で既知の事実として扱わない。ARC が上記のモデル照合、BA が業務上の単位を整理し、人間の PO が実装・テスト設計への引き渡し前に合意する。

相関情報の変更時は、本書と実行記録モデルの対応に加えて、`bps-task-selection-preparation`、`bps-parallel-required`、選択イベントの発行・利用側、および上の相関確認例を入力にするテスト設計への影響を確認する。下流の個別成果物 ID・実装契約は、依存と対応先を確認した後に特定する。
