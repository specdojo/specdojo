# タスク選択戦略

Ready なタスクが複数あるとき、選択戦略（`critical-first` / `fifo`）に従って候補の順位を決め、次に着手するタスクを一つに定める判定ルール。

## 1. 概要

- 業務価値: 限られた実行主体（人・AI Agent）と作業時間を、全体の完了を遅らせるタスクから順に充てることで、特定の参加者が調整を抱え込まずに進行を継続できるようにする（[[prj-0001:prj-overview|プロジェクト概要]] の `BV-02`・`BV-03`）。誰が選んでも同じ入力から同じ順位を再現できる規則にし、着手順の判断を引き継げることを目指す。
- 参照する業務プロセス: 実行受入（`bps-task-selection-preparation`、`P-07-01`）で、実行対象の候補を絞り込んだ後の着手順の決定に使う。
- 主な利用者: 実行を起動する PM・Orchestrator は戦略を指定し、PO は既定戦略の妥当性を承認する。
- 適用範囲: Schedule（track）から展開されたタスクのうち Ready なもの。単発の着手（1 件選択）と、並行実行で上位から複数件を順に取り出す場合の両方に同じ順位を使う。
- 前提: 候補タスク集合は、Ready 判定および担当ロール・実行区分・mode による絞り込みを終えた同一確認時点の集合として与えられること。なお、先行する実行受入（`bps-task-selection-preparation`）が未作成のため、frontmatter の `based_on` は依存関係の宣言であり、適用場面と対象外の境界は同仕様の作成後に照合する（`U-01`）。
- 対象外:
  - タスクが Ready かどうかの判定（依存の完了状況による判定は Schedule 側の責務）。
  - 担当ロール・実行区分・mode による候補の絞り込み（`br-actor-assignment` の責務）。
  - 実行主体の上限や隔離方法による着手の延期（実行受入の責務）。
  - 登録簿（register）の個票や定期実行定義（routine）の選択。

## 3. ルール（判定/計算）

### 3.1. 判定規則

#### 3.1.1. 戦略の確定

1. 明示指定の戦略があればそれを使う。大文字・小文字と前後の空白は区別しない。
2. 明示指定がなければ、実行主体の既定戦略を使う（起動経路による参照有無の差は `U-04`）。
3. どちらもなければ `critical-first` を使う（全体の既定値）。
4. 確定した戦略が `critical-first` / `fifo` 以外なら、選択を行わず例外 `E-01` とする（メンバー定義側の許容値との整合は `U-03`）。

#### 3.1.2. `critical-first` の順位

全体の完了を遅らせやすいタスクを先にする。余裕日数と最早開始日の両方を持つタスク同士は、次の順で比較する。

1. 余裕日数が小さいほうを先にする（クリティカルパス上のタスクは余裕日数 0）。
2. 余裕日数が同じなら、最早開始日が早いほうを先にする。
3. それも同じなら、タスク ID の辞書順で先のほうを先にする（実行環境に依存しない照合方法の確定は `U-06`）。

余裕日数と最早開始日のいずれも持たないタスクは、両方を持つタスクすべての後ろに置き、その中ではタスク ID の辞書順に並べる。一方の項目だけがない場合の扱いは未決であり、この草案では期待順位を確定しない（`U-05`）。

#### 3.1.3. `fifo` の順位

タスク ID の辞書順に並べる（名称と到着順の扱いは `U-02`、辞書順の照合方法は `U-06`）。工程計算結果は参照しない。

#### 3.1.4. 工程計算ができない場合

Schedule から工程計算結果を算出できない場合は、指定された戦略にかかわらず `fifo` と同じ順位（タスク ID の辞書順）で選ぶ（`E-02`）。着手は止めない。

#### 3.1.5. 着手タスクの決定

- track 指定がある場合は、候補タスク集合のうち指定された track に属するタスクだけを順位付けと選択の対象とする。
- 単発の着手では、順位の先頭を次の着手タスクとする。
- 並行実行では、順位の上位から順に取り出す。上位のタスクが実行受入で延期された場合は、順位を保ったまま次のタスクへ進む。
- 候補タスク集合（track 指定による絞り込み後を含む）が空なら、着手タスクなしとする（`E-03`）。

#### 3.1.6. Ready 一覧の派生ビューを使う経路

Ready 一覧の派生ビューを使って選ぶ場合は、その候補と戦略別順位を参照する。派生ビューが存在しない、または内容が壊れている場合は、順位を参照できないため `E-04` とする。工程計算不能時の代替順位（`E-02`）とは区別する。

### 3.2. 判定例

以下は既存の規則に対応する判定例である。一方の項目のみ欠損する場合（例: `T-A`（1 / 最早開始日なし）と `T-B`（1 / 2）の比較）および ID 比較方法に依存する場合（例: `T-2` と `T-10`、`T-A` と `T-a` の比較）の期待結果は、`U-05`・`U-06` の判断後に確定する。

| 例  | 入力・前提（戦略、余裕日数 / 最早開始日）                                 | 適用規則                            | 期待結果                           |
| --- | ------------------------------------------------------------------------- | ----------------------------------- | ---------------------------------- |
| 1   | `critical-first`、`T-B`（0 / 3）、`T-A`（2 / 1）                          | 3.1.2（余裕日数優先）               | `T-B` → `T-A`、着手は `T-B`        |
| 2   | `critical-first`、`T-B`（1 / 2）、`T-A`（1 / 5）                          | 3.1.2（最早開始日での比較）         | `T-B` → `T-A`、着手は `T-B`        |
| 3   | `critical-first`、`T-B`（1 / 2）、`T-A`（1 / 2）                          | 3.1.2（ID 辞書順での決着）          | `T-A` → `T-B`、着手は `T-A`        |
| 4   | `critical-first`、`T-A`（余裕日数・最早開始日ともになし）、`T-B`（3 / 9） | 3.1.2（計算結果なしは後方）         | `T-B` → `T-A`、着手は `T-B`        |
| 5   | `fifo`、`T-B`（0 / 3）、`T-A`（2 / 1）                                    | 3.1.3（`fifo` の ID 辞書順）        | `T-A` → `T-B`、着手は `T-A`        |
| 6   | `critical-first`、例 1 と同じ候補、工程計算不能                           | 3.1.4・`E-02`（代替順位）           | `T-A` → `T-B`、着手は `T-A`        |
| 7   | 明示指定なし、実行主体の既定戦略なし                                      | 3.1.1（戦略の確定）                 | `critical-first` を選択戦略とする  |
| 8   | `critical-first`、候補タスク集合が空                                      | 3.1.5・`E-03`（候補なし）           | 次の着手タスク「なし」（正常）     |
| 9   | 明示指定の戦略が許容外（`critical-first` / `fifo` 以外）                  | 3.1.1・`E-01`（許容外の戦略の拒否） | `E-01`。順位・着手タスクを返さない |

## 4. 出力

| 出力             | 意味・単位または区分                                                                                                 | 利用先                                                     |
| ---------------- | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 確定した選択戦略 | `critical-first` または `fifo`                                                                                       | 着手記録（claim）の根拠                                    |
| 戦略別の順位     | `critical-first` と `fifo` の両戦略それぞれの候補の並び順と順位番号。派生ビューで表示する既定戦略は `critical-first` | Ready 一覧の派生ビューへの提示、および派生ビュー経路の参照 |
| 次の着手タスク   | 確定した戦略の順位の先頭のタスク ID、または「なし」（候補タスク集合が空の場合）                                      | 実行受入・着手記録                                         |

候補タスク集合が空の場合（`E-03`）は、次の着手タスクを「なし」（対象なし）として正常終了する。工程計算不能時（`E-02`）は代替順位による結果を使う。戦略不正（`E-01`）または派生ビュー参照不能（`E-04`）の判定不能時は選択失敗とし、正常な対象なしと区別する。複数条件が重なる場合の優先順位は `U-07` で扱う。

## 5. 例外 / 異常系

| ID     | 状況                                                                               | 扱い                                                                                                   | 利用者の次の手                                          |
| ------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------- |
| `E-01` | 確定した戦略が本ルールで扱う戦略ではない                                           | 選択しない。指定可能な戦略を示して失敗とする                                                           | 指定者が戦略を修正する                                  |
| `E-02` | 工程計算結果を算出できない（Schedule の不整合など）                                | 着手は止めず、3.1.2 の比較を 3.1.4 の代替順位（タスク ID の辞書順）に置き換えて選ぶ                    | Schedule 側で工程計算の不具合を解消する                 |
| `E-03` | 候補タスク集合が空                                                                 | 着手タスクなしとして正常に終える。担当・mode や track の絞り込みで空になった場合はその旨を利用者に示す | PM・Orchestrator が候補の有無と絞り込み条件を確認する   |
| `E-04` | Ready 一覧の派生ビューを使う経路で、派生ビューが存在しない、または内容が壊れている | 選択しない。再生成を求めて失敗とする                                                                   | PM・Orchestrator が派生ビューを再生成して選択をやり直す |

例外条件が同時に成立する場合の優先順位は未決である。個別の例外規則から優先順を推測せず、`U-07` の判断後に判定規則と判定例へ反映する。

## 6. メモ / 将来課題

以下の判断依頼先は、解消を依頼するロールを示し、承認済みであることを表さない。

| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `U-01` | _ASSUMPTION_: 依存先 `bps-task-selection-preparation` が未作成のため、適用場面と対象外の境界を既存記述のまま仮置きしている                                              | PM に先行仕様の整備を依頼し、PO に境界の判断を依頼 | 先行仕様の作成後、本書の業務承認前 | BPS の手順と本書の適用範囲・対象外の対応が必要。実行受入との接続を確定できない                                                                |
| `U-02` | _UNDECIDED_: `fifo` を Ready になった到着順に変えるか、現行の ID 順を維持して名称・説明を改めるか                                                                       | PO                                                 | 本書の業務承認前                   | DEV の順位実装と QE の期待値に影響。判断までは到着順と解釈しない                                                                              |
| `U-03` | _UNDECIDED_: メンバー定義側の許容値と本ルールの許容範囲との差をそろえるか、追加戦略の意味を定めるか                                                                     | PO（ARC が定義間の整合を整理）                     | 設定と選択規則の整合を承認する前   | DEV の入力検証と `E-01` の受入条件に影響。現行の許容範囲を推測で広げない                                                                      |
| `U-04` | _ASSUMPTION_: 自動 claim は実行主体の既定戦略を参照し、エージェント実行の自動選択は参照しないと仮置きしている。差の確認と、統一するか意図的な差として残すかの判断が必要 | PO（PM・Orchestrator に利用経路の確認を依頼）      | 自動選択の適用方針の承認前         | 経路ごとの選択結果・着手記録の根拠・QE の期待値に影響。差の確認根拠と採用方針が必要                                                           |
| `U-05` | _UNDECIDED_: 余裕日数・最早開始日の一方だけが欠ける場合を、計算結果なしとするか、残る項目で比較するか                                                                   | PO（ARC が比較規則を整理）                         | 順位規則の実装・テスト仕様の確定前 | `T-A`（1 / ES なし）と `T-B`（1 / ES 2）の順位、および余裕日数なし・ES ありの扱いが決まらない。判断後に各項目の有無の定義と期待順位を追記する |
| `U-06` | _UNDECIDED_: ID の辞書順を環境に依存しないどの照合方法で比較するか                                                                                                      | PO（ARC が比較方法を提案）                         | 順位規則の実装・テスト仕様の確定前 | コードポイント順等の採用判断が必要。`T-2` と `T-10`、`T-A` と `T-a` の比較例を確定し、DEV・QE が同じ順位を再現できるようにする                |
| `U-07` | _UNDECIDED_: 戦略不正・派生ビュー参照不能・候補なし・工程計算不能の条件が重なる場合に、どの結果を優先するか                                                             | PO（ARC が競合条件を整理）                         | 例外規則の実装・テスト仕様の確定前 | 例として戦略不正かつ候補なしの場合に、失敗と正常な対象なしのどちらを返すかが決まらない。承認された優先順と判定例が必要                        |

業務承認を依頼できる条件は、`U-01` の先行仕様との照合と、`U-02`〜`U-07` の採用方針・根拠がそろい、影響する入力・規則・判定例へ反映されていることである。PO に適用範囲と戦略の業務的妥当性の承認を依頼し、未解消の間は該当範囲の実装・受入条件を確定しない。人間の承認前は `status: draft` を維持する。
