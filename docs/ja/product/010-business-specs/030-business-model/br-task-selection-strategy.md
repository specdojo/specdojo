# タスク選択戦略

Ready なタスクが複数あるとき、選択戦略（`critical-first` / `fifo`）に従って候補の順位を決め、次に着手するタスクを一つに定める判定ルール。

## 1. 概要

- 判断内容: 選択戦略を一つに確定し、その戦略で Ready なタスクの順位を付け、先頭を次の着手タスクとする。
- 業務価値: 限られた実行主体（人・AI Agent）と作業時間を、全体の完了を遅らせるタスクから順に充てることで、特定の参加者が調整を抱え込まずに進行を継続できるようにする（`BV-02`・`BV-03`）。戦略は誰が選んでも同じ入力から同じ順位になるため、着手順の判断を引き継げる。
- 参照する業務プロセス: 実行受入（`bps-task-selection-preparation`、`P-07-01`）で、実行対象の候補を絞り込んだ後の着手順の決定に使う。
- 主な利用者: 実行を起動する PM・Orchestrator は戦略を指定し、PO は既定戦略の妥当性を承認する。
- 適用範囲: Schedule（track）から展開されたタスクのうち Ready なもの。単発の着手（1 件選択）と、並行実行で上位から複数件を順に取り出す場合の両方に同じ順位を使う。
- 対象外:
  - タスクが Ready かどうかの判定（依存の完了状況による判定は Schedule 側の責務）。
  - 担当ロール・実行区分・mode による候補の絞り込み（`br-actor-assignment` の責務）。
  - 実行主体の上限や隔離方法による着手の延期（実行受入の責務）。
  - 登録簿（register）の個票や定期実行定義（routine）の選択。

## 2. 入力

| 入力               | 概念データ・項目                                                 | 利用目的                                    |
| ------------------ | ---------------------------------------------------------------- | ------------------------------------------- |
| 候補タスク集合     | Ready なタスクのタスク ID（担当・mode による絞り込み後）         | 順位付けの対象                              |
| 明示指定の戦略     | 実行起動時に指定された選択戦略                                   | 戦略の最優先の決定根拠                      |
| 実行主体の既定戦略 | メンバー定義（人・AI Agent）の既定選択戦略                       | 明示指定がない場合の決定根拠                |
| 工程計算結果       | 各タスクの余裕日数（slack）と最早開始日（ES）。Schedule から算出 | `critical-first` の順位の基準               |
| track 指定（任意） | 対象とする Schedule（track）                                     | 指定時に候補を同じ track のタスクだけに限る |

## 3. ルール（判定/計算）

### 3.1. 戦略の確定

1. 明示指定の戦略があればそれを使う。大文字・小文字と前後の空白は区別しない。
2. 明示指定がなければ、実行主体の既定戦略を使う。
3. どちらもなければ `critical-first` を使う（全体の既定値）。
4. 確定した戦略が `critical-first` / `fifo` 以外なら、選択を行わず例外 `E-01` とする。

_ASSUMPTION_: 実行主体の既定戦略（2.）は、1 件ずつ着手を割り当てる自動 claim では参照されるが、エージェント実行の自動選択では参照されず、明示指定がなければ直ちに 3. になる。両者をそろえるべきかは「メモ / 将来課題」に記録した。

### 3.2. `critical-first` の順位

全体の完了を遅らせやすいタスクを先にする。工程計算結果を持つタスク同士は、次の順で比較する。

1. 余裕日数が小さいほうを先にする（クリティカルパス上のタスクは余裕日数 0 で最優先）。
2. 余裕日数が同じなら、最早開始日が早いほうを先にする。
3. それも同じなら、タスク ID の辞書順で先のほうを先にする。

工程計算結果を持たないタスクは、持つタスクすべての後ろに置き、その中ではタスク ID の辞書順に並べる。

### 3.3. `fifo` の順位

タスク ID の辞書順に並べる。工程計算結果は参照しない。

### 3.4. 工程計算ができない場合

Schedule から工程計算結果を算出できない場合は、指定された戦略にかかわらず `fifo` と同じ順位（タスク ID の辞書順）で選ぶ。着手は止めない（`E-02`）。

### 3.5. 着手タスクの決定

- 単発の着手では、順位の先頭を次の着手タスクとする。
- 並行実行では、順位の上位から順に取り出す。上位のタスクが実行受入で延期された場合は、順位を保ったまま次のタスクへ進む。
- 候補タスク集合が空なら、着手タスクなしとする（`E-03`）。

```ts
type 候補 = { タスクID: string; 余裕日数?: number; 最早開始日?: number };

function 着手順位(候補一覧: 候補[], 戦略: "critical-first" | "fifo", 工程計算可: boolean): 候補[] {
  const ID順 = (a: 候補, b: 候補) => a.タスクID.localeCompare(b.タスクID);
  if (戦略 === "fifo" || !工程計算可) return [...候補一覧].sort(ID順);
  return [...候補一覧].sort((a, b) => {
    const aあり = a.余裕日数 !== undefined;
    const bあり = b.余裕日数 !== undefined;
    if (aあり !== bあり) return aあり ? -1 : 1;
    if (aあり && bあり) {
      if (a.余裕日数 !== b.余裕日数) return a.余裕日数! - b.余裕日数!;
      if (a.最早開始日 !== b.最早開始日) return a.最早開始日! - b.最早開始日!;
    }
    return ID順(a, b);
  });
}
```

### 3.6. 判定例

| 例  | 候補（余裕日数 / 最早開始日）             | 戦略             | 順位                    | 確認する規則       |
| --- | ----------------------------------------- | ---------------- | ----------------------- | ------------------ |
| 1   | `T-B`（0 / 3）、`T-A`（2 / 1）            | `critical-first` | `T-B` → `T-A`           | 余裕日数優先       |
| 2   | `T-B`（1 / 2）、`T-A`（1 / 5）            | `critical-first` | `T-B` → `T-A`           | 最早開始日での比較 |
| 3   | `T-B`（1 / 2）、`T-A`（1 / 2）            | `critical-first` | `T-A` → `T-B`           | ID 辞書順での決着  |
| 4   | `T-A`（工程計算結果なし）、`T-B`（3 / 9） | `critical-first` | `T-B` → `T-A`           | 計算結果なしは後方 |
| 5   | `T-B`（0 / 3）、`T-A`（2 / 1）            | `fifo`           | `T-A` → `T-B`           | ID 辞書順          |
| 6   | 例 1 と同じ、工程計算不能                 | `critical-first` | `T-A` → `T-B`           | `E-02` の代替順位  |
| 7   | 明示指定なし、実行主体の既定戦略なし      | （未指定）       | `critical-first` で判定 | 既定値             |

## 4. 出力

| 出力             | 内容                                                | 参照先                                 |
| ---------------- | --------------------------------------------------- | -------------------------------------- |
| 確定した選択戦略 | `critical-first` または `fifo`                      | 着手記録（claim）の根拠として残す      |
| 戦略別の順位     | 両戦略それぞれの候補の並び順と順位番号              | Ready 一覧の派生ビューで並べて提示する |
| 次の着手タスク   | 確定した戦略の順位の先頭のタスク ID、または「なし」 | 実行受入・着手記録                     |

Ready 一覧の派生ビューは、確定した戦略に関係なく `critical-first` と `fifo` の両方の順位を示し、既定戦略として `critical-first` を表示する。

## 5. 例外 / 異常系

| ID     | 状況                                                                                     | 扱い                                                                                          |
| ------ | ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `E-01` | 確定した戦略が `critical-first` / `fifo` 以外                                            | 選択しない。指定可能な戦略を示して失敗とし、指定者に戦略の修正を求める                        |
| `E-02` | 工程計算結果を算出できない（Schedule の不整合など）                                      | 着手は止めず、ID 辞書順で選ぶ。工程計算の不具合は Schedule 側で別途解消する                   |
| `E-03` | 候補タスク集合が空                                                                       | 着手タスクなしとして正常に終える。担当・mode の絞り込みで空になった場合はその旨を利用者に示す |
| `E-04` | Ready 一覧の派生ビューを使って選ぶ場合に、派生ビューが存在しない、または内容が壊れている | 選択しない。派生ビューの再生成を求めて失敗とする                                              |
