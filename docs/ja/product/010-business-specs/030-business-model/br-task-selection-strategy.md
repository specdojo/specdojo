# タスク選択戦略

Ready なタスクが複数あるとき、選択戦略（`critical-first` / `fifo`）に従って候補の順位を決め、次に着手するタスクを一つに定める判定ルール。

## 1. 概要

- 業務価値: 限られた実行主体（人・AI Agent）と作業時間を、全体の完了を遅らせるタスクから順に充てることで、特定の参加者が調整を抱え込まずに進行を継続できるようにする（[[prj-0001:prj-overview|プロジェクト概要]] の `BV-02`・`BV-03`）。誰が選んでも同じ入力から同じ順位を再現できる規則にし、着手順の判断を引き継げることを目指す。
- 参照する業務プロセス: 実行受入（`bps-task-selection-preparation`、`P-07-01`）で、実行対象の候補を絞り込んだ後の着手順の決定に使う。
- 主な利用者: 実行を起動する PM・Orchestrator は戦略を指定し、PO は既定戦略の妥当性を承認する。
- 適用範囲: Schedule（track）から展開されたタスクのうち Ready なもの。単発の着手（1 件選択）と、並行実行で上位から複数件を順に取り出す場合の両方に同じ順位を使う。
- 対象外:
  - タスクが Ready かどうかの判定（依存の完了状況による判定は Schedule 側の責務）。
  - 担当ロール・実行区分・mode による候補の絞り込み（`br-actor-assignment` の責務）。
  - 実行主体の上限や隔離方法による着手の延期（実行受入の責務）。
  - 登録簿（register）の個票や定期実行定義（routine）の選択。

_ASSUMPTION_: 依存先 `prj-0001:bps-task-selection-preparation` が未作成のため、上記の適用境界は既存記述を引き継いだ仮置きであり、同仕様との照合と PO の判断が必要である。`based_on` はこの依存先を明示するもので、内容を確認済みという意味ではない。解消条件は「メモ / 将来課題」の `U-01` に示す。

| 入力                   | 概念データ・項目                                                          | 利用目的                                    | 適用条件・欠損時の扱い                         |
| ---------------------- | ------------------------------------------------------------------------- | ------------------------------------------- | ---------------------------------------------- |
| 候補タスク集合         | Ready なタスクのタスク ID（担当・mode による絞り込み後）                  | 順位付けの対象                              | 空集合なら `E-03`                              |

| 工程計算結果           | 各タスクの余裕日数（slack、日数）と最早開始日（ES、工程計算上の開始時点） | `critical-first` の比較                     | 算出不能は `E-02`。項目ごとの一部欠損は `U-05` |

## 3. ルール（判定/計算）

### 3.1. 判定規則

#### 3.1.1. 戦略の確定

1. 明示指定の戦略があればそれを使う。大文字・小文字と前後の空白は区別しない。
2. 明示指定がなければ、実行主体の既定戦略を使う。
3. どちらもなければ `critical-first` を使う（全体の既定値）。
4. 確定した戦略が `critical-first` / `fifo` 以外なら、選択を行わず例外 `E-01` とする。

_ASSUMPTION_: 実行主体の既定戦略の参照には経路による差があると仮置きしている。依存先の業務プロセス仕様が未作成で、経路ごとの適用方針を確認できないためである。差の確認と PO の判断は「メモ / 将来課題」の `U-04` に示す。

#### 3.1.2. `critical-first` の順位

全体の完了を遅らせやすいタスクを先にする。余裕日数と最早開始日の両方を持つタスク同士は、次の順で比較する。

1. 余裕日数が小さいほうを先にする（クリティカルパス上のタスクは余裕日数 0）。
2. 余裕日数が同じなら、最早開始日が早いほうを先にする。
3. それも同じなら、タスク ID の辞書順で先のほうを先にする。

余裕日数と最早開始日のいずれも持たないタスクは、両方を持つタスクすべての後ろに置き、その中ではタスク ID の辞書順に並べる。一方の項目だけがない場合の扱いは未決であり、この草案では期待順位を確定しない（`U-05`）。

_UNDECIDED_: 本書の「辞書順」の照合方法は未確定である。実行環境によらず同じ順位になる比較規則と判定例を確定する必要がある（`U-06`）。

#### 3.1.3. `fifo` の順位

タスク ID の辞書順に並べる。工程計算結果は参照しない。

#### 3.1.4. 工程計算ができない場合

Schedule から工程計算結果を算出できない場合は、指定された戦略にかかわらず `fifo` と同じ順位（タスク ID の辞書順）で選ぶ。着手は止めない。

#### 3.1.5. 着手タスクの決定

- 単発の着手では、順位の先頭を次の着手タスクとする。
- 並行実行では、順位の上位から順に取り出す。上位のタスクが実行受入で延期された場合は、順位を保ったまま次のタスクへ進む。
- 候補タスク集合が空なら、着手タスクなしとする（`E-03`）。

#### 3.1.6. Ready 一覧の派生ビューを使う経路

Ready 一覧の派生ビューを使って選ぶ場合は、その候補と戦略別順位を参照する。派生ビューが存在しない、または内容が壊れている場合は、順位を参照できないため `E-04` とする。工程計算不能時の代替順位（`E-02`）とは区別する。

### 3.2. 判定例

以下は入力がそろう範囲の既存例である。ID 比較方法と項目の一部欠損の判定例は、`U-05`・`U-06` の判断後に確定する。

| 例  | 入力・前提（戦略、余裕日数 / 最早開始日）                                 | 適用規則           | 期待結果                |
| --- | ------------------------------------------------------------------------- | ------------------ | ----------------------- |
| 1   | `critical-first`、`T-B`（0 / 3）、`T-A`（2 / 1）                          | 余裕日数優先       | `T-B` → `T-A`           |
| 2   | `critical-first`、`T-B`（1 / 2）、`T-A`（1 / 5）                          | 最早開始日での比較 | `T-B` → `T-A`           |
| 3   | `critical-first`、`T-B`（1 / 2）、`T-A`（1 / 2）                          | ID 辞書順での決着  | `T-A` → `T-B`           |
| 4   | `critical-first`、`T-A`（余裕日数・最早開始日ともになし）、`T-B`（3 / 9） | 計算結果なしは後方 | `T-B` → `T-A`           |
| 5   | `fifo`、`T-B`（0 / 3）、`T-A`（2 / 1）                                    | ID 辞書順          | `T-A` → `T-B`           |
| 6   | `critical-first`、例 1 と同じ候補、工程計算不能                           | `E-02` の代替順位  | `T-A` → `T-B`           |
| 7   | 明示指定なし、実行主体の既定戦略なし                                      | 戦略の確定         | `critical-first` で判定 |

## 4. 出力

| 出力             | 内容                                                | 参照先                                 |
| ---------------- | --------------------------------------------------- | -------------------------------------- |
| 確定した選択戦略 | `critical-first` または `fifo`                      | 着手記録（claim）の根拠として残す      |
| 戦略別の順位     | 両戦略それぞれの候補の並び順と順位番号              | Ready 一覧の派生ビューで並べて提示する |
| 次の着手タスク   | 確定した戦略の順位の先頭のタスク ID、または「なし」 | 実行受入・着手記録                     |

Ready 一覧の派生ビューは、確定した戦略に関係なく `critical-first` と `fifo` の両方の順位を示し、既定戦略として `critical-first` を表示する。

## 5. 例外 / 異常系

| ID     | 状況                                                                               | 扱い                                                                                          | 利用者の次の手                                          |
| ------ | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `E-01` | 確定した戦略が本ルールで扱う戦略ではない                                           | 選択しない。指定可能な戦略を示して失敗とする                                                  | 指定者が戦略を修正する                                  |
| `E-02` | 工程計算結果を算出できない（Schedule の不整合など）                                | 着手は止めず、「工程計算ができない場合」の代替順位で選ぶ                                      | Schedule 側で工程計算の不具合を解消する                 |
| `E-03` | 候補タスク集合が空                                                                 | 着手タスクなしとして正常に終える。担当・mode の絞り込みで空になった場合はその旨を利用者に示す | PM・Orchestrator が候補の有無と絞り込み条件を確認する   |
| `E-04` | Ready 一覧の派生ビューを使う経路で、派生ビューが存在しない、または内容が壊れている | 選択しない。再生成を求めて失敗とする                                                          | PM・Orchestrator が派生ビューを再生成して選択をやり直す |
