# コミュニケーション計画 作成レシピ

Communication Plan Writing Recipe

ステークホルダーの情報要求を、必要なコミュニケーション機会と証跡へ変換する作り方です。

## 1. このレシピの使い方

- ステークホルダー登録簿から必要な合意・確認だけを選びます。
- 会議、報告、通知を一つの機会表へ統合します。
- エスカレーションと情報取扱いを加え、重複を削除します。
- 判断・情報要求（Why）、合意・確認する内容と時期（What）、機会・手段・責任（How）を整理し、ステークホルダー ID と証跡で対応を追跡します（Trace）。会議の進行詳細や関係者一覧は本書へ再掲しません。

## 2. 作成前に集める情報

| 項目     | 集める情報                                 |
| -------- | ------------------------------------------ |
| 対象     | 判断者、当事者、利用者、協力者、実行ロール |
| 情報要求 | 何を判断・確認・共有する必要があるか       |
| 契機     | 作業節目、代表試行、上限超過、公開、変更   |
| 手段     | 登録簿、Pull Request、Issue、試行記録など  |
| 証跡     | 判断・確認結果を残す正本                   |
| 取扱い   | 公開、限定共有、入力禁止の情報             |

## 3. 全体の作成手順

1. 対象とする主要な合意・確認を決めます。
2. 各機会について対象、内容、時期、手段、責任、証跡を書きます。
3. 同じ内容の会議・報告・通知を一行へ統合します。
4. 人間の判断が必要なエスカレーション条件を定義します。
5. 情報区分と取扱いを最小限で定義します。
6. 見直し条件と未決事項を記載します。

## 4. 各章の書き方

### 4.1. 方針と適用範囲

- 常設会議か非同期確認かを決めます。
- 関係者名簿は再掲せず、対象IDまたはRole codeを使います。
- AI Agentは伝達・整理を支援しても、合意主体にしません。

### 4.2. コミュニケーション機会

- 一行は一つの判断・確認機会にします。
- 伝える内容より、相手が何を判断・確認するかを明確にします。
- 結果を残す証跡を必ず置きます。

### 4.3. エスカレーション

- 当事者価値、費用・負荷、品質・安全、公開・権利を分けます。
- 一次対応と最終判断者を区別します。
- 「必要に応じて」だけで終わらせません。

### 4.4. 情報管理と公開

- 公開可能情報と入力禁止情報を区別します。
- 個人情報や秘密情報を公開記録とAgent入力へ含めません。
- 生成ビューではなく正本を更新します。

## 5. 深掘り手順

1. そのコミュニケーションがなければ誰の判断が止まるか確認します。
2. 同じ対象・内容・時期の行を統合します。
3. 証跡のない会議や報告を削除します。
4. 日常課題を登録簿へ移します。

## 6. 良い例 / 悪い例

| 観点 | 良い例                                   | 悪い例                   |
| ---- | ---------------------------------------- | ------------------------ |
| 機会 | 代表試行後に利用者が価値と負荷を確認する | 利用者会議を定期開催する |
| 証跡 | 評価結果と採否を試行記録へ残す           | 議論したことだけを書く   |
| 対象 | ステークホルダーIDまたはRole code        | 個人名と連絡先           |

## 7. レビュー観点

- ステークホルダーの必要な合意を漏らしていないか。
- 会議・報告・チャネルが重複していないか。
- 判断者と証跡が明確か。
- 公開・非公開の境界が守られているか。

## 8. 仕上げチェック

- コミュニケーション機会、エスカレーション、情報取扱いがある。
- 目的のない定例会議がない。
- 関係者一覧やRole code定義を再掲していない。
- Agentに合意・承認を委ねていない。
- 各コミュニケーション機会が、元の判断・情報要求と結果の証跡に対応している。
