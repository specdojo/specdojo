# プロジェクト管理計画 作成レシピ

Project Management Plan Writing Recipe

価値検証に必要な管理・判断・証跡だけを、一つの軽量な管理計画へまとめる作り方です。

## 1. このレシピの使い方

- 概要、スコープ、成功基準から管理すべき価値と上限を抜き出します。
- 管理領域を一表へ統合し、判断ゲートと正本を接続します。
- 個別計画、RACI、Schedule、登録簿との重複を削除して仕上げます。
- 検証する価値と逸脱リスク（Why）、管理基準・上限・判断ゲート（What）、確認契機・逸脱時対応・責任（How）を整理し、成功基準 ID と各正本の証跡で追跡します（Trace）。個別計画の詳細は参照先へ委譲します。

## 2. 作成前に集める情報

| 項目       | 集める情報                                                                  |
| ---------- | --------------------------------------------------------------------------- |
| 価値と判定 | 成功基準 ID、受入条件 ID、判定時期                                          |
| 境界       | スコープ内外、主要な変更条件                                                |
| 費用・負荷 | 現金支出、作業時間、継続運用負荷の上限                                      |
| 実行管理   | Schedule、依存、主要成果物、登録簿                                          |
| 判断       | 公開、例外、主要変更、継続・停止の判断者                                    |
| 正本       | 組織、RACI、品質、コミュニケーション、記録の参照先                          |
| 依存関係   | 概要・スコープ・成功基準・組織定義へのカタログ依存と、直接根拠にする文書 ID |

## 3. 全体の作成手順

1. カタログを使う場合は概要・スコープ・成功基準と、直接根拠にする組織定義への依存を確認し、不足を先行作業にします。根拠 ID と依存の対応が確認できてから管理目的を価値と期間で一文にします。
2. 軽量プロファイルを基本とし、拡張が必要な条件を決めます。
3. 管理対象ごとに価値・リスクの根拠 ID、基準・上限、確認契機、逸脱時対応、責任、証跡の正本と記録識別子を一表へ書きます。
4. 人間の判断が必要なゲートだけを定義します。
5. Schedule、RACI、費用記録、品質証跡、登録簿の正本を示します。
6. 未決事項へ決定時期と判断者を付けます。
7. 他文書の一覧や詳細手順を削除します。

## 4. 各章の書き方

### 4.1. 管理目的と適用方針

- どの価値を、いつからいつまで検証しますか。運用前に集める比較基準値も前提作業へ置けていますか。
- 人間が最終判断する事項と AI Agent が支援する作業は何ですか。
- 軽量・拡張のどちらを選び、契約・監査・組織規模の何が変わると拡張しますか。

### 4.2. 統合管理方針

- 各行はどの価値・リスク・条件 ID を守りますか。基準と証跡の該当記録を行から一意に辿れますか。
- 誰が、いつ逸脱を検知し、どの行動へ移りますか。構成の版・承認済み基準や技術依存の変更も確認します。
- 現金支出、準備・開発時間、継続運用負荷を区別でき、同じ基準・証跡だけを重ねた行を統合できていますか。

### 4.3. 判断ゲートとエスカレーション

- ゲートに適用する成功基準・受入条件 ID は何ですか。初期受入と後続の観測を区別します。
- 未達・材料不足・上限超過なら何を保留し、誰が是正・再判定を起案しますか。
- 人間の最終判断者と判断記録先を、材料の整理担当から区別できていますか。

### 4.4. 正本・報告・見直し

- 情報ごとの更新先と報告を確認する Role は誰ですか。未整備の正本には整備担当・時期を付けます。
- 判断・逸脱・作業節目のどれを報告契機にしますか。作業担当と成果物の承認責任を混同していませんか。
- 変更時の影響先、更新順序、担当・期限・確認担当をどの追従タスクへ渡しますか。

### 4.5. 未決事項

- どの論点が未決で、決定まで何を保留しますか。
- 決定時期と人間の判断者は誰ですか。他の正本にあれば該当論点を参照します。
- 期限超過時に誰が管理簿へ移し、担当 Role と転送先を追跡しますか。

## 5. 深掘り手順

1. 管理項目がどの価値または制約を守るか確認します。
2. 基準のない管理項目は削除するか基準を定めます。
3. 同じ責任・証跡を持つ行を統合します。
4. 個別計画へ委譲できる説明を削除します。

## 6. 良い例 / 悪い例

| 観点     | 良い例                           | 悪い例                       |
| -------- | -------------------------------- | ---------------------------- |
| 管理目的 | SC-01〜SC-03の代表試行を管理する | 一般的なPM項目を管理する     |
| コスト   | 現金支出と作業時間を別上限で確認 | 金額予算はないので管理しない |
| 正本     | 課題・リスクは登録簿を正とする   | 本文にも同じ一覧を持つ       |

## 7. レビュー観点

| 観点 | 確認内容                                                                     |
| ---- | ---------------------------------------------------------------------------- |
| 根拠 | 価値・スコープ・成功基準と管理行が対応し、カタログ依存から直接根拠を辿れるか |
| 委譲 | 個別計画、RACI、Schedule、登録簿を再掲せず、更新先と確認者を示せるか         |
| 判定 | 条件 ID、不足時の保留、人間の最終判断者、証跡が接続しているか                |
| 負荷 | 現金支出、作業時間、継続運用負荷を別々に判断できるか                         |

## 8. 仕上げチェック

- 統合管理表、判断ゲート、正本がそろっている。
- 未決事項に決定時期と判断者がある。
- Agentに最終判断を委ねていない。
- 必要性のない章・表・関連文書一覧を残していない。
- 各管理対象について、価値またはリスク、基準・上限、確認契機、逸脱時対応、証跡が一続きで追跡できる。
