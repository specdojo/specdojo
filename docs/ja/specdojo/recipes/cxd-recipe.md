# C4コンテキスト図 作成レシピ

C4 Context Diagram Writing Recipe

利用目的から対象システムの責務を選び、人・外部システムとの境界を説明するための作成手順です。境界の根拠が弱い箇所を見つけ、接続先の数や実装の細かさで全体像を埋めないようにします。

## 1. このレシピの使い方

- 利用者の課題と期待する成果を入力とし、対象システムが引き受ける責務と外へ委ねる責務を対にして書き出します。
- 図にする前に、直接の利用者、外部システム、やり取りの目的を短い表へ置きます。内部の分割や詳細な連携構文は下位設計へ渡します。
- 図と定義表を要素名・関係 ID で対応付け、境界の判断から根拠・未決事項をたどれるようにします。最後に外部依存が使えない場合をたどって、説明の抜けを探します。

## 2. 作成前に集める情報

| 項目         | 集める情報・問い                                                     |
| ------------ | -------------------------------------------------------------------- |
| 利用目的     | 誰の何の課題を解き、どの成果を対象システムが支えるか                 |
| 対象範囲     | 一つのシステムとして何を引き受け、何を人間・別システムへ委ねるか     |
| 利用者候補   | 直接操作する人と、判断・確認だけに関わる人は誰か                     |
| 外部依存候補 | どの情報・処理を外部へ依頼するか。必須か、特定機能を選んだときだけか |
| 関係の根拠   | 呼び出し元、相手、情報の要点を確認できる許可された文書は何か         |
| 詳細の更新先 | 操作、連携契約、内部構成、技術の詳細をどこへ渡すか                   |
| 未確定事項   | 根拠不足の接続経路、失敗時の保持範囲、解消する担当と条件は何か       |

## 3. 全体の作成手順

1. 利用目的と本図の対象外を「概要」へ書き、読む人が何を確認するかを整理します。
2. 「要素と境界の定義」で中核責務と委譲先を対にします。実装モジュール名を隠しても責務を説明できるか確かめます。
3. 直接の利用者と外部システムを選び、関係ごとに起点・終点・目的・情報の要点を記入します。利用者全員をプロジェクトの役職へ機械的に置き換えません。
4. 関係を短いラベルにして「C4コンテキスト図（Mermaid）」へ描きます。利用目的から選んだ対象を中心に、責務の分担を使って人・外部システムを配置します。矢印を利用・依頼の向きに読んでもらい、応答の省略や依存をまとめた表示で解釈が割れる箇所に注記を添えます。
5. 「技術前提・制約と検証観点」で、まず境界が成立する条件を整理し、次に各条件が崩れたときの確認事項を作ります。関係 ID または対象境界を使い、確認する結果と主確認ロールを対応付けます。
6. 不確かな論点を「メモ / 将来課題」へ分け、担当・解消条件・引き継ぎ先を添えます。値や構文の詳細はその更新先へ渡します。

## 4. 各章の書き方

### 4.1. 概要

- 誰がどの結果を得るためのシステムですか。
- 読み手は何を合意し、内部構造や操作の詳細はどこへ委ねますか。
- 関心を持つ人と直接操作する人を区別できていますか。

良い例は「店番担当が現金販売を記録する CLI と、商品・売上管理、印刷の境界を示す」です。「販売を便利にする全体像」では、対象と責務を選べません。

### 4.2. C4コンテキスト図（Mermaid）

- 図の中心が対象システム一つとして読めますか。
- 各矢印の向きを、利用・依頼・送信のどれとして説明できますか。
- 同じ端末にある外部ツールを、対象システムの内部部品として扱っていませんか。
- 人または外部システムの候補がない場合、利用・運用の接点を見落としていませんか。該当しないと判断した理由を説明できますか。

良い例は「CLI → 印刷基盤: 印字依頼・結果取得」です。「CLI → 印刷基盤: 連携」では目的を判断できません。呼び出しが未確認なら、既知の関係に見える線を増やす前に論点を分離します。

### 4.3. 要素と境界の定義

まず対象システムの責務を整理し、Person、External Software System、Relationship の順に具体化します。図の名称を照合の手掛かりにし、各表では図だけで判断できない責任分界や利用条件を掘り下げます。

#### 4.3.1. 対象システムとシステム境界

- 対象システムの名前から、概要で選んだ利用目的と範囲を特定できますか。
- 利用者が期待する結果のうち、対象システムが直接管理するものは何ですか。
- 自システムで引き受けない責務は、人間と別システムのどちらへ委ねますか。

良い例は「CLI はレシート控えを保持し、印刷基盤が物理印字を担う」です。「両方で印刷を管理する」では、失敗時に何を確認するかが曖昧です。

#### 4.3.2. Person（人・ロール）

- 各候補は、操作・運用・管理のどの接点で対象システムを直接利用しますか。
- その接点から何を入力し、どの結果を確認して次の判断へ進みますか。
- 概要で挙げた関係者のうち、直接利用せず設計・承認だけに関わる人は誰ですか。

良い例は「店番担当が会計・印字状態を確認し、結果不明の取引を店舗責任者へ渡す」です。「開発体制にいるので全員を利用者とする」では、製品との接点を説明できません。

#### 4.3.3. External Software System（外部システム）

- 外部へ依頼する処理と、その結果を対象システムが管理する範囲はどこで分かれますか。
- 相手が必要になるのは常時ですか、特定の機能や利用条件を選んだときですか。
- 未導入・障害・応答欠落で影響を受ける結果は何ですか。保持されると説明する情報には根拠がありますか。

良い例は「印刷基盤は会計確定後に使い、時間切れ時は控えと紙面を確認して印字結果を判断する」です。「外部基盤が落ちたら全機能を停止する」では、依存する範囲を切り分けられません。

#### 4.3.4. Relationship（関係・連携契約）

- 起点・終点・ラベルを図と照らし、各関係が支える利用目的を説明できますか。
- 渡す情報・制御の要点と、ローカル実行か外部通信かを確認できる根拠は何ですか。
- 関係 ID から操作・連携の詳細を更新する文書へたどれますか。未作成なら何の契約を引き継ぎますか。

良い例は「`REL-04`: CLI から印刷基盤へ控えを渡して結果を受け取り、引数は外部コマンド連携仕様で管理する」です。「印刷基盤と連携する」だけでは、方向・情報・詳細の更新先を特定できません。

### 4.4. 技術前提・制約と検証観点

- 「技術前提・制約」では、ローカル実行・外部通信・人間の承認のうち、どの条件が境界を成立させていますか。外部へ渡す情報と認証を管理する主体は誰ですか。
- 「システム境界・外部依存の検証観点」では、外部依存の失敗時に、誰が何を見れば結果不明と失敗確定を区別できますか。関係 ID または対象境界に結び付けて整理します。
- これから確かめる検証対象と、契約・実装で確認済みの保証を混ぜていませんか。

良い例は「印字が時間切れになった際、会計結果と控えを確認する」です。「障害でも問題なく動く」では期待結果を選べません。再試行や復旧の詳細は連携・運用の契約へ渡します。

### 4.5. メモ / 将来課題

- 本文の仮定と未決事項のどこに影響しますか。
- 誰がどの情報を得れば解消できますか。
- 未作成の詳細文書を既存のようにリンクしていませんか。

良い例は「売上応答欠落時の照合は契約未整備。ARC / DEV が受付照会の契約を整え、QE が期待結果を確認する」です。「後で検討する」では作業を引き継げません。

## 5. 深掘り手順

1. 線を一本選び、利用者が得たい結果へ逆向きにたどります。目的につながらない依存は本図へ入れる必要を見直します。
2. 相手が使えない場合を置き、失われる結果と保持できる情報を分けます。確認できない保持保証は仮定・論点へ戻します。
3. 外部ツールを内部に置いた場合、誰が変更・運用するのかを問い直します。同じホスト上という理由だけで境界を決めません。
4. 複数の外部基盤を一つにまとめた場合、利用条件や障害の影響が異ならないかを比較し、別要素にするか注記します。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                   | 悪い例                                     |
| ------------ | -------------------------------------------------------- | ------------------------------------------ |
| 利用者の選択 | 店番担当を直接利用者、店舗責任者を判断主体として説明する | 開発体制の全ロールを無条件に Person にする |
| 依存の粒度   | ローカル版管理とリモート共有の責務・利用条件を分ける     | リモート障害で全操作が停止すると断定する   |
| 確定度       | 根拠がない復旧方式は担当と解消条件を付けて残す           | 自動再送・ロールバックを推測で保証する     |
| 詳細への委譲 | 印字依頼の目的を残し、引数は外部コマンド仕様へ渡す       | 全オプションと電文を CXD に転載する        |

## 7. レビュー観点

| 観点         | 確認する問い                                                | 主な確認者 |
| ------------ | ----------------------------------------------------------- | ---------- |
| 価値と利用者 | 各利用関係が解決する課題と結果を説明できるか                | BA         |
| 境界と判断   | 対象範囲と委譲先、人間が判断する範囲を確認できるか          | PO / ARC   |
| 外部依存     | 依頼と結果の管理主体、必須・任意、未確定の条件が分かるか    | ARC        |
| 検証入力     | 不在・失敗・結果不明のときに確かめる情報を特定できるか      | QE         |
| 追跡         | 図の線から関係 ID、責任分界、詳細の更新先と論点をたどれるか | ARC / QE   |

## 8. 仕上げチェック

- 各利用・連携に固有の目的があり、概要の課題と対象範囲へつながっている。
- 図と定義表の名前・関係ラベルが対応し、表は責任分界や利用条件など図にない判断情報を補っている。
- 詳細な値・構文・構造を各正本へ委ね、境界判断に必要な要点を残している。
- 未確認の挙動を保証せず、仮定・未決事項に担当と解消条件がある。
