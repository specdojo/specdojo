# C4コンテキスト図 作成レシピ

C4 Context Diagram Writing Recipe

利用目的から対象システムの責務を選び、人・外部システムとの境界を説明する図と定義の作り方を示す。

## 1. このレシピの使い方

- CXD は、利用者の課題と期待する成果（Why）を引き継ぎ、対象システムが引き受ける責務と境界外へ委ねる責務（What）を定め、人・外部システムとの関係と、関係が崩れたときの確かめ方（How）を示す。図の要素と定義表を要素名・関係 ID で対応付け、境界の判断から根拠と論点をたどれるようにする（Trace）。
- 「作成前に集める情報」をメモでそろえてから、「全体の作成手順」の順に書く。

## 2. 作成前に集める情報

| 項目         | 集める情報                                                       | 取り出し元                                 |
| ------------ | ---------------------------------------------------------------- | ------------------------------------------ |
| 利用目的     | 誰の何の課題を解き、どの成果を対象システムが支えるか             | 上位の概要・要求の文書                     |
| 対象範囲     | 一つのシステムとして引き受けることと、人・別システムへ委ねること | 製品の責任者への確認                       |
| 利用者       | 直接操作する人と、判断・確認だけに関わる人                       | 利用場面の聞き取り                         |
| 外部依存     | 外部へ依頼する情報・処理と、常に要るか特定の機能でだけ要るか     | 既存の連携仕様、実装の呼び出し箇所、設計者 |
| 未確定の論点 | 根拠が見つからない接続経路や保持範囲と、その影響                 | 確認の過程のメモ                           |

## 3. 全体の作成手順

1. 対象システムの責務と委譲先を最初に対にする。ここが決まらないと、図に置く人・外部システムを選べない。
2. 概要に、利用目的と本図の対象外を書く。
3. 直接の利用者と外部システムを選び、関係ごとに、誰が何のために何を渡すかを書き出す。
4. 書き出した関係を短いラベルにして図を描く。表を先に作ると、図と表の名前がずれにくい。
5. 技術前提・制約と検証観点では、境界が成り立つ条件を先に挙げ、各条件が崩れたときに確かめることを後から作る。
6. 最後に、残った論点をメモ / 将来課題へ移す。

## 4. 各章の書き方

### 4.1. 概要

問い:

- 誰がどの結果を得るためのシステムか。
- 関心を持つだけの人と、直接操作する人をどう分けるか。

コツ:

- 目的が「便利にする」で止まったら、誰が何を記録・確認するのかまで聞く。
- 上位の文書にある目的や背景は写さず、参照に置き換える。

### 4.2. C4コンテキスト図（Mermaid）

問い:

- 各矢印の向きを、利用・依頼・送信のどれとして説明できるか。
- 人・外部システムの候補がない場合、利用・運用の接点を見落としていないか。

コツ:

- 関係を書き出してから描くと、ラベルが「連携」のような目的のない語になりにくい。
- 呼び出しを確かめられない関係は、線を引く前に論点へ分ける。線があると既知の関係に見える。

### 4.3. 要素と境界の定義

#### 4.3.1. 対象システムとシステム境界

問い:

- 利用者が期待する結果のうち、対象システムが直接管理するものは何か。
- 引き受けない責務は、人と別システムのどちらへ委ねるか。

コツ:

- 実装モジュール名を伏せても責務を説明できるかを試す。説明できなければ内部の分割を書いている。

#### 4.3.2. Person（人・ロール）

問い:

- 各候補は、操作・運用・管理のどの接点で直接利用するか。
- その接点で何を入力し、どの結果を確認して次の判断へ進むか。

コツ:

- 役職の一覧から始めず、利用場面ごとに誰が画面・コマンドに触れるかを聞く。

#### 4.3.3. External Software System（外部システム）

問い:

- 外部へ依頼する処理と、その結果を対象システムが管理する範囲はどこで分かれるか。
- 未導入・障害・応答欠落のとき、影響を受ける結果は何か。

コツ:

- 「保持される」「再送される」と聞いたら、確かめた連携仕様や実装を聞く。根拠がなければ仮定として残す。

#### 4.3.4. Relationship（関係・連携契約）

問い:

- 各関係は、どの利用目的を支えるか。
- ローカル実行か外部通信かを、何で確かめたか。

コツ:

- 引数や電文を書き始めたら、目的と渡す情報の要点だけを残し、詳細は写さず参照に置き換える。

### 4.4. 技術前提・制約と検証観点

問い:

- ローカル実行・外部通信・人の承認のうち、どの条件が境界を成り立たせているか。
- 外部依存が失敗したとき、誰が何を見れば「結果不明」と「失敗確定」を分けられるか。

コツ:

- これから確かめる検証対象と、契約・実装で確認済みの保証を混ぜやすい。確認済みかどうかを条件ごとに聞く。

### 4.5. メモ / 将来課題

問い:

- 論点は、本文のどの境界・関係に影響するか。
- どの情報が得られれば解消するか。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 関係を 1 本選び、利用者が得たい結果へ逆向きにたどる。目的につながらない関係は、本図に要るかを見直す。
2. 外部システムごとに、対象システムのどの責務を支えるかを確かめ、対応のない要素を外す。
3. 検証観点の各行が、どの関係または境界に対応するかを確かめる。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                                       | 悪い例                                   |
| ------------ | ---------------------------------------------------------------------------- | ---------------------------------------- |
| 概要の目的   | 「店番担当が現金販売を記録する CLI と、商品・売上管理、印刷の境界を示す」    | 「販売を便利にする全体像」               |
| 関係のラベル | 「CLI → 印刷基盤: 印字依頼・結果取得」                                       | 「CLI → 印刷基盤: 連携」                 |
| 責務の分担   | 「CLI はレシート控えを保持し、印刷基盤が物理印字を担う」                     | 「両方で印刷を管理する」                 |
| 依存の粒度   | ローカル版管理とリモート共有の利用条件を分け、通信失敗の影響を共有に限る     | リモート障害で全操作が停止すると断定する |
| 検証観点     | 「印字が時間切れになったとき、会計結果と控えを確認する」                     | 「障害でも問題なく動く」                 |
| 論点         | 「売上応答欠落時の照合は契約未整備。受付照会の契約で期待結果を確かめて解消」 | 「後で検討する」                         |

## 7. レビュー観点

| 観点         | 確認内容                                                               |
| ------------ | ---------------------------------------------------------------------- |
| 価値と利用者 | 各利用関係が、概要の課題のどの結果に応えるかを説明できるか             |
| 境界と判断   | 対象システムが引き受ける範囲と、人が判断する範囲を読み手が合意できるか |
| 外部依存     | 依頼と結果の管理主体、未確定の条件が分かるか                           |
| 検証入力     | 不在・失敗・結果不明のときに確かめる情報を特定できるか                 |

## 8. 仕上げチェック

- 外部依存が使えないときに保持されると書いた情報に、確かめた根拠がある。
- 確認済みの保証と、これから確かめる検証対象を分けて書いている。
- 同じ端末で動く外部ツールを、対象システムの内部に置いていない。
