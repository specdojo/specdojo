# 外部コマンド連携仕様 作成レシピ

External Command Interface Specification Writing Recipe

外部 CLI とのプロセス境界を、呼び出し元が成功・失敗を判定し、次の動作を一つに決められる契約に仕上げるための作り方を示す。

## 1. このレシピの使い方

- この仕様は、`ifx-index`（外部システム I/F 一覧）の連携目的を引き継ぎ（Why）、呼び出し元が成功後に得る状態と入出力・終了状態の約束を定め（What）、識別信号・再試行・認証の渡し方を決める（How）。起動方法は正本の文書・設定キーへの参照で、仕様自体は `ifx-index` の `spec_ref` からたどれるようにする（Trace）。
- 「作成前に集める情報」をメモでそろえてから、「全体の作成手順」の順に書く。判断が止まった項目だけ「深掘り手順」で調べ直す。

## 2. 作成前に集める情報

| 項目           | 集める情報                                                                   | 取り出し元                                                                         |
| -------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 連携目的       | 呼び出し元と連携先、成功後に残る状態、別の契約に分ける操作                   | `ifx-index` の対象行、呼び出し元の担当者への確認                                   |
| 起動方法の正本 | 起動方法を決める文書・設定キー、対応バージョン、シェルを使う理由             | AI provider CLI は起動設定と exec 設定ガイド、ほかはコマンドリファレンス・公式資料 |
| 入出力         | stdin の内容と終端、stdout の採用範囲、stderr の用途、ファイルのパスと作成者 | 正本、実際の出力 1 回分、呼び出し元の実装担当への確認                              |
| 終了状態       | 公開された終了コード、同じコードの失敗を分ける追加信号とその定義元           | 正本、検出信号を定義する設定                                                       |
| 副作用と再実行 | 残る変更、利用枠の消費、途中失敗後に残る状態、重複を防ぐ手段                 | 正本、運用担当への確認                                                             |
| 認証           | 認証方式、渡し方、参照名、供給元、ログの保存先                               | 認証を管理する担当への確認（秘密値そのものは集めない）                             |
| 制約           | 作業ディレクトリ、時間・並列数・ネットワークの上限と、固定・設定依存・未決定 | 起動設定、呼び出し元の実装担当への確認                                             |

## 3. 全体の作成手順

1. 連携単位を最初に決め、`ifx-index` の目的と成功後の状態を 1 文で対応させる。目的・権限・出力が違う操作を混ぜたままだと、終了状態と副作用が一つに決まらない。
2. `command` で起動方法の正本を決める。実行ファイル・引数・provider をどこまで書くかは、正本が何を持つかで決まる。
3. `streams` と `files` で、成功を観測する信号と、後続処理が採用する出力を分ける。
4. `exit_codes` を書く。前の手順で決めた観測信号が、同じコードの失敗を分ける材料になる。
5. `side_effects` と冪等性を書く。途中失敗後に残る状態が分からないと、再試行してよいかを決められない。
6. `authentication` を書く。
7. `execution` と `error_handling` を最後に書く。終了状態と副作用が決まってから再試行の対象を選ぶと、回復の条件がない再試行を避けられる。

## 4. 各章の書き方

### 4.1. 連携単位とメタ情報

問い:

- 呼び出し元の何が終われば、この連携は成功か。
- 複数の操作や provider をまとめても、同じ成功条件で確かめられるか。

コツ:

- 「何が残れば成功か」を呼び出し元の担当者に聞くと、分けるべき操作が見つかる。
- 上位の背景説明を写したくなったら、`ifx-index` の対象行への参照に置き換える。

### 4.2. コマンドと正本参照

問い:

- 起動方法を、どの文書・設定キーから解決するか。
- provider が増えたとき、この仕様のどこを直す必要があるか。

コツ:

- `executable` の括弧やコメント、`purpose` の括弧に provider 名を並べたくなったら書かない。一覧は起動設定の鍵が持ち、`executable` には先頭要素から解決する旨だけを書く。provider を足すたびに複数箇所を直すなら、写しが残っている。
- 一覧を削るときに、認証の参照名まで消しやすい。参照名は認証の対象を識別するのに要るので残す。
- シェルを使うかは、宣言ではなく実際の起動設定を見て確かめる。

### 4.3. ストリーム

問い:

- プロセスの終了と業務の完了を、それぞれ何で判断するか。
- stdout のうち、後続処理が採用するのはどこか。

コツ:

- 構造化した報告が出るからといって、stdout 全体が構造化とは限らない。実際の出力を 1 回分見て、進捗が混ざるか確かめる。
- 報告の項目一覧は写さず、判断に使う意味だけを残す。

### 4.4. ファイル

問い:

- 各ファイルのパスは、何を基準に何から決まるか。
- 各ファイルを作るのは CLI か、呼び出し元か。

コツ:

- 呼び出し元が保存するログや報告を、CLI の出力に数えやすい。作成者を実装担当に聞いて分ける。

### 4.5. 終了状態と識別条件

問い:

- 同じ終了コードを返す失敗を、どの追加信号で分けるか。
- どの信号にも一致しないとき、呼び出し元はどう動くか。

コツ:

- 認証失敗などを個別に検出できない実装は多い。検出できない原因は断定せず、人が確かめる扱いにする。
- 検出パターンを写したくなったら、定義している設定への参照に置き換える。

### 4.6. 副作用と冪等性

問い:

- 途中で失敗したとき、外部状態・ファイル・利用枠に何が残るか。
- 再実行の前に、誰が何を確かめるか。

コツ:

- 「同じファイルに書くから再実行しても安全」と考えやすい。利用枠の追加消費と、非決定的な編集の差分を聞いて確かめる。

### 4.7. 認証注入

問い:

- 認証値は誰が用意し、どの経路でプロセスに渡るか。
- 引数・stdout・stderr・保存ログのどこで、誰がマスクするか。

コツ:

- 担当者には秘密値ではなく、仕組みと参照名だけを聞く。例にも実値や個人環境のパスを使わない。

### 4.8. 実行制約と失敗処置

問い:

- 時間・並列数の上限は固定か、設定依存か、未決定か。
- タイムアウトや出力の解析失敗の後、子プロセス・部分出力・既存の変更をどう扱うか。

コツ:

- 上限が決まっていないとき、検査を通すために値を作りやすい。現在の動作と決めるべき判断を分け、_UNDECIDED_ で残す。
- 利用制限は、短時間の制限か利用枠の枯渇かを聞き分ける。待ち方が変わる。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 各制約・処置が防ぐ失敗を挙げ、`ifx-index` の目的に結び付かないものを外す。
2. 各終了コードについて、入力・追加信号・次の動作を並べ、同じ観測結果に複数の動作が残る箇所を探す。
3. 再試行の対象ごとに、副作用から回復する条件があるかを確かめる。
4. 正本と同じ一覧・テンプレート・検出パターンを書いた箇所を、参照に戻す。

## 6. 良い例 / 悪い例

| 観点          | 良い例                                                                                  | 悪い例                                                                    |
| ------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 連携単位      | 発注登録の成功を受付番号の受領とし、在庫照会とは別の仕様 ID にする                      | 登録と照会をまとめ、何が終われば成功か分からない                          |
| provider 一覧 | `executable` は起動設定の先頭要素から解決すると書き、`purpose` は成功後の状態だけを書く | `executable` の括弧、`purpose` の括弧、コメントに同じ provider 名を並べる |
| ストリーム    | stdout は進捗を含むテキストとし、末尾の報告を取り出して完了を確かめる                   | 報告があるだけで stdout 全体を JSON とし、exit 0 だけで完了とする         |
| 終了状態      | 非ゼロ終了と設定済みの検出信号が一致したときだけ利用制限とし、ほかは汎用失敗で止める    | exit 1 をすべて一時失敗にし、識別できない認証失敗まで自動で再試行する     |
| 失敗処置      | 出力の解析に失敗したら再試行を止め、変更を保持し、確認する人を示す                      | 「失敗時はリトライする」とだけ書く                                        |

## 7. レビュー観点

| 観点       | 確認内容                                                                      |
| ---------- | ----------------------------------------------------------------------------- |
| 目的整合   | 成功後の状態が `ifx-index` の連携目的とつながっているか                       |
| 回復       | 途中失敗後の状態から再実行を追い、二重処理と利用枠の消費を避ける条件があるか  |
| 委譲の境界 | API・ファイル・メッセージの詳細や起動テンプレートを、正本と別に書いていないか |

## 8. 仕上げチェック

- 根拠のない固定値や、実際の起動方式・作成者と違う宣言が残っていない。
- 本文・コメント・例に、秘密値、秘密値入り URL、個人環境の認証パスがない。
- 未決定の項目は、現在の動作と次の確認先をたどれる形で残っている。
