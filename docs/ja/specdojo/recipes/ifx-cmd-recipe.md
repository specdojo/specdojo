# 外部コマンド連携仕様 作成レシピ

External Command Interface Specification Writing Recipe

外部 CLI とのプロセス境界を、呼び出し元と運用担当が同じ判定条件で実装・検証できる契約に仕上げるための作り方を示します。

## 1. このレシピの使い方

- 最初に、連携で実現する目的と、外部 CLI の安定した公開契約を分けて確認する。CLI の便利機能を先に列挙しない。
- 次に、実行可能ファイル、引数、入出力、終了コードを、成功と主要失敗を再現できる粒度で整理する。
- その後、認証注入、タイムアウト、冪等性、再試行を確認し、秘密値を含めずに運用可能な契約にする。
- 最後に、ESIL の連携目的（Why）、コマンド契約（What）、実行・失敗時の扱い（How）、`spec_ref` と終了カテゴリ（Trace）が一貫しているか確認する。

## 2. 作成前に集める情報

| 項目         | 集める情報                                                               |
| ------------ | ------------------------------------------------------------------------ |
| 連携の目的   | 誰がどのシステムに何を依頼し、成功後にどの状態にするか                   |
| ESIL 項目    | 連携名、source、target、direction、timing、`spec_ref`                    |
| CLI 公開契約 | 実行ファイル名、サブコマンド、対応バージョン、引数、構造化出力           |
| ストリーム   | stdin の必須性、stdout のデータ形式、stderr の用途、文字コード           |
| 終了状態     | 成功、入力不正、認証・認可失敗、制限、一時失敗、恒久失敗の識別方法       |
| 認証・権限   | 認証方式、プロセスへの注入方式、必要権限、シークレット管理境界           |
| 実行制約     | タイムアウト、並列数、ネットワーク要否、実行ディレクトリ、副作用と冪等性 |
| 運用時の判定 | 再試行できる条件、打ち切り条件、再認証が必要な条件、ログから除外する値   |

## 3. 全体の作成手順

1. ESIL の 1 連携に対応する実行目的を 1 文で書き、別の入出力契約を持つサブコマンドが混じっていないか確認する。
2. ID、タイトル、状態、準拠ルール、仕様バージョンを設定し、ESIL の `spec_ref` と対応させる。
3. 実行可能ファイルとサブコマンドを分離し、利用できる CLI バージョン範囲を固定する。
4. 引数を option と positional に分け、必須性、値の型、供給元、公開可能な例を記載する。
5. stdin、stdout、stderr の契約を別々に書き、呼び出し元が解析する stdout の安定フィールドを固定する。
6. 公開された終了コードを共通カテゴリへ写像し、同じ入力で再試行できるか判定する。
7. 認証方式と注入機構を定義し、秘密値が引数、入出力例、ログに現れないことを確認する。
8. タイムアウト、並列度、冪等性、再試行、出力解析失敗、認証失敗の処置を定義する。
9. 最小の成功ケース、入力不正、認証失敗、タイムアウトを想定し、実行側の分岐が一意になるかレビューする。

## 4. 各要素の書き方

### 4.1. 実行目的とコマンド

問い:

- このコマンドの成功によって、連携先または呼び出し元の何が変わるか。
- 実行可能ファイル名とサブコマンドは、対応バージョンで安定しているか。
- 1 回の起動に異なる目的、権限、出力契約が混在していないか。

書き方:

- `purpose` はツールの説明ではなく、呼び出し側から見た成果を記載する。
- 実行可能ファイル、サブコマンド、引数を別要素にし、シェル構文を含む 1 本の文字列にしない。
- バージョン範囲は、出力契約と終了コードを確認した範囲だけにする。

### 4.2. 引数とストリーム

問い:

- 各引数は誰が生成し、必須性と型をどのように検証できるか。
- stdin を使う理由と、終端なしで入力が完結する条件は何か。
- stdout のどのフィールドを正本とし、stderr のどの情報を診断に使うか。

書き方:

- 引数の例は公開可能なダミー値にし、認証情報と個人環境の絶対パスは使わない。
- 機械処理する stdout は JSON／JSONL など安定形式を選び、必要なフィールドの意味を書く。
- stdout と stderr は別々に記録し、進捗文言を成功値として解析しない。

### 4.3. 終了コードとエラー処理

問い:

- 成功、利用者が修正すべき失敗、運用者が解消すべき失敗、自動再試行できる失敗を区別できるか。
- 同じ終了コードが複数の意味に使われる場合、追加の判定信号はあるか。
- 副作用のある実行を再試行しても、結果が重複しない条件は何か。

書き方:

- CLI 固有の終了コードを共通カテゴリに写像し、リトライ可否を同じ行に置く。
- 汎用的な exit 1 のみで制限や一時失敗と判定せず、専用コードや構造化エラーがある場合だけ自動分類する。
- タイムアウト、出力解析失敗、認証失敗は別の処置とし、一律の再試行にしない。

### 4.4. 認証注入と実行制約

問い:

- 認証状態はどの管理境界から、どの機構でプロセスへ渡されるか。
- 呼び出しに必要な最小権限と、認証失敗時の再開条件は何か。
- ネットワーク、実行ディレクトリ、タイムアウト、並列数の制約は何か。

書き方:

- 環境変数名、CLI プロファイル名、workload identity の識別名など、注入の参照だけを書く。
- 秘密値の実値、シークレットファイルの実パス、トークン付き URL は残さない。
- ログのマスク方針とプロセス強制終了後の不完全出力の扱いまで決める。

## 5. 深掘り手順

1. ESIL の対象行から、連携の目的、方向、タイミング、失敗時の影響を抽出する。
2. CLI のヘルプまたは公式の機械可読仕様から、引数、出力形式、終了コードを抜き出す。
3. 成功、入力不正、認証失敗、レート制限、接続失敗、不正出力の各ケースで観測可能な信号を並べる。
4. 自動再試行候補ごとに、冪等性、重複防止キー、試行上限、打ち切り後の操作を確認する。
5. 引数、stdin、stdout、stderr、エラー文言に秘密値が出る可能性を列挙し、それぞれのマスク条件を決める。
6. 呼び出し側が「成功」「再試行」「人の対応待ち」「入力修正」を仕様だけで分岐できるか確認する。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                      | 悪い例                                             |
| ------------ | ----------------------------------------------------------- | -------------------------------------------------- |
| コマンド分離 | `executable: supplier-cli`、`subcommands: [orders, submit]` | `command: "supplier-cli orders submit $FILE"`      |
| 引数の供給元 | `value_source: generated` とし、生成元の意味を説明する      | 値が固定、設定、利用者入力のどれか不明             |
| stdout       | `format: json` と安定フィールドを定義する                   | 人向けの「成功しました」を文字列一致で判定する     |
| stderr       | 診断用とし、成否は終了コードと構造化出力で判定する          | stderr が空なら成功とみなす                        |
| 終了カテゴリ | 専用コードと意味を `transient_failure` へ写像する           | すべての exit 1 を `rate_limit` と扱う             |
| 認証注入     | 環境変数名とシークレットストアの境界だけを記載する          | トークン実値または認証ファイルの個人パスを記載する |
| 再試行       | 冪等性キーがある一時失敗だけを上限付きで再試行する          | 副作用の有無を確認せず非 0 をすべて再試行する      |
| タイムアウト | 子プロセスを終了し、不完全出力を破棄して失敗とする          | 親プロセスだけが待機を止め、子プロセスを残す       |

## 7. レビュー観点

| 観点             | 確認内容                                                                           |
| ---------------- | ---------------------------------------------------------------------------------- |
| 目的と境界       | ESIL の 1 連携と対応し、API／ファイル／メッセージ仕様の責務を重複定義していないか  |
| 実行可能性       | 実行ファイル、サブコマンド、引数、対応バージョンが一意で、シェルに依存しないか     |
| 入出力契約       | stdin／stdout／stderr の形式と用途が分離され、機械処理する出力が安定しているか     |
| 失敗の識別       | 終了コードと追加信号から、入力修正、再認証、再試行、恒久失敗を分けられるか         |
| 認証と秘密保護   | 注入機構と必要権限が明確で、秘密値、個人パス、トークン付き URL が含まれていないか  |
| 回復可能性       | タイムアウト、再試行、打ち切り、不完全出力の扱いが定義され、副作用の重複を防げるか |
| トレーサビリティ | 仕様 ID、ESIL の `spec_ref`、終了カテゴリ、根拠文書を安定した識別子でたどれるか    |

## 8. 仕上げチェック

- 仕様 ID と ESIL の `spec_ref` が対応し、`kind: コマンド` の連携を 1 件だけ扱っている。
- 実行可能ファイル、サブコマンド、引数が分離され、シェル構文や秘密値を含む引数がない。
- stdin、stdout、stderr の使用有無、形式、文字コード、意味が判定可能な記述になっている。
- 成功と主要失敗の終了コードが共通カテゴリへ写像され、自動再試行の可否と一致している。
- 認証方式、注入機構、参照名、シークレット管理境界、ログのマスク方針が揃っている。
- タイムアウト、並列数、ネットワーク要否、冪等性、再試行条件、出力解析失敗時の処置を呼び出し側が実装できる。
- 認証情報、個人環境のパス、内部クラス名、プロセス起動ライブラリの実装詳細が残っていない。
