# 外部コマンド連携仕様 作成レシピ

External Command Interface Specification Writing Recipe

外部 CLI とのプロセス境界を、実装の二重記述を避けて正本を参照し、入出力の約束（渡すもの・受け取るもの・終了コードの意味・作るファイル・副作用・失敗の扱い）に絞って合意・検証できる契約に仕上げるための作り方を示します。

## 1. このレシピの使い方

- ESIL（外部システム I/F 一覧）の連携目的を出発点に、呼び出し元が成功後に得る状態を決める。共通の背景は上位から引き継ぎ、この仕様ではプロセス境界の契約を具体化する。
- 「作成前に集める情報」を短いメモにし、「全体の作成手順」の順で正本、入出力、終了判定、回復条件を決める。判断が止まった項目だけ「深掘り手順」で調べ直す。
- 起動方法や設定値は設定・リファレンスへ、値・構文・構造の詳細は `docs/specdojo/schemas/v1/ifx-cmd.schema.yaml` へ委ねる。ここでは呼び出し元が判断するための意味と参照先の選び方を扱う。
- 最後に ESIL の `spec_ref`、成功後の状態、観測信号、次の動作をたどる。実装が識別できない失敗や保証できない回復は、できることとして書かず、制約と確認先を残す。

## 2. 作成前に集める情報

| 項目           | 集める入力                                                                     | 判断に使う問い                                                             |
| -------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 連携目的と範囲 | ESIL の対象行、呼び出し元・連携先、方向、タイミング、`spec_ref`                | 成功後に何が残れば目的を満たすか。別契約として分ける操作はあるか           |
| 正本と適用範囲 | 対象操作のリファレンス、起動設定のキー、対応バージョン、共通事項を持つ上位文書 | どの参照先が何を決めるか。複数 provider の差異もそこで解決できるか         |
| 起動方式       | 実行ファイルの解決方法、サブコマンド、シェル利用の根拠、設定の管理境界         | 実際の起動方式は何か。シェルを使うなら展開値の検証先はどこか               |
| ストリーム     | stdin の要否と終端、stdout の受領範囲、stderr の用途、形式・文字コード         | プロセス終了と業務完了を何で判定するか。進捗と構造化報告は混在するか       |
| ファイル       | 入出力のパス解決規則、内容の正本、作成・更新主体                               | CLI が変更する成果物と呼び出し元が保存する記録を分けられるか               |
| 終了状態       | 公開された終了コード、追加の検出信号と定義元、判定順、未分類時の扱い           | 同じコードの失敗を区別できるか。識別できない原因は何か                     |
| 副作用と再実行 | 永続的変更、利用枠消費、重複排除の根拠、失敗後に残る状態                       | 再実行してよい条件は何か。保証がなければ何を確認して再開するか             |
| 認証と権限     | 認証方式、注入機構と参照名、必要権限、供給元、ログ保存境界                     | 誰が認証状態を管理し、どの段階で何をマスクするか。秘密値自体は収集しない   |
| 制約と回復     | 作業ディレクトリ、時間・並列数・ネットワークの制約、再試行方針                 | 上限は固定か設定依存か未決定か。子プロセス・部分出力・既存変更をどう扱うか |

## 3. 全体の作成手順

1. **連携単位とメタ情報**: ESIL の目的と成功後の状態を 1 文で対応させ、仕様 ID を `spec_ref` からたどれるようにする。目的・権限・出力契約が異なる操作は分け、複数 provider をまとめるなら共通契約の範囲を決める。
2. **`command`**: 対象操作の正本を選び、`reference` に文書・設定キー・適用範囲を示す。その根拠から実行ファイルの解決方法、起動方式、対応バージョンを記す。provider 一覧や引数表を別に作らない。
3. **`streams` と `files`**: 渡す内容、受け取る範囲、ファイルの解決規則と作成主体を整理する。成功を観測する信号と、後続処理が採用する内容を区別できたら次へ進む。
4. **`exit_codes`**: 正常・代表的失敗について、コードと追加信号からカテゴリへの判定順を組み立てる。区別できない原因には汎用失敗としての扱いを残す。
5. **`side_effects` と `execution.idempotency`**: 成功時と途中失敗時に残る変更・利用枠消費を確認し、重複排除の条件または保証できない理由と再開条件を記す。副作用の記述先は一つにまとめる。
6. **`authentication`**: 認証方式と渡し方、供給元、ログのマスク境界を整理する。参照名だけで利用対象を特定でき、秘密値を含まないことを確認する。
7. **`execution` と `error_handling`**: 制約の根拠を特定し、再試行の条件・上限・待機方式と、タイムアウト・出力解析失敗・認証失敗の処置を決める。未決定の制約は現在動作と必要な判断を分けて残す。
8. **分岐の照合**: 成功、同じコードの異なる失敗、出力欠落、途中失敗後の再実行を順に追う。各ケースの次の動作が一つに決まり、未確定項目の確認先を引き継げる状態で仕上げる。

## 4. 各章の書き方

YAML の各要素を、以下の判断単位として組み立てる。キーの必須性や型の一覧を作り直さず、呼び出し元が必要とする説明を該当要素へ置く。

### 4.1. 連携単位とメタ情報

問い:

- ESIL のどの連携目的を受け、呼び出し元の何を完了させるか。
- 複数の操作や provider をまとめても、同じ成功条件で検証できるか。
- 契約の改版と CLI の対応バージョンを混同していないか。

書き方:

- タイトルと実行目的を、対象と成功後の状態から書く。上位の背景説明を複製する代わりに、ESIL の対象行と仕様 ID の対応を確認する。
- `based_on` は確認した直接の根拠から選び、カタログ管理下では依存関係の範囲内か調べる。起動方法の参照は `command.reference` に置き、根拠一覧へ機械的に転記しない。

### 4.2. コマンドと正本参照

問い:

- 起動方法と実行ファイルをどの文書・設定キーから解決するか。
- provider が増えたとき、目的・実行ファイル・コメントの列挙を直さずに済むか。
- 実際にシェルを使うか。使う理由、設定の管理者、展開値の検証・制限をどこで確認できるか。

書き方:

- SpecDojo 自身のコマンドはコマンドリファレンス、AI provider CLI は起動設定と [[specdojo:exec-config-guide|exec 設定ガイド]]、その他の外部 CLI は対象操作の公式資料から正本を選ぶ。
- `purpose` は成功後の状態に絞る。可変の実行ファイルは、たとえば `providers.<provider>.command_template` の先頭要素から解決する旨を `executable` に書き、provider 一覧は設定の鍵へ委ねる。認証対象の参照名など、別の判断に必要な情報まで削らない。
- 通常の起動では実行ファイルとサブコマンドを分ける。管理された設定がシェルを必要とする場合は、理由と管理・検証の参照先を示して実態に合わせる。起動テンプレート全文や展開処理は転載しない。

### 4.3. ストリーム

問い:

- stdin は何を渡し、どこで入力終了となるか。使わない場合はどう表すか。
- stdout 全体が構造化データか、それとも進捗と報告が混在するか。
- stderr は何に使い、完了判定に使う信号とはどう区別するか。

書き方:

- 形式を実際のストリーム全体に合わせ、構造化部分だけを採用するなら抽出範囲と役割を書く。報告の詳細構造は正本を参照し、呼び出し元の判断に必要な意味を残す。
- 終了コードが保証する範囲と、報告内容で確かめる完了条件を分ける。欠落・解析失敗時は「実行制約と失敗処置」につなげる。

### 4.4. ファイル

問い:

- 入力・出力のパスはどのディレクトリを基準に、何から解決するか。
- 各ファイルを作成・更新するのは CLI か、呼び出し元か、別段階の担当か。
- 内容の詳細構造を持つ schema・仕様はどこか。

書き方:

- `files.inputs` / `files.outputs` では、形式・文字コード・用途と可変パスの解決規則を組み合わせ、利用者が対象を特定できるようにする。
- CLI が編集する成果物と、呼び出し元が保存するログ・報告を分けて説明する。後者を CLI 自身の生成物として数えず、内容のフィールド一覧は正本へ委ねる。

### 4.5. 終了状態と識別条件

問い:

- 同じ終了コードを返す失敗は、どの追加信号で区別するか。
- 複数の信号が一致したときの判定順と、どれにも一致しないときの動作は何か。
- 認証失敗などを個別検出できない場合、誰が何を確認するか。

書き方:

- コードと信号を組み合わせて `meaning` を書き、カテゴリと `retryable` を対応させる。利用制限や接続失敗の検出条件は定義元を参照し、パターン一覧を複製しない。
- 判断材料がない原因は断定しない。自動分類の範囲と手動確認の範囲を分け、exit 0 でも成果物の検証や業務完了には別条件があるか確かめる。

### 4.6. 副作用と冪等性

問い:

- 成功時と途中失敗時に、外部状態・ローカルファイル・利用枠へ何が残るか。
- 同一入力の再実行で重複処理を防ぐ根拠はあるか。
- 保証できない処理を再開する前に、誰がどの状態を確認するか。

書き方:

- `side_effects` には変更範囲、利用枠消費、変更してはならない境界をまとめる。別の配置を使う場合も同じ説明を二重に持たない。
- `execution.idempotency` は保証の有無を先に判断し、保証するなら重複排除条件、しないなら理由と既存変更を引き継ぐ条件を書く。同名ファイルへの書き込みだけを保証の根拠にしない。

### 4.7. 認証注入

問い:

- 認証の種類とプロセスへの渡し方はそれぞれ何か。既存ログイン状態を使うか。
- 参照名から対象の環境変数・プロファイルを特定できるか。認証不要ならその判断根拠は何か。
- 認証値の供給元と、引数・環境変数・stdout・stderr・保存ログの秘匿処理を誰が管理するか。

書き方:

- `method` と `injection` を実際の認証経路に合わせる。`names` は利用対象を識別するために残し、実行目的などへ同じ対象一覧を複製しない。
- `secret_source` に管理境界、`log_policy` にマスク対象と実施時点を書く。機構の参照名だけで説明し、秘密値や個人環境の認証パスは例にも使わない。

### 4.8. 実行制約と失敗処置

問い:

- 作業ディレクトリ、時間、並列実行、ネットワークの制約を何から決めるか。
- 再試行する失敗、回数の数え方、待機・切替・停止の条件は何か。
- タイムアウト、出力解析失敗、認証失敗の後に、子プロセス・部分出力・既存変更をどう扱うか。

書き方:

- 確認した設定や公開契約から制約を記す。設定依存の値を固定値へ置き換えず、schema で表現できない場合は許容されるプレースホルダと共通ラベルで draft に残し、現在動作・必要な判断・次の確認先を記録する。
- `retryable` と `retry.on_categories` を突き合わせ、副作用の回復条件を満たす場合だけ再試行につなげる。利用制限では短時間の制限と利用枠枯渇を区別し、細かな待機・切替方針は正本へ委ねる。
- 三つの失敗処置は、停止する対象、保持・破棄するもの、次の確認者または再開条件から書く。上限や処置が未決定なら、現在の待機動作と決めるべき方針を混同しない。

## 5. 深掘り手順

1. **目的に戻る**: 説明できない制約や処置を一つ選び、それが防ぐ失敗と ESIL の目的への影響を確認する。目的につながらない内部処理の説明は削るか委譲する。
2. **正本をたどる**: 主張の根拠となる文書・設定キー・適用範囲を確認する。provider の追加や設定変更で複数箇所の修正が要るなら、一覧を正本へ戻し、実行ファイルの解決規則と認証の参照名など独立した判断情報は残す。
3. **分岐を再現する**: 曖昧なケースについて、入力、コード、追加信号、採用する出力、次の動作を短く並べる。同じ観測結果に複数の動作が残るなら、判定順を補うか自動分類の限界を書く。
4. **途中状態から追う**: 出力欠落や途中失敗を起点に、子プロセス、ファイル、外部状態、利用枠を確認する。再開に必要な確認・重複防止が説明できるまで、自動再試行の範囲を広げない。
5. **未確定を切り分ける**: 調査不足は _TODO_:、意思決定待ちは _UNDECIDED_:、仮の前提は _ASSUMPTION_: で分ける。現在動作、根拠、不足する判断、確認先を実行記録へ残し、架空の値で埋めない。

## 6. 良い例 / 悪い例

| 判断単位           | 良い例                                                                                                       | 悪い例                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| 連携単位とメタ情報 | 発注登録の成功を受付番号の受領とし、在庫照会とは別の仕様 ID へ対応させる                                     | 登録と照会を一つにまとめ、何が終われば成功か区別できない                                |
| コマンドと正本     | `executable` は起動設定の先頭要素から解決し、provider 一覧は設定の鍵へ委ねる。`purpose` は成功後の状態を書く | 実行ファイル、目的、コメントに同じ provider 一覧を転載する                              |
| シェル利用         | stdin を起動引数へ変換するためのシェル利用と、管理された設定・展開値の検証先を示す                           | 実際はシェル起動なのに `shell: false` とする、または外部 CLI という理由だけで有効にする |
| ストリーム         | stdout は進捗を含むテキストとし、末尾の構造化報告を抽出して完了状態を確認する                                | 構造化報告があるだけで stdout 全体を JSON とみなし、exit 0 だけで業務完了とする         |
| ファイル           | CLI の編集対象は作業ディレクトリから解決し、runner が保存するログとは作成主体を分ける                        | 呼び出し元が保存するログも CLI が作るファイルへ含める                                   |
| 終了状態           | 非ゼロ終了と設定済み検出信号が一致した場合だけ利用制限とし、未一致は汎用失敗として停止する                   | exit 1 をすべて `transient_failure` にし、識別できない認証失敗まで自動再試行する        |
| 副作用と冪等性     | 非決定的な編集は冪等性を保証せず、差分を保持して確認後に再開する条件を書く                                   | 同じファイルへ書くので再実行も安全だと判断し、利用枠の追加消費を無視する                |
| 認証注入           | ログインプロファイルの参照名と管理境界を残し、保存前のマスク対象を示す                                       | 一覧の重複を削る際に認証対象まで不明にする、または秘密値・個人パスを例示する            |
| 実行制約と回復     | 時間上限が未決定なら現在は終了まで待つ事実と必要な判断を分け、出力異常後の変更保持と確認者を示す             | 検査を通すためだけに固定上限を作り、失敗処置を「リトライする」で済ませる                |

## 7. レビュー観点

| 観点                 | 確認方法                                                                                                   |
| -------------------- | ---------------------------------------------------------------------------------------------------------- |
| 目的と委譲境界       | 成功後の状態を ESIL の目的へたどり、API・ファイル・メッセージの詳細契約を重複して定義していないか確認する  |
| 正本への追跡         | 対象操作と設定キーから起動方法を解決し、provider 追加時に仕様内の一覧を複数更新する必要がないか試す        |
| 受領と生成の境界     | stdin から採用出力までを追い、進捗と報告、プロセス終了と業務完了、CLI の変更と呼び出し元の記録を区別する   |
| 分岐の実現性         | 同じコードの失敗を追加信号と判定順で追い、検出できない原因が手動確認へ進むか確かめる                       |
| 回復の成立条件       | 途中失敗後の状態から再実行を追い、重複処理と利用枠消費を考慮した条件が再試行方針に反映されているか確かめる |
| 認証の管理境界       | 参照名から供給元とマスク実施点を追い、秘密値を収集・転載せずに認証経路を説明できるか確認する               |
| 未確定事項の引き継ぎ | 固定値・設定依存・未決定を区別し、未決定項目から現在動作と次の確認先をたどれるか確認する                   |

## 8. 仕上げチェック

- 「全体の作成手順」の分岐照合で曖昧さが解消されている。判断できない項目は現在動作・必要な判断・確認先を記録し、確定済みの記述へ混ぜていない。
- 「作成前に集める情報」の入力と完成した契約を照合し、根拠のない固定値や、実際の起動方式・生成主体と異なる宣言が残っていない。
- 本文・コメント・例を通して同じ一覧や説明を探し、判断を失わず正本参照へ置き換えられる重複を除いている。認証の参照名など独立した判断情報は残している。
- 公開する本文・例・実行記録に秘密値、秘密値入り URL、個人環境の認証パスがなく、内部実装の説明は契約の参照に置き換わっている。
