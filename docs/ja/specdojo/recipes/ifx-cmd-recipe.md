# 外部コマンド連携仕様 作成レシピ

External Command Interface Specification Writing Recipe

外部 CLI とのプロセス境界を、実装の二重記述を避けて正本を参照し、入出力の約束（渡すもの・受け取るもの・終了コードの意味・作るファイル・副作用・失敗の扱い）に絞って合意・検証できる契約に仕上げるための作り方を示します。

## 1. このレシピの使い方

- 最初に、連携で実現する目的と、引数・オプションの仕様を定める「正本」（コマンドリファレンス、exec 起動設定、公式ドキュメント等）を特定する。引数・オプションの表を手作業で再掲しない。
- 次に、渡すもの（stdin、入力ファイル）、受け取るもの（stdout、stderr）、作るファイル（outputs）、副作用、終了コードを整理する。
- その後、認証注入、タイムアウト、冪等性、失敗の扱い（タイムアウト時処置、出力解析失敗時処置、認証失敗時処置、再試行）を確認し、秘密値を含めずに運用可能な契約にする。
- 最後に、ESIL の連携目的（Why）、正本参照とコマンド契約（What）、入出力・副作用・エラーハンドリング（How）、`spec_ref` と終了カテゴリ（Trace）が一貫しているか確認する。

## 2. 作成前に集める情報

| 項目               | 集める情報                                                                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| 連携の目的         | 誰がどのシステムに何を依頼し、成功後にどの状態にするか                                                                             |
| ESIL 項目          | 連携名、source、target、direction、timing、`spec_ref`                                                                              |
| 正本情報源         | コマンドリファレンス、`.specdojo/exec-defaults.yaml` の `command_template` と [[specdojo:exec-config-guide]]、外部公式ドキュメント |
| コマンド基本       | 実行ファイル名、サブコマンド、対応バージョン制約、シェル経由の有無（原則 false）                                                   |
| 入出力契約         | stdin の要否、stdout のデータ形式・主要フィールド、stderr の用途、文字コード                                                       |
| ファイル契約       | 渡す入力ファイル（inputs）、コマンドが作る出力ファイル（outputs）のパス・形式・役割                                                |
| 終了状態           | 成功、入力不正、認証・認可失敗、レート制限、一時失敗、恒久失敗の識別方法                                                           |
| 副作用と冪等性     | 外部サービスや環境への永続的影響、同一入力で再実行したときの結果保証条件                                                           |
| 認証・権限         | 認証方式、プロセスへの注入方式、必要権限、シークレット管理境界、マスク方針                                                         |
| 実行制約・失敗処置 | タイムアウト、並列数、ネットワーク要否、タイムアウト時処置、出力解析失敗時処置、認証失敗時処置、再試行ポリシー                     |

## 3. 全体の作成手順

1. ESIL の 1 連携に対応する実行目的を 1 文で書き、別の入出力契約を持つサブコマンドが混じっていないか確認する。
2. ID、タイトル、状態、準拠ルール、仕様バージョンを設定し、ESIL の `spec_ref` と対応させる。
3. 実行可能ファイルとサブコマンドを分離し、利用できる CLI バージョン範囲を固定する。
4. 引数・オプションの定義を持つ正本（コマンドリファレンス、exec 設定、外部ドキュメント）を特定し、`command.reference` に参照先を記載する（引数・オプションの表は作成しない）。
5. 渡すもの（stdin、入力ファイル）と受け取るもの（stdout、stderr）、作るファイル（出力ファイル）の形式・文字コード・データ契約を記載する。
6. 公開された終了コードを共通カテゴリ（`success`, `input_error`, `authentication_error`, `authorization_error`, `rate_limit`, `transient_failure`, `permanent_failure`）へ写像し、自動再試行の可否（`retryable`）を判定する。
7. コマンド実行に伴う副作用（外部状態の変化）と冪等性保証条件を定義する。
8. 認証方式と注入機構を定義し、秘密値が引数、入出力例、ログに現れないことを確認する。
9. タイムアウト、並列度、再試行条件、出力解析失敗・認証失敗時の処置を定義する。
10. 最小の成功ケース、入力不正、認証失敗、タイムアウトを想定し、呼び出し側の分岐が一意になるかレビューする。

## 4. 各要素の書き方

### 4.1. 実行目的と正本参照

問い:

- このコマンドの成功によって、連携先または呼び出し元の何が変わるか。
- 引数やオプションの完全な仕様はどの正本に書かれているか。
- 1 回の起動に異なる目的、権限、出力契約が混在していないか。

書き方:

- `purpose` はツールの説明ではなく、呼び出し側から見た成果・成功後の状態を記載する。
- `reference` には、SpecDojo 自身のコマンドならコマンドリファレンス、AI provider CLI 等なら起動設定とガイド、外部 CLI なら公式ドキュメントへの参照を記載する。
- 実行可能ファイルとサブコマンドを別要素にし、シェル構文を含む 1 本の文字列にしない。

### 4.2. 入出力の約束（渡すもの・受け取るもの・作るファイル）

問い:

- コマンドに渡すデータ（stdin、入力ファイル）と、受け取るデータ（stdout、出力ファイル）は何か。
- stdout のどのフィールドを正本とし、stderr のどの情報を診断に使うか。
- コマンド実行に伴って作られるファイル（受領書、生成物）のパスと形式は明確か。

書き方:

- 機械処理する stdout は JSON／JSONL など安定形式を選び、解析対象の主要フィールドの意味を書く。
- 出力ファイルや入力ファイルがある場合は `files.inputs` / `files.outputs` にパス、形式、文字コード、役割を明記する。
- stdout と stderr は別々に記録し、人向けの進捗文言を成否の判定根拠にしない。

### 4.3. 終了コードとエラー処理

問い:

- 成功、利用者が修正すべき失敗、運用者が解消すべき失敗、一時障害、レート制限を区別できるか。
- 同じ終了コードが複数の意味に使われる場合、追加の判定信号はあるか。
- タイムアウトや出力異常が起きたとき、後続プロセスをどのように安全に停止・回復させるか。

書き方:

- CLI 固有の終了コードを共通カテゴリに写像し、リトライ可否を同じ行に置く。
- 汎用的な exit 1 のみでレート制限や一時失敗と判定せず、専用コードや構造化エラーがある場合だけ自動分類する。
- タイムアウト処置（`timeout_action`）、出力解析失敗処置（`malformed_output_action`）、認証失敗処置（`authentication_failure_action`）を具体的に記載する。

### 4.4. 副作用と認証注入

問い:

- コマンド実行によって外部サービスやローカル環境の何が永続化・更新されるか。
- 再試行したときに二重処理やデータ破損が起きない保証条件（冪等性）は何か。
- 認証状態はどの管理境界から、どの機構でプロセスへ渡されるか。

書き方:

- `side_effects` に外部リソースの登録・変更・削除を具体的に記述する。
- `execution.idempotency` にリクエスト ID や一意キーによる重複排除条件を明記する。
- 環境変数名や CLI プロファイル名など、注入機構の参照名だけを書き、秘密値の実値は一切含めない。

## 5. 深掘り手順

1. ESIL の対象行から、連携の目的、方向、タイミング、失敗時の影響を抽出する。
2. コマンドリファレンスや起動設定、公式ドキュメントから、正本となる参照先を確定する。
3. 成功、入力不正、認証失敗、レート制限、接続失敗、不正出力の各ケースで観測可能な終了コードと信号を並べる。
4. 渡すもの（入力データ・ファイル）と受け取るもの（出力データ・作るファイル）の入出力境界を特定する。
5. 外部状態への副作用を洗い出し、再試行時の冪等性保証条件を確認する。
6. タイムアウト、出力解析失敗、認証失敗に対する個別のアクションを定義する。
7. 呼び出し側が「成功」「再試行」「人の対応待ち」「入力修正」を仕様だけで分岐できるか確認する。

## 6. 良い例 / 悪い例

| 観点           | 良い例                                                                         | 悪い例                                                                              |
| -------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| 引数と正本     | `reference` で公式リファレンスや設定・ガイドを参照し、引数の二重管理を排除する | 仕様書内に `--file` や `--timeout` などの引数表を詳細に再掲し、実装と二重管理にする |
| コマンド分離   | `executable: supplier-cli`、`subcommands: [orders, submit]`                    | `command: "supplier-cli orders submit $FILE"`                                       |
| 入出力の約束   | stdout の JSON 構造と作るファイル（outputs）のパス・形式を明記する             | 出力を「CLI の標準出力」とだけ書き、受け取るフィールドや生成ファイルが不明          |
| 終了カテゴリ   | 専用コードと意味を `rate_limit` や `transient_failure` へ適切に写像する        | すべての exit 1 を一時失敗とみなして無制限に再試行する                              |
| 副作用と冪等性 | 副作用と、同一リクエスト ID による重複防止条件を明記する                       | 副作用の有無を確認せず、再実行でデータが二重登録される                              |
| 認証注入       | 環境変数名とシークレットストアの境界だけを記載する                             | トークン実値または認証ファイルの個人パスを記載する                                  |
| 失敗の扱い     | タイムアウト処置や出力解析失敗処置を個別具体的に記載する                       | 失敗時の処置を「エラーとする」とだけ書き、プロセスの終了やクリーンアップが不明      |

## 7. レビュー観点

| 観点             | 確認内容                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------- |
| 目的と境界       | ESIL の 1 連携と対応し、API／ファイル／メッセージ仕様の責務を重複定義していないか                             |
| 実装重複排除     | 引数・オプションの表を持たず、正本（コマンドリファレンス、exec 設定、外部ドキュメント）を正しく参照しているか |
| 入出力契約       | 渡すもの、受け取るもの、作るファイル（outputs）の形式と用途が明確か                                           |
| 失敗の識別       | 終了コードとカテゴリから、入力修正、再認証、再試行、恒久失敗を機械的に分岐できるか                            |
| 副作用と回復性   | 副作用の内容と冪等性条件が明記され、タイムアウトや出力異常時の処置が定義されているか                          |
| 認証と秘密保護   | 注入機構と参照名が明確で、秘密値、個人パス、トークン付き URL が含まれていないか                               |
| トレーサビリティ | 仕様 ID、ESIL の `spec_ref`、正本参照先、根拠文書を安定した識別子でたどれるか                                 |

## 8. 仕上げチェック

- 仕様 ID と ESIL の `spec_ref` が対応し、`kind: コマンド` の連携を 1 件だけ扱っている。
- 引数・オプションの表を持たず、`command.reference` に正本への参照が記載されている。
- 実行可能ファイル、サブコマンド、シェル経由有無（`false`）が分離され、シェル構文を含まない。
- stdin、stdout、stderr の使用有無、形式、文字コード、主要フィールドが判定可能になっている。
- 作るファイルや渡すファイルがある場合、`files` にパス、形式、内容の説明が記載されている。
- 成功と代表的失敗の終了コードが共通カテゴリへ写像され、自動再試行の可否と一致している。
- コマンドの副作用と冪等性保証条件が具体的に記載されている。
- 認証方式、注入機構、参照名、シークレット管理境界、ログのマスク方針が揃っている。
- タイムアウト、出力解析失敗、認証失敗の各処置が個別に定義されている。
- 認証情報、個人環境のパス、内部クラス名、プロセス起動ライブラリの実装詳細が残っていない。
