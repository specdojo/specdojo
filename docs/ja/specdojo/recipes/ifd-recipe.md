# インフラ構成図 作成レシピ

Infrastructure Flow Diagram Writing Recipe

上位の責務を実行場所と通信境界へ変換し、境界設計と障害切り分けに使える構成図を作る。配置を描くだけで終わらず、外部へ渡る情報と依存が使えない場合の影響を具体化する。

## 1. このレシピの使い方

- 上位構成図とプロジェクト文脈から、何を継続して利用・引き継ぎたいか、守る情報は何かを確認する。背景全文を転載せず、配置判断に影響する条件を選ぶ。
- 「作成前に集める情報」を短いメモにし、「全体の作成手順」で環境・経路・前提を組み立てる。製品名や枠の数から設計を始めない。
- 「各章の書き方」で境界と通信条件を掘り下げ、最後に情報の受け渡しと障害影響を確かめる。業務判断・公開可否は人間の判断へ渡す。
- 継続利用の目的を、必要な配置・到達条件と対応付ける。経路 ID で情報・利用条件・検証対象・未決事項を結び、値・構文・設定・復旧操作は担当の詳細文書へ委ねる。

## 2. 作成前に集める情報

秘密値は収集せず、管理主体と確認先を控える。

| 項目         | 集める情報・問い                                                           |
| ------------ | -------------------------------------------------------------------------- |
| 利用目的     | 誰が何の記録・処理を継続し、どの障害を切り分けたいか                       |
| 上位の要素   | 処理・データ・外部依存の責務。物理配置の根拠と論理要素を区別する           |
| 実行場所     | ホスト、実行用コンテナ、別端末、外部基盤のどこで動くか。未確認の場所は何か |
| 正本とコピー | 何をどこに保持し、閲覧物・共有物・復元用コピーをどう区別するか             |
| 接続条件     | 誰が起動し、いつ外部接続が必要か。送る情報は何か                           |
| 管理・判断   | 接続・保管・公開の管理者と、人間が判断すべき範囲                           |
| 制約と依存   | 通信、費用、担当負荷、接続先不在が利用目的へ与える影響                     |
| 詳細の委譲先 | 技術構成、連携、運用の正本。未作成なら必要な契約と担当                     |

## 3. 全体の作成手順

1. 「概要」で対象環境と図で判断することを絞り、上位入力と詳細へ委ねる範囲を示す。
2. 上位の処理・データを実行場所へ仮置きする。同じホストにあることと、同じ管理主体であることを分けて考える。
3. 「配置と境界の定義」へ、環境・要素、上位との対応、管理主体、保持情報と到達条件を記入する。配置不明のものは仮定として残す。
4. 「通信経路と情報の境界」で、起点・終点・目的・送受信情報・利用条件を経路 ID へ結ぶ。ローカル操作と外部への持ち出しを分ける。
5. 「インフラ構成図（Mermaid）」へ、配置と経路を描く。矢印は主たる依頼・参照・転送の向きにし、応答の省略と仮定を注記する。ネットワークの中継を省略する場合も、到達条件が変わる点を本文に残す。
6. 「技術前提・制約と検証観点」で、境界が成立する条件と、依存が使えないときの影響・観測対象を整理する。
7. 「メモ / 将来課題」に、仮定と不足情報の影響、担当、解消条件・引き継ぎ先を集める。未決事項がなければ章を省略する。
8. 表と図の名前・経路 ID を合わせ、詳細設定の転載と、図をなぞるだけの説明を整理する。

## 4. 各章の書き方

### 4.1. 概要

- この図を使う人は、配置、接続、障害影響のどれを判断しますか。
- 上位の責務のうち、今回配置するものと対象外は何ですか。
- 費用や担当負荷を変える前提が、採用済みの事実として紛れ込んでいませんか。

良い例は「店頭から記録サービスまでの通信依存を判断する」。避けたい例は「クラウドを使う」で、達成したい利用結果が分かりません。

### 4.2. インフラ構成図（Mermaid）

- 各枠を越えると、実行場所・到達条件・管理主体の何が変わりますか。
- 一本の矢印を依頼・参照・転送のいずれとして説明できますか。
- 同じ処理の代替配置を、同時に動く別処理として描いていませんか。

良い例は「端末と外部保管先の間に、コピー転送の線を描く」。避けたい例は「Internet とだけ書いた線で全要素を結ぶ」で、目的別の通信条件が失われます。

### 4.3. 配置と境界の定義

- 上位要素をどこに配置し、どの役割を複数の工程へ展開しましたか。
- 正本、閲覧物、共有先、復元用コピーを区別できますか。
- 枠名だけで認証・隔離が成立したと説明していませんか。

良い例は「DB はアプリからだけ使う案で、到達制御は要確認」。避けたい例は「Private なので安全」です。表には図にない管理責務や到達条件を足します。

### 4.4. 通信経路と情報の境界

- 外部へ出る情報と、選択した機能でだけ必要になる経路は何ですか。
- 相手を変える場合、情報の持ち出し先と承認条件も変わりませんか。
- 接続方式を確認した根拠はありますか。詳細契約の更新先へたどれますか。

良い例は「共有時だけ変更履歴を送り、ローカル保存とは結果を分ける」。避けたい例は「全操作でリモート共有必須」と根拠なく決めることです。

### 4.5. 技術前提・制約と検証観点

- 外部サービス・通信・保存先を一つずつ使えなくした場合、どの利用結果に影響しますか。
- 到達、認証、処理結果、保存結果を別々に観測できますか。
- 必要な監視対象を示し、閾値・通知先・回復操作は詳細設計へ渡せていますか。

良い例は「送信応答の欠落と保存失敗を照合する」。避けたい例は「再試行すれば必ず回復する」です。確認できない保証は論点へ戻します。

### 4.6. メモ / 将来課題

- 仮定・不足情報がどの経路の判断や検証を止めますか。
- 誰が何を確認または判断すれば解消できますか。
- 未作成の正本を実在する仕様として扱っていませんか。

良い例は「閲覧範囲を PO が判断後、OPS が配信境界へ反映」。避けたい例は「後日確認」です。

## 5. 深掘り手順

1. 外部へ出る線を一本選び、その情報を渡さなくても利用目的を満たせるかを問う。不要な持ち出しは減らし、必要なら理由と条件を残す。
2. 同じ枠の二要素について、管理者、保持情報、到達許可が同じか比べる。異なるなら別境界または明示的な注記にする。
3. 依存を停止した場面を置き、ローカルの作業結果、相手側の受付、利用者が確認できる結果を分ける。結果不明を未実行と推測しない。
4. 別配置・別 provider へ切り替える案があれば、接続先だけでなく、送信範囲、認証、費用、担当負荷の判断が変わるか確認する。

## 6. 良い例 / 悪い例

| 観点   | 良い例                                   | 悪い例                                       |
| ------ | ---------------------------------------- | -------------------------------------------- |
| 境界   | 同じホストでも別管理のサービスを区別する | 同じネットワークにあるので同じ信頼範囲とする |
| 情報   | 共有時の変更履歴と推論時の文脈を分ける   | 外部接続をすべて同期と呼ぶ                   |
| 確定度 | 接続経路は仮定とし、到達性の確認者を残す | 製品名から構成済みの認証方式を推測する       |
| 継続性 | サービス停止で失う結果と残る記録を分ける | 外部障害時も問題なく動くと断定する           |

## 7. レビュー観点

| 観点     | 確認する問い                                               | 主な確認者 |
| -------- | ---------------------------------------------------------- | ---------- |
| 利用目的 | 配置案が守る利用結果と通信・費用・負荷の条件を説明できるか | BA / PO    |
| 配置境界 | 上位要素と実行場所、正本、管理主体が対応するか             | ARC        |
| 持ち出し | 情報、送信先、利用条件、人間の判断範囲が明らかか           | ARC / PO   |
| 検証入力 | 経路ごとの失敗・結果不明と、観測する情報を識別できるか     | QE         |
| 運用入力 | 監視・復旧の設計対象と詳細の更新先を選べるか               | OPS        |

## 8. 仕上げチェック

- 図の要素から、実行場所・管理主体・保持情報へたどれる。
- 経路 ID から、利用目的・情報・利用条件・検証対象を対応付けられる。
- 仮定と未決事項に影響・担当・解消条件があり、未確認の隔離や復旧を保証していない。
- 値・構文・構造の詳細を各正本へ委ね、図をなぞるだけの本文を残していない。
