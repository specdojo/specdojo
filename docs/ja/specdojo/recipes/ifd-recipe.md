# インフラ構成図 作成レシピ

Infrastructure Flow Diagram Writing Recipe

上位の責務を実行場所と通信境界へ移し、境界設計と障害の切り分けに使える構成図を作るための作り方を示す。

## 1. このレシピの使い方

- 構成図は、上位構成図とプロジェクト文脈から継続したい利用と守る情報を引き継ぎ（Why）、実行場所・境界・経路を定め（What）、技術前提と検証観点で境界の成り立ちを示す（How）。経路 ID で情報・利用条件・検証対象・未決事項を結ぶ（Trace）。
- 「作成前に集める情報」をメモでそろえてから、「全体の作成手順」の順に書く。製品名や枠の数から始めない。

## 2. 作成前に集める情報

秘密値は集めず、管理主体と確認先だけを控える。

| 項目         | 集める情報                                                             | 取り出し元                   |
| ------------ | ---------------------------------------------------------------------- | ---------------------------- |
| 利用目的     | 誰が何の記録・処理を続け、どの障害を切り分けたいか                     | 上位構成図、プロジェクト文脈 |
| 上位の要素   | 処理・データ・外部依存の責務                                           | 上位構成図                   |
| 実行場所     | ホスト、実行用コンテナ、別端末、外部基盤のどこで動くか、代替配置の有無 | 環境の管理者への確認         |
| 正本とコピー | 何をどこに保持し、閲覧物・共有物・復元用コピーをどう分けるか           | 環境の管理者への確認         |
| 接続条件     | 誰が起動し、いつ外部接続が要り、何を送るか                             | 連携の担当への確認           |
| 確認の根拠   | 配置・接続条件の確認元と、未検証の仮定                                 | 設定の確認記録、検証の記録   |

## 3. 全体の作成手順

1. 上位の処理・データを実行場所へ仮置きする。同じホストにあることと、同じ管理主体であることを分けて考える。
2. 「配置と境界の定義」を書く。配置が決まらないと、経路の起点・終点が決まらない。配置が不明なものは仮定として残す。
3. 「通信経路と情報の境界」で経路 ID を振る。ローカル操作と外部への持ち出しを分ける。
4. 「インフラ構成図」を、決めた配置と経路 ID から描く。図から先に描くと、表が図の言い直しになる。
5. 「技術前提・制約と検証観点」で、境界が成り立つ条件と、依存が使えないときの影響を書く。
6. 「メモ / 将来課題」に、仮定と不足情報がどの経路に効くかを集める。なければ章を省く。
7. 最後に「概要」を書く。判断範囲は配置と経路が決まってから絞ると、本文の言い直しにならない。

## 4. 各章の書き方

### 4.1. 概要

問い:

- この図を使う人は、配置、接続、障害影響のどれを判断するか。
- 上位の責務のうち、今回配置しないものは何か。

コツ:

- 上位構成図の背景を写したくなったら、上位構成図への参照に置き換える。
- 費用や担当負荷を変える前提が、採用済みの事実として紛れ込みやすい。決まっていなければ仮定にする。

### 4.2. インフラ構成図

問い:

- 各枠を越えると、実行場所・到達条件・管理主体の何が変わるか。
- 一本の矢印を、依頼・参照・転送のどれと説明できるか。

コツ:

- 中継を省いた線は、許可していない直接接続に見えやすい。省いたら、到達条件が変わる点を本文に残す。

### 4.3. 配置と境界の定義

問い:

- 正本、閲覧物、共有先、復元用コピーを区別できるか。
- 代替配置へ切り替えると、保持範囲・書込範囲・到達性のどれを確かめ直すか。

コツ:

- 同じ枠の二要素について、管理者・保持情報・到達許可が同じかを管理者に聞く。違えば別の枠か注記にする。
- 表には図にない管理責務と到達条件だけを足し、図の枠を読み上げない。

### 4.4. 通信経路と情報の境界

問い:

- 外部へ出る情報と、選んだ機能でだけ要る経路はどれか。
- 送り先を変えたら、持ち出す情報と承認条件も変わるか。

コツ:

- 連携の担当に「その情報を送らなくても利用目的を満たせるか」を聞くと、不要な持ち出しが見つかる。
- 接続方式は確認した根拠を聞く。製品名から認証方式を推測しやすい。

### 4.5. 技術前提・制約と検証観点

問い:

- 外部サービス・通信・保存先を一つずつ使えなくすると、どの利用結果に影響するか。
- これから確かめる条件と、既に確かめた証跡を区別できるか。

コツ:

- 到達、認証、処理結果、保存結果を別々に聞く。「接続できたので保存もできた」とまとめやすい。
- 確かめられない保証は書かず、「メモ / 将来課題」へ戻す。

### 4.6. メモ / 将来課題

問い:

- 仮定・不足情報が、どの経路の判断や検証を止めるか。
- 未作成の文書を、実在する仕様として扱っていないか。

コツ:

- 「後日確認」で済ませず、決まったら直す枠と経路を書く。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 外部へ出る経路ごとに、どの利用目的に応えるかを確かめ、対応のない持ち出しを外す。
2. 配置表の要素ごとに、どの上位要素の責務かを確かめ、対応のない要素を外す。
3. 依存を止めた場面ごとに、ローカルの結果、相手側の受付、利用者が確かめられる結果を分ける。結果不明を未実行と推測しない。

## 6. 良い例 / 悪い例

| 観点   | 良い例                                   | 悪い例                                       |
| ------ | ---------------------------------------- | -------------------------------------------- |
| 境界   | 同じホストでも別管理のサービスを区別する | 同じネットワークにあるので同じ信頼範囲とする |
| 情報   | 共有時の変更履歴と推論時の文脈を分ける   | 外部接続をすべて同期と呼ぶ                   |
| 継続性 | サービス停止で失う結果と残る記録を分ける | 外部障害時も問題なく動くと断定する           |

## 7. レビュー観点

| 観点     | 確認内容                                                     |
| -------- | ------------------------------------------------------------ |
| 利用目的 | 配置案が守る利用結果と、通信・費用・負荷の条件を説明できるか |
| 配置境界 | 上位要素と実行場所、正本、管理主体が対応するか               |
| 持ち出し | 送る情報、送り先、利用条件、人間が判断する範囲が分かるか     |
| 検証入力 | 経路ごとの失敗・結果不明と、観測する情報を分けられるか       |

## 8. 仕上げチェック

- 図の要素から、実行場所・管理主体・保持情報へたどれる。
- 経路 ID から、利用目的・情報・利用条件・検証対象へたどれる。
- 未確認の隔離や復旧を保証していない。
