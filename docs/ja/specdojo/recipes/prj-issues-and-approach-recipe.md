# プロジェクト課題と解決アプローチ 作成レシピ

Project Issues and Approach Writing Recipe

プロジェクト課題と解決アプローチを、関係者が何が課題で、どれを、どう解く方針かを合意できる内容に仕上げるための作り方を示す。

## 1. このレシピの使い方

- 本書は、概要の目指す価値（Why）を引き継ぎ、優先課題と採用方針（What）を定め、解決策候補・採否理由・軽減策（How）を書く。課題 ID と案 ID で、課題から原因・候補・採否までたどれるようにする（Trace）。方式設計と実装詳細は書かない。
- 「作成前に集める情報」をメモでそろえてから、「全体の作成手順」の順に書く。
- 書き終えたら「レビュー観点」で読み直し、「仕上げチェック」で確かめる。

## 2. 作成前に集める情報

| 項目           | 集める情報                                           | 取り出し元                             |
| -------------- | ---------------------------------------------------- | -------------------------------------- |
| 目指す価値     | 誰のどの業務価値に近づけたいか、放置で何が悪化するか | プロジェクト概要                       |
| 困っている現象 | 利用者や運用で実際に起きていること（解決策ではなく） | 利用者・運用担当への聞き取り、観察記録 |
| 境界と成立条件 | 対象範囲・対象外、守るべき前提・制約                 | スコープ、前提・制約・依存関係         |
| 原因の手がかり | 確認できた事実と、まだ推測の段階のこと               | 観察記録、既存の成果物、聞き取り       |
| 判断軸の順序   | 効果・費用・期間・負荷などを、今回どの順で重視するか | 承認者への確認                         |

## 3. 全体の作成手順

1. 課題一覧を最初に書き、課題 ID を振る。原因と候補が課題 ID を参照するため、ここが決まらないとほかの章が書けない。
2. 原因を、課題ごとに事実と仮説に分けて書く。
3. 解決策候補を 2 件以上挙げ、代替か補完かと対応課題を添える。
4. 採用アプローチと理由を、判断軸の順序に沿って書く。
5. 必要な場合だけ、トレードオフ/リスク、次の検討事項（ToDo）、見直しと変更管理を書く。書く内容がなければ置かない。
6. 最後に H1 直下の導入部（目的、承認者と利用ロール、合意対象と合意対象外）を書く。採用方針が決まってから書くと、本文の言い直しにならない。

## 4. 各章の書き方

### 4.1. 課題一覧

問い:

- 利用者や運用で、実際に困っている現象は何か。
- 放置すると、誰がどの業務価値で困るか。

コツ:

- 「〜がない」と書き始めたら解決策の先取りなので、それがないと何が起きているかを聞き直す。
- 概要の背景を写したくなったら、概要への参照に置き換え、本書では課題の影響だけを書く。

### 4.2. 原因（仮説でも可）

問い:

- その課題は、なぜ起きているか。
- それは確認した事実か、まだ推測か。

コツ:

- 仮説には、何を見れば確かめられるかを添えるよう聞く。確認方法がない仮説は、検証できないまま採否の根拠になりやすい。
- 一つの課題に原因を一つだけ書くと、候補が一つに絞られやすい。情報・判断基準・手順・制約の別に分けて聞く。

### 4.3. 解決策候補

問い:

- 候補は、同じ判断を置き換える代替案か、別の課題・原因を扱う補完策か。
- 各案は、どの課題に効き、何を失うか。

コツ:

- 案が一つしか出ないときは、「この案を採らないなら何をするか」と聞いて代替案を引き出す。
- 代替案どうしの詳細な比較を書き始めたら、比較が要る論点だけを残す。

### 4.4. 採用アプローチと理由

問い:

- どの案を採用し、単独で採用した場合に何が不足するか。
- 採用しない案は、どの判断軸で外れたか。

コツ:

- 判断軸の順序は承認者に先に聞く。順序が決まらないまま書くと、理由が「よさそう」に戻る。
- 補完策は、各案が担う課題・原因が重ならないかを確かめる。重なるなら代替の関係である。

### 4.5. トレードオフ/リスク

問い:

- 採用の代償として、何を捨てる・先送りするか。
- 起きうる失敗と、その軽減策は何か。

コツ:

- 採用理由の判断軸で劣る点を探すと、トレードオフが見つかりやすい。

### 4.6. 次の検討事項（ToDo）

問い:

- 次の意思決定に必要な調査・確認・承認は何で、誰が担うか。
- 何が決まれば完了で、いつまでに決める必要があるか。

コツ:

- 採否を保留した論点と、仮説の確認方法から拾うと漏れにくい。

### 4.7. 見直しと変更管理

問い:

- どんな変化があれば本書の合意を見直すか。
- そのとき何を確認し、どう対応するか。

コツ:

- 原因の仮説ごとに「反証されたら何を見直すか」を聞くと、契機と対応が対で決まる。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 各課題の影響が、目指す価値のどれに当たるかを確かめ、対応のない課題を外すか価値を問い直す。
2. 各原因が課題 ID に結び付き、仮説に確認方法があるかを確かめる。
3. 各候補が、どの課題・原因を扱うかを確かめ、対応先のない案を外す。
4. 採否の理由が判断軸のどれによるかを確かめる。
5. 設計詳細や特定技術の採否を書いた箇所を、後続の成果物への参照に戻す。

## 6. 良い例 / 悪い例

| 観点       | 良い例                                                            | 悪い例                   |
| ---------- | ----------------------------------------------------------------- | ------------------------ |
| 課題       | 記録ルールがばらつき、引き継ぎ時に確認に時間がかかる              | テンプレートがない       |
| 原因       | 事実: 担当ごとに記述様式が異なる / 仮説: 共通様式が浸透していない | なんとなく属人化している |
| 解決策候補 | A 案と B 案は同じ課題への代替、C 案は別原因への補完と整理する     | とにかく標準化する       |
| 採用理由   | A 案と C 案が異なる原因を扱い、単独では不足するため併用する       | A 案がよさそうだから採用 |

## 7. レビュー観点

| 観点             | 確認内容                                                       |
| ---------------- | -------------------------------------------------------------- |
| 業務価値との対応 | 課題と採用方針が、目指す価値・利用者・期待効果と対応しているか |
| 関係者・利用場面 | 承認者、利用ロール、合意対象が読み取れるか                     |
| 採否の再現性     | 後から読んだ人が、判断軸の順序から同じ採否を導けるか           |
| 委譲の境界       | 設計詳細・実装詳細・特定技術の採否を書きすぎていないか         |

## 8. 仕上げチェック

- 各課題が原因・候補・採否まで課題 ID と案 ID でたどれる。
- 仮説を事実として書いていない。
- 課題・原因・リスクの記述に、個人や特定の組織を識別できる情報や非公開の観察事実がない。
