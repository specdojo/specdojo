# プロジェクトスコープ 作成レシピ

Project Scope Writing Recipe

プロジェクトスコープを、関係者が今回やることとやらないことを合意できる内容に仕上げるための作り方を示す。

## 1. このレシピの使い方

- スコープは、プロジェクト概要の目的・期待効果（Why）を引き継ぎ、対象業務・対象システム・対象期間・スコープ外（What）を定め、任意で境界の判断基準と変更方針（How）を決める。各行は、上位の期待効果と境界の理由で、変更後は変更記録でもたどれるようにする（Trace）。

## 2. 作成前に集める情報

| 項目             | 集める情報                                                   | 取り出し元               |
| ---------------- | ------------------------------------------------------------ | ------------------------ |
| 目的と期待効果   | 取り組む理由、放置したときに悪化すること                     | プロジェクト概要         |
| 利用者と利用場面 | 誰が使い、誰の作業や判断が変わるか                           | プロジェクト概要、利用者 |
| 整備するもの     | 作る・変える・運用するシステム、ツール、正本データ、生成物   | 既存の構成、実行責任者   |
| 期間の区切り     | 初期対象の終わりを決める日付またはイベント                   | スケジュール、承認責任者 |
| 外す候補         | やらないことと理由、再検討する条件                           | 関係者への確認           |
| 迷う候補         | 含めるか外すかで意見が分かれた項目と、そのときの判断のしかた | 確認の過程のメモ         |

## 3. 全体の作成手順

1. 対象外の候補を先に書き出す。外すものが決まると、対象業務の範囲が狭まり書きやすくなる。
2. 対象業務を、利用者の作業や判断の単位で書く。
3. 対象システムを、対象業務を支えるものに限って並べる。
4. 対象期間で、初期対象と継続改善を分ける。
5. スコープ外に、1 で出した候補を理由と再検討条件を添えて書く。
6. 迷う候補が残った場合は境界の判断基準を、変更の決め方を合意した場合はスコープ変更方針を書く。どちらも任意の章で、なければ省く。

## 4. 各章の書き方

### 4.1. 対象業務

問い:

- 対象にすると、誰のどの作業や判断が変わるか。
- 作るだけでなく、運用・管理できる状態にしたいものは何か。

コツ:

- 機能名を書き始めたら、利用者に「その機能で何をするか」を聞いて作業の言葉に直す。
- 背景や期待効果を概要から写したくなったら、写さず概要への参照に置き換える。

### 4.2. 対象システム

問い:

- プロジェクトが整備・変更するツール、正本データ、生成物は何か。
- 外部サービスのうち、プロジェクトが担うのは設定・接続・利用のどこまでか。

コツ:

- 業務機能と文書体系、補助ツールが混ざると粒度がずれやすい。並べた後で、同じ大きさの項目かを見直す。
- 生成物は、生成元の正本と直接編集してよいかを聞くと、責務の境界が決まる。
- 画面・API・DB の名前が出てきたら、設計の話なので書かない。

### 4.3. 対象期間

問い:

- 初期対象はどの日付、または何が起きたら終わるか。
- 継続改善のうち、今回の範囲に含めるものはあるか。

コツ:

- 日付が出ないときは「初回公開まで」のようにイベントで聞く。決まっていなければ _UNDECIDED_ を残し、決める時期を添える。

### 4.4. スコープ外

問い:

- 今回やらないことは何で、なぜ外すのか。
- 外したことで困る利用者がいる項目は、いつ再検討するか。

コツ:

- 「必要なら考える」は対象外になっていない。含めないと言い切り、再検討の条件を添える。
- 書かないと「含まれる」と誤解されやすい項目を、関係者に聞いて拾う。

### 4.5. 境界の判断基準（任意）

問い:

- 含めるか外すかで迷ったとき、何を優先するか。
- 個別の要望や特定の技術に引っ張られたとき、何で判断するか。

コツ:

- 迷う候補で実際に判断した理由から書くと、後の変更判断にも使える原則になる。

### 4.6. スコープ変更方針（任意）

問い:

- 誰がどこに変更を提案し、誰が決めるか。
- 初期リリース前に足すとき、何を外すか延期するか。

コツ:

- 「関係者で相談する」で止めず、決める人と判断理由を残す場所を聞く。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 対象業務の各行が、概要のどの期待効果に応えるかを確かめ、対応のない行を外すかスコープ外へ移す。
2. 対象システムの各行が、どの対象業務を支えるかを確かめる。
3. スコープ外の各行に、外す理由と再検討条件があるかを確かめる。
4. 受入条件・設計・実装の詳細を書いた箇所を見つけ、後続の成果物へ移す。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                                | 悪い例                      |
| ------------ | --------------------------------------------------------------------- | --------------------------- |
| 対象業務     | 店主代表以外が店番する場合でも販売・在庫・つけ残高を確認できる状態    | 販売管理を改善する          |
| 対象システム | 販売登録、管理データ、生成レポートを分け、編集・責務の境界を示す      | 画面名、API、DBを混在させる |
| 対象期間     | 初期リリースから2週間の記録継続確認までを対象にする                   | できるだけ早く公開する      |
| スコープ外   | EC は店頭販売の記録継続を優先するため対象外とし、次フェーズで検討する | 必要なら EC も考える        |
| 境界判断     | 日々使う業務を優先し、高度な分析は記録安定後に扱う                    | 便利そうなものは入れる      |

## 7. レビュー観点

| 観点         | 確認内容                                                       |
| ------------ | -------------------------------------------------------------- |
| 業務価値     | 対象業務が概要の期待効果に対応し、利用者への影響が読み取れるか |
| システム境界 | ツール、正本データ、生成物、外部サービスの責務を区別できるか   |
| 境界の合意   | 関係者が、迷う候補を含めるか外すかをこの文書だけで判断できるか |

## 8. 仕上げチェック

- 対象業務・対象システムの各行が、概要の期待効果と境界の理由へたどれる。変更した行は、変更記録にもたどれる。
- 未確定の期間に _UNDECIDED_ と決める時期がある。
- 境界の判断基準・スコープ変更方針は、書いた場合だけ、後の判断に使える原則と決める人があるかを確かめる。
- 受入条件・設計・実装の詳細を書いていない。
- 個人情報、公開できない情報、機密情報を含めていない。
