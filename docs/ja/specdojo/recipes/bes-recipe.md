# 業務イベント仕様 作成レシピ

Business Event Specification Writing Recipe

起点が違っても同じ出来事と呼べるか、どの時点の何を事実として残すかを具体化するための手順です。業務上の混同を減らし、別の担当者も発生有無とデータの意味を判断できる記述へつなげます。

## 1. このレシピの使い方

- 上位の業務目的とイベント一覧から、誰が何を取り違えて困るのかを一つ選びます。その混同を解消する事実の境界を本書で定めます。
- 成立と不成立の場面を並べてから、何が起きたか、いつ、誰が／何が、発生条件、事実データの五章を書きます。処理後の手順や実装方式は委譲先へ分けます。
- 各主張を、上位イベント・状態定義・データモデルのどれで確認できるかたどります。確認できない境界は推測で埋めず、判断者と確認時期を添えて残します。

## 2. 作成前に集める情報

| 入力             | 確かめる問い                                                               |
| ---------------- | -------------------------------------------------------------------------- |
| 業務目的と利用者 | 定義が曖昧だと、誰が何を誤って数えたり引き継いだりするか                   |
| 上位イベント一覧 | どの出来事を詳細化するか。共通の対象範囲と個別の差分は何か                 |
| 似た出来事       | 要求、受付、確定、着手、処理完了を区別する必要があるか                     |
| 起点と主体       | 人の指名、自動判断、一括要求などで成立する事実が変わるか                   |
| 状態と業務ルール | 成立直前の状態をどこで判定するか。条件と判断ロジックの正本は何か           |
| データモデル     | 対象、取引、要求、実行をどう区別するか。既存の識別情報で相関を説明できるか |
| 承認と未決事項   | 誰が業務定義を承認するか。確認担当、判断期限、記録先が決まっているか       |

## 3. 全体の作成手順

1. 解消する混同と対象業務を一文にし、読者が発生有無・回数を判定できることを利用の基準にします。
2. 「何が起きたか」に、一回分の事実と含めない出来事を書きます。適用範囲が不明なら、確認できた業務と未判定の業務を分けます。
3. 「いつ」に、成立を観測できる時点を書きます。要求から後処理までを時系列に並べ、どこで初めて事実になるかを選びます。
4. 「誰が／何が」に、要求者と成立させる主体を並べます。起点が異なっても境界が同じかを比較します。
5. 「発生条件」に、共通条件、起点別の差分、不成立条件を書きます。正本にある判断ロジックをコピーせず、何を満たした事実なのかへ絞ります。
6. 「事実データ」に、その時点で分かる情報だけを置きます。一括要求は二件以上を紙上で並べ、要求と個別対象を混同しない相関情報を探します。
7. 発生・相関の確認例から判断を説明します。未決事項には判断者、確認担当、時期、記録先を付け、承認前に引き渡せる範囲を明示します。

## 4. 各章の書き方

### 4.1. 何が起きたか

問いは「誰のどの混同を防ぐ事実か」「同じ要求で二件確定したら一回か二回か」です。名詞だけでなく、対象と成立した事実を一文にします。

良い例は「一取引の会計が確定した。複数明細でも一回」。避けたい例は「販売処理」で、事実と処理を区別できません。

### 4.2. いつ

問いは「成立したと言える最初の観測点はどこか」「同じ排他区間で行う別の処理も同じ出来事なのか」です。処理の近さと業務上の同一性を分けて考えます。

良い例は「会計確定を記録した時点」。避けたい例は「会計中」で、発生前後を分けられません。

### 4.3. 誰が／何が

問いは「要求者と確定する主体は同じか」「人の判断とシステムの記録の責任はどこで分かれるか」です。名称を役割、構成要素、実際の担当者のどれとして使うか確かめます。

良い例は「店番担当が要求し、販売管理システムが確定を記録する」。避けたい例は「担当が実行する」で、何を担当したかが分かりません。

### 4.4. 発生条件

問いは「直前まで同じでも、何が欠けたら発生しないか」「今の依存文書だけで全業務への適用を判断できるか」です。成立する例の条件を一つだけ外して、不成立の境界を探します。

良い例は「未確定の取引で受領を確認して確定した場合。合計表示だけでは発生しない」。避けたい例は「条件が揃えば発生する」で、確認すべき条件が隠れます。

### 4.5. 事実データ

問いは「各項目は何を区別するために必要か」「最後にしか分からない件数を最初の事実にしていないか」「実行 ID で同じ要求をたどれる根拠はあるか」です。データモデルの項目名を先に決めず、意味と単位から対応を確認します。

良い例は「取引番号で確定と明細を対応付ける」。避けたい例は「時刻が近いので同じ要求」とする推定です。

## 5. 深掘り手順

1. 事実の境界で意見が分かれたら、同じ操作でも発生しない例を一つ示し、何を観測できていないか確認します。
2. 自動・一括で説明が崩れたら、二つの要求にそれぞれ複数の対象を置き、要求、対象、実行の対応を書き出します。既存モデルで対応できなければ未決事項にします。
3. 根拠が参照範囲にないときは、必要な文書 ID と依存追加の必要性を記録します。確認済みの範囲まで書き、未確認の業務を恒久的に除外する結論は出しません。

## 6. 良い例 / 悪い例

| 観点     | 良い例                                                           | 悪い例                       | 判断の違い                     |
| -------- | ---------------------------------------------------------------- | ---------------------------- | ------------------------------ |
| 発生単位 | 一取引に複数明細があっても確定は一回                             | 複数の場合も扱う             | 数える単位を決められるか       |
| 観測時点 | 確定記録の成立時。印字完了は後処理                               | 正常に終了した時             | 何の終了かが分かるか           |
| 未決事項 | 判断者と確認担当を分け、設計着手前に判断結果をレビュー結果へ記録 | 後で確認する                 | 誰がいつ何を決めるかたどれるか |
| 相関情報 | 同じ要求の二件は同じ相関情報、別要求では区別する                 | 同じ実行 ID を使えばよいはず | 根拠のある単位で関連付けるか   |

## 7. レビュー観点

| 観点             | 確認する問い                                           | 主な確認者 |
| ---------------- | ------------------------------------------------------ | ---------- |
| 業務価値         | 解消したい混同と、定義した発生境界が対応するか         | BA         |
| 業務承認         | 対象範囲と未決事項を判断する人間を識別できるか         | PO         |
| 技術への引き渡し | 状態定義とデータモデルに照合でき、未確認部分が分かるか | ARC        |
| 確認可能性       | 同じ場面から発生有無・回数・相関を判断できるか         | QE         |

## 8. 仕上げチェック

- 用いた主体名と識別情報の意味が、五章の間で変わっていないことを確認します。
- 発生条件を満たさない例と、成立後の処理が失敗する例を混同していないことを確認します。
- 確認できた範囲と未判定の範囲を区別し、判断者・時期・記録先のない論点を残していないことを確認します。
- 本文に残した情報が発生時点で観測でき、後処理の手順や正本の項目定義を重複していないことを確認します。
