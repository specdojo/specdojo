# 業務イベント仕様 作成レシピ

Business Event Specification Writing Recipe

起点が違っても同じ出来事か、どの時点の何を事実とするかを判断できる記述の作り方を示す。

## 1. このレシピの使い方

- 業務イベント仕様は、一覧から防ぎたい混同（Why）を引き継ぎ、一回の事実の境界・時点・条件・データ（What）を定め、要求者と成立させる主体（How）を分ける。主張は上位一覧・状態定義・データモデルでたどる（Trace）。

## 2. 作成前に集める情報

| 項目             | 集める情報                                     | 取り出し元           |
| ---------------- | ---------------------------------------------- | -------------------- |
| 防ぎたい混同     | 誰が何を誤って数え、引き継ぐか                 | 業務目的、利用者     |
| 対応するイベント | 対応する行と、共通の対象範囲・用語             | 業務イベント一覧     |
| 似た出来事・起点 | 取り違えやすい要求・受付・後処理と、起点の種類 | 業務の担当者         |
| 判断の根拠       | 成立直前の状態と、条件の正本                   | 状態定義、業務ルール |
| 識別情報         | 対象・取引・要求・実行を区別する情報           | データモデル         |
| 承認する人       | 業務定義を承認する人と判断時期                 | 業務の承認者         |

## 3. 全体の作成手順

1. 防ぐ混同を一文でメモする。これがないと一回の単位が決まらない。
2. 成立と不成立の場面を並べてから「何が起きたか」を書く。
3. 「いつ」「誰が／何が」「発生条件」「事実データ」の順に書く。前の章の境界が後の章の範囲になる。
4. 解釈が分かれた場面を確認例にする。
5. 導入は最後に書く。境界が決まる前に書くと本文の言い直しになる。

## 4. 各章の書き方

### 4.1. 導入

問い:

- この定義がないと、誰が何を取り違えるか。
- 何を判定できれば、この定義を使えたと言えるか。

コツ:

- 業務の目的や用語は、写さず上位一覧への参照に置き換える。
- 一覧に対応する行がなければ、推測で結び付けず未照合と書く。

### 4.2. 何が起きたか

問い:

- 同じ要求で二件確定したら、一回か二回か。
- まだ判定していない業務はどれか。

コツ:

- 「販売処理」のような名詞で止まったら、成立した事実を過去形にする。
- 承認する人と時期が未定の業務は、対象外にしない。

### 4.3. いつ

問い:

- 成立したと言える最初の観測点はどこか。
- 同じ排他区間の別の処理も、同じ出来事か。

コツ:

- 処理が近いことと、業務上同じ出来事であることを分ける。

### 4.4. 誰が／何が

問い:

- 要求者と事実を成立させる主体は同じか。
- 人の判断とシステムの記録は、どこで分かれるか。

コツ:

- 名称が役割・構成要素・担当者のどれかを聞く。混ざると章ごとに意味が変わる。

### 4.5. 発生条件

問い:

- 直前まで同じでも、何が欠けたら発生しないか。
- 今の参照文書だけで、全業務への適用を判断できるか。

コツ:

- 判断ロジックは写さず業務ルールを参照し、満たした事実だけを書く。

### 4.6. 事実データ

問い:

- 各項目は何を区別するために要るか。
- 最後にしか分からない件数を、最初の事実にしていないか。

コツ:

- 項目名より先に、意味と単位でデータモデルとの対応を確かめる。
- 一括要求は二件並べると、要求と対象の混同に気づく。

## 5. 深掘り手順

浅いときは、次の順で対応のない主張を探す。

1. 各境界が導入のどの混同を防ぐかを確かめ、対応のない境界を外す。
2. 発生条件の各行を、状態定義・業務ルールのどこで判定するか確かめる。
3. 事実データの各項目が使われる判定を確かめ、使われない項目を外す。
4. 根拠が参照範囲にない主張は、確認済みの範囲まで書く。

## 6. 良い例 / 悪い例

| 観点     | 良い例                                             | 悪い例                 |
| -------- | -------------------------------------------------- | ---------------------- |
| 発生単位 | 複数明細の一取引でも確定は一回                     | 複数の場合も扱う       |
| 観測時点 | 確定記録の成立時。印字完了は後処理                 | 正常に終了した時       |
| 発生条件 | 未確定の取引を確定した場合。合計表示では発生しない | 条件が揃えば発生する   |
| 相関情報 | 取引番号で確定と明細を対応付ける                   | 同じ実行 ID でよいはず |

## 7. レビュー観点

| 観点             | 確認内容                                               |
| ---------------- | ------------------------------------------------------ |
| 業務価値         | 混同と発生境界が対応するか                             |
| 技術への引き渡し | 状態定義・データモデルと照合でき、未確認部分が分かるか |
| 確認可能性       | 同じ場面から発生有無・回数・相関を判断できるか         |

## 8. 仕上げチェック

- 主体名と識別情報の意味が、章の間で変わっていない。
- 発生しない例と、成立後の処理の失敗を混同していない。
- 導入で上位一覧の対応イベントが分かるか、未照合と書いている。
- まだない文書は ID の仮置きにし、確認する人と時期を添えている。
