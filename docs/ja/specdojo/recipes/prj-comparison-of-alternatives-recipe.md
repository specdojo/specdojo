# 代替案比較 作成レシピ

Comparison of Alternatives Writing Recipe

代替案比較を、採択・非採択の理由と見直し条件を後から再現できる内容に仕上げるための作り方を示す。

## 1. このレシピの使い方

- 代替案比較は、課題と解決アプローチの課題・必要能力（Why）を引き継ぎ、決定 ID ごとに決めることと評価条件（What）を定め、候補案・採否・軽減策（How）を示す。採否は決定 ID・案 ID・課題 ID でたどれるようにする（Trace）。
- 「作成前に集める情報」をメモでそろえてから、「全体の作成手順」の順に書く。
- 書き終えたら「レビュー観点」で読み直し、「仕上げチェック」で確かめる。

## 2. 作成前に集める情報

最初から比較表を書かず、次を短いメモで集める。

| 項目             | 集める情報                                                  | 取り出し元                     |
| ---------------- | ----------------------------------------------------------- | ------------------------------ |
| 課題と必要能力   | 解くべき課題の ID、課題を解くのに要る能力（手段とは分ける） | 課題と解決アプローチ           |
| 範囲と対象外     | 比較に含める範囲、初期に優先する最小成立範囲、対象外        | スコープ                       |
| 制約と外部依存   | 予算・期間・端末・既存資産・判断責任の制約                  | 前提・制約・依存関係           |
| 決めることと順序 | 先に決める判断と、その結果で要否が変わる判断                | 最終判断者への確認             |
| 候補と選定根拠   | 現行方式、外部の直接競合、責務・保管場所・移行可能性        | 公式資料、現場の担当者への確認 |
| 測れる値         | 操作時間、記録漏れ件数、費用など判定境界に使える実測値      | 現行運用の記録、試行           |

## 3. 全体の作成手順

1. 比較目的と前提条件で、決定 ID と判断順序を先に決める。上位の判断（解決方式、購入 / 構築）が決まらないと、製品を比べる必要があるかが決まらない。
2. 候補カテゴリと選定基準を定めてから、比較対象案を調べる。具体名から始めると、知っている製品だけが並ぶ。
3. 評価軸と評価基準を、候補の評価より先に固定する。候補を見てから軸を選ぶと、結論に合わせた軸になる。
4. 比較結果と採択理由を書き、技術的実現性と影響、比較試行の完了条件を添える。
5. リスクとトレードオフに、採択案の不利な点と軽減策を書く。
6. 決定と見直しに、採否の要約、最終判断者、再評価トリガー、記録先を書く。
7. 最後に H1 直下の冒頭文を書く。採否が決まってから書くと、本文の言い直しにならない。

## 4. 各章の書き方

### 4.1. 比較目的と前提条件

問い:

- この比較で、どの判断を支援し、何を決めないのか。
- 複数の判断がある場合、どれを先に決め、後の判断へ何を引き継ぐのか。

コツ:

- 最終判断者に「この比較が終わったら次に何を決めるか」を聞くと、判断の順序と決めないことが一度に分かれる。
- 課題や範囲の本文を写したくなったら、課題と解決アプローチ・スコープへの参照に置き換える。

### 4.2. 比較対象案

問い:

- 各案は、単独でも同じ課題を解く一式の案になっているか。
- 現行案と根拠の異なる、採択しない可能性がある有力な外部案を含めたか。

コツ:

- 前段文書の案を並べ直すだけで終わりやすい。カテゴリ（非システム、汎用ツール、既存製品、個別構築など）ごとに 1 つ以上探す。
- 画面・データ・ツールなど組み合わせて使う部品を別案に分けたくなったら、業務運用を含む一式の案にまとめる。
- 市場占有率を調べていない候補は「代表」「標準」と呼ばず、比較候補と書く。

### 4.3. 評価軸と評価基準

問い:

- 各評価軸は、どの課題 ID・制約から来ているか。
- `High` / `Middle` / `Low` の境界を、測定値または観察できる状態で言えるか。

コツ:

- 軸を省く・ほかの軸へ統合するときは、その場で観点名と理由、統合先と判定条件を書く。別章に書いたことを理由にすると、省いた妥当性を確かめられない。
- 「低いほどよい」軸（コスト・期間など）は、判定基準の列に有利な方向を書き込む。
- 値が確かめられない軸は未判定のまま残し、確かめる作業を比較試行へ回す。

### 4.4. 比較結果と採択理由

問い:

- 採択案は、どの評価軸で他案より優れているのか。
- 比較試行を行う場合、同じ入力・測定項目・完了条件・撤退の基準は決まっているか。

コツ:

- 採択理由を表の後の段落と決定の要約に重ねて書きやすい。理由は比較結果に 1 回だけ書き、ほかは参照する。
- 製品・サービスを採る場合は、データの正本、移行方法、利用停止時の取り出し方を担当者に聞いて書く。

### 4.5. リスクとトレードオフ

問い:

- 採択によって先送りする範囲、受容する負荷、失う選択肢は何か。
- 軽減策を、誰が、何を確かめて終えるのか。

コツ:

- 軽減策を「注意する」「確認する」で止めず、実施者と完了の判定（差分 0 件など）まで聞く。
- 計画書・台帳の名前は、根拠資料で実在を確かめたものだけを書く。確かめられないときは「後続の品質確認」のように、確認済みの仕組みで言う。

### 4.6. 決定と見直し

問い:

- 現時点の採否を、決定 ID ごとに 1 文で言えるか。
- どの期間・測定値・依存の変化で、比較をやり直すのか。

コツ:

- 再評価トリガーを「特定製品が出たら採用」にしやすい。候補カテゴリ単位の条件に言い換える。
- AI Agent は比較分析の支援に留め、最終判断者の欄に入れない。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 各評価軸が、どの課題 ID・制約に結び付くかを確かめ、結び付かない軸を外す。
2. 各案の判定が、どの軸の評価から導かれるかを確かめ、軸に現れない採択理由を見つける。
3. 軽減策ごとに、どのリスクを抑えるかと完了の判定を確かめる。
4. 再評価トリガーごとに、どの判定を覆すかを確かめる。
5. 詳細設計・製品仕様を書きすぎた箇所を、後続成果物への参照に戻す。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                      | 悪い例                                                   |
| ------------ | ----------------------------------------------------------- | -------------------------------------------------------- |
| 代替案       | 紙運用改善、既存サービス、個別構築を解決案として比較する    | 画面、データ、開発ツールを別案として並べ、すべて採択する |
| 比較レイヤー | 購入 / 構築を先に判断し、必要な場合だけ製品を比較する       | 販売管理方式と開発タスク管理ツールを同じ表で採点する     |
| 軸の省略     | 「リスクは業務適合へ統合し、通信断時の記録保持で判定する」  | 「リスクは別章に書いたので評価しない」                   |
| 試行         | 同じ販売・つけ記録を 2 候補で試し、操作時間と記録漏れを測る | 導入してから使いやすそうか判断する                       |
| 見直し条件   | 2 週間の試行で記録漏れが許容値を超えたら採択案を見直す      | 必要なら見直す                                           |

## 7. レビュー観点

| 観点         | 確認内容                                                                       |
| ------------ | ------------------------------------------------------------------------------ |
| 課題との対応 | 比較目的と評価軸が、課題と解決アプローチ・スコープの課題・範囲と食い違わないか |
| 候補の公平さ | 前段文書の案の再掲に留まらず、カテゴリごとに有力な外部案を調べているか         |
| 判定の再現性 | 第三者が同じ判定境界で同じ判定にたどり着けるか                                 |
| 正本と可逆性 | 製品・サービスを採る場合、データの正本と撤退方法が読み取れるか                 |
| 委譲の境界   | 詳細設計・製品仕様を後続成果物へ委ね、採否を左右する差異だけを残しているか     |

## 8. 仕上げチェック

- 各案の判定が評価軸の評価から導かれ、各評価軸が課題 ID・制約にたどれる。
- 省いた・統合した評価軸に、理由または統合先と判定条件が書かれている。
- 未確認の値を、確認済みの高評価にしていない。
- AI Agent を最終判断者にしていない。
- 個人名・個人の連絡先・公開できない組織情報がなく、役割名・集団名で書かれている。
