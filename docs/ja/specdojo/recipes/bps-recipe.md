# 業務プロセス仕様 作成レシピ

Business Process Specification Writing Recipe

共通の起点から一つの業務成果へ至る流れを、業務担当者が合意でき、設計者とテスト担当者が後続作業に使える内容に仕上げるための作り方を示す。

## 1. このレシピの使い方

- BPS は、CDFD のプロセス領域が担う業務目的（Why）を引き継ぎ、起点と確定する業務成果（What）を定め、担当・処理・例外対応（How）を決める。トリガー ID・ステップ ID・例外 ID と CDFD プロセス ID・参照仕様 ID で対応をたどれるようにする（Trace）。

## 2. 作成前に集める情報

| 項目         | 集める情報                                                   | 取り出し元                     |
| ------------ | ------------------------------------------------------------ | ------------------------------ |
| 領域と流れ   | プロセス領域、個別プロセス ID、主要入出力、データストア名    | CDFD                           |
| 前後の境界   | 前後のプロセスと、領域をまたぐ順序・引き渡し                 | ユースケース別 CDFD            |
| 起点と判断   | 始まる出来事、開始前に確かめること、判断する人、迷うケース   | 業務担当者への聞き取り         |
| 参照する定義 | 判断に使うルール、発行・受領するイベント、状態、データの意味 | BR、BES、STSD、データ仕様      |
| 成果と受け手 | 確定する記録・通知と、それを使う人・後続処理                 | 業務担当者、後続プロセスの担当 |
| 止まる場面   | 成果を確定できない・後続へ渡せない場面と、その後の扱い       | 業務担当者への聞き取り         |

## 3. 全体の作成手順

1. CDFD から起点と業務成果の組を挙げ、独立して変わる組が複数あれば文書を分ける。分けると決めた時点で、業務成果を表す名前を付ける。後で分けると ID と参照を付け替えることになる。
2. 出力（業務成果）を先に書く。終わりが決まらないと、処理の範囲と例外の線引きが決まらない。
3. トリガーと前提条件を書き、不成立のときの行き先を決める。
4. 処理を正常な順に並べ、各ステップに入力・出力・完了条件を付ける。入力の表は処理が使うものから作る。
5. 例外・代替経路を書く。処理を並べた後でないと、検出するステップと再開位置が決まらない。
6. 検証・受入観点を、出力と例外の各経路から作る。
7. 最後に導入文と概要を書く。成果と境界が決まってから書くと、本文の言い直しにならない。

## 4. 各章の書き方

### 4.1. 導入文と概要

問い:

- 何が起きたら始まり、何が確定したら終わるか。
- 前後のどのプロセスから先を扱わないか。

コツ:

- 「在庫管理を行う」のように書けてしまうなら、起点と成果が複数混ざっている。
- 業務目的は CDFD を正本とし、写さず参照に置き換える。

### 4.2. トリガーと前提条件

問い:

- 始まった時点を、どの記録または誰の確認から特定できるか。
- 始める前に何を確かめ、成り立たないときは起動しない・差し戻す・例外のどれにするか。

コツ:

- 業務担当者に「始めたつもりで、実は始めなかった場面」を聞くと、正常な非起動と例外が分かれる。
- 処理の途中で初めて分かる事象は前提条件に入れやすい。該当ステップと例外へ回す。

### 4.3. 入力と処理

問い:

- 各ステップの完了を、誰が何を見て判断するか。
- 分岐した後、どこへ合流し、どこで終わるか。

コツ:

- 担当が 2 人出てきたら、承認や引き渡しでステップを分ける。
- 画面やシステムの操作を話されたら「それで何が決まるか」を聞き、業務の判断へ戻す。
- ルールの式やデータの意味を書き始めたら、参照仕様の ID と、この流れで使う結果だけに戻す。

### 4.4. 出力

問い:

- 正常終了と条件付き終了で、それぞれ何が確定するか。
- 誰が受け取り、次にどの処理が始まるか。

コツ:

- 「処理完了」と書きたくなったら、何の記録が残るかを聞く。
- 後続処理がない成果は「なし」と書く。空けると暗黙の連鎖に読まれる。

### 4.5. 例外・代替経路

問い:

- 業務成果または後続処理を変える事象は何か。
- 何を確定させずに止め、何がそろえばどこから再開するか。

コツ:

- 業務担当者に「確定できずに困った場面」を聞く。内部エラーやログの一覧から作らない。
- 例外が見つからないこともある。その場合は、正常系・条件付き処理・入力不足・出力確定失敗を確かめた範囲と、成果を変える例外がないという結論を書く。例外を作り出さない。

### 4.6. 検証・受入観点

問い:

- 正常系と条件付き処理、主要例外がある場合はその経路で、何を入れたら何が確定するか。
- その結果を、どの記録で確かめられるか。

コツ:

- 出力の各成果と例外の各行から 1 行ずつ作ると、確かめ漏れが出にくい。
- 主要例外がない BPS では、例外の経路の代わりに、例外がないと結論した範囲を確かめる行を置く。

### 4.7. 未決事項

問い:

- 決まらないと、どのステップの開始や成果の確定が止まるか。
- 決まるまで、どう扱うか。

コツ:

- 本文に未確定の目印を置いた箇所から論点を拾うと、漏れが出にくい。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 業務成果から逆向きに、その成果を確定するステップ・判断・入力をたどり、どの成果にも効かないステップを外す。
2. トリガーから順に、各ステップの出力が次の入力になるかをたどり、途切れる箇所を探す。
3. 分岐条件を一つずつ反転し、合流・終了・例外・非起動のどこにも届かない経路を探す。
4. CDFD のプロセス ID・入出力・データストア名と照らし、BPS だけで足した・消した・名前を変えた要素を探す。

## 6. 良い例 / 悪い例

| 観点     | 良い例                                                               | 悪い例                               |
| -------- | -------------------------------------------------------------------- | ------------------------------------ |
| 文書境界 | 在庫基準割れの検出から補充依頼の確定までを扱う                       | 在庫管理と仕入と販売をすべて扱う     |
| トリガー | 現在庫が補充基準を下回ったと在庫確認で判定された                     | 補充が必要になった                   |
| 前提条件 | 商品が販売中でない場合は補充不要として記録し、処理を開始しない       | 商品を確認して問題がなければ開始する |
| 処理     | 店主代表が判断根拠を確認し、商品と数量を持つ補充依頼を承認する       | 登録ボタンを押して API を呼ぶ        |
| 主要例外 | 補充基準を取得できない場合は依頼を確定せず、補完後に判定から再開する | エラー時は適切に再試行する           |
| 受入観点 | 未完了依頼がある場合は新規依頼を作らず、重複確認記録を確認できる     | 重複が正しく処理される               |

## 7. レビュー観点

| 観点         | 確認内容                                                                 |
| ------------ | ------------------------------------------------------------------------ |
| 業務目的     | 起点から業務成果までが一つの価値に対応し、扱わない範囲を説明できるか     |
| 開始の判定   | 業務担当者が、記録を見て始めるかどうかを判定できるか                     |
| 責任と完了   | 各ステップで、誰が何を見て完了と判断するかが分かるか                     |
| 例外の線引き | 業務判断を要する事象だけを扱い、例外がない場合はその結論の範囲が分かるか |
| 受入の判定   | テスト担当者が、画面や実装を仮定せずに受入シナリオを作れるか             |

## 8. 仕上げチェック

- 導入文の起点・業務成果と、トリガー・出力の内容が一致している。
- トリガーから業務成果または代替成果まで、どの分岐でも途切れない。
- 出力の各成果と、主要例外がある場合は各例外が、受入観点のいずれかの行で確かめられる。主要例外がない場合は、確かめた範囲と結論がある。
- ファイル名・Frontmatter の `id`・`type`・`rulebook` が rulebook の「ファイル命名・ID規則」と「推奨 Frontmatter 項目」に一致し、`npm run lint:md` と `npm run lint:fm` が通る。
- 個人情報、秘密情報、非公開の組織情報を含めていない。
