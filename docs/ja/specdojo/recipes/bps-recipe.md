# 業務プロセス仕様 作成レシピ

Business Process Specification Writing Recipe

一つのプロセス領域に属し、共通の起点から一つの業務成果へ至る流れを、業務担当者が合意でき、設計者とテスト担当者が後続作業へ利用できる粒度へ具体化する手順です。

## 1. このレシピの使い方

- 最初に CDFD から対象領域、個別プロセス、主要な入出力、データストアを抜き出し、一つの起点と業務成果に流れを限定します。
- 次に、業務担当者への聞き取りからトリガー、前提条件、担当、判断、例外を集め、開始から終了までを処理ステップとして並べます。
- その後、各ステップの入力、出力、完了条件を補い、BR、BES、STSD、データ定義へ委ねる情報を分離します。
- 最後に、正常系、条件付き処理、主要例外を業務成果と確認記録までたどり、第三者が受入可否を判定できるかを確認します。

この成果物は、プロセス領域が担う業務目的を Why、開始条件と確定する業務成果を What、担当・処理・例外対応を How、トリガー ID・ステップ ID・例外 ID・参照先の対応を Trace として整理します。判断式、イベント契約、状態定義、データ項目定義は複製せず、利用箇所から参照します。

## 2. 作成前に集める情報

| 項目       | 集める情報                                                                                  |
| ---------- | ------------------------------------------------------------------------------------------- |
| 対象領域   | CDFD のプロセス領域 ID・名称・業務目的・主担当・起点イベント                                |
| 対象の流れ | 共通の起点から一つの業務成果へ至る個別プロセスと、その開始・終了                            |
| 利用者     | 流れを実施・承認する役割と、成果を設計・テスト・後続業務へ利用する役割                      |
| トリガー   | 発生時点を観測できる出来事、発生元、受領情報、開始条件                                      |
| 前提条件   | 開始前に yes / no で確認する業務条件と、不成立時の扱い                                      |
| 入力と正本 | 業務上の入力名、入手元、利用目的、必須性、正本                                              |
| 処理と責任 | CDFD の個別プロセス、各活動・判断の担当、順序、分岐、完了条件                               |
| 業務成果   | 確定する記録、状態変化、通知、判断結果、受け手、後続処理                                    |
| 参照仕様   | 判断を定める BR、イベントを定める BES、状態を定める STSD、項目の意味を定めるデータ仕様の ID |
| 主要例外   | 正常な成果または後続起動を妨げる事象、停止範囲、処置、再開条件、代替成果                    |
| 受入根拠   | 正常・条件付き・例外の各経路で結果を確認できる記録                                          |
| 未決事項   | 調査不足、意思決定待ち、仮置き前提と、その影響・決定者・決定時期                            |

## 3. 全体の作成手順

1. CDFD から一つのプロセス領域を選び、領域 ID、名称、個別プロセス、主要入出力、データストアを控えます。
2. 起点と業務成果の組を列挙し、独立して変更・承認される組が複数あれば文書を分けます。
3. 選んだ流れについて、業務目的、対象者、主担当、開始点、終了点、対象外を定めます。
4. 開始を観測できる出来事をトリガーとして記載し、発生元、受領情報、開始条件、不成立時の扱いを対応させます。
5. 開始前に確認する前提条件を yes / no で書き、不成立時に非起動、差戻し、例外のどれに進むかを決めます。
6. 流れで使用する入力を業務上の論理名で整理し、入手元、利用目的、必須性、正本を特定します。
7. 正常な順序に沿って処理ステップを並べ、各行に CDFD プロセス、担当、入力、活動または判断、出力、完了条件を記載します。
8. 判断式、イベント契約、状態定義、データ項目定義を参照先へ移し、この流れでの利用目的と結果だけを残します。
9. 分岐ごとに合流先または終了先を確認し、正常終了と条件付き終了の業務成果を受け手、確定条件、正本、後続処理とともに整理します。
10. 業務成果または後続起動を変える主要例外を選び、検出条件、停止範囲、担当、処置、再開条件または代替成果を記載します。
11. 正常系、条件付き処理、主要例外ごとに、入力条件、期待する業務成果、確認可能な記録を対応させます。
12. トリガー ID、ステップ ID、例外 ID、プロセス ID、参照仕様 ID を照合し、開始から終了までの欠落、名称ゆれ、責任の空白を解消します。

## 4. 各章の書き方

### 4.1. 導入文と概要

問い:

- 何が起きたら始まり、誰または何を対象にし、何が確定したら終わりますか。
- この流れが必要な理由と、扱わない場合に損なわれる業務価値は何ですか。
- 対象は CDFD の一つのプロセス領域に収まっていますか。
- 主担当、実施者、成果を利用する役割を区別できますか。
- 前後のプロセス、横断順序、実装方式のどこから先を対象外にしますか。

導入文は起点、対象、業務成果を一文で結びます。概要では目的と境界を固定し、「在庫管理を行う」のように複数の起点と成果を含む広い表現を避けます。

### 4.2. トリガー

問い:

- 出来事の発生時点を、記録または人の確認から特定できますか。
- 発生元と受領情報から、開始対象を一意に特定できますか。
- 開始条件を yes / no で判定できますか。
- 条件不成立は正常な非起動、差戻し、主要例外のどれですか。
- 複数トリガーは同じ業務成果へ収束しますか。

「在庫が少ないとき」のような状態だけでなく、「在庫確認で現在庫が補充基準を下回ったと判定された」のように観測できる出来事として書きます。成果が異なるトリガーは同じ表へ追加せず、流れを分けます。

### 4.3. 前提条件

問い:

- トリガー発生後、処理を始める前に確認すべき販売状態、権限、正本、重複の有無は何ですか。
- 条件の真偽を確認する情報源はありますか。
- 不成立時に処理を開始しないのか、差し戻すのか、例外へ進むのかが明確ですか。
- 前提条件と最初の処理ステップで同じ判断を二重に定義していませんか。

条件と不成立時の扱いを一組で記述します。処理中に初めて判明する事象は、前提条件ではなく該当ステップと主要例外へ置きます。

### 4.4. 入力

問い:

- 各入力はどのステップの判断または活動に使われますか。
- 入手元と正本を区別でき、同じ論理名を CDFD と関連仕様で使っていますか。
- 必須入力が欠けた場合の非起動または例外を特定できますか。
- 物理テーブル、画面項目、API 項目ではなく業務上の情報として記述していますか。

参照仕様の定義を写さず、BPS ではその入力をいつ、何のために利用するかを示します。条件付き入力には利用条件と欠落時の扱いを添えます。

### 4.5. 処理

問い:

- 各ステップは一人または一つの責任主体が完了を判断できる単位ですか。
- CDFD のどの個別プロセスを具体化しているかを示せますか。
- 入力から活動または判断を経て、次へ渡す出力と完了条件へつながりますか。
- 分岐条件と、分岐後の合流先または終了先をたどれますか。
- BR を参照する判断では、ルール ID と判断結果だけを残していますか。

画面操作やシステム内部の呼び出し順ではなく、業務上の活動と判断を書きます。複数主体の承認や引き渡しは別ステップとし、完了条件は記録や成果から yes / no で判定できる文にします。

### 4.6. 出力

問い:

- 正常終了と条件付き終了で確定する業務成果をすべて挙げていますか。
- 受け手は誰で、何がそろえば確定と判断できますか。
- 成果の正本と、起動する後続処理を特定できますか。
- 状態変化またはイベント発行を参照仕様へ接続し、定義を複製していませんか。

「処理完了」ではなく、確定する記録、状態変化、通知、判断結果、または引き渡しを名詞で示します。後続処理がない場合も「なし」と明記し、暗黙の連鎖を残しません。

### 4.7. 例外・代替経路

問い:

- その事象は正常な非起動ではなく、業務成果または後続処理を変えますか。
- どのステップで、どの条件から検出できますか。
- 何を確定または起動してはならないかを停止範囲として示せますか。
- 誰が何を処置し、どの事実がそろえばどこから再開できますか。
- 再開しない場合に確定する代替成果を示せますか。

内部エラーやログを網羅せず、業務判断を要する主要例外へ絞ります。例外がない場合は、確認した正常系、条件付き処理、入力不足、出力確定失敗の範囲と、業務成果を変える例外がないという結論を記述します。

### 4.8. 検証・受入観点

問い:

- 正常系、条件付き処理、主要例外を少なくとも一つずつ確認できますか。
- 入力条件と期待する業務成果の組から、結果を一意に判定できますか。
- 確認可能な記録は、出力の正本または例外時の保留・差戻し記録と一致しますか。
- 後続のテスト担当者が、画面や実装方式を仮定せず受入シナリオを設計できますか。

「正しく処理される」ではなく、件数、確定項目、非作成、保留内容など観測できる結果を書きます。テスト手順や操作列ではなく、受け入れられる業務成果を定義します。

### 4.9. 未決事項（任意）

- 調査で確定できる不足情報は _TODO_:、意思決定待ちは _UNDECIDED_:、仮置き前提は _ASSUMPTION_: とします。
- 論点ごとに影響する章またはステップ、区分、決定者、決定時期を記載します。
- 未決事項がない場合は章を省略し、空表や「なし」だけの章を残しません。

## 5. 深掘り手順

1. 終了点の業務成果から逆向きにたどり、その成果を確定する最後のステップ、必要な判断、入力を確認します。
2. トリガーから順方向にたどり、各ステップの出力が次のステップの入力になるかを確認します。
3. 各ステップで担当を外した場合に完了判断が曖昧にならないかを確認し、責任主体が複数ならステップを分けます。
4. 分岐条件を一つずつ反転し、合流、正常終了、例外、非起動のいずれにも到達しない経路を探します。
5. BR、BES、STSD、データ仕様と同じ定義文を探し、参照 ID と利用目的へ置き換えます。
6. 主要例外ごとに、検出前に確定した記録、停止する後続、再開位置、代替成果を順に確認します。
7. 正常系、条件付き処理、主要例外の各経路について、入力条件から確認可能な記録までを一行で説明できるか確認します。
8. CDFD のプロセス ID、入出力、データストア名と照合し、BPS だけで追加・削除・改名した要素を解消します。

## 6. 良い例 / 悪い例

| 観点       | 良い例                                                               | 悪い例                               |
| ---------- | -------------------------------------------------------------------- | ------------------------------------ |
| 文書境界   | 在庫基準割れの検出から補充依頼の確定までを扱う                       | 在庫管理と仕入と販売をすべて扱う     |
| トリガー   | 現在庫が補充基準を下回ったと在庫確認で判定された                     | 補充が必要になった                   |
| 前提条件   | 商品が販売中でない場合は補充不要として記録し、処理を開始しない       | 商品を確認して問題がなければ開始する |
| 入力       | 現在庫を在庫記録から取得し、補充要否の判断に使う                     | 在庫テーブルの数量列を読む           |
| 処理       | 店主代表が判断根拠を確認し、商品と数量を持つ補充依頼を承認する       | 登録ボタンを押して API を呼ぶ        |
| 完了条件   | 商品、数量、判断根拠、承認者、承認時刻を持つ補充依頼が確定している   | 問題なく完了している                 |
| 主要例外   | 補充基準を取得できない場合は依頼を確定せず、補完後に判定から再開する | エラー時は適切に再試行する           |
| 受入観点   | 未完了依頼がある場合は新規依頼を作らず、重複確認記録を確認できる     | 重複が正しく処理される               |
| 参照の境界 | `br-reorder-point` の判定結果を使い、計算式は参照先を正本とする      | 発注点の計算式を本文へ再掲する       |

## 7. レビュー観点

| 観点       | 確認内容                                                                                 | 主な確認者                 |
| ---------- | ---------------------------------------------------------------------------------------- | -------------------------- |
| 業務目的   | 起点から業務成果までが一つの価値と責任境界を持ち、対象外を説明できる                     | 店主代表、業務分析担当     |
| CDFD 整合  | プロセス領域、プロセス ID、主要入出力、データストア名が CDFD と矛盾しない                | 業務分析担当               |
| 開始条件   | トリガーと前提条件を記録から yes / no で判定でき、不成立時の扱いが明確である             | 店主代表、品質確認担当     |
| 責任と完了 | 各ステップに一つの責任主体、入力、活動または判断、出力、判定可能な完了条件がある         | 業務分析担当               |
| 正本の分離 | 判断、イベント、状態、データ定義を複製せず、参照 ID とこの流れでの利用目的からたどれる   | アーキテクト、業務分析担当 |
| 例外       | 主要例外の検出条件、停止範囲、担当、処置、再開条件または代替成果を説明できる             | 品質確認担当、店主代表     |
| 検証可能性 | 正常・条件付き・例外の入力条件、期待成果、確認記録から受入可否を第三者が判定できる       | 品質確認担当               |
| 実装非依存 | 画面操作、物理データ構造、詳細 API、クラス、内部エラーを業務プロセスとして記述していない | アーキテクト               |

「業務分析担当」「品質確認担当」「アーキテクト」は、対象プロジェクトのロール定義または責任分担文書で正式な担当へ対応付けます。

## 8. 仕上げチェック

- 一文書が一つのプロセス領域に属し、共通の起点と一つの業務成果を持つ流れだけを扱っている。
- 導入文から起点、対象、業務成果を一文で説明できる。
- 業務目的、対象者、主担当、開始点、終了点、対象外があり、前後のプロセスと横断順序の境界を説明できる。
- 各トリガーに発生元、受領情報、開始条件、不成立時の扱いがある。
- 前提条件が yes / no で判定でき、不成立時の非起動、差戻し、例外を特定できる。
- 各入力に入手元、利用目的、必須性、正本があり、欠落時の扱いをたどれる。
- 全処理ステップに CDFD プロセス、担当、入力、活動または判断、出力、完了条件、例外の対応がある。
- 分岐から合流先または終了先をたどれ、正常終了と条件付き終了の業務成果が出力にある。
- BR、BES、STSD、データ仕様を正本として参照し、その定義を複製していない。
- 主要例外に検出条件、停止範囲、担当、処置、再開条件または代替成果がある。
- 正常系、条件付き処理、主要例外の受入観点に、入力条件、期待する業務成果、確認可能な記録がある。
- CDFD とプロセス ID、主要入出力、データストア名が一致し、BPS だけの追加・削除・改名がない。
- 画面操作、SQL、物理カラム、詳細 API、クラス、ログ文言を業務仕様へ持ち込んでいない。
- _TODO_ が残っていない。未決事項がある場合は区分、影響、決定者、決定時期がある。
- 個人情報、秘密情報、非公開の組織情報など、公開範囲に不適切な内容を含めていない。
