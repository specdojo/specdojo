# C4コンテナ図 作成レシピ

C4 Container Diagram Writing Recipe

利用者が必要とする結果から、実行単位・ストア・連携経路を選ぶ作り方を示す。

## 1. このレシピの使い方

- コンテナ図は、上位のコンテキスト図の利用目的と外部への委譲を引き継ぎ（Why）、それを担う実行単位・ストア・関係を定め（What）、配置の前提と結合で観測する結果までを扱う（How）。要素名と関係 ID で、図・定義・検証観点・仮定をたどれるようにする（Trace）。

## 2. 作成前に集める情報

| 項目           | 集める情報                                                   | 取り出し元                           |
| -------------- | ------------------------------------------------------------ | ------------------------------------ |
| 利用目的と境界 | 誰が何を達成するか、対象に含める責務と外へ委ねる処理         | 上位のコンテキスト図                 |
| 実行単位の候補 | 別に起動・配備するアプリと、別にする理由                     | 開発者への確認、起動・配備の手順     |
| 記録と生成物   | 正本、更新する主体、読む主体と時点                           | 開発者への確認、リポジトリの構成     |
| 外部依存       | 常時必要か特定の操作時だけか、同じ端末にある別ツール         | 上位のコンテキスト図、開発者への確認 |
| 配置の前提     | ローカル・リモート、構築時・閲覧時の区別と、根拠のない配置案 | 運用担当への確認                     |
| 詳細の正本     | 連携契約、データ構造、内部構成、インフラを扱う文書           | 文書の一覧                           |

## 3. 全体の作成手順

1. 概要に、分解する対象と分割の目的を先に書く。目的がないと、分割を止める所が決まらない。
2. 要素と境界の定義で、実行単位の候補ごとに別に起動・配備する理由を付ける。理由が機能名だけなら元のアプリへ戻す。
3. ストアを正本と生成物に分け、更新する主体と読む主体を書く。
4. 利用者の操作から保存・外部への依頼・結果の確認までをたどって関係を書き、上位図の利用目的・外部依存ごとに担当するコンテナか描かない理由を決める。
5. 定義と関係が決まってから C4コンテナ図を描く。図から書くと、根拠のない線が残りやすい。
6. 技術前提・制約と検証観点では、経路ごとの正常な結果を先に決め、その後で読取不能・外部停止・応答欠落で区別する状態を書く。
7. 根拠の足りない配置・経路をメモ / 将来課題へ移す。

## 4. 各章の書き方

### 4.1. 概要

問い:

- 上位図のどのシステムを分解し、どの利用場面で配置や接続の何を判断するための図か。
- サイトなどの派生した提供経路を含める場合、上位図との範囲の違いは何か。

コツ:

- 上位図の目的や利用者の説明は写さず、上位図への参照に置き換える。
- 目的を判断したいことに絞ると、分割を止める基準になる。

### 4.2. C4コンテナ図（Mermaid）

問い:

- 読み手は線から、依頼・参照の向きと、その線が成立する時点を説明できるか。
- 上位図の各利用目的・外部依存から経路をたどれるか。

コツ:

- ラベルを縮めると「構築時」「印刷時だけ」などの条件が落ちやすい。
- 方式が分からない接続は線で補わず、メモ / 将来課題へ移す。

### 4.3. 要素と境界の定義

問い:

- 各コンテナの責務は、誰のどの結果につながるか。
- ストアは正本か生成物か。直接更新するのは誰か。

コツ:

- 同じ端末にある外部ツールは、同じアプリにまとめやすい。管理する主体と、止まったときの影響を聞いて分ける。
- ファイルの保存場所、版管理の仕組み、共有サービスを聞き分け、更新する主体が複数なら排他制御の有無を開発者に聞く。

### 4.4. 技術前提・制約と検証観点

問い:

- 経路が正常に成立したとき、入力に対してどの保存内容・生成物・返却結果を照合できるか。
- 接続を止めたとき、失われる結果と残る記録は何か。

コツ:

- 書込先・外部の実行環境・閲覧先は、配置を設計する人に「何が未定だと困るか」を聞いて集める。
- 実行の成功と人の承認を同じ結果として書きやすい。分けて観測する対象を決める。

### 4.5. メモ / 将来課題

問い:

- 未確認の技術名・接続方式・配備先はどれで、そのために配置や結合確認の何が決められないか。
- 何が確かめられれば仮定を更新でき、それまでの当面の扱いは何か。

コツ:

- 解消条件は「配信先が公開範囲を満たすことを確かめる」のように、何が確かめられれば解消するかの形で聞く。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 一つの利用結果から逆にたどり、対応する結果のないコンテナ候補を外す。
2. 各関係を「いつ」「誰が起動し」「何を渡すか」で読み直し、上位図から取り残した経路を探す。
3. 正本の更新から閲覧・共有までをたどり、正常な結果を照合する記録と、障害の影響が止まる境界を確かめる。根拠へ戻れない期待結果はメモ / 将来課題へ移す。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                         | 悪い例                                         |
| ------------ | -------------------------------------------------------------- | ---------------------------------------------- |
| 分割の目的   | 「販売の入力、記録、印字の配備単位を示す」                     | 「業務に必要なすべての構成」                   |
| 分割の理由   | 画面はブラウザで動き、処理サービスはサーバーで動く             | 登録・検索・削除をそれぞれコンテナにする       |
| ストア       | 文書の正本はファイル群、閲覧用 HTML は生成物とする             | すべてを「DB」とし、更新元と派生物を区別しない |
| 関係のラベル | 「公開文書の参照（構築時）」                                   | 「データ連携」                                 |
| 外部依存     | 印刷時だけ印刷基盤へ依頼する                                   | 印刷基盤の停止で全参照も止まると断定する       |
| 検証観点     | 控えと紙面の一致と、印字失敗時に残る販売の記録を分けて確かめる | 「結合テストをする」                           |
| 未確定の配置 | ローカル構築を仮定し、配信先の確認を解消条件として残す         | 候補のホストを既存構成のように描く             |

## 7. レビュー観点

| 観点         | 確認内容                                                 |
| ------------ | -------------------------------------------------------- |
| 価値と範囲   | 利用者が得る結果が、分割後も上位図の境界からはみ出ないか |
| 配置への入力 | 実行単位、保持単位、必要な接続と仮定を分けて読み取れるか |
| 結合への入力 | 主要な経路と外部の失敗で観測する対象を関係 ID で追えるか |
| 詳細との分担 | 構文・データ構造・物理配置を書かず、更新先が分かるか     |

## 8. 仕上げチェック

- 各コンテナが一つ以上の利用結果につながっている。
- 正本、構築時の入力、閲覧用の生成物が区別され、関係が成立する時点が図と定義で食い違っていない。
- 仮定と確定事項が分かれ、各仮定に当面の扱いと解消条件がある。
