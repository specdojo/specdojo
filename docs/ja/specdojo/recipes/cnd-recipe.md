# C4コンテナ図 作成レシピ

C4 Container Diagram Writing Recipe

利用者が必要とする結果から、実行・配備単位、記録の保管単位、連携経路を選ぶ手順です。機能一覧を図に変換するだけで終わらせず、配置設計と結合検証へ渡せる境界を作ります。

## 1. このレシピの使い方

- 上位のコンテキスト図から対象システムの目的と外部への委譲を引き継ぎ、内部のどの実行単位がその責務を担うかを書き出します。
- 実行単位ごとの入出力と記録先をつなぎ、配置上の前提までを扱います。内部のクラス、API 構文、ホスト構築手順は詳細設計へ渡します。
- 要素名と関係 ID を手掛かりに、図、定義、制約、未確定事項を対応させます。仮定は根拠のある仕様と分け、確認先を付けます。

## 2. 作成前に集める情報

| 入力           | 集める情報・問い                                                               |
| -------------- | ------------------------------------------------------------------------------ |
| 利用目的・境界 | 誰が何を達成するか。上位図が対象に含める責務と外へ委ねる処理は何か             |
| 実行単位候補   | 別に起動・配備するアプリは何か。一つのアプリ内の機能を別単位と誤認していないか |
| 記録と生成物   | どれが正本か。誰が更新し、誰がどの時点で読むか                                 |
| 外部依存       | 常時必要か、特定の操作時だけか。同じ端末にある別ツールも含めたか               |
| 配置前提       | ローカル・リモート、構築時・閲覧時を区別できるか。根拠のない配置案はどこか     |
| 詳細の更新先   | 連携契約、データ構造、内部構成、インフラをどの文書へ渡すか                     |

## 3. 全体の作成手順

1. 「概要」に上位図の対象、分割の目的、本図の対象外を書きます。新たな提供経路を加える場合は中核責務との関係も説明します。
2. 「要素と境界の定義」に実行単位候補を並べ、個別に起動・配備する理由を一言ずつ付けます。理由が機能名だけなら元のアプリへ戻します。
3. 正本・生成物・共有先を区別し、保持する情報と直接アクセスする主体を整理します。ファイルを保存する場所と版管理ツールを分けます。
4. 利用者の操作から保存・外部依頼・結果確認までをたどり、関係表を作ります。起点、終点、目的、方式、成立する時点を書きます。
5. 「C4コンテナ図（Mermaid）」へ要素と関係を描きます。短いラベルにしても構築時だけの接続や任意依存の条件が残るか確かめます。
6. 「技術前提・制約と検証観点」に配置設計の前提と結合対象を置きます。成功だけでなく、読取不能・外部停止・応答欠落で何を確認するかを関係 ID に結びます。
7. 根拠不足の配置・経路は「メモ / 将来課題」へ移し、影響、担当、解消条件、引き継ぎ先を付けます。

## 4. 各章の書き方

### 4.1. 概要

- 上位図のどのシステムを分解しますか。
- 分割により、配置や接続について誰が何を判断できますか。
- サイトなどの派生した提供経路を含める場合、上位図との範囲の違いを説明できますか。

「販売の入力、記録、印字の配備単位を示す」のように目的を絞ります。「業務に必要なすべての構成」では分割を止める基準がありません。

### 4.2. C4コンテナ図（Mermaid）

- 各アプリは別に実行・配備されますか。内部処理を別コンテナにしていませんか。
- 読み手は線から依頼・参照の向きと情報の意味を説明できますか。
- 構築時の読取を、閲覧中のネットワーク接続と誤解しませんか。

「公開文書の参照（構築時）」までラベルに残します。「データ連携」だけでは、必要なネットワークと実行時点を選べません。

### 4.3. 要素と境界の定義

- 境界、Person、Container、Data Store、External Software System、Relationship の順に、図だけで決まらない条件を掘り下げます。
- コンテナの責務は誰の結果につながりますか。入力を受ける単位と、永続記録を持つ単位を説明できますか。
- ストアは正本ですか、生成物ですか。更新者は一人だけですか、複数ですか。不明な排他制御を保証していませんか。
- 同一端末にある外部ツールの管理主体と失敗影響は区別できますか。

「販売処理は取引を記録し、印刷基盤は紙面への出力を担う」と責務を分けます。「同じ端末なので一つのアプリ」では境界の判断材料が不足します。

### 4.4. 技術前提・制約と検証観点

- 配置設計者が必要とする、書込先、外部実行環境、閲覧先は識別できますか。
- 接続を止めたとき、失われる結果と残る記録を何で観測しますか。
- 実行成功と人間の承認を混同する経路はありませんか。

関係 ID を添えて「印字失敗でも販売の記録と印字結果を別々に確認する」と書きます。未確認の復旧保証や具体的な再試行回数は置きません。

### 4.5. メモ / 将来課題

- 未確認の技術名、接続方式、配備先はどれですか。
- その不確実さで配置・テストの何が決められませんか。
- 誰が何を確認すれば仮定を更新でき、どの詳細文書へ反映しますか。

_ASSUMPTION_: とした配備案には確認条件を付けます。「配備先未定」だけでは、検討を引き継げません。

## 5. 深掘り手順

1. 一つの利用結果から逆にたどり、必要な処理と保持記録を探します。対応する結果のないコンテナ候補を除きます。
2. 各関係を「いつ」「誰が起動」「何を渡す」の三点で読み直します。不明な方式は線を増やして補わず、論点として分けます。
3. 正本の更新から閲覧・共有までをたどり、再生成が必要な箇所と、障害の影響が止まる境界を特定します。

## 6. 良い例 / 悪い例

| 観点       | 良い例                                                   | 悪い例・問題                                                   |
| ---------- | -------------------------------------------------------- | -------------------------------------------------------------- |
| 分割理由   | 画面はブラウザで動き、処理サービスはサーバーで動く       | 登録・検索・削除をそれぞれコンテナにする。機能と実行単位の混同 |
| ストア     | 文書の正本はファイル群、閲覧用 HTML は生成物とする       | すべてを「DB」とし、更新元と派生物を区別しない                 |
| 外部依存   | 印刷時だけ印刷基盤へ依頼する                             | 印刷基盤の停止で全参照も停止すると根拠なく断定する             |
| 未確定配置 | ローカル構築を仮定し、配信先と公開範囲の確認を担当へ渡す | 候補のホストを既存構成のように描く                             |

## 7. レビュー観点

| 観点         | 確認する内容                                         | 主な確認者 |
| ------------ | ---------------------------------------------------- | ---------- |
| 価値・範囲   | 利用者が得る結果と上位図の境界を分割後も保っているか | BA / PO    |
| 配置入力     | 各実行単位、保持単位、必要な接続と仮定を区別できるか | ARC / DEV  |
| 結合入力     | 主要経路と外部失敗の観測対象を関係 ID で追えるか     | QE         |
| 詳細との分担 | 構文・schema・物理配置の更新先が識別できるか         | ARC        |

## 8. 仕上げチェック

- 図と表の要素名・関係ラベルをそろえ、説明を重複させず責務・条件を残しましたか。
- 正本、構築時の入力、閲覧用生成物を区別し、実行時点の違いを説明しましたか。
- 未確認の配置と経路を仮定として分け、影響・担当・解消条件を付けましたか。
- 主要判断と公開可否を、人間が判断する境界として残しましたか。
