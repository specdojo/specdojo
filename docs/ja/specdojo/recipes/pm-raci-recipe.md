# RACI 作成レシピ

RACI Writing Recipe

責任衝突が起きやすい成果物と判断だけを選び、Schedule の担当まで整理する作り方を示す。

## 1. このレシピの使い方

- 責任衝突や判断停滞を防ぐ理由（Why）から対象の成果物・判断（What）を選び、責任配置と担当（How）を決め、行名・Role code・Schedule の `owner` でたどれるようにする（Trace）。

## 2. 作成前に集める情報

| 項目      | 集める情報と取り出し元                                |
| --------- | ----------------------------------------------------- |
| 採用 Role | 列に使う Role code（組織定義）                        |
| 対象      | 主要成果物・公開対象（初期スコープ）                  |
| 判断      | 価値・費用・変更・品質例外・公開の判断者（PM に聞く） |
| 実行      | 明示 `owner`、タスク種別（WBS・Schedule）             |

## 3. 全体の作成手順

1. 対象の成果物と判断を先に選ぶ。カタログから始めると責任が埋もれる。
2. 列の Role を必要な分だけ残す。
3. 成果物別、判断・プロセス別の順に表を作る。承認者が先に決まると、プロセス行の判断を分けやすい。
4. Schedule と照合する。不一致で表を直すため表の後に行う。
5. 見直し条件を書く。

## 4. 各章の書き方

### 4.1. 適用方針

- 問い: どの成果物・判断で責任がぶつかり得るか。外す範囲の理由は何か。
- コツ: PM に「誰の判断を待って作業が止まったか」を聞く。採用 Role の一覧は写さず参照に置き換える。

### 4.2. 成果物別RACI

- 問い: 誰が作成し、どの Role の人間が内容を承認するか。
- コツ: 作業担当が複数なら、分担をその場で聞いて注記する。後から Schedule を見て選ぶと根拠が残らない。

### 4.3. 判断・プロセス別RACI

- 問い: 判断者が異なる判断はどれか。成果物行の承認と重なるとき、それぞれ何を判断するか。
- コツ: 「作成フローの運営」は内容の承認も含むと読まれやすいため、順序・進捗の判断と分ける。

### 4.4. Schedule・実行主体との対応

- 問い: WBS に明示の `owner` はあるか。なければ、どの `R` から担当を展開するか。
- コツ: 担当が一意に決まらなければ、タスクの分割を WBS の担当者に相談する。

### 4.5. 見直し条件

- 問い: 何が変わると見直し、どの行と Schedule が追従するか。
- コツ: 判断が止まった場面を聞くと、契機を具体的に書ける。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 各行が防ぐ責任衝突・判断停滞を確かめ、目的のない行を外す。
2. 各行の `A` が実際の最終判断者かを確かめる。
3. `C`・`I` がどの判断に効くかを確かめ、効かないものを外す。
4. Schedule の各 `owner` がどの行から来たかをたどる。

## 6. 良い例 / 悪い例

| 観点       | 良い例                                        | 悪い例                              |
| ---------- | --------------------------------------------- | ----------------------------------- |
| 判断の行名 | 「初期公開の可否」のように判断を名指す        | 「プロジェクト運営」とだけ書く      |
| 承認タスク | 別タスクにした承認を、その行の `A` と照合する | 承認タスクも作成者の `R` にそろえる |
| AI Agent   | 支援として注記し、`A` は人間の Role に置く    | AI Agent を承認者の列に入れる       |

## 7. レビュー観点

| 観点     | 確認内容                                                      |
| -------- | ------------------------------------------------------------- |
| 判断範囲 | 成果物行とプロセス行で、同じ判断を二つの `A` が持っていないか |

## 8. 仕上げチェック

- 各行の採用理由、`A`・`R`、Schedule の `owner` をたどれる。
- メンバーの割り当てを写していない。
