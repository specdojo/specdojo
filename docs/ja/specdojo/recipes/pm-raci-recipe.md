# RACI 作成レシピ

RACI Writing Recipe

責任衝突が起きやすい主要成果物と主要判断だけを、二つのマトリクスへ整理する作り方です。

## 1. このレシピの使い方

- 初期スコープから主要成果物と主要判断を選びます。
- 成果物別と判断・プロセス別のRACIを作ります。
- Schedule owner、member割り当てとの整合を確認します。
- 責任衝突や判断停滞の回避（Why）、対象となる主要成果物・判断（What）、RACI と owner 方針（How）を扱い、行名・Role code・Schedule owner の対応で追跡します（Trace）。member 割り当ては再掲しません。

## 2. 作成前に集める情報

| 項目      | 集める情報                                                          |
| --------- | ------------------------------------------------------------------- |
| Role code | 採用済みの責任語彙                                                  |
| 成果物    | 初期スコープ、管理計画、公開対象                                    |
| 判断      | 価値、費用・負荷、変更、品質例外、公開                              |
| 実行      | WBS の明示 `owner`、Schedule のタスク種別・action、作業ごとの主担当 |
| 割り当て  | member、兼務、Agent支援の正本                                       |

## 3. 全体の作成手順

1. 責任衝突の可能性がある成果物・判断だけを選びます。
2. 使用するRole code列を必要最小限に絞ります。
3. 各行へ一つの`A`と一つ以上の`R`を置きます。
4. 相談が必要なRoleに`C`、結果共有だけのRoleに`I`を置きます。
5. 複数 `R` の担当範囲を注記し、WBS の明示 `owner` とタスク種別から Schedule の担当を照合します。
6. 不一致時の更新先と見直し条件を定め、生成ビューや通常手順の重複行を削除します。

## 4. 各章の書き方

### 4.1. 適用方針

- どの成果物・判断で業務・技術・品質の責任衝突が起こり得ますか。対象外とする範囲と理由は何ですか。
- 兼務と AI Agent 支援を使っても、人間の最終判断を区別できますか。
- 採用済み Role のうち、どれを列に使い、どれをどの理由で省きますか。記号の意味は共通定義へ委譲します。

### 4.2. 成果物別RACI

- 主要成果物と管理文書を、作成・内容承認の責任が同じ単位でまとめられますか。
- 同じ正本から生成するビューを重ねず、各成果物 ID から行を一意に辿れますか。
- 誰が作成し、どの Role の人間が内容を承認しますか。複数の作業担当なら担当範囲を注記します。

### 4.3. 判断・プロセス別RACI

- 価値・費用・変更・品質例外・公開で、判断者や判断材料が異なるものはどれですか。
- 成果物行の承認とプロセス行の判断が重なる場合、それぞれ何を判断しますか。
- 当事者確認と必要な技術・品質相談を、どの採用 Role を介して受けますか。

### 4.4. Schedule・実行主体との対応

- WBS に明示 `owner` はありますか。あれば引き継ぎを先に確認し、未指定の作成作業は `R` から担当を展開します。複数なら action に最も近い担当を注記で特定し、一意でなければ分割します。`A/R` は作業担当も兼ねます。
- 対象は作成作業ですか、別タスクに分けた承認・レビュー・外部待ちですか。後者では対応する `A` / `C` と照合し、通知だけの `I` を担当にしません。
- WBS・Schedule、実行主体・兼務の正本はどこですか。不一致は責任配置の変更かタスク定義・生成処理の誤りかを調べ、修正先を決めます。

### 4.5. 見直し条件

- スコープ、成果物、採用 Role、判断ゲート、担当・兼務の何が変わると見直しますか。
- 誰が影響する RACI 行、正本、WBS・Schedule の追従担当と期限を整理しますか。
- 未決の担当変更・リスク・課題は、どの管理記録へ Role と転送先を付けて渡しますか。

## 5. 深掘り手順

1. 各行の`A`が本当に最終判断者か確認します。
2. `C`と`I`を必要最小限に減らします。
3. 同じ責任配置の行をグループ化します。
4. 各行が成果物または主要判断に使われるか確認し、目的のない行を削除します。未計画の主要判断は後続タスクへ渡します。

## 6. 良い例 / 悪い例

| 観点 | 良い例                                                             | 悪い例                      |
| ---- | ------------------------------------------------------------------ | --------------------------- |
| 対象 | 主要成果物と公開判断へ絞る                                         | 全カタログ行を転記する      |
| 責任 | 一行に`A`を一つ置く                                                | `A`を複数置く               |
| 実行 | 作成は WBS の明示担当を先に照合し、別の承認タスクは `A` と照合する | 全タスクを `R` に書き換える |

## 7. レビュー観点

| 観点 | 確認内容                                                               |
| ---- | ---------------------------------------------------------------------- |
| 責任 | 各行の `A` と作業ごとの主担当を識別できるか                            |
| 採用 | 列が採用済み Role に対応し、省略理由と専門支援の取り込み先が分かるか   |
| 展開 | WBS の明示担当、作成と承認・レビューの種別から Schedule と照合できるか |
| 範囲 | 業務・技術・品質の主要責任を辿れ、重複する行を増やしていないか         |

## 8. 仕上げチェック

- 成果物別、判断・プロセス別の二表がある。
- 省略範囲と見直し条件が明確である。
- member・Agent割り当てを再掲していない。
- Agentに`A`を割り当てていない。
- 各行の採用理由、`A` / `R`、Schedule owner または判断記録先の対応を追跡できる。
