# ロール定義 作成レシピ

Project Role Definition Writing Recipe

ロール定義を、PO が全 Role code とプロジェクト固有メモを承認・保留・差し戻しできる内容に仕上げるための作り方を示す。

## 1. このレシピの使い方

- ロール定義は、組織定義の採用判断（Why）を引き継ぎ、採用する Role code の集合（What）を転記し、プロジェクト固有の扱い（How）だけを `project_note` に添える。採用根拠は `based_on`、下流の利用は Schedule・RACI・メンバー定義の Role code 参照でたどる（Trace）。
- 「作成前に集める情報」をメモでそろえてから、「全体の作成手順」の順に書く。

## 2. 作成前に集める情報

| 項目                   | 集める情報                                             | 取り出し元                   |
| ---------------------- | ------------------------------------------------------ | ---------------------------- |
| 採用集合               | 採用・未採用の Role code、使用可能な `owner`、採用理由 | 組織定義                     |
| 正式名称               | 各 Role code の正式名称                                | 人と組織の定義標準           |
| 下流の参照値           | 実際に使われている Role code と、その使い手            | Schedule、RACI、メンバー定義 |
| プロジェクト固有の扱い | 強調する責務、専任化を検討する条件、公開判断上の注意   | PO・PM への確認              |
| 識別情報               | `project_id`、名称、版                                 | 配置先プロジェクト           |

## 3. 全体の作成手順

1. 組織定義を読み、採用集合を確かめてから `based_on` へ接続する。採用集合が決まらないと、`roles` の範囲が決まらない。
2. 下流の参照値を洗い出し、採用集合との差分を先に見つける。転記の後で見つけると、どちらを直すかの判断が遅れる。
3. 採用集合を `roles` へ転記し、`code` と正式名称を対応付ける。
4. PO の判断に要る固有の扱いだけを `project_note` に添える。
5. 最後にメタ項目を整える。採用根拠が決まってからだと、`based_on` を未確認の文書で埋めずに済む。

## 4. 各章の書き方

### 4.1. メタ項目と根拠

問い:

- `based_on` の各 ID は、採用集合を実際に確かめた文書か。
- 準拠先を、成果物自身から識別できるか。

コツ:

- 同じディレクトリの文書をまとめて `based_on` に入れたくなったら、採用判断に使った文書だけに絞る。
- 採用理由の本文は組織定義から写さず、ID での参照に置き換える。

### 4.2. `roles`

問い:

- 専任 member がいない Role code を、未採用と取り違えて落としていないか。
- 下流で使われているのに採用集合にない Role code はないか。

コツ:

- 「今いる人」から Role を数えると、兼務中のロールが抜けやすい。PO・PM に「誰もいなくても語彙として要るロールはどれか」と聞く。
- Role code を変えたり除いたりするときは、使っている下流の文書と使い手を先に聞き、責務の移り先を決めてから変える。

### 4.3. `roles[].project_note`

問い:

- PO が承認・保留を決めるのに、このメモがないと何が判断できないか。
- このプロジェクトに固有の扱いか、どのプロジェクトにも当てはまる一般責務か。

コツ:

- 担当者の名前や agent 名を書きたくなったら、メンバー定義へ移す。メモに書くと、割り当ての変更のたびに一覧を直すことになる。
- 「必要に応じて」と書きそうになったら、PO に「何が起きたら専任化を考えるか」を聞き、その条件を書く。
- 決めきれない点は推測で埋めず、判断する人と時期を PO に確かめる。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. `roles` の各 Role code が、組織定義の採用判断のどれに対応するかを確かめ、対応のないコードを外す。
2. 下流の各参照値が `roles` にあるかを確かめ、未定義のコードを見つける。
3. 各 `project_note` が、PO のどの判断に使われるかを確かめ、判断に使われないメモを削る。

## 6. 良い例 / 悪い例

| 観点       | 良い例                                                        | 悪い例                             |
| ---------- | ------------------------------------------------------------- | ---------------------------------- |
| 公開判断   | 公開可否の最終判断は PO に残す                                | agent が公開可否を判断する         |
| 下流の参照 | `roles[].code` を Schedule の `owner` に使う                  | `owner` に member nickname を使う  |
| 準拠先     | 成果物自身に `rulebook` を残す                                | カタログにあるので成果物から省く   |
| 専任化     | 「実装タスクが継続して増えたら DEV の専任化を検討する」と書く | 「必要に応じて体制を見直す」と書く |

## 7. レビュー観点

| 観点       | 確認内容                                                                  |
| ---------- | ------------------------------------------------------------------------- |
| 採用の対応 | 各 Role code が組織定義の採用判断に対応し、未採用のコードが紛れていないか |
| 下流の接続 | Schedule、RACI、メンバー定義が使う値がすべて `roles[].code` にあるか      |
| 委譲の境界 | 一般責務・採用理由・実行主体の割り当てを、各正本へ委ねているか            |

## 8. 仕上げチェック

- 各 Role code の採用根拠を `based_on` から、下流での利用を参照値からたどれる。
- `project_note` に担当者・agent 名・兼務の割り当てがない。
- 公開してよい情報だけで構成され、最終判断が PO に残っている。
