# 組織定義 作成レシピ

Organization Definition Writing Recipe

目的達成に必要な意思決定・実行・確認の分担を、最小体制として設計する作り方です。

## 1. このレシピの使い方

- 目的、関係者、主要判断から必要な責任領域を抽出します。
- 兼務可能な最小組織モデルを定めます。
- 採用判断をロール定義へ渡し、Member 割り当てと成果物別の責任を各正本へ接続します。
- プロジェクトの目的と主要判断（Why）、必要な責任領域と最終判断先（What）、最小組織モデルと owner 方針（How）を扱い、採用判断・正本の対応・見直し条件で追跡します（Trace）。共通の責務説明と Member 割り当ては各正本へ委譲します。

## 2. 作成前に集める情報

| 項目     | 集める情報                                                           |
| -------- | -------------------------------------------------------------------- |
| 規模     | 参加者数、外部関係者、継続運用の有無                                 |
| 判断     | 当事者価値、優先順位、費用・負荷、品質、公開                         |
| 実行     | 仕様化、開発、検証、運用、AI支援                                     |
| 正本     | ロール定義、メンバー定義、RACI、ステークホルダー登録簿               |
| 拡張条件 | 滞留、参加者増加、外部責任、専門性の必要性                           |
| 採用判断 | 標準ロールごとの採用可否、未採用時の代替先、独自ロールを検討する理由 |

## 3. 全体の作成手順

1. 必要な責任領域と最終判断を整理します。
2. 実行・確認を誰が兼務できるか決めます。
3. 人間とAI Agentの境界を明記します。
4. 各標準ロールと独自ロールの採用・未採用、判断理由、未採用時の代替先を整理し、Schedule の `owner` に使える集合を明示します。
5. 情報ごとの正本を一表で示します。
6. 体制を拡張する見直し条件を定めます。

## 4. 各章の書き方

### 4.1. 組織モデル

- 価値判断、実行、品質確認、公開・運用のどの責任領域が目的達成に必要ですか。
- 当事者・利用者の確認を誰が受け止め、内部 Role のどの人間が最終判断しますか。
- 兼務しても作業と判断を分けられますか。具体的な兼務先はメンバー定義で確認します。

### 4.2. ロール・owner方針

- 各標準ロールと独自ロールについて、採用・未採用を何を根拠に選びますか。未採用の責務は誰が代替するか、対象外の理由は何ですか。
- 採用は専任配置と別に判断できていますか。専門支援だけのロールを含め、使用可能な `owner` の集合はどれですか。
- RACI の採用列・省略列と、ロール定義へ転記する採用集合が一致しますか。未採用がなければその旨を残します。

### 4.3. 正本と責任境界

- 共通定義、採用判断、機械可読な採用結果、実行主体、詳細責任の更新先はどこですか。
- 名簿で必要な人間の責任領域をカバーでき、未作成の文書には作成時期または省略理由がありますか。
- 一覧・一般責務を再掲せず、参照先と本書で扱う判断を区別できていますか。

### 4.4. 見直し条件

- 作業・判断の滞留、参加者、範囲、公開・運用責任の何が変わると見直しを始めますか。
- 新しい Role を増やす前に既存責任を再配分できますか。採用変更を誰が判断しますか。
- ロール定義、メンバー定義、RACI、WBS・Schedule の追従を誰が管理・確認し、未決事項をどの管理記録へ渡しますか。

## 5. 深掘り手順

1. その責任領域がどの価値・判断に必要か確認します。
2. 専任化せず兼務できる領域を特定します。
3. 一人へ集中している判断と作業を分けます。
4. 一覧・定義の重複を削除します。

## 6. 良い例 / 悪い例

| 観点  | 良い例                               | 悪い例                     |
| ----- | ------------------------------------ | -------------------------- |
| 体制  | 小規模兼務で開始し、滞留時に分担する | すべてのRoleへ専任者を置く |
| Agent | 草案・検証を支援し、人間が判断する   | Agentを承認者にする        |
| 正本  | member割当はYAMLへ委譲する           | 本文にも同じ一覧を書く     |

## 7. レビュー観点

| 観点 | 確認内容                                                            |
| ---- | ------------------------------------------------------------------- |
| 目的 | 必要な責任領域と人間の最終判断を説明できるか                        |
| 採用 | 各ロールの採否・理由・代替先と使用可能な `owner` が明示されているか |
| 正本 | 共通定義や名簿を再掲せず、採用結果・割り当て・RACI と照合できるか   |
| 維持 | 見直し開始条件、判断者、追従先と確認担当が決まっているか            |

## 8. 仕上げチェック

- 組織モデル、owner方針、正本、見直し条件がある。
- Role codeと実行主体を混同していない。
- 個人情報・連絡先を記載していない。
- Agentに最終判断を委ねていない。
- 各責任領域が目的または主要判断に対応し、owner 方針と委譲先を追跡できる。
