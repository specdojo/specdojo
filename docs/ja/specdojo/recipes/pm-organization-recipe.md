# 組織定義 作成レシピ

Organization Definition Writing Recipe

判断・実行・確認の分担を最小体制で設計する作り方を示す。

## 1. このレシピの使い方

- 組織定義は、概要の目的と主要判断（Why）を引き継ぎ、責任領域と採用ロール（What）、兼務と見直しの方針（How）を決める。採用判断は `owner` と正本への参照でたどる（Trace）。

## 2. 作成前に集める情報

| 項目           | 集める情報                                  | 取り出し元             |
| -------------- | ------------------------------------------- | ---------------------- |
| 目的と主要判断 | 価値、優先順位、費用、受入、公開の判断      | プロジェクト概要       |
| 規模と関係者   | 参加者数、外部関係者、継続運用の有無        | ステークホルダー登録簿 |
| 担い手と兆し   | 作業の担い手、AI Agent の関与、滞留する判断 | 最終判断者への確認     |

## 3. 全体の作成手順

1. 組織モデルを最初に書く。最終判断の置き場が決まらないと、採否を決められない。
2. ロール・owner方針で、標準ロールの採否と `owner` を決める。
3. 正本と責任境界で、本書で決めることと他に任せることを分ける。
4. 見直し条件を書く。兼務が崩れる兆しは組織モデルで見えている。

## 4. 各章の書き方

### 4.1. 組織モデル

問い:

- 価値・計画・品質・公開を、それぞれ誰が最終判断するか。
- 当事者の確認を、どのロールが受け止めるか。

コツ:

- 「誰がやるか」より先に「どの判断が要るか」を聞くと、人数に引きずられない。

### 4.2. ロール・owner方針

問い:

- 採用しないロールの責務を、誰が代わりに担うか。
- Schedule の `owner` に、どのロールを使うか。

コツ:

- 採用と専任配置を分けて聞く。兼務者だけのロールを未採用にしやすい。

### 4.3. 正本と責任境界

問い:

- 採用結果・実行主体・成果物別の分担を、どこで更新するか。
- まだない定義をいつ作るか。

コツ:

- 一覧や名簿は写さず参照に置き換え、採用判断だけを残す。

### 4.4. 見直し条件

問い:

- 何が起きたら体制の見直しを始めるか。
- 誰が判断し、どの定義を追従させるか。

コツ:

- 「忙しくなったら」でなく、承認の滞留など観測できる出来事で聞く。

## 5. 深掘り手順

浅いときは次の順で対応のない主張を探す。

1. 責任領域ごとに応える主要判断を確かめ、対応のない行を外す。
2. 採用ロールごとに、担う責任領域を確かめる。
3. 見直し条件ごとに、崩れる兼務の前提を確かめる。

## 6. 良い例 / 悪い例

| 観点 | 良い例                             | 悪い例                       |
| ---- | ---------------------------------- | ---------------------------- |
| 体制 | 兼務で始め、承認が滞ったら分担する | すべてのロールに専任者を置く |
| 兼務 | 作業と最終判断を別のロールで書く   | 「全員で責任を持つ」         |

## 7. レビュー観点

| 観点       | 確認内容                                               |
| ---------- | ------------------------------------------------------ |
| 目的整合   | 責任領域が概要の主要判断に対応しているか               |
| 採用の根拠 | 採否を責任領域で説明でき、未採用の責務に担い手がいるか |

## 8. 仕上げチェック

- 責任領域の各行から採用ロールと `owner` までたどれる。
- 個人名・連絡先を書いていない。
- AI Agent に最終判断を任せていない。
