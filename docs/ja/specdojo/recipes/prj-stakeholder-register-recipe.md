# ステークホルダー登録簿 作成レシピ

Stakeholder Register Writing Recipe

ステークホルダー登録簿を、業務価値・利用者影響・合意対象が判断できる内容に仕上げるための作り方を示す。

## 1. このレシピの使い方

- 登録簿は、プロジェクト概要の目的と利用者影響（Why）から関係者と合意対象（What）を識別し、関与方針と情報要求（How）を決める。各関係者は同じ `STH-<KEY>` で関係者一覧から証跡要件までたどれるようにする（Trace）。

## 2. 作成前に集める情報

| 項目                   | 集める情報                                                | 取り出し元                 |
| ---------------------- | --------------------------------------------------------- | -------------------------- |
| 目的と利用者           | 誰のどの課題を改善するか、直接・間接の利用者と利用場面    | プロジェクト概要           |
| 判断と合意の場面       | 着手・範囲・変更・公開・利用開始で、誰が何を決めるか      | プロジェクト責任者への確認 |
| 実行・協力の体制       | 実行担当、運用担当、外部協力者と関わり方、採用済みの Role | 体制・メンバー定義         |
| 懸念                   | 利用負荷、変更影響、継続性、公開適性、合意遅延の要因      | 各関係者への聞き取り       |
| AI Agent・ツールの関与 | 入力・制約・生成結果の確認責任を持つ人の役割              | 実行担当への確認           |

## 3. 全体の作成手順

1. 関係者一覧を先に書き、ID を決める。ID が決まらないと、ほかの表の行をつなげられない。
2. 影響度/関心度分析で、期待・懸念・必要な合意と評価根拠を書く。
3. エンゲージメント方針は High の関係者から書く。合意が要る相手の行動が決まると、残りは情報共有で足りるかを判断しやすい。
4. コミュニケーション要件で、関係者が判断に使う情報と残す証跡を書く。
5. 最後に見直し条件を書く。ほかの表がそろってから、どの変更でどの行が動くかを確かめる。

## 4. 各章の書き方

### 4.1. 関係者一覧

問い:

- 誰が目的・範囲・公開や利用の可否を判断し、誰が直接利用し、誰が間接的に影響を受けるか。
- AI Agent やツールが関与する場合、その確認責任を持つのはどの人の役割か。

コツ:

- 「ユーザー」と書きたくなったら、利用場面ごとに集団を分けられないかを聞く。
- 個人名で挙がった人は、その人が担う役割名に置き換える。概要に書かれた利用者は写さず、概要への参照に置き換える。

### 4.2. 影響度/関心度分析

問い:

- 期待が満たされないと、誰の利用や継続にどのような影響が出るか。
- その関係者と、何を決めなければ先へ進めないか。

コツ:

- 「重要だから High」になりやすい。その人が左右する判断（方針・範囲・公開可否など）を聞き、それを根拠に書く。
- 懸念は「期待が満たされない場合の困りごと」として聞くと具体になる。

### 4.3. エンゲージメント方針

問い:

- 今の関与状態と目標の関与状態の差を、どの行動で埋めるか。
- その行動は、影響度/関心度分析とコミュニケーション要件に書いた合意の時点（リリース前の試利用など）に間に合うか。

コツ:

- 期限は「週次」のような会議の頻度ではなく、初期公開前などの判断の節目で書く。継続的な助言のように節目がない関与は、「設計方針の確定まで」のように関与を終える条件を書く。
- 会議の日時や頻度は、関係者一覧・影響度/関心度分析・関与方針に繰り返さず、コミュニケーション要件の「計画への反映」から計画へ渡す 1 か所に絞る。
- 外部関係者がまだ関与していなければ、現在の事実と将来の仮定を混ぜず、_ASSUMPTION_ を付ける。

### 4.4. コミュニケーション要件

問い:

- 関係者は何を受け取れば、判断・利用・協力ができるか。
- どの手段なら内容を確認でき、証跡を残せるか。

コツ:

- 「進捗」と聞いたら、優先順位・変更理由・利用手順など、何の判断に使う情報かを聞き返す。

### 4.5. 見直し条件

問い:

- どの変更が、関係者・期待・影響度・合意対象を変えるか。
- 誰が見直し、誰が承認するか。

コツ:

- 承認者を空欄や「-」にしない。見直し責任者が自分で承認してよいのは、その役割が見直す内容を最終判断する場合（目的・スコープの変更を `PO` が見直すなど）に限り、そのときも役割名を承認者に書く。
- 周期が決まっていなければ、_TODO_ を付けて決める時期を残す。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 目的と期待効果から利益を得る集団・影響を受ける集団をたどり、一覧にない集団を足す。
2. High の関係者ごとに、必要な合意がエンゲージメント方針の行動と期限で取れるかを確かめる（リリース前に要る合意を、リリース後の行動で埋めていないか）。
3. 情報要求ごとに、どの判断に使うかを確かめ、使い道のない行を外す。
4. 変更の出来事ごとに、動く行と承認者がいるかを確かめる。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                         | 悪い例                               |
| ------------ | -------------------------------------------------------------- | ------------------------------------ |
| 関係者の識別 | 「将来の利用者」を利用場面と期待を添えて書く                   | 「ユーザー」とだけ書く               |
| 影響度の根拠 | 「公開・利用可否を判断するため High」と書く                    | 「重要なので High」と書く            |
| 必要な合意   | 「初期公開の範囲と公開情報」と具体化する                       | 「いろいろ相談する」と書く           |
| 関与方針     | 「初期公開前に導入手順を公開し、Issue で不明点を集める」と書く | 「利用者と連携する」と書く           |
| 見直し条件   | 「公開方針の変更時に将来利用者の要件を見直す」と書く           | 「必要に応じて更新する」と書く       |
| 実行主体     | 「AI Agent 活用担当」のように責任を持つ人の役割として書く      | 「AI Agent」を単独の関係者として書く |

## 7. レビュー観点

| 観点       | 確認内容                                                         |
| ---------- | ---------------------------------------------------------------- |
| 業務価値   | 目的・利用者・期待効果から関係者を識別できているか               |
| 利用者影響 | 直接利用者・間接利用者・影響受容者の期待と懸念が分かるか         |
| 合意の時点 | 必要な合意を取る時点と、関与方針の行動・期限が食い違っていないか |
| 公開適性   | 個人情報、非公開情報、根拠のない推測がないか                     |

## 8. 仕上げチェック

- 各関係者を、関係者一覧から必要な合意・関与方針・証跡要件まで同じ ID でたどれる。
- High の関係者に、期待・懸念・必要な合意・関与方針がある。
- 見直し条件の各行に、承認する役割が書かれている。
