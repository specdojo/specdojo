# システム設計索引 作成レシピ

System Design Index Writing Recipe

変更する人が最初に直す正本と確かめ方を選べる索引の作り方を示す。

## 1. このレシピの使い方

- 索引は、正本探しと二重更新（Why）に応え、設計領域ごとの正本・派生物・非該当・未確認（What）を定め、変更目的から更新先と検証へたどる経路（How）を示す。所在・更新責任・追従先は同じ行で結び付ける（Trace）。

## 2. 作成前に集める情報

| 項目     | 集める情報                                             | 取り出し元                        |
| -------- | ------------------------------------------------------ | --------------------------------- |
| 利用目的 | 誰がどの設計情報を探し、どの領域に困っているか         | 開発担当・引継ぎを受けた担当      |
| 対象境界 | 対象システム、外部へ任せる部分、任意で使う構成         | システム概要・構成図              |
| 正本候補 | 値を変えるとき最初に編集するファイルと基準ディレクトリ | 各リポジトリの配置、開発担当      |
| 生成経路 | 生成の入力、script・サブコマンド、出力先               | `package.json` などの script 定義 |
| 確認経路 | 変更後に流す検査と対象ケース、観測できる結果           | テスト・CI の定義、品質担当       |
| 関連仕様 | 判断の根拠を持つ文書と、その現行・廃止状態             | 文書体系の一覧                    |

## 3. 全体の作成手順

1. 概要に対象と対象外を書く。範囲が決まらないと、SSOT 一覧に載せる領域が決まらない。
2. SSOT 一覧で、候補を正本・派生物・業務記録・未確認に仕分ける。
3. 自動生成物で、正本から再生成できる入力と出力を一対にする。正本の後に書くと、生成物を正本に載せずに済む。
4. 変更の入口で、代表的な変更を更新先から検証まで一度たどり、たどれない箇所は前の章で直す。
5. 関連ドキュメント導線で、読み手が判断に使う文書だけを並べる。
6. 途中でメモした未確認・未決を留保事項にまとめる。

## 4. 各章の書き方

### 4.1. 概要

問い:

- どの利用者の、どの調査・引継ぎを助けるか。
- 対象外と、外部に任せる部分はどこか。

コツ:

- 範囲は機能や実行単位（CLI、日次処理など）で区切ると対象外が見える。外部に任せる部分は、連携の正本として残る。
- プロジェクトの背景は写さず、上位の文書への参照に置き換える。

### 4.2. SSOT 一覧

問い:

- 値を変えるとき、最初に編集するのはどのファイルか。
- 「なし」と書く領域は、構成上ないのか、まだ調べていないのか。

コツ:

- 開発担当に「この値を変えるとき最初にどこを開くか」と聞くと、派生物ではなく正本が出てくる。
- DB がない構成では保存形式と移行の契約が、監視では形式・通知を決める設定が抜けやすい。

### 4.3. 自動生成物

問い:

- 入力、コマンド、出力が実際につながっているか。
- 生成後にどこを見れば更新を確かめられるか。

コツ:

- 出力名からコマンドを推測しやすい。script 定義を開いて照合する。
- 実行結果を保持するファイルは、生成物に見えても業務記録として分ける。

### 4.4. 変更の入口

問い:

- この変更が起きたら、最初に何を変え、何が追従するか。
- どのケースを見れば、今回の変更を判定できるか。

コツ:

- 品質担当に「この変更で壊れやすいのはどこか」と聞くと、正常系以外のケースを選べる。
- これから行う確認と実行済みの証跡を混ぜやすい。

### 4.5. 関連ドキュメント導線

問い:

- 読み手はこの参照で何を判断するか。
- 未作成の文書は、当面どこを参照するか。

コツ:

- 略号だけで分類すると、同じ文書を別名で呼び分けやすい。参照目的で分ける。
- 同名・後継・廃止の文書を取り違えやすい。

### 4.6. 留保事項

問い:

- 不明な事実、意思決定待ち、仮定のどれか。
- 解消したら、どの行・設定・手順へ反映するか。

コツ:

- 実装が動いたことと、未整備の監視を残したまま使えるかは別の論点として分ける。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 変更の入口の各行が、どの正本から始まり、どの検証で終わるかを確かめる。欠ける行は留保事項へ移す。
2. 非該当の行ごとに、代わりの保存・連携・観測の手段が残っているかを確かめる。
3. 自動生成物の各行の入力が、SSOT 一覧の正本にあるかを確かめる。ない行は正本か業務記録かを見直す。

## 6. 良い例 / 悪い例

| 観点       | 良い例                                                           | 悪い例                                |
| ---------- | ---------------------------------------------------------------- | ------------------------------------- |
| パスの解釈 | 複数リポジトリの入力・出力に、それぞれの基準ディレクトリを添える | 同名の `src/` を基準なしで並べる      |
| 検証の範囲 | 「二つの実行が別の保存先を使うことを、分離テストで確かめる」     | 「代表実行が成功したので分離も確認」  |
| 検証の段階 | CI の検査成功と、実機での確認が未実施であることを分けて書く      | CI が成功したので運用も確認済みとする |

## 7. レビュー観点

| 観点     | 確認内容                                                   |
| -------- | ---------------------------------------------------------- |
| 所在     | 初めて読む開発担当が、派生物ではなく正本を選べるか         |
| 検証経路 | 品質担当が、コマンド・対象ケース・期待結果を一組で選べるか |
| 委譲     | 値・電文・設定の中身を写さず、正本への導線だけを置いたか   |

## 8. 仕上げチェック

- 非該当の行に、代わりの手段か、代わりが要らない理由がある。
- 未確認の領域を確定情報にしていない。
- 実在しない文書やコマンドを現行の導線にしていない。
