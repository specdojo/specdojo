# システム設計索引 作成レシピ

System Design Index Writing Recipe

参照先を並べる前に、正本か派生物か、非該当か未確認かを切り分ける作成手順である。変更する人が最初の更新先と確認経路を選べる索引に仕上げる。

## 1. このレシピの使い方

- 担当交代時に正本探しや二重更新が起きる課題を引き継ぎ、対象範囲を先に定める。プロジェクトの背景全文は索引へ複製しない。
- 得たい成果は「設計領域から正本へ、変更目的から検証へたどれる状態」とする。所在、責任、追従先を同じ行で結び付ける。
- ファイルやコマンドの存在確認と、構成・公開の承認を分ける。値・構文・構造の詳細を作り込まず、未決事項を判断者へ渡す。

## 2. 作成前に集める情報

| 入力       | 集める情報・問い                                                                                                |
| ---------- | --------------------------------------------------------------------------------------------------------------- |
| 利用目的   | 誰がどの設計情報を探すか。調査・引継ぎで困る領域はどこか                                                        |
| 対象境界   | 対象システムと外部委譲先はどこか。任意利用の構成は何か                                                          |
| 正本候補   | API・外部連携、保存・移行、モジュール境界、設定・実行構成、Job・定期処理、監視、ソース管理・CI の変更元はどこか |
| 生成経路   | 何を入力に、どのコマンドが、どこへ出力するか。業務記録や実行状態と区別できるか                                  |
| 確認経路   | どの検査・対象ケースで、何が観測できれば合格か                                                                  |
| 関連仕様   | 境界・品質条件・運用・テスト・判断の根拠はどの現行文書にあるか。未作成なら何で補うか                            |
| 責任と留保 | 更新者、確認者、承認者、根拠不足の領域と判断時機は何か                                                          |

## 3. 全体の作成手順

1. 「概要（対象範囲・更新責任）」に、対象・対象外と担当を短く置く。兼務しても確認と承認の責務を区別する。
2. 「SSOT 一覧（表形式）」の候補を、正本・派生物・業務記録・未確認に仕分ける。非該当は構成上の理由と代替正本、または代替不要の理由を確かめてから記入する。
3. 「自動生成物（生成コマンド/生成先/閲覧先）」で、設計の正本から再生成できる入力と出力を一対にする。script・サブコマンド、基準ディレクトリ、再生成する時機を照合する。
4. 「変更の入口（典型ケース）」で、集めた正本候補から代表的変更を選ぶ。最初の更新先から追従先、検証ケースまで一度たどり、非該当領域を導入する場合は構成判断も切り出す。
5. 「関連ドキュメント導線（C4 / NFR / OPD / DEC 等）」で参照目的を付け、現行・廃止・未作成を区別する。廃止文書は後継へ接続する。
6. 「未決事項・変更影響・公開前確認」へ未確認・承認待ちを集め、担当・判断時機・解消後の更新先を添える。

## 4. 各章の書き方

### 4.1. 概要

- どの利用者の調査・引継ぎを助けるか。
- 対象外と外部依存を混同していないか。
- 誰が更新し、QE は何を確認し、人間は何を承認するか。

範囲は機能・実行単位と、対象外になる境界から具体化する。良い例は「CLI と日次処理を対象に、DEV が更新、QE が失敗ケースを確認、PO が公開を承認する」。避けたい例は「全体を担当者が確認する」で、対象と責任の抜けを判断できない。

### 4.2. SSOT 一覧

- 値を変えるとき、最初に編集するのはどのファイルか。
- DB がない場合、保存形式と移行の契約はどこにあるか。
- 監視は出力先だけでなく、形式・検知・通知を決める設定まで特定できるか。
- モジュールの依存方向や統合条件を変える場合、境界の定義、ブランチ規約、CI・フック・検査 script のどれを更新するか。

「なし」を使う前に、未確認か構成上の非該当かを問う。良い例は「RDBMS は非該当。保存レコード schema と移行処理を DEV が更新し、旧形式の読込を確認する」。避けたい例は「DB はなし」で、保存契約が索引から消える。代替も不要なら理由を確かめ、判断できなければ担当付きの _TODO_: とする。

### 4.3. 自動生成物

- 入力、コマンド、出力が実際につながっているか。
- 生成後にどこを見れば更新を確認できるか。
- 手編集が次の生成で失われるファイルを正本にしていないか。
- 設計定義から再生成できる派生物か、取引・実行結果を保持する記録か。

出力名からコマンドを推測せず、既存の script と出力先を照合する。良い例は「契約変更時に API 定義から型を生成し、IDE と型検査で更新を確認する」。避けたい例は「ビルドで全ファイルを更新する」で、生成経路や業務記録との境界を確認できない。生成しない構成なら、その理由を短くまとめる。

### 4.4. 変更の入口

- 変更が起きたら最初に何を変えるか。
- 再生成・テスト・運用手順のどれに波及するか。
- 正常、失敗、再実行のどのケースを確認すれば今回の変更を判定できるか。
- 検査を行う場所とコマンド・対象ケースは実在するか。今後の確認手順と実行済みの証跡を区別できるか。

観測結果から必要なケースを選ぶ。良い例は「二つの実行で異なる保存先を使うことを、分離テストの対象ケースで確認する」。避けたい例は「代表実行が成功したので分離も確認済み」で、確認していない性質を成功の意味に含めている。

### 4.5. 関連ドキュメント導線

- 読み手はこの参照で何を判断するか。
- 同名・後継・廃止文書のどれを指しているか。
- 未作成なら当面どこを参照し、誰が導線を直すか。

分類は読み手の参照目的から選び、略語は初出時の説明と揃える。良い例は「運用方針・手順: 障害対応の判断に使う。索引は未作成のため、当面は現行の個別手順を参照し、OPS が整備後に接続する」。避けたい例は「関連: 運用一式、旧フロー」で、読む目的と現行性が分からない。

### 4.6. 未決事項・公開前確認

- 不明な事実、意思決定待ち、仮定のどれか。
- 何に影響し、いつまでに誰が判断するか。
- 解消後にどの行・設定・手順へ反映するか。

実装の検証結果と、非該当範囲・未整備の監視を留保して公開できるかの判断を分ける。良い例は「通知先は未決。OPS が検知要件を確認し、公開前に人間の PO が留保可否を判断、決定後に設定と手順を更新する」。避けたい例は「動いたので公開する」で、判断者と解消条件が抜けている。

## 5. 深掘り手順

1. 一つの変更を選び、目的から正本、生成物、検証へ進む。到達しない箇所を情報不足として切り出す。
2. 非該当行を選び、代替の保存・連携・観測手段が索引から消えていないか確かめる。
3. 不在の参照や実行できないコマンドがあれば、推測で埋めず影響と担当を留保欄へ戻す。

## 6. 良い例 / 悪い例

| 観点       | 良い例                                                               | 悪い例                                |
| ---------- | -------------------------------------------------------------------- | ------------------------------------- |
| パスの解釈 | 複数リポジトリの生成入力・出力に、それぞれの基準ディレクトリを添える | 同名の `src/` を基準なしで並べる      |
| 検証の範囲 | CI の検査成功と実機受入の未実施を分け、公開判断へ引き継ぐ            | CI が成功したので運用も確認済みとする |
| 改訂・廃止 | 旧正本の参照元を洗い出し、生成・検証・運用導線の更新を各担当へ渡す   | 旧正本の行だけを削除して完了する      |

## 7. レビュー観点

| 観点       | 確認する問い                                                |
| ---------- | ----------------------------------------------------------- |
| 所在       | 初めて読む DEV が正本を選べるか。派生物を選んでしまわないか |
| 検証入力   | QE がコマンド・対象ケース・期待結果を一組で特定できるか     |
| 運用・承認 | OPS が設定と手順へ、PO が留保事項と承認条件へ到達できるか   |

## 8. 仕上げチェック

- 主な設計領域は所在または非該当理由と代替の要否に結び付き、未確認を確定情報にしていない。
- 変更トリガーから更新先・追従先・期待結果をたどれ、詳細定義は正本に委ねている。
- 現行文書のリンクと未作成のコード表記が区別され、判断待ちに担当と次アクションがある。
