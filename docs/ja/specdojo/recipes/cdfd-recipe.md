# 概念データフロー図（プロセスグループ別）作成レシピ

Conceptual Data Flow Diagram Process Group Writing Recipe

全体概要から一つのプロセスグループとそれに属する領域群を引き継ぎ、領域内部と領域間のプロセス、主要例外、グループ外への委譲を、関係者が再現可能な形で具体化するための作成手順です。状態を変えるプロセスは STSD へ接続し、状態定義と遷移の二重管理を防ぎます。

## 1. このレシピの使い方

- 最初に、全体概要から対象グループ、含む全領域、グループ単位の主要入力・主要出力・データストアを抜き出し、領域ごとの節へ配分します。
- 次に、各節を説明文、主要入力・主要出力・データストアの箇条書き、プロセス表の順で作り、全体概要の「データストア」から本グループが読み書きする部分集合を切り出します。
- その後、概念データフロー、個別プロセス主要入出力、状態遷移の参照、主要例外とグループ外への委譲を具体化します。
- 最後に、全領域と全プロセスの網羅性、データストア名称・区分・読み書き、同一グループ内の領域間フロー、STSD への参照、他グループとの責任境界を突き合わせます。

この成果物は、上位の業務目的を Why、グループ内で成立させる出力と境界を What、プロセス・例外対応・委譲を How、領域 ID・プロセス ID・例外 ID・参照先の対応を Trace として整理します。上位目的、状態定義、状態遷移は複製しません。

## 2. 作成前に集める情報

| 項目               | 集める情報                                                                           |
| ------------------ | ------------------------------------------------------------------------------------ |
| 対象グループ       | 全体概要のプロセスグループ名と `cdfd-<group>` の英小文字スラッグ                     |
| 対象領域           | グループに属する全領域の ID・名称。業務目的、担当、起点イベントは参照用に控える      |
| グループ入出力     | 全体概要にあるグループ単位の主要入力、主要出力、データストア                         |
| 領域別入出力       | グループ入出力を各領域へ配分した主要入力、主要出力、データストア                     |
| 利用者と判断       | 誰が内部フローを合意し、誰が境界を承認し、誰が設計・検証に使うか                     |
| プロセス候補       | 異なる業務目的、担当、正本更新、完了条件を持つ処理候補                               |
| 起動条件と必須性   | 外部イベント、前段完了、承認、条件値、および非起動時の正常な扱い                     |
| データストア       | 全体概要の「データストア」にある名称と区分、および各領域・プロセスでの参照・更新の別 |
| 状態定義・状態遷移 | 状態を変えるプロセスが参照する STSD の文書 ID                                        |
| 主要例外           | 入力不足、業務条件不成立、更新失敗など、結果または後続起動を変える分岐               |
| グループ外委譲     | 他グループまたは横断ユースケースへ渡す責務、情報、戻す条件                           |
| 責任分担           | 人間と AI Agent の責任分担を定める対応文書                                           |
| 未決事項           | 境界、起動条件、正本、判断者が未確定な論点と、影響・決定時期                         |

## 3. 全体の作成手順

1. 全体概要から一つのプロセスグループと、そこに属する全領域の ID・名称を転記します。
2. 全体概要のグループ単位の主要入力・主要出力・データストアを、領域ごとの節へ配分します。
3. 各領域について、役割と内部プロセスの連携を説明し、主要入力・主要出力・データストアを箇条書きにします。
4. 領域ごとの開始と最終出力から必要な処理をたどり、業務目的または完了条件が変わる箇所でプロセスを分けます。
5. 各プロセスへ所属領域 ID の枝番を付け、目的、担当、起動条件、必須性を同じ領域の表へ一行ずつ記入します。
6. 全体概要の「データストア」から、本グループが読み書きする行だけを同じ区分で転記し、参照・更新の別と利用内容を記入します。
7. 各プロセスの主要入力、主要出力、データストアを個別プロセス主要入出力へ整理します。
8. 一覧、検索、状態参照、検証など、独立した業務成果を持たない候補を支援先プロセスへ戻します。
9. 同一グループ内の領域間の受け渡しを特定し、領域ごと、または業務の性質が近いプロセスごとに図の分割単位を決めます。
10. 領域ごとの表の各行を一つずつプロセスノードへ置き、イベント、外部主体、データストアとラベル付きエッジでつなぎます。
11. 条件付き・選択プロセスの非起動経路を確認し、どの出力がそろえば各領域とグループが完了するかを図で示します。
12. 状態を変えるプロセスを抽出し、状態一覧と状態遷移図を統合した STSD を参照表へ記入します。状態一覧や遷移表は CDFD に書きません。
13. 業務結果または後続起動を変える主要例外を選び、検出条件、扱い、継続・再開条件を表にします。
14. 他グループの内部処理を委譲表へ移し、委譲先 `cdfd-<group>` または `cdfd-uc-<topic>`、引き渡す情報、戻す条件を記述します。
15. 領域 ID、プロセス ID、例外 ID、データストア名、参照先 ID を使って、表と図の重複・欠落・名称ゆれを解消します。

## 4. 各章の書き方

### 4.1. 目的

問い:

- この CDFD は全体概要のどのプロセスグループを詳細化しますか。
- 誰が、グループ内部のフロー、領域間の受け渡し、主要例外、委譲境界を判断または利用しますか。
- 上位の業務目的を書き写さず、このグループで得る成果と利用結果を説明できますか。

「仕入を詳しくする」のような曖昧な表現ではなく、「店主代表が発注から売場補充までの責任境界を承認し、開発担当が領域間の入出力を設計へ使う」のように、対象者と利用結果を結び付けます。

### 4.2. 適用範囲

問い:

- 対象グループに属する全領域を含み、別グループの領域を混在させていませんか。
- どのイベントから、どの出力がそろうまでを対象にしますか。
- 対象となる期間、組織、システム境界を説明できますか。
- 補助操作、実装詳細、他グループの責務、横断順序のどこから先を対象外にしますか。
- 人間と AI Agent の責任分担を本文で再定義せず、対応文書を参照していますか。

他グループへの委譲内容は「主要例外とグループ外への委譲」に集約し、本章では指し先だけを示します。対象プロダクトの現在の正本として読める業務語を使い、プロジェクトの実行フェーズ名や一時的な仮称を持ち込みません。

### 4.3. プロセス領域

問い:

- 全体概要で対象グループに属する領域が、一つも欠けず、一節ずつ登場しますか。
- 各節が、説明文、主要入力・主要出力・データストアの箇条書き、プロセス表の順になっていますか。
- 各領域の箇条書きを合わせると、全体概要のグループ単位の箇条書きを説明できますか。
- 領域 ID と名称は上位と一致し、業務目的・担当・起点イベントを書き写していませんか。
- プロセス ID は所属領域を示す `P-<nn>-<nn>` 形式ですか。
- 各領域に一つ以上の内部プロセスがあり、表の一行が一つの業務目的と完了条件を持ちますか。
- 起動条件はイベント、前段完了、承認、条件値のいずれかで判定できますか。
- 条件付きまたは選択のプロセスを起動しない場合、正常に領域完了へ進めますか。

最初にグループ単位の入出力を付箋のように並べ、どの領域が受け取り、どの領域が生み出すかを一つずつ割り当てます。次に、領域の役割を 1〜3 文で要約し、箇条書きの後へプロセス表を置きます。処理を分けるか迷う場合は、業務目的、主担当、更新する正本、完了条件を比較します。

### 4.4. データストア

問い:

- 本グループが読み書きするデータストアだけを、全体概要と同じ名称・区分で掲載していますか。
- 各行に参照・更新の別と、本グループでの利用内容がありますか。
- プロセス領域の箇条書きと個別プロセス主要入出力にあるデータストアを過不足なく含んでいますか。
- 各行が概念データフローの同名ノードに対応していますか。

全体概要の「データストア」から必要な行を切り出し、マスタ・構成データとトランザクションデータの区分を保ちます。新しい名称や区分が必要なら、先に全体概要を見直します。図を分割して同じノードを再掲する場合も、表の行とノードラベルの名称は変えません。

### 4.5. 概念データフロー

問い:

- プロセス領域の各表の行が同じ ID と名称を持つ一つのプロセスノードとして登場しますか。
- 同一グループ内の領域間の受け渡しを、起点イベントからグループ完了まで順方向にたどれますか。
- 図を領域ごと、または業務の性質が近い単位へ分けていますか。一図が 15 プロセスを超えていませんか。
- 条件付き・選択プロセスの起動条件と、非起動時の正常経路を区別できますか。
- データストアの名称、区分、色クラスは全体概要と一致していますか。
- 図直後の注記に、全体概要の凡例への参照、使用線種、省略した入出力と理由、別図と共有するノードを示していますか。
- 状態をノードとして並べたり、状態間の遷移を描いたりしていませんか。

図は順序と分岐へ集中させます。他グループは委譲先の代表ノードまたは境界イベントだけを置き、内部処理を展開しません。状態変化が重要な箇所でも、CDFD にはプロセスと起動条件を残し、状態名と遷移条件は STSD へ委ねます。

### 4.6. 個別プロセス主要入出力

問い:

- 図を領域単位で分けた場合、同じ領域単位で節と表を設けていますか。
- 各プロセスの主要入力・主要出力は、隣接プロセス、外部主体、データストアとの受け渡しとして説明できますか。
- データストアの名称と区分は「プロセス領域」「データストア」および全体概要と一致していますか。
- 業務目的、担当、起動条件、必須性を「プロセス領域」の表から重複させていませんか。

全プロセスをちょうど一度、所属領域または図の分割単位に対応する表へ記載します。主要出力という概念名と、保存先であるデータストア名を別の列に保ちます。

### 4.7. 状態遷移の参照

問い:

- 状態を変える全プロセスについて、状態一覧と状態遷移図を統合した STSD を特定できますか。
- CDFD は状態を変えるプロセスと起動条件だけを示し、状態名、状態説明、遷移元・遷移先、遷移条件を再定義していませんか。
- 参照先が未作成の場合、文書 ID をバッククォートで仮置きし、状態内容を CDFD へ代替記載していませんか。

対象、状態を変えるプロセス、STSD の三点を一行で結びます。状態を変えるプロセスがない場合も章は残し、その事実と確認根拠を一文で記載して表だけを省略します。

### 4.8. 主要例外とグループ外への委譲

問い:

- 例外 ID は最初に検出する領域の番号を含む `E-<nn>-<nn>` 形式ですか。
- その例外は、成果の採否、正本の確定、後続起動、人間の判断のいずれかを変えますか。
- どの条件で検出し、どのプロセスまで停止し、どこから再開しますか。
- 同一グループ内の領域間受け渡しを委譲扱いにしていませんか。
- 委譲先は他の `cdfd-<group>` または横断順序を扱う `cdfd-uc-<topic>` で、内部処理を書き写していませんか。

主要例外は件数を増やすより、正常完了できない理由と再開条件を一意にすることを優先します。委譲先が未作成でも安定した文書 ID をバッククォートで示し、作成状況は成果物本文ではなく登録簿で追跡します。

### 4.9. 未決事項（任意）

- 調査で確定できる不足情報は _TODO_:、意思決定待ちは _UNDECIDED_:、仮置きする前提は _ASSUMPTION_: とします。
- 未決論点には、影響する領域・プロセス・例外・委譲、決定者、決定時期を添えます。
- 未決事項がない場合は章を省略し、空表や「なし」だけの章を残しません。

## 5. 深掘り手順

1. 全体概要のグループ入力から順方向にたどり、どの領域が受け取り、どの領域が次へ渡すかを確認します。
2. グループの最終出力から逆向きにたどり、各領域と各プロセスが必要な理由を確認します。
3. 各領域について、領域単位の主要入力・主要出力・データストアがグループ単位の箇条書きへ対応するか確認します。
4. 一覧にだけあるプロセスと図にだけあるノードを列挙し、追加、削除、名称統一のいずれかで解消します。
5. 条件付き・選択プロセスを一つずつ非起動にし、必須出力が欠ける場合は必須性または起動条件を見直します。
6. 状態を表す名詞や遷移条件を検索し、CDFD で定義している内容を STSD の参照へ置き換えます。
7. 各主要例外について、検出前に確定した正本、停止する後続、再開位置を順にたどります。
8. 他グループのノードを隠しても本グループの完了条件を説明でき、委譲表から次の責任者が行動できるか確認します。
9. データストア名を全体概要、プロセス領域、データストア、図、個別プロセス主要入出力で機械的に照合します。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                                             | 悪い例                                           |
| ------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------ |
| グループ境界 | 仕入グループの仕入計画と入荷検品を一文書で扱う                                     | 仕入計画だけを一つの CDFD に分割する             |
| 領域別入出力 | 補充依頼を仕入計画へ、納品と売場補充を入荷検品へ配分する                           | グループ単位の入出力を各領域へそのまま複製する   |
| プロセス ID  | 領域 `P-02` の検品へ `P-02-02` を付ける                                            | 文書内の順番だけで `P-01` を付ける               |
| 起動条件     | 仕入先から商品が納品され、対応する発注記録を特定できた                             | 必要に応じて検品する                             |
| データストア | 「仕入記録」を全体概要と同じ名称・トランザクション区分で使う                       | 図だけ「発注 DB」と改名する                      |
| 図の分割     | 仕入計画と入荷検品を領域単位の二図に分け、受け渡す発注内容を一致させる             | 性質の異なる全プロセスを一図に詰め込む           |
| 状態遷移     | 検品を状態変更プロセスとして示し、商品状態の定義と遷移は STSD を参照する           | 未入荷→検品中→販売可能の遷移表を CDFD に複製する |
| 主要例外     | 発注記録を特定できない場合は入荷記録を確定せず、照合後に受入から再開する           | エラーなら適切に対応する                         |
| 委譲         | 補充判断を `cdfd-inventory`、グループ横断順序を `cdfd-uc-replenishment` へ委譲する | 在庫グループの補充判定手順を仕入 CDFD 内に描く   |

## 7. レビュー観点

| 観点         | 確認内容                                                                     | 主な確認者                 |
| ------------ | ---------------------------------------------------------------------------- | -------------------------- |
| 業務価値     | グループ内の各出力が、上位目的と対象者の利用場面のどちらを支えるか説明できる | 業務分析担当               |
| 領域網羅     | 対象グループの全領域が一度ずつ登場し、各領域に内部プロセスがある             | 業務分析担当、品質確認担当 |
| 必須性境界   | 必須・条件付き・選択プロセスの起動条件と非起動時の扱いを承認できる           | 店主代表                   |
| 設計入力     | 各プロセスの起動条件、入出力、データストア、委譲先を識別できる               | 技術メンター               |
| 状態責務     | CDFD が状態を定義せず、状態変更プロセスから STSD をたどれる                  | 技術メンター、品質確認担当 |
| 例外         | 主要例外の検出条件、停止範囲、再開条件が判定できる                           | 品質確認担当               |
| 用語整合     | 領域、プロセス、イベント、入出力、データストアの名称が上位・表・図で一致する | 業務分析担当、品質確認担当 |
| グループ境界 | 同一グループ内の領域間フローを描き、他グループの内部処理を作り込んでいない   | 業務分析担当、アーキテクト |

「業務分析担当」「品質確認担当」「技術メンター」「アーキテクト」は、対象プロジェクトのロール定義または対応する責任分担文書で正式な担当へ対応付けます。

## 8. 仕上げチェック

- 対象者、利用場面、対象グループ、開始・終了、組織・システム境界、対象外を明記した。
- 全体概要の対象グループに属する全領域を一度ずつ掲載し、各領域に一つ以上のプロセスがある。
- 領域単位の主要入力・主要出力・データストアが、全体概要のグループ単位の箇条書きと矛盾しない。
- プロセス ID は所属領域 ID の枝番で、一覧・図・入出力表に同じ ID と名称を使用した。
- 「データストア」が全体概要の部分集合で、名称・区分・読み書きの別が各表と図に一致する。
- 図を領域または業務の性質ごとに分け、図直後に凡例の参照、線種、省略事項、共有ノードを記載した。
- 条件付き・選択プロセスの起動条件と非起動時の正常な扱いを説明できる。
- 状態を変えるプロセスから STSD を参照し、状態定義・遷移表・状態遷移図を CDFD に複製していない。
- 主要例外に検出条件、扱い、継続・再開条件がある。
- グループ外委譲の委譲先、引き渡す情報、戻す条件があり、同一グループ内の領域間受け渡しを委譲扱いにしていない。
- 未決事項は共通ラベルで確定情報と区別し、ない場合は章を設けていない。
- 個人情報、秘密情報、非公開の組織情報など、公開範囲に不適切な内容を含めていない。
