# 概念データフロー図 作成レシピ

Conceptual Data Flow Diagram Writing Recipe

プロセス領域の境界を先に合意し、起点イベント、入出力、データストアを表と図へ一貫して落とし込むための作成手順です。コマンドや実装の列挙ではなく、関係者が業務上の受け渡しを説明できる CDFD に仕上げます。

## 1. このレシピの使い方

- 最初に、対象者のどの判断・業務課題を支える図か（Why）と、全体概要または領域別のどちらを作るかを決めます。
- 次に、独立した業務成果を持つプロセス領域（What）を洗い出し、起点、入出力、担当、正本（How）を一行ずつ定義します。
- 表を先に完成させ、その用語を変えずに Mermaid 図へ配置します。領域 ID、名称、入出力、詳細化先の対応で追跡可能にします（Trace）。
- 最後に、補助操作を独立領域へ混ぜていないか、表と図のどちらかにしかない要素がないか、後続成果物へ渡す粒度を越えていないかを確認します。

## 2. 作成前に集める情報

| 項目           | 集める情報                                                       |
| -------------- | ---------------------------------------------------------------- |
| 利用目的       | 誰が、何を合意・承認・設計・検証するために使うか                 |
| 対象境界       | 対象業務、組織、期間、システム境界、AS-IS / TO-BE                |
| 対象外         | 補助操作、実装詳細、別成果物へ委譲する領域                       |
| プロセス候補   | 固有の起点と業務成果を持つ処理のまとまり                         |
| 起点イベント   | 各候補をいつ開始するか判断できる出来事                           |
| 主要入力・出力 | 他領域または外部主体から受け取り、引き渡す情報・現物             |
| データストア   | 読み書きする台帳、文書、ファイル、データベースなどの論理的な正本 |
| 担当・外部主体 | 主担当ロール、入力元、結果の受け手、人間の最終判断者             |
| 詳細化先       | 全体概要の各領域を引き継ぐ領域別 CDFD の ID または仮置き名       |
| 未決事項       | 境界、名称、責務、判断者が未確定な論点と、その影響・決定時期     |

## 3. 全体の作成手順

1. 利用者、利用場面、対象範囲、対象外、AS-IS / TO-BE を一段落と箇条書きで定義します。
2. 業務を開始から結果利用まで並べ、固有の起点イベントと業務成果を持つまとまりへ分割します。
3. 一覧表の各行へ領域 ID、目的、担当、起点、主要入力、主要出力、データストア、詳細化先を記入します。
4. 一覧表から、固有の成果を作らない一覧、検索、参照、検証、dry-run などを取り除き、支援先へ戻します。
5. 表の名称をそのまま使って、外部主体、イベント、プロセス領域、データストアを Mermaid 図へ配置します。
6. 情報と現物のエッジを引き、受け渡す内容が分かる名詞形のラベルを付けます。
7. 全体概要では各領域を詳細化先へ一対一で割り当て、隣接領域との責務境界と委譲先を記述します。
8. 表と図の対応、起点・終点、補助操作の境界、人間の判断、未決事項を仕上げチェックで確認します。

## 4. 各章の書き方

### 4.1. 目的と適用範囲

問い:

- この CDFD を読む人は、どの範囲または受け渡しを判断する必要がありますか。
- 現行と将来のどちらを表し、どの時点からどの結果までを扱いますか。
- 詳細化を後続へ委譲するものと、業務成果を持たないため除外するものは何ですか。

利用者と判断を一文で結び付けます。「全体を分かりやすくする」ではなく、「PO が補助操作を独立領域に含めない境界を承認する」のように、確認結果が分かる表現にします。

### 4.2. プロセス領域一覧

問い:

- その行には、他の行と区別できる起点イベントと業務成果がありますか。
- 入力と出力は別の領域または利用者との受け渡しとして説明できますか。
- データストアは媒体名ではなく、何の正本かが分かる名称ですか。

全体概要では一行を一つの領域別 CDFD 候補にします。担当は個人名ではなくロールで書き、業務目的は「検証する」「生成する」だけでなく、その結果を誰が何に使うかまで具体化します。

### 4.3. 概念データフロー

問い:

- 表の各領域、起点イベント、主要データストアは図中にありますか。
- 各エッジのラベルを読めば、何がどこからどこへ渡るか説明できますか。
- 人間の判断や外部主体との受け渡しが、システム内部の処理へ吸収されていませんか。

図は表を視覚化するために作ります。先に図を描いて名称を増やすと表との不一致が生じるため、新しいノードが必要になったら表の行または入出力も同時に更新します。

### 4.4. 境界と分割方針

問い:

- 一覧、検索、参照、検証などは固有の業務成果を持ちますか。それとも別領域の補助ですか。
- 隣接領域のどちらが正本を更新し、どちらが結果を利用しますか。
- 全体概要の各領域は一つの詳細化先へ割り当てられていますか。

責務が重なる場合は、起点、更新する正本、最終出力の三点で境界を引きます。複数領域を一つの詳細化先へ統合する場合は、統合理由と、欠落をどう確認するかを記述します。

### 4.5. 未決事項

- 名称や責務が未確定でも図から黙って省略せず、_UNDECIDED_: として影響、決定者、決定時期を記述します。
- 調査すれば確定できる不足情報は _TODO_:、現時点で置く仮説は _ASSUMPTION_: と区別します。
- 未決事項がない場合は章を省略し、空の表を残しません。

## 5. 深掘り手順

1. 図中の各プロセスから逆向きにたどり、開始を判断できるイベントがあるか確認します。
2. 各プロセスから順向きにたどり、誰かが利用する出力または更新される正本があるか確認します。
3. 同じデータストアを更新する複数領域について、更新責務が重複していないか確認します。
4. 表にだけある要素と図にだけある要素を列挙し、名称統一、追加、削除のいずれかで解消します。
5. 全体概要の各領域を詳細化先へ一度ずつ対応付け、詳細化先のない領域と、二重に割り当てた領域を解消します。
6. コマンド名、ファイル名、状態値を隠して読んでも業務上の流れを説明できるか確認し、説明できない行は目的と入出力を書き直します。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                                | 悪い例                                 |
| ------------ | --------------------------------------------------------------------- | -------------------------------------- | --------- | ----------------------- |
| 業務目的     | 成果物定義と依存から、担当者が実行順を判断できる Schedule を作る      | build コマンドを実行する               |
| 起点イベント | カタログと計画方針が準備または変更された                              | 必要に応じて                           |
| 入出力       | 入力: 成果物カタログ、依存 / 出力: Schedule、実行可能タスク           | 入力: YAML / 出力: JSON                |
| データストア | 課題・判断の正本である登録簿                                          | `register-items.json`                  |
| 補助操作     | validate は計画展開の入力検証として扱う                               | validate を独立した業務領域にする      |
| エッジ       | `計画展開 -->                                                         | "Schedule・実行可能タスク"             | 実行計画` | `計画展開 --> 実行計画` |
| 分割         | `P-03` を一つの領域別 CDFD へ割り当て、タスク実行は `P-04` へ委譲する | 計画と実行を複数の詳細図へ重複記載する |

## 7. レビュー観点

| 観点     | 確認内容                                                                     | 主な確認者 |
| -------- | ---------------------------------------------------------------------------- | ---------- |
| 業務価値 | 各領域の目的が、対象者の判断、引き継ぎ、継続可能性のどれを支えるか説明できる | BA         |
| 対象境界 | 独立領域、補助操作、領域別詳細、人間の最終判断の境界を承認できる             | PO         |
| 入力適合 | 各領域の起点、入力、出力、データストアが領域別 CDFD の作成入力になる         | ARC        |
| 網羅性   | 表、図、詳細化先の対応に重複・欠落がなく、領域 ID で追跡できる               | QE         |
| 用語整合 | 表と図でプロセス、イベント、入出力、データストアの名称が一致する             | BA、QE     |
| 責務境界 | 全体概要へ実装詳細や例外分岐を作り込みすぎず、委譲先を識別できる             | BA、ARC    |

## 8. 仕上げチェック

- 目的、利用者、対象範囲、対象外、AS-IS / TO-BE が明記されている。
- 各領域に ID、目的、担当、起点イベント、主要入力、主要出力、データストアがある。
- 表の全領域が図へ登場し、図の全プロセスが表へ対応している。
- すべての情報・現物のエッジに、受け渡す内容のラベルがある。
- 補助操作が独立領域として残っていない。
- 人間の判断者と、入力元・結果利用者との受け渡しが示されている。
- 全体概要の各領域が、領域別 CDFD の詳細化先へ重複なく対応している。
- 未決事項は共通ラベル、影響、決定者、決定時期で管理されている。
