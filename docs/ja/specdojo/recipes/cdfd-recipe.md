# 概念データフロー図（プロセスグループ別）作成レシピ

Conceptual Data Flow Diagram Process Group Writing Recipe

全体概要から一つのプロセスグループを引き継ぎ、領域内と領域間のプロセス、主要例外、グループ外への委譲を、関係者が再現できる形で具体化するための作り方を示す。

## 1. このレシピの使い方

- この CDFD は、全体概要のグループの目的（Why）を参照で引き継ぎ、グループ内でそろえる出力と境界（What）を定め、プロセス・例外対応・委譲（How）を決める。領域 ID・プロセス ID・例外 ID・データストア名でたどれるようにする（Trace）。
- 上位の目的、状態の定義と遷移は写さず参照に置き換える。全体概要が正の領域・データストアの名称も言い換えない。
- 「作成前に集める情報」をメモでそろえてから、「全体の作成手順」の順に書く。

## 2. 作成前に集める情報

| 項目               | 集める情報                                                     | 取り出し元                   |
| ------------------ | -------------------------------------------------------------- | ---------------------------- |
| 対象グループと領域 | グループ名、`cdfd-<group>` のスラッグ、属する全領域の ID・名称 | 全体概要                     |
| グループの入出力   | グループ単位の主要入力・主要出力・データストアと区分           | 全体概要                     |
| プロセス候補       | 業務目的・担当・更新する正本・完了条件が異なる処理             | 領域の担当者への聞き取り     |
| 起動条件と非起動   | 起動のきっかけと、起動しないときに正常に終わる経路             | 領域の担当者への聞き取り     |
| 状態を変える処理   | 状態を変えるプロセスと、その状態を扱う STSD の文書 ID          | 状態を管理する担当者・文書群 |
| 主要例外           | 結果または後続の起動を変える分岐と、再開の位置                 | 品質確認担当・過去の障害記録 |
| 他グループとの境界 | 他グループや横断ユースケースへ渡す責務、情報、戻す条件         | 他グループの担当者           |

## 3. 全体の作成手順

1. 対象グループの全領域を書き出し、グループの入出力をどの領域が受け取り、どの領域が生み出すかを割り当てる。この割り当てがプロセスを切り出す手がかりになる。
2. 領域ごとに、最初の入力から最終出力までをたどり、業務目的または完了条件が変わる箇所でプロセスを分ける。
3. 一覧・検索・状態参照・検証など、独自の業務成果がない候補を支援先のプロセスへ戻す。
4. 本グループが読み書きするデータストアを全体概要から切り出す。
5. 領域間の受け渡しを特定してから図の分割単位を決め、概念データフローを描く。プロセスが固まる前に描くと、図と表の名称がずれる。
6. 各プロセスの主要入出力を整理する。
7. 状態を変えるプロセスを抽出し、STSD への参照を書く。
8. 主要例外とグループ外への委譲を書く。正常の流れが固まってから書くと、停止範囲と再開位置を特定しやすい。
9. 最後に目的と適用範囲を書く。境界が決まってから書くと、本文の言い直しにならない。

## 4. 各章の書き方

### 4.1. 目的

問い:

- どの利用場面（業務境界の合意、後続設計の入力など）で、グループ内のフロー・受け渡し・例外・委譲を使うか。
- このグループの図から、どの判断ができるようになるか。

コツ:

- 「仕入を詳しくする」で止まったら、「この図を見て何を決めるか」を聞くと、利用場面と判断が結び付く。文書を作る・確かめる・承認する役割の割り当ては書かない。
- 上位の業務目的を書きたくなったら、全体概要への参照に置き換える。

### 4.2. 適用範囲

問い:

- どのイベントから、どの出力がそろうまでを扱うか。
- 他グループの責務・横断の順序・実装詳細のどこから先を外すか。

コツ:

- 「この出力がそろったら、次は誰の仕事か」と聞くと、終了と対象外が一度に決まる。
- 人間と AI Agent の責任分担を書きたくなったら、全体概要またはプロジェクト方針への参照に置き換える。
- プロジェクトの実行フェーズ名や一時的な仮称が紛れやすい。対象プロダクトの業務語に置き換える。

### 4.3. プロセス領域

問い:

- 各プロセスは、一つの業務目的と、yes / no で判定できる完了条件を持つか。
- 条件付き・選択のプロセスを起動しない場合も、領域を正常に終えられるか。

コツ:

- 処理を分けるか迷ったら、業務目的・主担当・更新する正本・完了条件を並べて比べる。どれも同じなら一つにまとめる。
- 「必要に応じて」と答えが返ってきたら、「何が起きたら始めるか」を聞き直す。
- 領域の入出力を領域の節に書きたくなるが、入出力は「個別プロセス主要入出力」にまとめる。手順 1 の割り当てはメモに残す。

### 4.4. データストアと個別プロセス主要入出力

問い:

- 各プロセスの入出力は、隣のプロセス・外部主体・データストアとの受け渡しとして説明できるか。
- 図の同名ノードと、データストアの行が一対一に対応するか。

コツ:

- 新しい名称や区分が要ると気づいたら、この文書で作らず、先に全体概要の見直しを依頼する。
- 主要出力の概念名と、保存先のデータストア名を混同しやすい。「何ができたか」と「どこに残すか」を分けて聞く。

### 4.5. 概念データフロー

問い:

- 起点イベントからグループの完了まで、領域間の受け渡しを順方向にたどれるか。
- 他グループのノードを隠しても、本グループの完了を説明できるか。

コツ:

- 状態の変化を描きたくなったら、プロセスと起動条件だけを残し、状態名と遷移は STSD へ委ねる。
- 図を説明する注記は長くなりやすい。省略した入出力と別図と共有するノードだけを書く。

### 4.6. 状態遷移の参照、主要例外とグループ外への委譲

問い:

- その例外は、成果の採否・正本の確定・後続の起動・人間の判断のどれを変えるか。
- 委譲先の担当者は、引き渡す情報だけで次の行動を始められるか。

コツ:

- 例外の件数を増やすより、正常に終われない理由と再開の位置を一つに決める。
- 同じグループ内の領域間の受け渡しを委譲として書きやすい。委譲は他グループと横断ユースケースへ渡すものだけにする。
- STSD や委譲先がまだなくても、安定した文書 ID をバッククォートで示す。状態の内容や他グループの処理を代わりに書かない。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. グループの最終出力から逆向きにたどり、どの出力にもつながらないプロセスを外す。
2. 条件付き・選択のプロセスを一つずつ止め、必須の出力が欠けるなら必須性か起動条件を見直す。
3. 各主要例外について、検出の前に確定した正本と、止める後続をたどり、再開の位置が一つに決まるか確かめる。
4. 状態を表す名詞や遷移の条件を本文から探し、CDFD で定義している箇所を STSD への参照に戻す。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                                               | 悪い例                                           |
| ------------ | ------------------------------------------------------------------------------------ | ------------------------------------------------ |
| グループ境界 | 仕入グループの仕入計画と入荷検品を一文書で扱う                                       | 仕入計画だけを一つの CDFD に分割する             |
| 起動条件     | 仕入先から商品が納品され、対応する発注記録を特定できた                               | 必要に応じて検品する                             |
| データストア | 「仕入記録」を全体概要と同じ名称・区分で使う                                         | 図だけ「発注 DB」と改名する                      |
| 状態遷移     | 検品を状態を変えるプロセスとして示し、商品状態の定義と遷移は STSD を参照する         | 未入荷→検品中→販売可能の遷移表を CDFD に写す     |
| 主要例外     | 発注記録を特定できない場合は入荷記録を確定せず、照合後に受入から再開する             | エラーなら適切に対応する                         |
| 委譲         | 補充判断を `cdfd-inventory`、グループ横断の順序を `cdfd-uc-replenishment` へ委譲する | 在庫グループの補充判定の手順を仕入 CDFD 内に描く |

## 7. レビュー観点

| 観点       | 確認内容                                                                 |
| ---------- | ------------------------------------------------------------------------ |
| 業務価値   | グループ内の各出力が、上位の目的と利用場面のどちらを支えるか説明できるか |
| 必須性境界 | 条件付き・選択のプロセスを起動しない場合の正常な扱いを判定できるか       |
| 設計入力   | 各プロセスの起動条件・入出力・委譲先を、後続設計の入力として使えるか     |
| 例外       | 例外ごとに止める範囲と再開の位置を判定できるか                           |

## 8. 仕上げチェック

- Frontmatter の `id` が `cdfd-<group>`、`type` が `flow` で、`based_on` に全体概要など直接の根拠とした文書だけを挙げている。
- 目的が利用場面と判断を示し、役割の割り当てを書いていない。適用範囲の責任分担は全体概要またはプロジェクト方針への参照で示している。
- 各プロセスが、グループの最終出力のどれかにつながる。
- 条件付き・選択のプロセスを起動しなくても、領域を正常に終えられる。
- 状態の定義と遷移を CDFD で書かず、状態を変えるプロセスから STSD をたどれる。
- 他グループの内部処理を描かず、委譲先が引き渡す情報で次の行動を始められる。
- 個人名、秘密情報、非公開の組織情報を含めていない。
