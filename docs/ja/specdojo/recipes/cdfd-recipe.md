# 概念データフロー図（領域別）作成レシピ

Conceptual Data Flow Diagram Area Writing Recipe

全体概要から一つのプロセス領域を引き継ぎ、一ノード一プロセスの領域内フロー、主要例外、領域外への委譲を、関係者が再現可能な形で具体化するための作成手順です。

## 1. このレシピの使い方

- 最初に、全体概要から対象領域の目的、起点イベント、主要入力・出力、データストア、隣接領域との境界を抜き出します。
- 次に、各章の問いに答えながら、目的、適用範囲、領域内プロセス一覧、概念データフロー、個別プロセス主要入出力、主要例外と領域外への委譲を具体化します。
- 最後に、レビュー観点で「一ノード一プロセスを保っているか」「領域内プロセス一覧と個別プロセス主要入出力で同じ項目を重複させていないか」を確認します。

この成果物は、上位の業務目的を Why、領域内で成立させる出力・条件を What、プロセスと例外対応を How、プロセス ID・例外 ID・委譲表の対応を Trace として整理します。上位目的の全文は複製しません。

## 2. 作成前に集める情報

| 項目           | 集める情報                                                               |
| -------------- | ------------------------------------------------------------------------ |
| 上位境界       | 全体概要の領域 ID、目的、開始点、終了点、隣接領域へ委譲する責務          |
| 利用者と判断   | 誰が領域内フローを合意し、誰が境界を承認し、誰が設計・検証へ使うか       |
| 起点と完了     | 領域を開始するイベントと、領域の責務が完了したと判定できる出力・状態     |
| プロセス候補   | 異なる業務目的、担当、正本更新、完了条件を持つ処理の候補                 |
| 起動条件       | 前段の完了、外部イベント、承認、条件値など、各プロセスの開始判定         |
| 主要入力・出力 | プロセス間、外部主体、データストアとの間で受け渡す情報・現物             |
| 正本・生成先   | 読み書きする論理的な正本、代表ファイル、後続が成果を取得する場所         |
| 必須・条件付き | 常に必要なプロセスと、承認または入力条件で起動するプロセスの境界         |
| 主要例外       | 既存正本、入力不足、生成・更新失敗、業務条件不成立など、結果を変える分岐 |
| 委譲先         | 対象領域で扱わない処理、その責任領域、引き渡す情報、本領域へ戻す条件     |
| 未決事項       | 境界、起動条件、正本、判断者が未確定な論点と、影響・決定時期             |

## 3. 全体の作成手順

1. 対象者、利用場面、対象領域の開始・終了、対象外を定義します。
2. 全体概要の領域 ID、起点イベント、主要入力・出力、データストア、委譲境界を作業メモへ転記します。
3. 最終出力から逆向きに必要な処理をたどり、業務目的または完了条件が変わる箇所でプロセスを分けます。
4. 各プロセスへ ID を付け、目的、担当、起動条件、必須性を一覧の一行へ記入します。
5. 各プロセスの主要入力、主要出力、正本・生成先を個別プロセス主要入出力へ整理します。
6. 一覧、参照、検証、dry-run など、独立した業務成果を持たない候補を支援先プロセスへ戻します。
7. 一覧のプロセスを、起動条件・依存関係が近いプロセス群ごとにまとめます。一図あたりのプロセスノードが目安15個を超える、または必須系統と条件付き系統など性質の異なる群が併存する場合は、ノードを置く前に図をいくつに分けるか、各群のプロセス範囲、共通で登場するノードを決めます。
8. 群ごとに一覧の各行を一つずつプロセスノードへ置き、イベント、外部主体、データストアとラベル付きエッジでつなぎます。
9. 正常系と条件付きプロセスの非起動経路を確認し、どの出力がそろえば領域完了かを図で示します。
10. 業務結果または後続起動を変える主要例外を選び、検出条件、扱い、継続・再開条件を表にします。
11. 領域外の処理を委譲表へ移し、委譲先、引き渡す情報、本領域へ戻す条件を記述します。
12. プロセス ID と例外 ID を使って一覧、図、個別プロセス主要入出力、例外、委譲の重複・欠落を解消します。

## 4. 各章の書き方

### 4.1. 目的

問い:

- この領域別 CDFD は、全体概要のどの領域を詳細化しますか。
- 誰が、領域内フロー、必須・条件付きの境界、主要例外、委譲のどれを判断しますか。

上位目的は参照として引き継ぎ、本領域が実現する結論と影響だけを書きます。「初期化を行う」ではなく、「後続が同じ正本から計画を開始できる状態を作る」のように、利用結果を判定できる表現にします。

### 4.2. 適用範囲

問い:

- どのイベントから、どの出力または状態がそろうまでを対象にしますか。
- 隣接領域、補助操作、実装詳細のどこから先を対象外にしますか。
- 委譲先が具体的に何を行うか（委譲する事項・引き渡す情報・戻す条件）を書き写さず、委譲先の指し先（プロセス ID・参照）だけに留めていますか。
- 特定プロジェクトの実行計画・スケジュール上のフェーズ名や、実装検討段階だけの仮称を、前提知識のない読者への説明なく持ち込んでいませんか。

対象とする業務、期間、組織、システム境界を明示し、対象外は別成果物へ委譲する詳細、補助操作、外部責務と区別して記述します。委譲先の責務内容は「主要例外と領域外への委譲」（4.6）が正本のため、ここでは指し先だけを示します。領域別 CDFD は対象プロダクトの現在の正本の姿を示す仕様であるため、プロジェクト固有の用語は持ち込みません。

### 4.3. 領域内プロセス一覧

問い:

- その行は一つの業務目的と一つの完了条件を持ちますか。
- 起動条件はイベント、前段の完了、承認、条件値のどれで判定できますか。
- 条件付きプロセスを起動しない場合、領域完了へ進めるかを説明できますか。
- 主要入力・主要出力・正本・データストアを、本章の列に重複して書いていませんか。

処理を分けるか迷う場合は、業務目的、主担当、更新する正本、完了条件を比較します。四点が同じなら一プロセス、いずれかが変わり独立した成果を引き渡すなら別プロセスの候補です。主要入力・主要出力・データストアは「個別プロセス主要入出力」（4.5）へ記載し、ここでは繰り返しません。

### 4.4. 概念データフロー

問い:

- 一覧の各行が同じ ID と名称を持つ一つのプロセスノードとして登場しますか。
- 起点イベントから領域完了または委譲先まで、正常系を順方向にたどれますか。
- 条件付きプロセスの起動条件と、起動しない場合の正常な完了経路を区別できますか。
- すべてのエッジラベルから、何がどこからどこへ渡るかを説明できますか。
- 一図のプロセスノードが目安15個を超えていませんか、または起動条件・依存関係が異なるプロセス群が一図に混在していませんか。該当する場合、業務の性質が近いプロセスへ図を分け、両図に登場する共通ノードが同一の対象を指すことを明記していますか。
- 色・絵文字は、全体概要が「凡例（本プロダクト共通）」を設けている場合はそれを参照し、本図で再掲していませんか。
- 凡例は記号説明と共通ノード・イベントの参照に留めていますか。適用範囲、領域内プロセス一覧の起動条件・必須性、主要例外と委譲、未決事項など、他章に正本がある業務事実を凡例へ書き写していませんか。

図は順序と分岐へ集中させます。内部のコマンド手順、データ項目、ログを追加したくなった場合は、概念上の入出力へ戻すか、後続の詳細成果物へ委譲します。領域外の処理は代表ノードまたは完了イベントまでに留め、内部を展開しません。

### 4.5. 個別プロセス主要入出力

問い:

- プロセスをグループ化する場合、グループが扱う範囲を数行で要約していますか。概念データフロー（4.4）を複数図に分けた場合、同じ単位でグループ化していますか。要約に領域内プロセス一覧（4.3）の起動条件・必須性を書き写していませんか。
- 各プロセスの主要入力・主要出力は、隣接プロセスまたは外部主体との受け渡しとして説明できますか。
- 正本・生成先が複数ある場合、概念名と代表パスまたは論理的な生成先を分けて示していますか。生成先にプレースホルダを使う場合、置き換え対象を明示していますか。
- 業務目的、主な担当、起動条件、必須性を、領域内プロセス一覧（4.3）と重複して書いていませんか。

プロセス ID ごとに、主要入力、主要出力、データストアを表で示します。業務目的、主な担当、起動条件、必須性は「領域内プロセス一覧」（4.3）が正本のため、ここでは繰り返しません。

### 4.6. 主要例外と領域外への委譲

問い:

- その例外は、成果の採否、正本の確定、後続起動、人間の判断のいずれかを変えますか。
- どの条件で検出し、どのプロセスまで停止し、どこから再開しますか。
- 既に確定した正本と、失敗によって未確定の生成物を区別できますか。
- 条件付きプロセスを起動しない判断そのものを、主要例外に含めていませんか。
- 対象領域の責務ではない処理は、誰に何を渡し、どの条件で戻ってきますか。委譲先に対応する領域別 CDFD がある場合、参照を併記していますか。

主要例外は件数を増やすより、正常完了できない理由と再開条件を一意にすることを優先します。委譲先が未作成でも、安定した領域 ID またはバッククォートの仮置き名で責務を示します。

### 4.7. 未決事項（任意）

- 調査で確定できる不足情報は _TODO_:、意思決定待ちは _UNDECIDED_:、仮置きする前提は _ASSUMPTION_: とします。
- 未決論点には、影響するプロセス・例外・委譲、決定者、決定時期を添えます。
- 未決事項がない場合は章を省略し、空表や「なし」だけの章を残しません。

## 5. 深掘り手順

1. 領域の最終出力から逆向きにたどり、各プロセスが必要な理由と対応する上位目的を確認します。
2. 各プロセスから逆向きにたどり、開始を判定できるイベント、前段出力、承認条件があるか確認します。
3. 各プロセスから順向きにたどり、利用者または次プロセスが使う出力と生成先があるか確認します。
4. 同じ正本を更新する複数プロセスを並べ、更新責務と完了条件が重複していないか確認します。
5. 一覧にだけあるプロセスと図にだけあるノードを列挙し、追加、削除、名称統一のいずれかで解消します。
6. 条件付きプロセスを一つずつ無効にし、必須出力が欠ける場合は必須性または起動条件を見直します。
7. 各主要例外について、検出前に確定した正本、停止する後続、再開位置を順にたどります。
8. 領域外ノードを隠しても本領域の完了条件を説明でき、委譲表から次の責任者が行動できるか確認します。
9. 領域内プロセス一覧と個別プロセス主要入出力を見比べ、同じ項目（業務目的・主な担当・起動条件・必須性、または主要入力・主要出力・データストア）が重複して書かれていないか確認します。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                                 | 悪い例                                         |
| ------------ | ---------------------------------------------------------------------- | ---------------------------------------------- |
| プロセス粒度 | 設定初期化とカタログ生成を、目的と生成物が異なる二プロセスに分ける     | init コマンド全体を一ノードに詰め込む          |
| 起動条件     | provider 利用が承認され、接続に必要な入力がそろった                    | 必要に応じて実行する                           |
| 個別入出力   | 生成先は個別プロセス主要入出力の表に記載し、一覧には業務目的だけを書く | 領域内プロセス一覧に主要入力・正本まで詰め込む |
| 条件付き     | 任意設定を起動しなくても必須初期化は完了できる                         | 任意設定がない場合の経路を示さない             |
| 図の分割     | 起動条件が異なるプロセス群ごとに図を分け、各図に専用の凡例を置く       | 系統の異なる条件付きプロセスを一図に詰め込む   |
| 主要例外     | 既存正本を検出したら置換せず、採用判断後に対象プロセスから再開する     | エラーなら適切に対応する                       |
| 委譲         | 初期カタログを計画展開へ渡し、Schedule 生成は領域外とする              | 計画展開の内部手順まで本図に描く               |

## 7. レビュー観点

| 観点           | 確認内容                                                                   | 主な確認者 |
| -------------- | -------------------------------------------------------------------------- | ---------- |
| 業務価値       | 領域内の各出力が、上位目的と対象者の利用場面のどちらを支えるか説明できる   | BA         |
| 必須・任意境界 | 必須プロセスと条件付きプロセスの起動・非起動条件を承認できる               | PO         |
| 設計入力       | 各プロセスの起動条件、入出力、正本・生成先、委譲先を識別できる             | ARC        |
| 例外           | 主要例外の検出条件、停止範囲、再開条件が判定できる                         | QE         |
| 用語整合       | プロセス、イベント、入出力、正本の名称が一覧と図で一致する                 | BA、QE     |
| 責務境界       | 一ノード一プロセスを保ち、補助操作、領域外処理、実装詳細を作り込んでいない | BA、ARC    |

## 8. 仕上げチェック

- 対象者、利用場面、対象領域、開始・終了、対象外を明記した。
- 各プロセスに ID、目的、担当、起動条件、必須性がある。
- 各プロセスに主要入力、主要出力、正本・生成先がある。
- 一覧の全プロセスが、図に一つずつプロセスノードとして登場する。
- 図の全プロセスノードが一覧の一行へ対応し、エッジに受け渡す内容のラベルがある。
- 条件付きプロセスについて、起動条件と非起動時の正常な扱いを説明できる。
- 主要例外に検出条件、扱い、継続・再開条件がある。
- 領域外委譲に委譲先、引き渡す情報、本領域へ戻す条件がある。
- 領域内プロセス一覧・個別プロセス主要入出力の各表に、一覧の全プロセスが一度ずつ登場する。
- 「凡例（本プロダクト共通）」を全体概要が設けている場合、図の凡例がそれを再掲せず参照している。
- 未決事項は _TODO_ / _UNDECIDED_ / _ASSUMPTION_ で確定情報と区別し、影響、決定者、決定時期を記載した。未決事項がなければ章を設けていない。
