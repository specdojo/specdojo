# プロジェクト憲章 作成レシピ

Project Charter Writing Recipe

プロジェクト憲章を、承認責任者が立ち上げ認可・権限委譲・予算枠・後続判断条件を判断できる内容に仕上げるための作り方を示す。

## 1. このレシピの使い方

- 憲章は、プロジェクト概要の目的・期待効果（Why）を引き継ぎ、今回認可する範囲と後続判断条件（What）を定め、権限委譲・予算枠・GO / Not GO（How）を決める。認可は承認者・承認日・証跡リンクでたどれるようにする（Trace）。
- 「作成前に集める情報」をメモでそろえてから、「全体の作成手順」の順に書く。
- 書き終えたら「レビュー観点」で読み直し、「仕上げチェック」で確かめる。

## 2. 作成前に集める情報

| 項目                     | 集める情報                                                              | 取り出し元             |
| ------------------------ | ----------------------------------------------------------------------- | ---------------------- |
| 目的と期待効果           | 目的の 1 文、承認で期待する効果                                         | プロジェクト概要       |
| 関係者                   | 承認責任者、実行責任者、協議先、影響受容者、AI Agent の関与             | ステークホルダー登録簿 |
| 認可する行為・しない行為 | 立ち上げ・詳細計画・初期準備と、本格実行・外部公開・主要投資・主要変更  | 承認責任者への確認     |
| 権限と予算枠             | 委譲する判断、留保する判断、承認済みの費用、追加支出の可否と確定時期    | 承認責任者への確認     |
| 承認の証跡               | 承認の意思と承認した文書の状態を示す記録（決定記録、Pull Request など） | 決定記録               |
| 未決の論点               | 後続判断までに決める論点と、その影響                                    | 確認の過程のメモ       |

## 3. 全体の作成手順

1. 認可対象を最初に書き、認めることと認めないことを分ける。ここが決まらないと、ほかの章の範囲が決まらない。
2. プロジェクトの目的を、概要から 1〜2 文で要約する。
3. ハイレベルスコープで、対象・対象外・未確定を分ける。
4. 初期ステークホルダーを、登録簿から認可判断に関係する分だけ要約する。
5. 権限委譲で、委譲する判断と承認責任者に留保する判断を分ける。
6. 主要前提・制約に、予算枠・公開適性・人間の判断責任を書く。
7. 本格実行開始の GO / Not GO 判断の観点と記録先を書く。
8. 承認と未決事項を書く。
9. 最後に H1 直下の冒頭文を書く。認可対象と権限委譲が決まってから書くと、本文の言い直しにならない。

## 4. 各章の書き方

### 4.1. 認可対象

問い:

- 今回、何を始めてよいと認めるのか。
- 承認しても、まだ始めてはいけない活動は何か。

コツ:

- 承認責任者に「承認の直後に始めてよいこと」を聞くと、認可対象と認可しない範囲が一度に分かれる。
- 直接根拠には、本文の判断に実際に使った文書だけを挙げる。憲章の後に作る計画書を根拠に入れやすいので注意する。

### 4.2. プロジェクトの目的

問い:

- 放置すると、誰が何に困るのか。
- 承認責任者は、どの期待効果を見て承認・保留を決めるのか。

コツ:

- 概要の本文や指標表を写したくなったら、概要への参照に置き換える。
- 期待効果は、仕様共有・業務価値・透明性・継続性など、承認の判断に使う観点へ分ける。

### 4.3. ハイレベルスコープ

問い:

- 立ち上げ時点で含める活動と、明示的に外す活動は何か。
- 決めきれない範囲はどれか。

コツ:

- 成果物の一覧や受入条件を書き始めたら、詳細化先への参照に戻す。
- 決めきれない範囲は隠さず未確定に置き、未決事項へつなげる。

### 4.4. 初期ステークホルダー

問い:

- 誰が承認し、誰が実行し、誰が影響を受けるか。
- AI Agent は、どの範囲を支援するか。

コツ:

- 個人名や連絡先ではなく、役割名・集団名で書く。登録簿から写すと公開できない識別子が紛れやすい。
- AI Agent は草案作成と整合確認の支援者とし、承認者や責任者の欄に入れない。

### 4.5. 権限委譲と主要前提・制約

問い:

- 実行責任者に任せる判断と、承認責任者が持ち続ける判断はどれか。
- 予算はどこまで使えるか。追加支出を認めるか。

コツ:

- 「PM に任せる」の 1 行で済ませず、判断ごとに決裁者と証跡を聞く。
- 金額が決まらない場合は、「追加支出なし」「外部支出は未承認」などの支出の扱いと、確定する時期を聞いて書く。

### 4.6. GO / Not GO 判断、承認、未決事項

問い:

- 本格実行や外部公開の前に、何がそろえば進めてよいか。
- 承認の意思と承認した文書の状態を、どの記録で示せるか。

コツ:

- 未決事項のうち本格実行の前に解消が要るものは、GO / Not GO の合格条件へ移す。
- 承認の記録がまだなければ承認済みと書かず、_UNDECIDED_ を残す。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 認可対象の各行が、目的のどの期待効果に応えるかを確かめ、対応のない行を外す。
2. 権限委譲の各行が、どの認可対象を進める権限かを確かめる。
3. 未決事項ごとに、認可と GO / Not GO のどちらに効くかを確かめる。
4. 詳細スコープ・設計・受入条件を書きすぎた箇所を、詳細化先への参照に戻す。

## 6. 良い例 / 悪い例

| 観点           | 良い例                                                 | 悪い例                             |
| -------------- | ------------------------------------------------------ | ---------------------------------- |
| 認可対象       | 「立ち上げ、詳細計画策定、初期準備を認可する」と書く   | 「プロジェクトを進める」とだけ書く |
| 認可しない範囲 | 「外部公開と主要支出は別途承認責任者が判断する」と書く | 承認範囲を広く曖昧にする           |
| 権限委譲       | 判断ごとに決裁者、実行責任者、証跡を示す               | 「PM に任せる」とだけ書く          |
| 予算枠         | 「追加支出は未承認。上限は詳細計画で承認責任者が確定」 | 費用に触れない                     |

## 7. レビュー観点

| 観点       | 確認内容                                                         |
| ---------- | ---------------------------------------------------------------- |
| 目的整合   | 期待効果がプロジェクト概要の目的と食い違っていないか             |
| 認可の境界 | 承認責任者が認可・保留・差し戻しを判断できる範囲になっているか   |
| 権限範囲   | 委譲と留保が判断ごとに分かれ、決裁者と証跡があるか               |
| 関係者     | 登録簿と整合し、個人情報や公開できない情報がないか               |
| 委譲の境界 | 詳細スコープ・設計・受入条件を詳細化先へ委ね、書きすぎていないか |

## 8. 仕上げチェック

- 認可対象の各行が目的の期待効果に対応し、権限委譲と承認の証跡までたどれる。
- 予算枠が、金額または支出の扱いと確定時期で書かれている。
- 承認の証跡がないのに、正式認可済みと書いていない。
- AI Agent を承認者や責任者にしていない。
