# 外部システムI/F一覧 作成レシピ

External System Interface List Writing Recipe

外部連携の抜けと過剰な詳細化を避け、設計・実装・結合テストの担当が同じ連携対象を特定できる一覧へまとめるための手順を示す。

## 1. このレシピの使い方

- 上位の目的と対象範囲から、連携後に必要な結果を選ぶ。サービス名や採用ツールの列挙から始めない。
- 境界の両端と受け渡しを整理し、連携目的・方向・方式・発生条件を YAML の各要素へまとめる。接続・認証・回復の詳細は契約へ渡す。
- 連携名と `spec_ref` から後続の設計・結合テストへ追跡する。未整備の契約は、確認者・判断時点・保留する作業を整理して計画へつなぎ、人間の PO へ採否・公開の判断材料を渡す。

## 2. 作成前に集める情報

| 入力       | 集める内容                                                  | 判断する問い                                     |
| ---------- | ----------------------------------------------------------- | ------------------------------------------------ |
| 目的と範囲 | 対象業務・利用場面、連携が必要な結果、対象外                | 連携しなければ何が未完了になるか                 |
| 境界と両端 | 自システム、外部サービス、CLI、受け渡すデータ               | どこまでが自分たちの管理責任か                   |
| 発生条件   | 人の操作、イベント、周期、前提状態                          | 誰が何を確認した後に連携するか                   |
| 正本の所在 | 詳細契約、設定、構文・データ構造の参照先                    | 実在して対象操作へ対応しているか                 |
| 失敗の影響 | 未完了・結果不明、外部変更、回復担当                        | 再実行の前に何を照合する必要があるか             |
| 確認と合意 | 一覧の管理担当、承認・公開判断者、IF ごとの確認者と外部窓口 | 誰に何を確認すると採否や公開範囲を判断できるか   |
| 未完了作業 | 未決論点、担当 Role、判断時点、依存作業、Schedule・管理記録 | 何が決まらないとどの作業が進まず、誰へ報告するか |

秘密値や個人環境の認証ファイルは収集しない。認証設計に必要な管理主体と方式の確認先だけを控える。

## 3. 全体の作成手順

1. **対象範囲とメタ情報**: 対象システムと主要な対象外、管理担当と承認・公開判断者を冒頭コメントへ整理し、一覧を識別するタイトルと ID を決める。公開先と未合意の範囲を確認し、上位の背景は参照で引き継ぐ。
2. **連携単位**: 一つの利用場面を選び、境界を越える要求・データ・結果を追う。成功後の状態や失敗の影響を比べて分割を検討し、`interfaces` の各要素を結果が伝わる `name` で識別する。
3. **両端と方式**: `source` と `target` を固定してから `direction` を読む。自システムが API を直接呼ぶか、CLI やファイルを介するかを確かめ、`kind`・`format` と形式の内訳を記す。値域・構文は `docs/specdojo/schemas/v1/esil.schema.yaml` を参照する。
4. **発生条件**: `timing` に起動イベントと前提状態を組み合わせる。「随時」を、利用者が判別できる条件へ置き換える。
5. **異常と参照**: `error_handling` に未完了・結果不明時の判断を残し、実在する詳細仕様と対象操作を照合して `spec_ref` へ接続する。未整備なら、解消する論点と影響する連携をコメントへ整理する。
6. **合意と計画**: IF ごとの確認者と合意対象、残作業と判断時点を整理する。連携名から Schedule の作業や PJR・決定記録へたどれるようにし、未登録なら PM への登録依頼と登録する時点をコメントへ残す。
7. **検証と引き継ぎ**: 一覧の schema・整形検査を実行した後、連携名から目的、契約、失敗時の確認先、保留範囲をたどる。検証結果と未解消事項を設計・実装・テスト担当へ渡し、採否・公開は人間の PO の判断へつなぐ。

## 4. 各章の書き方

YAML の記入領域ごとに、次の問いを使う。

### 4.1. メタ情報と対象範囲

- 何のシステム・利用場面の一覧か。将来案と現在の対象を区別できるか。
- 一覧を維持する Role は誰か。人間の PO はどの範囲の承認・保留・公開可否を判断するか。文書の成熟度と個々の連携の合意を混同していないか。
- 良い例は「店舗から本部への販売連携。仕入先連携は対象外」。避けたい例は「全外部システム」。範囲が読み取れる具体名を使う。

### 4.2. 連携単位と両端

- 相手が同じでも、照会と更新で完了条件・失敗影響は異ならないか。
- その行からどのデータ・結果を受け渡すか説明できるか。
- 良い例は「商品照会」と「売上登録」を分ける。避けたい例は「本部連携」一行に全操作を詰める。製品名より結果を手掛かりに分ける。

### 4.3. 方向・方式・形式

- `source` と `target` に対して、どちらへ何が流れるか。要求と応答を同じ契約で扱うか。
- 呼び出し境界は API、外部プロセス、ファイルのどれか。形式はストリーム全体を表すか。
- 良い例は「印刷 CLI の入力テキストと結果 JSON をコメントで区別」。避けたい例は「結果の一部だけを見て全体を JSON とする」。

### 4.4. 発生条件

- 人の操作またはイベントのどの時点か。起動してはいけない前提不足は何か。
- 再実行と初回実行で条件が変わるか。
- 良い例は「会計確定と控え保存の後に印字」。避けたい例は「適宜印字」。具体的な固定時刻を推測して埋めない。

### 4.5. 異常時の判断

- 応答がないとき、未処理か結果不明か。副作用を誰が照合するか。
- その間に止める操作と維持する結果は何か。確認担当が何を照合できれば再開判断へ進めるか。
- 良い例は「受付結果不明なら記録を保持し担当が照合」。避けたい例は「失敗なら即再送」。数値や引数表を増やさず、回復条件の正本を選ぶ。

### 4.6. 詳細参照と未決事項

- 詳細契約は実在し、この操作の成功・結果不明時の判断へ対応するか。参照先があっても残る未決事項は何か。
- 未整備なら、誰が何を確認・決定すれば接続できるか。解消条件と期限または判断するマイルストーンは何か。決まるまでどの業務・後続作業・公開範囲を保留するか。
- コメントを書く際は、作成・確認待ちを `_TODO_:`、意思決定待ちを `_UNDECIDED_:`、仮定を `_ASSUMPTION_:` で整理する。良い例は「`spec_ref: TBD` とし、ARC が DEV と結果照合方式を決め、外部結合テスト着手前に QE が期待結果を確認するまで当該連携の受入を保留」。避けたい例は「契約は後で作る」。論点から解消後の次アクションまでをつなぐ。

### 4.7. 合意・計画・課題への引き継ぎ

- BA に利用場面・業務影響、ARC・DEV に契約、QE に期待結果の何を確認してもらうか。外部側の確認が必要なら窓口は誰か。未特定なら誰がいつ特定するか。
- 詳細仕様の未着手・作成中・確認待ちのどこで止まっているか。担当 Role、完了条件、判断時点、依存作業は計画のどこから確認できるか。
- 未決論点や方式変更は、どの連携・後続仕様・Schedule に影響するか。PM へどの作業・課題の登録をいつ依頼し、PO へ何の判断と保留範囲を報告するか。
- 良い例は「売上登録の認証未合意を、PM が結合テスト計画確定前に PJR へ登録し、着手条件と PO の判断を追跡する」。避けたい例は「関係者確認済み」。合意対象と残作業をコメントから管理記録へ結び、登録後は実在する作業・レコードへの参照へ付け替える。

### 4.8. 検証と引き渡し

- 対象 YAML に schema・整形検査を実行し、対象ファイル、コマンド、結果を記録したか。失敗箇所を直した後の再実行まで追えるか。
- 検査では分からないコメントの内容や参照先を、読み手は連携名から確認できるか。目的・両端・方向・詳細契約を一つの利用場面として説明してもらう。
- 良い例は「検査成功と、売上登録の合意待ちによる受入保留を分けて引き継ぐ」。避けたい例は「schema が通ったので公開する」。未解消事項には担当と次アクションを添えて判断者へ渡す。

## 5. 深掘り手順

1. 一つの利用場面について、連携がなくても同じ結果を得られるかを問う。必要性を説明できなければ範囲の判断へ戻す。
2. 正常応答と応答欠落を追い、同じ行の中で異なる回復担当・完了条件が現れたら契約の分割を検討する。
3. 未決事項から影響する後続作業を逆にたどる。判断者・確認窓口が不明なら特定する作業へ、期限が決められないなら依存するマイルストーンの確認へ分解する。
4. 方式変更や連携の追加・廃止を一件仮に当てはめる。旧名との対応、詳細契約、DEV の実装対象、QE の結合テスト対象を追い、対象範囲が変わるなら PO へ何を確認するか整理する。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                       | 悪い例                                   |
| ------------ | ------------------------------------------------------------ | ---------------------------------------- |
| 仮定と合意   | CLI 経由案は仮定とし、採否・公開条件を PO に確認する         | 技術案の採用で外部公開も承認済みとする   |
| 未決の出口   | 認証方式の決定後、DEV が契約を作成し QE が着手条件を確認する | 認証は後で決める                         |
| 変更の追跡   | 連携の分割元と影響する契約・テスト対象を対応づける           | 改称後の一覧だけを渡し、旧契約を放置する |
| 管理への接続 | 連携コメントから Schedule の作業と残論点をたどれる           | 一覧に期日・進捗表をコピーして別管理する |

## 7. レビュー観点

| 観点           | 確認する内容                                                                             |
| -------------- | ---------------------------------------------------------------------------------------- |
| 必要性と範囲   | 各連携が対象の目的へ結び付き、将来案と対象外を識別できるか                               |
| 境界の一貫性   | 両端、方向、方式、形式が同じ受け渡しを表すか                                             |
| 下流への接続   | 連携名から契約と失敗時の確認先へ到達し、変更後の実装・結合テスト対象を選べるか           |
| 合意と判断     | IF ごとの確認者・合意対象と、人間の PO に残る採否・公開判断の範囲を説明できるか          |
| 委譲と未決事項 | 詳細を重複管理せず、論点から担当・解消条件・判断時点・保留する作業へたどれるか           |
| 計画と管理     | 残作業やリスクが Schedule・PJR・決定記録へつながり、未登録なら PM への依頼時点が分かるか |

## 8. 仕上げチェック

- 作成前に集めた利用場面と一覧を突き合わせ、未記載の連携候補は対象外または判断待ちとして理由を説明できる。
- 各章の問いで得た回答が同じ連携を指し、例にある担当・判断時点を実案件の確認なしで転用していない。
- 検証記録と引き継ぎ内容が一致し、確認待ちを解消済みと扱わず、次の担当が着手条件を選べる。
