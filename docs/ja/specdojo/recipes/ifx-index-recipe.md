# 外部システムI/F一覧 作成レシピ

External System Interface List Writing Recipe

外部連携の抜けと過剰な詳細化を避け、設計・実装・結合テストの担当が同じ連携対象を特定できる一覧へまとめるための作り方を示す。

## 1. このレシピの使い方

- 一覧は、上位の要求から連携が必要な理由（Why）を引き継ぎ、連携ごとの目的・両端・発生条件・異常時の判断（What）を定め、方向と方式（How）を境界の上で示す。連携名と `spec_ref` から詳細契約・結合テスト対象へたどれるようにする（Trace）。
- 「作成前に集める情報」をメモでそろえてから、「全体の作成手順」の順に書く。
- 書き終えたら「レビュー観点」で読み直し、「仕上げチェック」で確かめる。

## 2. 作成前に集める情報

| 項目         | 集める情報                                               | 取り出し元・聞く相手           |
| ------------ | -------------------------------------------------------- | ------------------------------ |
| 目的と範囲   | 対象の利用場面、連携しないと未完了になる結果、対象外     | 上位の要求・プロジェクトの範囲 |
| 境界と両端   | 自システム、外部サービス、起動する CLI、受け渡すファイル | 構成図、実装担当への確認       |
| 発生条件     | 人の操作、業務イベント、周期、起動の前提                 | 業務の流れ、利用者への確認     |
| 詳細契約     | 対象操作に対応する詳細仕様の有無                         | 外部 I/F 仕様の文書群          |
| 失敗の影響   | 未完了・結果不明になる結果、副作用を照合する担当         | 業務担当・運用担当への確認     |
| 確認者と論点 | 連携ごとの確認者と合意対象、外部側の窓口、未決の方式     | 確認の過程のメモ               |

秘密値や個人環境の認証ファイルは集めない。認証は管理主体と方式の確認先だけを控える。

## 3. 全体の作成手順

1. 冒頭コメントに対象範囲と対象外を書く。範囲が決まらないと、連携候補を入れるか外すか決められない。
2. 利用場面を一つ選び、境界を越える要求・データ・結果を追って連携単位を切り出す。サービス名や採用ツールの列挙から始めると、目的のない行が混ざる。
3. 連携ごとに `source` と `target` を先に決め、その後で `direction`・`kind`・`format` を選ぶ。両端が決まらないと方向が読めない。
4. `timing` に発生条件を書く。
5. `error_handling` に異常時の判断を書く。
6. 詳細契約を対象操作と照らして `spec_ref` を決め、未整備や未決の論点をコメントに残す。
7. 連携ごとの確認者と合意対象をコメントに書く。
8. 最後に `id`・`title` を決める。対象範囲と連携がそろってからのほうが、一覧を識別できる名前になる。

## 4. 各章の書き方

### 4.1. メタ情報と対象範囲

問い:

- 何のシステム・利用場面の一覧か。
- 将来案と今の対象をどう区別するか。

コツ:

- 「全外部システム」のような範囲は、利用場面の具体名に置き換える。
- 上位の背景や目的を写したくなったら、上位成果物への参照に置き換える。

### 4.2. 連携単位と両端

問い:

- 相手が同じでも、照会と更新で完了条件や失敗の影響は変わらないか。
- その連携で何を受け渡し、成功後にどんな結果を得るか。

コツ:

- 製品名ではなく、得る結果で分ける。名前も結果が伝わるものにする。
- 一つの行で回復の担当や完了条件が二つ出てきたら、分ける合図にする。

### 4.3. 方向・方式・形式

問い:

- 自システムは API を直接呼ぶか、CLI を起動するか、ファイルを置くか。
- 形式は受け渡すストリーム全体を表しているか。

コツ:

- 実装担当に「自分たちのコードが何を起動するか」を聞くと、背後のサービスの方式と呼び出し側の方式を取り違えない。
- 結果の一部が JSON だからといって全体を JSON にしない。入力と結果の形式が違えば内訳をコメントで分ける。

### 4.4. 発生条件

問い:

- 誰の操作、どの業務イベントの後に連携するか。
- 起動してはいけない前提不足は何か。

コツ:

- 「随時」「適宜」と書きそうになったら、直前に何が終わっているかを聞く。
- 周期が分からないときは、固定時刻を推測で埋めない。

### 4.5. 異常時の判断

問い:

- 応答がないとき、未処理なのか結果不明なのか。
- 副作用を誰が照合し、その間どの操作を止め、どの結果を保つか。

コツ:

- 業務担当に「二重に登録・印字されたら何が困るか」を聞くと、再送してよいかが分かる。
- 引数や再試行の数値を書きたくなったら、回復条件の正本への参照に置き換える。

### 4.6. 詳細参照と未決事項

問い:

- 詳細契約はこの操作の成功・結果不明の判断に対応しているか。
- 決まるまで、どの連携の受入や後続作業を保留するか。

コツ:

- 文書 ID があるだけで対応を確かめずに `spec_ref` へ入れやすい。対象操作の記述まで開いて照らす。
- 詳細契約があっても残る論点は、`spec_ref` で解決済みにせずコメントに残す。

### 4.7. 合意と計画への引き継ぎ

問い:

- 利用場面・業務影響、契約、期待結果を、それぞれ誰に確かめてもらうか。
- 外部側の確認が要るなら、窓口は誰か。

コツ:

- 「関係者確認済み」で済ませず、何について合意したかを聞く。
- 計画の期日や進捗を写したくなったら、計画や管理記録への参照に置き換える。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 各連携について、連携がなくても同じ結果を得られるかを確かめ、目的に対応しない行を外すか範囲の判断へ戻す。
2. 各連携の方向と方式が、両端の間の同じ受け渡しを表しているかを確かめる。
3. 異常時の判断ごとに、照合の担当と止める操作が決まっているかを確かめる。
4. 未決事項ごとに、影響する連携と保留する後続作業を逆にたどる。たどれない論点は、どの連携の論点かを決め直す。

## 6. 良い例 / 悪い例

| 観点       | 良い例                                                       | 悪い例                                   |
| ---------- | ------------------------------------------------------------ | ---------------------------------------- |
| 連携単位   | 「商品照会」と「売上登録」を分ける                           | 「本部連携」一行に全操作を詰める         |
| 発生条件   | 「会計確定と控え保存の後に印字」                             | 「適宜印字」                             |
| 異常時     | 「受付結果不明なら記録を保持し担当が照合」                   | 「失敗なら即再送」                       |
| 未決の出口 | 照合方式が決まるまで売上登録の受入を保留する、とコメントする | 「契約は後で作る」                       |
| 変更の追跡 | 分割元の連携名と影響する契約・テスト対象を対応づける         | 改称後の一覧だけを渡し、旧契約を放置する |

## 7. レビュー観点

| 観点         | 確認内容                                                           |
| ------------ | ------------------------------------------------------------------ |
| 必要性と範囲 | 各連携が対象の目的に結び付き、将来案と対象外を区別できるか         |
| 境界の一貫性 | 両端、方向、方式、形式が同じ受け渡しを表しているか                 |
| 下流への接続 | 連携名から詳細契約と失敗時の確認先へ着き、結合テスト対象を選べるか |
| 委譲の境界   | 引数・設定値・計画の期日を写さず、参照に置き換えているか           |

## 8. 仕上げチェック

- 集めた利用場面と一覧を突き合わせ、載っていない連携候補を対象外または判断待ちとして説明できる。
- 各節の問いへの答えが同じ連携を指し、例の担当や条件を実案件の確認なしで転用していない。
- 確認待ちの連携を解消済みと扱っていない。
