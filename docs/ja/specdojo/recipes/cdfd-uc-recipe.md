# 概念データフロー図（ユースケース別）作成レシピ

Conceptual Data Flow Diagram Use Case Writing Recipe

全体概要で選定した一つのユースケースまたは系統について、開始から終了までの流れと、受け渡す情報・物を具体化するための作成手順です。参加単位と詳細化の境界は rulebook の「描き方の選択」に従います。

## 1. このレシピの使い方

- 全体概要からケース ID、業務目的、参加単位、開始・終了を抜き出します。
- 目的、適用範囲、役割表、データストアの部分集合を作り、上から下へ進む図で受け渡しを示します。
- 最後に表と図の名称・順序、全体概要との境界、有効な参照先を確認します。対象範囲の例外時の戻りを漏れなく図にし、線が多ければ図を分けます。

ケース ID、参加単位の名称・領域 ID、データストア名を軸に、範囲・表・図を対応させます。引き渡し ID を追加せず、情報・物の名前を線のラベルにします。

## 2. 作成前に集める情報

| 項目         | 集める情報                                                                   |
| ------------ | ---------------------------------------------------------------------------- |
| 対象ケース   | 全体概要にあるケース ID、業務名、業務目的                                    |
| 描く単位     | rulebook の「描き方の選択」で決める参加単位と詳細化の境界                    |
| 共通の領域   | 複数の系統が共通して通る領域と、内部を描く 1 か所の正本・その参照先          |
| 開始と終了   | 開始する出来事と、最後に利用可能になる成果                                   |
| 役割と順序   | 全体概要と同じグループ・区分、領域 ID、正常系の通過順、各参加単位の責務      |
| 受け渡し     | 隣接する参加単位やデータストアの間で渡す情報・物                             |
| データストア | 全体概要にある名称、マスタ・構成／トランザクションの区分、参照・更新する内容 |
| 共通の約束   | 全体概要の責任分担、凡例（絵文字の有無・割り当て）、Orchestrator の指示の図  |
| 参照先       | 有効な全体概要、必要な詳細文書と STSD。status が `deprecated` の文書は除く   |
| 例外の戻り   | 対象範囲のすべての戻り、補完・再判断を担う参加単位、返す不足情報や差異       |
| 未決事項     | 境界、名称、責務、判断者が未確定な論点、影響、決定者、決定時期               |

## 3. 全体の作成手順

1. 全体概要の「詳細 CDFD 一覧」からケースを選び、rulebook の「描き方の選択」で参加単位を決めます。共通して通る領域の内部を描く正本を全体概要またはその領域の詳細文書の 1 か所に定め、ほかの詳細では 1 ノードと受け渡しの線だけにします。
2. その業務が何のためにあるかを、開始からどの成果までを成立させるかという 1〜2 文で書きます。読み手の承認・設計・確認作業は含めません。
3. 対象と対象外を 1 行ずつ書き、共通原則は全体概要を参照します。`based_on` と本文の参照先が有効な文書であることを確認します。
4. 全体概要と同じグループ・区分ごとに節を設け、正常系の順序と責務を役割表だけで示します。共通して通る領域の内部の正本を「参照先」に示します。PDCA が必要なら独立した任意の列を追加します。
5. 全体概要から、このケースで参照・更新するデータストアを同じ名称・区分で切り出し、関連する参加単位と利用内容を書きます。
6. 開始イベント、参加単位、終了の出来事を上から下へ並べ、渡す情報・物の名前を線のラベルにします。D2 は `direction: down` とし、引き渡し条件のイベントや Orchestrator は置きません。
7. データストアを同名ノードで加え、表の各行と図を対応させます。イベントは一ノード一出来事の短い文とし、長ければ原文を保って改行します。
8. 図に業務の言葉で題を付け、読み取れることを 1 文で説明します。凡例は全体概要への短い参照にし、ノードの絵文字の有無・割り当てを文書内の全図と系統間でそろえます。
9. 対象範囲に例外時の戻りがある場合は、「概念データフロー」に図を追加し、返す情報を重要度で絞らず線にします。戻りの線は上側のノードを左辺にした `a <- b` で書きます。共通して通る領域の内部はその正本へ委ね、外へ返す情報は描きます。
10. rulebook の分割の目安（一図の線が 15 本超、または一ノードの入出力が合計 10 本以上）と読みやすさを確認し、正常系は連続する段、戻りは戻り先や段ごとに図を分けます。必要な線を削らず、同じ名称・領域 ID の共有ノードでつなぎます。
11. ケース ID、名称、領域 ID で範囲・表・図を突き合わせ、内部処理や状態定義・遷移の重複を除きます。

## 4. 各章の書き方

### 4.1. 目的

問い:

- そのユースケースまたは系統は何のためにありますか。
- どの出来事から、どの成果または判断までを成立させますか。

「欠品した商品を補充し、売場で販売できるようにする」のように業務の目的を 1〜2 文で書きます。BA・QE・承認者などの読み手の役割は書きません。

### 4.2. 適用範囲

問い:

- ケース ID、参加単位、開始・終了は全体概要と一致していますか。
- 対象と対象外がそれぞれ 1 行で分かりますか。
- 共通原則と調整役の指示を全体概要に委ねていますか。
- 本文と `based_on` に `deprecated` の文書が残っていませんか。

全体概要の選定を変える必要があれば先に全体概要を見直します。未作成の参照先は ID をインラインコードで仮置きします。

### 4.3. プロセス領域

問い:

- rulebook の「描き方の選択」に従い、全体概要と同じまとまりの節にしていますか。
- 各節は役割表だけですか。主要入力・主要出力・データストアの箇条書きが残っていませんか。
- 順序、プロセスグループ・区分、含む領域、横断上の役割、参照先を示していますか。
- 共通して通る領域の内部を描く正本が 1 か所に定まり、ほかの詳細では 1 ノードと受け渡しの線だけにしていますか。内部の正本を「参照先」に示していますか。
- PDCA を示す場合は独立した任意の列にし、全体概要の区分と混同していませんか。

表の一行を図の一つのプロセスノードに対応させます。全体概要を名称と領域の正本とし、入力・出力の正本は図にします。

### 4.4. データストア

問い:

- 対象ケースで参照・更新する正本だけですか。
- 名称と区分は全体概要と一致していますか。
- 関連する参加単位を名称・領域 ID で示し、利用内容を説明していますか。
- 表の各行と図の同名ノードが対応していますか。

マスタ・構成データとトランザクションデータに分け、該当する行がない区分は節ごと省略します。

### 4.5. 概念データフロー

問い:

- 正常系の参加単位を開始から終了まで上から下へ追えますか。
- 一つのイベントに一つの出来事だけを書き、短い文または改行で読めますか。入口の文言は選んだ方式の規定に合っていますか。
- 渡す情報・物を線の名詞ラベルから読み取れますか。条件のイベントや引き渡し ID が残っていませんか。
- Orchestrator と調整要求・応答を図から外していますか。
- 図の題は業務の言葉ですか。説明は読み取れることの 1 文ですか。
- 絵文字の有無・割り当ては全体概要の凡例に合い、文書内の全図とほかの系統でそろっていますか。
- 線数・集中の目安や読みにくさに応じて図を分け、共有ノードから接続を追えますか。

D2 は `direction: down` とします。必要な承認は「承認済みの補充依頼」など成果の性質として線に表し、条件の判定ノードは置きません。凡例は全体概要を参照します。

### 4.6. 例外時の戻りの図

問い:

- 対象範囲の戻りをすべて集め、重要度や線の多さを理由に除いていませんか。
- 戻す不足情報・差異と、補完・再判断を担う参加単位が線から分かりますか。
- 再提示も「修正・承認済みの補充依頼」などの情報として描いていますか。
- 戻り先や段ごとに図を分けても、必要な戻りと再提示が共有ノードでつながっていますか。

戻りがある場合は「概念データフロー」の節に漏れなく描き、通常の図と名称・領域 ID をそろえます。戻りがない場合だけ図を省略します。共通して通る領域の内部は 1 か所の正本に委ねます。「引き渡し」「例外時の戻り先」の章や、戻す条件・再開条件の表は作りません。

### 4.7. 未決事項（任意）

- 調査で確定できる不足情報は _TODO_:、意思決定待ちは _UNDECIDED_:、仮置きする前提は _ASSUMPTION_: とします。
- 未決論点には影響するケース・参加単位、決定者、決定時期を添えます。
- ない場合は章を省略し、空表や「なし」だけの章を残しません。

## 5. 深掘り手順

1. 最後の成果から逆にたどり、各参加単位と受け渡しが業務目的に必要か確認します。
2. 開始イベントから順にたどり、前段の成果が次段へ情報・物として渡っているか確認します。
3. 全体概要の区分と領域 ID を突き合わせ、PDCA の値で区分を置き換えた行を直します。
4. データストアを一つずつ確かめ、このケースの情報・物の受け渡しに不要なものを除きます。
5. 状態定義・遷移や内部プロセスが残っていれば、責任を持つ有効な文書の参照へ移します。
6. 収集した戻りと図を突き合わせ、すべての不足情報や差異が補完責任のある参加単位へ届くか確認します。共通して通る領域の内部は正本の参照で追います。
7. D2 を `d2 --layout elk` で SVG に出力し、上下の順序、ノードとラベルの大きさを確認します。読みづらい場合はイベントの改行や図の分割を見直します。

## 6. 良い例 / 悪い例

| 観点        | 良い例                                            | 悪い例                                             |
| ----------- | ------------------------------------------------- | -------------------------------------------------- |
| 目的        | 欠品した商品を補充し、売場で販売できるようにする  | BA が承認し、QE が検証へ使う                       |
| 区分と PDCA | 区分は調達、PDCA は別列で Do                      | 区分を Do に置き換える                             |
| 共通の領域  | 内部の正本を一つ決め、ほかでは 1 ノードで受け渡す | 各系統で同じ領域の内部を詳しく描く                 |
| 絵文字      | 全体概要の凡例に合わせて全図・系統でそろえる      | 正常系だけに付け、戻りや別系統では外す             |
| 渡す情報    | 在庫から仕入へ「承認済みの補充依頼」を直接つなぐ  | 途中に「H-01 受理できる」というイベントを置く      |
| イベント    | 「在庫が補充基準を下回った」を必要なら改行        | 複数の出来事を一つの長い六角形に詰める             |
| 戻り        | 戻りをすべて描き、線が多ければ戻り先ごとに分ける  | 重要な戻りだけを残し、ほかを図から削る             |
| 参照先      | 有効な全体概要を参照する                          | `deprecated` のグループ別 CDFD を参照する          |
| 調整役      | Orchestrator の指示は全体概要の図に任せる         | 詳細の図に Orchestrator と各段階への要求を再掲する |
| 状態責務    | 商品状態は STSD を参照する                        | 未発注から販売可能への状態遷移を本書で定義する     |

## 7. レビュー観点

| 観点       | 確認内容                                                   | 主な確認者                 |
| ---------- | ---------------------------------------------------------- | -------------------------- |
| 業務価値   | 目的が業務の存在理由・成果を示し、終了時の成果と一致する   | 業務分析担当、業務責任者   |
| 範囲と粒度 | rulebook の「描き方の選択」と全体概要に合う                | 業務分析担当               |
| 表と図     | 順序・名称・領域 ID が対応し、受け渡しを線から読み取れる   | 品質確認担当               |
| データ整合 | データストアの名称・区分と凡例が全体概要に合う             | 技術メンター、品質確認担当 |
| 戻り       | 対象範囲の戻りに漏れがなく、分割後も戻す情報と責任が分かる | 業務責任者、品質確認担当   |
| 共通の領域 | 内部の正本が 1 か所に定まり、ほかでは 1 ノードで受け渡す   | アーキテクト               |
| 絵文字     | 全体概要の凡例に合わせ、文書内と系統間で有無をそろえる     | 品質確認担当               |
| 正本の境界 | 調整・状態遷移・内部処理を重複させず、有効な文書を参照する | アーキテクト               |

確認者の呼称は、対象プロジェクトのロール定義または責任分担文書で正式な担当へ対応付けます。

## 8. 仕上げチェック

- 全体概要のケース ID、業務名、目的、名称・領域 ID を引き継いだ。
- 目的は業務のための 1〜2 文、適用範囲は対象と対象外が 1 行ずつになっている。
- 各節が役割表だけで、区分と任意の PDCA 列を分けた。
- 共通して通る領域の内部は 1 か所だけで描き、ほかの詳細では 1 ノードと受け渡しの線にして正本を参照した。
- 表と図の参加単位、データストアが対応し、開始から終了まで縦に追える。
- イベントは一ノード一出来事で短く、入口の原文を保っている。
- 受け渡しは線のラベルにあり、引き渡し ID・条件イベント・旧来の引き渡し／戻り先の章がない。
- Orchestrator を詳細の図に置かず、全体概要の指示の図へ委ねた。
- 図の題は業務の言葉、説明は読み取れることの 1 文で、凡例は全体概要を参照している。
- 絵文字の有無・割り当てが全体概要の凡例に合い、文書内の全図と系統間でそろっている。
- 対象範囲の例外時の戻りを省略せず描き、線数・集中の目安や読みやすさに応じて戻り先・段ごとに図を分け、共有ノードで追える。条件表や内部の再試行手順を置いていない。
- `based_on` と本文に `deprecated` の参照先がなく、状態定義・遷移を複製していない。
- 未決事項がない場合は章を省略し、公開範囲に不適切な情報を含めていない。
