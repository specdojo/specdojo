# 概念データフロー図（ユースケース別）作成レシピ

Conceptual Data Flow Diagram Use Case Writing Recipe

全体概要で選定した横断ユースケースを、プロセスグループの順序、引き渡す情報、引き渡し条件、条件不成立時の戻り先へ具体化し、グループ内部を重複させずに合意するための作成手順です。

## 1. このレシピの使い方

- 最初に、全体概要から一つのケース ID、業務目的、横断するプロセスグループを抜き出し、開始イベントと終了条件を短いメモにします。
- 次に、正常系のグループごとに、説明文、主要入力・主要出力・データストアの箇条書き、横断上の役割表を作ります。
- 全体概要の「データストア」から引き渡しに使う部分集合を切り出し、グループ代表ノードと引き渡し条件だけで図を作ります。
- その後、隣接するグループ間ごとに渡す情報、受け側を開始できる条件、受け取れない場合の戻す条件を具体化し、条件不成立時の戻り先と再開条件を表へ整理します。
- 最後に、全体概要との名称整合、全引き渡しの追跡、グループ内部と状態遷移の非重複をレビューします。

この成果物は、上位で合意した業務目的を Why として引き継ぎ、グループ間で成立させる情報と条件を What、順序と戻し方を How、ケース ID・引き渡し ID・参照先の対応を Trace として整理します。内部プロセスや状態遷移を複製せず、責任を持つ文書へ接続します。

## 2. 作成前に集める情報

| 項目             | 集める情報                                                                         |
| ---------------- | ---------------------------------------------------------------------------------- |
| 対象ケース       | 全体概要にある `C-<nn>`、ユースケース名、業務目的                                  |
| 開始と終了       | 最初のグループを起動するイベント、最後のグループが成果を利用可能と判断する条件     |
| 参加グループ     | 正常系で通過する二つ以上のプロセスグループ名、領域 ID、通過順、主要入出力          |
| グループ別責務   | 各グループが前段から受け取るものと、次段へ引き渡す成果                             |
| グループ別 CDFD  | 各参加グループの `cdfd-<group>` と、そこに定義された境界入出力                     |
| 引き渡す情報     | 受け側が業務を始めるために必要な情報・物・承認結果                                 |
| 引き渡し条件     | 必須情報の充足、承認、記録確定、現物との一致など、受け側が確認できる条件           |
| 戻す条件         | 情報不足、不一致、承認未了など、受け側が引き渡しを受理できない条件                 |
| 関連データストア | 引き渡す情報または条件判定の正本となる、全体概要の「データストア」にある名称と区分 |
| 判断者           | 引き渡し可否、戻し、再開を最終判断する人間のロール                                 |
| 状態の参照先     | 状態一覧と状態遷移図を統合した STSD。内容は転記せず参照先だけ控える                |
| 未決事項         | 横断境界、条件、戻り先、判断者が未確定な論点と、影響、決定者、決定時期             |

## 3. 全体の作成手順

1. 全体概要から対象のケース ID、ユースケース名、業務目的、参加グループを抜き出します。
2. 最初のグループが動き始める出来事を開始イベント、最後のグループが成果を受理した状態を終了条件として一文ずつ書きます。
3. 正常系の参加グループを順に並べ、各グループについて役割の説明文、主要入力・主要出力・データストアの箇条書き、横断上の役割表を作ります。
4. グループ名、含む領域 ID、境界入出力を全体概要と各 `cdfd-<group>` で突き合わせ、名称ゆれを解消します。
5. 隣接グループ間ごとに引き渡し候補を作り、正常順序に沿って `H-<nn>` を仮置きします。
6. 全体概要の「データストア」から、引き渡す情報または条件判定に使う行だけを同じ区分で転記し、関連する引き渡し ID と利用内容を記入します。
7. 開始イベント、グループ代表ノード、引き渡し条件、終了条件を左から右へ並べ、引き渡し ID と情報名を付けて図にします。
8. 「データストア」の各行を同名ノードとして図へ加え、行とノードが一対一で対応することを確認します。
9. 各引き渡しについて、情報、受け側が yes / no で判定できる引き渡し条件、送り元へ戻す条件を書きます。
10. 条件不成立ごとに、補完責任を持つ戻り先、戻す情報、同じ引き渡しを再評価できる再開条件を整理します。
11. 内部プロセス名、内部例外、状態名・遷移、実装項目を探し、対応する `cdfd-<group>` と STSD の参照へ置き換えます。
12. ケース ID と引き渡し ID を使って、範囲、プロセス領域、データストア、図、引き渡し表、戻り先表の重複・欠落を解消します。

## 4. 各章の書き方

### 4.1. 目的

問い:

- 誰がグループの通過順と責任境界を承認しますか。
- 誰が引き渡す情報と条件を設計入力として使いますか。
- 誰がグループ間の重複・欠落と戻り経路を確認しますか。

「業務を分かりやすくする」ではなく、「店主代表が在庫・仕入・販売の引き渡し条件を承認する」のように、対象者と利用結果を結び付けます。上位の業務目的はケース ID で引き継ぎ、同じ背景説明を繰り返しません。

### 4.2. 適用範囲

問い:

- ケース ID、ユースケース名、参加グループは全体概要と一致していますか。
- どの出来事で最初のグループが始まり、どの成果を誰が受理すれば終わりますか。
- 対象となる組織、システム境界、現物の範囲を説明できますか。
- 内部プロセス、補助操作、状態遷移、実装詳細をどこへ委ねますか。
- 承認と最終判断を担う人間のロールを参照できますか。

開始と終了は単なる期間ではなく、発生または成立を判定できる出来事・成果で区切ります。参加グループの追加や削除が必要なら、横断図だけで補正せず、全体概要へ判断を戻します。

### 4.3. プロセス領域

問い:

- 正常系のグループを開始から終了まで一節ずつ順に並べましたか。
- 各節が、説明文、主要入力・主要出力・データストアの箇条書き、横断上の役割表の順になっていますか。
- 各グループの名称と領域 ID は全体概要と同じですか。
- 主要入力・主要出力と横断上の役割は、前段から受け取るものと次段へ渡すものに限定されていますか。
- 各グループの内部を確認できる `cdfd-<group>` を一意に示せますか。

各節の表の一行を一つの代表ノードへ対応させます。同じグループが正常系で再登場する場合は節を分け、前回と異なる引き渡し目的を説明します。内部の処理順や担当は書き写しません。

### 4.4. データストア

問い:

- 引き渡す情報または引き渡し条件の判定に必要なデータストアだけを掲載していますか。
- 名称と区分は全体概要の「データストア」と一致していますか。
- 各行に関連する引き渡し ID と、横断上の利用内容がありますか。
- 各行が概念データフローの同名ノードに対応していますか。

全体概要の「データストア」から必要な行を切り出し、マスタ・構成データとトランザクションデータの区分を保ちます。グループ内部だけで使うデータストアは載せません。新しい名称や区分が必要なら、先に全体概要を見直します。

### 4.5. 概念データフロー

問い:

- 一つの角丸長方形が一つのプロセスグループを表していますか。
- 開始イベントから終了条件まで、正常系のグループ順序を左から右へ追えますか。
- 引き渡し ID と情報名を、図と引き渡し表で対応付けられますか。
- 図へ置いたデータストアは、引き渡し条件または引き渡す情報の正本として必要ですか。
- グループ内部のプロセス、例外、状態遷移を図へ混ぜていませんか。

グループ代表ノードの間に、引き渡し条件を表すイベントノードを置きます。データストアを加える場合も、どの内部処理が読む・書くかは描かず、横断条件の根拠となる情報だけを示します。図直後の注記で凡例、線種、省略境界、選定したデータストアを説明します。

### 4.6. 引き渡し

問い:

- 隣接するすべてのグループ間に一つ以上の引き渡しがありますか。
- 引き渡す情報は、受け側が何を受け取るか分かる名詞になっていますか。
- 引き渡し条件は、情報の充足、承認、記録確定、現物との一致を判定できますか。
- 条件を満たさないとき、何をどのグループへ戻すか分かりますか。

まず受け側が開始前に確認するチェックを列挙し、そのチェックに必要な情報だけを引き渡しへ残します。送り元の作業完了を条件にするのではなく、受け側が受理できる成果の状態を記述します。

### 4.7. 例外時の戻り先

問い:

- 各引き渡しの戻す条件を、戻り先表の条件不成立へ対応させましたか。
- 不足を補完または再判断できるグループが戻り先になっていますか。
- 戻す情報から、不足・不一致・判断待ちの内容が分かりますか。
- 再開条件は同じ引き渡しを再評価できる形になっていますか。

戻り先は内部プロセスではなくグループまでに留めます。受け側内部の再試行やログは扱わず、先行グループへ情報・判断を戻すことで横断順序が変わる場合だけを記載します。

### 4.8. 未決事項（任意）

- 調査で確定できる不足情報は _TODO_:、意思決定待ちは _UNDECIDED_:、仮置きする前提は _ASSUMPTION_: とします。
- 未決論点には、影響するケース ID または引き渡し ID、決定者、決定時期を添えます。
- 未決事項がない場合は章を省略し、空表や「なし」だけの章を残しません。

## 5. 深掘り手順

1. 最後のグループが受理する成果から逆向きにたどり、直前の引き渡し情報と条件が本当に必要かを確認します。
2. 開始イベントから順方向にたどり、各グループが前段から受け取らないと作れない成果を特定します。
3. 各引き渡し条件を yes / no の質問へ置き換え、判定者と根拠情報を答えられない条件を具体化します。
4. グループ代表ノードを隠し、内部プロセス名が図や表に残っていないか検索します。残っていればグループ責務または参照へ置き換えます。
5. 状態を表す語を検索し、状態の意味や遷移を定義している箇所を STSD の参照へ移します。
6. 引き渡し ID を一つずつ追い、データストア、図、引き渡し表、戻り先表で情報と条件が一致するか確認します。
7. 条件不成立を一つずつ仮定し、戻り先が不足を補完でき、再開条件の成立後に同じ引き渡しへ戻れるか確認します。
8. データストアを一つずつ外しても引き渡し条件を説明できるか試し、不要なものを図から削除します。

## 6. 良い例 / 悪い例

| 観点           | 良い例                                                        | 悪い例                                               |
| -------------- | ------------------------------------------------------------- | ---------------------------------------------------- |
| 対象ケース     | `C-02` の在庫 → 仕入 → 販売を扱う                             | 在庫グループ内の在庫確認だけを扱う                   |
| グループノード | 「在庫（P-05〜P-06）」を一つの代表ノードにする                | 補充判定や在庫更新を別々のプロセスノードにする       |
| 引き渡す情報   | 在庫から仕入へ「補充対象、数量、判断者」を渡す                | 必要なデータ一式を渡す                               |
| 引き渡し条件   | 補充対象と数量が確定し、店主代表が発注判断を承認した          | 在庫処理が適切に完了した                             |
| 戻す条件       | 商品または数量を一意に特定できない場合は在庫へ戻す            | エラー時は前へ戻す                                   |
| 再開条件       | 修正済みの補充依頼を店主代表が再承認し、`H-01` を再評価できる | 問題が解決したら再開する                             |
| データストア   | 引き渡し判定に使う在庫記録を全体概要と同じ名称で置く          | 図だけ「在庫 DB」と改名し、内部テーブルまで描く      |
| 状態責務       | 商品状態は STSD を参照し、図には引き渡し成立条件だけを描く    | 未発注 → 入荷済み → 販売可能の遷移を横断図で定義する |
| グループ内例外 | 発注不可の結果を在庫へ戻す条件だけを扱う                      | 仕入先選定、再発注、返品処理の手順を横断図へ展開する |

## 7. レビュー観点

| 観点         | 確認内容                                                                         | 主な確認者                 |
| ------------ | -------------------------------------------------------------------------------- | -------------------------- |
| 業務価値     | ケースの終了条件が上位の業務目的を満たし、各引き渡しがその成立に必要と説明できる | 業務分析担当、店主代表     |
| 横断範囲     | 二つ以上の参加グループ、通過順、領域 ID が全体概要と一致する                     | 業務分析担当               |
| 引き渡し     | 情報、条件、戻す条件を受け側が yes / no で判定できる                             | 業務分析担当、技術メンター |
| 責任境界     | 戻り先と判断者が明確で、内部プロセスを横断側で再定義していない                   | 店主代表、アーキテクト     |
| 図の追跡性   | ケース ID、引き渡し ID、グループ名、領域 ID を表と図で対応付けられる             | 品質確認担当               |
| データ整合   | 関連データストアの名称・区分が全体概要と一致し、条件判定に必要なものだけがある   | 技術メンター、品質確認担当 |
| 状態責務     | 状態定義・遷移を複製せず、必要な STSD へ接続している                             | 技術メンター               |
| 例外時の再開 | 条件不成立から戻り先、戻す情報、再開条件、再評価する引き渡しまでたどれる         | 品質確認担当、店主代表     |

「業務分析担当」「品質確認担当」「技術メンター」「アーキテクト」は、対象プロジェクトのロール定義または責任分担文書で正式な担当へ対応付けます。

## 8. 仕上げチェック

- 全体概要から一つのケース ID、ユースケース名、業務目的、二つ以上の参加グループを引き継いだ。
- 開始イベントと終了条件を第三者が判定できる形で記述した。
- 参加グループを正常系の順序で一節ずつ並べ、各節を説明文、三つの箇条書き、役割表の順で構成した。
- 隣接グループ間へ `H-<nn>` を付け、情報、引き渡し条件、戻す条件を記述した。
- 図の一つのプロセスノードが一つのプロセスグループを表し、内部プロセスを描いていない。
- 図の開始から終了までをたどれ、引き渡し ID と情報名を表へ対応付けられる。
- 「データストア」は全体概要と同じ名称・区分の部分集合で、各行を引き渡し ID と図の同名ノードへ対応させた。
- 全引き渡しについて、条件不成立、戻り先、戻す情報、再開条件を確認した。
- グループ内部の領域・プロセス・主要例外・操作手順を再掲していない。
- 状態の定義、遷移表、状態遷移図を記載せず、必要な STSD を参照した。
- 未決事項は共通ラベルで確定情報と区別し、ない場合は章を設けていない。
- 個人情報、秘密情報、非公開の組織情報など、公開範囲に不適切な内容を含めていない。
