# 概念データフロー図（ユースケース別）作成レシピ

Conceptual Data Flow Diagram Use Case Writing Recipe

全体概要で選んだ一つのユースケースまたは系統について、開始から終了までの流れと受け渡す情報・物を、読み手が図から追える内容に仕上げるための作り方を示す。

## 1. このレシピの使い方

- 全体概要のケース ID と業務目的（Why）を引き継ぎ、開始・終了と参加単位の範囲（What）を決め、参加単位の責務と受け渡しの線（How）で流れを示す。ケース ID・領域 ID・データストア名を表と図で同じにして、流れを全体概要までたどれるようにする（Trace）。

## 2. 作成前に集める情報

| 項目             | 集める情報                                                           | 取り出し元                       |
| ---------------- | -------------------------------------------------------------------- | -------------------------------- |
| 対象ケース       | ケース ID、業務名、業務目的、採用された描き方（横断・系統）          | 全体概要の「詳細 CDFD 一覧」     |
| 開始と終了       | 開始する出来事の原文と、最後に利用できるようになる成果               | 全体概要の「プロセス領域」       |
| 参加単位と順序   | グループ・区分、領域 ID、正常系の通過順、条件付きでだけ通る領域      | 全体概要、各領域の担当者への確認 |
| 共用する領域     | 複数の系統が通る領域と、その内部を描く文書                           | 全体概要、領域の詳細文書         |
| 受け渡し         | 隣り合う参加単位・データストアの間で渡す情報・物の名前               | 各領域の担当者への確認           |
| データストア     | このケースで参照・更新するものと、その名称・区分                     | 全体概要の「データストア」       |
| 例外時の戻り     | 不足や差異を返す先、返す情報、補完後に再提示する情報                 | 各領域の担当者への確認、過去事例 |
| 状態・調整の正本 | 状態を定める STSD、Orchestrator の指示の図、凡例（絵文字の割り当て） | 全体概要、STSD                   |

## 3. 全体の作成手順

1. 概念データフローの正常系の図を最初に描く。順序の正本は図なので、表から書くと順序欄と図がずれる。
2. 図の参加単位を 1 行ずつプロセス領域の役割表へ移し、順序欄を図から転記する。
3. 図に出たデータストアだけをデータストアの表へ移す。
4. 例外時の戻りを集め、戻りの図を描く。
5. 目的と適用範囲を書く。図が決まってからだと、開始と終了を図と同じ言葉で書ける。
6. 未決事項があれば最後の章にまとめ、最後に H1 直下の導入文を書く。

## 4. 各章の書き方

### 4.1. 導入文と目的

問い:

- どのケース ID と業務名の流れを示す文書か。
- その業務がないと、誰が何に困るのか。

コツ:

- 導入文はケース ID と業務名を全体概要から写し、言い換えない。ケースを特定しない導入文は、どの選定を詳細化したか分からなくなる。
- 目的に「BA が承認する」「QE が検証に使う」などの読み手の作業を書きそうになったら、業務が成り立たせる成果に言い直す。

### 4.2. 適用範囲

問い:

- 開始の出来事と、終了時に使えるようになる成果は何か。
- 内部の手順や状態遷移のうち、どれを別の文書へ委ねるか。

コツ:

- 全体概要の選定と食い違ったら、本書で範囲を変えず、先に全体概要を直す。
- 共通の責任分担や状態の定義は写さず、正本への参照に置き換える。

### 4.3. プロセス領域

問い:

- 各参加単位はこのケースで何を引き受けるか。
- 常に通る領域と、計画連携や補完のときだけ通る領域はどれか。

コツ:

- 条件付きで通る領域は、順序欄を「計画連携時」「補完時」などの参加場面にすると、主経路と混ざらない。
- 共用する領域の内部を描きたくなったら、内部を描く文書を参照先に書き、本書では 1 行に留める。
- PDCA の段階を区分の代わりに書きやすい。区分は全体概要の名前を使う。

### 4.4. データストア

問い:

- このケースで参照・更新するのはどれか。
- 各データストアを、どの参加単位が何のために使うか。

コツ:

- 全体概要の一覧を丸ごと写しやすい。図に線が引かれないものは外す。
- 保存先やカラムを書き始めたら、用途の 1 文に戻す。

### 4.5. 概念データフロー

問い:

- 前段の成果は、どの情報・物として次段へ渡るか。
- 図の題と説明 1 文で、何を読み取ってほしいか。

コツ:

- 線のラベルを担当者に聞くときは「次の人は何を受け取れば始められるか」と聞く。名詞で答えが返り、条件のイベントを置かずに済む。
- 承認が要る受け渡しは「承認済みの補充依頼」のように、渡す物の性質で表す。
- 線が込み入ったら、線を削らず業務の段ごとに図を分け、共有ノードで接続を示す。

### 4.6. 例外時の戻りの図

問い:

- どの不足や差異を、どの参加単位へ返すか。
- 補完した後に、何を再提示するか。

コツ:

- 担当者は重要な戻りだけを挙げやすい。「差し戻した事例をすべて」と聞いて集める。
- 共用する領域の内部の戻りは内部を描く文書に任せ、外へ返す情報だけを描く。

### 4.7. 未決事項（任意）

問い:

- 境界、名称、責務、判断者のうち決まっていないものはどれか。
- その論点はどのケース・参加単位に影響するか。

コツ:

- 本文の `_UNDECIDED_` と 1 対 1 で対応させる。決着した論点は本文へ反映して消す。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 終了の成果から逆にたどり、業務目的に寄与しない参加単位や線を外す。
2. 役割表の各行が図のどのノードに当たるかを確かめ、図にない行を外す。
3. データストアごとに、読み書きする線があるかを確かめる。
4. 状態の定義・遷移や内部の処理が残っていれば、正本の参照に置き換える。
5. 集めた戻りごとに、返す先の参加単位と再提示の線があるかを確かめる。

## 6. 良い例 / 悪い例

| 観点       | 良い例                                                | 悪い例                                        |
| ---------- | ----------------------------------------------------- | --------------------------------------------- |
| 導入文     | 「ケース `C-02`『欠品から補充まで』の流れを示す」     | 「補充業務の流れを示す」とだけ書く            |
| 区分       | 区分は全体概要の「調達」とし、PDCA は別の列で Do      | 区分の欄に Do と書く                          |
| 共用領域   | 内部を描く文書を一つ決め、ほかでは 1 ノードで受け渡す | 系統ごとに同じ領域の内部を描き直す            |
| 渡す情報   | 在庫から仕入へ「承認済みの補充依頼」を直接つなぐ      | 途中に「H-01 受理できる」というイベントを置く |
| イベント   | 「在庫が補充基準を下回った」を必要なら改行する        | 複数の出来事を一つのノードに詰める            |
| 戻り       | すべての戻りを描き、多ければ戻り先ごとに図を分ける    | 重要な戻りだけを残し、ほかを削る              |
| 状態の責務 | 商品の状態は STSD を参照する                          | 未発注から販売可能までの遷移を本書で定める    |

## 7. レビュー観点

| 観点           | 確認内容                                                         |
| -------------- | ---------------------------------------------------------------- |
| 業務価値       | 終了時の成果が目的に応え、目的に寄与しない参加単位や線がないか   |
| 表と図の対応   | 役割表の順序と名称が図と一致し、条件付きの領域が主経路と分かるか |
| 受け渡しの具体 | 各線のラベルから、次の参加単位が受け取る情報・物を特定できるか   |
| 戻りの網羅     | 集めた戻りがすべて、返す先と再提示の線とともに描かれているか     |
| 正本の境界     | 共用領域の内部・状態遷移・Orchestrator の調整を写していないか    |

## 8. 仕上げチェック

- ケース ID、領域 ID、データストア名が、導入文・表・図・全体概要で同じ表記になっている。
- 図を分けた場合も、共有ノードをたどって開始から終了まで追える。
- 絵文字の有無と割り当てが、文書内の全図とほかの系統でそろっている。
