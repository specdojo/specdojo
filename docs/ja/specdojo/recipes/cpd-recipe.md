# C4コンポーネント図 作成レシピ

C4 Component Diagram Writing Recipe

上位コンテナの責務を内部のまとまりへ分け、依存方向と確認すべき境界を見つける手順です。機能名を並べただけの図から、実装と結合設計の判断に使える構成へ具体化します。

## 1. このレシピの使い方

- 上位図から、対象コンテナの目的と利用者へ返す結果を取り出します。目的の全文は繰り返さず、分割の理由として使います。
- 内部の責務、利用者と外部依存への接点、保存する正本を整理し、責任が重なる箇所を分けます。別プロセス化やクラス設計はここで決めません。
- コンポーネント名と関係 ID を軸に、分割の理由、情報の受け渡し、失敗時の観測点をつなぎます。未確認の依存は確認先とともに引き継ぎます。

## 2. 作成前に集める情報

| 情報       | 書き出す問い                                                                             |
| ---------- | ---------------------------------------------------------------------------------------- |
| 上位の境界 | 分解する実行単位はどれか。外部のまま残す利用者・ストア・他システムは何か                 |
| 必要な成果 | 利用者は何に困り、どの結果を確認して次へ進むか。期待価値と成功基準の上位参照はどこか     |
| 責務の候補 | 入力の解釈、判断の適用、記録、外部依頼のうち別々に変更・確認したいものは何か             |
| 内容の根拠 | 設計上の決定と実装確認済みの事実を分けられるか。未確認なのに具体化した配置はないか       |
| 結合の論点 | 相手が不在・拒否・応答欠落のとき、どの結果が不明になるか                                 |
| 詳細化先   | 値・構文・構造・復旧条件を更新する正本と担当はどこか                                     |
| 確認と合意 | 構成・実装・結合・業務を誰にいつ確認してもらうか。最終合意と公開可否の判断者は誰か       |
| 公開と保守 | 誰にどの媒体で見せるか。公開前に確認する情報と、境界・契約が変わったときの相談先はどこか |

## 3. 全体の作成手順

1. 「概要」に対象コンテナと上位図との対応、分割が必要な理由、今回扱わない範囲を書きます。上位の業務課題・成功基準の参照先を選び、確認者・合意者と公開範囲を整理します。
2. 一つの代表依頼について、入力から結果の確認までをたどり、誰が結果を作り、誰が記録するかをメモします。
3. 責務の候補を比較し、異なる変更理由・失敗結果を持つまとまりを分けます。名前だけ違って入出力が同じ候補は統合します。
4. 「要素と境界の定義」で各まとまりの責務と入出力、論理配置を言葉にし、利用先を決めます。分割・共通化の採用理由を上位の目的または技術制約へ結び付けます。
5. 「C4コンポーネント図（Mermaid）」に主要な依頼・依存を描き、関係 ID で授受情報と詳細化先へ接続します。
6. 「技術前提・制約と検証観点」で成功と失敗の観測点を選び、「メモ / 将来課題」に未確認箇所の担当・判断者、判断時点と解消条件を残します。
7. 図の要素・関係を定義表から逆引きし、差異と省略理由を確かめます。リポジトリの検査設定から対象と期待結果を整理し、構文・描画・参照の確認結果を実行記録へ残します。
8. 構成上の確認結果と業務・公開判断の材料を分けて合意者へ渡します。改訂なら、変更した関係から後続設計・実装・検証・作業順への影響をたどり、更新先を決めます。

## 4. 各章の書き方

### 4.1. 概要

対象のコンテナ名を伏せても、分割によって何を判断したいか説明できますか。利用者の課題と成功基準をどの上位記述から引き継ぎますか。構成案と実装の確認済み構成を区別していますか。

確認対象から逆に、構成・実装・結合・業務それぞれの確認者と時点を探します。最終合意者と公開する相手・媒体・範囲を概要にまとめ、役割割当てや合意記録の参照へつなぎます。上位に成功基準が見つからないときは、BA への確認事項にします。

良い例は「交代時に未印字を引き継ぐという上位の成功基準に対応し、保存と印字の責任境界を結合設計へ渡す」です。「販売を管理する」だけでは分割の用途を判断できません。

### 4.2. C4コンポーネント図（Mermaid）

矢印は利用する側から利用される側へ向いていますか。応答を逆依存として足していませんか。上位で外側だった要素を内部へ移していませんか。

一つの正常な依頼と外部応答が欠ける依頼をたどり、確認が必要な経路を選びます。全呼び出しを増やす前に、主要経路を省いて判断が変わるかを考え、選んだ理由と省いた範囲を短く添えます。

良い例は「保存後の印字依頼を主要経路とし、画面内操作は別コンテナの責務として省く」です。「読みやすくするため矢印を減らした」だけでは、欠けた経路の影響を確かめられません。

### 4.3. 要素と境界の定義

その責務を削ると誰が結果を作れなくなりますか。二つの要素が同じ記録の更新判断を持っていませんか。論理配置をソースパスと混同していませんか。

まず対象コンテナ境界と利用者の接点、次にコンポーネントと論理配置、ストアと外部依存、最後に関係と詳細の正本を整理します。Person・ストア・外部依存が見当たらない場合は、直接の接点が別要素なのか、本当に非該当なのかを上位図から確認します。

入出力は「確認済み販売明細」「保存結果」のように意味で表し、判断する側と記録する側の分界を明らかにします。共通化の候補には、分けたままの場合と比べてどの判断の重複を減らせるかを問い、採用理由を残します。関係ごとに値・構文・構造を管理する正本を探し、未作成なら仮参照と確認先を残します。

良い例は「商品参照と販売記録の保存接点を共通化し、販売可否の判断は会計側に残す」です。「共通処理がすべて判断する」では更新責任を追えません。

### 4.4. 技術前提・制約と検証観点

相手の失敗が起点の成功を取り消す条件は確認済みですか。応答欠落で成功・未実施のどちらかに即断していませんか。正本を変更せず再生成できる派生物は何ですか。

各境界で「与える条件 → 観測する結果」を一組ずつ考え、確認できない期待値は詳細契約へ引き継ぎます。

良い例は「`REL-08` の応答欠落時に、保存済み販売と印字の結果不明を別々に観測する」です。「異常系を確認する」では、どの関係で何を見ればよいか決まりません。

### 4.5. メモ / 将来課題

未確認事項を確定するにはどの根拠が必要ですか。調査する担当と採否を判断する人を分けられますか。いつまでに判断できなければ、どの後続作業や合意を保留しますか。

未確認の主張を仮定・判断待ち・確認作業に分け、共通ラベルで確定事項と区別します。対象要素・関係から影響先をたどり、未発生の懸念か、発生済みの阻害か、変更提案か、決定済みかを整理します。継続追跡する論点は PM へ渡す PJR の参照、未起票なら登録候補の理由・起票担当・判断時点につなぎます。

良い例は「印字応答欠落の回復条件を ARC が整理し QE が観測点を確認する。人間の PO が実装着手前に採否を判断し、未解消なら印字経路を保留する。PM へ PJR 登録候補として渡す」です。「保存を検討」では、次の作業と判断者が決まりません。

## 5. 深掘り手順

1. 出力から入力へ戻り、その出力が必要な利用場面と、作成する責務を確認します。利用されない出力のためだけの分割は見直します。
2. 外部依頼の直前と直後で止まった場合を比べ、残る記録と結果不明を区別できるか考えます。
3. 共通機構を外した場合に複数の責務へ同じ判断が散らばるかを確かめます。単に同名関数があるという理由では共通化しません。
4. 分割・共通化の採用理由を上位の目的または技術制約まで戻って確かめます。根拠を辿れない候補は仮定と確認事項へ戻します。
5. 一つの変更を仮定し、上位の境界、内部の責務、関係 ID、詳細契約、結合観測点、作業順のどこが変わるかたどります。更新または更新不要の理由と担当を変更記録へ残し、再描画・再検証する範囲を選びます。

## 6. 良い例 / 悪い例

| 観点       | 良い例                                                                           | 悪い例                                 |
| ---------- | -------------------------------------------------------------------------------- | -------------------------------------- |
| 分割の理由 | 印字失敗と販売確定を分けて確認するため、印字連携を独立した責務にする             | コマンドがあるので同じ数の部品を作る   |
| 依存の意味 | 会計処理が保存済み控えの印字を依頼し、発行結果を受ける                           | 会計と印字が相互に処理する             |
| 確定度     | 同一プロセス内の論理配置案。実装対応は DEV が確認する                            | 未調査のソースパスを実装済みとして書く |
| 障害の分界 | 印字応答欠落時は販売結果と紙面の確認を分ける                                     | エラーなら全部やり直す                 |
| 公開判断   | OPS が公開先に応じて本文・図・ラベル・参照先を確認し、残る懸念を人間の PO へ渡す | lint が通ったので公開できる            |
| 改訂の影響 | 保存責務の統合で変わる関係を起点に、データ設計と結合観測点の更新担当を決める     | 図だけ差し替えて更新を終える           |

## 7. レビュー観点

| 観点         | 確認する問い                                                               |
| ------------ | -------------------------------------------------------------------------- |
| 目的と分割   | 各責務の必要性を上位コンテナの結果へ結び付けられるか                       |
| 更新責任     | 同じ結果を二つの部品が別々に確定しないか                                   |
| 境界の観測   | 外部不在・拒否・応答欠落で、起点が確認すべき結果を区別できるか             |
| 詳細への委譲 | 値や構文を変えたとき、本図にも同じ変更が必要な重複を作っていないか         |
| 合意の材料   | 技術・業務の確認結果と残る論点から、判断者が承認・保留・差し戻しを選べるか |
| 追従の範囲   | 上位境界・外部契約の変更から、図・定義表と後続設計の更新先を辿れるか       |

## 8. 仕上げチェック

- 図から定義表、定義表から図へ照合し、全要素・関係 ID の対応と省略理由を確認したか。
- 実装未確認の配置、外部連携の保証、未決の業務判断を仮定や論点として区別したか。
- 引き継ぎ先・担当・判断者と判断時点が特定でき、未解消時に進められる作業と保留する作業を説明できるか。
- メタ情報・参照・構文と描画の確認記録を辿れ、ラベル欠け・重なり・境界の誤読を解消したか。
- 公開する本文・図・ラベル・参照先に残る非公開情報の懸念を OPS と確認し、人間の PO が公開先と可否を判断する材料を用意したか。
