# C4コンポーネント図 作成レシピ

C4 Component Diagram Writing Recipe

上位コンテナの責務を内部のまとまりへ分け、依存方向と確認すべき境界を見つける手順です。機能名を並べただけの図から、実装と結合設計の判断に使える構成へ具体化します。

## 1. このレシピの使い方

- 上位図から、対象コンテナの目的と利用者へ返す結果を取り出します。目的の全文は繰り返さず、分割の理由として使います。
- 内部の責務、利用者と外部依存への接点、保存する正本を整理し、責任が重なる箇所を分けます。別プロセス化やクラス設計はここで決めません。
- コンポーネント名と関係 ID を軸に、分割の理由、情報の受け渡し、失敗時の観測点をつなぎます。未確認の依存は確認先とともに引き継ぎます。

## 2. 作成前に集める情報

| 情報       | 書き出す問い                                                                       |
| ---------- | ---------------------------------------------------------------------------------- |
| 上位の境界 | 分解する実行単位はどれか。外部のまま残す利用者・ストア・他システムは何か           |
| 必要な成果 | 利用者は何を依頼し、どの結果を確認して次へ進むか                                   |
| 責務の候補 | 入力の解釈、判断の適用、記録、外部依頼のうち別々に変更・確認したいものは何か       |
| 内容の根拠 | 設計上の決定と実装確認済みの事実を分けられるか。未確認なのに具体化した配置はないか |
| 結合の論点 | 相手が不在・拒否・応答欠落のとき、どの結果が不明になるか                           |
| 詳細化先   | 値・構文・構造・復旧条件を更新する正本と担当はどこか                               |

## 3. 全体の作成手順

1. 「概要」に対象コンテナと上位図との対応、分割が必要な理由、今回扱わない範囲を書きます。
2. 一つの代表依頼について、入力から結果の確認までをたどり、誰が結果を作り、誰が記録するかをメモします。
3. 責務の候補を比較し、異なる変更理由・失敗結果を持つまとまりを分けます。名前だけ違って入出力が同じ候補は統合します。
4. 「要素と境界の定義」で各まとまりの責務と入出力、論理配置を言葉にし、利用先を決めます。
5. 「C4コンポーネント図（Mermaid）」に主要な依頼・依存を描き、関係 ID で授受情報と詳細化先へ接続します。
6. 「技術前提・制約と検証観点」で成功と失敗の観測点を選び、「メモ / 将来課題」に未確認箇所の解消条件を残します。

## 4. 各章の書き方

### 4.1. 概要

対象のコンテナ名を伏せても、分割によって何を判断したいか説明できますか。上位の目的を引き継いでいますか。構成案と実装の確認済み構成を区別していますか。

「販売を管理する」から一歩進め、「販売結果の保持と印字の失敗を分けて扱うため」と書くと、分割の理由を追えます。

### 4.2. C4コンポーネント図（Mermaid）

矢印は利用する側から利用される側へ向いていますか。応答を逆依存として足していませんか。上位で外側だった要素を内部へ移していませんか。

一つの正常な依頼と外部応答が欠ける依頼をたどり、確認が必要な経路を選びます。全呼び出しを増やす前に、主要経路を省いて判断が変わるかを考えます。

### 4.3. 要素と境界の定義

その責務を削ると誰が結果を作れなくなりますか。二つの要素が同じ記録の更新判断を持っていませんか。論理配置をソースパスと混同していませんか。

入出力は「確認済み販売明細」「保存結果」のように意味で表します。項目名や型を並べるより、判断する側と記録する側の分界を明らかにします。

### 4.4. 技術前提・制約と検証観点

相手の失敗が起点の成功を取り消す条件は確認済みですか。応答欠落で成功・未実施のどちらかに即断していませんか。正本を変更せず再生成できる派生物は何ですか。

各境界で「与える条件 → 観測する結果」を一組ずつ考え、確認できない期待値は詳細契約へ引き継ぎます。

### 4.5. メモ / 将来課題

未確認事項を確定するにはどの根拠が必要ですか。担当が判断した後、どの定義・図・結合対象が変わりますか。影響先から次の作業を起こせますか。

「保存を検討」では着手できません。「DEV が保存方式を確認し、ARC が更新責務、QE が途中失敗の観測点を設計へ反映する」まで具体化します。

## 5. 深掘り手順

1. 出力から入力へ戻り、その出力が必要な利用場面と、作成する責務を確認します。利用されない出力のためだけの分割は見直します。
2. 外部依頼の直前と直後で止まった場合を比べ、残る記録と結果不明を区別できるか考えます。
3. 共通機構を外した場合に複数の責務へ同じ判断が散らばるかを確かめます。単に同名関数があるという理由では共通化しません。
4. 一つの変更を仮定し、上位の境界、内部の責務、関係、結合観測点のどこが変わるかたどります。

## 6. 良い例 / 悪い例

| 観点       | 良い例                                                               | 悪い例                                 |
| ---------- | -------------------------------------------------------------------- | -------------------------------------- |
| 分割の理由 | 印字失敗と販売確定を分けて確認するため、印字連携を独立した責務にする | コマンドがあるので同じ数の部品を作る   |
| 依存の意味 | 会計処理が保存済み控えの印字を依頼し、発行結果を受ける               | 会計と印字が相互に処理する             |
| 確定度     | 同一プロセス内の論理配置案。実装対応は DEV が確認する                | 未調査のソースパスを実装済みとして書く |
| 障害の分界 | 印字応答欠落時は販売結果と紙面の確認を分ける                         | エラーなら全部やり直す                 |

## 7. レビュー観点

| 観点         | 確認する問い                                                       |
| ------------ | ------------------------------------------------------------------ |
| 目的と分割   | 各責務の必要性を上位コンテナの結果へ結び付けられるか               |
| 更新責任     | 同じ結果を二つの部品が別々に確定しないか                           |
| 境界の観測   | 外部不在・拒否・応答欠落で、起点が確認すべき結果を区別できるか     |
| 詳細への委譲 | 値や構文を変えたとき、本図にも同じ変更が必要な重複を作っていないか |

## 8. 仕上げチェック

- 図と定義表で同じ要素名・依存方向を使い、授受情報と関係 ID を対応付けたか。
- 実装未確認の配置、外部連携の保証、未決の業務判断を仮定や論点として区別したか。
- 引き継ぎ先と担当が特定でき、次の設計・検証へ移れるか。
