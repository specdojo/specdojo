# C4コンポーネント図 作成レシピ

C4 Component Diagram Writing Recipe

上位コンテナの責務を内部のまとまりへ分け、機能名を並べただけの図から、実装と結合設計の判断に使える構成へ具体化する作り方を示す。

## 1. このレシピの使い方

- CPD は、上位図と上位の要求から分割の理由（Why）を引き継ぎ、コンポーネントの責務と境界で受け渡す情報（What）を定め、依存方向と失敗時の観測点（How）を示す。これらをコンポーネント名と関係 ID でたどれるようにする（Trace）。

## 2. 作成前に集める情報

| 項目       | 集める情報                                                             | 取り出し元・聞く相手    |
| ---------- | ---------------------------------------------------------------------- | ----------------------- |
| 上位の境界 | 展開するコンテナ、外部のまま残す利用者・ストア・他システム             | 上位のコンテナ図        |
| 必要な成果 | 利用者が確認して次へ進む結果、期待価値・成功基準の記述箇所             | 上位の要求・目的、BA    |
| 代表の依頼 | 入力から結果の確認までの流れと、結果を作る側・記録する側               | 業務の流れ、BA・DEV     |
| 責務の候補 | 入力の解釈・判断・記録・外部依頼のうち、別々に変更・確認したいもの     | 実装担当（DEV）への確認 |
| 確定度     | 設計上の決定と実装で確かめた構成の区別、未確認の配置                   | 実装担当（DEV）への確認 |
| 結合の論点 | 相手の不在・拒否・応答欠落で不明になる結果、依存する共通機構の保証範囲 | 外部 IF の仕様、ARC・QE |

## 3. 全体の作成手順

1. 代表の依頼を一つ選び、入力から結果の確認までをたどってメモする。分割の候補は、この流れで結果を作る側と記録する側から見つける。
2. 「要素と境界の定義」を先に書く。責務と入出力が決まらないと、図の矢印の意味が決まらない。
3. 「C4コンポーネント図（Mermaid）」に、主要な依頼と依存を関係 ID 付きで描く。
4. 「技術前提・制約と検証観点」で、関係ごとの成功と失敗の観測点を書く。
5. 確かめられなかった配置や保証を「メモ / 将来課題」へ移す。
6. 最後に「概要」を書く。分割と未確認の範囲が決まってから書くと、対象外と確定度を言い切れる。

## 4. 各章の書き方

### 4.1. 概要

問い:

- この分割で、後続の設計・実装は何を判断できるようになるか。今回扱わない範囲は何か。
- 期待価値・成功基準は、どの上位記述から引き継ぐか。

コツ:

- 上位の目的や成功基準は写さず、参照に置き換える。上位に見つからなければ BA に聞き、答えが出るまで論点に残す。
- 構成案と確かめた構成を混ぜやすい。DEV に「どこまでコードで確かめたか」を聞き、残りは _ASSUMPTION_: にする。

### 4.2. C4コンポーネント図（Mermaid）

問い:

- 矢印は利用する側から利用される側へ向いているか。応答を逆向きの依存として足していないか。
- 主要経路を省くと、どの判断が変わるか。

コツ:

- 正常な依頼と外部応答が欠ける依頼の二本をたどると、描く経路と省く経路を選べる。
- 同じ端末で動くという理由で、上位図の外側の要素を内側へ移しやすい。

### 4.3. 要素と境界の定義

問い:

- その責務を削ると、誰が結果を作れなくなるか。
- 二つの要素が同じ記録の更新判断を持っていないか。

コツ:

- 入出力は「確認済み販売明細」「保存結果」のように意味で書くと、判断する側と記録する側の分界が見える。
- 共通化の候補には「分けたままだと、どの判断が重複するか」を聞く。同名の関数があるだけでは共通化の理由にならない。
- 値・構文・構造は写さず、管理する文書への参照に置き換える。未作成なら仮の参照と確認先を残す。

### 4.4. 技術前提・制約と検証観点

技術前提の問い:

- どの共通機構・外部依存に頼るか。排他・原子性・再試行の保証は確かめたか。

検証観点の問い:

- 各境界で、どの条件を与えると何を観測すれば成功・失敗を区別できるか。

コツ:

- 応答欠落を、成功・未実施のどちらかに即断しやすい。結果不明として別に観測する。
- 確かめられない期待値は、詳細の契約へ引き継ぐ。

### 4.5. メモ / 将来課題

問い:

- 未確認事項を確定するには、どの根拠が要るか。
- 確定しないまま進むと、どの要素・関係と後続の作業が止まるか。

コツ:

- 未確認の主張を仮定・判断待ち・確認作業に分けると、当面の扱いと解消条件を書ける。
- 対象の要素名・関係 ID を必ず添える。添えないと影響先をたどれない。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 各出力が、どの利用場面と上位の成功基準に応えるかを確かめ、使われない出力のためだけの分割を外す。
2. 外部依頼の直前と直後で止まった場合を比べ、残る記録と結果不明を区別できない関係を探す。
3. 共通機構を外したとき、複数の責務へ同じ判断が散らばるかを確かめる。散らばらない共通化は外す。
4. 一つの変更（境界・責務・外部契約）を仮定し、関係 ID から上位図・詳細契約・観測点・作業順への影響をたどる。たどれない関係は定義を補う。

## 6. 良い例 / 悪い例

| 観点       | 良い例                                                                   | 悪い例                                 |
| ---------- | ------------------------------------------------------------------------ | -------------------------------------- |
| 分割の用途 | 「交代時の未印字引き継ぎに応え、保存と印字の責任境界を結合設計へ渡す」   | 「販売を管理する」                     |
| 分割の理由 | 印字失敗と販売確定を分けて確かめるため、印字連携を独立させる             | コマンドの数だけ部品を作る             |
| 依存の意味 | 会計処理が保存済み控えの印字を依頼し、発行結果を受ける                   | 会計と印字が相互に処理する             |
| 共通化     | 商品参照と販売記録の保存接点を共通化し、販売可否の判断は会計側に残す     | 共通処理がすべて判断する               |
| 確定度     | 同一プロセス内の論理配置案とし、実装対応は DEV が確かめる                | 未調査のソースパスを実装済みとして書く |
| 観測点     | `REL-08` の応答欠落で、保存済み販売と印字の結果不明を別々に観測する      | 「異常系を確認する」                   |
| 未確認事項 | 印字応答欠落の回復条件が定まるまで自動再送を認めず、印字経路の受入を保留 | 「保存を検討」                         |

## 7. レビュー観点

| 観点       | 確認内容                                                           |
| ---------- | ------------------------------------------------------------------ |
| 目的と分割 | 各責務の必要性を、上位コンテナが返す結果へ結び付けられるか         |
| 更新責任   | 同じ結果を二つの要素が別々に確定していないか                       |
| 境界の観測 | 外部の不在・拒否・応答欠落で、起点が確かめる結果を区別できるか     |
| 委譲の境界 | 値・構文・構造を写さず、変更が詳細の文書だけで済む形になっているか |

## 8. 仕上げチェック

- 図で省いた経路ごとに、省いても判断が変わらない理由を書いている。
- 実装で確かめていない配置や外部の保証を、確定事項として書いていない。
- 未確認事項ごとに、影響する要素・関係 ID と当面の扱いが分かる。
