# 概念データフロー図（全体概要）作成レシピ

Conceptual Data Flow Diagram Overview Writing Recipe

業務または運用の全体像を、プロセス領域のまとまりと、それらが読み書きするデータの関係として描くための作り方を示す。

## 1. このレシピの使い方

- 全体概要は、上位の業務目的を領域分割の理由として引き継ぎ（Why）、領域・グループまたは区分・データストアの分け方を定め（What）、受け渡しを代表ノードとストアの線で示す（How）。領域 ID とグループ・区分・ストアの名称で、領域表・ストア一覧・図・詳細 CDFD 一覧をたどれるようにする（Trace）。
- 「作成前に集める情報」をメモでそろえてから、「全体の作成手順」の順に書く。
- 書き終えたら「レビュー観点」で読み直し、「仕上げチェック」で確かめる。

## 2. 作成前に集める情報

| 項目                 | 集める情報                                                                   | 取り出し元                         |
| -------------------- | ---------------------------------------------------------------------------- | ---------------------------------- |
| 対象範囲             | 開始点、終了点、対象業務、組織・システム境界、別成果物に任せる事項           | 業務の責任者への確認、上位の概要   |
| 業務成果と起点       | 開始から結果利用までの業務成果と、それぞれの開始を判定できる出来事           | 業務の担当者への聞き取り、業務記録 |
| 担当                 | 各領域を主に担う役割、複数で担う場合の管理責任、人間の最終判断者             | 役割の定義（Role code の一覧など） |
| データの正本         | 各領域が参照・更新する台帳・文書・設定と、更新される契機、物理的な所在       | 既存の台帳・保管場所、実装         |
| 受け渡しと外部主体   | 領域とストアの間で動く情報・物、対象範囲外から入力を渡す主体と受け取る主体   | 業務の担当者への聞き取り           |
| 構成方式と横断の流れ | 今の方式か系統の関係を描く方式か、複数グループをまたぐ業務または各系統の流れ | 業務の責任者への確認               |

## 3. 全体の作成手順

1. 適用範囲を最初に書き、開始点・終了点・対象外を決める。範囲が決まらないと、領域の候補が増え続ける。
2. 構成方式を選ぶ。代表ノードをプロセスグループにするか区分にするかで、以降の章の単位が変わる。
3. 業務成果ごとに領域を切り、補助操作を支援先の領域へ戻してから、グループまたは区分にまとめる。
4. 領域表から参照・更新するストアを集め、ストア一覧を作る。図に置く名称はここで決める。
5. 代表ノードとストアを線でつなぎ、図を描く。
6. 詳細 CDFD 一覧で、各グループまたは各系統の詳細化先を決める。
7. 各章の冒頭文（領域数・グループ数、ストアの区分の意味、採用方式）を書く。表と図ができてから書くと数と名称がずれない。
8. 最後に、H1 直下の導入文と目的を書く。領域分割が決まってから書くと、本文の言い直しにならない。
9. 決めきれない論点は `_UNDECIDED_` を残し、未決事項に影響と合わせて置く。

## 4. 各章の書き方

### 4.1. 導入文と目的

問い:

- この文書は、どの業務または運用を扱うのか。
- 全体像として、どの領域のまとまりとデータの関係を示すのか。

コツ:

- 導入文は対象を一文で定義するだけにし、効果や指標を並べたくなったら上位の概要への参照に置き換える。
- 目的に承認や引き継ぎの作業、読み手の役割を書き始めたら外す。

### 4.2. 適用範囲

問い:

- どの出来事から、どの成果または判断までを扱うのか。
- 一覧・検索・検証などの補助操作と、領域内部の手順を、どこへ任せるのか。

コツ:

- 責任分担は、対応する方針文書があれば参照し、なければ原則を一文で書く。
- 特定プロジェクトの計画上のフェーズ名を持ち込みやすい。前提知識のない読者に通じる言葉に直す。

### 4.3. プロセス領域

問い:

- 各領域に、ほかと区別できる起点イベントと業務成果があるか。
- そのグループまたは区分の業務目的が、見出しと表から読み取れるか。

コツ:

- 分けるか迷ったら、起点、最終出力、更新する正本の三点を比べる。三点とも同じなら一つにする。
- 定義系の領域の起点を「時期が到来した」など実行の契機で書きやすい。定義系は「要件が判明した」で書く。
- 担当は役割の定義から取り、「全員」と書きたくなったら管理責任を持つ役割を聞く。
- 冒頭文の領域数とグループ数は、表を数えて書く。

### 4.4. データストア

問い:

- 各ストアは、何の正本かが名称から分かるか。
- 承認された変更で更新されるか、業務活動のたびに更新されるか。

コツ:

- 定義から生成される生成物は、更新の契機が違うため生成元と別の区分になりやすい。生成元を主な内容に書く。
- 保管先は、実装があれば確定値を、設計中なら候補と `_UNDECIDED_` を書き、概念段階では列ごと外す。推測でパスを書かない。
- 一つの保管先を複数のストアで共有するときは、どこまでがこのストアかと共有相手を注記する。
- 冒頭文では区分の意味、パスの略記、扱わないもの（リポジトリ基盤・開発環境の設定など）を各一文で書く。

### 4.5. 概念データフロー（概要）

問い:

- 線のラベルから、何がどこからどこへ渡るかが分かるか。
- 対象範囲の外にいるのは誰か。

コツ:

- 冒頭文で採用方式と示す関係を宣言してから描くと、分割の切り口がぶれない。
- 店主など対象範囲内の参加者を外部主体に描きやすい。参加者は領域の担当とし、参加者から直接受け取る入力を図から省いたときは、図の直後に省いたことを一文で書く。
- ノードが多くなったら、今の方式はストアの区分か使い方の流れで、系統の関係を描く方式はデータの種類で分ける。調整役（Orchestrator）の指示はデータの図に混ぜず、別の図にする。
- 図の説明に作図の約束を書き始めたら、凡例へ移す。

### 4.6. 詳細 CDFD 一覧

問い:

- 各領域の内部は、どの詳細 CDFD が扱うのか。
- 複数グループをまたぐ業務、または各系統の流れは、どこで詳細化するのか。

コツ:

- 単一グループに閉じる業務はグループ別の詳細 CDFD に任せ、横断のユースケース別 CDFD は必要になってから足す。
- 「未作成」などの作成状況を書きたくなったら、登録簿で追跡し、本文には ID だけを書く。

### 4.7. 凡例（本プロダクト共通）（任意）

問い:

- 複数の詳細 CDFD が、同じ形状・色・絵文字を使うか。
- 各図は、凡例を再掲せずに参照できるか。

コツ:

- 詳細 CDFD が一つだけなら章を設けない。

### 4.8. 未決事項（条件付き）

問い:

- 境界、名称、責務、判断者、保管先のうち、決めきれないものはどれか。
- 決まると、どの領域・ストア・図・詳細化先が変わるか。

コツ:

- 本文の `_UNDECIDED_` から論点を拾うと、表との対応が漏れない。決まった論点は本文へ反映して表から外す。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 各領域の業務目的から逆にたどり、応える利用者の判断または業務課題がない領域を外すかまとめる。
2. 図の出力の線を順にたどり、他のグループ・区分・外部主体が使うか、ストアに残るかを確かめる。行き先のない線を外す。
3. 同じストアを更新するグループを並べ、更新の責務が重なっていないかを確かめる。
4. ストア一覧のうち、図のどの線にも現れない行を探し、受け渡しの欠けか不要なストアかを決める。
5. コマンド名・画面名・ファイル名を隠しても目的と受け渡しを説明できるかを確かめ、説明できない行を概念の粒度へ戻す。
6. 補助操作を外したことで、必要な検証の入力が消えていないかを確かめ、支援先の入力として残す。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                                                          | 悪い例                                                   |
| ------------ | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 業務目的     | 現金販売を記録し、商品を顧客へ渡す                                                              | 販売登録画面を実行する                                   |
| 起点イベント | 定期実行定義は「定期的に確認・実行する事項が判明した」                                          | 定期実行定義に「指定された時期が到来した」（実行の契機） |
| グループ粒度 | 店頭販売とつけ販売を「販売」グループにまとめ、値引きや取消の手順は詳細 CDFD へ任せる            | 全体概要に値引き、取消、再入力を別ノードで並べる         |
| 受け渡し     | 購入依頼と支払、売価、つけ上限を受け、販売記録とつけ販売の記録を残す                            | 入力はフォーム、出力は JSON                              |
| データストア | 販売取引の正本「販売記録」と、その生成物「日次締め記録」を分ける                                | `sales-table`。または販売記録と締め記録を一つにまとめる  |
| 補助操作     | 商品検索は販売の入力確認として扱う                                                              | 商品検索を独立したプロセス領域にする                     |
| 図の要素     | 顧客と仕入先を外部主体、店主を各領域の担当として内側に置く                                      | 店主を外部主体として描く                                 |
| ノード数     | 代表ノード 6 とデータストア 15 の計 21 なのでデータの種類で分け、調整役がいれば指示を別図にする | 21 ノードを 1 図に並べる                                 |
| 詳細化先     | 販売グループを `cdfd-sales` へ、つけ販売から精算までを `cdfd-uc-credit-sales` へ割り当てる      | 領域ごとに詳細 CDFD を作り、横断業務を各図に重複記載する |

## 7. レビュー観点

| 観点       | 確認内容                                                                                 |
| ---------- | ---------------------------------------------------------------------------------------- |
| 業務価値   | 各領域の目的が、対象者のどの課題・判断・業務成果に応えるかを説明できるか                 |
| 対象境界   | 領域、補助操作、領域内部、人間の最終判断、外部主体の境界を、業務の責任者が判断できるか   |
| 詳細化入力 | 各グループまたは区分の受け渡し、ストア、詳細化先を、詳細 CDFD の書き手が引き継げるか     |
| 用語整合   | 領域、グループ・区分、ストアの名称が、領域表・ストア一覧・図・詳細 CDFD 一覧で一致するか |
| 粒度       | 領域単位の入出力、手順、状態、例外、実装の詳細を書きすぎていないか                       |

## 8. 仕上げチェック

- Frontmatter に `id`・`type`（`flow`）・`rulebook` があり、`based_on` には目的・範囲の直接の根拠とした先行成果物だけを書いている。
- H1 直下の導入文が対象業務を一文で定義し、目的が示す領域のまとまりとデータの関係を 1〜2 文で述べ、適用範囲が対象・対象外と詳細化先を特定している。
- 各章の冒頭文の数・区分・方式が、表と図の実際と一致している。
- 各領域が一つのグループまたは区分に属し、詳細 CDFD 一覧のいずれかの詳細化先へたどれる。
- ストア一覧の各行が、いずれかの図に同じ名称で現れる。
- 対象範囲内の参加者を外部主体にしておらず、参加者からの入力を省いた図には注記がある。
- 決めきれない論点は `_UNDECIDED_` のまま残し、確定したと書いていない。
