# 概念データフロー図（全体概要）作成レシピ

Conceptual Data Flow Diagram Overview Writing Recipe

業務または運用の全体をプロセス領域とプロセスグループへ分け、データストアを一覧化し、グループとデータストアの間の受け渡しと詳細 CDFD への引き渡し境界を、関係者が再現可能な形で合意するための作成手順です。

## 1. このレシピの使い方

- 最初に、対象業務・運用の範囲と、プロセス領域・データストアの候補を粗く書き出します。
- 次に、各章の問いに答えながら、目的、適用範囲、プロセス領域（グループごとの入出力を含む）、データストア、概念データフロー（概要）、詳細 CDFD 一覧を具体化します。
- 最後に、レビュー観点で「グループの入出力と図のエッジが対応しているか」「領域単位の詳細を書きすぎていないか」を確認します。

この成果物は、プロセスグループとデータストアの名称を軸に、プロセス領域の表・データストア・図・詳細 CDFD 一覧の四点を対応させ、上位の業務目的を領域分割の理由として引き継ぎます。領域内の手順や実装方式は作り込まず、各要素の対応関係で判断を追跡できるようにします（Trace）。

## 2. 作成前に集める情報

| 項目             | 集める情報                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| 利用者と判断     | 誰が対象範囲と領域分割を承認し、誰が詳細化・設計・網羅性確認に使うか                           |
| 対象範囲         | 開始点、終了点、対象業務、組織、システム境界                                                   |
| 対象外           | 補助操作、領域内の手順、実装詳細、別成果物が責任を持つ事項                                     |
| 領域候補         | 固有の業務目的、主な担当、起点イベントを持つ責務のまとまり                                     |
| グループ候補     | 業務の性質が近い領域のまとまり（例: 計画、実行、評価、改善のような段階）                       |
| 主な担当         | 各領域を主に担うロール、複数ロールが担う場合の管理責任、人間の最終判断者                       |
| 起点イベント     | 各領域の開始を判定できる出来事                                                                 |
| データストア     | 各グループが参照・更新する論理的な正本と、その内容。マスタ・構成かトランザクションかの区分     |
| 保管先           | データストアの物理的な所在。実装が先にある場合は確定値、設計中は候補、概念段階では扱わない     |
| 主要な受け渡し   | 各グループが受け取る入力、引き渡す出力として移動する情報・物                                   |
| 物理保管         | 現物（商品・現金など）を保管する場所（物の流れを図示する場合）                                 |
| 外部主体         | 対象範囲外から入力を渡す人・組織・システムと、結果を受け取る主体。対象範囲内の参加者は含めない |
| 横断ユースケース | 複数のグループをまたぎ、順序と引き渡し条件を定める必要がある業務                               |
| 未決事項         | 境界、名称、責務、判断者、保管先が未確定な論点と、影響、決定者、決定時期                       |

## 3. 全体の作成手順

1. 対象者、利用場面、開始点、終了点、対象外を定義します。
2. 開始から結果利用までの業務成果を並べ、起点イベントと最終出力が異なるまとまりへ分け、各まとまりへ安定した領域 ID を付けます。
3. 一覧、検索、状態参照、検証、dry-run など、独立した業務成果を持たない候補を支援先の領域へ戻します。
4. 業務の性質が近い領域をプロセスグループへまとめ、グループ数を 8 以下にします。各グループの主要入力・主要出力・データストアを箇条書きにします。
5. 各グループが参照・更新するデータストアを集め、更新契機でマスタ・構成データとトランザクションデータに区分し、一覧にします。保管先は確定度に応じて列を置くか省略します。
6. グループを代表ノード、「データストア」の各行をデータストアのノードにし、グループの入出力から導いた受け渡しを名詞形のラベル付きエッジで描きます。ノード総数が 16 を超える場合はトランザクションデータの図とマスタ・構成データの図に分けます。
7. プロセスグループ別 CDFD の表を作り、複数グループを横断し順序と引き渡し条件を定める必要がある業務だけをユースケース別 CDFD の表に載せます。
8. 名称を使って表、箇条書き、データストア、図、詳細 CDFD 一覧を突き合わせ、重複、欠落、名称ゆれを解消します。
9. 確定できない論点は影響と決定時期を添えて未決事項へ分離します。

## 4. 各章の書き方

### 4.1. 目的

問い:

- この全体概要によって、誰がどの判断のために使いますか（承認、詳細化、設計入力、網羅性確認など）。
- 対象者ごとに、何を読み取れれば目的を達成したと言えますか。

対象者ごとに利用場面を一文で結び付けます。「全体を分かりやすくする」ではなく、「店主代表が対象範囲と領域分割を承認する」のように、利用結果を判定できる表現にします。後続の詳細 CDFD の位置付けを明確にすることを目的に含めます。

### 4.2. 適用範囲

問い:

- どの出来事から、どの成果または判断までを扱いますか。
- 領域内部としてプロセスグループ別 CDFD へ委ねるものと、業務成果を持たないため補助操作として除外するものは何ですか。
- 人間が責任を持つ判断と、AI Agent やシステムが支援できる処理の境界はどこですか。対応する責任分担文書はありますか。
- 特定プロジェクトの実行計画・スケジュール上のフェーズ名を、前提知識のない読者への説明なく持ち込んでいませんか。

対象業務、開始点、終了点、対象外、補助操作の扱いを明示します。責任分担は対応する文書があれば参照し、なければ原則を一文で書きます。

### 4.3. プロセス領域

問い:

- 各領域には、他の領域と区別できる固有の起点イベントと業務成果がありますか。定義系の領域の起点を実行の契機で書いていませんか。
- 各グループの説明文から、グループの役割と内部の領域の連携が読み取れますか。
- グループの主要入力・主要出力は、他グループ、外部主体、データストアとの受け渡しとして説明できますか。他グループからの要求を入力に含めていますか。
- データストアの名称は「データストア」と一致していますか。
- 主な担当を「全員」だけで終わらせず、管理責任のロールを示していますか。

グループごとに節を設け、説明文、主要入力・主要出力・データストアの箇条書き、領域の表の順に書きます。業務目的は手段名ではなく、対象者が利用する成果または維持したい状態で書きます。領域を分けるか迷う場合は、起点、最終出力、更新する正本の三点を比較します。領域単位の入出力は書かず、プロセスグループ別 CDFD へ委ねます。

### 4.4. データストア

<!-- specdojo:finding id=F001 severity=minor rule=vp-qe-omissions-consistency line=81 成果物の必須構成要素である「導入文」について、他の章と同様に「問い」および「書き方」のガイドが提供されていない。 -->

問い:

- 各データストアは、何の正本かが分かる名称ですか。生成物の場合は生成元、退避先の場合は退避対象が主な内容に書かれていますか。
- 区分は更新契機で判定していますか。定義から生成される生成物を、生成元と同じ区分にしていませんか。
- 保管先の列を置く場合、確定度に合った書き方（確定値、`_UNDECIDED_`、列の省略）になっていますか。各保管先は一つのデータストアにだけ属していますか。
- リポジトリ基盤や開発環境の設定など、業務データでないものを除外していますか。

マスタ・構成データとトランザクションデータの 2 表に分けます。図に置くデータストアはこの一覧の行と一対一にするため、図で使いたい名称をここで確定します。

### 4.5. 概念データフロー（概要）

問い:

- 代表ノードはプロセスグループごとに一つで、ラベルにグループ名と含む領域 ID の範囲がありますか。`subgraph` で囲んでいませんか。
- データストアのノードは「データストア」の各行と一対一で、名称が一致していますか。
- 各エッジは「プロセス領域」の各グループの主要入力・主要出力のどれかに対応していますか。対応のないエッジ、エッジのない入出力はありませんか。
- エッジラベルだけを読んでも、何がどこからどこへ渡るか説明できますか。
- 対象範囲内の参加者を外部主体として描いていませんか。外部主体は対象範囲外の入力元・出力先だけですか。
- ノード総数が 16 を超える場合、トランザクションデータの図とマスタ・構成データの図に分け、両図で名称を統一し、グループ間の要求をトランザクションの図にだけ描いていますか。
- 各図の直後に、凡例の参照先、物の流れの有無、載せていない要素の参照先、外部主体の有無を注記していますか。

図はグループとデータストアの間の受け渡しに集中させます。グループ内の領域や手順を複数ノードへ展開したくなった場合は、その内容をプロセスグループ別 CDFD へ移します。物の受け渡しがある場合は、物理保管（売場棚、バックヤードなど）もデータストアと同様に図の要素として扱い、`==>` で描きます。

### 4.6. 詳細 CDFD 一覧

問い:

<!-- specdojo:finding id=F002 severity=minor rule=vp-qe-omissions-consistency line=113 「データストア」章の冒頭に記載すべき「区分の意味、パスの略記、除外対象」に関する記述ガイドが欠けている。 -->

- 章の冒頭で、プロセスグループ別 CDFD とユースケース別 CDFD の役割分担を示していますか。
- 状態の定義は STSD、状態遷移は CSTD を正本とし、詳細 CDFD は参照に留める役割分担を示していますか。
- プロセスグループ別 CDFD の表に全グループが 1 行ずつあり、各領域がちょうど一つの行に属していますか。
- ユースケース別 CDFD の表に載せた業務は、複数のグループを横断し、順序と引き渡し条件を定める必要がありますか。単一グループに閉じる業務を載せていませんか。
- 「未作成」などの作成状況を本文に書いていませんか。

作成状況は登録簿で追跡し、本文には ID だけを書きます。単一グループに閉じる業務は、必要になった時点でユースケース別 CDFD を追加する旨を本文に書きます。

### 4.7. 凡例（本プロダクト共通）（任意）

問い:

- 本プロダクトに複数の詳細 CDFD があり、共通のノード形状・色・絵文字を使いますか。
- 全体概要と詳細 CDFD の各図が、この章の定義を再掲せず参照する形になっていますか。
- サンプル図には、`specdojo:cdfd-mermaid-rulebook` が定義する全ノード種別が一つずつ含まれていますか。

<!-- specdojo:finding id=F003 severity=minor rule=vp-qe-omissions-consistency line=124 「概念データフロー（概要）」章の冒頭に記載すべき「ノード構成、矢印の意味、更新エッジ、外部主体の扱い」に関する記述ガイドが欠けている。 -->

詳細 CDFD が複数あり、色・絵文字の割り当てを毎回説明し直すと負担になる場合に設けます。単一の CDFD しかない場合は省略します。

### 4.8. 未決事項（条件付き）

問い:

- 境界、名称、責務、判断者、保管先のいずれかに未確定の論点がありますか。
- 本文中の `_UNDECIDED_` は、表の論点と対応していますか。

未決事項がある場合だけ最終章として設け、論点、影響、決定者、決定時期、状態の表にします。確定した論点は本文へ反映して表から削除します。

## 5. 深掘り手順

1. 各領域の目的から逆向きにたどり、その領域が応える利用者の判断または業務課題を確認します。
2. 各領域の起点イベントを見て、定義系の領域が実行の契機で書かれていないか、同じグループ内で同文になっていないかを確認します。
3. 各グループの主要出力から順向きにたどり、他グループまたは外部主体が利用するか、データストアに残るかを確認します。
4. 同じデータストアを更新する複数グループを並べ、更新責務が重複していないか確認します。
5. 図のエッジを一本ずつ、対応するグループの主要入力・主要出力に対応付け、対応のないものを追加または削除します。
6. 「データストア」の各行が図に一度ずつ登場し、保管先が他の行と重なっていないかを確認します。
7. コマンド名、画面名、ファイル名を隠しても目的と受け渡しを説明できるか確認し、説明できない行を概念粒度へ戻します。
8. 補助操作を除外したことで必要な検証入力が失われていないか確認し、独立領域ではなく支援先の入力として残します。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                                                     | 悪い例                                                   |
| ------------ | ------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| 業務目的     | 現金販売を記録し、商品を顧客へ渡す                                                         | 販売登録画面を実行する                                   |
| 起点イベント | 定期実行定義は「定期的に確認・実行する事項が判明した」                                     | 定期実行定義に「指定された時期が到来した」（実行の契機） |
| グループ粒度 | 店頭販売とつけ販売を「販売」グループにまとめ、値引きや取消の手順は詳細 CDFD へ委ねる       | 全体概要に値引き、取消、再入力を別ノードで並べる         |
| 入出力       | 入力は購入依頼と支払、売価、つけ上限。出力は販売記録とつけ販売の記録                       | 入力はフォーム、出力は JSON                              |
| データストア | 販売取引の正本である「販売記録」と、その生成物である「日次締め記録」を分ける               | `sales-table`。または販売記録と締め記録を一つにまとめる  |
| 区分         | 定期実行定義（定義）はマスタ・構成、実行記録（活動の記録）はトランザクション               | 定義と記録を同じ区分にする                               |
| 保管先       | 実装があるのでパスを書く。設計中は `_UNDECIDED_`。概念段階は列を省略                       | 未定なのに推測でパスを書く                               |
| 補助操作     | 商品検索は販売の入力確認として扱う                                                         | 商品検索を独立したプロセス領域にする                     |
| 図の要素     | 顧客と仕入先を外部主体、店主を各領域の担当として内側に置く                                 | 店主を外部主体として描く                                 |
| ノード数     | 代表ノード 6 とデータストア 15 の計 21 なので 2 図に分ける                                 | 21 ノードを 1 図に並べる                                 |
| 詳細化先     | 販売グループを `cdfd-sales` へ、つけ販売から精算までを `cdfd-uc-credit-sales` へ割り当てる | 領域ごとに詳細 CDFD を作り、横断業務を各図に重複記載する |

## 7. レビュー観点

| 観点       | 確認内容                                                                                                 | 主な確認者 |
| ---------- | -------------------------------------------------------------------------------------------------------- | ---------- |
| 業務価値   | 各領域の目的が、対象者の課題、判断、期待する業務成果のどれに応えるか説明できる                           | BA         |
| 対象境界   | 領域、プロセスグループ、補助操作、領域内部、人間の最終判断、外部主体の境界を承認できる                   | PO         |
| 詳細化入力 | 各グループの入出力、データストア、詳細化先を識別できる                                                   | ARC        |
| 網羅性     | 各領域がちょうど一つのグループとプロセスグループ別 CDFD に属し、図のエッジと入出力が相互に対応する       | QE         |
| 用語整合   | 領域、グループ、データストアの名称が表、箇条書き、一覧、図、詳細 CDFD 一覧で一致する                     | BA、QE     |
| 粒度       | 全体概要がグループ単位の入出力に留まり、領域単位の入出力、手順、状態、例外、実装詳細を詳細化先へ委譲する | BA、ARC    |
| 可読性     | グループ数が 8 以下で、ノード総数が 16 を超える場合は 2 図に分かれている                                 | BA、ARC    |

## 8. 仕上げチェック

- 対象者、利用場面、対象範囲、対象外、責任分担を明記した。
- 各領域に ID、目的、担当、起点イベントがあり、各グループに説明文と主要入力・主要出力・データストアの箇条書きがある。
- グループ数が 8 以下である。
- 「データストア」がマスタ・構成とトランザクションに分かれ、保管先列は確定度に合った扱いになっている。
- 図の代表ノードがグループごとに一つで、データストアが一覧の各行と一対一に対応し、`subgraph` を使っていない。
- 図の全エッジに名詞形のラベルがあり、グループの入出力と相互に対応する。
- ノード総数が 16 を超える場合は 2 図に分かれ、両図で名称が統一されている。
- 対象範囲内の参加者を外部主体として描いていない。
- プロセスグループ別 CDFD の表に全グループがあり、ユースケース別 CDFD の表には横断業務だけがある。「未作成」などの作成状況を書いていない。
- 補助操作を独立領域にせず、領域単位の入出力や実装方式を作り込んでいない。
