# 概念データフロー図（全体概要）作成レシピ

Conceptual Data Flow Diagram Overview Writing Recipe

業務または運用の全体像を、プロセス領域のまとまりと、それらが読み書きするデータの関係として示すための作成手順です。今の方式（プロセスグループ別 CDFD を置く方式）と、系統の関係を描く方式（区分を代表ノードにし、各系統をユースケース別 CDFD で詳細化する方式）から選びます。

## 1. このレシピの使い方

- 最初に、対象業務・運用の範囲と、プロセス領域・データストアの候補を粗く書き出します。
- 次に、各章の問いに答えながら、目的、適用範囲、プロセス領域の表、データストア、概念データフロー（概要）、詳細 CDFD 一覧を具体化します。
- 最後に、レビュー観点で「表と図の名称が対応し、受け渡しが図で読み取れるか」「領域単位の詳細を書きすぎていないか」を確認します。

この成果物は、プロセスグループまたは区分とデータストアの名称を軸に、プロセス領域の表・データストア・図・詳細 CDFD 一覧の四点を対応させ、上位の業務目的を領域分割の理由として引き継ぎます。領域内の手順や実装方式は作り込まず、各要素の対応関係で判断を追跡できるようにします（Trace）。

## 2. 作成前に集める情報

| 項目               | 集める情報                                                                                                      |
| ------------------ | --------------------------------------------------------------------------------------------------------------- |
| 全体像             | 対象業務を構成するプロセス領域のまとまりと、読み書きするデータの関係                                            |
| 対象範囲           | 開始点、終了点、対象業務、組織、システム境界                                                                    |
| 対象外             | 補助操作、領域内の手順、実装詳細、別成果物が責任を持つ事項                                                      |
| 領域候補           | 固有の業務目的、主な担当、起点イベントを持つ責務のまとまり                                                      |
| グループ・区分候補 | 業務の性質が近い領域のまとまり。系統の関係を描く方式では、系統・実行サイクル・調整役などの区分                  |
| 主な担当           | 各領域を主に担うロール、複数ロールが担う場合の管理責任、人間の最終判断者                                        |
| 起点イベント       | 各領域の開始を判定できる出来事                                                                                  |
| データストア       | 各グループまたは区分が参照・更新する論理的な正本と、その内容。マスタ・構成かトランザクションかの区分            |
| 保管先             | データストアの物理的な所在。実装が先にある場合は確定値、設計中は候補、概念段階では扱わない                      |
| 主要な受け渡し     | グループまたは区分とデータストアの間で移動する情報・物、区分間の実行要求、調整役の直接読み書きと CLI 経由の区別 |
| 物理保管           | 現物（商品・現金など）を保管する場所（物の流れを図示する場合）                                                  |
| 外部主体           | 対象範囲外から入力を渡す人・組織・システムと、結果を受け取る主体。対象範囲内の参加者は含めない                  |
| 横断ユースケース   | 今の方式では複数グループをまたぐ業務、系統の関係を描く方式では各系統の流れ                                      |
| 未決事項           | 境界、名称、責務、判断者、保管先が未確定な論点と、影響、決定者、決定時期                                        |

## 3. 全体の作成手順

1. 全体像として示す関係を 1〜2 文で書き、開始点、終了点、対象外を定義します。
2. 開始から結果利用までの業務成果を並べ、起点イベントと最終出力が異なるまとまりへ分け、各まとまりへ安定した領域 ID を付けます。
3. 一覧、検索、状態参照、検証、dry-run など、独立した業務成果を持たない候補を支援先の領域へ戻します。
4. 業務の性質が近い領域を、今の方式ではプロセスグループへ、系統の関係を描く方式では区分へまとめ、8 以下にします。各節には領域の表だけを置き、必要なら PDCA 列を追加します。受け渡しの正本は図とし、主要入力・主要出力の箇条書きは置きません。
5. 各グループまたは区分が参照・更新するデータストアを集め、更新契機でマスタ・構成データとトランザクションデータに区分し、一覧にします。保管先は確定度に応じて列を置くか省略します。
6. グループまたは区分を代表ノードにし、データストアとの関係と区分間の要求を名詞のラベル付きの線で描きます。16 ノードを超える場合は選択した方式で分けます。系統の関係を描く方式ではデータの種類で分け、区分の位置をそろえ、線のない区分を省きます。調整役の指示は別図にし、直接読み書きするストアだけを調整役につなぎます。
7. 今の方式ではプロセスグループ別 CDFD の表と、横断業務のユースケース別 CDFD の表を作ります。系統の関係を描く方式では、各系統の流れをユースケース別 CDFD の表に載せます。
8. 名称を使って領域表、データストア、図、詳細 CDFD 一覧を突き合わせ、重複、欠落、名称ゆれを解消します。
9. 確定できない論点は影響と決定時期を添えて未決事項へ分離します。

## 4. 各章の書き方

### 4.1. 目的

問い:

- どの業務または運用の全体像を示しますか。
- その全体像を構成するプロセス領域のまとまりと、読み書きするデータの関係は何ですか。

全体像として何を示すかを 1〜2 文で書きます。例えば「店舗運営の全体像として、仕入・販売・在庫・顧客・締めと、それらが読み書きするデータの関係を示す」とします。PO の承認や引き継ぎなどの作業、読み手の役割は目的に含めません。対象範囲と領域分割の PO 承認記録は、目的とは別に `ready` 昇格の完成判定で確認します。

### 4.2. 適用範囲

問い:

- どの出来事から、どの成果または判断までを扱いますか。
- 領域内部として選択した方式の詳細 CDFD へ委ねるものと、業務成果を持たないため補助操作として除外するものは何ですか。
- 人間が責任を持つ判断と、AI Agent やシステムが支援できる処理の境界はどこですか。対応する責任分担文書はありますか。
- 特定プロジェクトの実行計画・スケジュール上のフェーズ名を、前提知識のない読者への説明なく持ち込んでいませんか。

対象業務、開始点、終了点、対象外、補助操作の扱いを明示します。責任分担は対応する文書があれば参照し、なければ原則を一文で書きます。

### 4.3. プロセス領域

問い:

- 各領域には、他の領域と区別できる固有の起点イベントと業務成果がありますか。定義系の領域の起点を実行の契機で書いていませんか。
- グループまたは区分の見出しと領域表から、そのまとまりの業務目的が読み取れますか。
- 各領域は一つのグループまたは区分にだけ属していますか。PDCA を示す場合は任意の列にしていますか。
- 主な担当を「全員」だけで終わらせず、管理責任のロールを示していますか。

グループまたは区分ごとに節を設け、領域 ID、プロセス領域、業務目的、主な担当、起点イベントの表だけを置きます。PDCA は任意の列です。受け渡しは図を正本とし、主要入力・主要出力の箇条書きは置きません。業務目的は手段名ではなく、対象者が利用する成果または維持したい状態で書きます。領域を分けるか迷う場合は、起点、最終出力、更新する正本の三点を比較します。領域内部の詳細は選択した方式の詳細 CDFD へ委ねます。

### 4.4. データストア

問い:

- 各データストアは、何の正本かが分かる名称ですか。生成物の場合は生成元、退避先の場合は退避対象が主な内容に書かれていますか。
- 区分は更新契機で判定していますか。定義から生成される生成物を、生成元と同じ区分にしていませんか。
- 保管先の列を置く場合、確定度に合った書き方（確定値、`_UNDECIDED_`、列の省略）になっていますか。保管先を共有・包含する場合は、論理境界と共有相手を注記していますか。
- リポジトリ基盤や開発環境の設定など、業務データでないものを除外していますか。

マスタ・構成データとトランザクションデータの 2 表に分けます。図に置くデータストアはこの一覧の行と一対一にするため、図で使いたい名称をここで確定します。

### 4.5. 概念データフロー（概要）

問い:

- 今の方式と、系統の関係を描く方式のどちらを使いますか。凡例または章冒頭で宣言していますか。
- 代表ノードはグループまたは区分ごとに一つで、名称と含む領域 ID をラベルにしていますか。`subgraph` で囲んでいませんか。
- データストアは一覧の各行と一対一で名称が一致していますか。同じストアを複数図に再掲する場合も同じ名称ですか。
- 線のラベルは、何がどこからどこへ渡るか分かる名詞ですか。区分から区分への「対応要求」「実行要求」なども名詞のラベルで描いていますか。
- 対象範囲内の参加者を外部主体にしていませんか。外部主体は対象範囲外の入力元・出力先だけですか。
- 16 ノードを超える場合、選択した方式で分割していますか。今の方式ではデータストアの区分または使い方の流れで分け、名称を統一していますか。
- 系統の関係を描く方式では、データの種類で分けた図の間で区分の位置がそろっていますか。受け渡しの線のない区分をその図から省き、各区分をいずれかの図に出していますか。配置制御の非表示の線を受け渡しとして数えていませんか。
- 系統の関係を描く方式では、調整役（Orchestrator）をデータの図から外し、必要なら指示の図を別に設けていますか。調整役からストアへの線は直接の読み書きだけですか。CLI 経由のものはデータの図で該当区分からの線になっていますか。
- 図の題は業務の言葉で付けていますか。図の説明は、図から読み取れることを 1 文で書き、作図の約束は凡例に任せていますか。

系統の関係を描く方式では、例えば「PDCA のプロセスとデータの関係」「プロセスを実行する設定・構成情報の流れ」「Orchestrator による PDCA の調整」の 3 図にします。実行要求をトランザクションの図だけに限定する規則は設けず、調整役の指示は指示の図に描きます。グループや区分の内部は詳細 CDFD へ委ねます。物の流れがある場合は物理保管も図の要素として扱い、線種は採用した記法の凡例に従います。

### 4.6. 詳細 CDFD 一覧

問い:

- 選択した方式に応じた詳細 CDFD の役割分担を示していますか。状態の定義と遷移は STSD を正本にしていますか。
- 今の方式では、プロセスグループ別 CDFD の表に全グループが 1 行ずつあり、各領域がちょうど一つの行に属していますか。ユースケース別 CDFD は複数グループを横断する順序と引き渡し条件だけを扱っていますか。
- 系統の関係を描く方式では、各系統の流れをユースケース別 CDFD でプロセス領域の単位に詳細化していますか。プロセスグループ別 CDFD の表は省略するか、移行期・非推奨の記録として扱っていますか。
- 「未作成」などの作成状況を本文に書いていませんか。

作成状況は登録簿で追跡し、本文には ID だけを書きます。今の方式で単一グループに閉じる業務はグループ別 CDFD で扱い、ユースケース別 CDFD は横断業務が必要になった時点で追加します。

### 4.7. 凡例（本プロダクト共通）（任意）

問い:

- 本プロダクトに複数の詳細 CDFD があり、共通のノード形状・色・絵文字を使いますか。
- 全体概要と詳細 CDFD の各図が、この章の定義を再掲せず参照する形になっていますか。
- サンプル図には、採用する記法（Mermaid または D2）の rulebook が定義する全ノード種別が一つずつ含まれていますか。

詳細 CDFD が複数あり、色・絵文字の割り当てを毎回説明し直すと負担になる場合に設けます。単一の CDFD しかない場合は省略します。

### 4.8. 未決事項（条件付き）

問い:

- 境界、名称、責務、判断者、保管先のいずれかに未確定の論点がありますか。
- 本文中の `_UNDECIDED_` は、表の論点と対応していますか。

未決事項がある場合だけ最終章として設け、論点、影響、決定者、決定時期、状態の表にします。確定した論点は本文へ反映して表から削除します。

## 5. 深掘り手順

1. 各領域の目的から逆向きにたどり、その領域が応える利用者の判断または業務課題を確認します。
2. 各領域の起点イベントを見て、定義系の領域が実行の契機で書かれていないか、同じグループ内で同文になっていないかを確認します。
3. 図の出力の線から順向きにたどり、他グループ・区分または外部主体が利用するか、データストアに残るかを確認します。
4. 同じデータストアを更新する複数グループを並べ、更新責務が重複していないか確認します。
5. 図の線を一本ずつたどり、領域表の業務目的とストアの主な内容に照らして、欠けた受け渡しや不要な線を修正します。
6. 「データストア」の各行がいずれかの図に登場し、再掲時も名称が一致するか確認します。保管先が重なる場合は論理境界と共有相手の注記を確認します。
7. コマンド名、画面名、ファイル名を隠しても目的と受け渡しを説明できるか確認し、説明できない行を概念粒度へ戻します。
8. 補助操作を除外したことで必要な検証入力が失われていないか確認し、独立領域ではなく支援先の入力として残します。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                                                          | 悪い例                                                   |
| ------------ | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 業務目的     | 現金販売を記録し、商品を顧客へ渡す                                                              | 販売登録画面を実行する                                   |
| 起点イベント | 定期実行定義は「定期的に確認・実行する事項が判明した」                                          | 定期実行定義に「指定された時期が到来した」（実行の契機） |
| グループ粒度 | 店頭販売とつけ販売を「販売」グループにまとめ、値引きや取消の手順は詳細 CDFD へ委ねる            | 全体概要に値引き、取消、再入力を別ノードで並べる         |
| 入出力       | 入力は購入依頼と支払、売価、つけ上限。出力は販売記録とつけ販売の記録                            | 入力はフォーム、出力は JSON                              |
| データストア | 販売取引の正本である「販売記録」と、その生成物である「日次締め記録」を分ける                    | `sales-table`。または販売記録と締め記録を一つにまとめる  |
| 区分         | 定期実行定義（定義）はマスタ・構成、実行記録（活動の記録）はトランザクション                    | 定義と記録を同じ区分にする                               |
| 保管先       | 実装があるのでパスを書く。設計中は `_UNDECIDED_`。概念段階は列を省略                            | 未定なのに推測でパスを書く                               |
| 補助操作     | 商品検索は販売の入力確認として扱う                                                              | 商品検索を独立したプロセス領域にする                     |
| 図の要素     | 顧客と仕入先を外部主体、店主を各領域の担当として内側に置く                                      | 店主を外部主体として描く                                 |
| ノード数     | 代表ノード 6 とデータストア 15 の計 21 なのでデータの種類で分け、調整役がいれば指示を別図にする | 21 ノードを 1 図に並べる                                 |
| 詳細化先     | 販売グループを `cdfd-sales` へ、つけ販売から精算までを `cdfd-uc-credit-sales` へ割り当てる      | 領域ごとに詳細 CDFD を作り、横断業務を各図に重複記載する |

## 8. 仕上げチェック

最終的な完成判定は [[specdojo:cdfd-overview-rulebook|作成ルール]] の完成判定を正本とし、ここでは作成中の整合を確かめます。

- 目的は全体像として何を示すかを 1〜2 文で書き、対象範囲、対象外、責任分担は適用範囲に書いた。
- 各領域に ID、業務目的、担当、起点イベントがあり、各グループまたは区分の節は領域表だけにした。PDCA 列は必要な場合だけ追加した。
- グループまたは区分が 8 以下である。
- データストアをマスタ・構成とトランザクションに分け、保管先列を確定度に合った扱いにした。
- 代表ノード、領域表、データストア、詳細 CDFD 一覧の名称と ID が対応し、`subgraph` を使っていない。
- 受け渡しの全線に名詞のラベルがあり、区分間の実行要求も内容を読み取れる。
- 16 ノードを超える場合は選択した方式で分割した。系統の関係を描く方式ではデータの図で区分の位置をそろえ、線のない区分を省き、各区分はいずれかの図に出した。
- 系統の関係を描く方式では、調整役はデータの図に置かず、必要な指示の図に置いた。直接読み書きするストアだけにつなぎ、CLI 経由の読み書きはデータの図の該当区分から描いた。
- 図の題は業務の言葉で、図の説明は読み取れることを 1 文で書き、作図の約束を凡例にまとめた。
- 対象範囲内の参加者を外部主体にせず、補助操作を独立領域にしていない。
- 詳細 CDFD 一覧は選択した方式に従い、作成状況を書いていない。領域内部の詳細と状態定義はそれぞれの正本へ委ねた。
- 未決事項は `_UNDECIDED_` で区別し、影響、決定者、決定時期、状態を記載した。未決事項がなければ章を設けていない。
