# 概念データフロー図（全体概要）作成レシピ

Conceptual Data Flow Diagram Overview Writing Recipe

業務または運用の全体をプロセス領域へ分け、領域間の受け渡しと領域別 CDFD への詳細化境界を、関係者が再現可能な形で合意するための作成手順です。

## 1. このレシピの使い方

- 最初に、対象業務・運用の範囲とプロセス領域の候補を粗く書き出します。
- 次に、各章の問いに答えながら、目的、適用範囲、プロセス領域、概念データフロー（概要）、個別プロセス領域入出力、委譲境界を具体化します。
- 最後に、レビュー観点で「領域と代表ノードの対応が崩れていないか」「領域内の手順や実装詳細を書きすぎていないか」を確認します。

この成果物は、領域 ID を軸に、一覧表（プロセス領域）・図（概念データフロー（概要））・個別プロセス領域入出力・委譲境界の四点を対応させ、上位の業務目的を領域分割の理由として引き継ぎます。領域内の手順や実装方式は作り込まず、各要素の対応関係で判断を追跡できるようにします（Trace）。

## 2. 作成前に集める情報

| 項目           | 集める情報                                                               |
| -------------- | ------------------------------------------------------------------------ |
| 利用者と判断   | 誰が対象範囲を承認し、誰が詳細化・設計・網羅性確認に使うか               |
| 対象範囲       | 開始点、終了点、対象業務、組織、システム境界                             |
| 対象外         | 補助操作、領域内の手順、実装詳細、別成果物が責任を持つ事項               |
| 領域候補       | 固有の業務目的、成果を持つ責務のまとまり                                 |
| 主な担当       | 各領域を主に担うロールと、人間の最終判断者                               |
| 起点イベント   | 各領域の開始を判定できる出来事                                           |
| 主要な受け渡し | 各領域が受け取る入力、引き渡す出力として移動する情報・現物               |
| データストア   | 各領域が参照・更新する論理的な正本または保管先                           |
| 物理保管       | 現物（商品・現金など）を一時的に保管する場所（現物の流れを図示する場合） |
| 外部主体       | 対象範囲外から入力を渡す人・組織・システムと、結果を受け取る主体         |
| 詳細化先       | 各領域を引き継ぐ領域別 CDFD の ID または仮置き名                         |
| 受入観点       | 業務価値、対象境界、詳細化入力、重複・欠落を誰が何で判定するか           |
| 未決事項       | 境界、名称、責務、判断者が未確定な論点と、影響、決定者、決定時期         |

## 3. 全体の作成手順

1. 対象者、利用場面、開始点、終了点、対象外を定義します。
2. 開始から結果利用までの業務成果を並べ、起点イベントと最終出力が異なるまとまりへ分けます。
3. 各まとまりへ安定した領域 ID を付け、目的、担当、起点、入力、出力、データストア、詳細化先を一行にします。
4. 一覧、検索、状態参照、検証、dry-run など、独立した業務成果を持たない候補を支援先の領域へ戻します。
5. 表の各領域を一つずつ代表ノードにし、外部主体、起点イベント、主要データストア、必要な物理保管と共に図へ配置します。
6. 領域間の情報・イベント・現物を方向付きのエッジでつなぎ、受け渡す内容を名詞形のラベルにします。
7. 対象境界、各領域の詳細化先と委譲境界、確認者別の受入条件を記述します。
8. 領域 ID を使って一覧、図、詳細化先を突き合わせ、重複、欠落、粒度の混在を解消します。
9. 確定できない論点は影響と判断時期を添えて未決事項へ分離します。

## 4. 各章の書き方

### 4.1. 目的

問い:

- この全体概要によって、誰がどの判断のために使いますか（承認、領域別詳細化、設計入力、網羅性確認など）。
- 対象者ごとに、何を読み取れれば目的を達成したと言えますか。

対象者と利用場面を一文で結び付けます。「全体を分かりやすくする」ではなく、「業務責任者が三領域と補助操作の境界を承認する」のように、利用結果を判定できる表現にします。

### 4.2. 適用範囲

問い:

- どの出来事から、どの成果または判断までを扱いますか。
- 領域別詳細へ委譲するものと、業務成果を持たないため除外するものは何ですか。
- 人間が責任を持つ判断と、AI Agent やシステムが支援できる処理の境界はどこですか。対応する責任分担文書を参照していますか。
- 特定プロジェクトの実行計画・スケジュール上のフェーズ名を、前提知識のない読者への説明なく持ち込んでいませんか。

対象業務、開始点、終了点、対象外、補助操作の扱いを明示します。人間と AI Agent の責任分担の原則は本文で再定義せず、対応する文書への参照に留めます。全体概要は現在の正本の姿を示す仕様であるため、プロジェクト固有の用語は持ち込みません。

### 4.3. プロセス領域

問い:

- その候補には、他の候補と区別できる固有の起点イベントと業務成果がありますか。
- 主要入力と主要出力は、別領域または外部主体との受け渡しとして説明できますか。
- 参照または更新するデータストアは、何の正本かが分かる名称ですか。
- 一行から、領域別 CDFD を作るための開始条件と境界を読み取れますか。

一行を一つの領域別 CDFD 候補にします。業務目的は手段名ではなく、対象者が利用する成果または維持したい状態で書きます。領域を分けるか迷う場合は、起点、最終出力、更新する正本の三点を比較します。

### 4.4. 概念データフロー（概要）

問い:

- 一覧表の各領域が、同じ ID と名称を持つ一つの代表ノード（直接またはプロセスグループ経由）として登場していますか。
- 各領域の起点イベントと主要なデータストアを図からたどれますか。
- エッジラベルだけを読んでも、何がどこからどこへ渡るか説明できますか。
- 人間の承認、入力元、結果利用者が、内部処理へ吸収されていませんか。
- この図が概要であり、詳細を個別プロセス領域入出力（4.5）・委譲境界（4.6）へ委譲していることが、見出しと凡例から分かりますか。
- 現物の受け渡しがある場合、物理保管を図の要素として扱っていますか。一画面で追いにくいときは、外部主体・物理保管に着目した図とデータストアに着目した図に分け、両図で領域 ID・名称を統一していますか。
- 代表ノードの数はおおむね7〜9件までに収まっていますか。超える場合は、業務の性質が近い領域をプロセスグループへまとめていますか。

図は領域間の受け渡しに集中させます。一領域の内部手順を複数ノードへ展開したくなった場合は、その内容を個別プロセス領域入出力または委譲境界へ移します。関連領域を囲って見やすくする場合も、代表ノードは一領域につき一つに保ちます。代表ノードがおおむね7〜9件を超える場合は、業務の性質が近い領域をプロセスグループへまとめ、代表ノードをグループ単位にできます。現物の受け渡しがある場合は、物理保管（バックヤード、レジなど）も外部主体・データストアと同様に図の要素として扱います。

### 4.5. 個別プロセス領域入出力

問い:

- プロセスグループを設けた場合、グループが扱う範囲を数行で要約していますか。
- 各領域の主要入力・主要出力・データストアは、隣接領域または外部主体との受け渡しとして説明できますか。
- 業務目的、主な担当、起点イベントを、プロセス領域（3章）と重複して書いていませんか。

業務目的、主な担当、起点イベントは「プロセス領域」（3章）の一覧表が正本のため、ここでは繰り返しません。領域 ID ごとに主要入力・主要出力・データストアを表で示し、隣接領域との受け渡しを追えるようにします。

### 4.6. 委譲境界

問い:

- 独立領域、補助操作、領域内詳細、人間の最終判断、支援主体を区別できますか。
- 隣接領域のどちらが正本を更新し、どちらが結果を利用しますか。
- 各領域の委譲先が、具体的な領域 ID で示されていますか。
- 詳細化先（正本の CDFD）は「プロセス領域」（3章）の領域別 CDFD 列を参照する前提とし、ここで再掲していませんか。

責務が重なる場合は、「どの出来事で始まり、どの正本を更新し、誰に何を引き渡したら終わるか」を一文ずつ書きます。統合または分割の例外は、理由と重複・欠落の確認方法を併記します。領域 ID ごとに、対象外として他領域へ委ねる事項と委譲先の領域 ID を表で示します。

### 4.7. 凡例（本プロダクト共通）（任意）

問い:

- 本プロダクトに複数の領域別 CDFD があり、共通のノード形状・色・絵文字を使いますか。
- 全体概要と領域別 CDFD の各図が、この章の定義を再掲せず参照する形になっていますか。
- サンプル図には、本プロダクトが実際に使う全ノード種別（プロセス／プロセスグループ、起点イベント、データストア、物理保管、外部主体）が一つずつ含まれていますか。

領域別 CDFD が複数あり、色・絵文字の割り当てを毎回説明し直すと負担になる場合に設けます。単一の CDFD しかない、または再掲の負担が小さい場合は省略します。サンプル図と対応表は、本図が扱う業務データフローとは独立させ、ノード種別ごとの形状・色・絵文字の例を示すことに専念します。

## 5. 深掘り手順

1. 各領域の目的から逆向きにたどり、その領域が応える利用者の判断または業務課題を確認します。
2. 各代表ノードから逆向きにたどり、開始を判定できる起点イベントがあるか確認します。
3. 各代表ノードから順向きにたどり、他領域または外部主体が利用する出力があるか確認します。
4. 同じデータストアを更新する複数領域を並べ、更新責務が重複していないか確認します。
5. 一覧にだけある領域と図にだけある代表ノードを列挙し、追加、削除、名称統一のいずれかで解消します。
6. 全領域を詳細化先へ一度ずつ対応付け、詳細化先のない領域と二重に割り当てた領域を解消します。
7. コマンド名、画面名、ファイル名を隠しても目的と受け渡しを説明できるか確認し、説明できない行を概念粒度へ戻します。
8. 補助操作を除外したことで必要な検証入力が失われていないか確認し、独立領域ではなく支援先の入力または観測として残します。

## 6. 良い例 / 悪い例

| 観点         | 良い例                                                                         | 悪い例                                                |
| ------------ | ------------------------------------------------------------------------------ | ----------------------------------------------------- |
| 業務目的     | 販売情報を記録し、在庫管理とつけ管理へ同じ取引情報を引き渡す                   | 販売登録画面を実行する                                |
| 起点イベント | 顧客が商品を購入した                                                           | 必要に応じて                                          |
| 領域粒度     | 販売記録を一つの代表ノードにし、値引きや取消の手順は領域別 CDFD へ委譲する     | 全体概要に値引き、取消、再入力を別ノードで並べる      |
| 入出力       | 入力は購入依頼と支払区分、出力は販売情報と在庫更新情報                         | 入力はフォーム、出力は JSON                           |
| データストア | 販売取引の正本である販売記録簿                                                 | `sales-table`                                         |
| 補助操作     | 商品検索は販売記録の入力確認として扱う                                         | 商品検索を独立したプロセス領域にする                  |
| 分割         | 販売記録を `cdfd-sales` へ割り当て、補充判断とつけ残高更新は隣接領域へ委譲する | 販売、在庫、つけを複数の詳細図へ重複記載する          |
| ノード数     | 9領域を業務の性質が近い3グループへまとめ、代表ノードを3件に抑える              | 9件の代表ノードをそのまま一画面に並べて図が読みにくい |
| 受入条件     | 店主代表が販売・在庫・つけの三領域と補助操作の境界を表と図から承認できる       | 関係者が内容を確認する                                |

## 7. レビュー観点

| 観点       | 確認内容                                                                                         | 主な確認者 |
| ---------- | ------------------------------------------------------------------------------------------------ | ---------- |
| 業務価値   | 各領域の目的が、対象者の課題、判断、期待する業務成果のどれに応えるか説明できる                   | BA         |
| 対象境界   | 独立領域、補助操作、領域内詳細、人間の最終判断、支援主体の境界を承認できる                       | PO         |
| 詳細化入力 | 各領域の起点、入力、出力、データストア、詳細化先を一行で識別できる                               | ARC        |
| 網羅性     | 一覧、図、詳細化先が領域 ID で一対一に対応し、重複または欠落がない                               | QE         |
| 用語整合   | 領域、イベント、入出力、データストアの名称が一覧と図で一致する                                   | BA、QE     |
| 粒度       | 全体概要が一ノード一領域を保ち、領域内の手順、状態、例外、実装詳細を詳細化先へ委譲している       | BA、ARC    |
| 可読性     | 代表ノード数が目安（おおむね7〜9件）に収まる、または超える場合はプロセスグループへ統合されている | BA、ARC    |

## 8. 仕上げチェック

- 対象者、利用場面、対象範囲、対象外を明記した。
- 各領域に ID、目的、担当、起点イベント、主要入力、主要出力、データストア、詳細化先、委譲境界がある。
- 一覧の全領域が、概念データフロー（概要）に一つずつ代表ノード（直接またはプロセスグループ経由）として登場する。
- 代表ノードの数が目安（おおむね7〜9件）を超えないか確認し、超える場合はプロセスグループへ統合した。
- 図の全代表ノードが一覧の一行と詳細化先へ対応する。
- 個別プロセス領域入出力・委譲境界の各表に、一覧の全領域が一度ずつ登場する。
- すべての情報・現物のエッジに、受け渡す内容のラベルがある。
- 補助操作を独立領域にせず、領域内詳細と実装方式を作り込んでいない。
- 人間の判断者、入力元、結果利用者との受け渡しを示した。
- 業務価値、対象境界、詳細化入力、重複・欠落を確認者別に判定できる。
- 未決事項は _TODO_ / _UNDECIDED_ / _ASSUMPTION_ で確定情報と区別し、影響、決定者、決定時期を記載した。未決事項がなければ章を設けていない。
- 「凡例（本プロダクト共通）」を設けた場合、他の章の凡例がその定義を再掲せず参照している。設けない場合、各図の凡例で形状・色・絵文字の意味が完結している。
