# ステータス定義（STSD）作成レシピ

Status Definition Authoring Recipe

一つの業務対象について、状態で判断をそろえたい理由から、状態と遷移を説明できる内容に仕上げるための作り方を示す。

## 1. このレシピの使い方

- STSD は、状態で判断をそろえたい業務課題（Why）を「目的」で引き継ぎ、一つの対象の状態と遷移（What）を「状態一覧」と「状態遷移」で定め、現在状態の決め方と遷移の条件・判断者（How）を「状態の判定」と遷移表で示す。状態値と遷移 ID で、図・遷移表・関連文書・レビュー指摘から同じ状態と遷移をたどれるようにする（Trace）。実装条件式や操作手順は後続設計へ委ねる。

## 2. 作成前に集める情報

| 項目             | 集める情報                                                     | 取り出し元               |
| ---------------- | -------------------------------------------------------------- | ------------------------ |
| 対象と業務境界   | 状態を持つ一つの対象、状態変更が始まる業務と対象外の業務       | 関連 CDFD、業務分析担当  |
| 状態で行う判断   | 誰がその状態を見て、次に何をするかを決めるか                   | 現場の担当者への聞き取り |
| 状態候補         | 現場で「いま何の状態か」と答える名称・通称と、そう判断する事実 | 現場の担当者への聞き取り |
| 状態変更イベント | 誰が何をした、または何が起きたときに状態が変わるか             | 関連 CDFD、現場の担当者  |
| 管理場所と正本   | 現在状態を確かめる記録と、派生して作る一覧・集計               | 帳簿・台帳・記録の現物   |
| 旧記録の扱い     | 旧状態値・旧イベント・未設定の記録があるか                     | 既存の記録、移行の担当者 |

## 3. 全体の作成手順

1. 対象を一つに決め、「目的」と「適用範囲」を書く。対象が決まらないと、状態候補の粒度と終了点の要否が決まらない。
2. 状態候補と状態変更イベントを同時に聞き取り、意味か成立条件が同じ候補を統合して「状態一覧」を仮置きする。名称とイベントを別々に集めると、つながらない状態が残る。
3. 「状態の判定」に正本の記録と現在状態を一つに決める規則を書く。成立条件だけでは判定が分かれる箇所が、ここで見つかる。
4. 「状態遷移」で正常系の図と直下の遷移表を作り、その後に例外分岐と戻りを加える。正常系を先に描くと、例外がどの状態から外れるかが見える。
5. 図から到達できない状態、出口のない状態、区別できない状態を探し、「状態一覧」へ戻して直す。
6. 関連文書と状態名・イベント名を突き合わせ、残った未決事項だけを「今後の検討メモ」へ置く。
7. 最後に H1 直下の頭書きを書く。対象と到達点が決まってから書くと、本文の言い直しにならない。

## 4. 各章の書き方

### 4.1. 頭書きと目的

問い:

- 状態は対象の何を管理するのか（進み具合、利用可否など）。
- 誰がその状態を見て、どの業務の要否を判断するのか。

コツ:

- 「状態を区別しないと、どの判断がそろわないか」と聞くと、管理する内容と判断が一度に出る。
- 上位の概要や CDFD に書かれた背景は写さず、参照に置き換える。

### 4.2. 適用範囲

問い:

- どの開始イベントから、どこまでの業務で状態変更を扱うのか。
- 完了・中止の後も、差し戻しや記録更新のために状態を管理し続けるのか。

コツ:

- 「完了した後に戻すことはあるか」を聞くと、終了点を置くかどうかが決まる。記録を保存するだけなら継続の理由にならない。

### 4.3. 状態の判定

問い:

- 現在状態を確かめる正本はどの記録で、どれが派生した一覧か。
- 旧状態値や未設定の記録を、どう読み取るのか。

コツ:

- 同じ対象の記録を二人が別々に判定し、同じ状態になるか確かめる。分かれた箇所へ順序や優先関係を補う。
- 根拠のない読み替えや初期値は仮定せず、未決事項へ回す。

### 4.4. 状態一覧

問い:

- その状態になると、誰の判断や管理責任が変わるのか。
- 隣の状態と、どの事実で区別できるのか。

コツ:

- 単なる処理待ちを状態にしたくなったら、判断や責任が変わるかを確かめ、変わらなければ前の状態に含める。
- 二つの候補が同時に成り立つなら、統合するか「状態の判定」に優先関係を書く。

### 4.5. 状態遷移

問い:

- 例外の経路は、復帰・終了・人間の判断のどこへ進むのか。
- 分岐の条件は、記録や判断から yes / no で決められるのか。

コツ:

- 補足には、判断者・証跡・例外時の扱いなど、図から読めない根拠だけを書く。
- 承認者や共通条件など、運用ガイドなどの上位成果物を正とする内容は写さず、参照に置き換える。

### 4.6. 今後の検討メモ

問い:

- 決まっていない例外状態・条件・用語・責任境界はどれか。
- 決まるまで、どの遷移をどう扱うのか。

コツ:

- 「今後検討」だけで終えず、影響する状態または遷移 ID と、決まるまでの扱いを聞いて書く。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 各状態について「その直前は何か」「何が起きてこの状態になるか」を逆向きにたどり、入口のない状態を探す。
2. 各状態について「次に何へ進むか」「進めないときはどうなるか」を順向きにたどり、出口の理由を説明できない状態を探す。
3. 同じイベントから分かれる矢印で条件を一つずつ反転し、重なりと漏れを探す。
4. 各状態が「目的」のどの判断に使われるかを確かめ、使われない状態を統合する。
5. 関連 CDFD の状態変更プロセスを一つずつたどり、対応する遷移のないプロセスを探す。

## 6. 良い例 / 悪い例

| 観点     | 良い例                                                         | 悪い例                                 |
| -------- | -------------------------------------------------------------- | -------------------------------------- |
| 対象     | 商品の入荷から販売・返品までを一文書で扱う                     | 商品と発注の状態を同じ一覧へ混在させる |
| 分岐     | 合格と、数量違いまたは品質不良を別の条件にする                 | 成功 / それ以外                        |
| 処理待ち | 検品待ちは、検品者が受入可否の判断を負うため独立した状態にする | 画面の処理中表示をそのまま状態にする   |
| 補足     | 返品の判断者を店主代表とし、仕入記録に返品理由を残す           | 図と同じ経路を文章で順に説明する       |

## 7. レビュー観点

| 観点         | 確認内容                                                             |
| ------------ | -------------------------------------------------------------------- |
| 目的との対応 | 各状態と遷移が、「目的」に書いた誰のどの判断に使われるか             |
| 業務妥当性   | 現場の判断と例外を表し、対象の開始から到達点までを説明できるか       |
| テスト可能性 | 初期・正常・例外・到達点の経路と分岐条件から状態遷移テストを組めるか |
| 委譲の境界   | 実装条件式・画面操作・詳細 API を後続設計へ委ね、書きすぎていないか  |

## 8. 仕上げチェック

- 各状態が、「目的」に書いた判断のどれかに使われている。
- 例外の経路ごとに、復帰・終了・人間の判断のどこへ進むかを説明できる。
- 分岐の条件に「適切」「問題なし」など、判定できない語を使っていない。
- 未決事項ごとに、影響する状態または遷移 ID と決まるまでの扱いがある。
