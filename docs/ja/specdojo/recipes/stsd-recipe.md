# ステータス定義（STSD）作成レシピ

Status Definition Authoring Recipe

一つの業務対象について、状態の意味・成立条件と状態間の遷移を矛盾なく一文書へまとめる手順です。

## 1. このレシピの使い方

- 対象の開始から終了または継続管理に至るまでを時系列で聞き取り、状態候補と状態変更イベントを同時に集めます。
- 状態一覧を先に仮置きし、遷移図を描いた後で到達不能・出口なし・重複状態を見つけて一覧へ戻します。
- 遷移の説明を図と一行ずつ照合し、最後に関連フローや用語との名称一致を確認します。
- 実装値は状態の安定識別に必要な範囲だけ扱い、実装条件式や操作手順は後続設計へ委ねます。

## 2. 作成前に集める情報

| 入力             | 確認する内容                                                            |
| ---------------- | ----------------------------------------------------------------------- |
| 対象とスコープ   | 状態を持つ一つの対象、AS-IS / TO-BE、開始・終了または継続管理の業務境界 |
| 目的と利用者     | 状態管理で解決する課題、誰が何を判断・設計・検証するか                  |
| 状態候補         | 現場の正式名称・通称、その状態と判断する事実                            |
| 状態変更イベント | 誰が何をした、または何が起きたとき状態が変わるか                        |
| 分岐条件         | 同じイベントから遷移先が分かれる場合の判定条件                          |
| 管理場所         | 現在状態と変更結果を確認する帳簿、台帳、記録、物の保管先                |
| 関連文書         | 用語集、業務データ辞書、状態を変えるプロセスを示す CDFD                 |

## 3. 全体の作成手順

1. 対象を一つに限定し、H1 直下に頭書き、「目的」に状態管理の目的と利用者、「適用範囲」に対象・スコープ・正本・業務境界を記載します。終了点を置かない場合は、到達点と管理を続ける状態・理由も「適用範囲」へ記載します。
2. 現場で「いま何の状態か」と答える際の名称を集め、意味または成立条件が同じ候補を統合します。
3. 各状態へ値、正式名称、通称、意味、成立条件、管理場所を記入します。
4. 開始点から状態を並べ、状態を変えるイベントと条件を付けて Mermaid の状態遷移図を描きます。
5. 図の矢印へ `T-01` から遷移 ID を割り当て、遷移元・遷移先・イベント・条件・補足を表へ記載します。
6. 状態一覧と図を双方向に照合し、孤立状態、到達不能状態、継続管理の理由を説明できない出口なしの状態、条件の重複を解消します。
7. 関連文書と状態名・イベント名・管理場所を照合し、未決事項だけを今後の検討メモへ残します。

成果物は頭書きに続けて「目的」「適用範囲」「状態一覧」「状態遷移図」「遷移の説明」の順に章を設け、未決事項がある場合だけ「今後の検討メモ」を加えます。

## 4. 各章の書き方

### 4.1. 頭書き

問い:

- 何の状態と遷移を定義する文書か、対象を一つの業務用語で答えられますか。
- 読み手が H1 と頭書きだけで、この文書の主題を識別できますか。
- 利用目的や範囲の詳細を後続の章へ分け、1〜2 行にまとめられますか。

「商品の納品から販売または返品までの状態と遷移を定義する」のように、H1 直下へ記載します。頭書きには見出しを設けません。

### 4.2. 目的

問い:

- 状態を管理することで、どの業務課題を解消し、どの判断をそろえますか。
- 誰が現在状態を判断し、誰が遷移の定義を設計・検証に使いますか。
- 利用者ごとに、この定義を使って何を判断・合意できるか説明できますか。

「目的」へ、状態管理の目的と利用者を 1〜3 文で記載します。「店主代表が現在状態を判定し、開発担当が状態変更を設計し、品質確認担当が例外経路を検証する」のように、利用者と利用結果を結び付けます。

### 4.3. 適用範囲

問い:

- 状態を持つ対象を一つに絞り、AS-IS / TO-BE のどちらを扱うか特定していますか。
- どの開始イベントから、どの業務範囲で状態変更を扱い、どこから先を対象外にしますか。
- 状態を確認する正本はどの記録または保管先ですか。
- 業務上の完了・中止後も、差し戻し、状態確認、記録更新のために状態管理を続けますか。
- 終了点を置かない場合、業務上の到達点と管理を続ける状態・理由を説明できますか。

「適用範囲」へ、対象・スコープ、正本の管理場所、状態変更を起こす業務範囲を箇条書きで記載します。終了点を置くかは、ライフサイクルを閉じる業務イベントと条件の有無から判断します。置かない場合は到達点、継続管理の理由、出力遷移のない継続状態もここへ記載し、記録の保存だけを理由にしません。対象が一状態だけなら、状態変化がない根拠も記載します。

### 4.4. 状態一覧

問い:

- 状態名は業務上の名詞句で、実装フラグや処理名になっていませんか。
- 成立条件だけで第三者が現在状態を一つに判定できますか。
- 通称が正式名称と違う場合、その対応を一行で確認できますか。
- 管理場所から現在状態の根拠を確認できますか。

候補が同時に成立する場合は、状態を統合するか優先関係を明記します。単なる処理待ちを状態にする場合は、業務判断や管理責任が変わることを確認します。

### 4.5. 状態遷移図

問い:

- 開始点から主要な終了点または継続状態まで矢印をたどれますか。
- 状態一覧の全状態が図にあり、図の業務状態が一覧にありますか。
- 各矢印にイベントと条件があり、同じ分岐元の条件を区別できますか。
- 例外経路から復帰、終了、または人間の判断へ進めますか。

まず正常系を描き、その後に例外分岐と戻りを加えます。図が読みにくい場合は、状態を削るのではなく通常系・例外系などの観点で図を分けます。

### 4.6. 遷移の説明

問い:

- 図の全矢印を遷移 ID で一行ずつ説明していますか。
- 業務状態の遷移元・遷移先は状態一覧と同じ名称ですか。初期点は「開始」、終了点は「終了」とし、状態一覧へ追加していませんか。
- 条件は記録や業務判断から yes / no で判定できますか。
- 図だけでは分からない判断者、証跡、例外時の扱いを補足していますか。

図の言い換えだけで終わらせず、レビューとテストで使う判定根拠を補います。ただし、実装条件式や詳細な操作手順は記載しません。

### 4.7. 今後の検討メモ

- 未決の例外状態、条件、用語、責任境界だけを記載します。
- 影響する状態名または遷移 ID、決定者、決定時期を添えます。
- 調査・追記・修正が必要な事項は `_TODO_:`、意思決定待ちは `_UNDECIDED_:`、仮置き前提は `_ASSUMPTION_:` を付けて区別します。

## 5. 深掘り手順

1. 各状態について「その直前は何か」「何が起きてこの状態になるか」を逆向きに確認します。
2. 各状態について「次に何へ進むか」「進めない場合はどうなるか」を順方向に確認します。
3. 同じ成立条件を持つ状態を探し、意味の違いを説明できなければ統合します。
4. 同じイベントから複数の矢印が出る箇所で条件を一つずつ反転し、重複や漏れを探します。
5. 管理場所を一つずつ確認し、状態変更の証跡が残らない遷移へ記録方法または判断者を補います。
6. 関連 CDFD の状態変更プロセスを一つずつたどり、対応する STSD とイベントを特定します。

## 6. 良い例 / 悪い例

| 観点     | 良い例                                                 | 悪い例                                 |
| -------- | ------------------------------------------------------ | -------------------------------------- |
| 対象     | 商品の入荷から販売・返品までを一文書で扱う             | 商品と発注の状態を同じ一覧へ混在させる |
| 状態名   | 販売可能                                               | `is_sellable`                          |
| 成立条件 | 検品結果が合格で在庫数量へ反映された                   | 検品が終わったら                       |
| 遷移     | 検品完了 / 数量・品質が合格                            | 次へ進む                               |
| 分岐     | 合格と、数量違いまたは品質不良を別条件にする           | 成功 / それ以外                        |
| 管理場所 | 仕入記録で受入、在庫記録で販売可能を確認する           | システムで管理する                     |
| 文書分割 | 状態一覧・遷移図・遷移説明を `stsd-product` に集約する | 状態一覧と遷移図を別ファイルで管理する |

## 7. レビュー観点

| 観点         | 確認内容                                                             | 主な確認者             |
| ------------ | -------------------------------------------------------------------- | ---------------------- |
| 業務妥当性   | 状態と遷移が現場の判断・例外を表し、対象のライフサイクルを説明できる | 業務分析担当、店主代表 |
| 一意性       | 成立条件から現在状態を一意に判定できる                               | 業務分析担当           |
| 図表整合     | 状態一覧、状態遷移図、遷移の説明の名称・件数・条件が一致する         | 品質確認担当           |
| 設計入力     | 状態値、イベント、条件、管理場所を後続設計へ引き渡せる               | 技術メンター           |
| テスト可能性 | 初期、正常、例外、終了の経路と分岐条件から状態遷移テストを設計できる | 品質確認担当           |
| 用語整合     | 状態名・通称・イベント名が関連文書と一致する                         | 業務分析担当           |

## 8. 仕上げチェック

- 一文書が一つの対象と一つの AS-IS / TO-BE スコープだけを扱っている。
- 頭書きは H1 直下の 1〜2 行に収まり、「目的」に利用者と利用結果、「適用範囲」に対象・正本・業務境界が分かれている。
- 状態一覧の全行に値、状態名、通称、意味、成立条件、管理場所がある。コードや通称がない欄は `-` で示し、値は `-` を除いて文書内で一意になっている。
- 状態一覧と状態遷移図の業務状態が過不足なく一致している。
- 図の全遷移が遷移の説明に一度ずつあり、イベントと条件が一致している。
- 開始から正常系・例外系の終了状態または継続状態までをたどれ、終了点を置かない理由と継続管理する状態を「適用範囲」で説明できる。
- 条件分岐が相互に区別でき、判定不能な「適切」「問題なし」を使っていない。
- 状態名、通称、イベント名、管理場所が用語集・業務データ辞書・関連 CDFD と矛盾しない。
- 実装条件式、SQL、詳細 API、画面操作を状態定義として記載していない。
- 今後の検討メモの `_TODO_:` を解消し、残る `_UNDECIDED_:`・`_ASSUMPTION_:` には影響する状態または遷移 ID、決定者、決定時期がある。
- 公開対象の本文・図表に個人情報・非公開情報を含めていないことを確認し、公開可否の最終判断と説明責任を人間の PO が担うことを確認している。
- 公開対象と人間の承認者を特定し、`ready` への昇格条件として内容確認、未解決指摘の扱いの合意、公開前確認をそろえている。作成中は `draft` を保ち、昇格は人間の承認後に人間が行う。
