# ステータス定義（STSD）作成レシピ

Status Definition Authoring Recipe

一つの業務対象について、状態の意味・成立条件と状態間の遷移を矛盾なく一文書へまとめる手順です。

## 1. このレシピの使い方

- 状態で判断をそろえたい業務課題を起点に、対象の開始から終了または継続管理に至るまでを聞き取り、状態候補と状態変更イベントを同時に集めます。
- 状態一覧を先に仮置きし、遷移図を描いた後で到達不能・出口なし・重複状態を見つけて一覧へ戻します。
- 各図と直下の遷移表を遷移 ID で一行ずつ照合し、最後に関連フローや用語との名称一致を確認します。
- 実装値は状態の安定識別に必要な範囲だけ扱い、実装条件式や操作手順は後続設計へ委ねます。

## 2. 作成前に集める情報

| 入力             | 確認する内容                                                                                                           |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 対象と業務境界   | 状態を持つ一つの対象、開始・終了または継続管理の業務境界。同じ対象の TO-BE 文書と並ぶ場合だけ AS-IS / TO-BE を区別する |
| 状態管理の目的   | 対象の何を管理する状態か、誰がその状態で何を判断するか、解決する業務課題                                               |
| 状態候補         | 現場の正式名称・通称、その状態と判断する事実                                                                           |
| 状態変更イベント | 誰が何をした、または何が起きたとき状態が変わるか                                                                       |
| 分岐条件         | 同じイベントから遷移先が分かれる場合の判定条件                                                                         |
| 管理場所         | 現在状態と変更結果を確認する帳簿、台帳、記録、物の保管先                                                               |
| 判定規則と互換   | 正本と派生記録の区別、現在状態を一意に決める規則、旧状態値・旧イベント・未設定や欠損記録の扱い                         |
| 関連文書         | 用語集、業務データ辞書、状態を変えるプロセスを示す CDFD                                                                |

## 3. 全体の作成手順

1. 対象を一つに限定し、H1 直下に頭書き、「目的」に対象の何を状態で管理し、誰が何を判断するか、「適用範囲」に対象・業務境界・到達点を記載します。終了点を置かない場合は、管理を続ける状態と理由も「適用範囲」へ記載します。
2. 「状態の判定」に正本の管理場所、現在状態を一意に決める規則、互換の扱いを整理します。
3. 現場で「いま何の状態か」と答える際の名称を集め、意味または成立条件が同じ候補を統合します。
4. 「状態一覧」の各状態へ値、正式名称、通称、意味、成立条件、管理場所を記入し、判定規則と合わせて現在状態を特定できるか確認します。
5. 「状態遷移」で開始点から状態を並べ、矢印に `T-<nn> イベント / 条件` のラベルを付けて Mermaid の状態遷移図を描きます。新規文書では `T-01` から割り当てます。初回の確定前（`status: draft`）は、遷移の追加・削除・並べ替えに合わせて図と表の順に `T-01` から欠番なく振り直してかまいません。分割時も文書全体で通し番号にします。振り直すときは図のラベル・遷移表・本文中の遷移 ID への参照を同時に更新し、振り直したことと旧 ID・新 ID の対応（削除した遷移は削除した旨）を STSD 本文ではなく作業の記録へ残します。一度確定（`status: ready`）した後は既存 ID を保ち、削除した ID は欠番として再利用せず、追加する遷移には過去に未使用の ID を使います。
6. 各図のすぐ下に、その図の遷移 ID・遷移元・遷移先・イベント・条件・補足を一行ずつ記載した遷移表を置きます。分割時も図と表を一組として作成します。
7. 状態一覧・図・遷移表を照合し、孤立状態、到達不能状態、継続管理の理由を説明できない出口なしの状態、条件の重複を解消します。
8. 関連文書と状態名・イベント名・管理場所を照合し、未決事項だけを今後の検討メモへ残します。

成果物は頭書きに続けて「目的」「適用範囲」「状態の判定」「状態一覧」「状態遷移」の順に章を設け、未決事項がある場合だけ「今後の検討メモ」を加えます。スコープは現行を既定として省略し、同じ対象の TO-BE 文書と並ぶ場合だけ AS-IS / TO-BE を明記して文書を分けます。

## 4. 各章の書き方

### 4.1. 頭書き

問い:

- 何の状態と遷移を定義する文書か、対象を一つの業務用語で答えられますか。
- 読み手が H1 と頭書きだけで、この文書の主題を識別できますか。
- 利用目的や範囲の詳細を後続の章へ分け、1〜2 行にまとめられますか。

「商品の納品から販売または返品までの状態と遷移を定義する」のように、H1 直下へ記載します。頭書きには見出しを設けません。

### 4.2. 目的

問い:

- 状態は対象の何を管理しますか。進み具合、利用可否など、区別したい業務上の意味を答えられますか。
- 誰がその状態を見て、次に行える業務や対応の要否を判断しますか。
- 状態を区別しないと、どの判断が揃わず、業務にどのような支障が出ますか。

「商品の受入から販売・返品までの進み具合と販売可否を管理する。店主代表が、売場へ補充できるか、仕入先への返品が必要かを判断するために使う」のように、管理する内容と状態による業務判断を 1〜3 文で結び付けます。文書の承認者や実装・テストへの利用方法は目的に含めません。

### 4.3. 適用範囲

問い:

- 状態を持つ対象を一つの業務用語で特定できますか。
- どの開始イベントから、どの業務範囲で状態変更を扱い、どこから先を対象外にしますか。
- 業務上の完了・中止後も、差し戻し、状態確認、記録更新のために状態管理を続けますか。
- 終了点を置かない場合、業務上の到達点と管理を続ける状態・理由を説明できますか。

「適用範囲」へ、対象、状態変更を起こす業務範囲、到達点を箇条書きで記載します。終了点を置くかは、ライフサイクルを閉じる業務イベントと条件の有無から判断します。置かない場合は継続管理の理由、出力遷移のない継続状態もここへ記載し、記録の保存だけを理由にしません。対象が一状態だけなら、状態変化がない根拠も記載します。

### 4.4. 状態の判定

問い:

- 現在状態を確認する正本はどの記録ですか。履歴や集約記録を併用する場合、どれが正本でどれが派生物ですか。
- 同じ対象の記録から、現在状態を一つに決められますか。イベントをたどる場合の順序と初期値、導出状態がある場合の条件と再判定の契機、成立条件が重なる場合の優先関係は明らかですか。
- 旧状態値・旧イベント、未設定・欠損記録をどう読み取りますか。過去の記録の読み替えと、現在発行する遷移を混同していませんか。

同じ対象の記録を二人が別々に判定し、同じ状態へ至るか確かめます。判定が分かれた箇所へ順序や優先関係を補い、状態固有の成立条件は「状態一覧」にまとめます。互換の扱いが不要ならその旨を示し、根拠がない読み替えや初期値は仮定せず、未決事項へ残します。

### 4.5. 状態一覧

問い:

- 状態名は業務上の名詞句で、実装フラグや処理名になっていませんか。
- 成立条件と「状態の判定」の規則から第三者が現在状態を一つに判定できますか。
- 通称が正式名称と違う場合、その対応を一行で確認できますか。
- 管理場所から現在状態の根拠を確認できますか。

候補が同時に成立する場合は、状態を統合するか「状態の判定」に優先関係を記載します。単なる処理待ちを状態にする場合は、業務判断や管理責任が変わることを確認します。

### 4.6. 状態遷移

問い:

- 開始点から主要な終了点または継続状態まで矢印をたどれますか。
- 状態一覧の全状態が図にあり、図の業務状態が一覧にありますか。
- 各矢印のラベルが `T-<nn> イベント / 条件` となり、同じ分岐元の条件を区別できますか。
- 例外経路から復帰、終了、または人間の判断へ進めますか。
- 各図のすぐ下の遷移表と、図の全矢印が遷移 ID・遷移元・遷移先・イベント・条件で一対一に対応していますか。
- 初回の確定前か、一度確定した後かを確認し、遷移 ID の採番方法を選んでいますか。
- 遷移 ID を振り直した場合、作業の記録から旧 ID のレビュー指摘と対応する遷移を追えますか。
- 業務状態の遷移元・遷移先は状態一覧と同じ名称ですか。初期点は「開始」、終了点は「終了」とし、状態一覧へ追加していませんか。
- 条件は記録や業務判断から yes / no で判定できますか。
- 図だけでは分からない判断者、証跡、例外時の扱いを補足していますか。

まず正常系を描き、その後に例外分岐と戻りを加えます。`stateDiagram-v2` を使い、状態一覧に値がある場合は `状態名<br>値`、値が `-` なら状態名だけを表示します。無条件の矢印も `T-<nn> イベント / イベント発生時` として、開始・終了を含む全遷移を直下の表へ対応付けます。遷移の詳細は表を正本として図と同時に更新し、補足には判断者や証跡など図から読み取れない判定根拠だけを加えます。

図を分ける場合は、業務フェーズや通常系・例外系ごとに遷移を振り分け、分割理由・扱う遷移 ID の範囲・共有状態を各図の前で説明します。共有状態は同じ表示名と `state_id` にそろえ、図のすぐ下へその図の遷移表を置いてから次の図へ進みます。全図を共有状態でつないで到達性を確認し、一つの遷移を複数の図表へ重複させません。共通条件は適用する遷移 ID とともに図の前へまとめ、表から参照します。

### 4.7. 今後の検討メモ

- 未決の例外状態、条件、用語、責任境界だけを記載します。
- 影響する状態名または遷移 ID、決定者、決定時期を添えます。
- 調査・追記・修正が必要な事項は `_TODO_:`、意思決定待ちは `_UNDECIDED_:`、仮置き前提は `_ASSUMPTION_:` を付けて区別します。

## 5. 深掘り手順

1. 各状態について「その直前は何か」「何が起きてこの状態になるか」を逆向きに確認します。
2. 各状態について「次に何へ進むか」「進めない場合はどうなるか」を順方向に確認します。
3. 同じ成立条件を持つ状態を探し、意味の違いを説明できなければ統合します。
4. 同じイベントから複数の矢印が出る箇所で条件を一つずつ反転し、重複や漏れを探します。
5. 管理場所を一つずつ確認し、状態変更の証跡が残らない遷移へ記録方法または判断者を補います。
6. 関連 CDFD の状態変更プロセスを一つずつたどり、対応する STSD とイベントを特定します。

## 6. 良い例 / 悪い例

| 観点     | 良い例                                                             | 悪い例                                     |
| -------- | ------------------------------------------------------------------ | ------------------------------------------ |
| 対象     | 商品の入荷から販売・返品までを一文書で扱う                         | 商品と発注の状態を同じ一覧へ混在させる     |
| 状態名   | 販売可能                                                           | `is_sellable`                              |
| 成立条件 | 検品結果が合格で在庫数量へ反映された                               | 検品が終わったら                           |
| 目的     | 商品の販売可否を管理し、店主が補充・返品の要否を判断する           | 開発担当が設計し、品質確認担当がテストする |
| 判定     | 正本の記録を業務の発生順にたどり、最後に成立した遷移先で判定する   | 見た目で判断する                           |
| 遷移     | `T-02 検品完了 / 数量・品質が合格`                                 | 次へ進む                                   |
| 分岐     | 合格と、数量違いまたは品質不良を別条件にする                       | 成功 / それ以外                            |
| 管理場所 | 仕入記録で受入、在庫記録で販売可能を確認する                       | システムで管理する                         |
| 図の分割 | 「状態遷移」で通常系の図と直下の表、例外系の図と直下の表を順に置く | 図を先に並べ、全遷移の表を別章へ置く       |

| 目的との対応 | 状態が管理する内容と、その状態による業務上の判断が結び付いている                              | 業務分析担当、店主代表 |
| 一意性       | 正本・判定規則・互換の扱いと成立条件から現在状態を一意に判定できる                            | 業務分析担当           |
| 図表整合     | 各図と直下の遷移表の ID・遷移元・遷移先・イベント・条件が一致し、業務状態が状態一覧と対応する | 品質確認担当           |
| 設計入力     | 状態値、イベント、条件、管理場所を後続設計へ引き渡せる                                        | 技術メンター           |
| テスト可能性 | 初期、正常、例外、終了の経路と分岐条件から状態遷移テストを設計できる                          | 品質確認担当           |
| 用語整合     | 状態名・通称・イベント名が関連文書と一致する                                                  | 業務分析担当           |

## 8. 仕上げチェック

- 一文書が一つの対象を扱い、現行を既定としてスコープを省略している。同じ対象の TO-BE 文書と並ぶ場合だけ AS-IS / TO-BE を明記して文書を分けている。
- 頭書きは H1 直下の 1〜2 行に収まり、「目的」は状態が管理する内容と誰が何を判断するか、「適用範囲」は対象・業務境界・到達点、「状態の判定」は正本・判定規則・互換の扱いに分かれている。
- 状態一覧の全行に値、状態名、通称、意味、成立条件、管理場所がある。コードや通称がない欄は `-` で示し、値は `-` を除いて文書内で一意になっている。
- 状態一覧と状態遷移図の業務状態が過不足なく一致している。
- 「状態遷移」で各図のすぐ下にその図の遷移表があり、図と表の間に説明文や別の図を挟んでいない。全遷移のラベルが `T-<nn> イベント / 条件` で、直下の表と一対一に一致し、分割時も文書全体で重複や欠落がない。
- 開始から正常系・例外系の終了状態または継続状態までをたどれ、終了点を置かない理由と継続管理する状態を「適用範囲」で説明できる。
- 条件分岐が相互に区別でき、判定不能な「適切」「問題なし」を使っていない。
- 状態名、通称、イベント名、管理場所が用語集・業務データ辞書・関連 CDFD と矛盾しない。
- 実装条件式、SQL、詳細 API、画面操作を状態定義として記載していない。
- 今後の検討メモの `_TODO_:` を解消し、残る `_UNDECIDED_:`・`_ASSUMPTION_:` には影響する状態または遷移 ID、決定者、決定時期がある。
- 公開対象の本文・図表に個人情報・非公開情報を含めていないことを確認し、公開可否の最終判断と説明責任を人間の PO が担うことを確認している。
- 公開対象と人間の承認者を特定し、`ready` への昇格条件として内容確認、未解決指摘の扱いの合意、公開前確認をそろえている。作成中は `draft` を保ち、昇格は人間の承認後に人間が行う。
