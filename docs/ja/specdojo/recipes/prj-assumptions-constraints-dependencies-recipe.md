# 前提・制約・依存関係 作成レシピ

Assumptions, Constraints and Dependencies Writing Recipe

前提・制約・依存関係を、条件が変わったときに所有者が影響を確かめ、判断者へつなげられる内容に仕上げるための作り方を示す。

## 1. このレシピの使い方

- 本書は、スコープ・憲章が定めた守る成果と境界（Why）を引き継ぎ、それを実行するために置く条件・守る限界・受ける提供（What）を定め、確認・変化時の対応と判断者（How）を決める。各条件は項目 ID の同じ行で根拠から対応までたどれるようにする（Trace）。
- 「作成前に集める情報」をメモでそろえてから、「全体の作成手順」の順に書く。
- 書き終えたら「レビュー観点」で読み直し、「仕上げチェック」で確かめる。

## 2. 作成前に集める情報

| 項目             | 集める情報                                                 | 取り出し元                     |
| ---------------- | ---------------------------------------------------------- | ------------------------------ |
| 境界             | 対象外、境界の判断基準、すでに監視・記録先を持つ判断       | スコープ、憲章                 |
| 結論だけの制約   | 予算枠・公開情報など、結論はあるが監視の仕組みがない条件   | 憲章の主要前提・制約           |
| 成立条件         | 欠けると進めない人・情報・環境・先行成果物                 | 計画担当・実行担当への聞き取り |
| 受ける提供・判断 | 依存先、受け取る物、受け取れたと分かる記録、決定待ちの論点 | 依存先の担当、登録簿の決定記録 |
| 変化の知らせ     | 変化を最初に知る人と、その記録                             | 所有者候補への聞き取り         |

## 3. 全体の作成手順

1. 候補を挙げ、スコープ・憲章ですでに決まっている境界を先に外す。外さずに分類を始めると、上位文書の言い直しが行に残る。
2. 残った候補を、自分たちが成り立つと置く仮説（前提条件）、守る限界（制約事項）、他者から受ける提供・判断（依存関係）に分ける。迷う候補は「誰が提供を止められるか」で分ける。
3. 前提条件・制約事項・依存関係を、それぞれ根拠・影響・確認方法・対応と対にして書く。
4. 変化の種別ごとに、最初に確かめることと次の判断者を影響評価と対応方針へまとめる。
5. 最後に監視・変更管理と冒頭文を書く。登録した条件が決まってからだと、見直しの契機を条件から逆算できる。

## 4. 各章の書き方

### 4.1. 前提条件

問い:

- 何が成り立たないと計画が止まり、それはどの記録で確かめられるか。
- 崩れたとき、誰のどの作業が止まるか。

コツ:

- 「誰が止められるか」と聞き、相手が自分たち以外なら依存関係へ移す。端末・リポジトリ・作業環境は前提に入れやすいので注意する。
- 確かめられない仮説は断定せず、仮置きと確認先を残す。

### 4.2. 制約事項

問い:

- どの行為が起きたら、限界を越えたと判定するか。
- その限界は、どの作業・期間に掛かるか。

コツ:

- 憲章が結論だけを示す制約は、展開元の章を書き、監視と逸脱時の対応を足す。憲章がすでに監視・記録先を持つ判断は、写さず参照に置き換える。
- 製品名で書きたくなったら、守りたい意図（費用・外部依存・公開適性）を聞き直す。

### 4.3. 依存関係

問い:

- 誰から何を受け取れたら成立とし、誰がいつどの記録で確かめるか。
- 決定のうち、どこまで決まり、どこが未決か。

コツ:

- 依存先の担当に「受け取ったと言える記録は何か」を聞く。名前だけの依存は成立を判定できない。
- 本書の根拠として読んだだけの文書を依存先に入れやすいので注意する。

### 4.4. 影響評価と対応方針

問い:

- 変化したとき、最初に確かめる範囲はどこか。
- 一次対応を担う所有者と、最終判断者はそれぞれ誰か。

コツ:

- 「遅れる」「困る」で止まったら、どの成果物・作業・判断に響くかを聞き直す。
- 判断者が決まっていなければロールで補わず、決定先を残す。

### 4.5. 監視・変更管理

問い:

- 本書を見直す具体的な出来事は何か。
- 変化を検知したら、どの記録へ残し、どの計画・作業へ追従させるか。

コツ:

- 登録した各行の変化のトリガーを集めると、見直しの契機の漏れが見つかる。
- 発生済みの支障・将来の不確実性・計画変更・決定を一つの記録に混ぜやすいので、記録先を分けて聞く。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 各行が、スコープ・憲章のどの守る成果または境界に応えるかを確かめ、対応のない行と、上位文書で決まった境界の言い直しを外す。
2. 各行の対応方針が、その行の影響を減らすかを確かめる。
3. 影響評価と対応方針の各行が、どの項目 ID の変化から来るかを確かめる。
4. 監視・変更管理の契機に、登録した各行のトリガーが入っているかを確かめる。

## 6. 良い例 / 悪い例

| 観点     | 良い例                                                                   | 悪い例                                     |
| -------- | ------------------------------------------------------------------------ | ------------------------------------------ |
| 分類     | 「代表試行への協力者を確保できる」を前提にし、未確保時の延期判断を添える | 「店頭で使う端末を利用できる」を前提に書く |
| 依存     | 端末を依存先にし、営業開始前の動作確認とその記録先を書く                 | 「端末がある」とだけ書く                   |
| 重複排除 | 対象外の境界は章冒頭でスコープへ委ねる                                   | スコープの対象外を言い換えて制約に書く     |
| 制約     | 「承認済み予算枠がない間は発注しない」と、発注前の確認を書く             | 「予算に注意する」とだけ書く               |
| 部分決定 | 決定済みの部分と未決の部分を分け、未決の当面の扱いを書く                 | 一部の決定だけで依存を成立済みとする       |
| トリガー | 「対象外の機能を初期対象へ足そうとした」と書く                           | 「必要に応じて確認する」と書く             |

## 7. レビュー観点

| 観点         | 確認内容                                                         |
| ------------ | ---------------------------------------------------------------- |
| 根拠         | 各行がスコープ・憲章と食い違わず、守る成果か境界に対応しているか |
| 変化への備え | 所有者が変化を知る手段と、次の判断者へつなぐ対応があるか         |
| 下流入力     | 計画・受入の担当者が、待つべき条件と未決の論点を見分けられるか   |
| 責務の境界   | 計画・設計・実装の詳細やリスクの管理を本書に書き込んでいないか   |

## 8. 仕上げチェック

- 未確認の事実・責任者・期限を断定せず、確認先または決定時期を残している。
- 個人情報、秘密情報、非公開の組織情報を含めていない。
- 影響評価と対応方針・監視・変更管理から、変化した条件の項目 ID へたどれる。
