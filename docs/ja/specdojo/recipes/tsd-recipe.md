# 技術領域別 技術スタック詳細定義（TSD）作成レシピ

Technology Stack Detail Definition (TSD) Writing Recipe

採用した技術や実行基盤について、別の担当者が構成を再現し、利用できる状態か判断できる文書へ仕上げる手順を示します。初期構築、クライアント接続、日常利用の違いを整理し、設定の根拠から確認・復旧までをつなぎます。

## 1. このレシピの使い方

- 上位設計や非機能要件から、対象の技術で実現する利用場面と守る条件を短く抜き出す。技術一覧の採用理由や組織全体の運用方針は、その正本への参照で引き継ぐ。
- 「作成前に集める情報」をメモし、「全体の作成手順」で一冊の担当範囲を決める。初期構築・接続・日常利用をまとめるか分けるかは、読み手の開始条件と設定の更新単位から判断する。
- 「各章の書き方」を使い、構成、採用値、反映操作、正常性の判定を具体化する。必要な設定例やコマンドは対象環境で再現できる粒度にし、内部クラス、詳細 API 仕様、SQL 全文の設計はその担当文書へ委ねる。
- 最後に、利用目的に対する採用設定、設定を反映する操作、確認結果の対応をたどる。文書 ID、設定項目名、確認項目名で根拠を追跡し、未実施の確認は残る作業として示す。

## 2. 作成前に集める情報

秘密値を収集せず、次の問いに答える短いメモを作る。確認不足は _TODO_、意思決定待ちは _UNDECIDED_、仮の前提は _ASSUMPTION_ を付け、担当と確認・判断の時期を添える。

| 入力               | 答える問い・集める情報                                                                                   |
| ------------------ | -------------------------------------------------------------------------------------------------------- |
| 利用目的と根拠     | 誰が何をできるようにするか。上位設計のどの責務・品質条件に応えるか                                       |
| 文書の境界         | 技術一覧、既存の基盤定義、接続設定、利用手順のどこに正本があるか                                         |
| 環境と権限         | OS、実行環境、ユーザー、権限、依存の版、必要な CPU・メモリ・ディスクは何か。特別な条件がない項目はどれか |
| 配置と経路         | 接続元、ホスト、コンテナ、サービスはどこで動き、どの方向へ通信するか。公開範囲はどこまでか               |
| 設定の事実         | 導入済みの版、有効な設定、保存先、優先順位、再起動の要否を何で確認できるか                               |
| 採用の判断         | 決定済みの値と推奨候補は何か。互換性、ライセンス、資源の制約と採否の根拠は何か                           |
| 認証と公開範囲     | 認証方式、秘密情報の取得・保存・参照の仕組みは何か。固有の接続先や識別子を公開できるか                   |
| 確認と証跡         | 最小の利用成功は何か。確認場所、期待結果、確認環境・版・日付、記録先は何か                               |
| 継続利用と変更影響 | 切断、再起動、再構築で何が残るか。旧方式との競合、切り戻し、撤去で失う状態は何か                         |

## 3. 全体の作成手順

1. 利用目的を一文にし、文書を読み始める人の状態と、読み終えて確認する到達状態を書き出す。独立した利用目的が混ざっていたら別文書へ分ける。
2. 初期構築・接続設定・日常利用の担当を決める。同じ読み手が同じ前提で一続きに作業し、設定を一か所で保守できるなら一冊にまとめる。構築済み基盤を複数のクライアントが利用する、または接続・再開だけを繰り返すなら分冊を選ぶ。分冊ごとに前提の文書と開始できる確認結果をメモする。
3. 対象が分かる `tsd-<term>.md` の名前と配置を決め、既存文書との重複を確かめる。各設定の正本を一つ決め、別冊側ではその完了条件と本書で変える差分を示す。
4. 章の下書きを「概要・位置づけ」「対象環境・前提条件」「全体構成・接続経路」「採用技術・設定」「導入・初期設定」「接続設定」「動作確認」「継続利用・運用」「制約・トラブルシュート」「更新・復旧・撤去」「参照情報」の流れで置く。対象に応じて章を統合・並べ替え、扱わない手順は対象外とする理由や委譲先を概要へ残す。
5. 接続元・ホスト・コンテナなどに呼び名を付け、配置と通信方向を図か表にする。各操作の実行場所、設定保存先、権限をこの呼び名へそろえる。
6. 採用設定を表にし、推奨候補や任意の選択肢と分ける。実測・決定・公式情報のどれを根拠にしたか確かめ、裏付けがない版や容量は決めた値として埋めない。
7. 導入、設定変更、接続の順序を組み立てる。設定を追加・部分変更・全体置換する範囲と、既存設定を残す方法、反映に必要な操作を各段階へ添える。
8. 基盤の起動から最終利用まで確認を段階化し、各確認に期待結果と失敗時の戻り先を書く。設定の有効値の確認は、単なる疎通確認と分ける。
9. 切断・再接続・再起動・再構築の違いを調べ、必要な再開操作と失われる状態を書く。移行や撤去を扱う場合は、旧方式との共存可否、切り戻し、保持するデータを先に決める。
10. 本文、設定例、出力例を公開可否の観点で読み直す。秘密値は参照方法へ、機密の固有情報はプレースホルダーへ置き換える。
11. 「レビュー観点」と「仕上げチェック」で、別の担当者が開始条件から正常性の判定まで進めるか確認する。未確認の条件には残る確認方法を付け、成功した事実と区別して仕上げる。

## 4. 各章の書き方

以下は下書きを具体化するための順序である。各章を独立させるか、関連する章へまとめるかは、読み手が行う作業に合わせて選ぶ。

### 4.1. 概要・位置づけ

- 問い: どの利用目的に応え、初期構築・接続・日常利用のどこを扱うか。読み手が既に完了している作業は何か。
- 書き方: 目的、対象、対象外を短く置き、別冊へ進む境界にその開始条件を添える。既存文書は project 修飾 doc id の `[[id|title]]` 形式で参照し、未作成なら `tsd-<term>.md` のような仮のファイル名で示す。
- 良い例: 「構築済み基盤へ接続するクライアントの設定を扱う。基盤側の起動と利用対象の登録確認を開始条件とし、本体の導入は基盤定義へ委ねる」。避けたい例: 「関連技術の設定をまとめる」だけで責務を決めない。

### 4.2. 対象環境・前提条件

- 問い: コマンドをどこで、誰が、どの shell・作業ディレクトリで実行するか。OS や版によって変わる条件はあるか。
- 書き方: 実行場所ごとに OS、ランタイム、権限、導入済みの依存、必要資源をそろえる。特別な権限や追加資源が不要なら、その旨を明記する。実測した環境と一般的な推奨環境を分ける。
- 良い例: 「ホストで常駐プロセスを管理し、接続元コンテナで利用確認する。管理者権限を使う操作は導入時だけ」。避けたい例: 「ローカルで実行する」とだけ書き、端末とホストを混同させる。

### 4.3. 全体構成・接続経路

- 問い: どのプロセスがどこで動き、どこからどこへ接続するか。待受アドレス、接続先アドレス、公開範囲は対応するか。
- 書き方: 配置と通信方向を図か対応表にし、端末・ホスト・コンテナの境界を先に描く。名前解決、ポート転送、トンネルを使う場合は、経路ごとに入口と出口を結ぶ。
- 良い例: 「接続元 → トンネル → ホストの公開ポート → コンテナの待受ポート」と経路を示す。避けたい例: すべてを同じ `localhost` とし、どの環境のアドレスか説明しない。

### 4.4. 採用技術・設定

- 問い: その値は何を満たすために採用したか。候補・任意設定・未決事項との違いは何か。設定ファイルと環境変数のどちらが実行プロセスへ反映されるか。
- 書き方: 次の表へ、設定の適用範囲と確認方法まで一行でつなぐ。GUI 設定も画面項目・保存先・反映条件を調べる。推奨値を適用する場合は、採用を決めた記録を別に残す。
- 良い例: 「推奨候補の並列数は評価後に採否を決める。現行の採用値は有効値の確認結果に基づく」。避けたい例: 推奨値を無条件に採用済みの表へ混ぜる。

| 対象・用途         | 設定項目       | 採用値・版           | 適用範囲                 | 理由・制約     | 反映・確認方法                 |
| ------------------ | -------------- | -------------------- | ------------------------ | -------------- | ------------------------------ |
| 利用場面と構成要素 | 製品上の項目名 | 決定した値・単位・版 | 環境・ユーザー・プロセス | 根拠と適用条件 | 保存先・反映操作・有効値の確認 |

下書きでは次のように状態を整理し、未決の値を採用値の代わりに埋めない。

| 状態         | 書き進める方法                                                         |
| ------------ | ---------------------------------------------------------------------- |
| 採用値       | 決定の根拠と対象環境を示し、反映操作と確認へつなぐ                     |
| 推奨値       | 推奨する条件と採否の判断方法を添え、現行の採用値と分ける               |
| 任意の選択肢 | 利用する場合の前提と追加確認を示し、共通手順から分岐させる             |
| 確認不足     | _TODO_: 確認対象・方法・担当・確認時期を記す                           |
| 意思決定待ち | _UNDECIDED_: 選択肢・判断基準・担当・判断期限・未決による影響を記す    |
| 仮の前提     | _ASSUMPTION_: 仮置きの根拠・成立条件・検証方法・担当・見直し時期を記す |

### 4.5. 導入・初期設定

- 問い: 何を先に導入し、どの保存先を変更するか。既存の利用者設定を残せるか。再起動や権限変更で何が影響を受けるか。
- 書き方: 順序付き手順に実行場所、shell、作業ディレクトリ、事前条件、変更先を付ける。コマンドや再現に必要な補助スクリプトは言語識別子付きコードブロックへ置き、追加・部分変更・全体置換を区別する。導入と起動、起動と再起動は別の段階にする。
- 良い例: 「既存設定の対象セクションへ追加し、他の接続先を保持する。反映前にバックアップを取り、再起動が既存セッションへ与える影響を確認する」。避けたい例: ファイル全体の例を示して、そのまま上書きさせる。

### 4.6. 接続設定と秘密情報の扱い

- 問い: 接続方式と認証方式は何か。接続先の登録名、クライアントの選択名、リクエスト中の識別子は対応するか。例に含める値を公開できるか。
- 書き方: 接続先の基点、認証情報の参照方法、識別子の対応を先に整理する。秘密値を読まずに、設定の仕組みと公開可否を判断し、次の順序で例を作る。
- 良い例: 汎用の接続先 `service.example.invalid` と `<TOKEN>` を説明用に置き、実行時は credential store から渡す方法を示す。避けたい例: 実トークン付き URL や認証設定の全文を貼る。

1. ポートや接続方式、汎用ホスト名など、再現に必要で公開できる情報を選ぶ。接続情報という理由だけで一律に隠さない。
2. 個人・組織固有のホスト名、アカウント、URL は公開可否を確かめ、機密なら `<SERVICE_HOST>` などのプレースホルダーへ置き換える。公開可否が不明なら _TODO_ として確認先を示す。
3. API キー、トークン、パスワード、秘密鍵は実値を載せず、取得・保存・注入・参照方法を書く。認証不要の方式なら、その適用範囲と公開範囲を説明する。
4. 設定例、URL、出力例、ログ例、コマンド履歴にも秘密が残らない形を選ぶ。公開用の例と実行時に供給する値の対応を説明する。

### 4.7. 動作確認

- 問い: 起動、疎通、認証、識別子の解決、実際の利用のうち何を確認できたか。失敗したら一つ前のどの前提へ戻るか。
- 書き方: 下の段階を対象に合わせて選び、確認対象、実行場所・方法、期待結果、失敗時の確認先を表にする。認証不要などの段階は理由を添えて省く。有効値や版は専用の表示・照会で確かめ、疎通成功だけから設定反映を推定しない。
- 良い例: 「一覧応答は疎通と登録済み識別子の確認に使い、最小入力への応答で利用機能を確かめる」。避けたい例: 「起動したので設定と接続はすべて正常」とする。

| 段階           | 確認の組み立て方                                         | 期待結果と切り分けの例                                                         |
| -------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 基盤・プロセス | 基盤側で依存と起動状態、必要な有効値を確認する           | 対象プロセスが稼働し、有効値が採用値に一致する。起動設定・反映操作・ログへ戻る |
| 名前解決・疎通 | 実際の接続元から対象の入口へ到達できるか確認する         | 接続でき、所定の応答項目が返る。名前解決・待受・転送・公開範囲を調べる         |
| 認証・識別子   | 認証方式と利用対象の登録名・選択名を確認する             | 対象の権限と識別子で利用できる。認証の参照先・権限・登録名の対応へ戻る         |
| 最小利用       | 小さい入力で一機能を実行し、クライアント経由でも確認する | 意図した結果が得られる。直接利用が成功するならクライアント固有設定を調べる     |

負荷や応答時間の目標を扱うなら、根拠となる要求とともに入力サイズ、並列数、初回・再実行の別、測定方法、合否を判断する時点をそろえる。未実施なら _TODO_ と確認環境・担当・残る方法を残し、想定する期待結果と実測した結果を分ける。

### 4.8. 継続利用・運用

- 問い: 切断後に戻る場所はどこか。再接続だけで再開するものと、明示的な再開が必要なものは何か。設定、認証状態、作業データ、実行中セッションはどこに保存されるか。
- 書き方: 通信切断、プロセス再起動、環境再構築を分け、保持する状態と復元操作を表にする。長時間実行は監視対象、根拠のある正常範囲、負荷を減らす判断条件を添える。組織的な監視体制やバックアップ方針は運用設計へ委ねる。
- 良い例: 「接続断では実行セッションへ戻り、プロセス終了時は明示的に再開する。再構築時は永続化した設定を復元し、失ったセッションを作り直す」。避けたい例: 「接続し直せばすべて再開する」。

### 4.9. 制約・トラブルシュート

- 問い: どの症状からどの段階の失敗を疑うか。確認済みの制約と未検証の条件はどれか。
- 書き方: 動作確認の失敗先を症状別に並べ、最初の確認、次の確認、回避・復旧を結ぶ。原因が確定していないものは仮説として扱い、設定の削除や再インストールより先に観測できる情報を選ぶ。
- 良い例: 「基盤からの応答はあるがクライアントで対象を選べない場合、登録識別子と選択名を照合する」。避けたい例: 「接続できなければ再インストール」。

### 4.10. 更新・復旧・撤去

- 問い: 旧方式と共存できるか。何を停止し、何を保存してから変更するか。どの確認で切り戻しを判断するか。
- 書き方: 競合する待受・自動起動・保存先を洗い出し、変更前の退避、旧方式の停止、新方式への変更、確認、切り戻しの順に書く。撤去はプロセス、設定、認証状態、データごとに保持・削除を分ける。
- 良い例: 「新方式の利用確認が失敗したら旧設定へ戻す。データ削除は撤去とは別の選択として影響と復元可否を示す」。避けたい例: 停止や再構築の手順にデータ削除を混ぜる。

### 4.11. 参照情報

- 問い: 採用判断や手順のどの主張を、どの資料・確認記録で確かめ直せるか。適用した版や確認日は分かるか。
- 書き方: 公式情報には対象の版や確認日、関連文書にはその責務を添える。設定表や確認項目から根拠へたどれる名前を使い、参考に読んだ資料をすべて採用根拠にしない。
- 良い例: 「環境変数の反映条件」の根拠を、適用した版の公式情報と確認記録へ結ぶ。避けたい例: 製品トップページだけを列挙し、何を裏付けるか示さない。

## 5. 深掘り手順

1. 主要な採用設定を一つ選び、利用目的や上位の品質条件へ戻れるか調べる。戻れなければ、値の追加より先に採用理由を明らかにする。
2. 設定ごとに保存先、適用範囲、優先順位、反映操作、有効値の確認をつなぐ。shell で見える値と常駐プロセスが受け取る値が同じか確かめる。
3. 接続元を起点に経路をたどり、基盤側で成功する確認とクライアント側で成功する確認を分ける。識別子は登録・選択・確認要求の三か所で照合する。
4. 再接続や再構築を仮に起こしたとして、保存された設定だけで復帰できるか点検する。セッションや一時データが足りなければ再開操作を具体化する。
5. 事実に見える未検証の主張を探し、確認不足・意思決定待ち・仮の前提へ分ける。それぞれに確認・判断方法と担当、時期を付ける。
6. 別冊と同じ設定値を持つ箇所を探し、正本を一つに寄せる。参照側には値の転載に代えて開始条件と本書で変える差分を残す。

## 6. 良い例 / 悪い例

| 観点             | 良い例                                                       | 悪い例                                              |
| ---------------- | ------------------------------------------------------------ | --------------------------------------------------- |
| 文書の分け方     | 基盤導入と接続を分け、接続側に基盤の完了確認と差分だけを書く | 分冊した双方へ同じ導入・設定を転載する              |
| 実行場所         | ホストで起動し、接続元コンテナから疎通を確認する             | 「端末で実行する」だけで場所を特定しない            |
| 値の根拠         | 現行の採用値と推奨候補を分け、未決には判断条件を付ける       | 手本の版・容量・並列数をそのまま必須にする          |
| 設定の反映       | 保存先と優先順位を示し、反映後に対象プロセスの有効値を調べる | shell の値や API の応答だけで全設定の反映を断定する |
| 既存設定との統合 | 既存の接続先を保持して対象項目を追加する                     | 設定例で既存ファイル全体を無条件に置換する          |
| 確認の段階       | 疎通、認証、識別子、最小利用を分け、失敗時に戻る箇所を示す   | クライアントを起動できれば利用可能とする            |
| 継続利用         | 切断後の再接続と処理の再開を区別する                         | 履歴が保存されれば進行中の処理も自動再開するとする  |
| 秘密情報         | 公開可能な経路を示し、秘密値は保存・参照方法で説明する       | 認証設定やログの全文を実値のまま貼る                |
| 撤去             | 自動起動・本体・設定・データの扱いと復元可否を分ける         | アンインストールに全データ削除を含める              |

## 7. レビュー観点

| 観点         | 確認内容                                                                                 |
| ------------ | ---------------------------------------------------------------------------------------- |
| 目的との対応 | 主要な設定が利用目的・品質条件に結び付き、採用理由と制約を説明できるか                   |
| 文書の境界   | 一冊の開始・完了状態が分かり、分冊した設定の正本と差分をたどれるか                       |
| 環境と再現性 | OS・版・権限・依存・資源、実行場所・shell・変更先を特定できるか                          |
| 判断の確度   | 採用・推奨・任意・未決・仮説が混ざらず、未確定事項の担当と確認・判断時期が分かるか       |
| 反映と検証   | 採用値から反映操作・有効値・最終利用までを確認でき、失敗時の戻り先が分かるか             |
| 継続性と復旧 | 切断・再起動・再構築で保持・喪失する状態と、再開・切り戻し操作が対応するか               |
| 公開適性     | 接続経路の説明を残しつつ、秘密値や機密の固有情報を本文・設定例・出力例から除けているか   |
| 委譲と追跡   | 詳細 API・内部設計・組織的な運用方針を担当文書へ委ね、採用判断と確認の根拠を追跡できるか |

## 8. 仕上げチェック

- 初期構築・接続設定・日常利用の担当範囲と対象外が分かり、別冊の手順を始める条件が具体化されている。
- 構成の呼び名と各操作の実行場所が一致し、接続元から利用先までの経路と公開範囲をたどれる。
- 採用値に根拠と適用範囲があり、推奨値や任意設定、未決事項を採用済みと誤読しない。
- 設定の保存先、優先順位、反映条件がつながり、既存設定を保持する方法と変更影響が分かる。
- 確認に期待結果と失敗時の確認先があり、疎通と設定反映、最小利用を別々に判定できる。未実施の確認を成功としていない。
- 継続利用や変更を扱う箇所には、状態の保存、再開、切り戻し、削除の影響が対応している。
- 秘密値を含めず、機密情報のプレースホルダーと実行時の取得・参照方法が対応している。
- 参照先の存在、表内の wikilink の区切りのエスケープ、見出し名による章参照を確かめた。未作成の文書はコード表記で仮置きしている。
- 確認不足・未決・仮の前提には担当と確認・判断の時期があり、判断や再現を妨げる点を読み手が識別できる。
