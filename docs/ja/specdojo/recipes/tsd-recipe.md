# 技術領域別 技術スタック詳細定義（TSD）作成レシピ

Technology Stack Detail Definition (TSD) Writing Recipe

採用した技術や実行基盤を、別の担当者が対象環境で再現し、利用できる状態か判断できる文書に仕上げるための作り方を示す。

## 1. このレシピの使い方

- TSD は、上位設計・非機能要件が求める利用場面と品質条件（Why）を引き継ぎ、採用する設定値と到達状態（What）を定め、導入・接続・確認・復旧の操作（How）で実現する。設定項目名と確認項目名で、採用値から反映操作と確認結果までたどれるようにする（Trace）。
- 「作成前に集める情報」をメモでそろえてから、「全体の作成手順」の順に書く。
- 書き終えたら「レビュー観点」で読み直し、「仕上げチェック」で確かめる。

## 2. 作成前に集める情報

秘密値は集めない。確かめられない点は _TODO_、決まっていない点は _UNDECIDED_、仮に置いた前提は _ASSUMPTION_ を付けてメモに残す。

| 項目               | 集める情報                                                         | 取り出し元                                   |
| ------------------ | ------------------------------------------------------------------ | -------------------------------------------- |
| 利用目的           | 誰が何をできるようにするか、応える責務と品質条件                   | 上位設計、非機能要件                         |
| 文書の境界         | 技術一覧・基盤定義・接続設定・利用手順のどこに正本があるか         | 技術一覧、既存の TSD                         |
| 環境と権限         | 実行場所ごとの OS、ランタイム、ユーザー、権限、依存の版、資源      | 対象環境での確認、構築担当者への確認         |
| 配置と経路         | プロセスの配置、通信方向、待受と接続先のアドレス、公開範囲         | 構成図、ネットワーク設定                     |
| 設定の事実         | 導入済みの版、有効な設定値、保存先、優先順位、再起動の要否         | 対象環境での表示・照会の結果                 |
| 採用の判断         | 決定済みの値と推奨候補、互換性・ライセンス・資源の制約             | 決定記録、公式情報、技術選定の担当者への確認 |
| 認証の仕組み       | 認証方式、秘密の取得・保存・注入の方法、固有の接続先を公開できるか | 基盤の管理者への確認                         |
| 確認の記録         | 最小の利用成功、期待結果、確認した環境・版・日付                   | 確認の実行記録                               |
| 継続利用と変更影響 | 切断・再起動・再構築で残る状態、旧方式との競合、撤去で失う状態     | 対象環境での試行、運用担当者への確認         |

agent に技術の調査や選定を任せる場合は、任せる範囲を起票時の入力に書き、特定の章への指示は雛形のその章に書く（例: 「採用技術・設定」に `_CONTEXT_: 主流のフレームワークを比較し、選定理由と採用値を提案してください`）。

## 3. 全体の作成手順

1. 利用目的を一文にし、読み始める人の状態と、読み終えて確認する到達状態を書き出す。独立した目的が混ざっていたら、ここで別文書へ分ける。ほかの章の範囲はこの到達状態で決まる。
2. 初期構築・接続設定・日常利用を一冊にまとめるか分けるかを決める。同じ読み手が同じ前提で一続きに作業するならまとめ、構築済みの基盤へ複数のクライアントが接続する、または接続と再開だけを繰り返すなら分ける。
3. 接続元・ホスト・コンテナに呼び名を付け、「全体構成・接続経路」を先に描く。以降の章で実行場所と保存先をこの呼び名でそろえられる。
4. 「対象環境・前提条件」に、呼び名ごとの環境と権限を書く。
5. 「採用技術・設定」で採用値を決め、推奨候補・任意の選択肢・未決と分ける。
6. 「導入・初期設定」「接続設定と秘密情報の扱い」で、採用値を反映する順序を組み立てる。
7. 「動作確認」を基盤の起動から最終利用まで段階に分け、各段階の失敗が戻る先を決める。
8. 「継続利用・運用」「更新・復旧・撤去」に、切断・再起動・再構築・移行の影響を書く。
9. 「制約・トラブルシュート」を、動作確認の失敗先から症状別に組み立てる。動作確認を先に書くと、症状と確認箇所が対応する。
10. 「参照情報」に、採用判断と手順の根拠を集める。
11. 最後に「概要・位置づけ」を書く。担当範囲と別冊の開始条件は、ほかの章が決まってから書くと実態とずれない。
12. 本文・設定例・出力例を公開できるか読み直す。

## 4. 各章の書き方

### 4.1. 概要・位置づけ

問い:

- 初期構築・接続・日常利用のどこを扱い、読み手は何を済ませてから読み始めるか。
- 扱わない作業は、どの文書で済ませるか。

コツ:

- 技術一覧の採用理由や上位設計の目的は写さず、参照に置き換える。
- 「関連技術の設定をまとめる」のように担当が決まらない書き方になったら、手順 1 の到達状態へ戻る。

### 4.2. 対象環境・前提条件

問い:

- コマンドを、どこで、誰が、どの shell と作業ディレクトリで実行するか。
- OS や版によって変わる条件はあるか。

コツ:

- 「ローカルで」と書きかけたら、端末・ホスト・コンテナのどれかを構築担当者に聞く。
- 実測した環境と一般的な推奨環境は聞き分けて別の行に書く。

### 4.3. 全体構成・接続経路

問い:

- どのプロセスがどこで動き、どこからどこへ接続するか。
- 待受アドレス、接続先アドレス、公開範囲は対応するか。

コツ:

- 端末・ホスト・コンテナの境界を先に描き、名前解決・ポート転送・トンネルは経路ごとに入口と出口を結ぶ。
- すべてを `localhost` と書くと、どの環境のアドレスか分からなくなる。

### 4.4. 採用技術・設定

問い:

- その値は何を満たすために採用したか。
- 設定ファイルと環境変数のどちらが、実行中のプロセスへ届くか。

コツ:

- 値ごとに「実測・決定・公式情報」のどれが根拠かを聞く。根拠が出ない版・容量・並列数は採用値に入れない。
- 推奨値を採る場合は、採用を決めた記録があるかを確かめる。
- GUI で設定する項目は、画面項目名と保存先を実際に開いて確かめる。

### 4.5. 導入・初期設定

問い:

- 何を先に導入し、どの保存先を変えるか。
- 既存の利用者設定を残せるか。再起動で何が影響を受けるか。

コツ:

- 変更ごとに「追加・部分変更・全体置換」のどれかを決めてから手順を書く。決めずに設定例を置くと、全体の上書きとして読まれやすい。
- 反映前に取るバックアップと、再起動が既存のセッションへ与える影響を管理者に聞く。

### 4.6. 接続設定と秘密情報の扱い

問い:

- 接続先の登録名、クライアントの選択名、リクエスト中の識別子は対応するか。
- 例に含める値を公開できるか。

コツ:

- 秘密値を読まずに、設定の仕組みと公開できるかを管理者に聞く。
- ポートや汎用ホスト名は、接続情報という理由だけで一律に隠さない。公開できるか不明な固有名は _TODO_ にして確認先を書く。

### 4.7. 動作確認

問い:

- 起動、疎通、認証、識別子の解決、実際の利用のうち、何を確かめたか。
- 失敗したら、一つ前のどの前提へ戻るか。

コツ:

- 有効値や版は専用の表示・照会で確かめる。疎通の成功から設定の反映は推定できない。
- 負荷や応答時間を扱うなら、入力サイズ、並列数、初回か再実行か、測定方法、合否を決める時点をそろえて測る。

### 4.8. 継続利用・運用

問い:

- 切断の後にどこへ戻り、再接続だけで再開しないものは何か。
- 設定、認証状態、作業データ、実行中のセッションはどこに保存されるか。

コツ:

- 通信切断・プロセス再起動・環境再構築を、一つずつ仮に起こして確かめる。
- 組織の監視体制やバックアップ方針は書き始めず、運用設計の担当へ渡す。

### 4.9. 制約・トラブルシュート

問い:

- どの症状から、どの段階の失敗を疑うか。
- 確かめた制約と、まだ確かめていない条件はどれか。

コツ:

- 設定の削除や再インストールより先に、観測できる情報を確かめる順に並べる。
- 原因が確定していないものは仮説として書く。

### 4.10. 更新・復旧・撤去

問い:

- 旧方式と共存できるか。何を止め、何を保存してから変えるか。
- どの確認の結果で切り戻すか。

コツ:

- 競合する待受、自動起動、保存先を先に洗い出す。
- データの削除は撤去と別の選択として、影響と復元できるかを聞く。

### 4.11. 参照情報

問い:

- 採用判断や手順の主張を、どの資料や確認記録で確かめ直せるか。
- 適用した版や確認日は分かるか。

コツ:

- 参考に読んだ資料をすべて根拠に並べない。製品のトップページだけでは何を裏付けるか分からない。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 採用設定の各行が、どの利用目的・品質条件に応えるかを確かめる。戻れない行は、値を足すより先に採用理由を聞く。
2. 採用値ごとに、反映する操作と有効値の確認があるかを確かめる。shell で見える値と常駐プロセスが受け取る値は分けて見る。
3. 識別子を、登録・選択・確認の要求の三か所で照合し、食い違いを探す。
4. 確認済みに見える記述ごとに確認記録があるかを確かめ、なければ _TODO_ か _ASSUMPTION_ に戻す。
5. 別冊と同じ設定値を持つ箇所を探し、正本の側へ寄せて、参照側には差分だけを残す。

## 6. 良い例 / 悪い例

| 観点             | 良い例                                                         | 悪い例                                              |
| ---------------- | -------------------------------------------------------------- | --------------------------------------------------- |
| 文書の分け方     | 基盤導入と接続を分け、接続側に基盤の完了確認と差分だけを書く   | 分冊した双方へ同じ導入・設定を転載する              |
| 実行場所         | ホストで起動し、接続元コンテナから疎通を確認する               | 「端末で実行する」だけで場所を特定しない            |
| 値の根拠         | 現行の採用値と推奨候補を分け、未決には判断条件を付ける         | 手本の版・容量・並列数をそのまま必須にする          |
| 設定の反映       | 保存先と優先順位を示し、反映後に対象プロセスの有効値を調べる   | shell の値や API の応答だけで全設定の反映を断定する |
| 既存設定との統合 | 既存の接続先を保持して対象項目を追加する                       | 設定例で既存ファイル全体を無条件に置換する          |
| 継続利用         | 切断後の再接続と処理の再開を区別する                           | 履歴が保存されれば進行中の処理も自動再開するとする  |
| 秘密情報         | `<TOKEN>` を置き、実行時に credential store から渡す方法を示す | 実トークン付きの URL や認証設定の全文を貼る         |

## 7. レビュー観点

| 観点         | 確認内容                                                                     |
| ------------ | ---------------------------------------------------------------------------- |
| 文書の境界   | 一冊の開始状態と到達状態が分かり、分冊した設定の正本と差分をたどれるか       |
| 再現性       | 別の担当者が、実行場所・shell・変更先を特定して同じ手順を進められるか        |
| 判断の確度   | 採用値・推奨候補・任意の選択肢・未決・仮説が混ざっていないか                 |
| 継続性と復旧 | 切断・再起動・再構築で保持・喪失する状態と、再開・切り戻しの操作が対応するか |
| 委譲の境界   | 内部設計・詳細 API・組織の運用方針を書きすぎていないか                       |

## 8. 仕上げチェック

- 採用設定の各行が利用目的に対応し、反映する操作と確認結果までたどれる。
- 構成の呼び名と、各操作の実行場所が一致している。
- 確認記録のない確認を、成功と書いていない。
- 本文・設定例・出力例・ログ例に秘密値がない。
