# 成功基準と受入条件 作成レシピ

Success Criteria and Acceptance Criteria Writing Recipe

業務価値を起点に、プロジェクトの成功と初期受入の可否を、承認者が証跡で判断できる条件に仕上げるための作り方を示す。

## 1. このレシピの使い方

- 概要とスコープから対象利用者と期待効果（Why）を引き継ぎ、業務価値ごとの成功基準と受入条件（What）を定め、測定・確認・承認・再判定の進め方（How）を決める。各条件は業務価値 ID と証跡でたどれるようにする（Trace）。

## 2. 作成前に集める情報

| 項目             | 集める情報                                                   | 取り出し元                   |
| ---------------- | ------------------------------------------------------------ | ---------------------------- |
| 対象と対象外     | 今回判定する成果物・状態と、判定しない範囲                   | プロジェクトスコープ         |
| 利用者と期待効果 | 対象利用者、利用場面、期待する変化                           | プロジェクト概要             |
| 成功の状態       | 初期公開、短期、中長期のそれぞれで、どうなれば成功と言えるか | 承認者・代表利用者への確認   |
| 費用と負荷の上限 | 追加の現金支出、人の作業時間、運用負荷の上限と、その承認者   | 承認者・実行責任者への確認   |
| 測定と証跡       | 観察、件数集計、費用・作業記録などの確認方法と、残せる記録   | 実行責任者・品質担当への確認 |
| 決めきれない値   | 閾値、期限、前提のうち、決定が済んでいないもの               | 確認の過程のメモ             |

## 3. 全体の作成手順

1. 業務価値を最初に定め、ID を付ける。成功基準も受入条件も業務価値に対応付けるため、ここが決まらないと条件の要否を判断できない。
2. 判定対象と適用範囲で、初期受入に必須とする条件と、公開後に判定する成功基準の境目を決める。
3. 成功基準を、公開後の段階まで含めて書く。
4. 受入条件を、価値提供を始められる最小の状態に絞って書く。
5. 判定手順と証跡で、確認の順と否決時の再判定を書く。
6. 最後に例外条件と未解決事項を書く。条件を書く途中で出た決めきれない値を集めると、漏れが減る。

## 4. 各章の書き方

### 4.1. 判定対象と適用範囲

問い:

- 初期公開の GO / Not GO を、どの条件のすべてで判断するのか。
- 当該プロジェクトだけでは因果を判定できない成果はどれか。

コツ:

- スコープの対象・対象外を写したくなったら、スコープへの参照に置き換え、受入判断に要る境目だけを書く。
- 「品質を上げる」のような抽象語が出たら、「利用者が同じ根拠で判断できる」のように、利用者に生じる状態へ言い換える。

### 4.2. 成功基準

問い:

- どの業務価値が実現すれば、プロジェクトが成功したと言えるか。
- 公開後にしか測れない成果を、いつ誰が確かめるか。

コツ:

- 承認者に「公開から半年後、何が起きていれば続ける価値があったと言えるか」を聞くと、短期と中長期の成功の状態が出てくる。
- 「低コスト」を聞いたら、現金支出だけで答えが終わらないよう、作業時間と運用負荷、既存資産や寄付の扱いも続けて聞く。無償の作業を前提にした成功に気付ける。
- 閾値が出たら、何を数えるか、母数と比較対象は何かを、その場で聞き返す。

### 4.3. 受入条件

問い:

- 利用者は何を行い、どの結果なら受け入れられるか。
- 技術的な確認は、どの業務価値を支えるために要るのか。

コツ:

- 公開後の利用件数を受入条件に入れたくなったら、成功基準へ移す。
- 確認者と承認者を一人の役割にまとめがちなので、「誰が証跡を見るか」と「誰が受け入れを決めるか」を分けて聞く。

### 4.4. 判定手順と証跡

問い:

- どの条件を、誰が、どの順で確認するか。
- 否決したとき、何を直し、どの条件を確かめ直すか。

コツ:

- 費用と作業時間の上限は、試行の後では決めにくい。試行の前に承認する手順として置く。
- 証跡を「確認結果」とだけ書きそうになったら、確認日、確認者、条件 ID、母数など、記録に残す中身を聞く。

### 4.5. 例外条件と未解決事項

問い:

- 決めきれない値があっても、初期受入を進められるか。
- 保留したとき、どの条件の判定に効くか。

コツ:

- スコープなどの上位成果物の未決事項は写さず、本書の判定に効く分だけを _UNDECIDED_: で書く。上位成果物が _TODO_: と書いていても、本書では _UNDECIDED_: にそろえる。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 成功基準と受入条件の各行が、どの業務価値に応えるかを確かめ、対応のない行を外すか技術的受入へ移す。
2. 業務価値ごとに、初期公開・短期・中長期のどこで成功を確かめるかを確かめ、抜けている段階を足す。
3. 各条件の測定方法と証跡で、第三者が後から同じ判定を再現できるかを確かめる。
4. 受入条件に混じった公開後の成果や実装詳細を、成功基準や後続成果物へ戻す。

## 6. 良い例 / 悪い例

| 観点           | 良い例                                                            | 悪い例                      |
| -------------- | ----------------------------------------------------------------- | --------------------------- |
| 業務価値       | 店主と家族が同じ手順で在庫を確認できる                            | システムを便利にする        |
| 初期成功基準   | 店主と家族が販売・在庫・つけ確認の必須タスクをすべて完了できる    | 必要な機能が90%完成している |
| 中長期成功基準 | 人気商品の欠品回数が運用前1か月比で50%減少する                    | 店舗運営が改善する          |
| 受入条件       | 商品、数量、支払方法を入力して確定すると販売記録が1件作成される   | 販売機能が正しく動く        |
| 未解決事項     | _UNDECIDED_: オフライン時の記録方法を初期運用開始前に店主が決める | オフライン時は後で決める    |

## 7. レビュー観点

| 観点             | 確認内容                                                             |
| ---------------- | -------------------------------------------------------------------- |
| 業務価値との対応 | 各条件が対象利用者のどの期待効果に応えるかを説明できるか             |
| 初期受入との分離 | 公開後の利用実績や中長期の成果が、初期受入の合否に混じっていないか   |
| 費用と負荷       | 低コストを価値に置く場合、人の作業時間と運用負荷を見落としていないか |
| 対象範囲         | スコープの対象・対象外と食い違っていないか                           |

## 8. 仕上げチェック

- 各業務価値から、成功基準・受入条件・証跡・判断する役割までたどれる。
- 閾値に、測定対象・単位・母数または比較対象がある。
- 未確定の値が _UNDECIDED_: にそろい、上位成果物の _TODO_: を写したままにしていない。
- AI Agent を承認者にしていない。
