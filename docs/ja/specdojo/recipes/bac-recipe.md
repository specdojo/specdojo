# 業務受入条件 作成レシピ

Business Acceptance Criteria Writing Recipe

業務仕様から利用者が受け入れられる状態を取り出し、前提・行為・結果・証跡へ具体化する作り方を示す。

## 1. このレシピの使い方

- 業務受入条件は、上位の目的から誰の困りごとを解くか（Why）を引き継ぎ、業務が成立した状態（What）を決め、そこへ至る前提と業務行為（How）を逆算する。期待結果は根拠・シナリオ ID・証跡でたどれるようにする（Trace）。
- 「作成前に集める情報」をメモでそろえてから、「全体の作成手順」の順に書く。

## 2. 作成前に集める情報

| 項目           | 集める情報                                         | 取り出し元                   |
| -------------- | -------------------------------------------------- | ---------------------------- |
| 利用者と価値   | 誰のどの負担・誤判断・引き継ぎ漏れを減らすか       | プロジェクトの受入条件       |
| 業務の境界     | 何が起点で、どの記録や引き継ぎまでで終わるか       | 業務プロセス仕様             |
| 確定済みの判断 | 不足・拒否・途中変更をどう扱うと決まっているか     | 業務プロセス仕様、業務ルール |
| 前提           | 必要な状態・入力・権限と、不足すると止まること     | 業務プロセス仕様             |
| 確認者と証跡   | 誰がいつ何を照合して合否を決め、誰が合意するか     | 業務担当者の代表への確認     |
| 未決の論点     | 期待値を決める材料がない場面と、受入を止めるか否か | 確認の過程のメモ             |

## 3. 全体の作成手順

1. 概要の受入対象と価値を最初に書く。業務の終わりが決まらないと、シナリオの範囲が決まらない。
2. 正常完了のシナリオを一つ書く。終了状態を先に決め、開始状態と業務行為を逆算する。
3. 期待結果ごとに、誰がいつどの記録で確かめるかを書く。
4. 不足・拒否・途中変更・再開で結果が変わる場面を足す。
5. 根拠で期待値を決められない場面をメモ / 将来課題へ移す。
6. 最後に価値とシナリオ ID の対応を見直す。書いた後のほうが、確認漏れの価値に気づきやすい。

## 4. 各章の書き方

### 4.1. 概要

問い:

- この受入に合格すると、誰が次にどの業務を進められるか。
- 隣の業務の判断まで引き受けていないか。

コツ:

- 画面名から書くと、手段が受入対象になりやすい。困りごとを一つ選び、開始点と終了点を先に決める。
- 上位の目的や受入条件の本文は、写さず参照に置き換える。

### 4.2. 受入条件

問い:

- その前提でその行為を行うと、何が変わり、何が変わらないか。
- 別の人も同じ証跡から合否を判断できるか。

コツ:

- 業務担当者に「確定したと誰がどの記録で分かるか」を聞くと、操作の列挙から観測できる結果へ移れる。
- 数値には単位と確認時点を付ける。

### 4.3. メモ / 将来課題

問い:

- どのシナリオの期待値が未確定で、誰の判断があれば再開できるか。
- その論点は現行の受入を止めるか、将来の拡張か。

コツ:

- 既定値で期待結果を埋めたくなったら、論点として残す。
- 受入を止める論点は、当面どの経路を保留するかを聞いて書く。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 概要の価値からシナリオをたどり、確認されない価値と、根拠に結び付かないシナリオを探す。
2. 正常シナリオの前提を一つずつ外し、業務を進めてよいか、結果を確定してよいかを問う。
3. 途中で入力や対象が変わる場面を置き、前の記録を使えるかを確かめる。
4. 停止後に次の担当が受け取る情報をたどり、再開に要る状態と証跡を特定する。

## 6. 良い例 / 悪い例

| 観点     | 良い例                                               | 悪い例                         |
| -------- | ---------------------------------------------------- | ------------------------------ |
| 受入対象 | 家族が店番しても販売と在庫を記録して引き継げる       | 販売画面を作る                 |
| 根拠     | 業務仕様で決まった入力不足の扱いをシナリオで確かめる | 書き手が不足時の既定値を決める |
| 操作     | 家族利用者代表が販売を確定する                       | ボタンと画面遷移を列挙する     |
| 停止     | 販売を確定せず、不足情報を担当者へ渡す               | エラーを表示する               |
| 判定     | 数量 2 の販売の確定後、在庫が 5 から 3 へ減ると照合  | 在庫が正しい                   |
| 未決     | 記録不能時の販売継続は未決とし、その経路の受入を保留 | 例外は後で追加                 |

## 7. レビュー観点

| 観点       | 確認内容                                               |
| ---------- | ------------------------------------------------------ |
| 業務価値   | 各シナリオの必要性を利用者の困りごとから説明できるか   |
| 例外と継承 | 止める判断と、次の担当の行為を区別できるか             |
| 責務境界   | 新しい判断規則や実装方式を受入条件の中で決めていないか |

## 8. 仕上げチェック

- 概要の各価値がシナリオ ID で確認され、各シナリオが根拠へたどれる。
- 未決の値を確定済みの期待結果へ混ぜていない。
- 条件を合意できる状態と、受入を試行して合格した実績を区別している。
