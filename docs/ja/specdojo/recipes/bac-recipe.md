# 業務受入条件 作成レシピ

Business Acceptance Criteria Writing Recipe

業務仕様から利用者が受け入れられる状態を取り出し、前提・行為・結果・証跡へ具体化する作成手順です。正常完了だけでなく、判断を止める場面と次の担当へ渡す情報を掘り下げます。

## 1. このレシピの使い方

- 上位の業務目的から、誰が何をできずに困っているかを引き継ぎ、受入で守る価値を絞る。
- 業務が成立したと言える状態を先に書き、その状態へ至る前提と行為を逆算する。実装方式と詳細なテスト操作は後続の担当へ渡す。
- 業務仕様の判断とシナリオ ID、確認する証跡を結ぶ。根拠がない期待値は新たに決めず、判断依頼として残す。

## 2. 作成前に集める情報

| 項目           | 集める情報・問い                                            |
| -------------- | ----------------------------------------------------------- |
| 利用者と価値   | 誰のどの負担・誤判断・引き継ぎ漏れを減らすか                |
| 業務の境界     | 何が起点で、どの記録や引き継ぎまでできれば終わるか          |
| 確定済みの根拠 | BPS・業務ルール・プロジェクト受入条件のどの判断を確認するか |
| 前提           | 必要な状態、入力、判断権限は何か。不足すると何が止まるか    |
| 証跡と関係者   | 誰がいつ何を照合し、誰が業務的妥当性を承認するか            |
| 未決事項       | 期待値を決める材料はそろっているか。誰の判断を待つか        |

## 3. 全体の作成手順

1. 概要に受入対象、価値、利用場面、範囲と対象外を書く。確認者と承認者が合意する内容をそろえる。
2. 受入条件に、代表的な正常完了を一つ書く。開始状態を前提、担当者の業務行為を操作、終了状態を期待結果へ分け、根拠と ID を添える。
3. 期待結果の各項目に、確認時点・確認者・証跡を対応させて判定方法を書く。確認できない結果は観測可能な記録か状態へ具体化する。
4. 不足・拒否・途中変更などで結果が変わる場面を加える。同じ行為と観測点で入力だけが違う場合はケース表で差分を示す。
5. メモ / 将来課題へ未確定の期待値とその影響を移し、現行の受入範囲を確定できる条件を明らかにする。

## 4. 各章の書き方

### 4.1. 概要

- 問い: この受入に合格すると、誰が次にどの業務を進められるか。隣の業務の判断まで引き受けていないか。
- 具体化: 利用者の困りごとを一つ選び、開始点と終了点を先に決める。
- 良い例: 「家族が店番しても販売・在庫を記録して引き継げる」。悪い例: 「販売画面を作る」。手段だけで受入の価値を表していない。

### 4.2. 受入条件

- 問い: その前提でその行為を行ったとき、何が変わり、何が変わらないか。別の人も同じ証跡から合否を判断できるか。
- 具体化: 一つの記録を照合する場面から始め、正常、入力不足、停止後の再開で異なる結果を探す。必要な数値には単位と確認時点を添える。
- 良い例: 「数量 2 の販売後に在庫が 5 から 3 へ減ることを確定後の記録で照合する」。悪い例: 「在庫が正しい」。確認する差分を特定できない。

### 4.3. メモ / 将来課題

- 問い: どの期待値が未確定で、誰の判断があれば何を再開できるか。現行範囲の受入を止めるか。
- 具体化: 確認作業の不足、意思決定待ち、将来拡張を分け、判断を依頼する時点を添える。
- 良い例: 「返品時の在庫戻しは店主代表が返品シナリオ作成前に判断する」。悪い例: 「例外は後で追加」。影響を見積もれない。

## 5. 深掘り手順

1. 正常シナリオの前提を一つずつ外し、業務を進めてよいか、結果を確定してよいかを問う。
2. 行為の途中で入力や対象が変わる場面を置き、以前の記録をそのまま利用できるかを確認する。
3. 停止後に次の担当が受け取る情報をたどり、再開に必要な状態と証跡を特定する。根拠で判断できないものは未決事項へ戻す。

## 6. 良い例 / 悪い例

| 観点 | 良い例                                       | 悪い例                         | 良し悪しを分ける点                   |
| ---- | -------------------------------------------- | ------------------------------ | ------------------------------------ |
| 根拠 | 業務仕様の入力不足の扱いをシナリオで確認する | 書き手が不足時の既定値を決める | 決定済みの判断を受入へ変換しているか |
| 操作 | 家族利用者代表が販売を確定する               | ボタンと画面遷移を列挙する     | 業務行為として読めるか               |
| 停止 | 販売を確定せず、不足情報を担当者へ渡す       | エラーを表示する               | 未確定の範囲と次の手が分かるか       |
| 判定 | 確定後の販売記録と在庫差分を照合する         | 動けば合格とする               | 証跡から再現可能か                   |

## 7. レビュー観点

| 観点       | 確認する問い                                                     |
| ---------- | ---------------------------------------------------------------- |
| 業務価値   | 各シナリオの必要性を利用者の課題または根拠の判断から説明できるか |
| 観測可能性 | 前提・操作と期待結果がつながり、確認時点と証跡を特定できるか     |
| 例外と継承 | 止める判断・記録と、次の担当の行為を区別できるか                 |
| 責務境界   | 新しい承認規則や実装方式を受入条件の中で決めていないか           |

## 8. 仕上げチェック

- シナリオ ID と根拠をたどれ、同じ意味のケースを重ねていない。
- 共有前提と例外の前提が両立し、未決の値を確定済みの期待結果へ混ぜていない。
- 構文・保存構造・詳細テスト操作を整理し、必要な観測点、確認者、承認待ちの影響を残している。
