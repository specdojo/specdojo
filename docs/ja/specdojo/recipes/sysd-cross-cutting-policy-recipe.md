# システム設計 / 横断ルール 作成レシピ

System Design Cross-cutting Policy Writing Recipe

複数領域にまたがる失敗と回復を起点に、一般的な規約の列挙を、対象システムで判断に使える制約へ変えるための作り方を示す。

## 1. このレシピの使い方

- 横断ルールは、設計索引と上位の価値から利用者・保守担当の困り事（Why）を引き継ぎ、それを防ぐ不変条件と適用境界（What）を定め、検証の入口と例外の復帰条件（How）を決める。各制約は Rule ID で検証結果と正本へたどれるようにする（Trace）。
- 「作成前に集める情報」をメモでそろえてから、「全体の作成手順」の順に書く。

## 2. 作成前に集める情報

| 項目     | 集める情報                                                                   | 取り出し元                       |
| -------- | ---------------------------------------------------------------------------- | -------------------------------- |
| 困り事   | 誰が何を引き継げず、どの失敗で費用・作業負荷が増えるか                       | 上位の価値・課題、障害の記録     |
| 実行経路 | CLI、API、ジョブ、生成、外部プロセス、保存先のどこが共通制約を持つか         | システム設計索引                 |
| 正本     | 値と構造を決める設定・schema・リファレンス、実在する検証コマンドと対象ケース | 実装担当への確認、リポジトリ     |
| 途中状態 | 時間切れ・応答欠落・統合失敗の時点で、外部状態・ファイル・利用枠に何が残るか | 実装担当への確認、失敗注入の結果 |
| 観測     | 誰がどの証跡から対象の実行を特定し、停止と回復を判断するか                   | 運用担当への確認、ログの実例     |
| 不足     | 正本に値がない上限・優先順・通知先                                           | 確認の過程のメモ                 |

## 3. 全体の作成手順

1. 概要を最初に書き、対象の実行経路と対象外を決める。境界が決まらないと、ルールの抜けを判定できない。
2. 代表的な途中失敗を 1 つずつ追い、各ルール詳細を書く。一覧から書くと、実装の説明を規則に見せかけやすい。
3. 詳細がそろってから、同じ失敗を防ぐ制約をまとめてルール一覧を作る。
4. 承認済みの逸脱だけを例外に分け、未承認の不適合と混ぜない。
5. 一つの規則変更から実装・schema・生成物・回帰対象をたどり、関連導線を書く。
6. 最後に、確認できない値や判断待ちを未決事項に分け、どの Rule の受入を止めるかを書く。

## 4. 各章の書き方

### 4.1. 概要

問い:

- 共通規則がないと、誰が同じ調査や回復を繰り返すか。
- 安全な保存と速度などが競合したとき、何を先に守るか。

コツ:

- HTTP API や DB がなくても、CLI のエラーやファイル保存の途中状態で同じ責務が残る。技術の不在を対象外の理由にしない。
- 上位の価値や背景を写したくなったら、上位成果物への参照に置き換える。

### 4.2. ルール一覧

問い:

- 先に設定や契約を決めなければ確認できない規則はどれか。
- 要約と必須度を組み合わせて読んでも、意図が逆にならないか。

コツ:

- 構成上の実行経路を横に並べ、どの経路にも効く規則がない領域を探す。
- 規則を書いたことと実装済みの証拠を分けて聞く。照合していなければ未照合と書く。

### 4.3. 各ルール詳細

問い:

- 同じ入力と前提なら、次の動作と合否は一つに決まるか。
- 検証コマンドはそのリポジトリで実行でき、対象ケースへ到達するか。

コツ:

- 一つの途中失敗を、再試行・時間切れ・設定の競合・ログの欠落の順に追い、答えを適用境界と検証の説明に入れる。
- 上限値・設定キー・構文は写さず、正本への参照に置き換える。分からない値は推測で埋めず、実装担当に聞く。

### 4.4. 例外

問い:

- 一時的に許した逸脱か、既に起きた問題か、将来の懸念か。
- 期限が来たとき、どの検証で通常規則へ戻ったと判断するか。

コツ:

- 「緊急なら」など条件の広い許可を求められたら、対象の Rule と期限を具体的に聞き直す。

### 4.5. 関連導線

問い:

- 読む人はその参照で何を判断するか。
- schema を変えたとき、古い記録・生成物・CLI の利用者に何が起きるか。

コツ:

- 見出し・表・本文で同じ文書を同じ名称で呼ぶ。略号だけでは参照先を特定できない。
- 参照先が未作成なら未作成と書き、作成済みのように扱わない。

### 4.6. 未決事項と公開条件

問い:

- 不明な事実か、意思決定待ちか、仮定か。
- 解消しない間、どの Rule の受入を止めるか。

コツ:

- 不明は _TODO_、判断待ちは _UNDECIDED_、仮定は _ASSUMPTION_ で書き分ける。
- 未発行の作業 ID を、発行済みの証拠として数えない。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 各 Rule が、概要のどの困り事を防ぐかを確かめ、対応のない実装解説を外す。
2. 同じ失敗の再実行と並列の別実行を追い、識別・重複防止・時間上限・停止・観測が途切れる箇所を探す。
3. 手段だけがあり、支える制約や防ぐ失敗を説明できない Enforcement を探す。
4. 途切れた箇所の正本を確かめ、根拠がなければ固定値で穴を隠さず未決事項へ移す。

## 6. 良い例 / 悪い例

| 観点     | 良い例                                                        | 悪い例                                 |
| -------- | ------------------------------------------------------------- | -------------------------------------- |
| 対象範囲 | 「API はないが CLI の失敗記録を共通化し、再開対象を選べる」   | 「API がないのでエラー・監視は対象外」 |
| 冪等     | 同じ論理処理と attempt を区別し、保存・受付を照合して再開する | 同じファイル名へ書くので安全とする     |
| 時間制御 | 上限到達では部分出力を保持して停止し、受付結果を照合して再開  | 「タイムアウトしたら再実行する」       |
| 設定     | 同じ項目の競合指定を与え、正本の優先順と反映時点を確かめる    | 全項目で CLI が優先すると推測する      |
| 実装状況 | 「未照合、設定確定後に失敗注入で確かめる」                    | 規則を書いたので実装済みとする         |

## 7. レビュー観点

| 観点         | 確認内容                                                         |
| ------------ | ---------------------------------------------------------------- |
| 目的との対応 | 各 Rule が概要の困り事につながり、個別機能の手順を抱えていないか |
| 合否の再現   | 正本・入力・期待結果がつながり、第三者が同じ判定を出せるか       |
| 回復         | 途中状態から安全に再開でき、判断できなければ人へ情報を渡せるか   |
| 変更の追従   | Rule の変更から、実装・schema・生成物・回帰対象をたどれるか      |

## 8. 仕上げチェック

- 各 Rule が概要の困り事に対応し、検証の入口と正本までたどれる。
- 同じ状態に異なる動作を求める Rule がない。
- 確認していない値や実装状況を、確認済みのように書いていない。
