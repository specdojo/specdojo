# システム設計 / 横断ルール 作成レシピ

System Design Cross-cutting Policy Writing Recipe

複数領域にまたがる失敗と回復を起点に、実装上の不変条件と検証可能な境界を抽出する。一般的な規約の列挙を、対象システムで判断に使える制約へ変えるための作成手順である。

## 1. このレシピの使い方

- 利用者と保守担当が困る失敗を上位の価値・制約へ結び付ける。背景を繰り返さず、重複処理、無期限待機、判断の属人化など、横断ルールで減らす負担を選ぶ。
- 概要から対象範囲を決め、ルール一覧、詳細、例外、関連導線、未決事項と公開条件の順に具体化する。実装の説明から始めた場合も、何を防ぐ制約なのかに戻る。
- 値・構文・データ構造は正本へ、担当・期限・進捗は計画や登録簿へ委ねる。制約と検証結果を Rule ID で結び、判断できない境界は公開責任者へ渡す。

## 2. 作成前に集める情報

| 入力     | 集める情報・問い                                                                                           |
| -------- | ---------------------------------------------------------------------------------------------------------- |
| 目的     | 誰が何を引き継げず、どの失敗で費用・作業負荷・価値が損なわれるか                                           |
| 適用境界 | CLI、API、ジョブ、生成、外部プロセス、保存先のどこが共通制約を持つか                                       |
| 正本     | 設定、schema、リファレンス、設計索引のどれが値と構造を決めるか。実在する検証コマンドと対象ケースへ進めるか |
| 途中状態 | 時間切れ・応答欠落・統合失敗の時点で、外部状態・ファイル・利用枠に何が残るか                               |
| 観測     | 誰がどの証跡から対象実行を特定し、停止と回復を判断するか。保持・閲覧・検知・通知の方針はどこにあるか       |
| 責任     | 実装者、検証者、運用確認者、計画追跡者、人間の最終承認者は誰か                                             |
| 不足     | 未定義の上限・優先順・通知先は何か。いつまでに誰が決めるか                                                 |

## 3. 全体の作成手順

1. **概要**: 上位価値に関係する対象者の困り事を選び、適用する実行と対象外・代替を定める。安全な保存と速度などが競合するとき、何を先に守るかを説明する。
2. **ルール一覧**: 同じ失敗を防ぐ制約をまとめ、ID と更新責務を付す。構成上の実行経路を横に並べ、エラー、冪等、時間・再試行、ログ・監査・追跡、秘密・権限、設定、モジュール境界の抜けを探す。確認待ちを先行する設定・契約の判断へ結び付ける。
3. **各ルール詳細**: 代表的な入力と途中失敗を追い、守る条件、防ぐ事故、適用境界、合否の観測、例外、正本を一組にする。検証する場所・コマンド・対象ケースを確かめ、実行結果と区別して記す。
4. **例外**: 過渡期の逸脱と未承認の不適合を区別する。期限・判断・復帰条件を決定記録へ接続し、不適合・リスク・変更を報告する人と追跡者を決める。
5. **関連導線**: 一つの規則変更から、実装・schema・生成物・互換性・移行・回帰対象までたどる。低レベル手順を本文に増やさず、担当と正本を接続する。
6. **未決事項と公開条件**: 確認できない事項を分離し、対象 ID・影響・判断者・期限・次アクションを揃える。実装適合の確認と人間による公開可否を分けて提示する。

## 4. 各章の書き方

### 4.1. 概要

- 共通規則がないと誰が同じ調査や回復を繰り返すか。
- HTTP API がないときの CLI エラー、DB がないときのファイル保存など、技術が非該当でも代わりの責務は残っていないか。代替も不要なら構成から説明できるか。
- 誰が実装と運用を確認し、誰が公開の説明責任を持つか。

良い例は「CLI と日次処理の失敗記録を共通化し、交代担当が再開対象を選べるようにする」。避けたい例は「API がないのでエラー・監視は対象外」で、代替の CLI の責務を消してしまう。

### 4.2. ルール一覧

- 禁止・必須と要約を組み合わせても意図は変わらないか。
- 一覧から詳細へ、詳細から確認担当・実装状況へたどれるか。
- 先に設定や契約を決めなければ確認できない規則はどれか。確認群を使うなら全 ID が対応し、変更着手前・起動前・公開前のどこで確認するか分かるか。

良い例は「未照合、設定確定後に失敗注入で確認」と記し、実作業へ接続すること。避けたい例は「規則を書いたので実装済み」で、進捗を誤認させる。

### 4.3. 各ルール詳細

- 同じ入力と前提なら次の動作は一つに決まるか。
- どの正本のキーと単位を使い、何を入力し、どの観測なら合格か。検証コマンドはその repository で実行でき、対象ケースへ到達するか。
- 条件を判定できない場合、どの受入を保留し、誰へ照合を依頼するか。

一つの途中失敗を次の問いで追う。答えは適用境界や検証の説明へ反映し、値・構文・構造の転記で埋めない。

| 観点       | 具体化する問い                                                                                                                                                                            |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| エラー     | 入力不正、実行失敗、利用制限、競合、保護違反を何から識別するか。利用者は保持記録から訂正・回復・人間判断のどれを選べるか                                                                  |
| 冪等       | 同じ論理処理と別 attempt をどう識別するか。応答欠落時に外部受付・保存・統合のどこを照合し、二重処理を見分けるか                                                                           |
| 再試行     | 冪等性の前提、signal の分類、criticality を使う場合の区分はどこで確認するか。初回を含むかという回数の数え方、attempt・backoff 上限、fallback の候補条件、上限到達時の処置を一意に選べるか |
| 時間制御   | 経路別の設定キー・単位は何か。上限直前・到達時にどの子プロセスを終了し、部分出力・保存状態をどう確認して再開を判断するか                                                                  |
| ログ・追跡 | 診断と監査で何を追うか。親子実行と attempt を結び、秘密を除去した後も失敗を特定できるか。保持・閲覧・検知・通知・一次対応の正本と担当へ進めるか                                           |
| 設定       | 項目ごとにどの上書き階層が存在し、競合時の優先順・反映時点を何で確かめるか。不正値と指定なしで結果はどう変わるか                                                                          |
| 境界・権限 | 各モジュールが変更できる状態と呼出し先は何か。権限を越える経路や、生成物から正本へ状態変更が逆流する経路をどう検出するか                                                                  |

良い例は「上限到達では部分出力を保持して停止し、受付結果を照合してから再開する」。避けたい例は「criticality に従い再試行する」で、区分・signal・上限が不明のままになる。Rule は不変条件へ絞り、確認手段は Enforcement にまとめる。

### 4.4. 例外

- 一時許可なのか、既に発生した問題なのか、将来の懸念なのか。
- 例外の対象・期限が尽きたら誰が通常規則へ戻すか。
- 決定記録と課題・リスク・変更の追跡先を区別できるか。

良い例は「移行期間の対象 adapter のみ許可し、決定記録に期限と復帰の検証を付ける」。避けたい例は「緊急なら何でも許可」で、復帰できない。

### 4.5. 関連導線

- 読む人はその参照で何を判断するか。
- 参照先は現行・廃止・未作成のどれか。後継を一意に示せるか。
- 見出し・表・参照ラベルで同じ文書を同じ名称で呼び、略号から正式名へ戻れるか。
- schema 変更で古い記録・生成物・CLI 利用者に何が起きるか。

良い例は「DEV が schema と移行を更新し、旧形式の読込と再実行を検証する」。避けたい例は「関連文書一式を確認」で、更新と回帰の範囲が分からない。

### 4.6. 未決事項と公開条件

- 不明な事実、意思決定待ち、仮定のどれか。
- 誰がいつ判断し、解消しない間の受入・公開に何が制限されるか。
- 計画・登録簿の実 ID がない場合、誰が次の計画更新で接続するか。

良い例は「通知先は OPS が公開前に案を出し、PO が留保可否を判断。PM が未起票を接続する」。避けたい例は「OPD は後続で整備」で、判断と着手が浮いたままになる。

情報の照合待ちは `_TODO_:`、意思決定待ちは `_UNDECIDED_:`、仮説は `_ASSUMPTION_:` を使って書き分ける。各論点を対象 Rule ID と結び、未発行の作業 ID は発行済みの証拠に数えない。

## 5. 深掘り手順

1. 一つの途中失敗を選び、残る変更・外部受付・利用枠から目的への影響を追う。無関係な実装解説を削る。
2. 同じ失敗の再実行と並列の別実行を追い、識別、重複防止、時間上限、停止、観測の途切れを見つける。実装された手段だけがあり、支える制約や防ぐ失敗を説明できない箇所も拾う。
3. 途切れた箇所の正本を確認し、根拠不足なら確認者と判断期限を付ける。便宜的な固定値で穴を隠さず、影響を受ける検証と受入判断へつなぐ。

## 6. 良い例 / 悪い例

| 観点   | 良い例                                                     | 悪い例                                  |
| ------ | ---------------------------------------------------------- | --------------------------------------- |
| 冪等   | 同じ論理処理と attempt を区別し、保存・受付を照合して再開  | 同じファイル名へ書くので安全とする      |
| 検証   | 設定正本の上限直前・到達時を注入し、停止と保持状態で判定   | テスト名を列挙するだけ                  |
| 設定   | 同じ項目の競合指定を与え、正本の優先順と反映時点を確認する | 全項目で CLI が優先すると推測する       |
| 観測   | 親子の識別子、保存先、秘匿化、確認者を結ぶ                 | ログがあるので運用可能とする            |
| 未整備 | 対象 ID と影響・判断者・期限・計画接続を示す               | 存在しない OPD やタスクを発行済みと書く |

## 7. レビュー観点

| 観点       | 確認する問い                                                                   |
| ---------- | ------------------------------------------------------------------------------ |
| 目的と責務 | 各制約は対象者の負担・価値へつながり、個別実装や運用手順の詳細を抱えていないか |
| 実装と合否 | 正本・設定・入力・期待結果がつながり、未確認を実装済みとみなしていないか       |
| 回復と判断 | 途中状態から安全に再開でき、判断不能なら人間へ情報を引き渡せるか               |
| 変更       | 改訂・廃止時の参照元、生成、互換性、移行、回帰の担当が分かるか                 |

## 8. 仕上げチェック

- 本文の規定と実装確認の証拠を区別し、同じ状態に異なる動作を要求していない。
- 値・構文・構造の再掲を正本参照へ置き換え、Rule と検証説明の反復を整理している。
- 未決事項は判断者・期限・影響・次アクションを持ち、人間の承認・留保・差し戻しに必要な情報が残る。
