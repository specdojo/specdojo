# システム設計 重要フロー 作成レシピ

System Design Critical Flows Authoring Recipe

通常処理の説明を増やす前に、取り返しのつかない境界と失敗後の次の手を見つける。利用者の損失から成功条件を選び、実装・検証・運用の担当が同じ判断へ戻れる記述を作る。

## 1. このレシピの使い方

- 業務フローとプロジェクトの価値判断から、失敗すると誰の何が損なわれるかを引き継ぐ。
- この文書で確定するのは処理の境界、成功を認める保存状態、重複・中断後に許す動作である。
- How は整合性・排他・保持・再開の方針までとし、設定値や操作の構文は正本へ委ねる。
- フロー ID、受入条件、検証 ID、未決事項 ID を対応させ、主要な判断を根拠と証跡へ結ぶ。

## 2. 作成前に集める情報

| 集める情報                 | 答えたい問い                                                         |
| -------------------------- | -------------------------------------------------------------------- |
| 対象者・業務結果           | 失敗すると誰がどの作業をやり直すか。支出・参加負荷・履歴に何が残るか |
| システム設計索引・連携契約 | 内外の境界はどこか。要求、受付、永続化、完了を何で識別するか         |
| 状態遷移・権限             | 再実行・取消・承認の意味と責任はどこで定義され、現行の定義か         |
| 実装・設定の所在           | 上限と優先順位をどの正本から一意に辿れるか。実効値の確認は誰が行うか |
| テスト・運用・判断記録     | 期待結果と実績を区別できるか。未作成の手順や未承認の条件は何か       |

## 3. 全体の作成手順

1. 概要で入口・出口・対象外を決める。公開対象に実行記録や個人情報を含むか、人間の判断者が誰かを確認する。
2. 一覧で事故候補を比較する。通常処理より優先する理由を利用者の損失から説明する。候補が5件を超えたら、同じ事故を防ぐ候補の統合、既存との置換、対象外への整理を行い、整理後の件数と選定理由を確認してから詳細へ進む。
3. 詳細をフローごとに書く。起動条件と入出力から成功の確定点を置き、そこへ至る内外の処理・保存先・識別子と非同期の戻りを図にする。
4. 各保存点の直前・直後で停止させ、重複・応答欠落・部分成功の残存状態と次の手を決める。
5. 観測性と運用連携で、機械が検出する条件と人間が対応する責任を分ける。相関情報が境界を越えて追えるか確認する。
6. 関連ドキュメント導線へ実装・設定・テスト・運用・判断と変更影響を接続する。足りない根拠を担当・依存順・完了条件・判断時期へ変換して引き渡す。

## 4. 各章の書き方

### 4.1. 概要

- 問い: どの操作からどの業務結果までを扱うか。通常処理を除いた理由は何か。人間の承認を必要とする境界はどこか。
- 具体化: 設計索引と状態用語の定義先を確かめ、公開対象と除外する情報、最終判断を担う人間の Role code を短く書く。廃止済みの根拠しかなければ、現行仕様との照合を後続作業へ渡す。
- 対比: 「販売要求から受付照合まで。購入履歴は除外し、PO が公開を判断する」なら範囲を確認できる。「全体を安全にする」では入口・出口・判断者を決められない。

### 4.2. 重要フロー一覧

- 問い: 誰の損失を防ぐか。放置すると何が壊れるか。成功すればどの負荷が減るか。
- 具体化: 対象者・事故論点・業務影響・期待効果を一行で結び、候補間で影響を比較する。単純な処理でも重複・誤承認の影響を見落とさない。
- 対比: 「応答欠落後の再送が店番の二重売上照合を増やすため、閲覧より優先する」なら選定を説明できる。「複雑なので High」では他候補と比較できない。

### 4.3. フロー詳細

- 問い: 誰の何の要求で始まり、何を受け取り何を返すか。どの記録があれば成功と言えるか。再送で二度目の副作用が起きないか。取消不能なら何を保持して誰が照合するか。
- 具体化: 処理主体と保存先を分け、境界を越える要求・応答を同じ識別子で追う。矢印の凡例で同期・非同期を、保存記録で要求受付・業務完了を読み分けられるか試す。保存前後の中断から保持・補償・再開条件を決め、利用者が確認できる受入結果へ結ぶ。
- 対比: 「受付結果不明なら同じ取引 ID と控えを保持して照合し、未受付と確認して再送する」なら次の手が決まる。「timeout なら retry」では受付済みの副作用を判断できない。

### 4.4. 観測性と運用連携

- 問い: 同じ処理を内外でどう照合するか。trace はどこまで渡せるか。採用しない場合は何を根拠に代替キーで追えるか。検知後に誰が何を止め、どこへ相談するか。
- 具体化: イベントによる停止条件と、時間・滞留数などの監視条件を分ける。数値を使う場合は測定方法と判定時点を正本へ接続する。未決の通知方式・応答期限は追跡先へ渡し、異常・リスク・設計変更・人間の判断をどの管理記録へ引き渡すか整理する。
- 対比: 「重複を検出して処理を停止し、OPS が取引 ID で外部受付と控えを照合、ARC へ照会し PM へ記録を渡す」なら動作と責任を分けられる。「runner が担当」では人間の次の手が決まらない。

### 4.5. 関連ドキュメント導線

- 問い: 設定正本のどの箇所と、どのテスト・復旧手順を読めば再現できるか。フローの統合・廃止を含む変更で、契約・schema・生成物・CLI・保存済み記録の互換性に何が波及するか。
- 具体化: 受入条件ごとに実在するテストパスまたはテスト ID、実行方法、入力条件、期待結果、失敗判定を対応させる。内部・外部の結合境界を見分け、ITC／ETC のどちらへ引き渡すか考える。所在確認・網羅性確認・実行結果を分け、不足が受入・Schedule に与える影響と、担当・依存順・完了条件・判断時期・管理記録を結ぶ。
- 対比: 「応答欠落のテストで売上一件と照合待ち表示を確認する。復旧手順の未整備は OPS が受入前に解消する追跡 ID へ渡す」なら検証と不足を分けられる。「テストファイルがあるので pass、運用は後で」では受入可否を判断できない。

## 5. 深掘り手順

1. 「失敗なら再試行」と書いた箇所を探し、受付前・受付後・保存後で結果が変わらないか分ける。
2. 図の非同期境界で応答を失った場合を追い、照合キーと保存記録が両側に残るか確認する。
3. 同じ ID を二つの実行へ与え、排他範囲や重複排除が本当に副作用を守るか問い直す。
4. 設定値を参照だけにした箇所を辿り、実効条件を一意に解決できなければ未決事項とする。閾値を使う判断では、測定元と判定時点が同じ条件を指すか確かめる。
5. 成功条件を一つずつ検証・運用の担当へ渡せる形にし、対応しない説明を削る。

## 6. 良い例 / 悪い例

| 観点 | 良い例                                                 | 悪い例・不足する判断                             |
| ---- | ------------------------------------------------------ | ------------------------------------------------ |
| 再開 | 同じ block の最新状態を排他下で確認し、保持試行へ戻る  | 時刻が来たら全件再実行。重複・所有権が不明       |
| 補償 | 受付済みの売上を保持し、返品の判断を店主へ渡す         | 失敗表示なら取引記録を削除。部分成功の扱いが不明 |
| 変更 | 受付契約の変更時に旧控えからの照合と復旧手順を確認する | 新形式で動けば完了。既存記録への影響が不明       |

## 7. レビュー観点

| 観点         | 確認する対応                                                               |
| ------------ | -------------------------------------------------------------------------- |
| 価値と範囲   | 守る利用者・損失と、選んだ処理が対応しているか                             |
| 永続化と失敗 | 図の保存点で中断しても、保持・照合・補償・再開条件が矛盾しないか           |
| 人間の責任   | 実装主体、一次対応、技術確認、最終承認が区別されているか                   |
| 正本と証跡   | 設定・テスト・運用が一意に辿れ、未確認を確認済みと扱っていないか           |
| 変更の波及   | フローの追加・統合・廃止で影響する索引・契約・既存記録と確認担当を辿れるか |

## 8. 仕上げチェック

- 一覧の選定理由が詳細の受入条件につながっているか。
- 全成功経路に確定の証拠があり、全失敗経路に保持状態と次の手があるか。
- 詳細値・構文・状態定義の二重管理と、図の言い換えだけの文を除いたか。
- 未決事項に担当、判断時期、解消条件、計画・管理記録への引渡し先があるか。
- 公開版に raw signal、実在人物の情報、秘密値が混入せず、人間が公開可否を判断できるか。
