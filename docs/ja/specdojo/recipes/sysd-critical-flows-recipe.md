# システム設計 重要フロー 作成レシピ

System Design Critical Flows Authoring Recipe

取り返しのつかない境界と失敗後の次の手を見つけ、実装・検証・運用の担当が同じ判断へ戻れる重要フローに仕上げる作り方を示す。

## 1. このレシピの使い方

- 業務フローから、失敗すると誰の何が損なわれるか（Why）を引き継ぎ、処理の境界・成功を認める保存状態・中断後に許す動作（What）を決め、整合・排他・保持・再開の方針（How）までを書く。フロー ID で受入条件・検証・未決事項を結ぶ（Trace）。

## 2. 作成前に集める情報

| 項目             | 集める情報                                   | 取り出し元                   |
| ---------------- | -------------------------------------------- | ---------------------------- |
| 対象者と損失     | 失敗で誰が何をやり直し、何が残るか           | 業務フロー、プロジェクト概要 |
| 境界と識別子     | 内外の境界と、要求・受付・完了の識別キー     | システム設計索引、連携契約   |
| 状態と権限       | 再実行・取消・承認の意味と、それを判断する人 | 状態遷移仕様、判断記録       |
| 上限と設定の所在 | 上限と優先順位の正本                         | 実装・設定の担当への確認     |
| 検証と復旧の実績 | 既存のテスト・復旧手順と未整備のもの         | テスト担当・運用担当への確認 |

## 3. 全体の作成手順

1. 概要で入口・出口・対象外を決める。これが事故候補を比べる範囲になる。
2. 一覧で事故候補を利用者の損失で比べる。候補が多ければ、同じ事故を防ぐ候補をまとめる。
3. フロー詳細で、成功の確定点を先に置き、そこへ至る処理・保存先・識別子を図にする。確定点が先にないと、図が通常処理の説明になる。
4. 各保存点の直前・直後で止めた場合の残存状態と次の手を決める。
5. 観測性と運用連携で、機械が検出する条件と人間が対応する責任を分ける。
6. 最後に関連ドキュメント導線で、正本への参照と変更の波及をつなぐ。足りない根拠は未決事項にする。

## 4. 各章の書き方

### 4.1. 概要

問い:

- どの操作からどの業務結果までを扱い、通常処理を外した理由は何か。
- 公開版に、実行記録や個人を識別できる情報が紛れていないか。

コツ:

- 状態用語や対象者の説明を写したくなったら、業務フロー・状態遷移仕様への参照に置き換える。
- 根拠が廃止済みの文書だけなら、現行仕様との照合を未決事項にする。

### 4.2. 重要フロー一覧

問い:

- 放置すると誰の何が壊れ、成功すればどの負荷が減るか。
- その損失は、ほかの候補より重いか。

コツ:

- 対象者・事故・影響・効果を 1 行で言えない候補は、まだ詳細へ進めない。

### 4.3. フロー詳細

問い:

- どの記録が残れば成功と言えるか。
- 応答を失った後の再送で、二度目の副作用が起きないか。取り消せないなら、何を保持して誰が照合するか。

コツ:

- 処理主体と保存先を分け、境界を越える要求と応答を同じ識別子で追うと、受付と完了の取り違えが見つかる。

### 4.4. 観測性と運用連携

問い:

- 同じ処理を内外でどのキーで照合するか。trace を渡せない境界では何で追うか。
- 検知の後、誰が何を止め、どこへ相談するか。

コツ:

- 閾値を使うなら測定元と判定時点を正本に聞く。未決なら未決事項にし、無通知でよいとは書かない。

### 4.5. 関連ドキュメント導線

問い:

- どの設定とテスト・復旧手順を読めば、成功条件を再現できるか。
- フローの変更で、契約・保存済みの記録・CLI のどれに影響が及ぶか。

コツ:

- 設定値やテストの手順は写さず、所在への参照に置き換える。

## 5. 深掘り手順

内容が浅いときは、次の順で対応のない主張を探す。

1. 「再試行」「再開」の箇所ごとに、受付前・受付後・保存後で結果が変わらないかを確かめる。
2. 図の非同期の境界で応答を失った場合を追い、照合キーと保存記録が両側に残るかを確かめる。
3. 同じ ID を二つの実行へ与え、排他や重複排除が副作用を守るかを問い直す。
4. 設定値の参照を辿り、条件を一意に解決できなければ未決事項へ移す。
5. 成功条件ごとに検証・運用の担当へ渡せるかを確かめ、対応しない説明を削る。

## 6. 良い例 / 悪い例

| 観点 | 良い例                                                                 | 悪い例                            |
| ---- | ---------------------------------------------------------------------- | --------------------------------- |
| 選定 | 「応答欠落後の再送が店番の二重売上照合を増やすため、閲覧より優先する」 | 「複雑なので High」               |
| 失敗 | 「受付結果が不明なら同じ取引 ID と控えで照合し、未受付と確かめて再送」 | 「timeout なら retry」            |
| 補償 | 受付済みの売上を保持し、返品の判断を店主へ渡す                         | 失敗表示なら取引記録を削除する    |
| 責任 | 「重複を検出して停止し、OPS が取引 ID で外部受付と控えを照合する」     | 「runner が担当」                 |
| 検証 | 「応答欠落のテストで売上一件と照合待ち表示を確かめる」                 | 「テストファイルがあるので pass」 |
| 変更 | 受付契約の変更時に、旧控えからの照合と復旧手順を確かめる               | 新形式で動けば完了とする          |

## 7. レビュー観点

| 観点       | 確認内容                                           |
| ---------- | -------------------------------------------------- |
| 価値と範囲 | 守る利用者・損失と、選んだフローが対応しているか   |
| 機械と人間 | 機械の動作、人間の一次対応、照会先が分かれているか |

## 8. 仕上げチェック

- 一覧の選定理由が、詳細の受入条件までたどれる。
- すべての成功経路に確定の記録があり、すべての失敗経路に保持状態と次の手がある。
- 未確認のテスト・復旧手順を、確認済みと書いていない。
