# 概念データフロー図（全体概要）作成ルール

Conceptual Data Flow Diagram Overview Documentation Rulebook

業務または運用の全体を、プロセスグループとデータストアの間の受け渡しの流れとして定義するためのルールです。プロセス領域の分割とデータストアの一覧を合意し、各プロセスグループをプロセスグループ別 CDFD へ、横断的な業務をユースケース別 CDFD へ引き渡せる粒度を定めます。

## 1. 全体方針

- 全体概要は、業務または運用を構成するプロセス領域、プロセスグループ、データストア、グループとデータストアの間の受け渡しを合意する概念仕様とします。
- プロセス領域は業務の性質が近いものをプロセスグループにまとめ、概念データフローではプロセスグループを一つの代表ノードで表します。領域単位の内部プロセス、状態を変える処理と起点イベント、例外経路はプロセスグループ別 CDFD へ委ね、状態の定義と遷移は STSD へ委ねます。
- データストアは論理的な正本として一覧化し、マスタ・構成データとトランザクションデータに分けて定義します。図に置くデータストアは一覧の各行と一対一に対応させます。
- プロセス領域の表を領域定義の正本、「データストア」をデータストア定義の正本、概念データフロー図（Mermaid または D2）をグループとデータストアの間の受け渡しの正本とします。プロセス領域に主要入力・主要出力の箇条書きは設けず、受け渡しは図を正本とします。
- 各プロセス領域には業務目的、主な担当、起点イベントを割り当て、表で簡潔に定義します。
- 目的は 1〜2 文、適用範囲は対象と対象外を 1 行ずつとし、人間と AI Agent の責任分担などの共通原則は 1 か所に置いて参照します。

## 2. 位置づけと用語定義

| 用語                    | 定義                                                                                                                                                                   |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 全体概要                | プロセスグループとデータストアの間の受け渡しを表す最上位の CDFD                                                                                                        |
| プロセス領域            | 固有の業務目的、主な担当、起点イベントを持つ責務のまとまり。`P-01` 形式の領域 ID を持つ                                                                                |
| プロセスグループ        | 業務の性質が近いプロセス領域をまとめた集合。概念データフローの代表ノードであり、プロセスグループ別 CDFD の単位                                                         |
| 代表ノード              | 全体概要で一つのプロセスグループを表す角丸長方形のノード（Mermaid または D2）。`subgraph` やコンテナではなくノードとして描く                                           |
| 起点イベント            | プロセス領域を開始させる、発生した時点を判定できる出来事。プロセス領域の表に記載し、全体概要の図には描かない                                                           |
| データストア            | プロセスグループが参照または更新する、台帳、文書、ファイル、設定などの論理的な正本。マスタ・構成データとトランザクションデータに区分する                               |
| マスタ・構成データ      | 他のプロセスから参照される比較的安定した基準情報。更新契機は承認された変更である                                                                                       |
| トランザクションデータ  | 業務活動に伴い都度更新される記録。生成物や退避先を含む                                                                                                                 |
| 保管先                  | データストアの物理的な所在（ファイルパス、帳簿、システムなど）。概念段階では未確定でよい                                                                               |
| STSD                    | ステータス定義（Status Definition）。状態名、意味、成立条件、遷移元、遷移先、イベント、遷移条件の単一正本。作成規範は `specdojo:stsd-rulebook`                         |
| Role code               | 責務・判断権限・専門性を表す識別子。共通定義は `specdojo:people-and-organization-definition-standard`、プロジェクトで採用する値は `<project-id>:pm-roles` を正本とする |
| PO                      | Project Owner を表す標準 Role code。目的、スコープ、優先順位、公開方針、最終判断を担う                                                                                 |
| retrofit                | 既存実装をエビデンスとして現状の成果物へ反映する作成アプローチ。保管先など実装から確定できる事実を推測せず記録する                                                     |
| Orchestrator            | 利用者または自動実行の意図を受け、計画・実行・評価・改善の各プロセスグループへ要求を振り分ける調整役。採用する場合は、対象業務での責務と入力元を本文で定義する         |
| 補助操作                | 一覧、検索、状態参照、検証、dry-run など、独立した業務成果を作らず他の領域を支援する操作                                                                               |
| プロセスグループ別 CDFD | 一つのプロセスグループを引き継ぎ、領域の内部プロセス、起点イベント、例外・復旧、データストアの読み書きを定め、状態定義・遷移は STSD を参照する詳細 CDFD                |
| ユースケース別 CDFD     | 複数のプロセスグループをまたぐ業務について、グループ間の順序と引き渡し条件だけを定める詳細 CDFD。構造規範は `specdojo:cdfd-uc-rulebook`                                |

全体概要はプロセスグループとデータストアの分割、およびグループとデータストアの間の受け渡しを定義します。プロセスグループ別 CDFD は一グループの内部を、ユースケース別 CDFD はグループ間の順序を詳細化し、いずれも全体概要と同じ領域 ID、プロセスグループ名、データストア名を引き継ぎます。

## 3. ファイル命名・ID規則

- ファイル名は `cdfd-overview.md`、ドキュメント ID は `cdfd-overview` を基本とします。product 文書ではプロジェクト修飾（`<project-id>:`）を付けず、プロジェクト固有の現状分析をプロジェクト文書配下へ置く場合だけ `<project-id>:cdfd-overview` とします。
- 配置は対象プロダクトの業務仕様配下にあるデータフローディレクトリを基本とします。
- 領域 ID は文書内で一意な `P-01` 形式とし、プロセス領域の表、代表ノードのラベル、詳細 CDFD 一覧で同じ値を使います。採番順に業務上の意味を持たせず、名称変更後も同じ責務を表す限り維持します。
- プロセスグループ名は英語の短い名詞（例: Plan、Do、Check、Action）または日本語の短い名詞句とし、代表ノードのラベルには `P-02〜P-06` のように含む領域 ID の範囲を併記します。
- プロセスグループ別 CDFD の ID は `cdfd-<group>`、ユースケース別 CDFD の ID は `cdfd-uc-<topic>` とします。`<group>` はプロセスグループ名の英小文字、`<topic>` はユースケースを表す英小文字のスラッグです。
- ユースケース ID は文書内で一意な `C-01` 形式とします。

## 6. 記述ガイド

本章は作成方法と各規則の理由を説明します。`ready` 昇格の pass / fail は「完成判定」だけをチェックリストの正本として判定します。

### 6.1. 導入文

- 対象業務または運用が何を扱うかを一文で定義します。
- 詳細な効果、指標、実装方式は列挙しません。

### 6.2. 目的

- 全体概要を使用する対象者と利用場面を結び付け、1〜2 文で簡潔に記述します。
- 「PO が対象範囲と領域分割を承認し、後続の詳細 CDFD 作成の設計入力とする」のように、利用結果を判定できる表現にします。

### 6.3. 適用範囲

- 対象と対象外をそれぞれ 1 行（1 文）で明示します。
- 領域内部（個別コマンドの操作手順、ファイル単位の更新内容、処理の分岐、状態を変える処理と起点イベント、例外時の復旧手順）は対象外とし、プロセスグループ別 CDFD へ委ねることを明記します。状態の定義と遷移は STSD が正本であることも示します。
- 補助操作の扱い、人間と AI Agent の責任分担などの共通原則は本文で冗長に再定義せず、プロジェクト共通方針文書（または全体概要の適用範囲内の 1 文）に置いて参照します。

### 6.4. プロセス領域

- 章の冒頭で、領域数、プロセスグループ数、正本の所在（領域の分割は本書の表、受け渡しは本書の図、領域内部はプロセスグループ別 CDFD）を簡潔に示します。
- プロセスグループごとに節（`3.1.`、`3.2.`、…）を設け、見出しは「グループ名（含む領域 ID の範囲）」とします。
- 各節は領域の表のみで構成します。主要入力・主要出力・データストアの箇条書きは記載せず、受け渡しは概念データフロー図を正本とします。
- プロセスグループの数は 8 以下とします。超える場合は業務の性質が近いグループを統合します。1 領域だけのグループも認めます。

<!-- prettier-ignore -->
| 列 | 記載内容 | 判定基準 |
| --- | --- | --- |
| 領域 ID | `P-01` 形式の安定した識別子 | 表、代表ノードのラベル、詳細 CDFD 一覧で同じ ID を使う |
| プロセス領域 | 業務目的が分かる短い名称 | コマンド名や実装部品名だけにしない |
| 業務目的 | 対象者に生じる成果または維持する状態 | 手順や機能の列挙にしない |
| 主な担当 | 主担当ロール。複数ロールが担う場合は管理責任のロールを併記する | 同じ表では採用済み Role code または組織定義にある役割名のどちらかへ統一し、個人名や「全員」だけで終わらせない |
| 起点イベント | 領域の開始を判定できる出来事。定義系の領域は「要件が判明した」、実行系の領域は「指示された」「到来した」のように区別する | 「必要に応じて」で終わらせない。同じグループ内で同文にしない |

- 独立領域にするのは、固有の起点イベントと業務成果を持ち、他領域と区別できる入力、出力、またはデータストアがある場合です。補助操作は、独立した判断結果や更新成果を持たない限り領域にしません。
- プロジェクト管理を対象とする文書の「主な担当」は、`<project-id>:pm-roles` に定義された Role code を使います。

### 6.5. データストア

- 章の冒頭で、区分の意味、パスの略記（例: `<project-id>` が指す範囲）、データストアとして扱わないもの（リポジトリ基盤、開発環境の設定など）を簡潔に示します。
- マスタ・構成データとトランザクションデータの 2 表に分け、各行は次の列で構成します。

<!-- prettier-ignore -->
| 列 | 記載内容 | 判定基準 |
| --- | --- | --- |
| データストア | 論理的な正本の名称 | 図のノードラベル、詳細 CDFD と同じ名称を使う |
| 主な内容 | 保持する情報の種別。生成物なら生成元、退避先なら退避対象を書く | 「各種データ」のような抽象語だけにしない |
| 主な保管先 | 物理的な所在。複数ある場合は `、<br>` で区切る | 原則として別のデータストアと重ならない範囲に限定し、共有・包含する場合は論理境界と共有相手を注記する |

- 「主な保管先」列は条件付きです。実装が先にある場合（retrofit）は必須とし、実装エビデンスとして記載します。設計中で候補がある場合は列を置き、未確定のセルは `_UNDECIDED_` とします。保管先を扱わない概念段階では列ごと省略します。
- 一つの帳簿、ファイル、ディレクトリを複数の論理データストアが共有する場合は、境界と共有相手を注記します。
- 区分の判定基準は更新契機です。承認された変更で更新されるものはマスタ・構成データ、業務活動に伴い都度更新されるものはトランザクションデータとします。

### 6.6. 概念データフロー（概要）

- グループとデータストアの間の受け渡しの正本とします。エッジラベルには名詞形の具体的なデータ名を用います。更新エッジは更新前の参照を含みます。
- 章冒頭や各図の説明・注記は 1〜2 文で簡潔に記述します（図を文章でなぞる長文は不要）。
- 代表ノードはプロセスグループごとに一つとし、ラベルにグループ名と含む領域 ID の範囲を書きます。`subgraph` で領域や代表ノードを囲みません。
- データストアのノードは「データストア」の各行と一対一とし、同じ名称を使います。
- 対象範囲内の参加者（ロール）は各領域の担当として業務プロセスの内側にいるため、外部主体として描きません。外部主体を描くのは対象範囲外の入力元・出力先だけです。
- 起点イベントは「プロセス領域」の表に記載し、図には描きません。
- 図のノード総数は、代表ノードとデータストアの合計で数え、外部主体は含めません。合計が 16 を超える場合は、トランザクションデータに着目した図とマスタ・構成データに着目した図に分けます。分ける場合は、両図で代表ノードとデータストアの名称を統一します。
- 各図の直後に、凡例への参照、および図の趣旨や省略事項を 1〜2 文で簡潔に注記します。
- ノード形状、線種、色、絵文字の記法は、本プロダクト共通の凡例で選択した記法ルール（`specdojo:cdfd-mermaid-rulebook` または `specdojo:cdfd-d2-rulebook`）に従います。凡例で記法を宣言しない場合は Mermaid 記法に従います。

### 6.7. 詳細 CDFD 一覧

- 章の冒頭で、プロセスグループ別 CDFD とユースケース別 CDFD の役割分担を簡潔に示します。前者はグループ内部のプロセス・例外・データストア読み書きの正本、後者は `specdojo:cdfd-uc-rulebook` に従ってグループ間の順序と引き渡し条件だけを定め、内部プロセスを再掲しないことを明記します。状態の定義と遷移は STSD が正本であることも示します。
- プロセスグループ別 CDFD の表は、プロセスグループ、含む領域、CDFD の ID の 3 列とし、全プロセスグループを 1 行ずつ載せます。
- ユースケース別 CDFD の表は、ケース ID、ユースケース、業務目的、横断するプロセスグループ、CDFD の ID の 5 列とし、複数のプロセスグループを横断し順序と引き渡し条件を定める必要がある業務だけを載せます。
- 未作成の CDFD に「（未作成）」などの状態表記を付けません。作成状況は登録簿で追跡します。

### 6.8. 凡例（本プロダクト共通）

- 本プロダクトの詳細 CDFD が複数存在し、共通の記法（Mermaid または D2）、ノード形状・色・絵文字を使う場合に設けます。凡例は全体概要にだけ書きます。
- 本章で採用する記法（Mermaid または D2）を明示的に宣言します。
- 詳細 CDFD は本章を再掲せず、全体概要の凡例への参照に留めます。
- 本章を省略した場合、または記法を明示しない場合、全 CDFD は Mermaid 記法（`specdojo:cdfd-mermaid-rulebook` の既定凡例）に従います。

### 6.9. 未決事項

- 境界、名称、責務、判断者、保管先のいずれかが未確定な論点がある場合だけ設けます。ない場合は章ごと省略します。
- 表は論点、影響、決定者、決定時期、状態の 5 列とします。本文中の未確定箇所には `_UNDECIDED_` を付け、表の論点と対応させます。

### 6.10. 完成判定

本節だけを `ready` 昇格のチェックリストの正本とします。次の全項目を満たす必要があります。

- Frontmatter に `id`、`type: flow`、`status`、`rulebook: specdojo:cdfd-overview-rulebook` があり、`id` と `status` が「推奨 Frontmatter 項目」の制約を満たしています。
- H1 直下の導入文が対象業務または運用を一文で定義しています。
- 「目的」が 1〜2 文で対象者と利用場面を定義しています。
- 「適用範囲」に対象と対象外が 1 行ずつ明記され、共通の原則（人間と AI Agent の責任分担など）が 1 か所を参照しています。領域内部と状態定義・遷移の正本も特定できます。
- 「プロセス領域」は 8 以下のプロセスグループからなり、各節が領域表だけで構成されています（主要入力・主要出力・データストアの箇条書きを含まない）。領域表には「領域 ID」「プロセス領域」「業務目的」「主な担当」「起点イベント」の全列があり、各領域は一つのグループにだけ属しています。
- 「主な担当」は同じ表内で採用済み Role code または組織定義にある役割名へ統一されています。
- 「データストア」が「マスタ・構成データ」と「トランザクションデータ」に分かれ、各表に「データストア」「主な内容」と、確定度に応じた「主な保管先」があります。
- 概念データフローにはプロセスグループごとの代表ノードが一つずつあり、`subgraph` を使っていません。データストアのノードは「データストア」の各行と一対一で、表、図、詳細 CDFD 一覧の名称が一致しています。
- 概念データフロー図がグループとデータストアの間の受け渡しの正本となっており、各エッジに名詞形のデータ名があります。図の説明・注記は 1〜2 文で簡潔に記載されています。
- 「詳細 CDFD 一覧」のプロセスグループ別 CDFD 表に全グループがあり、ユースケース別 CDFD 表の各行は複数グループを横断しています。
- 「凡例（本プロダクト共通）」を設けた場合、採用する記法（Mermaid または D2）、形状・色・絵文字を示し、詳細 CDFD から参照可能になっています。
- `_TODO_` と作業メモの HTML コメントが残っていません。`_UNDECIDED_` がある場合は最終章の「未決事項」に対応しています。
- 対象範囲と領域分割を PO が承認した記録を、登録簿の決定記録またはレビュー結果から特定できます。

## 7. 禁止事項

本章は完成判定に反する代表例と、その理由を示します。

<!-- prettier-ignore -->
| 禁止事項 | 理由 |
| --- | --- |
| プロセス領域に主要入力・主要出力・データストアの箇条書きを記載する、または図の受け渡しを文章でなぞる長文の注記を書く | 受け渡しの正本である図と重複し、文書の冗長化や不整合を招くため |
| プロセスグループを `subgraph` で表す、または一つの領域を複数の代表ノードへ分割する | 代表ノードとプロセスグループ別 CDFD の対応が崩れ、表・図・詳細 CDFD の突き合わせができなくなるため |
| 業務の性質が異なる領域を、理由の説明なく一つのプロセスグループへ統合する | 詳細化先の境界が不明瞭になり、重複・欠落の確認ができなくなるため |
| 全体概要に領域内部の操作手順、状態を変える処理、例外分岐、物理テーブル・カラム、SQL、実装クラス、詳細 API、コマンドオプションを記載する | プロセスグループ別 CDFD の責務であり、二重管理と粒度超過を招くため |
| 全体概要または詳細 CDFD で状態の定義・遷移表を正本化する | 状態の定義と遷移は STSD が正本であり、CDFD との二重管理を招くため |
| 一覧、検索、状態参照、検証、dry-run などを、固有の業務成果がないまま独立領域にする | 補助操作を業務成果と誤認させるため |
| プロセス領域の表、データストア、図、詳細 CDFD 一覧で、同じ領域・グループ・データストアに異なる名称を使う | 読み手が同一対象と判断できなくなるため |
| ラベルのないエッジ、起点または到達先のないエッジ、「データストア」に行のないデータストアのノードを残す | 受け渡しの内容・方向・対応関係が読み取れなくなるため |
| 対象範囲内の参加者（ロール）を外部主体として描く | 業務プロセスの内側にいる担当を外部に置き、責任の所在を誤って示すため |
| 人間が責任を持つ主要判断、承認、公開可否を AI Agent またはシステムの自動処理として表す | 責任の所在を誤って示すため |
| 詳細 CDFD に独自の凡例を再掲・重複定義する | 全体概要の凡例を参照すべきであり、保守負荷と不整合を招くため |
| 詳細 CDFD 一覧や本文に「未作成」「TODO」などの作成状況を書く | 作成状況は登録簿で追跡するものであり、成果物本文が陳腐化するため |
| 作業メモや検討中の論点を HTML コメントで本文に残す | 読み手に見えない未決事項が生まれるため。「未決事項」章または登録簿へ移す |
