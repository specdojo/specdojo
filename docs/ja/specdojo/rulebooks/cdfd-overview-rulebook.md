# 概念データフロー図（全体概要）作成ルール

Conceptual Data Flow Diagram Overview Documentation Rulebook

業務または運用の全体像を、プロセス領域のまとまりと、それらが読み書きするデータの関係として示すためのルールです。全体概要と詳細 CDFD の粒度・責務境界を定めます。

## 1. 全体方針

- 全体概要は、プロセス領域の分割、データストアの区分と受け渡しを示す概念仕様とします。領域の定義は「プロセス領域」の表、ストアの定義は「データストア」の表、受け渡しとグループ間・区分間の要求は図を正本とします。
- 全体概要には領域表、データストア表、共通凡例を集約します。領域内部の処理・例外経路は選択した方式の詳細 CDFD へ、状態の定義と遷移は [[specdojo:stsd-rulebook|STSD 作成ルール]] に従う状態定義へ委ねます。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。文書の整形・lint はリポジトリの検証で扱い、業務の受入確認に含めません。

## 2. 位置づけと用語定義

構成方式は次のいずれかを選びます。凡例または「概念データフロー（概要）」冒頭に宣言がなければ、既定は今の方式（データストアの区分による図の分割）とします。

| 方式                 | 代表ノード                                                               | 詳細化先                                                                                       |
| -------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 今の方式             | 業務の性質が近い領域をまとめたプロセスグループ                           | グループ内部はプロセスグループ別 CDFD、複数グループ間の順序と引き渡し条件はユースケース別 CDFD |
| 系統の関係を描く方式 | 系統・実行サイクル・構成管理・調整役など、領域を業務の性質でまとめた区分 | 各系統の流れをユースケース別 CDFD でプロセス領域単位に詳細化                                   |

詳細 CDFD は全体概要の領域 ID、グループ名または区分名、データストア名を引き継ぎます。

- **プロセス領域**: 固有の業務目的、主な担当、起点イベントを持つ責務のまとまり。
- **代表ノード**: 一つのグループまたは区分を表す角丸のノード。領域を囲む `subgraph` やコンテナとは区別します。
- **Orchestrator**: 利用者または自動実行の意図を受け、各グループまたは区分へ要求を振り分ける調整役。採用する場合は対象業務での責務と入力元を定義します。
- **補助操作**: 一覧・検索・状態参照・検証・dry-run など、独立した業務成果を作らず他の領域を支援する操作。

## 3. ファイル命名・ID規則

- ファイル名と ID は `cdfd-overview.md`、`cdfd-overview` を基本とします。プロダクト文書の ID は修飾せず、プロジェクト固有の現状分析をプロジェクト文書配下へ置く場合だけ `<project-id>:cdfd-overview` とします。配置は業務仕様のデータフローディレクトリを基本とします。
- 領域 ID は文書内で一意な `P-01` 形式とし、表・代表ノード・詳細 CDFD 一覧で一致させます。採番順に業務上の意味を持たせず、名称変更後も同じ責務なら維持します。
- グループ名・区分名は短い名詞句（例: Plan、販売、register 系）とし、代表ノードには含む領域 ID の範囲（例: `P-02〜P-06`）を併記します。
- 詳細 CDFD の ID は、グループ別が `cdfd-<group>`、ユースケース別が `cdfd-uc-<topic>` とします。`<group>` はグループ名の英小文字、`<topic>` はユースケースを表す英小文字のスラッグです。
- ケース ID は文書内で一意な `C-01` 形式とします。

見出し順・表・記入欄の骨組みは template を正本とし、内容の要件は本書に従います。

| 見出し                   | 必須     | 内容・受入条件                                                                                        |
| ------------------------ | -------- | ----------------------------------------------------------------------------------------------------- |
| 導入文                   | ○        | 対象業務・運用を一文で定義                                                                            |
| 目的                     | ○        | 全体像として示す領域のまとまりとデータの関係（1〜2 文）                                               |
| 適用範囲                 | ○        | 対象と対象外を各 1 行で示し、詳細化先を特定                                                           |
| プロセス領域             | ○        | グループまたは区分ごとの節と領域表                                                                    |
| データストア             | ○        | マスタ・構成データとトランザクションデータの 2 表。物理保管の併記は「データストア」の記述ガイドに従う |
| 概念データフロー（概要） | ○        | グループまたは区分の代表ノードとストアの関係図（Mermaid または D2）。各図に業務の題と 1 文の説明      |
| 詳細 CDFD 一覧           | ○        | 選択した方式の詳細化先と領域の対応                                                                    |
| 凡例（本プロダクト共通） | 任意     | 採用記法、形状・色・絵文字のサンプル図と対応表。全体概要にのみ設置                                    |
| 未決事項                 | 条件付き | 未確定の論点と影響がある場合だけ最終章に設置                                                          |

- 凡例を省略する場合は章番号を詰めます。
- 概念データフローを複数図に分ける場合だけ `5.1.`、`5.2.`、… の節を設けます。

## 6. 記述ガイド

### 6.1. 導入文

対象業務または運用が何を扱うかを一文で定義します。詳細な効果・指標・実装方式は列挙しません。

### 6.2. 目的

全体像として示す業務・運用と、領域のまとまりとデータの関係を 1〜2 文で記述します。

例: 「店舗運営の全体像として、仕入・販売・在庫・顧客・締めの各グループと、それらが読み書きするデータの関係を示す。」

### 6.3. 適用範囲

- 対象と対象外をそれぞれ 1 行（1 文）で明示します。
- 領域内部の操作手順・ファイル単位の更新・処理分岐・状態を変える処理と起点イベント・例外復旧は、選択した方式の詳細 CDFD へ委ねることを明記します。状態の定義と遷移の正本も特定します。
- 補助操作の扱いなど、対象業務に共通する方針は一か所に置き、各領域で言い直しません。

### 6.4. プロセス領域

- 章冒頭で領域数、グループ数または区分数、正本の所在（領域は表、受け渡しは図、内部は詳細 CDFD）を示します。
- グループまたは区分ごとに節を設け、見出しは「名称（含む領域 ID の範囲）」とします。各節は領域表のみとし、主要入力・主要出力・データストアの箇条書きは置きません。
- グループ・区分は 8 以下とします。超える場合は業務の性質が近いまとまりを統合します。1 領域だけのまとまりも認めます。

<!-- prettier-ignore -->
| 列 | 記載内容・判定基準 |
| --- | --- |
| 領域 ID | `P-01` 形式の安定した識別子。表・代表ノード・詳細 CDFD 一覧で一致させる |
| プロセス領域 | 業務目的が分かる短い名称。コマンド名や実装部品名だけにしない |
| 業務目的 | 対象者に生じる成果または維持する状態。手順や機能の列挙にしない |
| 主な担当 | 主担当ロール。複数の場合は管理責任も併記。同じ表では採用済み Role code または組織定義の役割名へ統一し、個人名や「全員」だけにしない |
| PDCA（任意） | Plan、Do、Check、Action、全体など。領域の区分とは別の分類軸として必要な場合だけ追加 |
| 起点イベント | 開始を判定できる出来事。定義系は「要件が判明した」、実行系は「指示された」「到来した」など。「必要に応じて」や同じグループ内の同文にしない |

独立領域には固有の起点イベントと業務成果、および他領域と区別できる入力・出力・ストアが必要です。補助操作は独立した判断結果や更新成果がない限り領域にしません。プロジェクト管理を対象とする場合の「主な担当」は、`<project-id>:pm-roles` の Role code を使います。

### 6.5. データストア

- データストアは台帳・文書・ファイル・設定などの論理的な正本です。更新契機で、承認された変更により更新する比較的安定した基準情報の「マスタ・構成データ」と、業務活動に伴い都度更新される記録・生成物・退避先の「トランザクションデータ」に分けます。
- 章冒頭で区分の意味、パスの略記（例: `<project-id>` の範囲）、対象外（リポジトリ基盤・開発環境など）を示し、2 表に次の列を置きます。

<!-- prettier-ignore -->
| 列 | 記載内容・判定基準 |
| --- | --- |
| データストア | 論理的な正本の名称。図・詳細 CDFD と同名にする |
| 主な内容 | 保持する情報。生成物は生成元、退避先は退避対象も示し、「各種データ」だけにしない |
| 主な保管先（条件付き） | 物理的な所在。複数なら `、<br>` で区切る。共有・包含する場合は論理境界と共有相手を注記する |

- 「主な保管先」は実装が先にある場合（retrofit）は実装エビデンスとして必須です。設計中で候補がある場合は列を置き、未確定セルを `_UNDECIDED_` とします。保管先を扱わない概念段階では列ごと省略します。原則として別ストアの保管範囲と重複させません。
- **物理保管**は商品・現金など現物の保管先であり、情報の正本であるデータストアの 2 区分には属しません。図に置く場合は、例外としてトランザクションデータ表の末尾へ同じ列で併記します。template の同表に行を追加し、「データストア」列に場所名、「主な内容」に現物、「主な保管先」に所在と「物理保管」の注記を書きます。保管先列を省略する場合は「主な内容」に注記します。章冒頭または凡例で、併記と同色の使用は分類への所属を意味しないと説明します。
- 良い例: 「売場棚 ／ 店頭に陳列した商品の現物 ／ 店内の売場棚（物理保管）」。悪い例: 棚の現物を在庫記録と同一のデータストアにしたり、色が同じという理由でトランザクションデータに分類したりする。

### 6.6. 概念データフロー（概要）

- 章冒頭で採用方式と示す関係を宣言します。各図の題は「PDCA のプロセスとデータの関係」など業務の言葉とし、説明は読み取れることを 1 文で書きます。作図の約束は凡例にまとめます。
- 代表ノードはグループまたは区分ごとに一つとし、名称と領域 ID の範囲をラベルにします。一つの図で内部領域へ展開せず、`subgraph` やコンテナで囲みません。別図への同一ノードの再掲は認めます。
- データストアと物理保管のノードは「データストア」の各行と一対一に対応させ、名称を一致させます。複数図で再掲しても論理的には一つとします。
- エッジは具体的なデータ名・物の名・実行要求名（「対応要求」など）の名詞でラベルを付けます。更新の線は更新前の参照を含み、線は実行順や毎回の通過を意味しません。
- 対象範囲内の参加者は領域の担当であり、外部主体にしません。外部主体は対象範囲外の入力元・出力先に限ります。起点イベントは領域表に置きますが、系統の関係を描く方式では系統の入口を図示できます。
- 1 図の代表ノード・データストア・物理保管の合計が 16 を超えたら分割します（外部主体は数えない）。今の方式ではデータストアの区分または使い方の流れで、系統の関係を描く方式ではデータの種類で分けます。全図の名称を統一します。
- 系統の関係を描く方式では、データの図の間で区分の位置をそろえ、線のない区分はその図から省きます。各区分はいずれかの図に必ず出し、配置制御の非表示線は受け渡しに数えません。
- 同方式の Orchestrator はデータの図に置かず、指示の別図に描きます。ストアへの線は直接の読み書きだけとし、CLI 経由の読み書きはデータの図の該当区分から描きます。
- 形状・線種・色・絵文字は、凡例で選択した [[specdojo:cdfd-mermaid-rulebook|Mermaid 記法ルール]] または [[specdojo:cdfd-d2-rulebook|D2 記法ルール]] に従います。記法の宣言がなければ Mermaid を使います。

### 6.7. 詳細 CDFD 一覧

章冒頭で「位置づけと用語定義」にある詳細化の分担と、状態定義の正本を示します。内部プロセスは二重管理しません。ユースケース別の構造は [[specdojo:cdfd-uc-rulebook|ユースケース別 CDFD 作成ルール]] に従います。

| 表                      | 標準列                                                                                      | 受入条件                                                                                                                              |
| ----------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| プロセスグループ別 CDFD | プロセスグループ、含む領域、CDFD の ID                                                      | 今の方式では全グループを 1 行ずつ載せ、各領域をちょうど一つに対応させる。系統の関係を描く方式では省略するか移行期・非推奨の記録とする |
| ユースケース別 CDFD     | ケース ID、ユースケース（系統名）、業務目的、横断するグループ（対象系統・領域）、CDFD の ID | 今の方式では複数グループを横断する順序と引き渡し条件、系統の関係を描く方式では各系統の流れを定義する詳細 CDFD を載せる                |

### 6.8. 凡例（本プロダクト共通）

- 複数の詳細 CDFD が共通の記法・形状・色・絵文字を使う場合に設けます。
- 採用記法（Mermaid または D2）を宣言し、サンプル図と対応表を示します。構成方式も宣言できます。記法が未宣言なら Mermaid の既定凡例を使います。
- 詳細 CDFD は本章を参照し、凡例を再掲しません。

### 6.9. 未決事項

境界・名称・責務・判断者・保管先が未確定の場合だけ設け、表は「論点」「影響」の 2 列とします。本文中の `_UNDECIDED_` を論点に対応させ、決定によって変わる領域・ストア・図・詳細化先を影響に書きます。

### 6.10. 完成判定

次の順に業務内容を照合し、全項目が合格することを完成条件とします。

1. 導入文・目的・適用範囲を読み、対象業務、示す関係、対象外と詳細化先を「本文要件」と各記述ガイドの条件で特定できること。
2. 領域表を代表ノード・詳細 CDFD 一覧と突き合わせ、「プロセス領域」の必須列・担当表記・独立領域の条件を満たし、各領域が一つのグループまたは区分に属すること。グループ・区分は 8 以下であること。
3. ストア一覧と図を双方向に突き合わせ、「データストア」の区分・標準列・保管先条件を満たし、全行とノードが名称で一対一に対応すること。物理保管は同節の例外に従って併記され、データの 2 区分と区別できること。
4. 各図の線を始点から終点までたどり、「概念データフロー（概要）」の代表単位・ラベル・外部主体・16 ノード以内の分割条件を満たし、業務成果に必要な受け渡しに欠落がないこと。系統の関係を描く方式は区分の配置・網羅と、調整役の直接読み書きと CLI 経由の区別も確認すること。
5. 詳細化先・凡例・未決事項を読み、各記述ガイドに従う役割分担と参照先が特定でき、未確定の論点と影響が対応していること。

## 7. 禁止事項

<!-- prettier-ignore -->
| 禁止事項 | 理由 |
| --- | --- |
| 領域表に主要入力・主要出力・ストアの箇条書きを添える | 受け渡しの正本である図と二重管理になるため |
| グループ・区分を `subgraph` やコンテナで表す、または一つの図で内部領域へ展開する | 代表ノードと領域表・詳細化先の対応が崩れるため |
| 業務の性質が異なる領域を理由なく一つのグループへ統合する | 詳細化の境界と重複・欠落を確認できなくなるため |
| 全体概要に内部操作・例外分岐・物理テーブル・カラム・SQL・実装クラス・詳細 API・コマンドオプションを書く | 詳細 CDFD への委譲と概念粒度を損なうため |
| CDFD で状態定義・遷移表を正本化する | STSD と二重管理になるため |
| 業務成果のない補助操作を独立領域にする | 支援操作を業務成果と誤認させるため |
| 表・図・詳細化先で同じ対象に異なる名称を使う、ラベルや対応行のないエッジ・ノードを残す | 受け渡しと対応関係を読み取れないため |
| 対象範囲内の担当を外部主体として描く | 業務境界と責任の所在を誤って示すため |
| 物理保管を情報のデータストアと同じ概念に分類する | 現物とその記録の受け渡しを区別できなくなるため |
