# 概念データフロー図（全体概要）作成ルール

Conceptual Data Flow Diagram Overview Documentation Rulebook

業務または運用の全体を、プロセスグループとデータストアの間の情報・実行要求の流れとして定義するためのルールです。プロセス領域の分割とデータストアの一覧を合意し、各プロセスグループをプロセスグループ別 CDFD へ、横断的な業務をユースケース別 CDFD へ重複・欠落なく引き渡せる粒度を定めます。

## 1. 全体方針

- 全体概要は、業務または運用を構成するプロセス領域、プロセスグループ、データストア、グループとデータストアの間の受け渡し、人間の判断境界を合意する概念仕様とします。
- プロセス領域は業務の性質が近いものをプロセスグループにまとめ、概念データフローではプロセスグループを一つの代表ノードで表します。領域単位の内部プロセス、状態を変える処理と起点イベント、例外経路はプロセスグループ別 CDFD へ委ね、状態の定義と遷移は STSD / CSTD へ委ねます。
- データストアは論理的な正本として一覧化し、マスタ・構成データとトランザクションデータに分けて定義します。図に置くデータストアは一覧の各行と一対一に対応させます。
- プロセス領域の表を領域定義の正本、データストア一覧をデータストア定義の正本、Mermaid 図をグループとデータストアの間の流れの正本として併用し、名称を一致させます。
- 各プロセスグループには主要入力、主要出力、データストアを割り当て、図の各エッジの根拠にします。各プロセス領域には業務目的、主な担当、起点イベントを割り当てます。
- 対象者、利用場面、対象範囲、対象外を明示し、人間が担う承認や最終判断をシステムまたは AI Agent に置き換えません。

## 2. 位置づけと用語定義

| 用語                    | 定義                                                                                                                                                           |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 全体概要                | プロセスグループとデータストアの間の受け渡しを表す最上位の CDFD                                                                                                |
| プロセス領域            | 固有の業務目的、主な担当、起点イベントを持つ責務のまとまり。`P-01` 形式の領域 ID を持つ                                                                        |
| プロセスグループ        | 業務の性質が近いプロセス領域をまとめた集合。概念データフローの代表ノードであり、プロセスグループ別 CDFD の単位                                                 |
| 代表ノード              | 全体概要で一つのプロセスグループを表す角丸長方形の Mermaid ノード。`subgraph` ではなくノードとして描く                                                         |
| 起点イベント            | プロセス領域を開始させる、発生した時点を判定できる出来事。プロセス領域の表に記載し、全体概要の図には描かない                                                   |
| データストア            | プロセスグループが参照または更新する、台帳、文書、ファイル、設定などの論理的な正本。マスタ・構成データとトランザクションデータに区分する                       |
| マスタ・構成データ      | 他のプロセスから参照される比較的安定した基準情報。更新契機は承認された変更である                                                                               |
| トランザクションデータ  | 業務活動に伴い都度更新される記録。生成物や退避先を含む                                                                                                         |
| 保管先                  | データストアの物理的な所在（ファイルパス、帳簿、システムなど）。概念段階では未確定でよい                                                                       |
| 補助操作                | 一覧、検索、状態参照、検証、dry-run など、独立した業務成果を作らず他の領域を支援する操作                                                                       |
| プロセスグループ別 CDFD | 一つのプロセスグループを引き継ぎ、領域の内部プロセス、起点イベント、例外・復旧、データストアの読み書きを定め、状態定義・遷移は STSD / CSTD を参照する詳細 CDFD |
| ユースケース別 CDFD     | 複数のプロセスグループをまたぐ業務について、グループ間の順序と引き渡し条件だけを定める詳細 CDFD。構造規範は `specdojo:cdfd-uc-rulebook`                        |

全体概要はプロセスグループとデータストアの分割、およびグループとデータストアの間の受け渡しを定義します。プロセスグループ別 CDFD は一グループの内部を、ユースケース別 CDFD はグループ間の順序を詳細化し、いずれも全体概要と同じ領域 ID、プロセスグループ名、データストア名を引き継ぎます。

## 3. ファイル命名・ID規則

- ファイル名は `cdfd-overview.md`、ドキュメント ID は `cdfd-overview` を基本とします。product 文書ではプロジェクト修飾（`<project-id>:`）を付けず、プロジェクト固有の現状分析をプロジェクト文書配下へ置く場合だけ `<project-id>:cdfd-overview` とします。
- 配置は対象プロダクトの業務仕様配下にあるデータフローディレクトリを基本とします。
- 領域 ID は文書内で一意な `P-01` 形式とし、プロセス領域の表、代表ノードのラベル、詳細 CDFD 一覧で同じ値を使います。採番順に業務上の意味を持たせず、名称変更後も同じ責務を表す限り維持します。
- プロセスグループ名は英語の短い名詞（例: Plan、Do、Check、Action）または日本語の短い名詞句とし、代表ノードのラベルには `P-02〜P-06` のように含む領域 ID の範囲を併記します。
- プロセスグループ別 CDFD の ID は `cdfd-<group>`、ユースケース別 CDFD の ID は `cdfd-uc-<topic>` とします。`<group>` はプロセスグループ名の英小文字、`<topic>` はユースケースを表す英小文字のスラッグです。
- ユースケース ID は文書内で一意な `C-01` 形式とします。

見出し順・表・記入欄の骨組みは template を正本とします。本章は各章の目的と必須・任意を定めます。

| 番号 | 見出し                   | 必須     | 内容（要点）                                                                                                                            |
| ---- | ------------------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 冒頭 | 導入文                   | ○        | 対象業務・運用を一文で定義                                                                                                              |
| 1    | 目的                     | ○        | 対象者と利用場面                                                                                                                        |
| 2    | 適用範囲                 | ○        | 対象、対象外（領域内部の詳細化先）、補助操作の扱い、人間と AI Agent の責任分担                                                          |
| 3    | プロセス領域             | ○        | プロセスグループごとの節。各節に説明文、主要入力・主要出力・データストアの箇条書き、領域の表                                            |
| 4    | データストア一覧         | ○        | マスタ・構成データとトランザクションデータの 2 表。列はデータストア、主な内容、保管先（条件付き）                                       |
| 5    | 概念データフロー（概要） | ○        | プロセスグループの代表ノードとデータストアの Mermaid 図。ノード数が多い場合はトランザクションデータの図とマスタ・構成データの図に分ける |

- 「凡例（本プロダクト共通）」を省略する場合、章番号は詰めます。「未決事項」は最終章とします。
- 「概念データフロー（概要）」を 2 図に分ける場合は `5.1.`、`5.2.` の節を設け、分けない場合は節を設けず 1 図を置きます。

## 6. 記述ガイド

### 6.1. 導入文

- 対象業務または運用が何を扱うかを一文で定義します。
- 詳細な効果、指標、実装方式は列挙しません。

### 6.2. 目的

- 全体概要を使用する対象者と、承認、詳細化、設計入力、網羅性確認などの利用場面を結び付けて記述します。
- 「分かりやすくする」のような曖昧な表現ではなく、「PO が対象範囲と領域分割を承認する」のように利用結果を判定できる表現にします。
- 後続の詳細 CDFD（プロセスグループ別、ユースケース別）の位置付けを明確にすることを目的に含めます。

### 6.3. 適用範囲

- 対象業務、開始点、終了点、組織またはシステム境界を明示します。
- 領域内部（個別コマンドの操作手順、ファイル単位の更新内容、処理の分岐、状態を変える処理と起点イベント、例外時の復旧手順）は対象外とし、プロセスグループ別 CDFD へ委ねることを明記します。状態の定義と遷移は STSD / CSTD が正本であることも示します。
- 補助操作は独立した業務フローに含めず、各領域を支える操作として扱うことを明記します。
- 人間と AI Agent の責任分担は、対応するプロジェクト方針文書があればそれを参照し、なければ「承認・完了判断・構成変更の承認・非推奨化の判断は人間が担い、成果物の作成・評価・派生生成は人が担うほか AI Agent へ委譲できる」のように原則を一文で書きます。
- 特定プロジェクトの実行計画・スケジュール上のフェーズ名は、全体概要では扱いません。

### 6.4. プロセス領域

- 章の冒頭で、領域数、プロセスグループ数、正本の所在（領域の分割と受け渡しは本書、領域内部はプロセスグループ別 CDFD）を宣言します。
- プロセスグループごとに節（`3.1.`、`3.2.`、…）を設け、見出しは「グループ名（含む領域 ID の範囲）」とします。各節は次の順で構成します。
  - グループの役割と、グループ内の領域がどう連携するかを 1〜3 文で要約した説明文。
  - `**主要入力**`、`**主要出力**`、`**データストア**` の 3 項目の箇条書き。他グループからの要求（例: Orchestrator からの計画要求）も入力に含めます。
  - 領域の表。
- プロセスグループの数は 8 以下とします。超える場合は業務の性質が近いグループを統合します。1 領域だけのグループも認めます。

<!-- prettier-ignore -->
| 列 | 記載内容 | 判定基準 |
| --- | --- | --- |
| 領域 ID | `P-01` 形式の安定した識別子 | 表、代表ノードのラベル、詳細 CDFD 一覧で同じ ID を使う |
| プロセス領域 | 業務目的が分かる短い名称 | コマンド名や実装部品名だけにしない |
| 業務目的 | 対象者に生じる成果または維持する状態 | 手順や機能の列挙にしない |
| 主な担当 | 主担当ロール。複数ロールが担う場合は管理責任のロールを併記する | 個人名にしない。「全員」だけで終わらせない |
| 起点イベント | 領域の開始を判定できる出来事。定義系の領域は「要件が判明した」、実行系の領域は「指示された」「到来した」のように区別する | 「必要に応じて」で終わらせない。同じグループ内で同文にしない |

- 独立領域にするのは、固有の起点イベントと業務成果を持ち、他領域と区別できる入力、出力、またはデータストアがある場合です。補助操作は、独立した判断結果や更新成果を持たない限り領域にしません。
- 領域単位の主要入力・主要出力・データストアは本書に書かず、プロセスグループ別 CDFD へ委ねます。本書の箇条書きはグループ単位に留めます。

### 6.5. データストア一覧

- 章の冒頭で、区分の意味、パスの略記（例: `<project-id>` が指す範囲）、データストアとして扱わないもの（リポジトリ基盤、開発環境の設定など）を各一文で示します。
- マスタ・構成データとトランザクションデータの 2 表に分け、各行は次の列で構成します。

<!-- prettier-ignore -->
| 列 | 記載内容 | 判定基準 |
| --- | --- | --- |
| データストア | 論理的な正本の名称 | 図のノードラベル、プロセス領域の箇条書きと同じ名称を使う |
| 主な内容 | 保持する情報の種別。生成物なら生成元、退避先なら退避対象を書く | 「各種データ」のような抽象語だけにしない |
| 主な保管先 | 物理的な所在。複数ある場合は `、<br>` で区切る | 別のデータストアの保管先と重ならない範囲に限定する |

- 「主な保管先」列は条件付きです。実装が先にある場合（retrofit）は必須とし、実装エビデンスとして記載します。設計中で候補がある場合は列を置き、未確定のセルは `_UNDECIDED_` とします。保管先を扱わない概念段階では列ごと省略します。
- 区分の判定基準は更新契機です。承認された変更で更新されるものはマスタ・構成データ、業務活動に伴い都度更新されるものはトランザクションデータとします。定義から生成される生成物は、生成元の定義がマスタ・構成データであっても、生成物自体はトランザクションデータとします。
- 生成物の集約先（評価結果、報告、派生ビューなど）や退避先（保管庫など）も、プロセスグループが更新するならデータストアとして一覧に含めます。

### 6.6. 概念データフロー（概要）

- 章の冒頭で、ノードの構成（プロセスグループの代表ノードとデータストア）、矢印の意味（情報または実行要求の受け渡しであり実行順ではない）、更新エッジが参照を含むこと、外部主体の扱いを各一文で示します。
- 代表ノードはプロセスグループごとに一つとし、ラベルにグループ名と含む領域 ID の範囲を書きます。`subgraph` で領域や代表ノードを囲みません。
- データストアのノードは「データストア一覧」の各行と一対一とし、同じ名称を使います。
- 対象範囲内の参加者（ロール）は各領域の担当として業務プロセスの内側にいるため、外部主体として描きません。外部主体を描くのは対象範囲外の入力元・出力先だけです。
- 起点イベントは「プロセス領域」の表に記載し、図には描きません。
- 図のノード総数（代表ノードとデータストアの合計）が 16 を超える場合は、トランザクションデータに着目した図とマスタ・構成データに着目した図に分けます。分ける場合は、両図で代表ノードとデータストアの名称を統一し、あるグループから他グループへの要求（Orchestrator の要求など）はトランザクションの図にだけ描きます。
- 各図の直後に、凡例の参照先、現物の流れの有無、その図に載せていない要素の参照先、外部主体の有無を一段落で注記します。
- エッジは「プロセス領域」の各グループの主要入力・主要出力から導出し、ラベルは名詞形の具体的なデータ名にします。データストアを更新するエッジは更新前の参照を含むものとし、参照だけのエッジは別に描きます。
- ノード形状、線種、色、絵文字の記法は `specdojo:cdfd-mermaid-rulebook` に従います。全体概要の図に含める要素の種別（代表ノード、データストア、必要に応じた外部主体）は本節の規定を優先します。

### 6.7. 詳細 CDFD 一覧

- 章の冒頭で、プロセスグループ別 CDFD とユースケース別 CDFD の役割分担を箇条書きで示します。前者はグループ内部のプロセス・例外・データストア読み書きの正本、後者は `specdojo:cdfd-uc-rulebook` に従ってグループ間の順序と引き渡し条件だけを定め、内部プロセスを再掲しないことを明記します。状態の定義は STSD、状態遷移は CSTD が正本であり、詳細 CDFD は参照に留めることも示します。
- プロセスグループ別 CDFD の表は、プロセスグループ、含む領域、CDFD の ID の 3 列とし、全プロセスグループを 1 行ずつ載せます。各領域はちょうど一つの行に属します。
- ユースケース別 CDFD の表は、ケース ID、ユースケース、業務目的、横断するプロセスグループ、CDFD の ID の 5 列とし、複数のプロセスグループを横断し順序と引き渡し条件を定める必要がある業務だけを載せます。単一のグループに閉じる業務は載せず、必要になった時点で追加する旨を本文に書きます。
- 未作成の CDFD に「（未作成）」などの状態表記を付けません。作成状況は登録簿で追跡します。

### 6.8. 凡例（本プロダクト共通）

- 本プロダクトの詳細 CDFD が複数存在し、共通のノード形状・色・絵文字を使う場合に設けます。単一の CDFD しか存在しない場合は省略できます。
- `specdojo:cdfd-mermaid-rulebook` が定義する全ノード種別について、本プロダクトが実際に採用する色・絵文字の割り当てをサンプル図と対応表で示します。本図自体が業務データフローを表すものではないため、他章のプロセス領域や受け渡しとは独立させます。
- 本書自身の概念データフローと各詳細 CDFD の凡例は、この章の定義を再掲せず、本章への参照に留めます。

### 6.9. 未決事項

- 境界、名称、責務、判断者、保管先のいずれかが未確定な論点がある場合だけ設けます。ない場合は章ごと省略します。
- 表は論点、影響、決定者、決定時期、状態の 5 列とします。本文中の未確定箇所には `_UNDECIDED_` を付け、表の論点と対応させます。
- 確定した論点は、本文へ反映したうえで表から削除します。

### 6.10. 完成判定

本節をチェックリストの正本とし、他節の条件はここに集約します。

- プロセス領域の表の各領域が、ちょうど一つのプロセスグループの節に属し、ちょうど一つのプロセスグループ別 CDFD の行に属します。
- プロセスグループの数が 8 以下です。
- 各プロセスグループの主要入力・主要出力・データストアの箇条書きと、概念データフローのエッジが相互に対応します。箇条書きにあってエッジがない受け渡し、エッジにあって箇条書きにない受け渡しがありません。
- 概念データフローのデータストアが「データストア一覧」の各行と一対一で、名称が一致します。
- 「主な保管先」列を置く場合、各パスが一つのデータストアにだけ属します。
- 図の全エッジに名詞形のラベルがあり、起点と到達先が明らかです。`subgraph` を使っていません。
- 図のノード総数が 16 を超える場合は 2 図に分かれ、両図で名称が統一されています。
- 補助操作と領域内部の手順が独立領域として混入していません。
- ユースケース別 CDFD の各行が複数のプロセスグループを横断しています。
- 「凡例（本プロダクト共通）」を設けた場合、他の CDFD がそれを再掲せず参照しています。
- `_TODO_` が残っていません。`_UNDECIDED_` は「未決事項」の表と対応しています。

## 7. 禁止事項

<!-- prettier-ignore -->
| 禁止事項 | 理由 |
| --- | --- |
| プロセスグループを `subgraph` で表す、または一つの領域を複数の代表ノードへ分割する | 代表ノードとプロセスグループ別 CDFD の対応が崩れ、表・図・詳細 CDFD の突き合わせができなくなるため |
| 業務の性質が異なる領域を、理由の説明なく一つのプロセスグループへ統合する | 詳細化先の境界が不明瞭になり、重複・欠落の確認ができなくなるため |
| 全体概要に領域単位の主要入力・主要出力・データストアや、領域内の操作手順、状態を変える処理、例外分岐、物理テーブル・カラム、SQL、実装クラス、詳細 API、コマンドオプションを記載する | プロセスグループ別 CDFD の責務であり、二重管理と粒度超過を招くため |
| 全体概要または詳細 CDFD で状態の定義・遷移表を正本化する | 状態の定義は STSD、状態遷移は CSTD が正本であり、CDFD との二重管理を招くため |
| 一覧、検索、状態参照、検証、dry-run などを、固有の業務成果がないまま独立領域にする | 補助操作を業務成果と誤認させるため |
| プロセス領域の表、箇条書き、データストア一覧、図、詳細 CDFD 一覧で、同じ領域・グループ・データストアに異なる名称を使う | 読み手が同一対象と判断できなくなるため |
| ラベルのないエッジ、起点または到達先のないエッジ、データストア一覧に行のないデータストアのノードを残す | 受け渡しの内容・方向・対応関係が読み取れなくなるため |
