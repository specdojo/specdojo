# 運用手順 全体構成 作成ルール

Operations Procedure Runbook Index Documentation Rules

運用者が作業と証跡を再現できる `opr-index` の記述基準を定める。

## 1. 全体方針

- 点検・障害・変更などの運用作業を、どの条件でどう実施し何を証跡に残すかを判断するための、実行手順と証跡の正本とする。方針・統制は `opd-*`（`opd-index` と分冊の `opd-<term>`）に従う。
- 本文構成と記述ガイドで骨組み・記入基準が定まるため、別の recipe・template は不要とする。
- **共通の運用**: 役割は適用先のメンバー定義、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。作成・改訂後は Markdown lint（`npm run lint:md`）と Frontmatter スキーマ検証（`npm run lint:fm`）をエラーなしで通す。

## 2. 位置づけと用語定義

`opd`（Operations Policy and Design）は運用の方針・統制、`opr`（Operations Procedure Runbook）は方針に基づく実行手順と証跡を担う。

| 文書         | 担う内容                                                                           |
| ------------ | ---------------------------------------------------------------------------------- |
| `opd-*`      | 判断基準・統制（SLO/SLA、承認者、停止判断）。手順は書かない                        |
| `opr-index`  | 手順群の入口と共通規約（手順表の列、証跡、優先度の扱い）、および分冊しない章の手順 |
| `opr-<term>` | `opr-index` の共通規約を前提に、1 つの作業領域の具体手順と個別判断だけを書く分冊   |

章を分冊へ切り出すのは、作業領域（障害・監視・バッチ・権限・問い合わせ・変更など）の手順が独立して改訂される場合とする。証跡と関連導線は共通規約として `opr-index` に残す。

## 3. ファイル命名・ID規則

- ID はプロダクト文書なら `opr-index`、プロジェクト固有の成果物なら `<project-id>:opr-index` とし、成果物カタログの宣言と一致させる。分冊も同じ修飾方針で `opr-<term>`（kebab-case）とする。
- ファイル名は ID のローカル部と同名の `.md`（`opr-index.md` / `opr-<term>.md`）を推奨する。
- 配置は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] の `docs/ja/product/090-operations/` を推奨する。

## 4. 推奨 Frontmatter 項目

共通項目・必須性・型はドキュメントメタ情報標準と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` に従う。`specdojo.type` は `operations`、必須の `specdojo.rulebook` は `specdojo:opr-index-rulebook` とする。

## 5. 本文構成（標準テンプレ）

全章必須。該当作業がなければ章を残して「対象外」と理由を示し、分冊した手順は `opr-<term>` への参照で満たす。

| 章  | 内容                                             | 必須 | 受入条件                                                      |
| --- | ------------------------------------------------ | ---- | ------------------------------------------------------------- |
| 1   | 概要（index）                                    | ○    | 対象運用・目的・利用場面                                      |
| 2   | 手順適用範囲・前提                               | ○    | 対象内外・時間帯・権限・環境                                  |
| 3   | 日次/週次/月次点検手順                           | ○    | 頻度別の点検対象・操作・判定                                  |
| 4   | 障害対応手順（P1/P2…、切り分け、一次対応、復旧） | ○    | 優先度別の初動 SLA・段階別操作・連絡条件と連絡先の窓口        |
| 5   | アラート対応手順（確認→暫定対応→恒久対応）       | ○    | 各段階の操作・誤検知の終了条件                                |
| 6   | バックアップ確認・リストア手順（演習含む）       | ○    | 確認・復元操作・演習頻度・復旧目標の達成判定                  |
| 7   | バッチ再実行・失敗時対応                         | ○    | 再実行条件・上限回数・冪等性・上限到達時の対応                |
| 8   | 運用変更作業（設定変更・デプロイ・ロールバック） | ○    | 承認者・実施条件・切戻し条件と操作                            |
| 9   | アカウント付与/剥奪手順                          | ○    | 申請・承認・実施・権限検証・記録                              |
| 10  | 問い合わせ一次対応手順（テンプレ・ナレッジ）     | ○    | 分類・回答例・参照知識・引継ぎ条件と引継ぎ先の窓口            |
| 11  | 証跡（ログ、チケット、チェックリスト、実施記録） | ○    | 保存先・保管期間・参照権限・`ticket_id` / `run_id` 等の識別子 |
| 12  | 関連ドキュメント導線（`opd-index` 参照）         | ○    | 方針と分冊への導線（分冊なしも明示）                          |

## 6. 記述ガイド

- 方針と適用範囲を確認し、手順、証跡、関連導線の順に具体化する。未決の条件は該当章に論点と運用への影響を残す。
- 手順表の標準列は「実施者・入力条件・操作・完了条件・証跡」とする。良い例:「当番・再実行済み・実行 ID で結果照合・成功かつ重複なし・実行ログ」。悪い例:「適宜再実行」。
- 実施者・承認者・連絡先・引継ぎ先は Role 名または窓口名で、付与するアカウントは権限の種類で書く。良い例:「P1 は 15 分以内に Ops Lead 窓口へ連絡」「管理者権限を付与」。悪い例:「山田さんの携帯へ電話」「個人のログイン名を列挙して付与」。
- 受入確認は各手順を検証環境で実行または模擬し、完了条件と証跡を照合する。異常時の分岐を含め、操作・判断・記録を再現でき、`opd-*` と一致すれば合格とする。

## 7. 禁止事項

| 禁止事項                                           | 理由                                                     |
| -------------------------------------------------- | -------------------------------------------------------- |
| 優先度別の障害対応を未定義のまま確定する           | 障害時に初動と連絡の判断ができないため                   |
| 証跡要件（保存先・識別子）を省略する               | 作業の実施を後から照合できないため                       |
| `opd-*` と矛盾する手順を独自に定義する             | 方針と手順の正本が食い違い、どちらに従うか決まらないため |
| 個人名・個人の連絡先・個人のアカウント識別子を書く | 公開・配布時に個人情報が漏れ、異動のたびに改訂が要るため |
