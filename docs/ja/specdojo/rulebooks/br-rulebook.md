# ビジネスルール 作成ルール

Business Rule Documentation Rulebook

業務上の判断・制約・計算を、同じ入力から同じ結果を導ける仕様として記述するための規約です。業務担当者が妥当性を判断でき、実装とテスト設計へ引き継げる粒度を定めます。

## 1. 全体方針

- 1 文書で一つの判断目的を扱い、適用条件、概念入力、判定、出力、例外を対応させる。
- 業務価値は上位文書から引き継ぎ、本書の判断が守る価値と適用境界だけを記す。共通事項は上位の index または標準を正本とする。
- 業務上の比較・計算の意味を定義し、設定値の列挙、構文、物理構造は対応する schema・リファレンスを参照する。実装コードを仕様の代替にしない。
- 未決事項は共通ラベルで確定事項と区別し、承認なしに既定値や欠損時の扱いを補わない。

## 2. 位置づけ

BR は業務プロセスから呼び出される判断の正本である。BPS が適用する場面と手順を定め、BR がその時点の入力に対する結果を定める。画面操作、保存方法、実行制御、テスト手順はそれぞれの責務を持つ成果物へ委譲する。

独立して承認・変更できる判断目的が複数ある場合は文書を分ける。同じ判断を完結させる入力検証・計算・例外は、条件数だけを理由に分割しない。

- **主要な関係者（Role code）と確認観点**:
  - **BA（ビジネスアナリスト / 主作成者・問い合わせ対応）**: 業務上の判断目的・ルール・入出力・例外を記述し、改訂・廃止時の BPS への影響分析とルール解釈の問い合わせに対応する。
  - **PO（プロダクトオーナー / 承認者）**: 業務判断の妥当性、ルールの置き換えおよび廃止（`deprecated` 移行）を最終判断・承認する。
  - **ARC（アーキテクト / 確認者）**: システム制約、データモデル・外部スキーマとの整合性を確認する。
  - **DEV（開発者 / 利用者）**: ルールを実現するロジック・関数の実装、型制約との対応を確認する。
  - **QE（品質保証 / 確認者）**: 判定境界値の網羅性、検証可能性、業務受入条件（BAC）やテスト（UTC/ITC）への追従を確認する。
  - **PM（プロジェクトマネージャー / 進行管理）**: 改訂・廃止に伴う関連成果物・実装・テストの更新タスク（PJR）を起票・管理する。

## 3. ファイル命名・ID規則

- ファイル名は判断の意味を表す `br-<subject>.md` を推奨する。連番や特定プロジェクトの管理番号を必須にしない。
- 成果物の ID はプロジェクト内で一意にし、文書参照では `<project-id>:br-<subject>` のように project 修飾する。
- 配置は対象プロジェクトの成果物カタログに従う。ディレクトリと ID の共通規則は [[specdojo:docs-structure-guide|ドキュメント構造ガイド]] を正とする。

## 4. 推奨 Frontmatter 項目

共通項目・型・許可値は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と [成果物 Frontmatter schema](../../../specdojo/schemas/v1/deliverable-frontmatter.schema.yaml) を正本とする。

- `type` は業務の判断を表す `rule` とし、適用する主 rulebook を宣言する。
- `based_on` は判断の根拠となる先行成果物を示す。依存先が未作成の場合は本文にも未確認の範囲を残し、内容を確認済みと扱わない。
- `part_of` は親ルールへの所属がある場合だけ用いる。ルールの名称は H1 に置き、未承認の文書を `ready` にしない。
- `supersedes` は置き換え対象の旧 BR の ID 配列を指定する。判断規則の大幅な変更時に新 BR を作成して指定し、旧 BR は `status: deprecated` へ移行する。
- `status` は `draft` / `ready` / `deprecated` とする。作成・改訂中は `draft` とし、PO の承認を経て `ready` へ昇格する。廃止時は直接削除せず `deprecated` に移行して移行期間を設ける。
- **ライフサイクル操作と波及影響の追跡規則**:
  - **更新・置き換え**: 判断規則の大幅改訂時は新 BR を作成し `supersedes` に旧 ID を設定する（PO 承認）。保守担当（BA）は BPS 側での参照更新案を作成する。
  - **廃止**: 当該ビジネスルールが不要となった場合、`status: deprecated` に移行し、廃止理由と代替（無条件実行、別ルール等）を明記する（PO 承認）。`deprecated` の BR を有効な BPS や新規文書から参照してはならない。
  - **問い合わせ対応**: ルールの解釈、例外発生時の扱い、境界値の妥当性に関する問い合わせ窓口は BA が担当し、仕様の曖昧さが見つかった場合は改訂またはメモ／将来課題へ記録する。
  - **波及影響の識別・追従規則**:
    BR の条件・出力変更時は、共通基準 [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、参照元となる BPS、実装、テストへの影響を追跡して同期更新する。
    - **参照元業務プロセス仕様（BPS）**: BA は当該 BR を「活動・判断」で参照している全処理ステップを抽出し、入力項目の過不足、判定結果の分岐、完了条件の整合性を更新する。
    - **実装コード**: DEV は当該 BR をロジックや計算式として実装している関数・ドメインモデルを特定し、追従修正を実施する。
    - **テスト仕様・受入条件**: QE は当該 BR を検証する業務受入条件（BAC）、単体・結合テスト（UTC / ITC）の判定例・境界値を更新し、再検証を行う。
    - **変更タスク管理**: PM は波及する関連文書・実装・テストの更新タスク（PJR 項目）を起票・追跡する。

## 5. 本文要件

内容要件は次のとおり。すべて必須とし、該当する例外や未決事項がなければ「なし」と明示する。見出し順・表・記入欄の骨組みは frontmatter で宣言した template を正本とする。

| 扱う内容            | 成立条件                                                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 概要                | 判断の目的、利用者、適用する業務場面、前提、対象外が分かる                                                               |
| 入力                | 判定に使う全入力について概念項目、利用目的、適用条件、欠損時の扱いが分かる。派生ビュー等を使う経路も含む                 |
| ルール（判定/計算） | 適用順、条件、結果、境界値が対応する。複数条件の優先順位、同順位・欠損時の扱いを定め、代表的な判定例を置く               |
| 出力                | 正常な結果の意味、単位または区分、利用先が分かる。「対象なし」と判定不能を区別する                                       |
| 例外 / 異常系       | 状況、判定を続けるか、結果の有無、回復のために誰が何をするかが分かる                                                     |
| メモ / 将来課題     | 未決事項ごとに決定を依頼する相手、判断時点、下流への影響、必要な根拠を記す。未決事項がある場合は承認可能となる条件も示す |

## 6. 記述ガイド

### 6.1. 概要

- 判断基準: どの業務場面のどの判断を引き受けるかが一意で、対象外の責務と重ならないこと。
- 良い例: 「在庫確認時に、販売可能数が発注点を下回るかを判定する。発注量と発注の承認は対象外とする」。
- 悪い例: 「在庫を適切に管理する」。判断結果と責務境界を特定できない。

### 6.2. 入力

- 判断基準: 条件式と例外が参照する情報を全件たどれ、任意入力・条件付き入力と必須入力を区別できること。
- 推奨列は「入力 / 概念データ・項目 / 利用目的 / 適用条件・欠損時の扱い」。数値は業務上の単位と比較時点を添える。値の形式や列挙の詳細は正本へ委譲する。
- 良い例: 「予約数は個数で受け取り、販売可能数の計算に使う。未設定なら判定不能とする」。
- 悪い例: 「在庫データ一式を参照する」。どの項目の欠損が結果に影響するか分からない。

### 6.3. ルール（判定/計算）

- 判断基準: 同じ入力に対して複数の結果が生じないこと。比較対象の項目ごとに有無を定義し、既定値、同順位の決着、条件が重なる場合の優先順を明らかにする。
- 文字列で順位を決める場合は、照合方法の正本または決定済みの比較規則を示す。「辞書順」だけで言語・環境に依存する差を残さない。未決なら候補と影響をメモへ送る。
- 推奨する判定例の列は「例 / 入力・前提 / 適用規則 / 期待結果」。通常、境界、欠損、同順位のうち当該ルールに該当するケースを含める。
- 良い例: 「販売可能数と発注点が等しい場合は不足としない」。
- 悪い例: 「少なければ不足」。比較する量と等号の扱いが不明である。本文と同じ処理の擬似コードも重ねない。

### 6.4. 出力

- 判断基準: 利用者が結果の意味と次の業務への渡し方を判断でき、未計算を正常値と取り違えないこと。
- 良い例: 「不足判定は『不足 / 不足なし』。入力不備では判定値を返さず、不備項目を返す」。
- 悪い例: 「フラグを返す」。真偽の意味、判定不能時、利用先が分からない。

### 6.5. 例外 / 異常系

- 判断基準: 入力欠損、値の矛盾、外部参照の失敗など該当する状況を分け、正常な対象なしと区別すること。例外が重なる場合も扱いを決める。
- 推奨列は「ID / 状況 / 扱い / 利用者の次の手」。代替値や代替順位を使うなら、通常規則のどこを置き換えるかを特定する。
- 良い例: 「発注点が未設定なら判定を行わない。店主代表が発注点を登録した後に再判定する」。
- 悪い例: 「エラー時はログを出す」。業務が続くか、結果が有効かを判断できない。

### 6.6. メモ / 将来課題

- 判断基準: 作成済みの仕様で判断できる範囲と、承認前に解消すべき論点を区別できること。意思決定の未了は `_UNDECIDED_`、確認作業の不足は `_TODO_`、仮説は `_ASSUMPTION_` で示す。
- レポート引き継ぎ手順: 永続的なリスク、問題、変更要求、および決定事項は本文のラベルだけで放置せず、担当 Role code（BA / PM / ARC 等）と転送先レコード（PJR リスク登録簿 `pm-risk-register`、課題管理簿 `pm-issue-log`、変更要求ログ `pm-change-request-log`、決定記録 `pm-decision-log`、または PJR 登録項目）を明記し、PJR の共通管理手順に従って正式に起票・引き継ぎを行う。
- 良い例: 「`_UNDECIDED_`: 季節別の発注点を採用するか、店主代表へ判断を依頼する。導入承認前に決める（担当: BA、転送先: `pm-decision-log`）。未決の間は季節別判定の実装・受入条件を確定できない」。
- 悪い例: 「将来検討する」。依頼先、期限となる判断時点、下流の制約、引き継ぎ先レコードを追跡できない。

## 7. 禁止事項

- 業務プロセスの手順、画面操作、物理テーブル、SQL、実装クラスを BR の判断規則として持ち込まない。
- schema やリファレンスにある値・構文・構造の一覧を転記して別の正本を作らない。
- 複数の BR に同じ規則を複写しない。独立した判断は責務を分け、文書 ID で参照する。
- 不明な既定値、欠損時の順位、例外時の継続可否を推測で確定しない。未決事項を通常の判定例の期待値として扱わない。
- 未定義の略語や、根拠のない「適切に」「必要に応じて」で判定条件を代替しない。
- `deprecated` の BR を有効な BPS や新規文書から参照しない。
- 参照元 BPS、実装コード、テスト仕様への波及影響を確認・追従せずに BR を改訂または廃止しない。
