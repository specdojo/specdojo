# 品質管理計画 作成ルール

Quality Management Plan Documentation Rulebook

利用者価値と成果物品質を、少数の品質ゲート、証跡、是正方法で管理するためのルールです。

## 1. 全体方針

- 品質は、利用者価値の成立と、それを支える成果物・技術条件の両方で判定します。
- 小規模プロジェクトでは、代表試行、主要レビュー、公開前確認など必要なゲートだけを置きます。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。文書の整形・lint・見出し・wikilink の検査はリポジトリの検証で扱い、業務の受入条件に含めません。

## 2. 位置づけ

本計画は、管理計画の品質方針を判定時点・責任・証跡・是正へ具体化し、レビューと後続作業の計画に用います。

## 3. ファイル命名・ID規則

- 配置は `docs/ja/projects/<project-id>/030-project-management/pm-quality-management-plan.md` を推奨します。
- ID は `<project-id>:pm-quality-management-plan`、ファイル名は `pm-quality-management-plan.md` とします。
- 共通の命名規則は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従い、判定条件は成功基準 ID、受入条件 ID、成果物 ID など安定した識別子で参照します。

## 4. 推奨 Frontmatter 項目

- 共通項目・型・許容値は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と同標準から参照する成果物 schema に従います。`rulebook` は本書の ID、種別は本書の `deliverable_type` に合わせます。
- `based_on` には、管理計画など作成時に直接根拠とした先行成果物を記載します。カタログを利用する場合は `depends_on` の推移閉包内に限り、閉包外の根拠が必要なら依存関係の整備を先行させます。

## 5. 本文要件

見出し順・表・記入欄の骨組みは Frontmatter で宣言した template を正本とし、本書では各章が満たす意味要件を定めます。

| 要件                           | 必須条件                 | 記載する判断・根拠                                                   |
| ------------------------------ | ------------------------ | -------------------------------------------------------------------- |
| 品質方針と適用範囲             | 必須                     | 価値品質と成果物品質、対象範囲、適用開始・終了                       |
| 品質ゲート                     | 必須                     | ゲートごとの品質観点、条件 ID、確認方法と証跡、時期、確認・承認責任  |
| レビューと証跡                 | 必須                     | 対象、主要観点、実施責任、合否を判定できる出口条件、証跡、記録先     |
| 不適合と是正                   | 必須                     | 区分ごとの対応、再判定条件、再判定責任、記録先、重大不適合の通過制限 |
| 見直し条件と未決事項（見直し） | 必須                     | 見直し契機、影響する正本・後続作業                                   |
| 見直し条件と未決事項（未決）   | 未決事項がある場合に必須 | 未決論点と影響、未決中に保留する判定。なければ「なし」と明記できる   |

## 6. 記述ガイド

品質計画固有の判断基準と部分例を示します。

### 6.1. 品質方針と適用範囲

- 判断基準は、利用者価値とそれを支える成果物品質、対象範囲・期間を識別できることです。成功基準を根拠とし、技術検証だけで価値を判定しません。
- 適用開始・終了は日付または識別可能なイベントで示します。公開後の観測を含む場合は終了までの関係を示し、未確定の終了日は終了条件と見直し契機で代替できます。
- 良い例: 「代表試行開始から公開後価値ゲートの判定完了まで適用する。利用継続と負担を価値品質、再現性を成果物品質として確認する」。
- 悪い例: 「開発中の品質を高める」。価値品質と期間の境界を確認できません。

### 6.2. 品質ゲート

- 判断基準は、各ゲートから条件の正本、確認方法、証跡、時期、確認者と承認者を辿り、合否または保留を決められることです。初期受入と公開後の継続判断は適用時点を分けます。
- 合格条件は文書 ID と条件 ID で参照し、算出方法・閾値・計測頻度を正本から確認できるようにします。条件を満たさなければ未達、証跡不足・条件未定義なら保留とし、いずれも通過させません。
- 「確認者 / 承認者」は証跡に基づく品質確認と当該ゲートの判断を区別して示します。
- 費用・負荷を扱う場合は、現金支出、作業時間、継続運用負荷を別の基準・記録で確認します。
- 良い例: 「初期受入は SC-01・AC-01 に基づき試行終了時に判定する。確認者が試行記録を条件別に照合し、全条件の合格で通過する」。
- 悪い例: 「lint が通れば受入とし、利用者の評価は後で確認する」。価値の合否を判定できません。

### 6.3. レビューと証跡

- 判断基準は、対象版について誰が何を確認し、どの状態なら通過でき、どこに結果が残るかを再現できることです。レビュー種別は対象と対応が異なるものに絞ります。
- 列名は「対象」「実施責任」に統一します。「出口条件」は合否を分ける状態、「証跡」は判定を裏付ける記録、「記録先」はその記録へ到達する文書 ID またはパスです。三者を独立した列で必須とし、証跡名だけで出口条件を代替しません。
- 証跡には対象版、実施日、結果、未達条件・指摘と是正・再判定結果を追跡できる情報を残します。生成物の是正は生成元の正本を修正し、再生成して確認します。
- 良い例: 「試行結果を確認者が照合する。出口条件は AC-01 の合格、証跡は対象版と条件別結果を持つ試行記録、記録先は `execution/reviews/trial-1/result.md` とする」。パスは例示であり、実際の保存先を指定します。
- 悪い例: 「実施者: 関係者、出口条件・証跡: レビュー結果」。責任、通過条件、記録先を特定できません。

### 6.4. 不適合と是正

- 判断基準は、不適合から是正、再判定、結果記録までを追跡できることです。軽微、価値、構造・検証、公開など対応差がある区分だけを置きます。
- 「再判定条件」と「再判定責任」を独立した列に分けます。前者は是正後に再確認する条件 ID・ゲートと確認を再開する契機、後者は再確認を担う Role code です。
- 必須の価値・受入条件、検証の成立、公開安全性への影響から重大性の判定境界を示します。重大な不適合は是正完了、または管理計画が認める期限付き例外の成立まで該当ゲートを通過させません。例外には対象条件、理由、期限、再判定条件を残します。
- 記録先はレビュー記録・検証結果・登録簿の文書 ID またはパスで特定し、条件変更を伴う是正は変更要求・決定記録へ接続します。
- 良い例: 「技術不適合は生成元を修正する。再判定条件は再生成後に未達の AC-02 と影響範囲の検証が成功すること、再判定責任は `QE` とし、対象版・結果を課題個票から辿れる検証記録に残す」。
- 悪い例: 「対応: 修正、再判定: `QE`、記録先: 課題」。条件・確認契機と到達先が不明です。

### 6.5. 見直し条件と未決事項

- 判断基準は、見直しの契機と判定条件への影響を追えることです。成功基準、公開範囲、成果物構造、検証方法、体制、重大不適合の傾向の変化を確認します。
- 追従対象は管理計画・RACI・Schedule・証跡参照とし、影響する条件 ID・証跡・再確認範囲を特定します。
- 未決事項は「論点」「影響・未決中に保留する判定」を示し、決定時に直す条件・証跡を特定します。
- 良い例: 「`_UNDECIDED_:` 試行記録の形式。未決の間は代表試行ゲートを保留する。決定後は証跡参照を更新し、確認工数が変われば Schedule に反映する」。
- 悪い例: 「手順は後で決め、変更時は見直す」。ゲートと後続作業への影響を確認できません。

## 7. 禁止事項

| 禁止事項                                                | 理由                               |
| ------------------------------------------------------- | ---------------------------------- |
| 成功基準の閾値・算出方法を品質ゲートで再定義する        | 判定条件の正本が分散するため       |
| 品質目標、メトリクス、検査基準へ同じ条件を重複記載する  | 更新量と不整合が増えるため         |
| 技術検証だけで利用者価値の品質を代替する                | プロジェクト成功を判定できないため |
| 現金支出だけを確認し、人の負荷を除外する                | 負荷転嫁を見逃すため               |
| 生成物を直接修正して不適合を解消する                    | 再生成時に修正が失われるため       |
| 証跡名や Role code だけで出口条件・再判定条件を代替する | 合否と責任を別々に確認できないため |
