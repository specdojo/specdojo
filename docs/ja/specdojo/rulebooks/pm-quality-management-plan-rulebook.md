# 品質管理計画 作成ルール

Quality Management Plan Documentation Rulebook

利用者価値と成果物品質を、少数の品質ゲート、証跡、是正方法で管理するためのルールです。成功基準、rulebook、検証手順を再掲せず、いつ何を確認するかを定義します。

## 1. 全体方針

- 品質は、利用者価値の成立と、それを支える成果物・技術条件の両方で判定します。
- 成功基準・受入条件、成果物 rulebook、検証手順を正本とし、条件 ID と参照先で品質ゲートへ接続します。
- 品質目標、メトリクス、検査基準を重複させず、品質ゲートへ統合します。
- 小規模プロジェクトでは、代表試行、主要レビュー、公開前確認など必要なゲートだけを置きます。
- 低コストや継続性を価値に置く場合は、現金支出、作業時間、継続運用負荷を品質判断に含めます。
- AI Agent は検証や指摘整理を支援できますが、利用者価値、例外、公開可否の最終判断は人間が行います。

## 2. 位置づけと用語定義

- 本計画は、管理計画の品質方針を判定時点・責任・証跡・是正へ具体化し、レビューと後続作業の計画に用います。
- Role、Member、RACI の定義と委任方針は [[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] を正本とします。

| 用語       | 定義                                                           |
| ---------- | -------------------------------------------------------------- |
| 品質ゲート | 所定の時点で、条件・証跡・判断者をそろえて合否を確認する仕組み |
| 価値品質   | 利用者・業務・社会に期待する変化が成立したかを示す品質         |
| 成果物品質 | 構造、整合、検証、公開適性など価値提供を支える品質             |
| 不適合     | 品質ゲートの合格条件を満たさない状態                           |

## 3. ファイル命名・ID規則

- 配置は `docs/ja/projects/<project-id>/030-project-management/pm-quality-management-plan.md` を推奨します。
- ID は `<project-id>:pm-quality-management-plan`、ファイル名は `pm-quality-management-plan.md` とします。
- 共通の命名規則は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従い、判定条件は成功基準 ID、受入条件 ID、成果物 ID など安定した識別子で参照します。

## 4. 推奨 Frontmatter 項目

- 共通項目・型・許容値は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と同標準から参照する成果物 schema に従います。`rulebook` は本書の ID、種別は本書の `deliverable_type` に合わせます。
- `based_on` には、管理計画など作成時に直接根拠とした先行成果物を記載します。カタログを利用する場合は `depends_on` の推移閉包内に限り、閉包外の根拠が必要なら依存関係の整備を先行させます。
- 置き換え時の `supersedes` と状態変更はメタ情報標準に従います。

## 5. 本文要件

見出し順・表・記入欄の骨組みは Frontmatter で宣言した template を正本とし、本書では各章が満たす意味要件を定めます。

| 要件               | 必須条件                 | 記載する判断・根拠                                                             |
| ------------------ | ------------------------ | ------------------------------------------------------------------------------ |
| 適用する品質の選定 | 必須                     | 価値品質と成果物品質、適用開始・終了、人間と AI Agent の判断境界               |
| 合否判定の成立     | 必須                     | ゲートごとの品質観点、条件 ID、確認方法と証跡、時期、確認・承認責任            |
| レビューの完了判定 | 必須                     | 対象、主要観点、実施責任、合否を判定できる出口条件、証跡、記録先               |
| 不適合からの復帰   | 必須                     | 区分ごとの対応、再判定条件、再判定責任、記録先、重大不適合の通過制限           |
| 計画の維持         | 必須                     | 見直し契機、影響する正本・後続作業、追従更新の責任                             |
| 未決の扱い         | 未決事項がある場合に必須 | 未決論点、決定時期、判断者、決定まで保留する判定。なければ「なし」と明記できる |

## 6. 記述ガイド

共通のメタ情報・役割・値・構文は上位標準と schema を参照し、ここでは品質計画固有の判断基準と部分例を示します。責任を表す項目は、組織・ロール定義で採用された Role code を用い、RACI がある場合は該当する作業・判断の責任と整合させます。実行主体や兼務はメンバー定義へ委譲します。以下の Role code は例であり、未採用ロールの追加を要求しません。

### 6.1. 品質方針と適用範囲

- 判断基準は、利用者価値とそれを支える成果物品質、対象範囲・期間、判断主体を識別できることです。成功基準を根拠とし、技術検証だけで価値を判定しません。
- 適用開始・終了は日付または識別可能なイベントで示します。公開後の観測を含む場合は終了までの関係を示し、未確定の終了日は終了条件と見直し契機で代替できます。
- AI Agent が支援する確認作業と、人間が担う価値・例外・公開可否の最終判断を明記します。上位計画へ委譲する場合も、該当する判断と参照先を特定します。
- 良い例: 「代表試行開始から公開後価値ゲートの判定完了まで適用する。利用継続と負担を価値品質、再現性を成果物品質として確認する。AI Agent は検証記録を整理し、人間の `PO` が利用価値と公開可否を判断する」。
- 悪い例: 「開発中の品質を高め、AI Agent が問題なしと判定する」。期間の境界と人間の判断責任を確認できません。

### 6.2. 品質ゲート

- 判断基準は、各ゲートから条件の正本、確認方法、証跡、時期、確認者と承認者を辿り、合否または保留を決められることです。初期受入と公開後の継続判断は適用時点を分けます。
- 合格条件は文書 ID と条件 ID で参照します。数値を使う場合、算出方法・閾値・計測頻度を正本の該当箇所から確認できるようにします。未定義なら担当と決定期限を未決事項に置き、判定前に解消します。
- 確認者は証跡に基づく品質確認、承認者は当該判断の承認を担います。品質確認と公開可否を分け、RACI の異なる判断を一つの承認責任で代替しません。
- 費用・負荷を扱う場合は、現金支出、作業時間、継続運用負荷を別の基準・記録で確認します。
- 良い例: 「初期受入は成功基準の SC-01・AC-01 に基づき試行終了時に判定する。`QE` が試行記録を確認し、人間の `PO` が受入を判断する。未達または証跡不足なら保留する」。数値や検証コマンドは正本に残します。
- 悪い例: 「lint が通れば公開し、利用者の評価は後で確認する」。価値の合否と公開判断の根拠が欠けています。

### 6.3. レビューと証跡

- 判断基準は、対象版について誰が何を確認し、どの状態なら通過でき、どこに結果が残るかを再現できることです。レビュー種別は対象と対応が異なるものに絞ります。
- 列名は「対象」「実施責任」に統一します。「出口条件」は合否を分ける状態、「証跡」は判定を裏付ける記録、「記録先」はその記録へ到達する文書 ID またはパスです。三者を独立した列で必須とし、証跡名だけで出口条件を代替しません。
- 証跡には対象版、実施日、結果、未達条件・指摘と是正・再判定結果を追跡できる情報を残します。生成物の是正は生成元の正本を修正し、再生成して確認します。
- 良い例: 「公開対象の差分を `QE` が確認する。出口条件は公開に関する重大指摘が未解消で残っていないこと、証跡は対象版と指摘別結果を持つ公開前レビュー記録、記録先は `execution/reviews/release-1/result.md` とする」。パスは例示であり、実際の保存先を指定します。
- 悪い例: 「実施者: 関係者、出口条件・証跡: レビュー結果」。責任、通過条件、記録先を特定できません。

### 6.4. 不適合と是正

- 判断基準は、不適合から是正、再判定、結果記録までを追跡できることです。軽微、価値、構造・検証、公開など対応差がある区分だけを置きます。
- 「再判定条件」と「再判定責任」を独立した列に分けます。前者は是正後に再確認する条件 ID・ゲートと確認を再開する契機、後者は再確認を担う Role code です。公開・例外の承認が別に必要なら、その判断責任も区別します。
- 重大な不適合は課題または変更要求として登録し、是正完了または承認済み基準が認める期限付き例外の判断まで該当ゲートを通過させません。例外には理由、期限、人間の承認者、再判定条件を記録します。
- 記録先はレビュー記録・検証結果・登録簿の文書 ID またはパスで特定し、目的・スコープ・成功基準に影響する是正は変更要求と決定記録へ接続します。
- 良い例: 「技術不適合は生成元を修正する。再判定条件は再生成後に未達の AC-02 と影響範囲の検証が成功すること、再判定責任は `QE` とし、対象版・結果を課題個票から辿れる検証記録に残す」。
- 悪い例: 「対応: 修正、再判定: `QE`、記録先: 課題」。条件・確認契機と到達先が不明です。

### 6.5. 見直し条件と未決事項

- 判断基準は、計画を見直す契機と追従責任が明確で、未決事項を確定済みとして合格扱いしないことです。成功基準、公開範囲、成果物構造、検証方法、体制、重大不適合の傾向の変化を確認します。
- 未決事項は `_UNDECIDED_:` とし、決定時期、判断者、未決の間は保留するゲートを添えます。他の正本で管理する論点は該当記録を参照し、品質課題の個票は登録簿やレビュー記録へ委譲します。
- 計画の改訂・置き換え・廃止はメタ情報標準の「文書の改訂・廃止とライフサイクル変更管理」に従います。`PM` または兼務する採用ロールが管理計画・RACI・Schedule・証跡参照の追従先と担当 Role code・期限を整理し、`QE` または品質確認を担う採用ロールが判定条件への影響を確認します。
- 良い例: 「`_UNDECIDED_:` 試行記録の形式は試行開始前に `QE` が提案し、人間の `PO` が決定する。未決の間は代表試行ゲートを保留する。決定で確認工数が変われば `PM` が Schedule を更新する」。
- 悪い例: 「手順は後で決め、変更時は見直す」。期限、判断者、ゲートと後続作業への影響を確認できません。

## 7. 禁止事項

| 禁止事項                                                   | 理由                               |
| ---------------------------------------------------------- | ---------------------------------- |
| 成功基準、rulebook、schema、検証手順の詳細を本文へ複製する | 判定条件の正本が分散するため       |
| 品質目標、メトリクス、検査基準へ同じ条件を重複記載する     | 更新量と不整合が増えるため         |
| 技術検証だけで利用者価値の品質を代替する                   | プロジェクト成功を判定できないため |
| 現金支出だけを確認し、人の負荷を除外する                   | 負荷転嫁を見逃すため               |
| 生成物を直接修正して不適合を解消する                       | 再生成時に修正が失われるため       |
| 証跡名や Role code だけで出口条件・再判定条件を代替する    | 合否と責任を別々に確認できないため |
| AI Agent に価値、例外、公開可否の最終判断を委ねる          | 人間の判断責任を代替するため       |
