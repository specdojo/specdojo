# プロジェクト管理計画 作成ルール

Project Management Plan Documentation Rulebook

プロジェクトの価値、スコープ、成功基準を、実行時の管理・判断・証跡へ接続するためのルールです。個別計画や管理台帳の内容を再掲せず、横断的な管理方針だけを定義します。

## 1. 全体方針

- 管理対象ごとに、期待価値・リスク、逸脱の基準、対応、責任、証跡を結び付けます。
- プロジェクト概要、スコープ、成功基準を直接の根拠とし、期待価値の検証を管理目的にします。
- 個別計画や管理台帳の詳細は各正本へ委譲します。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。文書の整形・lint はリポジトリの検証で扱い、業務の受入確認に含めません。

## 2. 位置づけ

- 本計画は横断的な管理基準と判断の接続を担い、個別計画・管理記録の更新先を示します。
- 小規模では統合表と判断ゲートによる軽量プロファイルを基本とし、契約・監査・組織規模に応じて個別計画を追加する拡張プロファイルを選びます。

## 3. ファイル命名・ID規則

- 配置は `docs/ja/projects/<project-id>/030-project-management/pm-plan.md` を推奨します。
- ID は `<project-id>:pm-plan`、ファイル名は `pm-plan.md` とします。
- 共通の命名規則は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従います。

## 4. 推奨 Frontmatter 項目

- 共通項目・型・許容値はメタ情報標準と成果物 schema に従います。`rulebook` は本書の ID、種別は本書の `deliverable_type` に合わせます。
- `based_on` は必須とし、概要・スコープ・成功基準と、組織定義など直接根拠にした先行成果物の ID を記載します。
- カタログ利用時は参照先を `depends_on` の推移閉包に含め、不足する依存関係の整備を先行作業にします。根拠宣言の省略や閉包外の ID 追加で代替しません。

## 5. 本文要件

見出し順・表・記入欄の骨組みは Frontmatter で宣言した template を正本とします。本書は次の意味要件を定めます。

| 要件               | 必須条件                 | 記載する判断・根拠                                                                                                           |
| ------------------ | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| 管理範囲の選定     | 必須                     | 期待価値、対象期間、適用プロファイルと拡張条件                                                                               |
| 管理対象単位の追跡 | 必須                     | 価値・リスクまたは条件 ID と、基準・上限、確認契機、逸脱時対応、責任、証跡の正本を対応付ける                                 |
| 判断の成立条件     | 必須                     | 継続・公開・変更・停止などの条件、判断材料、起案者、最終判断者、証跡。未達・材料不足時の扱いを含む                           |
| 更新・報告の接続   | 必須                     | 情報ごとの正本、報告契機、確認者、見直しトリガーと追従先。個別計画や台帳へ委譲する責務を識別する                             |
| 未決の扱い         | 未決事項がある場合に必須 | 論点・現状、当面の扱い、決定によって変わる管理行・ゲート。別の正本にある論点は参照し、未決事項がなければ「なし」と明記できる |

## 6. 記述ガイド

### 6.1. 管理目的と適用方針

- 判断基準は、管理範囲と期間を価値・スコープ・成功基準へ結び付け、管理の厚さを選んだ理由を説明できることです。
- 良い例: 「初期公開から2週間で SC-01 の価値を検証する。軽量運用とし、外部契約が生じた場合は個別計画を追加する」。
- 悪い例: 「一般的な PM 項目をすべて管理する」。価値、期間、範囲の選定理由が不明です。

### 6.2. 統合管理方針

- 判断基準は、各行から根拠・判定条件・逸脱対応・責任・証跡を一続きで追跡できることです。標準列は次のとおりとし、行の結合 ID から一意に辿れる場合は列を統合できます。文書全体への参照だけで済ませません。

| 列         | 内容                                          |
| ---------- | --------------------------------------------- |
| 管理対象   | 追跡単位                                      |
| 根拠       | 価値・リスクの文書 ID と該当箇所または条件 ID |
| 基準・上限 | 適合・逸脱の判定条件                          |
| 確認契機   | 観測時点                                      |
| 逸脱時対応 | 次の行動                                      |
| 責任       | 担当 Role code                                |
| 証跡・正本 | 記録先と記録の識別方法                        |

- スコープ、Schedule、費用・負荷、品質、課題・リスク・変更から適用対象を選びます。現金支出、準備・開発の作業時間、日常操作・保守の継続運用負荷は別の行または基準・記録で管理し、負荷転嫁を削減とみなしません。
- 構成管理は対象版・承認済み基準・変更履歴の識別方法、確認者、記録先を示します。技術管理は技術制約・外部依存の変更検知契機、影響確認・判断を担う Role code、記録先を示します。個別方針へ委譲しても行から確認・対応を追跡できるようにします。
- 良い例: 「継続運用負荷」の根拠を成功基準文書の SC-03、基準を同条件の上限内、確認契機を試行中の営業日、超過時対応を `PM` による手順縮小案の起案、証跡を SC-03・確認日・確認者で識別する操作時間記録とします。数値・測定手順の正本は成功基準に残します。
- 悪い例: 「参加者の時間を無理のない範囲にし、必要に応じて確認する」。準備時間と日常負荷が混ざり、根拠、判定条件、証跡を照合できません。

### 6.3. 判断ゲートとエスカレーション

- 判断基準は、条件 ID、材料、最終判断者、判定記録が結び付き、未達と材料不足を合格扱いにしないことです。
- 成功基準・受入条件を複製せず、文書 ID と条件 ID を参照します。是正・再判定、保留・停止、例外判断を求める条件を定め、例外は上位の受入方針で認める範囲に限ります。
- 良い例: 「初期受入は成功基準の SC-01 と AC-01〜AC-04 を必須とし、未達・証跡不足なら保留する。是正後に `QE` が再確認結果を整理し、判断ゲートの最終判断者が条件 ID ごとの結果と判定を記録する」。
- 悪い例: 「初期成功基準を満たしたら公開し、問題があれば必要に応じて相談する」。参照条件、不足時の処理、判断者を特定できません。

### 6.4. 正本・報告・見直し

- 判断基準は、情報ごとの更新先と確認者が一意に分かり、見直し時の追従作業をタスク化できることです。正本が未整備なら、整備時期・担当または省略理由と責任を確認する代替先を示します。
- Schedule と責任の正本を接続し、作業担当だけで判断責任を代替しません。RACI の採用・省略条件は [[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] に従います。
- 判断・逸脱・作業節目の報告契機と確認者を定め、品質・コミュニケーションの詳細は各計画を参照します。
- 目的、スコープ、成功基準、体制、外部条件の変更時は、影響する個別計画・RACI・Schedule・証跡と担当 Role code を特定し、更新順序・期限・確認担当を追従タスクにします。
- 良い例: 「承認担当の交代時は、`PM` が RACI・メンバー定義・Schedule の影響箇所を特定し、更新担当と期限を設定する。`QE` が判断ゲートの最終判断者との整合を確認する」。
- 悪い例: 「担当は Schedule を参照し、変更時は関係文書を見直す」。成果物責任の正本、更新先、確認担当が不明です。

### 6.5. 未決事項

- 判断基準は、未決の論点と影響を示し、未決の上限や担当を確定済みとして着手・判定しないことです。他文書に正本があれば該当論点を参照します。
- 良い例: 「`_UNDECIDED_:` 試行準備の作業時間上限。未決中は着手を保留し、決定後に費用・負荷の管理行と準備着手ゲートへ反映する」。
- 悪い例: 「費用・時間上限は後で決める」。当面の扱いと変更先が不明です。

## 7. 禁止事項

| 禁止事項                                               | 理由                         |
| ------------------------------------------------------ | ---------------------------- |
| 管理対象を網羅目的で増やし、基準や逸脱時対応を置かない | 実行時の判断に使えないため   |
| 現金支出だけを費用とし、人の作業・運用負荷を除外する   | 負荷転嫁を見逃すため         |
| 成功基準を本文へ複製する                               | 判定条件の正本が分散するため |
