# プロジェクト管理計画 作成ルール

Project Management Plan Documentation Rulebook

プロジェクトの価値、スコープ、成功基準を、実行時の管理・判断・証跡へ接続するためのルールです。個別計画や管理台帳の内容を再掲せず、横断的な管理方針だけを定義します。

## 1. 全体方針

- 管理計画は、何を管理し、どの逸脱を、誰が、どの証跡で判断するかを示します。
- プロジェクト概要、スコープ、成功基準を直接の根拠とし、作業完了ではなく期待価値の検証を管理目的にします。これらの先行成果物を成果物カタログの依存関係に含め、Schedule・scaffold に展開できる状態にします。
- 小規模プロジェクトでは一つの統合表を基本とし、規模・契約・監査要件がある場合だけ個別計画へ展開します。
- 品質、コミュニケーション、組織、RACI、Schedule、登録簿は各正本へ委譲し、本書に一覧や詳細手順を複製しません。
- 現金支出、人の作業時間、継続運用負荷を区別し、人への負荷転嫁をコスト削減とみなしません。
- AI Agent は整理・更新・検証を支援できますが、優先順位、例外、公開、GO / Not GO の最終判断は人間が担います。

## 2. 位置づけ

- 本計画は横断的な管理基準と判断の接続を担い、個別計画・管理記録の更新先を示します。
- Role、Member、Task owner、RACI の共通定義は [[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] を正本とし、プロジェクト固有の採用判断は組織定義に従います。
- 必要最小限の統合表と判断ゲートで管理する方式を軽量プロファイル、契約・監査・組織規模に応じて個別計画や詳細手順を追加する方式を拡張プロファイルとします。

## 3. ファイル命名・ID規則

- 配置は `docs/ja/projects/<project-id>/030-project-management/pm-plan.md` を推奨します。
- ID は `<project-id>:pm-plan`、ファイル名は `pm-plan.md` とします。
- 共通の命名規則は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]]、Role code などの識別規則は人と組織の定義標準と各 YAML の schema を参照します。

## 4. 推奨 Frontmatter 項目

- 共通項目・型・許容値は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と同標準から参照する成果物 schema に従います。`rulebook` には本書の ID を指定し、種別は本書の `deliverable_type` に合わせます。
- 本系統では `based_on` を必須とし、概要、スコープ、成功基準の文書 ID を含めます。組織定義など、管理方針の直接根拠として使った先行成果物も記載します。本文のリンクだけで根拠宣言を代替しません。
- カタログを利用する場合、`based_on` の参照先は `depends_on` の推移閉包に含めます。閉包外なら依存関係の整備を先行作業とし、根拠参照を省略したり閉包外の ID を追加したりして適合扱いにしません。
- 置き換え時の `supersedes` と状態変更はメタ情報標準に従います。

## 5. 本文要件

見出し順・表・記入欄の骨組みは Frontmatter で宣言した template を正本とします。本書は次の意味要件を定めます。

| 要件               | 必須条件                 | 記載する判断・根拠                                                                                                                 |
| ------------------ | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| 管理範囲の選定     | 必須                     | 期待価値、対象期間、適用プロファイルと拡張条件、人間と AI Agent の判断・実行境界                                                   |
| 管理対象単位の追跡 | 必須                     | 価値・リスクまたは条件 ID と、基準・上限、確認契機、逸脱時対応、責任、証跡の正本を対応付ける                                       |
| 判断の成立条件     | 必須                     | 継続・公開・変更・停止などの条件、判断材料、起案者、人間の最終判断者、証跡。未達・材料不足時の扱いを含む                           |
| 更新・報告の接続   | 必須                     | 情報ごとの正本、報告契機、確認者、見直しトリガーと追従先。個別計画や台帳へ委譲する責務を識別する                                   |
| 未決の扱い         | 未決事項がある場合に必須 | 未決の状態、決定時期、判断者。別の正本で追跡する場合は対象の論点・記録を参照し、決定情報を複製しない。なければ「なし」と明記できる |

## 6. 記述ガイド

共通のメタ情報、役割、値・構文は上位標準と schema を参照し、ここでは計画固有の判断基準と部分例を示します。

### 6.1. 管理目的と適用方針

- 判断基準は、管理範囲と期間を価値・スコープ・成功基準へ結び付け、管理の厚さを選んだ理由を説明できることです。
- 軽量・拡張の選択と拡張条件、人間と AI Agent の判断・実行境界を簡潔に示します。
- 良い例: 「初期公開から2週間の試行で SC-01 の価値を検証する。軽量運用とし、外部契約が生じた場合は個別計画を追加する。Agent は整理・検証を支援し、公開は人間の `PO` が判断する」。
- 悪い例: 「一般的な PM 項目をすべて管理し、完了したら Agent が公開する」。価値、期間、管理範囲の選定理由、人間の判断境界が分かりません。

### 6.2. 統合管理方針

- 判断基準は、各行から「守る価値・回避するリスク → 基準・上限 → 確認・逸脱対応 → 責任 → 証跡」を一続きで追跡し、適合・逸脱を判定できることです。
- 表の列の意味は、管理対象が追跡単位、根拠が価値・リスクの文書 ID と該当箇所または条件 ID、基準・上限が判定条件、確認契機が観測時点、逸脱時対応が次の行動、責任が担当 Role code、証跡・正本が記録先と確認する記録の識別方法です。これらを各行で保持するか、行の結合 ID から一意に辿れるようにし、文書全体への参照だけで済ませません。
- スコープ、Schedule、費用・負荷、品質、課題・リスク・変更について適用を判断し、実際に管理する対象だけを行にします。費用・負荷は現金支出、準備・開発などの作業時間、日常操作・保守などの継続運用負荷を別の行または別の基準・記録で管理し、一方の削減を他方の削減とみなしません。
- 構成管理は、管理対象の版・承認済み基準・変更履歴を何で識別するか、変更時に誰が確認し、どこへ記録するかを示します。技術管理は、技術制約・外部依存の変更を検知する契機、影響確認と判断を担う Role code、記録先を示します。個別方針へ委譲する場合も、この確認・対応と委譲先を行から追跡できるようにし、設計や操作手順の詳細を再掲しません。
- 良い例: 「継続運用負荷」の根拠を成功基準文書の SC-03、基準を同条件の上限内、確認契機を試行中の営業日、超過時対応を `PM` による手順縮小案の起案、証跡を SC-03・確認日・確認者で識別する操作時間記録とします。数値・測定手順の正本は成功基準に残します。
- 悪い例: 「参加者の時間を無理のない範囲にし、必要に応じて確認する」。準備時間と日常負荷が混ざり、根拠、判定条件、証跡を照合できません。

### 6.3. 判断ゲートとエスカレーション

- 判断基準は、適用する条件 ID、材料、最終判断者、判定記録が結び付き、未達と材料不足を合格扱いにしないことです。公開、主要変更、例外、継続・停止など、人間の判断が必要なゲートを選びます。
- 成功基準・受入条件を複製せず、文書 ID と条件 ID を参照します。是正・再判定、保留・停止、例外判断を求める条件を定め、例外は上位の受入方針で認める範囲に限ります。
- 良い例: 「初期受入は成功基準の正本にある SC-01 と AC-01〜AC-04 を必須とし、未達または証跡不足なら保留する。`QE` が再確認結果を整理し、人間の `PO` が受入可否を判断して条件 ID ごとの結果とともに記録する」。
- 悪い例: 「初期成功基準を満たしたら公開し、問題があれば必要に応じて相談する」。参照条件、不足時の処理、判断者を特定できません。

### 6.4. 正本・報告・見直し

- 判断基準は、情報ごとの更新先と確認者が一意に分かり、見直し時の追従作業をタスク化できることです。正本が未整備なら、整備時期・担当または省略理由と責任を確認する代替先を示します。
- Schedule は作業順序・Task owner・進捗、RACI は成果物・主要判断の責任、ロール定義は責務、メンバー定義は実行主体を扱います。RACI を採用する体制では正本として明示し、Task owner だけで承認責任を代替しません。最小運用での RACI 省略条件は人と組織の定義標準に従います。
- 判断・逸脱・作業節目などの報告契機と確認者を定め、品質・コミュニケーションの詳細は各計画を参照します。課題・リスク・変更要求・決定は PJR または対応する管理簿へ分け、本文に個票を持ちません。
- 目的、スコープ、成功基準、体制、外部条件が変わった場合、管理担当が影響する個別計画・RACI・Schedule・証跡への参照と担当 Role code を特定し、更新順序・期限・確認担当を追従タスクにします。計画の置き換え・廃止はメタ情報標準の「文書の改訂・廃止とライフサイクル変更管理」に従います。
- 良い例: 「承認担当の交代時は、`PM` が RACI・メンバー定義・Schedule の影響箇所を特定し、更新担当と期限を設定する。`QE` が判断ゲートの最終判断者との整合を確認する」。
- 悪い例: 「担当は Schedule を参照し、変更時は関係文書を見直す」。成果物責任の正本、更新先、確認担当が不明です。

### 6.5. 未決事項

- 判断基準は、未決の論点、決定時期、判断者を追跡でき、未決の上限や担当を確定済みとして着手・判定しないことです。現状に `_UNDECIDED_:` を付けます。
- 既に他文書・管理簿で追跡している場合、本書では未決状態と参照先の論点・記録を示し、決定時期・判断者は参照先を正本にできます。期限を過ぎた事項は課題または判断事項として登録簿へ移し、担当 Role code と転送先を残します。
- 良い例: 「`_UNDECIDED_:` 試行準備の作業時間上限。試行着手前に人間の `PO` が決定し、未決の間は着手を保留する」。
- 悪い例: 「費用・時間上限は後で決める」。未決状態、期限、判断者、未決の間の扱いを確認できません。

## 7. 禁止事項

| 禁止事項                                               | 理由                             |
| ------------------------------------------------------ | -------------------------------- |
| 個別計画、RACI、Role code 一覧、登録簿の内容を再掲する | 正本が分散し、更新量が増えるため |
| 管理対象を網羅目的で増やし、基準や逸脱時対応を置かない | 実行時の判断に使えないため       |
| 現金支出だけを費用とし、人の作業・運用負荷を除外する   | 負荷転嫁を見逃すため             |
| 成功基準を本文へ複製する                               | 判定条件の正本が分散するため     |
| Agent に例外、公開、GO / Not GO の最終判断を委ねる     | 人間の説明責任を代替するため     |
| 個人情報、認証情報、秘密情報、実装詳細を記載する       | 公開適性と文書責務に反するため   |
