# トレーサビリティ（要求→仕様）作成ルール

Requirements Traceability (Requirements to Specs) Rulebook

仕様成果物の型付き ID 参照から要求と仕様の対応を派生ビューとして示し、要求漏れ・仕様漏れを見つける形式を定めます。

## 1. 全体方針

- **対象**: 要求と仕様の対応の可視化を扱い、要求・仕様の本文は扱いません。
- **正本と派生**: 対応の正本は仕様成果物の `relations.satisfies` とし、本ビューは派生ビューとして生成します。「目的と適用範囲」と「トレース対象の前提」は生成の条件として書き、「トレースマトリクス」「充足状況サマリ」「ギャップと対応方針」は生成元から導出します。
- **記載レベル**: 1 行は 1 つの要求 ID とその対応仕様 ID 群とします。
- **任意の管理ビュー**: 必要なプロジェクトだけが生成し、独自のドメインやトラックを持ちません。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。文書の整形・lint はリポジトリの検証で扱い、業務の受入確認に含めません。

## 2. 位置づけ

本ビューは、要求（業務の受入基準 `bac-*` など）と、それを充足する仕様（システム化機能 `sf-*`、業務仕様 `bes-*` など）の作成後に生成し、仕様のレビュー時と要求・仕様の変更時に再生成します。要求→テストの対応は [[specdojo:trc-requirements-to-tests-rulebook|トレーサビリティ（要求→テスト）作成ルール]] が扱います。

## 3. ファイル命名・ID規則

- **ファイル名**: `trc-requirements-to-specs.md` とします。分割する場合は `trc-requirements-to-specs-<term>.md` とします。
- **文書 ID**: 成果物カタログの宣言と一致させます。プロダクト仕様のカタログに置く場合は `trc-requirements-to-specs`、プロジェクト固有の場合は `<project-id>:trc-requirements-to-specs` とします（分割時は末尾に `-<term>`）。

## 4. 推奨 Frontmatter 項目

許可キーと型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- `specdojo.rulebook` は `specdojo:trc-requirements-to-specs-rulebook` とします。
- `specdojo.based_on` には、生成元とした要求・仕様の文書 ID を記載します。

## 5. 本文要件

| 章                   | 必須     | 内容・受入条件                                                                                             |
| -------------------- | -------- | ---------------------------------------------------------------------------------------------------------- |
| 目的と適用範囲       | 必須     | 対象の要求群・仕様群と対象外（理由付き）が分かること                                                       |
| トレース対象の前提   | 必須     | 要求の母集団、仕様の抽出範囲、トレース単位（1:1 / 1:N / N:1）、生成の手段と生成日、生成元の版が分かること  |
| トレースマトリクス   | 必須     | 標準6列で母集団の全要求を並べ、どの要求にも対応しない仕様を別の表で示すこと                                |
| 充足状況サマリ       | 必須     | 充足状況ごとの件数（合計が母集団の件数と一致）、要求に対応しない仕様の件数、優先して解消する要求 ID と理由 |
| ギャップと対応方針   | 必須     | ギャップごとに、直す生成元の成果物と解消の判定条件が分かること                                             |
| 変更履歴と更新ルール | 条件付き | 再生成の契機や前回からの差分を残す必要があるときに置き、生成日と差分の要点を示す                           |

### 5.1. 生成の手順

生成コマンドはないため、次の手順で生成し、手作業で生成したことを「トレース対象の前提」に書きます。

1. 母集団を決める: 対象の要求 ID をすべて列挙する。
2. 仕様を抽出する: 抽出範囲の仕様文書（`sf-*`・`bes-*` など）をすべて列挙し、各文書の `relations.satisfies` と `status` を読む。
3. 対応づける: 母集団の要求ごとに、その要求 ID を `relations.satisfies` に持つ仕様を対応仕様とする。
4. 照合する: `relations.satisfies` が空か、母集団の要求 ID を 1 つも持たない仕様を記録する。
5. 標準列と「充足状況の判定」に従って表を作り、サマリの件数を表から数えて合計を母集団の件数と照合する。

### 5.2. トレースマトリクスの標準列

| 列名       | 内容・判断条件                                                                        |
| ---------- | ------------------------------------------------------------------------------------- |
| 要求ID     | 追跡対象の要求 ID                                                                     |
| 要求要約   | 要求の要点を 1 行で示す                                                               |
| 対応仕様ID | その要求 ID を `relations.satisfies` に持つ仕様 ID（複数可、なければ空とせず `なし`） |
| 充足状況   | `未着手` / `一部充足` / `充足`。判定は「充足状況の判定」に従う                        |
| ギャップ   | 未対応点・不整合・未決事項。なければ `なし`                                           |
| 備考       | 判定の根拠（参照先の `status`、review result など）                                   |

手順 4 で記録した仕様は、マトリクスの後に「仕様ID / `relations.satisfies` の宣言 / ギャップ」の表で示します。この表の行は充足状況を持たず、サマリの充足状況ごとの件数に含めません。

### 5.3. 充足状況の判定

| 充足状況   | 条件                                                          |
| ---------- | ------------------------------------------------------------- |
| `未着手`   | その要求 ID を `relations.satisfies` に持つ仕様がない         |
| `一部充足` | 対応仕様はあるが、いずれかが `draft` であるか、ギャップが残る |
| `充足`     | 対応仕様がすべて `ready` であり、ギャップが `なし`            |

## 6. 記述ガイド

完成例は Frontmatter の `sample` で宣言された sample を参照してください。

### 6.1. 目的と適用範囲

- **判断基準**: どのレビュー・変更判断に使い、どのリリースや領域の要求を対象とするかが分かること。
- **良い例**: 「第 1 リリースの会計・在庫・値引き・監査の要求と、それを充足する仕様の対応を示し、仕様レビューで要求漏れを見つける。次期リリースの要求は対象外とする。」
- **悪い例**: 「要求と仕様の対応を管理する。」（対象範囲と使う場面が分からない）

### 6.2. トレース対象の前提

- **判断基準**: 別の人が同じ前提で「生成の手順」をたどり、同じ表を得られること。
- **良い例**: 「母集団: `bac-sales` の要求（4 件）。仕様: 販売領域の `sf-*`・`bes-*`。生成: 「生成の手順」による手作業で 2026-05-01 に生成、生成元は `main` の `a1b2c3d`。」
- **悪い例**: 「最新の仕様から作成した。」（母集団と抽出範囲・手段が分からず、検証できない）

### 6.3. トレースマトリクスと充足状況サマリ

- **判断基準**: 各行の充足状況が「充足状況の判定」の条件から説明でき、サマリの件数が表と一致すること。優先する要求 ID には、業務上の影響など判断の理由を添えること。
- **良い例**: 「req-r1-002 ／ 在庫引当をリアルタイムで更新する ／ bes-stock-allocation, ifx-msg-stock ／ 一部充足 ／ 障害時の再送仕様が未確定 ／ `ifx-msg-stock` が `draft`」
- **悪い例**: 「req-r1-002 ／ … ／ ほぼ対応 ／ ― ／ ―」（曖昧語で判定できず、根拠がない）

### 6.4. ギャップと対応方針

- **判断基準**: 解消は本ビューでなく生成元の成果物で行うこととし、どの成果物をどう直せば解消と判定するかが分かること。担当・期限は登録簿で追跡し、本ビューに列を設けません。
- **良い例**: 「req-r1-004 ／ 監査ログの保持先が未決定 ／ `bes-audit-log` に保持方針を追記し `relations.satisfies` に req-r1-004 を持たせる ／ 再生成で `充足` になる」
- **悪い例**: 「監査ログは今後対応する。」（直す成果物も判定条件もない）

### 6.5. 変更履歴と更新ルール

- **判断基準**: 再生成の契機（要求・仕様の追加、ID 参照の変更、仕様の `status` 変更）と、前回から充足状況が変わった要求 ID が分かること。

## 7. 禁止事項

| 禁止パターン                                                             | 理由                                               |
| ------------------------------------------------------------------------ | -------------------------------------------------- |
| 生成した表を手編集し、`relations.satisfies` と異なる対応や充足状況を書く | 正本と派生ビューが食い違い、再生成で消えるため     |
| 要求本文・仕様本文の全文転記                                             | 正本との二重管理になり、更新時に不整合が出るため   |
| 要求 ID または対応仕様 ID の空欄                                         | 未対応なのか記入漏れなのか判別できないため         |
| 充足状況に曖昧語（ほぼ対応、だいたい完了など）を使う                     | 「充足状況の判定」の条件で確かめられないため       |
| 対応仕様 ID が `なし` の行でギャップを `なし` とする                     | 要求漏れが表から隠れるため                         |
| 「トレース対象の前提」に母集団と生成手段を書かずに表を示す               | 再生成して照合できず、表が正しいか検証できないため |
