# 影響調査（テスト）作成ルール

Impact Analysis (Test) Rulebook

変更要求によるテストへの影響を整理し、変更要否・影響度・対応方針・未解決事項を判断する記述基準を定めます。この判断を省くと、回帰漏れによる欠陥流出や、受入直前のテスト追加による納期遅延を招くため、着手前に影響範囲と対応の合意を残します。

## 1. 全体方針

- 影響詳細はテスト対象単位とし、その単位は「影響詳細一覧」の行の単位に従う。仕様・I/F・運用への波及は概要と判断だけを示し、詳細は各影響調査へ委ねる。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱う。

## 2. 位置づけ

- 入力: プロジェクト登録簿の変更要求（`item_type: change-request` の個票。[[specdojo:pjr-rulebook|プロジェクト登録簿 作成ルール]]）。起票済みの要求・課題から派生した変更要求を含む。
- 判断対象: テスト観点・条件・ケース・判定基準への影響と、その対応方針。個別テスト手順の詳細設計は扱わない。
- 反映先: 判断結果は [[specdojo:tsp-index-rulebook|テスト戦略・方針 作成ルール]] に従うテスト戦略・方針と、各テストレベルのテストカタログ（`<level>c-index`）へ反映する。
- 並行する文書: 業務・データ・I/F・運用への影響は、それぞれ `imp-business`・`imp-data`・`imp-interface`・`imp-operations` で判断し、本書は互いの結論を参照する。

## 3. ファイル命名・ID規則

- 文書 ID は `<project-id>:imp-test`、推奨ファイル名は `imp-test.md` とする。
- 命名の共通規則は [[specdojo:id-and-file-naming-standard|ID・ファイル命名標準]] に従う。
- 追補文書は `<project-id>:imp-test-<term>` とする。

## 4. 推奨 Frontmatter 項目

共通項目・必須性・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。`type` は `project`、`rulebook` は `specdojo:imp-test-rulebook` とし、`based_on` に入力の変更要求を記載する。

## 5. 本文要件

本文は次の6章をこの順で置き、すべて必須とする。

| 章  | 見出し         | 目的                                                 |
| --- | -------------- | ---------------------------------------------------- |
| 1   | 目的と適用範囲 | 判断対象、対象・対象外のテスト範囲、対象期間を示す   |
| 2   | 変更要求の概要 | 変更の背景・狙い・要求の要点と成功条件を示す         |
| 3   | 影響分析サマリ | 影響度の尺度・集約規則と、影響度別の件数・優先対応   |
| 4   | 影響詳細一覧   | 影響対象テストごとの変更要否・影響度・根拠を記録する |
| 5   | 対応方針       | 対応項目ごとの期限・担当・前提条件を示す             |
| 6   | 未解決事項     | 判断待ち・調査不足と、その決定期限・担当を示す       |

表を置く章は、次の列を必須とする。列名はこのとおりに揃え、別名（例: 「優先度」「実施時期」）を使わない。

| 章             | 必須の列                                                                         |
| -------------- | -------------------------------------------------------------------------------- |
| 影響分析サマリ | 影響度、件数、主な影響対象テスト、優先対応（`要` / `否`）                        |
| 影響詳細一覧   | 影響対象テスト、変更要否、影響度、対応方針、判断根拠、備考                       |
| 対応方針       | 影響度、対応項目、期限、担当、前提条件                                           |
| 未解決事項     | 論点、不足情報、判断・対応への影響、当面の扱い、決定期限、担当、転記先の登録項目 |

## 6. 記述ガイド

各章の判断の基準と、良い例・悪い例を示す。完成例は Frontmatter の `sample` で宣言された sample を参照する。

### 6.1. 目的と適用範囲

- 対象変更要求の ID、対象テスト範囲、対象外のテスト範囲とその理由、対象期間を記載する。対象期間は変更をテストで確認する期間（着手日から受入判定日まで）とする。
- どの利用場面で何を判断するための文書かを 2〜4 行で示す。

| 観点     | 良い例                                                             | 悪い例               |
| -------- | ------------------------------------------------------------------ | -------------------- |
| 対象外   | 「性能テストは対象外。処理件数が変わらないため `imp-data` で確認」 | 対象外を書かない     |
| 対象期間 | 「2026-05-07〜2026-05-28（受入判定日）」                           | 「次回リリースまで」 |

### 6.2. 変更要求の概要

- 背景・狙いと要求の要点を示す。成功条件は指標と閾値、または達成状態に加え、確認対象・判定方法を記載する。

| 観点     | 良い例                                                                          | 悪い例                         |
| -------- | ------------------------------------------------------------------------------- | ------------------------------ |
| 成功条件 | 「重点回帰 20 ケースと追加結合 8 ケースが全件合格（テスト結果レポートで判定）」 | 「品質を落とさずリリースする」 |

### 6.3. 影響分析サマリ

- 欠陥流出リスク・回帰範囲・実行コスト・納期など、採用する評価観点ごとに高・中・低を分ける条件（数値の境界または状態）を表の前に定義する。
- 複数観点で判定が分かれる場合の集約規則（例: 最も高い影響度を採用）を定め、同じ規則で件数を集計する。
- 同じ影響度で優先順位を分ける場合は理由を添える。

| 観点 | 良い例                                                      | 悪い例                     |
| ---- | ----------------------------------------------------------- | -------------------------- |
| 尺度 | 「欠陥流出リスク: 高＝売上金額の誤りが本番で検出されうる」  | 高・中・低を定義せずに使う |
| 集約 | 「観点別の最大値を影響度とする。高 2 件、中 1 件、低 1 件」 | 観点ごとの件数を合算する   |

### 6.4. 影響詳細一覧

- 1 行はテストレベルとテスト観点の組とする。同じ観点に属する条件・ケース・判定基準への影響は、その行の判断根拠と備考に書く。
- 判断根拠には、変更要否の理由と、評価観点ごとの事実に尺度・集約規則を当てはめた結果を書く。
- 対応方針は `実施` / `代替` / `見送り` のいずれかとし、備考に制約・前提・関連文書を書く。

| 観点     | 良い例                                                                                           | 悪い例               |
| -------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| 行の単位 | 「結合テスト／値引き適用後の売上集計」                                                           | 「結合テスト」       |
| 判断根拠 | 「欠陥流出リスク: 高（集計差異が本番で出る）、回帰範囲: 中、実行コスト: 低。最大値規則により高」 | 「影響あり。要対応」 |

### 6.5. 対応方針

- 影響度の高い順に、対応項目ごとの期限、担当、前提条件を記載する。担当は Role code で書く。
- 見送り・代替は、再評価条件と再評価の期限を必ず記載する。
- 受入確認では「変更要求の概要」の成功条件に判定方法を適用し、全条件の達成を合格とする。未達は影響詳細一覧と対応方針へ戻す。

| 観点   | 良い例                                                                     | 悪い例                         |
| ------ | -------------------------------------------------------------------------- | ------------------------------ |
| 担当   | `QE`                                                                       | 個人名、連絡先、「テスト管理」 |
| 見送り | 「単体テスト追加は見送り。分岐が 3 件を超えたら再評価（期限 2026-07-31）」 | 「当面見送り」                 |

### 6.6. 未解決事項

- 論点ごとに不足情報、判断・対応への影響、当面の扱い、決定期限、担当（Role code）を記載する。該当がなければ「なし」とする。
- 次の条件に当てはまる事項はプロジェクト登録簿へ転記し、転記先の登録項目 ID（`PJR-XXXX`）を記載する。

| 条件                                               | 転記先の `item_type` |
| -------------------------------------------------- | -------------------- |
| 決定期限までに判断できず、確認や調査が必要な事項   | `question`           |
| 対応が遅れると受入判定や納期に影響するおそれがある | `risk`               |
| すでに計画や受入判定に支障が出ている               | `issue`              |
| 見送り・代替を決めた                               | `decision`           |

| 観点               | 良い例                                                                     | 悪い例                         |
| ------------------ | -------------------------------------------------------------------------- | ------------------------------ |
| 判断・対応への影響 | 「確定しないと重点回帰ケースを決められず、回帰テストの期限に間に合わない」 | 影響を書かず処理方針だけを書く |

## 7. 禁止事項

- 「影響あり」「要対応」のみで根拠を記載しない。
- 影響度の尺度を定義せずに高・中・低を使わない。
- 本文要件と異なる列名で同じ項目を書かない（例: 「影響度」の代わりに「優先度」）。
- 担当に個人名や連絡先を書かない。Role code で記載する。
