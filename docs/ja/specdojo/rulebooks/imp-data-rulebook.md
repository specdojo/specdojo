# 影響調査（データ）作成ルール

Impact Analysis (Data) Rulebook

変更要求によるデータへの影響を整理し、変更要否・影響度・対応方針・未解決事項を判断する記述基準を定めます。この判断を省くと、移行後のデータ欠損・集計の不整合や、移行直前の手順追加による停止時間の超過を招くため、着手前に影響範囲と対応の合意を残します。

## 1. 全体方針

- 本書は、変更の着手前に、どのデータをどの程度変えるか、移行・補正をどう進めるかを判断するための文書とする。
- 影響詳細はデータ対象（エンティティ・項目・格納先）単位とし、実装設計の詳細化は扱わない。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱う。

## 2. 位置づけ

- 入力: プロジェクト登録簿の変更要求（`item_type: change-request` の個票）と、その業務影響を判断した `imp-business`。
- 判断対象: データ構造・整合性・移行への影響と、その対応方針。
- 反映先: I/F・テスト・運用への波及の詳細は I/F 仕様（`ifx-*`）、テスト仕様（`itc-*` 等）、運用設計（`opd-*`）へ委ね、「影響詳細一覧」の備考に適用先カタログの成果物 ID を示す。

## 3. ファイル命名・ID規則

- 文書 ID は `<project-id>:imp-data`、推奨ファイル名は `imp-data.md` とする。
- 追補文書は `<project-id>:imp-data-<term>` とし、共通規則は [[specdojo:id-and-file-naming-standard|ID・ファイル命名標準]] に従う。

## 4. 推奨 Frontmatter 項目

共通項目・必須性・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。`type` は `project`、`rulebook` は `specdojo:imp-data-rulebook` とする。`based_on` には作成済みの `<project-id>:imp-business` と、入力の変更要求の個票 ID（`PJR-XXXX`）を記載する。

## 5. 本文要件

本文は次の6章をこの順で置き、すべて必須とする。

| 章  | 見出し         | 目的                                                   |
| --- | -------------- | ------------------------------------------------------ |
| 1   | 目的と適用範囲 | 変更要求、対象・対象外のデータ領域、対象期間を示す     |
| 2   | 変更要求の概要 | 背景・要求・狙いと、判定可能な成功条件を示す           |
| 3   | 影響分析サマリ | 影響度の尺度・案件の境界値と、影響度別の件数・優先対応 |
| 4   | 影響詳細一覧   | データ対象ごとの変更要否・影響度・根拠を記録する       |
| 5   | 対応方針       | 対応項目ごとの期限・担当・前提条件と受入確認を示す     |
| 6   | 未解決事項     | 判断待ち・調査不足と、その決定期限・担当・転記先を示す |

表を置く章は、次の列を必須とする。列名はこのとおりに揃える。

| 章             | 必須の列                                                                         |
| -------------- | -------------------------------------------------------------------------------- |
| 影響分析サマリ | 影響度、件数、主な影響対象データ、優先対応（`要` / `否`）                        |
| 影響詳細一覧   | 影響対象データ、変更要否、影響度、対応方針、判断根拠、備考                       |
| 対応方針       | 影響度、対応項目、期限、担当、前提条件                                           |
| 未解決事項     | 論点、不足情報、判断・対応への影響、当面の扱い、決定期限、担当、転記先の登録項目 |

## 6. 記述ガイド

各章の判断の基準と、良い例・悪い例を示す。完成例は Frontmatter の `sample` で宣言された sample を参照する。

### 6.1. 目的と適用範囲

- 変更要求の ID、対象データ領域、対象外の領域とその理由、対象期間（着手日から移行後の確認完了日まで）を記載する。

| 観点     | 良い例                                                         | 悪い例               |
| -------- | -------------------------------------------------------------- | -------------------- |
| 対象外   | 「顧客データは対象外。今回の変更で項目・件数が変わらないため」 | 対象外を書かない     |
| 対象期間 | 「2026-05-01〜2026-07-31（移行後の月次監査完了日）」           | 「次回リリースまで」 |

### 6.2. 変更要求の概要

- 背景・要求・狙いを要約し、成功条件は確認対象・指標・閾値（または達成状態）・判定方法で書く。

| 観点     | 良い例                                                        | 悪い例                     |
| -------- | ------------------------------------------------------------- | -------------------------- |
| 成功条件 | 「移行前後の日次売上合計の差額 0 円（締め処理の帳票で照合）」 | 「データ品質を向上させる」 |

### 6.3. 影響分析サマリ

- 整合性・可用性・移行難易度・利用者影響の4観点で評価し、観点別の最も高い判定を影響度とする。件数も同じ規則で集計する。
- 許容停止時間など案件の境界値を表の前に示してから、次の尺度を当てはめる。
  - 高: 補正しても解消できない、または業務判断を誤らせる欠損・不整合、許容時間を超える停止、復旧不能な移行、代替不能な業務停止のいずれかがある。
  - 中: 高に該当せず、補正で解消できる不整合、移行手順、または利用者の操作変更が必要。
  - 低: 高・中に該当せず、現行データと操作で継続できる。

| 観点   | 良い例                              | 悪い例                         |
| ------ | ----------------------------------- | ------------------------------ |
| 境界値 | 「許容停止時間: 閉店後 2 時間以内」 | 境界値を示さずに高・中を使う   |
| 観点   | 本文要件の4観点で評価する           | 「運用負荷」など別の観点を使う |

### 6.4. 影響詳細一覧

- 判断根拠には、構造・整合性、データ検証・移行テスト、実装変更への影響を必ず書く。影響がない観点も理由を残す。
- 対応方針は `実施` / `代替` / `見送り` のいずれかとし、備考に制約・前提と波及先の成果物 ID を書く。

| 観点     | 良い例                                                                                                    | 悪い例               |
| -------- | --------------------------------------------------------------------------------------------------------- | -------------------- |
| 判断根拠 | 「構造: 値引き理由コード列を追加。移行テスト: 既存3か月分の補正結果を照合。実装: 締め処理の集計式を変更」 | 「影響あり。要対応」 |
| 備考     | 「波及先: `itc-sales-closing`」                                                                           | 「関連資料参照」     |

### 6.5. 対応方針

- 影響度の高い順に、対応項目ごとの期限、担当（Role code）、前提条件を記載する。見送り・代替は再評価条件と期限を付す。
- 受入確認として、業務影響の各対象が「影響詳細一覧」に欠落なく対応し、データ検証・移行テストの確認手順と合格条件（「変更要求の概要」の成功条件）が特定できることを示す。

| 観点   | 良い例                                                                           | 悪い例         |
| ------ | -------------------------------------------------------------------------------- | -------------- |
| 担当   | `DEV`                                                                            | 個人名、連絡先 |
| 見送り | 「価格履歴の構造変更は見送り。差異が月 3 件を超えたら再評価（期限 2026-07-31）」 | 「当面見送り」 |

### 6.6. 未解決事項

- 論点ごとに不足情報、判断・対応への影響、当面の扱い、決定期限、担当（Role code）を記載する。該当がなければ「なし」とする。
- 次の条件に当てはまる事項はプロジェクト登録簿へ転記し、転記先の登録項目 ID（`PJR-XXXX`）を記載する。

| 条件                                                     | 転記先の `item_type` |
| -------------------------------------------------------- | -------------------- |
| 決定期限までに判断できず、確認や調査が必要な事項         | `question`           |
| 対応が遅れると移行・受入判定・納期に影響するおそれがある | `risk`               |
| すでに計画や移行に支障が出ている                         | `issue`              |
| 見送り・代替を決めた                                     | `decision`           |

## 7. 禁止事項

- 実装詳細（SQL 全文、クラス名、API リクエスト構造）を記載しない。
- 「影響あり」「要対応」だけで判定を済ませない。
- 「影響分析サマリ」の尺度・観点と異なる判定を混在させない。
- 本文要件と異なる列名で同じ項目を書かない（例: 「影響度」の代わりに「優先度」）。
- 担当に個人名や連絡先を書かない。Role code で記載する。
