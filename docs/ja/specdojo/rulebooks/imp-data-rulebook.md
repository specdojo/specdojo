# 影響調査（データ）作成ルール

Impact Analysis (Data) Rulebook

変更要求によるデータへの影響を整理し、変更要否・影響度・対応方針を判断する基準を定めます。

## 1. 全体方針

- データ責任者とプロジェクト管理者が合意できる粒度で、影響と判断根拠を記載する。
- 複数領域を扱う場合も影響詳細はデータ対象単位とし、実装設計の詳細化は扱わない。
- **共通の運用**: 役割は適用先のメンバー定義、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱う。

## 2. 位置づけ

業務影響をデータ構造・整合性・移行への影響に具体化する。波及先の詳細は I/F 仕様（`ifx-*`）、テスト仕様（`itc-*` 等）、運用設計（`opd-*`）へ委ね、「備考」に適用先カタログの対応する成果物 ID を示す。

## 3. ファイル命名・ID規則

- `local_id` は `imp-data`、Frontmatter の `id` は `<project-id>:imp-data`、推奨ファイル名は `imp-data.md` とする。
- 追補は `<project-id>:imp-data-<term>` とし、共通規則は [[specdojo:id-and-file-naming-standard|ID・ファイル命名標準]] に従う。

## 4. 推奨 Frontmatter 項目

共通項目・必須性・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。`type` は `project`、`rulebook` は `specdojo:imp-data-rulebook` とする。`based_on` には直接の根拠とした作成済みの `<project-id>:imp-business` を必須とし、追加の根拠もカタログの `depends_on` の推移閉包内に限る。

## 5. 本文構成（標準テンプレ）

本文は次の6章を標準とする。

| 章  | 見出し         | 必須 | 目的                 |
| --- | -------------- | ---- | -------------------- |
| 1   | 目的と適用範囲 | ○    | 対象と判断範囲       |
| 2   | 変更要求の概要 | ○    | 背景・要求・成功条件 |
| 3   | 影響分析サマリ | ○    | 尺度・件数・優先対象 |
| 4   | 影響詳細一覧   | ○    | 対象別の判定と根拠   |
| 5   | 対応方針       | ○    | 実施条件と受入確認   |
| 6   | 未解決事項     | ○    | 論点と影響           |

## 6. 記述ガイド

### 6.1. 目的と適用範囲

変更要求の識別子、対象データ領域、対象期間、判断目的を示す。

### 6.2. 変更要求の概要

背景・要求・狙いと判定可能な成功条件を要約する（例: 移行前後の売上合計の差額0円）。

### 6.3. 影響分析サマリ

整合性・可用性・移行難易度・利用者影響を次の尺度で評価し、最も高い判定を採る。許容停止時間など案件の境界値を先に示し、高・中・低の件数と優先対象をまとめる。

- 高: データ欠損・不整合、許容時間を超える停止、復旧不能な移行、代替不能な業務停止のいずれかがある。
- 中: 高に該当せず、補正・移行手順または利用者の操作変更が必要。
- 低: 高・中に該当せず、現行データと操作で継続可能。

### 6.4. 影響詳細一覧

次の6列を必須とする。

| カラム         | 内容                         |
| -------------- | ---------------------------- |
| 影響対象データ | エンティティ、項目、格納先   |
| 変更要否       | `要` / `否`                  |
| 影響度         | `高` / `中` / `低`           |
| 対応方針       | 実施・代替・見送りなどの方針 |
| 判断根拠       | 判定理由の要点               |
| 備考           | 制約、前提、関連ドキュメント |

「判断根拠」に構造・整合性、データ検証・移行テスト、実装変更への影響を必ず示す。影響なしも理由を残す。

### 6.5. 対応方針

- 影響度順に実施時期・担当・前提条件を示す。見送りは再評価条件と時期を付す。
- 受入確認では業務影響の各対象を「影響詳細一覧」と照合し、欠落がなく、各判定の根拠・対応と、データ検証・移行テストの確認手順・合格条件が特定できることを確認する。

### 6.6. 未解決事項

論点・不足情報・判断や対応への影響・当面の扱いを示す。なければ「なし」とする。

## 7. 禁止事項

- 実装詳細（SQL 全文、クラス名、API リクエスト構造）を記載しない。
- 「影響あり」「要対応」だけで判定を済ませない。
- 「影響分析サマリ」の尺度と異なる判定を混在させない。
