# 進捗報告 作成ルール

Progress Report Documentation Rulebook

報告期間ごとの完了・進行中の作業、リスク・課題、次期予定を、定期レビューで比べられる形で記録する進捗報告の記述基準を定めます。

## 1. 全体方針

- 進捗報告は、定期レビューで計画どおりか、対応が要るリスク・課題は何か、次期に何をいつまでに行うかを判断するための文書とする。
- 1 つのプロジェクトの 1 報告期間を 1 ファイルとし、期間は前回報告の翌日から始めて抜けと重なりを作らない。日次の細かな更新は報告せず、期間内の結果としてまとめる。
- 報告は記録の正本ではなく要約とする。リスク・課題・変更要求・判断待ちの正本は登録簿の個票（登録簿を使わない場合は各ログ）とし、報告からは ID で参照する。
- **共通の運用**: Frontmatter の項目（`specdojo.type` は `project`）、`status` の昇格と承認、改訂と廃止は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。役割は適用先のメンバー定義の Role code で書く。

## 2. 位置づけ

- 報告周期と提出期限は適用先のコミュニケーション計画に従う。定めがない場合は週次とし、期間の終了から 2 営業日以内に `ready` にする。
- 報告と登録簿の個票が食い違う場合は個票を正とする。報告の数値・状態を個票に合わせて直し、個票側は書き換えない。
- `ready` にした報告を訂正するときは、改訂の扱いを共通標準に従い、訂正の理由と参照し直した個票 ID を報告の該当章に書く。
- 配置は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] の `reporting/progress-reports/` とする。

## 3. ファイル命名・ID規則

- ファイル名は `pr-<yyyy-mm-dd>-<nn>.md` とする。日付は報告期間の終了日（ISO 形式）、`<nn>` は同日内の連番（2 桁ゼロ埋め）。
- 文書 ID はファイル名から拡張子を除いた部分を project で修飾し、`<project-id>:pr-<yyyy-mm-dd>-<nn>` とする（例: `prj-0001:pr-2026-04-19-01`）。

## 4. 本文要件

template を持たないため、次の 5 章をこの順にすべて置く。該当がない章は削らず `なし` と書く。

| 番号 | 見出し       | 必須 | 内容（要点）                                                     |
| ---- | ------------ | ---- | ---------------------------------------------------------------- |
| 1    | 報告期間     | ○    | 開始日と終了日（ISO 形式）                                       |
| 2    | 完了事項     | ○    | 期間内に完了した作業と、完了を確かめられる ID                    |
| 3    | 進行中事項   | ○    | 未完了の作業、進み具合の根拠、遅れの有無                         |
| 4    | リスク・課題 | ○    | 区分・内容・影響度・対応方針と、正本の個票 ID                    |
| 5    | 次期予定     | ○    | 次の期間に行う作業・担当・期日。判断を求める事項は個票 ID で示す |

## 5. 記述ガイド

### 5.1. 報告期間

- `2026-04-13 から 2026-04-19` のように開始日と終了日を書き、前回の終了日の翌日から始める。

### 5.2. 完了事項・進行中事項

- 表の列は `No.`・`内容`・`根拠 ID` とする。根拠 ID は project 修飾の文書 ID、登録簿の `PJR-XXXX`、schedule のタスク ID のいずれかで書き、独自の連番は使わない。
- 進行中事項の進み具合は、完了した節・件数など確かめられる量で書く。割合だけを書かない。
  - 良い例: `レジ締め手順の改訂案を作成中（全 5 節のうち 3 節を作成済み）。`
  - 悪い例: `レジ締め手順の改訂案を作成中（進捗60%）。`

### 5.3. リスク・課題

- 表の列は `区分`・`内容`・`影響度`・`対応方針`・`個票 ID` とする。区分は `リスク`（未顕在）・`課題`（顕在化済み）・`変更要求` のいずれかとする。
- 影響度は `高`（期日か範囲を守れない）・`中`（期日内に回復できるが対応が要る）・`低`（監視のみ）で判定する。
- 報告で新たに見つけた事項は、報告を書く前に登録簿へ起票し（`item_type` は `risk`・`issue`・`change-request`）、その ID を書く。
  - 良い例: `リスク | 欠品データの入力遅延 | 中 | 入力締切を16:00に統一する | PJR-AB12`
  - 悪い例: `リスク | 色々と遅れそう | - | 注意する | -`

### 5.4. 次期予定

- 表の列は `No.`・`内容`・`担当`・`期日` とする。担当は Role code で書き、個人名は書かない。
- 判断を求める事項（計画の変更、リスクへの対応の採否など）は、登録簿の `question` または `decision` の個票を起こして ID を予定の内容に書く。判断の結果は個票で追い、報告には書き写さない。
  - 良い例: `補充責任者の決定を求める（PJR-CD34） | PM | 2026-04-21`
  - 悪い例: `補充責任者を決める | 店主 | 来週`

## 6. 禁止事項

- 進み具合を割合だけで報告すること。
- 区分・影響度・対応方針・個票 ID のないリスク・課題、抽象語だけのリスク。
- 担当か期日のない次期予定を含めたまま `ready` にすること。
- 個人名・顧客情報・認証情報を書くこと。
- 個票と食い違う状態を報告に残すこと。
