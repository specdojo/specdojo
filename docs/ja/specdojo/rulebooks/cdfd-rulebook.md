# 概念データフロー図 作成ルール

Conceptual Data Flow Diagram Documentation Rulebook

業務または運用のプロセス領域と、領域をまたいで受け渡される情報・イベント・現物を、表と Mermaid 図で合意可能にするためのルールです。全体概要と領域別 CDFD の責務を分け、後続成果物が起点イベント、入出力、データストアを引き継げる粒度を定めます。

## 1. 全体方針

- CDFD は、対象者が業務の境界と情報の受け渡しを確認するための概念仕様です。実装方式や操作手順ではなく、業務上の目的、起点、入出力、正本となるデータストアを記述します。
- 全体概要ではプロセス領域どうしの関係と分割境界を示し、領域別 CDFD では一つの領域内の主要プロセスと例外を詳細化します。全体概要に領域別の手順を複製しません。
- 表を用語と責務境界の正本、図を流れの正本として併用します。プロセス名、イベント名、入出力名、データストア名は表と図で一致させます。
- 現行業務と将来業務を混在させません。両方が必要な場合はファイルを分け、タイトルと適用範囲で AS-IS / TO-BE を識別します。
- 人間の判断、利用者との合意、外部主体との受け渡しを省略しません。AI Agent やシステムは支援主体として記載できても、人間が負う最終判断を置き換えません。

## 2. 位置づけと用語定義

| 用語         | 定義                                                                                   |
| ------------ | -------------------------------------------------------------------------------------- |
| プロセス領域 | 同じ業務目的と責務境界を持ち、領域別 CDFD へ分割できるプロセスのまとまり               |
| プロセス     | 入力を受け、業務上意味のある出力または状態変化を生む処理単位                           |
| 起点イベント | プロセスまたはプロセス領域を開始させる、時点を識別できる出来事                         |
| データストア | 台帳、文書、ファイル、データベースなど、情報の正本または継続的な保管先                 |
| 外部主体     | 対象範囲の外から情報・現物を渡す、または結果を受け取る人、組織、外部システム           |
| 情報の流れ   | 依頼、判断、定義、記録、報告などの受け渡し。Mermaid ではラベル付きの `-->` で表す      |
| 物の流れ     | 商品、現金、帳票原本など現物の受け渡し。必要な場合だけラベル付きの `==>` で表す        |
| 補助操作     | 一覧、検索、状態参照、検証、dry-run など、独自の業務成果を作らず他プロセスを支える操作 |

## 3. ファイル命名・ID規則

- 配置は、対象プロダクトの業務仕様配下にあるデータフローディレクトリを基本とします。プロジェクト固有の現状分析として管理する場合は、プロジェクト文書配下へ配置できます。
- 全体概要のファイル名は `cdfd-overview.md`、ID は `<authority>:cdfd-overview` を基本とします。
- 領域別のファイル名は `cdfd-<domain>.md`、ID は `<authority>:cdfd-<domain>` とし、`<domain>` は英小文字・数字・ハイフンで業務領域を表します。
- 表と図でプロセスを対応付ける必要がある場合は、文書内で一意な `P-01` 形式の領域 ID またはプロセス ID を付けます。採番は意味を持たせず、名称変更後も同じ対象なら維持します。

## 4. 推奨 Frontmatter 項目

| 項目       | 説明                                                  | 必須 |
| ---------- | ----------------------------------------------------- | ---- |
| id         | `<authority>:cdfd-overview` または領域別 CDFD の ID   | ○    |
| type       | `flow`                                                | ○    |
| status     | `draft` / `ready` / `deprecated`                      | ○    |
| rulebook   | `specdojo:cdfd-rulebook`                              | ○    |
| based_on   | 目的、範囲、業務要求など、作成時に直接参照した文書 ID | 任意 |
| supersedes | 置き換える旧 CDFD の ID                               | 任意 |

- `based_on` は直接の内容根拠だけを列挙し、図中のすべての要素へ個別の根拠リンクを複製しません。
- 文書のタイトルと AS-IS / TO-BE の区分は本文 H1 と「目的と適用範囲」で示します。
- `status` の昇格は定められた承認者が行い、作成途中は `draft` とします。

## 5. 本文構成（標準テンプレ）

| 番号 | 見出し           | 必須 | 内容                                                                          |
| ---- | ---------------- | ---- | ----------------------------------------------------------------------------- |
| 1    | 目的と適用範囲   | ○    | 対象者、利用場面、対象範囲、対象外、AS-IS / TO-BE                             |
| 2    | プロセス領域一覧 | ○    | 領域 ID、目的、担当、起点イベント、主要入力、主要出力、データストア、詳細化先 |
| 3    | 概念データフロー | ○    | 一覧と同じ名称を使った Mermaid 図、凡例、図で省略した流れ                     |
| 4    | 境界と分割方針   | ○    | 補助操作の扱い、領域間の責務、領域別 CDFD との一対一対応、重複・欠落の判定    |
| 5    | 未決事項         | 任意 | 未決論点、影響、決定者、決定時期                                              |

## 6. 記述ガイド

### 6.1. 目的と適用範囲

- 誰が、どの合意または後続作業に使うかを 1〜3 文で示します。
- 対象とする業務、期間、組織、システム境界、AS-IS / TO-BE を明示します。
- 対象外は単なる省略ではなく、別成果物へ委譲する詳細、補助操作、外部責務を区別して記述します。

### 6.2. プロセス領域一覧

全体概要では次の列を使用します。領域別 CDFD では「プロセス領域」を「プロセス」に読み替え、詳細化先の列を省略できます。

<!-- prettier-ignore -->
| 列 | 記載内容 | 判定基準 |
| --- | --- | --- |
| 領域 ID | `P-01` 形式の安定した識別子 | 表、図、分割対応表で同じ ID を使う |
| プロセス領域 | 業務目的が分かる短い名称 | 手段名やコマンド名だけにしない |
| 業務目的 | 対象者に生じる成果または維持する状態 | 手順の列挙にしない |
| 主な担当 | 主担当となるロールまたは外部主体 | 個人名にしない |
| 起点イベント | 開始を判断できる出来事 | 「必要に応じて」で終わらせない |
| 主要入力 | 判断・処理に必要な情報または現物の概念名 | 物理カラムやオプションを列挙しない |
| 主要出力 | 次の領域または利用者へ渡す成果・状態の概念名 | 入力と区別できる名称にする |
| データストア | 読み書きする正本または保管先 | 媒体より論理的なまとまりを優先する |
| 領域別 CDFD | 詳細化を一意に引き継ぐ ID または仮置き名 | 一つの領域を複数行へ重複させない |

### 6.3. 概念データフロー

- Mermaid のノードとエッジは、Frontmatter の `includes` で指定した記法ルールに従います。
- プロセス領域、起点イベント、主要なデータストア、必要な外部主体を配置し、すべての情報・現物のエッジへ内容を表すラベルを付けます。
- 表にある全領域を図へ一度以上登場させます。読みやすさのために入出力を省略する場合は、図の直後に対象と理由を記述します。
- 現物を扱わない CDFD では物の流れを無理に追加せず、「本図は情報の流れだけを扱う」と凡例または補足で明示します。

### 6.4. 境界と分割方針

- 独立した領域にする条件は、固有の起点イベントと業務成果を持ち、主要な入出力またはデータストアを他領域と区別できることです。
- 補助操作は、それ自体が固有の業務成果を持たない限り独立領域にせず、支援する領域の入力確認、参照、検証として扱います。
- 全体概要の各領域を領域別 CDFD へ一対一で割り当てます。複数領域が同じ詳細化先を共有する場合は、統合理由と責務境界を明示します。
- 領域別 CDFD は、全体概要で定義した起点イベント、主要入出力、データストアを引き継ぎ、変更する場合は全体概要も更新します。

### 6.5. 完成判定

- 表の各領域について、図中のプロセス、起点イベント、主要入力、主要出力、データストアを追跡できます。
- 図中の各プロセスは表の一行へ対応し、対応先のないプロセスや重複する領域 ID がありません。
- 対象範囲と補助操作の境界を業務判断者が説明でき、領域別 CDFD の作成者が詳細化の入力として利用できます。
- 未決事項がある場合は _UNDECIDED_: として影響、決定者、決定時期を記載し、確定情報と混在させません。

## 7. 禁止事項

- 物理テーブル名、物理カラム名、SQL 全文、実装クラス名、関数名、詳細な API、コマンドオプションを概念フローへ記載しません。
- UI 操作や CLI 操作を一手順ずつ並べ、業務上の入力・出力・判断を埋没させません。
- ラベルのない情報・現物のエッジ、表と図で名称が異なる同一要素、起点または到達先のないエッジを残しません。
- 一覧、検索、状態参照、検証、dry-run などの補助操作を、固有の業務成果がないまま独立したプロセス領域にしません。
- 全体概要に領域別の例外分岐や実装エビデンスを丸写ししません。
- 色、線種、ノード形状を独自に増やし、同じ記号へ複数の意味を持たせません。
