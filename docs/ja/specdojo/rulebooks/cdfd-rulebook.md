# 概念データフロー図（プロセスグループ別）作成ルール

Conceptual Data Flow Diagram Process Group Documentation Rulebook

全体概要の一つのプロセスグループについて、全領域の内部プロセス、領域間の受け渡し、主要例外、グループ外委譲を、表と概念データフロー図（Mermaid または D2）で合意するためのルールです。

## 1. 全体方針

- 一文書で一つのプロセスグループに属する全領域を詳細化し、各領域をちょうど一文書に所属させます。単一領域のグループも同じ構成とします。
- プロセスの業務目的・担当・起動条件・完了条件・必須性は「プロセス領域」、受け渡しは図、プロセス単位の入出力は「個別プロセス主要入出力」を正本とします。
- 一ノードは一つの業務目的と完了条件を持つ処理とします。一操作ごとの機械的な分割や、複数の判断・更新・生成の詰め込みを避けます。
- 同一グループ内の領域間は内部フローとして描き、他グループの内部処理と横断順序は対応する CDFD へ委譲します。
- 状態を変えるプロセスと起点イベントだけを示し、状態名・成立条件・遷移元・遷移先・イベント・遷移条件は STSD を正本とします。
- 業務結果を変える主要例外を扱い、ログや内部エラーの全列挙は行いません。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。整形・lint はリポジトリの検証で扱い、業務の受入確認に含めません。

## 2. 位置づけと用語定義

全体概要は領域・グループの分割とグループ・データストア間の受け渡し、本書は一グループの内部、ユースケース別 CDFD は複数グループを横断する順序と引き渡し条件を定義します。

| 用語             | 区別する意味                                                            |
| ---------------- | ----------------------------------------------------------------------- |
| プロセスグループ | 業務の性質が近い領域の集合。一文書の単位                                |
| プロセス領域     | 全体概要で ID・名称・業務目的・担当・起点イベントを定めた責務のまとまり |
| プロセス         | 起動条件と入力を受け、一つの業務上の出力または状態変化を生む処理単位    |

## 3. ファイル命名・ID規則

- 対象プロダクトの業務仕様のデータフローディレクトリに `cdfd-<group>.md` を置きます。`<group>` は全体概要のグループ名を表す英小文字・数字・ハイフンのスラッグです。
- product 成果物 ID は修飾なしの `cdfd-<group>`（例: `cdfd-sales`）とします。全体概要の `cdfd-overview` とユースケース別の `cdfd-uc-<topic>` は対象外です。
- プロセス ID は領域 ID `P-<nn>` に二桁の枝番を付けた `P-<nn>-<nn>`（例: `P-03-02`）とし、文書内一意の `P-01` 形式は使いません。
- 例外 ID は `E-<nn>-<nn>` とし、複数領域にまたがる場合は最初に検出する領域の番号を使います。
- 同じプロセス・例外の ID は名称変更後も維持し、表・図で一致させます。

## 4. 推奨 Frontmatter 項目

共通の必須項目・許可キー・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` に従います。

- `id` は「ファイル命名・ID規則」、`type` は `flow`、`rulebook` は `specdojo:cdfd-rulebook` とします。
- `based_on` は、全体概要など実際に直接の根拠とした文書の ID とし、成果物カタログの `depends_on` の推移閉包内に限ります。product 文書は参照先も修飾なしの ID を使います。
- タイトルと利用目的は H1 と「目的」に記載します。

## 5. 本文要件

章の順序・骨組みは Frontmatter で宣言した template を使い、各章を次の条件で受け入れます。

| 見出し                       | 必須 | 内容                                                                        |
| ---------------------------- | ---- | --------------------------------------------------------------------------- |
| 目的                         | ○    | 対象者と利用場面を 1〜2 文で示す                                            |
| 適用範囲                     | ○    | 対象と対象外を各 1 行で示す                                                 |
| プロセス領域                 | ○    | 領域ごとにプロセス表だけを置く                                              |
| データストア                 | ○    | 全体概要の部分集合を同名・同区分で示し、読み書きを区別する                  |
| 概念データフロー             | ○    | 一ノード一プロセスの図と、1〜2 文の説明・注記                               |
| 個別プロセス主要入出力       | ○    | 図の分割単位に対応するプロセス単位の入出力表                                |
| 状態遷移の参照               | ○    | 状態を変えるプロセスと STSD の対応。該当なしでも事実と確認根拠を記載        |
| 主要例外とグループ外への委譲 | ○    | 検出・停止範囲・扱い・再開と委譲境界。各区分が 0 件でも事実と確認根拠を記載 |
| 未決事項                     | 任意 | 未決論点と影響する領域・プロセス・例外・委譲                                |

## 6. 記述ガイド

### 6.1. 目的と適用範囲

- 目的は、誰が内部フロー・領域間の受け渡し・主要例外・委譲を合意または設計入力に使うかを示します。
- 適用範囲の対象はグループ・期間・組織・システム境界・開始と終了、対象外は他グループの責務・横断ユースケース・詳細化先を示します。
- 人間と AI Agent の責任分担などの共通原則は全体概要またはプロジェクト方針を参照します。

### 6.2. プロセス領域

- 冒頭でグループ名・領域数・全体概要との正本関係を示します。所属する全領域の ID・名称を引き継ぎ、追加・削除・移動はしません。
- 領域ごとに「領域名（領域 ID）」の節を設け、プロセス表だけを置きます。領域の業務目的・担当・起点イベントは全体概要から書き写しません。
- 各領域に一つ以上のプロセスを置き、一行を一ノードに対応させます。

| 列          | 記載内容と判定基準                                                         |
| ----------- | -------------------------------------------------------------------------- |
| プロセス ID | 所属領域の枝番。表と図で一致                                               |
| プロセス    | 一つの業務目的が分かる短い名称。複数処理や操作列を詰め込まない             |
| 業務目的    | 対象者に生じる成果または維持する状態。手順・遷移の列挙にしない             |
| 主な担当    | 主担当ロールまたは外部主体。個人名を使わず、人間の最終判断を明示           |
| 起動条件    | 判定可能なイベント・前段完了・承認条件。「必要に応じて」で終わらせない     |
| 完了条件    | 主要出力または正本の確定に対応し、yes / no で判定できる事実                |
| 必須性      | 必須／条件付き／選択。条件付き・選択は起動条件と非起動時の正常な扱いを示す |

### 6.3. データストア

- 全体概要の「マスタ・構成データ」「トランザクションデータ」と同じ区分に、本グループが読み書きする行だけを置きます。該当行がない区分は節ごと省略します。
- 列は「データストア」「読み書き」「本グループでの利用」。読み書きは「参照」「更新」「参照・更新」とし、現物の保管先は利用内容に現物の受け渡しを示します。
- 名称・区分は上位と一致させ、表の行と図のノードを一対一に対応させます。分割図で同じノードを再掲する場合も名称を保ちます。

### 6.4. 概念データフロー

- 全体概要の「凡例（本プロダクト共通）」で選ばれた [[specdojo:cdfd-mermaid-rulebook|Mermaid 記法ルール]] または [[specdojo:cdfd-d2-rulebook|D2 記法ルール]] を適用し、記法未宣言時は Mermaid とします。
- 「プロセス領域」の各行を個別ノードにし、全体概要の領域代表ノードを再掲しません。
- 領域間の受け渡しは双方のプロセスを同じ図または対応する分割図に置きます。他グループは委譲先代表ノードまたは起点・完了イベントだけを置きます。
- 領域ごと、または業務の性質が近いプロセスごとに分けます。条件付き・選択プロセスは、起動時と非起動でも正常完了する経路をたどれるようにします。
- 図直後の注記は、記法ルールの「凡例と可読性」に従い、凡例の適用元・使用線種・省略した入出力と理由・共有ノードを 1〜2 文で示します。色・絵文字の割り当ては再掲しません。

### 6.5. 個別プロセス主要入出力

- 図と同じ分割単位で節を設け、全プロセスをちょうど一度掲載します。一プロセスだけでも表を省略しません。
- 列は「プロセス ID」「プロセス」「主要入力」「主要出力」「データストア」。業務目的・担当・起動条件・必須性は重複させません。
- データストアの名称・区分は「データストア」と全体概要に一致させます。

### 6.6. 状態遷移の参照

列は「対象」「状態を変えるプロセス」「ステータス定義（STSD）」とします。該当プロセスがない場合は、事実と確認根拠を一文で記載して表を省略します。

### 6.7. 主要例外とグループ外への委譲

- 主要例外の列は「例外 ID」「対象プロセス」「検出条件」「停止範囲」「本グループでの扱い」「継続・再開条件」。停止範囲には起動・確定してはならない後続プロセス・出力・委譲を示します。
- 委譲の列は「委譲先」「委譲する事項」「引き渡す情報」「本グループへ戻す条件」。
- 各区分が 0 件でも節を残し、確認範囲と該当なしの結論を一文で記載して表を省略します。

### 6.8. 完成判定

「本文要件」と「記述ガイド」、選択した記法ルール、型固有の禁止事項を併用して全必須条件を照合します。確認者は次の順に表と図をたどり、条件ごとに pass / fail を判断します。条件付き要件が非該当なら、その根拠を確認します。必須条件に欠落・不一致があれば不合格です。

1. 目的・適用範囲を読み、全体概要の全所属領域が一節ずつあることを照合します。
2. 各プロセスの起動から主要出力・正本確定までを追い、完了条件と条件付き・選択の非起動時の正常完了を確認します。表・図・入出力表の ID・名称、入出力表への一度だけの掲載、データストアの名称・区分・読み書きを照合します。
3. 領域間の内部フローと図直後の注記を確認し、状態を変える全プロセスから STSD を特定します。
4. 各主要例外について検出から停止・対応・再開、各委譲について受け手・責務・情報・戻す条件を表の全列で確認します。0 件の区分も確認根拠を読みます。

## 7. 禁止事項

- プロセス領域に主要入力・主要出力・データストアの箇条書きを置く、図を文章でなぞる長文注記を書く。
- 詳細 CDFD に独自の凡例を再掲・重複定義する。
- 所属領域の一部を別文書に切り出す、一領域を複数文書に重複配置する。
- 物理テーブル・カラム・SQL・実装クラス・詳細 API を概念フローに書く。
- 状態名・意味を CDFD で定義する、遷移元・遷移先・条件の表や状態を頂点とする遷移図を複製する。
- 他グループの内部処理を展開する、内部の領域間受け渡しをグループ外委譲として扱う。
- 一覧・検索・状態参照・検証・dry-run など、独自の業務成果がない補助操作を独立プロセスにする。
- プロセス表・入出力表・図直後注記・例外表の間で同じ事実を重複記載する。
