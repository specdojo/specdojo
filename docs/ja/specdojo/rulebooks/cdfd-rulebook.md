# 概念データフロー図（プロセスグループ別）作成ルール

Conceptual Data Flow Diagram Process Group Documentation Rulebook

全体概要で定めた一つのプロセスグループを引き継ぎ、グループに属する全領域の内部プロセス、領域間の受け渡し、主要例外、グループ外への委譲を、表と Mermaid 図で合意可能にするためのルールです。状態を変えるプロセスと起動条件は示しますが、状態の定義と遷移は STSD を参照します。

## 1. 全体方針

<!-- specdojo:finding id=F003 severity=minor rule=vp-qe-verifiability line=11 一プロセス一完了条件を要求していますが、プロセス領域表または個別入出力表のどの項目で完了条件を記録し、どうpass/fail判定するかが定義されていないため, 記載先と判定条件を明示してください。 -->
<!-- specdojo:finding id=F011 severity=major rule=vp-ux-language-consistency line=9 `プロセスグループ` を本書では複数領域で構成されるものに固定していますが、上位rulebookは1領域グループも同じ用語で認めているため、包含数を「一つ以上のプロセス領域」に統一してください。 -->
- 一文書は、全体概要で定めた一つのプロセスグループと、そのグループに属する複数のプロセス領域を詳細化します。各領域はちょうど一つのプロセスグループ別 CDFD に属します。
- 「プロセス領域」を領域単位の主要入力・主要出力・データストアとプロセスの業務目的・起動条件・必須性の正本、「データストア」を本グループが読み書きする上位一覧の部分集合、「個別プロセス主要入出力」をプロセス単位の入出力の正本、図を順序と分岐の正本として併用します。
- 一つのプロセスノードは、一つの業務目的と完了条件を持つ処理だけを表します。コマンドや画面の一操作を無条件に一プロセスへ分割せず、複数の判断・更新・生成を一ノードに詰め込みません。
- 同一グループ内の領域間の受け渡しは内部フローとして図に描きます。他グループの内部処理は展開せず、プロセスグループ別 CDFD またはユースケース別 CDFD へ委譲します。
- 状態を変えるプロセスとその起点イベントは記載しますが、状態名・成立条件・遷移元・遷移先・イベント・遷移条件は STSD を正本とし、本書では参照関係だけを示します。
- 正常系だけでなく、業務結果を変える主要例外を、検出条件、扱い、継続・再開条件で定義します。ログや内部エラーの全列挙は行いません。
- 人間の判断、利用者との合意、外部主体との受け渡しを省略しません。AI Agent やシステムは支援主体として記載できても、人間が負う最終判断を置き換えません。

## 2. 位置づけと用語定義

| 用語                   | 定義                                                                                                         |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| 全体概要               | プロセス領域、プロセスグループ、データストア、グループ間の受け渡しを定める最上位 CDFD                        |
| プロセスグループ       | 業務の性質が近いプロセス領域をまとめた集合。本 rulebook が扱う一文書の単位                                   |
| プロセス領域           | 全体概要で ID、名称、業務目的、担当、起点イベントが定義され、一つのプロセスグループに属する責務のまとまり    |
| プロセス               | 起動条件と入力を受け、業務上意味のある出力または状態変化を一つ生む処理単位                                   |
| 起点イベント           | 対象領域または内部プロセスを開始させる、発生を判定できる出来事                                               |
| データストア           | 全体概要で名称と区分が定義された、情報の正本または継続的な保管先                                             |
| 主要例外               | 正常系と異なる業務判断、生成結果、引き渡し可否を生じさせ、再開条件の合意が必要な分岐                         |
| グループ外委譲         | 他グループの内部処理を作り込まず、委譲先 CDFD、引き渡す情報、戻す条件によって責任境界を示すこと              |
| 状態遷移の参照         | 状態を変えるプロセスから、状態一覧と状態遷移図を統合した STSD をたどる対応。状態名や遷移表そのものは含めない |
| 個別プロセス主要入出力 | プロセスごとの主要入力・主要出力・データストアを示す章。「プロセス領域」の表と項目を重複させない             |

全体概要は領域とグループの分割、およびグループとデータストアの間の受け渡しを定義します。プロセスグループ別 CDFD は一グループの内部を詳細化し、ユースケース別 CDFD は複数グループを横断する順序と引き渡し条件だけを定義します。

## 3. ファイル命名・ID規則

- 対象プロダクトの業務仕様配下にあるデータフローディレクトリへ配置します。
- ファイル名と成果物 ID は `cdfd-<group>` とし、ファイル名だけ `.md` を付けます。`<group>` は全体概要のプロセスグループ名を表す英小文字・数字・ハイフンのスラッグです。
- product 成果物の ID にプロジェクト ID や authority は付けません。例: ファイル名 `cdfd-sales.md`、ID `cdfd-sales`。
- `cdfd-overview` は全体概要、`cdfd-uc-<topic>` はユースケース別 CDFD の ID であり、本 rulebook の対象外です。
- プロセス ID は、全体概要の領域 ID `P-<nn>` に二桁の枝番を付けた `P-<nn>-<nn>` 形式とします。例: 領域 `P-03` の二番目のプロセスは `P-03-02`。文書内一意の `P-01` 形式は使用しません。
- 主要例外 ID は、対象領域の番号に二桁の枝番を付けた `E-<nn>-<nn>` 形式とします。複数領域にまたがる例外は、最初に検出するプロセスの領域番号を使います。
- プロセス ID と例外 ID は名称変更後も同じ対象を示す限り維持し、一覧、図、入出力表、例外表で同じ値を使います。

- 文書のタイトルと利用目的は本文 H1 と「目的」で示し、未定義の Frontmatter 項目を追加しません。
- `status` の昇格は定められた承認者が行い、作成途中は `draft` とします。

## 6. 記述ガイド

### 6.1. 目的と適用範囲

<!-- specdojo:finding id=F002 severity=minor rule=vp-arc-cross-document-consistency line=79 適用範囲で期間を必須としている一方、対応templateに期間の記入欄がなくsampleにも期間の記載がないため、期間を必須とするなら両成果物へ反映し、不要なら本規則とrecipeの問いから削除してください。 -->
<!-- specdojo:finding id=F009 severity=minor rule=vp-qe-kata-conformance line=79 rulebookとrecipeが適用期間の明記を求めていますが、templateの適用範囲に記入欄がなくsampleも完成例を示していないため、骨組みと完成例へ期間を反映してください。 -->
- 誰が、グループ内部のフロー、領域間の受け渡し、主要例外、グループ外への委譲のどれを合意または後続利用するかを示します。
- 対象グループと含む領域の範囲は全体概要から引き継ぎます。期間、組織、システム境界と、どのイベントからどの出力までを扱うかを明記します。
- 対象外は、補助操作、実装詳細、他グループの責務、ユースケース別 CDFD が扱う横断順序に分けます。委譲内容の詳細は「主要例外とグループ外への委譲」にだけ記載します。
- 人間と AI Agent の責任分担は本文で再定義せず、対応する方針文書を参照します。
- 特定プロジェクトの実行フェーズ名や一時的な仮称を持ち込まず、対象プロダクトの現在の正本として読める語彙を使います。

### 6.2. プロセス領域

- 章の冒頭で、対象グループ名、含む領域数、全体概要との正本関係を示します。全体概要の対象グループ名と、そこに属する全領域の ID・名称を引き継ぎ、領域を追加・削除・別グループへ移動しません。
- 領域ごとに節（`3.1.`、`3.2.`、…）を設け、見出しは「領域名（領域 ID）」とします。各節は、領域の役割と内部プロセスの連携を示す 1〜3 文の説明、`**主要入力**`・`**主要出力**`・`**データストア**` の箇条書き、プロセスの表の順で構成します。
- 領域 ID、名称、業務目的、主な担当、起点イベントは全体概要を正本とします。本章では領域 ID と名称を見出しの対応キーとして使い、業務目的・担当・起点イベントを書き写しません。
- 各節の主要入力・主要出力・データストアを合わせると、全体概要にあるグループ単位の箇条書きを過不足なく説明できるようにします。データストアは「データストア」と同じ名称を使います。
- 各節の表は一行を一つのプロセスノードへ対応させます。主要入力・主要出力・データストアは箇条書きと「個別プロセス主要入出力」へ記載し、表の列には含めません。

| 列          | 記載内容                                       | 判定基準                                                   |
| ----------- | ---------------------------------------------- | ---------------------------------------------------------- |
| プロセス ID | 対応領域 ID に枝番を付けた `P-<nn>-<nn>`       | プロセス領域のいずれかへ一意に属し、表と図で同じ ID を使う |
| プロセス    | 一つの業務目的が分かる短い名称                 | 複数プロセスや操作列を一行へ詰め込まない                   |
| 業務目的    | 対象者に生じる成果または維持する状態           | 手順や状態遷移の列挙にしない                               |
| 主な担当    | 主担当となるロールまたは外部主体               | 個人名にせず、人間の最終判断を明示する                     |
| 起動条件    | 開始を判断できるイベント、前段の完了、承認条件 | 「必要に応じて」で終わらせない                             |
| 必須性      | 必須、条件付き、選択のいずれか                 | 条件付き・選択では起動条件と非起動時の正常な扱いを示す     |

### 6.3. データストア

- 全体概要の「データストア」と同じ「マスタ・構成データ」「トランザクションデータ」の節に分け、本グループが読み書きする行だけを掲載します。該当する行がない区分は節ごと省略します。
- 表の列は「データストア」「読み書き」「本グループでの利用」とします。「読み書き」は「参照」「更新」「参照・更新」のいずれかとし、物の保管先を扱う場合は利用内容に現物の受け渡しであることを示します。
- 名称と区分は全体概要から変更しません。新しいデータストアまたは区分変更が必要なら先に全体概要を変更し、本章だけへ追加しません。
- プロセス領域の全箇条書きと個別プロセス主要入出力にあるデータストアを過不足なく含め、各データストアがどの領域またはプロセスで参照・更新されるかを利用内容で説明します。
- 概念データフローを複数図に分けて同じデータストアを再掲する場合を除き、表の各行と図のデータストアノードを一対一に対応させ、名称を一致させます。

### 6.4. 概念データフロー

- Mermaid のノード、エッジ、形状、線種は Frontmatter の `includes` で指定した記法ルールに従います。
- 全体概要の各領域を一つの代表ノードとして再掲せず、「プロセス領域」の各表の行を一つずつ個別のプロセスノードとして配置します。
- 同一グループ内の領域間の受け渡しは、双方のプロセスを同じ図または対応する分割図に置いて示します。他グループは内部プロセスを描かず、委譲先の代表ノードまたは起点・完了イベントだけを置きます。
- 図は領域ごと、または業務の性質が近いプロセスごとに分けることを基本とします。一図のプロセスノードが目安 15 個を超える場合も分割します。
- 各図の直後に、全体概要の「凡例（本プロダクト共通）」への参照、線種、図から省略した入出力とその理由、別図と共有するノードを記載します。色・絵文字の割り当ては再掲しません。
- 状態名をノードとして並べたり、状態間の矢印を描いたりしません。状態を変える業務はプロセスと起点イベントだけを示し、「状態遷移の参照」から STSD へ接続します。

### 6.5. 個別プロセス主要入出力

- 図を領域単位で分けた場合は領域ごと、業務の性質で分けた場合は同じまとまりごとに節を設けます。
- プロセス ID ごとに、主要入力、主要出力、データストアを表で示します。業務目的、担当、起動条件、必須性は「プロセス領域」の表から重複させません。
- データストアの名称と区分は「プロセス領域」「データストア」および全体概要と一致させます。論理的な入出力名と保管先を同じ列へ混在させません。
- 全プロセスをちょうど一度掲載し、一プロセスだけのまとまりでも同じ表構成を省略しません。

### 6.6. 状態遷移の参照

- 状態を変えるプロセスがある場合、表の列は「対象」「状態を変えるプロセス」「ステータス定義（STSD）」とします。該当プロセスがない場合は、その事実と確認根拠を一文で記載して表を省略します。
- STSD は状態名・意味・成立条件と、遷移元・遷移先・イベント・遷移条件の単一正本として参照します。
- CDFD には状態の一覧、遷移表、状態を頂点とする状態遷移図を複製しません。参照先が未作成なら文書 ID をバッククォートで仮置きし、作成状況は登録簿で追跡します。
- プロセスの業務目的や入出力は CDFD に残し、状態定義だけを STSD へ委ねます。参照によってフローの説明を空洞化させません。

### 6.7. 主要例外とグループ外への委譲

- 主要例外は「例外 ID」「対象プロセス」「検出条件」「停止範囲」「本グループでの扱い」「継続・再開条件」の表で示します。「停止範囲」には、例外の検出後に確定または起動してはならない後続プロセス、出力、委譲を記載します。単なる内部エラー名やログメッセージは列挙しません。
- 条件付きプロセスを起動しない判断そのものは主要例外に含めません。非起動時の正常な扱いは「プロセス領域」の表にある必須性と図で示します。
- グループ外委譲は「委譲先」「委譲する事項」「引き渡す情報」「本グループへ戻す条件」の表で示します。
- 委譲先は、他のプロセスグループ別 CDFD `cdfd-<group>` または複数グループの順序を扱うユースケース別 CDFD `cdfd-uc-<topic>` とします。同一グループ内の領域を委譲先にしません。
- 委譲先 CDFD の内部プロセス、状態遷移、例外処理は展開しません。未作成の委譲先は文書 ID をバッククォートで示します。
- 主要例外が 0 件の場合も「主要例外」の節を残し、正常系・条件付きプロセス・更新失敗を確認した範囲と、業務結果または後続起動を変える例外がないという結論を一文で記載して表を省略します。
- グループ外委譲が 0 件の場合も「グループ外への委譲」の節を残し、対象外とした他グループの責務と横断ユースケースを確認した範囲、および委譲がないという結論を一文で記載して表を省略します。

<!-- specdojo:finding id=F007 severity=minor rule=vp-qe-omissions-consistency line=142 完成判定に必須Frontmatter、目的、適用範囲、およびプロセス表の必須列内容の確認が欠けているため、本文要件で必須とした項目を完成チェックへ過不足なく反映してください。 -->
### 6.8. 完成判定

- 全体概要で対象グループに属する全領域が「プロセス領域」にちょうど一つの節として登場し、各領域の表に内部プロセスが一つ以上あります。
- 領域単位の主要入力・主要出力・データストアを合算すると、全体概要のグループ単位の箇条書きと矛盾せず、名称と区分が一致します。
- 全プロセスが領域ごとの表、図、個別プロセス主要入出力へ同じ ID と名称で登場し、ID が所属領域を示します。
- 「データストア」が全体概要の部分集合であり、名称・区分が一致します。各行は図の同名ノードと対応し、読み書きの別がプロセス領域と個別プロセス主要入出力に矛盾しません。
- 同一グループ内の領域間受け渡しを内部フローとしてたどれ、他グループの内部処理を作り込んでいません。
- 状態を変えるプロセスは STSD を参照し、CDFD 本文に状態の定義、遷移表、状態遷移図を重複記載していません。
- 主要例外の検出、停止範囲、継続・再開条件と、グループ外への引き渡しを確認者が説明できます。
- 主要例外またはグループ外委譲が 0 件の場合は、対応する節に確認範囲と該当なしの結論があり、空表やプレースホルダーが残っていません。

## 7. 禁止事項

<!-- specdojo:finding id=F006 severity=major rule=vp-qe-omissions-consistency line=155 上位rulebookが許可する1領域グループの扱いが欠落したまま禁止事項で排除されているため、単一領域でもグループ全体を一文書として成立させる本文要件・template操作・完成条件を追加してください。 -->
<!-- specdojo:finding id=F008 severity=major rule=vp-qe-kata-conformance line=155 recipeは上位グループの全領域を引き継ぐ手順で領域数を限定しておらず、上位rulebookも1領域グループを認める一方、本書は一領域の文書化を禁止しているため、rulebook・recipe・templateが同じ有効入力を扱えるよう統一してください。 -->
<!-- specdojo:finding id=F010 severity=minor rule=vp-ux-readability line=155 「全体概要の一領域だけを一文書にしない」という記述は、複数領域グループの部分切り出しと正規の1領域グループを区別できないため、禁止対象を「複数領域を持つグループの一部だけを切り出すこと」と明確化してください。 -->
- 全体概要の一領域だけを一文書にしたり、一つの領域を複数のプロセスグループ別 CDFD に重複配置したりしません。
- product 成果物の ID を `<project-id>:cdfd-<group>` にしたり、領域名を使った `cdfd-<domain>` を新規採用したりしません。
- 文書内一意の `P-01` 形式を内部プロセス ID に使ったり、領域 ID と対応しないプロセス ID を付けたりしません。
- 全体概要と異なるデータストア名・区分を使用したり、物理テーブル名、物理カラム名、SQL、実装クラス、詳細 API を概念フローへ記載したりしません。
- 状態名・意味を CDFD で定義したり、遷移元・遷移先・遷移条件の表や状態遷移図を複製したりしません。
- 他グループの内部プロセスを展開したり、同一グループ内の領域間受け渡しをグループ外委譲として扱ったりしません。
- 一覧、検索、状態参照、検証、dry-run など、独自の業務成果を持たない補助操作を独立プロセスにしません。
- プロセス領域の表と個別プロセス主要入出力、図直後の注記、例外表の間で同じ事実を重複記載しません。
- すべての内部エラー、ログ、再試行を主要例外として列挙せず、停止範囲や再開条件を判定できない曖昧な記述を残しません。
