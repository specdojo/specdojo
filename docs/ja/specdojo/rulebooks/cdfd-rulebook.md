# 概念データフロー図（領域別）作成ルール

Conceptual Data Flow Diagram Area Documentation Rulebook

全体概要で定めた一つのプロセス領域を、一ノード一プロセスの領域内フロー、主要例外、領域外への委譲として表と Mermaid 図で合意可能にするためのルールです。起動条件、入出力、正本・生成先、再開条件を、後続の設計・検証へ引き渡せる粒度で定めます。

## 1. 全体方針

- 領域別 CDFD は、全体概要で定めた一領域の起点、主要入力・出力、データストア、委譲境界を引き継ぐ概念仕様です。実装方式や操作手順ではなく、領域内プロセスの業務目的と受け渡しを記述します。
- 一つのプロセスノードは一つの業務目的と完了条件を持つプロセスだけを表します。複数の判断・更新・生成を一ノードに詰め込まず、コマンドの一操作を無条件に一プロセスへ分割しません。
- プロセス一覧を用語・起動条件・必須性の正本、個別プロセス主要入出力を主要入力・主要出力・データストアの正本、図を順序と分岐の正本として併用します。同じ対象には表と図で同じプロセス ID と名称を使います。
- 正常系だけでなく、業務結果を変える主要例外を、検出条件、扱い、継続・再開条件で定義します。ログや内部エラーの全列挙は行いません。
- 領域外の責務は内部プロセスとして作り込まず、委譲先、引き渡す情報、必要時に本領域へ戻す条件を明示します。
- 領域別 CDFD は対象プロダクトの現在の正本の姿を示す概念仕様とします。過去の実装分析や将来計画としてのみ成立する内容を扱う場合は、プロジェクト固有の現状分析として別ファイルへ切り出します。
- プロセス数が多い、または起動条件・依存関係の異なるプロセス群が併存する場合は、業務の性質が近いプロセスをまとめて概念データフローを複数図に分割できます。図を分ける場合も、一覧表・個別プロセス主要入出力では一プロセスごとの記述を維持します。
- 人間の判断、利用者との合意、外部主体との受け渡しを省略しません。AI Agent やシステムは支援主体として記載できても、人間が負う最終判断を置き換えません。

## 2. 位置づけと用語定義

| 用語                   | 定義                                                                                         |
| ---------------------- | -------------------------------------------------------------------------------------------- |
| プロセス領域           | 全体概要で定義され、一つの領域別 CDFD が詳細化する責務のまとまり                             |
| プロセス               | 起動条件と入力を受け、業務上意味のある出力または状態変化を一つ生む処理単位                   |
| 起点イベント           | 対象領域または領域内プロセスを開始させる、時点を識別できる出来事                             |
| データストア           | 台帳、文書、ファイル、データベースなど、情報の正本または継続的な保管先                       |
| 外部主体               | 対象範囲の外から情報・現物を渡す、または結果を受け取る人、組織、外部システム                 |
| 情報の流れ             | 依頼、判断、定義、記録、報告などの受け渡し。Mermaid ではラベル付きの `-->` で表す            |
| 物の流れ               | 商品、現金、帳票原本など現物の受け渡し。必要な場合だけラベル付きの `==>` で表す              |
| 補助操作               | 一覧、検索、状態参照、検証、dry-run など、独自の業務成果を作らず他プロセスを支える操作       |
| 主要例外               | 正常系と異なる業務判断、生成結果、引き渡し可否を生じさせ、再開条件の合意が必要な分岐         |
| 領域外委譲             | 対象領域では処理せず、引き渡す情報と責任境界を明示して別領域または外部主体へ渡すこと         |
| 個別プロセス主要入出力 | プロセスごとの主要入力・主要出力・データストアを示す章。領域内プロセス一覧とは分けて記載する |

## 3. ファイル命名・ID規則

- 配置は、対象プロダクトの業務仕様配下にあるデータフローディレクトリを基本とします。プロジェクト固有の現状分析として管理する場合は、プロジェクト文書配下へ配置できます。
- 領域別のファイル名は `cdfd-<domain>.md`、ID は `<authority>:cdfd-<domain>` とし、`<domain>` は英小文字・数字・ハイフンで業務領域を表します。
- `cdfd-overview.md` と `cdfd-overview` ID は overview 専用 rulebook の対象であり、本 rulebook では扱いません。
- 領域内プロセスには、全体概要の領域 ID を接頭辞にした `P-01-01` 形式、または文書内で一意な `P-01` 形式のプロセス ID を付けます。主要例外には `E-01` 形式の ID を付け、名称変更後も同じ対象なら維持します。プロセス ID は、一覧表・図・個別プロセス主要入出力で同じ値を使います。

## 4. 推奨 Frontmatter 項目

| 項目       | 説明                                                  | 必須 |
| ---------- | ----------------------------------------------------- | ---- |
| id         | `<authority>:cdfd-<domain>`                           | ○    |
| type       | `flow`                                                | ○    |
| status     | `draft` / `ready` / `deprecated`                      | ○    |
| rulebook   | `specdojo:cdfd-rulebook`                              | ○    |
| based_on   | 目的、範囲、業務要求など、作成時に直接参照した文書 ID | 任意 |
| supersedes | 置き換える旧 CDFD の ID                               | 任意 |

- `based_on` は直接の内容根拠だけを列挙し、図中のすべての要素へ個別の根拠リンクを複製しません。
- 文書のタイトルと利用目的は本文 H1 と「1. 目的」で示し、対象範囲は「2. 適用範囲」で示します。
- 対象者、対象範囲は本文で定義し、未定義の Frontmatter 項目を追加しません。
- `status` の昇格は定められた承認者が行い、作成途中は `draft` とします。

## 6. 記述ガイド

### 6.1. 目的

- 誰が、領域内フロー、主要例外、委譲境界のどれを合意または後続利用するかを 1〜3 文で示します。
- 対象者ごとに、起動条件、入出力、主要例外、領域外への委譲のうちどれを確認するかを結び付けます。
- 「分かりやすくする」のような曖昧な表現ではなく、「〇〇が起動条件と例外の境界を承認する」のように利用結果を判定できる表現にします。

### 6.2. 適用範囲

- 対象とする業務、期間、組織、システム境界を明示します。
- 対象外は単なる省略ではなく、別成果物へ委譲する詳細、補助操作、外部責務を区別して記述します。
- 人間と AI Agent の責任分担の原則は、本文で再定義せず、対応する文書への参照に留めます。
- 特定プロジェクトの実行計画・スケジュール上のフェーズ名や、実装検討段階だけで使われる仮称は、領域別 CDFD では扱いません。読者が前提知識なしに読める語彙を使います。

### 6.3. 領域内プロセス一覧

次の列を使用し、一行を一つのプロセスノードへ対応させます。主要入力・主要出力・データストアは「個別プロセス主要入出力」（5章）へ記載し、本章の列には含めません。

<!-- prettier-ignore -->
| 列 | 記載内容 | 判定基準 |
| --- | --- | --- |
| プロセス ID | `P-01-01` または `P-01` 形式の安定した識別子 | 表と図で同じ ID を使う |
| プロセス | 一つの業務目的が分かる短い名称 | 複数プロセスやコマンド列を一行へ詰め込まない |
| 業務目的 | 対象者に生じる成果または維持する状態 | 手順の列挙にしない |
| 主な担当 | 主担当となるロールまたは外部主体 | 個人名にしない |
| 起動条件 | 開始を判断できるイベント、前段の完了、承認条件 | 「必要に応じて」で終わらせない |
| 必須性 | 必須、条件付き、選択のいずれか | 条件付きでは起動条件と非起動時の扱いを示す |

### 6.4. 概念データフロー

- Mermaid のノードとエッジは、Frontmatter の `includes` で指定した記法ルールに従います。ノード形状・線種・色・絵文字は `specdojo:cdfd-mermaid-rulebook` に従い、対象プロダクトの全体概要が「凡例（本プロダクト共通）」を設けている場合はそれを参照し、本図の凡例では色・絵文字の意味を再掲しません。
- 一覧の各行を一つのプロセスノードとして配置し、起点イベント、主要なデータストア、必要な外部主体、委譲先をつなぎます。
- 正常系と、起動するかどうかで後続フローが変わる条件付きプロセスを図で追跡可能にします。主要例外の詳細は表で管理し、図へ載せる場合も例外 ID を一致させます。
- 表にある全プロセスを図へ一度登場させます。読みやすさのために入出力を省略する場合は、図の直後に対象と理由を記述します。
- プロセスの性質（必須・条件付きなど）によって図が追いにくい場合、または一画面でプロセス・データストア・外部主体の関係を追いにくい場合は、複数の図に分割できます。分ける場合は各図の直後に専用の凡例を置き、両図に登場する共通ノードが同一の対象を指すことを明記します。
- 現物を扱わない CDFD では物の流れを無理に追加せず、「本図は現物の流れを扱わない」と凡例または補足で明示します。

### 6.5. 個別プロセス主要入出力

- プロセスをグループ化する場合は、グループごとに見出しを立て、グループが扱う範囲を数行で要約します。概念データフロー（4章）を複数図に分けた場合は、同じ単位でグループ化すると対応関係が追いやすくなります。
- プロセス ID ごとに、主要入力、主要出力、データストアを表で示します。業務目的、主な担当、起動条件、必須性は「領域内プロセス一覧」（3章）が正本のため、本章では重複させて記載しません。
- 正本・生成先が複数ある場合は、概念名（主要出力）と代表パスまたは論理的な生成先（データストア）を分けて示します。生成先にプレースホルダ（`<project-id>` 等）を使う場合は、置き換え対象を明示する注記を添えます。
- プロセスグループが一プロセスだけで構成される場合も、同じ表構成を省略せず記載します。

### 6.6. 主要例外と領域外への委譲

- 主要例外は、例外 ID、対象プロセス、検出条件、本領域での扱い、継続・再開条件を表で示します。単なる内部エラー名やログメッセージは列挙しません。
- 既存正本、入力不足、生成・更新失敗など、成果の採否や後続起動を変える分岐を優先します。業務結果が同じ再試行や補助検証は対象プロセスの内部へ留めます。
- 条件付きプロセスを起動しない判断そのものは主要例外に含めません。起動しない場合の正常終了条件は、必須性の記載（3章）と整合させます。
- 領域外への委譲は、委譲先、委譲する事項、引き渡す情報、本領域へ戻す条件を表で示します。他領域の内部プロセスは展開しません。委譲先に対応する領域別 CDFD がある場合は、委譲先名にその CDFD への参照を併記します。

### 6.7. 完成判定

- 表の各プロセスについて、図中の一つのプロセスノード、起動条件、必須性を「領域内プロセス一覧」（3章）から追跡できます。
- 表の各プロセスについて、主要入力、主要出力、データストアを「個別プロセス主要入出力」（5章）から追跡できます。
- 図中の各プロセスは表の一行へ対応し、対応先のないプロセスや重複するプロセス ID がありません。
- 主要例外の検出、停止範囲、継続・再開条件と、領域外への引き渡しを確認者が説明できます。
- 「凡例（本プロダクト共通）」を全体概要が設けている場合、本図の凡例がそれを再掲せず参照していることを確認できます。
- 未決事項がある場合は _UNDECIDED_: として影響、決定者、決定時期を記載し、確定情報と混在させません。

## 7. 禁止事項

- 物理テーブル名、物理カラム名、SQL 全文、実装クラス名、関数名、詳細な API、コマンドオプションを概念フローへ記載しません。
- UI 操作や CLI 操作を一手順ずつ並べ、業務上の入力・出力・判断を埋没させません。
- ラベルのない情報・現物のエッジ、一覧表・図・個別プロセス主要入出力で名称が異なる同一要素、起点または到達先のないエッジを残しません。
- 一覧、検索、状態参照、検証、dry-run などの補助操作を、固有の業務成果がないまま独立したプロセス領域にしません。
- 全体概要の一領域を一つの代表ノードとして再掲しただけの図や、領域外プロセスの内部処理を作り込んだ図にしません。
- すべての内部エラー、ログ、再試行を主要例外として列挙しません。
- 例外後の停止範囲、継続・再開条件、領域外への引き渡しが判定できない曖昧な記述を残しません。
- 特定プロジェクトの実行計画・スケジュール上のフェーズ名や実装検討段階だけの仮称を、前提知識なしの読者に説明なく使いません。
- 「領域内プロセス一覧」（3章）と「個別プロセス主要入出力」（5章）の両方に、同じ項目（業務目的・主な担当・起動条件・必須性、または主要入力・主要出力・データストア）を重複して記載しません。
