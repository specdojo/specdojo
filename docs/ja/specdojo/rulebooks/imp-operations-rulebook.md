# 影響調査（運用）作成ルール

Impact Analysis (Operations) Rulebook

変更要求による運用への影響を整理し、変更要否・影響度・対応方針・未解決事項を判断する記述基準を定めます。

## 1. 全体方針

- 本書は、変更の着手前に、どの運用をどの程度変えるか、変更要求を運用面で受け入れるかを判断するための文書とする。
- 影響詳細は運用対象（監視・アラート・手順・体制・統制・SLA 運用など）単位とし、影響対象運用ごとに判定・根拠・対応方針を 1 行で対応させる。実運用手順の詳細化は扱わない。
- 6章と各表の必須列は本文要件と sample で定まるため、別の作成手順・雛形は不要とし、`recipe`・`template` は `not-needed` とする。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱う。

## 2. 位置づけ

- 入力: プロジェクト登録簿の変更要求（`item_type: change-request` の個票）。
- 判断対象: 運用品質・障害対応・運用負荷・利用者への影響と、その対応方針。
- 他の影響調査との分担: 同じ変更要求を業務（`imp-business`）・データ（`imp-data`）・I/F（`imp-interface`）・テスト（`imp-test`）の影響調査が並行して扱う。本書は運用面だけを判定し、他領域の判定を再掲しない。他領域の判定を前提とする行は、備考にその文書 ID を示す。
- 反映先: 詳細はデータ仕様（`bdd-*`）、I/F 仕様（`ifx-*`）、テスト戦略・方針（`tsp-index`）、運用設計（`opd-*`）などへ委ね、備考に適用先カタログの成果物 ID を示す。
- 追従: 変更要求が改訂されたら、「影響詳細一覧」「対応方針」と、備考に示した他の影響調査・委譲先の文書を見直す。

## 3. ファイル命名・ID規則

- 文書 ID は `<project-id>:imp-operations`、推奨ファイル名は `imp-operations.md` とする。
- 追補は `<project-id>:imp-operations-<term>` とし、共通規則は [[specdojo:id-and-file-naming-standard|ID・ファイル命名標準]] に従う。

## 4. 推奨 Frontmatter 項目

共通項目・必須性・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。`type` は `project`、`rulebook` は `specdojo:imp-operations-rulebook` とする。`based_on` には入力の変更要求の個票 ID（`PJR-XXXX`）と、前提とした他の影響調査の ID を記載する。

## 5. 本文要件

本文は次の6章をこの順で置き、すべて必須とする。

| 章  | 見出し         | 目的                                                           |
| --- | -------------- | -------------------------------------------------------------- |
| 1   | 目的と適用範囲 | 変更要求、対象・対象外の運用領域、対象期間、判断目的を示す     |
| 2   | 変更要求の概要 | 背景・要求・狙いと、判定可能な成功条件を示す                   |
| 3   | 影響分析サマリ | 評価観点と影響度の尺度、影響度別の件数・優先対応、運用面の結論 |
| 4   | 影響詳細一覧   | 運用対象ごとの変更要否・影響度・対応方針・根拠を記録する       |
| 5   | 対応方針       | 対応項目ごとの期限・担当・前提条件を示す                       |
| 6   | 未解決事項     | 判断待ち・不足情報と、その影響・決定期限・担当・転記先を示す   |

表を置く章は、次の列を必須とする。列名はこのとおりに揃える。

| 章             | 必須の列                                                                       |
| -------------- | ------------------------------------------------------------------------------ |
| 影響分析サマリ | 影響度、件数、主な対象運用、優先対応（`要` / `否`）                            |
| 影響詳細一覧   | 影響対象運用、変更要否（`要` / `否`）、影響度、対応方針、判断根拠、備考        |
| 対応方針       | 影響度、対応項目、期限、担当、前提条件                                         |
| 未解決事項     | 論点、不足情報、運用判断への影響、当面の扱い、決定期限、担当、転記先の登録項目 |

## 6. 記述ガイド

各章の判断の基準と、良い例・悪い例を示す。完成例は Frontmatter の `sample` で宣言された sample を参照する。

### 6.1. 目的と適用範囲

- 変更要求の ID、対象運用領域、対象外の領域とその理由、対象期間（着手日から変更後の運用確認完了日まで）を記載する。

| 観点     | 良い例                                                           | 悪い例               |
| -------- | ---------------------------------------------------------------- | -------------------- |
| 対象外   | 「問い合わせ窓口の体制は対象外。受付時間と人数が変わらないため」 | 対象外を書かない     |
| 対象期間 | 「2026-05-01〜2026-07-31（変更後の月次運用レビュー完了日）」     | 「次回リリースまで」 |

### 6.2. 変更要求の概要

- 背景・要求・狙いを判断に必要な要点に絞って要約し、成功条件は確認対象・指標・閾値（または達成状態）・判定方法で書く。

| 観点     | 良い例                                                                 | 悪い例                 |
| -------- | ---------------------------------------------------------------------- | ---------------------- |
| 成功条件 | 「値引き適用エラーの検知から初動開始まで 15 分以内（当番記録で確認）」 | 「運用品質を維持する」 |

### 6.3. 影響分析サマリ

- 運用品質（監視・統制・監査）、障害対応力、運用負荷、利用者影響の4観点で評価し、観点別の最も高い判定を影響度とする。件数も同じ規則で集計する。
- 許容停止時間や当番の対応上限など案件の境界値を表の前に示してから、次の尺度を当てはめる。
  - 高: 障害を検知・初動できない、許容時間を超える停止、統制・監査の要件を満たせないのいずれかがある。
  - 中: 高に該当せず、手順・監視設定・体制の変更か、利用者への周知が必要。
  - 低: 高・中に該当せず、現行の運用で継続できる。
- 表の後に、変更要求に対する運用面の結論を `受入` / `条件付き受入` / `見送り` のいずれかで推奨し、条件付き受入はその条件を、見送りは理由を示す。

| 観点   | 良い例                                                       | 悪い例                             |
| ------ | ------------------------------------------------------------ | ---------------------------------- |
| 境界値 | 「許容停止時間: 営業時間中 10 分以内」                       | 境界値を示さずに高・中を使う       |
| 観点   | 本文要件の4観点で評価する                                    | 観点を一部だけ使う、別の観点を足す |
| 結論   | 「条件付き受入。監視項目の追加が 2026-05-15 までに済むこと」 | 結論を書かず件数だけを示す         |

### 6.4. 影響詳細一覧

- 対応方針は `実施` / `代替` / `見送り` のいずれかとし、判断根拠に影響度の判定理由を「影響分析サマリ」の観点に沿って書く。影響がない観点も理由を残す。
- 備考には制約・前提と、委譲先・前提とした他の影響調査の文書 ID を書く。

| 観点     | 良い例                                                                       | 悪い例               |
| -------- | ---------------------------------------------------------------------------- | -------------------- |
| 判断根拠 | 「障害対応力: 値引き適用エラーの監視がなく、売上差異を締めまで検知できない」 | 「影響あり。要対応」 |
| 備考     | 「委譲先: `opd-monitoring`。前提: `imp-data` の締め集計変更」                | 「関連資料参照」     |

### 6.5. 対応方針

- 影響度の高い順に、対応項目ごとの期限、担当（Role code）、前提条件を記載する。
- 見送り・代替は、再評価条件と期限を必ず記載する。

| 観点   | 良い例                                                                                                 | 悪い例         |
| ------ | ------------------------------------------------------------------------------------------------------ | -------------- |
| 担当   | `OPS`                                                                                                  | 個人名、連絡先 |
| 見送り | 「問い合わせテンプレートの改訂は見送り。関連の問い合わせが週 5 件を超えたら再評価（期限 2026-07-31）」 | 「当面見送り」 |

### 6.6. 未解決事項

- 論点ごとに不足情報、運用判断への影響、当面の扱い、決定期限、担当（Role code）を記載する。該当がなければ「なし」とする。
- 次の条件に当てはまる事項はプロジェクト登録簿へ転記し、転記先の登録項目 ID（`PJR-XXXX`）を記載する。転記しない事項は「転記先の登録項目」を「なし」とする。

| 条件                                                         | 転記先の `item_type` |
| ------------------------------------------------------------ | -------------------- |
| 決定期限までに判断できず、確認や調査が必要な事項             | `question`           |
| 対応が遅れると運用開始・受入判定・納期に影響するおそれがある | `risk`               |
| すでに運用や計画に支障が出ている                             | `issue`              |
| 見送り・代替を決めた                                         | `decision`           |

## 7. 禁止事項

- 「影響あり」「要対応」だけで判定を済ませない。
- 「影響分析サマリ」の尺度・観点と異なる判定を混在させない。
- 本文要件と異なる列名で同じ項目を書かない（例: 「影響度」の代わりに「優先度」「重要度」）。
- 担当に個人名や連絡先を書かない。Role code で記載する。
- 見送り・代替を、再評価条件と期限なしで記載しない。
- 監視設定値や手順の操作ステップなど、実運用手順の詳細を書かない。委譲先の文書へ送る。
