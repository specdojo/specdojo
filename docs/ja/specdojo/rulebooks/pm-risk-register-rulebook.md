# リスク登録簿 作成ルール

Risk Register Documentation Rules

顕在化前のリスクを評価・対応・監視し、納期・品質・後続成果物への影響を事前に抑えるためのリスク登録簿の記述基準を定める。

## 1. 全体方針

- リスク登録簿は、リスクごとに優先度を評価基準から再現し、対応への着手・受容・監視の継続を判断するための文書である。
- 本書の判断基準は、プロジェクト登録簿の個票と、登録簿を使わない単独のリスク登録簿の両方に適用する。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱う。

## 2. 位置づけ

- プロジェクト登録簿を使うプロジェクトでは、リスク 1 件を `item_type: risk` の個票に書く。`controls/generated/pm-risk-register.md` は `register build` が個票から生成し、Frontmatter の `template` はこの生成ビューの骨組みを指す。個票の節・フィールド・生成と検証の手順は [[specdojo:pjr-rulebook|プロジェクト登録簿 作成ルール]] に従う。
- 単独のリスク登録簿には対応する template がないため、本文要件の 6 章で構成する。
- リスクが顕在化したら `pm-issue-log` 側の課題、スコープや計画の変更が要るなら `pm-change-request-log` 側の変更要求として起票し、関連ドキュメントで結ぶ。

## 3. ファイル命名・ID規則

- `id` は `<project-id>:pm-risk-register`、ファイル名は `pm-risk-register.md` とする。
- リスク ID は登録簿では `PJR-XXXX`、単独の登録簿では `RK-NNN` とし、再利用しない。
- 単独の登録簿から登録簿へ移るときは、各 `RK-NNN` を個票として起票し、旧 ID を個票の `入力` 節に残す。同じパスに生成ビューを出力するため、単独の登録簿は `register build` の前に取り除く。

## 4. 推奨 Frontmatter 項目

- 許可キーと型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] を正本とし、`type` は `project` とする。

## 5. 本文要件

単独の登録簿の章と、個票で同じ内容を書く場所は次のとおり。個票は 1 件のリスクだけを扱うため、全リスクに共通する評価基準と監視周期は `pm-plan` などの管理計画に置き、個票の関連ドキュメントから文書 ID で参照する。

| 番号 | 見出し           | 必須 | 個票で書く場所                                                                                           |
| ---- | ---------------- | ---- | -------------------------------------------------------------------------------------------------------- |
| 1    | 概要             | ○    | 管理計画（個票では不要）                                                                                 |
| 2    | リスク登録簿一覧 | ○    | 生成ビュー。優先度・ステータス・担当・期限は Frontmatter の `priority`・`item_status`・`owner`・`due_on` |
| 3    | 評価基準         | ○    | 共通の基準は管理計画、各リスクの発生確率・影響度は `影響評価` 節                                         |
| 4    | 対応計画         | ○    | `対応方針` 節。受容の判断と残存影響は終端時に `conclusion`                                               |
| 5    | モニタリング     | ○    | 共通の周期は管理計画、個別のトリガーは `モニタリング` 節                                                 |
| 6    | 関連ドキュメント | ○    | `関連ドキュメント` 節                                                                                    |

## 6. 記述ガイド

### 6.1. 概要

- 管理対象、見直し頻度、記録単位を 1〜3 行で示す。

### 6.2. リスク登録簿一覧

- リスク ID、内容、発生確率、影響度、優先度、対応策、担当、ステータスを一覧にする。
- 優先度とステータスは登録簿の `priority`・`item_status` の値を使い、言い換えない。
- 担当は適用先のメンバー定義の Role code で書く。公開リポジトリに置くため、個人名・連絡先と、要員・取引先・契約条件など公開できないリスクの内容を書かない。
  - 良い例: 担当 `PM`、内容「業務側の確認が遅れ、受入の期日に間に合わない」
  - 悪い例: 担当「山田（090-…）」、内容「仕入先 A 社の経営不安」

### 6.3. 評価基準

- 発生確率と影響度の段階ごとの判定条件と、その組み合わせから優先度を決める対応表を書く。
- 影響度の判定条件には、納期（スケジュールの遅れ日数）、品質、後続成果物への影響を観点として含める。
  - 良い例: 影響度「高」= 受入の期日が 1 週間以上遅れる、または後続成果物の作り直しが要る
  - 悪い例: 影響度「高」= 影響が大きい
- 再評価の条件と、評価を変える判断をする Role code を書く。評価の変更と受容は人間の役割が判断し、agent は判断の材料をまとめるにとどめる。

### 6.4. 対応計画

- 回避・低減・受容・移転のどれを採るかと、具体の対応、期限、完了条件を書く。完了条件は確認の手段と合格の基準で書く。
  - 良い例: 負荷試験で 100 件同時の会計が 2 秒以内に終わる
  - 悪い例: 閾値以内
- 受容する場合は、受容を判断した Role code と、許容する残存影響を書く。受容がスコープ・計画を変える場合は決定記録にも起票し、関連ドキュメントで結ぶ。
- 顕在化して課題・変更要求へ移したら、移管先を関連ドキュメントに書き、元のリスクは追跡を移管先に任せて終える（登録簿では `done`）。残存影響を監視する場合は終えずに監視を続ける。

### 6.5. モニタリング

- 監視周期、顕在化を判定するトリガー、状態を更新する契機を書く。
- 期限超過や見直し漏れのときの連絡先と、連絡を受けた側が行う是正（再評価、担当の再割り当て、ステータスの更新）を書く。

### 6.6. 関連ドキュメント

- 根拠、影響を受ける成果物、リスクから起票した課題・変更要求・決定記録を文書 ID で示す。なければ `（本書のみ）` と書く。

## 7. 禁止事項

| 禁止事項                                         | 理由                                       |
| ------------------------------------------------ | ------------------------------------------ |
| リスク ID なしで記録する                         | 追跡不能になるため                         |
| 評価基準なしで優先度を決める                     | 判断が恣意的になるため                     |
| 担当を未記載にする                               | 対応遅延が発生するため                     |
| 担当に個人名・連絡先を、内容に非公開の情報を書く | 公開リポジトリに不適切な情報が載るため     |
| agent がリスクの受容や評価の変更を判断する       | 残存リスクの受容に人間の判断が入らないため |
| モニタリング周期を未定義にする                   | 兆候を見落とすため                         |
| 顕在化したリスクを課題として起票せず放置する     | 対応が課題ログで追跡されないため           |
| 生成された `pm-risk-register.md` を直す          | 再生成で修正が失われるため                 |
