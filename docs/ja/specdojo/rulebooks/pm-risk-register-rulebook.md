# リスク登録簿 作成ルール

Risk Register Documentation Rules

顕在化前のリスクを評価・対応・監視し、納期や品質への影響を事前に抑えるためのリスク登録簿の記述基準を定める。

## 1. 全体方針

- リスクごとに、発生確率・影響度から優先度を再現でき、対応に着手するかを判断できる形で残す。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱う。

## 2. 位置づけ

- プロジェクト登録簿を使うプロジェクトでは、リスク 1 件を `item_type: risk` の個票に書き、`controls/generated/pm-risk-register.md` は `register build` が個票から生成する。生成物の Frontmatter は `rulebook: specdojo:pjr-rulebook` とし、直接編集しない（[[specdojo:pjr-rulebook|プロジェクト登録簿 作成ルール]] に従う）。
- 本書の判断基準は、個票と、登録簿を使わない単独のリスク登録簿の両方に適用する。
- リスクが顕在化したら `pm-issue-log` 側の課題として、スコープや計画の変更が要るなら `pm-change-request-log` 側の変更要求として起票し、関連ドキュメントで結ぶ。

## 3. ファイル命名・ID規則

- `id` は `<project-id>:pm-risk-register`、ファイル名は `pm-risk-register.md` とする。
- リスク ID は登録簿では `PJR-XXXX`、単独の登録簿では `RK-NNN` とし、再利用しない。

## 4. 推奨 Frontmatter 項目

- 許可キーと型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] を正本とし、`type` は `project` とする。

## 5. 本文構成（標準テンプレ）

| 番号 | 見出し           | 必須 |
| ---- | ---------------- | ---- |
| 1    | 概要             | ○    |
| 2    | リスク登録簿一覧 | ○    |
| 3    | 評価基準         | ○    |
| 4    | 対応計画         | ○    |
| 5    | モニタリング     | ○    |
| 6    | 関連ドキュメント | ○    |

## 6. 記述ガイド

### 6.1. 概要

- 管理対象、見直し頻度、記録単位を 1〜3 行で示す。

### 6.2. リスク登録簿一覧

- リスクID、内容、発生確率、影響度、優先度、対応策、担当、ステータスを一覧にする。
- 優先度とステータスは登録簿の `priority`・`item_status` の値を使い、言い換えない。

### 6.3. 評価基準

- 発生確率と影響度の段階ごとの判定条件と、その組み合わせから優先度を決める対応表を書く。
- 再評価の条件と、評価を変える判断をする者を書く。

### 6.4. 対応計画

- 回避・低減・受容・移転のどれを採るかと、具体の対応、期限、完了条件を書く。完了条件は確認の手段と合格の基準で書く。
- 受容する場合は、受容を判断した者と、許容する残存影響を書く。

### 6.5. モニタリング

- 監視周期、顕在化を判定するトリガー、状態を更新する契機を書く。
- 見直しが行われなかったときの連絡先を書く。

### 6.6. 関連ドキュメント

- 根拠、影響を受ける成果物、リスクから起票した課題・変更要求を文書 ID で示す。なければ `（本書のみ）` と書く。

## 7. 禁止事項

| 禁止事項                                     | 理由                             |
| -------------------------------------------- | -------------------------------- |
| リスクIDなしで記録する                       | 追跡不能になるため               |
| 評価基準なしで優先度を決める                 | 判断が恣意的になるため           |
| 対応責任者を未記載にする                     | 対応遅延が発生するため           |
| モニタリング周期を未定義にする               | 兆候を見落とすため               |
| 顕在化したリスクを課題として起票せず放置する | 対応が課題ログで追跡されないため |
| 生成された `pm-risk-register.md` を直す      | 再生成で修正が失われるため       |
