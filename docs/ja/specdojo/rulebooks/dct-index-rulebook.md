# 成果物カタログ（インデックス）作成ルール

Deliverables Catalog Index Documentation Rules

本ドキュメントは、成果物カタログ索引の正本 `dct-index.yaml` と、そこから生成する `generated/dct-index.md` の記述ルールです。プロジェクト横断の表示順・グループ・名称・概要・規模を宣言へ集約し、ドメイン別カタログとの整合を機械的に検証できる状態を保ちます。

## 1. 全体方針

- `dct-index.yaml` は、プロジェクト規模とドメイン一覧の表示意図を保持する唯一の正本とする。
- `generated/dct-index.md` は `catalog build` が生成する表示専用ビューとし、直接編集しない。
- 各ドメインの成果物定義は `dct-<domain>.yaml` に置き、索引には表示名・概要・順序・グループだけを置く。
- 共通ルールなどの散文と生成物の外枠は `dct-index-template.md` が保持し、YAML の文字列へ複製しない。
- `dct-index.yaml` の宣言ドメイン集合と実在する `dct-*.yaml` の `domain` 集合を一致させる。

## 2. 位置づけと用語定義

| 用語         | 正本・生成物                | 役割                                                       |
| ------------ | --------------------------- | ---------------------------------------------------------- |
| 索引宣言     | `dct-index.yaml`            | 規模、グループ、ドメイン順、表示名、概要を宣言する         |
| 本文テンプレ | `dct-index-template.md`     | Frontmatter 雛形、共通ルール、一覧挿入スロットを保持する   |
| 索引ビュー   | `generated/dct-index.md`    | 宣言と実在カタログから生成されるプロジェクトの参照起点     |
| ドメイン正本 | `dct-<domain>.yaml`         | ドメインに属する成果物、配置、依存関係、完了条件を定義する |
| ドメイン表示 | `generated/dct-<domain>.md` | 1 ドメインの成果物定義を読みやすい Markdown として表示する |

- `domain` は論理的な管理単位であり、物理ファイル名ではなく各 `dct-*.yaml` の `domain` 値で識別する。
- 同じ `domain` を持つ物理分割ファイルが複数あっても、索引宣言と索引ビューでは 1 ドメインとして扱う。
- `group` は索引ビューの分類見出しを表す。ルートのグループは `domains` または子 `groups` のどちらか一方を持つ。
- `subgroup` はルートグループ直下の表分割を表し、`domains` を持つ。Markdown 見出しを H4 までに収めるため、さらに子 `groups` は持てない。
- グループとサブグループの順序は、成果物定義の依存順や Schedule の実行順を意味しない。

## 3. ファイル命名・ID規則

- 索引宣言はカタログディレクトリ直下の `dct-index.yaml` とする。
- 索引ビューは同ディレクトリの `generated/dct-index.md` に生成する。
- 索引ビューの文書 ID は `<project-id>:dct-index` とし、宣言の `project_id` と一致させる。
- ドメイン表示へのリンクは `./dct-<domain>.md` とし、索引ビューと同じ `generated/` ディレクトリ内で解決する。
- ドメイン識別子は英小文字・数字・ハイフンからなる kebab-case とする。

## 4. 本文要件

構造・必須キー・型制約は `dct-index.schema.yaml` を SSOT とし、本章は各キーの運用意図を補う。生成ビューの見出し・共通ルールの骨組みは `dct-index-template.md` を正本とする。

### 4.1. ルート項目

| 項目         | 必須 | 目的・記述規約                                                     |
| ------------ | ---- | ------------------------------------------------------------------ |
| `id`         | ○    | `<project-id>:dct-index`。生成ビューの文書 ID としても使う         |
| `type`       | ○    | `project` 固定                                                     |
| `status`     | ○    | `draft` / `ready` / `deprecated`                                   |
| `title`      | ○    | 生成ビューの文書名                                                 |
| `rulebook`   | ○    | `specdojo:dct-index-rulebook` 固定                                 |
| `project_id` | ○    | 対象プロジェクト ID。`id` の接頭辞と一致させる                     |
| `size`       | ○    | scaffold に用いる `small` / `medium` / `large`                     |
| `groups`     | ○    | 索引ビューに出すルートグループの配列。配列順を表示順として使用する |

### 4.2. `groups[]`（ルートグループ）

| 項目      | 必須 | 目的・記述規約                                                  |
| --------- | ---- | --------------------------------------------------------------- |
| `name`    | ○    | 索引ビューの H3 グループ見出し                                  |
| `domains` | 選択 | グループ内のドメイン配列。`groups` と同時には指定できない       |
| `groups`  | 選択 | H4 で出力するサブグループ配列。`domains` と同時には指定できない |

`domains` と `groups` はどちらか一方だけを必須とする。分類を 1 段で足りる場合は `domains` を、2 段に分ける場合は `groups` を指定する。

### 4.3. `groups[].groups[]`（サブグループ）

| 項目      | 必須 | 目的・記述規約                                               |
| --------- | ---- | ------------------------------------------------------------ |
| `name`    | ○    | 索引ビューの H4 サブグループ見出し                           |
| `domains` | ○    | サブグループ内のドメイン配列。配列順を表の行順として使用する |

サブグループは `groups` を持てない。見出しを `## 2. 成果物カタログ一覧`、H3 グループ、H4 サブグループの 2 段までに収めるためである。

### 4.4. `domains[]`

| 項目       | 必須 | 目的・記述規約                                                     |
| ---------- | ---- | ------------------------------------------------------------------ |
| `domain`   | ○    | 実在する `dct-*.yaml` の `domain` と一致する論理識別子             |
| `name`     | ○    | 利用者向けの日本語表示名。索引ビューの表とサイドバーの表示名に使う |
| `overview` | ○    | ドメインが管理する成果物の関心領域を示す 1 文の概要                |

- 各要素のキーは `domain`、`name`、`overview` の順に書く。文書サイトのサイドバーは `domain` の直後の `name` を表示名として読むため、順序を入れ替えると表示名を解決できない。
- 全ドメインの出現順（ルートグループ、サブグループ、`domains` の順に走査した順）は、サイドバーでのドメイン表示の並び順にもなる。

### 4.5. 生成ビューの構成

| 章  | 内容               | 必須 | 生成元                                            |
| --- | ------------------ | ---- | ------------------------------------------------- |
| 1   | 共通ルール         | ○    | `dct-index-template.md`                           |
| 2   | 成果物カタログ一覧 | ○    | template のスロットへ `groups` ごとの表を生成する |

- `domains` を持つルートグループは、`### 2.<グループ番号>. <名称>` と表を 1 組生成する。
- `groups` を持つルートグループは H3 見出しだけを生成し、各サブグループを `#### 2.<グループ番号>.<サブグループ番号>. <名称>` と表の組で生成する。
- グループ番号とサブグループ番号は、それぞれの配列順に 1 から採番する。
- 複数の物理ファイルが同じ `domain` を持つ場合、索引には 1 行だけ生成する。

各表は次の標準列をこの順序で持つ。

| 列名           | 生成内容                                         |
| -------------- | ------------------------------------------------ |
| ドメイン       | `domain` をバッククォートで囲んだ値              |
| 名称           | 宣言の `name`                                    |
| 成果物カタログ | `generated/dct-<domain>.md` へ解決する相対リンク |
| 概要           | 宣言の `overview`                                |

## 5. 記述ガイド

### 5.1. グループ分類の決め方

- 分類の正本は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] の文書構成図とする。ルートグループはプロジェクト成果物とプロダクト成果物のような文書分類、サブグループは構成図が示す論理的なまとまり（要件〜設計、品質保証、運用など）に対応させる。
- 成果物リファレンスは個別成果物を引くための一覧であり、章の粒度は rulebook 単位で索引のグループとは一致しない。分類が食い違う場合は構成ガイドを正として宣言する。
- 1 つのドメインが複数の分類に当てはまるように見える場合は、構成図でそのドメインが置かれた枠に従って 1 か所だけへ置き、判断理由を YAML コメントに残す。
- サブグループに分けるのは、ルートグループ内のドメインが読み手の探索単位として 2 つ以上のまとまりに分かれる場合に限る。ドメインが少数で 1 表に収まるなら `domains` を直接置く。

| 判断         | 良い例                                                             | 悪い例                                                            |
| ------------ | ------------------------------------------------------------------ | ----------------------------------------------------------------- |
| 所属の決定   | 外部I/F仕様を、構成図で置かれている業務仕様群へ 1 か所だけ宣言する | 外部I/F仕様を業務仕様群とアーキテクチャの両方へ宣言する           |
| 階層の選択   | ドメインが 2 つだけのルートグループへ `domains` を直接置く         | ドメイン 1 件ずつのサブグループを並べ、見出しだけが増える         |
| 分類名の付与 | `品質保証` のように、含まれるドメインの共通の関心を名前にする      | `その他`・`追加分` のように、所属理由を示さない名前で受け皿を作る |

### 5.2. `name` と `overview` の書き方

- `name` はドメインの表示名に限定し、状態・担当・件数など変動する情報を含めない。サイドバーにも出るため、親ノードの「成果物カタログ」を繰り返さない。
- `overview` は管理対象の関心領域を 1 文で記述し、個別成果物を列挙しない。個別成果物はドメイン表示が正本である。

| 項目       | 良い例                                                       | 悪い例                                                       |
| ---------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| `name`     | `データモデル`                                               | `成果物カタログ（データモデル）`、`データモデル（作成中）`   |
| `overview` | `データの概念、論理構造、分類、状態を表す成果物を管理する。` | `概念データモデル、論理データモデル、状態遷移表を管理する。` |

### 5.3. `size` の決め方

- `size` はプロジェクト全体の scaffold 方針として決め、生成 Markdown へ重複記載しない。
- ドメインの増減に合わせて `size` を機械的に変えない。変更する場合は、scaffold の対象範囲を見直す判断として扱う。

### 5.4. 生成と検証

- `catalog build` は宣言順を保持し、同じ入力から同じ見出し順・行順・リンクを生成する。生成前に宣言ドメインと実在ドメインを突き合わせ、不一致があれば索引ビューを生成しない。
- schema 検証は、必須項目・列挙値・文字種・空配列と、グループの `domains` / `groups` の排他、サブグループの `groups` 禁止を検出する。
- `catalog validate` は、宣言だけのドメインと実在ファイルだけのドメイン、入れ子全体での同一ドメインの重複宣言、同一階層の同名グループをエラーにする。
- ドメインを追加・削除・改名したら、同じ変更で `dct-index.yaml` を更新し、`catalog build` 後に索引ビューの各リンクとサイドバーの表示名が解決することを確認する。

## 6. 禁止事項

| 禁止事項                                             | 理由                                                   |
| ---------------------------------------------------- | ------------------------------------------------------ |
| `generated/dct-index.md` を直接編集する              | 次回生成で失われ、正本と差異が生じるため               |
| 表示順や表示名を各 `dct-*.yaml` へ分散して持たせる   | ドメイン横断の編集意図が複数ファイルへ分散するため     |
| 同じ `domain` を複数のグループへ宣言する             | 索引上の所属と行が重複するため                         |
| 1 グループへ `domains` と `groups` の両方を記載する  | 見出し直下の表とサブグループの責務が曖昧になるため     |
| サブグループの下にさらに `groups` を記載する         | H5 以下の見出しが必要になり、Markdown 規約に反するため |
| 実在しないドメインを宣言する                         | 生成リンクの参照先を作れないため                       |
| `domains[]` の要素で `name` を `domain` より前に書く | サイドバーが表示名を解決できなくなるため               |
| 実在するドメインを索引宣言から省略する               | 管理対象カタログを参照起点から辿れなくなるため         |
| `name` / `overview` に改行または `\|` を含める       | Markdown 表の列構造を壊すため                          |
| 個別成果物の配置・依存・完了条件を索引宣言へ記載する | ドメイン正本との二重管理になるため                     |
