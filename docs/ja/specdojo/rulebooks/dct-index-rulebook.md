# 成果物カタログ（インデックス）作成ルール

Deliverables Catalog Index Documentation Rules

本ドキュメントは、成果物カタログ索引 `dct-index.yaml` に書くドメインの分類・表示順・名称・概要と、scaffold に用いるプロジェクト規模の判断基準を定めます。

## 1. 全体方針

- `dct-index.yaml` は、プロジェクト規模とドメイン一覧の表示意図を保持する唯一の正本とする。
- `generated/dct-index.md` は `catalog build` が生成する表示専用ビューとし、直接編集しない。
- 各ドメインの成果物定義は `dct-<domain>.yaml` に置き、索引には表示名・概要・順序・グループだけを置く。
- `dct-index.yaml` の宣言ドメイン集合と実在する `dct-*.yaml` の `domain` 集合を一致させる。
- 文書の配置は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] を正本とし、要求・品質・受入の詳細は各ドメインの成果物へ委ねて、索引へ転載しない。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直さない。

## 2. 位置づけ

- `domain` は論理的な管理単位であり、物理ファイル名ではなく各 `dct-*.yaml` の `domain` 値で識別する。物理分割ファイルが複数あっても、索引では 1 ドメインとして扱う。

## 3. ファイル命名・ID規則

- 索引宣言はカタログディレクトリ直下の `dct-index.yaml`、索引ビューは同ディレクトリの `generated/dct-index.md` とする。
- 両者は `<project-id>:dct-index` を共有する。表示用の別 ID を作らず、既存の参照を維持する。

## 4. 本文要件

構造・必須キー・型・列挙値・排他制約は `docs/specdojo/schemas/v1/dct-index.schema.yaml` を正本とし、本章は内容の判断基準を示す。独立 YAML のためメタ情報もトップレベルに置く。コマンドの構文は [[specdojo:command-reference|コマンドリファレンス]] の「catalog / deliverable」を参照する。

### 4.1. ルート項目

| 項目                           | 必須 | 目的・記述規約                                                                                         |
| ------------------------------ | ---- | ------------------------------------------------------------------------------------------------------ |
| `id` / `project_id`            | ○    | 対象プロジェクトを識別し、他プロジェクトの索引との取り違えを防ぐ                                       |
| `type` / `status` / `rulebook` | ○    | 文書種別・成熟度・適用規約を示す。`status` は `draft` / `ready` / `deprecated` のいずれか              |
| `title`                        | ○    | 読み手が参照起点と認識できる生成ビューの文書名                                                         |
| `size`                         | ○    | 今後の scaffold で選択する成果物セットの規模（`small` / `medium` / `large`）。現在のドメイン数ではない |
| `groups`                       | ○    | 管理対象ドメインを、読み手が探す分類と順序でまとめる                                                   |

### 4.2. グループとサブグループ

- グループはドメインを探すための分類、サブグループはその中の探索単位である。`name` と、`domains` を直接置くか子 `groups` へ分けるかは「グループ分類の決め方」に従う。
- 配列順は索引ビューとサイドバーの表示順であり、成果物の依存順・Schedule の実行順・優先度を表さない。

### 4.3. ドメイン項目

| 項目       | 必須 | 目的・記述規約                                                     |
| ---------- | ---- | ------------------------------------------------------------------ |
| `domain`   | ○    | 実在する `dct-*.yaml` の `domain` と一致する論理識別子             |
| `name`     | ○    | 利用者向けの日本語表示名。索引ビューの表とサイドバーの表示名に使う |
| `overview` | ○    | ドメインが管理する成果物の関心領域を示す 1 文の概要                |

### 4.4. 生成ビューの確認要件

- 宣言した分類・順序・表示名・概要が索引ビューへ反映されていること。
- 各ドメインの表示から、対応するドメイン別カタログへ到達できること。
- サイドバーでも索引と同じドメイン名・順序で探せること。

## 5. 記述ガイド

### 5.1. メタ情報と規模の決め方

`size` ごとの成果物セットは、カタログ template（`docs/ja/specdojo/templates/dct-*-template.yaml`）の章と成果物の `min_size` で決まる。scaffold は `min_size` が `size` 以下（`small` < `medium` < `large`）か未指定のものを取り込む。規模は、`min_size` で増える成果物が要るかで比べて決める。

| 判断             | 良い例                                                            | 悪い例                                                  |
| ---------------- | ----------------------------------------------------------------- | ------------------------------------------------------- |
| プロジェクト識別 | 対象が prj-0001 なら、その索引 ID と `project_id` を対応させる    | 別プロジェクトから複製した ID を残す                    |
| 文書名           | `成果物カタログ` のように参照起点を示す                           | `第3回レビュー用` のように一時的な用途だけを表す        |
| 規模の変更       | 追加で必要な成果物セットを確認し、scaffold 方針の変更として決める | ドメインを 1 件足したことだけを理由に `size` を変更する |

### 5.2. グループ分類の決め方

- 分類の正本は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] の文書構成図とする。ルートグループはプロジェクト成果物とプロダクト成果物のような文書分類、サブグループは構成図が示す論理的なまとまり（要件〜設計、品質保証、運用など）に対応させる。
- 成果物リファレンスの章（rulebook 単位）と分類が食い違う場合は、構成ガイドを正とする。
- 複数の分類に当てはまるように見えるドメインは、構成図で置かれた枠に従い、判断理由を YAML コメントに残す。
- サブグループは、ルートグループ内のドメインが読み手の探索単位として 2 つ以上に分かれる場合に限る。

| 判断         | 良い例                                                                                         | 悪い例                                                            |
| ------------ | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 所属の決定   | 外部I/F仕様を、構成図で置かれている業務仕様群へ 1 か所だけ宣言する                             | 外部I/F仕様を業務仕様群とアーキテクチャの両方へ宣言する           |
| 階層の選択   | 業務仕様群・品質保証・運用のように探索目的で分ける。単独ドメインでも独立した探索単位なら分ける | 探索目的が同じドメインを件数だけで分割し、見出しを増やす          |
| 分類名の付与 | `品質保証` のように、含まれるドメインの共通の関心を名前にする                                  | `その他`・`追加分` のように、所属理由を示さない名前で受け皿を作る |

### 5.3. ドメインの選定と説明の書き方

- 管理対象を物理ファイル数や今後作る予定の文書から推測しない。
- `name` はドメインの表示名に限定し、状態・担当・件数など変動する情報や、親ノードの「成果物カタログ」を含めない。
- `overview` は管理対象の関心領域を 1 文で記述し、個別成果物を列挙しない。

| 項目       | 良い例                                                       | 悪い例                                                       |
| ---------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| `name`     | `データモデル`                                               | `成果物カタログ（データモデル）`、`データモデル（作成中）`   |
| `overview` | `データの概念、論理構造、分類、状態を表す成果物を管理する。` | `概念データモデル、論理データモデル、状態遷移表を管理する。` |

### 5.4. 変更時の影響確認

- ドメインの追加・削除・改名時は、索引とドメイン正本を同じ変更で整合させ、schema 検証・`catalog validate`・`catalog build` 後の「生成ビューの確認要件」で確かめる。

| 判断       | 良い例                                                                   | 悪い例                                                   |
| ---------- | ------------------------------------------------------------------------ | -------------------------------------------------------- |
| 追加・改名 | ドメイン正本と索引を揃え、参照先へ到達できることまで確認する             | 索引の表示名だけ変えて完了とする                         |
| 除去       | 同じドメインのカタログが残る間は索引から外さず、参照元の追従対象を決める | 個別成果物を非推奨にしただけでドメイン全体を索引から外す |
| 完了判断   | 構造・実在カタログとの整合・生成後の表示と到達をそれぞれ確かめる         | schema 検証だけで完了とする                              |

## 6. 禁止事項

| 禁止事項                                             | 理由                                               |
| ---------------------------------------------------- | -------------------------------------------------- |
| `generated/dct-index.md` を直接編集する              | 次回生成で失われ、正本と差異が生じるため           |
| 表示順や表示名を各 `dct-*.yaml` へ分散して持たせる   | ドメイン横断の編集意図が複数ファイルへ分散するため |
| 同じ `domain` を複数のグループへ宣言する             | 索引上の所属と行が重複するため                     |
| schema で許可されないキー・値・階層を独自に追加する  | 読み込み・検証・生成処理と互換性を保てないため     |
| 実在しないドメインを宣言する                         | 生成リンクの参照先を作れないため                   |
| `domains[]` の要素で `name` を `domain` より前に書く | サイドバーが表示名を解決できなくなるため           |
| 実在するドメインを索引宣言から省略する               | 管理対象カタログを参照起点から辿れなくなるため     |
| 個別成果物の配置・依存・完了条件を索引宣言へ記載する | ドメイン正本との二重管理になるため                 |
