# 成果物カタログ（インデックス）作成ルール

Deliverables Catalog Index Documentation Rules

本ドキュメントは、成果物カタログ索引の正本 `dct-index.yaml` の記述ルールです。ドメインを探すための分類・表示順・名称・概要と、scaffold に用いるプロジェクト規模の判断基準を定めます。

## 1. 全体方針

- `dct-index.yaml` は、プロジェクト規模とドメイン一覧の表示意図を保持する唯一の正本とする。
- `generated/dct-index.md` は `catalog build` が生成する表示専用ビューとし、直接編集しない。
- 各ドメインの成果物定義は `dct-<domain>.yaml` に置き、索引には表示名・概要・順序・グループだけを置く。
- `dct-index.yaml` の宣言ドメイン集合と実在する `dct-*.yaml` の `domain` 集合を一致させる。
- 共通事項は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] を正本とし、索引へ転載しない。要求・品質・受入・運用の詳細も、各ドメインの成果物へ委ねる。

## 2. 位置づけと用語定義

| 用語         | 正本・生成物                | 役割                                                       |
| ------------ | --------------------------- | ---------------------------------------------------------- |
| 索引宣言     | `dct-index.yaml`            | 規模、グループ、ドメイン順、表示名、概要を宣言する         |
| 索引ビュー   | `generated/dct-index.md`    | 宣言と実在カタログから生成されるプロジェクトの参照起点     |
| ドメイン正本 | `dct-<domain>.yaml`         | ドメインに属する成果物、配置、依存関係、完了条件を定義する |
| ドメイン表示 | `generated/dct-<domain>.md` | 1 ドメインの成果物定義を読みやすい Markdown として表示する |

- `domain` は論理的な管理単位であり、物理ファイル名ではなく各 `dct-*.yaml` の `domain` 値で識別する。
- 同じ `domain` を持つ物理分割ファイルが複数あっても、索引宣言と索引ビューでは 1 ドメインとして扱う。
- グループはドメインを探すための分類、サブグループはその中の探索単位を表す。宣言できる階層は schema に従う。
- グループとサブグループの順序は、成果物定義の依存順や Schedule の実行順を意味しない。

## 3. ファイル命名・ID規則

- 索引宣言はカタログディレクトリ直下の `dct-index.yaml` とする。
- 索引ビューは同ディレクトリの `generated/dct-index.md` に生成する。
- 索引宣言と索引ビューは `<project-id>:dct-index` を共有する。表示用の別 ID を作らず、既存の参照を維持する。
- ドメイン識別子や ID の文字種・形式は `docs/specdojo/schemas/v1/dct-index.schema.yaml` に従う。

## 4. 本文要件

構造・必須キー・型・列挙値・排他制約は `docs/specdojo/schemas/v1/dct-index.schema.yaml` を正本とし、本章は内容を判断するための目的を示す。独立 YAML のためメタ情報もトップレベルに置き、Frontmatter 専用章は設けない。コマンドの構文は [[specdojo:command-reference|コマンドリファレンス]] の「catalog / deliverable」、生成処理の詳細は `src/catalog/build.ts` を参照する。

### 4.1. ルート項目

| 項目                           | 必須 | 目的・記述規約                                                                |
| ------------------------------ | ---- | ----------------------------------------------------------------------------- |
| `id` / `project_id`            | ○    | 対象プロジェクトを識別し、他プロジェクトの索引との取り違えを防ぐ              |
| `type` / `status` / `rulebook` | ○    | 文書種別・成熟度・適用規約を示す。値の制約は schema、意味はメタ情報標準に従う |
| `title`                        | ○    | 読み手が参照起点と認識できる生成ビューの文書名                                |
| `size`                         | ○    | 今後の scaffold で選択する成果物セットの規模。現在のドメイン数ではない        |
| `groups`                       | ○    | 管理対象ドメインを、読み手が探す分類と順序でまとめる                          |

### 4.2. グループとサブグループ

- 各グループの `name` は必須とし、含めるドメインの共通の関心を示す。
- `domains` を直接置くか、子 `groups` へ分けるかは探索単位で判断する。サブグループは任意であり、ドメイン数だけで追加しない。
- 配列順を索引ビューとサイドバーの表示順として扱う。優先度・着手順・担当者順の管理には用いない。

### 4.3. ドメイン項目

| 項目       | 必須 | 目的・記述規約                                                     |
| ---------- | ---- | ------------------------------------------------------------------ |
| `domain`   | ○    | 実在する `dct-*.yaml` の `domain` と一致する論理識別子             |
| `name`     | ○    | 利用者向けの日本語表示名。索引ビューの表とサイドバーの表示名に使う |
| `overview` | ○    | ドメインが管理する成果物の関心領域を示す 1 文の概要                |

- 各要素のキーは `domain`、`name`、`overview` の順に書く。文書サイトのサイドバーは `domain` の直後の `name` を表示名として読むため、順序を入れ替えると表示名を解決できない。

### 4.4. 生成ビューの確認要件

- 宣言した分類・順序・表示名・概要が、読み手の参照起点となる索引ビューへ反映されていること。
- 各ドメインの表示から、対応するドメイン別カタログへ到達できること。物理分割されていても論理ドメイン単位で辿れること。
- サイドバーでも索引と同じドメイン名・順序で探せること。生成ビューの見出し・表・リンクを YAML に手書きで保持しない。

## 5. 記述ガイド

### 5.1. メタ情報と規模の決め方

対象プロジェクトと予定する成果物セットを確認してからメタ情報を記入する。`size` を変える場合は scaffold の対象範囲を見直す判断として扱い、変更理由を実行記録へ残す。

| 判断             | 良い例                                                            | 悪い例                                                  |
| ---------------- | ----------------------------------------------------------------- | ------------------------------------------------------- |
| プロジェクト識別 | 対象が prj-0001 なら、その索引 ID と `project_id` を対応させる    | 別プロジェクトから複製した ID を残す                    |
| 文書名           | `成果物カタログ` のように参照起点を示す                           | `第3回レビュー用` のように一時的な用途だけを表す        |
| 規模の変更       | 追加で必要な成果物セットを確認し、scaffold 方針の変更として決める | ドメインを 1 件足したことだけを理由に `size` を変更する |

### 5.2. グループ分類の決め方

- 分類の正本は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] の文書構成図とする。ルートグループはプロジェクト成果物とプロダクト成果物のような文書分類、サブグループは構成図が示す論理的なまとまり（要件〜設計、品質保証、運用など）に対応させる。
- 成果物リファレンスは個別成果物を引くための一覧であり、章の粒度は rulebook 単位で索引のグループとは一致しない。分類が食い違う場合は構成ガイドを正として宣言する。
- 1 つのドメインが複数の分類に当てはまるように見える場合は、構成図でそのドメインが置かれた枠に従って 1 か所だけへ置き、判断理由を YAML コメントに残す。
- サブグループに分けるのは、ルートグループ内のドメインが読み手の探索単位として 2 つ以上のまとまりに分かれる場合に限る。探索単位が 1 つなら `domains` を直接置く。

| 判断         | 良い例                                                                                         | 悪い例                                                            |
| ------------ | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 所属の決定   | 外部I/F仕様を、構成図で置かれている業務仕様群へ 1 か所だけ宣言する                             | 外部I/F仕様を業務仕様群とアーキテクチャの両方へ宣言する           |
| 階層の選択   | 業務仕様群・品質保証・運用のように探索目的で分ける。単独ドメインでも独立した探索単位なら分ける | 探索目的が同じドメインを件数だけで分割し、見出しを増やす          |
| 分類名の付与 | `品質保証` のように、含まれるドメインの共通の関心を名前にする                                  | `その他`・`追加分` のように、所属理由を示さない名前で受け皿を作る |

### 5.3. ドメインの選定と説明の書き方

- 管理対象は実在カタログの `domain` で判断し、物理ファイル数や今後作る予定の文書から推測しない。
- `name` はドメインの表示名に限定し、状態・担当・件数など変動する情報を含めない。サイドバーにも出るため、親ノードの「成果物カタログ」を繰り返さない。
- `overview` は管理対象の関心領域を 1 文で記述し、個別成果物を列挙しない。個別成果物はドメイン表示が正本である。

| 項目       | 良い例                                                                            | 悪い例                                                                 |
| ---------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `name`     | `データモデル`                                                                    | `成果物カタログ（データモデル）`、`データモデル（作成中）`             |
| `overview` | `データの概念、論理構造、分類、状態を表す成果物を管理する。`                      | `概念データモデル、論理データモデル、状態遷移表を管理する。`           |
| 管理単位   | データモデルのカタログが物理分割されていても同じ `domain` として 1 件だけ宣言する | 分割ファイルごとに別ドメインを作る、または同じドメインを複数回宣言する |

### 5.4. 変更時の影響確認

- ドメインの追加・削除・改名時は、索引とドメイン正本を同じ変更で整合させる。構造の適合は schema 検証、実在カタログとの整合は `catalog validate` で確認し、`catalog build` 後に「生成ビューの確認要件」を満たすことを確かめる。
- 改訂・廃止の共通原則は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] の「文書の改訂・廃止とライフサイクル変更管理」に従う。個別成果物の非推奨化とドメインの除去は分けて判断し、同じドメインのカタログが残る間は索引から外さない。
- ARC は分類と参照先の構造整合、QE は索引ビュー・サイドバーからの到達と表示、PM は残る追従作業の担当・実行順を確認する。プロジェクト固有の役割分担がある場合は、その定義に従う。

| 判断       | 良い例                                                           | 悪い例                                                    |
| ---------- | ---------------------------------------------------------------- | --------------------------------------------------------- |
| 追加・改名 | ドメイン正本と索引を揃え、参照先へ到達できることまで確認する     | 索引の表示名だけ変えて完了とする                          |
| 除去       | 同じドメインの残存カタログと参照元を調べ、追従対象を決める       | 個別成果物を非推奨にしただけでドメイン全体を索引から外す  |
| 完了判断   | 構造・実在ドメインとの整合・生成後の表示と到達をそれぞれ確かめる | YAML が読み込めること、または schema 検証だけで完了とする |

影響確認の記録は、`変更対象`（ドメインまたは項目）、`理由`（分類・規模を変える根拠）、`影響先`（参照元・生成表示・scaffold）、`担当 Role code`、`確認結果` の列で整理すると、未解消の追従作業を引き継げる。

## 6. 禁止事項

| 禁止事項                                             | 理由                                               |
| ---------------------------------------------------- | -------------------------------------------------- |
| `generated/dct-index.md` を直接編集する              | 次回生成で失われ、正本と差異が生じるため           |
| 表示順や表示名を各 `dct-*.yaml` へ分散して持たせる   | ドメイン横断の編集意図が複数ファイルへ分散するため |
| 同じ `domain` を複数のグループへ宣言する             | 索引上の所属と行が重複するため                     |
| schema で許可されないキー・値・階層を独自に追加する  | 読み込み・検証・生成処理と互換性を保てないため     |
| 実在しないドメインを宣言する                         | 生成リンクの参照先を作れないため                   |
| `domains[]` の要素で `name` を `domain` より前に書く | サイドバーが表示名を解決できなくなるため           |
| 実在するドメインを索引宣言から省略する               | 管理対象カタログを参照起点から辿れなくなるため     |
| 個別成果物の配置・依存・完了条件を索引宣言へ記載する | ドメイン正本との二重管理になるため                 |
