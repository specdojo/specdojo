# 個別システム設計（SYSD）作成ルール

System Design Topic Documentation Rulebook

`sysd-<term>.md` の構造・責務・制約・検証観点を定める。実装・検証・運用判断に使う個別設計と、子設計を束ねる hub を対象とする。

## 1. 全体方針

- 一冊は一つの設計関心事に絞る。同じ共通設計に属する複数 provider・方式は、hub と子設計に分冊できる。
- コード・設定全文は一次情報、運用判断は `opd-*`、操作手順は `opr-*` を参照する。
- **共通の運用**: 役割は適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱い、業務の検証に含めない。

## 2. 位置づけ

| 文書                        | 正本とする内容                       |
| --------------------------- | ------------------------------------ |
| `sysd-index`                | システム設計全体への入口             |
| `sysd-cross-cutting-policy` | 複数トピックの必須・禁止ルール       |
| `sysd-critical-flows`       | 最大5件の事故予防フロー              |
| `sysd-<term>`（hub）        | 共通の目的・境界、子設計の選択条件   |
| `sysd-<term>`（子設計）     | 一つの方式・provider・機能の詳細設計 |

## 3. ファイル命名・ID規則

- ファイル名は `sysd-<term>.md`、ID は `sysd-<term>`。`<term>` は英小文字・数字・ハイフンで設計関心事を表す。
- hub と子設計は同じディレクトリに置く。provider 別なら `sysd-<provider>-<topic>.md` のように選択軸を含める。
- 索引・横断ルール・重要フローは本書の対象外とする。

## 4. 推奨 Frontmatter 項目

共通項目の必須性・型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。

- `type` は `architecture`、`rulebook` は `specdojo:sysd-rulebook`。
- 子設計の `part_of` は必須とし、hub の ID を参照して子設計一覧と一致させる。
- `based_on` は設計判断へ直接利用した成果物 ID を任意で示す。

## 5. 本文要件

章構成は任意だが、次の観点を追跡可能にする。観点表と記述ガイドで作成判断ができるため、recipe・template は不要とする。

| 観点                         | hub      | 子設計・単独設計 | 内容                                   |
| ---------------------------- | -------- | ---------------- | -------------------------------------- |
| 目的・適用範囲               | ○        | ○                | 対象、対象外、利用者                   |
| 設計方針・採用理由           | ○        | ○                | 選択理由、前提、代替との境界           |
| 責務分担・境界               | ○        | ○                | コンポーネント、人、外部システムの責務 |
| 全体構成・主要フロー         | 推奨     | ○                | 構成要素、データ・制御の流れ、永続化点 |
| 設定・インターフェース       | 導線のみ | 必要時○          | SSOT の所在、解決規則、互換性          |
| 失敗時・再実行・セキュリティ | 導線のみ | 必要時○          | 失敗境界、復旧条件、権限制約           |
| 子設計一覧                   | ○        | -                | 選択条件、責務、参照先                 |
| 検証観点・関連文書           | ○        | ○                | テスト、運用、横断ルールへの導線       |

## 6. 記述ガイド

### 6.1. 目的・適用範囲

- 対象・対象外と利用者を1〜3段落で示す。
- 横断ルール・運用方針・手順への委譲先を区別する。
- 現行と将来構想を分け、未確定事項は共通ラベルで論点と影響を示す。

### 6.2. 設計方針・責務境界

- 採用理由・制約・責務外を判定可能にする。
- 責務表の列は構成要素、責務、責務外、参照する SSOT とする。
- 横断の MUST / MUST NOT は `sysd-cross-cutting-policy` の Rule ID を参照する。

### 6.3. hub と子設計

- 子設計一覧の列は子設計 ID、対象、固有責務、選択条件とする。
- provider 固有の認証・モデル・設定・制限シグナルは子設計に置く。
- 良い例: 「Codex 利用時は Codex 子設計を参照」。悪い例: hub に全 provider の設定全文を並べる。

### 6.4. 構成・フロー・設定

- 図は主要コンポーネントと境界に用い、クラス・関数単位へ展開しない。
- 設定は項目の意味・解決順序・検証条件を示す。
- 再実行性・順序・補償・監査が事故時に問題になるフローは `sysd-critical-flows` に切り出す。

### 6.5. 検証観点・関連文書

- 設計制約ごとに、コード・設定検証・単体／統合テスト・レビューから確認方法を選び、手順と期待結果を示す。
- `sysd-index`、横断ルール、必要な重要フロー、テスト設計、OPD / OPR へ導く。
- 参照先がなければ `（なし）` または共通の未確定ラベルを記す。

## 7. 禁止事項

| 禁止事項                                      | 理由                                 |
| --------------------------------------------- | ------------------------------------ |
| hub に子設計の設定全文を再掲する              | SSOT が分散するため                  |
| 横断ルールを複数の `sysd-<term>` に複製する   | 変更時に不整合となるため             |
| 運用コマンドを長い手順として記載する          | OPR の責務を侵食するため             |
| 失敗・再実行・権限・検証観点を省略する        | 実装とテストの判断材料が欠落するため |
| 親子関係のない設計を便宜的に同じ hub へ束ねる | 選択軸と責務境界が不明になるため     |
