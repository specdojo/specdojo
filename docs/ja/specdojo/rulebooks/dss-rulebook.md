# デザインシステム（DSS）作成ルール

Design System Specification (DSS) Authoring Rule

GUI 共通の表現を揃え、部品・レイアウトの選択と適合確認に使う設計の決まりを定めます。

## 1. 全体方針

- 対象はトークン・部品・レイアウト・状態表示・アクセシビリティです。
- 各決まりに適用条件・必須または禁止する内容・検証方法を示します。
- デザインツール、トークン定義、部品カタログに正本があれば所在・版・参照キーを示し、転載しません。正本がない範囲だけ本書で定義します。
- 利用者の課題と採用理由を結び、操作性目標から決まり、試作・実装の検証へ辿れるようにします。
- **実践の型の構成**: 章構成・判断基準・完成例が揃うため、`recipe`・`template` は `not-needed` とします。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。文書の整形・lint はリポジトリの検証で扱い、業務の検証に含めません。

## 2. 位置づけ

| 型                                                                        | 持つ内容                                                     | DSS との境界                                                   |
| ------------------------------------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------- |
| [[specdojo:uis-rulebook\|画面仕様（UIS）]]                                | 画面ごとの利用目的・項目・操作・遷移・エラーの要点と回復操作 | DSS は業務上の操作や遷移を追加せず、その見せ方を定める         |
| [[specdojo:nfr-usability-rulebook\|操作性要件]]                           | 完了率・誤操作率・操作時間などの測れる目標と評価条件         | 目標は NFR、目標を満たす設計の決まりは DSS に置く              |
| [[specdojo:sysd-cross-cutting-policy-rulebook\|システム設計の横断ルール]] | エラー契約・リトライ・認可・ログなど実装の共通ルール         | DSS はエラー等の表示を扱い、通信や業務処理の成立条件は扱わない |
| [[specdojo:sysd-index-rulebook\|システム設計の全体構成]]                  | 設計と実装の正本への導線                                     | DSS とトークン・部品の正本への入口を載せる                     |

画面ごとのワイヤーフレームは保守せず、UIS・DSS から作る試作をプロダクトリポジトリに置いて検証します。採用する変更は UIS・DSS・実装の該当する正本へ反映します。

## 3. ファイル命名・ID規則

- 略号は `dss`、ファイル名・ローカル ID は `dss-<term>` とし、[[specdojo:id-and-file-naming-standard|ドキュメントIDおよびファイル命名標準]] に従います。
- 複数系列から参照する共通定義の既定は `dss-common.md` / `dss-common` です。端末群等で適用範囲が独立する場合だけ `dss-store-gui` のように分けます。
- プロダクト成果物は `docs/ja/product/040-system-design/`、プロジェクト限定なら設計ドメイン配下に置き、ID は `<project-id>:dss-<term>` とします。分冊時は共通定義を参照します。
- 規則を個別に追跡する ID は、文書内で一意の `dss-<カテゴリ>-<連番>`（例: `dss-a11y-01`）とします。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- `specdojo.type` は `architecture`、`specdojo.rulebook` は `specdojo:dss-rulebook` とします。
- `specdojo.based_on` は直接根拠とした要求・仕様の ID、`specdojo.relations.satisfies` は操作性要件等との対応に用います。

## 5. 本文要件

以下の章を番号付きで配置します。すべて必須とし、対象外の観点は理由を記載します。

| 順序 | 章                       | 内容                                                           |
| ---- | ------------------------ | -------------------------------------------------------------- |
| 1    | 目的・適用範囲           | 利用者、課題、対象 GUI・端末・表示環境、対象外、採用理由       |
| 2    | 正本と適用方法           | 領域ごとの正本・版・参照キー・更新責任、試作と実装への適用方法 |
| 3    | デザイントークン         | 色・文字・余白・角丸等の用途、値または正本参照、利用制約       |
| 4    | 部品の使い方             | 選択条件、バリエーション、組合せ、禁止する使い方               |
| 5    | レイアウトの型           | 適用条件、情報の優先順位、幅・拡大時の振る舞い                 |
| 6    | 状態の見せ方             | 通常・エラー・無効・読み込み中・空・完了の表現と通知           |
| 7    | アクセシビリティ         | キーボード、フォーカス、読み上げ、色以外の識別、視認性の決まり |
| 8    | 検証・変更管理と関連文書 | 要求と決まりの対応、確認方法・合格条件・担当、例外と変更影響   |

## 6. 記述ガイド

各節は「本文要件」の同名の章に対応します。

### 6.1. 目的・適用範囲

- 利用者の課題と色・文字・部品等の採用理由を結び付けます。
- GUI、入力手段、画面幅、テーマ、支援技術の確認範囲を表にします。物理寸法と CSS viewport 幅を区別します。
- 対象外を示し、画面固有の業務仕様は UIS、測れる利用結果の目標は NFR を参照します。

判断基準: 対象環境と規則の適用境界を判断できること。

- 良い例: 「店頭の読み違いを防ぐため主要金額を大きくする。ライトテーマ、CSS viewport 幅 360px 以上の販売 GUI が対象で、レシートは対象外。」
- 悪い例: 「全端末で使いやすく美しくする。」（利用者・環境・採用理由が不明）

### 6.2. 正本と適用方法

- 推奨列: 領域 / 正本の所在 / 版・参照キー / 更新責任。デザインツールはファイルとライブラリ、コードはリポジトリと相対パスを特定します。
- 正本が分かれる領域では優先順位を定めます。
- UIS と DSS から作る試作の置き場所、実装へ採用する際の反映先、入力文書と試作の版の記録方法を示します。

判断基準: 同じ版の定義へ到達し、値を重複保守せず試作・実装に適用できること。

- 良い例: 「色はプロダクトリポジトリの `design/tokens.json` の `color.action` を参照し、検証記録に commit を残す。」
- 悪い例: 「最新のデザインに合わせる。」（所在・版がなく再現不能）

### 6.3. デザイントークン

- 推奨列: 名前 / 用途 / 値・単位または参照キー / 制約。色・文字・余白・角丸・操作領域・フォーカス枠等を扱います。
- 色は前景と背景の許可する組合せ、文字はサイズ・行高・太さ、寸法は単位と拡大時の扱いを定めます。複数テーマには切替条件を示します。
- 既存の用途に合わない場合はトークンの追加を検討し、画面内で独自値を増やしません。

判断基準: 値を推測せず用途に合うトークンを選べること。

- 良い例: 「`text-caption` は補足専用。金額・エラー・操作名には使わず、寸法は相対値で拡大に追従させる。」
- 悪い例: 「小さい文字と青を使う。」（名前・単位・利用制約がない）

### 6.4. 部品の使い方

- 推奨列: 規則 ID・部品 / 選択条件・使い方 / 禁止・制約。ボタン・入力・表・ダイアログを含め、不使用の理由を示します。
- 選択条件、バリエーション、ラベル、寸法の参照先、組合せを示します。業務上の操作名・確認の要否は UIS に委ねます。
- 状態表示・アクセシビリティは共通規則を参照し、部品固有の条件だけ補います。

判断基準: 同じ用途に同じ部品が選ばれ、禁止する組合せも判別できること。

- 良い例: 「一つの操作群の主操作は一つ。補助操作は枠付きとし、ラベルは UIS の操作名を使う。」
- 悪い例: 「重要そうな操作は塗りボタンにする。」（選択条件と優先度が不明）

### 6.5. レイアウトの型

- 一覧・入力・確認等の再利用可能な型を選びます。推奨列: 規則 ID・型 / 適用条件 / 配置と幅変化の決まり。
- 情報の優先順位・幅の境界、列切替、折り返し、スクロール、拡大時の扱いを定めます。画面別の座標・配置図は作りません。
- 視覚と読み上げ・Tab の順序を揃え、長文・大量データ・最大桁の金額等が収まらない場合も操作を保つ条件を書きます。

判断基準: 境界の前後や拡大時にも情報の意味と操作順序を保てること。

- 良い例: 「入力と集計は幅 960px 以上で二列、未満で一列。入力、集計、操作の順を保ち、操作群は折り返す。」
- 悪い例: 「販売画面の確定ボタンは座標 (800, 600) に置く。」（画面固有で再利用できない）

### 6.6. 状態の見せ方

- 推奨列: 状態 / 視覚表現 / 通知・フォーカス / 操作上の注意。通常・エラー・無効・読み込み中・空・完了を含めます。
- 原因・対処・次の操作は UIS を参照し、表示位置、色以外の識別、通知時機、フォーカスと入力値の保持を定めます。
- 通信中・失敗を空と区別し、重複操作防止とフォーカス保持を両立させます。再送条件は横断ルールに委ねます。

判断基準: 利用者が状態と次の操作を認識でき、支援技術にも変化が伝わること。

- 良い例: 「エラーは枠と『エラー』の文字を併用する。送信時は最初の不正入力へフォーカスし、値を保持する。」
- 悪い例: 「失敗時は赤くし、一定時間後に消す。」（色依存で回復前に情報を失う）

### 6.7. アクセシビリティ

- キーボード操作、フォーカスの出入り、ラベルと説明の関連付け、読み上げ通知、色以外の識別を必須とします。
- コントラスト、操作領域、文字拡大、動きの抑制を要求・規格と評価条件に結び付け、設計値と操作性目標を区別します。
- 推奨列: 規則 ID / 必須の決まり / 確認条件。支援技術とブラウザの組合せ、版の記録、対象状態、手動確認する操作を特定します。

判断基準: 同じ環境・操作で合否を再現でき、一部の数値だけで規格全体への適合を宣言していないこと。

- 良い例: 「ダイアログの Tab は内部を循環し、Escape で中止して起点へ戻す。起点消失時は次の操作群へ移す。」
- 悪い例: 「アクセシビリティに配慮する。」（確認する操作と合否の条件がない）

### 6.8. 検証・変更管理と関連文書

- 推奨列: 対象の規則・正本キー / 対応する要求 / 確認方法 / 合格条件 / 担当。トークンの静的確認・部品表示・試作操作・利用者評価を使い分け、規則への適合と操作性目標の達成を別に確かめます。
- 試作確認、規則検証、利用者評価、設計採用の順と終了条件を示します。未作成の入力・試験文書は想定 ID と不足する論点・影響、未確定時に止める段階を書きます。
- 変更時はトークン・部品・適用画面・検証への影響を示します。例外には対象規則、理由、影響範囲、検証結果、期限、判断記録と失効時の扱いを残します。
- UIS、操作性要件、設計の入口・横断ルール、受入・試験への導線を置きます。

判断基準: 証跡と未解決事項を添えて採用判断へ進められ、更新後も規則から検証・判断記録へ辿れること。

- 良い例: 「試作で UIS の全操作と DSS の型を対応付け、規則検証の不適合を修正・再確認する。利用者評価を要件の目標・条件と照合し、未達の必須条件があれば採用を保留する。」
- 悪い例: 「試作ができたら採用する。」（要件照合と検証結果がなく採否を追えない）

## 7. 禁止事項

| 禁止事項                                                     | 理由                                      |
| ------------------------------------------------------------ | ----------------------------------------- |
| 画面ごとの目的・項目・操作・遷移、業務上の判定条件を定義する | UIS と責務が重複するため                  |
| 画面ごとのワイヤーフレームを文書として保守する               | UIS・DSS と試作の間に別の正本ができるため |
| 実装の共通ルールや操作性の達成目標を再定義する               | 横断ルールや NFR と競合するため           |
| デザインツール・トークン定義・部品カタログの内容を転載する   | 正本の更新が反映されず二重管理になるため  |
| 値・選択条件・検証方法を示さず、抽象的な形容だけで規則を書く | 実装と合否判断が揃わないため              |
