# デザインシステム（DSS）作成ルール

Design System Specification (DSS) Authoring Rule

GUI の画面をまたいで見た目と操作時の表現を揃える、デザインシステムの記述ルールです。実装者・生成 agent が部品とレイアウトの型を選び、品質保証担当者が適合を確認できる設計の決まりを定めます。

## 1. 全体方針

- 基本の値（デザイントークン）、部品の使い方、レイアウトの型、状態表示、アクセシビリティを対象にします。
- 各決まりには適用条件・必須または禁止する内容・検証方法を記載し、「見やすくする」だけで終わらせません。
- デザインツール、トークン定義、部品カタログに正本がある場合は、所在・対象の版・参照キーを示し、その値や仕様を転載しません。正本がない範囲だけ本書で定義します。
- 利用者の課題と設計の採用理由を結び、操作性の目標から決まり、試作・実装の検証へ辿れるようにします。

## 2. 位置づけと用語定義

### 2.1. 他の型との分担

| 型                                                                        | 持つ内容                                                     | DSS との境界                                                   |
| ------------------------------------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------- |
| [[specdojo:uis-rulebook\|画面仕様（UIS）]]                                | 画面ごとの利用目的・項目・操作・遷移・エラーの要点と回復操作 | DSS は業務上の操作や遷移を追加せず、その見せ方を定める         |
| [[specdojo:nfr-usability-rulebook\|操作性要件]]                           | 完了率・誤操作率・操作時間などの測れる目標と評価条件         | 目標は NFR、目標を満たす設計の決まりは DSS に置く              |
| [[specdojo:sysd-cross-cutting-policy-rulebook\|システム設計の横断ルール]] | エラー契約・リトライ・認可・ログなど実装の共通ルール         | DSS はエラー等の表示を扱い、通信や業務処理の成立条件は扱わない |
| [[specdojo:sysd-index-rulebook\|システム設計の全体構成]]                  | 設計と実装の正本への導線                                     | DSS とトークン・部品の正本への入口を載せる                     |

画面ごとのワイヤーフレームは文書として保守しません。UIS と DSS を入力として agent 等が試作を作り、プロダクトのリポジトリに置きます。試作は決まりの検証に使い、変更を採用するときは UIS・DSS・実装の該当する正本へ反映します。

### 2.2. 用語

| 用語             | 定義                                                                           |
| ---------------- | ------------------------------------------------------------------------------ |
| デザイントークン | 色・文字・余白・角丸等の再利用する値に、用途が分かる名前を付けたもの           |
| 部品             | ボタン・入力・表・ダイアログなど、複数画面で共通の表現・操作を担う単位         |
| レイアウトの型   | 特定画面の配置図ではなく、情報や操作を組み立てる再利用可能な配置・幅変化の規則 |

## 3. ファイル命名・ID規則

- 略号は `dss`、ファイル名とローカル ID は `dss-<term>` とします。命名の共通規則は [[specdojo:id-and-file-naming-standard|ドキュメントIDおよびファイル命名標準]] に従います。
- 既定は `dss-common.md` / `dss-common` です。画面仕様など複数系列から参照する共通定義として `common` を用い、端末群等で適用範囲が独立する場合だけ `dss-store-gui` のように分けます。
- プロダクト成果物は `docs/ja/product/040-system-design/` へ置きます。プロジェクト限定の成果物はプロジェクトの設計ドメイン配下に置き、ID を `<project-id>:dss-<term>` とします。分冊時は共通定義への参照を示し、値を複製しません。
- 成果物の規則を個別に追跡する場合は `dss-<カテゴリ>-<連番>`（例: `dss-a11y-01`）を文書内で一意に付けます。

## 5. 本文要件

以下の章を番号付きで配置します。すべて必須とし、対象外の観点は理由を記載します。

| 順序 | 章                       | 内容                                                           |
| ---- | ------------------------ | -------------------------------------------------------------- |
| 1    | 目的・適用範囲           | 利用者、課題、対象 GUI・端末・表示環境、対象外、採用理由       |
| 2    | 正本と適用方法           | 領域ごとの正本・版・参照キー・更新責任、試作と実装への適用方法 |
| 3    | デザイントークン         | 色・文字・余白・角丸等の用途、値または正本参照、利用制約       |
| 4    | 部品の使い方             | 選択条件、バリエーション、組合せ、禁止する使い方               |
| 5    | レイアウトの型           | 適用条件、情報の優先順位、幅・拡大時の振る舞い                 |
| 6    | 状態の見せ方             | 通常・エラー・無効・読み込み中・空・完了の表現と通知           |
| 7    | アクセシビリティ         | キーボード、フォーカス、読み上げ、色以外の識別、視認性の決まり |
| 8    | 検証・変更管理と関連文書 | 要求と決まりの対応、確認方法・担当、例外と更新の入口           |

## 6. 記述ガイド

各節は「本文要件」の同名の章に対応します。共通の要求・用語・実装契約は上位文書を正本とし、DSS には参照と設計上の選択だけを残します。

### 6.1. 目的・適用範囲

- 誰のどの課題を解くかを示し、色・文字・部品等の採用理由を結び付けます。
- 対象 GUI、入力手段、画面幅、テーマ、支援技術の確認範囲を表で定めます。端末の物理寸法と CSS viewport 幅を混同しません。
- 対象外を明記し、画面固有の業務仕様は UIS、測れる利用結果の目標は NFR を参照します。

判断基準は、実装者が対象環境と規則の適用境界を判断できることです。

- 良い例: 「店頭で金額を読み違えないよう主要金額の文字を大きくする。ライトテーマ、CSS viewport 幅 360px 以上の販売 GUI を対象とし、レシートは対象外。」
- 悪い例: 「すべての端末で使いやすく美しい画面にする。」（利用者・環境・採用理由を判断できない）

### 6.2. 正本と適用方法

- 推奨表は「領域 / 正本の所在 / 版・参照キー / 更新責任」です。デザインツールはファイルとライブラリ、コードはリポジトリと相対パスを特定し、閲覧権限の取得先も必要に応じて示します。
- 正本が分かれる場合は領域ごとの優先順位を決め、不一致の報告先を指定します。正本がない範囲は DSS で定義することを明記します。
- UIS と DSS から作る試作の置き場所、実装へ採用する際の反映先、入力文書と試作の版の記録方法を示します。

判断基準は、同じ版の定義へ到達でき、重複した値を保守せず試作・実装に適用できることです。

- 良い例: 「色はプロダクトリポジトリの `design/tokens.json` の `color.action` を参照し、検証記録に commit を残す。不一致は ARC へ報告する。」
- 悪い例: 「最新のデザインファイルに合わせる。」（所在・版・更新責任がなく、再現できない）

### 6.3. デザイントークン

- 推奨表は「名前 / 用途 / 値・単位または参照キー / 制約」です。色・文字・余白・角丸に加え、操作領域とフォーカス枠等に必要な値を扱います。
- 色は前景と背景の許可された組合せ、文字はサイズ・行高・太さ、寸法は単位と拡大時の扱いを定めます。テーマを複数持つ場合は切替条件も記載します。
- 外部に正本がある値は転載せず、用途と利用制約を記載します。既存の用途に合わない場合の追加依頼先を示し、画面内での独自値の増殖を防ぎます。

判断基準は、利用者が値を推測せず用途に合うトークンを選べることです。

- 良い例: 「`text-caption` は補足専用。金額・エラー・操作名には使わず、寸法は相対値で拡大に追従させる。」
- 悪い例: 「小さい文字と青を使う。」（名前・単位・利用制約がない）

### 6.4. 部品の使い方

- 推奨表は「規則 ID・部品 / 選択条件・使い方 / 禁止・制約」です。ボタン・入力・表・ダイアログを含め、使わない部品は理由を示します。
- 選択条件、バリエーション、ラベル、寸法の参照先、組合せを記載します。業務上の操作名や確認の要否は UIS に委ねます。
- 状態表示とアクセシビリティの共通規則を参照し、部品ごとに違いがある条件だけ補います。

判断基準は、同じ用途に同じ部品が選ばれ、禁止する組合せも判別できることです。

- 良い例: 「一つの操作群の主操作は一つ。補助操作は枠付きとし、ラベルは UIS の操作名を使う。」
- 悪い例: 「重要そうな操作をすべて塗りボタンにする。」（選択条件が揃わず、優先度を区別できない）

### 6.5. レイアウトの型

- 一覧・入力・確認等、複数画面に再利用できる型を選び、推奨表を「規則 ID・型 / 適用条件 / 配置と幅変化の決まり」とします。
- 情報の優先順位と幅の境界を決め、列の切替、折り返し、スクロール、拡大時の扱いを指定します。画面別の座標や配置図は作りません。
- 視覚上の順序と読み上げ・Tab 順序を揃え、長文・大量データ・最大桁の金額等が収まらない場合も操作を失わない条件を書きます。

判断基準は、境界の前後や拡大時にも情報の意味と操作順序を保てることです。

- 良い例: 「入力と集計は幅 960px 以上で二列、未満で一列。入力、集計、操作の順を保ち、操作群は折り返す。」
- 悪い例: 「販売画面の確定ボタンを座標 (800, 600) に置く。」（画面固有の配置であり、再利用可能な型にならない）

### 6.6. 状態の見せ方

- 推奨表は「状態 / 視覚表現 / 通知・フォーカス / 操作上の注意」です。通常・エラー・無効・読み込み中・空・完了を含めます。
- 原因・対処・次の操作は UIS を参照し、DSS では表示位置、色以外の識別、通知のタイミング、フォーカスと入力値の保持を定めます。
- 通信中や失敗を空と区別し、読み込み中の重複操作防止とフォーカス保持を両立させます。通信の再送条件は横断ルールに委ねます。

判断基準は、利用者が現在の状態と次の操作を認識でき、支援技術にも変化が伝わることです。

- 良い例: 「エラーは枠と『エラー』の文字を併用する。送信時は最初の不正入力へフォーカスし、値を保持する。」
- 悪い例: 「失敗時は赤くし、一定時間後に消す。」（色に依存し、確認・回復前に情報が失われる）

### 6.7. アクセシビリティ

- キーボード操作、フォーカスの出入り、ラベルと説明の関連付け、読み上げ通知、色以外の識別を必須の決まりとして記載します。
- コントラスト、操作領域、文字拡大、動きの抑制は適用する要求・規格と評価条件に結び付けます。設計値と操作性の達成目標を区別し、目標を複製しません。
- 推奨表は「規則 ID / 必須の決まり / 確認条件」です。支援技術とブラウザの組合せ、版の記録、対象の状態、手動確認が必要な操作を特定します。

判断基準は、確認者が同じ環境と操作で合否を再現でき、数値の一部だけで規格全体への適合を宣言していないことです。

- 良い例: 「ダイアログの Tab は内部を循環し、Escape で中止して起点へ戻す。起点消失時は次の操作群へ移す。」
- 悪い例: 「アクセシビリティに配慮する。」（確認する操作と合否の条件がない）

### 6.8. 検証・変更管理と関連文書

- 「対象の規則・正本キー / 対応する要求 / 確認方法 / 担当」の表で、静的確認・部品表示・試作操作・利用者評価を使い分けます。規則への適合だけで操作性目標の達成とみなしません。
- 試作確認、規則検証、利用者評価、設計採用の順と終了条件を示します。未作成の入力や試験文書には、想定 ID・定義責任・確認期限・未確定時に止める段階を書きます。
- 変更時はトークン・部品・適用画面・検証への影響を調べます。検証不適合・変更提案・例外判断の報告先と責任を分け、例外には対象規則、理由、影響範囲、承認 Role、期限、判断記録と失効時の扱いを示します。
- 関連文書には UIS、操作性要件、設計の入口・横断ルール、受入・試験への導線を置きます。実在する文書は project 修飾 ID の wikilink、未作成なら想定 ID のインラインコードとします。

判断基準は、必要な証跡と未解決事項を添えて採用判断へ進められ、更新後も規則から検証・判断記録へ辿れることです。責務は [[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] の Role code で示します。

- 良い例: 「QE が規則ごとの検証結果を試験記録に残し、BA が要件と受入条件を確認した後、PO が未解決事項と残余リスクを確認して基準版の採用を判断する。」
- 悪い例: 「試作ができたらそのまま採用する。」（要件の確認・検証結果・承認責任がなく、採用可否を追えない）

## 7. 禁止事項

| 禁止事項                                                     | 理由                                      |
| ------------------------------------------------------------ | ----------------------------------------- |
| 画面ごとの目的・項目・操作・遷移、業務上の判定条件を定義する | UIS と責務が重複するため                  |
| 画面ごとのワイヤーフレームを文書として保守する               | UIS・DSS と試作の間に別の正本ができるため |
| 実装の共通ルールや操作性の達成目標を再定義する               | 横断ルールや NFR と競合するため           |
| デザインツール・トークン定義・部品カタログの内容を転載する   | 正本の更新が反映されず二重管理になるため  |
| 値・選択条件・検証方法を示さず、抽象的な形容だけで規則を書く | 実装と合否判断が揃わないため              |

## 8. 運用ルール

- 本文要件や記述ガイドを変えたら、Frontmatter で宣言した完成例の同名の章と必須項目を確認します。正本への参照で済む値や規則を追加転載しません。
- 本型は Markdown の設計文書であり、章ごとの判断基準と完成例で作成できるため、recipe と template は不要とします。要否を見直す場合は Frontmatter の宣言も更新します。
- 改訂時は [[specdojo:rulebook-authoring-standard|Rulebook 記述標準]]、完成例は [[specdojo:sample-authoring-standard|Sample 記述標準]] に照らし、Frontmatter・Markdown 検査と grade で整合を確認します。`ready` への昇格と公開は人間の PO が判断し、根拠と承認を実行記録へ残します。
- 名称・略号・配置を変える場合は、命名標準、成果物・配置のリファレンス、文書サイトの導線、種類を列挙するレビュー観点の適用設定を確認します。保護された設定の変更が必要なら変更案を申し送り、executor は変更しません。
