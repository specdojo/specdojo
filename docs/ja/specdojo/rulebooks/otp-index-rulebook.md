# 運用切替計画（ハイパーケア含む） 作成ルール

Operations Transition Plan Documentation Rules

本ドキュメントは、`otp-index`（運用切替計画の入口・共通SSOT）を一貫した粒度で作成するためのルールを定義する。

## 1. 全体方針

- `otp-index` は切替後の運用が安定するまでの共通方針と判断軸（監視・窓口・初期増員体制・クローズ条件）を定義する入口とする。本書の初期増員体制は、ハイパーケア期間の当番と SLA を指す。
- 対象別の運用詳細は `otp-<term>` に委譲し、`otp-index` には共通運用と導線だけを書く。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直さない。

## 2. 位置づけ

| 文書                       | 役割                                                |
| -------------------------- | --------------------------------------------------- |
| `mip-index`                | 移行計画・成功条件・ハイパーケア方針の合意          |
| `cop-index`                | 当日切替の実行計画（Runbook）。本書はその後を受ける |
| `otp-index`                | 運用切替の共通設計（本書）                          |
| `otp-<term>`               | 対象別の運用詳細（監視、窓口、当番、手順差分）      |
| `mtp-index` / `mtp-<term>` | リハーサル計画と証跡                                |

## 3. ファイル命名・ID規則

- **文書 ID**: プロジェクト固有の成果物は `<project-id>:otp-index`（例: `prj-0001:otp-index`）とし、成果物カタログの宣言と一致させる。
- **ファイル名**: 成果物カタログの `path` に従い、`otp-index.md` を基本とする。
- **分冊**: 対象別の分冊は `<project-id>:otp-<term>` とし、`<term>` は英小文字の kebab-case とする。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。

- `specdojo.type` は `operations`、`specdojo.rulebook` は `specdojo:otp-index-rulebook` とする。
- `specdojo.based_on` には、実際に読んで根拠とした作成済み文書（`cop-index` など）の ID を記載する。

```yaml
---
specdojo:
  id: prj-0001:otp-index
  type: operations
  status: draft
  rulebook: specdojo:otp-index-rulebook
  based_on:
    - prj-0001:cop-index
---
```

## 5. 本文要件

本文は次の 11 章をすべて必須とする。

| 章                              | 受入条件                                                                         |
| ------------------------------- | -------------------------------------------------------------------------------- |
| 概要（index）                   | 運用安定化の目的と適用範囲を 1〜3 行で示し、詳細が `otp-<term>` にあると分かる   |
| 監視/アラート                   | 監視対象ごとに指標・閾値・通知先・初動ルールが表で分かる                         |
| バックアップ/リストア           | 頻度・保管先・保持期間・リストア責任者が分かる                                   |
| 権限/アカウント移行             | 旧新の権限差分・移行タイミング・検証方法が分かる                                 |
| 運用手順の変更点                | 手順ごとに旧・新・変更理由・影響・参照先が表で分かる                             |
| 問合せ窓口/一次対応             | 受付時間・チャネル・優先度分類・エスカレーション条件が分かる                     |
| 障害対応フロー                  | 判断・連絡・復旧・報告の流れと指揮系統が分かる                                   |
| 初期増員体制（期間・当番・SLA） | ハイパーケア期間・当番と時間帯・SLA・終了判断者が表で分かる                      |
| 旧システムの停止/参照方針       | 停止時期・参照可否と期間・アーカイブ方針が分かる                                 |
| 移行完了後のクローズ条件        | 測定可能な完了条件・クローズ判断者・最終報告物が分かる                           |
| 関連ドキュメント（必須）        | 各 `otp-<term>` と前後の文書への導線がある。分冊が無ければ `（本書のみ）` と書く |

## 6. 記述ガイド

完成例の全体像は Frontmatter の `sample` で宣言された sample を参照する。各章は次の判断基準に従う。

- **事実と仮定を分ける**: 合意済みの値（期間・SLA・閾値）と仮置きの値を混ぜない。仮置きは `_ASSUMPTION_`、未合意は `_UNDECIDED_` を付ける。
- **判断者を書く**: エスカレーション先・ハイパーケア終了・クローズは、判断する役割を章内に書く。
- **閾値と期限で書く**: 「早めに」「状況に応じて」ではなく、数値・時間・件数で書く。

| 章                       | 良い例                                                                      | 悪い例                       |
| ------------------------ | --------------------------------------------------------------------------- | ---------------------------- |
| 監視/アラート            | API 5xx が 5 分平均 1% 超で #ops へ通知し、P1 は 30 分以内に一次応答        | 異常があれば速やかに対応する |
| 初期増員体制             | 切替後 2 週間、8:00-20:00 は 2 名、夜間はオンコール。延長は運用責任者が判断 | 当面は手厚く対応する         |
| 移行完了後のクローズ条件 | 重大障害 0 件が 30 日継続し、問合せが日次平均 5 件以下                      | 運用が安定したらクローズする |

## 7. 禁止事項

| 禁止パターン                                              | 理由                                                                           |
| --------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `otp-<term>` に委譲すべき個別運用詳細を重複記載すること   | 分冊と食い違い、改訂時に片方が取り残されるため                                 |
| 監視・窓口・SLA・クローズ条件のいずれかを未定義にすること | ハイパーケアの開始・終了と一次対応を判断できなくなるため                       |
| `otp-<term>` への導線を欠くこと                           | 入口として対象別の詳細へ辿れなくなるため                                       |
| 実装依存の長大な手順やコードを本文に書くこと              | Runbook・手順書との二重管理になるため                                          |
| 個人名・電話番号・個人のメールアドレスを書くこと          | 公開・配布できず、異動時に改訂漏れが起きるため。役割名と窓口のチャネル名で書く |
