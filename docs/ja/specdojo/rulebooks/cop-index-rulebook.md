# カットオーバー計画（本番切替手順） 作成ルール

Cutover Plan Index Documentation Rules

カットオーバー計画の全体SSOT `cop-index` を、当日の切替を分単位で実行でき、判断・責任・ロールバックが明確な形で記述する基準を定めます。

## 1. 全体方針

- **記載レベル**: 当日は本書と分冊だけを見て、時刻・判定・ロールバック・連絡を判断できる粒度で書く。
- **分冊との関係**: 分冊（`cop-<term>`）がある場合も、全体前提と判断体系は `cop-index` を正とし、分冊は対象固有の手順に限る。
- **当日の決定と課題の引き継ぎ**: GO/NO-GO の判定結果とロールバックの発動は決定記録（`pm-decision-log`）へ、当日の障害と積み残しは課題管理簿（`pm-issue-log`）へ、各判定点の判断者が切替の終了報告までに転記する。本書には転記先の登録簿を書き、判定結果は書き足さない。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直さない。

## 2. 位置づけ

| 成果物                    | `cop-index` との関係                             |
| ------------------------- | ------------------------------------------------ |
| `mip-index`               | 成功条件・骨格・判定点・ロールバック方針を受ける |
| `dmd-index`, `dmd-<term>` | データ移行の手順と所要時間を受ける               |
| `mtp-index`, `mtp-<term>` | リハーサルの結果で時刻と判定条件を確かめる       |
| `otp-index`, `otp-<term>` | 切替後の監視・運用窓口へ引き渡す                 |

関係先が変わったとき、または本書の判定点・時刻・手順を変えたときは、影響を受ける側を「関連ドキュメント」に挙げて見直す。

## 3. ファイル命名・ID規則

- `id` は `cop-index`（プロジェクト固有の成果物は `<project-id>:cop-index`）とし、成果物カタログの宣言と一致させる。
- ファイル名は `cop-index.md` とする。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- `specdojo.type` は `operations`、`specdojo.rulebook` は `specdojo:cop-index-rulebook` とし、`title` は置かない。
- `specdojo.based_on` には切替判断に直接使った作成済み成果物だけを記載する。
- 編集後は `npm run lint:fm` で Frontmatter を rulebook の宣言と照合する。終了コード 0 で合格とし、エラーは示された宣言値・許可キーに合わせて直す。

## 5. 本文要件

本文は次の10章をこの順序で置き、すべて必須とします。

| 章                           | 内容・受入条件                                                                                    |
| ---------------------------- | ------------------------------------------------------------------------------------------------- |
| 概要（index）                | 切替対象・目的と、対象外のシステム・業務・作業を1〜3行で示す                                      |
| 当日タイムライン             | 列は「時刻（相対） / イベント / 完了条件 / 判定点」。分単位で書く                                 |
| 作業手順チェックリスト       | 列は「手順 / 作業内容 / 実施者 / 証跡 / 備考」。順序付きで書く                                    |
| 担当者、連絡系統             | 列は「役割 / 担当 / 連絡先 / 備考」。エスカレーション先を含める。担当・連絡先はロールと窓口で書く |
| 実施条件（事前完了条件）     | 事前に完了している条件と、未達時の扱い（延期、代替手順）と判断者                                  |
| 切替判定ポイント（GO/NO-GO） | 列は「判定点 / 条件 / 判断者 / 失敗時の扱い」。失敗時はロールバック・延期・代替手順のいずれか     |
| ロールバック手順             | 発動条件、復旧方針（旧系復帰、接続戻しなど）、手順ごとの実施者・証跡・完了条件                    |
| 障害時判断、エスカレーション | 重大度・SLO逸脱・復旧見込みの判断基準と、連絡経路                                                 |
| 周知（ユーザ通知、停止告知） | 通知対象・手段・時期、停止時間・影響範囲・問い合わせ先、配信の証跡、計画変更時の再周知            |
| 関連ドキュメント             | 分冊と見直し対象への導線。分冊がなければ `（本書のみ）` と書く                                    |

## 6. 記述ガイド

完成例は Frontmatter の `sample` で宣言された sample を参照してください。

### 6.1. 当日タイムラインと判定点

- **判断基準**: 判定点の時刻・条件・失敗時の扱いが、タイムラインと判定ポイントの表で一致していること。
- **良い例**: 「T+30分 ／ 旧系の受付停止 ／ 未処理の注文が0件 ／ GO1」と「GO1 ／ 未処理の注文が0件 ／ 店主 ／ 延期（旧系の受付を再開）」。
- **悪い例**: 「午前中 ／ 切替作業 ／ 完了したら次へ」（分単位でなく、判定点もない）。

### 6.2. 担当者、連絡系統

- **判断基準**: 連絡先はロールの窓口（業務用の電話、チャットのチャンネル）に限り、個人の電話番号・私用アドレスはリポジトリ外の内部連絡網に置いて、その名称だけを書くこと。
- **良い例**: 「切替責任者 ／ 店主 ／ 切替用チャットのチャンネル ／ 不通時は店の固定電話」。
- **悪い例**: 「切替責任者 ／ 山田太郎 ／ 090-xxxx-xxxx」（公開される文書に個人情報が載る）。

### 6.3. ロールバック手順

- **判断基準**: 発動条件が判定ポイントの「失敗時の扱い」と一致し、各手順に実施者・証跡・完了条件があり、旧系で業務を再開できたことを確かめる手順で終わること。
- **良い例**: 「GO2 失敗で発動 ／ 1. レジの接続先を旧系へ戻す（開発担当・設定画面の写真）2. 旧系で試し打ち1件（店主・レシート）→ 完了条件: 旧系で会計できる」。
- **悪い例**: 「問題があれば元に戻す」（発動条件・手順・完了条件がない）。

### 6.4. 障害時判断、エスカレーション

- **判断基準**: 重大度ごとに、続行・ロールバック・延期のどれを選ぶかを SLO の逸脱と復旧見込みの時間で判断でき、連絡経路が「担当者、連絡系統」の役割と一致すること。
- **良い例**: 「会計不可が15分を超え、復旧見込みが立たない → 重大度高、切替責任者がロールバックを判断」。
- **悪い例**: 「重大な障害は関係者で協議する」（基準と判断者がなく、当日に決まらない）。

### 6.5. 周知

- **判断基準**: 利用者が停止時間・影響・問い合わせ先を判断でき、内部の連絡先や作業手順を書かないこと。
- **良い例**: 「前日18時に店頭掲示で告知。停止は翌日9時〜10時、その間は現金のみ。問い合わせは店頭窓口」。
- **悪い例**: 担当者の個人電話番号や内部の作業手順を告知文に書く。

## 7. 禁止事項

| 禁止事項                                         | 理由                                   |
| ------------------------------------------------ | -------------------------------------- |
| 当日タイムラインを分単位で書かない               | 実行性が担保できないため               |
| ロールバックの発動条件や手順を省略する           | 失敗時の判断ができないため             |
| 周知を書かない、または内部限定情報を周知に混ぜる | 利用者の混乱と情報漏えいにつながるため |
| 判定条件を `mip-index` や分冊と矛盾させる        | SSOTが崩れ、当日参照が割れるため       |
