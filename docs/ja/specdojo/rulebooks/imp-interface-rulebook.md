# 影響調査（I/F）作成ルール

Impact Analysis (Interface) Rulebook

変更要求による I/F への影響を整理し、変更要否・影響度・対応方針・未解決事項を判断する記述基準を定めます。この判断を省くと、連携先の受入れ漏れによる連携停止や、切替直前の互換対応の追加による納期遅延を招くため、着手前に影響範囲と対応の合意を残します。

## 1. 全体方針

- 本書は、変更の着手前に、どの I/F をどの程度変えるか、連携先とどう調整するかを判断するための文書とする。
- 影響詳細は I/F（API・ファイル・メッセージなど）単位とし、連携方式が複数あっても I/F ごとに 1 行とする。実装設計の詳細化は扱わない。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱う。

## 2. 位置づけ

- 入力: プロジェクト登録簿の変更要求（`item_type: change-request` の個票。[[specdojo:pjr-rulebook|プロジェクト登録簿 作成ルール]]）と、その業務影響を判断した `imp-business`。
- 判断対象: 連携先との契約・互換性・障害波及・利用者への影響と、その対応方針。
- 反映先: 判断結果は [[specdojo:ifx-index-rulebook|外部システムI/F一覧 作成ルール]] に従う I/F 一覧と各 I/F 仕様（`ifx-*`）へ反映し、「影響詳細一覧」の備考に適用先カタログの成果物 ID を示す。
- 並行する文書: データ・テスト・運用への影響は `imp-data`・`imp-test`・`imp-operations` で判断し、本書は概要と結論の参照にとどめる。

## 3. ファイル命名・ID規則

- 文書 ID は `<project-id>:imp-interface`、推奨ファイル名は `imp-interface.md` とし、配置は適用先の成果物カタログに合わせる。
- 追補文書は `<project-id>:imp-interface-<term>` とし、共通規則は [[specdojo:id-and-file-naming-standard|ID・ファイル命名標準]] に従う。

## 4. 推奨 Frontmatter 項目

共通項目・必須性・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、`npm run lint:fm` で検証する。`type` は `project`、`rulebook` は `specdojo:imp-interface-rulebook` とする。`based_on` には入力の変更要求の個票 ID（`PJR-XXXX`）と、作成済みの `<project-id>:imp-business` を記載する。

## 5. 本文要件

本文は次の6章をこの順で置き、すべて必須とする。

| 章  | 見出し         | 目的                                                   |
| --- | -------------- | ------------------------------------------------------ |
| 1   | 目的と適用範囲 | 変更要求、対象・対象外の I/F、対象期間を示す           |
| 2   | 変更要求の概要 | 背景・要求・狙いと、判定可能な成功条件を示す           |
| 3   | 影響分析サマリ | 影響度の尺度・集約規則と、影響度別の件数・優先対応     |
| 4   | 影響詳細一覧   | I/F ごとの変更要否・影響度・根拠を記録する             |
| 5   | 対応方針       | 対応項目ごとの期限・担当・調整先・前提条件・完了条件   |
| 6   | 未解決事項     | 判断待ち・調査不足と、その決定期限・担当・転記先を示す |

表を置く章は、次の列を必須とする。列名はこのとおりに揃え、別名（例: 「優先度」「実施時期」）を使わない。

| 章             | 必須の列                                                                         |
| -------------- | -------------------------------------------------------------------------------- |
| 影響分析サマリ | 影響度、件数、主な影響対象I/F、優先対応（`要` / `否`）                           |
| 影響詳細一覧   | 影響対象I/F、変更要否（`要` / `否`）、影響度、対応方針、判断根拠、備考           |
| 対応方針       | 影響度、対応項目、期限、担当、調整先、前提条件、完了条件                         |
| 未解決事項     | 論点、不足情報、判断・対応への影響、当面の扱い、決定期限、担当、転記先の登録項目 |

## 6. 記述ガイド

各章の判断の基準と、良い例・悪い例を示す。完成例は Frontmatter の `sample` で宣言された sample を参照する。

### 6.1. 目的と適用範囲

- 変更要求の ID、対象 I/F、対象外の I/F とその理由、対象期間（着手日から連携先の受入確認完了日まで）を記載する。
- 対象外には、調べて影響がないと判断した I/F と、本書では判断しない事項を分けて書く。

| 観点     | 良い例                                                     | 悪い例               |
| -------- | ---------------------------------------------------------- | -------------------- |
| 対象外   | 「会員ポイント連携は対象外。値引き項目を送受信しないため」 | 対象外を書かない     |
| 対象期間 | 「2026-05-01〜2026-05-31（取引先の受入確認完了日）」       | 「次回リリースまで」 |

### 6.2. 変更要求の概要

- 背景・要求・狙いを要約し、成功条件は確認対象・指標・閾値（または達成状態）・判定方法で書く。

| 観点     | 良い例                                                                     | 悪い例                     |
| -------- | -------------------------------------------------------------------------- | -------------------------- |
| 成功条件 | 「既存クライアント全件が互換試験に合格し、切替後 1 週間の連携エラー 0 件」 | 「連携を止めずに導入する」 |

### 6.3. 影響分析サマリ

- 契約互換性・障害波及・連携先調整の3観点で評価し、観点別の最も高い判定を影響度とする。件数も同じ規則で集計する。
- 高: 互換性が壊れて連携先の改修が必須、または連携停止が業務を止める。中: 高に該当せず、連携先の設定変更・段階導入・手順追加で吸収できる。低: 高・中に該当せず、現行の連携で継続できる。

| 観点 | 良い例                         | 悪い例                         |
| ---- | ------------------------------ | ------------------------------ |
| 尺度 | 表の前に高・中・低の条件を示す | 高・中・低を定義せずに使う     |
| 観点 | 本文要件の3観点で評価する      | 「開発工数」など別の観点を使う |

### 6.4. 影響詳細一覧

- 判断根拠には、変更要否の理由と、評価観点ごとの事実に尺度を当てはめた結果を書く。
- 対応方針は `実施` / `代替` / `見送り` のいずれかとし、備考に制約・前提と波及先の成果物 ID を書く。

| 観点     | 良い例                                                                             | 悪い例               |
| -------- | ---------------------------------------------------------------------------------- | -------------------- |
| 判断根拠 | 「互換性: 中（新項目は任意）、障害波及: 高（集計差異が出る）。最大値規則により高」 | 「影響あり。要対応」 |
| 備考     | 「波及先: `ifx-pos-sales-api`」                                                    | 「関連資料参照」     |

### 6.5. 対応方針

- 影響度の高い順に、対応項目ごとの期限、担当、調整先の連携先、前提条件、完了条件を記載する。担当は適用先のメンバー定義の Role code で書く。
- 完了条件は互換試験の合格や連携先の受入確認など、達成を判定できる状態で書く。
- 見送り・代替は、再評価条件と再評価の期限を必ず記載する。

| 観点     | 良い例                                                                         | 悪い例         |
| -------- | ------------------------------------------------------------------------------ | -------------- |
| 担当     | `DEV`                                                                          | 個人名、連絡先 |
| 完了条件 | 「主要取引先 2 社の受入試験が合格」                                            | 「対応完了」   |
| 見送り   | 「Webhook は見送り。監視アラートが月 5 件を超えたら再評価（期限 2026-07-31）」 | 「当面見送り」 |

### 6.6. 未解決事項

- 論点ごとに不足情報、判断・対応への影響、当面の扱い、決定期限、担当（Role code）を記載する。該当がなければ「なし」とする。
- 次の条件に当てはまる事項はプロジェクト登録簿へ転記し、転記先の登録項目 ID（`PJR-XXXX`）を記載する。

| 条件                                                     | 転記先の `item_type` |
| -------------------------------------------------------- | -------------------- |
| 決定期限までに判断できず、確認や調査が必要な事項         | `question`           |
| 対応が遅れると連携先の受入れや納期に影響するおそれがある | `risk`               |
| すでに計画や連携先との調整に支障が出ている               | `issue`              |
| 見送り・代替を決めた                                     | `decision`           |

## 7. 禁止事項

- 実装詳細（SQL 全文、クラス名、API リクエスト構造）を記載しない。
- 「影響あり」「要対応」だけで判定を済ませない。
- 「影響分析サマリ」の尺度・観点と異なる判定を混在させない。
- 本文要件と異なる列名で同じ項目を書かない（例: 「影響度」の代わりに「優先度」）。
- 担当・調整先に個人名や連絡先を書かない。担当は Role code、調整先は連携先の組織名・システム名で記載する。
