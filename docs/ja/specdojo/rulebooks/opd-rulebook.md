# 運用方針・設計 作成ルール

Operations Policy and Design (OPD) Documentation Rules

切替後の恒常運用の「あるべき姿」（SLO/SLA・責任分界・統制）を、運用方針・設計（`opd-index` / `opd-<term>`）に定義する基準を定めます。

## 1. 全体方針

`opd-index`（必要に応じて `opd-<term>`）は、恒常運用の方針と統制基準を一元化する SSOT とする。

- 運用の範囲・前提を明示し、責務境界を曖昧にしない
- **共通の運用**: 役割は適用先のメンバー定義、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱い、運用方針の受入条件に含めない。

### 1.1. index / term 分割方針

- 原則 `opd-index` を作成して入口とし、`opd-<term>` は運用ドメイン（監視/障害対応/権限等）を分冊した方が維持しやすい場合に追加する
- 共通の統制（SLO/SLA/KPI、責任分界、変更管理レベル、バックアップ原則など）は `opd-index` を正とし、`opd-<term>` には **`opd-index` との差分（補足・具体化・例外）** だけを書く

## 2. 位置づけ

- **`opd-index` / `opd-<term>`**: 恒常運用の方針と統制（あるべき姿・判断基準）の SSOT
- `opr-index` / `opr-<term>`: 運用手順・Runbook。手順と証跡（再現可能な作業）を責務とする

## 3. ファイル命名・ID規則

- `id` は `opd-index` または `opd-<term>`（kebab-case。例: `opd-monitoring`）。
- `<term>` は用語集(GL)の論理名キー（英小文字kebab-case）を用いる。
- ファイル名はプロジェクト内で一意にする（日本語可。例: `運用方針・設計-監視.md`）。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- `specdojo.type` は `operations`、`specdojo.rulebook` は `specdojo:opd-rulebook` とする
- `based_on` には恒常運用の設計判断に直接利用した成果物（例: `nfr-*` / `sac-*` / `br-*` / `issue-*`）のみ列挙する。OPR は本文の導線で扱い、`based_on` に載せない

## 5. 本文構成（標準テンプレ）

見出しは次の順序で配置します。`opd-<term>` の条件付きの章は、`opd-index` との差分がある章だけを置き、章番号は詰めます。

| 番号 | 見出し                                             | `opd-index` | `opd-<term>` |
| ---- | -------------------------------------------------- | ----------- | ------------ |
| 1    | 概要（`index` / `<term>`）                         | 必須        | 必須         |
| 2    | 運用の範囲・前提                                   | 必須        | 条件付き     |
| 3    | SLO・SLA・KPI                                      | 必須        | 条件付き     |
| 4    | 体制・責任分界（RACI・当番・エスカレーション）     | 必須        | 条件付き     |
| 5    | 監視・アラート方針（指標・閾値・通知先・初動）     | 必須        | 条件付き     |
| 6    | 障害対応方針（優先度・停止判断・周知）             | 必須        | 条件付き     |
| 7    | 変更管理（リリース・設定変更・承認・ロールバック） | 必須        | 条件付き     |
| 8    | バックアップ・リストア方針（RTO/RPO）              | 必須        | 条件付き     |
| 9    | 権限・アカウント運用（棚卸し・監査ログ）           | 必須        | 条件付き     |
| 10   | 定期運用方針（バッチ・点検）                       | 必須        | 条件付き     |
| 11   | 問い合わせ運用方針（窓口・分類・SLA）              | 必須        | 条件付き     |
| 12   | 関連ドキュメント導線（`opr` 等）                   | 必須        | 必須         |

`opd-<term>` の 2〜11 を条件付きとするのは、`opd-index` と同じ内容を分冊へ重複記載させないためです。`opd-<term>` は 2〜11 のうち少なくとも 1 章を置きます。

## 6. 記述ガイド

### 6.1. 概要（`index` / `<term>`）

- 何を運用方針として定義するかを 1〜3 行で示す
- `opd-index` は恒常運用の SSOT であること、`opd-<term>` は `opd-index` の差分・補足であることを 1 行で明示する

### 6.2. 運用の範囲・前提

- 対象システム、対象業務、対象時間帯、非対象範囲を明記する
- 前提制約（法令/契約/セキュリティ/組織体制）を明記する

### 6.3. SLO・SLA・KPI

- 可用性/応答時間/一次応答などの目標を定量で定義し、判定期間・測定方法・証跡・判定者を明記する

| 指標 | 目標値 | 測定期間 | 測定方法 | 証跡 | 判定者 |
| ---- | ------ | -------- | -------- | ---- | ------ |

### 6.4. 体制・責任分界（RACI・当番・エスカレーション）

- RACI、当番体制、連絡系統と、優先度別のエスカレーション条件（いつ・誰が・どこへ）を明記する

| 対象 | R   | A   | C   | I   | 備考 |
| ---- | --- | --- | --- | --- | ---- |

### 6.5. 監視・アラート方針（指標・閾値・通知先・初動）

- 監視対象、閾値、通知先、初動ルールを明記する。誤検知/検知漏れ対策は必要に応じて書く

| 監視対象 | 指標/閾値 | 通知先 | 初動（誰が何をするか） | 備考 |
| -------- | --------- | ------ | ---------------------- | ---- |

### 6.6. 障害対応方針（優先度・停止判断・周知）

- 優先度分類（P1/P2/P3 等）と停止判断条件、周知対象・手段・タイミングを明記する

| 優先度 | 例  | 目標（一次応答/復旧） | 停止判断 | 周知 |
| ------ | --- | --------------------- | -------- | ---- |

### 6.7. 変更管理（リリース・設定変更・承認・ロールバック）

- 変更種別、承認フロー、実施条件（時間帯/凍結期間等）、ロールバック条件と承認者を明記する

### 6.8. バックアップ・リストア方針（RTO/RPO）

- バックアップ方式、保管先、保持期間、RTO/RPO と復旧手順の参照先を明記する（詳細手順は OPR に寄せる）

### 6.9. 権限・アカウント運用（棚卸し・監査ログ）

- 権限付与/剥奪ルール、棚卸し周期、監査ログ方針、緊急権限（ブレークグラス）の管理条件を明記する

### 6.10. 定期運用方針（バッチ・点検）

- 定期バッチ、定期点検、実施責任者、証跡と、未実施時のエスカレーション方針を明記する

### 6.11. 問い合わせ運用方針（窓口・分類・SLA）

- 受付窓口、分類ルール、一次対応 SLA と、連携先（開発/業務/運用）への引き継ぎ条件を明記する

### 6.12. 関連ドキュメント導線（`opr` 等）

- `opr-index` への導線を **必ず** 記載し、`opr-<term>` がある場合は該当する手順への導線を併記する
- 分冊がない場合でも `（本書のみ）` または `（なし）` を明記する
- 移行ドキュメント（`mip-*` / `mtp-*` / `cop-*` / `otp-*`）は必要時のみ参考情報として記載する

| 種別 | ドキュメントID | 目的 | 備考 |
| ---- | -------------- | ---- | ---- |

## 7. 禁止事項

| 禁止事項                                             | 理由                                         |
| ---------------------------------------------------- | -------------------------------------------- |
| SLO/SLA/KPI を定量定義せず曖昧語で記述する           | 判定基準が成立しないため                     |
| 責任分界（RACI/当番/エスカレーション）を省略する     | 障害時の判断遅延・責任不明確を招くため       |
| 監視閾値/通知先/初動ルールを未記載にする             | 初動遅延や見落としの原因となるため           |
| 変更管理の承認/ロールバック条件を未定義にする        | 変更統制が崩壊するため                       |
| バックアップ/リストア方針に RTO/RPO 観点を含めない   | 復旧計画の実効性が担保できないため           |
| 関連ドキュメント導線（`opr` 等）を省略する           | 参照先が分散し、運用時に判断を誤るため       |
| `opd-<term>` に `opd-index` と同じ統制を再掲する     | 正本が二重になり、改訂時に食い違うため       |
| 手順（コマンド/チェックリスト）を OPD に大量記載する | OPR と二重管理になり、更新不整合を起こすため |
