# 運用方針・設計 作成ルール

Operations Policy and Design (OPD) Documentation Rules

恒常運用の方針を運用ドメインごとに分冊した `opd-<term>` の記述基準を定めます。

## 1. 全体方針

- 本書の対象は `opd-<term>` だけとする。`opd-index` の章立てと記述基準は [[specdojo:opd-index-rulebook|運用方針・設計 全体構成 作成ルール]] を正本とし、本書では扱わない。
- `opd-<term>` は、監視・障害対応・権限など一つの運用ドメインについて、`opd-index` の統制との差分（補足・具体化・例外）を判断するための文書とする。
- `opd-<term>` は、`opd-index` の該当章が長くなり分冊した方が維持しやすい場合にだけ作る。分冊しない運用ドメインは `opd-index` に書く。
- 本文構成と記述ガイドで骨組みと記入基準が定まるため、別の recipe・template は不要とする。
- **共通の運用**: 役割は適用先のメンバー定義、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱い、運用方針の受入条件に含めない。

## 2. 位置づけ

| 文書           | 担う内容                                                        | 記述基準の正本                                                      |
| -------------- | --------------------------------------------------------------- | ------------------------------------------------------------------- |
| `opd-index`    | 恒常運用の方針と統制（SLO・責任分界・変更管理・復旧など）の正本 | [[specdojo:opd-index-rulebook\|運用方針・設計 全体構成 作成ルール]] |
| `opd-<term>`   | 一つの運用ドメインの、`opd-index` との差分                      | 本書                                                                |
| `opr-index` 等 | 実行手順と証跡                                                  | [[specdojo:opr-rulebook\|運用手順 作成ルール]]                      |

- `opd-index` と `opd-<term>` で同じ統制が食い違う場合は `opd-index` を正とする。
- `opd-index` の統制を改訂したときは、その章を差分として持つ `opd-<term>` を見直し、差分の前提が崩れていないかを確かめる。

## 3. ファイル命名・ID規則

- ID は `opd-<term>`（kebab-case。例: `opd-monitoring`）とする。`<term>` は用語集の論理名キー（英小文字 kebab-case）を使う。
- ファイル名は ID と同名の `.md` を推奨する。
- 配置は `opd-index` と同じく [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] の `docs/ja/product/090-operations/` を推奨する。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- `specdojo.type` は `operations`、`specdojo.rulebook` は `specdojo:opd-rulebook` とする。
- `based_on` には恒常運用の設計判断に直接利用した成果物（例: `nfr-*` / `sac-*` / `br-*` / `issue-*`）だけを列挙する。OPR は本文の導線で扱い、`based_on` に載せない。

## 5. 本文構成（標準テンプレ）

見出しは次の順序で配置し、章番号は詰めます。

| 順序 | 見出し                           | 必須 | 内容                                                                                                    |
| ---- | -------------------------------- | ---- | ------------------------------------------------------------------------------------------------------- |
| 先頭 | 概要（`<term>`）                 | ○    | 扱う運用ドメインと、`opd-index` の差分であること                                                        |
| 中間 | 差分を持つ章                     | ○    | `opd-index` の章（運用の範囲・前提〜問い合わせ運用方針）のうち差分がある章を、同じ見出しで 1 章以上置く |
| 末尾 | 関連ドキュメント導線（`opr` 等） | ○    | `opr-index` と、このドメインの手順への導線                                                              |

差分がない `opd-index` の章は置きません。同じ内容を分冊へ重複させないためです。

## 6. 記述ガイド

### 6.1. 概要（`<term>`）

- 扱う運用ドメインと、`opd-index` のどの章を補足・具体化・例外にするかを 1〜3 行で示す。
- 良い例:「権限付与・剥奪、棚卸し、監査ログ、緊急権限を `opd-index` の差分として定める」。悪い例:「権限について説明する」。

### 6.2. 差分を持つ章

- 章ごとの記入内容（範囲・指標・判断者・通知先など）は [[specdojo:opd-index-rulebook|運用方針・設計 全体構成 作成ルール]] の記述ガイドに従う。
- 各記述は補足・具体化・例外のどれかが分かるように書き、例外には理由を添える。
- 判断者・承認者・通知先は Role 名または窓口名で書き、条件は数値・周期・期限で判定できる形にする。
- 良い例:「棚卸しは `opd-index` の四半期を月次に短縮する（例外: 共有アカウントを使うため）」。悪い例: `opd-index` の SLO 表をそのまま再掲する。

### 6.3. 関連ドキュメント導線（`opr` 等）

- `opr-index` への導線を必ず置く。このドメインを扱う `opr-<term>` があれば併記する。
- このドメインの `opr-<term>` がない場合は、その行の備考に `opr-<term> なし（opr-index で扱う）` と書き、`opr-index` の導線は省略しない。
- 移行ドキュメント（`mip-*` / `mtp-*` / `cop-*` / `otp-*`）は判断に使う場合だけ参考として載せる。

| 種別 | ドキュメントID | 目的 | 備考 |
| ---- | -------------- | ---- | ---- |

## 7. 禁止事項

| 禁止事項                                                                            | 理由                                                     |
| ----------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `opd-index` と同じ統制を差分として示さずに再掲する                                  | 正本が二重になり、改訂時に食い違うため                   |
| 差分の根拠となる `opd-index` の章を示さずに例外を書く                               | どの統制を上書きするのかが判定できないため               |
| 条件・目標を数値・周期・期限のない曖昧語だけで書く                                  | 達成・未達を判定できないため                             |
| 手順を逐次（コマンド列・チェックリスト）で書く。手順は `opr-*` へ置き参照だけを置く | 方針と手順の正本が二重になり、更新不整合を起こすため     |
| `opr-index` への導線を省略する                                                      | 運用時に手順の入口が分からなくなるため                   |
| 個人名・個人の連絡先を書く                                                          | 公開・配布時に個人情報が漏れ、異動のたびに改訂が要るため |
