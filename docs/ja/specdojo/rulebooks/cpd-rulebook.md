# C4コンポーネント図（CPD）作成ルール

C4 Component Diagram (CPD) Authoring Rule

一つのコンテナ内部を主要な責務へ分け、依存方向と境界で受け渡す情報を定義する規約です。実装配置と結合テストの設計入力を扱い、クラス構造や連携構文は各詳細仕様へ委ねます。

## 1. 全体方針

- 上位 C4 コンテナ図から対象コンテナを一つ選び、利用者、外部依存、ストアの境界を引き継ぎます。別コンテナを内部コンポーネントへ取り込みません。
- 分割単位は固有の責務と入出力を持つまとまりです。主要コンポーネントは 5〜15 個程度を目安とし、数合わせやコマンド・ファイル単位の機械的な分割はしません。
- 図は主要依存、定義表は責務・情報の受け渡し・制約を担います。主要経路を選んだ理由と省略範囲を示し、全関数・全呼び出しの一覧にしません。
- 記法は `includes` で適用する [[specdojo:cpd-mermaid-rulebook|CPD Mermaid 記法ルール]] を正本とし、形状・色・構文は本書で再定義しません。

### 1.1. 作成・確認・合意の分担

以下を作業単位とし、PM が対象コンテナ数、関係数、未確認の依存を基に担当と見積もりを Schedule に割り当てます。Role code と実行主体の対応・兼務はプロジェクトの組織定義に従い、CPD に別の名簿を作りません。

| 作業・確認対象                                 | 担当 Role code                 | 判断タイミング・完了条件                                                                |
| ---------------------------------------------- | ------------------------------ | --------------------------------------------------------------------------------------- |
| 対象者の課題・期待価値と分割の目的             | BA、業務確認者となる利用者代表 | 分割案の作成前。上位の目的と成功基準に対応すること                                      |
| 境界・責務・依存方向の作成とアーキテクチャ確認 | ARC                            | 詳細設計への引き渡し前。上位図との対応と採用理由を説明できること                        |
| 実装配置・詳細契約への対応確認                 | DEV                            | 実装着手前。確認済みの対応と未確認の論点を分離できること                                |
| 図・定義表の照合と結合観測点の確認             | QE                             | 合意依頼前。「検証と合意の判定」の条件を満たすこと                                      |
| 未決事項・後続作業・期限の調整                 | PM                             | 依存変更時と合意依頼前。PJR と Schedule への反映先が定まること                          |
| 公開前確認と最終合意                           | OPS、人間の PO                 | 公開・確定前。OPS が確認結果を提示し、PO が承認・保留・差し戻しと公開可否を判断すること |

## 2. 位置づけと用語定義

| 用語           | 本書での意味                                                                 |
| -------------- | ---------------------------------------------------------------------------- |
| コンテナ       | 上位図が定める実行・配備単位。コンポーネントごとの別プロセス化を意味しない   |
| コンポーネント | 対象コンテナ内で、まとまった責務と他要素との接点を持つ論理単位               |
| 依存方向       | 主たる利用・依頼の起点から終点への向き。時系列や応答データの向きとは区別する |

上位図は実行単位間の境界、本図は一単位の内部責務を扱います。物理配置、内部クラス、値・構文・データ構造はインフラ設計、実装、リファレンス、schema、外部 IF 仕様を正本とします。

## 3. ファイル命名・ID規則

- 共通規則は [[specdojo:id-and-file-naming-standard|ID・ファイル命名標準]] と [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従います。
- ファイル名は `cpd-<context>.md` とし、対象コンテナを識別する英小文字・数字・ハイフンの名前を使います。プロダクト文書の配置は原則 `docs/<lang>/product/030-architecture/010-c4/` とします。
- プロダクト文書の ID は `cpd-<context>`、プロジェクト文書は `<project-id>:cpd-<context>` とし、H1 に対象名と図の種別を示します。
- 関係には文書内で一意な `REL-01` 形式の ID を付け、図の端点・ラベルと関係表を対応付けます。名称変更だけでは ID を振り直しません。

## 4. 推奨 Frontmatter 項目

共通項目の型・値・必須条件は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- メタ情報は `specdojo:` 配下に置き、`type` は `architecture`、主 `rulebook` は `specdojo:cpd-rulebook` とします。記法部品を主 rulebook にしません。
- `based_on` には対象コンテナの根拠となる上位 CND を接続します。適用する外部 IF・用語定義も根拠を辿れるよう本文の該当箇所へ参照を置きます。カタログ管理下の `based_on` は `depends_on` の推移閉包に限り、必要な依存が閉包外なら PM にカタログの整備を引き継ぎます。プロジェクト共通文脈は本文で必要な結論だけ参照します。
- 作成・編集時の `status` は `draft` とします。`owner`、`part_of`、`supersedes` は共通規約に従い、本文の設計前提を独自メタ項目で代用しません。
- 未同梱の上位図を使う学習用例は、架空参照と `based_on` 未接続の理由を概要へ明記します。実案件の依存未接続を、この例外で解決済みにはできません。

## 5. 本文要件

見出し順・表の列・記入欄の骨組みは template を正本とし、ここでは意味要件を定めます。

| 章の役割             | 必須     | 満たす内容                                                                                                                       |
| -------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 概要                 | 必須     | 上位図の対象コンテナ、業務目的との対応、分割の目的、利用する設計判断、対象外、確定度、確認者・最終合意者と公開範囲               |
| 構成図               | 必須     | 一つのコンテナ境界、主要コンポーネント、接点となる利用者・ストア・外部依存、ラベル付きの関係                                     |
| 要素・境界の定義     | 必須     | 内外の分界、コンポーネントの責務・入出力・論理配置と採用理由、外部依存の利用条件、関係の授受情報と詳細の正本                     |
| 技術前提・検証対象   | 必須     | 依存の制約、失敗時に区別する結果、関係 ID に結び付く結合検証の観測点                                                             |
| 未確定事項の引き継ぎ | 条件付き | 仮定・未確認箇所がある場合の区分、影響、担当・判断者、判断タイミング、次アクション、解消条件、合意への影響、PJR などの引き継ぎ先 |

Person・ストア・外部システムが該当しない場合は、定義欄へ非該当の理由を書きます。論理配置はコンテナ内部の責務の配置までとし、確認できていないソースパスを断定しません。

確認者・公開範囲・変更時の影響は概要、技術前提またはメモの該当箇所に記録し、独立した章を増やすことは必須にしません。作業・検証・承認の証跡は実行記録や決定記録を正本とし、CPD から参照します。

## 6. 記述ガイド

共通のメタ情報・命名は上位標準を参照し、以下ではコンポーネント分割に固有の判断を扱います。

### 6.1. 概要

- 上位図のどのコンテナを展開するか、何の設計入力に使うか、何を扱わないかを書きます。
- 対象者の業務課題、放置時の影響、期待価値・成功基準は、上位の要求・目的の該当箇所へ必ず参照を置きます。上位に定義がなければ BA が論点化し、CPD だけで業務上の成功を確定しません。
- 作成者、アーキテクチャ確認者、業務確認者、最終合意者を「作成・確認・合意の分担」に対応付け、プロジェクトの役割割当てまたは合意記録を参照します。公開する相手・媒体・範囲も示します。
- 設計案と実装の確認済み構成を区別し、未確認の分割は _ASSUMPTION_: として影響と確認先を残します。
- 良い例: 「販売処理サービス内部を分け、保存と印字の責任境界を結合設計へ渡す。再送の詳細は連携仕様へ委ねる」。悪い例: 「システム全体の詳細を示す」。対象と用途を限定できるかが基準です。

### 6.2. C4コンポーネント図（Mermaid）

- 上位図で対象外のストア・他コンテナは境界外に置きます。同じ端末で動くことを境界内に置く理由にしません。
- 矢印が依存・依頼を表すかを明示し、応答を同じ関係に含めるか説明します。主要経路の省略範囲も短く示します。
- 良い例: 「会計処理 → 印字連携: 保存済み控えの印字依頼」。悪い例: 「会計処理 ↔ 共通処理: 処理」。責務と依存方向を読めるかが基準です。

### 6.3. 要素と境界の定義

- コンポーネントは固有の責務、入力と出力の種類、コンテナ内での論理配置を記述します。実装上の配置を示す場合は根拠を付け、未確認なら論点に残します。
- 主要な分割・共通化・依存の採用理由を、概要で参照した業務目的または技術制約へ対応付けます。同じ理由で分けた責務はまとめて説明し、各行で上位の目的を繰り返しません。
- 関係表の推奨列は「関係 ID / 起点 → 終点 / 授受情報・条件 / 詳細の正本」です。外部の別コンテナ、ストア、外部システムを区別し、未作成の正本はバッククォートで仮置きします。
- 良い例: 「会計処理は確認済み明細を受け、確定結果を返す。印字の成否は印字連携が扱う」。悪い例: 「会計処理は販売のすべてを行う」。他コンポーネントとの更新責任を分けられるかが基準です。

### 6.4. 技術前提・制約と検証観点

- 共通機構への依存、外部依頼、正本と派生物の区別を、対象コンテナに必要な範囲で示します。未確認の排他・原子性・再試行保証は置きません。
- 関係 ID または要素名に、入力条件と観測する結果を対応付けます。テストケースの全件列挙や実施結果の記録は行いません。
- 良い例: 「保存成功後の印字失敗で、販売結果と未印字を別々に観測する」。悪い例: 「正常系と異常系を十分テストする」。境界ごとの確認対象を識別できるかが基準です。

### 6.5. メモ / 将来課題

- 仮定・未確認事項は共通ラベルで確定事項と区別し、対象要素・関係 ID と対応付けます。区分は、未発生の懸念をリスク、発生済みの阻害を課題、合意した構成の変更提案を変更要求、合意結果を決定事項とします。
- 推奨する記録項目は「対象・区分 / 影響と後続成果物 / 担当 Role code・判断者 / 期限または判断タイミング / 次アクション・解消条件 / 承認への影響・引き継ぎ先」です。表の既存列へ併記しても構いません。担当と判断者は分け、業務・公開判断の判断者は人間の PO とします。
- ARC は境界・契約・結合設計・作業順に影響する論点を PM へ報告します。PM は継続追跡するリスク・課題・変更要求・決定事項を共通のライフサイクル規約に従って PJR へ転記し、転送先レコードと担当を接続します。未起票なら登録候補として理由・起票担当・判断タイミングを残します。合意を要する事項は PO へ報告し、後続作業の着手可否・Schedule の順序や期限への影響も記録します。
- 良い例: 「印字応答欠落は結果不明を生むリスク。ARC が外部 IF の回復条件を整理し QE が観測点を確認する。人間の PO が実装着手前に採否を判断し、未解消なら当該経路を保留する。PM が PJR 登録候補として結合設計の開始条件へ反映する」。悪い例: 「将来検討する」。判断する人と時点、判断後の作業が特定できるかが基準です。

### 6.6. 検証と合意の判定

QE は、図の全要素が定義表または境界の説明へ、全関係が一意な関係 ID へ対応することを照合します。逆に、定義表だけにある要素・関係には省略理由が必要です。主要経路では、通常時と失敗・応答欠落時の条件および観測結果を関係 ID から辿れ、上位図と異なる内外配置や依存方向が説明なく残らないことを合格条件とします。

検証コマンドは対象リポジトリの `package.json`・hook 設定を正本とします。SpecDojo 本体での対応は次表のとおりです。`<対象.md>` は変更した CPD、`<id>` はその参照先 ID へ置き換えます。実行記録には対象・コマンド・結果を残し、親 runner が実施する検査はその証跡を使います。

| 確認                           | コマンド・確認方法                                                             | 期待結果・失敗時の対応                                                                                       |
| ------------------------------ | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| メタ情報・主 rulebook の型宣言 | `npm run lint:fm`（対象は `docs/` の Markdown）                                | CPD の schema・型宣言エラーがない。指摘された項目を正本と照合して直す                                        |
| 参照先                         | `node --import tsx src/specdojo.ts index lookup <id>` と参照先の該当箇所の閲読 | 既存 ID が意図した文書へ解決する。索引不整合は管理側に再生成を依頼し、未作成参照は仮参照と引き継ぎ事項へ直す |
| Mermaid 構文                   | `node tools/lint-mermaid.mjs <対象.md>`                                        | 全図が passed、構文エラー・未検査がない。指摘された fence を修正し、未検査なら依存環境を整える               |
| 描画・可読性                   | `npm run docs:build:mermaid` 後に対象図の SVG を閲覧                           | 要素名・関係ラベルが欠けず、境界内外・矢印の端点を判読できる。重なりや切れを修正して再描画する               |

OPS は公開前に対象の本文・図・ラベル・参照先について、個人情報、認証情報、内部ホスト名や非公開の構成情報が含まれないか、プロジェクトの公開方針と照合します。確認範囲・除外または匿名化した情報・残る懸念を合意記録へ残し、人間の PO が公開先と最終可否を判断します。技術検証の成功や `status` だけでは公開許可を表しません。

人間の PO が `ready` へ昇格できる条件は、必須内容と検証の充足、技術・業務確認の完了、依存と詳細化先の接続、公開前確認の完了、および判断記録の存在です。未解決事項を残せるのは、承認対象の境界・責務・受け渡し・成功基準・公開可否を変えず、担当・解消時点と影響を限定できる場合に限ります。判断材料不足は保留、上位境界との矛盾や検証失敗は差し戻しとし、対象範囲と次アクションを記録します。

良い例: 「全関係の照合と描画確認を終え、公開用の接続先表記を PO が承認した。対象外の将来拡張だけを担当・期限付きで残す」。悪い例: 「lint が通ったので公開・確定する」。技術検証と人間の合意の両方を証跡から確認できるかが基準です。

### 6.7. 変更・保守時の影響確認

更新契機は上位 CND の境界変更、責務の追加・統合・廃止、外部 IF・ストアの契約変更、実装との不一致、結合検証での前提否定です。ARC を保守の窓口とし、問い合わせはプロジェクトの役割割当てから担当を辿り、判断が必要なら「メモ / 将来課題」から PJR へ接続します。

- ARC は上位 CND、用語定義、外部 IF、下位のデータ・詳細設計を照合し、影響する要素・関係 ID、変更理由、変更前後、更新要否と理由を変更記録へ残します。図と定義表は同じ改訂で同期します。
- DEV は実装、schema、参照元、生成物・運用手順への追従を確認し、QE は結合観測点とテスト仕様の更新・再検証を確認します。実践の型へ一般化した規定を変える場合は ARC が sample・recipe・template の追従要否も判断します。値・構文・構造は各正本を更新し、CPD には複製しません。
- PM は後続成果物と Schedule への波及を整理して PJR の更新作業へ割り当てます。OPS は変更図を再描画し、QE が「検証と合意の判定」の該当検査を再実施した証跡を確認して、人間の PO に再合意・公開判断を依頼します。改訂・廃止・置き換えと履歴は共通のライフサイクル規約に従います。

良い例: 「保存責務の統合で `REL-05` の終点を変えるため、ARC が図・関係表とデータ設計、DEV が実装対応、QE が保存失敗の観測点、PM が結合作業の開始条件を確認する」。悪い例: 「図だけ差し替える」。影響先ごとに更新または更新不要の根拠を残せるかが基準です。

## 7. 禁止事項

- 複数の実行・配備単位を一つのコンテナとして描くことや、コンポーネントを別サービスと根拠なく断定すること。
- クラス・関数・ファイル一覧、コマンドオプション、API 構文、データ項目・値制約を詳細仕様と重複して管理すること。
- ラベルのない関係、方向の意味が混在する矢印、図と表で対応しない名称・接続。
- 未確認の依存・物理配置・障害回復保証を確定事項として記載すること。
- 自動検査や AI 作業の成功を、業務判断・承認・公開許可と同一視すること。
