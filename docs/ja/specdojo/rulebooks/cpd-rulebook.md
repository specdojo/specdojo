# C4コンポーネント図（CPD）作成ルール

C4 Component Diagram (CPD) Authoring Rule

一つのコンテナ内部を主要な責務へ分け、依存方向と境界で受け渡す情報を定義する規約です。実装配置と結合テストの設計入力を扱い、クラス構造や連携構文は各詳細仕様へ委ねます。

## 1. 全体方針

- 上位 C4 コンテナ図から対象コンテナを一つ選び、利用者、外部依存、ストアの境界を引き継ぎます。別コンテナを内部コンポーネントへ取り込みません。
- 分割単位は固有の責務と入出力を持つまとまりです。主要コンポーネントは 5〜15 個程度を目安とし、数合わせやコマンド・ファイル単位の機械的な分割はしません。
- 図は主要依存、定義表は責務・情報の受け渡し・制約を担います。主要経路を選んだ理由と省略範囲を示し、全関数・全呼び出しの一覧にしません。
- 記法は `includes` で適用する [[specdojo:cpd-mermaid-rulebook|CPD Mermaid 記法ルール]] を正本とし、形状・色・構文は本書で再定義しません。
- ARC が境界と依存方向を整理し、DEV が実装への対応、QE が結合確認の対象を確認します。業務判断・公開可否は人間の判断責任に残します。

## 2. 位置づけと用語定義

| 用語           | 本書での意味                                                                 |
| -------------- | ---------------------------------------------------------------------------- |
| コンテナ       | 上位図が定める実行・配備単位。コンポーネントごとの別プロセス化を意味しない   |
| コンポーネント | 対象コンテナ内で、まとまった責務と他要素との接点を持つ論理単位               |
| 依存方向       | 主たる利用・依頼の起点から終点への向き。時系列や応答データの向きとは区別する |

上位図は実行単位間の境界、本図は一単位の内部責務を扱います。物理配置、内部クラス、値・構文・データ構造はインフラ設計、実装、リファレンス、schema、外部 IF 仕様を正本とします。

## 3. ファイル命名・ID規則

- 共通規則は [[specdojo:id-and-file-naming-standard|ID・ファイル命名標準]] と [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従います。
- ファイル名は `cpd-<context>.md` とし、対象コンテナを識別する英小文字・数字・ハイフンの名前を使います。プロダクト文書の配置は原則 `docs/<lang>/product/030-architecture/010-c4/` とします。
- プロダクト文書の ID は `cpd-<context>`、プロジェクト文書は `<project-id>:cpd-<context>` とし、H1 に対象名と図の種別を示します。
- 関係には文書内で一意な `REL-01` 形式の ID を付け、図の端点・ラベルと関係表を対応付けます。名称変更だけでは ID を振り直しません。

## 4. 推奨 Frontmatter 項目

共通項目の型・値・必須条件は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- メタ情報は `specdojo:` 配下に置き、`type` は `architecture`、主 `rulebook` は `specdojo:cpd-rulebook` とします。記法部品を主 rulebook にしません。
- `based_on` は上位コンテナ図など直接の内容根拠とし、カタログ管理下では `depends_on` の推移閉包に限ります。プロジェクト共通文脈は本文で必要な結論だけ参照します。
- 作成・編集時の `status` は `draft` とします。`owner`、`part_of`、`supersedes` は共通規約に従い、本文の設計前提を独自メタ項目で代用しません。

## 5. 本文要件

見出し順・表の列・記入欄の骨組みは template を正本とし、ここでは意味要件を定めます。

| 章の役割             | 必須     | 満たす内容                                                                                         |
| -------------------- | -------- | -------------------------------------------------------------------------------------------------- |
| 概要                 | 必須     | 上位図の対象コンテナ、分割の目的、利用する設計判断、対象外、確定度                                 |
| 構成図               | 必須     | 一つのコンテナ境界、主要コンポーネント、接点となる利用者・ストア・外部依存、ラベル付きの関係       |
| 要素・境界の定義     | 必須     | 内外の分界、コンポーネントの責務・入出力・論理配置、外部依存の利用条件、関係の授受情報と詳細の正本 |
| 技術前提・検証対象   | 必須     | 依存の制約、失敗時に区別する結果、関係 ID に結び付く結合検証の観測点                               |
| 未確定事項の引き継ぎ | 条件付き | 仮定・未確認箇所がある場合の影響、担当ロール、解消条件・引き継ぎ先                                 |

Person・ストア・外部システムが該当しない場合は、定義欄へ非該当の理由を書きます。論理配置はコンテナ内部の責務の配置までとし、確認できていないソースパスを断定しません。

## 6. 記述ガイド

共通のメタ情報・命名は上位標準を参照し、以下ではコンポーネント分割に固有の判断を扱います。

### 6.1. 概要

- 上位図のどのコンテナを展開するか、何の設計入力に使うか、何を扱わないかを書きます。
- 設計案と実装の確認済み構成を区別し、未確認の分割は _ASSUMPTION_: として影響と確認先を残します。
- 良い例: 「販売処理サービス内部を分け、保存と印字の責任境界を結合設計へ渡す。再送の詳細は連携仕様へ委ねる」。悪い例: 「システム全体の詳細を示す」。対象と用途を限定できるかが基準です。

### 6.2. C4コンポーネント図（Mermaid）

- 上位図で対象外のストア・他コンテナは境界外に置きます。同じ端末で動くことを境界内に置く理由にしません。
- 矢印が依存・依頼を表すかを明示し、応答を同じ関係に含めるか説明します。主要経路の省略範囲も短く示します。
- 良い例: 「会計処理 → 印字連携: 保存済み控えの印字依頼」。悪い例: 「会計処理 ↔ 共通処理: 処理」。責務と依存方向を読めるかが基準です。

### 6.3. 要素と境界の定義

- コンポーネントは固有の責務、入力と出力の種類、コンテナ内での論理配置を記述します。実装上の配置を示す場合は根拠を付け、未確認なら論点に残します。
- 関係表の推奨列は「関係 ID / 起点 → 終点 / 授受情報・条件 / 詳細の正本」です。外部の別コンテナ、ストア、外部システムを区別し、未作成の正本はバッククォートで仮置きします。
- 良い例: 「会計処理は確認済み明細を受け、確定結果を返す。印字の成否は印字連携が扱う」。悪い例: 「会計処理は販売のすべてを行う」。他コンポーネントとの更新責任を分けられるかが基準です。

### 6.4. 技術前提・制約と検証観点

- 共通機構への依存、外部依頼、正本と派生物の区別を、対象コンテナに必要な範囲で示します。未確認の排他・原子性・再試行保証は置きません。
- 関係 ID または要素名に、入力条件と観測する結果を対応付けます。テストケースの全件列挙や実施結果の記録は行いません。
- 良い例: 「保存成功後の印字失敗で、販売結果と未印字を別々に観測する」。悪い例: 「正常系と異常系を十分テストする」。境界ごとの確認対象を識別できるかが基準です。

### 6.5. メモ / 将来課題

- 仮定・未確認事項ごとに、対象関係、設計への影響、担当ロール、解消に必要な根拠と引き継ぎ先を残します。
- 境界や責務を変更・廃止したときは、ARC が上位図と下位設計、DEV が配置と参照元、QE が結合対象への影響を確認します。変更記録は共通のライフサイクル規約に従います。
- 良い例: 「印字応答欠落時の扱いは ARC / QE が連携契約で定め、結合設計へ反映する」。悪い例: 「将来検討する」。担当と解消条件から次の作業へ進めるかが基準です。

## 7. 禁止事項

- 複数の実行・配備単位を一つのコンテナとして描くことや、コンポーネントを別サービスと根拠なく断定すること。
- クラス・関数・ファイル一覧、コマンドオプション、API 構文、データ項目・値制約を詳細仕様と重複して管理すること。
- ラベルのない関係、方向の意味が混在する矢印、図と表で対応しない名称・接続。
- 未確認の依存・物理配置・障害回復保証を確定事項として記載すること。
- 自動検査や AI 作業の成功を、業務判断・承認・公開許可と同一視すること。
