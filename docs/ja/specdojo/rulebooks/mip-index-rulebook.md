# 移行計画 作成ルール

Migration Plan (MIP) Documentation Rules

移行計画（`mip-index`）は、移行の範囲・方式・成功条件・切替判断を固定し、移行の合意と GO/NO-GO の判断に使う文書です。本書はその作成基準を定めます。

## 1. 全体方針

- 判断に必要な情報（停止許容時間、許容誤差、GO/NO-GO 基準）を必ず含める。
- カットオーバーは骨格（マイルストーン・判定点・ロールバック方針）までを書き、分単位の手順は `cop-*` に分ける。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱い、移行の業務の検証に含めない。

## 2. 位置づけ

`mip-index` は移行の合意・判断の正本とし、詳細は次の文書へ委ねる。

| 成果物                    | `mip-index` との関係                                   | 追従の担当 |
| ------------------------- | ------------------------------------------------------ | ---------- |
| `dmd-index`, `dmd-<term>` | 移行対象・成功条件を受け、マッピング・変換・照合を設計 | ARC・DEV   |
| `mtp-index`, `mtp-<term>` | 成功条件・判定点を受け、リハーサルの観点と合否を定める | QE         |
| `cop-index`, `cop-<term>` | カットオーバーの骨格・判定点・ロールバック方針を受ける | OPS        |
| `otp-index`, `otp-<term>` | ハイパーケア方針を受け、監視・窓口・運用切替を定める   | OPS        |

- **改訂時の追従**: スコープ・成功条件・判定点・ロールバック方針・ハイパーケア方針を変えたときは、上表の影響する下流成果物を「移行後ハイパーケア方針」の導線に挙げ、各担当が見直す。見直しの作業は PM が登録簿の個票に起票して追う。
- 上流（`based_on` に挙げた成果物）が変わったときは、本書の該当章を見直してから下流へ波及させる。

## 3. ファイル命名・ID規則

- ローカル ID は `mip-index` 固定とし、完全 ID は `<project-id>:mip-index` とする。`mip-<term>` は作成しない。
- ファイル名は `mip-index.md` を推奨する。`id` とファイル名は独立であり、ファイル名の変更は許容する。
- sample は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、成果物と区別する ID・ファイル名を使う。

## 4. 推奨 Frontmatter 項目

共通の必須項目・型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。

- `specdojo.type` は `project`、`specdojo.rulebook` は `specdojo:mip-index-rulebook` とする。文書名「移行計画: 概要（対象名）」は H1 に書く。
- `specdojo.based_on` には、移行判断に直接使った作成済みの上流成果物を挙げる。例: 対象と非対象を決めた `prj-scope`、停止許容時間や許容誤差の根拠となる `nfr-*`（可用性・完全性・運用）、受入の基準となる `bac-*`・`sac-*`、移行先の構成と運用を定める `opd-index`。

## 5. 本文要件

本文は次の9章をこの順序で置き、すべて必須とする。

| 章                                                             | 内容・受入条件                                                                                                                         |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 移行の背景/目的                                                | 移行が必要な理由を1〜3行で示し、対象の範囲と期待する成果を書く                                                                         |
| 前提・制約                                                     | 対象環境・停止可能な時間帯・使えるリソースと、法務・セキュリティ・契約・外部依存の制約                                                 |
| 移行方式と期間（方式/フェーズ/タイムライン）                   | 方式（一斉・並行など）と、列「フェーズ / 期間 / 目的 / 成果物/完了条件」の表を時系列で書く                                             |
| 移行対象一覧（スコープ/非対象）                                | 列「区分 / 対象 / 補足」。業務・機能・I/F・データ種別・非対象を含め、テーブル・項目・変換の詳細は `dmd-*` に委ねる                     |
| 成功条件・受入基準                                             | 列「項目 / 基準 / 測定対象（対象データ/期間/業務） / 測定/証跡 / 判定者 / 失敗時の扱い（ロールバック/延期/代替手順）」と GO の最低条件 |
| 体制・役割（GO判断含む）                                       | 移行実行・照合・切替判断・移行後支援の分担、GO/NO-GO の判断主体と参照する成功条件、エスカレーション先                                  |
| 移行リスクと対策                                               | 列「リスク / 影響 / 対策 / 検知/判断」。重大リスクは判断する役割と時点を書く                                                           |
| カットオーバー概要（当日タイムライン/判定点/ロールバック方針） | 列「時刻（相対） / イベント / 完了条件 / 判定点 / 失敗時の扱い」と、ロールバックの発動条件・復旧方針。詳細手順は `cop-*` に委ねる      |
| 移行後ハイパーケア方針                                         | 監視期間・体制・対応範囲・窓口と SLA 目安、旧システムの扱い（参照期間/停止/アーカイブ）、`dmd-*`・`mtp-*`・`cop-*`・`otp-*` への導線   |

## 6. 記述ガイド

完成例は Frontmatter の `sample` で宣言された sample を参照する。

### 6.1. 成功条件・受入基準

- **判断基準**: 各基準が測定対象・測定方法・証跡・判定者・失敗時の扱いと結び付き、測定対象はデータ種別・期間・業務シナリオのうち2つ以上を具体化していること。
- **良い例**: 「2024年以降の受注・請求データを全件照合し、件数差異0件。証跡は全件照合レポート、判定は業務責任者、不合格なら切替延期」。
- **悪い例**: 「データ移行が問題なく完了したら GO」（測定対象・許容誤差・証跡を特定できない）。

### 6.2. 体制・役割（GO判断含む）

- **判断基準**: 移行作業の責任分担と GO/NO-GO の判断主体が読み取れること。本書の作成・承認の役割は書かない。
- **良い例**: 「業務責任者が成功条件の全基準と業務スモークの結果で GO/NO-GO を決める。重大障害は業務責任者へ即時連絡」。
- **悪い例**: 「関係者で協議して判断する」（判断主体と基準がない）。

### 6.3. カットオーバー概要（当日タイムライン/判定点/ロールバック方針）

- **判断基準**: 判定点ごとに完了条件と失敗時の扱い（ロールバック・延期・代替手順のいずれか）があり、成功条件の表と矛盾しないこと。
- **良い例**: 「T-60分 ／ 新DB投入・照合 ／ 成功条件の件数・金額基準に合格 ／ GO3 ／ 投入データを移行実行ID単位で無効化し旧系で継続」。
- **悪い例**: 分単位の作業チェックリストを並べ、判定点と失敗時の扱いがない。

## 7. 禁止事項

| 禁止事項                                                          | 理由                                                     |
| ----------------------------------------------------------------- | -------------------------------------------------------- |
| スコープ（対象/非対象）を曖昧に書く                               | 合意形成と実行判断が不能になるため                       |
| 成功条件・受入基準や GO 判断主体を記載しない                      | GO判断の基準点と責任がなくなるため                       |
| カットオーバー概要（判定点/ロールバック方針）を省略する           | 当日判断と失敗時対応が不明確になるため                   |
| テーブル/項目レベルのマッピングや変換ロジックを本書に詳細記載する | 下位ドキュメントと二重管理になり、更新不整合を起こすため |
| 分単位の作業チェックリストや手順書を本書に全面記載する            | Runbookの責務を侵食し、運用時に参照先が割れるため        |
