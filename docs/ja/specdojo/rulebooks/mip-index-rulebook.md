# 移行計画 作成ルール

Migration Plan (MIP) Documentation Rules

移行計画（`mip-index`）の範囲・方式・成功条件・切替判断を定義し、関係者が移行の合意と実行に使うための基準を定めます。

## 1. 全体方針

- 共通方針・前提・スコープ・成功条件を **明確に固定** する
- 判断に必要な情報（停止許容時間、許容誤差、GO/NO-GO基準）を必ず含める
- カットオーバーは **概要（骨格）** を必ず含め、分単位の手順は別ドキュメントに分離する
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱い、移行の業務の検証に含めない。

## 2. 位置づけ

詳細は次の文書へ委譲する。

- `mip-index`：移行の合意・判断の正本
- `dmd-*`：マッピング・変換・検証の設計
- `mtp-*`：リハーサルの観点・手順・証跡
- `cop-*`：当日実行の詳細手順
- `otp-*`：運用切替の監視・手順・窓口

## 3. ファイル命名・ID規則

- 成果物のローカル ID は `mip-index` 固定とし、プロジェクトでの完全 ID は `<project-id>:mip-index` とする。
- `mip-<term>` は作成しない。
- ファイル名は `mip-index.md` を推奨する。番号や日本語を使う場合もプロジェクト内で一貫した命名とする。
- `id`（参照用の不変キー）とファイル名（可読性/並び順）は独立であり、ファイル名変更は許容する。
- sample は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、成果物と区別する ID・ファイル名を使う。

## 4. 推奨 Frontmatter 項目

### 4.1. 設定内容

共通の必須項目・型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。SpecDojo の項目は `specdojo:` 配下に置き、本型では `type: project`、`rulebook: specdojo:mip-index-rulebook` を指定する。文書名「移行計画: 概要（対象名）」は本文先頭の H1 に書く。

### 4.2. 推奨ルール

- `based_on` には移行判断に直接利用した上位成果物を列挙する。

## 5. 本文構成（標準テンプレ）

`mip-index` は以下の9章を順序固定で配置する。「記述ガイド」の同名の節を各章の受入条件とする。

| 番号 | 見出し                                                         | 必須 |
| ---- | -------------------------------------------------------------- | ---- |
| 1    | 移行の背景/目的                                                | ○    |
| 2    | 前提・制約                                                     | ○    |
| 3    | 移行方式と期間（方式/フェーズ/タイムライン）                   | ○    |
| 4    | 移行対象一覧（スコープ/非対象）                                | ○    |
| 5    | 成功条件・受入基準                                             | ○    |
| 6    | 体制・役割（GO判断含む）                                       | ○    |
| 7    | 移行リスクと対策                                               | ○    |
| 8    | カットオーバー概要（当日タイムライン/判定点/ロールバック方針） | ○    |
| 9    | 移行後ハイパーケア方針                                         | ○    |

## 6. 記述ガイド

### 6.1. 移行の背景/目的

- なぜ移行が必要かを 1〜3 行で明確にする
- 対象の範囲と期待する成果を簡潔に示す

### 6.2. 前提・制約

- 移行の前提（対象環境、停止可能時間帯、使用可能なリソース）を列挙する
- 制約（法務/セキュリティ/契約/外部依存）を明記する

### 6.3. 移行方式と期間（方式/フェーズ/タイムライン）

- 移行方式（例: 一斉/並行）を明記する
- 主要フェーズと期間（準備/移行/検証/切替/撤退）を時系列で示す

| フェーズ | 期間 | 目的 | 成果物/完了条件 |
| -------- | ---- | ---- | --------------- |

### 6.4. 移行対象一覧（スコープ/非対象）

- スコープを **一覧表** で示す
- 以下の観点を含める: 業務/機能/I/F/データ種別/非対象
- 詳細（テーブル/項目/変換ロジック）は書かず、下位ドキュメントへリンクする

| 区分 | 対象 | 補足 |
| ---- | ---- | ---- |

### 6.5. 成功条件・受入基準

- 停止許容時間、許容誤差、完了定義を明記する
- 測定方法と証跡の種類・所在（照合レポート、業務テストの実行ログ等）を示す
- 測定対象はデータ種別・期間・業務シナリオのうち最低2つを具体化する
- GO/NO-GO の最低限の判定条件を箇条書きで明文化する

| 項目 | 基準 | 測定対象（対象データ/期間/業務） | 測定/証跡 | 判定者 | 失敗時の扱い（ロールバック/延期/代替手順） |
| ---- | ---- | -------------------------------- | --------- | ------ | ------------------------------------------ |

### 6.6. 体制・役割（GO判断含む）

- 移行実行・照合・切替判断・移行後支援の責任分担を示す。ここでは文書作成・公開の役割を定義しない
- GO/NO-GO の判断主体と判断基準（参照する成功条件）を明記する
- 連絡系統（エスカレーション先）を最小限で示す

| 役割 | 担当 | 責務 | 連絡/判断 |
| ---- | ---- | ---- | --------- |

### 6.7. 移行リスクと対策

- リスク、影響、対策、検知方法、発動条件（必要に応じて）を整理する
- 重大リスクは「誰がいつ判断するか」を落とさない

| リスク | 影響 | 対策 | 検知/判断 |
| ------ | ---- | ---- | --------- |

### 6.8. カットオーバー概要（当日タイムライン/判定点/ロールバック方針）

- 当日の流れをマイルストーンで示す
- 各判定点（GO1/GO2…）での失敗時の扱いを、ロールバック・延期（切替中止）・代替手順から明記する
- ロールバックの発動条件と復旧方針（旧系復帰・データ無効化等）を示す
- 詳細Runbook（`cop-*`）がある場合はリンクする

| 時刻（相対） | イベント | 完了条件 | 判定点 | 失敗時の扱い（ロールバック/延期/代替手順） |
| ------------ | -------- | -------- | ------ | ------------------------------------------ |

### 6.9. 移行後ハイパーケア方針

- 監視期間、体制、対応範囲を明記する
- 問い合わせ窓口とSLA目安があれば記載する
- 旧システムの扱い（参照期間/停止/アーカイブ）を方針レベルで書く
- `dmd-*` / `mtp-index`・`mtp-*` / `cop-index`・`cop-*` / `otp-index`・`otp-*` への導線を示す

| 項目 | 方針 |
| ---- | ---- |

## 7. 禁止事項

| 禁止事項                                                          | 理由                                                     |
| ----------------------------------------------------------------- | -------------------------------------------------------- |
| スコープ（対象/非対象）を曖昧に書く                               | 合意形成と実行判断が不能になるため                       |
| 成功条件・受入基準を記載しない                                    | GO判断の基準点がなくなるため                             |
| 体制・役割やGO判断主体を未記載にする                              | 責任が不明確になり判断が遅れるため                       |
| リスクと対策を列挙しない                                          | 失敗時の影響が拡大するため                               |
| カットオーバー概要（判定点/ロールバック方針）を省略する           | 当日判断と失敗時対応が不明確になるため                   |
| ハイパーケア方針を省略する                                        | 移行後の不具合対応が不明確になるため                     |
| テーブル/項目レベルのマッピングや変換ロジックを本書に詳細記載する | 下位ドキュメントと二重管理になり、更新不整合を起こすため |
| 分単位の作業チェックリストや手順書を本書に全面記載する            | Runbookの責務を侵食し、運用時に参照先が割れるため        |

## 8. サンプル（最小）

9章と切替判断の最小例を示す。完成例の所在は Frontmatter の `sample` 宣言を正本とする。

```markdown
---
specdojo:

  type: project
  status: draft
  rulebook: specdojo:mip-index-rulebook

# 移行計画: 概要（受注・請求システム）

## 1. 移行の背景/目的

保守期限を迎える旧基盤から新基盤へ移し、受注・請求を継続する。

## 2. 前提・制約

停止は休日深夜帯の最大6時間。外部決済のリハーサルには sandbox を使う。

## 3. 移行方式と期間（方式/フェーズ/タイムライン）

並行移行とする。準備（3月、リハーサル合格）、移行・検証（4月1日、照合合格）、切替（同日、業務スモーク合格）、旧系撤退判定（4月15日）の順に進める。

## 4. 移行対象一覧（スコープ/非対象）

| 区分   | 対象                   | 補足               |
| ------ | ---------------------- | ------------------ |
| 業務   | 受注・請求             | 新基盤へ移行       |
| I/F    | 決済連携               | 切替日に接続先変更 |
| データ | マスタ・取引           | 2024年以降を移行   |
| 非対象 | 2023年以前のアーカイブ | 旧系で参照のみ     |

## 5. 成功条件・受入基準

| 項目       | 基準      | 測定対象（対象データ/期間/業務） | 測定/証跡                        | 判定者     | 失敗時の扱い（ロールバック/延期/代替手順） |
| ---------- | --------- | -------------------------------- | -------------------------------- | ---------- | ------------------------------------------ |
| 停止時間   | 6時間以内 | 切替日の受注・請求業務           | 作業ログの停止・再開時刻         | 運用責任者 | 延期して旧系を再開                         |
| 件数差異   | 0件       | 2024年以降の受注・請求データ     | 全件照合レポート                 | 業務責任者 | 切替延期                                   |
| 金額差異率 | 0.1%未満  | 同期間の売上・売掛集計           | 旧系合計を分母とした照合レポート | 業務責任者 | 切替延期                                   |

GO の最低条件:

- 上記の全基準に合格
- 受注・請求の業務スモークに合格
- 未解決の重大障害なし

## 6. 体制・役割（GO判断含む）

業務責任者が成功条件に基づき GO/NO-GO を決める。移行チームが投入・照合・切替を実行し、運用チームが監視と一次対応を行う。重大障害は業務責任者へ即時連絡する。

## 7. 移行リスクと対策

- データ不整合は請求誤りを招く。全件照合し、業務責任者が成功条件で判定する。
- 切替遅延は停止延長を招く。リハーサルで所要時間を測り、業務責任者がT-15分で切替未完了なら延期する。

## 8. カットオーバー概要（当日タイムライン/判定点/ロールバック方針）

| 時刻（相対） | イベント       | 完了条件                       | 判定点 | 失敗時の扱い（ロールバック/延期/代替手順）             |
| ------------ | -------------- | ------------------------------ | ------ | ------------------------------------------------------ |
| T-120分      | 旧系受付停止   | 新規受付0件                    | GO1    | 延期し旧系で継続                                       |
| T-90分       | 最終差分抽出   | 対象期間の抽出完了             | GO2    | 抽出条件を修正して1回だけ再抽出、失敗なら延期          |
| T-60分       | 新DB投入・照合 | 成功条件の件数・金額基準に合格 | GO3    | 投入データを移行実行ID単位で無効化し旧系で継続         |
| T-15分       | 接続先切替     | 受注・請求の業務スモーク合格   | GO4    | 接続先を旧系へ戻し、投入データを無効化                 |
| T+0          | 利用開始       | 最初の受注・請求が完了         | GO5    | 旧系へ復帰し、新系で受けた取引を作業ログから照合・反映 |

詳細手順は `cop-index` で定める。

## 9. 移行後ハイパーケア方針

移行後2週間、運用チームが8:00〜20:00に障害・問い合わせを受け、30分以内に応答する。旧系は3か月参照専用とし、その後アーカイブする。

詳細は `dmd-index`（データ）、`mtp-index`（リハーサル）、`otp-index`（運用）で定める。
```

- **良い例**: 「2024年以降の受注・請求データを全件照合し、件数差異0件で GO」と、対象・測定・合格条件を結ぶ。
- **悪い例**: 「データ移行が問題なく完了したら GO」だけでは、測定対象・許容誤差・証跡を特定できない。
