# 外部API仕様 作成ルール

External API Specification Documentation Rules

外部システム（本部、仕入先、会計、物流など）と同期で連携する 1 つの REST API インターフェースを、OpenAPI 形式の YAML 1 ファイルで定義する基準を定めます。

## 1. 全体方針

- **1 連携 1 ファイル**: 1 ファイルは、`ifx-index` の 1 行（1 つの外部連携）が使う REST API の契約とする。同じ相手でも成功後の状態と失敗の影響が異なる連携は、ファイルを分ける。
- **外部との合意に必要な最小十分**: 合意の判断に使う項目だけを書く。最小十分とは、相手側がこのファイルだけで要求を作り、応答の各状態で次の動作を決められることをいう。
- **対象外**: 非同期のメッセージ連携は `ifx-msg`（[[specdojo:ifx-msg-rulebook|外部メッセージ仕様 作成ルール]]）、ファイル連携は `ifx-file`、外部 CLI の起動は `ifx-cmd`（[[specdojo:ifx-cmd-rulebook|外部コマンド連携仕様作成ルール]]）で定める。
- **共通の運用**: `status` の昇格と承認、改訂と廃止は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書では言い直しません。

## 2. 位置づけ

- `ifx-index`（[[specdojo:ifx-index-rulebook|外部システムI/F一覧 作成ルール]]）の `interfaces[].spec_ref` が指す詳細仕様である。一覧で連携の目的・方向・失敗時の扱いを決め、本仕様で要求・応答の契約を決める。
- 作る順序: `ifx-index` に連携の行を置き、`spec_ref: TBD` で未決事項を残したうえで本仕様を作り、作った ID を `spec_ref` に入れる。一覧にない連携の API 仕様を先に作らない。
- 合意の当事者: 自システム側の DEV（開発担当）が ARC（技術メンター）の助言を受けて契約を作り、相手システムの窓口と合意する。業務上の採否と `ready` への昇格は PO が判断する。Role の定義は適用先のロール定義に従う。

## 3. ファイル命名・ID規則

- 配置先: プロダクト文書の `020-external-interface-specs/`。ディレクトリ構成は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従う。
- ファイル名は `ifx-api-<term>.yaml`（例: `ifx-api-sales.yaml`）、ID のローカル部分は `ifx-api-<term>` とする。`<term>` は連携の目的を表す kebab-case とし、版や状態を含めない。
- id やファイル名を変えるときは、`ifx-index` の `spec_ref`、`based_on` で参照する他仕様、YAML の表示のページ（`generated/<name>.md`、yaml-pages で作り直す）を同じ変更でそろえる。旧 id の扱いは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] の改訂・廃止に従う。
- 同梱の完成例の ID `specdojo:ifx-api-sample` は命名上の例外であり、実際の `ifx-index` の参照先には使用しない。

## 4. 先頭メタ項目

ファイルの先頭行に `# specdojo-schema: none reason=external-openapi` を置く。OpenAPI の構造は SpecDojo の schema で検証しないことを示し、`x-spec-meta` の照合は省略されない（[[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] 参照）。

メタ情報は `x-spec-meta` に置く。

| キー     | 説明                                                                  | 必須 |
| -------- | --------------------------------------------------------------------- | ---- |
| id       | API仕様ID（`ifx-api-...`）                                            | ○    |
| type     | `api` 固定                                                            | ○    |
| rulebook | `specdojo:ifx-api-rulebook`                                           | ○    |
| status   | ドキュメントメタ情報標準の値                                          | ○    |
| based_on | 根拠となる文書の ID リスト。参照元の `ifx-index` の ID を最低限入れる | ○    |

## 5. 本文要件

OpenAPI の版は 3.0.3 を既定とする。3.1.x は、相手側の検証器・コード生成が 3.1 に対応すると確認できた場合に限り、DEV が ARC と合意して選ぶ。選んだ版は `openapi` に書く。

| 対象キー                     | 必須性               | 契約として定める内容                                                                                    |
| ---------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------- |
| `openapi`                    | 必須                 | `3.0.3` または合意した `3.1.x`                                                                          |
| `info.title`                 | 必須                 | 連携の目的が分かる名前                                                                                  |
| `info.version`               | 必須                 | 契約の版（`MAJOR.MINOR.PATCH`）                                                                         |
| `info.description`           | 必須                 | 対応する `ifx-index` の連携名、連携の前提、合意対象、未決事項                                           |
| `x-spec-meta`                | 必須                 | 先頭メタ項目の表のキー                                                                                  |
| `servers`                    | 必須（1 つ以上）     | 接続先の種別。実の接続先が未確定なら例示用ドメイン（`example.com`）とする                               |
| `paths`                      | 必須（1 つ以上）     | 実際に提供・利用するエンドポイントだけ。各操作に `operationId` と `responses` を置く                    |
| `responses`                  | 各操作で必須         | 成功の応答と、エラーの応答の表の各コード。各応答の `description` で呼び出し側の次の動作を判断できること |
| `components/schemas`         | 必須                 | 要求・応答・エラーのスキーマ。操作からは `$ref` で参照する                                              |
| `components/securitySchemes` | 認証がある場合は必須 | 認証の方式。操作または全体の `security` で適用する。認証不要ならその旨を `info.description` に書く      |

エラーの応答は、共通の形式（例: `components/schemas/ErrorResponse`）を各操作から参照する。次のコードは、操作に該当しない場合を除き必須とし、省略する場合は省略の理由を `info.description` に書く。

| コード | 意味         | 呼び出し側の扱いとして書く内容           |
| ------ | ------------ | ---------------------------------------- |
| `400`  | 入力不正     | 修正して送り直す項目                     |
| `401`  | 認証失敗     | 再認証の要否                             |
| `403`  | 認可失敗     | 権限の確認先                             |
| `404`  | リソースなし | 対象の指定誤りか、相手側の未登録か       |
| `409`  | 競合         | 既存の登録との関係（既存の ID を返すか） |
| `429`  | 利用制限     | 待機して再試行できるか                   |
| `500`  | 内部エラー   | 再試行の可否と、結果不明として扱うか     |

## 6. 記述ガイド

### 6.1. 操作とスキーマ

- `operationId` は英字の camelCase で一意にする（例: `createSale`）。
- payload のプロパティ名は snake_case とする（例: `sale_id`、`transaction_id`）。識別子・コードの項目には `pattern` か `maxLength` で形式を書く。
- 金額・税・合計など、送るかどうかで相手の計算が変わる項目は、送らない場合も「どちらが計算するか」を `description` に書く。
- 応答の `enum` に失敗を表す値を含める場合は、HTTP の状態コードとの使い分けを `description` に書く。

### 6.2. 再試行と結果不明

- 登録系の操作は、重複を判定する項目（例: 取引 ID）と、`409` で既存の登録を返すかを書く。
- 時間切れなどで結果が分からないときの照会の手段（照会の操作、または未決として `_UNDECIDED_`）を書く。
- 良い例: `409` の応答で既存の `sale_id` を返し、呼び出し側は登録済みとして扱う。
- 悪い例: 「失敗時はリトライ」とだけ書き、二重登録を防ぐ条件がない。

### 6.3. 版と改訂

- 互換を保つ変更（任意の項目の追加、応答への項目の追加）は `info.version` の MINOR を上げる。受信側は知らない応答の項目を無視する前提を `info.description` に書く。
- 互換を壊す変更（項目の削除・改名・必須化、意味の変更）は MAJOR を上げ、パスの版（`/v1` → `/v2`）も上げる。旧版を併存させる期間と廃止の通知は相手と合意し、`ifx-index` の注記にも残す。
- 改訂は、本仕様の変更、`ifx-index` の注記の更新、相手との合意の記録の順に進める。

### 6.4. 未決事項と検証

- 未決事項は `_UNDECIDED_`、仮置きは `_ASSUMPTION_`、未確認は `_TODO_` をコメントで書き、確認先と `ready` にする前に解消する事項を示す。
- 本ファイルは `validate:schema` で構造を検証しない。作成・改訂のたびに、OpenAPI の版に対応した検証器（例: Redocly CLI、Spectral）で構造を確かめ、使った検証器と結果を実行記録に残す。

## 7. 禁止事項

| 禁止事項                                                | 理由                                           |
| ------------------------------------------------------- | ---------------------------------------------- |
| DB の物理テーブル名・物理カラム名・SQL 全文を書く       | 内部の実装で、相手との合意の対象にならないため |
| 実装のクラス・関数名、内部のモジュール構成を書く        | 実装の変更のたびに契約を改訂することになるため |
| UI 操作を逐語で並べる                                   | 画面の仕様の正本と二重になるため               |
| 実の接続先の認証情報・API キーの値を書く                | 文書から秘密情報が漏れるため                   |
| `responses` のない操作を置く                            | 相手が応答ごとの次の動作を決められないため     |
| 互換を壊す変更を `info.version` の MAJOR を上げずに行う | 相手が影響に気づかず連携が壊れるため           |
