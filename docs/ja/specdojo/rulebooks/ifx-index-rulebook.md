# 外部システムI/F一覧 作成ルール

External System Interface List (ESIL) Documentation Rules

外部システムI/F一覧は、システム境界を越える連携の目的、相手、方式、発生条件を YAML で整理する入口である。詳細な接続・認証・障害回復の設計と、外部結合テストの対象を特定できる粒度を定める。

## 1. 全体方針

- 一覧の対象範囲を冒頭コメントに示し、その範囲の連携を一つの正本で管理する。外部サービスだけでなく、境界を越えて起動する CLI や受け渡すファイルも候補にする。
- 連携目的と成功後に得る結果を `name` とコメントで示す。目的、相手、タイミング、失敗の影響が異なる契約は別要素にする。
- 一覧には連携境界と異常時の判断を残す。引数、データ項目、接続先、認証値、終了コード表、再試行の数値は詳細仕様・設定・リファレンスへ委譲する。
- 未決の方式や仮置きの範囲を合意済みとして記さない。未決事項・合意・計画への引き継ぎはコメントで扱い、schema にない管理用キーを追加しない。

## 2. 位置づけと用語定義

| 文書・用語                  | 本系統での役割・意味                                                               |
| --------------------------- | ---------------------------------------------------------------------------------- |
| 外部システムI/F一覧（ESIL） | 連携スコープと詳細契約への入口。内部の関数・全依存パッケージの一覧にはしない       |
| 連携境界                    | 対象システムと、別システム・外部プロセス・外部管理データの間の受け渡し             |
| 詳細 I/F 仕様               | プロトコル、認証、入出力、失敗・回復条件を定義する契約。`spec_ref` で対応づける    |
| 結合テスト                  | 一覧の連携名と詳細仕様から正常・失敗時の対象を選ぶ。テスト手順は本一覧へ展開しない |

要求や業務判断の理由は上位の正本に置く。一覧で必要な影響だけを要約し、技術方式の選択を業務承認の代わりにしない。

## 3. ファイル命名・ID規則

- 全体一覧は `ifx-index.yaml` とし、外部 I/F 仕様の文書群へ配置する。分割時は領域を表す接尾辞を付け、同じ対象範囲の一覧を複製しない。
- `id` は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う修飾 ID とし、ローカル ID は `ifx-index` を基準に対象範囲内で一意にする。許容形式の正本は `docs/specdojo/schemas/v1/esil.schema.yaml` とし、独自の正規表現で制限しない。成果物の `prj-0001:ifx-index` と完成例の `specdojo:ifx-index-sample` は、所有元と用途を区別する ID である。
- 連携名は一覧内で一意にし、改称・分割時は旧名との対応をコメントへ残す。位置番号を連携の識別子として使用しない。
- 追加・廃止・方式変更時は ARC が影響する連携と詳細仕様を特定し、DEV へ実装範囲、QE へ結合テスト対象、スコープ変更なら PO へ判断事項を引き継ぐ。文書の置き換えは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。

## 4. 先頭メタ項目

YAML のトップレベルへメタ情報を置く。必須キー、値域、型、参照形式は `docs/specdojo/schemas/v1/esil.schema.yaml` を正本とし、ファイル先頭の modeline で参照する。

- `id`・`title` は一覧と対象システムを識別できる内容にし、`type` は本系統の成果物種別、`rulebook` は本書の ID とする。
- `status` は文書の成熟度を表し、個々の連携の採否・進捗や公開許可を代用しない。人間の PO が一覧の承認・保留・差し戻し、`ready` への昇格と公開可否の最終判断を担う。agent は `draft` のまま引き継ぐ。
- `based_on` は実際の依存関係に含まれる直接の根拠だけを記す。プロジェクト共通文脈や詳細仕様を機械的に転記しない。

## 5. 本文要件

キーの骨組みは宣言された雛形に置く。本章は各記入領域の目的と判断条件を定め、キーの型・列挙値・構文は schema へ委譲する。

| 記入領域                  | 必須性 | 目的・記述要件                                                                                                                                      |
| ------------------------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 冒頭コメント              | 必須   | 対象範囲・境界・主要な対象外、一覧の管理担当 Role code、承認・公開判断者と公開対象を示す。仮定や未決のスコープはラベルで区別する                    |
| `interfaces` の目的と両端 | 必須   | `name`・`source`・`target` で連携目的と両端を特定する。抽象名だけなら目的をコメントで補う                                                           |
| 方向と方式                | 必須   | `direction`・`kind`・`format` で境界上の受け渡しを示す。サービス内部の方式と呼び出し側の方式を混同しない                                            |
| 発生条件                  | 必須   | `timing` で業務イベント・操作・周期と、起動する条件を示す。周期が不明なら仮の時刻を固定しない                                                       |
| 異常時の判断              | 必須   | `error_handling` に未完了・結果不明になる結果、停止・保留の条件、確認対象と担当を示す。副作用の確認前に再送できると断定しない                       |
| 詳細への導線              | 必須   | `spec_ref` に実在する対応仕様 ID を置く。未整備・対応未確認なら `TBD` とし、「詳細参照と未決事項」の情報をコメントに残す                            |
| 合意・管理への導線        | 必須   | IF ごとの確認者・合意対象をコメントで対応づける。未決事項・リスク・課題・変更要求がある場合は、影響する後続作業と計画・管理記録への引き継ぎ先を示す |

`direction` は指定した `source` と `target` に対して読む。要求と応答の両方を一契約として扱う場合は双方向とし、送信データと受付結果の意味をコメントで区別する。schema で任意の項目でも、本一覧から下流へ判断を渡すために本章が要求する項目は記入する。

## 6. 記述ガイド

### 6.1. メタ情報と対象範囲

- 判断基準: どのシステム・利用場面の境界を管理するか、対象外と仮定を含めて識別でき、管理担当と公開判断者をたどれること。
- 良い例: 「店舗端末から本部への商品照会・売上登録を対象とする。仕入先連携は対象外。管理は ARC、一覧の承認と社外公開判断は人間の PO」と冒頭に記す。
- 悪い例: タイトルを「外部連携」とだけ書いて将来候補を現在の対象へ混ぜる、または `status` だけで公開可能と扱う。

### 6.2. 連携単位・目的・両端

- 判断基準: 同じ詳細契約と完了条件で追える単位に分け、相手を一意に識別できること。同じ相手でも参照と更新の失敗影響が異なれば分ける。
- 良い例: 「商品照会」と「売上登録」を別要素にし、それぞれ取得結果と受付結果を示す。
- 悪い例: 「本部連携」に照会・登録・夜間転送をまとめ、どの操作が失敗したか追えない。

### 6.3. 方向・方式・形式

- 判断基準: この境界で渡す形式を選ぶ。外部 CLI の背後に API があっても、呼び出し側がプロセスを起動する契約ならコマンドとして扱う。
- 良い例: CLI へ印字を依頼し結果を受け取る契約を双方向・コマンドとし、テキストと結果報告が混在するなら形式の内訳をコメントで補う。
- 悪い例: SaaS を使うという理由だけで API に分類する、または stdout の一部が JSON だから全ストリームを JSON と断定する。

### 6.4. 発生条件

- 判断基準: 誰の操作・どのイベントで、何が整ったら連携するかを読み取れること。
- 良い例: 「会計確定と控え保存の後、レシート印字を要求した時」とする。
- 悪い例: 「随時」「必要時」だけで終え、実行条件を実装者へ任せる。

### 6.5. 異常時の判断

- 判断基準: 失敗で何が未完了・結果不明になるか、誰が確認して次へ進むかが分かること。
- 良い例: 「印字結果不明なら会計は維持し、控えを保持して店番担当が紙面確認する」とする。
- 悪い例: 「失敗したらリトライ」とだけ書き、二重登録・二重印字の可能性を扱わない。

### 6.6. 詳細参照と未決事項

- 判断基準: 実在する契約へ到達できること。`TBD` や未決の方式には、論点、担当 Role code、解消条件、期限または判断するマイルストーン、影響する業務・後続作業・公開範囲、次アクションをコメントで残す。作成・確認待ちは `_TODO_:`、意思決定待ちは `_UNDECIDED_:`、仮定は `_ASSUMPTION_:` で区別する。
- 良い例: `spec_ref: TBD` に「`_UNDECIDED_:` ARC が DEV と売上受付の照合方式を決め、詳細仕様を作成する。外部結合テスト着手前に QE が結果不明時の期待結果を確認するまで、売上登録の受入を保留し PO へ判断を依頼する」と添える。
- 悪い例: 説明なしの `TBD`、担当・判断時期のない「後で決める」、未作成の文書 ID を完成した契約として扱う参照。期限を推測で固定したり、影響する連携を区別せず一覧全体を完了扱いにしたりしない。

共通条件は一覧冒頭、契約固有条件は詳細仕様を正本とする。詳細仕様が存在しても未決事項があれば `spec_ref` だけで解決済みとせず、判断に必要な影響と追跡先を一覧に残す。

### 6.7. 合意・計画・課題への引き継ぎ

IF ごとのコメントは次の情報を対応づける。既存の計画・管理記録にある情報は参照先から解決できればよく、値を転載しない。複数 IF で共通なら、対象の連携名を明示して冒頭または末尾にまとめてよい。

| 対象                     | コメントに残す判断情報                                                                                                             | 正本・引き継ぎ先                                                                                                      |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 確認と合意               | 利用場面・業務影響を確認する BA、契約を確認する ARC・DEV、期待結果を確認する QE と合意対象。外部側との調整が必要なら確認窓口も示す | 役割の割当は組織・メンバー定義を参照する。必要な窓口が未特定なら担当 Role と特定する時点を未決事項として残す          |
| 詳細仕様の作成と進捗     | 担当 Role code、未着手・作成中・確認待ちなどの現在の論点、完了条件、期限または判断するマイルストーン、依存する後続作業             | PM が Schedule の作業へ接続する。担当・期日・進捗の正本は計画に置き、一覧には作業 ID と引き継ぎ時点の未完了事項を残す |
| リスク・課題・変更・決定 | 対象の連携名、発生条件または未決論点、業務・公開・後続仕様・Schedule への影響、対応担当 Role code、報告先、次アクション            | PM が PJR または採用済み管理簿へ接続し、PO の判断を決定記録へ残す。一覧には転送先レコードと連携への影響を残す         |

- 判断基準: 連携名から確認者、未完了作業、管理記録を追跡できること。未登録なら PM への登録依頼と登録時点を記し、登録後は実在するレコードへ参照を付け替える。採否・公開条件が未決なら、PO に渡す判断対象と保留する範囲を明示する。
- 良い例: 「売上登録は ARC が契約を作成中。BA と本部運用窓口が保留時の運用、QE が結果照合を確認する。PM は外部結合テスト計画確定前に認証未合意を PJR へ登録し、テスト着手への影響と PO の採否判断を追跡する」と記す。
- 悪い例: 「関係者確認済み」「進捗は順調」だけで合意対象や残作業を隠す、または一覧に管理簿の全履歴・期日・進捗表を複製する。

### 6.8. 検証と引き渡しの判定

- 対象と方法: repository のルートで、`<対象YAMLファイルのrepository相対パス>` を実際の一覧に置き換える。schema 検証は `validate:schema:file` script がある場合、整形検査は Prettier が導入されている場合に次を実行する。別環境では同じ schema による検証と採用済み整形手順を用いる。

  ```bash
  npm run validate:schema:file -- --schema docs/specdojo/schemas/v1/esil.schema.yaml --data '<対象YAMLファイルのrepository相対パス>'
  npx prettier --check '<対象YAMLファイルのrepository相対パス>'
  ```

- 合格条件: 両コマンドが終了コード 0 となり、schema 違反と整形差分がないこと。エラーは対象箇所を修正して再実行し、検証対象・コマンド・結果を実行記録に残す。
- 内容の判定: schema だけではコメントの充足や参照先の実在を判定できない。各連携について「本文要件」の必須領域、連携名の一意性、方向と両端の一致、詳細仕様との対応、未決事項と管理記録への導線を照合する。不足は未解消として担当と次アクションを引き継ぎ、検証成功を承認・公開判断の代わりにしない。

## 7. 禁止事項

- 根拠のない接続方式、認証方式、承認済みの範囲を確定情報として記すこと。
- 連携の目的・失敗影響が異なる操作を、相手が同じという理由だけでまとめること。
- 認証情報、個人環境の認証パス、秘密値入り URL を記載すること。
- 引数、ペイロード構造、設定値、再試行回数、終了コード一覧を正本から転載すること。
- 未作成文書へのリンク、確認していない詳細仕様 ID、説明のない `TBD` を残すこと。
- `status` や技術レビューの成功だけで、人間の PO の承認・公開判断を済んだものとすること。
- schema にない担当・期限・進捗・リスクのキーを追加したり、Schedule・管理簿・決定記録を一覧へ複製したりすること。
