# 外部システムI/F一覧 作成ルール

External System Interface List Documentation Rules

外部システムI/F一覧は、システム境界を越える連携の目的、相手、方式、発生条件を YAML で整理する入口である。詳細な接続・認証・障害回復の設計と、外部結合テストの対象を特定できる粒度を定める。

## 1. 全体方針

- 一覧の対象範囲を冒頭コメントに示し、その範囲の連携を一つの正本で管理する。外部サービスだけでなく、境界を越えて起動する CLI や受け渡すファイルも候補にする。
- 連携目的と成功後に得る結果を `name` とコメントで示す。目的、相手、タイミング、失敗の影響が異なる契約は別要素にする。
- 一覧には連携境界と異常時の判断を残す。引数、データ項目、接続先、認証値、終了コード表、再試行の数値は詳細仕様・設定・リファレンスへ委譲する。
- 未決の方式や仮置きの範囲を合意済みとして記さない。未決事項・合意・計画への引き継ぎはコメントで扱い、schema にない管理用キーを追加しない。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱い、業務の受入確認に含めない。

## 2. 位置づけ

連携境界は、対象システムと別システム・外部プロセス・外部管理データの間の受け渡しを指す。一覧は上位の要求を受けて詳細 I/F 仕様へ接続し、連携名と詳細仕様から正常・失敗時の結合テスト対象を選ぶ入口とする。内部の関数・全依存パッケージやテスト手順の一覧にはしない。

## 3. ファイル命名・ID規則

- 全体一覧は `ifx-index.yaml` とし、外部 I/F 仕様の文書群へ配置する。分割時は領域を表す接尾辞を付け、同じ対象範囲の一覧を複製しない。
- `id` は修飾 ID とし、ローカル ID は `ifx-index` を基準に対象範囲内で一意にする。許容形式は `docs/specdojo/schemas/v1/ifx-index.schema.yaml` を正本とし、独自の正規表現で制限しない。
- 連携名は一覧内で一意にし、改称・分割時は旧名との対応をコメントへ残す。位置番号を連携の識別子として使用しない。
- 連携の追加・廃止・方式変更では、影響する詳細仕様、実装範囲、結合テスト対象と、連携スコープの変化を特定する。

## 4. 先頭メタ項目

YAML のトップレベルへメタ情報を置く。必須キー、値域、型、参照形式は `docs/specdojo/schemas/v1/ifx-index.schema.yaml` を正本とし、ファイル先頭の modeline で参照する。

- `id`・`title` は一覧と対象システムを識別できる内容にし、`type` は本系統の成果物種別、`rulebook` は本書の ID とする。
- `status` の値は `draft`・`ready`・`deprecated` とする。個々の連携の採否・進捗はコメントで区別する。
- `based_on` は実際の依存関係に含まれる直接の根拠だけを記す。プロジェクト共通文脈や詳細仕様を機械的に転記しない。

## 5. 本文要件

キーの骨組みは宣言された雛形に置く。本章は各記入領域の目的と判断条件を定め、キーの型・構文は schema へ委譲する。列挙値は選び方に関わるものだけを本章で示す。

| 記入領域                  | 必須性 | 目的・記述要件                                                                                                                |
| ------------------------- | ------ | ----------------------------------------------------------------------------------------------------------------------------- |
| 冒頭コメント              | 必須   | 対象範囲・境界・主要な対象外を示す。仮定や未決のスコープはラベルで区別する                                                    |
| `interfaces` の目的と両端 | 必須   | `name`・`source`・`target` で連携目的と両端を特定する。抽象名だけなら目的をコメントで補う                                     |
| 方向と方式                | 必須   | `direction`・`kind`・`format` で境界上の受け渡しを示す。サービス内部の方式と呼び出し側の方式を混同しない                      |
| 発生条件                  | 必須   | `timing` で業務イベント・操作・周期と、起動する条件を示す。周期が不明なら仮の時刻を固定しない                                 |
| 異常時の判断              | 必須   | `error_handling` に未完了・結果不明になる結果、停止・保留の条件、確認対象と担当を示す。副作用の確認前に再送できると断定しない |
| 詳細への導線              | 必須   | `spec_ref` に実在する対応仕様 ID を置く。未整備・対応未確認なら `TBD` とし、「詳細参照と未決事項」の情報をコメントに残す      |
| 合意・管理への導線        | 必須   | IF ごとの確認者・合意対象をコメントで対応づける。未決事項がある場合は、影響する連携と後続作業、当面の保留範囲を示す           |

`direction` は指定した `source` と `target` に対して読み、`source` から送るなら `source_to_target`、`target` から受けるなら `target_to_source` とする。要求と応答の両方を一契約として扱う場合は `bidirectional` とし、送信データと受付結果の意味をコメントで区別する。`kind` は境界で受け渡す手段を `API`・`ファイル`・`メッセージ`・`コマンド` から選ぶ。`format` は `CSV`・`JSON`・`XML` から選び、どれにも当たらなければ `その他`、未決なら `TBD` としてコメントで内訳や論点を補う。schema で任意の項目でも、本一覧から下流へ判断を渡すために本章が要求する項目は記入する。

## 6. 記述ガイド

### 6.1. メタ情報と対象範囲

- 判断基準: どのシステム・利用場面の境界を管理するか、対象外と仮定を含めて識別できること。
- 良い例: 「店舗端末から本部への商品照会・売上登録を対象とする。仕入先連携は対象外」と冒頭に記す。
- 悪い例: タイトルを「外部連携」とだけ書いて将来候補を現在の対象へ混ぜる。

### 6.2. 連携単位・目的・両端

- 判断基準: 同じ詳細契約と完了条件で追える単位に分け、相手を一意に識別できること。同じ相手でも参照と更新の失敗影響が異なれば分ける。
- 良い例: 「商品照会」と「売上登録」を別要素にし、それぞれ取得結果と受付結果を示す。
- 悪い例: 「本部連携」に照会・登録・夜間転送をまとめ、どの操作が失敗したか追えない。

### 6.3. 方向・方式・形式

- 判断基準: この境界で渡す形式を選ぶ。外部 CLI の背後に API があっても、呼び出し側がプロセスを起動する契約ならコマンドとして扱う。
- 良い例: CLI へ印字を依頼し結果を受け取る契約を双方向・コマンドとし、テキストと結果報告が混在するなら形式の内訳をコメントで補う。
- 悪い例: SaaS を使うという理由だけで API に分類する、または stdout の一部が JSON だから全ストリームを JSON と断定する。

### 6.4. 発生条件

- 判断基準: 誰の操作・どのイベントで、何が整ったら連携するかを読み取れること。
- 良い例: 「会計確定と控え保存の後、レシート印字を要求した時」とする。
- 悪い例: 「随時」「必要時」だけで終え、実行条件を実装者へ任せる。

### 6.5. 異常時の判断

- 判断基準: 失敗で何が未完了・結果不明になるか、誰が確認して次へ進むかが分かること。
- 良い例: 「印字結果不明なら会計は維持し、控えを保持して店番担当が紙面確認する」とする。
- 悪い例: 「失敗したらリトライ」とだけ書き、二重登録・二重印字の可能性を扱わない。

### 6.6. 詳細参照と未決事項

- 判断基準: 実在する契約へ到達できること。`TBD` や未決の方式には、論点、解消条件、影響する連携・業務・後続作業、当面の扱いをコメントで残す。
- 良い例: `spec_ref: TBD` に「`_UNDECIDED_:` 売上受付の照合方式が未決。詳細契約と結果不明時の期待結果がそろうまで、売上登録の受入を保留する」と添える。
- 悪い例: 説明なしの `TBD`、未作成の文書 ID を完成した契約として扱う参照、影響する連携を区別せず一覧全体を完了扱いにする記述。

共通条件は一覧冒頭、契約固有条件は詳細仕様を正本とする。詳細仕様が存在しても未決事項があれば `spec_ref` だけで解決済みとせず、残る論点と影響を一覧に残す。

### 6.7. 合意・計画・課題への引き継ぎ

- 判断基準: 連携名から利用場面・業務影響、契約、期待結果それぞれの確認者と合意対象を特定できること。外部側との調整が必要なら確認窓口も示す。複数 IF で共通なら、連携名を明示してコメントを冒頭または末尾にまとめてよい。
- 良い例: 「売上登録は店番担当と本部運用窓口が保留時の店頭対応、契約の確認者が受付・回復条件、テストの確認者が結果照合を確認する。認証方式が未合意のため外部結合テストの着手は保留」と記す。
- 悪い例: 「関係者確認済み」「進捗は順調」だけで合意対象や残る論点を隠す、または一覧に計画・管理簿の期日・進捗表を複製する。

### 6.8. 検証と引き渡しの判定

- 対象と方法: 対象範囲の利用場面と各連携を突き合わせ、正常時・失敗時の受け渡しをたどる。「本文要件」の必須領域、連携名の一意性、方向と両端の一致、詳細仕様との対応を照合し、IF ごとの確認者と合意対象を確かめる。
- 合格条件: 対象内の連携に抜けがなく、目的・発生条件・成功後の結果と、失敗時に止める操作・確認対象・担当を特定できること。詳細仕様が対象操作に対応し、結果不明時に無条件の再送を要求していないこと。
- 未解消事項の扱い: 詳細仕様が未整備、または方式・期待結果が未合意なら、該当連携の論点と影響、保留する業務・後続作業を明示して引き渡す。ほかの連携と分けて判定し、一覧全体を解消済みとしない。

### 6.9. 表示ページでのレビュー

YAML を正本とし、`specdojo yaml-pages build` が同階層の `generated/` へ表形式の表示ページを生成する。レビューは表示ページで行い、修正は YAML へ戻す。

| ページの部分   | YAML からの取り出し方                                                                                                            |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 要約の表       | `id`・`status`・`interfaces` の件数・`spec_ref` が `TBD` の件数                                                                  |
| 連携の一覧     | `interfaces` の順に、連携名・`target`・`direction`・`kind`・`format`・`spec_ref`・注記の件数と目印（`_TODO_` など）を 1 行に置く |
| 連携ごとの詳細 | 連携ごとに、schema の項目（`source`・`timing`・`error_handling` を含む）を表にし、その連携のコメントを注記として続ける           |
| 一覧全体の注記 | `interfaces` の外にある冒頭・末尾のコメント                                                                                      |
| YAML の正本    | YAML 全文を折りたたんで添える                                                                                                    |

- 連携のコメントは、連携の直前（`- name` と同じ字下げ）と連携の内側（より深い字下げ）に置いたものとする。行頭から始まるコメントは一覧全体の注記になる。連携に関わる未決事項・留保はこの位置に書く。
- `spec_ref` は詳細仕様への wikilink にし、プロジェクトの修飾がなければ一覧の `id` の修飾を補う。`TBD` は「未整備（TBD）」と表示する。
- `direction` は「連携元 → 連携先」「連携先 → 連携元」「双方向」と表示する。表示ページのために schema にないキーを YAML へ足さない。

## 7. 禁止事項

- 連携の目的・失敗影響が異なる操作を、相手が同じという理由だけでまとめること。
- 引数、ペイロード構造、設定値、再試行回数、終了コード一覧を正本から転載すること。
- 対象操作との対応を確認していない詳細仕様 ID、説明のない `TBD` を残すこと。
- schema にない担当・期限・進捗・リスクのキーを追加したり、Schedule・管理簿・決定記録を一覧へ複製したりすること。
