# 非機能要件 / 保守性 作成ルール

Non-Functional Requirements Maintainability Documentation Rules

本書は、非機能要件のうち保守性（変更容易性・障害解析容易性）を定義する `nfr-maintainability` の作成ルールを定める。`nfr-maintainability` は、受入判定（`sac-*`）と運用設計・手順（`opd-*` / `opr-*`）が同じ閾値で変更・障害対応の効率を判定するための文書である。

## 1. 全体方針

- 保守性は、変更と障害対応にかかる時間・手間を、指標と閾値で判定できる要件として書く。実装方法ではなく、達成すべき作業効率を書く。
- 保守性の中核の要件（障害の切り分け・切り戻し・軽微変更の反映）は未決に回さない。利用者が決める閾値は推測で埋めず `_UNDECIDED_` で残す。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直さない。文書の整形・lint はリポジトリの検証で扱い、「測定・検証方法」に含めない。
- _UNDECIDED_: `recipe`・`template` の要否は未判断である。sample を「本文要件」の構成に揃えた後、同じ構成を NFR 分冊で共通の template にできるかを論点として判断する。

## 2. 位置づけと用語定義

### 2.1. 位置づけ

変更・障害対応の効率の閾値を判断するための文書であり、次の文書と接続する。閾値を変えたときは「閾値を変えたときの波及」の列の文書を同時に見直す。

| 文書               | 関係                                               | 閾値を変えたときの波及                                |
| ------------------ | -------------------------------------------------- | ----------------------------------------------------- |
| `nfr-index`        | NFR 全体の入口。分冊として `part_of` で属する      | なし                                                  |
| `nfr-availability` | 停止許容・RTO/RPO の正本。本書は作業効率だけを扱う | 一次切り分け・切り戻しの時間が RTO に収まるか確かめる |
| `sac-*`            | 保守性要件の受入判定で閾値を参照する               | 判定基準を同じ値に直す                                |
| `opd-*` / `opr-*`  | 本書の閾値を前提に障害対応・変更の手順を組む       | 手順の所要時間・訓練の基準を直す                      |
| `dec-*`            | 閾値・測定方法を決めた・見直した判断の記録         | 見直しの判断を新しい `dec-*` に残す                   |

### 2.2. 用語定義

| 用語             | 定義                                                                         |
| ---------------- | ---------------------------------------------------------------------------- |
| MTTR             | 障害の検知から業務の再開までにかかった時間の平均                             |
| 変更リードタイム | 変更の要求を受けてから本番へ反映するまでの時間                               |
| 一次切り分け時間 | 障害の検知から、原因の範囲（アプリ・データ・端末・外部）を特定するまでの時間 |
| ロールバック時間 | 切り戻しを決めてから、直前の正常な版で業務を再開するまでの時間               |

## 3. ファイル命名・ID規則

- 配置とファイル名は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従い、文書 ID は `nfr-maintainability` とする。
- 要件 ID は `nfr-mnt-<連番>`（3 桁、例: `nfr-mnt-001`）とする。廃止・統合した ID の連番は再利用しない。
- 要件 ID を廃止・改訂したときは、その ID を参照する `sac-*`・`opr-*` の記述を同じ変更で追従させる。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。

- `specdojo.type` は本書の `deliverable_type` と同じ `requirement` とする（`lint:fm` が照合する）。`specdojo.rulebook` は `specdojo:nfr-maintainability-rulebook` とする。
- `specdojo.part_of` は `nfr-index` とする。
- `specdojo.based_on` には、監視・ログ・Runbook の水準の根拠として実際に読んだ作成済み文書の ID を記載する。

## 5. 本文要件

`nfr-maintainability` は次の章を **順序固定** で置く。生成する本文の見出しは番号と見出しをそのまま使う。

| 番号 | 見出し               | 必須 | 受入条件                                                                           |
| ---- | -------------------- | ---- | ---------------------------------------------------------------------------------- |
| 1    | 概要（対象・目的）   | ○    | 対象の変更・障害対応、業務影響、応えるプロジェクトの目的が分かる                   |
| 2    | 適用範囲・前提条件   | ○    | 対象システム・時間帯・保守作業を担う役割・測定の前提となる基盤・対象外が揃っている |
| 3    | 保守性要件一覧       | ○    | 全要件が標準 5 列で、基準から pass / fail を一意に判定できる                       |
| 4    | 測定・検証方法       | ○    | 全要件 ID に測定方法・判定タイミング・判定者がある                                 |
| 5    | 関連ドキュメント導線 | ○    | 「位置づけ」の表の文書（`nfr-index` を除く）への導線がある                         |

- 「保守性要件一覧」の列は `id` / `内容` / `指標` / `基準` / `備考` の順とする。
- 「測定・検証方法」の列は `要件ID` / `測定方法` / `判定タイミング` / `判定者` の順とする。

## 6. 記述ガイド

完成例の全体像は Frontmatter の `sample` で宣言された sample を参照する。

### 6.1. 概要（対象・目的）

- **判断基準**: どの変更・障害対応の効率を担保するか、効率が落ちると業務がどう止まるか（業務停止時間、変更待ちの影響）、プロジェクトのどの目的に応えるかが 2〜3 文で分かること。閾値の根拠をこの業務影響からたどれること。
- **良い例**: 「店主不在の日も家族が店番を続けられるよう、レジが止まったときの切り分けと切り戻しを短時間で終え、販売記録の中断を抑える」
- **悪い例**: 「保守しやすいシステムにする」（対象の作業も業務影響も分からない）

### 6.2. 適用範囲・前提条件

- **判断基準**: 対象システム、対象時間帯、保守作業（切り分け・修正・切り戻し）を担う役割の Role code、測定の前提となる外部依存（監視・ログ基盤、インシデント記録、CI）を項目ごとに書く。
- 対象外として、他の NFR との境界を書く。停止許容と RTO/RPO は `nfr-availability`、処理時間は `nfr-performance` に置き、本書では重ねて定義しない。
- **良い例**: 「測定の前提: 障害の検知時刻と再開時刻をインシデント記録に残す」
- **悪い例**: 「監視は別途用意する」（測定の前提になる記録の有無が分からない）

### 6.3. 保守性要件一覧

- **判断基準**: 基準に閾値・集計方法（平均・最大・パーセンタイル）・集計期間を併記し、基準だけで pass / fail を一意に判定できること。指標の例は MTTR、変更リードタイム、一次切り分け時間、ロールバック時間である。
- **良い例**: 「一次切り分け時間 / 各障害で最大 15 分以内（障害ごとに判定）」「変更リードタイム / 標準変更の 90 パーセンタイルで 3 営業日以内（月次集計）」
- **悪い例**: 「MTTR 60 分」（平均か最大か、どの期間で集計するかが分からない）

### 6.4. 測定・検証方法

- **判断基準**: 要件 ID ごとに、測定方法（監視記録、障害レポート、訓練、CI の計測など）、判定タイミング、判定者を書く。判定者は人の Role code とし、agent には測定値の集計の補助までを担わせる。
- 判定で見つかった事柄の記録先を区別する。閾値が決まっていないものは `_UNDECIDED_` として登録簿へ引き継ぎ、基準未達は課題として登録簿の個票に残し、閾値・測定方法の変更の判断は `dec-*` に残す。
- 閾値を見直す契機（基準未達が続く、測定の前提となる基盤が変わる、業務時間帯が変わる）を書き、見直した結果は `dec-*` に残して「位置づけ」の表の波及先を直す。
- **良い例**: 「`nfr-mnt-003` / 障害レポートの検知時刻と切り分け完了時刻の差 / 障害事後レビュー / `OPS`」
- **悪い例**: 「判定者: SRE / PM」（Role code ではなく、誰が判定するか一意に決まらない）

### 6.5. 関連ドキュメント導線

- 「位置づけ」の表の文書へ、種別・ドキュメント ID・目的の表で導線を置く。まだ存在しない文書はバッククォートで仮置きする。

## 7. 禁止事項

| 禁止事項                               | 理由                                    |
| -------------------------------------- | --------------------------------------- |
| 「保守しやすい」だけで閾値を示さない   | 判定不能のため                          |
| 集計方法・集計期間のない基準を書く     | 判定者によって合否がぶれるため          |
| 体制依存の一時運用を恒久要件化する     | 再現性がないため                        |
| 測定データの取得方法を書かない         | 継続評価できないため                    |
| 停止許容時間・RTO/RPO を本書で定義する | `nfr-availability` と二重管理になるため |
| 判定者を職名や agent で書く            | 判定の責任が一意に決まらないため        |
