# 非機能要件 / 可用性 作成ルール

Non-Functional Requirements Availability Documentation Rules

本書は、非機能要件のうち可用性（停止許容・復旧目標）を定義する `nfr-availability` の作成ルールを定める。`nfr-availability` は、障害時にどこまでの停止とデータ損失を許すかを判断し、受入・試験・運用の判定基準を揃えるための文書である。

## 1. 全体方針

- 可用性は稼働率、許容停止時間、RTO/RPO で定量的に定義する。
- 基準値は、重要業務時間帯と停止時の業務影響を示す根拠文書から導き、要件ごとに根拠を辿れるようにする。
- 対象時間帯と除外条件（計画停止など）を明記し、監視と復旧判断に結びつけて要件化する。
- **実践の型の構成**: 本文要件・記述ガイド・完成例で作成を判断できるため、`recipe`・`template` は `not-needed` とする。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直さない。文書の整形・lint はリポジトリの検証で扱い、「測定・検証方法」に含めない。

## 2. 位置づけと用語定義

### 2.1. 位置づけ

- `nfr-index`：NFR全体の入口
- `sac-*` / `stc-*`：可用性要件の合否判定基準と試験
- `opd-*` / `opr-*`：障害対応・復旧手順
- 基準値を変更したときは、`sac-*` / `stc-*` の判定基準と `opr-*` の復旧手順を見直す。

### 2.2. 用語定義

| 用語   | 定義                                                                                   |
| ------ | -------------------------------------------------------------------------------------- |
| 稼働率 | 対象時間から除外時間を引いた時間のうち、サービスを提供できた時間の割合                 |
| RTO    | 障害の検知から、業務を再開できる状態に戻すまでに許容する時間（目標復旧時間）           |
| RPO    | 復旧後に失ってよいデータの範囲を、障害発生時点から遡る時間で表したもの（目標復旧時点） |

## 3. ファイル命名・ID規則

- ルールドキュメントIDは `specdojo:nfr-availability-rulebook`。
- 生成対象ドキュメントIDは `nfr-availability` を推奨する。
- 要件IDは `nfr-avl-<連番>` を推奨する。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。

- `specdojo.id` は `nfr-availability`、`specdojo.type` は `requirement`、`specdojo.rulebook` は `specdojo:nfr-availability-rulebook`、`specdojo.part_of` は `nfr-index` とする。
- 重要業務時間帯（営業時間、締め時刻）と停止時の業務影響の根拠文書を `specdojo.based_on` に挙げ、本文の対象時間帯と揃える。

## 5. 本文要件

`nfr-availability` は以下の章を順序固定で配置する。

| 順序 | 章                   | 必須     | 内容                                                       |
| ---- | -------------------- | -------- | ---------------------------------------------------------- |
| 1    | 概要（対象・目的）   | ○        | 対象業務、停止時の業務影響、復旧判断の担当                 |
| 2    | 適用範囲・除外条件   | ○        | 対象時間帯、計画停止、外部依存の停止と SLA の扱い          |
| 3    | 可用性要件一覧       | ○        | 要件ID、対象範囲、指標、基準値、根拠、技術前提             |
| 4    | 測定・検証方法       | ○        | 算出式、測定期間、RTO/RPO の起点と終点、測定方法、判定時期 |
| 5    | 関連ドキュメント導線 | ○        | 検証先・復旧手順・設計判断の文書                           |
| 6    | 未決事項             | 条件付き | 未確定の基準値・外部 SLA・技術前提があるときだけ置く       |

## 6. 記述ガイド

各節は「本文要件」の同名の章に対応する。

### 6.1. 概要（対象・目的）

- 可用性を定める対象業務と、停止したときに起きる業務影響（売上の取りこぼし、記録漏れなど）を書く。
- 基準値の根拠とした文書（営業時間、業務フローなど）を示す。
- 障害時に復旧の判断を担う運用者を Role code で示す。文書の作成・承認の担当は書かない。

判断基準: 対象業務と停止の影響から、基準値の厳しさの理由を説明できること。

- 良い例: 「店頭の会計が止まると販売記録が残らない。営業時間中の会計を対象とし、復旧の判断は OPS が行う。」
- 悪い例: 「システムを安定稼働させる。」（対象業務と停止の影響がない）

### 6.2. 適用範囲・除外条件

- 対象時間帯（営業時間、締め処理の時刻など）を書く。
- 計画停止の時間帯と、稼働率の計算から除くかどうかを書く。
- 外部依存サービス（決済、クラウドなど）ごとに SLA を示し、自システムの基準値と整合するかを確かめる。整合しない場合は「未決事項」にリスクとして書く。

判断基準: 停止がどの条件で要件の対象になるかを一意に判断できること。

- 良い例: 「対象は営業日の 10:00〜19:00。計画停止は閉店後に限り稼働率から除く。決済サービスの SLA 99.5% は会計の基準 99.9% を下回るため、未決事項に記載する。」
- 悪い例: 「メンテナンス時は除く。」（時間帯と外部依存の扱いがない）

### 6.3. 可用性要件一覧

- 表形式（`要件ID` / `対象範囲` / `指標` / `基準` / `根拠・業務影響` / `技術前提`）で記述する。
- `対象範囲` はシステム・機能・コンポーネントのどれかを明記する。指標は月間稼働率、RTO、RPO など。
- `基準` は単位と比較方向（以上／以内）を付ける。初期仮説の値は `_ASSUMPTION_` を付け、確定値と区別する。
- `技術前提` には基準値を支える冗長化・バックアップ・監視の前提と、対応する設計文書または `dec-*` を書く。

判断基準: 要件ごとに対象・基準・根拠・支える仕組みが揃い、確定か仮説かが分かること。

- 良い例: 「`nfr-avl-002` / 会計機能 / RPO / 15 分以内 / 会計記録の欠落防止 / 15 分ごとのバックアップ（`dec-0003`）」
- 悪い例: 「RPO / 短く / 重要なため」（対象・単位・比較方向・技術前提がない）

### 6.4. 測定・検証方法

- 要件IDごとに、監視値・障害訓練・復旧試験による測定方法と判定時期を定める。
- 稼働率は算出式（対象時間・除外時間の扱い）と測定期間を示す。
- RTO は起点（障害の検知）と終点（業務の再開）、RPO は失ったデータの範囲の確かめ方を示す。基準値は「可用性要件一覧」を参照し、言い直さない。

判断基準: 測定結果から pass / fail を一意に判定できること。

- 良い例: 「`nfr-avl-001`：月間の（対象時間 − 計画停止）に占める提供時間を外形監視で算出し、月次の運用レビューで判定する。」
- 悪い例: 「定期的に確認する。」（算出式・期間・判定時期がない）

### 6.5. 関連ドキュメント導線

- 「位置づけ」の文書と設計判断の `dec-*` を、種別・ドキュメントID・目的の表で紐づける。
- 基準値を変えたときに見直す `sac-*` / `stc-*` / `opr-*` が分かるようにする。
- 未作成の文書はバッククォートで仮置きする。

判断基準: 各要件の検証先と復旧手順へ辿れること。

- 良い例: 「受入条件 / `sac-availability` / 稼働率・RTO の合否判定」
- 悪い例: 「関連資料を参照。」（文書と目的が特定できない）

### 6.6. 未決事項

- 未確定の基準値・外部 SLA・技術前提は推測で確定せず、`_UNDECIDED_` を付して論点と影響（当面の扱い、決まったときに直す要件ID）を書く。

## 7. 禁止事項

| 禁止事項                       | 理由                   |
| ------------------------------ | ---------------------- |
| 稼働率の対象時間を示さない     | 指標比較ができないため |
| RTO/RPOを定義しない            | 復旧判断ができないため |
| 「可能な限り復旧」など曖昧表現 | 検証不能のため         |
| 単位・比較方向なしで基準を書く | 判定できないため       |
