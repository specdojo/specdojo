# 業務データ辞書 作成ルール

Business Data Dictionary (BDD) Documentation Rules

業務データ辞書（BDD）で、業務上の管理単位と項目の意味を記述するための基準を定めます。

## 1. 全体方針

- **適用範囲**: 業務分析・要求定義・設計で利用する `bdd-*.yaml` を対象とする。
- **実装重複の排除**: 実装詳細を再掲するのではなく、schema や実装（TypeScript 型）が存在するエンティティはそれらを正本として参照し、業務データ辞書にはスキーマから読み取れない業務上の意味（項目の業務的定義、enum 値が表す業務状態など）に特化して記述する。
- **完成条件**: 「本文要件」を満たし、「成果物の検証手順」の機械検証と手動照合をともに完了する。コマンドの成功だけで業務上の正しさを判定しない。
- **確定条件**: BDD の `status: ready` への昇格は PO・BA・ARC・DEV・QE の確認を経て人間が判断する。本 rulebook 自体の昇格には、さらに「rulebook 改訂候補の enum 網羅確認」の対象別証跡を必要とする。agent は `draft` のまま編集する。
- **変更時の影響範囲**: BDD の検証スキーマ、成果物カタログ、参照するスキーマ・型定義、用語集、CCD、状態・業務ルールの正本を確認する。正本の変更と業務注釈の整合を別々に確認する。

## 2. 位置づけと用語定義

- **成果物の種別**: 本ルールは `type: data` の成果物に適用する（成果物メタデータとしての `type` は `data` 固定であり、各フィールドのデータ型を表す `type` と区別する）。
- **機械検証正本との依存関係**: YAML の構造・型・正規表現の正本は `docs/specdojo/schemas/v1/bdd.schema.yaml` とする。本書は各キーの用途と業務上の判断を扱い、構文の詳細はスキーマを参照する。
- **共通規約の正本**: メタ情報は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]]、配置・命名は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従い、共通事項を BDD ごとに再掲しない。
- **主要な関係者（Role code）と確認観点**:
  - **BA（ビジネスアナリスト / 主作成者）**: 業務上の管理単位・フィールドの業務的意味・状態定義の正確性と完全性を記述する（`vp-ba-requirements-completeness`）。
  - **PO（プロダクトオーナー / 確認者）**: 業務概念のスコープ、エンティティ境界、業務用語の整合性を確認・承認する（`vp-po-purpose-alignment`, `vp-po-decision-readiness`）。
  - **ARC（アーキテクト / 確認者・利用者）**: システム設計・データ構造・正本スキーマ参照（`schema_ref`）との整合性、技術制約を確認する（`vp-arc-technical-constraints`）。
  - **DEV（開発者 / 利用者）**: 実装（モデル・型定義・テーブル設計）の基礎情報として参照し、TypeScript 型参照（`type_ref`）やスキーマとの対応を確認する（`vp-dev-implementation-readiness`）。
  - **QE（品質保証 / 確認者）**: 制約条件、許容値、検証可能性を確認する（`vp-qe-verifiability`）。
- **用語定義**:
  - **エンティティ（entities）**: 業務上の独立した管理単位・データオブジェクト。
  - **フィールド（fields）**: エンティティを構成する個々のデータ項目。
  - **論理名（`logical_name`）**: 業務利用者が直感的に理解できる日本語名称（単数形）。
  - **物理名（`physical_name`）**: DB 列名やシステム識別子に対応する英語 `lower_snake_case` 名称。
  - **キー項目（`key_fields`）**: エンティティを一意に識別する業務上のキー項目のリスト。
  - **用語集参照キー（`glossary_term_id`）**: 用語集（glossary）に登録された正式な用語 ID（`tm-...`）。
  - **関連用語（`related_terms`）**: 関連する用語集の用語 ID リスト。

## 3. ファイル命名・ID規則

### 3.1. ID規約

- `id` は `bdd.schema.yaml` の制約に合致する一意 ID を用いる。
  - プロジェクト成果物: `<project-id>:bdd-<name>`（例: `prj-0001:bdd-project-config`）
  - SpecDojo 同梱成果物: `specdojo:bdd-<name>`（例: `specdojo:bdd-sample`）
  - 単体 ID: `bdd-<name>`
- 成果物メタデータの `type` は `data` 固定とする。
- **変更管理手順**:
  - 置き換えによる大幅な改訂がある場合は `supersedes` に旧 ID を列挙する。
  - 用語集（`gl-*.yaml`）や概念クラス図（CCD）が改訂された場合は、保守担当（BA / ARC）が関連する `bdd-*.yaml` の `logical_name`, `glossary_term_id`, `related_terms` を同期更新する。
  - `schema_ref` / `type_ref` の参照元が改訂された場合、ARC / DEV が参照先の移動、フィールドの追加・改名・廃止、キー変更、enum 値の追加・改名・廃止を差分から抽出する。BA / ARC は該当する BDD の参照、`physical_name`、`key_fields`、許容値と業務注釈（論理名・説明・ラベル・用語参照）を照合する。
  - 参照元との対応が未解決の項目は、旧新の対応・影響・確認担当を変更記録に残す。業務注釈の意味を確認し、「成果物の検証手順」を完了するまで更新を受け入れない。値の機械的な置換だけで同期完了としない。
  - フィールドの非推奨・廃止時は、直接削除せず `description` に非推奨理由および代替フィールドを明記して移行期間を設ける。

### 3.2. ファイル命名規約

- **配置ディレクトリ**: プロジェクト内の業務データ辞書は、成果物カタログの `base_path`（通常は `docs/ja/product/010-business-specs/020-data-model/`）直下に配置する。
- **ファイル形式**: YAML 形式（`.yaml`）で管理する。
- **ファイル名**: `bdd-<term>.yaml`（英小文字 kebab-case）とする（例: `bdd-project-config.yaml`, `bdd-payment.yaml`）。

## 4. 推奨 Frontmatter 項目

独立 YAML のため、メタデータをルートに置き、Markdown 用の `specdojo:` ラッパーや `---` で囲まない。共通の意味はドキュメントメタ情報標準、許可キーと型の詳細は `bdd.schema.yaml` に従う。

| 項目         | 説明                                     | 必須 |
| ------------ | ---------------------------------------- | ---- |
| `id`         | データ辞書ID（`bdd-...`）                | ○    |
| `type`       | 成果物種別（`data` 固定）                | ○    |
| `title`      | 対象業務・管理単位が分かる表示名         | ○    |
| `status`     | 状態（`draft` / `ready` / `deprecated`） | ○    |
| `rulebook`   | 準拠ルール（`specdojo:bdd-rulebook`）    | ○    |
| `supersedes` | 置き換え関係（旧IDの配列）               | 任意 |

## 5. 本文要件

- ファイル先頭のコメントとして `# yaml-language-server: $schema=<相対パス>` を必須とする。パスは出力 YAML ファイルのディレクトリを基準に解決し、BDD 検証用の `docs/specdojo/schemas/v1/bdd.schema.yaml` を指すこと。`schema_ref` が指す業務エンティティのスキーマとは用途が異なる。
- 例えば `docs/ja/product/010-business-specs/020-data-model/bdd-payment.yaml` では、`# yaml-language-server: $schema=../../../../specdojo/schemas/v1/bdd.schema.yaml` とする。別の配置へこの相対パスをそのまま転記しない。
- ルートの必須キー `entities` に一つ以上のエンティティを置く。エンティティの管理境界と、注釈を付けるフィールドの選定理由が説明から判断できること。

### 5.1. entities の構成

各エンティティには以下のサブ項目を定義する。

| サブ項目           | 説明                                                                   | 必須     |
| ------------------ | ---------------------------------------------------------------------- | -------- |
| `logical_name`     | 業務上の論理名（日本語単数形）                                         | ○        |
| `physical_name`    | DB互換の物理名（`lower_snake_case`）                                   | ○        |
| `description`      | 業務データエンティティの説明・役割                                     | 任意     |
| `schema_ref`       | 正本スキーマへの参照パス（JSON Schema / YAML Schema 等）               | 任意     |
| `type_ref`         | 正本型定義への参照パス（TypeScript 等、例: `src/types/xxx.ts#Type`）   | 任意     |
| `glossary_term_id` | 用語集の用語ID（`tm-...`）                                             | 任意     |
| `related_terms`    | 関連用語IDのリスト                                                     | 任意     |
| `key_fields`       | キー項目（`physical_name` のリスト）                                   | ○        |
| `fields`           | 業務データフィールドの一覧（スタンドアロン定義では必須、参照時は任意） | 条件付き |

※ `schema_ref` と `type_ref` は同時に指定できない。どちらも指定しない場合（スタンドアロン定義）は `fields` の定義が必須となる。

### 5.2. fields の構成

各フィールドには以下のサブ項目を定義する。

| サブ項目                  | 説明                                                                                                          | 必須     |
| ------------------------- | ------------------------------------------------------------------------------------------------------------- | -------- |
| `logical_name`            | 業務上の論理名（日本語単数形）                                                                                | ○        |
| `physical_name`           | DB互換の物理名（`lower_snake_case`）                                                                          | ○        |
| `glossary_term_id`        | 用語集の用語ID（`tm-...`）                                                                                    | 任意     |
| `type`                    | データ型（`integer` / `string` / `boolean` / `date` / `datetime` / `enum` / `money`。スタンドアロン時は必須） | 条件付き |
| `description`             | フィールドの業務的説明・役割                                                                                  | 任意     |
| `unit`                    | 単位（該当時、例: 円、個、kg）                                                                                | 任意     |
| `constraints`             | フィールドの制約条件（スタンドアロン定義時）                                                                  | 任意     |
| `example`                 | フィールドの例値                                                                                              | 任意     |
| `allowed_values`          | 許容値リスト（簡易列挙。`type: enum` または状態定義時）                                                       | 条件付き |
| `allowed_values_detailed` | 許容値と業務ラベルのリスト（詳細列挙。`type: enum` または状態定義時）                                         | 条件付き |

※ `type: enum` を指定する場合、またはスキーマ・型参照エンティティで業務状態の許容値を定義する場合、`allowed_values` または `allowed_values_detailed` のいずれか一方を必須とする。
※ `schema_ref` または `type_ref` を指定したエンティティでは、`type` や `constraints` は参照先で定義されているため省略し、業務上の意味（`description` や `allowed_values_detailed`）のみを記述する。

### 5.3. constraints の構成

スタンドアロン定義で制約条件を明記する場合、以下のサブ項目を用いる。

| サブ項目   | 説明                             | 必須 |
| ---------- | -------------------------------- | ---- |
| `required` | 必須入力かどうか（true / false） | 任意 |
| `unique`   | 一意性制約（true / false）       | 任意 |
| `min`      | 最小値                           | 任意 |
| `max`      | 最大値                           | 任意 |
| `pattern`  | 正規表現パターン                 | 任意 |

## 6. 記述ガイド

### 6.1. 記述の基本方針

メタ情報・エンティティ・フィールドは、次の基準で書き分ける。共通事項は「位置づけと用語定義」で示した上位文書を正本とする。

| 対象                       | 判断の基準                                 | 良い例                                                         | 悪い例                                             |
| -------------------------- | ------------------------------------------ | -------------------------------------------------------------- | -------------------------------------------------- |
| メタ情報                   | ID と表示名から対象を識別できる            | `bdd-register-entry`、業務データ辞書（登録項目個票）           | タイトルが「データ定義」のみで対象が不明           |
| エンティティの説明         | 管理単位・範囲・他の正本との境界が分かる   | 「登録簿で個別に追跡する作業・課題。状態遷移は状態定義を参照」 | 「登録項目の情報」のみ、または状態遷移表を複写     |
| フィールドの説明           | 業務判断に使う意味と区別すべき概念が分かる | 「文書成熟度。対応の進捗を表す処理状態とは別の判断軸」         | 「状態」や「文字列」のみ                           |
| スタンドアロンの単位・制約 | 業務上の根拠を持つ条件だけを定義する       | 数量の単位を「個」とし、受注可能数の下限を業務ルールから定める | 根拠のない上限を設定する、参照元の制約を重ねて書く |

### 6.2. スキーマ・実装参照と選定基準

エンティティの定義形態は、対象データの仕様管理状況に応じて次の3通りから選定する。

#### 6.2.1. schema があるエンティティ（スキーマ参照: `schema_ref`）

- **選定基準**: 対象エンティティの JSON Schema / YAML Schema / OpenAPI 仕様が既に存在し、物理構造・制約の正本として管理されている場合に選択する。
- **記述規則**:
  - `schema_ref` に正本スキーマのファイルパス（例: `schemas/payment.schema.yaml`）またはポインタ（例: `schemas/order.schema.yaml#/$defs/Payment`）を明記する。
  - `fields` には、スキーマから読み取れない業務上の意味（項目の業務的定義、enum の値が表す業務上の状態遷移や業務ルール上の分岐など）だけを書く。
  - データ型（`type`）、必須（`required`）、最小/最大（`min` / `max`）、パターン（`pattern`）など、スキーマに定義済みの制約は絶対に繰り返さない。
- **良い例**: `schema_ref` で支払いの正本を示し、状態項目の注釈で「入金確認が済み、出荷判断に使える状態」と説明する。
- **悪い例**: 正本に定義済みの `type: string` や `constraints.required: true` を転記し、説明を「文字列」にとどめる。

#### 6.2.2. schema のないエンティティの選定基準（スタンドアロン定義 vs TypeScript 型参照）

スキーマが存在しないエンティティは、開発フェーズや正本の所在に応じて次のいずれかを選択する。

| 方式                                | 選定基準                                                                                                                                            | 記述規則                                                                                                                  |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **スタンドアロン定義**              | 実装（コードやDB）が未着手の企画・要求分析初期フェーズ、または特定の実装言語に依存しない純粋なドメイン概念モデルを独立して定義したい場合に選択する  | `fields` に `type`、`constraints`、`example` などの物理・論理仕様を直接定義する。                                         |
| **TypeScript 型参照（`type_ref`）** | すでに TypeScript で `interface` や `type` が正本として実装・運用されており、JSON Schema がない内部モデルや設定値の業務仕様を整理する場合に選択する | `type_ref` に型定義パス（例: `src/types/xxx.ts#Type`）を明記し、`fields` にはコードから読めない業務的意味のみを記述する。 |

- **良い例**: 実装前の商品数量をスタンドアロンで `type: integer`、`unit: 個` と定義する。型が正本になった内部取引は `type_ref` を示し、業務上の区分だけを注釈する。
- **悪い例**: 実在する正本を調べずにスタンドアロンで同じ型を定義する、または型のない項目へ推測で `type_ref` を付ける。

### 6.3. 命名と参照の指針

- 論理名は日本語単数形とする（例: `商品`, `支払い`）。
- 物理名（`physical_name`）は entity / field とも `lower_snake_case` を用いる（例: `product_code`, `credit_balance`, `payment_status`）。
- 参照先の lowerCamelCase 名と対応させる場合は相互変換を確認する。参照先の定義がネストされている場合は、対象位置をポインタまたは説明で特定し、同名の別項目と区別する。
- `key_fields` は `physical_name` を指定する。
- `glossary_term_id` は用語集で定義された ID（`tm-...`）と厳密に一致させる。
- `schema_ref` / `type_ref` はリポジトリルートから辿れるパスと対象定義を示す。キー一覧は参照先で確認し、`fields` は業務注釈が必要な項目に絞ってよい。
- **良い例**: `key_fields: [product_code]` が実際の識別項目に対応し、`glossary_term_id: tm-product-code` が対象用語集に存在する。
- **悪い例**: `key_fields` に論理名を指定する、表示用の導出値を保存キーとして扱う、用語 ID の存在を名前から推測する。

### 6.4. enum および業務ステータスの記述方法

- enum フィールドや状態遷移を持つ項目では、許容値を必ず明示する。
- 記述方式は用途に応じて選択する:
  - **簡易列挙（`allowed_values`）**: 値の名称自体で意味が自明な場合（例: `allowed_values: [PENDING, PAID, CANCELED]`）。
  - **詳細列挙（`allowed_values_detailed`）**: 各値が表す業務上の状態や画面表示名を明示する場合（`value` と `label` を指定）。スキーマ参照エンティティで状態の業務的意味を定義する際は、原則として詳細列挙を用いる。
- **判断基準**: 値の詳細な構文や遷移条件は正本へ譲り、辞書では値と業務上の意味の対応を確認できる粒度にする。参照元の enum 値と過不足なく対応させ、ラベルだけを値として置き換えない。
- **良い例**: `value: PAID` に `label: 入金確認済み` を対応させる。状態遷移や承認条件は、その正本を説明から参照する。
- **悪い例**: 同じフィールドに `allowed_values` と `allowed_values_detailed` を併記する、参照元にない値を追加する、状態遷移の仕様を辞書へ複写する。

### 6.5. 成果物の検証手順

作成・改訂した業務データ辞書 YAML は、機械検証と手動照合の両方で判定する。変更記録には対象ファイル・参照した正本・実行コマンドと終了結果・手動照合の結果を残す。

#### 6.5.1. 個別の構造・modeline 検証

```bash
npm run validate:schema:file -- --schema docs/specdojo/schemas/v1/bdd.schema.yaml --data <対象YAMLファイルパス>
node packages/docs-lint/bin/specdojo-docs-lint.js yaml-schema --modeline <対象YAMLファイルパス>
```

- **期待結果**: 両方が対象ファイルを `valid` と表示して終了コード 0 となること。明示的な `--schema` 指定の合格だけでは、先頭コメントの存在や相対パスの正しさを確認したことにならない。

#### 6.5.2. 全体検証と整形

```bash
npm run validate:schema
npx prettier --check <対象YAMLファイルパス>
```

- **期待結果**: 全体検証が終了コード 0、対象 YAML の整形差分がゼロであること。失敗時は報告された対象・キー・参照先を確認して修正し、該当検査を再実行する。
- **検証の限界**: `validate:schema:glossary` は用語集内の用語間参照を検査し、BDD の `glossary_term_id` / `related_terms` の参照解決は検査しない。`bdd.schema.yaml` はスタンドアロンの各フィールドの `type` 必須、列挙方式の排他性、参照元との意味・値・キーの一致を保証しない。これらは次の手動照合で判定する。

#### 6.5.3. 業務要件と参照整合の手動照合

BA / ARC は以下の合格条件を一つずつ確認し、DEV は参照元との対応、QE は証跡を確認する。該当しない行は対象形態と理由を記録する。

| 確認対象           | 合格条件                                                                                                                                                                                                             | 残す証跡                                                   |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| スタンドアロン定義 | 全フィールドに `type` があり、単位・制約・例値が業務上の意味と矛盾しない                                                                                                                                             | エンティティ・フィールドと確認結果                         |
| enum・業務状態     | 対象項目に空でない列挙を一方式だけ持つ。詳細列挙では `value` が重複せず、各ラベルで業務上の意味を識別できる                                                                                                          | フィールド・方式・値と意味の確認結果                       |
| 用語集・CCD        | エンティティとフィールドの全 `glossary_term_id`、全 `related_terms` が対象用語集の用語 ID に存在し、論理名・意味が用語集と CCD に整合する                                                                            | 対象用語集・CCD の ID と照合箇所。該当文書がない場合は理由 |
| フィールドとキー   | スタンドアロンでは `key_fields` の全要素が `fields` に存在する。参照型では参照先のファイルと対象定義が存在し、注釈する全フィールドとキーが正本の実在項目に対応する。いずれも単独・複合キーとしての識別意味が一致する | 対象定義・キーとフィールドの対応                           |
| 参照元の許容値     | 参照元の enum 値と辞書の列挙に不足・余分がなく、業務ラベルが各値の意味に一致する                                                                                                                                     | フィールド・参照元の定義位置・値ごとの対応                 |
| 二重管理の防止     | 参照型の `fields` に `type` / `constraints` を再掲せず、業務上の判断に必要な注釈だけを持つ。状態遷移・承認条件は正本へ参照する                                                                                       | 注釈の選定と重複の有無                                     |

- **良い判定例**: 個別検証と modeline 検証の成功に加え、用語 ID・キー・enum 値を正本の箇所と対応付けて合格を記録する。
- **悪い判定例**: `validate:schema` の終了コード 0 だけで、辞書の参照と業務注釈も整合していると判定する。

### 6.6. rulebook 改訂候補の enum 網羅確認

`npm run validate:schema:rulebook-enums` は `ready` の YAML / JSON rulebook だけを対象とする。`draft` の本書に対しては、コマンド全体の成功を網羅確認の証跡にしない。

1. `draft` を維持したまま、`docs/specdojo/schemas/v1/bdd.schema.yaml` 内のすべての文字列 enum を定義位置ごとに抽出する。入れ子の定義も確認し、scaffold 専用のプレースホルダは除く。
2. 各値が本書の本文に独立した値として明記されているか照合する。Frontmatter と finding コメントは数えない。値の追加・変更時には対応する用途の説明も確認する。
3. 次の列で対象別の照合記録を残す。全値の対応が埋まり、欠落がゼロであることを確定前の合格条件とする。

   | 証跡の列          | 記録する内容                                                        |
   | ----------------- | ------------------------------------------------------------------- |
   | 対象と版          | 本 rulebook と BDD 検証スキーマのパス、照合時の版または内容ハッシュ |
   | enum 定義位置・値 | スキーマ内の定義位置と各文字列値                                    |
   | 本文の記載位置    | その値を記載した見出し名と行、または未記載                          |
   | 判定・確認者      | 値ごとの合否、欠落数、確認者                                        |

4. 人間による最終承認にはこの対象別証跡を添える。昇格後は通常コマンドの出力にも本書のパスを含む `enum coverage valid` があることを確認する。

- **良い例**: `draft` の改訂候補とスキーマを直接照合し、各値の本文位置と欠落ゼロを記録する。
- **悪い例**: 対象パスが出力されていない通常コマンドの成功を根拠にする、または確認のために本書を `ready` へ書き換える。

## 7. 禁止事項

- **技術的属性の無断追加の禁止**: 業務要件として監査証跡や有効期限管理・世代管理が明示的に要求され、プロダクトオーナー（PO）またはアーキテクト（ARC）が認めた場合を除き、技術的属性（`created_at`, `updated_at`, `deleted_at` 等）を含めない。例外として含める場合は、業務上の必要性（法的要件・監査要件等）をフィールドの説明（`description`）に明記する。
- **スキーマ・実装定義の二重管理・重複記述の禁止**: `schema_ref` や `type_ref` を指定したエンティティにおいて、正本側に既に定義されているデータ型（`type`）や制約条件（`constraints`）を `fields` 内に再掲・重複記述しない。
- **言語混在・不規則な命名の禁止**: 論理名（`logical_name`）に英数字のみの識別子を記述したり、物理名（`physical_name`）に日本語や `lower_snake_case` 以外の記法（UpperCamelCase、kebab-case、空白混在等）を使用したりしない。
- **用語集・CCD との不整合の禁止**: 用語集や CCD で定義された用語・ID と異なる名称や略称を使用しない。
- **曖昧な説明・略語のみの記述の禁止**: 意味が不明瞭な説明や、業務的な文脈を欠いた略語のみの記述をしない。
