# 組織定義 作成ルール

Organization Definition Documentation Rulebook

プロジェクトの目的に必要な意思決定・実行・確認の分担方針を定義するルールです。組織定義には、体制の設計根拠、Role code の採用判断、使用可能な `owner` と見直し条件を残します。

## 1. 全体方針

- プロジェクト規模、関係者、判断の複雑さに合う最小体制を定義します。
- 組織図や役職の網羅ではなく、価値判断、実行、品質確認、公開・運用の責任境界を示します。
- 共通のロール定義は上位標準を参照し、対象プロジェクトで採用するかどうかの判断は組織定義に残します。
- 小規模では兼務を認めますが、Role code の採用と専任者の配置を分け、最終判断と実作業の責任を読み分けられるようにします。
- AI Agent は実行支援者とし、最終承認、当事者価値、公開可否、説明責任を人間に残します。
- 参加者や責務が増えた場合に、軽量体制から分担体制へ拡張する条件を示します。

## 2. 位置づけ

- Role、Member、Task owner、Executor、RACI の共通定義と整合性ルールは、[[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] を正本とします。
- 組織定義は、プロジェクト固有の採用・未採用 Role code、使用可能な `owner`、体制の設計根拠を管理し、Schedule と RACI のロール適合を確認する起点とします。
- `pm-roles.yaml` は採用ロールの機械可読な定義、メンバー定義は実行主体と兼務、RACI は成果物・プロセス別の責任分担を扱います。これらの内容を組織定義に複製しません。

## 3. ファイル命名・ID規則

- 配置は `docs/ja/projects/<project-id>/030-project-management/pm-organization.md` を推奨します。
- ID は `<project-id>:pm-organization`、ファイル名は `pm-organization.md` とします。
- 共通の命名規則は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]]、Role code などの値・構文は人と組織の定義標準と各 YAML の schema を参照します。

## 4. 推奨 Frontmatter 項目

- 共通項目の必須・任意、型・許容値は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と同標準から参照する成果物 schema に従います。
- `rulebook` には本書の ID を指定し、成果物の種別は本書の `deliverable_type` に合わせます。
- `based_on` には採用判断の根拠となる先行成果物を指定します。依存関係に含まれない文書は本文で参照し、置き換え時の `supersedes` はメタ情報標準に従います。

## 5. 本文要件

以下はすべて必須です。見出し順・表・記入欄の骨組みは Frontmatter で宣言した template を正本とします。

| 要件               | 記載する判断・根拠                                                                                                                                                                             |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 体制の設計         | 規模と目的に必要な責任領域、最終判断、実行・確認、兼務方針、人間と AI Agent の境界                                                                                                             |
| ロールの採用判断   | 上位標準の各標準ロールとプロジェクト独自ロールについて、採用・未採用の Role code、判断理由、プロジェクトでの扱い。未採用の場合は責務の代替先または対象外の理由。未採用がなければ「なし」と明記 |
| 使用可能な `owner` | Schedule で使用できる Role code の集合を明示。採用ロールの範囲内とし、RACI の列も採用判断およびロール定義と整合させる                                                                          |
| 正本への参照       | 人と組織の定義標準、ロール定義、メンバー定義、RACI などの正本と責務境界。未作成の文書は作成予定または省略理由を明記                                                                            |
| 体制の見直し       | 開始を判定できるトリガー、確認事項、更新先、判断者の Role code。変更時の追従確認と未決事項の管理先                                                                                             |

## 6. 記述ガイド

共通定義・値・構文を再掲せず、人と組織の定義標準、メタ情報標準、各 schema を参照します。以下の例は個々の判断の書き方を示します。

### 6.1. 組織モデル

- 判断基準は、目的に必要な責任領域に漏れがなく、最終判断と実行・確認を区別できることです。当事者・利用者の価値確認と内部の管理責任も分けます。
- 推奨表の列は「責任領域」「設計方針」「最終判断」「実行・確認」です。成果物・プロセス単位の割り当ては RACI を参照し、その割り当てと矛盾する責任者を書きません。
- 良い例: 「初期は人間が複数ロールを兼務し、AI Agent は草案と検証を支援する。費用・受入・公開の最終判断は人間の `PO` が行う」。
- 悪い例: 「小規模なので責任は全員で持ち、公開可否は Agent が決める」。判断者と実行支援の境界を確認できません。

### 6.2. ロール・owner方針

- 判断基準は、各ロールの採用可否と根拠が分かり、Schedule の `owner` と RACI の列を照合できることです。ロール定義への参照だけで採用判断を済ませません。
- 推奨表の列は「Role code」「採用／未採用」「判断理由・プロジェクトでの扱い」「未採用時の代替方針」です。共通の正式名称・責務は転載せず、使用可能な `owner` はこの表から特定できるように明示します。
- 良い例: 「`PO` と `BA` を採用し、使用可能な `owner` は `PO`、`BA` とする。`PM` は未採用とし、計画・進捗管理は `PO` が担う」。他の標準ロールも採用可否を記載し、実行主体の兼務割り当てはメンバー定義で管理します。
- 悪い例: 「`PM` は専任者がいないので未採用だが、Schedule の `owner` に使う」。採用と配置を混同し、未採用ロールを使用しています。

### 6.3. 正本と責任境界

- 判断基準は、情報の更新先が一意に分かり、本書に残す採用判断を外部へ委譲していないことです。
- 推奨表の列は「情報」「正本」「本書で扱うこと」です。採用判断と使用可能な `owner` は本書、採用ロールの定義はロール定義、実行主体はメンバー定義、詳細な責任割り当ては RACI に分けます。
- 良い例: 「共通定義は人と組織の定義標準を参照し、本書で採用を決める。ロール定義にはその採用結果を反映する」。参照先が存在する場合は文書 ID でリンクします。
- 悪い例: 「使用できるロールはロール定義を参照」とだけ書く、またはメンバー名簿・詳細な RACI を本文にも複製する。前者は採用根拠が欠け、後者は更新先が分散します。

### 6.4. 見直し条件

- 判断基準は、体制変更を開始する状態と、その後の更新・確認をタスク化できることです。目的・スコープ、関係者、参加者、作業滞留、公開・運用責任の変化からプロジェクトに必要な条件を選び、新しい Role code を増やす前に既存責任の再配分を検討します。
- 推奨表の列は「トリガー」「確認すること」「更新先」「判断者」です。PM（未採用なら管理責務を代替する採用ロール）が追従タスクを管理し、PO が採用変更を判断する方針を示します。
- 採用変更・置き換え・廃止時は、メタ情報標準の「文書の改訂・廃止とライフサイクル変更管理」に従い、ロール定義、メンバー定義、RACI、WBS、Schedule の影響箇所と担当 Role code を特定します。未決事項・リスク・課題・変更要求・決定は PJR または対応する管理簿へ分け、担当と転送先を記録します。
- 良い例: 「兼務による承認待ちで Schedule の期限を超えた場合、管理担当が役割再配分を検討し、PO が採否を判断する。変更対象の RACI と Schedule の更新を確認する」。
- 悪い例: 「忙しくなったら体制を強化する」。開始条件、更新先、判断者が分かりません。

## 7. 禁止事項

| 禁止事項                                                                                  | 理由                                                     |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 採用・未採用 Role code と使用可能な `owner` を省略し、ロール定義への参照だけで済ませる    | プロジェクト固有の採用判断と適合確認の根拠が失われるため |
| 共通のロール定義、メンバー名簿、詳細な RACI を再掲する                                    | 正本が分散するため                                       |
| 未採用・未定義の Role code を Schedule の `owner` や RACI 列に使う                        | 採用判断と責任語彙が不整合になるため                     |
| member nickname、人名、agent 名を Schedule の `owner` にする                              | 責任語彙と実行主体を混同するため                         |
| 兼務を理由に最終判断者を曖昧にする、または Agent に最終承認・当事者価値・公開可否を委ねる | 人間の判断責任と説明責任が不明になるため                 |
| 必要性を示さず Role code や階層を増やす                                                   | 小規模運用の負荷を増やすため                             |
| 個人情報、秘密情報、アクセス情報を記載する                                                | 公開適性に反するため                                     |
