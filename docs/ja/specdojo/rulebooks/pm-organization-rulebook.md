# 組織定義 作成ルール

Organization Definition Documentation Rulebook

プロジェクトの目的に必要な分担方針、Role code の採用判断、使用可能な `owner` と見直し条件を定義します。

## 1. 全体方針

- 規模・関係者・判断の複雑さに合う最小体制とし、価値判断、実行、品質確認、公開・運用の責任境界を示します。
- ロールの採用と専任配置を分け、兼務時も最終判断と実作業を区別します。
- 参加者や責務の増加に応じて、分担体制へ拡張する条件を示します。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。文書の整形・lint はリポジトリの検証で扱い、業務の受入確認に含めません。

## 2. 位置づけ

共通定義と整合性ルールは [[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] を正本とします。組織定義はプロジェクト固有の採用判断を残し、Schedule と RACI のロール適合を確認する起点です。採用結果の機械可読な定義は `pm-roles.yaml`、実行主体と兼務はメンバー定義、成果物・プロセス別の分担は RACI で扱います。

## 3. ファイル命名・ID規則

- 配置は `docs/ja/projects/<project-id>/030-project-management/pm-organization.md` を推奨します。
- ID は `<project-id>:pm-organization`、ファイル名は `pm-organization.md` とします。
- 共通の命名規則は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従います。

## 4. 推奨 Frontmatter 項目

- 共通項目の必須・任意、型・許容値は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と同標準から参照する成果物 schema に従います。
- `rulebook` には本書の ID を指定し、成果物の種別は本書の `deliverable_type` に合わせます。
- `based_on` には採用判断の根拠となる先行成果物を指定し、依存関係に含まれない文書は本文で参照します。

## 5. 本文要件

以下はすべて必須です。見出し順・表・記入欄の骨組みは Frontmatter で宣言した template を正本とします。

| 要件               | 記載する判断・根拠                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 体制の設計         | 規模と目的に必要な責任領域、最終判断、実行・確認、兼務方針、人間と AI Agent の境界                                                         |
| ロールの採用判断   | 各標準ロールと独自ロールの採用・未採用、理由、プロジェクトでの扱い。未採用は代替先または対象外の理由を示し、未採用がなければ「なし」と明記 |
| 使用可能な `owner` | Schedule に使える採用ロールの集合。RACI の列とロール定義との整合                                                                           |
| 正本への参照       | 関連定義との責務境界。未作成の文書は作成予定または省略理由                                                                                 |
| 体制の見直し       | 開始トリガー、確認事項、更新先、判断者の Role code、追従確認。未決事項がある場合は論点と体制への影響                                       |

## 6. 記述ガイド

以下の判断基準と例に従います。Role code の値・構文は人と組織の定義標準と各 YAML の schema を参照します。

### 6.1. 組織モデル

- 判断基準は、目的に必要な責任領域に漏れがなく、当事者・利用者の価値確認と内部の管理責任を区別できることです。
- 推奨表の列は「責任領域」「設計方針」「最終判断」「実行・確認」です。責任者は RACI と整合させます。
- 良い例: 「店主の操作確認を `BA` が受け止め、`PO` が受入を判断する。初期は兼務する」。
- 悪い例: 「小規模なので責任は全員で持つ」。判断者と実行・確認の分担が分かりません。

### 6.2. ロール・owner方針

- 判断基準は、採用可否の根拠と使用可能な `owner` を特定し、Schedule と RACI の列を照合できることです。
- 推奨表の列は「Role code」「採用／未採用」「判断理由・プロジェクトでの扱い」「未採用時の代替方針」です。共通の正式名称・責務は転載しません。
- 良い例: 「`PO` と `BA` を採用し、`owner` に使う。`PM` は未採用とし、計画・進捗管理は `PO` が担う」。他の標準ロールも採否を記載します。
- 悪い例: 「`PM` は専任者がいないので未採用だが、`owner` に使う」。採用と配置を混同しています。

### 6.3. 正本と責任境界

- 判断基準は、情報の更新先が一意で、本書の採用判断を外部へ委譲していないことです。
- 推奨表の列は「情報」「正本」「本書で扱うこと」です。「位置づけ」の責務境界に従います。
- 良い例: 「本書で採用を決め、ロール定義に採用結果を反映する」。
- 悪い例: 「使用できるロールはロール定義を参照」とだけ書く、または名簿・詳細 RACI を複製する。採用根拠が欠けるか、更新先が分散します。

### 6.4. 見直し条件

- 判断基準は、目的・スコープ、関係者、参加者、作業滞留、公開・運用責任の変化から、体制変更の開始条件を判定できることです。ロール追加の前に既存責任の再配分を検討します。
- 推奨表の列は「トリガー」「確認すること」「更新先」「判断者」です。追従先はロール定義、メンバー定義、RACI、WBS、Schedule とし、採用変更の影響箇所を確認します。
- 良い例: 「兼務による承認待ちで Schedule の期限を超えたら、役割再配分を検討する。変更対象の RACI と Schedule に担当不在や使用不可ロールが残らないことを確認する」。
- 悪い例: 「忙しくなったら体制を強化する」。開始条件、更新先、判断者が分かりません。

## 7. 禁止事項

| 禁止事項                                                                               | 理由                                                     |
| -------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 採用・未採用 Role code と使用可能な `owner` を省略し、ロール定義への参照だけで済ませる | プロジェクト固有の採用判断と適合確認の根拠が失われるため |
| 共通のロール定義、メンバー名簿、詳細な RACI を再掲する                                 | 正本が分散するため                                       |
| 未採用・未定義の Role code を Schedule の `owner` や RACI 列に使う                     | 採用判断と責任語彙が不整合になるため                     |
| 必要性を示さず Role code や階層を増やす                                                | 小規模運用の負荷を増やすため                             |
