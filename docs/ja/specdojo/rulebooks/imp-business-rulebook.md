# 影響調査（業務）作成ルール

Impact Analysis (Business) Rulebook

変更要求による業務への影響を整理し、変更要否・影響度・対応方針・未解決事項を判断するための記述基準を定めます。

## 1. 全体方針

- 影響詳細は業務単位とする。プロセス・データ・テスト仕様への波及は概要と判断だけを示し、詳細は各仕様へ委ねる。
- **共通の運用**: 役割は適用先のメンバー定義、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱う。

## 2. 位置づけ

起票済みの要求・課題を含む変更要求を受け、業務プロセス・ルール・運用手順への影響と対応を判断するための文書とする。実装設計の詳細化は扱わない。

## 3. ファイル命名・ID規則

- 文書 ID は `<project-id>:imp-business`、推奨ファイル名は `imp-business.md` とする。
- 追補文書は `<project-id>:imp-business-<term>` とし、共通規則は [[specdojo:id-and-file-naming-standard|ID・ファイル命名標準]] に従う。

## 4. 推奨 Frontmatter 項目

共通項目・必須性・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。`type` は `project`、`rulebook` は `specdojo:imp-business-rulebook` とし、`based_on` に入力の変更要求 ID を列挙する。

## 5. 本文要件

本文は次の6章をこの順で置き、すべて必須とする。

| 章  | 見出し         | 目的                                               |
| --- | -------------- | -------------------------------------------------- |
| 1   | 目的と適用範囲 | 判断対象、対象業務領域、対象期間を示す             |
| 2   | 変更要求の概要 | 変更の背景・狙い・要求の要点と成功条件を示す       |
| 3   | 影響分析サマリ | 影響度の尺度・集約規則と、影響度別の件数・優先対応 |
| 4   | 影響詳細一覧   | 影響対象業務ごとの変更要否・影響度・根拠を記録する |
| 5   | 対応方針       | 対応項目ごとの実施時期・担当・前提条件・完了条件   |
| 6   | 未解決事項     | 判断待ち・調査不足と、その決定期限・担当を示す     |

表を置く章は、次の列を必須とする。列名はこのとおりに揃え、別名（例: 「優先度」）を使わない。

| 章             | 必須の列                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------- |
| 影響分析サマリ | 影響度、件数、主な対象業務、優先対応（`要` / `否`）                                           |
| 影響詳細一覧   | 影響対象業務、変更要否（`要` / `否`）、影響度（`高` / `中` / `低`）、対応方針、判断根拠、備考 |
| 対応方針       | 影響度、対応項目、実施時期、担当、前提条件、完了条件                                          |
| 未解決事項     | 論点、不足情報、判断・対応への影響、当面の扱い、決定期限、担当、転記先の登録項目              |

## 6. 記述ガイド

各章の判断の基準と、良い例・悪い例を示す。完成例は Frontmatter の `sample` で宣言された sample を参照する。

### 6.1. 目的と適用範囲

- 対象変更要求の ID、対象業務領域、対象期間を記載し、どの利用場面で何を判断するための文書かを 2〜4 行で示す。

| 観点     | 良い例                                              | 悪い例               |
| -------- | --------------------------------------------------- | -------------------- |
| 対象業務 | 「店頭販売、在庫補充、日次締め、ツケ管理の 4 業務」 | 「店舗業務全般」     |
| 対象期間 | 「2026-05-01〜2026-07-31」                          | 「次回リリースまで」 |

### 6.2. 変更要求の概要

- 背景・狙い・要求の要点を判断に必要な範囲に絞り、成功条件は指標と閾値、または達成状態で示す。

| 観点     | 良い例                                                       | 悪い例             |
| -------- | ------------------------------------------------------------ | ------------------ |
| 成功条件 | 「平日 16:00-18:00 の 1 会計あたり平均処理時間を 90 秒以内」 | 「会計を速くする」 |

### 6.3. 影響分析サマリ

- 業務継続性・利用者影響・手戻りなど採用する評価観点ごとに、高・中・低を分ける条件を表の前に定義する。尺度の例: 高＝代替不能な業務停止、中＝代替可能だが手順変更が必要、低＝現行手順で継続可能。
- 複数観点で判定が分かれる場合の集約規則（例: 最も高い影響度を採用）を定め、同じ規則で件数を集計する。
- 優先順位は影響度で決める。優先対応を `要` とする影響度の範囲と、同じ影響度で順位を分ける場合の理由を書く。

| 観点 | 良い例                                                      | 悪い例                     |
| ---- | ----------------------------------------------------------- | -------------------------- |
| 尺度 | 「業務継続性: 高＝ピーク時の会計が代替手段なく止まる」      | 高・中・低を定義せずに使う |
| 集約 | 「観点別の最大値を影響度とする。高 2 件、中 1 件、低 1 件」 | 観点ごとの件数を合算する   |

### 6.4. 影響詳細一覧

- 判断根拠には、変更要否の理由と、評価観点ごとの事実に尺度・集約規則を当てはめた結果を書く。
- 対応方針は `実施` / `代替` / `見送り` のいずれかとし、備考に制約・前提・関連文書を書く。

| 観点     | 良い例                                                                     | 悪い例               |
| -------- | -------------------------------------------------------------------------- | -------------------- |
| 判断根拠 | 「値引き後の売上集計項目がないと現金残高と差異が出て締めを再計算する。高」 | 「影響あり。要対応」 |

### 6.5. 対応方針

- 影響度の高い順に、対応項目ごとの実施時期、担当、前提条件、完了条件を記載する。担当は適用先のメンバー定義の Role code で書く。
- 完了条件は、タスク化後の進捗確認で完了を判定できる状態（成果物・確認結果）で書く。
- 見送り・代替は、再評価条件と再評価の期限を必ず記載する。

| 観点     | 良い例                                                    | 悪い例               |
| -------- | --------------------------------------------------------- | -------------------- |
| 担当     | `BA`                                                      | 個人名、「業務担当」 |
| 完了条件 | 「新手順書を公開し、レジ担当全員が訓練を受けた」          | 「新手順を適用する」 |
| 見送り   | 「ツケ会計が月 20 件を超えたら再評価（期限 2026-07-31）」 | 「当面見送り」       |

### 6.6. 未解決事項

- 論点ごとに不足情報、判断・対応への影響、当面の扱い、決定期限、担当（Role code）を記載する。該当がなければ「なし」とする。
- 次の条件に当てはまる事項はプロジェクト登録簿へ転記し、転記先の登録項目 ID（`PJR-XXXX`）を記載する。決定の進み具合は個票で追う。

| 条件                                             | 転記先の `item_type` |
| ------------------------------------------------ | -------------------- |
| 決定期限までに判断できず、確認や調査が必要な事項 | `question`           |
| 対応が遅れると成功条件や実施時期に影響するおそれ | `risk`               |
| すでに業務運用や対応計画に支障が出ている         | `issue`              |
| 見送り・代替を決めた                             | `decision`           |

| 観点               | 良い例                                                           | 悪い例                         |
| ------------------ | ---------------------------------------------------------------- | ------------------------------ |
| 判断・対応への影響 | 「確定しないと店頭販売の値引き確認手順を決められず訓練が遅れる」 | 影響を書かず処理方針だけを書く |

## 7. 禁止事項

- 実装詳細（SQL 全文、クラス名、API リクエスト構造）を記載しない。
- 「影響あり」「要対応」のみで根拠を記載しない。
- 影響度の尺度を定義せずに高・中・低を使わない。
- 本文要件と異なる列名で同じ項目を書かない。
- 担当に個人名や連絡先を書かない。
