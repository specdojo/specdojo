# 影響調査（業務）作成ルール

Impact Analysis (Business) Rulebook

変更要求による業務への影響を整理し、変更要否・影響度・対応方針・未解決事項を判断するための記述基準を定めます。

## 1. 全体方針

- 業務担当者とプロジェクト管理者が合意できる粒度で、業務影響と判断根拠を記載する。
- 複数領域を扱う場合も影響詳細は業務単位とする。プロセス・データ・テスト仕様への波及は概要と判断を示し、詳細は各仕様へ委ねる。
- **共通の運用**: 役割は適用先のメンバー定義、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱う。

## 2. 位置づけ

起票済みの要求・課題を含む変更要求を受け、業務プロセス・ルール・運用手順への影響と対応を判断する。実装設計の詳細化は扱わない。

## 3. ファイル命名・ID規則

- 対象ドキュメント ID は `<project-id>:imp-business` とする（例: `prj-0001:imp-business`）。
- 推奨ファイル名は `imp-business.md` とする。
- 命名の共通規則は [[specdojo:id-and-file-naming-standard|ID・ファイル命名標準]] に従う。
- 関連する追補文書を分割する場合は `<project-id>:imp-business-<term>` 形式を用いる。

## 4. 推奨 Frontmatter 項目

共通項目・必須性・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。`type` は `project`、`rulebook` は `specdojo:imp-business-rulebook` とする。

## 5. 本文構成（標準テンプレ）

本文は次の6章を標準とする。

| 章  | 見出し         | 必須 | 目的                                         |
| --- | -------------- | ---- | -------------------------------------------- |
| 1   | 目的と適用範囲 | ○    | 対象と判断対象範囲を明確化する               |
| 2   | 変更要求の概要 | ○    | 変更背景と要求内容を要約する                 |
| 3   | 影響分析サマリ | ○    | 影響の全体像と優先順位を俯瞰する             |
| 4   | 影響詳細一覧   | ○    | 影響対象業務ごとの変更要否・影響度を記録する |
| 5   | 対応方針       | ○    | 採用方針、実施条件、担当と期限を整理する     |
| 6   | 未解決事項     | ○    | 意思決定待ちや調査不足を明示する             |

## 6. 記述ガイド

### 6.1. 目的と適用範囲

- 対象変更要求の識別子、対象業務領域、対象期間を明記する。
- 「何を判断する文書か」を 2〜4 行で示す。

### 6.2. 変更要求の概要

- 変更の背景・狙い・成功条件を示す。要求詳細は判断に必要な要点に絞る。

### 6.3. 影響分析サマリ

- 業務継続性、利用者影響、手戻りなどの評価観点と、高・中・低を分ける条件を先に定義する。複数観点で判定が分かれる場合の集約方法も示す。
- 尺度の例: 高＝代替不能な業務停止、中＝代替可能だが手順変更が必要、低＝現行手順で継続可能。案件に合わせて条件を具体化する。
- 定義した尺度で件数を集計し、優先対応対象を明記する。

### 6.4. 影響詳細一覧

- 影響詳細は表形式で、次の6列を必須とする。

| カラム       | 内容                                 |
| ------------ | ------------------------------------ |
| 影響対象業務 | 影響を受ける業務名または業務プロセス |
| 変更要否     | `要` / `否`                          |
| 影響度       | `高` / `中` / `低`                   |
| 対応方針     | 実施・代替・見送りなどの方針         |
| 判断根拠     | 判定理由の要点                       |
| 備考         | 制約、前提、関連ドキュメント         |

### 6.5. 対応方針

- 影響度が高い項目から順に、実施時期、担当、前提条件を記載する。
- 見送りの場合は、再評価条件と時期を必ず記載する。

### 6.6. 未解決事項

- 論点、不足情報、判断・対応への影響と当面の扱いを記載する。未解決事項がなければ「なし」とする。

## 7. 禁止事項

- 実装詳細（SQL 全文、クラス名、API リクエスト構造）を記載しない。
- 「影響あり」「要対応」のみで根拠を記載しない。
- 影響度の尺度を定義せずに高・中・低を混在させない。
