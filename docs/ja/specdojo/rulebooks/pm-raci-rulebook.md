# RACI 作成ルール

RACI Documentation Rulebook

成果物・判断の責任境界を示し、責任衝突・判断停滞を防ぐ基準です。

## 1. 全体方針

- 標準運用以上の責任境界を扱います。最小運用での省略条件は、[[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] の「ファイル別の責務」に従います。
- 全成果物を列挙せず、主要成果物、価値、変更、品質例外、公開など責任衝突があり得る対象を選びます。
- 業務・技術・品質の作業責任、最終判断、必要な相談先を確認できることを網羅条件とします。該当しない観点は省略理由を示し、確認のためだけに行や未採用 Role を増やしません。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。文書の整形・lint はリポジトリの検証で扱い、業務の受入条件に含めません。

## 2. 位置づけと用語定義

記号・用語は [[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] に従います。

採用 Role は組織定義、Role code と責務はロール定義を正本とします。RACI は責任配置、Schedule は個別タスクの `owner` を管理します。

## 3. ファイル命名・ID規則

- 配置は `docs/ja/projects/<project-id>/030-project-management/pm-raci.md` を推奨します。
- ID は `<project-id>:pm-raci`、ファイル名は `pm-raci.md` とします。
- 行は成果物 ID または判断・プロセス名で特定し、統合した行も各成果物から一意に照合できるようにします。

## 4. 推奨 Frontmatter 項目

共通項目は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と成果物 Frontmatter schema に従います。`rulebook` は本書の ID、`based_on` を使う場合は依存関係に含まれる組織定義など実際の根拠を指定します。

## 5. 本文要件

骨組みは宣言した template、完成例は sample を正本とし、次を必須とします。

- 責任の確認範囲: 対象範囲、省略範囲と理由、採用 Role の参照、兼務・Agent 支援の扱い。
- 責任配置: 成果物別と判断・プロセス別の二表。各行は一つの `A` と一つ以上の `R` を持ち、`A/R` の兼任は可、`C` / `I` は必要時に記載します。
- 担当照合: 主担当の識別、Schedule と割り当て先の正本への参照、不一致時の更新先。
- 責任の継続: 見直しのトリガーと確認対象。

## 6. 記述ガイド

### 6.1. 適用方針

- 判断基準: 初期スコープと組織定義から、業務の合意、技術の実現・変更、品質の検証・判定を扱う行を確認します。列は必要な採用 Role code とし、省く列は理由を示します。
- 雛形の `_ROLE_CODE_` は採用 Role に置換して増減する例であり、固定の必須列ではありません。
- 良い例: 「初期公開を対象とし、業務合意・実装・品質判定を扱う。次期拡張は対象外」と限定し、組織定義を参照する。
- 悪い例: 「全作業を対象」とだけ書き、未採用 Role を含む列をそのまま使う。

### 6.2. 成果物別 RACI

- 判断基準: 主要成果物、管理計画、公開対象を責任が同じ単位でまとめます。主担当や `A` が異なる成果物は分け、正本と同じ責任の生成ビューは独立行にしません。
- 相談・共有の関与がないセルは空欄または `—` とし、表内で統一します。
- 良い例: 同じ責任配置の管理文書を対象 ID でまとめ、技術担当が主導する設計文書は別行にする。
- 悪い例: カタログ全体を転記する、または担当の異なる戦略文書まで一括して管理担当の `R` に含める。

### 6.3. 判断・プロセス別 RACI

- 判断基準: 当事者価値、費用・負荷、変更、品質例外、公開など最終判断者が異なる対象を分けます。成果物行と重なる場合は各 `A` の判断範囲を明記し、業務・技術・品質の確認者・相談先を採用 Role から追跡可能にします。
- 良い例: 「作成フローの運営」の `A` は順序・進捗を判断し、内容の承認は各成果物行の `A` が行うと区別する。
- 悪い例: 「成果物作成」の `A` が各成果物の内容も承認すると読める、または品質例外と公開判断を担当の確認なしにまとめる。

### 6.4. Schedule・実行主体との対応

- 主担当は対象作業を主導する一つの `R`（`A/R` を含む）です。複数 `R` の行には、作業ごとの主担当 Role code と担当範囲を注記します。
- 主担当はタスクの action に最も近い `R` とし、一意に決まらなければ責任境界を確認してタスクを分割します。
- 担当照合は [[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] の「Schedule への担当展開」に従います。WBS の明示 `owner` を先に確認し、作成作業と、`A` / `C` を許容する承認・レビュー・外部待ちの別 Task / Milestone を区別します。
- WBS・Schedule の正本（生成する場合は戦略・設定）と割り当て先を文書 ID で参照します。不一致の原因から、RACI の責任配置かタスク定義の正本か、修正先を明記します。
- 良い例: 複数 `R` の行に「要件整理は業務担当、構成設計は技術担当」と採用 Role code で注記し、承認タスクは対応する `A` と照合する。
- 悪い例: 複数 `R` の主担当を注記せず、Schedule に現在入っている `owner` を理由に後付けで選ぶ。

### 6.5. 見直し条件

- 判断基準: スコープ、採用 Role、主要成果物の統合・分割・廃止、判断ゲート、Schedule の担当、兼務の継続可能性の変化から、影響する行・参照・担当を特定します。組織・ロール・メンバー定義、WBS・Schedule、コミュニケーション計画との整合を確認します。
- 良い例: 品質判定の滞留時に、判断待ちの責任境界と影響タスク、当面の扱いを示し、相談先とエスカレーションを見直す。
- 悪い例: 「必要時に見直す」とだけ書く、または判断履歴や課題の状態を RACI の行へ蓄積する。

## 7. 禁止事項

| 禁止事項                                              | 理由                                   |
| ----------------------------------------------------- | -------------------------------------- |
| 成果物カタログ全体や生成ビューを機械的に列挙する      | 保守量が増え、主要責任が埋もれる       |
| `A` の欠落・複数配置、`R` の欠落を許す                | 最終責任または作業責任が不明になるため |
| 複数 `R` の担当範囲と主担当を識別不能なままにする     | 個別タスクの担当を照合できないため     |
| WBS の優先順やタスク種別を無視して `owner` を変更する | 上位標準と責任配置の対応が失われるため |
| 兼務を理由に責任境界を統合する                        | 判断と作業の区別が失われるため         |
