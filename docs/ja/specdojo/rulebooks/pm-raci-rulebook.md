# RACI 作成ルール

RACI Documentation Rulebook

主要成果物と主要判断の責任境界を、最小限のマトリクスで示すためのルールです。責任衝突や判断停滞を防ぎ、作業の計画化と担当の照合に使える粒度へ絞ります。

## 1. 全体方針

- 標準運用以上で、作成・判断・相談・共有の責任境界が必要な対象に適用します。最小運用で作成を省略できる条件は、[[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] の「ファイル別の責務」に従います。
- 全成果物を列挙せず、主要成果物、価値判断、変更、品質例外、公開など責任衝突があり得る対象を選びます。
- 業務・技術・品質の各観点で、対象範囲内の作業責任、最終判断、必要な相談先を確認できることを網羅条件とします。該当しない観点は省略理由を記載し、確認のためだけに行や未採用 Role を増やしません。
- 共通の用語・担当展開規則は上位標準を正本とし、本書では RACI 固有の判断基準を定めます。実装・schema・リファレンスが定める値・構文・構造は再掲しません。

## 2. 位置づけと用語定義

`R` / `A` / `C` / `I`、Role、Member、Task owner の意味は、[[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] に従います。主担当とは、対象作業を主導する一つの `R` の Role code です。行に複数の `R` がある場合の識別方法は「Schedule・実行主体との対応」で定めます。

採用 Role は組織定義、Role code と責務はロール定義、実行主体・兼務はメンバー定義を正本とします。RACI は責任配置、Schedule は個別タスクの `owner` を管理し、人物・Agent の一覧や成果物カタログを複製しません。

## 3. ファイル命名・ID規則

- 配置は `docs/ja/projects/<project-id>/030-project-management/pm-raci.md` を推奨します。
- ID は `<project-id>:pm-raci`、ファイル名は `pm-raci.md` とします。
- 行の対象は成果物 ID または判断・プロセス名で特定します。複数成果物をまとめる場合も、各成果物から対象行を一意に照合できる名称または参照を残します。

## 4. 推奨 Frontmatter 項目

共通項目の必須性・値・構造は、[[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と成果物 Frontmatter schema に従います。`rulebook` には本書の ID を指定し、`based_on` を使う場合は、成果物の依存関係に含まれる組織定義など実際の根拠を指定します。

## 5. 本文要件

見出し順・表・記入欄の骨組みは Frontmatter で宣言した template を正本とします。以下は内容の必須要件であり、完成例は sample で扱います。

- 対象範囲、省略範囲と理由、採用 Role の参照、兼務・Agent 支援の扱いを必須とし、責任の確認範囲を判断できるようにします。記号の説明は上位標準への参照とプロジェクト固有の補足で足ります。
- 成果物の責任配置と判断・プロセスの責任配置を二表で示すことを必須とします。同じ責任境界の行は統合でき、各行には一つの `A` と一つ以上の `R` を置きます。`A/R` の兼任は可とし、`C` / `I` は相談・共有が必要な場合に記載します。
- 個別タスクの担当を照合するため、主担当の識別、Schedule と割り当て先の正本への参照、不一致時の更新先を必須とします。
- 継続して責任を保つため、見直しのトリガーと確認対象を必須とします。未決事項・リスク・変更要求の詳細や状態は管理記録へ分離します。

## 6. 記述ガイド

### 6.1. 適用方針

- 判断基準: 初期スコープと組織定義に照らし、業務上の確認・合意、技術上の実現・変更、品質の検証・判定をどの行で扱うか確認します。列は採用済み Role code から必要なものを選び、採用済みでも省く列には理由を示します。
- 雛形などの `_ROLE_CODE_` は列の例であり、採用 Role に置換して必要数に増減します。固定の Role 一式を必須列として読み替えません。
- 良い例: 「初期公開を対象とし、業務合意・実装・品質判定を扱う。次期拡張は対象外」と限定し、組織定義を参照する。
- 悪い例: 「全作業を対象」とだけ書き、未採用 Role を含む列をそのまま使う。

### 6.2. 成果物別 RACI

- 判断基準: 初期スコープの主要成果物、管理計画、公開対象を、作成・最終判断の責任が同じ単位でまとめます。主担当や `A` が異なる成果物は分け、生成ビューは正本と責任が同じなら独立行にしません。
- 相談・共有の関与がないセルは空欄または `—` とし、表内で統一します。
- 良い例: 同じ責任配置の管理文書を対象 ID でまとめ、技術担当が主導する設計文書は別行にする。
- 悪い例: カタログ全体を転記する、または担当の異なる戦略文書まで一括して管理担当の `R` に含める。

### 6.3. 判断・プロセス別 RACI

- 判断基準: 当事者価値、費用・負荷、変更、品質例外、公開など、最終判断者が異なる対象を分けます。成果物行とプロセス行が重なる場合は、各 `A` が判断する範囲を明記します。必要な業務確認者・技術相談先・品質確認者は採用 Role を介して追跡できるようにします。
- 良い例: 「作成フローの運営」の `A` は順序・進捗を判断し、内容の承認は各成果物行の `A` が行うと区別する。
- 悪い例: 「成果物作成」の `A` が成果物ごとの内容の承認まで行うように読める、または品質例外と公開判断を担当の確認なしに一行へまとめる。

### 6.4. Schedule・実行主体との対応

- `R` が一つならその Role を主担当とし、`A/R` も `R` として扱います。
- 複数 `R` の行は、行に付随する注記で対象作業ごとに一つの主担当 Role code と担当範囲を明記します。
- 主担当は Schedule タスクの action フィールドが表す作業に最も近い `R` とし、一意に決められない場合は責任境界を確認してタスクを分割します。
- Schedule の `owner` の優先順と例外は、[[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] の「Schedule への担当展開」に従います。照合時は WBS の明示 `owner` を先に確認し、作成作業の主担当と、承認・レビュー・外部待ちの別 Task / Milestone を区別します。後者では対象に応じた `A` / `C` を許容し、全タスクを `R` へ一律に合わせません。
- 対応する WBS・Schedule または生成元の戦略・設定と、実行主体を割り当てる正本を文書 ID で参照します。不一致は上位標準と対象作業から原因を判断し、RACI の責任配置かタスク定義の正本か、修正先を明記します。生成ビューは直接更新しません。
- 良い例: 複数 `R` の行に「要件整理は業務担当、構成設計は技術担当」と採用 Role code で注記し、承認タスクは対応する `A` と照合する。
- 悪い例: 複数 `R` の主担当を注記せず、Schedule に現在入っている `owner` を理由に後付けで選ぶ。

### 6.5. 見直し条件

- 判断基準: スコープ、採用 Role、主要成果物の統合・分割・廃止、判断ゲート、Schedule の担当、兼務の継続可能性の変化をトリガーとし、影響する行・参照・担当を特定します。
- 改訂・廃止は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] の「文書の改訂・廃止とライフサイクル変更管理」に従います。PM 責務を担う採用 Role は、RACI と組織・ロール・メンバー定義、WBS・Schedule、コミュニケーション計画への波及を確認し、更新タスクと担当を管理します。
- 良い例: 品質判定の滞留を契機に、相談先とエスカレーションを見直し、課題・リスク・変更要求・決定は種別に応じたプロジェクト登録簿（PJR）等の管理記録へ担当 Role と参照を付けて引き継ぐ。
- 悪い例: 「必要時に見直す」とだけ書く、または判断履歴や課題の状態を RACI の行へ蓄積する。

## 7. 禁止事項

| 禁止事項                                              | 理由                                   |
| ----------------------------------------------------- | -------------------------------------- |
| 成果物カタログ全体や生成ビューを機械的に列挙する      | 保守量が増え、主要責任が埋もれる       |
| 未採用 Role、Member、人名、Agent 名を列に使う         | 正本と責任語彙が一致しないため         |
| `A` の欠落・複数配置、`R` の欠落を許す                | 最終責任または作業責任が不明になるため |
| 複数 `R` の担当範囲と主担当を識別不能なままにする     | 個別タスクの担当を照合できないため     |
| Agent に `A` を割り当てる                             | 人間の説明責任を代替するため           |
| WBS の優先順やタスク種別を無視して `owner` を変更する | 上位標準と責任配置の対応が失われるため |
| 兼務を理由に責任境界を統合する                        | 判断と作業の区別が失われるため         |
