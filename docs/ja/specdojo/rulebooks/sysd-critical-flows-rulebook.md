# システム設計 重要フロー 作成ルール

System Design Critical Flows Documentation Rules

事故や仕様誤解につながる処理の境界・永続化点・再実行性・失敗時挙動と、実装・テスト・運用の正本への導線を定める。

## 1. 全体方針

- 一覧と詳細は同じフロー ID の集合で、例外なく最大5件とする。超過時は統合・置換・対象外を先に判断し、件数と選定理由を確認する。
- 順序・排他・重複・部分成功・外部障害・人間承認を誤る結果を、通常処理の網羅より優先する。
- 値・構文・データ構造は実装・schema・リファレンスを正本とし、一意な参照と確認条件だけを置く。
- 設計要求・確認済み動作・未確認の適合を区別し、未決の業務判断・運用条件を完成済みと扱わない。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱い、業務の受入確認に含めない。

## 2. 位置づけと用語定義

| 情報                       | 本書との責務境界                                             |
| -------------------------- | ------------------------------------------------------------ |
| システム設計索引           | 実装・設定・定義ファイルの所在と共通条件の正本               |
| 業務フロー・状態遷移仕様   | 対象者・起動条件・状態用語の正本                             |
| テスト・運用手順・判断記録 | 検証・復旧操作・採否の正本。フローとの対応と不足の影響を示す |

- **永続化点**: 中断後も状態確定の証拠となる保存地点。要求送信だけの地点と区別する。
- **再実行性**: 繰返し操作の結果と実行を許す条件。冪等を保証しない経路も示す。
- **補償**: 部分成功後の取消・戻し・代替処理による整合回復。履歴削除と区別する。

## 3. ファイル命名・ID規則

- ファイルは `sysd-critical-flows.md` を基準に、対象のシステム設計文書群へ置く。
- 文書 ID は適用先の名前空間に従う。フロー ID は `scf-001` 形式で一意とし、廃止 ID を再利用しない。
- フロー名は成功後の結果を表す。未決事項・検証条件にも文書内で一意な ID を付け、フロー ID と結ぶ。

## 4. 推奨 Frontmatter 項目

共通の形式・必須キー・型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] を正本とする。

- `type` は `architecture`、`rulebook` は本規約の ID とする。
- `part_of` は所属するシステム設計索引を示す。
- `based_on` は判断に用いた依存範囲内の根拠に限り、参照ハブの先を一律に転記しない。

## 5. 本文要件

全章必須。見出し順・表・記入欄は宣言された雛形、意味要件は以下を正本とする。

| 内容                 | 目的と満たす条件                                                                                                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 概要                 | 対象・対象外、最大5件の管理方針、設計索引への接続、公開する情報と除外する情報を示す                                                                                                         |
| 重要フロー一覧       | ID・名称・事故論点に、影響を受ける利用者／運用者、放置時の影響、期待効果、通常処理より優先する理由を対応させる                                                                              |
| フロー詳細           | フローごとに目的・トリガー・範囲・主要入出力、図、永続化点、整合性・冪等・再実行、失敗時の保持・補償・再開条件、利用者が確認できる受入条件を示す                                            |
| 観測性と運用連携     | フローごとの相関キーと追跡範囲、trace の伝搬範囲または非採用理由、監視条件・閾値の正本、実装動作、人間の一次対応とエスカレーション先を分離して示す                                          |
| 関連ドキュメント導線 | 実装・設定、テスト、運用、判断記録への一意な導線と、契約・schema・生成物・CLI・保存済み記録の互換性への変更影響を示す。未決事項は論点・依存・受入や運用への影響・当面の扱い・解消条件を示す |

図はシステム内外・サービス／プロセス・保存先の境界、主要識別子、同期・非同期と矢印の意味を示し、要求受付と業務完了を分ける。分散トレースは必須とせず、プロセス間の相関方法を示す。

テスト参照は実在するパスまたはテスト ID とし、受入条件に実行方法・対象条件・期待結果・失敗判定を対応させる。所在・網羅性・実行結果を区別し、不足は未決事項に接続する。内部結合は ITC（`itc-` 系）、外部結合は ETC（`etc-` 系）とする。

## 6. 記述ガイド

### 6.1. 概要

- 判断基準: 対象の入口・出口と公開範囲が特定できること。
- 良い例: 「販売要求から受付照合まで。公開版は設計条件だけを含み、顧客別の購入記録は除く」。
- 悪い例: 「システム全体を安全に運用する」。境界が分からない。

### 6.2. 重要フロー一覧

- 推奨列は ID、名称、事故論点、対象者、業務影響、期待効果・選定理由。優先度だけでは選定理由にならない。
- 判断基準: 重複・中断による対象者の損失で、追加候補と既存フローを比較できること。
- 良い例: 「応答欠落後の再送は二重売上になるため、閲覧より優先する」。
- 悪い例: 「重要なので High」。他候補より優先する根拠がない。

### 6.3. フロー詳細

- 判断基準: 各永続化点で中断後の残存状態・再開条件が一意に定まること。設定依存の上限はキーか一意な設計参照へ結ぶ。
- 良い例: 「受付後の応答欠落は取引 ID で照合し、未受付と確認するまで再送しない。受入では同一 ID の二回入力が売上一件になることを確認する」。
- 悪い例: 「失敗なら retry」。受付済み、保存失敗、通信失敗を区別していない。
- 図の良い例: CLI 内部・端末保存・外部受付を分け、同じ取引 ID で結ぶ。凡例で送信と応答欠落後の照合を区別する。
- 図の悪い例: 「受付 → 保存 → 完了」。保存主体・識別子・応答欠落時の経路が不明。

### 6.4. 観測性と運用連携

- 判断基準: 検知条件・実装動作・人間の対応・照会先・記録先を分けること。閾値未決を無通知でよいと扱わない。
- 良い例: 「重複確定一件で自動処理を停止。一次対応者が保持記録を確認して技術照会先へ渡す」。
- 悪い例: 「runner が担当」。機械を責任者としている。
- 相関の良い例: 「内部 trace を渡せない外部受付は、取引 ID と受付 ID で CLI・保存控えと照合する」。共通方針は一度だけ記し、フロー別のキー・範囲へ結ぶ。採否未確認なら代替手段と確認条件を示す。
- 相関の悪い例: 「`trace_id` を記録する」。境界から保存先まで追えるか不明。

### 6.5. 関連ドキュメント導線

- 判断基準: 正本・検証・未決事項へ辿れ、未作成の手順と確認済みの参照を見分けられること。
- 良い例: 「V-01 は指定テストで二重反映を fail とする。U-01 の照合手順が未整備なら、受付不明時の自動再送を保留する」。
- 悪い例: 「テスト、OPR を参照」。所在・成立条件・未整備の影響が不明。

## 7. 禁止事項

- 総数6件以上のフローを掲載すること、全 API や通常処理を網羅すること。
- 保存前に完了扱いすること、根拠のない retry・補償・自動再開を指示すること。
- 一般名称や glob だけで実装・設定・テスト・復旧手順の参照を済ませること。
- テストファイルの存在を、シナリオ網羅・実行成功の証拠として扱うこと。
- 未決事項の影響・当面の扱い・解消条件を省くこと、機械の動作主体と人間の一次対応を混同すること。
