# システム設計 重要フロー 作成ルール

System Design Critical Flows Documentation Rules

事故や仕様誤解につながる処理に絞り、境界・永続化点・再実行性・失敗時挙動を共有するための規約である。実装、テスト、運用の詳細を複製せず、それぞれの正本と未決事項への導線を定める。

## 1. 全体方針

- 一覧と詳細が扱うフローは同じ ID の集合とし、総数を最大5件とする。上限の例外は設けない。追加候補で超過する場合は既存との統合・置換・対象外への整理を先に行い、整理後も5件以内であることと選定理由を確認してから反映する。
- 通常処理の網羅より、順序、排他、重複、部分成功、外部障害、人間承認を誤った場合の結果を明確にする。
- 読み手が開始条件、成功の確定、失敗時に残るもの、再開の可否を判断できる粒度にする。
- 値・構文・データ構造は実装、schema、リファレンスを正本とする。本書には一意な参照と確認条件だけを置く。
- 設計上の要求、確認済みの動作、未確認の適合を区別する。未決の業務判断や運用条件を完成済みと扱わない。

## 2. 位置づけと用語定義

| 情報                       | 本書との責務境界                                                         |
| -------------------------- | ------------------------------------------------------------------------ |
| システム設計索引           | 実装・設定・定義ファイルの所在と共通条件の正本。本書から参照する         |
| 業務フロー・状態遷移仕様   | 対象者、起動条件、状態用語の定義先。本書で状態体系を再定義しない         |
| テスト・運用手順・判断記録 | 検証、復旧操作、採否の正本。本書には対象フローとの対応と不足の影響を示す |

- **永続化点**: 中断後も状態確定の証拠として参照する保存地点。要求を送っただけの地点と区別する。
- **再実行性**: 同じ操作を繰り返した場合の結果と、その実行を許せる条件。冪等を保証しない経路も明示する。
- **補償**: 部分成功後に取り消し、戻し、代替処理で整合を回復すること。履歴を消す操作とは区別する。

## 3. ファイル命名・ID規則

- ファイルは `sysd-critical-flows.md` を基準とし、対象範囲のシステム設計文書群へ置く。
- 文書 ID は対象リポジトリの名前空間規約に従う。フロー ID は `scf-001` 形式で一意にし、廃止した ID を別の意味へ再利用しない。
- フロー名は成功後の結果が分かる表現にする。未決事項や検証条件にも文書内で一意な ID を付け、フロー ID と対応させる。
- 統合・廃止時は ARC が図・一覧・設計索引を、DEV が実装・schema・CLI・互換性を、QE がテストを、OPS が運用導線を確認する。PM は計画・登録簿への影響を管理し、人間の PO が採否を承認する。

## 4. 推奨 Frontmatter 項目

共通の形式・必須キー・型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml`（共通定義は `common-frontmatter.schema.yaml`）を正本とする。以下の項目は `specdojo:` 名前空間配下に置く。文書名は本文先頭の H1 に記し、`specdojo.title` は使用しない。

| 項目                   | 必須性 | 本系統での判断・記入方針                                                                       |
| ---------------------- | ------ | ---------------------------------------------------------------------------------------------- |
| `id`                   | 必須   | 対象範囲で一意な文書 ID を示す                                                                 |
| `type`                 | 必須   | システム設計として `architecture` を使う                                                       |
| `status`               | 必須   | 文書の成熟度を示す。AI Agent は `ready` へ昇格させない                                         |
| `rulebook`             | 必須   | 本規約の ID を示す                                                                             |
| `owner`                | 任意   | 更新責任の Role code を示す。人間の最終承認者とは区別する                                      |
| `part_of` / `based_on` | 任意   | 所属索引と、実際に判断へ用いた依存範囲内の根拠を示す。参照ハブから辿れる文書を一律に転記しない |

## 5. 本文要件

全章を必須とする。見出し順・表・記入欄の骨組みは宣言された雛形を正本とし、ここでは意味要件を定める。

| 内容                 | 目的と満たす条件                                                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 概要                 | 対象・対象外、最大5件の管理方針、設計索引への接続、公開する情報と除外する情報、人間の最終承認責任を示す                                            |
| 重要フロー一覧       | ID・名称・事故論点に、影響を受ける利用者／運用者、放置時の影響、期待効果、通常処理より優先する理由を対応させる                                     |
| フロー詳細           | フローごとに目的・トリガー・範囲・主要入出力、図、永続化点、整合性・冪等・再実行、失敗時の保持・補償・再開条件、利用者が確認できる受入条件を示す   |
| 観測性と運用連携     | フローごとの相関キーと追跡範囲、trace の伝搬範囲または非採用理由、監視条件・閾値の正本、実装動作、人間の一次対応とエスカレーション先を分離して示す |
| 関連ドキュメント導線 | 実装・設定、テスト、運用、判断記録への一意な導線と変更影響を示す。未解決事項、依存順・担当・完了条件・判断時期、公開／承認条件もここで管理する     |

フロー詳細の図はシステム内外、サービス／プロセスと保存先の境界、主要識別子、同期・非同期の区別を示す。矢印の意味を定義し、要求受付と業務完了を同一視しない。分散トレースの導入は必須とせず、複数プロセスを関連付ける方法を示す。

テスト参照は実在するパスまたはテスト ID とし、実行方法、対象条件、期待結果、失敗判定を対応させる。既存テストの所在確認とシナリオ網羅の確認を区別し、未網羅なら担当と解消先を示す。内部結合テストは ITC（`itc-` 系）、外部結合テストは ETC（`etc-` 系）の名称を使う。

## 6. 記述ガイド

共通の状態・権限・設定は上位の索引・仕様を正本とし、本書にはフロー固有の条件だけを書く。

### 6.1. 概要

- 判断基準: 対象の入口・出口と最終承認責任が特定でき、公開範囲を判断できること。
- 良い例: 「販売要求から受付照合までを扱う。公開版は設計条件だけを含み、顧客別の購入記録は含めない。実運用の採否は人間の PO が判断する」。
- 悪い例: 「システム全体を安全に運用する」。境界と判断者が分からない。

### 6.2. 重要フロー一覧

- 推奨列は ID、名称、事故論点、対象者、業務影響、期待効果・選定理由。優先度だけで選定理由の代わりにしない。
- 判断基準: 重複実行や中断によって誰のどの作業が損なわれるかを説明でき、追加候補と既存フローの比較から対象を絞れていること。
- 良い例: 「応答欠落後の売上再送は二重計上の恐れがあるため、閲覧より先に扱う」。
- 悪い例: 「重要なので High」。他候補より優先する根拠がない。

### 6.3. フロー詳細

- 判断基準: 任意の永続化点で止めても、残存状態と再開条件が一つに定まること。設定依存の上限はキーまたは一意な設計参照へ接続する。
- 良い例: 「外部受付後に応答が失われた場合は取引 ID で照合し、未受付と確認するまで再送しない。受入では同一 ID の二回入力が一件の売上になることを確認する」。
- 悪い例: 「失敗なら retry」。受付済み、保存失敗、通信失敗を区別していない。
- 図の良い例: 内部 CLI、端末保存、外部受付を境界で分け、同じ取引 ID を送信・受付・控えに対応させる。矢印の凡例から、送信と応答欠落後の照合を見分けられる。
- 図の悪い例: 「受付 → 保存 → 完了」だけを並べる。保存主体・識別子・応答欠落時の経路が分からない。

### 6.4. 観測性と運用連携

- 判断基準: 検知条件、プログラムの動作、人間の対応、問い合わせ先、記録先が混ざっていないこと。閾値が未決なら無通知でよいとは判断しない。
- 良い例: 「重複確定を一件検知したら自動処理を停止する設計。OPS が保持記録を確認して ARC へ照会し、PM へ issue 起票を依頼する」。
- 悪い例: 「runner が担当」。機械を責任者としている。
- 相関の良い例: 「外部受付へ内部 trace を渡せないため、取引 ID と受付 ID で CLI・外部受付・保存控えを照合する」。全フロー共通の方針は一度だけ記し、フロー別のキーと範囲へ対応付ける。採否未確認なら代替手段と確認担当・解消先を示す。
- 相関の悪い例: 「`trace_id` を記録する」。境界を越えた対応や保存先まで追えるか判断できない。

### 6.5. 関連ドキュメント導線

- 判断基準: 読み手が同じ正本・検証・未決事項へ辿れ、未作成の手順と確認済みの参照を見分けられること。
- 良い例: 「検証 V-01 は指定したテストファイルを実行し、二重反映を fail とする。未作成の障害手順は U-01 で OPS が追跡し、受入前に PM が Schedule へ依存を登録する」。
- 悪い例: 「関連テスト、障害対応 OPR を参照」。所在・成立条件・未整備の影響が分からない。

## 7. 禁止事項

- 総数6件以上のフローを掲載すること、全 API や通常処理を網羅すること。
- 設定値・構文・schema の表、実装の逐語説明、図をなぞるだけの本文を二重管理すること。
- 保存前に完了扱いすること、根拠のない retry・補償・自動再開を指示すること。
- 一般名称や glob だけで参照を済ませること、未作成文書を存在するリンクとして記載すること。
- テストファイルの存在を、シナリオ網羅・実行成功・人間承認の証拠として扱うこと。
- 未決事項の影響・担当・解消条件を省くこと、機械の動作主体と人間の責任を混同すること。
