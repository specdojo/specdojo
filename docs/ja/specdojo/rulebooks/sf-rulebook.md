# システム化機能仕様 作成ルール

System Function Specification (SF) Documentation Rules

業務要件を個別のシステム機能へ割り当て、設計・実装・受入判断に必要な目的、入出力、振る舞い、制約を定義するためのルールです。値・構文・データ構造の詳細は、それぞれの schema・リファレンス・ガイドを正本として参照します。

## 1. 全体方針

- 1 成果物で 1 個別機能を扱い、利用者の業務課題、期待価値、対象範囲・対象外から責務を定めます。主要な要件は上位目的または根拠仕様に対応付けます。
- 業務プロセス仕様（BPS）や利用接点の要件を、入力・処理・出力・例外・受入条件へつなぎます。画面を持たない CLI・自動実行の機能も対象です。
- システムとして保証する結果と責務境界を記述します。操作手順、内部実装、schema のフィールド定義や設定値一覧を複製しません。
- 全体の機能一覧・共通方針は上位の `sf-index` を正本とし、個別機能には差分と対応関係を記述します。プロジェクトの進捗・課題・変更判断は Schedule・プロジェクト登録簿（PJR）・レビュー記録へ接続します。
- 読者、確認者、公開範囲と人間の PO による最終承認責任を明示します。例や証跡に認証情報・個人情報・非公開データを含めません。

## 2. 位置づけ

- 一覧ハブには [[specdojo:sf-index-rulebook|システム化機能一覧 作成ルール]] を適用します。本書は一覧行を詳細化する個別機能を扱い、一覧全体の網羅性を重複して定義しません。
- 上流の BPS・ビジネスルール（BR）・業務イベント仕様（BES）から、機能が担当する業務ステップと判断の参照先を特定します。利用接点は画面仕様（UIS）、CLI 仕様（CLIS）、外部 I/F 仕様（IFX）などへ対応付けます。
- 下流のコンポーネント設計、データ設計、テスト仕様、運用手順は本仕様の要件を入力にします。変更時には入出力・状態・連携・受入条件を起点に影響先を識別します。

## 3. ファイル命名・ID規則

- ファイル名は `sf-<term>.md`、成果物 ID は `sf-<term>` とします。`<term>` は機能の業務的責務を表す英小文字・数字・ハイフンのスラッグとし、Unit 内で一意にします（例: `sf-task-execution`）。
- `sf-index.md` と ID `sf-index` は一覧ハブ用に予約します。個別機能の ID にプロジェクト ID、authority、実装クラス名、一時的な連番を付けません。
- 配置は成果物カタログの宣言を優先し、命名・管理境界の共通原則は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従います。責務を分割・統合するときは一覧と参照元の対応も確認します。

## 4. 推奨 Frontmatter 項目

- 共通の必須・任意項目と ID・参照・状態の制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` に従います。項目の型や許可値を本書で再定義しません。
- 個別機能の `type` は `requirement`、`rulebook` は `specdojo:sf-rulebook` とします。文書名は H1 に置きます。
- `part_of` で一覧・親成果物、`based_on` で直接の根拠を表す場合は、実在する文書を参照し、カタログ上の先行依存と照合します。単に読んだ資料を根拠へ追加しません。
- 作成・改訂中は `status: draft` とします。静的検査の成功や作業タスクの完了だけで `ready` へ昇格せず、人間の PO が「完成判定と承認」の条件で判断します。

## 5. 本文要件

次の章を開始時の構成とし、各章の意味要件を満たします。内容に応じて処理や連携ごとの小節を設け、見出しには階層ごとの連番を付けます。

| 章  | 章タイトル                 | 必須     | 目的と記載要件                                                                                                               |
| --- | -------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 1   | 目的と概要                 | ○        | 業務課題・期待価値と上位目的の関係、対象・対象外、利用者・読者、確認者と合意対象、公開範囲・承認責任を定義する               |
| 2   | 業務プロセス・画面との対応 | ○        | BPS の処理ステップと機能の責務、UIS・CLIS・IFX・BES など該当する接点と受け渡しを対応付ける。接点がない場合も理由を示す       |
| 3   | 入出力と前提条件           | ○        | 入出力の論理情報、入手元・提供先、必須となる条件、契約の正本、着手条件と正常・異常終了時の事後条件を定義する                 |
| 4   | 処理要件・機能振る舞い     | ○        | 開始条件、処理の責務、確定する結果、BR・状態定義（STSD）の参照、例外時の通知・保持・回復条件を定義する                       |
| 5   | 非機能・技術制約           | ○        | 該当する性能・可用性・権限・秘匿・外部依存・互換性の制約と適用範囲を示す。値・構造・版の正本を特定し、未確定事項を分離する   |
| 6   | 操作手順・コマンド参照     | ○        | 操作・設定・障害回復の参照先と参照目的を示す。運用上の問い合わせ・エスカレーション先をロールと参照文書で特定する             |
| 7   | 検証・受入観点             | ○        | 要件と対応する正常・異常・境界条件、観測できる期待結果、検証方法・確認ロールを示し、第三者が合否を判断できるようにする       |
| 8   | 未決事項                   | 条件付き | 未決・仮定・調査事項がある場合に論点、影響、担当・判断者、期限または判断時点、次アクション、追跡先、承認を保留する条件を示す |

## 6. 記述ガイド

共通事項は上位の一覧・根拠仕様を参照し、各章にはその機能の判断に必要な情報を残します。実在する文書へのリンクは `[[id|title]]`、表のセル内は `[[id\|title]]` とし、未作成の参照先は ID をインラインコードで仮置きします。以下の良い例・悪い例は判断の差を示す断片です。

### 6.1. 目的と概要

- 「誰のどの課題を、どの成果によって改善するか」を示し、上位目的や要求の参照先を添えます。成功を確認する観点は「検証・受入観点」に対応付けます。
- 対象と対象外を対にして示し、他機能・人の判断へ引き渡す境界を明記します。利用者、設計・検証に使う読者、公開対象を区別します。
- 確認者と合意対象を明記します。例として BA は業務対応、ARC・DEV は設計入力、QE は受入可能性、PO はスコープと公開可否を確認します。ロールと担当者はプロジェクトの組織・メンバー定義を参照し、個人の連絡先を複製しません。
- 良い例: 「PM が停止理由と保存済み成果を確認して再開を判断できる。実行結果の記録までを担当し、業務上の完了承認は PO に引き渡す」。
- 悪い例: 「agent を起動する機能である」。起動という手段だけで、解決する課題と責務境界を判断できません。

### 6.2. 業務プロセス・画面との対応

- BPS の処理ステップから本機能の入出力・処理要件まで追えるようにします。画面のない機能では CLI やイベントなど実際の起動接点を示し、架空の UIS を要求しません。
- 上流仕様が未作成なら、確認済みのカタログ等の根拠と暫定範囲を示します。詳細ステップ ID を創作せず、照合担当と判断時点を「未決事項」へ残します。
- 対応表は「根拠仕様・ステップ」「本機能の責務」「対応要件・入出力」を基本列とし、連携には「接点」「トリガー・受け渡し」「責務境界」を加えます。
- 良い例: 「検証ステップで結果を受け取り、失敗を記録して統合を止める。検証コマンドの契約は対応するリファレンスを参照する」。
- 悪い例: 「BPS と対応する」。どのステップの何を担うか不明です。

### 6.3. 入出力と前提条件

- データは業務論理名で示し、BDD・CDT・BES・IFX・schema 等の正本を特定します。実装上の変数・内部構造の一覧は書きません。
- 前提条件、正常時の確定結果、失敗時に保持・変更しない情報を区別します。経路や実行方式で条件が異なる場合は、その適用範囲を付けます。
- 良い例: 「状態追跡する実行では完了状態を記録する。追跡しない単発実行では状態を変更しない」。
- 悪い例: 「成功したら常にタスクを完了にする」。追跡しない経路にも事後条件を広げています。

推奨する入出力表の列と記入断片:

| 区分 | 情報                     | 入手元 / 提供先     | 必須性・確定条件 | 正本仕様                      | 対応要件       |
| ---- | ------------------------ | ------------------- | ---------------- | ----------------------------- | -------------- |
| 入力 | 保存済みの成果と停止理由 | 実行記録 / 再開処理 | 再開時に必須     | 記録契約の文書・schema を指定 | 再開の前提条件 |

### 6.4. 処理要件・機能振る舞い

- 開始条件、処理責務、観測できる結果をひとまとまりにします。処理を識別できる見出しや要件 ID を使い、設計・テストへ割り当てられる単位に分けます。
- 業務判断は BR、状態・遷移は STSD を参照し、機能がその判断結果をどう利用するかを書きます。処理成功、作業完了、人間の受入承認を区別します。
- 異常系は「条件」「通知と保持する情報」「回復・再開条件」で整理し、外部サービスの失敗を成功扱いにしません。
- 良い例: 「検証失敗時は失敗結果を残し、未検証の成果を統合しない。修正後の再検証成功を統合条件とする」。
- 悪い例: 「問題があれば適切に復旧する」。停止位置、保持情報、復旧条件がありません。

### 6.5. 非機能・技術制約

- 制約の対象、適用経路、根拠、判定方法を示します。性能・同時実行・タイムアウト等の値は設定・契約の正本へ委ね、上書き・省略・適用外の場合も判定できるようにします。
- 連携先と利用側の責務、障害時の扱い、権限と秘匿要件を示します。公開データ契約がある場合は、論理契約・schema・版管理の正本と互換性の確認先を特定し、既存契約にない互換動作を断定しません。
- 現行動作と要求する変更を区別します。既存動作と異なる制約を採用する場合は、変更判断・下流影響を PJR 等へ接続し、未承認の値を既定値として書きません。
- 良い例: 「上限が適用される経路では有効設定値の超過時に停止理由を残す。上限省略時と対象外の経路は設定ガイドの契約で判定する」。
- 悪い例: 「すべての経路で上限は 1」。正本・対象・設定による差を示さない固定値です。

### 6.6. 操作手順・コマンド参照

- 「参照先」「種類」「参照目的」を列にして、利用開始・設定・障害回復に必要な文書を案内します。該当する操作がない場合は、その理由と運用上の確認先を示します。
- 障害時に誰が一次対応し、どの条件でどのロールへ引き渡すかを定めます。手順と連絡先の詳細は運用手順・組織定義へ委ねます。
- 良い例: 「再開判断は実行担当が運用ガイドで確認する。契約や保護設定の変更が必要なら PM・ARC へ引き渡す」。
- 悪い例: 「困ったら担当者に連絡する」。担当ロールと参照導線が特定できません。

### 6.7. 検証・受入観点

- 各主要要件に正常系、入力不成立、外部障害、境界条件を対応付けます。該当しない観点は理由を示します。成功基準は利用者が得る成果や失敗時の保護にも結び付けます。
- 表は「観点 ID」「対象要件」「対象条件」「観測する期待結果」「検証方法・証跡」「確認ロール」を基本列とします。条件と結果は yes / no で判定できる表現にします。
- 制約値は正本の有効値を使い、上書き・省略・適用外の条件を区別します。計測や実機確認が必要な場合は、その方法と担当を示し、未実施を合格扱いにしません。
- 良い例: 「検証が失敗した場合、失敗出力が証跡に残り、統合記録と完了記録が作られないことを QE が実行記録で確認する」。
- 悪い例: 「正常・異常とも正しく動作する」。観測する情報と合否境界がありません。

### 6.8. 未決事項と変更影響

- `_TODO_`・`_UNDECIDED_`・`_ASSUMPTION_` の使い分けはドキュメントメタ情報標準に従います。論点ごとに影響先、担当・判断者の Role code、期限または判断時点、次アクション、追跡先、承認への影響を記録します。
- 要件変更時は、変更する入出力・状態・接点・制約・受入条件から、上流仕様、UI・DB・コンポーネント設計、schema・生成処理・コマンド、テスト、運用手順の該当する影響先を特定します。互換性、依存する作業の着手可否、再確認が必要な条件も示します。
- 機能別の作業単位と完了条件は要件・受入観点からカタログへ、担当・順序・期限やマイルストーンは Schedule へ接続します。進捗は実行結果、課題・リスク・変更要求・決定は PJR 等へ分け、PM に追跡・計画見直しを引き渡します。機能仕様には恒久的な要件と追跡参照を残し、管理台帳を複製しません。
- 良い例: 「上流 BPS 作成時に BA が処理ステップ対応を照合し、ARC が設計境界への影響を確認する。PM が追跡先を管理し、対応の合意までは PO の承認を保留する」。
- 悪い例: 「詳細は後で決める」。判断者・影響・次の行動がありません。

### 6.9. 完成判定と承認

- 文書検査では、利用リポジトリの package・hook 設定と実行規約から適用コマンドを確認します。Markdown 整形、Markdown lint、Frontmatter・参照の検査について、対象ファイル、実行コマンド、結果を実行記録に残します。SpecDojo 同梱リポジトリでは `lint:md`・`lint:fm` 等の設定を参照します。適用検査がすべてエラーなく終了することを合格条件とし、失敗は修正後に再確認します。これは機能の受入試験の代わりにはなりません。
- 内容の完成条件は、必須章と参照が成立し、主要要件に受入条件が対応し、カタログの `done_criteria` を担当ロールが確認できることです。上流未作成や契約不一致を、形式検査の成功だけで充足扱いにしません。
- BA・ARC・DEV・QE 等の該当する確認者は合意対象と未充足条件をレビュー記録へ残します。スコープ・受入値・公開可否に影響する未決事項や未解決指摘があれば、PO は承認を保留または差し戻します。承認対象外として切り出す場合も、その境界と後続作業の追跡先を明示します。
- 人間の PO は公開対象、非公開情報の除外、確認結果と未決事項の扱いを確認し、承認・保留・差し戻しの判断を記録します。仕様の `ready`、作業タスクの完了、製品リリースの判断はそれぞれの管理規約に従います。
- 良い例: 「文書検査は合格したが、上流との照合と資源制約の合意が残るため `draft` を維持し、BA・ARC・QE の確認後に PO が承認する」。
- 悪い例: 「lint が通ったので公開・リリース可能」。内容の合意と人間の最終判断を検査で置き換えています。

## 7. 禁止事項

- 一覧ハブと個別機能の責務を混同し、機能一覧表だけで個別仕様を終えない。
- コマンド構文・引数・オプション一覧・対話手順・画面操作手順を再掲しない。
- schema の項目一覧、実装クラス・メソッド・内部構造、SQL、物理テーブル定義を転記しない。
- BPS の全手順、BR の判定ロジック、UIS のレイアウトを複製しない。
- 未作成の参照先や未合意の値・互換性方針を確定事項として扱わない。
- 適用範囲のない事後条件や「適切に」「正しく」だけの合否基準を置かない。
- 進捗台帳・レビュー履歴・個人の連絡先・秘密情報を本文で管理しない。
- agent が `ready` 昇格や公開・リリースの最終承認を代行しない。
