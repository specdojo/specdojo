# システム化機能仕様 作成ルール

System Function Specification (SF) Documentation Rules

業務要件を個別のシステム機能へ割り当て、設計・実装・受入判断に必要な目的、入出力、振る舞い、制約を定義します。値・構文・データ構造は schema・リファレンス・ガイドを正本とします。

## 1. 全体方針

- 1 成果物で 1 機能を扱い、利用者の業務課題・期待価値・対象・対象外から責務を定め、主要要件を上位目的・根拠仕様に対応付けます。
- 業務プロセス仕様（BPS）や利用接点の要件を、入力・処理・出力・例外・受入条件へつなぎます。画面を持たない CLI・自動実行の機能も対象です。
- システムとして保証する結果と責務境界を記述します。操作手順、内部実装、schema のフィールド定義や設定値一覧を複製しません。
- 全体の機能一覧・共通方針は上位の `sf-index` を正本とし、個別機能には差分と対応関係を記述します。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。文書の整形・lint はリポジトリの検証で扱います。

## 2. 位置づけ

- 一覧ハブには [[specdojo:sf-index-rulebook|システム化機能一覧 作成ルール]] を適用し、本書は一覧行を詳細化する個別機能を扱います。
- 上流の BPS・ビジネスルール（BR）・業務イベント仕様（BES）から担当する業務ステップと判断の参照先を特定し、利用接点を画面仕様（UIS）・CLI 仕様（CLIS）・外部 I/F 仕様（IFX）へ対応付けます。
- 下流のコンポーネント設計、データ設計、テスト仕様、運用手順は本仕様を入力にします。変更影響は「未決事項と変更影響」で扱います。

## 3. ファイル命名・ID規則

- ファイル名は `sf-<term>.md`、成果物 ID は `sf-<term>` とします。`<term>` は機能の業務的責務を表す英小文字・数字・ハイフンのスラッグとし、Unit 内で一意にします（例: `sf-task-execution`）。
- `sf-index.md` と ID `sf-index` は一覧ハブ用に予約します。個別機能の ID にプロジェクト ID、authority、実装クラス名、一時的な連番を付けません。
- 配置は成果物カタログ、命名・管理境界は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従います。分割・統合時は一覧と参照元の対応も確認します。

## 4. 推奨 Frontmatter 項目

- 共通項目と制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` に従います。
- 個別機能の `type` は `requirement`、`rulebook` は `specdojo:sf-rulebook` とします。
- `part_of` は一覧・親成果物、`based_on` は直接の根拠を表し、カタログの先行依存と照合します。

## 5. 本文要件

次の章を開始時の構成とし、必要に応じて処理や連携ごとの小節を設けます。

| 章  | 章タイトル                 | 必須     | 目的と記載要件                                                                                                             |
| --- | -------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------- |
| 1   | 目的と概要                 | ○        | 業務課題・期待価値と上位目的の関係、対象・対象外、利用者・読者と利用場面を定義する                                         |
| 2   | 業務プロセス・画面との対応 | ○        | BPS の処理ステップと機能の責務、UIS・CLIS・IFX・BES など該当する接点と受け渡しを対応付ける。接点がない場合も理由を示す     |
| 3   | 入出力と前提条件           | ○        | 入出力の論理情報、入手元・提供先、必須となる条件、契約の正本、着手条件と正常・異常終了時の事後条件を定義する               |
| 4   | 処理要件・機能振る舞い     | ○        | 開始条件、処理の責務、確定する結果、BR・状態定義（STSD）の参照、例外時の通知・保持・回復条件を定義する                     |
| 5   | 非機能・技術制約           | ○        | 該当する性能・可用性・権限・秘匿・外部依存・互換性の制約と適用範囲を示す。値・構造・版の正本を特定し、未確定事項を分離する |
| 6   | 操作手順・コマンド参照     | ○        | 操作・設定・障害回復の参照先と参照目的を示す。運用上の問い合わせ・エスカレーション先をロールと参照文書で特定する           |
| 7   | 検証・受入観点             | ○        | 要件と対応する正常・異常・境界条件、観測できる期待結果、検証方法・確認ロールを示し、第三者が合否を判断できるようにする     |
| 8   | 未決事項                   | 条件付き | 未決・仮定・調査事項がある場合に論点と影響を示す。当面の扱いと、確定後に直す要件・受入条件を含める                         |

## 6. 記述ガイド

各章の判断基準と良い例・悪い例を示します。

### 6.1. 目的と概要

- 「誰のどの課題を、どの成果によって改善するか」と上位目的・要求を示し、成功の確認を「検証・受入観点」に対応付けます。
- 対象と対象外を対にして示し、他機能・人の判断へ引き渡す境界を明記します。利用者と設計・検証に使う読者を区別します。
- 良い例: 「実行担当が停止理由と保存済み成果を確認して再開を判断できる。実行結果の記録までを担当し、業務上の完了判断へ引き渡す」。
- 悪い例: 「agent を起動する機能である」。起動という手段だけで、解決する課題と責務境界を判断できません。

### 6.2. 業務プロセス・画面との対応

- BPS の処理ステップと本機能の入出力・処理要件を対応付けます。画面のない機能では CLI・イベント等の起動接点を示します。
- 上流仕様が未作成なら、確認済みのカタログ等の根拠と暫定範囲を示します。詳細ステップ ID を創作せず、未照合の対応と影響を「未決事項」へ残します。
- 対応表は「根拠仕様・ステップ」「本機能の責務」「対応要件・入出力」を基本列とし、連携には「接点」「トリガー・受け渡し」「責務境界」を加えます。
- 良い例: 「検証ステップで結果を受け取り、失敗を記録して統合を止める。検証コマンドの契約は対応するリファレンスを参照する」。
- 悪い例: 「BPS と対応する」。どのステップの何を担うか不明です。

### 6.3. 入出力と前提条件

- データは業務論理名で示し、BDD・CDT・BES・IFX・schema 等の正本を特定します。実装上の変数・内部構造の一覧は書きません。
- 前提条件、正常時の確定結果、失敗時に保持・変更しない情報を区別します。経路や実行方式で条件が異なる場合は、その適用範囲を付けます。
- 良い例: 「状態追跡する実行では完了状態を記録する。追跡しない単発実行では状態を変更しない」。
- 悪い例: 「成功したら常にタスクを完了にする」。追跡しない経路にも事後条件を広げています。

推奨する入出力表の列と記入断片:

| 区分 | 情報                     | 入手元 / 提供先     | 必須性・確定条件 | 正本仕様                      | 対応要件       |
| ---- | ------------------------ | ------------------- | ---------------- | ----------------------------- | -------------- |
| 入力 | 保存済みの成果と停止理由 | 実行記録 / 再開処理 | 再開時に必須     | 記録契約の文書・schema を指定 | 再開の前提条件 |

### 6.4. 処理要件・機能振る舞い

- 開始条件・処理責務・観測結果をまとめ、設計・テストへ割り当てられる単位に見出しや要件 ID を付けます。
- 業務判断は BR、状態・遷移は STSD を参照し、機能がその判断結果をどう利用するかを書きます。処理成功、作業完了、人間の受入承認を区別します。
- 異常系は「条件」「通知と保持する情報」「回復・再開条件」で整理し、外部サービスの失敗を成功扱いにしません。
- 良い例: 「検証失敗時は失敗結果を残し、未検証の成果を統合しない。修正後の再検証成功を統合条件とする」。
- 悪い例: 「問題があれば適切に復旧する」。停止位置、保持情報、復旧条件がありません。

### 6.5. 非機能・技術制約

- 制約の対象、適用経路、根拠、判定方法を示します。性能・同時実行・タイムアウト等の値は設定・契約の正本へ委ね、上書き・省略・適用外の場合も判定できるようにします。
- 連携双方の責務、障害時の扱い、権限・秘匿要件を示します。公開データ契約は論理契約・schema・版管理の正本と互換性の確認先を特定し、未定義の互換動作を断定しません。
- 現行動作と要求する変更を区別し、既存動作と異なる制約の下流影響を示します。未確定の値を既定値として書きません。
- 良い例: 「上限が適用される経路では有効設定値の超過時に停止理由を残す。上限省略時と対象外の経路は設定ガイドの契約で判定する」。
- 悪い例: 「すべての経路で上限は 1」。正本・対象・設定による差を示さない固定値です。

### 6.6. 操作手順・コマンド参照

- 「参照先」「種類」「参照目的」の列で利用開始・設定・障害回復の文書を案内し、操作がなければ理由と確認先を示します。
- 障害時に誰が一次対応し、どの条件でどのロールへ引き渡すかを定めます。手順と連絡先の詳細は運用手順・組織定義へ委ねます。
- 良い例: 「再開判断は実行担当が運用ガイドで確認する。契約や保護設定の変更が必要なら PM・ARC へ引き渡す」。
- 悪い例: 「困ったら担当者に連絡する」。担当ロールと参照導線が特定できません。

### 6.7. 検証・受入観点

- 各主要要件に正常系・入力不成立・外部障害・境界条件を対応付け、非該当には理由を示します。成功基準は利用者の成果と失敗時の保護に結び付けます。
- 表は「観点 ID」「対象要件」「対象条件」「観測する期待結果」「検証方法・証跡」「確認ロール」を基本列とし、条件と結果は合否を判定できる表現にします。
- 制約値は正本の有効値を使い、上書き・省略・適用外の条件を区別します。計測や実機確認が必要な場合は、その方法と担当を示し、未実施を合格扱いにしません。
- 良い例: 「検証が失敗した場合、失敗出力が証跡に残り、統合記録と完了記録が作られないことを QE が実行記録で確認する」。
- 悪い例: 「正常・異常とも正しく動作する」。観測する情報と合否境界がありません。

### 6.8. 未決事項と変更影響

- 未確定の対応・契約・受入値は、論点と影響（当面の扱い、確定後に直す要件・受入条件）を示します。
- 入出力・状態・接点・制約・受入条件の変更から、上流仕様、UI・DB・コンポーネント設計、schema・生成処理・コマンド、テスト、運用手順への影響を特定します。互換性、依存作業の着手可否、再確認の条件も示します。
- 良い例: 「BPS が未作成で、ステップ対応と設計境界は暫定である。確定後に『業務プロセス・画面との対応』と入出力・処理要件を照合し、それまで未照合部分を確定した設計入力に使わない」。
- 悪い例: 「詳細は後で決める」。未確定の範囲・影響・当面の扱いがありません。

### 6.9. 完成判定と承認

- 完成条件は、必須章の具体化、上流仕様・契約との整合、主要要件と受入条件の対応、カタログの `done_criteria` の確認です。未作成の上流仕様・契約不一致に依存する条件は未充足とします。
- 「検証・受入観点」の条件で実行・照合・計測し、期待結果と証跡を比較します。受入値が未確定・確認が未実施の範囲は合格にせず、判定済みの範囲と区別します。
- 良い例: 「再開試験で保存済み成果を引き継げた。資源制約は受入値未確定のため未判定とし、結果を分ける」。
- 悪い例: 「正常系が動いたので機能全体を受け入れる」。例外・境界条件と未充足条件を確認していません。

## 7. 禁止事項

- 一覧ハブと個別機能の責務を混同し、機能一覧表だけで個別仕様を終えない。
- コマンド構文・引数・オプション一覧・対話手順・画面操作手順を再掲しない。
- schema の項目一覧、実装クラス・メソッド・内部構造、SQL、物理テーブル定義を転記しない。
- BPS の全手順、BR の判定ロジック、UIS のレイアウトを複製しない。
- 未作成の参照先や未合意の値・互換性方針を確定事項として扱わない。
- 適用範囲のない事後条件や「適切に」「正しく」だけの合否基準を置かない。
