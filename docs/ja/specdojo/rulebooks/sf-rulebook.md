# システム化機能仕様 作成ルール

System Function Specification (SF) Documentation Rules

業務プロセス仕様（BPS）や画面仕様（UIS）で定義された業務要件に基づき、システムとして提供する個別機能の目的・入出力・処理要件・関連仕様との対応を定義するためのルールです。操作の説明やコマンドの使い方・オプション・手順は含めず、コマンドリファレンスや各ガイドを参照します。

## 1. 全体方針

- システム化機能仕様（`sf-<term>`）は、業務モデル（BPS/BR/BES）やユーザーインターフェースモデル（UIS/BDS）で定義された要件を、システムが提供する独立した機能として定義します。
- 機能の目的と、業務プロセス仕様（BPS）・画面仕様（UIS）との対応関係に記述を絞ります。どの業務プロセスを支援・自動化し、どの画面やUI操作から起動・利用されるかを明確にします。
- コマンドの使い方、オプション、引数、実行手順などの操作説明は記載しません。これらはコマンドリファレンスや各運用ガイドを正本とし、本書からは参照リンクのみを置きます。
- 実装詳細（物理テーブル名、SQL、具体クラス名、メソッド名、内部データ構造）は含めません。
- 1成果物 = 1個別機能とし、ファイルの肥大化や責務の混在を防ぎます。全体構成と一覧は `sf-index`（システム化機能一覧）を正本とします。
- プロジェクトの進行管理（進捗報告、課題追跡、変更要求の審査）を本文で管理せず、プロジェクト登録簿（PJR）やレビュー結果で追跡します。
- 公開責任と機密性: 社外秘や認証情報、個人情報などの非公開データは含めず、業務要件とシステム機能境界の定義に徹します。

## 2. 位置づけと用語定義

| 用語                          | 定義                                                                                                 |
| ----------------------------- | ---------------------------------------------------------------------------------------------------- |
| システム化機能（SF）          | 業務プロセスや画面操作をシステム上で実現するための機能単位（例: タスク実行、商品登録、レジ締めなど） |
| 業務プロセス仕様（BPS）       | システム化機能が担う業務処理ステップの正本                                                           |
| 画面仕様（UIS）               | システム化機能のユーザー接点となる画面表示・操作の正本                                               |
| ビジネスルール（BR）          | システム化機能が適用する業務判断・計算ロジックの正本                                                 |
| 業務イベント仕様（BES）       | システム化機能が発行または購読する業務イベントの正本                                                 |
| コマンドリファレンス / ガイド | コマンドの構文、オプション、対話手順、運用手順の正本                                                 |

システム化機能（SF）は、業務要件（BPS/BR/BES）やUI要件（UIS/BDS）と、詳細設計・実装との間を繋ぐ機能要件です。業務上の責務をどのようにシステム機能として分割・実現するかを示し、テスト仕様（単体・結合・受入テスト）やアーキテクチャ設計（C4コンポーネント図）の入力となります。仕様変更時は、上流の業務プロセス（BPS）や画面仕様（UIS）との整合性を確認し、下流のテスト仕様やアーキテクチャ設計への影響範囲を特定します。

## 3. ファイル命名・ID規則

- ファイル名は `sf-<term>.md`、成果物 ID は拡張子を除いた `sf-<term>` とします。`<term>` は機能の役割や責務を表す英小文字・数字・ハイフンのスラッグです（例: `sf-task-execution`, `sf-product-sales`）。
- 全体構成・一覧ハブは `sf-index.md`（ID: `sf-index`）とし、個別機能とは区別します。
- プロダクト成果物の ID にはプロジェクト ID や authority を付けません。
- ドキュメント ID・機能 ID は正規表現 `^sf-[a-z0-9-]+$` に合致する一意な ID を使用します。
- 実装クラス名や一時的な連番を ID に含めず、機能の業務的責務に基づく命名を維持します。

## 4. 推奨 Frontmatter 項目

Frontmatter の共通原則はドキュメントメタ情報標準、許可される項目と型は成果物 Frontmatter スキーマに従います。

| 項目       | 説明                                                                        | 必須 |
| ---------- | --------------------------------------------------------------------------- | ---- |
| id         | 一意な機能 ID（`sf-<term>`）                                                | ○    |
| type       | `requirement` 固定                                                          | ○    |
| status     | `draft` / `ready` / `deprecated`                                            | ○    |
| rulebook   | `specdojo:sf-rulebook`                                                      | ○    |
| part_of    | 一覧または親成果物（例: `sf-index`）                                        | 任意 |
| based_on   | 根拠となる先行仕様 ID（BPS, UIS など）                                      | 任意 |
| supersedes | 置き換え対象の旧仕様 ID                                                     | 任意 |
| relations  | 要求充足や検証関係を表す型付き参照（`satisfies`, `verifies`, `implements`） | 任意 |

- SpecDojo が所有する項目は `specdojo:` 配下に置きます。
- 作成中は `status: draft` とし、PO・レビュアーによる承認後に `ready` へ昇格します。

## 5. 本文要件

各 `sf-<term>` は次の意味要件を満たさなければなりません。

| 章番号 | 章タイトル                 | 必須     | 目的と記載要件                                                                                                                     |
| ------ | -------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 1      | 目的と概要                 | ○        | 機能の目的、期待されるビジネス価値、スコープ境界（インスコープ・アウトオブスコープ）、主対象ユーザー・利用ロールを定義する         |
| 2      | 業務プロセス・画面との対応 | ○        | 対応する業務プロセス仕様（BPS）の処理ステップ、対応する画面仕様（UIS）の画面・操作、関連する外部I/F仕様（IFX）との対応表を定義する |
| 3      | 入出力と前提条件           | ○        | 機能の実行に必要な入力情報と正本、機能がもたらす出力・業務成果と正本、処理の開始前提条件・完了事後条件を定義する                   |
| 4      | 処理要件・機能振る舞い     | ○        | 機能が実行する主要な処理要件、参照するビジネスルール（BR）、状態遷移（STSD）、エラー・例外時の振る舞いを定義する                   |
| 5      | 非機能・技術制約           | ○        | 性能、可用性、セキュリティ、外部システム依存などの制約事項と設計上の前提を定義する                                                 |
| 6      | 操作手順・コマンド参照     | ○        | 操作手順やコマンドの詳細を記載せず、対応するコマンドリファレンスや各種運用ガイドへの参照先を明記する                               |
| 7      | 検証・受入観点             | ○        | 品質基準や受入条件を満たしているかを第三者が客観的に検証できる合否基準・受入シナリオを定義する                                     |
| 8      | 未決事項                   | 条件付き | 意思決定待ち（`_UNDECIDED_`）や調査中事項（`_TODO_`）がある場合に、論点・影響・決定者・期限を記載する                              |

## 6. 記述ガイド

### 6.1. 目的と概要

- 機能の目的は「何のためにその機能が存在し、どのビジネス課題を解決するか」を簡潔に記述します。
- スコープ境界表（インスコープ / アウトオブスコープ）を設け、機能の担当範囲と担当外（他機能・手作業など）を明示します。
- 主な利用者・ステークホルダー（業務担当者、システム管理者など）を定義します。

### 6.2. 業務プロセス・画面との対応

- BPS との対応表: 「業務プロセス ID」「処理ステップ ID」「機能の責務」
- UIS との対応表: 「画面 ID」「画面名」「トリガー操作」「連携内容」
- 外部I/F仕様（IFX）や業務イベント（BES）がある場合も対応関係を明記します。

推奨する業務プロセス対応表:

| 業務プロセス ID      | 処理ステップ ID | 機能の責務                                                 |
| -------------------- | --------------- | ---------------------------------------------------------- |
| `bps-sample-process` | S-01            | 業務ステップ S-01 を自動化し、入力データの検証と変換を行う |

推奨する画面仕様対応表:

| 画面 ID             | 画面名       | トリガー操作   | 連携内容                                         |
| ------------------- | ------------ | -------------- | ------------------------------------------------ |
| `uis-sample-screen` | サンプル画面 | 登録ボタン押下 | 画面入力値を受け取り、本機能の登録処理を呼び出す |

### 6.3. 入出力と前提条件

- 入力情報は業務論理名で記載し、正本仕様（BDD や CDT）を参照します。物理カラム名や内部変数は記載しません。
- 出力情報は機能の完了により確定する記録や状態変化（STSD 参照）、発行イベント（BES 参照）を記載します。
- 前提条件と事後条件を yes / no で判定できる文で記述します。

推奨する入出力表:

| 区分 | 項目名       | 入手元 / 提供先  | 必須性 / 確定条件 | 正本仕様                 |
| ---- | ------------ | ---------------- | ----------------- | ------------------------ |
| 入力 | 取引データ   | クライアント端末 | 必須              | `bdd-sample-transaction` |
| 出力 | 処理完了通知 | 外部システム     | 正常完了時        | `bes-sample-completed`   |

### 6.4. 処理要件・機能振る舞い

- 処理フロー要件は、システムとしての機能振る舞いを箇条書きで示します。
- 業務判断や計算は BR を正本とし、BR ID と利用結果のみを記述してロジックを重複させません。
- 異常系や例外発生時の振る舞い（エラー通知、ロールバック、再開条件など）を明記します。

### 6.5. 非機能・技術制約

- 応答時間、スループット、同時実行数などの性能制約を記述します。
- セキュリティ要件（認証・認可、暗号化、監査ログなど）を記述します。
- 外部連携（ネットワーク、外部API障害時のタイムアウトなど）の制約を記述します。

### 6.6. 操作手順・コマンド参照

- コマンドの使い方、CLI オプション、引数の構文、対話形式の手順、GUI の操作マニュアルなどは本書に記述せず、対応するドキュメントを参照します。
- 推奨する参照表:

| 参照先ドキュメント                             | 種類       | 参照目的・内容                                 |
| ---------------------------------------------- | ---------- | ---------------------------------------------- |
| `docs/ja/product/090-operations/opr-sample.md` | 運用手順書 | コマンドの起動オプション、実行手順、障害時対応 |

### 6.7. 検証・受入観点

- 品質基準や受入条件を満たしているかを検証できる客観的なテスト観点を記述します。
- 推奨表:

| 観点 ID | 対象条件           | 期待する振る舞い・成果                                 | 検証レベル |
| ------- | ------------------ | ------------------------------------------------------ | ---------- |
| V-01    | 正常系データ入力時 | 処理が正常終了し、期待される出力が正しく生成されること | 結合テスト |
| V-02    | 必須項目欠落時     | 入力エラーを検出し、適切なエラーメッセージを返すこと   | 単体テスト |

### 6.8. 未決事項

- 意思決定待ちの事項は `_UNDECIDED_`、調査中事項は `_TODO_`、仮置き前提は `_ASSUMPTION_` で明記します。
- 表は「論点」「影響」「区分」「決定者」「決定時期」で構成します。

### 6.9. 完成判定チェックリスト

- Frontmatter に `id`、`type: requirement`、`status`、`rulebook: specdojo:sf-rulebook` があること。
- 機能の目的と、業務プロセス仕様（BPS）・画面仕様（UIS）との対応関係が明確であること。
- コマンドの使い方、オプション、手順が書かれておらず、リファレンスやガイドへの参照に留まっていること。
- 物理テーブル、SQL、具体クラス名などの実装詳細が含まれていないこと。
- 入出力、処理要件、非機能制約、検証・受入観点が客観的に判定可能な粒度で定義されていること。
- `_TODO_` が残っておらず、未決事項がある場合は決定者と決定時期が定義されていること。

## 7. 禁止事項

- コマンドの使い方、オプション一覧、引数詳細、画面操作手順を本文に書かない（コマンドリファレンスやガイドを参照する）。
- 実装クラス名、メソッド名、SQL 全文、物理テーブル名、内部データ構造を記載しない。
- 業務プロセス（BPS）の処理ステップやビジネスルール（BR）の判定ロジックを丸ごと再掲・複製しない。
- 画面仕様（UIS）のレイアウト、ワイヤーフレーム、デザイン仕様を記載しない。
- 曖昧な表現（「適切に処理する」「問題なければ完了」等）だけで判定基準を済ませない。
- 進捗状況やレビュー履歴を本文内で管理しない（プロジェクト登録簿等で追跡する）。
- `sf-index` と `sf-<term>` の役割を混同し、一覧表だけの記述で個別機能文書を終わらせない。

## 8. サンプル

完成例は sample（`specdojo:sf-sample`）へ外出しします。以下は形式の輪郭が伝わる最小限の記述例です。

```markdown
# 商品販売機能 仕様

## 1. 目的と概要

レジ端末において、商品の読取から合計計算・販売確定を行う。

## 2. 業務プロセス・画面との対応

- BPS: `bps-sales-order-flow`（ステップ S-01, S-02, S-03）に対応
- UIS: `uis-sales-register`（販売確定操作）に対応

## 3. 入出力と前提条件

- 入力: 商品コード（`bdd-product-master`）、支払方法（`cdt-payment-method`）
- 出力: 販売記録（`bds-sales-receipt`）、売上確定イベント（`bes-sales-completed`）

## 4. 処理要件・機能振る舞い

商品読取時に単価を取得し、割引ルール（`br-discount`）を適用して合計を算出する。

## 5. 非機能・技術制約

バーコード読取時の応答速度は 200ms 以内とする。

## 6. 操作手順・コマンド参照

具体的な操作手順やコマンドオプションは `opr-pos-operation` を参照する。

## 7. 検証・受入観点

正常系・割引適用・オフライン時の動作が受入条件を満たすことを検証する。
```
