# カットオーバー計画 作成ルール

Cutover Plan (COP) Documentation Rules

対象別のカットオーバー計画 `cop-<term>` を、当日の切替を分単位で実行でき、対象固有の判定・ロールバック・連絡が明確な Runbook として記述する基準を定めます。

## 1. 全体方針

- **目的と適用範囲**: 対象が複数（ウェーブ、領域、拠点、システム群）に分かれる場合に、対象ごとに `cop-<term>` を作成する。当日タイムライン、作業手順、判定ポイント（GO/NO-GO）、ロールバック、連絡系統、周知を対象固有の粒度で定義する。
- **正本参照と責務境界**: 全体前提・共通ルール・判断体系は `cop-index`、成功条件と GO/NO-GO の最低条件は `mip-index` を正とし、`cop-<term>` は再掲せず矛盾させない。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項と当日の課題の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直しません。文書の整形・lint・スキーマ検証はリポジトリの検証で扱います。

## 2. 位置づけ

| 成果物                    | `cop-<term>` との関係                                    |
| ------------------------- | -------------------------------------------------------- |
| `cop-index`               | 全体方針・共通判断を受け、対象固有の手順だけを定義する   |
| `mip-index`               | 成功条件・カットオーバー骨格・ロールバック方針を受ける   |
| `dmd-index`, `dmd-<term>` | 抽出・投入・照合の手順と所要時間を受ける                 |
| `mtp-index`, `mtp-<term>` | リハーサルの合格を実施条件とし、時刻と判定条件を確かめる |
| `otp-index`, `otp-<term>` | 切替後の監視・運用窓口へ引き渡す                         |

## 3. ファイル命名・ID規則

- `id` は `cop-<term>`（プロジェクト固有の成果物は `<project-id>:cop-<term>`）とし、成果物カタログの宣言と一致させる（例: `cop-cutover-day`、`cop-wave1`）。
- ファイル名は `cop-<term>.md` 等、プロジェクト内で一意にする。`<term>` は用語集の論理名キー（英小文字 kebab-case）とする。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- `specdojo.type` は `operations`、`specdojo.rulebook` は `specdojo:cop-rulebook` とし、`title` は置かない。
- `specdojo.based_on` には切替判断に直接使った作成済み成果物（`cop-index`、`mip-index`、`dmd-*` 等）だけを記載する。

## 5. 本文要件

本文は次の10章をこの順序で置き、すべて必須とします。

| 章                           | 内容・受入条件                                                                                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 概要（`<term>`）             | 切替対象・目的と、対象外・責務境界を1〜3行で示す。未決の論点があれば `_UNDECIDED_` で論点と影響を書く                           |
| 当日タイムライン             | 列は「時刻（相対） / イベント / 完了条件 / 判定点」。分単位で書く                                                               |
| 作業手順チェックリスト       | 列は「手順 / 作業内容 / 実施者 / 証跡 / 備考」。順序付きで書き、実施者はメンバー定義の役割で書く                                |
| 担当者/連絡系統              | 列は「役割 / 担当 / 連絡先 / 備考」。エスカレーション先を含める。連絡先はチャネルや当番表で書く                                 |
| 実施条件（事前完了条件）     | 事前に完了している条件、他チームの作業や後続予定への依存、未達時の扱い（延期、代替手順）と判断者                                |
| 切替判定ポイント（GO/NO-GO） | 列は「判定点 / 条件 / 判断者 / 失敗時の扱い」。条件は照合対象・閾値・証跡で書き、失敗時はロールバック・延期・代替手順のいずれか |
| ロールバック手順             | 発動条件（判定点と事象）、復旧方針（旧系復帰、接続戻し、投入データ無効化など）、手順ごとの実施者・証跡・完了条件                |
| 障害時判断・エスカレーション | 重大度・SLO逸脱・復旧見込みの判断基準と、連絡経路                                                                               |
| 周知（ユーザ通知/停止告知）  | 通知対象・手段・時期、停止時間・影響範囲・問い合わせ先、配信の証跡                                                              |
| 関連ドキュメント             | `cop-index` への導線と、本書で使う `mip-index`・`mtp-index`・`dmd-*`・`otp-*`                                                   |

## 6. 記述ガイド

完成例は Frontmatter の `sample` で宣言された sample を参照してください。

### 6.1. 当日タイムラインと判定点

- **判断基準**: 判定点の時刻・条件・失敗時の扱いが、タイムラインと判定ポイントの表で一致し、条件を誰が見ても pass/fail を同じに判定できること。
- **良い例**: 「T-60m ／ 新DB投入 ／ 投入ログOK ／ GO3」と「GO3 ／ 投入件数と抽出件数が一致し、照合レポートの不一致が0件 ／ PO ／ ロールバック（投入無効化、旧系継続）」。
- **悪い例**: 「午前中 ／ 切替作業 ／ 完了したら次へ」「GO3 ／ 投入が問題ない」（分単位でなく、判定の根拠もない）。

### 6.2. 担当者と周知

- **判断基準**: 実施者・判断者が役割で一意に引け、個人の連絡先などの内部限定情報は「担当者/連絡系統」に閉じ、周知には利用者が判断に要る情報だけがあること。
- **良い例**: 「前日18時に店頭掲示で告知。停止は翌日9時〜10時、その間は現金のみ。問い合わせは店頭窓口」。
- **悪い例**: 担当者の個人電話番号や内部の作業手順を告知文に書く。

## 7. 禁止事項

| 禁止事項                                                   | 理由                                   |
| ---------------------------------------------------------- | -------------------------------------- |
| 当日タイムラインを分単位で書かない                         | 実行性が担保できないため               |
| ロールバックの発動条件や手順を省略する                     | 失敗時の判断ができないため             |
| 判定条件を「問題ない」など照合対象のない言葉で書く         | 判定者によって GO/NO-GO が変わるため   |
| 周知を書かない、または内部限定情報を周知に混ぜる           | 利用者の混乱と情報漏えいにつながるため |
| `cop-index` の共通方針を複製する、`mip-index` と矛盾させる | SSOTが崩れ、当日参照が割れるため       |

## 8. サンプル（最小・整合版）

形式の輪郭を示す最小例です。生成するドキュメントでは `## 1.` から開始します。

```yaml
---
specdojo:
  id: cop-cutover-day
  type: operations
  status: draft
  rulebook: specdojo:cop-rulebook
  based_on:
    - cop-index
    - mip-index
---
```

```markdown
## 2. 当日タイムライン

| 時刻（相対） | イベント                     | 完了条件            | 判定点 |
| ------------ | ---------------------------- | ------------------- | ------ |
| T-120m       | 旧系受付停止・ジョブ停止確認 | 受付停止/停止ログOK | GO1    |
| T-60m        | 新DB投入                     | 投入ログOK          | GO3    |
| T-15m        | 接続先切替・監視正常確認     | スモークOK/監視OK   | GO4    |

## 6. 切替判定ポイント（GO/NO-GO）

| 判定点 | 条件                                       | 判断者 | 失敗時の扱い                      |
| ------ | ------------------------------------------ | ------ | --------------------------------- |
| GO1    | 未処理の受付が0件、停止ログに失敗ジョブ0件 | Ops    | 延期：旧系で継続                  |
| GO3    | 投入件数＝抽出件数、照合の不一致0件        | PO     | ロールバック：投入無効化→旧系継続 |
| GO4    | スモーク全件成功、重大アラート0件          | PO     | ロールバック：接続戻し→延期判断   |
```
