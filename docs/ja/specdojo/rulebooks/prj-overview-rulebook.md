# プロジェクト概要 作成ルール

Project Overview Documentation Rulebook

本ドキュメントは、**プロジェクト概要（Project Overview）** を統一形式で記述するためのルールです。
関係者が「何を、なぜ、どの考え方で進めるのか」を短時間で合意できる粒度に整えます。

## 1. 全体方針

- 本ルールの対象は **プロジェクト概要**（背景、必要性、基本方針、狙いの共有）です。
- 目的は「プロジェクトの立ち上げ判断と後続成果物作成の前提を揃える」ことです。
- 背景、必要性、基本的な考え方、実現したいこと、期待効果、前提条件を概要レベルで記述します。
- 詳細なスコープ、認可・承認、成功判定・受入条件、設計、実装、テスト設計は本書の対象外とします。委譲先は「プロジェクト憲章・成功基準との分担」に従います。
- 曖昧表現（例:「適切に」「可能な限り」「十分に」）は避け、合意できる表現にします。
- 数値目標を置く場合は、測定方法、判定時期、初期仮説か確定目標かを明示します。

## 2. 位置づけ

本書（`prj-overview`）は、ステークホルダー登録簿（`prj-stakeholder-register`）とプロジェクト憲章（`prj-charter`）の起点となる構想・概要文書です。本書を扱う立ち上げトラックの位置づけは [[specdojo:track-design-guide|トラック設計ガイド]]、立ち上げで扱う成果物の一覧は [[specdojo:deliverables-reference|成果物リファレンス]] を参照してください。

## 3. ファイル命名・ID規則

### 3.1. 配置（推奨）

- `docs/ja/projects/<project-id>/` のように、プロジェクト単位のフォルダ配下に配置します。
- 配下の章ディレクトリは `020-project-definition/` を用います（構成は [[specdojo:docs-structure-guide]] に従う）。
- 章ディレクトリには、サブディレクトリを切って、プロジェクトの背景や目的に関わる関連資料（図表、参考資料など）を置いてもよい。

### 3.2. ドキュメントID（推奨）

メタ情報（Frontmatter）を付ける場合、ID は一意である必要があります。

- 推奨: `<project-id>:prj-overview`
  - 例: `prj-0001:prj-overview`
- YAML Frontmatter では、必要に応じてコロンを含む ID をクォートします。

### 3.3. ファイル名（推奨）

ファイル名は`prj-overview.md` を推奨。日本語の場合は、`プロジェクト概要.md` 。

## 4. 推奨 Frontmatter 項目

### 4.1. 設定内容

Frontmatter は共通スキーマに従い、項目はすべて `specdojo:` 名前空間配下に置きます（あわせてドキュメントのメタ情報の記述ルールも参照）。

- 参照スキーマ: [deliverable-frontmatter.schema.yaml](/docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml)
- メタ情報標準: [[specdojo:document-metadata-standard]]

| 項目                  | 説明                               | 必須 |
| --------------------- | ---------------------------------- | ---- |
| `specdojo.id`         | `<project-id>:prj-overview`        | ○    |
| `specdojo.type`       | `project` 固定                     | ○    |
| `specdojo.status`     | `draft` / `ready` / `deprecated`   | ○    |
| `specdojo.rulebook`   | `specdojo:prj-overview-rulebook`   | ○    |
| `specdojo.based_on`   | 既存の経営方針・制度資料・過去 DEC | 任意 |
| `specdojo.supersedes` | 置き換え関係                       | 任意 |

作成・更新後は `npm run lint:fm` と `npm run lint:md` を実行し、エラーが 0 件であることを確認します。`lint:fm` は `type` が本 rulebook の `deliverable_type`（`project`）と一致するかも照合します。

### 4.2. 推奨ルール

- `based_on` は、既存の経営方針・制度資料・過去 DEC など、根拠として直接参照するものがある場合のみ列挙します。
- 仮説・期待効果・前提条件の見直しは同一文書の改訂とします。中心仮説や実現したいことを根本から作り直す場合だけ新文書を作成して `supersedes` に旧文書 ID を指定し、旧文書を `deprecated` にします。手順と担当 Role code は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] の「文書の改訂・廃止とライフサイクル変更管理」に従い、置き換えの判断は PO、波及更新の起票は PM が担います。
- 本書を改訂したら、参照している `prj-stakeholder-register`・`prj-charter`・`prj-scope`・`prj-success-criteria-and-acceptance-criteria` の要約・参照が改訂後の内容と矛盾しないかを確かめます。
- 本 rulebook の本文要件や期待効果の時間軸を改訂した場合は、`prj-overview-template`・`prj-overview-sample`・`prj-overview-recipe` と、本 rulebook に従う既存プロジェクトの `prj-overview` を追従させます。

## 5. 本文要件

見出し順・表・記入欄の骨組みは template を正本とします。各章の目的と必須・任意は次のとおりです。

| 章             | 必須 | 目的                                                   |
| -------------- | ---- | ------------------------------------------------------ |
| 導入文         | ○    | 対象プロジェクトまたはフレームワークを一文で定義する   |
| 背景           | ○    | 現状、文脈、構造的な問題を示す                         |
| 必要性         | ○    | なぜ今取り組むか、放置した場合の課題を示す             |
| 基本的な考え方 | ○    | 進め方の原則と判断軸を示す                             |
| 実現したいこと | ○    | 整備・提供したい成果、対象利用者、適用領域を示す       |
| 期待効果       | ○    | 時間軸ごとの効果、指標、初期仮説、測定方法を示す       |
| 初期公開指標   | 任意 | 提供開始前に代表利用者の試行等で確認する価値・成立条件 |
| 短期指標       | 任意 | 提供後の利用、定着、再利用、直接的な利用者課題の改善   |
| 中長期指標     | 任意 | 事業・活動の成果、継続性、参加機会、透明性等の波及効果 |
| 前提条件       | ○    | 依存条件、制約、変えないこと、適用上の前提を示す       |

## 6. 記述ガイド

### 6.1. 共通

- 見出し配下は「箇条書き＋必要最小限の表」を基本とします。
- “事実/観察” と “推測/仮説” を混ぜないでください（混ざる場合はラベルで区別）。
- 読み手が「次に何を決めればよいか」が分かるように、未確定は未確定として明示します。
- 本書は概要文書であるため、後続文書で詳細化する内容は要約に留め、必要に応じて文書名を示します。

### 6.2. 導入文

- H1 直下に、対象プロジェクトまたはフレームワークを一文で説明します。
- 「何を通じて」「誰を支援し」「何を実現するか」が分かる粒度にします。
- 導入文では詳細な効果、指標、実装方式を列挙しません。

### 6.3. 背景

- 何が起きているか（現状）と、何が困りごとか（問題）を分けて書きます。
- 推奨: 事実は具体例（頻度・件数・影響）を添える。

### 6.4. 必要性

- 期限、制度/契約、競合、障害、属人化など「今やる理由」を明確にします。
- 背景で述べた可能性や課題に対し、なぜ既存のやり方では足りないかを説明します。
- 問題を列挙する場合は、後続の「基本的な考え方」や「実現したいこと」につながる粒度にします。
- プロジェクトの成立仮説を一文で表せる場合は、「誰のどの課題に、どの働きかけを行うと、どの変化が生じるか」を中心仮説として置きます。仮説を事実として断定せず、必要に応じて 2〜4 件の価値仮説へ分解します。

### 6.5. 基本的な考え方

- プロジェクトの設計思想や判断軸を 2〜5 件程度に絞って記述します。
- 原則には、名称、短い説明、プロジェクト上の意味を含めます。
- 原則は中心仮説や価値仮説を成立させるための判断軸とし、学習や検証結果に応じて見直せる表現にします。
- 特定の開発手法、ツール、製品に過度に寄せず、後続文書で再利用できる表現にします。

### 6.6. 実現したいこと

- 整備・提供したい成果を箇条書きで記述します。
- 対象利用者、適用領域、公開・再利用方針を必要に応じて含めます。

### 6.7. 期待効果

- 初期公開前に試行できる価値、公開・運用開始後の短期的な利用成果、中長期の事業・社会的な成果を分けます。
- 置いた時間軸ごとに、観点・指標・目標・測定方法の計測定義を置きます。計測定義を省略できるのは、その時間軸を置かない場合だけです。省略する場合は、期待効果の本文に省略理由または別の判定時期を書きます。
- 目標値を決められない場合は、空欄や「未確定」で済ませず、何を記録して、いつ判定するかを書きます。
- 中心仮説を置いた場合は、価値仮説ごとに初期検証または後続時期の確認方法があるかを確かめます。
- 初期公開指標は、成果物や機能の完成率だけでなく、対象利用者が主要な利用場面を完遂できるかを確認します。
- 短期指標は、実際の利用、定着、再利用、利用者が認識する直接的な改善を扱います。
- 中長期指標は、プロジェクトが最終的に寄与したい事業・業務・社会的成果を扱います。成果を当該プロジェクトだけに帰属できない場合は「寄与」として記述します。
- 数値目標は、初期公開時点、運用開始後、ベースライン確定後のどこで判定するかを明示します。
- QCD は必要に応じて補助指標にできますが、成果物の完成、工数、納期だけで利用者価値を代替しません。
- 表の目標の列名は、試行で判定する初期公開指標を「目標」、ベースライン確定前の仮説として置く短期指標・中長期指標を「初期目標」とします。

### 6.8. 前提条件

- 変えない前提（例: 運用体制は当面変えない）と、依存前提（例: 他部門の協力が必要）を区別します。
- 人間の判断責任、AI Agent の役割、適用範囲、公開方針、利用時の取捨選択方針などを明示します。

### 6.9. プロジェクト憲章・成功基準との分担

本節を後続文書との責務境界の正本とします。

- 本書では、背景・必要性・基本的な考え方・実現したいこと・期待効果を中心に記述します。
- 承認者、承認日、権限委譲、承認経路、証跡リンクなどの認可情報は `prj-charter` 側で管理します。
- 受入条件、完了定義、GO / Not GO 判断など確定管理する成功判定の値は `prj-success-criteria-and-acceptance-criteria` 側で管理し、本書では期待効果と初期仮説に留めます。
- 詳細な対象範囲や対象外は `prj-scope` 側で管理します。
- 同一情報を両文書に重複記載する場合は、本文を複製せず、要約 + 参照リンクで整合を保ちます。

## 7. 禁止事項

| 項目                                                     | 理由                                                                       |
| -------------------------------------------------------- | -------------------------------------------------------------------------- |
| 設計詳細（DB設計、API設計等）                            | プロダクト仕様/設計ドキュメントへ委譲                                      |
| “だいたい/適切に” 等の曖昧表現                           | 合意・検証ができない                                                       |
| 根拠のない数値目標                                       | 誤った期待形成・炎上の原因になる                                           |
| 成果物数・機能数・作業完了率だけを業務価値として扱う     | 利用者や事業に生じる変化を判定できないため                                 |
| 短期の利用件数だけで中長期の事業・社会的成果を置き換える | プロジェクトの最終的な目的を矮小化するため                                 |
| 認可・受入条件・GO / Not GO 判定の詳細管理               | 責務重複を防ぐため（「プロジェクト憲章・成功基準との分担」の委譲先で扱う） |
| 個人名・連絡先等の公開不適切情報                         | 公開リポジトリでの利用を想定するため                                       |
