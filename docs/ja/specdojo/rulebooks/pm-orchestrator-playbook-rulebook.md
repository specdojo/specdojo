# オーケストレーター運用メモ 作成ルール

Orchestrator Playbook Documentation Rulebook

対話型オーケストレーターがプロジェクトごとに積み上げる長く効く知見（agent の使い分け、実行の運び方、止まったときの再開、close の前の確かめ方、保護された設定、リリースの手順など）を、どのプロジェクトでも同じ章立てで残すための基準です。

## 1. 全体方針

- 運用メモは、オーケストレーターが作業を始める前に読み、そのプロジェクトで実行を組む・止まった実行を再開する・項目を close するときに判断の拠り所にする文書です。
- 配布するオーケストレーターの指示の本文に書かれた一般的な進め方は再掲せず、そのプロジェクトに固有の事情と、実際の運用で分かった手順・落とし穴だけを書きます。
- 各記述は、実際に起きた事例か利用者の決定に基づかせます。手順・落とし穴には、根拠になった項目や事例（日付）と、回避策を直す側の項目を添えます。
- 状況が変わった記述は書き直し、道具が直って要らなくなった回避策は消します。履歴を残す文書にしません（履歴は登録簿と commit が持ちます）。
- **共通の運用**: `status`・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。文書の整形・lint はリポジトリの検証で扱います。

## 2. 位置づけと用語定義

### 2.1. 知見の置き場所の分け方

運用メモは、オーケストレーターが引き継ぐ情報の置き場所のうち、プロジェクトに固有で長く効く知見を受け持ちます。次の表は、情報の種類ごとの置き場所と、運用メモに入れない理由を示します。

| 情報の種類                                                     | 置き場所                                       | 運用メモとの関係                                                                             |
| -------------------------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------- |
| どのプロジェクトでも同じ振る舞い・進め方                       | 配布するオーケストレーターの指示の本文（本体） | 運用メモに書かない。運用メモで見つけた一般的な知見は本体へ移す                               |
| そのプロジェクトだけで長く効く手順・癖・決まり                 | 運用メモ                                       | 本書の対象                                                                                   |
| 道具の欠けを手作業で補っている回避策                           | 運用メモ（回避策）と、コマンドを直す登録簿項目 | 回避策に直す側の項目を添え、直ったら運用メモから消す                                         |
| セッションや LLM を切り替えるときの引き継ぎ                    | 登録簿の `handoff`                             | 有効な承認の範囲と注意点のうち長く効くもの・決まりになるものを、受け取った後に運用メモへ移す |
| 利用者の返事を待っている判断                                   | 登録簿の `question`                            | 運用メモにも `handoff` にも抱えない。決まった回答のうち長く効くものだけを運用メモへ移す      |
| 特定の項目だけに効く制約・前提                                 | 登録簿の個票の入力・完了条件                   | 運用メモに書かない                                                                           |
| 登録簿や実行の状態（進行中の run、review・waiting の項目など） | 登録簿と実行状態（コマンドで組み立てる）       | 書き写さない                                                                                 |

### 2.2. 用語定義

| 用語   | 定義                                                                                                                       |
| ------ | -------------------------------------------------------------------------------------------------------------------------- |
| 本体   | 配布するオーケストレーターの指示の本文。どのプロジェクトでも同じ振る舞いを定める                                           |
| 回避策 | 道具（コマンド・runner）の欠けや不具合を、手作業・手順・スクリプトで補うやり方。直す側の登録簿項目が閉じるまでの一時の知見 |
| 列     | 複数の登録簿項目やタスクを順に、または並べて流すための実行の予約・並び                                                     |

## 3. ファイル命名・ID規則

- 配置は `docs/ja/projects/<project-id>/030-project-management/pm-orchestrator-playbook.md` を推奨します。1 プロジェクトに 1 つとし、分割しません。
- ID は `<project-id>:pm-orchestrator-playbook` とします。
- 登録簿項目は項目 ID（例: `PJR-XXXX`）で、文書は project 修飾 doc id の wikilink で参照します。agent は実行主体の nickname、責務は Role code で書きます。

## 4. 推奨 Frontmatter 項目

共通項目はドキュメントメタ情報標準に従います。

- `type`: `project`
- `rulebook`: `specdojo:pm-orchestrator-playbook-rulebook`
- `based_on`: 任意。運用メモの決まりの直接の根拠になる決定（decision の個票）があれば挙げる

## 5. 本文要件

章の順序と記入欄は template を正本とします。次の表は、各章が受け持つ判断と必須・任意を示します。任意の章は、そのプロジェクトに書くべき事実がある場合だけ置き、空の章を残しません。

| 章                           | 必須   | 内容・受入条件                                                                                             |
| ---------------------------- | ------ | ---------------------------------------------------------------------------------------------------------- |
| 目的と適用範囲               | ○      | 対象プロジェクト、本体との分担、記述の根拠にした運用の期間と書き直す条件が分かること                       |
| agent の使い分けと癖         | ○      | 難しさごとの既定の振り分けの正本、使わない agent と理由、agent ごとの癖と対応が分かること                  |
| 実行の運び方                 | ○      | 列の組み方、並べる本数の上限と根拠、直列にする作業、列の予約の仕方が分かること                             |
| 止まったときの再開           | ○      | 止まり方ごとに、原因の見分け方と再開の仕方を選べること                                                     |
| close の前の確かめ方         | ○      | 統合の後に自分で確かめること（executor の報告に頼らない検証を含む）と、それが要る項目の条件が分かること    |
| 保護された設定の扱い         | ○      | agent が書けない設定の範囲と、変更が要るときの経路（変更案の置き場所と反映の仕方）が分かること             |
| 登録簿項目の完了条件の書き方 | 任意   | 並べて流すときの衝突を避けるための、完了条件の書き方の決まり                                               |
| 落とし穴                     | 任意   | 上の章のどれにも属さない、起きた事例と避け方                                                               |
| リリースの手順               | 条件付 | 成果物を公開・配布するプロジェクトでは必須。範囲の決め方、集め方、漏れの確かめ方、公開と公開後の確認の手順 |
| プロジェクトに固有の章       | 任意   | 別の project との分担、定期の検査など。上の章の後ろに置く                                                  |

## 6. 記述ガイド

### 6.1. 知見の育て方

知見は「本体 → 運用メモ → コマンド」の順に置き場所を考え、オーケストレーターの記憶やセッションの中だけに置きません。

1. どのプロジェクトでも同じ振る舞いなら、本体へ入れる変更案を起票する。本体は保護された設定のため、運用メモには入れずに起票の項目で追う。
2. そのプロジェクトだけで長く効くなら、運用メモの該当の章へ書く。根拠の事例（項目 ID・日付）を添える。
3. 道具の欠けを手作業で補っているなら、運用メモへ回避策として書き、同時にコマンドを直す登録簿項目を起票して、回避策の行に項目 ID を添える（例: 「回避策: `PJR-XXXX`」）。
4. 同じ種類の手作業の回避策が運用メモに 2 回以上出たら、まだ起票していなくても、コマンドにする項目を起票する。
5. 直す側の項目が close されたら、運用メモから回避策を消すか、コマンドの使い方へ書き換える。

### 6.2. handoff と question からの移し方

- `handoff` を受け取ったら、有効な承認の範囲と注意点を読み、長く効くもの（以後のセッションでも守る決まり、繰り返し起きる落とし穴）だけを運用メモの該当の章へ移してから `handoff` を close する。その夜・そのセッションだけの承認は移さない。
- `question` の回答のうち、以後の運用を決めるものは、運用メモに決まりとして書き、根拠に `question` または decision の項目 ID を添える。回答待ちの間は、運用メモに仮の決まりを書かない。
- 進行中の run や待っている項目を運用メモに書かない。登録簿と実行状態から組み立てる。

### 6.3. 章ごとの書き方

- 目的と適用範囲: 本体に従う範囲と、本書が加える範囲を 1〜3 項目で分けます。根拠にした運用の期間か版を書きます。
- agent の使い分けと癖: 振り分けの数値や既定は設定ファイルを正本として参照し、表に再掲しません。癖は次の表で書きます。

| agent | 癖・制約 | 対応 |
| ----- | -------- | ---- |

- 実行の運び方: 列の起動の例はコードブロックで 1 つだけ示し、並べる本数の上限には根拠（同時実行の設定、メモリなど）を添えます。
- 止まったときの再開: 次の表で、止まり方から再開の仕方を引けるようにします。再開のオプションの意味はコマンドリファレンスを参照し、再掲しません。

| 止まり方 | 原因の例 | 再開の仕方 |
| -------- | -------- | ---------- |

- close の前の確かめ方: 「何を変えた項目なら」「何を流して」「何を見れば close してよいか」を書きます。executor が `requires_human` と報告した検証を自分で流す手順を含めます。
- 保護された設定の扱い: 保護の範囲は設定の正本を参照して列挙し、変更案は executor が個票の対応結果と報告の `handoff` に書き、オーケストレーターが利用者の承認を得て反映する、という経路を書きます。
- リリースの手順: 番号付きの手順にし、各手順に確かめる条件（何が通れば次へ進むか）を書きます。
- 未確定の決まりは `_UNDECIDED_` を付け、決まるまでの扱いを添えます。

## 7. 禁止事項

| 禁止事項                                                             | 理由                                                                 |
| -------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 本体に書かれた一般的な進め方を再掲する                               | 正本が分散し、本体の更新に追従できなくなるため                       |
| 進行中の run・項目の状態や、利用者の返事を待っている判断を書き写す   | 登録簿・実行状態と食い違い、`handoff`・`question` の役割と重なるため |
| 直す側の項目を添えずに回避策を書く                                   | 回避策が恒久の手順として残り、道具が直らないため                     |
| 直った回避策や、状況が変わった記述を残す                             | 古い手順で作業を誤るため                                             |
| 設定ファイルの値（同時実行数、振り分けの表など）の正本を本書に置く   | 設定と食い違うため。値は参照し、判断に要る範囲だけ書く               |
| 文書を作る・確かめる・承認する役割の割り当てや、承認の進み具合を書く | 承認と留保は登録簿の個票で追うため                                   |
| 認証情報・秘密鍵・token の値を書く                                   | 運用メモは agent と共有され、リポジトリに残るため                    |
