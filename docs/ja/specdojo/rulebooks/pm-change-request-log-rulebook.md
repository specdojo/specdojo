# 変更要求ログ 作成ルール

Change Request Log Documentation Rules

本ドキュメントは、`変更要求ログ` を一貫した粒度で作成するためのルールを定義する。

## 1. 全体方針

- 変更要求ごとに、申請から影響評価、審査・決定、実施追跡までを判定できる形で残す。
- 変更要求として起票するのは、合意済みのスコープ・スケジュール・品質基準・成果物の変更を求めるものに限る。合意した基準を変えずに直せる不具合や障害は `pm-issue-log` 側で扱う。
- 審査は `pm-plan` のスコープと優先順位に照らして行い、その対応を決定の根拠に書く。
- 申請者・評価者・決定者・実施担当は個人名ではなく Role code（`PO`・`PM` など）で書く。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱う。

## 2. 位置づけ

- プロジェクト登録簿を使うプロジェクトでは、変更要求 1 件を `item_type: change-request` の個票に書き、`controls/generated/pm-change-request-log.md` は `register build` が個票から生成する。生成物の Frontmatter は `rulebook: specdojo:pjr-rulebook` とし、直接編集しない（[[specdojo:pjr-rulebook|プロジェクト登録簿 作成ルール]] に従う）。
- 本書の記述ガイドは、個票の各節と単独の変更要求ログの各章に適用する。個票の「変更要求」節には `変更要求一覧` の基準を、そのほかの節には同じ名前の章の基準を当てる。
- 登録簿を使わない場合は、単独のログを `030-project-management/pm-change-request-log.md` に置き、Frontmatter を `rulebook: specdojo:pm-change-request-log-rulebook` とする。
- 変更から生じたリスク・課題は `pm-risk-register`・`pm-issue-log` 側の項目として起票し、関連ドキュメントで結ぶ。

## 3. ファイル命名・ID規則

- `id` は `<project-id>:pm-change-request-log`、ファイル名は `pm-change-request-log.md` とする。
- 変更 ID は登録簿では `PJR-XXXX`、単独のログでは `CR-NNN` とし、再利用しない。
- 申請者が取り下げた要求は同じ ID のまま状態を `取下げ` にする。決定後に内容を変えて審査し直す場合は新しい ID で起票し、元の ID を関連ドキュメントに書く。

## 4. 推奨 Frontmatter 項目

- 許可キーと型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] を正本とし、`type` は `project` とする。

## 5. 本文構成（標準テンプレ）

| 番号 | 見出し           | 必須 |
| ---- | ---------------- | ---- |
| 1    | 概要             | ○    |
| 2    | 変更要求一覧     | ○    |
| 3    | 影響評価         | ○    |
| 4    | 審査・決定       | ○    |
| 5    | 実施追跡         | ○    |
| 6    | 関連ドキュメント | ○    |

## 6. 記述ガイド

### 6.1. 概要

- 管理対象、運用期間、記録単位を 1〜3 行で示す。

### 6.2. 変更要求一覧

- 変更 ID、要求内容、変更理由（応える業務課題・期待価値）、申請者、申請日、状態を書く。
- 要求内容は「何を・どう変えるか」が 1 文で分かる形にする。良い例は「日次売上CSVの列順を会計ソフトの取込順に変える」、悪い例は「CSVを改善する」。
- 状態は、登録簿では `item_status` の値を言い換えずに使う。単独のログでは `審査中`・`保留`・`実施中`・`完了`・`却下`・`取下げ` のいずれかとし、`完了` は `done`、`却下`・`取下げ` は `rejected` に当たる。

### 6.3. 影響評価

- スコープ・工数・品質・納期の観点ごとに、影響の有無と量（人日・日数など）と根拠を書き、評価者を Role code で書く。
- 採否の判断材料として、見送ったときの影響と期待効果を書く。

### 6.4. 審査・決定

- 審査結果は `承認`・`条件付き承認`・`却下`・`保留` のいずれかとし、決定者・決定日・実施条件と、`pm-plan` のスコープ・優先順位との対応を書く。
- 決定者は人間の役割（`PO`・`PM` など）とし、agent を決定者にしない。agent が影響評価を下書きした場合も、決定は人間の役割が行う。
- `保留` には、再審査の期限または条件と、追加で必要な判断材料を書く。良い例は「4/15 の在庫棚卸結果を見て再審査する」、悪い例は「保留」だけで止めること。

### 6.5. 実施追跡

- 実施担当、期限、進捗、完了条件を書く。進捗は `変更要求一覧` の状態と同じ値を使う。
- 完了条件は確認の手段と合格の基準で書く。良い例は「受入テストで新しい列順を会計ソフトへ取り込めること」、悪い例は「受入テスト合格」。

### 6.6. 関連ドキュメント

- 根拠（`pm-plan` など）、影響先、変更から起票したリスク・課題、再審査で起票し直した元の変更 ID を文書 ID で示す。関連がない場合は `（本書のみ）` と書く。

## 7. 禁止事項

| 禁止事項                                     | 理由                         |
| -------------------------------------------- | ---------------------------- |
| 変更IDを未採番で記録する                     | 追跡不能になるため           |
| 影響評価なしで承認可否を記載する             | 判断根拠が欠落するため       |
| 決定者・決定日を省略する                     | 監査性が失われるため         |
| agent を決定者として記録する                 | 決定の責任が人に残らないため |
| 実装詳細やコード差分を本文に貼り付ける       | 管理対象が肥大化するため     |
| 個人名などの個人情報・認証情報を書き写す     | 公開範囲を超えて広がるため   |
| 生成された `pm-change-request-log.md` を直す | 再生成で修正が失われるため   |
