# 変更要求ログ 作成ルール

Change Request Log Documentation Rules

本ドキュメントは、`変更要求ログ` を一貫した粒度で作成するためのルールを定義する。

## 1. 全体方針

- 変更要求ごとに、申請から影響評価、審査・決定、実施追跡までを判定できる形で残す。
- 審査は `pm-plan` のスコープと優先順位に照らして行い、その対応を決定の根拠に書く。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱う。

## 2. 位置づけ

- プロジェクト登録簿を使うプロジェクトでは、変更要求 1 件を `item_type: change-request` の個票に書き、`controls/generated/pm-change-request-log.md` は `register build` が個票から生成する。生成物の Frontmatter は `rulebook: specdojo:pjr-rulebook` とし、直接編集しない（[[specdojo:pjr-rulebook|プロジェクト登録簿 作成ルール]] に従う）。
- 本書の章ごとの判断基準は、個票の同名の節と、登録簿を使わない単独の変更要求ログの両方に適用する。
- 変更から生じたリスク・課題は `pm-risk-register`・`pm-issue-log` 側の項目として起票し、関連ドキュメントで結ぶ。

## 3. ファイル命名・ID規則

- `id` は `<project-id>:pm-change-request-log`、ファイル名は `pm-change-request-log.md` とする。
- 変更 ID は登録簿では `PJR-XXXX`、単独のログでは `CR-NNN` とし、再利用しない。

## 4. 推奨 Frontmatter 項目

- 許可キーと型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] を正本とし、`type` は `project` とする。

## 5. 本文構成（標準テンプレ）

| 番号 | 見出し           | 必須 |
| ---- | ---------------- | ---- |
| 1    | 概要             | ○    |
| 2    | 変更要求一覧     | ○    |
| 3    | 影響評価         | ○    |
| 4    | 審査・決定       | ○    |
| 5    | 実施追跡         | ○    |
| 6    | 関連ドキュメント | ○    |

## 6. 記述ガイド

### 6.1. 概要

- 管理対象、運用期間、記録単位を 1〜3 行で示す。

### 6.2. 変更要求一覧

- 変更 ID、要求内容、申請者、申請日、状態に加え、変更理由（応える業務課題・期待価値）を書く。
- 要求内容は「何を・どう変えるか」が 1 文で分かる形にする（例: 「日次売上CSVの列順を会計ソフトの取込順に変える」）。

### 6.3. 影響評価

- スコープ・工数・品質・納期の観点ごとに、影響の有無と量（人日・日数など）と根拠を書く。
- 採否の判断材料として、見送ったときの影響と期待効果を書く。

### 6.4. 審査・決定

- 審査結果は「承認・条件付き承認・却下・保留」のいずれかとし、決定者・決定日・実施条件と、`pm-plan` のスコープ・優先順位との対応を書く。

### 6.5. 実施追跡

- 実施担当、期限、進捗、完了条件を書く。完了条件は確認の手段と合格の基準で書く（例: 「受入テストで新しい列順を会計ソフトへ取り込めること」）。

### 6.6. 関連ドキュメント

- 根拠（`pm-plan` など）、影響先、変更から起票したリスク・課題を文書 ID で示す。関連がない場合は `（本書のみ）` と書く。

## 7. 禁止事項

| 禁止事項                                     | 理由                       |
| -------------------------------------------- | -------------------------- |
| 変更IDを未採番で記録する                     | 追跡不能になるため         |
| 影響評価なしで承認可否を記載する             | 判断根拠が欠落するため     |
| 決定者・決定日を省略する                     | 監査性が失われるため       |
| 実装詳細やコード差分を本文に貼り付ける       | 管理対象が肥大化するため   |
| 個人情報・認証情報を要求内容や根拠に書き写す | 公開範囲を超えて広がるため |
| 生成された `pm-change-request-log.md` を直す | 再生成で修正が失われるため |
