# システム受入条件仕様（SAC）作成ルール

System Acceptance Criteria (SAC) Documentation Rules

システム全体としての合格基準（機能・非機能・障害・移行など）を、検証可能な Markdown 形式で記述し、受入判断の根拠を明確にするための基準を定めます。

## 1. 全体方針

- SAC は **システム全体としての出口条件（合格基準）** です。
  - 例: 「性能試験で全ての NFR を満たし、重大障害 0 件であること」
- 受入条件は **観測・計測できる事実**として書き、手順書にはせず入力/操作と期待結果を要約します。
- 1ファイル = 1 受入対象（合格基準のまとまり）を基本とします。
  - 例: `性能`, `障害復旧`, `セキュリティ（権限/監査）`, `移行（初期データ）`
- 決定済みの NFR・BAC 等を合格基準へ変換します。新しい閾値や要求を SAC で確定しません。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直しません。文書の整形・lint はリポジトリの検証で扱い、受入条件に含めません。

## 2. 位置づけ

SAC は、システムを受け入れてよいかを判断する場面と、下位のテスト設計で合格基準を分解する場面で使う文書です。

- 根拠: 非機能要件（[[specdojo:nfr-index-rulebook|非機能要件]] の各カテゴリ）とプロジェクトの受入条件。閾値と要求の定義は根拠側を正本とします。
- BAC との境界: 業務担当者が業務を進められるかは [[specdojo:bac-rulebook|業務受入条件]] で扱います。SAC はシステムとしての機能・非機能・障害・移行の合格基準を扱い、業務シナリオの成立条件を再掲しません。
- 下位: [[specdojo:stc-rulebook|総合テスト仕様]] と [[specdojo:atc-rulebook|受入テスト仕様]] が受入条件 ID を分解して参照するため、ID は安定させます。テストの詳細手順と実行結果は SAC に含めません。

## 3. ファイル命名・ID規則

- ファイル名: `sac-<term>.md` とし、`<term>` は受入対象を表す英小文字の kebab-case とします（例: `sac-performance.md`、`sac-reliability.md`）。
- 文書 ID: SAC はプロダクト文書のため、[[specdojo:id-and-file-naming-standard|ドキュメントIDおよびファイル命名標準]] に従い名前空間なしの `sac-<term>` とし、成果物カタログの `local_id` と一致させます。
- 文書タイトル（H1）: `# システム受入条件: <受入対象>` とします（例: `# システム受入条件: 性能`）。
- 受入条件には文書内で一意な ID（例: `SAC-PERF-01`）を付け、改訂で番号を振り直しません。
- 受入対象が肥大化する場合は、カテゴリやサブシステム単位で分割し、下位文書側で `part_of` に上位 SAC を指定します。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

| 項目                  | 必須 | 規約                                                                          |
| --------------------- | ---- | ----------------------------------------------------------------------------- |
| `specdojo.type`       | ○    | `requirement`                                                                 |
| `specdojo.rulebook`   | ○    | `specdojo:sac-rulebook`                                                       |
| `specdojo.based_on`   | ○    | 受入条件の根拠となる NFR・BAC 等の ID。成果物カタログの `depends_on` の範囲内 |
| `specdojo.part_of`    | 任意 | 分割した場合の上位 SAC                                                        |
| `specdojo.supersedes` | 任意 | 置き換える旧 SAC                                                              |

`based_on` の各 ID が既存文書へ解決することは、作成・更新後に `npm run lint:fm` などリポジトリの検証で確認します。

## 5. 本文要件

template 未整備のため、各 SAC は次の章を順に置きます。見出しは Markdown 規約に従い連番を付けます。

| 章                 | 必須 | 成立条件                                                                                 |
| ------------------ | ---- | ---------------------------------------------------------------------------------------- |
| 1. 概要            | ○    | 何を合格とするか（出口条件）、受入対象の範囲と対象外、根拠（`based_on` と整合）が分かる  |
| 2. 受入条件        | ○    | 受入条件ごとに ID、前提、操作、期待結果、判定方法を対応させる                            |
| 3. メモ / 将来課題 | ○    | 未確定の前提の論点・影響する受入条件・当面の扱いを記す。未決がなければ「なし」と明記する |

受入条件は 1 件を 1 つの `###` 見出しにし、要素を `####` で置きます。

- `### 2.n. <受入条件 ID> <短い条件名>`
  - `#### 2.n.1. 前提`（前提状態、試験環境、負荷条件、データ量）
  - `#### 2.n.2. 操作`（入力/操作/イベントの要約）
  - `#### 2.n.3. 期待結果`（観測点、計測値、閾値）
  - `#### 2.n.4. 判定方法`（観測先と合否の境界）

条件/入力だけ変えて同じ操作を反復する場合は、期待結果の代わりに `#### 2.n.3. ケース一覧` の表（推奨列: ケース ID / 前提（条件・負荷・データ量） / 期待結果（観測点・基準））へ差分をまとめてよいです。操作と判定方法は共通部分に置き、各行に繰り返しません。

## 6. 記述ガイド

### 6.1. 概要

- 判断基準: 1〜3 文で出口条件を述べ、対象範囲と対象外、根拠の NFR・BAC を示す。対象外を別 SAC で扱う場合は参照先を添える。
- 良い例: 「在庫照会と販売登録の API が平常時・ピーク時に NFR-PERF の閾値内で応答することを合格とする。帳票出力は sac-reporting で扱う」。
- 悪い例: 「システムの性能が十分であること」。対象と閾値が分からない。

### 6.2. 受入条件

- 判断基準: 前提と操作から期待結果が決まり、判定方法の観測先で合否を判断できること。代表パターンを 2〜8 件程度で押さえ、1 件に複数の要件を詰め込まない。
- 区分ごとの期待結果と観測点は次を目安にします。

| 区分   | 期待結果                                         | 観測点の例                   |
| ------ | ------------------------------------------------ | ---------------------------- |
| 機能   | 処理後の状態・記録・出力が仕様どおりに確定する   | データの状態、出力ファイル   |
| 非機能 | 指標が基準（数値と単位）を満たす                 | 試験レポート、監視の計測値   |
| 障害   | 検知・停止範囲・復旧時間（RTO）・損失範囲（RPO） | 障害試験の記録、監視アラート |
| 移行   | 件数・合計値の一致、移行後に業務データを参照可能 | 移行前後の照合結果           |

- 判定方法: 合否の境界（例: P95 が 500ms 以内なら合格）と観測先を書きます。判定する人の割り当ては本文で求めず、適用先のメンバー定義と登録簿で扱います。
- 良い例: 「ピーク時相当の負荷 100 RPS で在庫照会 API を 10 分間呼び出し、応答時間 P95 が 500ms 以内。負荷試験レポートの P95 値で判定する」。
- 悪い例: 「負荷をかけても問題なく動くこと」。前提・指標・観測先がない。

### 6.3. メモ / 将来課題

- 判断基準: 現行の受入を止める論点と将来の拡張を区別でき、影響する受入条件と当面の扱いが分かること。確認待ちは `_TODO_`、意思決定待ちは `_UNDECIDED_` を付け、確定したら本文へ反映してラベルを外す。
- 良い例: 「`_UNDECIDED_`: ピーク時の定義（年末の駄菓子まとめ買い）。SAC-PERF-02 の負荷条件に影響し、確定まで同条件の合否を保留する」。
- 悪い例: 「性能は今後検討」。影響範囲と当面の扱いが不明である。

## 7. 禁止事項

| 項目                                                 | 理由                         |
| ---------------------------------------------------- | ---------------------------- |
| 物理テーブル名・物理カラム名・SQL全文                | 概念レベル逸脱、変更に弱い   |
| 実装クラス/関数名、特定ライブラリの設定値の列挙      | 実装依存で変更に弱い         |
| クリック/画面遷移の逐語列挙                          | UI変更に弱い・本質が埋もれる |
| 「正しく動く」「問題ない」「性能が良い」等の曖昧表現 | 検証不能                     |
| 根拠のない閾値・要求の追加                           | 正本の NFR・BAC と食い違う   |
| テストの詳細手順・実行結果の記載                     | 下位のテスト仕様と重複する   |
