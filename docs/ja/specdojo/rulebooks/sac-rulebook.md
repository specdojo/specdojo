# システム受入条件仕様（SAC）作成ルール

System Acceptance Criteria (SAC) Documentation Rules

システム全体としての合格基準（機能・非機能・障害・移行など）を、検証可能な Markdown 形式で記述し、受入判断の根拠を明確にするための基準を定めます。

## 1. 全体方針

- SAC は **システム全体としての出口条件（合格基準）** です。
  - 例: 「性能試験で全ての NFR を満たし、重大障害 0 件であること」
- 受入条件は **観測・計測できる事実**として書き、手順書にはせず入力/操作と期待結果を要約します。
- 1ファイル = 1 受入対象（合格基準のまとまり）を基本とします。
  - 例: `性能`, `障害復旧`, `セキュリティ（権限/監査）`, `移行（初期データ）`
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直しません。文書の整形・lint はリポジトリの検証で扱い、受入条件に含めません。

## 2. 位置づけ

SAC は非機能要件（NFR）や業務受入条件（BAC）を根拠に、システム全体の合格基準を定めます。下位のテスト設計（テスト条件一覧、システムテスト仕様など）は SAC の受入条件を分解して参照するため、ID は安定させます。

## 3. ファイル命名・ID規則

- ファイル名: `sac-<term>.md` とし、`<term>` は受入対象を表す英小文字の kebab-case とします（例: `sac-performance.md`、`sac-reliability.md`）。
- 文書 ID: ファイル名と同じ `sac-<term>` とし、成果物カタログの宣言と一致させます。
- 文書タイトル（H1）: `# システム受入条件: <受入対象>` とします（例: `# システム受入条件: 性能`）。
- 受入対象が肥大化する場合は、カテゴリやサブシステム単位で分割し、下位文書側で `part_of` に上位 SAC を指定します。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- `specdojo.type` は `requirement`、`specdojo.rulebook` は `specdojo:sac-rulebook` とします。
- `specdojo.based_on` に、受入条件の根拠となる NFR・BAC 等の ID を必ず紐づけます。

## 5. 本文構成（標準テンプレ）

各 SAC ファイルは以下の見出しを順番に並べます。

1. 概要
2. 受入条件
3. メモ / 将来課題

## 6. 記述ガイド詳細

### 6.1. 概要

- 1〜3文で「何を合格とするか（出口条件）」を書きます。
- 対象仕様（NFR/BAC/主要機能）に言及し、`based_on` と整合させます。

### 6.2. 受入条件

- シナリオは 2〜8 個程度を目安に、合否判定が必要な代表パターンを押さえます。
- 非機能は「指標＋基準（閾値）」まで書きます（例: 応答時間（P95）/ 稼働率 / エラー率 / RTO / RPO / 監査ログの保持期間）。

シナリオの標準テンプレ（推奨）:

- `### シナリオ: <短い条件名>`
  - `#### 前提`（箇条書き。前提状態、試験環境、負荷条件など）
  - `#### 操作`（箇条書き。入力/操作/イベントの要約）
  - `#### 期待結果`（箇条書き。観測点/計測値/閾値を含める）
  - `#### 判定方法`（任意。どこを見て合否判定するか）

#### 6.2.1. ケース表

条件/入力だけ変えて同じ操作を反復する場合は、`### シナリオ: <共通の操作/イベント>` の下の `#### ケース一覧` の表へ差分をまとめてよいです。

| ケース | 前提（条件/負荷/データ量） | 操作 | 期待結果（観測点/基準） |
| ------ | -------------------------- | ---- | ----------------------- |
| C1     | …                          | …    | …                       |

### 6.3. メモ / 将来課題

- 未確定の前提（例: ピーク時の定義、想定データ量、外部依存のSLA）の論点と影響
- 将来追加したい SAC（例: DR訓練頻度、監査ログの検索性）

## 7. 禁止事項

| 項目                                            | 理由                         |
| ----------------------------------------------- | ---------------------------- |
| 物理テーブル名・物理カラム名・SQL全文           | 概念レベル逸脱、変更に弱い   |
| 実装クラス/関数名、特定ライブラリの設定値の列挙 | 実装依存で変更に弱い         |
| クリック/画面遷移の逐語列挙                     | UI変更に弱い・本質が埋もれる |
| 「正しく動く」「問題ない」等の曖昧表現          | 検証不能                     |

## 8. よくある誤りと対策

- 期待結果が曖昧（「性能が良い」） → 指標と基準（数値/単位）に分解する
- 前提がない（平常/ピークが不明） → 前提に条件（例: ピーク時相当の負荷 100 RPS、データ量、時間帯）を書く
- 期待結果が測れない → 観測点（ログ/監視/試験レポート等）を期待結果や判定方法に含める
- 1つのシナリオに要件を詰め込みすぎ → シナリオを分割する

## 9. サンプル（簡易）

```markdown
---
specdojo:
  id: sac-performance
  type: requirement
  status: draft
  rulebook: specdojo:sac-rulebook
  based_on:
    - nfr-performance
---

# システム受入条件: 性能

## 1. 概要

主要 API が平常時に業務上許容できる時間内で応答することを合格基準とする。

## 2. 受入条件

### シナリオ: 在庫照会APIの応答時間（平常時）

#### 前提

- 平常時相当の負荷（20 RPS）を与えている

#### 操作

- 在庫照会APIを呼び出す

#### 期待結果

- 応答時間（P95）が 500ms 以内であること

## 3. メモ / 将来課題

- ピーク時の同時接続数・データ量の確定
```
