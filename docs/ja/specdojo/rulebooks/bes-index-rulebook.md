# 業務イベント一覧（BES Index）作成ルール

Business Event Specification Index (BES Index) Documentation Rules

業務の各プロセス領域を起動する出来事を一覧にし、業務プロセス仕様・イベント処理設計・テスト設計が同じ出来事の単位を参照できるようにする入口文書の作成ルールです。一覧の網羅範囲、行の粒度、個別の業務イベント仕様（BES）へ詳細化する判断を定めます。

## 1. 全体方針

- 一つのシステムまたは合意した対象範囲につき、業務イベント一覧の正本を一つにします。範囲は上位の概念データフロー図（全体概要）が定めるプロセス領域とし、一覧の行はその起点イベントから起こします。
- 網羅は上位のプロセス領域に対して判定します。すべての領域に一つ以上の行が対応し、どの行も一つの領域へたどれる状態を目指します。領域の内部で生じる出来事は、上位文書の起点イベントでない限り一覧に加えません。
- 一行は一つの業務上の出来事を、発生した事実として過去形で表します。処理手順、画面操作、実装上のメッセージは扱いません。
- 一行で発生境界・時点・起点・相関を判定できない出来事だけを個別 BES へ詳細化します。詳細化の要否の判断と個別仕様の書き方は [[specdojo:bes-rulebook|業務イベント仕様 作成ルール]] を正本とします。
- 上位文書から確認できた内容と、推定・未決の内容を分けます。範囲の承認は人間の PO が担い、承認までは `status: draft` を維持します。
- 本書の `ready` 化には、ARC による完成例と本文要件の照合、recipe・template の要否判断の記録、QE による未解決指摘の確認を要します。残る判断は `_UNDECIDED_:` として影響・判断者・次のアクションを記録し、人間の PO が公開可否を判断します。

## 2. 位置づけと用語定義

| 文書・用語                     | 本書での意味・責務                                                                                |
| ------------------------------ | ------------------------------------------------------------------------------------------------- |
| 概念データフロー図（全体概要） | プロセス領域の分割、領域 ID、起点イベントの文言の正本。一覧の網羅を判定する基準になる             |
| 業務イベント一覧（BES Index）  | 起点イベントを行として並べ、イベント ID・発生条件・事実データの概要と個別仕様への入口を持つ       |
| 業務イベント仕様（BES）        | 一覧の行、または行の一部の成立の仕方について、発生境界を詳細化する個別仕様                        |
| 業務プロセス仕様（BPS）        | イベントを受けた後の手順を定める。イベントとプロセスの起動関係は BPS 側で記述する                 |
| 業務ルール・状態定義           | 判定の規則と状態の意味・遷移の正本。一覧には発生に必要な条件の要旨だけを置く                      |
| 起点イベント                   | プロセス領域を起動する業務上の出来事。一覧の行の出典                                              |
| 事実データ                     | 出来事の発生時点で観測できる業務上の情報。項目の構造・値・構文はデータモデル・schema を正本とする |

- **主要な関係者（Role code）と確認観点**:
  - **BA（主作成者）**: 起点イベントの網羅、行の粒度、事実データの業務上の意味を定義する。
  - **PO（承認者）**: 一覧の範囲と、未決事項を制限事項として受け入れるかを判断する。
  - **ARC（確認者）**: 上位文書・個別 BES・データモデルとの構造整合と、イベント処理設計の入力としての単位を確認する。
  - **QE（確認者）**: 発生条件から発生する場合・しない場合を判定でき、テスト設計で網羅を確かめられるかを確認する。
- **主な利用者（Role code）**: BA は BPS・BR、UX は UI 仕様、QE はテスト仕様の作成時にイベント ID と発生条件を参照します。ARC・DEV は個別 BES とデータモデルを併せてイベント処理設計へ接続します。

## 3. ファイル命名・ID規則

- ファイル名は `bes-index.md`、文書 ID は `bes-index` を基本とし、プロジェクト配下ではそのプロジェクトの authority を付けます。命名・配置の共通規則は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] を正本とします。
- 一覧のイベント ID は `bes-<event>` とし、`<event>` は出来事を区別できる英小文字・数字・ハイフンのスラッグにします（例: `bes-cash-sale-confirmed`）。`^bes-[a-z0-9][a-z0-9-]*$` に適合し、廃止行を含め一覧の中で一意にします。
- 個別 BES が行の全体を詳細化する場合は、個別 BES の文書 ID を行のイベント ID と一致させます。行の一部の成立の仕方だけを詳細化する場合は、個別 BES に別の ID を付け、「個別仕様への詳細化」の表で対応を示します。sample の文書 ID はメタ情報標準に従って実物と区別し、イベント ID との対応を詳細化表で示します。
- 既存文書への参照は相対パスではなく、project 修飾 doc id の `[[id|title]]` 形式を使います。表のセル内では `[[id\|title]]` とし、未作成文書は文書 ID をインラインコードで仮置きします。詳細化表から個別 BES へリンクし、個別 BES からも一覧と対応行のイベント ID を識別できるようにします。

### 3.1. 追加・変更・廃止の管理

- 新規追加時は BA が上位文書の起点イベントと既存行を照合し、重複のない ID と必須列を記入します。上位にない出来事は先に上位文書の範囲を確認し、ARC が詳細化の要否、QE が発生・不成立の判定を確認します。
- イベント ID は再利用しません。廃止・置換時は行を残し、イベント名に「（廃止）」を付け、発生条件に廃止理由・時期・後継 ID（なければ代替運用）を記載します。廃止行を現行領域の網羅件数に含めず、有効な参照元は後継または代替へ更新します。
- ID の変更・廃止時は BA が個別 BES・BPS・BR、UX が UI、QE がテスト仕様・受入条件の参照を抽出して更新し、ARC・DEV がデータモデル・イベント契約・実装への影響を確認します。未完の追従は PM が担当と移行時期を持つ PJR 項目へ引き継ぎます。
- 文書を置き換える場合は、新しい一覧または個別 BES の `supersedes` に旧文書 ID を指定します。文書でない一覧の行 ID は Frontmatter の `supersedes` に入れず、旧行と新行の対応を本文で示します。文書の廃止・承認は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] の「文書の改訂・廃止とライフサイクル変更管理」に従います。

## 5. 本文要件

template は置かないため、以下を本文構成の基準とします。Markdown の `##`〜`####` には階層ごとに連番と末尾の `.` を付けます。

| 記述対象           | 必須・任意                          | 判定基準                                                                                     |
| ------------------ | ----------------------------------- | -------------------------------------------------------------------------------------------- |
| 冒頭の概要         | 必須                                | 対象範囲、起点イベントの出典、一覧の利用者と委譲先（BES・BPS・BR・状態定義）が分かる         |
| 業務イベント一覧   | 必須                                | 上位文書のすべての起点イベントが行に対応し、各行が下表の列を満たす                           |
| 個別仕様への詳細化 | 個別 BES がある、または予定する場合 | 詳細化する行、個別仕様、詳細化する範囲、理由を対応させる                                     |
| 未決事項と承認条件 | 未決・推定の内容がある場合          | 論点、現時点の扱い、判断者・確認担当、解消の時期と記録先、一覧を確定入力として扱う条件を示す |

「個別仕様への詳細化」「未決事項と承認条件」は該当する内容がなければ省略できます。目的・適用範囲は冒頭の概要にまとめ、独立章の追加は任意とします。処理手順・構文・データ構造の詳細を記す章は不要であり、それぞれの正本を参照します。

### 5.1. 業務イベント一覧の列

列順は次の表の順に固定します。

| 列名         | 必須 | 記述内容                                                   |
| ------------ | ---- | ---------------------------------------------------------- |
| イベントID   | ○    | 「ファイル命名・ID規則」に従う一意の ID                    |
| イベント名   | ○    | 業務の利用者が理解できる過去形の日本語名                   |
| 起点領域     | ○    | 起動するプロセス領域の領域 ID                              |
| 何が起きたか | ○    | 成立した業務上の事実を一文で記述する                       |
| いつ         | ○    | 発生時点として観測する時点。要求・確定・後処理の区別を示す |
| 誰が／何が   | ○    | 出来事を起こす人・システム・外部、または時間の経過         |
| 発生条件     | ○    | 成立に必要な条件の要旨。成立の仕方が複数あれば区別する     |
| 事実データ   | ○    | 発生時点で観測できる情報の業務上の概念名                   |

列の追加・削除・意味の変更時は、ARC が rulebook の本文要件と sample の対応を確認し、BA が一覧・個別 BES・BPS・BR、UX が UI、QE がテスト仕様の利用箇所を照合して、影響する記述を同じ変更の採用時に更新します。契約・schema への影響は DEV と確認し、値・構文・構造をこの一覧へ複製しません。

### 5.2. 個別仕様への詳細化の列

| 列名           | 必須 | 記述内容                                                    |
| -------------- | ---- | ----------------------------------------------------------- |
| イベントID     | ○    | 詳細化する一覧の行                                          |
| 個別仕様       | ○    | 個別 BES へのリンク。未作成なら文書 ID を仮置きして明示する |
| 詳細化する範囲 | ○    | 行の全体か、行の一部の成立の仕方か                          |
| 詳細化の理由   | ○    | 一行では判定できない点（境界・時点・起点・相関のどれか）    |

## 6. 記述ガイド

上位文書の領域 ID・領域名・起点イベントの文言は転記で済ませ、一覧では発生の判定に要る情報を足します。共通の対象範囲と用語は一覧を正本とし、個別 BES では差分だけを具体化します。

### 6.1. 冒頭の概要

- 判断基準: 読者が、何を網羅した一覧か、何を一覧で扱わずどこへ委ねるかを説明できるようにします。
- 良い例: 「概念データフロー図（全体概要）の 10 領域の起点イベントを一覧にする。受けた後の手順は BPS、金額の計算は BR に委ねる。」
- 悪い例: 「システムで発生するイベントをまとめる。」範囲も網羅の基準も分かりません。

### 6.2. 行の切り出し

- 判断基準: 上位文書の起点イベントに「、」で別々の出来事が並ぶ場合は行を分け、「または」で同じ出来事の成立の仕方が並ぶ場合は一行にして発生条件で区別します。複数の領域に同じ出来事が書かれていても、同じ事実か判断できなければ別の行にして未決事項へ挙げます。
- 良い例: 「『閉店した』と『月末の締めが確定した』を別の行にする。」
- 悪い例: 「締めに関する出来事をまとめて一行にする。」発生時点も起点領域も一つに決まりません。

### 6.3. 何が起きたか・イベント名

- 判断基準: 成立した事実を過去形で書き、処理や操作の名前にしません。名前だけで隣接する出来事と区別できるようにします。
- 良い例: 「店頭の現金会計が確定した」
- 悪い例: 「会計処理」出来事なのか手順なのか判定できません。

### 6.4. いつ

- 判断基準: 要求・受付・確定・後処理の完了のどれを発生時点とするかを示します。周期で到来する出来事は、周期の定めに達した時点とします。
- 良い例: 「店番担当が受領を確認して確定した時点。控えの印字完了は待たない。」
- 悪い例: 「会計時」入力・確定・印字のどれか分かりません。

### 6.5. 誰が／何が

- 判断基準: 出来事を起こす主体を Role code・役割名・システムの責務名で書きます。時間の経過で生じる出来事は、その旨を書き、担当者を当てはめません。承認の責任と出来事を起こす主体は分けます。
- 良い例: 「店番担当（管理責任: 店主代表）」「時間の経過（閉店時刻）」
- 悪い例: 「担当者またはシステム」どちらが起こすのか分かりません。

### 6.6. 発生条件

- 判断基準: 成立に必要な条件の要旨を書き、判定の規則そのものは BR、状態の遷移は状態定義を参照します。発生しない典型の場合が判定に要るなら、条件の否定として読める形にします。
- 良い例: 「受領金額が請求金額以上で、未確定の取引である。」
- 悪い例: 「会計可能な場合」判定の根拠がありません。

### 6.7. 事実データ

- 判断基準: 発生時点で観測できる情報だけを業務上の概念名で挙げます。発生後にしか分からない結果は含めません。正本のデータモデルと照合していない場合は、その旨を未決事項に残します。
- 良い例: 「取引番号、確定時点、確定担当、請求金額」
- 悪い例: 「`sales_tbl.amt`、処理結果」物理名と、発生後の結果が混ざっています。

### 6.8. 個別仕様への詳細化

- 判断基準: 一行では境界・時点・起点・相関のどれかを判定できない行だけを詳細化します。行の一部だけを詳細化する場合は範囲を書き、残りが一覧の定義のままであることが分かるようにします。未作成の個別仕様は wikilink にせず、文書 ID を仮置きします。
- 良い例: 「つけ販売の受付は、上限超過時に受付と承認のどちらで成立するかが割れるため個別仕様へ詳細化する。」
- 悪い例: 「重要なので個別仕様を作る。」何が一行で判定できないのか分かりません。

### 6.9. 未決事項と承認条件

- 判断基準: 推定で埋めた列、上位文書から判断できない境界、正本との未照合を論点として残し、判断者・確認担当・時期・記録先を添えます。確定入力として扱える条件を一文で示します。
- 良い例: 「事実データは販売記録のデータモデルと未照合。ARC がイベント処理設計への引き渡し前に確認する。」
- 悪い例: 「詳細は今後検討する。」誰がいつ何を決めるのか分かりません。

### 6.10. 検証と引き渡し

- 判断基準: BA・QE が上位領域と有効な行の対応、必須列、ID の形式と一意性、個別 BES の対応範囲、未決事項の扱いを照合できることを引き渡し条件とします。ID は「業務イベント一覧」の表から抽出し、「ファイル命名・ID規則」の正規表現へ全件適合し、廃止行を含む重複が 0 件であることを確認します。
- Markdown は `npm run lint:md`、Frontmatter は `npm run lint:fm` でエラーがないことを確認します。これらの lint は行 ID の一意性や業務上の網羅を保証しないため、前項の照合を別に記録します。executor / reporter pipeline で親検証に設定されているコマンドは runner の結果を用います。
- 良い例: 「14 領域に有効な 16 行が対応し、廃止行を含む ID の形式違反・重複は 0 件。事実データの未照合は ARC がテスト設計への引き渡し前に確認する。」
- 悪い例: 「lint が通ったので網羅・承認済み。」静的検査では業務範囲や承認を判定できません。

## 7. 禁止事項

| 禁止する記述・扱い                                                                             | 理由                                               |
| ---------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 上位文書にない領域・起点イベントを、根拠なく一覧へ追加する                                     | 網羅の基準が崩れ、範囲を誤って確定するため         |
| 上位文書の起点イベントに対応する行を欠く                                                       | 下流の BPS・テスト設計が出来事を取りこぼすため     |
| 処理手順、画面の操作、例外時の回復を一覧に書く                                                 | BPS・画面仕様の責務と重複するため                  |
| BR の判定規則や状態遷移表を一覧に複製する                                                      | 正本の変更に追従できなくなるため                   |
| 発生条件・事実データを「その他」「適宜」「など」で省略し、成立条件や対象項目を特定できなくする | 発生有無と必要な情報の充足を判定できないため       |
| 物理テーブル・カラム、SQL、実装クラス・関数、API、コマンドの構文を記載する                     | 概念上の出来事と実装契約を混同するため             |
| 発生後にしか分からない結果を事実データにする                                                   | 観測時点と事実が矛盾するため                       |
| 未作成の個別仕様を存在するようにリンクする                                                     | 参照切れと、詳細化済みとの誤認を招くため           |
| 廃止したイベント ID を別の出来事に再利用する                                                   | 参照元の BPS・テストが別の出来事を指してしまうため |
| 推定や未決の内容を確定済みとして表し、範囲の承認前に確定入力とする                             | 下流が不確かな前提で設計・検証を始めるため         |
