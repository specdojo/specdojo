# 技術領域別 技術スタック詳細定義（TSD）作成ルール

Technology Stack Detail Definition (TSD) Documentation Rules

`tsd-<term>.md` は、採用した技術や実行基盤の構成・設定・利用手順を定義する。構築・接続・日常利用を行う人と確認者が、対象環境で構成を再現し、採用設定と正常性を照合するために使う。

## 1. 全体方針

- 一冊は技術領域・接続関係・一連の利用場面を単位とし、目的を共有する複数技術を含めてよい。
- 採用値・推奨値・任意の選択肢・未決事項を区別し、根拠のない製品名・版・容量・並列数を補わない。
- 初期構築・接続設定・日常利用は必要に応じて分冊し、各設定の正本を一つにする。
- 再現に必要な設定・コマンド・補助スクリプトを記載する。アプリケーション内部設計・詳細 API 仕様・SQL 全文は対象外とする。
- **共通の運用**: 作成・維持・確認の役割は適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱い、業務の動作確認に含めない。

## 2. 位置づけ

| 文書・情報           | TSD との分担                                                |
| -------------------- | ----------------------------------------------------------- |
| `tsd-index`          | 採用技術・区分・担当責務の一覧から詳細へ導く                |
| `tsd-<term>`         | 対象領域の構成・採用設定・再現手順の正本                    |
| 接続設定の分冊       | 基盤導入を前提とするクライアント設定                        |
| 日常利用の分冊       | 初期構築後の接続・再接続・起動・停止                        |
| 上位設計・非機能要件 | 責務分界・品質要求・採用判断の根拠                          |
| 運用設計・運用手順   | 体制・SLO・障害対応・バックアップ方針。技術固有の操作は TSD |

分冊では前提文書と完了条件、本書で定義する差分を示し、共通設定や技術一覧は参照する。

## 3. ファイル命名・ID規則

- ファイル名は `tsd-<term>.md` とし、`<term>` は対象技術・基盤・接続関係を表す英小文字・数字・ハイフンとする。
- 接続設定は `tsd-<technology>-<client>.md`、日常利用は `tsd-<environment>-usage.md` のように用途を区別してよい。
- `id` はファイル名の stem に対応させ、配置はプロジェクトの構成に従って `tsd-index.md` と同じ文書群に置く。

## 4. 推奨 Frontmatter 項目

共通項目・型・必須性は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` に従う。

- `type` は `architecture`、`rulebook` は `specdojo:tsd-rulebook` とする。
- `part_of` には所属する `tsd-index` などの ID 配列を推奨する。
- `based_on` は構成・設定の直接の根拠となる上位設計や基盤定義がある場合に示す。接続設定・利用手順の分冊では前提の基盤文書を含める。

## 5. 本文要件

以下は内容要件であり、章の統合・分割・順序変更を認める。別冊へ委ねる条件付きの内容は、正本と前提の完了条件を示す。

| 内容                   | 必須     | 目的・記述要件                                                                                     |
| ---------------------- | -------- | -------------------------------------------------------------------------------------------------- |
| 概要・位置づけ         | ○        | 誰がどの作業・判断に使うか、目的、対象範囲・対象外、他文書との責務分担を示す                       |
| 対象環境・前提条件     | ○        | OS、実行環境、必要な権限、導入済みの依存、必要な資源を示す。特別な前提がない項目はその旨を書く     |
| 全体構成・接続経路     | 条件付き | 複数のホスト、プロセス、クライアントを使う場合、配置、役割、通信方向、公開範囲を示す               |
| 採用技術・設定         | ○        | 用途、採用する版・モデル・設定値、適用範囲、理由、制約を対応させる                                 |
| 導入・初期設定         | 条件付き | 初期構築を扱う場合、実行場所、順序、変更先、既存設定との統合方法を示す                             |
| 接続設定               | 条件付き | 外部サービスや別の実行環境へ接続する場合、接続方式、認証方法、識別子の対応を示す                   |
| 動作確認               | ○        | 前提の確認と最終的な利用確認を分け、確認方法、期待結果、失敗時の切り分け先を示す                   |
| 継続利用・運用         | 条件付き | 常駐、長時間実行、再接続などを扱う場合、起動・停止・再開、設定の永続化、再構築で失われる状態を示す |
| 制約・トラブルシュート | ○        | 既知の制約、症状別の確認箇所、回避方法を示す。未確認の条件は未確認と分かる形で残す                 |
| 更新・復旧・撤去       | 条件付き | 既存環境を変更する場合、切り戻し、旧方式との共存可否、設定・データの保持や削除の範囲を示す         |
| 参照情報               | 任意     | 判断や手順の根拠となる公式情報、確認した版や日付、関連文書への導線を示す                           |

冒頭に初期構築・接続設定・日常利用の対象と開始条件を示し、手順を別冊へ委ねても完了の確認方法は残す。版・環境別の条件と任意設定を分け、未決事項は論点と影響（当面の扱い）を記す。

## 6. 記述ガイド

### 6.1. 対象環境と責務分界

- 接続元端末・ホスト・コンテナを構成図か対応表で区別し、呼び名を各操作の実行場所と統一する。
- 導入先・設定保存先・作業ディレクトリ・実行ユーザーを特定する。
- OS・ハードウェア・資源・並列数の制約を採用理由に結び付け、検証済み構成と一般的な推奨を分ける。

### 6.2. 採用設定の表

| 列             | 記述内容                                       |
| -------------- | ---------------------------------------------- |
| 対象・用途     | どの構成要素や利用場面に適用するか             |
| 設定項目       | 製品や設定ファイル上の項目名                   |
| 採用値・版     | 値、単位、版、モデル ID など                   |
| 適用範囲       | ユーザー、プロジェクト、プロセスなどの有効範囲 |
| 理由・制約     | 採用根拠、互換性、資源上の制約                 |
| 反映・確認方法 | 再起動の要否、有効値の確認方法                 |

設定ファイルと環境変数の優先順位・反映先、GUI 設定の画面項目名・保存先・反映条件を示す。

### 6.3. 導入・変更手順

- 順序付き手順と言語識別子付きコードブロックに、シェル・実行場所・事前条件を示す。
- 追加・部分変更・全体置換を区別し、既存の provider や利用者設定との統合方法を書く。
- 導入・起動・再起動・停止を分け、権限変更やデータ削除の影響・事前確認を添える。
- 移行では旧方式の停止・競合回避・切り戻しを示し、撤去では設定・認証状態・データの保持と削除を分ける。

### 6.4. 動作確認と切り分け

| 列             | 記述内容                                   |
| -------------- | ------------------------------------------ |
| 確認対象       | 接続、設定反映、利用機能など               |
| 実行場所・方法 | コマンド、GUI 操作、ログ確認など           |
| 期待結果       | 出力項目、状態、応答内容などの判定条件     |
| 失敗時の確認先 | 前提の依存、保存先、ログ、次の切り分け手順 |

- 対象に応じ、起動・疎通・認証・モデルや provider の識別子・最終利用を段階的に確認する。
- 期待結果は表示の丸写しを避け、版や環境に応じた合否判定項目を示す。
- 確認環境・未確認条件・残る確認方法を示し、未実施を成功と扱わない。

### 6.5. 継続利用と状態の保存

- 再接続・処理再開・プロセス再起動と、自動復旧の範囲を区別する。
- 再起動・再構築で保持・喪失する設定・認証状態・データ・セッションを示す。
- 資源制約・長時間実行では、監視項目・正常範囲・処理を減らす条件を示す。

### 6.6. 接続情報と秘密情報

- 接続方式・公開可能なポート・汎用ホスト名・API 基点は再現に必要なら記載する。
- 固有のホスト名・アカウント・URL は公開可否を判断し、機密ならプレースホルダーにする。
- 認証情報は実値に代えて取得・保存・参照方法を示し、設定例・出力例でも同じ扱いとする。

## 7. 禁止事項

| 禁止事項                                                       | 理由                                   |
| -------------------------------------------------------------- | -------------------------------------- |
| 実行場所や適用条件が異なる手順を区別せず並べる                 | 誤った環境や権限で設定を変更するため   |
| 未確認の構成や未採択の設定を、動作確認済み・採用済みとして書く | 実行と判断の前提を誤らせるため         |
| 技術一覧や他の TSD の設定を複数箇所で正本として管理する        | 更新時に構成が食い違うため             |
| 無関係な技術領域や独立した利用目的を一つの文書に詰め込む       | 適用範囲と保守単位が分からなくなるため |
| 停止、削除、再構築を、状態やデータへの影響を示さず指示する     | 復旧や継続利用に必要な状態を失うため   |
