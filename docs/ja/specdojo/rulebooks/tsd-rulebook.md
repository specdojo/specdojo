# 技術領域別 技術スタック詳細定義（TSD）作成ルール

Technology Stack Detail Definition (TSD) Documentation Rules

`tsd-<term>.md` は、採用した技術や実行基盤について、構成、設定、導入、接続、動作確認、継続利用に必要な情報を定義する。`tsd-index.md` の技術一覧を具体化し、別の担当者が対象環境で同じ構成を再現し、正常性を判断できる内容を残す。

## 1. 全体方針

- 一つの文書は、技術領域、接続関係、または一連の利用場面を単位とする。目的を共有する複数の技術を、一つの実行基盤として扱ってよい。
- 目的、対象環境、前提条件、実行場所を明示し、採用設定と動作確認を対応させる。
- 採用した値、推奨する値、任意の選択肢、未決事項を区別する。根拠のない製品名、版、容量、並列数を補わない。
- 一覧、技術基盤の初期構築、クライアントからの接続、日常利用を必要に応じて分冊し、同じ設定の正本を一つにする。
- 再現に必要な設定ファイル、コマンド、補助スクリプトの記述を認める。アプリケーションの内部設計、詳細 API 仕様、SQL 全文は扱わない。
- 秘密値は記載せず、取得・保存・参照の方法を記載する。公開可能な接続方式、ポート、汎用ホスト名と、個人・組織固有の機密情報を区別する。

## 2. 位置づけ

| 文書・情報           | 役割                                       | TSD との関係                                                    |
| -------------------- | ------------------------------------------ | --------------------------------------------------------------- |
| `tsd-index`          | 採用技術、区分、担当責務の一覧             | 全体の入口とし、技術領域ごとの詳細へ導く                        |
| `tsd-<term>`         | 技術領域や実行基盤の構成と採用設定         | 対象領域の設定と再現手順の正本にする                            |
| 接続設定の分冊       | 既存の技術基盤を利用するクライアントの設定 | 基盤側の導入を前提として参照し、重複記載しない                  |
| 日常利用の分冊       | 接続、再接続、起動、停止などの利用手順     | 初期構築の完了を前提とし、設定の正本を参照する                  |
| 上位設計・非機能要件 | 責務分界、品質要求、採用判断の根拠         | TSD の設定が満たすべき条件を示す                                |
| 運用設計・運用手順   | 体制、SLO、障害対応、バックアップなど      | 組織的な運用方針は参照し、技術固有の操作だけを TSD で具体化する |

- 分冊した文書には、前提となる文書と、本書で定義する差分を明示する。
- ホスト、コンテナ、接続元端末などで役割が異なる場合は、構成図または対応表で境界を示す。
- 共通設定や技術一覧を転載せず、正本への参照でつなぐ。参照だけでは実行順が分からない場合は、前提の完了条件を併記する。

## 3. ファイル命名・ID規則

- ファイル名は `tsd-<term>.md` とする。`<term>` は対象技術、実行基盤、接続関係が分かる英小文字・数字・ハイフンで表す。
- 接続設定は `tsd-<technology>-<client>.md`、日常利用は `tsd-<environment>-usage.md` のように用途を区別してよい。名称だけで内容を判断できない分割は避ける。
- `id` はファイル名の stem と対応させ、名前空間や一意性は共通のメタデータ規約に従う。
- 配置先は `tsd-index.md` と同じ技術基盤の文書群とする。プロジェクトのディレクトリ構成を優先する。

## 4. 推奨 Frontmatter 項目

項目は `specdojo` 配下に置く。共通の型と参照形式は [document-metadata-standard.md](../standards/document-metadata-standard.md) と成果物の Frontmatter スキーマに従う。

| 項目         | 必須     | 値・記述内容                                                 |
| ------------ | -------- | ------------------------------------------------------------ |
| `id`         | ○        | 対象文書を一意に識別する `tsd-<term>` 系の ID                |
| `type`       | ○        | `architecture`                                               |
| `status`     | ○        | `draft` / `ready` / `deprecated`                             |
| `rulebook`   | 推奨     | `specdojo:tsd-rulebook`                                      |
| `part_of`    | 推奨     | 所属する `tsd-index` などの ID 配列                          |
| `based_on`   | 条件付き | 構成や設定の直接の根拠となる上位設計、基盤定義などの ID 配列 |
| `supersedes` | 条件付き | 既存の構成定義を置き換える場合の旧文書 ID 配列               |

接続設定や利用手順を分冊する場合は、前提となる技術基盤の文書を `based_on` に示す。参考として読んだだけの文書を、採用判断の根拠として列挙しない。

## 5. 本文要件

以下は内容要件であり、固定した見出し順を要求しない。対象に合わせて章をまとめたり分けたりしてよい。条件付きの内容を別冊へ委ねる場合は、その正本と前提の完了条件を示す。

| 内容                   | 必須     | 目的・記述要件                                                                                     |
| ---------------------- | -------- | -------------------------------------------------------------------------------------------------- |
| 概要・位置づけ         | ○        | 目的、対象範囲、対象外、他文書との責務分担を明示する                                               |
| 対象環境・前提条件     | ○        | OS、実行環境、必要な権限、導入済みの依存、必要な資源を示す。特別な前提がない項目はその旨を書く     |
| 全体構成・接続経路     | 条件付き | 複数のホスト、プロセス、クライアントを使う場合、配置、役割、通信方向、公開範囲を示す               |
| 採用技術・設定         | ○        | 用途、採用する版・モデル・設定値、適用範囲、理由、制約を対応させる                                 |
| 導入・初期設定         | 条件付き | 初期構築を扱う場合、実行場所、順序、変更先、既存設定との統合方法を示す                             |
| 接続設定               | 条件付き | 外部サービスや別の実行環境へ接続する場合、接続方式、認証方法、識別子の対応を示す                   |
| 動作確認               | ○        | 前提の確認と最終的な利用確認を分け、確認方法、期待結果、失敗時の切り分け先を示す                   |
| 継続利用・運用         | 条件付き | 常駐、長時間実行、再接続などを扱う場合、起動・停止・再開、設定の永続化、再構築で失われる状態を示す |
| 制約・トラブルシュート | ○        | 既知の制約、症状別の確認箇所、回避方法を示す。未確認の条件は未確認と分かる形で残す                 |
| 更新・復旧・撤去       | 条件付き | 既存環境を変更する場合、切り戻し、旧方式との共存可否、設定・データの保持や削除の範囲を示す         |
| 参照情報               | 任意     | 判断や手順の根拠となる公式情報、確認した版や日付、関連文書への導線を示す                           |

- 初期構築、接続設定、日常利用のいずれを扱う文書かを冒頭で明示する。
- 版や環境で手順が変わる場合は、適用条件を分ける。任意の設定を全利用者の必須条件として書かない。
- 手順を省略して別文書へ導く場合も、本書の開始条件と完了を判断する確認方法は残す。

## 6. 記述ガイド

### 6.1. 対象環境と責務分界

- 接続元端末、ホスト、コンテナなどに一貫した呼び名を付け、各コマンドをどこで実行するか示す。
- インストール先、設定保存先、作業ディレクトリ、実行ユーザーを、手順を再現できる粒度で記載する。
- OS、ハードウェア、メモリ、ディスク、並列数などの制約は採用理由と結び付ける。検証した構成と一般的な推奨を区別する。

### 6.2. 採用設定の表

| 列             | 記述内容                                       |
| -------------- | ---------------------------------------------- |
| 対象・用途     | どの構成要素や利用場面に適用するか             |
| 設定項目       | 製品や設定ファイル上の項目名                   |
| 採用値・版     | 値、単位、版、モデル ID など                   |
| 適用範囲       | ユーザー、プロジェクト、プロセスなどの有効範囲 |
| 理由・制約     | 採用根拠、互換性、資源上の制約                 |
| 反映・確認方法 | 再起動の要否、有効値の確認方法                 |

設定ファイルと環境変数の両方がある場合は、優先順位と反映先を記載する。GUI で保存する設定も、画面の項目名、保存先、反映条件を示す。

### 6.3. 導入・変更手順

- 順序付きリストと、言語識別子付きのコードブロックを使う。シェル、実行場所、事前条件が分かるようにする。
- 設定の追加、部分的な変更、ファイル全体の置換を区別する。既存の provider や利用者設定を残す必要がある場合は統合方法を示す。
- 再起動、権限変更、データ削除などの影響と、実行前に確認すべき条件を併記する。導入、起動、再起動、停止を同じ操作として扱わない。
- 既存環境からの移行では、旧方式の停止、競合の回避、切り戻し方法を示す。撤去時は設定・認証状態・データの保持と削除を分ける。

### 6.4. 動作確認と切り分け

| 列             | 記述内容                                   |
| -------------- | ------------------------------------------ |
| 確認対象       | 接続、設定反映、利用機能など               |
| 実行場所・方法 | コマンド、GUI 操作、ログ確認など           |
| 期待結果       | 出力項目、状態、応答内容などの判定条件     |
| 失敗時の確認先 | 前提の依存、保存先、ログ、次の切り分け手順 |

- プロセスの起動、ネットワーク疎通、認証、モデルや provider の識別子、実際の利用機能を必要に応じて段階的に確認する。
- 期待結果は版や環境で変わる表示を丸写しせず、正常と判断する項目を明示する。
- 未実施の確認を成功した事実として書かない。確認環境、未確認条件、残る確認方法を記載する。

### 6.5. 継続利用と状態の保存

- 切断後の再接続、処理の再開、プロセスの再起動を区別し、自動で復旧する範囲を明記する。
- 再起動や再構築で保持される設定、認証状態、作業データと、失われるセッションを示す。
- 資源制約や長時間実行が関係する場合は、監視項目、正常範囲、処理を減らす判断条件を示す。

### 6.6. 接続情報と秘密情報

- 接続方式、公開可能なポート、汎用ホスト名、API の基点など、再現に必要な情報は記載してよい。
- 個人・組織固有のホスト名、アカウント、URL などは公開可否を判断し、機密の場合はプレースホルダーで示す。
- API キー、トークン、パスワード、秘密鍵の実値を載せず、credential store などの保存・参照方法を示す。設定例や出力例にも秘密値を含めない。

## 7. 禁止事項

| 禁止事項                                                                  | 理由                                    |
| ------------------------------------------------------------------------- | --------------------------------------- |
| 秘密値や機密の接続先を本文・設定例・ログ例に載せる                        | 文書の配布や Git 履歴を通じて漏れるため |
| 実行場所や適用条件が異なる手順を区別せず並べる                            | 誤った環境や権限で設定を変更するため    |
| 未確認の構成や未採択の設定を、動作確認済み・採用済みとして書く            | 実行と判断の前提を誤らせるため          |
| 根拠なく「最新」「十分」「問題ない」だけで版や正常性を定義する            | 再現や合否判定ができないため            |
| アプリケーションの内部クラス、関数設計、詳細 API 仕様、SQL 全文を展開する | 技術基盤の構成定義を超えるため          |
| 技術一覧や他の TSD の設定を複数箇所で正本として管理する                   | 更新時に構成が食い違うため              |
| 無関係な技術領域や独立した利用目的を一つの文書に詰め込む                  | 適用範囲と保守単位が分からなくなるため  |
| 停止、削除、再構築を、状態やデータへの影響を示さず指示する                | 復旧や継続利用に必要な状態を失うため    |
