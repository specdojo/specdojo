# 業務イベント仕様 作成ルール

Business Event Specification Documentation Rulebook

業務イベント一覧の一行では解釈が分かれる出来事を、発生した事実として定義するためのルールです。発生境界、時点、主体、条件、事実データを明確にし、業務承認とイベント処理・テスト設計の入力にします。

## 1. 全体方針

- 一つの BES は、一つの業務上の出来事を扱います。確定・受付などの境界、時点、起点、条件、データのいずれかが一覧だけでは判定できない場合に詳細化します。
- 冒頭には、この定義が解消する業務上の混同、対象範囲、定義を使えると判断する基準を簡潔に置きます。業務全体の目的は上位文書を正本とし、全文を再掲しません。
- 人、システム、外部からの要求を同じイベントにまとめる場合は、同じ事実が成立する境界と、一回の要求から生じるイベントの単位を示します。対象外と適用未判定は区別します。
- 確認できた事実と未決事項を分けます。未決事項には影響、判断者、確認担当、判断時期、記録先を添え、根拠や承認が揃うまで実装・公開可能な完成仕様と扱いません。

## 2. 位置づけと用語定義

| 用語                    | 本書での意味・責務                                                                                           |
| ----------------------- | ------------------------------------------------------------------------------------------------------------ |
| 業務イベント一覧（BEL） | イベントの網羅性と個別仕様への入口を持つ上位の一覧。共通の対象範囲・用語は一覧を正本とする                   |
| 業務イベント仕様（BES） | 一覧のうち解釈が分かれる一件について、発生した事実とその観測境界を詳細化する仕様                             |
| 業務プロセス仕様（BPS） | イベントを受けた後の手順、担当解決、通知、失敗時の回復などを定める仕様                                       |
| 業務ルール（BR）        | 選択、計算、可否判定の規則。BES には発生に必要な条件と参照だけを残す                                         |
| 相関情報                | 同じ要求・取引から生じた複数イベントを関連付ける業務上の識別情報。個別イベントや実行一回の識別子とは区別する |

状態の意味・遷移は状態定義、項目の構造・値・構文はデータモデル・schema・リファレンスを正本とします。BES は事実データの業務上の意味と必要になる条件を扱います。

## 3. ファイル命名・ID規則

- ファイル名は `bes-<event>.md` とし、`<event>` は出来事を区別できる英小文字のスラッグにします。
- 文書 ID は `bes-<event>` を基本とし、プロジェクト配下ではそのプロジェクトの authority を付けます。命名・配置の共通規則は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] を正本とします。
- イベント一覧が存在する場合は対応行から個別 BES へリンクし、BES からも一覧の対応イベントを識別できるようにします。一覧がなければ未解決の参照を wikilink にせず、文書 ID を仮置きして照合担当と時期を残します。

## 4. 推奨 Frontmatter 項目

- メタ情報の構文と許容値は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。
- BES の `type` は `requirement`、`rulebook` は `specdojo:bes-rulebook` とします。作成中は `status: draft` を維持し、`ready` への昇格は人間が行います。
- `based_on` には実際に根拠とした先行成果物だけを記載します。依存として宣言されていない文書やプロジェクト共通文脈を、根拠に見せるために追加しません。
- 業務承認を担う人間と承認条件は本文で識別します。未確認の個人名・担当割当を補完せず、実名または Member の確認を未決事項に残します。

## 5. 本文要件

見出し順・表・記入欄の骨組みは template を正本とします。以下は各章の意味要件であり、任意の小節も該当する章の範囲に置きます。Markdown の `##`〜`####` には階層ごとに連番と末尾の `.` を付けます。

| 記述対象                   | 必須・任意                           | 判定基準                                                                                                                             |
| -------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| 導入                       | 必須                                 | 解消する混同、対象範囲、利用できると判断する基準、上位一覧との対応が分かる                                                           |
| 「何が起きたか」の事実境界 | 必須                                 | 対象と確定した事実を過去形で示す。一回の発生単位、似ているが含めない出来事、対象業務の境界を区別できる                               |
| 「いつ」の観測時点         | 必須                                 | 要求・受付・確定・後処理のどの時点か判定できる。繰り返し・一括要求がある場合は各イベントの発生時点を説明できる                       |
| 「誰が／何が」の主体       | 必須                                 | 要求する主体と事実を成立させる主体を区別する。システム名は責務を定義し、業務承認者と混同しない                                       |
| 「発生条件」の成立・不成立 | 必須                                 | 共通条件と起点別の差異を示す。候補なし・条件未充足など、発生しない場合を判定できる。判断ロジックは BR、状態は状態定義へ委ねる        |
| 「事実データ」の内容       | 必須                                 | 項目ごとの業務上の意味と必要になる条件を示す。一括・並列などでは相関情報の単位と照合先を示す。未来の処理結果を発生時点の事実にしない |
| 発生判定・相関の確認例     | 境界や相関の解釈が分かれる場合に必須 | 同じ条件から発生有無・回数・同じ要求への帰属を判断できる。テスト実装や網羅的なケース集は持ち込まない                                 |
| 未決事項と承認条件         | 未決事項がある場合に必須             | 関連する章に、未決の内容、利用への影響、決定者、確認担当、時期、記録先を置く。解消済み・承認済みと誤認させない                       |

## 6. 記述ガイド

共通の業務範囲・用語は上位一覧を参照し、各 BES では個別の差分だけを具体化します。完成例を本文へ埋め込まず、以下では判断を分ける短い例だけを示します。

### 6.1. 導入

- 判断基準: 読者が、何の混同を防ぎ、どこまでを判断できる定義か説明できるようにします。
- 良い例: 「入力途中を売上と混同しないため、店頭の現金会計の確定を定義する。成立・不成立の代表例から記録対象を判断できることを確認する。」
- 悪い例: 「システムの重要イベントを説明する。」対象も利用の判定基準も分かりません。

### 6.2. 何が起きたか

- 判断基準: 対象、一回の単位、隣接する出来事との境界を示します。適用未判定の業務を、確認済みの対象や恒久的な対象外にしません。
- 良い例: 「一取引の現金会計が確定した。明細追加と日次締めの確定は含めない。」
- 悪い例: 「会計処理をする。」出来事が成立したのか、処理手順なのかを判定できません。

### 6.3. いつ

- 判断基準: 観測できる成立時点を選び、要求時や後処理の完了時と区別します。同時実行されることだけを根拠に、複数の事実を一つにしません。
- 良い例: 「店番担当が金額と受領を確認して会計を確定した時点。控えの印字完了は待たない。」
- 悪い例: 「会計時。」入力・確定・印字のどこかが分かりません。

### 6.4. 誰が／何が

- 判断基準: 起点が複数なら、起点区分、要求者、成立させる主体、差異を表で並べます。承認者の責任は成立主体の責任と分けます。
- 良い例: 「店番担当が確定を要求し、販売管理システムが確定を記録する。業務定義の承認は人間の店主代表が担う。」
- 悪い例: 「担当またはシステム。」どちらが何をするか不明です。

### 6.5. 発生条件

- 判断基準: 成立条件と不成立条件を対にして示します。根拠にない適用範囲は未決のまま、確認担当・判断者・時期・記録先を具体化します。
- 良い例: 「受領金額が請求金額以上で、未確定の取引を確定した場合に発生する。金額確認だけでは発生しない。」
- 悪い例: 「会計可能なら発生する。」判定根拠がなく、発生しない境界も分かりません。

### 6.6. 事実データ

- 判断基準: 項目、意味、必要になる条件を表で示します。相関は要求単位・取引単位・イベント単位を分け、正本との対応と確認例を添えます。物理項目名を推測して確定しません。
- 良い例: 「取引番号は確定対象を識別する。明細は同じ取引番号に属する。一括要求の識別が別に必要なら、その対応をデータモデルで確認する。」
- 悪い例: 「ID、明細など。」何の ID か、何を同じ単位とみなすか分かりません。

## 7. 禁止事項

| 禁止する記述・扱い                                                                  | 理由                                       |
| ----------------------------------------------------------------------------------- | ------------------------------------------ |
| 一覧にない適用範囲や未確認の担当を、合意済みとして追加する                          | 境界と承認責任を誤って確定するため         |
| 着手・通知・後処理・例外回復の詳細手順を BES に展開する                             | プロセス仕様の責務と重複するため           |
| BR の順位付け・計算式、状態遷移表を複製する                                         | 正本の変更を追従できなくなるため           |
| 物理テーブル・カラム、SQL、実装クラス・関数、詳細 API、CLI 構文を正本として記載する | 概念上の事実と実装契約を混同するため       |
| 発生後にしか分からない最終件数・結果を、発生時点の確定データとする                  | 観測時点と事実が矛盾するため               |
| 相関情報を実行 ID や時刻で代用できると、根拠なしに断定する                          | 複数イベントの同一要求への帰属を誤るため   |
| 未決事項や承認未了を隠して完成・公開可能と表す                                      | 下流が不確かな前提で設計・検証を始めるため |
