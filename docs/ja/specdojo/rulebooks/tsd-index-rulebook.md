# 技術スタック一覧（TSD Index）作成ルール

Technology Stack Index (TSD Index) Documentation Rules

`tsd-index.md` は、対象システムや開発基盤で採用する技術と担当責務を一覧にし、詳細な構成・設定の正本へ導く入口文書である。技術の用途と適用範囲を俯瞰し、構築、実装、運用、変更時に参照すべき定義を判断できる内容を記載する。

## 1. 全体方針

- 一つのシステムまたは合意した対象範囲につき、技術一覧の正本を一つにする。複数システムを扱う場合は、一覧の対象範囲を明示する。
- 採用技術の名称、区分、担当責務を一覧で対応させる。実行基盤だけでなく、対象範囲に含まれる開発、検証、文書化、配布、運用の技術も扱う。
- すべての依存パッケージを列挙するのではなく、構成や作業の前提として関係者が把握すべき技術を選ぶ。
- 採用済みの必須構成と任意利用の構成を区別する。未決の候補は採用技術に混ぜず、判断の記録へ導く。
- 詳細な設定、構築手順、接続方法、資源制約は `tsd-<term>` または設定ファイルなどの正本へ委ねる。
- 版の粒度と参照元を明確にし、lockfile や詳細 TSD と異なる固定値を二重管理しない。

## 2. 位置づけ

| 文書・情報               | 役割                                 | 一覧からの導線                             |
| ------------------------ | ------------------------------------ | ------------------------------------------ |
| `tsd-index`              | 採用技術と担当責務の全体一覧         | 対象範囲の技術を俯瞰する入口とする         |
| `tsd-<term>`             | 技術領域や実行基盤の詳細定義         | 構成、前提、設定、導入、動作確認を参照する |
| 接続設定・日常利用の TSD | 基盤を利用するクライアント設定や操作 | 初期構築と利用時の手順を区別して導く       |
| 設定ファイル・依存定義   | 実際に適用する版や設定の正本         | 正確な版や有効設定が必要な場合に参照する   |
| 採用判断の記録           | 技術を選んだ理由と未決事項           | 一覧で説明しきれない判断の根拠へ導く       |

- 詳細 TSD が未作成でも、採用が確認できた技術と担当責務は一覧に記載してよい。未整備の詳細文書を存在するように参照しない。
- 一つの技術に基盤設定と接続設定など複数の詳細文書がある場合は、参照先ごとの役割を示す。
- 同じ技術を複数の用途で使う場合は、責務を一行にまとめるか、適用範囲を明示して行を分ける。説明のない重複は作らない。

## 3. ファイル命名・ID規則

- ファイル名は `tsd-index.md` とする。
- `id` は `tsd-index` を基準に、名前空間と対象範囲内の一意性を共通のメタデータ規約に従って定める。
- 配置先はプロジェクトのアーキテクチャまたは技術基盤の文書群とし、詳細な `tsd-<term>.md` も同じ文書群にまとめる。
- 環境や領域ごとの補足を分冊する場合も、全体一覧の正本を複製せず、本書から参照する。

## 4. 推奨 Frontmatter 項目

項目は `specdojo` 配下に置く。共通の型と参照形式は [document-metadata-standard.md](../standards/document-metadata-standard.md) と成果物の Frontmatter スキーマに従う。

| 項目         | 必須     | 値・記述内容                                       |
| ------------ | -------- | -------------------------------------------------- |
| `id`         | ○        | 対象範囲で一意な `tsd-index` 系の ID               |
| `type`       | ○        | `architecture`                                     |
| `status`     | ○        | `draft` / `ready` / `deprecated`                   |
| `rulebook`   | 推奨     | `specdojo:tsd-index-rulebook`                      |
| `part_of`    | 任意     | 所属するアーキテクチャ文書などの ID 配列           |
| `based_on`   | 条件付き | 技術構成の直接の根拠となる設計や採用判断の ID 配列 |
| `supersedes` | 条件付き | 既存の技術一覧を置き換える場合の旧文書 ID 配列     |

## 5. 本文要件

| 内容               | 必須     | 目的・記述要件                                                  |
| ------------------ | -------- | --------------------------------------------------------------- |
| 冒頭の概要         | ○        | 対象システム、環境、一覧の利用目的と対象範囲を 1〜3 文で示す    |
| 技術スタック一覧   | ○        | 区分、採用技術、担当責務を一つの主一覧表で対応させる            |
| 補足・詳細への導線 | 条件付き | 詳細 TSD や設定の正本がある場合、各参照先の役割と適用条件を示す |

- 実行時に使う技術と、開発・検証・運用に使う技術の範囲が分かるようにする。対象外の領域まで空欄や仮の技術で埋めない。
- 版、利用環境、必須・任意が判断に必要な場合は、一覧の列または補足に記載する。
- 補足では全体の共通条件と参照先を示し、設定値や手順の詳細を転載しない。

## 6. 記述ガイド

### 6.1. 技術スタック一覧の列

| 列         | 必須     | 記述内容                                                             |
| ---------- | -------- | -------------------------------------------------------------------- |
| 区分       | ○        | 言語、ランタイム、DB、文書化など、利用目的を俯瞰できる分類           |
| 採用技術   | ○        | 製品・サービス・技術の識別できる名称。版を含める場合は粒度をそろえる |
| 担当責務   | ○        | 対象システムや作業のどこで、何を担うか                               |
| 版・正本   | 条件付き | 版の制約、または正確な版を管理する設定ファイル・詳細文書             |
| 適用範囲   | 条件付き | 対象環境、実行場所、必須・任意など、利用条件の違い                   |
| 詳細・備考 | 任意     | 詳細 TSD への参照、短い制約や選定理由                                |

- 担当責務は「開発用」「利用する」だけで終えず、対象と役割を一文で示す。
- 複数の製品を一つの実行基盤としてまとめる場合は、構成の内訳と各役割を詳細 TSD へ導く。
- 版を採用技術名に含める場合は、別の版列で同じ情報を繰り返さない。

### 6.2. 区分と網羅範囲

- 言語・ランタイム・フレームワーク、データ保存・連携、ホスティング・ネットワークなど、対象の実行に必要な技術を確認する。
- build・テスト・静的検査・文書化・図解・ソース管理・CI/CD・パッケージ配布・運用監視など、対象の開発と保守を支える技術も確認する。
- AI 実行環境やローカルモデル基盤など固有の領域は、実際に採用した範囲で追加する。区分名や製品名の例を、すべてのプロジェクトの必須構成にしない。

### 6.3. 版と採用状態

- 一覧ではメジャーバージョンや互換性の制約など、構成を理解するために必要な粒度を使う。特定の版が採用判断に不可欠な場合は、その理由と正本を示す。
- 正確なパッチ版や依存解決結果を lockfile などで管理する場合は、その参照先を示す。確認していない版を推測で記入しない。
- 任意利用の技術は、採用済みの選択肢であることと適用条件を明示する。未採択の比較候補や将来案は、採用一覧の外で扱う。
- 「最新版」と記載する場合は、取得元と更新方針を示す。実際に使用した版の確認方法が分からない表現にしない。

### 6.4. 詳細文書と更新

- 技術の初期構築、クライアント接続、日常利用を分冊している場合は、それぞれの目的が分かる参照名にする。
- 採用・廃止・責務・適用範囲が変わったときに一覧を更新し、詳細 TSD や設定の正本との不一致を確認する。
- 未作成の詳細や未決の条件は共通ラベルで示し、仮の参照先や設定値を確定情報として残さない。

## 7. 禁止事項

| 禁止事項                                                     | 理由                                           |
| ------------------------------------------------------------ | ---------------------------------------------- |
| 担当責務を空欄や技術名の言い換えだけにする                   | 採用技術が担う役割を判断できないため           |
| 採用済みの構成と未決の候補を区別せず並べる                   | 構築や実装の前提を誤らせるため                 |
| 同じ技術や一覧を、適用範囲を示さず重複させる                 | 責務と更新先が分からなくなるため               |
| 全依存パッケージやすべての版固定値を転載する                 | 一覧の目的を超え、依存定義と二重管理になるため |
| 詳細設定、接続先、構築コマンド、コードを一覧の本文へ展開する | 詳細 TSD や設定の正本との責務が重なるため      |
| API キー、トークン、秘密鍵、機密の接続情報を記載する         | 一覧の配布や履歴を通じて漏れるため             |
| 任意利用の製品や実例の構成を一律の必須技術にする             | 対象範囲や環境による違いを失うため             |
