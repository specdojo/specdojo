# 技術スタック一覧（TSD Index）作成ルール

Technology Stack Index (TSD Index) Documentation Rules

`tsd-index.md` は、採用技術と担当責務を俯瞰し、構築・実装・運用・変更時に詳細な構成や設定の正本へ導く入口文書である。

## 1. 全体方針

- 合意した対象範囲につき一覧の正本を一つにする。複数システムの場合も範囲を明示する。
- 全依存パッケージではなく、構成や作業の前提として把握すべき技術を選ぶ。網羅範囲は「区分と網羅範囲」に従う。
- 詳細な設定・手順・資源制約は「位置づけ」の正本に委ね、版や採用状態は「版と採用状態」に従う。
- **共通の運用**: 役割は適用先のメンバー定義、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。整形・lint はリポジトリの検証で扱い、業務の受入確認に含めない。

## 2. 位置づけ

| 文書・情報               | 役割                     | 一覧からの導線                   |
| ------------------------ | ------------------------ | -------------------------------- |
| `tsd-index`              | 採用技術と担当責務の一覧 | 対象範囲を俯瞰する入口           |
| `tsd-<term>`             | 技術領域・実行基盤の詳細 | 構成・前提・設定・導入・動作確認 |
| 接続設定・日常利用の TSD | クライアント設定や操作   | 初期構築と利用手順を区別する     |
| 設定ファイル・依存定義   | 適用する版・設定の正本   | 正確な版・有効設定               |
| 採用判断の記録           | 選定理由と未決事項       | 一覧で説明しきれない判断の根拠   |

- 詳細 TSD が未作成でも、採用を確認できた技術と責務は記載できる。
- 同じ技術の複数用途は責務を一行にまとめるか、適用範囲で行を分ける。

## 3. ファイル命名・ID規則

- ファイル名は `tsd-index.md` とする。
- `id` は `tsd-index` を基準とし、名前空間と一意性は共通のメタデータ規約に従う。
- アーキテクチャまたは技術基盤の文書群に詳細な `tsd-<term>.md` とまとめる。環境・領域別の補足は一覧を複製せず参照する。

## 4. 推奨 Frontmatter 項目

共通項目・必須性・型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と成果物の Frontmatter スキーマに従う。

- `type` は `architecture`、`rulebook` は `specdojo:tsd-index-rulebook` とする。
- `part_of` は任意で、所属するアーキテクチャ文書の ID 配列を記す。
- `based_on` は直接の根拠となる設計・採用判断、`supersedes` は置き換える旧一覧がある場合に ID 配列で記す。

## 5. 本文要件

| 内容               | 必須     | 目的・記述要件                                                  |
| ------------------ | -------- | --------------------------------------------------------------- |
| 冒頭の概要         | ○        | 対象システム、環境、一覧の利用目的と対象範囲を 1〜3 文で示す    |
| 技術スタック一覧   | ○        | 区分、採用技術、担当責務を一つの主一覧表で対応させる            |
| 補足・詳細への導線 | 条件付き | 詳細 TSD や設定の正本がある場合、各参照先の役割と適用条件を示す |

- 対象外の領域を空欄や仮の技術で埋めない。
- 版・利用環境・必須と任意の違いは、判断に必要な場合に列または補足で示す。
- 補足には全体の共通条件と参照先を記す。

## 6. 記述ガイド

### 6.1. 技術スタック一覧の列

| 列         | 必須     | 記述内容                                                             |
| ---------- | -------- | -------------------------------------------------------------------- |
| 区分       | ○        | 言語、ランタイム、DB、文書化など、利用目的を俯瞰できる分類           |
| 採用技術   | ○        | 製品・サービス・技術の識別できる名称。版を含める場合は粒度をそろえる |
| 担当責務   | ○        | 対象システムや作業のどこで、何を担うか                               |
| 版・正本   | 条件付き | 版の制約、または正確な版を管理する設定ファイル・詳細文書             |
| 適用範囲   | 条件付き | 対象環境、実行場所、必須・任意など、利用条件の違い                   |
| 詳細・備考 | 任意     | 詳細 TSD への参照、短い制約や選定理由                                |

- 担当責務は対象と役割を一文で示す。「開発用」「利用する」だけにしない。
- 複数製品を実行基盤としてまとめる場合は、内訳と各役割を詳細 TSD へ導く。
- 版を採用技術名に含める場合は、別の版列で同じ情報を繰り返さない。

### 6.2. 区分と網羅範囲

- 実行時の技術: 言語・ランタイム・フレームワーク、データ保存・連携、ホスティング・ネットワーク。
- 開発・保守の技術: build・テスト・静的検査・文書化・図解・ソース管理・CI/CD・配布・運用監視。
- AI 実行環境やローカルモデル基盤など固有の領域は採用範囲で追加する。例示を一律の必須構成にしない。

### 6.3. 版と採用状態

- メジャー版や互換性制約など必要な粒度を使い、特定版が採用判断に不可欠なら理由と正本を示す。
- パッチ版や依存解決結果は lockfile 等の参照先を示し、未確認の版を推測しない。
- 必須・任意を区別し、任意技術には採用済みであることと適用条件を示す。未採択の候補・将来案は判断の記録へ導く。
- 「最新版」は取得元・更新方針・使用版の確認方法を示す。

### 6.4. 詳細文書と更新

- 初期構築・クライアント接続・日常利用を分冊する場合は、各参照名で目的を示す。
- 技術の採用・廃止・責務・適用範囲の変更時は一覧と詳細 TSD・設定の正本を照合し、不一致を解消する。
- 未作成の詳細や未決条件は共通ラベルで示し、仮の参照先や設定値を確定情報にしない。

## 7. 禁止事項

| 禁止事項                                                     | 理由                                           |
| ------------------------------------------------------------ | ---------------------------------------------- |
| 担当責務を空欄や技術名の言い換えだけにする                   | 採用技術が担う役割を判断できないため           |
| 採用済みの構成と未決の候補を区別せず並べる                   | 構築や実装の前提を誤らせるため                 |
| 同じ技術や一覧を、適用範囲を示さず重複させる                 | 責務と更新先が分からなくなるため               |
| 全依存パッケージやすべての版固定値を転載する                 | 一覧の目的を超え、依存定義と二重管理になるため |
| 詳細設定、接続先、構築コマンド、コードを一覧の本文へ展開する | 詳細 TSD や設定の正本との責務が重なるため      |
| 任意利用の製品や実例の構成を一律の必須技術にする             | 対象範囲や環境による違いを失うため             |
