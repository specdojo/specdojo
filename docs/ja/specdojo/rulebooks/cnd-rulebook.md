# C4コンテナ図（CND）作成ルール

C4 Container Diagram (CND) Authoring Rule

対象システムを主要な実行・配備単位とデータストアに分け、責務、接続、配置上の前提を定義する規約です。インフラ設計と結合テストへ渡す境界を扱い、内部実装や連携構文は各正本へ委ねます。

## 1. 全体方針

- 一つの対象システムを扱い、上位の C4 コンテキスト図の利用者・外部依存・責任分界を引き継ぎます。範囲の拡張や仮定は明示します。
- コンテナは実行・配備単位として分け、機能名やソースディレクトリだけを理由に分割しません。データストアはファイル群やリポジトリでもよく、DB 製品の導入を前提にしません。
- 図は主要経路を、本文は責務・利用条件・技術制約を説明します。図の矢印を文章でなぞる説明は置きません。
- 記法は `includes` の [[specdojo:cnd-mermaid-rulebook|CND Mermaid 記法ルール]] に従います。形状・色・構文は本書で再定義しません。

### 1.1. 作成・合意・保守の責任

- ARC が作成と技術判断を担い、本 rulebook の継続更新・問い合わせ窓口となります。上位図の境界を確認した後に着手し、下位コンポーネント図・インフラ構成図の具体化と結合検証設計への引き渡し前に、利用する範囲をレビューします。
- BA は業務側の利用者代表と対象範囲・利用場面を、DEV は実行単位と接続方式を、QE は境界ごとの観測結果を、OPS は配備・公開・運用の前提を確認します。図に描く Person と設計の確認者は区別します。
- PO が対象範囲・残るリスク・公開可否を最終判断し、人間が承認または保留・差し戻しを記録します。ARC の技術確認や自動検査の成功だけでは承認完了としません。
- PM は作成・レビュー・課題解消をタスクへ分け、担当 Role code と判断期限を計画します。兼務と実行主体は [[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] および適用先のロール・メンバー定義に従います。

## 2. 位置づけと用語定義

| 用語         | 本書での意味                                                               |
| ------------ | -------------------------------------------------------------------------- |
| コンテナ     | アプリケーションなどの実行・配備単位。Docker の利用を意味しない            |
| データストア | 永続記録の保持単位。コンテナと並べて描き、生成物と正本を区別する           |
| システム境界 | 対象が責務を持つ範囲。同一端末・同一ネットワークという物理配置とは区別する |

上位コンテキスト図は対象システムと外部との境界、本図はその内部構成、コンポーネント図は各コンテナ内部、インフラ構成図は物理配置・ネットワークを扱います。バージョン、コマンド構文、データ構造は技術スタック・リファレンス・schema・外部 IF 仕様を正本とします。

## 3. ファイル命名・ID規則

- 共通規則は [[specdojo:id-and-file-naming-standard|ID・ファイル命名標準]] と [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従います。
- ファイル名は `cnd-<context>.md` とし、対象を表す英小文字・数字・ハイフンで識別します。プロダクト文書は原則 `docs/<lang>/product/030-architecture/010-c4/` に置きます。
- プロダクト文書の ID は `cnd-<context>`、プロジェクト文書は `<project-id>:cnd-<context>` とします。H1 に対象名と C4 コンテナ図であることを示します。
- 関係には文書内で一意な `REL-01` 形式の ID を付け、図の端点名・ラベルと定義表を対応付けます。名称変更だけでは関係 ID を振り直しません。

## 4. 推奨 Frontmatter 項目

共通項目の配置・必須条件・型・値は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- SpecDojo のメタ情報は `specdojo:` 配下に置きます。文書名は本文先頭の H1 に記し、Frontmatter の `title` で代用しません。
- `type` は `architecture`、主 `rulebook` は `specdojo:cnd-rulebook` とします。記法部品を主 rulebook にしません。
- `based_on` は上位コンテキスト図など、カタログの `depends_on` の推移閉包にある直接の内容根拠に限ります。共通のプロジェクト文脈は本文で参照します。
- 作成・編集時は `draft` を維持します。上位文書への所属や置き換えは共通規約に従い、仮定の説明をメタ項目の追加で代用しません。

## 5. 本文要件

見出し順、表の列、記入欄の骨組みは template を正本とし、ここでは各章の意味要件を定めます。

| 章の役割             | 必須     | 満たす内容                                                                                                                                       |
| -------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 概要                 | 必須     | 対象、上位図との対応、利用目的、対象外を示す                                                                                                     |
| 構成図               | 必須     | 一つのシステム境界に主要コンテナとストアを置き、直接利用者と外部依存を結ぶ。全関係にラベルを付ける                                               |
| 要素・境界の定義     | 必須     | 境界内外、利用者の接点、コンテナの責務・技術区分・配置前提、ストアの正本と生成物、外部依存の利用条件・失敗影響、関係の方式と詳細の正本を説明する |
| 技術前提・検証対象   | 必須     | 実行時と構築時、ローカルとリモート、読み書きの境界を区別する。結合確認の対象を関係 ID または要素名で識別する                                     |
| 未確定事項の引き継ぎ | 条件付き | 仮定・未確定の経路・配置がある場合、影響、担当ロール、解消条件、引き継ぎ先を残す                                                                 |

Person・外部システム・ストアが該当しない場合は、その旨と理由を定義欄へ記載します。主要コンテナは 2〜7 個程度を目安としますが、数に合わせて未根拠の実行単位を追加しません。

## 6. 記述ガイド

共通のメタ情報・用語は上位標準を参照し、本章では CND 固有の判断だけを扱います。

### 6.1. 概要

- 上位図のどの対象を分解するかと、読み手が配置・結合について何を判断するかを示します。
- 上位図が扱わない閲覧経路などを加える場合は、中核責務を変えるのか、派生した提供経路なのかを説明します。
- 承認対象と確認者を Role code で識別し、業務側の確認が必要な利用場面を対応付けます。実際の承認記録はプロジェクトの決定記録を参照し、図中の Person 名から承認者を推定しません。
- 良い例: 「販売システムを画面、処理サービス、記録ストアへ分け、店頭入力から保存までを示す」。悪い例: 「便利なシステムの全体像」。後者は対象と分割の目的を判定できません。

### 6.2. C4コンテナ図（Mermaid）

- 責務と実行・配備単位で候補を選びます。構築時だけ成立する線や任意の外部依存は、ラベルまたは注記で条件を示します。
- 良い例: 「サイト → 文書ストア: 公開対象文書の参照（構築時）」。悪い例: 「サイト → 文書ストア: 連携」。後者では稼働中にストアへアクセスする必要があるか判断できません。
- 矢印が依頼の方向か情報移動の方向かを注記し、応答を省略する場合も意味が通るようにします。
- 「主要経路」は上位図の各利用目的・外部依存を実現する経路とします。各経路の担当コンテナを特定し、描かない経路は対象外の理由を示します。数の目安だけで要素や関係を省きません。

### 6.3. 要素と境界の定義

- 境界、Person、Container、Data Store、External Software System、Relationship に分けて説明します。名称と関係ラベルは図と一致させます。
- コンテナごとに責務、実行・配備形態、既知の技術区分を示します。未確認の技術名やホストは仮定とし、内部モジュールは列挙しません。
- 推奨する関係表の列は「関係 ID」「起点 → 終点」「図中ラベル」「方式・条件と情報の要点」「詳細の正本」です。構文やフィールド一覧は参照先へ委ねます。
- 良い例: 「文書リポジトリは仕様の正本を保持し、閲覧用サイトはその生成物を配る」。悪い例: 「GitHub DB に全データを保存」。後者はファイル、版管理機構、共有サービスを混同しています。
- 外部依存は常時必須か、機能選択時だけ必要かを示します。ストアの直接更新者が複数ある場合、線の省略を単独書込の保証にしません。
- 図の全ノードに定義を、全関係に一意な関係 ID と定義行を対応付けます。図と表の起点・終点・ラベル・境界内外が一致することを合格条件とし、表だけに残った要素・関係も解消します。

### 6.4. 技術前提・制約と検証観点

- 配置設計に必要な入力と、決まっていない入力を分けます。ホスト台数・ポート・製品バージョンを埋めて合意済みと扱いません。
- 関係 ID を使い、保存・生成・外部呼び出しなどの結合対象と観測する結果を示します。テストケースや復旧手順の詳細までは定義しません。
- 下流の結合検証へ渡す各経路には正常時の結果を、外部依存・保存先には不在・失敗・結果不明時に区別する状態を記します。未確定の期待結果は検証済みの保証にせず、引き継ぐ論点にします。
- 良い例: 「構築時の読取不能と公開済みサイトの参照を分けて確認する」。悪い例: 「結合テストを実施する」。後者は対象と失敗の影響を識別できません。

### 6.5. メモ / 将来課題

- _ASSUMPTION_ と確定事項を分離し、影響する要素・関係、担当、解消条件を記録します。
- 配置・接続・公開の判断を妨げる論点は ARC が影響と対応案を PM へ報告し、PM が PJR の課題・リスク・変更要求・決定記録へ引き継ぎます。本図には転送先レコード、担当 Role code、判断期限または下流着手前などの判断時点を残し、解消後は ARC が図と参照先へ反映します。
- 良い例: 「配信先未確定。ARC が公開範囲と配備方式を整理し、PM が課題登録する。転送先レコードを本図へ記録し、配備設計の着手前に PO が判断する」。悪い例: 「配信は後で考える」。後者は担当と判断時点を追跡できません。
- 境界やコンテナを改訂・廃止したときは ARC が上位図・下位コンポーネント図・インフラ構成図の参照影響を確認し、DEV が連携実装、QE が該当する結合対象を追従させます。ライフサイクルの共通手続きはメタ情報標準を正本とします。

### 6.6. 検証・承認前の確認

このリポジトリではルートから次を実行します。`<対象.md>` は作成・変更した CND 文書の相対パスへ置き換えます。利用先では導入済みツールと検証設定に合わせ、同じ確認を行います。

| 確認              | コマンド                                                                             | 合格条件                                                            |
| ----------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| Markdown          | `node packages/docs-lint/bin/specdojo-docs-lint.js markdownlint <対象.md>`           | 終了コード 0、記法違反なし                                          |
| Frontmatter・本文 | `node packages/docs-lint/bin/specdojo-docs-lint.js remark <対象.md> --quiet --frail` | 終了コード 0、成果物 schema と主 rulebook の宣言に適合              |
| Mermaid 構文      | `node tools/lint-mermaid.mjs <対象.md>`                                              | 終了コード 0、対象の全図が passed、エラー・未検査なし               |
| Mermaid 描画      | `npm run docs:build:mermaid`                                                         | 終了コード 0、対象図の SVG が生成され、文字・矢印・境界を判読できる |

- QE は「C4コンテナ図（Mermaid）」「要素と境界の定義」「技術前提・制約と検証観点」の合格条件を照合し、コマンド結果と対象図の目視確認をレビュー記録へ残します。描画の成功だけでは内容の合格としません。失敗・未検査は原因を修正して再検査し、確認不能なら理由と次の確認者を記録して承認を保留します。
- ARC は必須の内容要件、上位図との対応、各確認者のレビュー結果、未解決指摘と PJR の転送先をそろえて PO へ渡します。構成・接続・公開可否を左右する未決事項は解消するか、採用する前提・影響・後続作業の制限について PO の判断を記録します。
- 人間の PO が承認を記録した後に、人間が `ready` への昇格を判断します。OPS は公開対象と承認対象が一致し、公開範囲の未決事項が解消していることを確認してから公開します。生成成功や `ready` の値だけを公開許可と扱いません。

## 7. 禁止事項

- 機能一覧・クラス・関数・ソース階層を、そのままコンテナとして描くこと。
- ストアのファイル群と、Git の履歴操作、リモート共有サービスを一つの実行単位として混同すること。
- IF の引数・ペイロード、schema の項目一覧、SQL、技術スタックのバージョン一覧を転載すること。
- 構築時だけの関係を常時接続として示すこと、または根拠のない配置・再試行・保存保証を確定事項として書くこと。
- 人間が担う承認や公開判断を、作成・生成・外部処理の成功だけで代替すること。
