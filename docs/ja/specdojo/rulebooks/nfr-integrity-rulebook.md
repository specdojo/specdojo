# 非機能要件 / 完全性 作成ルール

Non-Functional Requirements Integrity Documentation Rules

本書は、非機能要件のうち完全性（業務データの正確性・整合性・改ざん検知・変更履歴の追跡性）を定義する `nfr-integrity` の作成ルールを定める。誰がデータを参照・操作できるかとアクセスの監査は機密性・安全性（`nfr-security-safety`）に書く。

## 1. 全体方針

- 要件は対象データ・整合性境界・指標・基準を明示し、合否判定可能にする。
- 設計・実装手順ではなく、結果として満たす品質基準を書く。業務上重要な記録の欠落・不整合を許容しない基準にする。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直さない。文書の整形・lint はリポジトリの検証で扱い、「測定・検証方法」に含めない。
- _UNDECIDED_: `recipe`・`template` の要否は未判断である。sample は「本文構成（標準テンプレ）」の 5 章に揃っていないため、sample を揃えることと、同じ構成を NFR 分冊で共通の template にできるかの判断を、本書を `ready` にする前提条件とする。

## 2. 位置づけ

完全性の基準値やデータ不整合・改ざんの判断に使う文書であり、次の文書と接続する。

| 文書                  | 関係                                                                                         | 本文からの導線 |
| --------------------- | -------------------------------------------------------------------------------------------- | -------------- |
| `nfr-index`           | NFR 全体の入口。分冊として `part_of` で属する                                                | 必須           |
| `nfr-security-safety` | 認証・認可とアクセス監査の正本。改ざんを防ぐ権限制御はそちらに書き、本書は改ざんの検知を書く | 必須           |
| `sac-*` / `stc-*`     | 完全性要件の合否判定基準・試験仕様                                                           | 必須           |
| `opd-*` / `opr-*`     | 整合性チェック・監査証跡の保管の運用方針・手順                                               | 必須           |
| `dec-*`               | 基準値や除外条件の設計判断                                                                   | 任意           |

## 3. ファイル命名・ID規則

- 配置先は `docs/ja/product/060-non-functional-requirements/nfr-integrity.md` とし、[[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従う。
- 文書 ID は `nfr-integrity` とする。プロダクト文書のため名前空間を付けない。
- 要件 ID は `nfr-int-<連番>`（例: `nfr-int-001`）とし、欠番を作らない。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目（`id` / `type` / `status` を含む）・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。

- `specdojo.type` は `requirement`、`specdojo.rulebook` は `specdojo:nfr-integrity-rulebook` とする。
- `specdojo.part_of` には `nfr-index` を置く。
- `specdojo.based_on` には、監査証跡の保持期間などの根拠となる法令・監査基準・業務規程を示す文書を挙げる。

## 6. 記述ガイド

### 6.1. 概要（対象・目的）

- 正確性を担保する業務データ、完全性が損なわれたときの業務影響、重要記録として選んだ基準を書く。各要件の優先度を業務影響からたどれるかで判断する。
- 良い例: 「売上記録が欠けると日次の売上集計と仕入れ判断を誤るため、売上と在庫の記録を重要記録とする」。
- 悪い例: 「データの正確性を担保する」（対象データと影響が分からない）。

### 6.2. 適用範囲・前提条件

- 対象データ、整合性境界（どのデータ間の一致を保つか）、除外条件、監査証跡の保持期間とその根拠を書く。
- 良い例: 「整合性境界は販売記録と在庫数。監査証跡は 7 年保持する（根拠は `based_on` の帳簿保存の規程）」。
- 悪い例: 「監査証跡は必要な期間保持する」（期間と根拠がない）。

### 6.3. 完全性要件一覧

- 表の列は `id` / `内容` / `指標` / `基準` / `備考` とする。
- 指標の例は整合性違反件数、監査証跡欠落率、改ざん検知漏れ件数、重複記録件数である。
- `基準` は数値・単位・集計期間で書き、割合の指標は分子と分母を定義する。基準だけで pass/fail を一意に判定できるかで判断する。
- 良い例: 「監査証跡欠落率 = 変更履歴のない売上記録の変更件数 ÷ 売上記録の全変更件数（月次）、0%」。
- 悪い例: 「整合性違反は原則なし」（判定できない）、「HMAC で署名する」（実装手段であり品質基準ではない）。

### 6.4. 測定・検証方法

- 要件 ID ごとに、測定手段（整合性チェック・監査レビュー・試験）、判定のタイミング、合否条件、判定する Role code を表で書く。判定者はメンバー定義の Role code とし、職種名（DBA など）や agent を判定者にしない。
- 用語は「整合性チェック」に統一し、「日次整合チェック」などの言い換えを持ち込まない。
- 改ざん検知の要件は少なくとも 1 件を試験で判定し、対応する `sac-*` / `stc-*` を示す。
- 基準未達や改ざんを検知したときの記録先（課題・登録簿の個票など）と、要件や基準を見直す契機を書く。

### 6.5. 関連ドキュメント導線

- 「位置づけ」の表の文書へ導線を置き、必須・任意も同表に従う。

## 7. 禁止事項

| 禁止事項                                       | 理由                                       |
| ---------------------------------------------- | ------------------------------------------ |
| 整合性違反を「原則なし」で済ませる             | 合否判定できず監査不能になるため           |
| 改ざん検知の要件に検証方法がない               | 実効性が担保できないため                   |
| 監査証跡の保持期間と根拠を省略する             | 追跡不能になるため                         |
| 認証・認可・アクセス監査の要件を本書で定義する | `nfr-security-safety` と二重管理になるため |
| 署名方式などの実装手段を要件・基準として書く   | 実装依存で保守不能になるため               |
