# 運用方針・設計 全体構成 作成ルール

Operations Policy and Design Index Documentation Rules

恒常運用の方針・統制の正本となる `opd-index` の記述基準を定める。

## 1. 全体方針

- 運用の品質基準・責任分界・変更管理・復旧方針を判定可能な条件で定め、恒常運用の判断に使う文書とする。
- 本文構成と記述ガイドで骨組み・記入基準が定まるため、別の recipe・template は不要とする。
- **共通の運用**: 役割は適用先のメンバー定義、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。作成・改訂後は Markdown lint（`npm run lint:md`）と Frontmatter スキーマ検証（`npm run lint:fm`）を通す。

## 2. 位置づけと用語定義

`opd-index` を入口・方針の正本とし、`opd-<term>` は差分（補足・具体化・例外）、`opr-*` は実行手順と証跡を担う。移行期の一時体制（ハイパーケアなど）は `otp-*` が扱い、本書の対象外とする。

| 用語    | 本書での意味                                                     |
| ------- | ---------------------------------------------------------------- |
| SLO     | 運用側が自ら守る内部の数値目標                                   |
| SLA     | 利用者・委託先と合意し、未達時の扱いを伴う外部の約束             |
| KPI     | 運用の改善状況を追う管理指標（未達でも契約上の扱いを伴わない）   |
| RACI    | 作業ごとの実行（R）・説明責任（A）・相談（C）・共有（I）の割当て |
| RTO/RPO | 復旧までの目標時間（RTO）と、許容するデータ損失の時点（RPO）     |

## 3. ファイル命名・ID規則

- ID は `opd-index`、分冊は `opd-<term>`（kebab-case）とする。
- ファイル名は ID と同名の `.md` を推奨する。
- 配置は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] の `docs/ja/product/090-operations/` を推奨する。

## 4. 推奨 Frontmatter 項目

共通項目・必須性・型はドキュメントメタ情報標準と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` に従う。`specdojo.type` は `operations`、`specdojo.rulebook` は `specdojo:opd-index-rulebook` とする。

## 5. 本文構成（標準テンプレ）

全章必須。該当する運用がなければ章を残して「対象外」と理由を示し、分冊した内容は `opd-<term>` への参照で満たす。

| 章  | 内容                                               | 必須 |
| --- | -------------------------------------------------- | ---- |
| 1   | 概要（index）                                      | ○    |
| 2   | 運用の範囲・前提                                   | ○    |
| 3   | SLO・SLA・KPI                                      | ○    |
| 4   | 体制・責任分界（RACI・当番・エスカレーション）     | ○    |
| 5   | 監視・アラート方針（指標・閾値・通知先・初動）     | ○    |
| 6   | 障害対応方針（優先度・停止判断・周知）             | ○    |
| 7   | 変更管理（リリース・設定変更・承認・ロールバック） | ○    |
| 8   | バックアップ・リストア方針（RTO/RPO）              | ○    |
| 9   | 権限・アカウント運用（棚卸し・監査ログ）           | ○    |
| 10  | 定期運用方針（バッチ・点検）                       | ○    |
| 11  | 問い合わせ運用方針（窓口・分類・SLA）              | ○    |
| 12  | 関連ドキュメント導線（`opr-index` 等）             | ○    |

## 6. 記述ガイド

- 運用の範囲・前提は、対象システム・対象外・運用時間帯・前提とする外部サービスを示す。
- SLO・SLA・KPI の標準列は「指標・目標値・測定期間・測定方法・証跡・判定者」とし、各行が SLO・SLA・KPI のどれかを区別する。良い例:「可用性・99.9%以上・月次・監視の稼働率集計・監視レポート・運用責任者」。悪い例:「安定稼働を目指す」。
- 体制は RACI・当番・優先度別エスカレーション条件を、監視・障害・変更管理は条件・判断者・通知先を示す。担当・判断者・通知先は Role 名または窓口名で書く。良い例:「P1 は 15 分以内に Ops Lead へ連絡」。悪い例:「必要に応じて上長へ相談」。
- 変更管理は、承認が必要な変更の範囲・承認者・ロールバック条件を示す。
- 復旧は RTO/RPO と復元の検証頻度を示す。
- 権限・アカウント運用は、棚卸しの頻度、付与・剥奪の承認者、監査ログの保管期間を示す。
- 定期運用方針は、バッチ・点検ごとの周期・失敗時の扱い・確認者を示す。
- 問い合わせ運用方針は、窓口、問い合わせの分類、分類ごとの応答目標（SLA）を示す。
- 関連導線は `opr-index` と分冊を含め、分冊がない場合もその旨を示す。

## 7. 禁止事項

| 禁止事項                                                      | 理由                                                     |
| ------------------------------------------------------------- | -------------------------------------------------------- |
| コマンド列・逐次チェックリストを書く（手順は `opr-*` へ委譲） | 方針と手順の正本が二重になり、片方が取り残されるため     |
| SLO・SLA・KPI を数値・測定期間のない曖昧語だけで定義する      | 達成・未達を判定できないため                             |
| 責任分界・エスカレーション条件を未定義のまま確定する          | 障害時に判断者と連絡先が決まらず初動が遅れるため         |
| 変更の承認者・ロールバック条件を省略する                      | 変更失敗時に戻す判断ができないため                       |
| 個人名・個人の連絡先（電話番号・メールアドレス）を書く        | 公開・配布時に個人情報が漏れ、異動のたびに改訂が要るため |
