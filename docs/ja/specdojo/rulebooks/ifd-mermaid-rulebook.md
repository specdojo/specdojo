# Mermaidを用いたインフラ構成図 作成ルール

Infrastructure Flow Diagram (IFD) Documentation Rules using Mermaid

実行環境・ネットワーク・信頼境界と、主要な通信経路を合意するための規約を定める。配置と依存の判断に集中し、詳細設定や操作手順の正本を増やさない。

## 1. 全体方針

- 上位アーキテクチャの要素を実行場所へ対応付け、配置の事実・仮定・未決事項を区別する。
- 同じホスト上でも管理主体・到達範囲が異なる境界は区別する。枠だけで隔離やアクセス制御の実装済みを保証しない。
- 通信は目的、起点、終点、利用条件、境界を越える情報を示す。障害の影響範囲と検証対象を識別できる粒度にする。
- CIDR、IP、ポート、台数、版、認証値、FW・IAM 設定、コマンド構文は載せない。必要な詳細は技術構成・連携・運用の正本へ委ねる。

## 2. 位置づけと用語定義

| 用語・文書         | 本書での意味・責務                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------ |
| 実行環境           | ホスト・コンテナ・外部サービスなど、処理やデータを置く単位                                 |
| ネットワーク境界   | 到達経路・接続条件が変わる区切り。必ずしも物理ネットワークと一致しない                     |
| 論理ゾーン         | 管理主体、公開範囲、情報の持ち出し条件を検討する区切り                                     |
| 上位構成図         | 処理・データ・外部依存の責務を定義する入力。論理的なコンテナと実行用コンテナを同一視しない |
| 詳細設計・運用文書 | 接続設定、認証方式、監視閾値、復旧手順を管理する委譲先                                     |

## 3. ファイル命名・ID規則

- ファイル名は `ifd-<target>.md` とし、対象システムまたは配置範囲を英小文字・数字・ハイフンで表す。
- `id` はファイル名の stem と対応させる。名前空間・配置の共通規則は [[specdojo:docs-structure-guide|ドキュメント構造ガイド]] を正とする。
- Mermaid のノード ID と表示名を分離する。文書内で一意な ID を使い、改訂時も同じ要素・経路の ID を維持する。

## 4. 推奨 Frontmatter 項目

共通の値・構文は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と成果物 Frontmatter schema を正とする。

| 項目                     | 扱い     | IFD での用途                                         |
| ------------------------ | -------- | ---------------------------------------------------- |
| `id` / `type` / `status` | 必須     | 文書の識別、`architecture` 分類、成熟度              |
| `rulebook`               | 必須     | `specdojo:ifd-mermaid-rulebook` を指定する           |
| `owner`                  | 推奨     | 配置・境界設計を担うロール                           |
| `based_on`               | 条件付き | 直接の根拠となる上位構成図。単なる参考文書は含めない |
| `part_of` / `supersedes` | 条件付き | 所属・置き換え関係がある場合に記載する               |

## 5. 本文要件

見出し順・記入欄の骨組みは frontmatter で宣言した template を正本とする。以下は内容の成立条件であり、同じ表を全文書へ複製する指示ではない。

| 内容                     | 必須性   | 目的・判定条件                                                                                                                                     |
| ------------------------ | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 概要                     | 必須     | 対象環境、図で判断すること、上位入力、対象外を識別できる                                                                                           |
| インフラ構成図           | 必須     | 実行場所、必要な境界、主要経路を Mermaid で示し、凡例で向き・線種・省略を説明する                                                                  |
| 配置と境界の定義         | 必須     | 図中の要素に管理主体・保持情報・到達条件を対応付け、上位要素の配置または対象外の扱いを示す。代替配置がある場合は適用条件と置き換わる要素を区別する |
| 通信経路と情報の境界     | 必須     | 図と本文の経路 ID・起点・終点が対応し、目的、情報の要点、利用条件、詳細の正本または引き継ぎ先を追える                                              |
| 技術前提・制約と検証観点 | 必須     | 隔離・認証・公開に関する前提と、境界別の障害影響・観測対象・主確認ロールを示す                                                                     |
| メモ / 将来課題          | 条件付き | 仮定・未決事項がある場合、対象、影響、担当、解消条件・引き継ぎ先を残す                                                                             |

### 5.1. Mermaid の表現規約

- `flowchart LR` を使う。矢印の意味は依頼・参照・転送などの主たる起点から終点への向きとし、通常の応答は同じ線に含める。独立した逆方向の起動だけを別線にする。
- `subgraph` は最大 3 階層とする。実行環境・ネットワーク・論理ゾーンのうち必要な境界だけを描き、各枠が何の区切りか明記する。階層数を埋めるための枠は作らない。
- 表示名は役割を主語とする。配置や接続先の識別に必要な製品名は「推論サービス（製品名）」のように補記してよい。製品名だけで責務を表さない。
- 処理は矩形、DB は円筒、ファイル保管は角丸を基本とする。形状・色・絵文字だけに意味を持たせず文字で識別できるようにする。
- 経路ラベルに ID と通信目的を付ける。プロトコル名だけのラベルは使わない。線種を分ける場合は凡例で意味を定義する。
- 中継を省略して論理的な経路を一本で描く場合は、図の近傍で省略した中継と到達条件を説明する。中継方式が未確定なら仮定とし、直接接続が許可されている図と誤読させない。
- 装飾は任意とし、色を使う場合は `classDef` で役割の分類を統一する。交差が判断を妨げる場合は範囲を分割し、共有要素と経路 ID を対応付ける。

## 6. 記述ガイド

共通のメタ情報・リンク記法は上位標準を正本とし、本章では IFD 固有の判断だけを扱う。

### 6.1. 概要

対象環境と判断範囲を先に選ぶ。良い例は「店舗端末から共有サービスまでの到達範囲を示し、通信不能時の切り分けに使う」。悪い例は「システム全体を説明する」で、配置判断の範囲が選べない。

### 6.2. インフラ構成図

枠を越えるごとに実行場所・接続条件・管理主体のどれが変わるかで描き分ける。良い例は「店舗端末と外部保管サービスを別枠にし、送信する記録をラベルにする」。悪い例は「同じ製品なので外部サービスも端末の枠に入れる」。仮の経路は図の近傍にも仮定と記す。入口の中継を省略するなら「入口経由の記録要求を論理線で表す」と注記し、端末から内部サービスへ直接到達できるように描かない。

### 6.3. 配置と境界の定義

配置表では図にない管理責務・保持情報を補う。推奨列は「図中の環境・要素、上位要素、管理主体、情報・到達条件」。良い例は「作業記録は端末側、外部には送信対象だけを渡す案」。悪い例は「Private 枠なので安全」で、アクセス制御の根拠がない。

代替配置は同時稼働か選択肢かを判断し、後者なら置き換え後の保持範囲・到達性を確認対象にする。良い例は「コンテナ実行の代わりにホストで同じ役割を実行し、書込範囲を再確認する」。悪い例は「両環境に同名の処理を置き、稼働条件を示さない」。上位の責務は配置を変えても引き継ぐ。

### 6.4. 通信経路と情報の境界

条件付きの外部依存を常時必須の経路と混ぜない。推奨列は「経路 ID、起点 → 終点、目的・情報、利用条件・詳細の委譲先」。良い例は「共有時だけ控えを外部へ送り、接続・認証の契約は連携仕様で定める」。悪い例は「全データを同期する」で、情報範囲と正本の位置が不明である。

### 6.5. 技術前提・制約と検証観点

境界が成立する条件と、条件が崩れたときに観測するものを結ぶ。良い例は「別ホストへの到達不能、サービスの応答欠落、記録の保存失敗を分けて観測する」。悪い例は「トンネルがつながるので作業も成功する」。検証設計への入力と実施済みの証跡を区別し、監視対象は識別するが、閾値や復旧コマンドを再定義しない。

### 6.6. メモ / 将来課題

不明点が承認・検証・運用のどこを止めるかで影響を具体化する。良い例は「公開先未決。ARC が到達範囲を整理し、PO の公開判断後に配置へ反映する」。悪い例は「後で検討する」。単なる調査待ちと仮定は共通ラベルで区別する。

## 7. 禁止事項

- 上位図の責務を変更したり、業務判断・公開可否・製品採択を根拠なく確定したりしない。
- 論理ゾーンやトンネルの存在だけから、隔離・認証・情報非保持を保証しない。
- 詳細設定・schema・リファレンスの値、構文、構造を複製しない。秘密値や個人固有の接続先を載せない。
- 完成図の例を本書に埋め込まない。対応する型の所在は frontmatter の宣言で管理する。
- 改訂・廃止で経路や境界が変わる場合、追従先を省略しない。ARC が上位構成図・連携設計、QE が検証対象、OPS が監視・運用参照、PO が公開判断への影響を確認する。ライフサイクル手続きは共通メタ情報標準に従う。
