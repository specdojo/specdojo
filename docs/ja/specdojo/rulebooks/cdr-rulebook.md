# コーディング規約（agent 向け instructions）作成ルール

Coding Rules (Agent Instructions) Documentation Rulebook

実装の段で agent が読むコーディング規約を、言語・枠組みごとに 1 ファイルの正本として定めます。正本の置き場所、本文に絞る項目、Claude Code や `AGENTS.md` など環境別の薄いラッパーの作り方を規定し、agent がどの環境でも同じ規約で実装・検証できる状態にします。

## 1. 全体方針

- 実装の段の型はこの 1 種類とする。実装の設計書（モジュール分割、コンポーネントの境界、依存の向きの設計）は置かず、設計の段の文書（`cpd`・`sysd-*`）で決める。
- 使う言語・ライブラリ・版の選定は技術スタックの定義（`tsd-index`・`tsd-<term>`）に任せ、本書の成果物では扱わない。コーディング規約は、選定済みの技術を「どう書くか」と「どう検証するか」だけを定める。
- 読み手は実装する agent とレビューする人とする。agent が編集の直前に読んで判断できる命令形の規則と、実行できる検証コマンドで書く。
- 正本は 1 つにし、環境別のファイルは正本を読み込ませるラッパーに限る。規則の本文を環境別のファイルへ複製しない。
- 中身は最低限に絞る。対象は基本方針、モジュールと import、型、エラー処理、命名、テストと検証のコマンド、禁止事項とし、linter・formatter の設定で強制できる細則は設定ファイルを正本として参照する。

## 2. 位置づけと用語定義

| 文書・ファイル            | 役割                                                     | 本書の成果物との関係                                                  |
| ------------------------- | -------------------------------------------------------- | --------------------------------------------------------------------- |
| `tsd-index`・`tsd-<term>` | 言語・枠組み・ライブラリ・版の選定と実行基盤             | 規約の前提。選定の理由や版は書かず、参照する                          |
| `cpd`・`sysd-*`           | コンポーネントの境界、横断ルール（エラー形式・ログなど） | 境界と横断ルールの正本。規約は依存の向きの検査方法だけ書く            |
| 正本                      | `.github/instructions/<言語>.instructions.md`            | 本書の成果物。規則の唯一の本文。Copilot は `applyTo` に従って直接読む |
| 環境別のラッパー          | `.claude/rules/<言語>.md`、`AGENTS.md` の参照節など      | 正本を各環境へ読み込ませる。規則の本文を持たない                      |
| linter・formatter の設定  | `eslint.config.*`、`tsconfig.json`、`.editorconfig` など | 機械で強制する細則の正本。規約からは名前と検査コマンドで参照          |

## 3. ファイル命名・ID規則

- 正本はリポジトリルートの `.github/instructions/<言語>.instructions.md` に置く。`<言語>` は英小文字・数字・ハイフンで、言語名（`typescript`・`csharp`・`python`）または対象を絞った枠組み名（`vitest`・`nextjs`・`unity-csharp`）とする。
- 1 ファイルは 1 つの適用範囲（`applyTo` の glob）に対応させる。同じ言語でもテストコードなど適用するファイルが異なり規則も異なる場合は、`typescript` と `vitest` のように分ける。適用範囲が同じなら分けない。範囲が重なる場合（`vitest` は `typescript` の範囲に含まれる）は、狭い方の正本に追加の規則だけを書き、広い方の規則と矛盾させない。
- `id` は `<言語>-instructions` とする（例: `typescript-instructions`）。ファイル名の `.` は ID に使えないため `-` に置き換える。
- 成果物カタログでは、グループの `base_path` を `/.github/instructions`、各成果物の `path` を `<言語>.instructions.md`、`rulebook` を `specdojo:cdr-rulebook` とする。ラッパーはカタログへ載せない。
- ラッパーのファイル名は環境の規約に従う。Claude Code は `.claude/rules/<言語>.md` とし、正本と同じ `<言語>` を使う。

## 4. 推奨 Frontmatter 項目

正本の Frontmatter は、トップレベルに Copilot の `applyTo` を置き、SpecDojo の項目を `specdojo:` 配下に置く。共通の型と参照形式は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。

| 項目                  | 必須     | 値・記述内容                                                                                                                        |
| --------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `applyTo`             | ○        | 規約を当てるファイルの glob（例: `"{src,tests}/**/*.ts"`）。トップレベルに置く                                                      |
| `specdojo.id`         | ○        | `<言語>-instructions`                                                                                                               |
| `specdojo.type`       | ○        | `architecture`                                                                                                                      |
| `specdojo.status`     | ○        | `draft` / `ready` / `deprecated`                                                                                                    |
| `specdojo.rulebook`   | ○        | `specdojo:cdr-rulebook`                                                                                                             |
| `specdojo.based_on`   | 推奨     | 前提とする `tsd-index`・`tsd-<term>`・`sysd-cross-cutting-policy` などの ID 配列                                                    |
| `specdojo.supersedes` | 条件付き | 既存の規約を置き換える場合の旧 ID 配列。旧正本は `deprecated` にし、同じ変更でラッパーと `AGENTS.md` の参照を新しい正本へ付け替える |

`.github/` は文書サイトと `lint:fm` の対象外のため、Frontmatter の検査は成果物カタログの登録と grade で行う。`status` を `ready` にするのは、テストと検証の章のコマンドが実行でき、使う環境のラッパーで正本の読み込みを確かめた後とする。

## 5. 本文要件

見出しの順序と記入欄は template を正本とする。各章の目的と必須・任意は次のとおり。

| 章                  | 必須     | 目的・記述要件                                                                                                     |
| ------------------- | -------- | ------------------------------------------------------------------------------------------------------------------ |
| 導入文              | ○        | H1 の直後に、対象の言語・枠組みと適用範囲を 1〜2 文で書く                                                          |
| 基本方針            | ○        | 型検査の厳しさ、既存コードの書き方への追従、変更の最小化など、全規則の前提になる方針を 3〜5 項目で書く             |
| モジュールと import | ○        | モジュール方式、import の書き方、依存の向きの制約と、その制約を検査する仕組み（linter の規則名など）を書く         |
| 型                  | 条件付き | 静的型のある言語で必須。型の宣言、不明な外部入力の扱い、型の強制の制限を書く。動的型の言語は型ヒントの方針で代える |
| エラー処理          | ○        | 例外と戻り値の使い分け、エラーメッセージに含める文脈、握りつぶしの禁止を書く                                       |
| 命名                | ○        | 識別子の大文字小文字の規則、略語の扱い、真偽値の名前を書く                                                         |
| テストと検証        | ○        | 変更後に実行するコマンドを、対象（型検査・lint・単体テスト・統合テスト）と実行条件ごとに書く                       |
| 禁止事項            | ○        | 破ると被害の大きい書き方と理由を表で書く。表に書いた禁止は本文の章で繰り返さない                                   |

- `型` を省けるのは、動的型の言語で型ヒントも使わない場合に限る。省く場合は、その理由を導入文か基本方針に 1 行で書く。
- 枠組み固有の章（例: Unity のライフサイクル、Next.js のサーバーとクライアントの境界）は、上記の必須章の後ろに 1〜2 章まで追加してよい。

## 6. 記述ガイド

### 6.1. 規則の書き方

- 1 項目に 1 つの規則を、agent が守ったかどうかを判定できる命令形で書く（例: 「`any` を使わない。型が不明な値は `unknown` で受けて検証する」）。
- 規則の理由は、規則だけでは判断を誤る場合に限って 1 文で添える。理由の詳しい背景は書かない。
- コード例は、規則の形が文章だけでは伝わらない場合に 10 行程度までで示す。業務ロジックや API の詳細を例に含めない。
- linter・formatter・型検査で強制している規則は、設定ファイル名と規則名を書き、規則の中身を再掲しない。
- 1 ファイルは 300 行程度までを目安とする。超える場合は、適用範囲を分けられないかを先に検討する。

### 6.2. テストと検証の書き方

| 列       | 記述内容                                             | 例                                      |
| -------- | ---------------------------------------------------- | --------------------------------------- |
| コマンド | リポジトリの `package.json` などに定義済みのコマンド | `npm run typecheck`                     |
| 対象     | 何を検査するか                                       | 型検査（`src`・`tests`）                |
| 実行条件 | どの変更のときに実行するか                           | TypeScript を変更したとき（毎回）       |
| 失敗時   | 失敗したときに agent が取る行動                      | 型エラーを直す。`@ts-ignore` で隠さない |

- 存在しないコマンドを書かない。定義が無い場合は、追加するか、該当の検査が無いことを書く。
- 実 Git・子プロセス・外部サービスを使う重い検査は、agent の sandbox で実行するものと親の runner・CI で実行するものを分けて書く。

### 6.3. 環境別のラッパーの作り方

ラッパーには、適用範囲の宣言と正本への参照だけを書く。規則を追加・変更するときは DEV が正本だけを直し、ARC が設定・コマンドとの整合とラッパーの追従を確かめる。

| 環境           | ラッパーの置き場所             | 正本の読み込ませ方                                                      | 適用範囲の宣言         |
| -------------- | ------------------------------ | ----------------------------------------------------------------------- | ---------------------- |
| GitHub Copilot | 不要                           | 正本を直接読む                                                          | 正本の `applyTo`       |
| Claude Code    | `.claude/rules/<言語>.md`      | 本文に `@../../.github/instructions/<言語>.instructions.md` を 1 行書く | Frontmatter の `paths` |
| Codex など     | リポジトリルートの `AGENTS.md` | 正本のパスと適用範囲を列挙し、該当ファイルの編集前に読むよう指示する    | `AGENTS.md` の本文     |
| Gemini CLI     | `GEMINI.md`                    | `@.github/instructions/<言語>.instructions.md` で読み込む               | `GEMINI.md` の本文     |

Claude Code のラッパーの例:

```markdown
---
paths:
  - "{src,tests}/**/*.ts"
---

# TypeScript Rules

このファイルは Claude Code 向けの薄いラッパーです。

@../../.github/instructions/typescript.instructions.md
```

`AGENTS.md` の参照節の例:

```markdown
## Coding Rules

次のファイルを編集する前に、対応する規約を読んで従う。

- `src/**/*.ts`・`tests/**/*.ts`: `.github/instructions/typescript.instructions.md`
- `tests/**/*.test.ts`: `.github/instructions/vitest.instructions.md`
```

- ラッパーの `paths` と `AGENTS.md` に書く適用範囲は、正本の `applyTo` と同じ glob にする。正本の `applyTo` を変えたら、同じ変更でラッパーを直す。
- ラッパーを作成・変更したら、使う環境ごとに、対象のファイルを編集するときに正本が読み込まれ、対象外のファイルでは読み込まれないことを確かめる。
- 使わない環境のラッパーは作らない。プロジェクトが使う agent の環境は、メンバー定義や実行設定から判断する。

### 6.4. ほかの言語・枠組みへの当てはめ

- 章立ては言語によらず同じにし、各章の中身だけを言語の慣習に合わせる。
- 言語の規則に枠組みの規則を足す場合（TypeScript に Next.js の規則を足すなど）は、言語の正本に枠組み固有の章を足すか、適用範囲が異なれば枠組みの正本（`nextjs.instructions.md`）を分ける。言語の正本の規則を枠組みの正本へ複製しない。
- Unity の C# のようにエンジンが規約を持つ場合は、エンジンの命名・ライフサイクルの規則を `命名` と枠組み固有の章で書き、検証はエディタを起動しない検査（`dotnet format` など）と起動が必要な検査を分ける。

## 7. 禁止事項

| 禁止事項                                                 | 理由                                                                            |
| -------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 言語・ライブラリの選定理由や版を書く                     | `tsd` と二重管理になり、選定の変更が規約に取り残されるため                      |
| モジュールの分割やコンポーネントの境界を設計する         | 設計の段（`cpd`・`sysd-*`）の責務であり、実装の設計書を置かない方針に反するため |
| ラッパーに規則の本文を書く・正本を複製する               | 環境ごとに規則がずれ、agent ごとに異なる実装になるため                          |
| ラッパーの適用範囲を正本の `applyTo` と変える            | 環境によって規約が当たるファイルが変わるため                                    |
| 実行できない・定義されていない検証コマンドを書く         | agent が検証を失敗させるか、検証を省くため                                      |
| linter で強制済みの細則を本文に再掲する                  | 設定の変更に本文が取り残されるため                                              |
| 「適切に」「なるべく」など判定できない語だけで規則を書く | agent が守ったかどうかを判定できないため                                        |
