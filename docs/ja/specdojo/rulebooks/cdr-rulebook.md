# コーディング規約（agent 向け instructions）作成ルール

Coding Rules (Agent Instructions) Documentation Rulebook

実装する agent がどの環境でも同じ規約で実装・検証できるよう、言語・枠組みごとの正本と環境別の薄いラッパーの要件を定めます。

## 1. 全体方針

- 実装の段の型はこの 1 種類とし、選定済みの技術を「どう書くか」「どう検証するか」に絞る。
- 実装する agent とレビューする人に向け、命令形の規則と実行できる検証コマンドで書く。
- ラッパーは適用先のメンバー定義・実行設定にある使用環境だけに用意する。
- **共通の運用**: 役割は適用先のメンバー定義、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱い、規約の受入確認に含めない。

## 2. 位置づけと用語定義

- 技術選定と実行基盤は `tsd-index`・`tsd-<term>`、モジュール分割・境界・依存方向と横断ルールは `cpd`・`sysd-*` を正本とする。コーディング規約から参照し、実装の設計書を別に置かない。
- 規則の本文は `.github/instructions/<言語>.instructions.md` を唯一の正本とする。Copilot は `applyTo` に従って直接読み、ほかの環境ではラッパーを使う。
- 機械で強制する細則は `eslint.config.*`・`tsconfig.json`・`.editorconfig` 等を正本とする。

## 3. ファイル命名・ID規則

- 正本はリポジトリルートの `.github/instructions/<言語>.instructions.md` に置く。`<言語>` は英小文字・数字・ハイフンの言語名（`typescript`・`csharp`・`python`）または枠組み名（`vitest`・`nextjs`・`unity-csharp`）とする。
- 1 ファイルは 1 つの適用範囲（`applyTo` の glob）とする。対象ファイルと規則が異なる場合だけ分ける。範囲が重なる場合は狭い方に追加規則だけを書き、広い方と矛盾させない。
- `id` は `<言語>-instructions` とする（例: `typescript-instructions`）。
- 成果物カタログでは、グループの `base_path` を `/.github/instructions`、各成果物の `path` を `<言語>.instructions.md`、`rulebook` を `specdojo:cdr-rulebook` とする。ラッパーはカタログへ載せない。

## 4. 推奨 Frontmatter 項目

共通の必須項目・型・参照形式は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。トップレベルに Copilot の `applyTo`、`specdojo:` 配下に SpecDojo の項目を置く。

| 項目                | 必須 | 値・記述内容                                                                   |
| ------------------- | ---- | ------------------------------------------------------------------------------ |
| `applyTo`           | ○    | 適用する glob（例: `"{src,tests}/**/*.ts"`）                                   |
| `specdojo.id`       | ○    | `<言語>-instructions`                                                          |
| `specdojo.type`     | ○    | `architecture`                                                                 |
| `specdojo.rulebook` | ○    | `specdojo:cdr-rulebook`                                                        |
| `specdojo.based_on` | 推奨 | 前提とする `tsd-index`・`tsd-<term>`・`sysd-cross-cutting-policy` 等の ID 配列 |

## 5. 本文要件

見出しの順序と記入欄は template を正本とする。各章の目的と必須・任意は次のとおり。

| 章                  | 必須     | 目的・記述要件                                                                                                     |
| ------------------- | -------- | ------------------------------------------------------------------------------------------------------------------ |
| 導入文              | ○        | H1 の直後に、対象の言語・枠組みと適用範囲を 1〜2 文で書く                                                          |
| 基本方針            | ○        | 型検査の厳しさ、既存コードの書き方への追従、変更の最小化など、全規則の前提になる方針を 3〜5 項目で書く             |
| モジュールと import | ○        | モジュール方式、import の書き方、依存の向きの制約と、その制約を検査する仕組み（linter の規則名など）を書く         |
| 型                  | 条件付き | 静的型のある言語で必須。型の宣言、不明な外部入力の扱い、型の強制の制限を書く。動的型の言語は型ヒントの方針で代える |
| エラー処理          | ○        | 例外と戻り値の使い分け、エラーメッセージに含める文脈、握りつぶしの禁止を書く                                       |
| 命名                | ○        | 識別子の大文字小文字の規則、略語の扱い、真偽値の名前を書く                                                         |
| テストと検証        | ○        | 変更後に実行するコマンドを、対象（型検査・lint・単体テスト・統合テスト）と実行条件ごとに書く                       |
| 禁止事項            | ○        | 破ると被害の大きい書き方と理由を表で書く。表に書いた禁止は本文の章で繰り返さない                                   |

- `型` を省けるのは、動的型の言語で型ヒントも使わない場合に限る。省く場合は、その理由を導入文か基本方針に 1 行で書く。
- 枠組み固有の章（例: Unity のライフサイクル、Next.js のサーバーとクライアントの境界）は、上記の必須章の後ろに 1〜2 章まで追加してよい。

## 6. 記述ガイド

### 6.1. 規則の書き方

- 1 項目に 1 規則を書く。良い例は「型が不明な値は `unknown` で受けて検証する」、悪い例は「型をなるべく安全に扱う」（守ったか判定できない）。理由は判断を誤る場合だけ 1 文で添える。
- コード例は文章だけでは形が伝わらない場合に 10 行程度までとし、業務ロジックや API の詳細を含めない。
- 機械で強制する規則は、設定ファイル名・規則名と検査コマンドへの参照にまとめる。
- 1 ファイルは 300 行程度までを目安とし、超える場合は適用範囲の分割を検討する。

### 6.2. テストと検証の書き方

| 列       | 記述内容                                             | 例                                      |
| -------- | ---------------------------------------------------- | --------------------------------------- |
| コマンド | リポジトリの `package.json` などに定義済みのコマンド | `npm run typecheck`                     |
| 対象     | 何を検査するか                                       | 型検査（`src`・`tests`）                |
| 実行条件 | どの変更のときに実行するか                           | TypeScript を変更したとき（毎回）       |
| 失敗時   | 失敗したときに agent が取る行動                      | 型エラーを直す。`@ts-ignore` で隠さない |

- コマンドが未定義なら追加するか、該当する検査が無いと書く。
- 実 Git・子プロセス・外部サービスを使う重い検査は、sandbox と親 runner・CI の実行分担を書く。
- 規約の受入確認では、上位設計・設定と本文を照合し、各コマンドを指定環境で実行する。一致し、所定の検査が成功することを合格条件とする。未決の規則や未提供の検査は、論点・適用への影響・当面の扱いを該当箇所に書く。

### 6.3. 環境別のラッパーの作り方

ラッパーには適用範囲と正本への参照だけを書く。Claude Code の `<言語>` は正本とそろえる。

| 環境           | ラッパーの置き場所             | 正本の読み込ませ方                                                      | 適用範囲の宣言         |
| -------------- | ------------------------------ | ----------------------------------------------------------------------- | ---------------------- |
| GitHub Copilot | 不要                           | 正本を直接読む                                                          | 正本の `applyTo`       |
| Claude Code    | `.claude/rules/<言語>.md`      | 本文に `@../../.github/instructions/<言語>.instructions.md` を 1 行書く | Frontmatter の `paths` |
| Codex など     | リポジトリルートの `AGENTS.md` | 正本のパスと適用範囲を列挙し、該当ファイルの編集前に読むよう指示する    | `AGENTS.md` の本文     |
| Gemini CLI     | `GEMINI.md`                    | `@.github/instructions/<言語>.instructions.md` で読み込む               | `GEMINI.md` の本文     |

Claude Code のラッパーの例:

```markdown
---
paths:
  - "{src,tests}/**/*.ts"
---

# TypeScript Rules

@../../.github/instructions/typescript.instructions.md
```

`AGENTS.md` の参照節の例:

```markdown
## Coding Rules

次のファイルを編集する前に、対応する規約を読んで従う。

- `src/**/*.ts`・`tests/**/*.ts`: `.github/instructions/typescript.instructions.md`
```

- `paths` 等の適用範囲は正本の `applyTo` と同じ glob とし、変更時は同期する。使用環境ごとに対象・対象外のファイルで確認し、対象でのみ正本が読み込まれることを合格条件とする。
- 差し替えの対象は、成果物カタログの ID・パス、旧 instructions の `applyTo`、各環境のラッパーと `AGENTS.md`・`GEMINI.md` 等の参照節とする。旧正本を自動適用の対象外へ退避し、新正本の適用範囲と各参照をそろえて上記の読み込み確認を行う。旧規約が読み込まれず、新規約が指定範囲で有効になることを切替の完了条件とする。
- 未決事項・読み込み不具合・参照の切替漏れは、影響する環境・ファイル範囲と当面の扱いを記す。

### 6.4. ほかの言語・枠組みへの当てはめ

- 章立てを保ち、中身を言語の慣習に合わせる。
- 枠組みの規則（TypeScript に Next.js の規則を足す等）は固有章に置き、適用範囲が異なる場合は「ファイル命名・ID規則」に従って分ける。
- Unity の C# 等は、エンジンの命名・ライフサイクルを `命名` と固有章で扱う。検証はエディタ不要の検査（`dotnet format` 等）と起動が必要な検査に分ける。

## 7. 禁止事項

| 禁止事項                                         | 理由                                                                            |
| ------------------------------------------------ | ------------------------------------------------------------------------------- |
| 言語・ライブラリの選定理由や版を書く             | `tsd` と二重管理になり、選定の変更が規約に取り残されるため                      |
| モジュールの分割やコンポーネントの境界を設計する | 設計の段（`cpd`・`sysd-*`）の責務であり、実装の設計書を置かない方針に反するため |
| ラッパーに規則の本文を書く・正本を複製する       | 環境ごとに規則がずれ、agent ごとに異なる実装になるため                          |
| ラッパーの適用範囲を正本の `applyTo` と変える    | 環境によって規約が当たるファイルが変わるため                                    |
| 実行できない・定義されていない検証コマンドを書く | agent が検証を失敗させるか、検証を省くため                                      |
| linter で強制済みの細則を本文に再掲する          | 設定の変更に本文が取り残されるため                                              |
