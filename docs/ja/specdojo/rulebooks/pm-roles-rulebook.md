# プロジェクトロール定義 作成ルール

Project Role Definition Documentation Rulebook

`pm-roles.yaml` に、組織定義で採用した Role code を機械可読な一覧として記録するためのルールです。Schedule、RACI、member 定義が同じ責務語彙を参照でき、PO がプロジェクト固有の扱いを承認できる内容にします。

## 1. 全体方針

- ロールの採用判断と使用可能な `owner` は組織定義を正本とし、本成果物では採用結果を転記します。
- 専任者の配置と Role code の採用を分けます。専任 member がいなくても、責務語彙として使うロールは一覧に残します。
- 共通の責務や規模別の採用パターンは上位標準を参照し、プロジェクト固有の扱いだけを短く補足します。

## 2. 位置づけ

共通用語と標準ロールの定義は [[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] を正本とします。情報の更新先は次のように分けます。

| 管理先                                             | 担う情報・接続                                                                          |
| -------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `pm-organization.md`                               | 採用・未採用 Role code、使用可能な `owner`、採用理由、見直し条件の正本                  |
| `pm-roles.yaml`                                    | 採用結果の機械可読な転記先。Role code、正式名称、プロジェクト固有メモを保持する         |
| `pm-members.yaml` / `.specdojo/agent-members.yaml` | 人間 / agent の実行主体と対応ロール・兼務の割り当て                                     |
| Schedule / `pm-raci.md`                            | 組織定義の方針に従い、ロール一覧のコードをタスクの `owner` / 責任分担の列として参照する |

## 3. ファイル命名・ID規則

- 配置は `docs/ja/projects/<project-id>/030-project-management/pm-roles.yaml` を推奨します。
- ファイル名は `pm-roles.yaml`、ID は `<project-id>:pm-roles` とし、`project_id` を配置先プロジェクトに合わせます。
- 組織定義・人間のメンバー定義と同じ管理ディレクトリに置きます。共通の命名・配置規則は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従います。

## 4. 推奨メタ項目

独立 YAML のため、メタ項目は先頭のトップレベルに置きます。許可キー・必須性・型・値制約は `docs/specdojo/schemas/v1/pm-roles.schema.yaml`、メタ情報の意味は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] を正本とします。

| 項目                          | この成果物で確認する内容                                                                                        |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `id` / `project_id` / `title` | 必須。対象プロジェクトと一覧の名称を識別できること                                                              |
| `type` / `status` / `version` | 必須。成果物種別は `project`。状態は `draft` / `ready` / `deprecated` を使い分け、データの版を示すこと          |
| `rulebook`                    | 必須。準拠先として `specdojo:pm-roles-rulebook` を指定すること                                                  |
| `based_on` / `supersedes`     | 任意。採用判断の根拠となる先行成果物 / 置き換え対象を示すこと。適用範囲とライフサイクル管理はメタ情報標準に従う |

## 5. 本文要件

メタ項目以外の本文キーは次の役割を担います。YAML の骨組みは Frontmatter で宣言した template、構造・型の詳細は対応 schema を正本とします。

| キー                   | 必須・任意 | 目的・内容要件                                                                                         |
| ---------------------- | ---------- | ------------------------------------------------------------------------------------------------------ |
| `roles`                | 必須       | 採用した全 Role code の配列。`PO` を必ず含め、各コードを一意にする。組織定義で採用した集合と一致させる |
| `roles[].code`         | 必須       | 下流の `owner`、RACI、member 定義を接続する識別子                                                      |
| `roles[].name`         | 必須       | 上位標準の正式名称により、コードが表す責務を識別する                                                   |
| `roles[].project_note` | 任意       | PO の判断に必要なプロジェクト固有の扱いを短く示す。補足がなければ省略する                              |

## 6. 記述ガイド

### 6.1. メタ項目と根拠

`based_on` は、実際に確認した採用判断の根拠を指します。カタログの依存関係がある場合は、その推移閉包内の先行成果物に限定します。新規作成は `draft` とし、`ready` への昇格は人間が判断します。

| 判断点     | 良い例                                     | 悪い例                                   |
| ---------- | ------------------------------------------ | ---------------------------------------- |
| 根拠の選択 | 採用方針を確認した組織定義の ID を指定する | 同じディレクトリの文書を未確認で列挙する |
| 準拠先     | 成果物の `rulebook` に本書の ID を指定する | 計画側に記載済みとして成果物から省く     |

### 6.2. `roles` の採用範囲

組織定義の採用結果と、Schedule・RACI・member 定義の参照値を照合します。差分があれば一覧だけを追加・削除せず、採用判断と下流の使い方のどちらを改訂するかを先に確認します。記載順は上位標準の定義順を推奨します。

| 判断点       | 良い例                                       | 悪い例                                       |
| ------------ | -------------------------------------------- | -------------------------------------------- |
| 最小構成     | 最終判断を担う `PO` を含む採用集合を転記する | 実作業だけを見て `BA` と `QE` だけを列挙する |
| 兼務時の扱い | 採用済みの `PM` を管理タスクの語彙として残す | 専任者がいないという理由だけで `PM` を除く   |

### 6.3. `roles[].code` と `roles[].name`

`code` は schema の標準コード `PO`、`PM`、`BA`、`ARC`、`DEV`、`QE`、`UX`、`OPS` に限定します。`name` は人と組織の定義標準の正式名称と対応させ、担当者や職位で置き換えません。

| 判断点   | 良い例                              | 悪い例                               |
| -------- | ----------------------------------- | ------------------------------------ |
| 識別子   | `code: PM` を下流でも同じ表記で使う | `code: project-manager-agent` を使う |
| 正式名称 | `name: Project Manager`             | `name: 開発部長`                     |

### 6.4. `roles[].project_note`

プロジェクト固有の責務強調、専任化を検討する条件、公開判断上の注意を 1 行で記述します。標準の一般責務と採用理由は各正本に委ねます。未決事項は `_UNDECIDED_:`、確認・追記待ちは `_TODO_:` で識別し、判断者・判断時点を示します。

| 判断点           | 良い例                                                | 悪い例                             |
| ---------------- | ----------------------------------------------------- | ---------------------------------- |
| 判断できる条件   | 週次管理の滞留が続く場合、PO が PM の専任化を判断する | 必要に応じて管理する               |
| 固有性           | 店頭の欠品と記録漏れを受入確認で重視する              | 上位標準の品質責務を全文転記する   |
| 実行主体との分離 | 実行主体はメンバー定義で管理する                      | PM は特定の個人や agent が担当する |

### 6.5. 変更時の追従と完了判断

改訂・廃止はメタ情報標準の「文書の改訂・廃止とライフサイクル変更管理」に従います。PM は組織定義、WBS・Schedule の `owner`、RACI、両 member 定義、レビュー観点の参照を調べ、波及更新をタスク化します。ARC は参照・schema との整合、QE は機械検証と採用集合・コード重複・名称対応の照合を確認し、人間の PO が採用変更と公開可否を判断します。

| 判断点     | 良い例                                                                                   | 悪い例                                      |
| ---------- | ---------------------------------------------------------------------------------------- | ------------------------------------------- |
| 変更完了   | 採用変更と参照元の追従を確認し、未決事項は担当 Role code と転送先を付けて PJR に引き継ぐ | YAML の構文が通ったことだけで変更完了にする |
| ロール削除 | 使用中の参照値と責務の移管先を確認してから除く                                           | 専任者の離脱に合わせてコードだけを消す      |

## 7. 禁止事項

| 禁止事項                                                              | 理由                                             |
| --------------------------------------------------------------------- | ------------------------------------------------ |
| schema にないキーを追加し、採用理由や兼務割り当てを独自構造で管理する | 機械処理の互換性と正本の責任境界を損なうため     |
| 個人情報、連絡先、非公開組織情報、アクセス情報を固有メモに含める      | 公開可能なロール一覧として再利用できなくなるため |
| AI Agent に最終承認・公開可否・説明責任を持たせる                     | 人間の PO が最終判断を担う前提に反するため       |
