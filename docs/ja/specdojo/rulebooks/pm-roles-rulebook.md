# ロール定義 作成ルール

Project Role Definition Documentation Rulebook

`pm-roles.yaml` に、組織定義で採用した Role code を機械可読な一覧として記録し、Schedule、RACI、メンバー定義を同じ責務語彙で接続するためのルールです。

## 1. 全体方針

- 専任者の有無と Role code の採用を分け、責務語彙として必要なロールは一覧に残します。
- 共通の責務や規模別の採用パターンは上位標準を参照し、プロジェクト固有の扱いだけを短く補足します。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。文書の整形・lint はリポジトリの検証で扱い、業務の受入確認に含めません。

## 2. 位置づけ

共通用語と標準ロールは [[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] を正本とします。

| 管理先                                             | 担う情報・接続                                                     |
| -------------------------------------------------- | ------------------------------------------------------------------ |
| `pm-organization.md`                               | 採用・未採用コード、使用可能な `owner`、採用理由、見直し条件の正本 |
| `pm-roles.yaml`                                    | 採用コード・正式名称・固有メモの機械可読な転記先                   |
| `pm-members.yaml` / `.specdojo/agent-members.yaml` | 人間 / agent の実行主体・対応ロール・兼務                          |
| Schedule / `pm-raci.md`                            | コードを `owner` / 責任分担の列として参照                          |

## 3. ファイル命名・ID規則

- 組織定義・メンバー定義と同じ `docs/ja/projects/<project-id>/030-project-management/pm-roles.yaml` に置くことを推奨します。
- ID は `<project-id>:pm-roles`、`project_id` は配置先プロジェクトに合わせます。
- 共通規則は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従います。

## 4. 推奨メタ項目

メタ項目は YAML 先頭のトップレベルに置きます。許可キー・必須性・型・値制約は `docs/specdojo/schemas/v1/pm-roles.schema.yaml` を正本とします。

- `id` / `project_id` / `title` / `type` / `status` / `version` / `rulebook` は必須です。
- `type` は `project`、`rulebook` は `specdojo:pm-roles-rulebook`、`status` の値域は `draft` / `ready` / `deprecated` です。
- `based_on` / `supersedes` は任意です。

## 5. 本文要件

骨組みは Frontmatter の template、構造・型は対応 schema を正本とします。

| キー                   | 必須・任意 | 目的・内容要件                                                          |
| ---------------------- | ---------- | ----------------------------------------------------------------------- |
| `roles`                | 必須       | 採用全コードの配列。`PO` を含み、コードは一意。組織定義の採用集合と一致 |
| `roles[].code`         | 必須       | 下流の `owner`・RACI・メンバー定義を接続する識別子                      |
| `roles[].name`         | 必須       | 上位標準の正式名称で責務を識別                                          |
| `roles[].project_note` | 任意       | プロジェクト固有の扱い。補足がなければ省略する                          |

## 6. 記述ガイド

### 6.1. メタ項目と根拠

カタログ利用時、`based_on` は依存の推移閉包内に限定します。

| 判断点     | 良い例                                     | 悪い例                                   |
| ---------- | ------------------------------------------ | ---------------------------------------- |
| 根拠の選択 | 採用方針を確認した組織定義の ID を指定する | 同じディレクトリの文書を未確認で列挙する |

### 6.2. `roles` の採用範囲

採用集合と使用可能な `owner` の部分集合を取り違えず、記載順は上位標準の定義順を推奨します。

| 判断点       | 良い例                                       | 悪い例                                       |
| ------------ | -------------------------------------------- | -------------------------------------------- |
| 最小構成     | 最終判断を担う `PO` を含む採用集合を転記する | 実作業だけを見て `BA` と `QE` だけを列挙する |
| 兼務時の扱い | 採用済みの `PM` を管理タスクの語彙として残す | 専任者がいないという理由だけで `PM` を除く   |

### 6.3. `roles[].code` と `roles[].name`

`code` は schema の標準コード `PO`、`PM`、`BA`、`ARC`、`DEV`、`QE`、`UX`、`OPS` に限定します。`name` は人と組織の定義標準の正式名称と対応させ、担当者や職位で置き換えません。

| 判断点   | 良い例                              | 悪い例                               |
| -------- | ----------------------------------- | ------------------------------------ |
| 識別子   | `code: PM` を下流でも同じ表記で使う | `code: project-manager-agent` を使う |
| 正式名称 | `name: Project Manager`             | `name: 開発部長`                     |

### 6.4. `roles[].project_note`

責務の重点や専任化の条件など、固有の扱いを 1 行で記述します。一般責務と採用理由は各正本に委ねます。未決事項は `_UNDECIDED_:`、確認・追記待ちは `_TODO_:` で識別し、論点と採用範囲・下流参照への影響を示します。

| 判断点           | 良い例                                                | 悪い例                             |
| ---------------- | ----------------------------------------------------- | ---------------------------------- |
| 判断できる条件   | 週次管理の滞留が続く場合、PO が PM の専任化を判断する | 必要に応じて管理する               |
| 固有性           | 店頭の欠品と記録漏れを受入確認で重視する              | 上位標準の品質責務を全文転記する   |
| 実行主体との分離 | 実行主体はメンバー定義で管理する                      | PM は特定の個人や agent が担当する |

### 6.5. 変更時の追従と完了判断

受入確認は次の順で行います。

1. `pm-roles.schema.yaml` で検証します。SpecDojo 開発リポジトリでは `npm run validate:schema:file -- --schema docs/specdojo/schemas/v1/pm-roles.schema.yaml --data <対象ファイル>` の終了コード 0 を確認します。
2. schema の配列要素全体の一意性ではコード重複を検出しきれないため、コードの重複なし、組織定義の採用集合との差分なし、上位標準のコードと正式名称の組との差分なしを別途照合します。
3. WBS・Schedule の `owner`、RACI、人間・agent のメンバー定義、レビュー観点の参照を照合し、未定義コードがないことを確認します。採用判断と下流参照に差分があれば修正先を確かめ、ロール削除時は責務の移管先も確認します。

| 判断点     | 良い例                                             | 悪い例                                      |
| ---------- | -------------------------------------------------- | ------------------------------------------- |
| 変更完了   | 採用集合・名称・下流参照の照合結果がすべて一致する | YAML の構文が通ったことだけで変更完了にする |
| ロール削除 | 使用中の参照値と責務の移管先を確認してから除く     | 専任者の離脱に合わせてコードだけを消す      |

## 7. 禁止事項

- schema にないキーで採用理由や兼務割り当てを管理しません。機械処理の互換性と正本の責任境界を損なうためです。
