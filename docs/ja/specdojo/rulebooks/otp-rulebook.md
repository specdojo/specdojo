# 運用切替計画 作成ルール

Operations Transition Plan (OTP) Documentation Rules

対象別の運用切替計画 `otp-<term>` を、切替後の運用を途切れさせず、初期不具合と問合せの増加に対象固有の体制で耐えられる計画として記述する基準を定めます。

## 1. 全体方針

- **目的と適用範囲**: 運用領域・拠点・システム群・運用ドメインごとに `otp-<term>` を作成し、監視対象、窓口、当番、手順差分など対象固有の内容を定義する。
- **正本参照と責務境界**: ハイパーケア期間・SLA・優先度分類・クローズ条件の共通方針は `otp-index` を正とする。`otp-<term>` は共通方針を再掲せず、対象固有の追加と、共通方針を上書きする差分（理由つき）だけを書く。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直さない。

## 2. 位置づけ

| 成果物                    | `otp-<term>` との関係                                               |
| ------------------------- | ------------------------------------------------------------------- |
| `otp-index`               | 期間・SLA・優先度分類・クローズ条件の共通方針を受け、差分だけを書く |
| `mip-index`               | 成功条件とハイパーケア方針を受ける                                  |
| `cop-index`, `cop-<term>` | 当日の切替手順（Runbook）の完了後を引き受ける                       |
| `mtp-index`, `mtp-<term>` | リハーサルで確かめた監視・手順を前提にする                          |
| `dmd-index`, `dmd-<term>` | 旧データの保持・照会の前提を受ける                                  |

## 3. ファイル命名・ID規則

- `id` は `otp-<term>`（プロジェクト固有の成果物は `<project-id>:otp-<term>`）とし、成果物カタログの宣言と一致させる（例: `otp-hypercare`、`otp-support-desk`）。
- ファイル名は成果物カタログの `path` に従い、`otp-<term>.md` とする。`<term>` は用語集の論理名キー（英小文字 kebab-case）とし、日本語の表示名は H1 に書く。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。

- `specdojo.type` は `operations`、`specdojo.rulebook` は `specdojo:otp-rulebook` とする。宣言との不一致は `npm run lint:fm` が検出する。
- `specdojo.based_on` には、運用・移行の判断に実際に使った作成済み成果物（`otp-index`、`mip-index`、`cop-index` など）だけを記載する。

## 5. 本文要件

本文は次の 11 章をこの順序で `## <番号>. <見出し>` として置き、すべて必須とする。`otp-index` の共通方針に従う項目は、値を再掲せず「`otp-index` に従う」と書き、上書きする場合だけ値と理由を書く。

| 章                              | 目的・受入条件                                                                                                                                  |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 概要（`<term>`）                | 運用安定化の目的、対象範囲（運用領域・チーム・サービス）、対象外（当日手順の `cop-*`、共通方針の `otp-index` などへ委ねる範囲）を 1〜3 行で示す |
| 監視/アラート                   | 列は「監視対象 / 指標/閾値 / 通知先 / 初動ルール / 備考」。初動ルールに一次応答期限とエスカレーション条件を書く                                 |
| バックアップ/リストア           | 頻度・保管先・保持期間、リストアの責任者・手順（参照可）・完了基準（整合性確認）。RTO/RPO は任意                                                |
| 権限/アカウント移行             | 旧新の権限差分、移行タイミングと切替当日の扱い、主要ロールでのアクセス検証方法。緊急時の権限付与は該当時のみ                                    |
| 運用手順の変更点                | 列は「手順 / 旧 / 新 / 変更理由 / 影響 / 参照」。詳細手順は参照に置く                                                                           |
| 問合せ窓口/一次対応             | 窓口・受付時間・チャネル・一次対応範囲・エスカレーション条件。優先度分類は `otp-index` との差分だけ                                             |
| 障害対応フロー                  | 判断・連絡・復旧・報告の流れ、エスカレーション先と判断基準（重大度・影響範囲・復旧見込み）、重大障害時の指揮系統                                |
| 初期増員体制（期間・当番・SLA） | 列は「期間 / 体制（当番/時間帯） / SLA目安 / 判断者 / 備考」。期間と SLA は `otp-index` との差分だけ、当番と終了の判断者は必ず書く              |
| 旧システムの停止/参照方針       | 停止時期、参照の可否と期間、データ保持・アーカイブ方針、停止後の問合せ先（どこで何を見られるか）                                                |
| 移行完了後のクローズ条件        | 完了条件ごとの判定値（日数・件数など）と測定方法、クローズ判断者、最終報告物（振り返り・運用引継ぎ・残課題）                                    |
| 関連ドキュメント                | `otp-index` への導線と、本書で使う前後の文書。分冊が無い場合も `（本書のみ）` と書き空欄にしない                                                |

## 6. 記述ガイド

完成例は Frontmatter の `sample` で宣言された sample を参照する。

### 6.1. 共通方針との差分

- **判断基準**: 期間・SLA・優先度分類・クローズ条件の各項目が、「`otp-index` に従う」か「上書き値と理由」のどちらかで読み取れること。
- **良い例**: 「SLA は `otp-index` に従う。ただし店頭レジは営業中の停止影響が大きいため、P1 の一次応答を 15 分に短縮する」。
- **悪い例**: `otp-index` と同じ期間・SLA の表を丸ごと写す（共通方針の改訂時に片方が取り残される）。

### 6.2. 監視と障害時の判断

- **判断基準**: 閾値・期限・判断者が数値と役割で書かれ、誰が読んでもエスカレーションするかを同じに判定できること。
- **良い例**: 「API 5xx が 5 分平均 1% 超で #ops へ通知し、P1 は 30 分以内に一次応答。1 時間で復旧見込みが立たなければ運用責任者が PO へエスカレーションする」。
- **悪い例**: 「異常があれば速やかに対応し、必要に応じて上位へ相談する」。

### 6.3. クローズ条件

- **判断基準**: 各完了条件に判定値と測定方法があり、収束したかを記録から判定できること。
- **良い例**: 「P1 が 30 日連続 0 件（障害記録で確認）、問合せが直近 7 日の日次平均 5 件以下（窓口の受付記録で確認）」。
- **悪い例**: 「問合せが収束傾向で、運用が安定したらクローズする」。

### 6.4. 当番と窓口の書き方

- **判断基準**: 当番・窓口・指揮系統・責任者が、Role code や公開できるチャネル名で書かれていること。
- **良い例**: 「当番: OPS 2 名 + 業務 1 名。窓口: #support」。
- **悪い例**: 当番表に個人名と個人の電話番号を書く。

## 7. 禁止事項

| 禁止事項                                                           | 理由                                                                         |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| 監視/アラートの通知先や閾値を書かない                              | 初動が遅れ、障害影響が拡大するため                                           |
| 初期増員体制（当番・終了の判断者）を省略する                       | 初期の負荷増加に耐えられず、終了も判断できないため                           |
| 旧システムの停止時期・参照方針を曖昧にする                         | 利用者と運用の問合せ先が定まらず混乱を招くため                               |
| 判定値と測定方法のないクローズ条件を書く                           | 収束を判定できないため                                                       |
| `otp-index` の共通方針を再掲する、または理由なく矛盾させる         | 正本が割れ、改訂時に片方が取り残されるため                                   |
| 個人名・電話番号・個人のメールアドレスなど公開に適さない情報を書く | 公開・配布できず、異動時に改訂漏れが起きるため。Role code とチャネル名で書く |
