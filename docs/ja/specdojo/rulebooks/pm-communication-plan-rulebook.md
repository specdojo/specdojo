# コミュニケーション計画 作成ルール

Communication Plan Documentation Rulebook

判断・確認・共有のためのコミュニケーション機会と証跡を定義する基準です。

## 1. 全体方針

- 重要判断、当事者確認、費用・負荷の合意、公開判断の伝達漏れを防ぎます。
- 会議・報告・通知は一表へ統合し、定例会議は必須とせず、非同期確認を選べます。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。文書の整形・lint はリポジトリの検証で扱い、業務の受入確認に含めません。

## 2. 位置づけ

管理計画の判断ゲートとステークホルダー登録簿の情報要求を、報告・連絡・会議へ具体化します。作業節目や問題発生時に、伝達先・時期・判断経路・記録先を判断するための文書です。関係者の期待・懸念・影響度は登録簿、Role code はロール定義を正とします。

## 3. ファイル命名・ID規則

- 配置は `docs/ja/projects/<project-id>/030-project-management/pm-communication-plan.md` を推奨します。
- ID は `<project-id>:pm-communication-plan` とします。
- 関係者はステークホルダー ID、責任主体は採用済み Role code で記述します。

## 4. 推奨 Frontmatter 項目

共通項目はドキュメントメタ情報標準に従います。

- `type`: `project`
- `rulebook`: `specdojo:pm-communication-plan-rulebook`

## 6. 記述ガイド

### 6.1. 方針と適用範囲

対象プロジェクト、必要な合意の種類、常設会議か作業節目の非同期確認かを要約します。AI Agent は記録整理や草案の支援に留め、合意・承認・公開の判断は人間の Role code が担うことを明記します。

- 良い例: 「Issue と Pull Request の非同期確認を基本とし、対面は試用の準備と聞き取りに限る。AI Agent は草案を作り、承認と公開は `PO` が判断する」
- 悪い例: 「関係者と密に連携する」（同期・非同期の別も AI Agent の境界も読めない）

### 6.2. コミュニケーション機会

登録簿の情報要求を判断・確認・共有・相談の機会へ変換し、対象をステークホルダー ID、責任を採用済み Role code、証跡を結果の記録先で書きます。どの情報要求にも対応しない行、記録先のない行は置きません。

- 良い例: 「`STH-SHOP-OWNER` へ範囲変更の判断を Issue で依頼する。責任は `PM`、証跡は変更要求ログの変更 ID」
- 悪い例: 「店主と定例で打ち合わせる」（判断内容・責任・記録先がない）

### 6.3. エスカレーション

目的・スコープ、当事者価値、費用・負荷、品質・安全（Agent 出力の疑義を含む）、公開・権利など、判断者が変わる条件を分けます。緊急度よりも誰の判断が必要かを基準にし、一次対応が判断者へ渡す材料を書きます。

- 良い例: 「作業時間が上限を超える見込みは、`PM` が縮小案と中止案を整理し `PO` が決める」
- 悪い例: 「重大な問題は速やかに報告する」

### 6.4. 情報管理と公開

公開、限定共有、記録禁止など必要な区分を定義し、各手段で扱える情報と記録先を対応させます。判断・課題・リスク・変更要求は課題ログ・リスク登録簿・変更要求ログなどの管理記録へ分けて転記し、口頭の決定を転記する担当を Role code で示します。

- 良い例: 「口頭の決定は `PM` が課題ログへ転記し、変更を伴うものは変更要求ログへ起票する」
- 悪い例: 「決定事項は記録する」（記録先も転記する担当もない）

### 6.5. 見直し条件と未決事項

- ステークホルダー、判断ゲート、公開方針、連絡手段が変わった場合に見直します。
- 連絡時期・判断経路・共有手段を変えたときは、追従対象（管理計画の判断ゲート、Schedule の確認・承認タスク、エスカレーションの判断者、チャネル設定）と、それぞれを更新する Role code を示し、連絡運用へ反映された証跡の記録先を書きます。
- 未決事項は `_UNDECIDED_` を付し、論点、伝達先・時期・手段への影響、決定時期と判断者を示します。

## 7. 禁止事項

| 禁止事項                                         | 理由                                   |
| ------------------------------------------------ | -------------------------------------- |
| ステークホルダー登録簿やRole code一覧を再掲する  | 正本が分散するため                     |
| 会議体、報告、チャネルへ同じ情報を重複記載する   | 更新漏れと過剰な運用を招くため         |
| 目的や証跡のない定例会議を必須にする             | コミュニケーション自体が負荷になるため |
| エスカレーション条件を「必要に応じて」とだけ書く | 判断時点が不明になるため               |
