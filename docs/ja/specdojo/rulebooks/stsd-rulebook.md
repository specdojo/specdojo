# ステータス定義（Status Definition: STSD）作成ルール

Status Definition Documentation Rulebook

業務上の一つの対象が取り得る状態と状態間の遷移を、一文書で定義するためのルールです。

## 1. 全体方針

- 一文書は一つの対象（エンティティまたは業務概念）だけを扱います。
- 状態一覧を状態の意味・成立条件の正本、「状態遷移」の遷移表を遷移の正本とし、同じ文書で管理します。状態遷移図は遷移表の全行の投影であり、不一致時は遷移表へ合わせて両者を同じ変更で更新します。
- スコープは現行を既定とし、同じ対象の TO-BE 文書と並ぶ場合だけ AS-IS / TO-BE を明記して文書を分けます。両者を同じ図に混在させません。
- 状態値や記録形式に schema・型定義・リファレンスがある場合は、構文・構造の詳細を正本に委ね、STSD には状態を識別する値と業務上の判定に必要な意味・条件だけを残します。
- 共通の運用: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直しません。文書の整形・lint はリポジトリの検証で扱い、成果物の完成判定に含めません。

## 2. 位置づけと用語定義

| 用語       | 定義                                                                                |
| ---------- | ----------------------------------------------------------------------------------- |
| 対象       | 状態を持つ一つの業務上のエンティティまたは概念                                      |
| 状態       | 対象について、意味と成立条件を業務上判定できる時点の区分                            |
| 遷移       | イベントと条件により、対象が遷移元の状態から遷移先の状態へ変わること                |
| 初期・終了 | Mermaid の `[*]` で表すライフサイクルの開始点・終了点。業務上の状態一覧には含めない |

## 3. ファイル命名・ID規則

- ファイル名は `stsd-<term>.md`、成果物 ID は拡張子を除いた `stsd-<term>` とします。
- `<term>` は対象を表す英小文字・数字・ハイフンのスラッグにし、同じ対象の TO-BE 文書と並ぶ場合だけ AS-IS / TO-BE を識別するスコープを含めます。
- 一つの対象・スコープに STSD は一つとし、同じライフサイクルの例外状態も同じ文書へ記載します。
- 状態名は業務で使う日本語の名詞句にします。外部参照に使う状態値は `lower-kebab-case` で文書内で一意にし、一つの値を複数の状態へ割り当てません（コードを持たない `-` は対象外）。
- 遷移 ID は文書内で一意な `T-<nn>` 形式とし、図のラベル・遷移表・レビュー指摘で同じ ID を使います。
- 初回の確定前（`status: draft`）は、図と表の順に `T-01` から文書全体の通し番号で振り直してかまいません。図のラベル・遷移表・本文中の参照を同じ変更で更新し、旧 ID・新 ID の対応は STSD 本文ではなく作業の記録へ残します。
- 確定（`status: ready`）後は既存 ID を振り直さず、削除した ID も再利用しません。新規遷移には未使用の ID を割り当てます。

## 4. 推奨 Frontmatter 項目

共通の項目と値は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。STSD 固有の指定は次のとおりです。

- `id` の文書名部分は「ファイル命名・ID規則」に従います。
- `type` は `data`、`rulebook` は `specdojo:stsd-rulebook` とします。
- `based_on` には、作成根拠にした対象定義・業務データ辞書などのうち、成果物カタログの `depends_on` の推移閉包に含まれる先行成果物だけを記載します。
- 対象名や文書タイトルの独自メタ項目は追加せず、H1 と「適用範囲」で示します。

## 5. 本文要件

見出し順と表の骨組みは template を正本とし、本章では満たすべき内容と必須性を定めます。構造・必須項目・禁止事項が recipe / sample / template と異なる場合は本 rulebook を優先します。

| 内容領域         | 必須     | 判断できること                                                                                                             |
| ---------------- | -------- | -------------------------------------------------------------------------------------------------------------------------- |
| 主題・目的・境界 | ○        | 一つの対象の何を状態で管理し、その状態でどの業務判断を行うか。状態変更を起こす業務範囲と対象外、終了または継続管理の到達点 |
| 現在状態の根拠   | ○        | 状態の正本となる管理場所、現在状態を一意に決める規則、互換の扱い                                                           |
| 状態と遷移の定義 | ○        | 各状態の意味・成立条件・管理場所と、初期・終了または継続状態を含む全遷移                                                   |
| 未決事項         | 条件付き | 未決の例外状態・遷移・用語・責任境界の論点と影響。未決事項がある場合だけ記載する                                           |

状態自体を持たない対象には STSD を作成しません。

## 6. 記述ガイド

### 6.1. 頭書きと目的

- 頭書きは H1 直下に見出しなしで置き、何の状態と遷移を定義するかを 1〜2 行で示します。
- 「目的」には、状態で対象の何を管理し、その状態でどの業務判断を行うかを 1〜3 文で示します。文書の読み手や使い方は書かず、境界は「適用範囲」、判定規則は「状態の判定」へ置きます。

| 判断の基準                       | 良い例                                                         | 悪い例                               |
| -------------------------------- | -------------------------------------------------------------- | ------------------------------------ |
| 頭書きで主題を識別できる         | タスク実行の状態と状態遷移を定義する                           | 状態について説明する                 |
| 目的が利用者の業務判断に結び付く | 実行の進み具合を管理し、担当者が着手・引き継ぎの要否を判断する | 実装担当とテスト担当が読むために作る |

### 6.2. 適用範囲

- 対象を一つの業務用語で特定し、状態変更を起こす業務の開始と対象外の境界を示します。
- 業務上の到達点を示します。終了点を置かない場合は、管理を続ける理由と、出力遷移のない継続状態を示します。

| 判断の基準                     | 良い例                                                                     | 悪い例                         |
| ------------------------------ | -------------------------------------------------------------------------- | ------------------------------ |
| 対象内外の境界を区別できる     | 商品受領から販売・返品までを扱い、納品前の発注は対象外とする               | 商品に関係する業務全般         |
| 終了点の要否を業務で説明できる | 完了後も差し戻しを受け付け、中止後も補足記録を更新するため終了点を置かない | 記録を保存するので終了点は不要 |

### 6.3. 状態の判定

- 現在状態を確認する正本の管理場所を示し、履歴・集約記録を併用する場合は正本か派生物かを区別します。
- 現在状態を一意に判定する規則として、イベント再生の順序と初期値、導出状態の導出条件と再判定の契機、複数の成立条件を満たす場合の優先関係を該当する範囲で定めます。
- 旧状態値・旧イベント、未設定・欠損記録の読み取りや移行など互換の扱いを、過去の記録を読む規則と現在発行する遷移に分けて示します。不要な場合はその旨を明記します。

| 判断の基準                             | 良い例                                                             | 悪い例                                   |
| -------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------- |
| 同じ記録から同じ現在状態に至る         | 個票の状態欄を正本とし、一覧はその派生物として再生成する           | 個票か一覧の新しそうな方を見る           |
| 過去の読み取りと現在の操作を区別できる | 旧イベントは読み取り時だけ読み替え、新規記録には現行イベントを使う | 古い記録もあるのでどちらの操作も許可する |

### 6.4. 状態一覧

| 列名     | 記述ルール                                                            |
| -------- | --------------------------------------------------------------------- |
| 値       | 外部参照に使う安定した `lower-kebab-case`。コードを持たない場合は `-` |
| 状態名   | 対象が置かれた状態を表す、日本語の名詞句                              |
| 通称     | 現場で異なる呼び方を使う場合の呼称。ない場合は `-`                    |
| 意味     | その状態に含む範囲と、含まない範囲が分かる説明                        |
| 成立条件 | いつその状態と判定できるかを、確認可能な事実で記述                    |
| 管理場所 | 現在状態を確認する正本の帳簿、台帳、記録、または概念上の保管先        |

- `値` の形式と一意性は「ファイル命名・ID規則」に従い、`-` は複数行で使用できます。
- 終了条件は遷移表へ置き、成立条件と重複させません。
- 同じ状態を管理場所ごとに別名で複製せず、意味または成立条件が異なる場合だけ別状態とします。
- 状態が一つしかない対象は、状態変化がない根拠を記載し、図では初期点からその状態への遷移を示します。

| 判断の基準                             | 良い例                                                   | 悪い例                   |
| -------------------------------------- | -------------------------------------------------------- | ------------------------ |
| 意味と成立条件から隣接状態と区別できる | 販売可能: 検品合格を記録し、在庫を更新して売場へ配置済み | 販売可能: 販売できる状態 |
| 現在状態の根拠を確認できる             | 管理場所を在庫記録とし、正本の対象行を確認する           | 管理場所はシステム       |

### 6.5. 状態遷移

- 図と遷移表を同じ「状態遷移」章へ置き、各図のすぐ下にその図の遷移表を置きます。図を分けた場合も図と表を一組として繰り返し、分割理由・遷移 ID の範囲・共有状態の置き方は stsd-mermaid-rulebook の「図の分割」に従います。
- 複数の遷移に共通する条件や補足は、適用する遷移 ID を示して章の冒頭などへ集約し、表から参照します。
- 図の矢印・表の行・分割図の共有状態の宣言は対応に必要なため削らず、冗長さは図表をなぞる本文から削ります。

| 判断の基準                             | 良い例                                                       | 悪い例                                 |
| -------------------------------------- | ------------------------------------------------------------ | -------------------------------------- |
| 図から直下の表で条件・補足を確認できる | 同じ遷移 ID で図の矢印と表の一行を対応付ける                 | 図の後に同じ経路を文章でも順に説明する |
| 分割しても経路を接続できる             | 共有状態の表示名と内部 ID をそろえて各図で宣言する           | 重複を避けるため後続図の共有状態を削る |
| 共通条件の適用範囲を判断できる         | 対象の遷移 ID を挙げて操作権限を一度定義し、各行から参照する | 操作権限の説明全文を各行へ繰り返す     |

#### 6.5.1. 図

- Mermaid の `stateDiagram-v2` を使い、表示名・`state_id`・遷移ラベル・図の分割の記法は [[specdojo:stsd-mermaid-rulebook|STSD の状態遷移図を Mermaid で記述するルール]] に委ねます。
- 同じ遷移元から同じイベントで分岐する場合は、遷移先ごとの矢印へ同じイベントと相互排他的な条件を記載します。異なるイベントで出る遷移は分岐として扱いません。
- 初期点は必ず `[*]` で示し、初期点・終了点を状態一覧へ追加しません。
- 終了点は、ライフサイクルを閉じる業務イベントと条件が定義されている場合だけ `[*]` で示します。完了・中止後も差し戻しや確認・記録更新のために状態管理が続く場合は置かず、省略理由を「適用範囲」に記載します。記録の保存だけでは継続とみなさず、終了点のためにイベントを作りません。
- 差し戻せる完了には戻りの遷移を示し、確認・記録更新だけを続ける中止は出力遷移のない継続状態とします。

#### 6.5.2. 遷移表

| 列名     | 記述ルール                                                        |
| -------- | ----------------------------------------------------------------- |
| 遷移 ID  | 文書内で一意な `T-<nn>`                                           |
| 遷移元   | 状態一覧の状態名。初期点の場合は `開始`                           |
| 遷移先   | 状態一覧の状態名。終了点の場合は `終了`                           |
| イベント | 状態変更の契機となる業務上の出来事または操作                      |
| 条件     | 遷移成立を yes / no で判定できる条件。無条件なら `イベント発生時` |
| 補足     | 判断者、例外時の扱い、記録する証跡など、図だけでは伝わらない事項  |

- 直上の図にある全遷移を一行ずつ記載します。分割時も一つの遷移を複数の表へ重複させません。
- 自己遷移は、状態の意味を変えずに記録更新や再確認を行う業務上の必要がある場合だけ使用します。

### 6.6. 今後の検討メモ

- 調査で確定できる不足は _TODO_:、意思決定待ちは _UNDECIDED_:、仮置きする前提は _ASSUMPTION_: とし、論点・影響する状態または遷移 ID・決まるまでの扱いを記載します。
- 未決事項がない場合は章を省略します。

| 判断の基準                     | 良い例                                                                       | 悪い例             |
| ------------------------------ | ---------------------------------------------------------------------------- | ------------------ |
| 未決の影響と当面の扱いが分かる | _UNDECIDED_: `T-07` の再開に承認を要するか。決まるまで再開は承認後だけとする | 再開は今後検討する |

### 6.7. 完成判定

- 各 `値` から状態を一つに特定できます。
- 「状態の判定」の正本・判定規則・互換の扱いと「状態一覧」の成立条件から、現在状態を一意に判定できます。
- 各図の全遷移が直下の遷移表へ一度ずつ対応して内容が一致し、文書全体で遷移の重複や欠落がありません。
- 状態一覧と図の状態の対応・到達性が stsd-mermaid-rulebook の「完成判定」を満たし、例外系の全遷移について終了、正常系への復帰、または人間の判断への引き渡しを説明できます。
- 状態名、通称、イベント名が用語集・業務データ辞書・関連 CDFD と矛盾していません。

### 6.8. 改訂時の影響確認

- 状態値・状態名・遷移 ID を変えるときは、参照する業務データ辞書・CDFD・業務ルール、型・schema、状態遷移テスト・受入条件の追従を確認します。

## 7. 禁止事項

- 同じ対象の状態一覧と状態遷移図を別文書へ分けません。
- 状態名に `is_active`、`FLAG_01`、数値だけのコードなど、実装上の識別子を使いません。
- 物理テーブル、画面ページ、API 呼び出し、関数実行を業務状態または業務イベントとしてそのまま記載しません。
- 遷移ラベルから遷移 ID やイベントを省略したり、条件を実装式だけで表したりしません。
- 直上の図にない遷移を遷移表へ追加しません。
- 「状態遷移」の図と表を別章へ分けたり、分割図の表を一括して後置したりしません。
- CDFD、業務データ辞書、用語集に同じ状態一覧や遷移表を複製しません。
