# 非機能要件インデックス 作成ルール

Non-Functional Requirements Index Documentation Rules

非機能要件（NFR）を8カテゴリ（信頼性、可用性、保守性、完全性、機密性・安全性、性能、運用、操作性）の分冊で管理する入口 `nfr-index` の作成ルールを定めます。

## 1. 全体方針

- **目的と適用範囲**: `nfr-index` を対象とし、分冊と検証・運用・判断記録への導線を一か所に集めます。
- **責務境界**: 要求・合否基準・検証方法の正本は各 `nfr-<category>` 分冊とし、`nfr-index` は詳細要求を再掲しません。
- **記載レベル**: 分冊の要求は合否判定できる状態を前提とし、実装詳細は書きません。
- **変更の起点**: 分冊の追加・統廃合では `nfr-index` を最初に更新します。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直しません。文書の整形・lint はリポジトリの検証で扱い、成果物の業務の検証に含めません。

## 2. 位置づけ

- `nfr-<category>`: カテゴリ別の NFR 本文（分冊）。
- `sac-*` / `stc-*`: NFR の合否を検証する受入条件・試験仕様。
- `opd-*` / `opr-*`: 運用方針・運用手順。
- `dec-*`: 例外基準や判断記録。

## 3. ファイル命名・ID規則

- 文書 ID は `nfr-index`、ファイル名は `nfr-index.md` とします。
- 分冊の ID はカテゴリ名を用い（例: `nfr-reliability`）、1分冊 = 1カテゴリを原則とします。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- `specdojo.type` は `requirement`、`specdojo.rulebook` は `specdojo:nfr-index-rulebook` とします。
- `specdojo.based_on` には NFR 策定の根拠（業務仕様・アーキテクチャ方針・運用方針）だけを列挙します。

## 5. 本文要件

本文は次の見出しを順序固定で配置します。

| 番号 | 見出し                                      | 必須 | 受入条件                                            |
| ---- | ------------------------------------------- | ---- | --------------------------------------------------- |
| 1    | 概要（対象範囲・管理方針）                  | ○    | 分冊管理の目的と要求本文の正本が分かる              |
| 2    | カテゴリ一覧（8カテゴリ）                   | ○    | 8カテゴリすべてに目的と代表指標がある               |
| 3    | 分冊ドキュメント一覧（ID/参照先/Owner）     | ○    | 各カテゴリの分冊 ID・参照先・更新責任が一意に辿れる |
| 4    | 変更の入口（追加・統廃合・改定）            | ○    | 分冊の追加・削除・統合・分割の手順と完了条件がある  |
| 5    | 関連ドキュメント導線（SAC/STC/OPD/OPR/DEC） | ○    | カテゴリごとの検証・運用・判断記録の導線がある      |

## 6. 記述ガイド

### 6.1. 概要（対象範囲・管理方針）

- 分冊管理の目的（探索性、保守性、レビュー効率）を 1〜3段落で示し、要求本文は分冊が正本であることを明示します。

### 6.2. カテゴリ一覧（8カテゴリ）

- 8カテゴリを固定で列挙し、カテゴリごとに「目的」と「代表指標」を短く示します。
- 良い例: 「可用性 ／ 利用可能性の維持 ／ 稼働率、RTO/RPO」。悪い例: 「可用性 ／ 止まらないこと ／ 高いこと」（指標が測れない）。

### 6.3. 分冊ドキュメント一覧

- 分冊 ID・参照先・更新責任（Role code）・備考を表で記載し、参照先はリポジトリ相対パスか ID で一意に辿れる形にします。

### 6.4. 変更の入口

- 追加・削除・統合・分割ごとに、更新する文書（本書のカテゴリ一覧・分冊一覧、関連する `sac-*` / `stc-*`）を示します。
- 完了条件は、旧分冊の要求が新分冊へ重複なく移ったこと、検証導線が新分冊を指すことで判定します。

### 6.5. 関連ドキュメント導線

- カテゴリごとに検証（SAC/STC）・運用（OPD/OPR）・判断記録（DEC）への導線を置きます。
- 導線がない場合は `（なし）` を明示します。

## 7. 禁止事項

| 禁止事項                                 | 理由                             |
| ---------------------------------------- | -------------------------------- |
| `nfr-index` にカテゴリ詳細要求を記述する | 分冊との重複・不整合を招くため   |
| 8カテゴリ定義を欠落させる                | 網羅性と比較可能性が低下するため |
| 参照先が不明なIDだけを並べる             | 追跡不能になるため               |
| 合否判定不可の曖昧表現を残す             | 要件として検証不能になるため     |

## 8. サンプル

注: 形式の輪郭を示す最小例です。生成する `nfr-index` では `## 1.` から始まります。

```markdown
---
specdojo:
  id: nfr-index
  type: requirement
  status: draft
  rulebook: specdojo:nfr-index-rulebook
  based_on: []
---

# 非機能要件インデックス

## 1. 概要（対象範囲・管理方針）

本書は非機能要件をカテゴリ別に分冊管理するための入口である。要求本文の正本は各分冊に置く。

## 2. カテゴリ一覧（8カテゴリ）

| カテゴリ | 目的                 | 代表指標         |
| -------- | -------------------- | ---------------- |
| 信頼性   | 障害抑止と誤動作防止 | 障害件数、失敗率 |
| 性能     | 応答性・処理能力     | P95/P99、RPS     |

（8カテゴリすべてを記載する）

## 3. 分冊ドキュメント一覧（ID/参照先/Owner）

| ID              | 参照先               | Owner  | 備考       |
| --------------- | -------------------- | ------ | ---------- |
| nfr-reliability | `nfr-reliability.md` | QA/DEV | 信頼性要件 |
| nfr-performance | `nfr-performance.md` | DEV    | 性能要件   |

（8カテゴリすべてを記載する）

## 4. 変更の入口（追加・統廃合・改定）

- 統合時は2章・3章を更新し、旧分冊の要求を新分冊へ重複なく移し、`sac-*` / `stc-*` の参照先を付け替える。

## 5. 関連ドキュメント導線（SAC/STC/OPD/OPR/DEC）

| カテゴリ | 検証              | 運用          | 判断記録 |
| -------- | ----------------- | ------------- | -------- |
| 性能     | `sac-performance` | `opr-monitor` | （なし） |
```
