# 概念データストア定義 作成ルール

Conceptual Data Stores Definition (CDSD) Documentation Rules

業務で継続的に保持・参照する情報の集合について、管理単位・用途・更新責務を定義する基準を定めます。
BA が業務上の境界を合意し、ARC・DEV が設計へ接続し、QE が整合性確認の対象を識別できる一覧を作ります。

## 1. 全体方針

- **適用範囲**: 業務分析・要求定義から設計への引き渡しで利用する `cdsd-*.md` を対象とします。帳簿・台帳に加え、定義、実行記録、派生ビュー、人が確定する報告記録も業務上の管理対象なら含めます。
- **入力**: 成果物カタログの対象範囲・依存・受入条件、上位の目的、関連する BDD・プロセス仕様を確認します。主要な管理単位の採否と用途を、それらの根拠に対応付けます。
- **記載レベル**: 一覧の各行は独立した管理単位とします。ファイルが複数あることだけで分割せず、正本区分、粒度、更新責務が異なる場合は区別します。
- **対象外**: 全項目の型・許容値、保存形式、コマンド構文、状態遷移、復旧操作の詳細は、それぞれの schema・型定義・リファレンス・状態定義・運用手順を参照します。概念上の管理境界を判断するための説明だけを残します。

## 2. 位置づけと用語定義

- **概念データストア**: 業務上ひとまとまりとして保持・参照する情報です。物理的な保管場所や DB テーブルと一対一とは限りません。
- **隣接仕様との分担**: BDD は項目の業務的意味、CCD は概念間の関連、プロセス仕様・CDFD は情報の生成・利用の流れ、保管場所一覧は物理的・論理的な場所を扱います。CDSD はこれらを管理単位と更新責務でつなぎます。
- **共通事項の正本**: メタ情報・改訂と廃止は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]]、配置は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従います。共通方針は上位文書を参照し、各 CDSD へ再掲しません。

| Role code | 作成・確認・利用の責務                                                                                                               |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| BA        | 主作成者・業務確認者として、対象者の課題、管理境界、名称、用途と上位根拠の対応を整理する。業務担当者による確認が必要な箇所を特定する |
| ARC       | 正本・派生物の区別、生成元、外部依存と後続設計への引き渡しを確認する                                                                 |
| DEV       | 保存単位と正本の参照先、schema・型・生成処理への変更影響を確認する                                                                   |
| QE        | 対象の網羅、必須情報、検証対象と合否条件を照合する                                                                                   |
| PM        | 未決事項の担当・依存順・判断時期を計画へ接続し、課題・リスク等を報告する                                                             |
| OPS       | 公開前確認、継続更新・再生成・問い合わせの導線を確認する                                                                             |
| PO        | 管理境界と用途を最終合意し、公開範囲・確定・置き換えを人間として承認する                                                             |

業務担当者や「運用担当」などの呼称を使う場合は、適用先の組織定義の Role code に対応付けます。実担当者・兼務は組織・メンバー定義を参照します。

## 3. ファイル命名・ID規則

- ファイル名は `cdsd-<term>.md` とし、`<term>` は対象業務領域を表す kebab-case とします。プロセス群など、読者が管理境界を合意できる単位でまとめます。
- プロジェクト成果物の文書 ID は `<project-id>:cdsd-<term>` とします。例は `prj-0001:cdsd-execution` です。文書内のデータストアは名称で一意に対応付け、同名で異なる管理単位を混在させません。
- 配置はカタログの `base_path` と成果物の `path` から解決します。業務仕様のデータモデル配下を基本とし、既存カタログのパスを推測で変更しません。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型はドキュメントメタ情報標準と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とし、メタ情報は `specdojo:` 配下に置きます。

- `type` は `data`、`rulebook` は `specdojo:cdsd-rulebook` とします。表示名は対象領域が分かる H1 に置き、`title` を併記する場合は H1 と意味を一致させます。
- `based_on` には実際に読んで直接の根拠とした作成済み文書を記録します。カタログがある場合は `depends_on` の推移閉包内に限定します。単なる関連先や未作成文書を追加しません。
- `status` の確定判断、`supersedes` による置き換えは共通規約に従います。agent は `draft` のまま編集し、人間の PO による承認へ渡します。

## 5. 本文要件

次の構成を標準とし、見出しは `## 1.` から連番、小節も階層ごとの連番にします。表はヘッダー・区切り行・データ行を連続させ、途中に空行を入れません。

| 章                   | 必須     | 内容・受入条件                                                                                                                                       |
| -------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 概要                 | 必須     | 対象者、利用場面、業務課題と放置時の影響、期待する判断結果、対象・対象外とその根拠を示す。上位文書で説明済みの内容は参照する                         |
| 概念データストア一覧 | 必須     | 対象の全管理単位を標準6列で定義し、カタログの対象範囲と照合できること                                                                                |
| 正本区分と更新責務   | 必須     | 一覧の全行について、正本か派生・参照情報か、生成元、更新契機、利用制約、担当 Role code を識別できること                                              |
| 関連仕様と検証       | 必須     | 各管理単位から、根拠となる辞書・プロセス・制約の正本、検証対象と確認手順を辿れること                                                                 |
| 確認事項と変更影響   | 条件付き | 未決・欠落・矛盾、または改訂・廃止がある場合に、影響、担当、判断者、期限または判断時期、次アクションと追跡先を示す。なければ「なし」または省略とする |

### 5.1. 一覧の標準列

列順は次の順に固定します。関連仕様への参照や補足は別表・本文に置けますが、データストア名で対応付けます。

| 列名           | 内容・判断条件                                                                                |
| -------------- | --------------------------------------------------------------------------------------------- |
| データストア名 | BDD・用語集と対応する業務名称。日本語の単数形を基本とし、慣用名・正式名称は定義先を示して使う |
| 対応プロセス   | 生成・更新・利用する業務プロセス。複数なら「、」で区切る                                      |
| 主な内容       | 管理対象が分かる代表情報を名詞句で示す。全フィールドを列挙しない                              |
| 更新タイミング | 発生イベントまたは周期と、その適用条件を示す                                                  |
| 粒度           | 最小記録単位と識別の文脈。履歴と集計など複数の単位を混同しない                                |
| 主な用途       | 誰のどの業務判断・確認に使うかを示す。概要の目的に対応すること                                |

更新タイミングは「イベント（会計確定時）」「日次（閉店時）」「月次（締め）」「年次（決算）」「随時（定義変更時）」のように契機を具体化します。複数契機は併記でき、業種固有のイベントをこの例に限定しません。

### 5.2. 正本区分と更新責務

- 正本は何を確定する情報かを示します。派生・参照情報は生成元の文書 ID または管理単位、再生成の契機と基準時点を示します。人が確定する報告記録は、その判断の範囲を明示します。
- 更新担当と確認担当を Role code で示し、参照だけのプロセスと更新するプロセスを区別します。直接編集・再生成・追記などの業務上の制約は、その理由または正本への参照を添えます。
- 保存・引き渡し単位が境界判断に必要なら、対象ファイル群や運用手順への参照を付けます。詳細なパス規則や実装内部構造は転記しません。更新失敗・不整合時の問い合わせ先と訂正・復旧手順の参照も対応付けます。

### 5.3. 関連仕様への追跡

- 関連 BDD・CCD・用語集・プロセス仕様・CDFD、該当する保管場所一覧（SLL）を文書 ID で特定します。名称・内容・粒度・入出力・管理場所のうち何を照合するかを対応付けます。関連文書がない種別を形式的に作成する必要はありません。
- schema・型・実装・リファレンスが正本の場合は、BDD 等の参照先を辿れるようにし、外部システムを含む入力元・出力先と更新制約を確認します。構造の詳細を CDSD 独自の定義として複製しません。
- 既存文書は project 修飾 ID のリンクで示します。未作成文書は ID をコード表記し、欠ける根拠、現時点で判断できる範囲、解消担当を「確認事項と変更影響」に残します。依存未整備を対象行の黙示的な除外理由にしません。

### 5.4. 検証と受入条件

BA が対象行を作成し、ARC・DEV が正本区分と依存を確認した後に QE が照合します。各データストアを作成・確認の作業単位とし、PM は依存順と確認時期を計画に記録します。

| 確認                  | 合格条件・証跡                                                                                                                            |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| BA: 業務範囲と用途    | カタログの対象と一覧の対応に欠落・重複がなく、標準6列が埋まり、用途が概要の課題・期待価値へつながる                                       |
| ARC・DEV: 境界と依存  | 一覧と更新責務の対象集合が一致し、正本・生成元・担当・制約と、参照する BDD 等の定義が矛盾しない                                           |
| QE: 整形・メタ情報    | リポジトリに導入された Prettier・Markdown lint・Frontmatter schema 検査で対象ファイルのエラーがない。コマンド・対象・結果を実行記録へ残す |
| QE・OPS: データと運用 | 管理単位ごとに検証対象、適用 schema または手動確認基準、確認コマンド・手順、期待結果、失敗時の対応を参照できる                            |

本リポジトリでは `npx prettier --write <対象.md>`、`npm run lint:md`、`npm run lint:fm` を使います。成功は終了コード 0 と対象の違反なしです。他のリポジトリでは導入済みの対応コマンドを用い、pipeline で親検証に設定されたものは runner の結果を証跡とします。

CDSD 本文は標準6列・行の網羅・参照対応を手動照合します。参照先データの schema 検証はその正本で定める手順を用い、CDSD の Frontmatter 検証とは分けます。検証対象・期待結果の詳細は正本を参照し、実行記録に対象と結果を残します。失敗時は担当へ差し戻して修正・再確認し、未解決を合格として扱いません。

### 5.5. 未決事項・変更・公開判断

- BA は確認不足・欠落・矛盾とその業務影響を整理し、PM へ報告します。計画済み作業の進捗は Schedule で追跡し、既発問題は課題、未発生の懸念はリスク、承認が必要な差分は変更要求、採用方針と理由は決定記録の PJR 転記候補として分けます。担当 Role code、報告先・判断者、判断時期、次アクション、転記先レコードを記録します。
- 改訂・廃止ではドキュメントメタ情報標準の変更管理に従います。BA は名称・用途・粒度の変更を BDD・CCD・用語集・プロセス仕様・SLL と照合し、ARC・DEV は schema・型・生成処理・コマンドへの影響を特定します。QE は参照元の受入条件と既存成果物を再確認し、PM は非互換変更の移行対象・順序・期限・担当を追跡します。
- 本 rulebook の変更時は、Frontmatter で宣言する関連 Kata と適用済み CDSD を照合し、本文要件・標準列・禁止事項の差分と同期対象を実行記録に残します。段階的な整備では未同期箇所・担当・次の作業を明記し、矛盾時は rulebook を正とします。要否判断を見直す場合も BA・ARC が理由と影響を提示し、人間の PO が合意します。
- 公開・`ready` 化の前に、BA・ARC・QE の受入確認と OPS の公開前確認を完了します。公開対象と閲覧範囲、個人情報・非公開情報の有無、未決事項・未解決指摘と影響を提示し、人間の PO が承認・保留・差し戻しを判断します。本 rulebook 自体の確定には関連 Kata の同期確認も必要です。公開後の問い合わせは BA、再生成・運用上の問題は OPS が受け、仕様変更が必要なら PM へつなぎます。

## 6. 記述ガイド

章ごとの判断は次の基準で行います。共通事項は上位文書を正本とし、良い例の短文は判断点だけを示すものです。

| 対象章               | 判断の基準                                               | 良い例                                                                                                                   | 悪い例                                               |
| -------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| 概要                 | 対象者・放置時の影響・期待する判断と、境界の理由が分かる | 「担当交代時の更新漏れを防ぐため、BA が販売記録の更新責務を確認する。在庫は別領域の定義を参照する」                      | 「データを一覧にする」のみ、または対象を根拠なく省く |
| 概念データストア一覧 | 代表情報・更新契機・最小単位・用途を区別できる           | 「売上台帳／販売、会計／販売日・金額／イベント（会計確定時）／販売取引毎／店主の売上確認」                               | 「SalesTbl／販売／全項目／随時／データ毎／管理」     |
| 正本区分と更新責務   | 更新元と参照先、担当と許可される扱いが分かる             | 「売上集計は売上台帳から日次再生成。OPS が生成し、BA が元帳との一致を確認。集計の直接訂正はしない」                      | 「システムが適切に更新する」                         |
| 関連仕様と検証       | 参照先・比較内容・合否を辿れる                           | 「売上台帳に対応する BDD の文書 ID と検証手順を示し、取引粒度の一致と検証エラー0件を確認する」                           | 「BDD 等と整合すること」のみ                         |
| 確認事項と変更影響   | 誰がいつ何を決め、その結果どこを直すかが分かる           | 「粒度変更による集計影響を BA が課題化し PM へ報告。次回レビューで PO が範囲を判断し、ARC が生成元との対応を再確認する」 | 「詳細は後日」、未決のまま確定する                   |

業務名称と正式な識別子の対応が必要なら、名称の初出で短く補足するか正本を参照します。物理名を独立して示す必要がある場合だけ任意の `physicalName` 列を標準6列の後ろに追加し、既存の正本の表記を使います。CDSD のために綴りや命名規則を変換しません。

## 7. 禁止事項

- 略語・物理名だけで管理対象を表し、業務上の意味や定義先を示さないこと。
- カタログの対象を未記載のまま除外したり、未決の粒度・更新責務を確定済みとして扱ったりすること。
- 全項目・型・許容値・状態遷移・コマンド構文・詳細パスを正本から複製し、二重管理すること。
- 派生・参照情報を正本と混同し、生成元や更新担当の不明なまま後続設計へ渡すこと。
- 表を空行で分断すること、存在しない文書へのリンクや未確認の検証成功を記載すること。
- agent に公開可否・`ready` 昇格・置き換えの最終承認を委ねること。
