# 非機能要件 / 性能 作成ルール

Non-Functional Requirements Performance Documentation Rules

本書は、非機能要件のうち性能（応答性・処理能力・資源効率）を定義する `nfr-performance` の作成ルールを定める。`nfr-performance` は、平常時・ピーク時の負荷条件で処理がどこまでの応答時間と処理量を満たすべきかを判断し、受入・試験・運用監視の判定基準を揃えるための文書である。

## 1. 全体方針

- 性能は応答時間・スループット・同時実行数の観点で定義する。
- 負荷条件（同時接続数・RPS・データ量・時間帯）とその根拠を明示し、測定を再現できるようにする。
- 平均値より P95/P99 等の分位値を優先して評価する。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直さない。文書の整形・lint はリポジトリの検証で扱い、「測定・検証方法」に含めない。
- _UNDECIDED_: `recipe`・`template` の要否は未判断である。sample は「本文要件」の章に揃っていないため、sample を揃えることを本書を `ready` にする前提条件とする。

## 2. 位置づけ

| 文書              | 関係                                          | 本文からの導線 |
| ----------------- | --------------------------------------------- | -------------- |
| `nfr-index`       | NFR 全体の入口。分冊として `part_of` で属する | 必須           |
| `sac-*` / `stc-*` | 性能要件の合否判定基準・試験仕様              | 必須           |
| `opd-*`           | 運用時の監視閾値                              | 必須           |
| `dec-*`           | 基準値・負荷条件・測定手段を決めた設計判断    | 任意           |

- 基準値や負荷条件を変更したときは、`sac-*` の受入条件、`stc-*` の試験条件、`opd-*` の監視閾値を見直す。

## 3. ファイル命名・ID規則

- 配置先は `docs/ja/product/060-non-functional-requirements/nfr-performance.md` とし、[[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従う。
- 文書 ID は `nfr-performance` とする。プロダクト文書のため名前空間を付けない。
- 要件 ID は `nfr-perf-<連番>`（例: `nfr-perf-001`）とし、欠番を作らない。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。

- `specdojo.type` は `requirement`、`specdojo.rulebook` は `specdojo:nfr-performance-rulebook`、`specdojo.part_of` は `nfr-index` とする。
- ピーク条件の根拠とした文書（販売実績、販促計画、業務フローなど）を `specdojo.based_on` に挙げる。

## 5. 本文要件

`nfr-performance` は以下の章を順序固定で配置する。見出しは番号と章名をそのまま使う。

| 順序 | 章                   | 必須     | 内容                                                     |
| ---- | -------------------- | -------- | -------------------------------------------------------- |
| 1    | 概要（対象・目的）   | ○        | 対象処理と、遅延したときの業務影響                       |
| 2    | 適用範囲・負荷条件   | ○        | 平常時・ピーク時の負荷条件とその根拠、外部依存の扱い     |
| 3    | 性能要件一覧         | ○        | 要件ID、内容、指標、基準、備考                           |
| 4    | 測定・検証方法       | ○        | 要件IDごとの測定方法・測定環境・計測条件・判定タイミング |
| 5    | 関連ドキュメント導線 | ○        | 「位置づけ」の文書への導線                               |
| 6    | 未決事項             | 条件付き | 未確定の負荷条件・基準値・測定手段があるときだけ置く     |

## 6. 記述ガイド

各節は「本文要件」の同名の章に対応する。

### 6.1. 概要（対象・目的）

- 性能を定める対象処理と、遅延したときに起きる業務影響を書く。

判断基準: 業務影響から、基準値の厳しさの理由を説明できること。

- 良い例: 「会計確定が遅れると夕方の混雑時にレジ待ちが伸びるため、会計確定 API を対象とする。」
- 悪い例: 「システムを高速に動作させる。」（対象処理と業務影響がない）

### 6.2. 適用範囲・負荷条件

- 平常時とピーク時を分け、それぞれ同時接続数、RPS（秒間処理件数）、データ量、時間帯を書く。
- ピーク条件は根拠（`based_on` に挙げた実績・計画）を示す。根拠のない値は `_ASSUMPTION_` を付ける。
- 外部依存（決済サービスなど）の遅延を要件に含めるか、切り分けるかを書く。

判断基準: 負荷条件とその根拠を後から確かめ、同じ条件で再測定できること。

- 良い例: 「ピーク時は 16〜18 時、同時接続 50、100 RPS。昨年の販売実績の最大値を根拠とする。決済サービスの応答時間は計測から除く。」
- 悪い例: 「ピーク時は高負荷とする。」（条件と根拠がない）

### 6.3. 性能要件一覧

- 表形式（`要件ID` / `内容` / `指標` / `基準` / `備考`）で記述する。
- 指標例は P95、P99、RPS、バッチ完了時間。`基準` は単位と比較方向（以上／以内）を付ける。
- 適用する負荷条件（平常時・ピーク時）を `備考` に書く。

判断基準: 基準だけで pass / fail を一意に判定できること。

- 良い例: 「`nfr-perf-002` / 会計確定 API / 応答時間（P95） / 800 ms 以内 / ピーク時」
- 悪い例: 「会計 / 応答 / 速い」（指標・単位・負荷条件がない）

### 6.4. 測定・検証方法

- 「性能要件一覧」と同じ `要件ID` 列で、測定方法・判定タイミング・合格条件を表にし、負荷試験と運用監視の双方で判定できる形にする。
- 測定環境（本番相当か、外部依存をスタブにするか）と、計測時間・試行回数を書く。
- 合格条件は「性能要件一覧」の基準を参照し、基準値を言い直さない。

判断基準: 同じ環境・条件で測定し直したときに、同じ判定になること。

- 良い例: 「`nfr-perf-002`：本番相当環境で決済をスタブにし、ピーク負荷を 30 分 × 3 回かけて P95 を計測する。リリース前試験で判定する。」
- 悪い例: 「負荷試験で確認する。」（環境・計測時間・試行回数がない）

### 6.5. 関連ドキュメント導線

- 「位置づけ」の表の文書へ導線を置き、必須・任意も同表に従う。未作成の文書はバッククォートで仮置きする。

### 6.6. 未決事項

- 未確定の項目は推測で確定せず、`_UNDECIDED_` を付して論点と影響（当面の扱い、決まったときに直す要件ID）を書く。管理台帳の区分・担当・判断時期の列は設けない。
- 良い例：「`_UNDECIDED_`: ピーク時の同時接続数（販促の規模が未定）。当面は平常時の 5 倍で試験し、決まったら `nfr-perf-002` の基準を見直す。」
- 悪い例：未定のピーク条件を推測値のまま確定基準として書く。

## 7. 禁止事項

| 禁止事項                   | 理由                 |
| -------------------------- | -------------------- |
| 負荷条件なしで閾値だけ書く | 再現不能のため       |
| 平均値のみで評価する       | 体感性能を見逃すため |
| 単位なしの数値を記載する   | 判定不能のため       |
