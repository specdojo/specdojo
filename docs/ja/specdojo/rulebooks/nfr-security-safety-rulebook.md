# 非機能要件 / 機密性・安全性 作成ルール

Non-Functional Requirements Security and Safety Documentation Rules

本書は、非機能要件のうち機密性・安全性（認証、認可、保護、監査）を定義する `nfr-security-safety` の作成ルールを定める。

## 1. 全体方針

- 機密性・安全性はアクセス制御、情報保護、監査可能性で定義する。
- 要件は「許可されない操作が実行されない」ことを基準化する。
- 脅威・規制要件に対する検証可能な制約として記述する。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直さない。文書の整形・lint はリポジトリの検証で扱い、「測定・検証方法」に含めない。

## 2. 位置づけと用語定義（必要に応じて）

### 2.1. 位置づけ

- `nfr-index`：NFR全体の入口
- `sac-*` / `stc-*`：機密性・安全性要件の検証先
- `opd-*` / `opr-*`：監視・インシデント対応

### 2.2. 用語定義

| 用語     | 定義                                       |
| -------- | ------------------------------------------ |
| 機密性   | 許可された主体のみ情報へアクセスできる性質 |
| 安全性   | 不正操作や有害事象を抑制する性質           |
| 認可逸脱 | 権限外の操作が許可されること               |

## 3. ファイル命名・ID規則

- ルールドキュメントIDは `specdojo:nfr-security-safety-rulebook`。
- 生成対象ドキュメントIDは `nfr-security-safety` を推奨する。
- 要件IDは `nfr-sec-<連番>` を推奨する。

## 4. 推奨 Frontmatter 項目

### 4.1. 設定内容

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。

- `specdojo.id` は `nfr-security-safety`、`specdojo.type` は `requirement`、`specdojo.rulebook` は `specdojo:nfr-security-safety-rulebook` とする。
- `specdojo.part_of` には `nfr-index` を置く。

### 4.2. 推奨ルール

- 規制・監査基準（個人情報保護法、社内セキュリティポリシー等）への適合要件がある場合は、その根拠文書を `specdojo.based_on` に挙げる。

## 5. 本文構成（標準テンプレ）

`nfr-security-safety` は以下の見出し構成を **順序固定** で配置する。

| 番号 | 見出し                 | 必須 |
| ---- | ---------------------- | ---- |
| 1    | 概要（対象・目的）     | ○    |
| 2    | 適用範囲・脅威前提     | ○    |
| 3    | 機密性・安全性要件一覧 | ○    |
| 4    | 測定・検証方法         | ○    |
| 5    | 関連ドキュメント導線   | ○    |

## 6. 記述ガイド

### 6.1. 概要（対象・目的）

生成する本文の見出しは **## 1. 概要（対象・目的）**

- 保護対象（情報・操作）と守るべき目的を示す。

### 6.2. 適用範囲・脅威前提

生成する本文の見出しは **## 2. 適用範囲・脅威前提**

- 想定脅威、対象境界、適用する規制、対象外を表で明記する。

### 6.3. 機密性・安全性要件一覧

生成する本文の見出しは **## 3. 機密性・安全性要件一覧**

- 表形式（`id` / `内容` / `指標` / `基準` / `備考`）で記述し、認証・認可・情報保護・監査を別の行に分ける。
- 「基準」は件数・割合・期限などの判定値で書く。指標例：認可逸脱件数、脆弱性修正SLA、監査ログ欠落率。
- **良い例**: 「権限外ユーザーは顧客情報を参照できない ／ 認可逸脱件数 ／ 0 件/四半期」
- **悪い例**: 「顧客情報を安全に管理する ／ － ／ 適切に」（指標も判定値もなく検証できない）

### 6.4. 測定・検証方法

生成する本文の見出しは **## 4. 測定・検証方法**

- 要件IDごとに、セキュリティ試験・監査ログ検証・脆弱性スキャンなどの測定方法と判定時期を定める。

### 6.5. 関連ドキュメント導線

生成する本文の見出しは **## 5. 関連ドキュメント導線**

- 「位置づけ」の文書、設計判断の `dec-*`、セキュリティ方針文書を、種別・ドキュメントID・目的の表で紐づける。

## 7. 禁止事項

| 禁止事項                             | 理由                     |
| ------------------------------------ | ------------------------ |
| 「安全にする」だけで基準がない       | 検証不能のため           |
| 認可・監査の要件を分離せず曖昧化する | 事故原因追跡が困難なため |
| 例外運用を本文に散在させる           | 統制不能になるため       |

## 8. サンプル

注：形式の輪郭を示す最小例。成果物の見出しは `## 1...` から始まる。

```yaml
---
specdojo:
  id: nfr-security-safety
  type: requirement
  status: draft
  rulebook: specdojo:nfr-security-safety-rulebook
  part_of: [nfr-index]
---
```

### 8.1. 適用範囲・脅威前提（例）

| 項目     | 内容                                     |
| -------- | ---------------------------------------- |
| 想定脅威 | 不正ログイン、権限昇格、インジェクション |
| 対象外   | 物理セキュリティ（別文書）               |

### 8.2. 機密性・安全性要件一覧（例）

| id          | 内容                                         | 指標            | 基準        | 備考              |
| ----------- | -------------------------------------------- | --------------- | ----------- | ----------------- |
| nfr-sec-001 | 権限外ユーザーは機密データを参照できないこと | 認可逸脱件数    | 0 件/四半期 | STC で検証        |
| nfr-sec-002 | 重大脆弱性は期限内に修正する                 | 修正 SLA 達成率 | 95% 以上    | CVSS 7.0 以上対象 |
| nfr-sec-003 | 監査ログは改ざん不能で保管すること           | 改ざん検知率    | 100%        | WORM ストレージ   |

### 8.3. 測定・検証方法（例）

| 要件ID      | 測定方法                                         | 判定タイミング      |
| ----------- | ------------------------------------------------ | ------------------- |
| nfr-sec-001 | ペネトレーションテスト（権限かいくぐりシナリオ） | リリース前 / 四半期 |
| nfr-sec-002 | 脆弱性管理ツールの修正完了データ                 | 月次集計            |
| nfr-sec-003 | WORM ストレージの書き込み禁止確認テスト          | 四半期監査          |
