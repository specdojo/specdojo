# 非機能要件 / 機密性・安全性 作成ルール

Non-Functional Requirements Security and Safety Documentation Rules

非機能要件のうち機密性・安全性（認証、認可、情報保護、監査）を定義する `nfr-security-safety` の作成ルールを定める。

## 1. 全体方針

- 機密性・安全性は、アクセス制御・情報保護・監査可能性の観点ごとに、許可されない操作が実行されないことを判定値で定義する。
- 脅威と適用規制を前提に置き、試験・監査で pass / fail を判定できる制約として書く。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直さない。文書の整形・lint はリポジトリの検証で扱い、「測定・検証方法」に含めない。

## 2. 位置づけと用語定義

### 2.1. 位置づけ

- `nfr-security-safety` は機密性・安全性要求の正本で、`nfr-index` を入口とする。
- 合否基準・試験は `sac-*` / `stc-*`、監視・インシデント対応は `opd-*` / `opr-*` を正本とし、本書から参照する。

### 2.2. 用語定義

| 用語         | 定義                                                             |
| ------------ | ---------------------------------------------------------------- |
| 認可逸脱     | 権限範囲の外にある操作が許可されること                           |
| アクセス主体 | システムを操作する利用者区分・運用者・外部システムの区分         |
| 例外運用     | 要件を一時的に満たさない状態を、代替統制と期限を付けて認めること |

## 3. ファイル命名・ID規則

- 生成対象ドキュメント ID は `nfr-security-safety` を推奨する。
- 要件 ID は `nfr-sec-<連番>`（3 桁）、例外 ID は `nfr-sec-ex-<連番>`（3 桁）を推奨する。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。

- `specdojo.type` は `requirement`、`specdojo.rulebook` は `specdojo:nfr-security-safety-rulebook`、`specdojo.part_of` は `nfr-index` とする。
- 適合が必要な規制・監査基準（個人情報保護法、社内セキュリティポリシー等）がある場合は、その根拠文書を `specdojo.based_on` に挙げる。

## 5. 本文要件

見出しは次の構成で **順序固定** とする。

| 番号 | 見出し                 | 必須 | 受入条件                                                                                     |
| ---- | ---------------------- | ---- | -------------------------------------------------------------------------------------------- |
| 1    | 概要（対象・目的）     | ○    | 保護対象（情報・操作）と防ぎたい事象が分かる                                                 |
| 2    | 適用範囲・脅威前提     | ○    | 想定脅威・対象境界・適用規制・対象外と、アクセス主体ごとの権限範囲が揃っている               |
| 3    | 機密性・安全性要件一覧 | ○    | 全要件が標準 5 列で、指標と基準から pass / fail を判定できる                                 |
| 4    | 測定・検証方法         | ○    | 全要件 ID に測定方法・判定時期・検証先がある                                                 |
| 5    | 例外運用               | ○    | 例外が本章の表に集約され、各例外に代替統制・期限・承認者がある。例外がなければ「なし」と書く |
| 6    | 関連ドキュメント導線   | ○    | `nfr-index`・`sac-*`・`stc-*`・`opd-*` / `opr-*` への導線がある                              |

- 「機密性・安全性要件一覧」の標準 5 列は `id` / `内容` / `指標` / `基準` / `備考` の順とする。
- 「測定・検証方法」の列は `id` / `測定方法` / `判定時期` / `検証先` とする。
- 「例外運用」の列は `例外ID` / `対象要件` / `理由` / `代替統制` / `期限` / `承認者` とする。`承認者` はセキュリティ例外を認める業務上の権限者であり、本書の承認とは別である。

## 6. 記述ガイド

完成例の全体像は Frontmatter の `sample` で宣言された sample を参照する。

### 6.1. 概要（対象・目的）

- **判断基準**: どの情報・操作を、どの事象（漏えい・改ざん・不正操作）から守るかが 2〜3 文で分かること。
- **良い例**: 「顧客の連絡先と売上データを、権限外の参照と改ざんから守る」
- **悪い例**: 「システムを安全に運用する」（保護対象も防ぐ事象も分からない）

### 6.2. 適用範囲・脅威前提

- **判断基準**: 想定脅威・対象境界・適用規制・対象外を項目ごとの表で書き、さらにアクセス主体ごとの権限範囲を表（`主体` / `許可する操作` / `許可しない操作`）で書く。認可要件の「権限外」がこの表から特定できること。
- **良い例**: 「店員 ／ 販売登録・在庫参照 ／ 顧客情報の出力・価格マスタの変更」
- **悪い例**: 「一般ユーザーと管理者」（権限範囲がなく、認可逸脱を判定できない）

### 6.3. 機密性・安全性要件一覧

- **判断基準**: 認証・認可・情報保護・監査を別の行に分け、`基準` を件数・割合・期限で書く。割合の指標は判定の母数（対象・期限）を `内容` か `備考` で定める。指標例は認可逸脱件数、脆弱性修正期限の遵守率、監査ログ欠落率。
- **良い例**: 「`nfr-sec-002` ／ CVSS 7.0 以上の脆弱性を公表から 14 日以内に修正する ／ 修正期限の遵守率 ／ 95% 以上 ／ 対象は本番環境」
- **悪い例**: 「重大脆弱性は期限内に修正する ／ 修正 SLA 達成率 ／ 95% 以上」（期限がなく母数が決まらない）

### 6.4. 測定・検証方法

- **判断基準**: 要件 ID ごとに測定手段（セキュリティ試験・監査ログ検証・脆弱性スキャン）、判定時期、判定結果を記録する検証先（`stc-*`・`sac-*`・`opr-*`）が分かること。検証の作業を担う役割は検証先の計画で割り当て、本書では書かない。
- **良い例**: 「`nfr-sec-001` ／ 権限外の操作を試すペネトレーションテスト ／ リリース前・四半期 ／ `stc-security`」
- **悪い例**: 「定期的にセキュリティを確認する」（どの要件をいつ判定するか分からない）

### 6.5. 例外運用

- **判断基準**: 要件を満たせない状態を認める場合は、本章の表だけに書き、要件一覧の `備考` や他章に散らさない。期限切れの例外が表から判別できること。
- **良い例**: 「`nfr-sec-ex-001` ／ `nfr-sec-002` ／ 旧レジ端末の OS 更新待ち ／ 端末をネットワーク分離 ／ 2027-03-31 ／ 店長」
- **悪い例**: 「当面は対応を見送る」（代替統制も期限もなく統制できない）

### 6.6. 関連ドキュメント導線

- **判断基準**: 「位置づけ」の文書、設計判断の `dec-*`（任意）、セキュリティ方針文書を、種別・ドキュメント ID・目的の表で紐づけること。

## 7. 禁止事項

| 禁止事項                             | 理由                                   |
| ------------------------------------ | -------------------------------------- |
| 「安全にする」だけで基準がない       | 検証不能のため                         |
| 認可・監査の要件を 1 行にまとめる    | 事故原因の追跡が困難なため             |
| 例外運用を「例外運用」以外の章に書く | 例外の期限と代替統制を統制できないため |
| 権限範囲を定めずに認可要件を書く     | 「権限外」が特定できず判定できないため |
