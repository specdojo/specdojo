# システム設計 / 横断ルール 作成ルール

System Design Cross-cutting Policy Documentation Rules

複数の実装領域で守る制約、例外、検証条件を一つの正本にまとめるための規定である。値・構文・構造の詳細は実装・schema・リファレンスに委ねる。

## 1. 全体方針

- 複数モジュールに共通する必須・禁止条件を扱い、個別機能の手順や一時作業の計画は持ち込まない。
- 各ルールを入力条件と観測可能な期待結果で判定できるようにし、規定の存在と実装済みの証拠を区別する。未確定の値は推測しない。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、文書の改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直さない。文書の整形・lint はリポジトリの検証で扱い、ルールの適合確認に含めない。

## 2. 位置づけと用語定義

| 情報                       | 責務                                                   |
| -------------------------- | ------------------------------------------------------ |
| システム設計索引           | 実装・設定・schema・生成物の所在と変更の入口           |
| 横断ルール                 | 複数領域に共通する不変条件、適用範囲、例外、検証の正本 |
| 個別設計・非機能要件・運用 | 個別の構成、目標値、通知・保持・回復手順の詳細         |
| 決定記録・登録簿           | 例外承認、課題・リスク・変更の正本                     |

「例外」は承認を得て通常規則から外れる条件、「不適合」は未承認の逸脱、「未確認」は適合証拠が未取得の状態とする。未確認を例外や実装済みへ読み替えない。

## 3. ファイル命名・ID規則

- ファイル名は `sysd-cross-cutting-policy.md` を基本とする。
- ルール ID は `scp-<カテゴリ>-<連番>` とし、同じ適用範囲内で一意にする。
- カテゴリは `ERR`（エラー）、`IDM`（冪等）、`TIM`（時間制御）、`RET`（再試行）、`LOG`（ログ）、`TRC`（追跡）、`SEC`（保護）、`CFG`（設定）、`MOD`（境界）等を使う。カテゴリ追加で必須領域を隠さない。
- 置き換え・廃止した Rule ID は再利用せず、ルール一覧に後継 Rule ID または廃止理由を残す。その Rule の Owner が、「関連導線」の変更影響に挙げた参照先（システム設計索引・実装・テスト・運用文書）と検証の対応の更新を確かめる。

## 4. 推奨 Frontmatter 項目

- 共通の型・許容値は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と成果物 Frontmatter schema を正とする。
- `type` は `architecture`、`rulebook` は `specdojo:sysd-cross-cutting-policy-rulebook` とし、設計索引へは `part_of` で接続する。`based_on` は判断に使った依存範囲内の文書だけにする。

## 5. 本文要件

見出し順・表の骨組みは template を正とし、ここでは意味要件を定める。

| 内容               | 必須 | 意味・判定に必要な情報                                                                          |
| ------------------ | ---- | ----------------------------------------------------------------------------------------------- |
| 概要               | ○    | 対象・対象外、競合時の優先判断、上位価値への寄与、誰がどの判断に使うか                          |
| ルール一覧         | ○    | ID・カテゴリ・要約・必須度・Owner。全詳細と対応し、実装状況または確認待ちと確認時機へ接続       |
| 各ルール詳細       | ○    | Rule、Rationale、Scope、Enforcement、Exception、References の六要素。条件・期待結果・正本・検証 |
| 例外               | ○    | 承認済み例外の対象 Rule ID・理由・影響・期限・判断者・復帰条件・決定参照。不適合との区別        |
| 関連導線           | ○    | 設計、非機能、運用、テスト、判断記録への入口。Rule 変更から schema・互換性・移行・回帰への影響  |
| 未決事項・公開条件 | ○    | 未確定の対象 Rule ID、論点と影響（当面の扱い）。実装の根拠にする前に済ませる適合確認            |

- 共通エラー・冪等・時間上限と打切り・retry・診断ログと監査・トレーシング・秘密と権限・設定上書き・モジュール境界を必ず検討する。非該当は理由と代替手段（または代替不要の理由）を示す。
- HTTP API がなければ CLI 等のエラー契約、DB がなければファイル保存と途中状態の整合性を扱う。特定技術の不在を領域全体の対象外理由にしない。
- retry は冪等前提、signal 分類、回数の数え方、attempt・backoff 上限、上限到達時の処置を正本の値または設定キーへ接続する。未定義なら受入を保留する。
- timeout は経路別の設定・単位、終了対象、部分出力・保存状態、再開条件を結ぶ。ログ・監視は相関、秘匿化、保持、検知・通知・一次対応の範囲を示す。
- 完成例では架空の正本・検証コマンドを未同梱と明示し、検証計画を実行済み証跡として扱わない。

## 6. 記述ガイド

以下は局所的な判断例であり、完成例は sample を参照する。

### 6.1. 概要

判断基準は、読む人が対象と適用しない境界、競合時の判断を説明できることである。

- 良い例: 「CLI と日次処理を対象にし、無限再試行を防いで参加者の復旧負荷を減らす。外部連携の契約と競合した場合は契約を優先する」。
- 悪い例: 「全体に適切な規則を適用する」。対象と境界が判断できない。

### 6.2. ルール一覧

判断基準は、一覧・詳細・適合確認の Rule ID が対応し、要約と必須度の組合せで要求・禁止が同じ意味になることである。推奨列は `Rule ID / Category / Summary / Level / Owner` とし、適合状況・確認時機は別表へ分けてもよい。作業の進捗は本文で二重管理しない。

- 良い例: 「`scp-CFG-001`、不正設定で起動しない、MUST、DEV、実装未照合、起動前に V2 で確認」。
- 悪い例: 「設定責務を分離する、MUST NOT」。必須度を組み合わせると意図と逆になる。

### 6.3. 各ルール詳細

判断基準は、条件が同じなら期待動作と合否が一意になり、検証する正本へ到達できることである。Rule は不変条件に絞り、検証の入口は Enforcement、低レベル手順は実装・運用正本に置く。

- 良い例: 「再送は保存済みの受付結果を照合した後だけ許可する。応答欠落では結果不明を保持し、自動再送しない。回帰対象と実行コマンドは検証表へ接続する」。
- 悪い例: 「criticality に応じて retry」。区分・signal 対応・上限の正本がなく判断不能。

### 6.4. 例外

判断基準は、通常ルールへ復帰でき、未承認の不適合と承認済みの逸脱を区別できることである。

- 良い例: 「依存の暫定許可は対象 adapter のみ、移行完了日まで、decision と復帰条件を記録。違反は issue として報告する」。
- 悪い例: 「緊急時は担当判断で無期限に解除」。影響・期限・復帰が追跡できない。

### 6.5. 関連導線

判断基準は、読み手が現行正本へ進み、変更時の追従先を選べることである。呼称は参照先の文書名に揃える。

- 良い例: 「保存形式変更は schema と移行を同期し、旧形式・再実行の回帰を確認する。運用索引は未作成のため整備後に接続する」。
- 悪い例: 「provider 別設計、運用一式、旧フロー参照」。実在する ID・相対パスがなく特定できない。

### 6.6. 未決事項と公開条件

判断基準は、未決の論点がどの Rule ID の受入を止めるかと当面の扱いが分かることである。未発行の作業 ID を発行済みとみなさない。

- 良い例: 「`_UNDECIDED_`: 通知先。決まるまで `scp-LOG-001` の検知・通知は未確認とし、失敗注入での確認を受入の前提に残す」。
- 悪い例: 「NFR / OPD は後続で接続する」。何が未決でどのルールに効くか分からない。

## 7. 禁止事項

| 禁止事項                                                 | 理由                           |
| -------------------------------------------------------- | ------------------------------ |
| 実装・schema・リファレンスの値・構文・構造を全文転載する | 二重管理になる                 |
| 確認していない上限値・設定キー・実装状況を作る           | 実装・検証の前提を誤らせる     |
| 非該当と未整備を混同し必須領域を消す                     | 障害・回復・観測の責務が欠ける |
| 検査名だけで入力・期待結果・実行経路を示さない           | 合否を再現できない             |
| 例外を散在させ、期限・判断・復帰を省く                   | 通常規則へ戻せない             |
| 置き換え・廃止した Rule ID を再利用する、後継を示さない  | 実装・テストの参照が追えない   |
