# システム設計 / 横断ルール 作成ルール

System Design Cross-cutting Policy Documentation Rules

複数の実装領域で守る制約、例外、検証条件を一つの正本にまとめるための規定である。値・構文・構造の詳細は実装・schema・リファレンスに委ね、共通の判断と適用境界を定める。

## 1. 全体方針

- 対象システムの複数モジュールに共通する必須・禁止条件を扱う。個別機能の詳細手順や一時作業の計画は持ち込まない。
- 対象者の課題と上位の価値・成功基準への寄与を短く示す。プロジェクト背景の全文を再掲しない。
- 各ルールを入力条件と観測可能な期待結果で判定できるようにする。規定の存在と実装済みの証拠を区別する。
- 未確定の値や業務判断を推測しない。担当、判断期限、影響、次アクションを伴う共通ラベルで残す。

## 2. 位置づけと用語定義

| 情報                       | 責務                                                     |
| -------------------------- | -------------------------------------------------------- |
| システム設計索引           | 実装・設定・schema・生成物の所在と変更の入口             |
| 横断ルール                 | 複数領域に共通する不変条件、適用範囲、例外、検証の正本   |
| 個別設計・非機能要件・運用 | 個別の構成、目標値、通知・保持・回復手順の詳細           |
| 決定記録・登録簿・Schedule | 例外承認、課題・リスク・変更、担当・期限・作業進捗の正本 |

「例外」は通常規則から承認を得て外れる条件、「不適合」は未承認の逸脱、「未確認」は適合証拠が未取得の状態とする。未確認を例外や実装済みへ読み替えない。

## 3. ファイル命名・ID規則

- ファイル名は `sysd-cross-cutting-policy.md` を基本とし、文書 ID の authority はプロジェクトの共通命名規約に従う。
- ルール ID は `scp-<カテゴリ>-<連番>` とし、同じ適用範囲内で一意かつ改訂後も追跡可能にする。
- カテゴリは `ERR`（エラー）、`IDM`（冪等）、`TIM`（時間制御）、`RET`（再試行）、`LOG`（ログ）、`TRC`（追跡）、`SEC`（保護）、`CFG`（設定）、`MOD`（境界）等を使う。カテゴリ追加で必須領域を隠さない。

## 4. 推奨 Frontmatter 項目

- 共通の型・許容値は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と成果物 Frontmatter schema を正とし、ここで再定義しない。
- 成果物・完成例と template の生成物 Frontmatter では、`type` を本書の `deliverable_type` と同じ `architecture` に、`rulebook` を本書の完全 ID にする。template 自身の `type: template` と混同しない。設計索引へ所属する成果物は `part_of` で接続する。
- `based_on` は実際に判断に使った依存範囲内の文書だけにする。プロジェクト共通文脈を機械的に転記しない。
- `status` は agent が `ready` に変更しない。公開可否と昇格の判断責任は本文にも示す。

## 5. 本文要件

見出し順・表・記入欄の骨組みは frontmatter で宣言する template を正とし、ここでは意味要件を定める。Markdown の `##`〜`####` には階層ごとの連番と末尾の `.` を付ける。

| 内容               | 必須 | 意味・判定に必要な情報                                                                                                          |
| ------------------ | ---- | ------------------------------------------------------------------------------------------------------------------------------- |
| 概要               | ○    | 対象・対象外、競合時の優先判断、上位価値への寄与、利用者・確認者・人間の最終承認者                                              |
| ルール一覧         | ○    | ID・カテゴリ・要約・必須度・Owner。全詳細と対応し、実装状況または確認待ち、確認時機と依存順へ接続                               |
| 各ルール詳細       | ○    | Rule、Rationale、Scope、Enforcement、Exception、References の六要素。条件・期待結果・正本・検証コマンドを特定                   |
| 例外               | ○    | 承認済み例外の有無、対象 Rule ID・理由・影響・期限・判断者・復帰条件・決定参照。不適合・risk・change・decision の記録と追跡責務 |
| 関連導線           | ○    | 設計、非機能、運用、テスト、判断記録への入口。Rule 変更から schema・生成物・互換性・移行・回帰対象への影響と担当                |
| 未決事項・公開条件 | ○    | 未確定の対象 ID、判断者・期限・影響・次アクション、計画登録の状況。確認完了と人間による公開・昇格の条件                         |

- 完成例にも上表の必須内容とルール詳細の六要素を適用する。架空の正本・検証コマンドは未同梱と明示し、検証計画を実行済み証跡として扱わない。
- 共通エラー・冪等・時間上限と打切り・retry・診断ログと監査・トレーシング・秘密と権限・設定上書き・モジュール境界を必ず検討する。非該当は構成上の理由と代替手段、または代替不要の理由を示す。
- HTTP API がなければ CLI 等のエラー契約を扱い、DB がなければファイル保存と途中状態の整合性を扱う。特定技術がないことを領域全体の対象外理由にしない。
- retry は冪等前提、signal 分類、回数の数え方、attempt・backoff 上限、fallback・上限到達時の処置を正本の値または設定キーへ接続する。未定義なら受入を保留し、判断課題を明示する。
- timeout は経路別の設定・単位、終了対象、部分出力・保存状態、再開条件を結ぶ。ログ・監視は相関、秘匿化、保持、検知・通知・一次対応の適用範囲を示す。

## 6. 記述ガイド

共通の値・構造・用語は上位索引または各正本へ委ねる。以下の例は局所的な判断例であり、完成例を本文へ埋め込まない。

### 6.1. 概要

判断基準は、読む人が対象と適用しない境界、競合時の判断、人間の承認責務を説明できることである。

- 良い例: 「CLI と日次処理を対象にし、無限再試行を防いで参加者の復旧負荷を減らす。DEV が実装、QE / OPS が確認し、人間の PO が公開可否を判断する」。
- 悪い例: 「全体に適切な規則を適用する」。対象と責任が判断できない。

### 6.2. ルール一覧

判断基準は、一覧・詳細・適合確認の Rule ID が相互に対応し、要約と必須度の組合せで要求・禁止が同じ意味になることである。推奨列は `Rule ID / Category / Summary / Level / Owner` とする。適合状況、依存、確認時機は別の対応表へ分けてもよい。作業の進捗を本文で二重管理しない。

- 良い例: 「`scp-CFG-001`、不正設定で起動しない、MUST、DEV、実装未照合、起動前に V2 で確認」。
- 悪い例: 「設定責務を分離する、MUST NOT」。必須度を組み合わせると意図と逆になり、進捗にも展開できない。

### 6.3. 各ルール詳細

判断基準は、条件が同じなら期待動作と合否が一意になり、検証する正本へ到達できることである。共通の検証群へ束ねる場合も Rule ID との対応を残す。

- 良い例: 「再送は保存済みの受付結果を照合した後だけ許可する。応答欠落では結果不明を保持し、自動再送しない。設定キーは契約正本、回帰対象と実行コマンドは検証表へ接続する」。
- 悪い例: 「criticality に応じて retry」。区分・signal 対応・上限の正本がなく判断不能。
- Rule は不変条件に絞る。検証の入口を Enforcement、低レベル手順を実装・運用正本に集約し、同じ内容を Scope に繰り返さない。

### 6.4. 例外

判断基準は、通常ルールへ復帰でき、未承認の不適合と承認済みの逸脱を区別できることである。

- 良い例: 「依存の暫定許可は対象 adapter のみ、移行完了日まで、PO の decision と復帰条件を記録。違反は issue として DEV が報告、PM が追跡する」。
- 悪い例: 「緊急時は担当判断で無期限に解除」。影響・期限・責任が追跡できない。

### 6.5. 関連導線

判断基準は、読み手が参照目的を理解して現行正本へ進め、変更時の追従先を選べることである。見出し・表・リンクでは参照先の文書名を基準に呼称を揃え、略号を使う場合は対応する文書名を示す。

- 良い例: 「保存形式変更は DEV が schema と移行を同期し、旧形式・再実行の回帰を確認。運用索引は未作成のため OPS が整備後に接続する」。
- 悪い例: 「provider 別設計、運用一式、旧フロー参照」。実在する ID・相対パスがなく特定できない。
- 呼称の良い例: 「システム設計索引」「重要フロー」を表と参照ラベルで揃える。悪い例: 同じ参照先を表では「SYSD Critical Flows」、導線では説明なく「SYSD-CF」と呼び分ける。

### 6.6. 未決事項と公開条件

判断基準は、PO が承認・保留・差し戻しを選べることである。未発行の作業 ID を発行済みとみなさない。

- 良い例: 「通知先は未決。OPS が公開前に設計し、PM が issue と Schedule へ接続、QE が失敗注入で確認、PO が期限付き留保の可否を判断する」。
- 悪い例: 「NFR / OPD は後続で接続する」。誰がいつ何を判断するか分からない。

## 7. 禁止事項

| 禁止事項                                                 | 理由                           |
| -------------------------------------------------------- | ------------------------------ |
| 実装・schema・リファレンスの値・構文・構造を全文転載する | 二重管理になる                 |
| 確認していない上限値・設定キー・実装状況を作る           | 実装・検証の前提を誤らせる     |
| 非該当と未整備を混同し必須領域を消す                     | 障害・回復・観測の責務が欠ける |
| 検査名だけで入力・期待結果・実行経路を示さない           | 合否を再現できない             |
| 例外を散在させ、期限・判断・復帰を省く                   | 通常規則へ戻せない             |
| agent に公開・昇格の最終判断を委ねる                     | 人間の説明責任を失う           |
