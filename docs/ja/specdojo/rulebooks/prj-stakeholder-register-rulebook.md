# ステークホルダー登録簿 作成ルール

Stakeholder Register Documentation Rulebook

プロジェクトの関係者を業務価値と利用者影響から整理し、合意対象、関与方針、後続のコミュニケーション計画への入力を定める規約です。

## 1. 全体方針

- 対象は、意思決定、実行、利用、運用、評価、影響受容に関わる個人・組織・集団である。
- 目的は、関係者の関心と影響を可視化し、合意漏れと利用者影響の見落としを防ぐことである。
- 会議体、配信頻度、議事録の運用はコミュニケーション計画へ委譲し、入力となる要求だけを扱う。
- ステークホルダーは人・組織との関係を示し、タスクの担当責務である Role と区別する。対応する Role がある場合だけ Role code を併記する。
- AI Agent・ツール自体は登録せず、入力・制約・確認責任を持つ人・組織を記載する。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱い、業務の受入確認には含めない。

## 2. 位置づけ

概要の目的・利用者・期待効果を合意対象と関与方針へ具体化する。情報要求、合意・報告の必要性、証跡要件を後続のコミュニケーション計画へ渡す。

## 3. ファイル命名・ID規則

### 3.1. 配置（推奨）

- `docs/ja/projects/<project-id>/020-project-definition/prj-stakeholder-register.md` に配置する。
- 個人連絡先、非公開の利害情報、詳細な連絡網は、アクセス制限された管理資料へ分離する。

### 3.2. ドキュメントID（推奨）

- 推奨: `<project-id>:prj-stakeholder-register`
- 例: `prj-0001:prj-stakeholder-register`
- 文書 ID と関係者 ID は区別する。

### 3.3. ファイル名（推奨）

- 推奨: `prj-stakeholder-register.md`
- 関係者 ID は `STH-<KEY>` 形式とし、同じ関係者を全ての表で同じ ID で参照する。
- 個人名より役割名・組織名・集団名を優先する。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は「共通の運用」の参照先と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` に従う。

- `type` は `project` とする。
- `rulebook` は `specdojo:prj-stakeholder-register-rulebook` とする。
- 任意の `based_on` には、関係者、期待、合意対象を判断した概要や憲章などの直接根拠を記載する。

## 5. 本文要件

骨組み（見出し順・表・記入欄）は `template` を正とし、各章の必須性・受入条件は次に定める。

| 章                     | 必須 | 目的・受入条件                                                                                          |
| ---------------------- | ---- | ------------------------------------------------------------------------------------------------------- |
| 関係者一覧             | ○    | 調整先を識別する。ID、関係者名、関与区分、所属/組織、対応 Role code、主な責任、利用場面または備考を示す |
| 影響度/関心度分析      | ○    | 関与の優先度を判断する。影響度、関心度、期待、懸念、必要な合意、評価根拠を対応付ける                    |
| エンゲージメント方針   | ○    | 関与の差分を埋める。現状、目標、対応方針、責任者、期限、証跡を対応付ける                                |
| コミュニケーション要件 | ○    | 詳細計画への入力を示す。情報要求、希望チャネル、合意・報告の必要性、証跡要件、計画への反映を記載する    |
| 見直し条件             | ○    | 関係者への影響を再評価する契機を示す。更新トリガー、見直し内容、見直し責任者、承認者、証跡を記載する    |

## 6. 記述ガイド

### 6.1. 関係者一覧

- 関与区分は意思決定、実行、利用、運用、外部協力、影響受容で識別する。
- 1 行で主な責任とプロジェクトへの関わり方を示す。
- 同じ対象を別名で重複登録しない。
- 対応 Role code は採用済みのものだけを使い、該当しない外部集団には割り当てない。

### 6.2. 影響度/関心度分析

- 影響度・関心度は High / Medium / Low で評価し、方針・範囲・利用・合意形成への影響を根拠にする。
- 期待・懸念と、着手・変更・公開・利用・運用のために確認・承認する「必要な合意」を対応付ける。
- High の関係者は、必要な合意または関与方針を空欄にしない。

| 評価   | 影響度の基準                                       | 関心度の基準                                   |
| ------ | -------------------------------------------------- | ---------------------------------------------- |
| High   | 方針、範囲、優先順位、公開・利用可否を直接左右する | 成果または進行に継続的な確認・判断を必要とする |
| Medium | 一部の成果物、利用、運用、合意形成に影響する       | 節目または変更時に確認・調整を必要とする       |
| Low    | 影響は限定的または間接的である                     | 通知または必要時の共有で足りる                 |

### 6.3. エンゲージメント方針

- 現状と目標を対比し、差分を埋める対応方針を書く。
- 情報提供、相談、合意形成、承認依頼、巻き込み、リスク低減の目的が分かる行動にする。
- 証跡は議事録、決定記録、Issue、Pull Request などで辿れるようにする。未確定の関与方針・期限は、論点と利用者影響を明示する。

### 6.4. コミュニケーション要件

- 情報要求は、受け取る情報と、それによる判断・確認を示す。
- 希望チャネルは対面、Issue、文書、公開ページなどの手段を示す。
- 詳細計画を作る場合は、情報要求と証跡要件を入力として渡し、同じ配信計画を二重管理しない。

### 6.5. 見直し条件

- 概要、範囲、体制、公開方針、主要な利用者影響が変わるときは見直す。
- 定期見直しを行う場合は、周期だけでなく、確認する内容と承認者を明記する。
- 関係者の追加・削除・関与変更と、同じ ID を使う各章・コミュニケーション計画への影響を、変更差分や決定記録で辿れるようにする。

## 7. 禁止事項

| 項目                                             | 理由                                       |
| ------------------------------------------------ | ------------------------------------------ |
| 役割・責任・関与区分の欠落                       | 調整先と利用者影響を判断できないため       |
| 根拠のない影響度・関心度の評価                   | 対応優先度を説明できないため               |
| 必要な合意の空欄                                 | 意思決定者と合意対象を識別できないため     |
| ステークホルダー ID をタスクの owner に使う      | 関係者と責務 Role を混同するため           |
| 未採用の Role code の推測                        | 組織・責務定義と不整合になるため           |
| 個人連絡先・非公開情報・機密の利害関係の記載     | 公開時の情報管理リスクがあるため           |
| 詳細な会議運営・配信計画の重複管理               | コミュニケーション計画と二重管理になるため |
| AI Agent・ツール自体をステークホルダーとして登録 | 責任を持つ人・組織との関係が不明になるため |
