# 画面仕様（UI）作成ルール

User Interface Specification (UIS) Authoring Rule

本ドキュメントは、業務分析・要求定義のために **画面仕様（User Interface: UI）を統一形式で記述する標準ルール** です。
Web/GUI 画面に加え、CLI のコマンド群を画面に見立てる画面仕様（CUI/CLI）も本ルールの対象とします。
CLI のコマンド群を画面に見立てる場合は、引数・オプションの表や使い方の詳細は持たずコマンドリファレンスを参照し、利用目的・操作の流れ・表示・エラー表示の要点に絞って記述します。

## 1. 全体方針

- 画面仕様は、**業務ユーザー視点** での画面の利用目的・操作の流れ・表示項目・操作・遷移・エラー表示を明確に記述します。
- 画面の機能と業務対話に着目し、**画面のレイアウトやワイヤーフレーム（ピクセル・座標・CSS・コンポーネント配置など）は含めません**。
- 実装詳細（例: 物理テーブル名、物理カラム名、SQL、実装クラス/関数名、UIライブラリ名）は記載しません。
- **CLI のコマンド群を画面に見立てる画面仕様（CUI/CLI）の規約**:
  - CLI のコマンド群を「CLI 操作単位としての画面」に見立てて定義する場合（例: `uis-exec-commands`）、引数・オプションの表や使い方の詳細は書かず、**コマンドリファレンスを参照**します。
  - 文書には、**利用目的**、**操作の流れ（どのコマンドからどのコマンドへ進むか）**、**表示される項目の要点**、**エラー表示と利用者の次の手** に絞って記述します。
  - コマンド構文やフラグ定義の重複を排除し、業務フローとユーザーの操作手順・意思決定コンテキストに集中させます。
- 原則として 1 ファイル = 1 画面（または 1 つの業務目的を担う CLI コマンド群）。
- 規範語の体系は **必須**・**任意**・**禁止** で統一し、曖昧な表現（「原則」「推奨（必須）」など）は使用しません。

### 1.1. 対象者と期待効果

| 対象者                                  | 画面仕様（UIS）適用によって解決する課題                                                      | 確認可能な期待効果                                                                                            |
| --------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| ビジネスアナリスト（BA）・業務担当者    | レイアウトやコマンド構文の詳細に紛れて、本来の業務目的や操作フローの合意形成が滞る問題       | 目的・操作の流れ・表示要点・エラー時の次の手に絞ることで、業務対話と意思決定プロセスを迅速に合意できる        |
| ソフトウェアアーキテクト（ARC）・設計者 | 画面・CLI とバックエンドの責務境界や遷移条件が曖昧で、システム連携仕様に落とし込めない問題   | 画面間の遷移条件や引き渡しデータ、エラー時の回復方針が整理され、API・外部連携・状態管理設計へ的確に接続できる |
| 開発者（DEV）                           | コマンド仕様の多重管理により、リファレンス改訂時に画面仕様との不整合が発生する問題           | コマンド構文・引数はコマンドリファレンスを参照するため、二重管理なく一貫した UI/CLI 実装に専念できる          |
| 品質保証担当者（QE）                    | 正常系以外のエラーメッセージや復旧手順の要件が不明確で、エラーハンドリングの検証が漏れる問題 | エラー表示の要点と「利用者の次の手」が明文化されるため、例外処理・回復シナリオのテストを確実に設計できる      |
| プロダクトオーナー（PO）                | ユーザーがどのような流れで業務を遂行し、失敗時にどう対処できるのかが仕様から見えない問題     | 操作の流れとエラー回復アクションが明確になり、使いやすさと業務達成性を迅速に判断・承認できる                  |

## 2. 位置づけと用語定義

### 2.1. 成果物としての位置づけ

画面仕様（UIS）は、業務仕様ドメイン（`user-interface-model`）における成果物です。
業務フロー（bds/bps）やシステム化機能（sf）から導出され、業務ユーザーがシステムと対話する境界を定義します。
CLI コマンド群を画面に見立てる場合は、コマンドの正本であるコマンドリファレンス（`command-reference` など）や外部コマンド連携仕様（`ifx-cmd`）と連携し、業務操作の文脈と手順を定義します。

### 2.2. 用語定義

| 用語                       | 定義                                                                                             |
| -------------------------- | ------------------------------------------------------------------------------------------------ |
| 画面                       | 業務ユーザーが操作する単位。Web/GUI 画面、または CLI における一連の対話・操作コンテキスト        |
| 操作の流れ                 | 利用目的を達成するために、どのコマンド/操作からどのコマンド/操作へ進むかの順序と状態変化         |
| 表示項目                   | 画面または CLI 標準出力に表示する情報の要点（一覧列、詳細項目、集計値、状態メッセージ等）        |
| 操作                       | ユーザーが実行できるアクション。GUI のボタン押下・フォーム送信、または CLI コマンドの実行        |
| 遷移                       | 画面間またはコマンド実行後の移動。前提条件・遷移先・引き渡しデータを含む                         |
| バリデーション             | 入力値・指定値の業務妥当性判定（必須、形式、範囲、相関等）                                       |
| エラー表示と利用者の次の手 | 異常や制約違反時にユーザーに伝える表示要点と、回復のために利用者が次に取るべき具体的なアクション |
| コマンドリファレンス       | コマンド名、実行構文、引数、オプション、フラグの詳細を定義した正本文書                           |

## 3. ファイル命名・ID規則

- ファイル名:
  - GUI 画面: `uis-<番号>-<短い日本語名>.md`（例: `uis-0010-商品一覧.md`）
  - CLI コマンド群: `uis-<機能名>.md`（例: `uis-exec-commands.md`, `uis-sales-commands.md`）
- Frontmatter:
  - `id`: `uis-<kebab-case>`（例: `uis-product-list`, `uis-exec-commands`）
- ドキュメント名（画面名）:
  - 本文先頭の H1 に記述します（Frontmatter の `title` プロパティは使用しません）。

## 4. 推奨 Frontmatter 項目

Frontmatter は共通スキーマ（`docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml`）および [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、`specdojo:` 名前空間配下に置きます。

| 項目       | 説明                                                       | 必須 |
| ---------- | ---------------------------------------------------------- | ---- |
| id         | 画面ID（小文字ハイフン）                                   | ○    |
| type       | `ui` 固定                                                  | ○    |
| status     | `draft` / `ready` / `deprecated`                           | ○    |
| rulebook   | 準拠する rulebook ID（例: `specdojo:uis-rulebook`）        | ○    |
| `part_of`  | 所属する親・集約ドキュメントID（ID配列。未指定は `[]`）    | 任意 |
| `based_on` | 根拠となる仕様ID（API/業務フロー等。未指定時は `[]`）      | 任意 |
| supersedes | 置き換え対象のドキュメントID（ID配列。未指定時は `[]`）    | 任意 |
| relations  | 型付き参照（`satisfies`, `verifies`, `implements` の配列） | 任意 |

### 4.1. NG/OK例

- **NG例**:
  - `type: screen`（`ui` 以外は不可）
  - `id: UIS_ProductList`（大文字・アンダースコアは不可）
  - `title: 商品一覧`（Frontmatter への `title` の記述は不可。本文 H1 に記述する）
  - `extra_prop: foo`（未定義プロパティは不可）
- **OK例**:

```yaml
---
specdojo:
  id: uis-product-list
  type: ui
  status: draft
  rulebook: specdojo:uis-rulebook
  part_of: []
  based_on: []
---
```

## 5. 本文要件

各画面仕様ファイル（GUI 画面・CLI コマンド群画面仕様共通）は、以下の見出しを順番に並べます。

1. 概要
2. 対象ユーザー/利用目的
3. 操作の流れ
4. 表示項目
5. 操作
6. 遷移
7. バリデーション
8. エラー表示と利用者の次の手
9. メモ / 将来課題

各章の目的・記述規約は以下のとおりです。

| 章見出し                   | 必須/任意 | 目的と記述規約                                                                                                                                                  |
| -------------------------- | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 概要                       | 必須      | 画面または CLI コマンド群が何を達成するかを、業務ユーザーの言葉で 1〜2 文で簡潔に記述します。                                                                   |
| 対象ユーザー/利用目的      | 必須      | 想定する対象ユーザー（業務ロール）と、そのユーザーがこの画面/コマンド群を利用する業務目的を箇条書きで記述します。                                               |
| 操作の流れ                 | 必須      | 業務目的を達成するための標準的な操作順序を記述します。CLI では「どのコマンドからどのコマンドへ進むか」の典型フローを順序付きリストまたは Mermaid で明記します。 |
| 表示項目                   | 必須      | 画面または CLI 標準出力に表示されるべき情報の要点を記述します。レイアウトではなく「何が表示されるか」に絞り、CLI では出力の要点を整理します。                   |
| 操作                       | 必須      | ユーザーが実行できる操作（ボタン押下、コマンド実行など）を記述します。**CLI コマンド群では引数・オプションの表は持たず、コマンドリファレンスを参照します**。    |
| 遷移                       | 必須      | 操作後の状態変化、画面間遷移、または別コマンドへの移行を記述します。契機、遷移元、遷移先、条件、引き渡しデータを明記します。                                    |
| バリデーション             | 任意      | 入力欄や引数・パラメータの業務妥当性チェック条件（必須、範囲、形式、相関等）を記述します。入力項目がない場合は省略可能です。                                    |
| エラー表示と利用者の次の手 | 必須      | 代表的なエラー事象（入力不備、権限不足、状態不整合等）における「表示メッセージの要点」と、回復のために「利用者が次に取るべき具体的なアクション」を記述します。  |
| メモ / 将来課題            | 任意      | 現フェーズでは対応しない拡張要望、技術的検討事項、運用上の留意点などを記述します。不要な場合は省略可能です。                                                    |

## 6. 記述ガイド

### 6.1. 概要

画面または CLI コマンド群の役割を、業務視点で明確に 1〜2 文で書きます。

- 良い例: 「店頭で来店客が購入する駄菓子のバーコードを読み取り、合計金額の計算と販売登録を行うためのレジ操作コマンド群。」
- 悪い例: 「`kinuya sales` CLI のパーサーとハンドラーの仕様。」（実装詳細・内部構造に言及している）

### 6.2. 対象ユーザー/利用目的

- 対象ユーザー: 業務ロール（例: 店員、店主、システム管理者）
- 利用目的: 業務上の達成ゴール（例: 商品を検索し、在庫数を確認した上で販売登録へ進む）

### 6.3. 操作の流れ

業務目的を完了するまでの標準的な操作順序を示します。
CLI コマンド群では、利用者がどのコマンドを実行してセッションを開始し、どのような順序でコマンドを実行して完了に至るかを明記します。

推奨形式（順序リスト例）:

1. `sales start`: 販売セッションを開始し、取引番号を発行する。
2. `sales add`: 商品コードと数量を入力して明細を追加する（繰り返し）。
3. `sales total`: 合計金額・税額を確認し、来店客へ提示する。
4. `sales complete`: 預かり金を入力して会計を確定し、釣銭を表示して取引を完了する。

※分岐や差し戻しが複雑な場合は Mermaid の状態遷移図やフローチャートを用いても構いません。

### 6.4. 表示項目

画面または CLI 標準出力に表示する情報の要点を記述します。
CLI では、全プロパティのダンプではなく、ユーザーが業務判断に必要な情報の要点を整理します。

推奨表フォーマット:

| 項目名     | 種別/対象 | 表示内容要点                         | 備考                        |
| ---------- | --------- | ------------------------------------ | --------------------------- |
| 商品名     | 一覧/出力 | 登録された商品の正式名称             | 例: 「きぬや特製 きなこ棒」 |
| 単価       | 明細      | 1個あたりの税込販売価格              | 10円単位                    |
| 数量       | 明細      | 今回追加した購入数量                 | 1以上の整数                 |
| 現在合計額 | サマリー  | 現在の取引に含まれる全明細の暫定合計 | 小計表示に相当              |

### 6.5. 操作

ユーザーが実行できるアクション（GUI 操作または CLI コマンド）を列挙します。
**CLI コマンド群の場合、引数やオプションの表は作成せず、正本となるコマンドリファレンスを参照します。**

推奨表フォーマット（CLI コマンド群の例）:

| 操作名   | 対象コマンド     | 利用目的・操作の意味                           | 正本リファレンス                                                                |
| -------- | ---------------- | ---------------------------------------------- | ------------------------------------------------------------------------------- |
| 販売開始 | `sales start`    | 新規の販売取引セッションを開始する             | `[[command-reference#sales-start\|きぬや CLI リファレンス: sales start]]`       |
| 明細追加 | `sales add`      | 取引に商品と数量を追加する                     | `[[command-reference#sales-add\|きぬや CLI リファレンス: sales add]]`           |
| 会計完了 | `sales complete` | 預かり金を登録し、釣銭計算と販売記録を確定する | `[[command-reference#sales-complete\|きぬや CLI リファレンス: sales complete]]` |

### 6.6. 遷移

操作後の状態変化や画面間移動を記述します。

推奨表フォーマット:

| 遷移名     | 契機（操作/コマンド） | 遷移元状態 | 遷移先状態 | 条件                | 引き渡しデータ   | 備考                           |
| ---------- | --------------------- | ---------- | ---------- | ------------------- | ---------------- | ------------------------------ |
| 取引開始   | `sales start`         | 待機中     | 明細登録中 | 前の取引が完了      | 取引ID           | 新規セッション発行             |
| 会計確定へ | `sales complete`      | 明細登録中 | 完了       | 預かり金 ≥ 合計金額 | 取引ID、預かり金 | 釣銭を出力し取引セッション終了 |
| 取引中断   | `sales cancel`        | 明細登録中 | 待機中     | 取消確認に同意      | 取引ID           | 明細を破棄して待機状態へ戻る   |

### 6.7. バリデーション

入力値の業務妥当性チェック条件（必須、形式、範囲、相関等）を簡潔に記述します。

- 商品コード: 有効な登録済み商品コードであること。
- 販売数量: 1 以上の整数であり、現在の在庫数以下であること。
- 預かり金: 請求合計金額以上の金額であること。

### 6.8. エラー表示と利用者の次の手

異常や制約違反が発生した際に、ユーザーに表示するメッセージの要点と、利用者が状況を打開・回復するために次に取るべき具体的なアクション（次の手）を記述します。

推奨表フォーマット:

| エラー事象       | 表示要点                                   | 利用者の次の手（回復アクション）                           |
| ---------------- | ------------------------------------------ | ---------------------------------------------------------- |
| 商品コード未登録 | 「商品コード [XXXX] は登録されていません」 | コードの打ち間違いを確認するか、商品一覧コマンドで確認する |
| 在庫不足         | 「在庫数が不足しています（現在庫: N個）」  | 数量を現在庫以下に減らして再入力するか、バックヤードを確認 |
| 預かり金不足     | 「預かり金が不足しています（不足: N円）」  | 来店客から不足分の代金を追加で受け取り、再入力する         |
| セッション未開始 | 「販売取引が開始されていません」           | `sales start` コマンドを実行して販売を開始する             |

## 7. 禁止事項

| 項目                                       | 理由                                                                   |
| ------------------------------------------ | ---------------------------------------------------------------------- |
| CLI コマンドの引数・オプション表の再掲     | コマンドリファレンスと二重管理になり、不整合や陳腐化を招くため         |
| ワイヤーフレーム/ピクセル座標/CSS指定      | 画面レイアウトは要求定義の段階では過剰であり、変更に弱いため           |
| 物理テーブル名・物理カラム名・SQL全文      | 概念的な業務データから逸脱し、実装結合を高めてしまうため               |
| 実装クラス名/関数名/UIライブラリ名         | 実装詳細に依存し、フレームワーク選定や改修時に仕様書が陳腐化するため   |
| クリック手順やキー入力の逐語列挙           | 操作の本質的意味や業務目的が埋没し、可読性と保守性が低下するため       |
| 利用者の次の手を伴わないエラー表示の羅列   | 障害発生時にユーザーがどう行動すれば業務を継続できるか判断できないため |
| Frontmatter への `type: screen` などの記述 | メタ情報スキーマ違反（`ui` 固定）となり機械検証で失敗するため          |

## 8. サンプル

完成例の正本は `specdojo:uis-sample` を参照してください。
以下は形式の輪郭を示す最小例です。

```markdown
---
specdojo:
  id: uis-sales-commands
  type: ui
  status: draft
  rulebook: specdojo:uis-rulebook
  part_of: []
  based_on: []
---

# 販売業務コマンド群 画面仕様

## 1. 概要

店頭での販売登録・合計確認・会計完了を行うための CLI 操作群。

## 2. 対象ユーザー/利用目的

- 対象ユーザー: 店員、店主
- 利用目的: 来店客が購入する駄菓子を登録し、代金を受け取って販売を記録する。

## 3. 操作の流れ

1. `sales start` で販売セッションを開始する。
2. `sales add` で商品と数量を追加する（繰り返し）。
3. `sales complete` で預かり金を登録し会計を完了する。

## 4. 表示項目

| 項目名   | 種別 | 表示内容要点        | 備考             |
| -------- | ---- | ------------------- | ---------------- |
| 商品名   | 出力 | 追加した商品の名称  | -                |
| 合計金額 | 出力 | 税込合計請求金額    | -                |
| 釣銭     | 出力 | 預かり金 - 合計金額 | 会計完了時に表示 |

## 5. 操作

| 操作名   | 対象コマンド     | 利用目的・操作の意味           | 正本リファレンス                                                        |
| -------- | ---------------- | ------------------------------ | ----------------------------------------------------------------------- |
| 販売開始 | `sales start`    | 取引セッションを開始する       | `[[command-reference#sales-start\|CLIリファレンス: sales start]]`       |
| 明細追加 | `sales add`      | 商品と数量を取引に追加する     | `[[command-reference#sales-add\|CLIリファレンス: sales add]]`           |
| 会計完了 | `sales complete` | 預かり金を登録し会計を確定する | `[[command-reference#sales-complete\|CLIリファレンス: sales complete]]` |

## 6. 遷移
```
