# 画面仕様（UI）作成ルール

User Interface Specification (UIS) Authoring Rule

本ドキュメントは、業務分析・要求定義のために **画面仕様（User Interface: UI）を統一形式で記述する標準ルール** です。
Web やデスクトップ等の GUI 画面を対象とします。コマンドラインインターフェース（CLI）の仕様は本ルールの対象外とし、CLI仕様（[[specdojo:clis-rulebook|specdojo:clis-rulebook]]）に従って記述します。

## 1. 全体方針

- 画面仕様は、**業務ユーザー視点** での画面の利用目的・表示項目・操作・遷移・エラー表示を明確に記述します。
- 画面の機能と業務対話に着目し、**画面のレイアウトやワイヤーフレーム（ピクセル・座標・CSS・コンポーネント配置など）は含めません**。画面をまたぐ色・文字・余白、部品、レイアウトの型、状態表示、アクセシビリティは [[specdojo:dss-rulebook|デザインシステム（DSS）]] で定めます。画面ごとのワイヤーフレームは文書として保守せず、UIS と DSS から試作を作り、プロダクトのリポジトリに置きます。
- 実装詳細（例: 物理テーブル名、物理カラム名、SQL、実装クラス/関数名、UIライブラリ名）は記載しません。
- コマンドラインインターフェース（CLI）の仕様は本ルールの対象外とし、CLI仕様（[[specdojo:clis-rulebook|specdojo:clis-rulebook]]）で記述します。
- 原則として 1 ファイル = 1 画面。
- 規範語の体系は **必須**・**任意**・**禁止** で統一し、曖昧な表現（「原則」「推奨（必須）」など）は使用しません。

### 1.1. 対象者と期待効果

| 対象者                                  | 画面仕様（UIS）適用によって解決する課題                                                      | 確認可能な期待効果                                                                                                         |
| --------------------------------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| ビジネスアナリスト（BA）・業務担当者    | レイアウトや装飾の詳細に紛れて、本来の業務目的や画面操作・対話フローの合意形成が滞る問題     | 画面の目的・表示項目・操作・エラー時の次の手に絞ることで、業務対話と意思決定プロセスを迅速に合意できる                     |
| ソフトウェアアーキテクト（ARC）・設計者 | 画面とバックエンドの責務境界や画面間遷移条件が曖昧で、システム連携仕様に落とし込めない問題   | 画面間の遷移条件や引き渡しデータ、エラー回復方針が整理され、API・状態管理設計へ的確に接続できる                            |
| 開発者（DEV）                           | 画面コンポーネントやレイアウトの試行錯誤により業務対話や状態遷移の実装が後回しになる問題     | レイアウトから独立して操作・遷移・バリデーション・エラー回復が明確化されているため、UIロジックと状態管理の実装に集中できる |
| 品質保証担当者（QE）                    | 正常系以外のエラーメッセージや復旧手順の要件が不明確で、エラーハンドリングの検証が漏れる問題 | エラー表示の要点と「利用者の次の手」が明文化されるため、例外処理・回復シナリオのテストを確実に設計できる                   |
| プロダクトオーナー（PO）                | ユーザーがどのような流れで画面を操作し、失敗時にどう対処できるのかが仕様から見えない問題     | 操作とエラー回復アクションが明確になり、使いやすさと業務達成性を迅速に判断・承認できる                                     |

## 2. 位置づけと用語定義

### 2.1. 成果物としての位置づけ

画面仕様（UIS）は、業務仕様ドメイン（`user-interface-model`）における成果物です。
業務プロセス仕様（`bps`）やシステム化機能（`sf`）から導出され、業務ユーザーが GUI 画面を介してシステムと対話する境界を定義します。
なお、システム自身が提供するコマンドラインインターフェース（CLI）の仕様は、CLI仕様（[[specdojo:clis-rulebook|specdojo:clis-rulebook]]）として定義します。

### 2.2. 用語定義

| 用語                       | 定義                                                                                             |
| -------------------------- | ------------------------------------------------------------------------------------------------ |
| 画面                       | 業務ユーザーが操作する GUI 画面の単位。目的・表示項目・操作・遷移を持つ                          |
| 表示項目                   | 画面に表示する情報の要点（一覧列、詳細項目、集計値、状態メッセージ等）                           |
| 操作                       | ユーザーが実行できるアクション。ボタン押下、フォーム入力、一覧行選択等                           |
| 遷移                       | 画面間の移動。契機・遷移元・遷移先・条件・引き渡しデータを含む                                   |
| バリデーション             | 入力値・指定値の業務妥当性判定（必須、形式、範囲、相関等）                                       |
| エラー表示と利用者の次の手 | 異常や制約違反時にユーザーに伝える表示要点と、回復のために利用者が次に取るべき具体的なアクション |

## 3. ファイル命名・ID規則

- ファイル名:
  - GUI 画面: `uis-<番号>-<短い日本語名>.md`（例: `uis-0010-商品一覧.md`）
- Frontmatter:
  - プロダクト文書: `uis-<kebab-case>`（例: `uis-product-list`）。namespace は付けません。
  - プロジェクト文書: `<project-id>:uis-<kebab-case>`（例: `prj-0001:uis-product-list`）。同じプロジェクトの中で参照するときは `<project-id>:` を省略できます。
  - SpecDojo が同梱する sample: `specdojo:uis-sample`。記述例を識別するための例外で、成果物の ID には `specdojo:` を付けません。
- ドキュメント名（画面名）:
  - 本文先頭の H1 に記述します（Frontmatter の `title` プロパティは使用しません）。

## 4. 推奨 Frontmatter 項目

Frontmatter は共通スキーマ（`docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml`）および [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、`specdojo:` 名前空間配下に置きます。

| 項目       | 説明                                                       | 必須 |
| ---------- | ---------------------------------------------------------- | ---- |
| id         | 画面ID（小文字ハイフン）                                   | ○    |
| type       | `ui` 固定                                                  | ○    |
| status     | `draft` / `ready` / `deprecated`                           | ○    |
| rulebook   | 準拠する rulebook ID（`specdojo:uis-rulebook`）            | ○    |
| `part_of`  | 所属する親・集約ドキュメントID（ID配列。未指定は `[]`）    | 任意 |
| `based_on` | 根拠となる仕様ID（API/業務フロー等。未指定時は `[]`）      | 任意 |
| supersedes | 置き換え対象のドキュメントID（ID配列。未指定時は `[]`）    | 任意 |
| relations  | 型付き参照（`satisfies`, `verifies`, `implements` の配列） | 任意 |

### 4.1. NG/OK例

- **NG例**:
  - `type: screen`（`ui` 以外は不可）
  - `id: UIS_ProductList`（大文字・アンダースコアは不可）
  - `title: 商品一覧`（Frontmatter への `title` の記述は不可。本文 H1 に記述する）
  - `extra_prop: foo`（未定義プロパティは不可）
- **OK例**:

```yaml
---
specdojo:
  id: uis-product-list
  type: ui
  status: draft
  rulebook: specdojo:uis-rulebook
  part_of: []
  based_on: []
---
```

## 5. 本文要件

各画面仕様ファイルは、以下の見出しを順番に並べます。

1. 概要
2. 対象ユーザー/利用目的
3. 表示項目
4. 操作
5. 遷移
6. バリデーション
7. エラー表示と利用者の次の手
8. メモ / 将来課題

各章の目的・記述規約は以下のとおりです。

| 章見出し                   | 必須/任意 | 目的と記述規約                                                                                                                                                         |
| -------------------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 概要                       | 必須      | 画面が何を達成するかを、業務ユーザーの言葉で 1〜2 文で簡潔に記述します。                                                                                               |
| 対象ユーザー/利用目的      | 必須      | 想定する対象ユーザー（業務ロール）と、そのユーザーがこの画面を利用する業務目的を箇条書きで記述します。                                                                 |
| 表示項目                   | 必須      | 画面に表示されるべき情報の要点を記述します。レイアウトではなく「何が表示されるか」に絞り、一覧・詳細・状態表示等の要点を整理します。                                   |
| 操作                       | 必須      | ユーザーが実行できる操作（ボタン押下、フォーム入力、行選択等）と、前提条件・結果（更新/遷移）を記述します。クリック手順の逐語列挙ではなく操作の意味を書きます。        |
| 遷移                       | 必須      | 操作後の画面間遷移を記述します。契機、遷移元、遷移先、条件、引き渡しデータを明記します。                                                                               |
| バリデーション             | 任意      | 入力欄の業務妥当性チェック条件（必須、範囲、形式、相関等）を記述します。入力項目がない画面は省略可能です。                                                             |
| エラー表示と利用者の次の手 | 必須      | 代表的なエラー事象（入力不備、権限不足、対象なし、通信障害等）における「表示メッセージの要点」と、回復のために「利用者が次に取るべき具体的なアクション」を記述します。 |
| メモ / 将来課題            | 任意      | 現フェーズでは対応しない拡張要望、技術的検討事項、運用上の留意点などを記述します。不要な場合は省略可能です。                                                           |

## 6. 記述ガイド

### 6.1. 概要

画面の役割を、業務視点で明確に 1〜2 文で書きます。

- 良い例: 「店頭で来店客が購入する駄菓子を登録し、合計金額の計算と会計確定を行うための販売レジ画面。」
- 悪い例: 「`SalesRegisterComponent` の state と event handler の仕様。」（実装詳細・コンポーネント構造に言及している）

### 6.2. 対象ユーザー/利用目的

- 対象ユーザー: 業務ロール（例: 店員、店主、システム管理者）
- 利用目的: 業務上の達成ゴール（例: 商品を検索し、在庫数を確認した上で販売登録へ進む）

### 6.3. 表示項目

画面に表示する情報の要点を記述します。レイアウト指定ではなく「何が表示されるか」を記述します。

推奨表フォーマット:

| 項目名   | 種別     | 表示内容要点                     | 編集可否 | 備考                        |
| -------- | -------- | -------------------------------- | -------- | --------------------------- |
| 商品名   | 一覧     | 登録された商品の正式名称         | 不可     | 例: 「きぬや特製 きなこ棒」 |
| 単価     | 明細     | 1個あたりの税込販売価格          | 不可     | 10円単位                    |
| 数量     | 明細     | 今回購入する数量                 | 可       | 1以上の整数                 |
| 合計金額 | サマリー | 取引に含まれる全明細の税込合計額 | 不可     | 請求金額                    |

### 6.4. 操作

ユーザーが実行できる操作（アクション）を列挙し、前提条件と結果（更新/遷移）を明確にします。
クリック手順の逐語列挙ではなく、操作の業務的意味を記述します。

推奨表フォーマット:

| 操作名   | 対象               | 前提条件                               | 結果（更新/遷移）                                  | 備考                       |
| -------- | ------------------ | -------------------------------------- | -------------------------------------------------- | -------------------------- |
| 商品追加 | 商品コード入力欄   | 有効な商品コードが入力されている       | 販売明細に商品を追加し、合計金額を再計算する       | バーコードスキャンでも発火 |
| 数量変更 | 明細行の数量       | 対象の明細が存在する                   | 指定行の数量を変更し、小計および合計金額を更新する | 1以上の整数                |
| 会計完了 | 「会計確定」ボタン | 明細が1件以上あり、預かり金 ≥ 合計金額 | 販売実績を記録し、釣銭金額を表示して取引を完了する | -                          |

### 6.5. 遷移

画面間の移動を記述します。

推奨表フォーマット:

| 遷移名     | 契機（操作）       | 遷移元画面   | 遷移先画面         | 条件                | 引き渡しデータ           | 備考                       |
| ---------- | ------------------ | ------------ | ------------------ | ------------------- | ------------------------ | -------------------------- |
| 取引開始   | 「新規販売」ボタン | 店舗待機画面 | 販売登録画面       | なし                | 取引ID                   | 新規取引セッション開始     |
| 商品検索へ | 「商品検索」ボタン | 販売登録画面 | 商品検索ダイアログ | なし                | なし                     | モーダル表示               |
| 会計完了へ | 「会計確定」ボタン | 販売登録画面 | 販売完了画面       | 預かり金 ≥ 合計金額 | 取引ID、預かり金、釣銭額 | レシート発行後に待機画面へ |

### 6.6. バリデーション

入力値の業務妥当性チェック条件（必須、形式、範囲、相関等）を簡潔に記述します。

- 商品コード: 有効な登録済み商品コードであること。
- 販売数量: 1 以上の整数であり、現在の在庫数以下であること。
- 預かり金: 請求合計金額以上の金額であること。

### 6.7. エラー表示と利用者の次の手

異常や制約違反が発生した際に、ユーザーに表示するメッセージの要点と、利用者が状況を打開・回復するために次に取るべき具体的なアクション（次の手）を記述します。

推奨表フォーマット:

| エラー事象       | 表示要点                                   | 原因                               | 利用者の次の手（回復アクション）                                   |
| ---------------- | ------------------------------------------ | ---------------------------------- | ------------------------------------------------------------------ |
| 商品コード未登録 | 「商品コード [XXXX] は登録されていません」 | 存在しない商品コードを入力した     | コードの打ち間違いを確認するか、「商品検索」ボタンから商品を探す   |
| 在庫不足         | 「在庫数が不足しています（現在庫: N個）」  | 指定数量が現在庫数を超えている     | 数量を現在庫以下に減らして再入力するか、バックヤード在庫を確認する |
| 預かり金不足     | 「預かり金が不足しています（不足: N円）」  | 入力金額が請求合計金額未満         | 来店客から不足分の代金を追加で受け取り、再入力する                 |
| サーバー通信切断 | 「店舗サーバーとの通信に失敗しました」     | ネットワーク瞬断またはサーバー停止 | ネットワーク接続を確認し、画面上の「再試行」ボタンを押す           |

### 6.8. メモ / 将来課題

現フェーズでは対応しない拡張要望、技術的検討事項、UI/UX の留意点などを記述します。

## 7. 禁止事項

| 項目                                                     | 理由                                                                              |
| -------------------------------------------------------- | --------------------------------------------------------------------------------- |
| CLI コマンド仕様の混入                                   | CLI の仕様は CLI仕様（clis）で記述し、責務と設計観点を分離するため                |
| ワイヤーフレーム/ピクセル座標/CSS指定                    | 画面レイアウトは要求定義の段階では過剰であり、変更に弱いため                      |
| 物理テーブル名・物理カラム名・SQL全文                    | 概念的な業務データから逸脱し、実装結合を高めてしまうため                          |
| 実装クラス名/関数名/UIライブラリ名                       | 実装詳細に依存し、フレームワーク選定や改修時に仕様書が陳腐化するため              |
| クリック手順やキー入力の逐語列挙                         | 操作の本質的意味や業務目的が埋没し、可読性と保守性が低下するため                  |
| 利用者の次の手を伴わないエラー表示の羅列                 | 障害発生時にユーザーがどう行動すれば業務を継続できるか判断できないため            |
| Frontmatter への `type: screen` などの記述               | メタ情報スキーマ違反（`ui` 固定）となり機械検証で失敗するため                     |
| 本文中への sample / recipe / template へのリンク章の設置 | 実践の型の解決は Frontmatter を正本とし、本文リンクは参照手段として機能しないため |

## 8. 運用ルール

- **完成例の正本は sample**: 完成例は `docs/ja/specdojo/samples/uis-sample.md` を正本とし、rulebook 本文にはサンプルの章を置きません。
- **CLI仕様との分担**: CLI コマンド群の仕様は本ルールでは扱わず、CLI仕様（[[specdojo:clis-rulebook|specdojo:clis-rulebook]]）に従って記述します。
- **レイアウト変更と画面仕様の分離**: ボタンの配置場所やカラーリング、フォント等のスタイリング変更が発生しても、画面仕様（UIS）は改訂しません。画面仕様を改訂するのは、画面の利用目的、表示項目、操作の意味、画面間遷移、またはエラー時の回復アクションに変更が生じた場合のみとします。
- **スキーマ整合性の担保**: Frontmatter の `type` は常に `ui` を使用し、`rulebook` には対応する rulebook ID（`specdojo:uis-rulebook`）を明記します。
