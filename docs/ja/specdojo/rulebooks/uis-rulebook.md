# 画面仕様（UIS）作成ルール

User Interface Specification (UIS) Authoring Rule

業務ユーザーが GUI 画面を介して達成する目的、表示情報、操作、遷移、入力の制約、エラー時の回復を統一形式で記述するためのルールです。

## 1. 全体方針

- Web・タブレット・デスクトップ・エディタ拡張の入力欄などの GUI を対象とし、1 ファイルで 1 画面を定義します。付随する確認ダイアログは、その画面の操作・遷移に含めます。CLI は [[specdojo:clis-rulebook|CLI仕様作成ルール]] に従います。
- 利用者から観察できる条件と結果を記述します。正常系に加え、空の一覧、処理中、入力不備、権限不足、通信失敗など、対象画面で起こる状態を扱います。
- 表示項目の意味と操作の業務上の効果を定義します。画面をまたぐ色・文字・部品・レイアウトの型・アクセシビリティは [[specdojo:dss-rulebook|デザインシステム（DSS）]] で定め、画面ごとのワイヤーフレームは文書として保守しません。
- 同じ判断は 1 か所に書きます。入力の条件は「バリデーション」、失敗時の表示と回復は「エラー表示と利用者の次の手」を正とし、ほかの章は章タイトルで参照します。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直しません。

## 2. 位置づけ

- 業務仕様の `user-interface-model` に属し、業務プロセス仕様（`bps`）やシステム化機能（`sf`）を利用者との対話へ具体化します。共通の業務規則・用語は上位仕様を正本として参照します。
- 内部 API、保存方式、UI 部品の設計は後続のシステム設計で扱います。画面仕様には、利用者が確認できる保存の成否や再試行の条件までを記述します。

## 3. ファイル命名・ID規則

- ファイル名は `uis-<term>.md` とし、`<term>` は画面を表す英小文字の kebab-case とします（例: `uis-sales-register.md`）。
- 文書 ID はプロダクトの文書で `uis-<term>`、プロジェクトの文書で `<project-id>:uis-<term>` とし、成果物カタログの宣言と一致させます。同梱の完成例は `specdojo:uis-sample` とします。
- H1 には画面名を書きます。命名の共通原則は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従います。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- `specdojo.type` は `ui`、`specdojo.rulebook` は `specdojo:uis-rulebook` とします。
- `part_of` には所属する画面索引、`based_on` には根拠とした作成済みの業務プロセス・機能の ID を書きます。関係がなければ空配列にし、未作成の文書 ID を書きません。

```yaml
---
specdojo:
  id: uis-sales-register
  type: ui
  status: draft
  rulebook: specdojo:uis-rulebook
  part_of: []
  based_on: []
---
```

## 5. 本文要件

章は次の順で構成します。任意章を省略した場合は番号を詰めます。

| 章                         | 必須/任意                        | 目的と記述要件                                                                                                        |
| -------------------------- | -------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 概要                       | 必須                             | 対象業務と画面で達成する結果を 1〜2 文で示す。利用環境や対象範囲を補足できる                                          |
| 対象ユーザー/利用目的      | 必須                             | 操作する業務ロールと、各ロールが達成する業務目的を示す。権限差があれば操作範囲を示す                                  |
| 表示項目                   | 必須                             | 項目名、種別、表示内容の意味、編集可否、初期値・未取得時・更新契機などを示す                                          |
| 操作                       | 必須                             | 操作名、対象、前提条件、結果を示す。更新の確定時点、処理中や失敗後の再実行条件を含める                                |
| 遷移                       | 必須                             | 契機、遷移元、遷移先、条件、引き渡す情報を示す。戻る・中止時の入力の保持/破棄も示す。画面間移動がなければその旨を記す |
| バリデーション             | 任意。ただし入力がある場合は必須 | 対象、必須性、形式・範囲・相関、判定時点、違反時の扱いを示す                                                          |
| エラー表示と利用者の次の手 | 必須                             | 発生条件、表示要点、保持/更新される状態、利用者の回復操作とその結果を示す                                             |
| メモ / 将来課題            | 任意                             | 現在の対象範囲に含めない拡張と、未決事項の論点と影響を示す                                                            |

関連する操作・遷移・入力制約・エラーは、同じ名称で対応づけます。既存の要求・業務規則・受入条件は参照し、全文を再掲しません。

## 6. 記述ガイド

表の列は推奨形式であり、本文要件を満たす別形式も使えます。

### 6.1. 概要

- **判断基準**: どの業務のどの場面で、誰が何を完了する画面かが分かること。表示項目や操作の全件はそれぞれの章へ置く。
- **良い例**: 「店員が店頭で購入商品と預かり金を登録し、販売を確定して釣銭を確認する画面。」
- **悪い例**: 「販売を便利にする画面。」（利用者と完了する業務が分からない）

### 6.2. 対象ユーザー/利用目的

- **判断基準**: ロールごとに利用場面と達成する結果が対応し、権限差があれば許可される操作の範囲が分かること。顧客が直接操作するか、店員を介して結果を受け取るかを区別する。
- **良い例**: 「店員・店主が接客中に購入明細と釣銭を確認する。両ロールに販売登録を許可する。来店客へは担当者が合計額を伝える。」
- **悪い例**: 「ユーザーがシステムを利用する。」（業務ロールと利用目的が定まらない）

### 6.3. 表示項目

- **判断基準**: 表示する業務情報と、空・未取得・処理中を含む値の意味が読み取れること。金額や数量には単位を記す。計算値は算出の意味か上位規則を参照し、入力の許容範囲は「バリデーション」に置く。
- **良い例**: 「合計請求金額 ／ 集計 ／ 明細小計の合計、円単位 ／ 不可 ／ 明細なしは 0 円。追加・数量変更・削除の成功時に再計算」
- **悪い例**: 「合計欄を右下に赤色で表示する。」（値の意味や更新条件が定まらない）

### 6.4. 操作

- **判断基準**: 操作の実行可否と、成功・中止・失敗後の業務状態を判定できること。保存や確定を伴う操作では、処理中の再操作、結果が不明な場合の確認方法、再試行できる条件を記す。
- **良い例**: 「会計確定 ／ 明細があり、入力制約を満たす登録中の取引 ／ 処理中は再操作を無効化。成功時に販売・在庫を確定して完了画面へ移る。結果不明時は「エラー表示と利用者の次の手」に従う」
- **悪い例**: 「確定ボタンを押すと保存する。」（保存の条件や二重操作時の扱いが不明）

### 6.5. 遷移

- **判断基準**: 流入・流出・戻りを、契機と業務上の条件から辿れること。ダイアログを介する場合は確定と取り消しの両方を示し、渡す情報がなければ「なし」と記す。未作成の遷移先は画面名・ID をバッククォートで記す。
- **良い例**: 「商品選択から復帰 ／ 「選択」 ／ `商品検索画面` ／ `販売登録画面` ／ 商品を選択済み ／ 商品コード。既存明細を保持」
- **悪い例**: 「選択すると次画面へ進む。」（行き先と受け渡し情報が定まらない）

### 6.6. バリデーション

- **判断基準**: 同じ入力に同じ可否を判断でき、境界値で検証できること。入力時と確定時で条件が異なれば区別し、失敗時に前の有効値を保持するか、修正用に入力値を残すかを記す。
- **良い例**: 「数量 ／ 必須 ／ 1〜999 の整数かつ現在庫数以下 ／ 数量変更時と会計確定時 ／ 明細・合計は直前の有効値を保持」
- **悪い例**: 「数量が適切であること。」（許容範囲も確認時点も判定できない）

### 6.7. エラー表示と利用者の次の手

- **判断基準**: 利用者が現在の状態、確定の有無、次に実行できる操作を判断できること。内部例外名を表示要点の代わりにしない。回復に別画面や運用担当者が要る場合は、行き先と渡す情報を示す。
- **良い例**: 「会計結果不明 ／ 確定要求後に応答を受信できない ／ 「会計結果を確認してください」と取引番号 ／ 明細と預かり金を保持し、編集・会計確定を無効化 ／ 「結果確認」で同じ取引を照会する」
- **悪い例**: 「通信エラー。もう一度確定する。」（確定済みの取引を再登録するおそれがある）

### 6.8. メモ / 将来課題

- **判断基準**: 現在の動作と将来の拡張を区別できること。未決事項は `_UNDECIDED_` などを付けて論点と影響を書き、管理台帳の区分・担当・判断時期の列は設けない（追跡は登録簿で行う）。現行動作に要る判断はこの章だけに置かない。
- **良い例**: 「電子決済は将来の拡張とし、導入時に決済方法と取消手順を決める。」
- **悪い例**: 「エラー時の扱いは後で検討する。」（現行画面を実装・検証する条件が欠ける）

## 7. 禁止事項

| 禁止する記述                                                              | 理由                                             |
| ------------------------------------------------------------------------- | ------------------------------------------------ |
| CLI コマンド群を画面・画面遷移として定義する                              | CLI 固有の要件は clis が担うため                 |
| ワイヤーフレーム、配置図、ピクセル座標、CSS、色・フォント・部品配置の指定 | 業務仕様の判断範囲を越えるため                   |
| 物理テーブル・物理カラム・SQL・実装クラスや関数・UI ライブラリの指定      | 後続設計の選択に結合するため                     |
| クリックやキー入力の逐語列挙だけで操作を説明する                          | 操作の前提条件と業務上の効果を判断できないため   |
| 回復操作を伴わないエラー一覧、結果不明の更新を無条件に再実行させる指示    | 利用者が業務を安全に再開できる条件が欠けるため   |
| 入力の条件や回復の手順を、正とする章以外で言い直す                        | 同じ判断が複数か所に書かれ、改訂時に食い違うため |
| 共通の業務規則や上位仕様の全文再掲                                        | 正本との不整合や更新漏れを招くため               |
