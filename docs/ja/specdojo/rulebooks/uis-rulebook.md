# 画面仕様（UIS）作成ルール

User Interface Specification (UIS) Authoring Rule

業務ユーザーが GUI 画面を介して達成する目的、表示情報、操作、遷移、入力の制約、エラー時の回復を統一形式で記述するためのルールです。

## 1. 全体方針

- Web・タブレット・デスクトップ等の GUI を対象とし、1 ファイルで 1 画面を定義します。付随する確認ダイアログは、その画面の操作・遷移に含められます。
- 利用者から観察できる条件と結果を記述します。正常系に加え、空の一覧、処理中、入力不備、権限不足、通信失敗など、対象画面で起こる状態を扱います。
- CLI の仕様は [[specdojo:clis-rulebook|CLI仕様作成ルール]] に従います。
- 表示項目の意味と操作の業務上の効果を定義します。ワイヤーフレーム、レイアウト、装飾、内部実装は「禁止事項」に従います。画面をまたぐ色・文字・余白、部品、レイアウトの型、状態表示、アクセシビリティは [[specdojo:dss-rulebook|デザインシステム（DSS）]] で定めます。画面ごとのワイヤーフレームは文書として保守せず、UIS と DSS から試作を作ります。
- 規範語は **必須**・**任意**・**禁止** で統一します。条件付きの要件には適用条件を明記します。

### 1.1. 利用者と確認すること

| 利用者                               | 本書に従う画面仕様で確認すること                     |
| ------------------------------------ | ---------------------------------------------------- |
| 業務担当者・ビジネスアナリスト（BA） | 業務目的、対象ロール、表示情報と業務上の判断の対応   |
| 設計者（ARC）・開発者（DEV）         | 操作前後の状態、画面間の受け渡し、更新の確定時点     |
| 品質保証担当者（QE）                 | 入力境界、遷移条件、失敗時の状態と回復操作の期待結果 |
| プロダクトオーナー（PO）             | 対象範囲と、利用者が業務を完了できる条件             |

## 2. 位置づけ

- 業務仕様の `user-interface-model` に属し、業務プロセス仕様（`bps`）やシステム化機能（`sf`）を利用者との対話へ具体化します。根拠とする成果物は `based_on` で参照します。
- 共通の業務規則・用語は上位仕様を正本として参照し、画面固有の表示・入力・操作条件を記述します。上位の画面索引がある場合、共通事項を索引へ集約します。
- 内部 API、保存方式、UI 部品の設計は後続のシステム設計で扱います。画面仕様には、利用者が確認できる保存の成否や再試行の条件までを記述します。

## 3. ファイル命名・ID規則

- ファイル名は `uis-<番号>-<短い日本語名>.md` とします。例として `uis-0010-販売登録.md` を用います。
- プロダクト文書の ID は `uis-<kebab-case>`、プロジェクト文書は `<project-id>:uis-<kebab-case>` とします。例として `uis-sales-register`、`prj-0001:uis-sales-register` を用います。
- 同梱の完成例は `specdojo:uis-sample` とします。画面の業務 ID と区別するための例外です。
- 本文先頭の H1 に画面名を記述します。命名の共通原則は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従います。

## 4. 推奨 Frontmatter 項目

共通スキーマ `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` と [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、次の項目を `specdojo:` 配下に置きます。

| 項目         | 必須/任意 | 画面仕様での値・用途                                                         |
| ------------ | --------- | ---------------------------------------------------------------------------- |
| `id`         | 必須      | 「ファイル命名・ID規則」に従う文書 ID                                        |
| `type`       | 必須      | `ui` 固定。主 rulebook の `deliverable_type` と一致させる                    |
| `status`     | 必須      | `draft` / `ready` / `deprecated`。作成・編集時は `draft` とし、人が確定する  |
| `rulebook`   | 必須      | `specdojo:uis-rulebook`                                                      |
| `part_of`    | 任意      | 所属する画面索引などの ID 配列。所属先がなければ `[]`                        |
| `based_on`   | 任意      | 根拠となる業務プロセス・機能などの ID 配列。根拠がなければ `[]`              |
| `supersedes` | 任意      | 置き換える旧文書の ID 配列                                                   |
| `relations`  | 任意      | `satisfies` / `verifies` / `implements` ごとに参照 ID 配列を持つオブジェクト |

### 4.1. メタ情報の判断基準と例

- 良い例では、成果物の種別と所属・根拠を分けて宣言します。参照先には存在する文書 ID を使います。
- 悪い例として `type: screen`、`id: UIS_Sales`、`title: 販売登録` を指定すると、種別・ID の制約や H1 に名前を書く規約に反します。
- `part_of` と `based_on` は役割に応じて記入します。関係がない場合は空配列にし、未作成の文書 ID を架空の参照先として登録しません。

```yaml
---
specdojo:
  id: uis-sales-register
  type: ui
  status: draft
  rulebook: specdojo:uis-rulebook
  part_of: []
  based_on: []
---
```

## 5. 本文要件

章は次の順で構成し、`##` から `####` の見出しに 1 始まりの連番と末尾の `.` を付けます。任意章を省略した場合は番号を詰めます。

| 章                         | 必須/任意                        | 目的と記述要件                                                                                                        |
| -------------------------- | -------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 概要                       | 必須                             | 対象業務と画面で達成する結果を 1〜2 文で示す。利用環境や対象範囲を補足できる                                          |
| 対象ユーザー/利用目的      | 必須                             | 操作する業務ロールと、各ロールが達成する業務目的を示す。権限差があれば操作範囲を示す                                  |
| 表示項目                   | 必須                             | 項目名、種別、表示内容の意味、編集可否、初期値・未取得時・更新契機などを示す                                          |
| 操作                       | 必須                             | 操作名、対象、前提条件、結果を示す。更新の確定時点、処理中や失敗後の再実行条件を含める                                |
| 遷移                       | 必須                             | 契機、遷移元、遷移先、条件、引き渡す情報を示す。戻る・中止時の入力の保持/破棄も示す。画面間移動がなければその旨を記す |
| バリデーション             | 任意。ただし入力がある場合は必須 | 対象、必須性、形式・範囲・相関、判定時点、違反時の扱いを示す。入力のない画面は省略できる                              |
| エラー表示と利用者の次の手 | 必須                             | 発生条件、表示要点、保持/更新される状態、利用者の回復操作とその結果を示す                                             |
| メモ / 将来課題            | 任意                             | 現在の対象範囲に含めない拡張や、判断待ちの事項と次の確認先を記す                                                      |

関連する操作・遷移・入力制約・エラーは、同じ名称または画面内の識別子で対応づけます。既存の要求・業務規則・受入条件がある場合は参照し、本文へ全文を再掲しません。

## 6. 記述ガイド

各節の判断基準を満たす粒度で記述します。表の列は推奨形式であり、本文要件を満たす別形式も使用できます。共通事項の正本と画面固有の条件は「位置づけ」に従って記述します。

### 6.1. 概要

- どの業務のどの場面で、誰が何を完了する画面かを判断できることを基準とします。
- 利用端末、開始・終了の境界、対象となる取引の範囲など、後続の操作条件に必要な前提を補足します。
- 表示項目や操作の全件列挙はそれぞれの章へ置きます。

**良い例**として「店員が店頭で購入商品と預かり金を登録し、販売を確定して釣銭を確認する画面。」と記述します。

**悪い例**の「販売を便利にする画面。」では、利用者と完了する業務を判断できません。

### 6.2. 対象ユーザー/利用目的

- ロールごとに利用場面と達成する結果が対応することを基準とします。
- 権限に差がある場合、参照・登録・取消など許可される操作の範囲を明記します。
- 顧客が画面を操作するか、店員を介して結果を受け取るかを区別します。

**良い例**として「店員・店主が接客中に購入明細と釣銭を確認する。両ロールに販売登録を許可する。来店客へは担当者が合計額を伝える。」と記述します。

**悪い例**の「ユーザーがシステムを利用する。」では、業務ロールと利用目的が定まりません。

### 6.3. 表示項目

- 表示する業務情報と、空・未取得・処理中を含む値の意味が読み取れることを基準とします。
- 項目名、種別（入力・一覧・集計・状態等）、表示内容、編集可否、表示条件・初期値・更新契機を列として持たせます。金額や数量には単位を記します。
- 計算値は算出の意味か上位規則の参照を示し、入力の許容範囲は「バリデーション」へまとめます。

| 項目名       | 種別 | 表示内容               | 編集可否 | 表示条件・更新契機                                    |
| ------------ | ---- | ---------------------- | -------- | ----------------------------------------------------- |
| 合計請求金額 | 集計 | 明細小計の合計、円単位 | 不可     | 明細なしは 0 円。追加・数量変更・削除の成功時に再計算 |

この表を **良い例**とします。**悪い例**の「合計欄を右下に赤色で表示する。」では、値の意味や更新条件が定まりません。

### 6.4. 操作

- 操作の実行可否と、成功・中止・失敗後の業務状態を判定できることを基準とします。
- 操作名、対象、前提条件、結果を列として持たせます。利用できない状態と、その際に無効化するかエラーを表示するかを定めます。
- 保存や確定を伴う操作では、処理中の再操作、結果が不明な場合の確認方法、再試行可能になる条件を記します。回復操作も操作表へ含めます。

| 操作名   | 対象         | 前提条件                                 | 結果                                                                                                           |
| -------- | ------------ | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 会計確定 | 「会計確定」 | 明細があり、入力制約を満たす登録中の取引 | 処理中は再操作を無効化。成功時に販売・在庫を確定して完了画面へ移る。結果不明時はエラー表に従って取引状態を確認 |

この表を **良い例**とします。**悪い例**の「確定ボタンを押すと保存する。」では、保存の条件や二重操作時の扱いが不明です。

### 6.5. 遷移

- 流入・流出・戻りを、契機と業務上の条件から辿れることを基準とします。
- 遷移名、契機、遷移元、遷移先、条件、引き渡し情報を列として持たせます。渡す情報がなければ「なし」と記します。
- ダイアログを介する場合は、選択確定と取り消して戻る場合の両方を示します。遷移先の文書があればリンクし、未作成なら画面名・ID をバッククォートで記します。

| 遷移名           | 契機     | 遷移元         | 遷移先         | 条件           | 引き渡し情報・入力の扱い                                       |
| ---------------- | -------- | -------------- | -------------- | -------------- | -------------------------------------------------------------- |
| 商品選択から復帰 | 「選択」 | `商品検索画面` | `販売登録画面` | 商品を選択済み | 商品コード。既存明細を保持し、追加条件を満たす場合に明細へ反映 |

この表を **良い例**とします。**悪い例**の「選択すると次画面へ進む。」では、行き先と受け渡し情報が定まりません。

### 6.6. バリデーション

- 同じ入力に対して同じ可否を判断でき、境界値で検証できることを基準とします。
- 対象、必須性、形式・範囲・相関、判定時点、違反時の扱い・対応エラーを列として持たせます。空欄・範囲の上限下限を具体化します。
- 入力時と確定時に判定する条件が異なる場合は区別します。失敗時に前の有効値を保持するか、修正用に入力値を残すかを明記します。

| 対象 | 必須性 | 条件                          | 判定時点                                 | 違反時の扱い                                             |
| ---- | ------ | ----------------------------- | ---------------------------------------- | -------------------------------------------------------- |
| 数量 | 必須   | 1〜999 の整数かつ現在庫数以下 | 数量変更時。現在庫数は会計確定時にも確認 | 明細・合計は直前の有効値を保持し、修正対象と在庫数を表示 |

この表を **良い例**とします。**悪い例**の「数量が適切であること。」では、許容範囲も確認時点も判定できません。

### 6.7. エラー表示と利用者の次の手

- 利用者が現在の状態、確定の有無、次に実行できる操作を判断できることを基準とします。
- エラー事象、発生条件、表示要点、状態の扱い、回復アクションを列として持たせます。内部例外名を表示要点の代わりに使用しません。
- 入力不備・対象なし・権限不足・通信障害など、対象画面で起こる代表ケースを扱います。回復に別画面や運用担当者が必要な場合は、その行き先と連絡時に渡す情報を示します。

| エラー事象   | 発生条件                       | 表示要点                                 | 状態の扱い                                     | 利用者の次の手                                                                           |
| ------------ | ------------------------------ | ---------------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 会計結果不明 | 確定要求後に応答を受信できない | 「会計結果を確認してください」と取引番号 | 明細と預かり金を保持し、編集・会計確定を無効化 | 「結果確認」で同じ取引を照会。確定済みは完了画面へ、未確定が確認できた場合は登録中へ戻る |

この表を **良い例**とします。**悪い例**の「通信エラー。もう一度確定する。」では、確定済みの取引を再登録するおそれがあります。

### 6.8. メモ / 将来課題

- 現在の操作・制約と将来の拡張を識別できることを基準とします。
- 未確定事項は共通ラベルを用い、影響範囲と確認先・次のアクションを示します。
- 現行動作に必要な判断をこの章だけへ移さず、該当する本文要件にも反映します。

**良い例**として「電子決済は将来の拡張候補とし、導入検討時に店主が決済方法と取消手順を確認する。」と記述します。

**悪い例**の「エラー時の扱いは後で検討する。」では、現行画面を実装・検証する条件が欠落します。

## 7. 禁止事項

| 禁止する記述                                                              | 理由                                             |
| ------------------------------------------------------------------------- | ------------------------------------------------ |
| CLI コマンド群を画面・画面遷移として定義する                              | CLI 固有の要件は clis が担うため                 |
| ワイヤーフレーム、配置図、ピクセル座標、CSS、色・フォント・部品配置の指定 | 業務仕様の判断範囲を越えるため                   |
| 物理テーブル・物理カラム・SQL・実装クラスや関数・UI ライブラリの指定      | 後続設計の選択に結合するため                     |
| クリックやキー入力の逐語列挙だけで操作を説明する                          | 操作の前提条件と業務上の効果を判断できないため   |
| 回復操作を伴わないエラー一覧、結果不明の更新を無条件に再実行させる指示    | 利用者が業務を安全に再開できる条件が欠けるため   |
| 共通の業務規則や上位仕様の全文再掲                                        | 正本との不整合や更新漏れを招くため               |
| 未定義の Frontmatter 項目、`ui` 以外の成果物 `type`                       | メタ情報スキーマと主 rulebook の宣言に反するため |
