# 非機能要件 / 信頼性 作成ルール

Non-Functional Requirements Reliability Documentation Rules

本書は、非機能要件のうち信頼性（障害の発生抑止・誤動作防止・自動回復）を定義する `nfr-reliability` の作成ルールを定める。信頼性は「障害をどれだけ起こさず、起きても自動で回復できるか」を扱い、停止をどこまで許すか・いつまでに復旧するかは可用性（`nfr-availability`）に書く。

## 1. 全体方針

- 要件は対象・条件・指標・基準を明示し、合否判定可能にする。
- 設計・実装手順ではなく、結果として満たす品質基準を書く。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直さない。文書の整形・lint はリポジトリの検証で扱い、「測定・検証方法」に含めない。
- _UNDECIDED_: `recipe`・`template` の要否は未判断である。sample を「本文構成（標準テンプレ）」に揃えた後、同じ構成を NFR 分冊で共通の template にできるかを論点として判断する。

## 2. 位置づけ

信頼性の基準値や障害の判断に使う文書であり、次の文書と接続する。

| 文書               | 関係                                                                                 | 本文からの導線 |
| ------------------ | ------------------------------------------------------------------------------------ | -------------- |
| `nfr-index`        | NFR 全体の入口。分冊として `part_of` で属する                                        | 必須           |
| `nfr-availability` | 停止許容・RTO/RPO の正本。自動回復で扱えない障害の復旧目標を変えるときは双方を見直す | 必須           |
| `sac-*` / `stc-*`  | 信頼性要件の合否判定基準・試験仕様                                                   | 必須           |
| `opd-*` / `opr-*`  | 障害時の運用方針・手順                                                               | 必須           |
| `dec-*`            | 基準値や除外条件の設計判断                                                           | 任意           |

## 3. ファイル命名・ID規則

- 配置先は `docs/ja/product/060-non-functional-requirements/nfr-reliability.md` とし、[[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従う。
- 文書 ID は `nfr-reliability` とする。プロダクト文書のため名前空間を付けない。
- 要件 ID は `nfr-rel-<連番>`（例: `nfr-rel-001`）とする。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。

- `specdojo.type` は `requirement`、`specdojo.rulebook` は `specdojo:nfr-reliability-rulebook` とする。
- `specdojo.part_of` には `nfr-index` を置く。
- `specdojo.based_on` には障害履歴・業務重要度を示す文書を挙げる。

## 5. 本文構成（標準テンプレ）

`nfr-reliability` は以下の見出し構成を **順序固定** で配置する。生成する本文の見出しは番号と見出しをそのまま使う。

| 番号 | 見出し               | 必須 |
| ---- | -------------------- | ---- |
| 1    | 概要（対象・目的）   | ○    |
| 2    | 適用範囲・前提条件   | ○    |
| 3    | 信頼性要件一覧       | ○    |
| 4    | 測定・検証方法       | ○    |
| 5    | 関連ドキュメント導線 | ○    |

## 6. 記述ガイド

### 6.1. 概要（対象・目的）

- 対象業務、障害が起きたときの業務影響、信頼性要求の目的を書く。基準値の根拠を業務影響からたどれるかで判断する。
- 良い例: 「レジの会計処理が失敗すると客を待たせ売上を取りこぼすため、会計処理の失敗を抑える」。
- 悪い例: 「システムを安定稼働させる」（対象業務と影響が分からない）。

### 6.2. 適用範囲・前提条件

- 対象システム、対象時間帯、除外条件（計画停止など）を書く。

### 6.3. 信頼性要件一覧

- 表の列は `id` / `内容` / `指標` / `基準` / `備考` とする。
- 指標の例は障害率（処理失敗・異常終了の割合）、MTBF（平均故障間隔）、再試行を含めた処理成功率である。
- 割合の指標は分子と分母（対象処理と集計期間）を定義し、基準だけで pass/fail を一意に判定できるかで判断する。
- 良い例: 「障害率 = 失敗した会計処理件数 ÷ 全会計処理件数（月次）、0.1% 以下」。
- 悪い例: 「障害率 月次 0.1% 以下」（分母が分からない）、「3 回まで再試行」（実装の設定値であり品質基準ではない）。

### 6.4. 測定・検証方法

- 要件 ID ごとに、監視・テスト・レビューのどれで、いつ、どの Role code が判定するかを書く。判定者は人の Role code とし、agent を判定者にしない。
- 少なくとも 1 件はテストで判定し、対応する `sac-*` / `stc-*` を示す。
- 基準未達や重大障害が起きたときの記録先（課題・登録簿の個票など）と、要件や基準を見直す契機を書く。

### 6.5. 関連ドキュメント導線

- 「位置づけ」の表の文書へ導線を置き、必須・任意も同表に従う。

## 7. 禁止事項

| 禁止事項                                         | 理由                                    |
| ------------------------------------------------ | --------------------------------------- |
| 「安定稼働する」だけで基準を書かない             | 合否判定できないため                    |
| 再試行回数などの実装設定値を要件・基準として書く | 実装依存で保守不能になるため            |
| 停止許容時間・RTO/RPO を本書で定義する           | `nfr-availability` と二重管理になるため |
| 検証方法を省略する                               | 要件が運用されないため                  |
