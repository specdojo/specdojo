# 非機能要件 / 操作性 作成ルール

Non-Functional Requirements Usability Documentation Rules

操作性（使いやすさ・誤操作防止・学習容易性）の非機能要件 `nfr-usability` の作成ルールを定めます。

## 1. 全体方針

- 操作性は、利用者前提を置いたうえで指標と基準値で定義し、受入試験やユーザ検証で合否を判定できるようにする。
- UI 表現の詳細設計ではなく、利用結果としての品質基準を書く。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直さない。文書の整形・lint はリポジトリの検証で扱い、成果物の測定・検証方法に含めない。

## 2. 位置づけ

- `nfr-usability` は操作性要求の正本で、`nfr-index` を入口とする。
- 画面仕様は `uis-*`、受入・試験仕様は `sac-*` / `stc-*` を正本とし、本書から参照する。

## 3. ファイル命名・ID規則

- 生成対象ドキュメント ID は、プロダクト文書なら `nfr-usability`、プロジェクト文書なら `<project-id>:nfr-usability` とし、カタログの宣言に合わせる。
- 要件 ID は `nfr-usb-<連番>`（3 桁）を推奨する。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- `specdojo.type` は `requirement`、`specdojo.rulebook` は `specdojo:nfr-usability-rulebook` とする。
- `specdojo.part_of` は `nfr-index` とする（任意）。プロジェクト文書では ID と同じく `<project-id>:nfr-index` と修飾する。

## 5. 本文要件

見出しは次の構成で **順序固定** とする。

| 番号 | 見出し               | 必須 | 受入条件                                                       |
| ---- | -------------------- | ---- | -------------------------------------------------------------- |
| 1    | 概要（対象・目的）   | ○    | 対象利用者と、どの業務の操作品質を守るかが分かる               |
| 2    | 適用範囲・利用者前提 | ○    | 対象画面・対象業務・利用者属性（熟練度・利用環境）が揃っている |
| 3    | 操作性要件一覧       | ○    | 全要件が標準 5 列で、指標と基準値から合否を判定できる          |
| 4    | 測定・検証方法       | ○    | 全要件 ID に測定方法・判定タイミング・判定者がある             |
| 5    | 関連ドキュメント導線 | ○    | `nfr-index`・`sac-*`・`stc-*`・`uis-*` への導線がある          |

「操作性要件一覧」の標準 5 列は `id` / `内容` / `指標` / `基準` / `備考` の順とする。`基準` は数値と単位、または網羅条件（`100%`）で書き、`備考` に対象利用者・対象操作を絞り込む。率の指標は、分母（操作回数・タスク数・利用者数のどれか）と数え方を `指標` または `備考` に書く。

## 6. 記述ガイド

完成例の全体像は Frontmatter の `sample` で宣言された sample を参照してください。

### 6.1. 概要（対象・目的）

- **判断基準**: 誰がどの業務タスクで、何を防ぎたいか（迷い・誤操作・習熟の遅れ）が 2〜3 文で分かること。

### 6.2. 適用範囲・利用者前提

- **判断基準**: 基準値がどの利用者・環境で成り立つか特定できること。属性で基準が変わる場合は属性を分けて書く。
- **良い例**: 「新任利用者: 業務知識あり・システム未経験 ／ 対象デバイス: 店頭のタブレット端末」
- **悪い例**: 「一般利用者」（熟練度も利用環境も分からず、試験の被験者を選べない）

### 6.3. 操作性要件一覧

- **判断基準**: 1 行 1 指標とし、指標・基準値・`備考` の対象から合否を出せること。指標は完了率・完了時間・誤操作率・習熟時間・エラーメッセージの対処方法含有率・破壊的操作の確認網羅率などから選ぶ。率の指標は分母が分かり、測定値を比べられること。
- **良い例**: 「`nfr-usb-002` ／ 会計の誤操作を基準以下に抑える ／ 誤操作率（取消・修正した会計数 ÷ 全会計数） ／ 2% 以下 ／ 新任利用者の会計操作」
- **悪い例**: 「`nfr-usb-002` ／ 誤操作を抑える ／ 誤操作率 ／ 2% 以下 ／ 取消導線を提供」（分母がなく操作単位か利用者単位かで値が変わる。`備考` が対象ではなく実現手段になっている）

### 6.4. 測定・検証方法

- **判断基準**: 要件 ID ごとに、測定手段（ユーザビリティテスト・操作ログ集計・レビュー）と被験者数などの条件、判定の時期と判定者が分かること。
- **良い例**: 「`nfr-usb-001` ／ ユーザビリティテスト（新任 5 名×主要タスク） ／ リリース前受入試験 ／ UX・QA」
- **悪い例**: 「利用者アンケートで確認する。」（どの要件をどの基準で判定するか分からない）

### 6.5. 関連ドキュメント導線

- **判断基準**: 合否基準（`sac-*`）、試験（`stc-*`）、画面仕様（`uis-*`）、設計判断（`dec-*`、任意）の参照先と目的が表で分かること。

## 7. 禁止事項

| 禁止事項                       | 理由                                       |
| ------------------------------ | ------------------------------------------ |
| 「使いやすい」だけで要件を書く | 判定不能のため                             |
| 画面詳細仕様を丸ごと再掲する   | `uis-*` と二重管理になるため               |
| 利用者前提を書かない           | 評価条件が揃わないため                     |
| 測定方法のない要件 ID を置く   | 受入試験で合否を出せず要件が形骸化するため |
