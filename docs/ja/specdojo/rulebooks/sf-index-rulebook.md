# システム化機能一覧（全体構成）作成ルール

System Functions Index Documentation Rules

`sf-index.md` は、対象システムが実現する機能の全体構成と一覧を定義し、業務プロセス仕様（BPS）・利用接点の仕様・個別機能仕様（`sf-<term>`）へ導く入口文書である。業務プロセス領域ごとにシステムが担う責務を一覧で示し、スコープの承認、機能分割、テスト対象の網羅確認に使える内容を記載する。

## 1. 全体方針

- 一つのシステムまたは合意した対象範囲につき、機能一覧の正本を一つにする。複数システムを扱う場合は、一覧の対象範囲を冒頭で明示する。
- 機能は業務プロセス領域を起点に洗い出し、すべての業務プロセス領域が、いずれかの機能に属するか、システム化しない理由を持つ状態にする。
- 一覧行には機能 ID、機能名、概要、対応する業務プロセス仕様と利用接点、個別仕様の有無を対応させる。各行は要約参照にとどめ、入出力・振る舞い・受入条件は個別機能仕様へ委ねる。
- システムが担う処理（記録・検証・生成・起動）と、人間に残す判断を区別する。承認や確定の判断をシステム化機能として数えない。
- 上流の BPS・利用接点の仕様が未作成でも、成果物カタログなど確認できた根拠から一覧を作ってよい。未照合の対応は確定扱いにせず、未決事項で追跡する。

## 2. 位置づけ

| 文書・情報                       | 役割                                             | 一覧との関係                                                         |
| -------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------- |
| `sf-index`                       | 機能の全体構成と一覧、機能 ID の採番元           | 本書の対象                                                           |
| `sf-<term>`                      | 個別機能の入出力・処理要件・制約・受入観点       | 一覧行から参照する。一覧の内容を詳細化し、一覧全体の網羅性は扱わない |
| 業務プロセス仕様（BPS）          | 業務のトリガー・処理ステップ・判断               | 一覧の網羅の起点。各行が担う業務プロセスの参照先                     |
| 利用接点の仕様（CLIS・UIS・IFX） | コマンド群・画面・外部 I/F の利用方法と入出力    | 各行の利用接点の参照先。構文・画面配置は接点の仕様を正本とする       |
| 成果物カタログ                   | 個別機能仕様を作るかどうかと、その依存・完了条件 | 個別仕様を追加するときは先にカタログへ登録する                       |

- 個別機能仕様の作成ルールは [[specdojo:sf-rulebook|システム化機能仕様 作成ルール]] とし、本書は一覧ハブだけを扱う。
- 一覧に載せた機能のうち、どれを個別仕様へ詳細化するかは成果物カタログで管理する。個別仕様がない機能は、一覧行の要約を正とする。
- 作成の入力は、上位の目的・スコープ、業務プロセス領域と BPS、利用接点の仕様、成果物カタログとする。業務から機能への割当てを先に決め、実装・schema・リファレンスは参照先や現行制約の照合に使う。

## 3. ファイル命名・ID規則

- ファイル名は `sf-index.md`、成果物 ID は `sf-index` とする。`sf-index` は一覧ハブ用に予約し、個別機能には使わない。
- 機能 ID は `SF-<AREA>-<NN>` とする。`<AREA>` は機能領域を表す英大文字の略号（例: `POS`、`EXEC`）、`<NN>` は領域内の 2 桁連番とする。
- 機能 ID は一度採番したら意味を変えない。機能を廃止・統合した場合は ID を再利用せず、一覧から外した理由を未決事項または変更記録に残す。
- 配置は成果物カタログの宣言を優先し、命名・管理境界の共通原則は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従う。

## 4. 推奨 Frontmatter 項目

- 共通の必須・任意項目と ID・参照・状態の制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` に従う。項目の型や許可値を本書で再定義しない。
- `type` は `requirement`、`rulebook` は `specdojo:sf-index-rulebook` とする。文書名は H1 に置く。
- 作成・改訂中は `status: draft` とする。静的検査の成功や作業タスクの完了だけで `ready` へ昇格せず、人間の PO がスコープを承認して判断する。

## 5. 本文要件

次の章を開始時の構成とする。見出しには階層ごとの連番を付ける。

| 章  | 章タイトル         | 必須     | 目的と記載要件                                                                                                                     |
| --- | ------------------ | -------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| -   | 冒頭の概要         | ○        | 対象システム、一覧の利用目的と対象範囲を 1〜3 文で示す                                                                             |
| 1   | 目的と対象範囲     | ○        | 一覧で判断できることと上位目的の関係、対象者の業務課題、対象・対象外、読者・確認者、保守担当、公開範囲と承認者を示す               |
| 2   | 機能構成           | ○        | 機能領域ごとに、略号、対応する業務プロセス領域、システムの責務、人間に残す判断を示す。システム化しない業務プロセス領域と理由を示す |
| 3   | システム化機能一覧 | ○        | 機能 ID、機能名、概要、業務プロセス仕様、利用接点、個別仕様を一つの主一覧表で対応させる                                            |
| 4   | 未決事項           | 条件付き | 未照合の対応や未作成の参照先がある場合に、論点、影響、担当・判断者、判断時点、次アクション、追跡先と承認への影響を示す             |

- 機能構成と一覧の両方で、すべての業務プロセス領域を確認できるようにする。一覧から機能構成へ、機能構成から業務プロセス領域へ辿れれば、網羅の確認表を別に設けない。
- 行が多く一つの表で領域を見分けにくい場合は、機能領域ごとに小節を分けてよい。列は全小節でそろえる。

## 6. 記述ガイド

共通事項は上位の目的・スコープ、BPS、利用接点の仕様を正本として参照し、一覧には割当てと責務境界を残す。実在する文書へのリンクは `[[id|title]]`、表のセル内は `[[id\|title]]` とし、未作成の参照先は ID をインラインコードで仮置きする。以下の良い例・悪い例は判断の差を示す断片である。

### 6.1. 目的と対象範囲

- 対象者のどの業務課題を解消し、一覧で何を判断できるようにするかを書き、上位目的の参照先を添える。システムの紹介文や機能の列挙で終えない。
- 対象と対象外を対にして示す。対象外には、人間が行う判断、外部製品の内部処理、個別機能の詳細を必要に応じて含める。
- 読者ごとの用途（機能分割、実装範囲、テスト対象の洗い出し、業務対応の確認）、確認者と保守担当の Role code、スコープと公開可否を最終判断する人間の PO を示す。担当者の割当てはプロジェクトの組織・メンバー定義を参照する。
- 公開する相手と範囲を明記する。顧客の個人情報、認証情報、非公開の接続先や内部構成を本文・例・証跡に含めず、説明には架空名を使う。
- 良い例: 「店番交代時の記録漏れを減らすため、販売・在庫の責務分担を確定する。BA が一覧を保守し、店主代表（PO）が対象範囲と外部公開用の匿名化を確認する」。
- 悪い例: 「本システムの機能を一覧にする」。一覧で判断することと対象範囲が分からない。

### 6.2. 機能構成

- 機能領域は業務プロセス領域のまとまりを基に分ける。業務の区分と責務が異なる処理を同じ領域に入れる場合、または一つの区分を分ける場合は、その理由を示す。
- 「システムの責務」には、記録・検証・生成・起動など、システムが行うことを動詞で書く。「人間に残す判断」には承認・確定・方針決定など、システム化しない判断を書く。
- システム化しない業務プロセス領域がある場合は、その領域と理由（手作業で足りる、外部サービスが担う、対象外と合意した等）を示す。ない場合も、ないことを明記する。
- 推奨する列は「機能領域」「略号」「業務プロセス領域」「システムの責務」「人間に残す判断」とする。
- 良い例: 「実行サイクル: タスクの実行受入から検証・統合・結果記録までを行う。業務上の完了承認は人間に残す」。
- 悪い例: 「実行サイクル: タスクを管理する」。システムが行うことと人間の判断の境界がない。

### 6.3. システム化機能一覧

| 列               | 必須 | 記述内容                                                                                       |
| ---------------- | ---- | ---------------------------------------------------------------------------------------------- |
| 機能 ID          | ○    | `SF-<AREA>-<NN>` 形式の ID                                                                     |
| 機能名           | ○    | 業務上の責務が分かる名詞句。実装のモジュール名やコマンド名を機能名にしない                     |
| 概要             | ○    | 何を入力に、何を確定・記録・生成するかを 1 文で示す                                            |
| 業務プロセス仕様 | ○    | 対応する BPS の ID またはリンク。複数ある場合は代表とするものを含めて並べる                    |
| 利用接点         | ○    | 画面、CLI コマンド群、外部 I/F、自動実行などの起動接点と、その仕様への参照。接点がなければ理由 |
| 個別仕様         | ○    | 個別機能仕様へのリンク、または「一覧行で要約」などの扱い                                       |

- 利用接点の列は、接点の種類に合わせて列名を変えてよい（画面中心なら「画面」、CLI 中心なら「CLI」）。構文・引数・画面配置は接点の仕様を正本とし、一覧へ転記しない。
- 一つの接点（コマンド群・画面）が複数の機能にまたがる場合は、機能ごとに行を分け、表の後にまたがりを注記する。
- 機能の境界が業務プロセスの区分とずれる場合（ある機能が別の領域の記録も担う等）は、表の後に責務の分担を注記する。
- 良い例: 「`SF-EXEC-02` 成果物評価: editor から独立した runner が成果物を評価し、grade と finding を記録する」。
- 悪い例: 「`SF-EXEC-02` grade: grade コマンド」。機能名がコマンド名で、何を確定するかが分からない。

### 6.4. 未決事項

- `_TODO_`・`_UNDECIDED_`・`_ASSUMPTION_` の使い分けはドキュメントメタ情報標準に従う。論点ごとに影響する機能 ID・参照先、担当・判断者の Role code、期限または判断時点、次アクション、追跡先、承認を保留する条件を示す。
- 上流の BPS や利用接点の仕様が未作成で暫定の対応を置いた場合は、照合する時点と担当を残す。網羅の根拠（成果物カタログの依存など）と一覧の範囲が一致しない場合も論点にする。
- 上流仕様の作成・改訂、機能の追加・廃止・統合、接点や個別仕様の変更を再照合の契機とする。BA は BPS と一覧、ARC は機能分割・コンポーネント設計、DEV は接点・実装・schema・生成処理・運用手順、QE はテスト対象への影響先を機能 ID から特定する。該当しない影響先には理由を残す。
- 依存の不足や責務境界の未合意で後続設計・実装・検証の着手を妨げる場合は、PM に対象機能、影響する成果物・タスク、再開条件を渡す。PM は課題・リスク・変更要求・決定を PJR へ、追従作業の担当・順序・期限を Schedule へ接続し、進捗は実行記録で報告する。一覧には追跡参照を残し、管理台帳を複製しない。
- 改訂・廃止の共通手続きは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] の「文書の改訂・廃止とライフサイクル変更管理」に従う。
- 良い例: 「BA が BPS 作成時に `SF-INV-01` の在庫反映の責務を照合する。未合意の間は当該境界の承認を保留し、PM が PJR で追跡して在庫設計の着手時期を見直す」。
- 悪い例: 「対応は後で確認する」。担当と確認の時点がない。

### 6.5. 完成判定と継続保守

一覧の内容確認は次を基準とし、確認結果と未充足条件をレビュー記録へ残す。具体的な責任分担と成果物の完了条件は、プロジェクトの Role 定義・成果物カタログを正とする。

| 確認ロール | 合格と判断できる状態                                                                                             |
| ---------- | ---------------------------------------------------------------------------------------------------------------- |
| BA         | 全業務プロセス領域が機能または対象外の理由に対応し、各行の概要と根拠仕様の責務が矛盾しない                       |
| ARC        | 機能 ID が一意で領域に対応し、重なる責務の分担と外部・人間との境界を設計入力として特定できる                     |
| DEV        | 各行から起動接点と仕様の正本を辿れ、個別仕様を作る機能と一覧で要約する機能が区別できる                           |
| QE         | 対象機能 ID をテスト対象へ対応付けられ、必須列の欠落、参照切れ、未記録の暫定対応がない                           |
| PM         | 機能領域ごとの照合と影響先の追従を作業単位に分け、完了条件・担当・判断時点をカタログ・Schedule・PJR で追跡できる |
| PO         | 上位目的に沿う対象範囲、人間に残す判断、公開範囲と非公開情報の除外を確認し、未決事項を含めて承認可否を判断できる |

- 文書検査は利用リポジトリの package・hook 設定と実行規約に従い、Markdown 整形・lint、Frontmatter と参照の検査を行う。同梱リポジトリでは `lint:md`・`lint:fm` 等の設定を参照する。対象ファイル、コマンド、結果を実行記録に残し、適用検査がすべてエラーなく終了することを合格条件とする。
- 人間の PO は、未照合の対応や未解決指摘がスコープ・責務境界・公開可否に影響する場合は承認を保留または差し戻す。承認範囲から切り出す場合も、その範囲と後続作業の追跡先を明記する。文書検査の成功は、内容の合意、機能の受入試験、製品リリースの判断を代替しない。
- 公開後の対応漏れや参照切れは保守担当へ渡し、スコープ変更は PO、技術境界の矛盾は ARC、計画への影響は PM へ接続する。変更後は影響する一覧行と参照先を再確認する。
- 良い例: 「lint は成功したが、在庫反映の責務が未照合のため `draft` を維持する。BA・ARC の確認後に PO が対象範囲を承認する」。
- 悪い例: 「一覧が埋まり lint が通ったので `ready` として公開する」。網羅性・責務の合意と人間の最終判断を省いている。

## 7. 禁止事項

| 禁止事項                                                                   | 理由                                                         |
| -------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 業務プロセス領域を確認せず、実装のモジュールやコマンドの列挙から一覧を作る | 業務仕様からの漏れと、業務に対応しない機能を判断できないため |
| 人間の承認・確定の判断をシステム化機能として数える                         | システムが保証する範囲を誤らせるため                         |
| 個別機能の入出力・処理要件・受入条件を一覧へ展開する                       | 個別機能仕様と責務が重なり、更新先が分からなくなるため       |
| コマンド構文・引数・画面配置・schema の項目を一覧へ転記する                | 利用接点の仕様や schema と二重管理になるため                 |
| 成果物カタログに登録していない個別仕様を、存在するようにリンクする         | デッドリンクと、作成判断の不在を招くため                     |
| 未照合の対応や未作成の参照先を、未決事項に残さず確定事項として扱う         | 上流仕様の作成時に照合されず、誤りが残るため                 |
| 機能 ID を再利用する、または意味を変える                                   | 個別仕様・テスト・変更記録からの参照が壊れるため             |
| 文書検査の成功だけで agent が `ready` 昇格や公開の承認を行う               | スコープと公開可否の最終判断は人間の PO が担うため           |
