# 概念データフロー図（ユースケース別）作成ルール

Conceptual Data Flow Diagram Use Case Documentation Rulebook

全体概要で選定した一つのユースケースまたは系統について、開始から終了までの流れと、受け渡す情報・物を表と概念データフロー図（Mermaid または D2）で示すためのルールです。状態の定義と遷移は STSD を正本とします。

## 1. 全体方針

- 一文書は、全体概要の「詳細 CDFD 一覧」にある一つのケース ID と、そのユースケースまたは系統を詳細化します。描く単位と詳細化の境界は「描き方の選択」に従います。
- 「プロセス領域」は順序と責務の正本、「データストア」は全体概要の一覧の部分集合、図は開始から終了までの順序と受け渡しの正本とします。主要入力・主要出力の箇条書きや、引き渡しを列挙する章は設けません。
- 渡す情報・物は図の線のラベルで表します。引き渡し条件のイベントや引き渡し ID は使いません。業務上重要な戻りの流れだけ、任意の図で示します。
- 詳細の図に Orchestrator（調整役）を置きません。調整は全体概要の「Orchestrator による PDCA の調整」などの指示の図へ委ねます。
- 目的はその業務が何のためにあるかを 1〜2 文、適用範囲は対象と対象外を 1 行ずつとします。人間と AI Agent の責任分担などの共通原則と凡例は、全体概要を参照し、本書で再定義しません。
- 状態名・成立条件・遷移元・遷移先・イベント・遷移条件は STSD を正本とします。本書は状態の定義や遷移表を持ちません。

## 2. 位置づけと用語定義

| 用語             | 定義                                                                       |
| ---------------- | -------------------------------------------------------------------------- |
| 全体概要         | 領域のまとまり、データストア、詳細 CDFD の割り当てを定める `cdfd-overview` |
| ケース ID        | 全体概要でユースケースまたは系統に割り当てられた `C-<nn>` 形式の識別子     |
| 起点イベント     | 業務を始める、発生を判定できる出来事                                       |
| 関連データストア | 対象ケースで参照・更新する、全体概要と同じ名称・区分を持つ正本             |
| 例外時の戻り     | 不足や不一致を、補完・再判断を担う参加単位へ返す業務上の流れ               |

全体概要がケースの業務目的と対象範囲を選定し、本書がその流れを具体化します。領域の分割、名称、担当、起点イベントは全体概要を正本とします。

## 3. ファイル命名・ID規則

- 対象プロダクトの業務仕様配下にあるデータフローディレクトリへ配置します。
- ファイル名と成果物 ID は `cdfd-uc-<topic>` とし、ファイル名だけ `.md` を付けます。`<topic>` は全体概要のユースケースまたは系統を表す英小文字・数字・ハイフンのスラッグです。
- product 成果物の ID にプロジェクト ID や authority を付けません。例: ファイル名 `cdfd-uc-replenishment.md`、ID `cdfd-uc-replenishment`。
- ケース ID は全体概要の `C-<nn>` を引き継ぎ、新しい ID の採番や別ケースの ID の流用はしません。
- 領域 ID、プロセスグループ名・区分名、データストア名は全体概要と一致させます。図を分けても同じ対象に同じ ID・名称を使い、接続のための独自 ID は付けません。

## 4. 推奨 Frontmatter 項目

| 項目       | 説明                                     | 必須 |
| ---------- | ---------------------------------------- | ---- |
| id         | プロジェクト修飾なしの `cdfd-uc-<topic>` | ○    |
| type       | `flow`                                   | ○    |
| status     | `draft` / `ready` / `deprecated`         | ○    |
| rulebook   | `specdojo:cdfd-uc-rulebook`              | ○    |
| `based_on` | 全体概要など、有効な直接の内容根拠の ID  | 任意 |
| supersedes | 置き換える旧ユースケース別 CDFD の ID    | 任意 |

- `based_on` に全体概要を記載する場合も product 成果物 ID を使用し、成果物カタログの `depends_on` の推移閉包に含まれる根拠だけを列挙します。
- status が `deprecated` の文書を `based_on` と本文の参照先にしません。有効な全体概要や後継文書へ参照を更新します。
- ケース ID、ユースケース名、開始・終了は本文で定義し、未定義の Frontmatter 項目を追加しません。
- 作成途中の `status` は `draft` とし、完成判定と所定の承認を満たした後の昇格は定められた承認者が行います。

## 5. 本文要件

見出し順・表・記入欄の骨組みは template を正本とします。本章は各章の目的と必須・任意を定めます。

| 番号 | 見出し           | 必須     | 内容                                                                                                  |
| ---- | ---------------- | -------- | ----------------------------------------------------------------------------------------------------- |
| 冒頭 | 導入文           | ○        | ケース ID とユースケースまたは系統を一文で定義                                                        |
| 1    | 目的             | ○        | その業務が何のためにあるか、開始からどの成果までを成立させるか（1〜2 文）                             |
| 2    | 適用範囲         | ○        | 対象と対象外を 1 行ずつ。責任分担などの共通原則は全体概要を参照                                       |
| 3    | プロセス領域     | ○        | 全体概要と同じまとまりごとの節。各節は順序と役割の表のみ                                              |
| 4    | データストア     | ○        | 対象ケースで参照・更新する全体概要のデータストアの部分集合                                            |
| 5    | 概念データフロー | ○        | 開始・終了のイベント、参加単位、関連データストア、情報・物の流れ。各図に業務の言葉による題と説明 1 文 |
| 6    | 未決事項         | 条件付き | 境界、名称、責務、判断者が未確定な論点。ある場合だけ最終章に設ける                                    |

「引き渡し」「例外時の戻り先」の章は設けません。図を分ける場合は「概念データフロー」に `5.1.`、`5.2.` の節を設けます。「例外時の戻り」は業務上重要な場合だけ同章内に追加できる任意の図であり、必須の章や表にしません。

## 6. 記述ガイド

### 6.1. 描き方の選択

全体概要で採用された方式から、次のどちらかを選びます。以下では、表の一行と図の一つのプロセスノードが表す対象を「参加単位」と呼びます。

| 観点         | 通常の横断ユースケース                                                                 | 系統の関係を描く方式の詳細                                                       |
| ------------ | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 対象         | 二つ以上のプロセスグループを横断する一つの業務。単一グループに閉じる業務には作成しない | 全体概要で選定した一つの系統と、通過する共用領域                                 |
| 参加単位     | 一つのプロセスグループを一つの代表ノードにし、名称と含む領域 ID を併記                 | 一つのプロセス領域を一つのノードにし、`P-xx 領域名` を表示                       |
| 表のまとまり | 全体概要のプロセスグループごと                                                         | 全体概要の区分ごと。PDCA の段階で区分を置き換えない                              |
| 詳細化の境界 | グループ内部の領域・プロセス・主要例外は有効な `cdfd-<group>` へ委ねる                 | 対象系統と共用領域の流れを領域単位で示し、非推奨のグループ別 CDFD へ依存しない   |
| 入口         | ケースの開始イベントを描く                                                             | 系統の入口の起点イベントを描き、文言を全体概要の「プロセス領域」の表と一致させる |

### 6.2. 導入文と目的

- 導入文は「ケース `C-02` の欠品から補充まで」のように、ケース ID と業務名を明示します。
- 目的は、そのユースケースまたは系統が何のためにあるかを 1〜2 文で記述します。例: 「欠品した商品を補充し、売場で販売できるようにするために、在庫の補充判断から仕入・販売への流れを示す。」
- BA・QE・承認者など、読み手ごとの承認・設計・確認作業を目的に書きません。

### 6.3. 適用範囲

- 対象はケース ID、参加単位、開始イベント、終了時の成果、必要な組織・システム境界を 1 行（1 文）で示します。
- 対象外は操作手順、補助操作、実装詳細などを 1 行（1 文）で示し、詳細化の境界は「描き方の選択」に従います。状態の定義と遷移は STSD を正本とします。
- 人間と AI Agent の責任分担などの共通原則は、全体概要を参照します。

### 6.4. プロセス領域

- 章冒頭にケース ID、正常系の通過順、全体概要との正本関係を簡潔に示します。
- 全体概要と同じまとまりごとに節（`3.1.`、`3.2.`、…）を設け、見出しは「グループ名または区分名（含む領域 ID）」とします。各節には役割の表だけを置き、入力・出力やデータストアの箇条書きは置きません。
- 表の列は次のとおりです。同じ参加単位が再登場する場合は別の行にして役割を区別します。

| 列                     | 記載内容                                                                                             |
| ---------------------- | ---------------------------------------------------------------------------------------------------- |
| 順序                   | 正常系で通過する順番                                                                                 |
| プロセスグループ・区分 | 全体概要で領域をまとめている名称                                                                     |
| 含む領域               | 全体概要と同じ領域 ID。領域単位の行では領域名も併記し、「プロセス領域」という列名にしてよい          |
| PDCA（任意）           | 全体概要にある Plan、Do、Check、Action、全体などの位置付け。「プロセスグループ・区分」とは別の分類軸 |
| 横断上の役割           | このケースで担う業務上の責務                                                                         |
| 参照先                 | 全体概要または有効な詳細文書。未作成の文書は ID をインラインコードで仮置き                           |

### 6.5. データストア

- 全体概要と同じ「マスタ・構成データ」「トランザクションデータ」の節に分け、対象ケースで参照・更新する行だけを同じ名称・区分で示します。該当行がない区分は節ごと省略します。
- 表は「データストア」「関連する参加単位」「横断上の利用」の列とします。関連は参加単位の名称または領域 ID で示します。
- 各行を図の同名ノードへ対応させます。物理保管は全体概要の区分に従い、保管先の詳細や物理項目へ展開しません。

### 6.6. 概念データフロー

- ノード、線種、色、絵文字は全体概要の「凡例（本プロダクト共通）」で選択された記法ルール（[[specdojo:cdfd-mermaid-rulebook|Mermaid 記法ルール]] または [[specdojo:cdfd-d2-rulebook|D2 記法ルール]]）に従います。記法の宣言がなければ Mermaid とし、sample と template は D2 の例とします。参加単位・方向・イベントの要件が記法部品と異なる場合は本書を優先し、Mermaid も `flowchart TB` で縦に描きます。
- 正常系を上から下へ並べます。D2 は `direction: down` とし、戻りの線は上にあるノードを左辺にした `a <- b` で書きます。
- プロセスノードを役割表の行へ対応させ、通常の流れ全体を通して開始イベントと終了の出来事を描きます。分割図や戻りの図へ開始・終了を再掲する必要はありません。イベントは一つのノードに一つの出来事とし、発生を判定できる短い文にします。長い場合は改行し、原文を言い換えません。全体概要の起点イベントが複数の出来事を列挙している場合は、各出来事の文言を保ってノードを分けます。
- 参加単位どうし、または参加単位とデータストアを直接結び、渡す情報・物を名詞のラベルにします。必要な承認は「承認済みの補充依頼」のように成果の性質として表し、引き渡し条件を判定するイベントは置きません。
- Orchestrator とその調整要求・応答は描かず、全体概要の指示の図を参照します。対象範囲内の担当ロールを外部主体として追加しません。
- 図の題は「欠品から売場補充まで」「起票から完了記録まで」のように業務の言葉で付けます。説明は、その図から読み取れる流れや関係を 1 文で書きます。凡例への参照は別の短い注記にし、凡例を再定義しません。
- 一図で追いにくい場合は連続する業務の範囲で分け、接続する参加単位・データストアを同じ ID・名称で再掲します。図ごとに省略事項と共有ノードを短く注記します。

### 6.7. 例外時の戻りの図（任意）

- 不足や不一致を先行する参加単位へ返すことが業務上重要な場合だけ、「概念データフロー」に「例外時の戻り」の図を追加できます。すべての受け渡しを網羅する表は作りません。
- 補完・再判断を担う参加単位へ戻る線に「不足項目」「記録と受入品の差異」などの戻す情報を付けます。通常の図と同じ名称・領域 ID を使います。
- 再提示を示す場合も「修正・承認済みの補充依頼」のような情報の線で表し、戻す条件・再開条件の列や条件イベントは設けません。内部の再試行、ログ、操作手順は描きません。

### 6.8. 未決事項

- 境界、名称、責務、判断者のいずれかが未確定な場合だけ設け、ない場合は章ごと省略します。
- 表は「論点」「影響するケース・参加単位」「決定者」「決定時期」の 4 列とし、本文中の `_UNDECIDED_` と対応させます。

### 6.9. 完成判定

本節だけを `ready` 昇格のチェックリストの正本とします。次の全項目を満たす必要があります。

- ケース ID、業務名、目的、対象範囲、領域 ID・名称が全体概要と一致し、「描き方の選択」で決めた参加単位と詳細化の境界を守っています。
- 「目的」が業務の存在理由・成果を 1〜2 文で示し、読み手の役割を含みません。「適用範囲」は対象と対象外が 1 行ずつで、共通原則は全体概要を参照しています。
- 「プロセス領域」の各節は役割表だけで構成され、全体概要のグループ・区分と一致しています。PDCA の値を示す場合は独立した任意の列にしています。
- 正常系の全参加単位が表と図で同じ順序・名称・領域 ID に対応し、開始から終了まで上から下へ追えます。開始・終了のイベントは一ノード一出来事の短い文で、入口の文言は選んだ方式の規定に従っています。
- 渡す情報・物を線のラベルから読み取れ、引き渡し ID や条件のイベント、「引き渡し」「例外時の戻り先」の章がありません。
- Orchestrator は図に含まれず、その調整は全体概要の指示の図へ委ねられています。
- 図には業務の言葉による題と、読み取れることを示す説明 1 文があり、凡例は全体概要を参照しています。図を分けた場合も共有ノードと接続が追えます。
- 関連データストアは全体概要と同じ名称・区分で、表の各行と図のノードが対応しています。
- 例外時の戻りの図を設けた場合、戻す情報と補完・再判断の責任を持つ参加単位を読み取れます。戻りの図が不要な場合は省略されています。
- `based_on` と本文に `deprecated` の文書への参照がありません。状態定義・遷移を複製せず、有効な STSD や詳細文書を参照しています。

## 7. 禁止事項

- プロセス領域に主要入力・主要出力・データストアの箇条書きを置く、または図をなぞる長文の注記を書く。
- 詳細 CDFD に独自の凡例を再掲・重複定義する。
- 全体概要にないケースや領域分割を作る、または「描き方の選択」の粒度・詳細化の境界を越えて内部処理を再掲する。
- 全体概要と異なるグループ名・区分名・領域 ID・データストア名を使う、または PDCA の値をグループ・区分の列に入れる。
- 引き渡し ID を採番する、引き渡し条件のイベントを図に置く、引き渡し・戻す条件・再開条件の表を設ける。
- Orchestrator の調整を詳細の図に複製する、または対象範囲内の担当者を外部主体にする。
- `deprecated` の文書を `based_on` または本文から参照する。
- 状態定義・遷移表・状態遷移図を複製する、または物理テーブル、カラム、SQL、実装クラス、詳細 API、画面操作を記載する。
