# 概念データフロー図（ユースケース別）作成ルール

Conceptual Data Flow Diagram Use Case Documentation Rulebook

全体概要で選定した一つのユースケースまたは系統について、開始から終了までの流れと、受け渡す情報・物を表と概念データフロー図（Mermaid または D2）で示すためのルールです。状態の定義と遷移は STSD を正本とします。

## 1. 全体方針

- 一文書は、全体概要の「詳細 CDFD 一覧」にある一つのケース ID と、そのユースケースまたは系統を詳細化します。描く単位と詳細化の境界は「描き方の選択」に従います。
- 開始から終了までの横断順序と受け渡しは「概念データフロー」の図だけを正本とします。「プロセス領域」は責務の正本であり、順序欄と章冒頭の通過順は図に一致させる対応表現です。不一致時は図を根拠に表・通過順を修正し、順序を変えるときは図を先に改訂します。「データストア」は全体概要の一覧の部分集合とします。
- 人間と AI Agent の責任分担などの共通原則と凡例は全体概要、状態の定義と遷移は STSD を正本とし、本書で再定義しません。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎ、`deprecated` の文書を参照しないことは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直しません。文書の整形・lint はリポジトリの検証で扱い、「完成判定」に含めません。

## 2. 位置づけ

全体概要（`cdfd-overview`）がケース ID（`C-<nn>`）と業務目的・対象範囲を選定し、本書がその流れを具体化します。領域の分割、名称、担当、起点イベントは全体概要を正本とします。構造・必須項目・禁止事項の判断は本 rulebook に従い、骨組みや作成手順と矛盾する場合もこの内容要件を優先します。

## 3. ファイル命名・ID規則

- 対象プロダクトの業務仕様配下にあるデータフローディレクトリへ配置します。
- ファイル名と成果物 ID は `cdfd-uc-<topic>` とし、ファイル名だけ `.md` を付けます。`<topic>` は全体概要のユースケースまたは系統を表す英小文字・数字・ハイフンのスラッグです。
- product 成果物の ID にプロジェクト ID や authority を付けません。例: ファイル名 `cdfd-uc-replenishment.md`、ID `cdfd-uc-replenishment`。
- ケース ID は全体概要の `C-<nn>` を引き継ぎ、新しい ID の採番や別ケースの ID の流用はしません。
- 領域 ID、プロセスグループ名・区分名、データストア名は全体概要と一致させます。図を分けても同じ対象に同じ ID・名称を使い、接続のための独自 ID は付けません。

## 4. 推奨 Frontmatter 項目

- 共通の必須項目、値・構文・構造は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と同標準が参照するスキーマに従い、本書では再定義しません。成果物種別は本 rulebook の `deliverable_type` に従います。
- `based_on` に全体概要を記載する場合も product 成果物 ID を使用し、成果物カタログの `depends_on` の推移閉包に含まれる根拠だけを列挙します。
- ケース ID、ユースケース名、開始・終了は本文で定義し、未定義の Frontmatter 項目を追加しません。

## 5. 本文要件

見出し順・表・記入欄の骨組みは template を正本とし、本章では重複させず、必要な判断情報を定めます。

- **業務の識別と境界（必須）**: 導入文でケース ID と業務名、目的で業務の存在理由と成果、適用範囲で対象と対象外を示します。
- **責務と正本の利用（必須）**: プロセス領域で参加単位の責務と詳細化の境界を、データストアで全体概要から選んだ正本の用途を示します。各節は役割表または利用の表とし、入出力の列挙に展開しません。
- **流れの合意（必須）**: 概念データフローで開始・終了、参加単位、関連データストア、情報・物の受け渡しを示します。各図に業務の言葉による題と説明 1 文を付けます。
- **判断待ちの可視化（条件付き）**: 境界、名称、責務、判断者に未確定の論点がある場合だけ、未決事項を最終章に置きます。

「引き渡し」「例外時の戻り先」の章は設けません。図を分ける場合は「概念データフロー」に `5.1.`、`5.2.` の節を設け、例外時の戻りも同章内の図で示します。

## 6. 記述ガイド

### 6.1. 描き方の選択

全体概要で採用された方式から、次のどちらかを選びます。以下では、表の一行と図の一つのプロセスノードが表す対象を「参加単位」と呼びます。

| 観点         | 通常の横断ユースケース                                                                 | 系統の関係を描く方式の詳細                                                       |
| ------------ | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 対象         | 二つ以上のプロセスグループを横断する一つの業務。単一グループに閉じる業務には作成しない | 全体概要で選定した一つの系統と、通過する共用領域                                 |
| 参加単位     | 一つのプロセスグループを一つの代表ノードにし、名称と含む領域 ID を併記                 | 一つのプロセス領域を一つのノードにし、`P-xx 領域名` を表示                       |
| 表のまとまり | 全体概要のプロセスグループごと                                                         | 全体概要の区分ごと。PDCA の段階で区分を置き換えない                              |
| 詳細化の境界 | グループ内部の領域・プロセス・主要例外は有効な `cdfd-<group>` へ委ねる                 | 対象系統と共用領域の流れを領域単位で示し、非推奨のグループ別 CDFD へ依存しない   |
| 入口         | ケースの開始イベントを描く                                                             | 系統の入口の起点イベントを描き、文言を全体概要の「プロセス領域」の表と一致させる |

どちらの方式でも、複数の系統（ユースケース）が共通して通るプロセス領域（領域のまとまりを含む）の内部は、全体概要またはその領域の詳細文書の 1 か所だけで描きます。ほかの詳細文書では、その領域を 1 つのノードとして置き、領域との受け渡しの線だけを描きます。内部を描く文書を役割表の「参照先」に示し、内部のプロセス・データストアの読み書き・例外時の戻りを重複して展開しません。その領域から外へ返す例外の情報は、受け渡しとして省略せず描きます。

良い例: 共用する実行・評価・完了を 1 ノードにまとめ、内部の正本を参照する。悪い例: 系統ごとに共用領域の内部を描き直す。

### 6.2. 導入文と目的

- 導入文は、全体概要で選んだケース ID と業務名を一文で明示し、目的の前に置きます。
- 目的は、そのユースケースまたは系統が何のためにあるかを 1〜2 文で記述します。
- BA・QE・承認者など、読み手ごとの承認・設計・確認作業を目的に書きません。

良い例: 導入文は「ケース `C-02`『欠品から補充まで』の流れを示す」、目的は「欠品した商品を補充し、売場で販売できるようにする」。悪い例: ケースを特定せず、目的を「BA が承認し、QE が検証するため」とする。

### 6.3. 適用範囲

- 対象はケース ID、参加単位、開始イベント、終了時の成果、必要な組織・システム境界を 1 行（1 文）で示します。
- 対象外は操作手順、補助操作、実装詳細などを 1 行（1 文）で示し、詳細化の境界は「描き方の選択」に従います。

良い例: 対象を「在庫の補充基準割れから販売の商品引受けまで」、対象外を「内部の発注手順・状態遷移は各正本へ委ねる」と分ける。悪い例: 「補充に関する全業務」とだけ書き、内部処理との境界を決めない。

### 6.4. プロセス領域

- 章冒頭にケース ID、図に従う正常系の通過順、全体概要との正本関係を簡潔に示します。条件付きの計画連携・補完だけを担う参加単位は、常に通る主経路と区別し、順序欄に「計画連携時」「補完時」など図に対応する参加場面を示します。
- 全体概要と同じまとまりごとに節（`3.1.`、`3.2.`、…）を設け、見出しは「グループ名または区分名（含む領域 ID）」とします。各節には役割の表だけを置き、入力・出力やデータストアの箇条書きは置きません。
- 表の列は次のとおりです。同じ参加単位が再登場する場合は別の行にして役割を区別します。

| 列                     | 記載内容                                                                                             |
| ---------------------- | ---------------------------------------------------------------------------------------------------- |
| 順序                   | 図から転記する正常系の通過順または条件付きの参加場面。表の独自判断で順番を定めない                   |
| プロセスグループ・区分 | 全体概要で領域をまとめている名称                                                                     |
| 含む領域               | 全体概要と同じ領域 ID。領域単位の行では領域名も併記し、「プロセス領域」という列名にしてよい          |
| PDCA（任意）           | 全体概要にある Plan、Do、Check、Action、全体などの位置付け。「プロセスグループ・区分」とは別の分類軸 |
| 横断上の役割           | このケースで担う業務上の責務                                                                         |
| 参照先                 | 全体概要または有効な詳細文書。未作成の文書は ID をインラインコードで仮置き                           |

良い例: 図の在庫→仕入→販売に合わせて順序欄を 1・2・3 とする。悪い例: 図が在庫→仕入→販売でも、表の節順だけで仕入を 1 とする。

### 6.5. データストア

- 全体概要と同じ「マスタ・構成データ」「トランザクションデータ」の節に分け、対象ケースで参照・更新する行だけを同じ名称・区分で示します。該当行がない区分は節ごと省略します。
- 表は「データストア」「関連する参加単位」「横断上の利用」の列とします。関連は参加単位の名称または領域 ID で示します。
- 各行を図の同名ノードへ対応させます。物理保管は全体概要の区分に従い、保管先の詳細や物理項目へ展開しません。

良い例: 全体概要の「商品台帳」を同じ区分で選び、「在庫が補充基準を参照する」と用途を示す。悪い例: 商品台帳の全カラムや保存パスを転載する。

### 6.6. 概念データフロー

- ノード、線種、色、絵文字は全体概要の「凡例（本プロダクト共通）」で選択された記法ルール（[[specdojo:cdfd-mermaid-rulebook|Mermaid 記法ルール]] または [[specdojo:cdfd-d2-rulebook|D2 記法ルール]]）に従います。記法の宣言がなければ Mermaid とし、sample と template は D2 の例とします。参加単位・方向・イベントの要件が記法部品と異なる場合は本書を優先し、Mermaid も `flowchart TB` で縦に描きます。
- ノードのラベルに絵文字を付けるか付けないかは、全体概要の凡例の方針に合わせ、文書内の全図と系統間でそろえます。付ける場合は凡例の割り当てに従い、同じ対象には同じ絵文字を使います。詳細文書だけで追加・削除・変更しません。
- 正常系を上から下へ並べます。D2 は `direction: down` とし、戻りの線は上にあるノードを左辺にした `a <- b` で書きます。
- プロセスノードを役割表の行へ対応させ、通常の流れ全体を通して開始イベントと終了の出来事を描きます（分割図・戻りの図へは再掲不要）。イベントは一つのノードに一つの出来事とし、発生を判定できる短い文にします。長い場合は改行し、原文を言い換えません。全体概要の起点イベントが複数の出来事を列挙している場合は、各出来事の文言を保ってノードを分けます。
- 参加単位どうし、または参加単位とデータストアを直接結び、渡す情報・物を名詞のラベルにします。必要な承認は「承認済みの補充依頼」のように成果の性質として表し、引き渡し条件を判定するイベントは置きません。
- Orchestrator とその調整要求・応答は描かず、全体概要の指示の図を参照します。対象範囲内の担当ロールを外部主体として追加しません。
- 図の題は「欠品から売場補充まで」「起票から完了記録まで」のように業務の言葉で付けます。説明は、その図から読み取れる流れや関係を 1 文で書きます。凡例への参照は別の短い注記にし、凡例を再定義しません。
- 分割の目安は、一図の受け渡しの線が 15 本を超える場合、または一ノードに入出力の線が合計 10 本以上集まる場合とし、連続する業務の段ごとに図を分けます。線は情報・物・起動・完了・戻り・再提示を各 1 本として数え、配置制御用の非表示線や凡例の線は含めません。目安以内でも線の交差やラベルの密集で接続を追いにくければ分けます。
- 分割後も必要な線を省略せず、接続する参加単位・データストアを同じ ID・名称で再掲します。図ごとに共有ノードと、別図・参照先へ委ねる範囲を短く注記し、開始から終了までの接続を追えるようにします。

良い例: 仕入から販売へ「入荷数量・受入結果」を渡す線を描き、題を「欠品から売場補充まで」とする。悪い例: 「処理フロー」とだけ題を付け、受け渡しの線に情報名を付けない。

### 6.7. 例外時の戻りの図

- 対象範囲に、不足や不一致を補完・再判断する参加単位へ返す流れがある場合は、「概念データフロー」に「例外時の戻り」の図を追加し、重要度で絞らずにすべて描きます（共用領域の内部は「描き方の選択」に従う）。すべての受け渡しを網羅する表は作りません。
- 補完・再判断を担う参加単位へ戻る線に「不足項目」「記録と受入品の差異」などの戻す情報を付けます。通常の図と同じ名称・領域 ID を使います。
- 再提示を示す場合も「修正・承認済みの補充依頼」のような情報の線で表し、戻す条件・再開条件の列や条件イベントは設けません。内部の再試行、ログ、操作手順は描きません。
- 線が多い場合は「概念データフロー」の分割の目安に従い、戻り先または業務の段ごとに図を分け、題に「補充依頼の補完」のように戻す対象を示します。読みやすさのために必要な戻りを削りません。

良い例: 仕入が不足項目を在庫へ返し、在庫が修正・再承認済みの補充依頼を再提示する。悪い例: 「エラー」を行き先なしで描く、または線が増えたので戻りを削る。

### 6.8. 未決事項

- 境界、名称、責務、判断者のいずれかが未確定な場合だけ設け、ない場合は章ごと省略します。
- 各論点は本文中の `_UNDECIDED_` と対応させ、論点と、影響するケース・参加単位を示します。解決済みの論点や論点のない空表は残しません。

良い例: 「共用領域の内部の正本が未確定。`C-01`〜`C-03` の共用領域のノードと参照先に影響」と示す。悪い例: 「詳細は後で検討」とだけ書く。

### 6.9. 完成判定

内容の確認は次の全項目で行います。

- ケース ID、業務名、目的、対象範囲、領域 ID・名称が全体概要と一致し、「描き方の選択」で決めた参加単位と詳細化の境界を守っています。
- 共用領域の内部を描く文書が 1 か所に定まり、ほかの詳細文書では 1 ノードと受け渡しの線で示しています。
- 「目的」が業務の存在理由・成果を 1〜2 文で示し、読み手の役割を含みません。「適用範囲」は対象と対象外が 1 行ずつです。
- 「プロセス領域」の各節は役割表だけで構成され、全体概要のグループ・区分と一致しています。PDCA の値を示す場合は独立した任意の列にしています。
- 図を正本として、役割表の順序欄と章冒頭の通過順が一致しています。全参加単位の名称・領域 ID が表と図で対応し、主経路と条件付きの経路を区別して開始から終了まで上から下へ追えます。開始・終了のイベントは一ノード一出来事の短い文で、入口の文言は選んだ方式の規定に従っています。
- 渡す情報・物を線のラベルから読み取れ、引き渡し ID や条件のイベント、「引き渡し」「例外時の戻り先」の章がありません。
- Orchestrator は図に含まれず、その調整は全体概要の指示の図へ委ねられています。
- 図には業務の言葉による題と説明 1 文があり、凡例は全体概要を参照しています。図を分けた場合も共有ノードと接続が追えます。
- ノードの絵文字の有無・割り当てが全体概要の凡例に合い、文書内の全図と系統間でそろっています。
- 関連データストアは全体概要と同じ名称・区分で、表の各行と図のノードが対応しています。
- 対象範囲の例外時の戻りを重要度で省略せず、戻す情報と補完・再判断の責任を持つ参加単位を読み取れます。戻りがない場合だけ戻りの図を省略しています。
- 状態定義・遷移を複製せず、有効な STSD や詳細文書を参照しています。

## 7. 禁止事項

- プロセス領域に主要入力・主要出力・データストアの箇条書きを置く、または図をなぞる長文の注記を書く。
- 詳細 CDFD に独自の凡例を再掲・重複定義する。
- 全体概要にないケースや領域分割を作る、または「描き方の選択」の粒度・詳細化の境界を越えて内部処理を再掲する。
- 全体概要と異なるグループ名・区分名・領域 ID・データストア名を使う、または PDCA の値をグループ・区分の列に入れる。
- 引き渡し ID を採番する、引き渡し条件のイベントを図に置く、引き渡し・戻す条件・再開条件の表を設ける。
- Orchestrator の調整を詳細の図に複製する、または対象範囲内の担当者を外部主体にする。
- 状態定義・遷移表・状態遷移図を複製する、または物理テーブル、カラム、SQL、実装クラス、詳細 API、画面操作を記載する。
