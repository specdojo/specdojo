# 概念データフロー図（ユースケース別）作成ルール

Conceptual Data Flow Diagram Use Case Documentation Rulebook

全体概要で選定した一つの横断ユースケースについて、複数のプロセスグループを通る順序、グループ間で引き渡す情報、引き渡し条件、条件不成立時の戻り先を、表と Mermaid 図で合意可能にするためのルールです。グループ内部のプロセスと状態遷移は、それぞれプロセスグループ別 CDFD と STSD を参照します。

## 1. 全体方針

- 一文書は、全体概要の「詳細 CDFD 一覧」にある一つのケース ID とユースケースを詳細化します。単一のプロセスグループに閉じる業務には作成しません。
- 「プロセス領域」を順序とグループ別責務の正本、「データストア」を引き渡しで使う上位一覧の部分集合、「引き渡し」を情報・条件・戻す条件の正本、図を開始から終了までの横断順序の正本として併用します。
- 図の一つのプロセスノードは一つのプロセスグループを表します。グループ内部の領域やプロセスを再掲せず、対応する `cdfd-<group>` を参照します。
- 引き渡し条件は、送り元の成果が受け側の開始に足りることを判定できる形にします。条件を満たさない場合の戻り先、戻す情報、再開条件も定めます。
- 状態名・成立条件・遷移元・遷移先・イベント・遷移条件は STSD を正本とします。本書は状態の定義や遷移表を持たず、グループ間の引き渡しだけを扱います。
- 人間が担う承認や最終判断を省略しません。AI Agent やシステムは支援主体として扱えても、責任分担の正本は対応する方針文書を参照します。

## 2. 位置づけと用語定義

| 用語                       | 定義                                                                                                      |
| -------------------------- | --------------------------------------------------------------------------------------------------------- |
| 全体概要                   | プロセス領域、プロセスグループ、データストア、詳細 CDFD の割り当てを定める `cdfd-overview`                |
| ユースケース別 CDFD        | 複数のプロセスグループをまたぐ一つの業務について、グループ間の順序と引き渡し条件だけを定める CDFD         |
| プロセスグループ代表ノード | 横断順序に参加する一つのプロセスグループを表す角丸長方形のノード。グループ内部のプロセスは含めない        |
| 引き渡し                   | 送り元グループの成果を、判定可能な条件の成立後に受け側グループの入力として渡す責任境界                    |
| 引き渡し条件               | 引き渡す情報の完全性、承認、記録の確定など、受け側グループを開始できることを判定する条件                  |
| 戻す条件                   | 引き渡し条件の不成立または受け側で判明した不足により、情報や判断を送り元または先行グループへ返す条件      |
| 例外時の戻り先             | 条件不成立時に補完・再判断を担い、再開条件を成立させるプロセスグループ                                    |
| 関連データストア           | 引き渡し条件の判定または引き渡す情報の正本として必要な、全体概要と同じ名称・区分を持つデータストア        |
| グループ内部               | `cdfd-<group>` が正本とする、領域、個別プロセス、プロセス入出力、主要例外、データストアの具体的な読み書き |

全体概要は横断ユースケースの業務目的、ケース ID、参加グループを選定します。ユースケース別 CDFD はその選定を変えずにグループ間の順序と引き渡しを具体化し、各グループの内部はプロセスグループ別 CDFD へ委ねます。

## 3. ファイル命名・ID規則

- 対象プロダクトの業務仕様配下にあるデータフローディレクトリへ配置します。
- ファイル名と成果物 ID は `cdfd-uc-<topic>` とし、ファイル名だけ `.md` を付けます。`<topic>` は全体概要のユースケースを表す英小文字・数字・ハイフンのスラッグです。
- product 成果物の ID にプロジェクト ID や authority を付けません。例: ファイル名 `cdfd-uc-replenishment.md`、ID `cdfd-uc-replenishment`。
- ケース ID は全体概要の `C-<nn>` 形式をそのまま引き継ぎ、新しい ID を採番したり別のユースケースの ID を流用したりしません。
- 引き渡し ID は文書内で一意な `H-<nn>` 形式とし、正常順序に沿って採番します。同じ引き渡しには、引き渡し表、図、例外時の戻り先で同じ ID を使います。
- プロセスグループ名、領域 ID、データストア名は全体概要と一致させます。プロセスグループ別 CDFD の参照先は `cdfd-<group>` 形式とします。

## 4. 推奨 Frontmatter 項目

| 項目       | 説明                                                  | 必須 |
| ---------- | ----------------------------------------------------- | ---- |
| id         | プロジェクト修飾なしの `cdfd-uc-<topic>`              | ○    |
| type       | `flow`                                                | ○    |
| status     | `draft` / `ready` / `deprecated`                      | ○    |
| rulebook   | `specdojo:cdfd-uc-rulebook`                           | ○    |
| based_on   | 全体概要など、依存関係上許可された直接の内容根拠の ID | 任意 |
| supersedes | 置き換える旧ユースケース別 CDFD の ID                 | 任意 |

- `based_on` に全体概要を記載する場合も product 成果物 ID を使用し、成果物カタログの `depends_on` の推移閉包に含まれる根拠だけを列挙します。
- ケース ID、ユースケース名、対象者、開始・終了条件は本文で定義し、未定義の Frontmatter 項目を追加しません。
- 作成途中の `status` は `draft` とし、完成判定と所定の承認を満たした後の昇格は定められた承認者が行います。

## 5. 本文要件

見出し順・表・記入欄の骨組みは template を正本とします。本章は各章の目的と必須・任意を定めます。

| 番号 | 見出し           | 必須     | 内容                                                                                                          |
| ---- | ---------------- | -------- | ------------------------------------------------------------------------------------------------------------- |
| 冒頭 | 導入文           | ○        | ケース ID、ユースケース、横断目的を一文で定義                                                                 |
| 1    | 目的             | ○        | 対象者と、横断順序・責任境界・設計入力の利用場面                                                              |
| 2    | 適用範囲         | ○        | ケース ID、開始イベント、終了条件、参加グループ、組織・システム境界、対象外、責任分担                         |
| 3    | プロセス領域     | ○        | グループごとの節。説明文、主要入力・主要出力・データストアの箇条書き、横断上の役割の表                        |
| 4    | データストア     | ○        | 全体概要と同じ名称・区分を持つ、引き渡す情報または条件判定に使うデータストアの部分集合                        |
| 5    | 概念データフロー | ○        | 開始イベント、グループ代表ノード、引き渡し条件、関連データストア、終了条件だけを示す Mermaid 図と図直後の注記 |
| 6    | 引き渡し         | ○        | 引き渡し ID、送り元、受け側、引き渡す情報、引き渡し条件、戻す条件                                             |
| 7    | 例外時の戻り先   | ○        | 対象引き渡し、条件不成立、戻り先グループ、戻す情報、再開条件                                                  |
| 8    | 未決事項         | 条件付き | 横断境界、引き渡し条件、戻り先、判断者が未確定な論点。未決事項がある場合だけ設ける                            |

「未決事項」を設ける場合は最終章とします。図を分割する場合は「概念データフロー」に `5.1.`、`5.2.` の節を設け、引き渡し ID を接続キーにします。

## 6. 記述ガイド

### 6.1. 導入文と目的

- 導入文は「ケース `C-02` の欠品から補充まで」のように、全体概要のケース ID とユースケース名を明示し、どのグループ間の引き渡しを定めるかを一文で示します。
- 目的は、誰が横断順序を承認し、誰がグループ間の入出力を設計へ使い、誰が重複・欠落を確認するかを利用結果と結び付けます。
- 上位の業務目的を長く書き写さず、グループ境界の合意によって防ぐ欠落や手戻りを示します。

### 6.2. 適用範囲

- 全体概要からケース ID、ユースケース名、横断するプロセスグループを引き継ぎます。グループを追加・削除・改名する必要がある場合は、先に全体概要を変更します。
- 開始イベントは最初のグループが動き始める出来事、終了条件は最後のグループが受け取った成果を利用可能と判断できる状態として記述します。
- 対象外には、グループ内部の領域・プロセス・主要例外、補助操作、実装詳細、状態の定義・遷移を明記し、対応する `cdfd-<group>` と STSD へ委ねます。
- 人間と AI Agent の責任分担は本文で再定義せず、対応する方針文書を参照します。参照先がない場合は、人間が承認と最終判断を担う原則だけを記載します。

### 6.3. プロセス領域

- 章の冒頭で、ケース ID、参加グループ数、正常系の通過順、全体概要との正本関係を示します。
- 正常系で通過するプロセスグループごとに節（`3.1.`、`3.2.`、…）を設け、見出しは「グループ名（含む領域 ID の範囲）」とします。同じグループが正常系で再登場する場合は別の節とし、その理由を説明します。
- 各節は、そのグループが前段から何を受け取り次段へ何を渡すかを示す 1〜3 文の説明、`**主要入力**`・`**主要出力**`・`**データストア**` の箇条書き、横断上の役割を示す表の順で構成します。
- 表は「順序」「プロセスグループ」「含む領域」「横断上の役割」「参照先」の 5 列とし、一節に一行を記載します。グループ名と領域 ID は全体概要から引き継ぎ、参照先は `cdfd-<group>` 形式とします。
- 内部プロセス、内部例外、担当は書き写しません。未作成の参照先も安定した ID をバッククォートで示し、作成状況は登録簿で追跡します。

### 6.4. データストア

- 全体概要の「データストア」と同じ「マスタ・構成データ」「トランザクションデータ」の節に分け、引き渡す情報または引き渡し条件の判定に使う行だけを掲載します。該当する行がない区分は節ごと省略します。
- 表の列は「データストア」「関連引き渡し」「横断上の利用」とします。関連引き渡しには `H-<nn>` を記載し、どの情報または条件の正本かを利用内容で説明します。
- 名称と区分は全体概要から変更しません。新しいデータストアまたは区分変更が必要なら先に全体概要を変更し、本章だけへ追加しません。
- 各行は概念データフローの同名ノードに対応させます。図に置かないデータストアや、本章に行のないデータストアノードを残しません。

### 6.5. 概念データフロー

- Mermaid のノード、エッジ、形状、線種は Frontmatter の `includes` で指定した記法ルールに従います。
- プロセスノードは「プロセス領域」の各表の一行に対応する代表ノードとし、ラベルにグループ名と含む領域 ID を記載します。内部プロセス ID や処理名は描きません。
- 開始イベント、引き渡し条件、終了条件をイベントノードとして置き、引き渡し ID と情報名をエッジラベルまたはイベントラベルで追跡可能にします。
- データストアは、引き渡し条件の判定または引き渡す情報の正本として必要なものだけを、全体概要と同じ名称・区分で置きます。個別プロセスの読み書きや項目は描きません。
- 図直後に、全体概要の「凡例（本プロダクト共通）」への参照、使用した線種、内部プロセスを省略したこと、図に置いたデータストアの選定理由を記載します。
- 一図で順序を追えない場合は連続する引き渡し単位で分割し、前図の終了側と後図の開始側へ同じ引き渡し ID を記載します。

### 6.6. 引き渡し

- 一行を一つのグループ間引き渡しとし、「引き渡し ID」「送り元グループ」「受け側グループ」「引き渡す情報」「引き渡し条件」「戻す条件」の 6 列を使用します。
- 引き渡す情報は「補充依頼」「承認済みの評価結果」のような業務上の名詞で記述し、ファイル形式や API 項目へ展開しません。
- 引き渡し条件は、必要情報、承認、記録確認などの成立を第三者が yes / no で判定できる形にします。「処理が終わった」「問題がない」だけで終わらせません。
- 戻す条件は、どの不足または不一致で受け側が開始できないかを示します。戻しが発生しない引き渡しは、その根拠を記載し、空欄にしません。

### 6.7. 例外時の戻り先

- 表は「対象引き渡し」「条件不成立」「戻り先グループ」「戻す情報」「再開条件」の 5 列とし、すべての引き渡し ID を一度以上確認します。
- 戻り先は補完・再判断の責任を持つ参加グループから選びます。グループ内部のどのプロセスへ戻すかは、対応するプロセスグループ別 CDFD に委ねます。
- 再開条件は、修正済み情報の再提示、承認の成立、正本の読み返し確認など、同じ引き渡しを再評価できる条件にします。
- 受け側の内部だけで完結する例外、ログ、再試行は記載しません。横断順序またはグループ間責任が変わるものだけを扱います。

### 6.8. 未決事項

- 横断境界、引き渡し条件、戻り先、判断者のいずれかが未確定な場合だけ設けます。ない場合は章ごと省略します。
- 表は「論点」「影響するケース・引き渡し」「決定者」「決定時期」の 4 列とし、本文中の `_UNDECIDED_` と対応させます。
- 調査で埋める不足は `_TODO_`、意思決定待ちは `_UNDECIDED_`、仮置きする前提は `_ASSUMPTION_` として区別します。

### 6.9. 完成判定

- 全体概要のケース ID、ユースケース名、業務目的、参加グループと矛盾せず、二つ以上のプロセスグループを横断しています。
- 正常系の全参加グループが「プロセス領域」の節と図へ同じ順序・名称・領域 ID で登場し、各節が説明文、三つの箇条書き、役割表の順で構成されています。
- 隣接するグループ間に引き渡し ID があり、引き渡す情報、引き渡し条件、戻す条件が空欄なく定義されています。
- 図の各プロセスノードが一つのプロセスグループを表し、内部領域・内部プロセス・グループ内例外を再掲していません。
- 関連データストアの名称・区分が全体概要と一致し、引き渡し条件に不要なデータストアや物理項目がありません。
- 「データストア」は全体概要の部分集合で、各行が引き渡し ID と図の同名ノードに対応しています。
- 例外時の戻り先から、条件不成立、戻す情報、補完責任、再開条件を説明できます。
- 状態定義、遷移表、状態遷移図を持たず、必要な STSD と各 `cdfd-<group>` を参照しています。
- `_TODO_` が残っていません。`_UNDECIDED_` は「未決事項」と対応しています。

## 7. 禁止事項

- 単一グループに閉じる業務へユースケース別 CDFD を作成したり、全体概要にないケースを先に詳細化したりしません。
- product 成果物 ID を `<project-id>:cdfd-uc-<topic>` にしたり、`cdfd-<group>` と同じ命名で作成したりしません。
- ケース ID を採番し直したり、引き渡し ID を図・引き渡し表・例外時の戻り先で不一致にしたりしません。
- グループ内部の領域、個別プロセス、プロセス入出力、主要例外、操作手順を再掲しません。
- プロセスグループ別 CDFD と異なる責務をグループ代表ノードへ割り当てたり、全体概要と異なる領域 ID・データストア名・区分を使ったりしません。
- 状態名・成立条件を定義したり、遷移元・遷移先・遷移条件の表や状態遷移図を複製したりしません。
- 引き渡し条件や再開条件を「完了した」「適切になった」「問題がなくなった」のような判定不能な表現だけで記述しません。
- 物理テーブル、カラム、SQL、実装クラス、詳細 API、画面操作を概念フローへ記載しません。
- 受け側グループ、戻り先グループ、引き渡す情報のいずれかがない矢印や表行を残しません。
- 作成状況やレビュー状態を成果物本文へ記載せず、登録簿で追跡します。
