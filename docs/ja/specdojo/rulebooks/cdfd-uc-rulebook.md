# 概念データフロー図（ユースケース別）作成ルール

Conceptual Data Flow Diagram Use Case Documentation Rulebook

全体概要で選定した一つの横断ユースケース、または系統の関係を描く方式における一つの系統について、プロセス領域や複数のプロセスグループを通る順序、引き渡す情報、引き渡し条件、条件不成立時の戻り先を、表と概念データフロー図（Mermaid または D2）で合意可能にするためのルールです。グループ内部のプロセスと状態遷移は、それぞれプロセスグループ別 CDFD と STSD を参照します（系統の関係を描く方式の詳細として使う場合は、プロセス領域の単位で描きます）。

## 1. 全体方針

- 一文書は、全体概要の「詳細 CDFD 一覧」にある一つのケース ID とユースケース（または系統）を詳細化します。単一のプロセスグループに閉じる業務には作成しません（系統の関係を描く方式の詳細として使う場合を除く）。
- 「プロセス領域」を順序とグループ別（または領域別）責務の表の正本、「データストア」を引き渡しで使う上位一覧の部分集合、「引き渡し」を情報・条件・戻す条件の正本、図を開始から終了までの横断順序の正本として併用します。プロセス領域に主要入力・主要出力の箇条書きは設けず、受け渡しは図を正本とします。
- 図の一つのプロセスノードは、通常の横断ユースケースでは一つのプロセスグループを表します（対応する `cdfd-<group>` を参照）。系統の関係を描く方式の詳細として使う場合は、プロセスグループの代表ノードではなくプロセス領域（`P-xx`）の単位でノードを描くことができます。
- 系統の関係を描く方式の詳細として使う場合は、その系統の入口の起点イベントを図に描きます。起点イベントの文言は全体概要の「プロセス領域」の表と同じにします。
- 引き渡し条件は、送り元の成果が受け側の開始に足りることを判定できる形にします。条件を満たさない場合の戻り先、戻す情報、再開条件も定めます。
- 状態名・成立条件・遷移元・遷移先・イベント・遷移条件は STSD を正本とします。本書は状態の定義や遷移表を持たず、グループ間（または領域間）の引き渡しだけを扱います。
- 目的は 1〜2 文、適用範囲は対象と対象外を 1 行ずつとし、人間と AI Agent の責任分担などの共通原則は全体概要を参照します。凡例は全体概要の凡例を参照し、本書で再定義しません。

## 2. 位置づけと用語定義

| 用語                       | 定義                                                                                                                                     |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 全体概要                   | プロセス領域、プロセスグループ、データストア、詳細 CDFD の割り当てを定める `cdfd-overview`                                               |
| ユースケース別 CDFD        | 複数のプロセスグループをまたぐ一つの業務、または一つの系統について、順序と引き渡し条件だけを定める CDFD                                  |
| プロセスグループ代表ノード | 横断順序に参加する一つのプロセスグループを表す角丸長方形のノード。グループ内部のプロセスは含めない                                       |
| プロセス領域ノード         | 系統の関係を描く方式の詳細として使う場合に、プロセス領域（`P-xx`）を表す角丸長方形のノード                                               |
| 起点イベント               | 系統の入口となるプロセス領域を開始させる出来事。系統の関係を描く方式の詳細では図に描き、文言は全体概要の「プロセス領域」の表と同じにする |
| 引き渡し                   | 送り元グループ（または領域）の成果を、判定可能な条件の成立後に受け側の入力として渡す責任境界                                             |
| 引き渡し条件               | 引き渡す情報の完全性、承認、記録の確定など、受け側を開始できることを判定する条件                                                         |
| 戻す条件                   | 引き渡し条件の不成立または受け側で判明した不足により、情報や判断を送り元または先行グループへ返す条件                                     |
| 例外時の戻り先             | 条件不成立時に補完・再判断を担い、再開条件を成立させるプロセスグループ（または領域）                                                     |
| 関連データストア           | 引き渡し条件の判定または引き渡す情報の正本として必要な、全体概要と同じ名称・区分を持つデータストア                                       |
| グループ内部               | `cdfd-<group>` が正本とする、領域、個別プロセス、プロセス入出力、主要例外、データストアの具体的な読み書き                                |

全体概要は横断ユースケースの業務目的、ケース ID、参加グループ（または系統の範囲）を選定します。ユースケース別 CDFD はその選定を変えずに順序と引き渡しを具体化し、今の方式では各グループの内部はプロセスグループ別 CDFD へ委ね、系統の関係を描く方式の詳細として使う場合はプロセス領域の単位で描きます。

## 3. ファイル命名・ID規則

- 対象プロダクトの業務仕様配下にあるデータフローディレクトリへ配置します。
- ファイル名と成果物 ID は `cdfd-uc-<topic>` とし、ファイル名だけ `.md` を付けます。`<topic>` は全体概要のユースケースを表す英小文字・数字・ハイフンのスラッグです。
- product 成果物の ID にプロジェクト ID や authority を付けません。例: ファイル名 `cdfd-uc-replenishment.md`、ID `cdfd-uc-replenishment`。
- ケース ID は全体概要の `C-<nn>` 形式をそのまま引き継ぎ、新しい ID を採番したり別のユースケースの ID を流用したりしません。
- 引き渡し ID は文書内で一意な `H-<nn>` 形式とし、正常順序に沿って採番します。同じ引き渡しには、引き渡し表、図、例外時の戻り先で同じ ID を使います。
- プロセスグループ名、領域 ID、データストア名は全体概要と一致させます。プロセスグループ別 CDFD の参照先は `cdfd-<group>` 形式とします。

## 4. 推奨 Frontmatter 項目

| 項目       | 説明                                                  | 必須 |
| ---------- | ----------------------------------------------------- | ---- |
| id         | プロジェクト修飾なしの `cdfd-uc-<topic>`              | ○    |
| type       | `flow`                                                | ○    |
| status     | `draft` / `ready` / `deprecated`                      | ○    |
| rulebook   | `specdojo:cdfd-uc-rulebook`                           | ○    |
| based_on   | 全体概要など、依存関係上許可された直接の内容根拠の ID | 任意 |
| supersedes | 置き換える旧ユースケース別 CDFD の ID                 | 任意 |

- `based_on` に全体概要を記載する場合も product 成果物 ID を使用し、成果物カタログの `depends_on` の推移閉包に含まれる根拠だけを列挙します。
- ケース ID、ユースケース名、対象者、開始・終了条件は本文で定義し、未定義の Frontmatter 項目を追加しません。
- 作成途中の `status` は `draft` とし、完成判定と所定の承認を満たした後の昇格は定められた承認者が行います。

## 5. 本文要件

見出し順・表・記入欄の骨組みは template を正本とします。本章は各章の目的と必須・任意を定めます。

| 番号 | 見出し           | 必須     | 内容                                                                                                                                                                                |
| ---- | ---------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 冒頭 | 導入文           | ○        | ケース ID、ユースケース、横断目的を一文で定義                                                                                                                                       |
| 1    | 目的             | ○        | 対象者と利用場面（1〜2 文）                                                                                                                                                         |
| 2    | 適用範囲         | ○        | 対象と対象外を 1 行ずつ。共通の原則（人間と AI Agent の責任分担など）は全体概要を参照                                                                                               |
| 3    | プロセス領域     | ○        | グループ（またはプロセス領域）ごとの節。各節は役割の表のみ（主要入力・主要出力・データストアの箇条書きは不要）                                                                      |
| 4    | データストア     | ○        | 全体概要と同じ名称・区分を持つ、引き渡す情報または条件判定に使うデータストアの部分集合                                                                                              |
| 5    | 概念データフロー | ○        | 開始イベント（系統の詳細では入口の起点イベントを含む）、プロセスノード、引き渡し条件、関連データストア、終了条件の図（Mermaid または D2）。図の説明は 1〜2 文。凡例は全体概要を参照 |
| 6    | 引き渡し         | ○        | 引き渡し ID、送り元、受け側、引き渡す情報、引き渡し条件、戻す条件                                                                                                                   |
| 7    | 例外時の戻り先   | ○        | 対象引き渡し、条件不成立、戻り先グループ、戻す情報、再開条件                                                                                                                        |
| 8    | 未決事項         | 条件付き | 横断境界、引き渡し条件、戻り先、判断者が未確定な論点。未決事項がある場合だけ設ける                                                                                                  |

「未決事項」を設ける場合は最終章とします。図を分割する場合は「概念データフロー」に `5.1.`、`5.2.` の節を設け、引き渡し ID を接続キーにします。

## 6. 記述ガイド

### 6.1. 導入文と目的

- 導入文は「ケース `C-02` の欠品から補充まで」のように、全体概要のケース ID とユースケース名を明示し、どのグループ間の引き渡しを定めるかを一文で示します。
- 目的は、誰が横断順序を承認し、誰がグループ間の入出力を設計へ使い、誰が重複・欠落を確認するかを 1〜2 文で簡潔に記述します。

### 6.2. 適用範囲

- 対象（ケース ID、ユースケース名、横断するプロセスグループ、開始イベント、終了条件）と対象外（グループ内部の領域・プロセス・主要例外、補助操作、状態定義・遷移）をそれぞれ 1 行（1 文）で明記します。
- 人間と AI Agent の責任分担などの共通原則は本文で再定義せず、全体概要（またはプロジェクト方針文書）を参照します。

### 6.3. プロセス領域

- 章の冒頭で、ケース ID、参加グループ数（または対象領域数）、正常系の通過順、全体概要との正本関係を簡潔に示します。
- 正常系で通過するプロセスグループごとに節（`3.1.`、`3.2.`、…）を設け、見出しは「グループ名（含む領域 ID の範囲）」とします。系統の関係を描く方式の詳細として使う場合は、プロセスグループごと、またはプロセス領域ごとに節を設けます。
- 各節は役割を示す表のみで構成します。主要入力・主要出力・データストアの箇条書きは記載せず、受け渡しは概念データフロー図および「引き渡し」章を正本とします。
- 表は「順序」「プロセスグループ」「含む領域」（または「プロセス領域」）「横断上の役割」「参照先」の列とし、一節に一行を記載します。

### 6.4. データストア

- 全体概要の「データストア」と同じ「マスタ・構成データ」「トランザクションデータ」の節に分け、引き渡す情報または引き渡し条件の判定に使う行だけを掲載します。該当する行がない区分は節ごと省略します。
- 表の列は「データストア」「関連引き渡し」「横断上の利用」とします。
- 名称と区分は全体概要から変更しません。

### 6.5. 概念データフロー

- ノード、エッジ、形状、線種は、全体概要の「凡例（本プロダクト共通）」で選択された記法ルール（`specdojo:cdfd-mermaid-rulebook` または `specdojo:cdfd-d2-rulebook`）に従います。全体概要で記法が宣言されていない場合は Mermaid 記法に従います。
- プロセスノードは「プロセス領域」の各表の一行に対応するノードとします。通常の横断ユースケースでは代表ノードとし、ラベルにグループ名と含む領域 ID を記載します。系統の関係を描く方式の詳細として使う場合は、プロセスグループの代表ノードではなくプロセス領域（`P-xx`）の単位でノードを描くことができます（例: `P-01 領域名`）。いずれの場合も内部プロセス ID や処理名は描きません。
- 開始イベント、引き渡し条件、終了条件をイベントノードとして置き、引き渡し ID と情報名をエッジラベルまたはイベントラベルで追跡可能にします。系統の関係を描く方式の詳細として使う場合は、その系統の入口の起点イベントを図に描きます。起点イベントの文言は全体概要の「プロセス領域」の表と同じにします。
- データストアは、引き渡し条件の判定または引き渡す情報の正本として必要なものだけを、全体概要と同じ名称・区分で置きます。
- 図直後に、全体概要の「凡例（本プロダクト共通）」を参照する旨、および省略事項を 1〜2 文で簡潔に注記します。

### 6.6. 引き渡し

- 一行を一つのグループ間引き渡しとし、「引き渡し ID」「送り元グループ」「受け側グループ」「引き渡す情報」「引き渡し条件」「戻す条件」の 6 列を使用します。
- 引き渡す情報は「補充依頼」「承認済みの評価結果」のような業務上の名詞で記述し、ファイル形式や API 項目へ展開しません。
- 引き渡し条件は、第三者が yes / no で判定できる形にします。

### 6.7. 例外時の戻り先

- 表は「対象引き渡し」「条件不成立」「戻り先グループ」「戻す情報」「再開条件」の 5 列とし、すべての引き渡し ID を一度以上確認します。
- 戻り先は補完・再判断の責任を持つ参加グループから選びます。
- 再開条件は、修正済み情報の再提示、承認の成立、正本の読み返し確認など、同じ引き渡しを再評価できる条件にします。

### 6.8. 未決事項

- 横断境界、引き渡し条件、戻り先、判断者のいずれかが未確定な場合だけ設けます。ない場合は章ごと省略します。
- 表は「論点」「影響するケース・引き渡し」「決定者」「決定時期」の 4 列とし、本文中の `_UNDECIDED_` と対応させます。

### 6.9. 完成判定

本節だけを `ready` 昇格のチェックリストの正本とします。次の全項目を満たす必要があります。

- 全体概要のケース ID（または系統の指定）、ユースケース名、業務目的、参加グループ（またはプロセス領域）と矛盾していません（通常の横断ユースケースでは二つ以上のプロセスグループを横断し、系統の関係を描く方式の詳細では対象系統のプロセス領域を網羅している）。
- 「目的」が 1〜2 文で定義され、「適用範囲」に対象と対象外が 1 行ずつ明記され、共通原則として全体概要が参照されています。
- 正常系の全参加グループ（またはプロセス領域）が「プロセス領域」の節と図へ同じ順序・名称・領域 ID で登場し、各節が役割表だけで構成されています（箇条書きを含まない）。
- 隣接するグループ（または領域）間に引き渡し ID があり、引き渡す情報、引き渡し条件、戻す条件が空欄なく定義されています。
- 図の各プロセスノードが一つのプロセスグループ（系統の関係を描く方式の詳細として使う場合はプロセス領域 `P-xx`）を表し、内部プロセス・グループ内詳細例外を再掲していません。
- 系統の関係を描く方式の詳細として使う場合、その系統の入口の起点イベントが図に描かれ、その文言が全体概要の「プロセス領域」の表と一致しています。
- 図の説明・注記は 1〜2 文で簡潔に記載され、凡例は全体概要の凡例を参照しています。
- 関連データストアの名称・区分が全体概要と一致し、引き渡し条件に不要なデータストアや物理項目がありません。
- 例外時の戻り先から、条件不成立、戻す情報、補完責任、再開条件を説明できます。
- 状態定義、遷移表、状態遷移図を持たず、必要な STSD と各 `cdfd-<group>`（または全体概要）を参照しています。

## 7. 禁止事項

- プロセス領域に主要入力・主要出力・データストアの箇条書きを記載する、または図の受け渡しを文章でなぞる長文の注記を書く。
- ユースケース別 CDFD に独自の凡例を再掲・重複定義する。
- 系統の関係を描く方式の詳細として使う場合を除き、単一グループに閉じる業務へユースケース別 CDFD を作成したり、全体概要にないケースを先に詳細化したりする。
- 系統の関係を描く方式の詳細としてプロセス領域単位で描く場合を除き、グループ内部の領域、個別プロセス、プロセス入出力、主要例外、操作手順を再掲する。
- 系統の関係を描く方式の詳細において、起点イベントの文言を全体概要の「プロセス領域」の表と異なる文言で描く。
- プロセスグループ別 CDFD と異なる責務をグループ代表ノードへ割り当てたり、全体概要と異なる領域 ID・データストア名・区分を使ったりする。
- 状態名・成立条件を定義したり、遷移元・遷移先・遷移条件の表や状態遷移図を複製したりする。
- 物理テーブル、カラム、SQL、実装クラス、詳細 API、画面操作を概念フローへ記載する。
