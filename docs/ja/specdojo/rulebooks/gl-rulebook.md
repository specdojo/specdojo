# 用語集（Glossary）作成ルール

Glossary Documentation Rules

業務分析・要求定義・設計・テストで参照する用語集を YAML 形式で記述するルールです。用語の意味と境界を定義し、利用者がガイドや画面・CLI で目にする言葉と対応付けます。

## 1. 全体方針

- 用語集は、同じ言葉を同じ意味で使うための辞書とする。業務の概念に加え、利用者が扱う操作・状態・役割も対象にする。
- 定義は `locale` の言語で書く。英語名、利用者向けのコマンド名、固有名詞の併記は認めるが、翻訳版の定義は別ファイルにする。
- 領域別に分ける場合は、横断の用語を `gl-common`（対象名を付ける場合は `gl-<対象>-common`）へ集め、同じ概念を複数の用語集に定義しない。
- 業務データ辞書やビジネスルールなどから参照する前に用語 ID を採番し、確定後は変更しない。

## 2. 位置づけ

- 用語の意味は用語集を正本とし、業務の判定条件、データ項目、操作手順、実装詳細はそれぞれの仕様・設計へ委ねる。
- 領域ごとの冒頭のコメントまたは代表用語の注記で、扱う範囲と共通・他領域の正本を示す。
- 共通メタ情報とリンク記法は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]]、配置は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] を正本とする。

## 3. ファイル命名・ID規則

### 3.1. ファイル命名

- ファイル名は `gl-<対象領域>.yaml` を基本とする（例: `gl-common.yaml`、`gl-sales.yaml`）。
- 同じ領域の翻訳版を併置するときは `gl-<対象領域>-<locale>.yaml` とし、ファイル名・用語集 ID で区別する（例: `gl-sales-ja.yaml`、`gl-sales-en.yaml`）。
- 同梱の完成例のファイル名は `gl-sample.yaml` とする。

### 3.2. ID規約

- 用語集 ID は schema の `^([a-z0-9-]+:)?gl-[a-z0-9-]+$` に従う。成果物の例は `gl-common`、同梱の完成例は authority を付けた `specdojo:gl-sample` とする。
- 用語 ID は `^tm-[a-z0-9-]+$` に従う。新規採番では `tm-<領域>-<概念>` とし、共通用語には `common` など共有範囲を示す接頭辞を使う。
- 用語 ID は同一プロジェクトの用語集をまたいで一意にする。既に確定・参照されている ID は、接頭辞がなくても維持し、整形や領域分割を理由に改名しない。

## 4. 推奨 Frontmatter 項目

YAML のメタ情報は `specdojo:` で包まずルートに置く。構造と値の制約は `docs/specdojo/schemas/v1/gl.schema.yaml` を正本とし、先頭の modeline から対応 schema を参照する。

| 項目       | 説明                                         | 必須 |
| ---------- | -------------------------------------------- | ---- |
| `id`       | 「ID規約」に従う用語集 ID                    | ○    |
| `type`     | `glossary` 固定                              | ○    |
| `rulebook` | `specdojo:gl-rulebook`                       | ○    |
| `title`    | 対象領域が分かる用語集名                     | ○    |
| `locale`   | 定義の言語（例: `ja` / `en`）                | ○    |
| `status`   | 文書成熟度。`draft` / `ready` / `deprecated` | ○    |

`status` は schema 上は省略可能だが、共通メタ情報の規約に従って記載する。`ready` への昇格は人間が行う。

## 5. 本文要件

### 5.1. ルートキー要件

- メタ情報に加え、ルートに `terms`（用語オブジェクトの配列）を必ず持つ。
- 掲載範囲の概念を識別できる用語を収録し、定義のない分類名や参照先を残さない。
- schema にないルートキーや用語のキーは追加しない。

### 5.2. `terms` の項目

各用語の要素は以下のキーを持つ。

| 項目           | 説明                                                    | 必須 |
| -------------- | ------------------------------------------------------- | ---- |
| `id`           | 用語を安定して識別する用語 ID                           | ○    |
| `term`         | 利用者が目にする正式な呼び方                            | ○    |
| `englishName`  | 概念の英語名                                            | 任意 |
| `aliases`      | 同じ概念の別名・従来表記の配列                          | 任意 |
| `definition`   | 意味と他の概念との境界が分かる定義                      | ○    |
| `notes`        | 読み手向けの前提・例外・使用文脈                        | 任意 |
| `category`     | 同じ用語集内で分類に使う用語 ID                         | 任意 |
| `relatedTerms` | 同じ用語集内の関連用語 ID の配列                        | 任意 |
| `source`       | 根拠文書へのリンク、schema のパス・定義名、URL など     | 任意 |
| `status`       | 用語の採用状態。`official` / `deprecated` / `candidate` | 任意 |
| `example`      | 用語を使う短い例文                                      | 任意 |

必須は `id`・`term`・`definition` の 3 項目とする。任意項目は説明に必要なものだけ記載し、用語の `status` とルートの文書成熟度を混同しない。

## 6. 記述ガイド

### 6.1. 全体方針・位置づけの判断

利用者が概念を区別するために必要な語か、どの領域が意味の正本を持つかで収録先を決める。共通事項は「位置づけ」で示す上位標準を参照し、各領域へ再掲しない。

- 良い例: 販売と在庫の両方で使う「商品」は共通へ置き、販売固有の「つけ残高」は販売へ置く。
- 悪い例: 販売と在庫に同じ「商品」をそれぞれ定義し、更新時にどちらを直すか決まらない。

### 6.2. ファイル命名・ID の判断

新規 ID は領域と概念が読める英小文字の名詞を基本とし、略語は読み手に通じるものに限る。既存の確定 ID の維持を、新規の接頭辞規則より優先する。

- 良い例: 販売の新しい用語に `tm-sales-credit-limit` を採番し、既存の `tm-accounts-receivable` は維持する。
- 悪い例: 領域ごとに `tm-status` を新設する、または接頭辞をそろえるために確定済み ID を改名する。

### 6.3. メタ情報・ルート構造の判断

`title` で対象領域、`locale` で定義の言語が分かり、メタ情報と `terms` が同じ階層にあるかを確認する。

- 良い例: `title: 用語集（販売）`、`locale: ja` とルートの `terms` を持つ。
- 悪い例: 全メタ情報を `specdojo:` の下に入れる、または `terms` を文章で代用する。

### 6.4. 用語の見出し・英語名の判断

`term` はガイド・画面や CLI の表示・コマンド名で利用者が目にする言い方に合わせ、言い換えは `aliases` に置く。英語の用語と `englishName` は小文字にし、SpecDojo の概念名として大文字が定着したもの（Kata など）と固有名詞（SpecDojo など）だけを例外とする。別名として過去の表記を残すことは認める。

- 良い例: `term: つけ`、`englishName: sale on credit`、`aliases: [ツケ, 掛け売り]`。英語の見出しなら `term: job run` とする。
- 悪い例: 利用者が「つけ」と呼ぶものを `term: 売掛債権取引` とする、または `englishName: Sale On Credit` とする。

### 6.5. 定義・注記・根拠の判断

`definition` は一文で意味と境界が分かる説明を基本とする。`notes` は前提・例外・使用文脈だけを補い、定義の繰り返しや、`category`・`relatedTerms` の指定方法など YAML の書き方を含めない。設定キーやコマンドとの対応は概念の理解に必要な範囲で示せるが、項目名の羅列を避け、独立して説明できる概念が増えたら用語を分ける。

- 良い例: つけの注記を「店主が認めた常連客だけが利用する。」とし、残高と限度額は別の用語にする。
- 悪い例: 「構成要素の `category` に本用語を指定する。」と注記する、または定義を「つけとはツケのこと。」で済ませる。
- schema の条件付き規則は、用語間の関係を短く説明し、条件分岐・必須キーの一覧は写さない。根拠は `source` に実在する文書のリンクや schema のパス・定義名で示す。
- 良い例: 「つけは常連客に認める後払いの販売で、つけ残高を管理する。」と関係を示し、厳密な条件は根拠へ委ねる。
- 悪い例: 注記へ schema の `if` / `then` と必須項目をそのまま転記する。
- 未確定の内容には共通ラベル（`_TODO_` / `_UNDECIDED_` / `_ASSUMPTION_`）を使い、確定時には解消する。

### 6.6. 分類・関連用語の判断

ほかの用語の分類に使う概念も用語として定義し、`category` でまとめる。`relatedTerms` は同じ文脈で理解すべき用語に絞る。いずれも同じ用語集内の用語 ID だけを指定する。

- 良い例: 「販売」を定義して、同じファイルの「つけ」の `category` にその ID を指定する。
- 悪い例: 分類名を未定義の文字列にする、または共通用語を分類に使うためだけに領域別の用語集へ複製する。
- 領域をまたぐ関係は `notes` または `source` に正本の用語集への文書リンクと必要なら用語 ID を記し、`category`・`relatedTerms` には入れない。
- 良い例: 共通用語が別ファイルなら「商品の定義は共通用語集を参照する」と文書リンクで案内する。
- 悪い例: 別ファイルにしかない `tm-common-product` を `relatedTerms` に指定する。
- `validate:schema` はファイル内の用語 ID の重複と参照先の存在を検証する。用語集をまたぐ ID の一意性と同じ概念の重複定義は、別途横断で照合する。

### 6.7. 改訂・廃止時の判断

意味の変更・廃止では、共通メタ情報標準の「文書の改訂・廃止とライフサイクル変更管理」に従い、BA が用語 ID を参照するデータ辞書・業務ルール・画面や CLI の用語を洗い出し、DEV が実装、QE がテスト・受入条件の追従を確認する。廃止・確定は PO が判断し、PM が移行作業を管理する。schema にない変更管理項目は YAML に増やさず、個票などの変更記録へ残す。

- 良い例: 意味が変わる用語は新しい ID で定義し、旧用語は `status: deprecated` として後継を注記し、参照元を更新する。
- 悪い例: 旧 ID の定義を別の意味に上書きする、または参照元を確認せず用語を削除する。

## 7. 禁止事項

- 用語 ID を未採番・重複のままにすること、意味の違う用語に使い回すこと、確定後に変更すること。
- `definition` を曖昧に書くこと（例: 「正しく処理される」「いい感じの在庫」など）。
- 用語の説明へ物理テーブル名・内部クラス名・SQL 全文などの実装詳細や、仕様・schema の条件一覧を持ち込むこと。
- 同じ概念を別名・別領域で重複定義し、別名または正本への参照にまとめないこと。
- 読み手向けの意味を補わない編集手順・YAML 記法のメモを `notes` に書くこと。
