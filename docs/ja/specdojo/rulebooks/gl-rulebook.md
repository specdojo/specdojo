# 用語集（Glossary）作成ルール

Glossary Documentation Rules

本ドキュメントは、業務分析・要求定義・設計・テストで参照する **用語集（Glossary）を YAML 形式で記述する標準ルール**です。

## 1. 全体方針

- 用語集は YAML 形式で記述し、プロジェクト内で同じ言葉を同じ意味で使うための「辞書」として機能する。
- 業務データ辞書（BDD）やビジネスルール（BR）などで参照する用語は、先に用語集に登録して **用語ID（`tm-...`）を固定**し、用語集をその正式な参照先（正）とする。
- 用語は **業務用語（日本語）**で記述し、UI文言や内部コード名の辞書化は必要最小限にする。
- プロジェクト固有の用語集はプロジェクトごとに作成・保守し、実データは対象プロジェクトの文書内に記述する。

## 2. 位置づけと用語定義

- 本用語集（Glossary）は、プロジェクト全体の SSOT（Single Source of Truth）としての役割を持つ。
- 各種設計ドキュメントの `glossaryTermId` 等は、すべて本ルールで採番された `tm-...` ID を参照する。

## 3. ファイル命名・ID規則

### 3.1. ファイル命名

- ファイル名: `gl-<対象領域>-<locale>.yaml`
  - 例: `gl-sales-ja.yaml`, `gl-inventory-ja.yaml`
- 多言語化する場合はファイルを分け、1 つのファイル内で言語を混在させない。

### 3.2. ID規約

- 用語集ID: `^gl-[a-z0-9-]+$` の形式とする。
- 用語ID: `^tm-[a-z0-9-]+$` の形式とする。

## 4. 推奨 Frontmatter 項目

YAML ファイルの先頭に、以下のメタデータ（ルートキー）を持たせることを推奨する。

| 項目   | 説明                               | 必須 |
| ------ | ---------------------------------- | ---- |
| id     | 用語集ID（`gl-...`）               | ○    |
| title  | 用語集名（例: 用語集: 在庫・調達） | ○    |
| locale | 言語（例: `ja` / `en`）            | ○    |
| status | `draft` / `ready` / `deprecated`   | 任意 |

## 5. 本文要件

### 5.1. ルートキー要件

- メタデータに加え、トップレベルに `terms`（配列）を必ず持つ。

### 5.2. `terms` の項目

各用語の要素は以下のキーを持つ。

| 項目         | 説明                                                      | 必須 |
| ------------ | --------------------------------------------------------- | ---- |
| id           | 用語ID（`tm-...`）                                        | ○    |
| term         | 用語（正式名称）                                          | ○    |
| englishName  | 英語名（概念の英語表記）                                  | 任意 |
| aliases      | 別名（配列）                                              | 任意 |
| definition   | 定義（境界が分かる説明）                                  | ○    |
| notes        | 補足・運用メモ（前提、例外、使って良い文脈/ダメな文脈等） | 任意 |
| category     | 分類（推奨: 分類用の用語ID、例: `tm-inventory`）          | 任意 |
| relatedTerms | 関連用語ID（配列）                                        | 任意 |
| source       | 出典/参考（URL等）                                        | 任意 |
| status       | `official` / `deprecated` / `candidate` など              | 任意 |
| example      | 用例（短い例文）                                          | 任意 |

## 6. 記述ガイド

### 6.1. IDの命名推奨

- `tm-` の命名は「名詞」を基本とする（例: `tm-reorder-point`）。
- 略語を使う場合は、業務用語集で一般的に通じるものに限定し、必要なら `definition` に補足する。

### 6.2. 定義の書き方

- 用語の定義は「一文で意味が通り、境界が分かる」ように書く。
- 単なる同義語の羅列にならないようにし、他と区別できる条件を明記する。
- 未確定事項や仮置き情報は、共通ラベル（`_TODO_` / `_UNDECIDED_` / `_ASSUMPTION_`）で記述する。

### 6.3. 関連用語の運用

- `relatedTerms` は **用語ID（`tm-...`）** を列挙する。
- 関連が強い（同じ業務文脈でセットで出る）ものを中心にし、増やしすぎない。

## 7. 禁止事項

- 用語IDを未採番のままにすること、または重複させること。
- 用語IDを意味の違う用語に使い回すこと。
- `definition` を曖昧に書くこと（例: 「正しく処理される」「いい感じの在庫」など）。
- 用語の説明に実装詳細（物理テーブル名、内部クラス名、SQL 等）を混ぜること。
- 同じ概念を別名で重複登録し、`aliases` で統合しないこと。
- 1 つのファイル内で言語を混在させること。
- 章番号なし見出しを使用したり、章番号末尾の `.` を省略したりすること。
