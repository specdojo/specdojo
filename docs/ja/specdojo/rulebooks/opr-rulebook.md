# 運用手順 作成ルール

Operations Procedure Runbook (OPR) Documentation Rules

運用手順（`opr-index` / `opr-<term>`）に、第三者が再現できる操作・判断・証跡を記述する基準を定めます。

## 1. 全体方針

`opr-index`（必要に応じて `opr-<term>`）は、恒常運用の実行手順と証跡ルールを一元化する SSOT とする。

- 日次/週次/月次運用を再現可能な手順として定義する
- 障害/アラート対応を優先度別に明文化し、初動を標準化する
- 変更作業（設定変更/デプロイ/ロールバック）の統制を明確化する
- バックアップ確認・リストア演習・バッチ再実行を手順化する
- 証跡（ログ/チケット/チェックリスト/実施記録）を必須化する
- **共通の運用**: 役割は適用先のメンバー定義、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱い、「運用作業の受入確認」に含めない。

### 1.1. index / term 分割方針

- `opr-index` を入口とし、証跡・作業承認・優先度・エスカレーション・手順の記述書式の共通規約を置く
- `opr-<term>` は障害・監視・バッチ・権限・問い合わせ・変更等のドメインが独立する場合に追加する
- 分冊は共通規約を参照し、差分となる具体手順と個別判断を記述する

### 1.2. 運用作業の受入確認

成果物の章ではなく、手順を確定する前に行う運用上の確認である。確認結果は成果物の「証跡」章に、確認日・確認環境・`run_id` 等の識別子と合否を残す。

- 手順を検証環境で実行または模擬し、実施条件・判断分岐・完了条件と証跡を照合する
- 障害時の停止・復旧、再実行時の重複防止、変更時のロールバックを該当する手順で確認する
- 第三者が同じ操作・判断・記録を再現でき、各章の完了条件と、`based_on` の OPD が定める基準（優先度定義と初動目標、RTO/RPO、変更の承認基準と凍結期間、権限の棚卸し周期）のうち該当するものを満たせば合格とする。満たさない基準は該当章に論点として記載する

## 2. 位置づけと用語定義

### 2.1. 位置づけ（他ドキュメントとの関係）

- `opd-index` / `opd-<term>`：運用方針・統制（あるべき姿・判断基準）
- `opr-index` / `opr-<term>`：その方針に基づく実行手順と証跡
- `mip-index`（移行計画）/ `cop-index`（カットオーバー計画）/ `otp-index`（運用切替計画）：本番切替までと切替直後の計画。OPR は恒常運用へ引き継ぐ手順・監視強化期間・切戻し条件を受け取る

### 2.2. 用語定義

一次対応は影響拡大防止の暫定措置と状況確定（切り分け・通知・暫定復旧）、恒久対応は根本原因の除去（修正・設定変更・再発防止）を指す。

## 3. ファイル命名・ID規則

- `id` は `opr-index` または `opr-<term>`（kebab-case。例: `opr-incident`）とし、文書参照ではプロジェクト文書を `<project-id>:opr-index` のように project 修飾する。共通規則は [[specdojo:docs-structure-guide|ドキュメント構造ガイド]] に従う。
- ファイル名はプロジェクト内で一意になるように命名する（日本語可）。
  - 例: `運用手順.md` / `運用手順-障害対応.md`
  - 並び順が必要な場合は接頭辞の番号付与（例: `opr-010-...`）を **任意** で用いてよい
- `<term>` は用語集(GL)の論理名キー（英小文字kebab-case）を用いる（表示名は H1 / ファイル名で日本語を使用してよい）。

## 4. 推奨 Frontmatter 項目

### 4.1. 設定内容

共通項目の必須性・型は「共通の運用」の参照先と [成果物スキーマ](../../../specdojo/schemas/v1/deliverable-frontmatter.schema.yaml) に従う。OPR 固有の値は次のとおり。

| 項目     | 値                              | 必須 |
| -------- | ------------------------------- | ---- |
| id       | `opr-index` または `opr-<term>` | ○    |
| type     | `operations`                    | ○    |
| rulebook | `specdojo:opr-rulebook`         | ○    |

### 4.2. 推奨ルール

- `based_on` には手順判断に直接利用した成果物（例: `opd-*` / `nfr-*` / `issue-*`）のみ列挙する

## 5. 本文要件

本文の見出し順と記入欄の骨組みは Frontmatter で宣言した template を正本とし、本章では各章の目的と必須性だけを定めます。

- 概要、適用範囲・前提、定期点検、障害対応、アラート対応、バックアップ・リストア、バッチ再実行、運用変更、アカウント付与・剥奪、問い合わせ一次対応、証跡、関連文書導線を必須とします。
- 各章は、実施条件、実施者、判断条件、完了条件、証跡のうち該当する要素を第三者が再現できる粒度で定義します。
- `opr-<term>` で該当する作業がない章も省略せず、`なし`、`opr-index 参照`、`本書の範囲外` のいずれかと理由を記載します。
- 未決の条件は該当章に論点と運用への影響を記載します。

## 6. 記述ガイド

以下の節名は扱う内容を示すもので、成果物に生成する見出し・表の列名は template に従う。

### 6.1. 概要（`index` / `<term>`）

- 手順の対象と目的を 1〜3 行で示す
- `opr-index` が実行手順の SSOT であることを明示する
- `opr-<term>` の場合は「`opr-index` の差分・具体化である」ことを 1 行で明示する

### 6.2. 手順適用範囲・前提

- 適用対象、適用外、実施可能時間帯、必要権限を明記する
- 前提（環境、ツール、連絡経路、参照先）を明記する

### 6.3. 日次/週次/月次点検手順

- 頻度別に手順、実施者、完了条件、証跡を定義する
- 実施漏れの検知方法とエスカレーションを明記してよい

### 6.4. 障害対応手順（P1/P2…、切り分け、一次対応、復旧）

- 優先度別に初動目標、切り分け手順、一次対応、復旧手順を明記する
- エスカレーション条件と判断者を明記する
- 停止判断・ロールバックが関わる場合は、判断条件と承認者を必ず書く

### 6.5. アラート対応手順（確認→暫定対応→恒久対応）

- 検知後の確認、暫定対応、恒久対応の流れを明記する
- 誤検知時の扱い（クローズ条件、閾値調整、抑止）を明記する

### 6.6. バックアップ確認・リストア手順（演習含む）

- バックアップ確認項目、リストア手順、演習頻度を明記する
- 演習結果の証跡（ログ/レポート/所要時間）を必須化する
- RTO/RPO がある場合は、達成可否の判定方法を明記する（方針は OPD、実施は OPR）

### 6.7. バッチ再実行・失敗時対応

- 失敗検知、再実行条件、再実行上限、エスカレーションを明記する
- 再実行でデータ重複が起きうる場合は、冪等性/防止策（`run_id` 等）を明記する

### 6.8. 運用変更作業（設定変更・デプロイ・ロールバック）

- 変更種別、承認者、実施条件（時間帯/凍結）、ロールバック条件を明記する
- 変更の証跡（チケット、差分、承認ログ、実施ログ）を必須化する
- 重大変更は事前周知の要否と手段を明記する

### 6.9. アカウント付与/剥奪手順

- 申請→承認→実施→検証→記録の流れを明記する
- 棚卸し（定期）と緊急権限（ブレークグラス）がある場合は、その実施手順と証跡を明記する

### 6.10. 問い合わせ一次対応手順（テンプレ・ナレッジ）

- 問い合わせ分類、一次対応テンプレ、ナレッジ参照先を明記する
- 引き継ぎ条件（開発/業務/運用）を明記する

### 6.11. 証跡（ログ、チケット、チェックリスト、実施記録）

- 必須証跡、保存先、保管期間、参照権限を明記する
- 証跡は URL や `ticket_id`、`run_id` 等で実施結果を第三者が追跡できる粒度で残す
- 表の列は template に従う。「最低限残す識別子」には、チケットは `ticket_id`、実施ログは `run_id` / `job_id`、チェックリストは実施日と実施者のように、証跡種別ごとに検索できる識別子を書く

### 6.12. 関連ドキュメント導線（`opd` 参照、`mip` / `otp` / `cop` 連携）

- `opd-index` への導線を必ず記載する
- `mip-*` / `otp-*` / `cop-*` は必要時のみ連携情報として記載する
- 分冊がない場合でも `（本書のみ）` または `（なし）` を明記する
- 「手順適用範囲・前提」等に記載済みの参照先（技術スタック・環境構成など）は、表の行を `手順適用範囲・前提 参照` のように章タイトルへの参照で満たし、同じリンク・目的を再掲しない

## 7. 禁止事項

| 禁止事項                                               | 理由                                          |
| ------------------------------------------------------ | --------------------------------------------- |
| 優先度別手順（P1/P2等）を省略する                      | 障害時初動が標準化できないため                |
| 証跡要件（ログ/チケット/チェックリスト）を未定義にする | 監査性・追跡性が欠落するため                  |
| 変更作業の承認・ロールバック条件を未記載にする         | 変更統制が崩壊するため                        |
| バックアップ確認・リストア演習を手順化しない           | 復旧可能性が検証できないため                  |
| OPD と矛盾する運用手順を独自定義する                   | 方針と手順の整合が崩れ、運用品質を損なうため  |
| 長大なコマンド列や設定全文を本文に貼り付ける           | 差分管理が破綻するため（別紙/リンクに寄せる） |
