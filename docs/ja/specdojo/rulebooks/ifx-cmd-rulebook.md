# 外部コマンド連携仕様作成ルール

External Command Interface Specification (ECIS) Documentation Rules

外部 CLI プロセスを起動する連携について、実行契約、入出力の約束（渡すもの・受け取るもの・終了コードの意味・作るファイル・副作用・失敗の扱い）、認証注入を YAML 1 ファイルで定義します。引数・オプションの表は持たず、正本（コマンドリファレンスや設定・ガイド）を参照して実装重複を排除します。

## 1. 全体方針

- **1 連携 1 ファイル**: 一つの実行目的と共通の入出力契約を単位とする。CLI やサブコマンドが同じでも、目的・権限・出力契約が異なる場合は分割する。複数 provider をまとめる場合は、共通契約と差異を解決する正本を示す。
- **合意境界に絞る**: 渡すもの、受け取るもの、作るファイル、終了状態、副作用、失敗時の処置を定める。引数・オプション表、起動テンプレート全文、内部実装は転載しない。
- **正本を分担する**: 共通事項は上位の外部 I/F 一覧・設計、値・構文・構造の制約は対応 schema、起動方法は設定・リファレンスを参照する。本書は各キーに必要な判断情報と記述規約を定める。
- **起動方式を事実に合わせる**: 原則はシェルを経由しない。設定を正本とするシェル起動の例外条件は「コマンドと正本参照」に従い、実装と異なる方式を仕様上だけ宣言しない。
- **秘密値を持たない**: 認証は注入方式・参照名・管理境界で表す。秘密値を本文、入力例、出力例、ログに含めない。

## 2. 位置づけ

- ESIL（外部システム I/F 一覧）は連携の存在・方向・目的を示し、本仕様は `spec_ref` の先でプロセス境界の契約を定める。API・ファイル・メッセージ連携が本体で CLI が操作手段にすぎない場合は、各方式の仕様を正本とする。
- 起動方法の正本は対象によって選ぶ。SpecDojo 自身のコマンドはコマンドリファレンス、SpecDojo が起動する AI provider CLI は起動設定の `command_template` と [[specdojo:exec-config-guide|exec 設定ガイド]]、その他の外部 CLI は公式リファレンスや製品マニュアルを参照する。
- ARC は境界・制約・正本分担、DEV は起動と結果判定の実装可能性、QE は正常・異常・再試行の検証可能性、PO / BA は実行目的と副作用の業務上の妥当性を確認する。

## 3. ファイル命名・ID規則

- ファイル名は `ifx-cmd-<term>.yaml`、ID のローカル部分は `ifx-cmd-<term>` とする。`<term>` は連携目的または外部 CLI を表す kebab-case とし、配置と ID の所有範囲は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従う。
- ESIL の `interfaces[].kind` は `コマンド` とし、`interfaces[].spec_ref` から本仕様の ID を一意に解決できるようにする。詳細仕様が未作成の間だけ `TBD` を使用できる。
- 同じ CLI の読取・更新など、契約を分ける場合は `ifx-cmd-git-read` / `ifx-cmd-git-write` のように目的を付ける。バージョンや状態は ID に含めない。
- 同梱の完成例の ID `specdojo:ifx-cmd-sample` は命名上の例外であり、実際の ESIL の参照先には使用しない。

## 4. 先頭メタ項目

- YAML は Frontmatter を持たない。先頭メタ項目の共通原則は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] の「独立 YAML データファイルのメタ情報」に従う。
- 成果物は `type: api`、再利用可能な雛形は `type: template` とし、`rulebook: specdojo:ifx-cmd-rulebook` を指定する。`title` で対象と実行目的を識別する。項目の必須性・型・許容値は `docs/specdojo/schemas/v1/ifx-cmd.schema.yaml` を正本とする。
- 成果物の状態（`status`）は `draft`（作成・改訂中）、`ready`（確定・承認済み）、`deprecated`（非推奨・廃止予定）のいずれかを指定する。成果物の状態を agent が独断で確定（`ready`）へ昇格させない。
- `based_on` には実際に確認した直接の根拠だけを書く。カタログ管理下では `depends_on` の推移閉包内に限定し、起動方法の参照先を示す `command.reference` と役割を混同しない。
- メタ項目の `version` は呼び出し契約の改版、`command.version_constraint` は CLI の対応バージョンを表す。

## 5. 本文要件

YAML の構造、入れ子キー、型、列挙値は `docs/specdojo/schemas/v1/ifx-cmd.schema.yaml` を参照する（スキーマ検証の手順とコマンドは「6.9. 成果物の検証手順」を参照）。以下は契約として満たす内容要件であり、schema が互換性のため任意としている項目も、ここで必須とした場合は記述する。

| 対象キー         | 必須性                         | 契約として定める内容                                                                                                           |
| ---------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| `command`        | 必須                           | 実行目的、実行ファイルの識別方法、起動方式。`reference` に起動方法を解決できる正本を必ず示す                                   |
| `streams`        | 必須                           | stdin の要否、stdout の受領内容と解析対象、stderr の診断用途。各ストリームの形式と意味を明示し、テキストは原則 UTF-8 とする    |
| `files`          | ファイル入出力がある場合は必須 | 渡すファイルと作るファイルのパスまたは解決規則、形式、用途、作成・更新主体。内容の構造は対応する schema・仕様を参照する        |
| `side_effects`   | 副作用の有無の説明が必須       | 外部状態・ローカル環境への変更と利用枠消費。ルートまたは `execution.side_effects` の一方にまとめ、副作用がなければその旨を書く |
| `exit_codes`     | 必須                           | 成功と代表的失敗の終了コード、識別条件、共通カテゴリ、自動再試行の可否                                                         |
| `authentication` | 必須                           | 認証方式、注入機構、参照名、供給元の管理境界、マスク方針。認証不要でもその旨を明示する                                         |
| `execution`      | 必須                           | 作業ディレクトリ、時間・並列実行・ネットワークの制約、冪等性の成立条件または保証できない理由                                   |
| `error_handling` | 必須                           | 再試行の対象と上限・待機方式、タイムアウト、出力解析失敗、認証失敗に対する個別の処置                                           |

schema の後方互換性定義として残されている `arguments` の各項目（種別 `kind` の `argument` / `option` / `positional`、値の供給元 `value_source` の `literal` / `generated` / `config` / `secret` / `user_input`）は、過去の既存仕様との互換性のための定義である。新規作成および改訂では引数表を持たず（PJR-4N3R）、正本参照（`command.reference`）および入出力の約束（`streams`・`files`・`exit_codes`・`side_effects`）へ一本化する。

## 6. 記述ガイド

### 6.1. 連携単位とメタ情報

- **判断基準**: ESIL の連携目的と成功後の状態が対応し、1 ファイルを一つの契約として検証できること。共通事項は上位を参照し、同じ provider 一覧や設定値を複数キーへ繰り返さない。
- **良い例**: 読取と更新を別 ID にし、`title` に対象と目的を書く。provider ごとに実行ファイルが変わるときは、`executable` に設定の該当キーから解決する旨を示し、一覧自体は設定へ委ねる。
- **悪い例**: 一つの仕様に読取・登録・削除を混在させる。設定の provider 一覧を目的・実行ファイル・コメントへそれぞれ転載する。

### 6.2. コマンドと正本参照

- **判断基準**: `purpose` で呼び出し元から見た成功後の状態を示し、`reference` で正本の文書・設定キー・対象操作を特定する。通常は実行ファイルとサブコマンドを分け、`shell: false` とする。
- **シェル起動の例外**: 管理された起動設定を呼び出し元が展開し、その起動契約がシェルを必要とする場合は `shell: true` を認める。シェルを必要とする理由、テンプレートの正本と管理境界、展開する値の検証・制限を確認できる参照先を示す。利用者入力を無制限にシェル構文として評価する契約は認めない。テンプレート全文や複数コマンドの処理手順は仕様へ転載しない。
- **良い例**: AI provider CLI では `reference` に `.specdojo/exec-defaults.yaml` の `providers.<provider>.command_template` と exec 設定ガイドを示す。`shell: true` の理由を stdin から起動引数への変換として説明し、設定の保護と展開値の検証は同ガイドの契約を参照する。
- **悪い例**: 実際はシェルを使うのに `false` と書く。「外部 CLI だから」という理由だけで `true` にする。`executable` に引数やパイプを連結し、起動設定と別のコマンド全文を管理する。

### 6.3. ストリーム

- **判断基準**: stdin は渡す内容と入力終了の約束、stdout は呼び出し元が採用する範囲、stderr は診断の用途を記述する。stdin を使わない場合も要否と形式を明示する。出力内容の詳細構造は正本を参照し、呼び出し元の判定に必要な意味を残す。
- **良い例**: テキストの進捗が混在する stdout では、末尾の構造化報告を抽出する範囲と、欠落・解析失敗時の扱いを示す。終了コードと報告内容の両方で完了を判断する契約なら、どちらが何を保証するかを書く。
- **悪い例**: 構造化部分があることを理由に stdout 全体を JSON と記す。「CLI の既定出力」とだけ書く。stderr が空なら成功と判定する。

### 6.4. ファイル

- **判断基準**: 入力と出力を分け、パスの基準ディレクトリ、可変部分の解決方法（可変パラメータの供給元と書式）、形式、作成・更新主体（producer / consumer）、内容仕様の正本を特定する。外部 CLI が作るファイルと呼び出し元が保存する実行記録を区別する。
- **ファイル入出力を伴わない場合の例外**: CLI がファイルを作成しない場合は `outputs: []`（入力ファイルがない場合は `inputs: []`）を明記し、呼び出し元が保存する実行ログや電子控えの責務と区別する。ファイル入出力を一切行わない CLI では `files` キー自体を省略できる。
- **良い例**: 入力ファイルについて作業ディレクトリからの相対パス、可変部分の解決元（確定済み取引の識別情報など）、作成主体（呼び出し元プロセス）、内容仕様の正本（schema やフォーマット仕様）を示す。CLI 自身が出力ファイルを作成しない場合は `outputs: []` と明記し、呼び出し元のログ保存と責務境界を分ける。
- **悪い例**: 出力を「各種ファイル」とだけ書く。呼び出し元が保存するログや別段階で作成する result を、同じ CLI の出力として列挙する。入力ファイルの作成主体や可変部分の解決元が書かれていない。

### 6.5. 終了状態と識別条件

- **判断基準**: 各終了コードから呼び出し元の次の動作を判断できること。同じコードが複数の意味を持つ場合は、`meaning` に追加信号・判定順・未分類時の扱いを記す。正本に定義された構造化エラーや stdout / stderr の検出条件を参照できればよく、検出パターンの一覧は転載しない。
- **カテゴリの使い分け**: `success` はプロセスの成功を表し、業務完了に別の条件があれば区別する。`input_error` は入力修正、`authentication_error` は再認証、`authorization_error` は権限の見直し、`permanent_failure` は原因解消を必要とする。`rate_limit` は利用制限、`transient_failure` は一時的障害であり、再試行できる条件を失敗処置で定める。
- **良い例**: 非ゼロ終了と設定済み検出信号が一致した場合だけ利用制限とし、ほかの非ゼロ終了は汎用失敗として停止する。認証失敗を個別検出できない実装なら、その制約と手動確認の扱いも書く。
- **悪い例**: 汎用的な exit 1 をすべて一時失敗とする。識別信号がないのに原因別の自動分岐ができると宣言する。exit 0 だけで成果物の検証まで成功したとみなす。

### 6.6. 副作用と冪等性

- **判断基準**: 永続的な変更、利用枠・課金への影響、変更してはならない範囲を示す。`idempotency` は同一入力での再実行の保証を表し、自動再試行する場合は二重処理を防ぐ条件を明記する。保証がなければ、再開前に既存状態をどう扱うかを書く。
- **良い例**: 発注登録では同じリクエスト ID による重複排除を条件とする。非決定的な編集処理では冪等性を保証せず、同じ作業ディレクトリの差分を引き継ぎ、確認して再開する条件を示す。
- **悪い例**: 同じファイル名へ書くという理由だけで業務処理全体が冪等とする。再試行による二重登録や利用枠の追加消費を説明しない。

### 6.7. 認証注入

- **判断基準**: `method` と `injection` は認証の種類と渡し方を分け、`names` には必要な参照名を書く。認証値は起動引数や標準入力へ埋め込まない。`secret_source` には管理境界、`log_policy` には引数・環境変数・stdout・stderr・保存ログのマスク対象とタイミングを書く。認証不要の場合の表現も schema の制約を満たすこと。
- **良い例**: CLI のログインプロファイルを利用する場合、プロファイル名と保管を担う管理境界を示し、呼び出し元が秘密値を注入しないことを書く。環境変数で渡す場合は変数名だけを示す。
- **悪い例**: 認証トークンの実値、秘密値入り URL、個人環境の認証ファイルの実パスを例示する。プロファイルを利用するのに環境変数注入と記す。

### 6.8. 実行制約と失敗処置

- **判断基準**: 作業ディレクトリと時間・並列実行・ネットワークの制約は公開契約や確認した実装・設定を根拠にする。設定から決まる上限を架空の固定値へ置き換えない。schema で参照値や上限なしを表せず判断が未了なら、許容されるプレースホルダと共通ラベルで draft に残し、現在動作・不足する判断・次の確認先を記録する。
- **再試行と回復**: `retryable` と `retry.on_categories` を照合し、対象条件、試行上限の数え方、待機方式を揃える。利用制限でも短時間の制限と利用枠の枯渇を区別し、実際の停止・待機・切替条件は正本へ委ねる。タイムアウト時の子プロセスと部分出力、出力解析失敗時の既存変更、認証失敗時の確認先を個別に定める。
- **良い例**: タイムアウトが未決定なら、現在は終了まで待つことと、上限・終了処置を決める必要を区別して記す。出力異常時は自動再試行を止め、変更を保持して人の確認または再開に委ねる。
- **悪い例**: schema を通すためだけに時間や並列数を捏造する。「失敗時はリトライ」とだけ書く。認証・認可・入力不正を待機だけで回復する一時失敗として扱う。

### 6.9. 成果物の検証手順

作成・改訂した外部コマンド連携仕様 YAML は、schema 検証・modeline 検証・整形確認の機械検証を実施したうえで、呼び出し契約と正本参照の手動照合を行う。移行先リポジトリで同等の検証コマンドが定義されている場合は、その設定に従い相当するコマンドを使用できる。

#### 6.9.1. 個別のスキーマ・modeline 検証

対象ファイルに対して `ifx-cmd.schema.yaml` を用いた構造検証および modeline コメントの検証を実行する。

```bash
# schema を指定した個別ファイルの検証
npm run validate:schema:file -- --schema docs/specdojo/schemas/v1/ifx-cmd.schema.yaml --data <対象YAMLファイルパス>

# modeline（先頭コメントのスキーマ指定）に基づく検証
node packages/docs-lint/bin/specdojo-docs-lint.js yaml-schema --modeline <対象YAMLファイルパス>
```

- **期待結果**: 対象ファイルに対して `valid` と表示され、終了コード 0 で正常終了すること。
- **検証の限界**: スキーマ検証の合格だけでは、正本参照先の実在や、引数・ストリーム・終了コードの業務上の妥当性を保証しない。これらは手動照合で判定する。

#### 6.9.2. 全体検証と整形確認

リポジトリ全体のスキーマ検証および Prettier による整形状態を確認する。

```bash
# 全体スキーマ検証
npm run validate:schema

# 整形の確認
npx prettier --check <対象YAMLファイルパス>
```

- **期待結果**: 全体検証が終了コード 0 で完了し、Prettier の整形差分がゼロ（終了コード 0）であること。エラーが出た場合はエラーメッセージに従って該当箇所を修正し、再実行する。

## 7. 禁止事項

- 引数表、起動テンプレート全文、検出パターン一覧、schema の定義を正本と別に管理すること。
- シェル起動の例外条件を満たさず `shell: true` とすること、または実際の起動方式を隠して `false` とすること。
- 秘密値、秘密値を含む URL、個人の認証パスを本文・例・ログに含めること。
- stdout / stderr、プロセス終了 / 業務完了、CLI の生成物 / 呼び出し元の記録を混同すること。
- 追加信号のない終了コードだけで原因を断定したり、副作用の回復条件がないまま自動再試行したりすること。
- 内部クラス名、プロセス起動ライブラリの API 呼び出し、スクリプト全文など、合意境界に不要な内部実装を記載すること。
