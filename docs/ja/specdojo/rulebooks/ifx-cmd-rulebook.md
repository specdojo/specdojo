# 外部コマンド連携仕様作成ルール

External Command Interface Specification (ECIS) Documentation Rules

外部 CLI プロセスを起動する連携について、実行契約、入出力の約束（渡すもの・受け取るもの・終了コードの意味・作るファイル・副作用・失敗の扱い）、認証注入を YAML 1 ファイルで定義します。引数・オプションの表は持たず、正本（コマンドリファレンスや設定・ガイド）を参照して実装重複を排除します。

## 1. 全体方針

- **1 連携 1 ファイル**: 1 ファイルで、1 つの実行目的と共通の入出力契約を持つコマンド連携を定義する。サブコマンドや出力契約が異なる場合はファイルを分ける。
- **実装重複の排除（正本の参照）**: 引数・オプションの表は仕様内に持たず、正本を参照する。
  - SpecDojo 自身のコマンド: コマンドリファレンス（`command-reference.md` など）を正本とする。
  - SpecDojo が起動する外部の CLI（AI provider CLI など）: その起動を定める設定（`.specdojo/exec-defaults.yaml` の `command_template`）と [[specdojo:exec-config-guide]] を正本とする。
  - その他の外部システム CLI: 当該 CLI の公式コマンドリファレンスや製品マニュアルを正本とする。
- **入出力の約束に特化**: 文書には、呼び出し元と外部 CLI の合意境界に必要な入出力の約束を記載する。
  1. 渡すもの（`streams.stdin`、`files.inputs`）
  2. 受け取るもの（`streams.stdout`、`streams.stderr`）
  3. 終了コードの意味（`exit_codes`）
  4. 作るファイル（`files.outputs`）
  5. 副作用（`side_effects`、`execution.idempotency`）
  6. 失敗の扱い（`error_handling`）
- **シェル経由の禁止**: 実行可能ファイルと引数は配列要素として分離し、既定ではシェルを経由しない（`command.shell: false`）。パイプ、リダイレクト、コマンド置換は 1 つのコマンド契約に埋め込まない。
- **秘密値の保護**: 認証情報は値ではなく注入方式と参照名だけを定義し、仕様、標準入力、出力例、ログに秘密値を記載しない。

## 2. 位置づけと用語定義

| 用語           | 定義                                                                                                        |
| -------------- | ----------------------------------------------------------------------------------------------------------- |
| 外部コマンド   | 対象システムのプロセス境界外にあり、実行可能ファイルと引数を指定して起動する CLI                            |
| 正本参照       | 引数やオプションの完全な定義・テンプレートを展開・解釈する単一の真実情報源（SSOT）への参照                  |
| ストリーム契約 | stdin、stdout、stderr それぞれの使用有無、形式、文字コード、成功時・失敗時の意味                            |
| ファイル契約   | コマンド実行に際して渡す入力ファイル（inputs）や、コマンド実行に伴って作られる出力ファイル（outputs）の約束 |
| 副作用         | コマンド実行によって外部サービスやローカル環境に引き起こされる永続的な状態変化                              |
| 終了カテゴリ   | CLI 固有の終了コードを、成功、入力不正、認証失敗、一時失敗など呼び出し元が扱える意味へ分類した値            |
| 認証注入       | シークレットストアや CLI 認証プロファイルから、プロセスに認証状態を渡す方式。秘密値自体は仕様に含めない     |

ESIL（外部システムI/F一覧）は連携の存在と方向を一覧化し、本仕様は対応する `spec_ref` の先でプロセス起動の契約を定義します。API、ファイル転送、メッセージングが連携の本体であり CLI が単なる操作ツールの場合は、対応する API／ファイル／メッセージ仕様を正本とし、本仕様との責務の重複を避けます。

### 主要な関係者と確認観点

- **ARC（アーキテクト）**: プロセス境界、システム間の責務分担、冪等性、正本参照の妥当性を確認する（`vp-arc-technical-constraints`）。
- **DEV（開発者）**: 正本から起動コマンドを構成でき、渡すもの・受け取るもの・作るファイル・終了コードの分岐が実装可能か確認する（`vp-dev-implementation-readiness`）。
- **QE（品質保証）**: 正常系・異常系の終了コード、入力エラー、タイムアウト、再試行条件がテスト可能か確認する（`vp-qe-verifiability`）。
- **PO / BA（プロダクトオーナー / ビジネスアナリスト）**: コマンドの目的と副作用が業務要件・ユースケースと整合しているか確認する（`vp-po-purpose-alignment`）。

## 3. ファイル命名・ID規則

- ファイル名は `ifx-cmd-<term>.yaml`、`id` は `ifx-cmd-<term>` とし、`<term>` は連携目的または外部 CLI を表す kebab-case にする。
- ESIL の `interfaces[].kind` は `コマンド`、`interfaces[].spec_ref` は本仕様の `id` と一致させる。詳細仕様が未作成の間だけ `TBD` を使用できる。
- 1 つの CLI で複数の実行目的を持つ場合は、`ifx-cmd-git-read` と `ifx-cmd-git-write` のように連携契約単位で分割する。バージョンや状態は ID に含めない。
- package に同梱する sample の ID `specdojo:ifx-cmd-sample` は記述例を識別するための例外であり、ESIL の `spec_ref` には使用しない。

## 4. 先頭メタ項目

YAML の先頭に次のメタ項目を置きます。

| キー         | 説明                                             | 必須 |
| ------------ | ------------------------------------------------ | ---- |
| `id`         | コマンド連携仕様 ID。成果物では `ifx-cmd-<term>` | ○    |
| `type`       | `api` 固定                                       | ○    |
| `title`      | 対象と実行目的が分かる仕様名                     | ○    |
| `status`     | `draft` / `ready` / `deprecated`                 | ○    |
| `rulebook`   | `specdojo:ifx-cmd-rulebook`                      | ○    |
| `version`    | 呼び出し契約の変更を追跡する正の整数             | 任意 |
| `based_on`   | 作成時に直接確認した設計・運用文書の ID 配列     | 任意 |
| `supersedes` | 置き換え対象の文書 ID 配列                       | 任意 |

`based_on` は実際に内容を確認した文書だけとします。コマンド自体のバージョン制約はメタ項目の `version` ではなく、`command.version_constraint` に記載します。

## 5. 本文要件（YAML構成）

外部コマンド連携仕様の YAML は、次のルートキーで構成します。各入れ子キーの必須・任意と条件付き必須に従い、仕様単体で検証可能にします。

### 5.1. ルートキー一覧

| ルートキー       | 定義内容                                                                         | 必須 |
| ---------------- | -------------------------------------------------------------------------------- | ---- |
| `command`        | 実行可能ファイル、用途、正本参照、サブコマンド、シェル経由有無、バージョン制約   | ○    |
| `streams`        | stdin、stdout、stderr の使用有無、データ形式、文字コード、契約                   | ○    |
| `files`          | コマンドに渡す入力ファイル（inputs）や、コマンドが作る出力ファイル（outputs）    | 任意 |
| `side_effects`   | 外部サービスや環境に与える状態変化の定義                                         | 任意 |
| `exit_codes`     | 終了コードと意味、共通カテゴリ、リトライ可否                                     | ○    |
| `authentication` | 認証方式、注入機構、参照名、秘密値の供給元、ログのマスク方針                     | ○    |
| `execution`      | 実行ディレクトリ、タイムアウト、ネットワーク要否、並列実行数、冪等性             | ○    |
| `error_handling` | 再試行対象、試行上限、待機方式、タイムアウト時、出力解析失敗時、認証失敗時の処置 | ○    |
| `arguments`      | 引数・オプションの表。新形式では非推奨（正本参照に一本化、後方互換用に許容）     | 任意 |

### 5.2. 入れ子キーの要件

#### command

| キー                 | 説明                                                                       | 必須 |
| -------------------- | -------------------------------------------------------------------------- | ---- |
| `executable`         | 実行可能ファイル名または配布済み実行パス                                   | ○    |
| `purpose`            | 呼び出し側から見た実行目的と成功後の状態                                   | ○    |
| `reference`          | 正本（コマンドリファレンス、exec 設定、外部マニュアル等）への参照          | ○    |
| `subcommands`        | 起動順のサブコマンド文字列配列（サブコマンドがない場合は空配列または省略） | 任意 |
| `shell`              | シェルを経由するかどうか（原則 `false` 固定）                              | ○    |
| `version_constraint` | 利用を許容する CLI のバージョン範囲                                        | 任意 |

#### streams

| キー     | 説明                                                                                                 | 必須 |
| -------- | ---------------------------------------------------------------------------------------------------- | ---- |
| `stdin`  | 標準入力の契約。`format`（○）、`mode`（`none` / `optional` / `required`）、`encoding`、`description` | ○    |
| `stdout` | 標準出力の契約。`format`（○）、`encoding`、`description`（解析する主要フィールド）                   | ○    |
| `stderr` | 標準エラー出力の契約。`format`（○）、`encoding`、`description`（診断・警告用途）                     | ○    |

#### files（渡すファイル・作るファイル）

ファイル入出力が存在する場合に記載します。

| キー      | 説明                                                                                                  | 必須 |
| --------- | ----------------------------------------------------------------------------------------------------- | ---- |
| `inputs`  | コマンドに渡す入力ファイルの配列。各要素に `path`（○）、`format`（○）、`encoding`、`description`（○） | 任意 |
| `outputs` | コマンドが作る出力ファイルの配列。各要素に `path`（○）、`format`（○）、`encoding`、`description`（○） | 任意 |

#### exit_codes

空配列にせず、少なくとも成功と代表的な失敗コードを定義します。

| キー        | 説明                                                                                                                                                  | 必須 |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| `code`      | CLI が返す整数の終了コード（0 は成功）                                                                                                                | ○    |
| `meaning`   | CLI 固有の意味と呼び出し元が識別できる条件                                                                                                            | ○    |
| `category`  | 終了カテゴリ（`success` / `input_error` / `authentication_error` / `authorization_error` / `rate_limit` / `permanent_failure` / `transient_failure`） | ○    |
| `retryable` | 同じ入力で自動再試行してよいかどうか（boolean）                                                                                                       | ○    |

#### authentication

外部コマンドが認証を必要としない場合は、`method: none`、`injection.mechanism: none`、`injection.names: []`、`secret_source: なし`、`log_policy: マスク対象なし` を明記します。

| キー            | 説明                                                                         | 必須 |
| --------------- | ---------------------------------------------------------------------------- | ---- |
| `method`        | 認証方式（`none` / `api_token` / `oauth` / `ssh_key` / `provider_login` 等） | ○    |
| `injection`     | 認証注入機構。`mechanism`（○）、`names`（○: 参照名配列）                     | ○    |
| `secret_source` | シークレットストアや CLI プロファイルなど値の管理境界                        | ○    |
| `log_policy`    | 引数、環境変数、stdout、stderr、エラー記録のマスク条件                       | ○    |

#### execution

| キー                | 説明                                                                                     | 必須 |
| ------------------- | ---------------------------------------------------------------------------------------- | ---- |
| `working_directory` | 実行時の作業ディレクトリ（例: `repository_root`）                                        | ○    |
| `timeout_seconds`   | 1 回の起動上限秒数（正の整数）                                                           | ○    |
| `network_required`  | ネットワークアクセスの要否（boolean）                                                    | ○    |
| `max_parallel`      | 同時実行上限（正の整数）                                                                 | ○    |
| `idempotency`       | 冪等性の保証。`guaranteed`（boolean、○）、`condition`（成立条件または保証不可の理由、○） | ○    |
| `side_effects`      | 外部システムや環境に与える状態変化の記述（ルートキーまたはここに記載）                   | 任意 |

#### error_handling

| キー                            | 説明                                                                                                                                 | 必須 |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ---- |
| `retry`                         | 再試行ポリシー。`on_categories`（○: 対象カテゴリ配列）、`max_attempts`（○: 0以上の整数）、`backoff`（○: `exponential` / `fixed` 等） | ○    |
| `timeout_action`                | タイムアウト時の処置（プロセス終了、不完全出力破棄、人へのエスカレーション等）                                                       | ○    |
| `malformed_output_action`       | 出力解析失敗時の処置（自動再試行の抑止、ログ記録、確認依頼等）                                                                       | ○    |
| `authentication_failure_action` | 認証失敗時の処置（再認証依頼、運用担当通知等）                                                                                       | ○    |

## 6. 記述ガイド

### 6.1. command と 正本の参照

- `command.reference` には、引数・オプション定義の正本を明記する。
  - SpecDojo 自身のコマンド: コマンドリファレンス（例: `command-reference.md`）
  - SpecDojo が起動する外部 CLI（AI provider CLI など）: 起動設定（`.specdojo/exec-defaults.yaml` の `command_template`）と [[specdojo:exec-config-guide]]
  - その他の外部システム CLI: 公式ドキュメントの URL やマニュアル
- `command.executable` は実行可能ファイル名または配布済みパスを記載し、引数やパイプを連結しない。
- `command.shell` は `false` 固定とする。複数コマンドの連携は実行側のワークフローで表し、文字列のシェルスクリプトとして仕様化しない。
- 引数やオプションの表（`arguments`）は本文中に作成せず、正本側に委ねる。これにより、実装コードや CLI 側の変更に伴う二重メンテや記述の食い違いを排除する。

### 6.2. 入出力の約束（渡すもの・受け取るもの・作るファイル）

- **渡すもの**:
  - `streams.stdin` は標準入力を通じてデータを渡す場合に記載する。使用しない場合は `mode: none`、`format: none` とする。
  - 入力ファイルとしてデータを渡す場合は、`files.inputs` にファイルパス、形式、文字コード、内容の説明を記載する。
- **受け取るもの**:
  - `streams.stdout` は成功時に呼び出し元が解析する形式と主要フィールドを記載する。機械処理する場合は `json` または `jsonl` を優先し、人向けの可変文言に依存しない。
  - `streams.stderr` は進捗、警告、失敗詳細のどれが出力されるかを記載する。stderr の文言だけで成否を判定せず、終了コードと構造化出力を優先する。
- **作るファイル**:
  - コマンド実行に伴って成果物や受領書、ログファイル等が作成・更新される場合は、`files.outputs` にパス、形式、内容の説明を記載する。
- 形式は `text` / `json` / `jsonl` / `yaml` / `binary` / `none` から選び、テキスト形式には原則 `UTF-8` を指定する。

### 6.3. 終了コードと終了カテゴリ

CLI が返す終了コードを次の共通カテゴリ（`category`）に写像し、呼び出し元が機械的に分岐できるようにします。

| カテゴリ               | 意味と使い分け                                                               | retryable の原則 |
| ---------------------- | ---------------------------------------------------------------------------- | ---------------- |
| `success`              | 処理が正常に完了した（通常 exit 0）                                          | `false`          |
| `input_error`          | コマンド引数・入力データ・前提ファイルの形式が不正（呼び出し側の修正が必要） | `false`          |
| `authentication_error` | 認証情報の未設定、失効、期限切れ（再認証や設定修正が必要）                   | `false`          |
| `authorization_error`  | 実行に必要な権限が不足している                                               | `false`          |
| `rate_limit`           | API や外部サービスの利用枠・短時間あたりの呼び出し頻度制限に達した           | `true`（待機後） |
| `transient_failure`    | ネットワーク瞬断、相手先サービスの一時的過負荷・メンテナンスなど             | `true`           |
| `permanent_failure`    | 存在しないリソースの指定、サポート外の操作など（再試行しても成功しない失敗） | `false`          |

複数の意味に使われる終了コードは、追加の判定条件を `meaning` に記載します。汎用的な exit 1 のみを安易に `rate_limit` や `transient_failure` とみなさず、専用コードまたは構造化エラー出力で識別できる場合だけそれらのカテゴリを使用します。

### 6.4. 副作用と冪等性

- `side_effects` には、コマンド実行によって生じる外部リソースの作成・変更・削除や外部システムへの永続化内容を記載する。副作用がない読み取り専用コマンドの場合は「副作用なし（参照のみ）」と記載する。
- `execution.idempotency.guaranteed` は同一入力で複数回実行した際に結果が一貫するかを示し、`condition` にその成立条件（例: 「同じリクエスト ID に対して既存の結果を返す」「同一ファイルパスを上書きする」など）を明記する。副作用のあるコマンドを自動再試行する場合は、二重処理を防ぐ条件の明記が必須となる。

### 6.5. 認証注入

- `method` は `none` / `api_token` / `oauth` / `ssh_key` / `provider_login` から選び、連携先が要求する認証の種類を示す。
- `injection.mechanism` は `none` / `environment_variable` / `credential_store` / `workload_identity` / `cli_profile` から選び、必要な参照名を `injection.names` に列挙する。
- `secret_source` に値を供給する管理境界を記載し、`log_policy` に引数、環境変数、stdout／stderr のマスク条件を記載する。
- 認証トークン、秘密鍵、パスワード、認証プロファイルの実パスを仕様や例に記載しない。コマンド引数への秘密値の埋め込みも禁止する。

### 6.6. 実行制約と失敗の扱い

- `execution.timeout_seconds` は 1 回の起動上限秒数、`max_parallel` は同時実行上限とし、コマンドの公開契約や実測根拠から決める。
- `error_handling.retry` は `on_categories` に再試行対象のカテゴリ（`transient_failure`, `rate_limit` 等）を指定し、`max_attempts`（最大試行回数）と `backoff`（バックオフ方式）を記載する。認証失敗や入力不正は自動再試行しない。
- タイムアウト時のプロセス強制終了、不完全出力の破棄、stdout の解析失敗時の処置、認証失敗時の再認証依頼先をそれぞれのキー（`timeout_action`, `malformed_output_action`, `authentication_failure_action`）に具体的に記載する。

## 7. 禁止事項

- 引数やオプションの表を仕様内に網羅的に二重記述すること。正本（コマンドリファレンス、exec 設定、公式仕様等）を参照すること。
- 実行可能ファイル、サブコマンド、引数を 1 本のシェル文字列として記載すること。`command.shell: true`、パイプ、リダイレクト、コマンド置換を使用すること。
- トークン、パスワード、秘密鍵、秘密値を含む URL、個人環境に固有の認証パスを本文や例に記載すること。
- 標準出力と標準エラーを混同したり、出力形式を「CLI の既定」とだけ記載したり、終了コードの意味を定義せずに文言解析のみで成否を判定すること。
- 副作用があるコマンドを冪等性条件なしで自動再試行対象にすること。認証失敗、認可失敗、入力不正を一時失敗（`transient_failure`）として扱うこと。
- DB 物理構造、内部クラス名、プロセス起動ライブラリの API 呼び出し、スクリプト全文などの内部実装詳細を含めること。
