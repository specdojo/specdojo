# D2 を用いた概念データフロー図 作成ルール

Conceptual Data Flow Diagram Notation Rulebook for D2

D2 で CDFD のプロセス・イベント・データストア・外部主体・受け渡しを表す記法ルールです。全体概要・プロセスグループ別・ユースケース別 CDFD の主 rulebook の `includes` から適用します。プロダクト固有の割り当ては全体概要の「凡例（本プロダクト共通）」、共通凡例がなければ本書の既定凡例を使います。

## 1. 全体方針

- 方向は `direction: down`、配置エンジンは文書サイトと同じ ELK を基本とし、横長に適する場合は `direction: right` を選べます。矢印は情報・物・実行要求の受け渡しを示し、包含元が明示した場合だけ業務順序も示します。プロセスの並び順と戻りの矢印は「エッジ」に従います。以下、プロセスグループ別とユースケース別を「詳細 CDFD」と呼びます。
- 一画面で関係を追いにくい場合は「凡例と可読性」に従って分割します。分割単位とノード数の目安は包含元が定めます。
- 一つの記号へ一つの意味を割り当て、ノード形状だけでプロセス、イベント、データストア、外部主体を区別できるようにします。
- 情報の流れと物の流れは線種（線の太さ）で区別し、すべてのエッジへ内容を表す名詞形のラベルを付けます。
- 業務上の合意に必要な概念を形状で区別し、色は「見栄えを整える最小限スタイル」に従う補助表現とします。物理名や詳細な操作は使いません。
- **共通の運用**: 役割は適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。コードブロックは `npm run lint:d2` が終了コード 0 になることで確かめ、業務の受入確認に含めません。

| 概念                 | D2 表現                                                                                                             | 表示例                                                                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| プロセス             | 角丸四角形（`shape: rectangle`、`style.border-radius: 8`）                                                          | `sales_record: "P-01-01 販売記録\n（担当: 店員）" { class: process }` |
| プロセスグループ     | 角丸四角形（`shape: rectangle`、`style.border-radius: 8`）（代表ノード）                                            | `sales: "販売\nP-01〜P-02" { class: process }`                        |
| サブグラフ           | コンテナ `{ ... }`（関連プロセスを囲む視覚上のまとまり。グループの表現には使わない）                                | `sales_area: "販売領域" { ... }`                                      |
| データストア         | 円柱（`shape: cylinder`）                                                                                           | `sales_ledger: "販売記録簿" { class: store }`                         |
| 物理保管             | 大角丸四角形（`shape: rectangle`、`style.border-radius: 20`）（現物の保管先。トランザクションデータと同じ色を使う） | `display_shelf: "売場棚" { class: physical_store }`                   |
| 外部主体             | 四角形（`shape: rectangle`）                                                                                        | `customer: "顧客" { class: actor }`                                   |
| イベント             | 六角形（`shape: hexagon`）                                                                                          | `purchase_request: "顧客が商品の購入を要求した" { class: event }`     |
| 情報・実行要求の流れ | ラベル付き有向エッジ `->`（戻りの矢印は `<-`）                                                                      | `sales_record -> sales_ledger: "販売情報"`                            |
| 物の流れ             | ラベル付き太線エッジ `->`（太線の class を適用）                                                                    | `display_shelf -> sales_record: "商品" { class: material_flow }`      |

## 2. 位置づけと用語定義

コード内で要素を参照するノード ID と、図上に見せる表示ラベルを区別します。表示ラベルは業務用語に必要な領域 ID を併記し、エッジラベルは渡す情報・物・起動条件の名称とします。

- ノード ID には日本語文字や記号を避け、`sales_record` や `sales_ledger` のような英数字・スネークケースを基本とします。
- 表示ラベルは `"..."` で指定し、改行が必要な場合は `\n` を使います。
- 担当を表示する場合は、プロセスの表示ラベル末尾へ `\n（担当: ロール）` を付けます。
- イベントは「〜された」「〜が到来した」「〜を要求した」など、発生を判断できる短い文にします。

## 3. ファイル命名・ID規則

- 本 rulebook は独立した成果物を生成せず、`cdfd-*.md` 内の D2 コードブロック（` ```d2 `）へ適用します。
- D2 コードブロックに独立した文書 ID は付けず、包含する CDFD の ID とプロセス ID で追跡します。
- ノード ID は一つのコードブロック内で一意にし、同じ対象には表と図で同じ領域 ID または名称を使用します。
- 複数図に分ける場合は、包含する CDFD 本文の見出しで図の観点を識別します。

## 4. 推奨 Frontmatter 項目

成果物の `rulebook` は図種別を定める主 CDFD rulebook とし、本記法を重複記載しません。記法単独では適用しません。プロセスグループ別なら `rulebook: specdojo:cdfd-rulebook` とします。

## 5. 本文構成（標準テンプレ）

コードは次表の順を基本とします。全体概要はグループ代表・データストア・情報の流れ、プロセスグループ別は個別プロセス・イベント・データストア・情報／物の流れを必須とします。外部主体・物理保管は存在する場合だけ置き、全図に直後の注記を付けます。ユースケース別のイベントも必須です。ユースケース別の開始・終了は通常の流れ全体で必須とし、分割図や任意の戻りの図への再掲は不要です。

| 順序 | 区分           | 必須     | 内容                                                                                                                                           |
| ---- | -------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 方向宣言       | ○        | `direction: down`（基本）または `direction: right`                                                                                             |
| 2    | `classes` 定義 | ○        | 概念の大分類ごとに形状・スタイルを定義した `classes: { ... }` ブロック                                                                         |
| 3    | プロセスノード | ○        | 全体概要はグループ代表ノード、ユースケース別は包含元の単位、プロセスグループ別は個々のプロセス                                                 |
| 4    | イベント       | 条件付き | プロセスグループ別では開始契機、ユースケース別では通常の流れ全体の開始・終了の出来事（引き渡し条件のイベントは置かない）。全体概要では描かない |
| 5    | 外部主体       | 任意     | 対象範囲外の入力元・出力先                                                                                                                     |
| 6    | データストア   | 条件付き | 読み書きする主要な情報の保管先。ユースケース別では対象ケースで参照・更新するものだけ置く                                                       |
| 7    | 物理保管       | 条件付き | 現物の保管先が情報・物の受け渡しまたは境界の理解に必要な場合だけ置く                                                                           |
| 8    | 情報・物の流れ | ○        | ラベル付きエッジ（物の流れには `material_flow` class を指定）                                                                                  |
| 9    | 図直後の注記   | ○        | 共通凡例がある場合はその参照、ない場合は本 rulebook の既定凡例に従う旨、使用線種、省略事項、共有ノード                                         |

## 6. 記述ガイド

### 6.1. ノードとコンテナ

- プロセスは角丸四角形、外部主体は四角形、イベントは六角形、データストアは円柱で表します。現物の保管先を図へ置く場合は物理保管として大角丸四角形（`style.border-radius: 20`）を使い、プロセス、外部主体、データストアの代替にはしません。
- プロセス名は「販売記録」「計画展開」のように、何を扱う処理か分かる短い名詞句にします。
- 全体概要では一プロセスグループを一つの代表ノードとして表し、表示ラベルにグループ名と含む領域 ID の範囲を記載します。グループ内の領域や処理を別ノードとして追加しません。
- プロセスグループ別 CDFD ではグループ内の主要プロセスを個別ノードにし、全体概要の代表ノードをプロセスとして重複配置しません。
- ユースケース別 CDFD では包含元が定める参加単位を正常系の通過順に配置し、その内部プロセスは描きません。開始・終了のイベントは一ノード一出来事の短い文とし、長ければ原文を保って改行します。引き渡し条件のイベントは置かず、受け渡す情報・物を線のラベルで表します。
- コンテナ（`container: { ... }`）はプロセスグループ別 CDFD で関連プロセスを視覚的にまとめる場合にだけ使用できます。プロセスグループの表現や代表ノードの代替には使いません。

```d2
direction: down
classes: {
  process: {
    shape: rectangle
    style.border-radius: 8
  }
}
sales_area: "販売領域" {
  sales_record: "P-01-01 販売記録\n（担当: 店員）" { class: process }
}
```

### 6.2. 絵文字アイコン（任意）

表示差・幅崩れを考慮し、絵文字は任意とします。表示ラベルの先頭に一つまで付け、名称のテキストを併記します。ノード ID には付けません。

```d2
direction: down
classes: {
  process: {
    shape: rectangle
    style.border-radius: 8
  }
}
sales_record: "📋 P-01-01 販売記録\n（担当: 店員）" { class: process }
```

禁止例（絵文字がノード ID に付いている、または表示ラベルに無い）:

```text
direction: down
📋sales_record: "販売記録"
```

### 6.3. エッジ

- 情報は通常エッジ `->`、物は太線のエッジ（`material_flow` class を適用）を使用します。イベントからプロセスへのエッジも `purchase_request -> sales_record: "販売開始条件"` のようにラベルを付けます。
- エッジラベルは「販売情報」「在庫数量」「実行結果」のような名詞形にし、「処理する」など動作だけの語を使用しません。
- 一つのエッジに異なる責務の情報を詰め込まず、受け手が別ならエッジを分けます。
- プロセスは上から Orchestrator・Plan・Do・Check・Action の順（Onboarding がある図では Onboarding を Orchestrator の上）に並べます。並び順に逆らう戻りの矢印（Orchestrator への応答、Action から Plan への再計画要求、上流のデータストアへの更新など）は `b -> a` ではなく `a <- b` と書き、ELK に並びを決めさせないようにします（矢印の向きは `b` から `a` のまま、配置上で `a` を上に保ちます）。
- プロセスどうしの受け渡しがなく `a <- b` では並び順を決められない図（プロセスが同一行に横に並んでしまう場合など）では、並び順を固定するために透明度 0 の線（`style.opacity: 0`、ラベルなし。例: `onboarding -> orchestrator -> plan -> do_exec -> check -> action: {style.opacity: 0}`）を使って構いません。その線は業務上の受け渡しではないため、直前に受け渡しではないことを示すコメント（例: `# 配置制御用（受け渡しではない）`）を必ず記述します。

```d2
direction: down

classes: {
  process: {
    shape: rectangle
    style.border-radius: 8
  }
  event: {
    shape: hexagon
  }
  store: {
    shape: cylinder
  }
  actor: {
    shape: rectangle
  }
}

customer: "顧客" {
  class: actor
}
purchase_request: "顧客が商品の購入を要求した" {
  class: event
}
sales_record: "P-01-01 販売記録" {
  class: process
}
sales_ledger: "販売記録簿" {
  class: store
}

customer -> purchase_request: "購入依頼"
purchase_request -> sales_record: "販売開始条件"
sales_record -> sales_ledger: "販売情報"
```

### 6.4. 凡例と可読性

- 図直後に、共通凡例の参照先、使用線種、省略した入出力と理由、別図と共有するノードを示します。共通凡例がなければ「ノード形状・線種・色・絵文字は `specdojo:cdfd-d2-rulebook` の既定凡例に従う」と書きます。
- 共通凡例の割り当てを再掲せず、未定義の割り当ても使いません。共通凡例がなければ本書の対応表と「見栄えを整える最小限スタイル」を使い、図ごとの独自割り当ては追加しません。
- 物の流れを使わない場合は「`->` は情報・実行要求の流れ。本図は物の流れを対象外とする」と記述します。
- 図を分ける観点とノード数の目安は包含元の rulebook に従います。分けた図の間で同じプロセス ID・名称を維持します。ユースケース別 CDFD では、共有する参加単位・データストアの名称と領域 ID で接続を追跡し、引き渡し ID は付けません。
- ノードの表示ラベルは1行あたり全角20字（半角40字）程度を目安にし、超える場合は `\n` で改行して2行程度に収めます。エッジラベルは改行に頼らず短い名詞句に収めます。

### 6.5. 見栄えを整える最小限スタイル（任意）

- 形状で意味を読めれば色は不要です。色を付ける場合は `classes` と `class` に限り、ノード単位の `style` 指定はしません。
- プロセス／イベント／データストア／外部主体ごとに色相を統一し、大分類間で混同しません。
- 大分類内は、変更頻度・更新契機・参照側／更新側などの業務上の区別を説明できる場合だけ、同系統色の濃淡・彩度で分けられます。サブ分類名と色は共通凡例に定義します。

```d2
direction: down

classes: {
  process: {
    shape: rectangle
    style: {
      border-radius: 8
      fill: "#e3f2fd"
      stroke: "#1e88e5"
      font-color: "#000000"
    }
  }
  event: {
    shape: hexagon
    style: {
      fill: "#fff3e0"
      stroke: "#fb8c00"
      font-color: "#000000"
    }
  }
  store: {
    shape: cylinder
    style: {
      fill: "#c8e6c9"
      stroke: "#2e7d32"
      font-color: "#000000"
    }
  }
  actor: {
    shape: rectangle
    style: {
      fill: "#f5f7fa"
      stroke: "#607d8b"
      font-color: "#000000"
    }
  }
}

customer: "顧客" {
  class: actor
}
purchase_request: "顧客が商品の購入を要求した" {
  class: event
}
sales_record: "P-01-01 販売記録\n（担当: 店員）" {
  class: process
}
sales_ledger: "販売記録簿" {
  class: store
}

customer -> purchase_request: "購入依頼"
purchase_request -> sales_record: "販売開始条件"
sales_record -> sales_ledger: "販売情報"
```

大分類「データストア」の中でマスタ・構成データとトランザクションデータを同系統色（緑系の濃淡）で塗り分ける例:

```d2
direction: down

classes: {
  store_master: {
    shape: cylinder
    style: {
      fill: "#e8f5e9"
      stroke: "#43a047"
      font-color: "#000000"
    }
  }
  store_transaction: {
    shape: cylinder
    style: {
      fill: "#c8e6c9"
      stroke: "#2e7d32"
      font-color: "#000000"
    }
  }
  physical_store: {
    shape: rectangle
    style: {
      border-radius: 20
      fill: "#c8e6c9"
      stroke: "#2e7d32"
      font-color: "#000000"
    }
  }
}

item_master: "商品マスタ" {
  class: store_master
}
sales_ledger: "販売記録簿" {
  class: store_transaction
}
```

この例の凡例では形状に加え、薄い緑（`#e8f5e9` / `#43a047`）をマスタ・構成データ、中間の緑（`#c8e6c9` / `#2e7d32`）をトランザクションデータ、同色の大角丸四角形を物理保管と定義します。

## 7. 禁止事項

- ラベルのないエッジ（並び順固定用の透明度 0 の線を除く）、同じ線種へ情報と物の両方の意味を持たせたエッジを記載しません。
- プロセスとデータストア、イベントと外部主体など、異なる概念へ同じノード形状を使用しません。
- 全体概要にプロセスグループ内の領域や処理を複数ノードで展開したり、プロセスグループをコンテナで表したり、プロセスグループ別 CDFD に他グループの内部処理を作り込んだりしません。
- 物理テーブル、物理カラム、実装クラス、関数、詳細 API、コマンドオプションをノードやエッジへ記載しません。
- 独自形状、根拠のないノード単位の色付け、大分類間での色相の混同、区別基準のないサブ分類を追加しません。スタイルは「見栄えを整える最小限スタイル」に従います。
- 起点も到達先も説明できないノード、自己ループだけで完結するプロセス、読み手が解釈できない略語を残しません。
- 外部ファイルのインポート（import）、および layers・scenarios・steps による複数ページ出力を使いません（1 ブロック 1 SVG 出力の描画仕様に従います）。
