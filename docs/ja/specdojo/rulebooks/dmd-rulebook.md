# データ移行設計 作成ルール

Data Migration Design (DMD) Documentation Rules

対象別データ移行設計（`dmd-<term>`）で、旧→新のデータ移行を再現可能に定義し、正確性・完全性を確かめる基準を定めます。

## 1. 全体方針

- **目的と単位**: `dmd-<term>` は、データ領域（例: 受注・請求・在庫）またはデータセットごとの個別 SSOT とします。
- **上位との分担**: 抽出方式の扱い、`run_id` 規約、冪等性、検証の種類は `dmd-index` を正とし、`dmd-<term>` には対象固有の値だけを書きます。
- **再現性**: 「何を・どこから・どこへ・どの条件で移すか」と変換・除外ルールを、再実行しても同じ結果になる形で書き、検証は合格基準（差分0 / 許容差ε）で合否を判定できるようにします。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直しません。文書の整形・lint はリポジトリの検証で扱い、移行の検証に含めません。

## 2. 位置づけ

- `mip-index`：移行の合意・判断のSSOT（成功条件・カットオーバー骨格を含む）
- `dmd-index`：データ移行の入口（共通方針、`run_id` 規約、検証の共通方針）
- **`dmd-<term>`：対象別データ移行の詳細設計（マッピング/変換/検証）**
- `mtp-index` / `mtp-<term>`：リハーサル計画・検証設計（観点/手順/証跡）
- `cop-index` / `cop-<term>`：当日実行の詳細手順（Runbook）
- `otp-index` / `otp-<term>`：運用切替の詳細（監視設定/運用手順/窓口）

## 3. ファイル命名・ID規則

- **ファイル名**: `dmd-<term>.md` とし、`<term>` は用語集(GL)の論理名キー（英小文字 kebab-case。例: `order-data`）を用います。
- **文書 ID**: プロダクト仕様の成果物は `dmd-<term>`、プロジェクト固有の成果物は `<project-id>:dmd-<term>` とし、成果物カタログの宣言と一致させます。
- **文書タイトル（H1）**: `# データ移行設計: <対象名>` とし、対象名は日本語でよいものとします。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- `specdojo.type` は `data`、`specdojo.rulebook` は `specdojo:dmd-rulebook` とします。
- `specdojo.based_on` には移行判断に直接利用した作成済みの成果物（例: `mip-index` / `br-*` / `nfr-*` / `issue-*`）の ID だけを列挙します。

## 5. 本文要件

本文は次の見出しを順序固定で置き、見出しは `## <番号>. <見出し>` として表の文言のまま書きます（`<term>` は対象の term に置き換えます）。

| 番号 | 見出し                                            | 必須 |
| ---- | ------------------------------------------------- | ---- |
| 1    | 概要（`<term>`）                                  | ○    |
| 2    | 対象データ詳細（テーブル/期間/抽出条件/概算件数） | ○    |
| 3    | データマッピング                                  | ○    |
| 4    | 変換ルール                                        | ○    |
| 5    | 除外ルール                                        | ○    |
| 6    | 移行手順（手動/バッチ/ツール）                    | ○    |
| 7    | 性能/所要時間見積                                 | ○    |
| 8    | ログ/再実行性                                     | ○    |
| 9    | 検証方法（件数照合/サンプル照合/重要値）          | ○    |
| 10   | 関連ドキュメント（必須）                          | ○    |

## 6. 記述ガイド

完成例の全体像は Frontmatter の `sample` で宣言された sample を参照してください。

### 6.1. 概要（`<term>`）

- 対象データが何であり、どの移行範囲を扱うかを 1〜3 行で示す
- 依存する前提（移行方式、移行期間、上位の成功条件）を簡潔に述べる

### 6.2. 対象データ詳細（テーブル/期間/抽出条件/概算件数）

- 対象テーブル/コレクション、移行期間/抽出条件、抽出方式と増分基準を明記する
- 概算件数は見積り根拠が分かる粒度で示す

推奨フォーマット（表）:

| 対象 | 期間/抽出条件 | 方式（フル/増分） | 増分基準（カラム/キー/基準時刻） | 概算件数 | 備考 |
| ---- | ------------- | ----------------- | -------------------------------- | -------- | ---- |

### 6.3. データマッピング

- 旧→新の対応を明確に示し、1対多/多対1の関係は変換ルールと合わせて記述する
- 主キー/参照整合（FK相当）の扱い（維持/再採番/変換テーブル、投入順序の前提）を明記する

推奨フォーマット（表）:

| 旧データ | 新データ | 変換/補足 |
| -------- | -------- | --------- |

### 6.4. 変換ルール

- 変換規則（正規化、コード変換、丸め、文字種変換等）を列挙する
- 変換の根拠（参照表/仕様ID）がある場合はリンクする

### 6.5. 除外ルール

- 移行対象外となる条件と除外理由（業務上の不要、期限切れ、品質不良等）を列挙する
- 除外した場合の影響（参照のみ/業務に影響なし/代替手段あり）を必要に応じて追記する

### 6.6. 移行手順（手動/バッチ/ツール）

- 実行順序と依存関係、入出力（形式/置き場）、実行単位（ジョブ名/コマンド/ツール名）が分かるように記述する（詳細はリンクでよい）

推奨フォーマット（表）:

| 手順 | 内容 | 入力 | 出力 | 実行単位（ジョブ/コマンド） | 備考 |
| ---- | ---- | ---- | ---- | --------------------------- | ---- |

### 6.7. 性能/所要時間見積

- 所要時間見積と前提条件（件数、並列度、スループット）、目標時間がある場合はその値を示す
- ボトルネックが想定される場合は、暫定対策（並列化/分割/先行移行）を方針として記載してよい

### 6.8. ログ/再実行性

- 実行ログの保存先と識別キー（例: `run_id`）、再実行条件（再投入可能範囲）を示す
- 冪等性方式（例: `upsert` / `run_id隔離` / `再投入前truncate` / `差分適用`）を明記する

推奨フォーマット（表）:

| 項目         | 方針                                       |
| ------------ | ------------------------------------------ |
| 識別キー     | run_id                                     |
| ログ保存先   | （例：S3/ログ基盤/DB）                     |
| 冪等性方式   | upsert / run_id隔離 / …                    |
| 再実行可否   | （例：同一run_id不可、別run_idで再実行可） |
| データ無効化 | （例：run_id単位で隔離/フラグ）            |

### 6.9. 検証方法（件数照合/サンプル照合/重要値）

- 件数照合、サンプル照合、重要値照合の方法と証跡（レポート/ログ）を示す
- 合格基準は「差分0」か「許容差（ε）」かを、理由 1 行とともに明示する

推奨フォーマット（表）:

| 検証種別 | 検証項目 | 方法 | 合格基準（差分0 / 許容差ε） | 証跡 |
| -------- | -------- | ---- | --------------------------- | ---- |

### 6.10. 関連ドキュメント（必須）

- `dmd-index`（入口SSOT）への導線を必ず記載し、分冊が無い場合でも `（本書のみ）` を明記する

## 7. 禁止事項

| 禁止事項                                                           | 理由                                                             |
| ------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 対象データの範囲（期間/抽出条件/件数/方式）を曖昧に書く            | 再現性と品質担保ができないため                                   |
| 変換ルール・除外ルールを未記載にする                               | 移行結果が再現できず、意図しない欠落が発生するため               |
| 移行手順の手段（手動/バッチ/ツール）や入出力を曖昧に書く           | 実行計画が確定できないため                                       |
| 検証方法を「確認する」など合格基準のない書き方にする               | 合否判定できないため                                             |
| 移行ツールの実装コードや長大なSQLを本文に貼り付ける                | 差分管理が破綻し、更新不整合を起こすため（参照リンクに寄せる）   |
| `dmd-index` と矛盾する共通方針（run_id/冪等性/検証種別）を記載する | ドキュメント間で判断基準が分裂するため                           |
| 文書の整形・lint の実行を移行の検証方法に含める                    | リポジトリの検証と移行結果の照合が混ざり、合否判定が埋もれるため |
