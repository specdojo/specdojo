# 移行テスト計画 作成ルール

Migration Test Plan (MTP) Documentation Rules

移行テスト計画（`mtp-index` / `mtp-<term>`）は、移行手順と結果の妥当性をリハーサルで事前に確かめ、GO/NO-GO を判断する根拠を集めるための文書です。本書はその作成基準を定めます。

## 1. 全体方針

- **記載レベル**: リハーサルを再現でき、結果から合否と GO・条件付き GO・NO-GO を判断できる粒度で、回数・日程・観点・合否基準・差異の扱い・報告項目を書く。
- **全体と分冊**: 原則 `mtp-index` に全体の計画をまとめる。ウェーブ分割・責任分界・対象の独立性が高い場合に限り `mtp-<term>` を追加し、共通方針・全体日程・合否基準・GO/NO-GO の判断プロセスは `mtp-index` を正とする。
- **結果と管理記録の分離**: リハーサルの結果は「結果報告フォーマット」で定めた報告先に記録し、本書には書き足さない。管理記録へ転記する条件は「差異発生時の扱い（許容/修正/再実行）」に定める。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。本書固有の追従対象は「位置づけ」に定める。

## 2. 位置づけ

| 成果物                    | `mtp-index` との関係                                     | 変わったときに MTP で見直す箇所                   |
| ------------------------- | -------------------------------------------------------- | ------------------------------------------------- |
| `mip-index`               | 成功条件・停止許容時間・判定点を受ける                   | 合否基準、GO/NO-GO判断プロセス                    |
| `dmd-index`, `dmd-<term>` | マッピング・変換・検証（件数/重要値/許容差）を受ける     | 検証観点、合否基準の許容差、テスト環境/データ準備 |
| `cop-index`, `cop-<term>` | 当日手順・判定点を、リハーサルで確かめる対象として受ける | リハーサル回数とスケジュール、検証観点の判定点    |
| `otp-index`, `otp-<term>` | 運用切替後の監視・窓口の確認をリハーサルの観点へ渡す     | 検証観点（業務シナリオ）                          |

- 上表の成果物が変わったときは、QE が同じ行の見直す箇所を確かめ、影響を受ける章を直す。見直しの作業は PM が登録簿の個票に起票して追う。
- 本書の合否基準・判定点を変えたときは、`cop-*` の判定条件と `mip-index` の成功条件に矛盾がないかを同じ個票で確かめる。

## 3. ファイル命名・ID規則

- `id` のローカル部分は `mtp-index` または `mtp-<term>`（kebab-case。例: `mtp-cutover-rehearsal`）とし、成果物カタログの宣言と一致させる。
- ファイル名は `mtp-index.md` / `mtp-<term>.md` を推奨する。`id` とファイル名は独立であり、プロジェクト内で一意であればファイル名の変更は許容する。
- `<term>` は用語集（GL）の論理名キー（英小文字 kebab-case）を用いる。表示名は H1 で日本語を使用してよい。

## 4. 推奨 Frontmatter 項目

共通の必須項目・型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。

- `specdojo.type` は `test`、`specdojo.rulebook` は `specdojo:mtp-rulebook` とし、`title` は置かない。
- `specdojo.based_on` には移行判断に直接使った作成済みの成果物だけを挙げる。成果物カタログに `depends_on` がある場合は、その推移閉包内に限定する。
- 編集後は `npm run lint:fm` で Frontmatter を rulebook の宣言と照合し、`npm run lint:md` で本文の記法を確かめる。どちらも終了コード 0 で合格とし、エラーは示された宣言値・規則に合わせて直す。

## 5. 本文要件

`mtp-index` / `mtp-<term>` は次の9章をこの順序で置き、すべて必須とする。

| 章                                   | 内容・受入条件                                                                                                             |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 概要（`index` / `<term>`）           | 何を移行し、何をリハーサルで事前に確かめるかを1〜3行で示す。`mtp-<term>` は対象に含むもの・含まないものを書く              |
| リハーサル回数とスケジュール         | 列「回数 / 予定日 / 目的 / 完了条件」。`mtp-<term>` は全体日程との関係（ウェーブ順・前提）を書く                           |
| テスト環境/データ準備                | 環境と前提設定、データセット ID、初期化と後始末、データ準備の担当 Role code と手順の参照先                                 |
| 検証観点（件数/差分/業務シナリオ）   | 列「観点 / 方法 / 期待値」。件数照合・差分検知・業務シナリオを含め、許容差は `dmd-*` の値と一致させる                      |
| 合否基準                             | 列「項目 / 基準 / 判定者」。停止許容時間・差分許容・重大障害を含め、判定者は Role code で書く                              |
| 差異発生時の扱い（許容/修正/再実行） | 許容差内・許容差超・重大障害ごとの扱い、再実行の上限（回数と期限）と判定者、管理記録へ転記する条件                         |
| 結果報告フォーマット                 | 列「項目 / 記載内容」。日時・結果・差異・所要時間・証跡・GO/NO-GO 案と未決事項を含め、報告先を書く                         |
| GO/NO-GO判断プロセス                 | 判定者、参照する証跡、GO・条件付き GO・NO-GO の判断条件。`mtp-<term>` は固有の判定点がある場合のみ書き、なければ本体を参照 |
| 関連ドキュメント                     | `mtp-index` は各 `mtp-<term>` へ、`mtp-<term>` は `mtp-index` への導線。分冊がなければ `（本書のみ）` と書く               |

## 6. 記述ガイド

完成例は Frontmatter の `sample` で宣言された sample を参照する。必須の値が未確定のときは空欄や「可能なら」で済ませず、`_UNDECIDED_:` で論点と決める時点を書く。

### 6.1. 合否基準

- **判断基準**: 各項目が測定できる基準値を持ち、判定者が適用先メンバー定義の Role code で書かれていること。許容差は「検証観点」と同じ値であること。
- **良い例**: 「件数差異 ／ 0件 ／ QE」「所要時間 ／ `mip-index` の停止許容時間（60分）以内 ／ OPS」「重大障害 ／ 0件 ／ PO」。
- **悪い例**: 「データが概ね一致 ／ 業務責任者」（基準値がなく、判定者が Role code でない）。

### 6.2. 差異発生時の扱い（許容/修正/再実行）

- **判断基準**: 区分ごとに扱いと判定者があり、再実行の上限が回数と期限で書かれていること。許容差超の差異と原因が未解決の差異は課題管理簿（`pm-issue-log`）へ、再実行と NO-GO 案の判断は決定記録（`pm-decision-log`）へ、判定者がリハーサルの結果報告までに転記すること。
- **良い例**: 「許容差超: 原因を直して最大1回、本番の3日前までに再実行する。QE が判断し、差異と原因を `pm-issue-log` へ、再実行の判断を `pm-decision-log` へ転記する」。
- **悪い例**: 「差異があれば必要に応じて再実行する」（上限・判定者・転記先がない）。

### 6.3. 結果報告フォーマットと GO/NO-GO判断プロセス

- **判断基準**: 報告項目が GO/NO-GO の判断で参照する証跡と対応し、GO・条件付き GO・NO-GO を選ぶ条件と判定者が読み取れること。未決事項は論点と移行判断への影響を書くこと。
- **良い例**: 「QE が結果報告・差異一覧・所要時間を集約し、PO が判断する。全基準合格なら GO、軽微な差異が残り回避策があれば条件付き GO、重大障害または再実行の上限超過なら NO-GO（延期）」。
- **悪い例**: 「結果を見て関係者で判断する」（証跡・条件・判定者がない）。

### 6.4. 分冊（`mtp-<term>`）

- **判断基準**: 分冊は対象固有の観点・判定点・差異の扱いだけを書き、共通の合否基準と判断プロセスは `mtp-index` を参照すること。
- **良い例**: 「共通基準は `mtp-index` に従う。本書では接続切替後のスモーク全項目成功を判定点に加える」。
- **悪い例**: `mtp-index` と異なる許容差を分冊で言い直す。

## 7. 禁止事項

| 禁止事項                                                      | 理由                                           |
| ------------------------------------------------------------- | ---------------------------------------------- |
| リハーサル回数/日程を曖昧に書く                               | 実行計画が不明確になるため                     |
| 合否基準を基準値なしで書く、判定者を Role code 以外で書く     | GO/NO-GO判断と判定者の特定ができないため       |
| 差異発生時の扱い・再実行の上限を未定義にする                  | 再実行判断がぶれるため                         |
| リハーサルの結果を本書に書き足す                              | 計画と結果の記録が混ざり、追跡が困難になるため |
| `mtp-<term>` に共通方針を重複記載し、`mtp-index` と矛盾させる | SSOTが崩れ、判断根拠が分散するため             |
