# 移行テスト計画 作成ルール

Migration Test Plan (MTP) Documentation Rules

移行テスト計画（リハーサル計画）の記述基準を定めます。移行手順と結果の妥当性を事前に検証し、当日の失敗確率を下げるための内容を定義します。

## 1. 全体方針

- **目的と適用範囲**: `mtp-index` / `mtp-<term>` に、再現可能なリハーサル計画と評価基準を定義し、GO/NO-GO判断の根拠を提供する。
- **全体と分冊**: 原則 `mtp-index` に全体の計画をまとめる。ウェーブ分割・責任分界・対象の独立性が高い場合に限り `mtp-<term>` を追加し、共通方針・全体日程・GO/NO-GOの基準点は `mtp-index` を正とする。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱う。

## 2. 位置づけ

- `mip-index`：移行の合意・判断のSSOT（成功条件・カットオーバー骨格を含む）
- `dmd-index` / `dmd-<term>`：データ移行の詳細設計（マッピング/変換/検証）
- **`mtp-index` / `mtp-<term>`：リハーサル計画・検証設計（観点/手順/証跡）**
- `cop-index` / `cop-<term>`：当日実行の詳細手順（Runbook）
- `otp-index` / `otp-<term>`：運用切替の詳細（監視設定/運用手順/窓口）

## 3. ファイル命名・ID規則

- `id` のローカル部分は `mtp-index` または `mtp-<term>`（kebab-case。例: `mtp-cutover-rehearsal`）。
- ファイル名は `mtp-010-移行テスト計画.md` / `mtp-020-移行テスト計画-<term>.md` 等、プロジェクト内で一意になるように命名する。
- `<term>` は用語集(GL)の論理名キー（英小文字kebab-case）を用いる。表示名は H1 / ファイル名で日本語を使用してよい。

## 4. 推奨 Frontmatter 項目

### 4.1. 設定内容

共通の必須項目・型制約はドキュメントメタ情報標準と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とし、SpecDojo の項目は `specdojo:` 配下に置く。文書名は Frontmatter の `title` ではなく本文先頭の H1 に書く。

| 項目       | MTP 固有の設定               | 必須 |
| ---------- | ---------------------------- | ---- |
| `type`     | `test` 固定                  | ○    |
| `rulebook` | `specdojo:mtp-rulebook` 固定 | ○    |

### 4.2. 推奨ルール

- `based_on` には移行判断に直接利用した作成済みの成果物のみ列挙する。成果物カタログに `depends_on` がある場合は、その推移閉包内に限定する。

## 5. 本文構成（標準テンプレ）

`mtp-index` / `mtp-<term>` は以下の見出し構成を **順序固定** で配置します。

| 番号 | 見出し                               | 必須 |
| ---- | ------------------------------------ | ---- |
| 1    | 概要（`index` / `<term>`）           | ○    |
| 2    | リハーサル回数とスケジュール         | ○    |
| 3    | テスト環境/データ準備                | ○    |
| 4    | 検証観点（件数/差分/業務シナリオ）   | ○    |
| 5    | 合否基準                             | ○    |
| 6    | 差異発生時の扱い（許容/修正/再実行） | ○    |
| 7    | 結果報告フォーマット                 | ○    |
| 8    | GO/NO-GO判断プロセス                 | ○    |
| 9    | 関連ドキュメント                     | ○    |

## 6. 記述ガイド

### 6.1. 概要（`index` / `<term>`）

- 何のリハーサルを、どの目的で行うかを 1〜3 行で示す
- `mip-index` と整合すること
- `mtp-<term>` の場合は「term固有の目的・範囲（何を含み、何を含まないか）」を明記する

### 6.2. リハーサル回数とスケジュール

- 実施回数、実施日程、実施目的を明記する
- `mtp-<term>` の場合は、term固有の日程と全体日程の関係（ウェーブ順/前提）を明記する

| 回数 | 予定日 | 目的 | 完了条件 |
| ---- | ------ | ---- | -------- |

### 6.3. テスト環境/データ準備

- 環境（staging/検証環境等）と前提設定を明記する
- データ準備（データセットID、初期化/後始末）を明記する
- 可能なら、データ準備の責任者と手順参照先（runbook等）を示す

### 6.4. 検証観点（件数/差分/業務シナリオ）

- 件数照合、差分検知、業務シナリオ検証の観点を整理する
- `dmd-*` で定義した検証（件数/重要値/許容差）と整合すること

| 観点 | 方法 | 期待値 |
| ---- | ---- | ------ |

### 6.5. 合否基準

- 合格基準、許容誤差、判断者を明記する
- 重要な合否基準（停止許容/差分許容/重大障害）を最低限含める

| 項目 | 基準 | 判定者 |
| ---- | ---- | ------ |

### 6.6. 差異発生時の扱い（許容/修正/再実行）

- 許容できる差異、修正が必要な差異、再実行条件を明記する
- 再実行の上限（回数/期限）と判断者を可能な限り明記する

### 6.7. 結果報告フォーマット

- 報告に必要な項目（日時/結果/差異/所要時間/証跡/GO・NO-GO案と未決事項）を明記する。未決事項は論点と移行判断への影響を示す
- 報告先（チケット/共有フォルダ/リポジトリ）を可能な限り明記する

| 項目 | 記載内容 |
| ---- | -------- |

### 6.8. GO/NO-GO判断プロセス

- 判断プロセス、判断主体、必要な証跡を明記する
- `mtp-<term>` は term固有の判定点がある場合のみ追記する

### 6.9. 関連ドキュメント

- `mtp-index` の場合：各 `mtp-<term>`（分冊）への導線を必ず記載する
- `mtp-<term>` の場合：`mtp-index` への導線（本体SSOT）を必ず記載する
- 分冊が無い場合でも `（なし）` または `（本書のみ）` を明記する

## 7. 禁止事項

| 禁止事項                                                      | 理由                               |
| ------------------------------------------------------------- | ---------------------------------- |
| リハーサル回数/日程を曖昧に書く                               | 実行計画が不明確になるため         |
| 合否基準を曖昧にする                                          | GO/NO-GO判断ができないため         |
| 差異発生時の扱いを未定義にする                                | 再実行判断がぶれるため             |
| 結果報告フォーマットを省略する                                | 合意形成と追跡が困難になるため     |
| `mtp-<term>` に共通方針を重複記載し、`mtp-index` と矛盾させる | SSOTが崩れ、判断根拠が分散するため |
| 「関連ドキュメント」セクションを省略する                      | 導線が失われ、参照先が分散するため |

## 8. サンプル（最小・整合版）

以下は架空の対象・日付による最小例である。

### 8.1. `mtp-index`（全体SSOT・入口）

```markdown
---
specdojo:
  id: mtp-index
  type: test
  status: draft
  rulebook: specdojo:mtp-rulebook
  based_on: [mip-index]
---

# 移行テスト計画: 全体

## 1. 概要（index）

受注システムの移行手順と結果を事前検証する。全体の計画を本書、判定点の詳細を `mtp-cutover-rehearsal` に定める。

## 2. リハーサル回数とスケジュール

| 回数 | 予定日     | 目的               | 完了条件                 |
| ---- | ---------- | ------------------ | ------------------------ |
| 1    | 2026-03-01 | 手順の実行確認     | 全工程完了・所要時間計測 |
| 2    | 2026-03-15 | 差異検知と再現確認 | 差異0または許容内        |

## 3. テスト環境/データ準備

staging に受注データセット `DS-ORDER-01` を投入する。実行前に初期化し、終了後は `run_id` 単位でログを保全する。

## 4. 検証観点（件数/差分/業務シナリオ）

| 観点         | 方法               | 期待値                      |
| ------------ | ------------------ | --------------------------- |
| 件数照合     | 旧/新件数比較      | 差分0                       |
| 差分検知     | 重要項目の差分抽出 | `dmd-order-data` の許容差内 |
| 業務シナリオ | 受注→請求を実行    | 成功・重大障害0             |

## 5. 合否基準

| 項目       | 基準                         | 判定者     |
| ---------- | ---------------------------- | ---------- |
| 件数差異   | 0                            | 業務責任者 |
| 重要値差異 | 「検証観点」の許容差内       | 業務責任者 |
| 所要時間   | `mip-index` の停止許容時間内 | 運用責任者 |
| 重大障害   | 0                            | PO         |

## 6. 差異発生時の扱い（許容/修正/再実行）

- 許容差内: 本番影響がないことを確認し、原因とともに記録する。
- 許容差超: 原因修正後に最大1回再実行する。移行責任者が判断する。
- 重大障害: NO-GO候補としてPOへエスカレーションする。

## 7. 結果報告フォーマット

チケットに次の項目を記録する。

| 項目     | 記載内容                         |
| -------- | -------------------------------- |
| 日時     | 実施日・開始終了時刻             |
| 結果     | 合格/不合格                      |
| 差異     | 差分件数・重要値差分・原因/対応  |
| 所要時間 | 全体/主要工程別                  |
| 証跡     | `run_id` とログ・レポート参照先  |
| 判断     | GO/NO-GO案、未決の論点と本番影響 |

## 8. GO/NO-GO判断プロセス

移行責任者が結果報告・差分一覧・重大障害一覧・所要時間を集約し、POがGO / 条件付きGO / NO-GO（延期）を判断する。

## 9. 関連ドキュメント

- `mtp-cutover-rehearsal`: カットオーバーの判定点とロールバック前提。
```

### 8.2. `mtp-<term>`（個別：例）

```markdown
---
specdojo:
  id: mtp-cutover-rehearsal
  type: test
  status: draft
  rulebook: specdojo:mtp-rulebook
  based_on: [mip-index]
---

# 移行テスト計画: カットオーバーリハーサル

## 1. 概要（cutover-rehearsal）

受付停止〜差分抽出〜投入〜接続切替〜利用開始の判定点GO1〜GO5と所要時間を確認する。共通基準は `mtp-index` に従う。

## 2. リハーサル回数とスケジュール

全体日程の第1回で全工程の実行、第2回で差異0または許容内であることを確認する。

## 3. テスト環境/データ準備

`mtp-index` の staging・データセットを使用する。旧系相当データの投入と外部I/Fの sandbox 接続を開始条件とする。

## 4. 検証観点（件数/差分/業務シナリオ）

| 観点     | 方法                                             | 期待値                      |
| -------- | ------------------------------------------------ | --------------------------- |
| 判定点   | `cop-cutover-runbook` のGO1〜GO5の完了条件を確認 | 全て成立                    |
| スモーク | GO4の接続切替後に代表API/画面を確認              | 全項目成功                  |
| 差分検知 | 抽出〜投入ログと差分一覧を照合                   | `dmd-order-data` の許容差内 |

## 5. 合否基準

共通基準は `mtp-index` に従う。運用責任者がGO4後のスモーク全項目成功と主要工程の停止許容時間内での完了を、POが重大障害0を判定する。

## 6. 差異発生時の扱い（許容/修正/再実行）

- GO2/GO3失敗: 原因修正後に最大1回再実行し、不可ならNO-GO案とする。
- GO4失敗: 接続先を旧系へ戻し、NO-GO案とする。
- 軽微な差異: 許容差内なら記録し、次回までに原因を調査する。

## 7. 結果報告フォーマット

`mtp-index` のチケットに共通項目を記録し、GO1〜GO5の完了条件・実績時刻・所要時間、ロールバックの有無・理由・復旧完了時刻を加える。

## 8. GO/NO-GO判断プロセス

個別判定点の結果を記録し、全体判断は `mtp-index` に従う。

## 9. 関連ドキュメント

- `mtp-index`: 全体方針・合否基準・判断プロセス。
- `cop-cutover-runbook`: 判定点と当日手順。
- `dmd-order-data`: 抽出・変換・検証の詳細。
```
