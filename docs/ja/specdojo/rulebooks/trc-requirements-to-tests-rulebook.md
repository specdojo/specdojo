# トレーサビリティ（要求→テスト）作成ルール

Requirements Traceability (Requirements to Tests) Rulebook

テスト成果物の型付き ID 参照とトレース表から要求とテストの対応を派生ビューとして示し、要求漏れ・テスト漏れを見つける形式を定めます。

## 1. 全体方針

- **対象**: 要求とテストの対応の可視化を扱い、要求本文・テスト手順は扱いません。テストの実行結果も扱わず、充足状況はテストの対応と作成状態で判定します。
- **正本と派生**: 文書単位の対応の正本は、`relations.verifies` を定める種別（受入テスト）ではその宣言、定めない種別（総合テスト）では「トレース」の表が指す要求文書、項目単位の対応の正本はテスト成果物の「トレース」の表（`trace_key` と仕様ID）とします。本ビューはこの 2 つと要求文書から「生成の手順」に従って生成します。
- **編集の境界**: 作成者が書くのは「目的と適用範囲」「トレース対象の前提」、充足状況サマリの優先する要求項目と理由、ギャップごとの対応方針、「変更履歴と更新ルール」だけです。それ以外は生成元から導出し、直すときは生成元の成果物を直して再生成します。
- **記載レベル**: 1 行は母集団の 1 つの要求項目と、その対応テスト群とします。
- **任意の管理ビュー**: 必要なプロジェクトだけが生成し、独自のドメインやトラックを持ちません。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。文書の整形・lint はリポジトリの検証で扱い、業務の受入確認に含めません。

## 2. 位置づけ

本ビューは、要求（業務の受入基準 `bac-*` など）と、それを検証するテスト（受入テスト `atc-*`、総合テスト `stc-*` など）の作成後に生成し、テストのレビュー時と要求・テストの変更時に再生成します。要求→仕様の対応は [[specdojo:trc-requirements-to-specs-rulebook|トレーサビリティ（要求→仕様）作成ルール]] が扱います。

## 3. ファイル命名・ID規則

- **ファイル名**: `trc-requirements-to-tests.md` とします。分割する場合は `trc-requirements-to-tests-<term>.md` とします。
- **文書 ID**: 成果物カタログの宣言と一致させます。プロダクト仕様のカタログに置く場合は `trc-requirements-to-tests`、プロジェクト固有の場合は `<project-id>:trc-requirements-to-tests` とします（分割時は末尾に `-<term>`）。
- **要求項目の表記**: 要求文書 ID と文書内の項目 ID の組で `<要求文書ID> <項目ID>`（例: `bac-checkout BAC-01`）と書きます。項目 ID は要求文書が定めたもの（業務の受入基準ならシナリオ ID）をそのまま使い、本ビューで採番しません。

## 4. 推奨 Frontmatter 項目

許可キーと型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- `specdojo.rulebook` は `specdojo:trc-requirements-to-tests-rulebook` とします。
- `specdojo.based_on` は必須とし、母集団とした要求文書と、対応テストとして抽出したテスト文書の ID をすべて記載します。索引（`atc-index` など）は抽出に使った場合だけ加え、個々の文書の代わりにしません。

## 5. 本文要件

| 章                   | 必須     | 内容・受入条件                                                                                                   |
| -------------------- | -------- | ---------------------------------------------------------------------------------------------------------------- |
| 目的と適用範囲       | 必須     | 対象の要求群・テスト群と対象外（理由付き）が分かること                                                           |
| トレース対象の前提   | 必須     | 要求の母集団と件数、テストの抽出条件、生成の手段と生成日、生成元の版（参照したコミットなど）が分かること         |
| トレースマトリクス   | 必須     | 標準6列で母集団の全要求項目を並べ、母集団外を参照するテストを別の表で示すこと                                    |
| 充足状況サマリ       | 必須     | 充足状況ごとの要求項目の件数（重複なし、合計が母集団の件数と一致）、母集団外の参照の件数、優先する要求項目と理由 |
| ギャップと対応方針   | 必須     | ギャップごとに、直す生成元の成果物と解消の判定条件が分かること                                                   |
| 変更履歴と更新ルール | 条件付き | 再生成の契機や前回からの差分を残す必要があるときに置き、生成日と差分の要点を示す                                 |

### 5.1. 生成の手順

生成コマンドがない場合は次の手順で生成し、手作業で生成したことを「トレース対象の前提」に書きます。

_UNDECIDED_: 生成コマンドと recipe・template の要否。決めたら本節の手順を更新する。

1. 母集団を決める: 対象の要求文書を選び、各文書の項目 ID をすべて列挙する。
2. テストを抽出する: 次の 2 つの経路で集め、重複を除く。
   - `relations.verifies` に母集団の要求文書 ID を 1 つ以上持つテスト文書。
   - 索引（`atc-index`・`stc-index` など）に載るテスト文書のうち、「トレース」の表の仕様ID が母集団の要求文書を指すもの。`relations.verifies` を定めていない種別（総合テスト `stc-*` など）は、この経路でだけ集まる。
3. 項目単位で対応づける: 各テストの「トレース」の表から、仕様ID が母集団の要求項目を指す行を拾う。その `trace_key` をケース表の `トレース` 列が参照しているかも確かめる。仕様ID は次の規則で要求項目へ読み替える。
   - 要求文書は、wikilink（`[[id|表示名]]`）なら `id`、ローカル ID の表記ならその ID とする。
   - 項目 ID は、仕様ID の文書を示す部分より後ろにある、要求文書が定めた形式の ID とする。
   - `・` や `,` で複数の項目 ID を併記した行は、項目ごとに 1 件の対応として数える。
   - 下位項目（例: `BAC-01 の C-01`）は、その上位の項目 ID（`BAC-01`）への対応とする。
   - 要求文書だけで項目 ID がない行は、項目への対応とせず手順 4 で記録する。
4. 照合する: 母集団にない項目または文書を指す行を記録する。また、`relations.verifies` を定める種別のテストで、「トレース」の表が指す要求文書が `relations.verifies` にない場合を記録する。
5. 標準列と「充足状況の判定」に従って表を作り、サマリの件数を表から数えて合計を母集団の件数と照合する。

### 5.2. トレースマトリクスの標準列

| 列名         | 生成元と導出規則                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------- |
| 要求ID       | 母集団の要求項目（`<要求文書ID> <項目ID>`）。要求文書での記載順に並べる                                       |
| 要求要約     | 要求文書の項目の見出しまたは 1 行目の要点                                                                     |
| 対応テストID | 手順 3 で対応づけたテスト文書 ID と `trace_key`（例: `atc-cash-sale TR-01`）。複数可、なければ空とせず `なし` |
| 充足状況     | `未着手` / `一部充足` / `充足`。「充足状況の判定」に従う                                                      |
| ギャップ     | 「充足状況の判定」で `充足` を妨げた条件を、該当するテスト ID とともに書く。なければ `なし`                   |
| 備考         | 判定に使った各テストの `status`                                                                               |

母集団外の参照は、マトリクスの後に「参照ID / テストID / ギャップ」の表で示します。参照ID には手順 4 で記録した要求項目または要求文書を書きます。この表の行は充足状況を持たず、サマリの充足状況ごとの件数に含めません。

### 5.3. 充足状況の判定

対応テストは手順 3 で対応づけたものを指します。`relations.verifies` の宣言が必要なのは、そのテスト種別の rulebook が宣言を定めている種別（受入テスト `atc-*`）だけです。定めていない種別（総合テスト `stc-*`）は、「トレース」の表の仕様ID が要求項目を指すことを文書単位の対応とし、宣言の有無を判定に使いません。

| 充足状況   | 条件                                                                                                                                                                    |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `未着手`   | 対応テストがない                                                                                                                                                        |
| `一部充足` | 対応テストはあるが、いずれかが `draft` である、`trace_key` を参照するケースがない（検証ケース未記載）、または宣言が必要なテストで要求文書が `relations.verifies` にない |
| `充足`     | 対応テストがすべて `ready` で、`trace_key` を参照するケースがあり、宣言が必要なテストは要求文書を `relations.verifies` に持つ                                           |

## 6. 記述ガイド

完成例は Frontmatter の `sample` で宣言された sample を参照してください。

### 6.1. 目的と適用範囲

- **判断基準**: どのレビュー・受入判断に使い、どのリリースや領域の要求を対象とするかが分かること。
- **良い例**: 「第 1 リリースの会計・在庫・値引き・監査の受入基準と、それを検証する受入テスト・総合テストの対応を示し、テストレビューでテスト漏れを見つける。性能試験は対象外とする。」
- **悪い例**: 「要求とテストの対応を管理する。」（対象範囲と使う場面が分からない）

### 6.2. トレース対象の前提

- **判断基準**: 別の人が同じ前提で「生成の手順」をたどり、同じ表を得られること。
- **良い例**: 「母集団: `bac-sales` の BAC-01〜BAC-04（4 件）。テスト: `relations.verifies` に `bac-sales` を持つ `atc-*`、および「トレース」の表が `bac-sales` を指す `stc-*`。生成: 「生成の手順」による手作業で 2026-05-01 に生成、生成元は `main` の `a1b2c3d`。」
- **悪い例**: 「最新のテストから作成した。」（母集団と抽出条件が分からず、検証できない）

### 6.3. トレースマトリクスと充足状況サマリ

- **判断基準**: 各行の充足状況が「充足状況の判定」の条件から説明でき、サマリの件数が表の行数と一致すること。優先する要求項目には、業務上の影響など判断の理由を添えること。
- **良い例**: 「`bac-sales BAC-02` ／ 在庫と同数の購入で在庫が 0 個になる ／ `stc-cash-sale TR-01` ／ 一部充足 ／ `stc-cash-sale` が `draft` ／ `stc-cash-sale`: `draft`」
- **悪い例**: 「`bac-sales BAC-02` ／ … ／ ほぼ対応 ／ ― ／ ―」（曖昧語で判定できず、根拠がない）

### 6.4. ギャップと対応方針

- **判断基準**: ギャップはマトリクスから転記し、対応方針にはどの生成元の成果物をどう直せば再生成で解消と判定できるかを書くこと。担当・期限は登録簿で追跡し、本ビューに列を設けません。
- **良い例**: 「`bac-sales BAC-04` ／ 対応テストがない ／ `atc-audit-retention` を作成し、`relations.verifies` に `bac-sales`、トレースの表に BAC-04 を持たせる ／ 再生成で `一部充足` 以上になる」
- **悪い例**: 「監査ログのテストは今後対応する。」（直す成果物も判定条件もない）

### 6.5. 変更履歴と更新ルール

- **判断基準**: 再生成の契機（要求・テストの追加、ID 参照やトレースの表の変更、テストの `status` 変更）と、前回から充足状況が変わった要求項目が分かること。

## 7. 禁止事項

| 禁止パターン                                                    | 理由                                                 |
| --------------------------------------------------------------- | ---------------------------------------------------- |
| 生成した表を手編集し、生成元と異なる対応や充足状況を書く        | 正本と派生ビューが食い違い、再生成で消えるため       |
| `relations.verifies` の文書 ID だけで要求項目との対応を判定する | どの項目を検証するか分からず、テスト漏れが隠れるため |
| 要求本文・テスト本文の全文転記                                  | 正本との二重管理になり、更新時に不整合が出るため     |
| 要求 ID または対応テスト ID の空欄                              | 未対応なのか記入漏れなのか判別できないため           |
| 充足状況に曖昧語（ほぼ対応、だいたい完了など）を使う            | 「充足状況の判定」の条件で確かめられないため         |
| 対応テスト ID が `なし` の行でギャップを `なし` とする          | テスト漏れが表から隠れるため                         |
| 「トレース対象の前提」に母集団と生成手段を書かずに表を示す      | 再生成して照合できず、表が正しいか検証できないため   |
