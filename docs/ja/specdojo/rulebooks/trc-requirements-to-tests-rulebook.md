# トレーサビリティ（要求→テスト）作成ルール

Requirements Traceability (Requirements to Tests) Rulebook

テスト成果物の型付き ID 参照から要求とテストの対応を派生ビューとして示し、要求漏れ・テスト漏れを見つける形式を定めます。

## 1. 全体方針

- **対象**: 要求とテストの対応の可視化を扱い、要求本文・テスト手順は扱いません。テストの実行結果も扱わず、充足状況はテストの対応と作成状態で判定します。
- **正本と派生**: 対応の正本はテスト成果物の `relations.verifies` とし、本ビューは派生ビューとして生成します。「目的と適用範囲」と「トレース対象の前提」は生成の条件として書き、「トレースマトリクス」「充足状況サマリ」「ギャップと対応方針」は生成元から導出します。充足状況やギャップを直すときは生成元の成果物を直して再生成し、本ビューへ直接書きません。
- **記載レベル**: 1 行は 1 つの要求 ID とその対応テスト ID 群とします。
- **任意の管理ビュー**: 必要なプロジェクトだけが生成し、独自のドメインやトラックを持ちません。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従います。文書の整形・lint はリポジトリの検証で扱い、業務の受入確認に含めません。

## 2. 位置づけ

本ビューは、要求（業務の受入基準 `bac-*` など）と、それを検証するテスト（受入テスト `atc-*`、総合テスト `stc-*` など）の作成後に生成し、テストのレビュー時と要求・テストの変更時に再生成します。要求→仕様の対応は [[specdojo:trc-requirements-to-specs-rulebook|トレーサビリティ（要求→仕様）作成ルール]] が扱います。

## 3. ファイル命名・ID規則

- **ファイル名**: `trc-requirements-to-tests.md` とします。分割する場合は `trc-requirements-to-tests-<term>.md` とします。
- **文書 ID**: 成果物カタログの宣言と一致させます。プロダクト仕様のカタログに置く場合は `trc-requirements-to-tests`、プロジェクト固有の場合は `<project-id>:trc-requirements-to-tests` とします（分割時は末尾に `-<term>`）。

## 4. 推奨 Frontmatter 項目

許可キーと型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とします。

- `specdojo.rulebook` は `specdojo:trc-requirements-to-tests-rulebook` とします。
- `specdojo.based_on` は必須とし、生成元とした要求とテストの文書 ID をすべて記載します。索引だけを挙げて要求側を省きません。

## 5. 本文要件

| 章                   | 必須     | 内容・受入条件                                                                                                              |
| -------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------- |
| 目的と適用範囲       | 必須     | 対象の要求群・テスト群と対象外（理由付き）が分かること                                                                      |
| トレース対象の前提   | 必須     | 要求の母集団（`based_on` の要求文書の全要求 ID）、テストの範囲、生成の手段（コマンドまたは手順）と生成日が分かること        |
| トレースマトリクス   | 必須     | 標準6列で母集団の全要求を並べ、テストのない要求と、母集団にない要求 ID を `relations.verifies` に持つテストが識別できること |
| 充足状況サマリ       | 必須     | 充足状況ごとの要求 ID の件数（重複なし、合計が母集団の件数と一致）と、優先して解消する要求 ID が分かること                  |
| ギャップと対応方針   | 必須     | ギャップごとに、直す生成元の成果物と解消の判定条件が分かること                                                              |
| 変更履歴と更新ルール | 条件付き | 再生成の契機や前回からの差分を残す必要があるときに置き、生成日と差分の要点を示す                                            |

### 5.1. トレースマトリクスの標準列

| 列名         | 内容・判断条件                                                                            |
| ------------ | ----------------------------------------------------------------------------------------- |
| 要求ID       | 母集団の要求 ID。母集団にない参照は `なし` とし、その参照を持つテストを対応テストIDに書く |
| 要求要約     | 要求文書の記述から要点を 1 行で示す                                                       |
| 対応テストID | その要求 ID を `relations.verifies` に持つテスト ID（複数可、なければ空とせず `なし`）    |
| 充足状況     | `未着手` / `一部充足` / `充足`。判定は「充足状況の判定」に従う                            |
| ギャップ     | 未対応点・不整合・未決事項。なければ `なし`                                               |
| 備考         | 判定の根拠（参照先の `status`、review result など）                                       |

### 5.2. 充足状況の判定

| 充足状況   | 条件                                                                 |
| ---------- | -------------------------------------------------------------------- |
| `未着手`   | その要求を `relations.verifies` に持つテストがない                   |
| `一部充足` | 対応テストはあるが、参照先が未作成・`draft` であるか、ギャップが残る |
| `充足`     | 対応テストがすべて存在して `ready` であり、ギャップが `なし`         |

## 6. 記述ガイド

完成例は Frontmatter の `sample` で宣言された sample を参照してください。

### 6.1. 目的と適用範囲

- **判断基準**: 誰がどのレビュー・受入判断に使い、どのリリースや領域の要求を対象とするかが分かること。
- **良い例**: 「第 1 リリースの会計・在庫・値引き・監査の受入基準と、それを検証する受入テスト・総合テストの対応を示し、テストレビューでテスト漏れを見つける。性能試験は対象外とする。」
- **悪い例**: 「要求とテストの対応を管理する。」（対象範囲と使う場面が分からない）

### 6.2. トレース対象の前提

- **判断基準**: 別の人が同じ前提で再生成し、同じ表を得られること。
- **良い例**: 「要求の母集団: `bac-sales` の全受入基準。テスト: `relations.verifies` を持つ `atc-*`・`stc-*`。生成: `<生成コマンド>` で 2026-05-01 に生成。」
- **悪い例**: 「最新のテストから作成した。」（母集団と生成の手段が分からず、検証できない）

### 6.3. トレースマトリクスと充足状況サマリ

- **判断基準**: 各行の充足状況が「充足状況の判定」の条件から説明でき、サマリの件数が表の要求 ID 数と一致すること。
- **良い例**: 「req-r1-004 ／ 監査ログを 1 年保持する ／ なし ／ 未着手 ／ 保持期間を検証するテストがない ／ ―」
- **悪い例**: 「req-r1-002 ／ … ／ ほぼ対応 ／ ― ／ ―」（曖昧語で判定できず、根拠がない）

### 6.4. ギャップと対応方針

- **判断基準**: どの生成元の成果物をどう直せば解消と判定するかが分かること。担当・期限は登録簿で追跡し、本ビューに列を設けません。
- **良い例**: 「req-r1-004 ／ 保持期間の受入テストがない ／ `atc-audit-retention` を作成し `relations.verifies` に req-r1-004 を持たせる ／ 再生成で `一部充足` 以上になる」
- **悪い例**: 「監査ログのテストは今後対応する。」（直す成果物も判定条件もない）

### 6.5. 変更履歴と更新ルール

- **判断基準**: 再生成の契機（要求・テストの追加、ID 参照の変更、テストの `status` 変更）と、前回から充足状況が変わった要求 ID が分かること。

## 7. 禁止事項

| 禁止パターン                                                            | 理由                                               |
| ----------------------------------------------------------------------- | -------------------------------------------------- |
| 生成した表を手編集し、`relations.verifies` と異なる対応や充足状況を書く | 正本と派生ビューが食い違い、再生成で消えるため     |
| 要求本文・テスト本文の全文転記                                          | 正本との二重管理になり、更新時に不整合が出るため   |
| 要求 ID または対応テスト ID の空欄                                      | 未対応なのか記入漏れなのか判別できないため         |
| 充足状況に曖昧語（ほぼ対応、だいたい完了など）を使う                    | 「充足状況の判定」の条件で確かめられないため       |
| 対応テスト ID が `なし` の行でギャップを `なし` とする                  | テスト漏れが表から隠れるため                       |
| 「トレース対象の前提」に母集団と生成手段を書かずに表を示す              | 再生成して照合できず、表が正しいか検証できないため |
