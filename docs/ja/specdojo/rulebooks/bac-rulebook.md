# 業務受入条件 作成ルール

Business Acceptance Criteria Documentation Rulebook

業務担当者が「この仕組みで業務を進められる」と判断するための受入条件を定めます。利用場面、前提、業務行為、観測可能な期待結果を対応させ、承認と受入テスト設計に渡せる粒度を規定します。

## 1. 全体方針

- [[specdojo:deliverables-reference|成果物リファレンス]] の業務受入条件として、業務仕様が利用者の課題を解決するかを合意・確認する基準を定める。仕様が存在するだけでは業務を進められると判断できないため、利用場面と確認できる結果へ具体化する。
- 1 文書で一つの受入対象（業務の塊）を扱い、対象者の課題と期待価値に結び付くシナリオを選ぶ。
- 決定済みの業務仕様を受入条件へ変換する。新しい業務判断、閾値、例外承認を BAC で確定しない。
- 期待結果は状態、記録、引き継ぎなど観測できる事実にする。実装や画面の手順を受入基準の代替にしない。
- 共通事項は上位の index・標準を正本とし、構文・値・保存構造は schema・リファレンスへ委譲する。

## 2. 位置づけと用語定義

BAC は BPS や業務ルール、プロジェクトの受入条件を根拠に、業務としての成立を確認する要求である。BA が作成し、PO が業務的な妥当性を承認する。ARC は設計への入力として、QE は受入テスト設計への入力として利用する。テストの詳細手順と実行結果は BAC に含めない。

[[specdojo:track-design-guide|トラック設計ガイド]] の品質仕様カテゴリで業務仕様を受け取り、受入テスト仕様とその実施へ渡す。BPS の業務の流れ、BR の判断規則、UIS の利用者操作、BES の業務イベントと発生条件を、業務の開始から結果まで横断して確認する。各仕様の定義は入力元を正本とし、BAC はそれらの組合せで業務が成立する条件を担う。

| 用語     | 本系統での意味                                             |
| -------- | ---------------------------------------------------------- |
| 受入対象 | 一連の結果として業務担当者が受け入れる能力・業務の範囲     |
| シナリオ | 特定の開始状態から、業務行為を経て期待結果を確認する一単位 |
| 判定方法 | 誰が、どの時点で、何の証跡を照合して期待結果を確認するか   |

## 3. ファイル命名・ID規則

- ファイル名は受入対象を表す `bac-<subject>.md` を推奨し、配置は成果物カタログに従う。連番や日本語名を採用する場合は、同じ対象の ID とパスの対応をカタログで一意にし、表示順や表示名の変更だけでは ID を変えない。
- 新規 ID は `<project-id>:bac-<subject>` のようにプロジェクトを表す authority と対象のローカル ID を組み合わせる。既存文書は宣言された ID を使い、ファイル名から別の ID を推測しない。共通規則は [[specdojo:docs-structure-guide|ドキュメント構造ガイド]] に従う。
- シナリオには文書内で一意な識別子を付ける。ケース表を用いる場合も行 ID を持たせ、根拠やテスト設計から追跡できるようにする。

## 4. 推奨 Frontmatter 項目

メタ情報の型・許可値・キーの配置・必須項目は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と [成果物 Frontmatter schema](../../../specdojo/schemas/v1/deliverable-frontmatter.schema.yaml) を正本とする。SpecDojo の項目は `specdojo` 名前空間配下に置く。

- `type` は業務受入基準を表す `requirement` とし、必須の `rulebook` に本 rulebook の ID を宣言する。文書の名称は H1 に置く。
- `based_on` は受入条件の根拠となる先行成果物を示す。カタログ管理下では `depends_on` の範囲に従い、プロジェクト文脈をそのまま転記しない。
- 作成・改訂中の文書は `draft` とする。`part_of` は親 BAC がある場合、`supersedes` は旧 BAC を置き換える場合に用いる。
- 要求の充足やテストからの検証関係はメタ情報標準の「型付き参照」を使う。根拠を示す `based_on` と区別し、独自の関係キーを追加しない。
- 改訂・廃止はメタ情報標準の「文書の改訂・廃止とライフサイクル変更管理」に従う。BA が理由・代替先・移行時期と影響を整理し、PO が判断する。BA はカタログと BPS・BR 等の本文参照、ARC は設計、QE は受入テスト仕様・ケースと再検証、PM は追従作業と期限を担当する。ID・シナリオ ID または条件を変える場合は旧参照を検索し、参照先と期待値を更新して参照切れがないことを確認する。

## 5. 本文要件

見出し順・表・記入欄の骨組みは frontmatter で宣言した template を正本とする。内容の成立条件は次のとおり。

| 扱う内容        | 必須 | 成立条件                                                                                                                              |
| --------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 概要            | ○    | 受入対象、対象者、守る価値、利用場面、対象範囲と対象外、根拠が分かる。確認者・承認者と合意対象を示す                                  |
| 受入条件        | ○    | シナリオごとに ID、根拠、前提、操作、期待結果、判定方法を対応させる。正常経路と、業務上結果が異なる例外・停止・再開を必要な範囲で扱う |
| メモ / 将来課題 | ○    | 未確定事項の影響、判断依頼先、解消時点・条件を記す。未決がなければ「なし」と明記する                                                  |

### 5.1. シナリオの記述規約

- 前提は開始時点の状態、必要な入力、権限を記す。共通前提は受入条件の冒頭に一度だけ置き、例外シナリオでは異なる前提を明示する。
- 操作は担当者による業務行為を示す。期待結果は操作後の変化に加え、停止時に確定してはならない記録と次の担当への引き継ぎを示す。
- 判定方法は必須とし、期待結果の各項目に確認者、確認時点、観測先（記録・画面・帳票等）、照合対象を対応させる。前提と入力から期待結果を導けない箇所は未決事項へ送る。
- 同じ操作と観測点で条件だけが変わる場合はケース表へまとめてよい。停止範囲や再開先が異なる場合はシナリオを分ける。

### 5.2. 確認完了と確定の条件

- BA は、概要の価値・対象範囲に必要なシナリオがそろい、各シナリオの根拠と `based_on` が有効な先行成果物へ解決できることを確認する。カタログ管理下では依存関係との整合も確認する。
- QE は、全シナリオに前提・操作・観測可能な期待結果・判定方法があり、正常経路と必要な例外・停止・再開を判断できることを確認する。ARC は設計への引き渡しと参照の整合を確認する。
- BA・QE は、メタ情報標準の「バリデーション」とリポジトリの検査設定に従う。本リポジトリでは `npm run lint:md` と `npm run lint:fm` が終了コード 0 となり、Markdown・Frontmatter・参照にエラーがないことを確認する。失敗箇所を修正して再検査する。executor / reporter pipeline では設定済みの親検証結果を用いる。
- PO は業務側の確認者との合意と、受入の合否を左右する未確定事項の解消を確認して確定を判断する。PM は残る準備作業の担当・判断時点・追跡先を確認する。`ready` への昇格は人が行い、文書の確定を受入試行の合格実績とは扱わない。

## 6. 記述ガイド

### 6.1. 概要

- 判断基準: 対象者の業務課題・期待価値、利用場面、対象範囲と対象外、業務側の確認者・合意者を必ず記す。各価値をどのシナリオ ID で確認するかを示し、対象外を別 BAC で扱う場合は参照先を添える。上位の Why は要約と参照で引き継ぐ。
- 良い例: 「家族が店番しても販売と在庫を記録して引き継げることを BAC-01 で確認し、店主代表が受入に合意する。返品と仕入れは対象外とする」。
- 悪い例: 「システムが正常に動くこと」。利用者、対象、成立する業務が不明である。

### 6.2. 受入条件

- 判断基準: 前提と操作から期待結果が決まり、確認者が証跡で合否を判断できること。業務仕様の判断自体は参照先を正本とする。
- 良い例: 「在庫が 5 個の商品の 2 個販売を確定する。販売記録が 1 件残り、在庫が 3 個になる。家族利用者代表が確定後に両記録を照合する」。
- 悪い例: 「確定ボタンを押すと正しく処理される」。観測点がなく、画面操作に依存している。

#### 6.2.1. 差分と例外の書き分け

- ケース表の推奨列は「ケース ID / 条件・入力 / 期待結果（観測点）」。操作と判定方法は共通部分に置き、同じ内容を各行に繰り返さない。
- 良い例: 同じ販売操作で数量だけが異なる場合は表にまとめ、記録不能の場合は別シナリオで未確定の状態と引き継ぎ先を示す。
- 悪い例: 正常完了、入力不足、再開を一つの「エラーなら対応する」にまとめる。業務を続けられる条件が判別できない。

### 6.3. メモ / 将来課題

- 判断基準: 現行の受入を止める論点と将来の拡張を区別でき、誰のどの判断で解消するかが分かること。
- 記録規約: 確認・追記作業には `_TODO_`、意思決定待ちには `_UNDECIDED_` を付ける。推奨列は「論点 / 影響するシナリオ ID・受入への影響 / 担当・判断者 / 判断時点・解消条件 / 追跡先」。解決した記述は確定内容へ更新し、ラベルを外す。
- 管理への接続: 将来追加するシナリオは対象外の範囲と追加条件を BAC に残す。現行の受入、期限、依存先に影響する未確定事項は PJR 登録候補とし、BA が影響を整理して PM へ渡す。課題・リスク・変更要求・決定の追跡は [[specdojo:pjr-rulebook|プロジェクト登録簿 作成ルール]] に従い、登録後は BAC に受入への影響と個票への参照を残す。
- 上流変更への追従: `based_on` 先の改訂・廃止、業務判断や受入範囲の変更時に、BA が影響するシナリオと期待値を特定する。未確定の判断は入力元へ戻し、確定後に BAC と参照を更新する。QE が判定方法と後続テストを再確認し、PO が変更後の業務条件を承認するまで、旧条件で受入を確定しない。追従作業は PM が PJR で管理する。
- 良い例: 「`_UNDECIDED_`: 記録不能時に販売を続けるかは店主代表が当該シナリオ作成前に判断する。現行は記録可能な場合に限定し、BA が販売停止への影響を整理して PM へリスク登録候補として渡す」。
- 悪い例: 「例外は今後検討」。影響範囲と次の判断が不明である。

## 7. 禁止事項

- 物理テーブル、SQL、実装クラス、詳細 API、クリック手順を業務条件として書かない。
- schema・リファレンスの値・構文・構造の詳細を再掲しない。確認に必要な正本の参照を示す。
- 「問題ない」「正しく処理される」だけで期待結果や判定方法を代替しない。
- 根拠のない数値、判断権限、例外承認を追加しない。未決事項を合格済み・承認済みとして扱わない。
- 業務仕様の全文、テストの詳細手順、受入実績を BAC の本文へ複写しない。
