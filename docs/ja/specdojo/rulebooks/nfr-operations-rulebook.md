# 非機能要件 / 運用 作成ルール

Non-Functional Requirements Operations Documentation Rules

本書は、非機能要件のうち運用（監視、バックアップ、手順、体制）を定義する `nfr-operations` の作成ルールを定める。`nfr-operations` は、平常時の監視と異常時の対応を続けられるかを判断し、運用方針・運用手順・受入判定の基準を揃えるための文書である。

## 1. 全体方針

- 運用は監視可能性、通知、手動介入の条件、復旧性を、合否判定できる要求として定義する。
- 本書には満たすべき運用結果（達成基準）だけを書く。実現手段（監視製品・通知ツールの選定や設定）は `opd-*`、実行手順は `opr-*` に置く。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status` の昇格と承認、改訂と廃止、未決事項の登録簿への引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、本書と成果物で言い直さない。文書の整形・lint はリポジトリの検証で扱い、「測定・検証方法」に含めない。
- _UNDECIDED_: `recipe`・`template` の要否は未判断である。sample は「本文要件」の 5 章に揃っていないため、sample を揃えることと、同じ構成を NFR 分冊で共通の template にできるかの判断を、本書を `ready` にする前提条件とする。

## 2. 位置づけ

運用の達成基準を決め、運用方針・手順・受入判定がそれを満たすかを判断するための文書であり、次の文書と接続する。

| 文書        | 関係                                                                     | 参照する場面                           |
| ----------- | ------------------------------------------------------------------------ | -------------------------------------- |
| `nfr-index` | NFR 全体の入口。分冊として `part_of` で属する                            | NFR 全体の中で運用の基準を位置づける時 |
| `opd-*`     | 本書の基準を `based_on` に取り、監視・通知・バックアップの方式を設計する | 基準を満たす手段を決める時             |
| `opr-*`     | `opd-*` に沿った実行手順（Runbook・障害対応・バックアップ）              | 手順が基準を満たすかを確かめる時       |
| `sac-*`     | 本書の要件 ID ごとの合否判定基準                                         | 受入で運用要件を判定する時             |
| `dec-*`     | 基準値や対象外の設計判断                                                 | 基準値の根拠を辿る時                   |

- 本書を先に作り、`opd-*`・`opr-*`・`sac-*` は本書の要件 ID を参照する。それらが未作成の間は、本文の導線にバッククォートで仮置きする。
- 基準値・対象範囲を変えたときは、該当する要件 ID を参照する `sac-*` の判定基準、`opd-*` の方式、`opr-*` の手順を見直す。

## 3. ファイル命名・ID規則

- 配置先は `docs/ja/product/060-non-functional-requirements/nfr-operations.md` とし、[[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従う。
- 文書 ID は `nfr-operations` とする。プロダクト文書のため名前空間を付けない。
- 要件 ID は `nfr-ops-<連番>`（例: `nfr-ops-001`）とし、欠番を作らない。

## 4. 推奨 Frontmatter 項目

許可キー・必須項目（`id` / `type` / `status` を含む）・型制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。

- `specdojo.type` は `requirement`、`specdojo.rulebook` は `specdojo:nfr-operations-rulebook` とする。
- `specdojo.part_of` は配列で `[nfr-index]` とする。
- `specdojo.based_on` には、営業時間や体制など基準値の根拠となる文書を挙げる。

## 5. 本文要件

`nfr-operations` は以下の章を順序固定で配置し、見出しは章名をそのまま使う。

| 順序 | 章                   | 必須 | 目的・内容                                                         |
| ---- | -------------------- | ---- | ------------------------------------------------------------------ |
| 1    | 概要（対象・目的）   | ○    | 守る業務と、運用要件を満たせないときの業務影響を示す               |
| 2    | 適用範囲・体制前提   | ○    | 対象システム・対象外、監視時間帯、オンコール体制、通知と段階を示す |
| 3    | 運用要件一覧         | ○    | 4 領域の要件を、合否判定できる基準とともに一覧にする               |
| 4    | 測定・検証方法       | ○    | 要件 ID ごとの測定方法、判定時期、判定者、未達時の扱いを示す       |
| 5    | 関連ドキュメント導線 | ○    | 「位置づけ」の文書へ、種別・文書 ID・目的で辿れるようにする        |

## 6. 記述ガイド

各節は「本文要件」の同名の章に対応する。判定者や体制は、適用先のメンバー定義の Role code（例: `OPS`）で書く。

### 6.1. 概要（対象・目的）

- 運用要件で守る業務（営業時間中の販売の継続、記録の保全など）を書く。
- 守れなかったときの業務影響（売上の取りこぼし、記録の欠落など）を書く。
- 基準値の根拠とした文書を示す。

判断基準: 守る業務と影響から、各要件の厳しさの理由を説明できること。

- 良い例: 「営業時間中にレジの障害に気づけないと会計ができず売上を取りこぼす。営業時間中の販売の継続を守る。」
- 悪い例: 「安定した運用を実現する。」（守る業務と影響がない）

### 6.2. 適用範囲・体制前提

- 対象システムと対象外（運用を外部委託する部分など）を書く。
- 監視時間帯と、時間外の扱いを書く。
- オンコール体制（Role code・人数）と、通知・エスカレーションの段階（何分で次の段へ上げるか）を書く。通知手段は「電話」「チャット」のように手段の種類で書き、製品名は `opd-*` に置く。

判断基準: 異常の発生時に、誰へどの順で何分以内に届くかを一意に判断できること。

- 良い例: 「監視は営業日 10:00〜19:00。異常はまず `OPS` にチャットで通知し、15 分応答がなければ `PO` へ電話する。」
- 悪い例: 「PagerDuty で通知する。」（製品名だけで、段階と時間がない）

### 6.3. 運用要件一覧

- 表の列は `要件ID` / `領域` / `内容` / `指標` / `基準` / `備考` とする。
- `領域` は監視・バックアップ・手順・体制の 4 領域とし、すべてを扱う。扱わない領域は対象外として理由を書く。
- `基準` は数値・単位・比較方向・集計期間で書く。指標の例は MTTD、アラート誤検知率、バックアップ成功率、Runbook 網羅率である。

判断基準: 要件ごとに pass / fail を一意に判定でき、4 領域の抜けがないこと。

- 良い例: 「`nfr-ops-002` / バックアップ / 日次バックアップを成功させる / 成功率 / 月次で 99.5% 以上」
- 悪い例: 「バックアップを適切に取る」（指標・基準・期間がない）

### 6.4. 測定・検証方法

- 要件 ID ごとに、測定方法（監視ダッシュボード、運用レポート、訓練結果）、判定時期、判定者の Role code を書く。基準値は「運用要件一覧」を参照し、言い直さない。
- 基準を満たさなかった結果は `sac-*` の判定記録に残し、是正するか基準値を見直すかを判定者が決める。基準値を見直す場合は `dec-*` に判断を残す。
- 基準値を見直す契機（未達が続いた、体制や営業時間が変わったなど）を書く。

判断基準: 測定結果から pass / fail と、未達のときの次の扱いを一意に判断できること。

- 良い例: 「`nfr-ops-001`：障害の事後レビューで発生から検知までの時間を計り、`OPS` が判定する。2 か月続けて未達なら基準値を見直す。」
- 悪い例: 「定期的に確認する。」（方法・時期・判定者がない）

### 6.5. 関連ドキュメント導線

- 「位置づけ」の文書を、種別・文書 ID・目的の表で紐づける。
- 基準値を変えたときに見直す `sac-*` / `opd-*` / `opr-*` が分かるようにする。
- 未作成の文書はバッククォートで仮置きする。

判断基準: 各要件の判定先と、それを実現する方針・手順へ辿れること。

- 良い例: 「運用手順 / `opr-backup` / バックアップの実行と失敗時の再実行」
- 悪い例: 「関連資料を参照。」（文書と目的が特定できない）

## 7. 禁止事項

| 禁止事項                                   | 理由                                  |
| ------------------------------------------ | ------------------------------------- |
| 手順書の全文を再掲する                     | 文書責務が混在するため                |
| 通知先や判定条件を曖昧にする               | 運用不能になるため                    |
| 監視指標を定義しない                       | 品質評価が継続できないため            |
| 基準を単位・集計期間なしで書く             | 判定できないため                      |
| 監視製品・通知ツールの選定を要件として書く | 手段の決定は `opd-*` の責務であるため |
