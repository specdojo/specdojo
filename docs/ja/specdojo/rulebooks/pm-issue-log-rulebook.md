# 課題ログ 作成ルール

Issue Log Documentation Rules

顕在化した課題の優先度・期限・対応・状態を追跡する課題ログの記述基準を定める。

## 1. 全体方針

- 顕在化した課題ごとに、未解決かどうかと次の対応を判定できる形で残す。
- 課題ログは、対応順の決定、期限超過時のエスカレーション、完了の確認を判断するための文書とする。
- 対象は既に発生して対応が要る課題とする。未顕在の事象はリスク登録簿、仕様・範囲の変更はその変更要求に記録し、課題ログへ二重に記録しない。課題の対応でリスクや変更要求が生じた場合は、それを起票して関連ドキュメントから文書 ID で参照する。
- **共通の運用**: 役割の割り当ては適用先のメンバー定義に、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。文書の整形・lint はリポジトリの検証で扱う。

## 2. 位置づけ

- プロジェクト登録簿を使うプロジェクトでは、課題 1 件を `item_type: issue` の個票に書き、`controls/generated/pm-issue-log.md` は `register build` が個票から生成する。生成物の Frontmatter と枠組みは Frontmatter で宣言した template に従い（`rulebook: specdojo:pjr-rulebook`）、直接編集しない。個票の必須節は [[specdojo:pjr-rulebook|プロジェクト登録簿 作成ルール]] に従い、本書からは記述ガイドの判断基準だけを適用する。
- 登録簿を使わないプロジェクトでは、単独の課題ログを本書の本文要件と記述ガイドに従って書く。

## 3. ファイル命名・ID規則

- 単独の課題ログの `id` は `<project-id>:pm-issue-log`、ファイル名は `pm-issue-log.md` とする。
- 課題 ID は登録簿では `PJR-XXXX`、単独のログでは `IS-NNN` とし、再利用しない。
- 単独のログから登録簿へ移すときは、未完了の課題を個票へ起票し、個票の本文に元の `IS-NNN` を書いて対応を残す。完了済みの課題は移さず、単独のログを `deprecated` にして登録簿の生成物を後継とする。

## 4. 推奨 Frontmatter 項目

- 許可キーと型は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] を正本とし、`type` は `project` とする。
- 単独の課題ログの `rulebook` は `specdojo:pm-issue-log-rulebook` とする。

## 5. 本文要件

単独の課題ログに適用する。登録簿の生成物は template、個票は登録簿の作成ルールに従う。

| 番号 | 見出し           | 必須 | 目的                                               |
| ---- | ---------------- | ---- | -------------------------------------------------- |
| 1    | 概要             | ○    | 管理対象と記録単位を示す                           |
| 2    | 課題ログ一覧     | ○    | 未解決の課題と次の対応を一覧で判定できるようにする |
| 3    | 優先度と期限     | ○    | 対応順とエスカレーションの基準を示す               |
| 4    | 対応計画         | ○    | 対応策と完了条件を示す                             |
| 5    | 進捗レビュー     | ○    | 完了の確認と状態更新の進め方を示す                 |
| 6    | 関連ドキュメント | ○    | 根拠と課題から起票した記録を辿れるようにする       |

## 6. 記述ガイド

### 6.1. 概要

- 管理対象、レビュー頻度、記録単位を 1〜3 行で示す。

### 6.2. 課題ログ一覧

- 課題 ID、発生日、内容、優先度、対応策、担当、期限、ステータスを一覧にする。
- 担当は適用先のメンバー定義の Role code で書き、個人名を書かない。
- 優先度とステータスは register-item-frontmatter schema の `Priority`・`ItemStatus` の値（例: `high`、`in-progress`）を単独のログでも使い、「高」「対応中」などに言い換えない。
  - 良い例: `IS-001 | ... | high | ... | QE | 2026-04-08 | in-progress`
  - 悪い例: `IS-001 | ... | 高 | ... | 山田 | 2026-04-08 | 対応中`

### 6.3. 優先度と期限

- 優先度の基準、期限の決め方、期限超過時のエスカレーション先、優先度の変更を決める者を Role code で書く。

### 6.4. 対応計画

- 対応策、依存事項、完了条件を書く。完了条件は確認の手段と合格の基準で書く。
  - 良い例: `テストデータ生成後、結合テスト 120 件を実行して全件が実行可能`
  - 悪い例: `テストが実行可能`

### 6.5. 進捗レビュー

- レビュー周期、完了を判定する者と判定の観点、状態を更新する契機を書く。
- 対応方針の採否など、選択肢から選んだ判断は決定記録（登録簿では `decision` の個票）へ起票し、課題ログには決定記録の ID だけを書く。

### 6.6. 関連ドキュメント

- 根拠、影響先、課題から起票したリスク・変更要求・決定記録を project 修飾の文書 ID（例: `<project-id>:pm-risk-register`）で示す。なければ `（本書のみ）` と書く。

## 7. 禁止事項

| 禁止事項                                   | 理由                       |
| ------------------------------------------ | -------------------------- |
| 課題IDなしで記録する                       | 追跡不能になるため         |
| 優先度・期限を未記載にする                 | 対応順序が判断できないため |
| 根拠のない完了判定を記載する               | 品質低下を招くため         |
| 個人情報・認証情報を内容や対応策に書き写す | 公開範囲を超えて広がるため |
| 生成された `pm-issue-log.md` を直す        | 再生成で修正が失われるため |
