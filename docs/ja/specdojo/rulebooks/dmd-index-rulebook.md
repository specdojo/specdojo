# データ移行設計 作成ルール

Data Migration Design Documentation Rules

データ移行設計の入口（`dmd-index`）は、移行の共通方針・`run_id` 規約・検証の共通方針を固定し、対象別の `dmd-<term>` へ導く文書です。本書はその作成基準を定めます。

## 1. 全体方針

- 共通方針を正本とし、対象別の詳細は `dmd-<term>` に委譲する。
- 再実行で同一結果となる条件と検証の合否を定義する。
- **共通の運用**: 役割は適用先のメンバー定義、`status`・承認・改訂と廃止・未決事項の引き継ぎは [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。整形・lint はリポジトリの検証で扱う。
- _UNDECIDED_: `recipe`・`template` の要否は未判断である（template は PJR-WYTX で扱う）。判断までは「本文要件」を作成時の構成の正とし、ready 化前に解消する。

## 2. 位置づけ

`mip-index` の対象・成功条件・停止許容時間を受ける。個別設計は `dmd-<term>`、リハーサル・証跡設計は `mtp-*`、当日手順は `cop-*` が担う。

## 3. ファイル命名・ID規則

命名と配置は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] に従う。

- ファイル名は `dmd-index.md` とし、プロジェクトでは移行のドメイン `060-migration-planning/` に置く。
- ID はプロダクト仕様では `dmd-index`、プロジェクトでは `<project-id>:dmd-index`（例: `prj-0001:dmd-index`）。sample の ID は共通標準に従う。

## 4. 推奨 Frontmatter 項目

共通項目は「共通の運用」の標準に従う。`specdojo.type: data`、`specdojo.rulebook: specdojo:dmd-index-rulebook` とし、文書名は H1 に置く。

## 5. 本文要件

本文は次の章をこの順序で置き、すべて必須とする。

| 見出し                                            | 受入条件                                                                   |
| ------------------------------------------------- | -------------------------------------------------------------------------- |
| 概要（index）                                     | 目的（再現性・品質担保）と範囲を1〜3行で示す                               |
| 共通方針（抽出/変換/除外/冪等性/ログ）            | フル/増分の選択と増分基準、変換/除外の原則と根拠、冪等性、ログ必須項目     |
| `run_id` 規約（命名/採番/記録/参照方法）          | 命名・採番方法、ログ/投入データ/照合レポートの関連付け                     |
| 検証の共通方針（種別/基準/証跡/保管）             | 件数/サンプル/重要値の照合手順、差分0または許容差εと理由、証跡保管先・命名 |
| 対象一覧（スコープ/非対象/担当/対応ドキュメント） | 対象/非対象/担当/対応DMDの一覧と `mip-index` との整合                      |
| 関連ドキュメント（必須）                          | 各 `dmd-<term>` への導線。分冊がなければ「（本書のみ）」と明記             |

## 6. 記述ガイド

完成例は Frontmatter の `sample` で宣言された sample を参照する。

### 6.1. `run_id` 規約（命名/採番/記録/参照方法）

- **判断基準**: 名前から実行日・対象・回次を特定でき、ログ・投入データ・照合レポートを同じ `run_id` で辿れること。
- **良い例**: `DMD-YYYYMMDD-<term>-NN`（当日内連番）を照合レポート名と投入データに付与する。
- **悪い例**: 「実行ごとに識別子を付ける」（命名・採番・付与先が分からない）。

### 6.2. 検証の共通方針（種別/基準/証跡/保管）

- **判断基準**: 検証の種別ごとに合格基準（差分0 または許容差εと理由）と証跡の保管単位があり、合否を判定できること。
- **良い例**: 「旧/新の期間別売上を照合し差分0。レポートを `run_id` 単位で保管」。
- **悪い例**: 「移行後に問題がないことを確認」。

### 6.3. 対象一覧（スコープ/非対象/担当/対応ドキュメント）

- **判断基準**: 対象と非対象が `mip-index` の移行対象一覧と一致し、各対象に方針・担当・対応DMDがあること。
- 推奨列は「区分 / 対象（論理名） / 旧→新 / 方針（フル/増分） / 担当 / 対応DMD」とする。
- 「担当」には移行作業を担う役割を、適用先のメンバー定義にある Role code（例: `DEV`）で書く。非対象は `-` とする。
- **良い例**: 「データ ／ 受注 ／ old.orders → new.orders ／ フル ／ DEV ／ dmd-order-data」。
- **悪い例**: 「担当」に独自の略称（例: `Mig`）や個人名を書く（メンバー定義と照合できない）。

## 7. 禁止事項

- 個別の変換仕様・実行手順を `dmd-<term>` と重複記載しない。
- 対象/非対象・対応DMDの導線、`run_id` 規約、検証共通方針を欠落させない。
