# 分類一覧 作成ルール

Code Table (CDT) Documentation Rules

本ドキュメントは、業務分析・要求定義・設計・実装で利用する **分類一覧（Code Table: CDT）を統一形式で記述する標準ルール**です。
業務上の分類（カテゴリ、種別、区分、コード値など）について、正本となるスキーマ（schema enum）や実装（TypeScript union 型）を参照し、重複を排除しながら業務上の意味と使い分けを定義します。

## 1. 全体方針

- **業務概念の基準化と使い分けの明確化**: 業務データ辞書（BDD）の属性や画面選択肢、集計軸などで利用される業務上の分類（カテゴリ、種別、区分など）について、各値の業務上の意味・成立条件・使い分けを Markdown 形式で明確に定義する。
- **実装重複の排除（正本参照原則）**: スキーマ（JSON Schema / YAML Schema の enum）や実装（TypeScript の union 型等）が存在する分類はそれらを正本（SSOT）として参照する。分類一覧には値そのものの機械的な列挙や型制約を再掲せず、実装から読み取れない業務上の意味（値が表す業務概念、選定基準、判断の使い分け）に特化して記述する。
- **実装にない業務上の分類の記述**: システム実装やスキーマを持たない、人が業務判断で区分する分類（店舗運営上の区分、一時的な施策分類など）は、スタンドアロン定義として値・表示名・説明の一覧を記述する。
- **完成条件**:
  - 必須メタデータ（`id`, `type`, `title`, `status`, `rulebook`）および分類定義（対象エンティティ、分類定義名、種別、正本参照）が充足していること。
  - schema または TypeScript 型を参照する分類は、正本参照先（`schema_ref` または `type_ref`）を明記し、値の重複列挙を行わず、業務上の意味と使い分けを記載していること。
  - 実装にない業務上の分類は、スタンドアロン定義として値・分類名・表示名・説明が網羅されていること。
  - `npm run lint:md`（Markdown 構文検証）および `npm run lint:fm`（Frontmatter 検証）に合格していること。
  - 業務データ辞書（BDD）、用語集（glossary）、画面仕様（UIS）、概念クラス図（CCD）と整合していること。
- **`status: ready` への昇格判定条件**:
  - 分類定義と値の業務上の意味・使い分けが、BA・PO・DEV・ARC・QE 各ロールのレビュー観点に照らして合意・承認されていること。
  - 正本参照先（スキーマまたは TypeScript 型）が実在し、参照パスが有効であること。
- **変更時の同期対象（影響範囲）**:
  - ルールブック正本: `docs/ja/specdojo/rulebooks/cdt-rulebook.md`
  - サンプル: `docs/ja/specdojo/samples/cdt-sample.md`
  - テンプレート: `docs/ja/specdojo/templates/dct-data-model-cdt-template.yaml`
  - 成果物カタログ: `docs/ja/projects/prj-0001/010-deliverables-catalog/dct-data-model-cdt.yaml`
  - 関連仕様: 業務データ辞書（BDD）、用語集（`gl-*.yaml`）、画面仕様（UIS）、ビジネスルール（BR）

## 2. 位置づけと用語定義

- **成果物の種別**: 本ルールは `type: data` の成果物に適用する（成果物メタデータとしての `type` は `data` 固定）。
- **主要な関係者（Role code）と確認観点**:
  - **BA（ビジネスアナリスト / 主作成者）**: 分類の業務的意味、各値の成立条件、使い分けの判断境界が業務要件として網羅されているかを確認する（`vp-ba-requirements-completeness`）。
  - **PO（プロダクトオーナー / 確認者）**: 業務スコープや区分けがビジネス意図・方針と合致しているかを確認・承認する（`vp-po-purpose-alignment`, `vp-po-decision-readiness`）。
  - **ARC（アーキテクト / 確認者・利用者）**: データモデル全体の整合性、正本スキーマ参照（`schema_ref`）や型定義参照（`type_ref`）の妥当性を確認する（`vp-arc-technical-constraints`）。
  - **DEV（開発者 / 利用者）**: 実装（schema enum, TypeScript union 型, マスタテーブル）との対応関係、識別子（コード値）の妥当性を確認する（`vp-dev-implementation-readiness`）。
  - **QE（品質保証 / 確認者）**: 各分類値の境界条件、同値分割・境界値テスト観点、検証可能性を確認する（`vp-qe-verifiability`）。
- **用語定義**:
  - **業務分類（Business Classification）**: 業務ロジックに基づいて固定的に存在する分類（例: 商品区分、顧客種別）。値は少数で変動が少ない。
  - **コード表（System Code List）**: システムで使用されるコード値の一覧（例: 都道府県コード、支払方法コード、税種別コード）。マスタテーブルまたは enum として管理される。
  - **動的分類（Dynamic Classification）**: ユーザーが業務運用の中で自由に追加・編集・削除できる分類（例: タグ、ラベル、フォルダ）。値が流動的であるため BDD の enum にしてはならず、テーブルで管理する。
  - **正本参照（SSOT Reference）**: スキーマ（JSON/YAML Schema enum）やソースコード（TypeScript union 型）など、値の一覧が機械的に確定している情報源への参照。
  - **業務上の意味と使い分け**: 単なる値の字面や名称の再掲ではなく、その値が業務上何を表し、どのような条件・文脈でその値を選択・適用すべきかの判断基準。

## 3. ファイル命名・ID規則

### 3.1. ID規約

- `id` は正規表現 `^(?:[a-z][a-z0-9-]*:)?cdt-[a-z0-9-]+$` に合致する一意 ID を用いる。
  - プロジェクト成果物: `<project-id>:cdt-<term>`（例: `prj-0001:cdt-register-type`）
  - SpecDojo 同梱成果物: `specdojo:cdt-<term>`（例: `specdojo:cdt-sample`）
  - 単体 ID: `cdt-<term>`
- 成果物メタデータの `type` は `data` 固定とする。
- 置き換えによる大幅改訂時は `supersedes` に旧 ID（例: `specdojo:cld-rulebook`）を明記する。

### 3.2. ファイル命名規約

- **配置ディレクトリ**: プロジェクト内の分類一覧は、成果物カタログの `base_path`（通常は `docs/ja/product/010-business-specs/020-data-model/`）直下に配置する。
- **ファイル形式**: Markdown 形式（`.md`）で管理する。
- **ファイル名**: `cdt-<term>.md`（英小文字 kebab-case）とする（例: `cdt-register-type.md`, `cdt-deliverable-kind.md`, `cdt-product-type.md`）。

## 4. 推奨 Frontmatter 項目

Markdown ドキュメントの先頭メタデータとして、以下の項目を定義する。

| 項目       | 説明                                     | 必須 |
| ---------- | ---------------------------------------- | ---- |
| id         | 分類一覧ID（`cdt-...`）                  | ○    |
| type       | 成果物種別（`data` 固定）                | ○    |
| title      | ドキュメント名（分類名）                 | ○    |
| status     | 状態（`draft` / `ready` / `deprecated`） | ○    |
| rulebook   | 準拠ルール（`specdojo:cdt-rulebook`）    | ○    |
| supersedes | 置き換え関係（旧IDの配列）               | 任意 |

記述例:

```yaml
---
specdojo:
  id: prj-0001:cdt-register-type
  type: data
  status: draft
  rulebook: specdojo:cdt-rulebook
---
```

## 5. 本文要件

分類一覧ドキュメントは以下の章構成を基本とする。

| 章番号 | 章タイトル               | 必須 | 説明                                                                     |
| ------ | ------------------------ | ---- | ------------------------------------------------------------------------ |
| 1      | 概要                     | ○    | 対象エンティティ、分類の業務的目的、管轄・関係ロール、適用範囲をまとめる |
| 2      | 分類定義                 | ○    | 対象エンティティ、分類定義名、種別、正本参照、説明を表形式で定義する     |
| 3      | 値の業務的意味と使い分け | ○    | 正本参照先または値の一覧と、各値の業務上の意味・使い分け・判断基準を示す |
| 4      | 関連仕様との関係         | 任意 | BDD（業務データ辞書）、UIS（画面仕様）、BR（ビジネスルール）との関係     |

### 5.1. 分類定義の要件

「分類定義」の章では、以下の 2 列の表で分類の基本属性を定義する。

| 定義項目         | 説明                                                                                         |
| ---------------- | -------------------------------------------------------------------------------------------- |
| 対象エンティティ | 分類が属する業務上の対象（例: 登録項目、成果物、商品、顧客）                                 |
| 分類定義名       | 分類を表す項目・属性名（論理名および物理名、例: 登録項目種別 / `item_type`）                 |
| 種別             | 「業務分類」「コード表」「動的分類」のいずれか                                               |
| 正本参照（SSOT） | スキーマ参照（`schema_ref`）、型定義参照（`type_ref`）、または「なし（スタンドアロン定義）」 |
| 説明             | 分類が業務上果たす役割、導入の背景・目的                                                     |

### 5.2. 値の業務的意味と使い分けの要件

定義形態（正本参照の有無）および分類種別に応じて、以下の規約に従って記述する。

1. **スキーマまたは TypeScript 型を参照する場合（正本参照あり）**:
   - 値の一覧・識別子は参照先（SSOT）を正とし、本文で値そのものを再定義・再列挙しない。
   - 正本参照先（パスおよび識別子）を明記した上で、各値の「業務上の意味と使い分け」に絞って表を構成する。
   - 推奨表カラム: `値`（参照先に対応する識別子）、`分類名`（論理名/表示名）、`業務上の意味と使い分け`（選定基準・適用条件）。
2. **実装にない業務上の分類の場合（スタンドアロン定義）**:
   - 人が業務判断で区分する分類など、実装側に型定義が存在しない場合は、値の一覧をスタンドアロンで記述する。
   - 推奨表カラム: `値`（コード値）、`分類名`（正式名称）、`表示名`（UI表示名）、`説明・成立条件`（業務上の定義と選定ルール）。
3. **動的分類の場合**:
   - ユーザー定義の分類（タグ等）は固定の値一覧を持たないため、値一覧は記述しない。
   - 管理方式（BDD enum 禁止、マスタテーブル管理）、作成権限、命名規約、削除・アーカイブ方針を定義する。

## 6. 記述ガイド

### 6.1. 記述の基本方針

- **業務視点への特化**: 実装コードの enum や union 型を単にコピー＆ペーストするのではなく、「なぜその値が存在し、いつどの値を選択すべきか」という業務判断の基準を記述する。
- **重複の排除**: スキーマやコードから自明な情報（型の構文、単なる英単語の直訳）は記述しない。
- **整合性の維持**: 分類定義名や分類名は、用語集（glossary）および業務データ辞書（BDD）の論理名と完全に一致させる。

### 6.2. 正本参照の選定基準と記述方法

対象分類の実装・管理状況に応じて、次の3通りから選定する。

| 方式                                | 選定基準                                                                                                   | 正本参照（SSOT）の記述例                                                                     | 記述ルール                                                                                               |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **スキーマ参照（`schema_ref`）**    | JSON Schema / YAML Schema に enum 定義が存在し、物理制約の正本として管理されている場合                     | `schema_ref: docs/specdojo/schemas/v1/register-item-frontmatter.schema.yaml#/$defs/ItemType` | 値の一覧はスキーマを正とし、各値の業務上の意味・成立条件・使い分けのみを記述する。値の再列挙は行わない。 |
| **TypeScript 型参照（`type_ref`）** | ソースコード上に TypeScript の union 型や enum が定義されており、スキーマがない内部モデル・引数の場合      | `type_ref: src/register/register.ts#RegisterItemType`                                        | 値の一覧は TypeScript 型定義を正とし、コードから読み取れない業務上の使い分け・選定基準のみを記述する。   |
| **スタンドアロン定義（今の形）**    | 実装（スキーマやコード）に存在しない、人が業務判断で決める区分（例: 店舗運営上の棚割区分、施策カテゴリ等） | `なし（スタンドアロン定義）`                                                                 | 値、分類名、表示名、説明・成立条件の一覧をスタンドアロンで網羅して記述する。                             |

### 6.3. 分類種別別の扱い

#### 1. 業務分類（Business Classification）

- 業務ロジックに基づいて固定的に存在する分類（例: 商品区分、会員ランク）。
- 値は少数（通常3〜5個程度）で固定的。
- スキーマまたは TypeScript 型参照を用いるか、実装未着手時はスタンドアロン定義とする。

#### 2. コード表（System Code List）

- システム内で使用されるコード値の一覧（例: 都道府県コード、決済種別コード、税種別コード）。
- 値が多く（10以上）変更可能性がある場合はマスタテーブル管理を推奨する。
- システム連携や schema enum と対応する場合は `schema_ref` または `type_ref` を明記する。

#### 3. 動的分類（Dynamic Classification）

- ユーザーが業務画面等から自由に追加・編集・削除できる分類（例: 商品タグ、顧客グループラベル）。
- **BDD の enum にしてはならない**（値の動的変更に対応できず仕様が破綻するため）。
- CDT では値の一覧ではなく、管理方式（テーブル定義への委譲）、作成権限、命名規則、上限値などの運用規約を記述する。

### 6.4. BDD（業務データ辞書）との関係

| 分類種別 | BDD の扱い                   | CDT での記述内容                                     |
| -------- | ---------------------------- | ---------------------------------------------------- |
| 業務分類 | enum 可能                    | `schema_ref` / `type_ref` またはスタンドアロン値一覧 |
| コード表 | enum または マスターテーブル | `schema_ref` / `type_ref` による使い分け、または参照 |
| 動的分類 | enum 禁止、別テーブルで管理  | 値一覧は記載せず、管理ルール・作成権限を定義         |

### 6.5. 成果物の検証手順

作成・改訂した分類一覧 Markdown は、以下の手順で合否を確認する。

1. **Markdown 構文検証**:

   ```bash
   npm run lint:md
   ```

   - 期待結果: Markdown 構文規約違反（見出しレベル、表のフォーマット等）がないこと。

2. **Frontmatter 検証**:

   ```bash
   npm run lint:fm
   ```

   - 期待結果: Frontmatter のスキーマ検証に合格すること。

3. **カタログ整合検証**:

   ```bash
   npm run validate:catalog
   ```

   - 期待結果: 成果物カタログ（`dct-data-model-cdt.yaml`）で定義されたパス・成果物情報と整合していること。

## 7. 禁止事項

- **実装・スキーマ定義の機械的再掲の禁止**: `schema_ref` や `type_ref` を指定しているにもかかわらず、スキーマやコードに定義済みの値一覧や型定義をそのまま再掲・転記しない。
- **自明な言葉の言い換え・曖昧な説明の禁止**: 「`snack` はスナックのこと」「適切に選択する」といった、値の名称の単なる言い換えや判断基準のない曖昧な説明を記述しない。
- **動的分類の enum 化の禁止**: ユーザーが自由に追加・変更する動的分類を、BDD の enum や固定値一覧として固定化しない。
- **過剰な実装詳細の混入の禁止**: 物理テーブルの DDL、SQL クエリ、内部関数名などの過剰な実装詳細を記述しない。
- **規約違反の見出し記法**: 章番号なし見出し（`## 概要`）や章番号末尾のピリオド欠落（`## 1 概要`）を使用しない。
- **本文中へのリンク章・wikilink の記載禁止**: 本文中に sample / recipe / template へのリンク章や wikilink を置かない（対応関係は Frontmatter で宣言する）。

## 8. サンプル

完成例の正本は `specdojo:cdt-sample`（`docs/ja/specdojo/samples/cdt-sample.md`）を参照する。以下に、正本参照を用いた分類一覧の最小例を示す。

```markdown
# 商品区分

## 1. 概要

取扱商品の業務上の大分類と適用税率・保管基準を定義する。

## 2. 分類定義

| 定義項目         | 内容                               |
| ---------------- | ---------------------------------- |
| 対象エンティティ | 商品（`product`）                  |
| 分類定義名       | 商品区分（`product_type`）         |
| 種別             | 業務分類                           |
| 正本参照（SSOT） | `src/types/product.ts#ProductType` |
| 説明             | 商品の特性に応じた業務上の大分類   |

## 3. 値の業務的意味と使い分け

値の一覧は `src/types/product.ts#ProductType` を正本とする。

| 値      | 分類名 | 業務上の意味と使い分け                                                |
| ------- | ------ | --------------------------------------------------------------------- |
| `snack` | お菓子 | 間食用食品全般。賞味期限管理が必要で軽減税率（8%）対象。常温棚で保管  |
| `toy`   | 玩具   | 児童向け玩具類。賞味期限はなく標準税率（10%）対象。直射日光を避け陳列 |
| `drink` | 飲料   | 清涼飲料水類。賞味期限管理を行い軽減税率（8%）対象。冷蔵または専用棚  |
```
