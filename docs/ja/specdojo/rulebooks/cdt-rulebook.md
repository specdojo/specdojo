# 分類一覧 作成ルール

Code Table (CDT) Documentation Rules

業務上の分類（カテゴリ、種別、区分、コード値など）について、値を選ぶための意味・成立条件・判断境界を定義します。値・構文・構造の詳細はスキーマ・実装・リファレンスを正本として参照し、分類一覧（CDT）はそこから読み取れない業務判断を補います。

## 1. 全体方針

- **目的と適用範囲**: BDD の属性、画面選択肢、集計軸などに使う分類を Markdown で記述する。分類する対象と、利用者が何を判断するための区分かを明らかにする。
- **正本参照**: スキーマや実装に許容値がある場合は、その定義を正とする。CDT には各値の選定条件と隣接する値との境界を記述する。実装にない業務上の分類はスタンドアロンで定義し、動的分類は値を固定せず管理規約を定義する。
- **完成条件**: メタデータが共通標準・schema に適合し、分類定義と業務判断が「本文要件」を満たすこと。正本参照が解決でき、関連する BDD・用語・画面・ルールと矛盾しないことを「成果物の検証」で確認する。
- **確定と変更**: BA・PO が意味と区分方針、ARC・DEV が正本との対応、QE が境界の検証可能性を確認する。`ready` への昇格は人間が判断する。変更時は分類を利用する仕様と実装への影響を確認し、未解消の不整合を実行結果へ記録する。

## 2. 位置づけと用語定義

- **成果物の責務**: CDT は分類の選び方を担い、BDD は属性定義、用語集は共通の語義、画面仕様は表示・操作、ビジネスルールは詳細な業務規則を担う。状態遷移や承認の詳細も対応する仕様へ委ね、選定に必要な条件だけを残す。
- **分類種別**: 業務分類は業務判断に基づく区分、コード表はシステムや外部連携で識別するコードの体系、動的分類は利用者が運用中に値を追加・変更する区分を指す。件数だけで種別や管理方式を決めない。
- **正本参照とスタンドアロン定義**: 正本参照は許容値が確定するスキーマ・型・管理元への参照を指す。スタンドアロン定義は実装に値の定義がない業務区分を CDT 自体で定義する方式であり、既存の正本を読めない場合の代替ではない。

## 3. ファイル命名・ID規則

- **ID**: プロジェクト成果物は `<project-id>:cdt-<term>`（例: `prj-0001:cdt-register-type`）とする。`<term>` は分類の主題を表す英小文字の kebab-case とし、共通の文字制約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。
- **ファイル名と配置**: `cdt-<term>.md` とし、成果物カタログの `base_path` と `path` に従う。配置の共通方針は [[specdojo:docs-structure-guide|ドキュメント構成ガイド]] を正とする。
- **改訂と参照**: ID は同じ分類を追跡できるよう維持する。別文書で置き換える場合に限り `supersedes` で旧 ID を示す。既存の関連文書は project 修飾 ID の wikilink、未作成文書やソースコードはインラインコードで参照する。

## 4. 推奨 Frontmatter 項目

- 共通項目の必須・任意と意味は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]]、許可項目・型制約は `docs/specdojo/schemas/v1/deliverable-frontmatter.schema.yaml` を正本とする。CDT 固有のメタデータ項目は追加しない。
- `specdojo` 配下の `type` は `data`、`rulebook` は `specdojo:cdt-rulebook` とする。新規作成時の `status` は `draft` とする。
- 文書名は本文先頭の H1 に記載し、`specdojo.title` は追加しない。`schema_ref`・`type_ref` は本文の正本参照欄で使用する表記であり、Frontmatter の項目ではない。

最小メタデータ例:

```yaml
---
specdojo:
  id: prj-0001:cdt-register-type
  type: data
  status: draft
  rulebook: specdojo:cdt-rulebook
---
```

## 5. 本文要件

本文は次の章を基本とする。H1 は文書名だけに用い、`##`〜`####` の見出しには階層ごとの連番と末尾のピリオドを付ける（例: `### 3.1.`、`#### 3.1.1.`）。任意章を省略した場合も章番号を飛ばさない。

| 章タイトル               | 必須 | 目的・内容要件                                                                                      |
| ------------------------ | ---- | --------------------------------------------------------------------------------------------------- |
| 概要                     | ○    | 業務目的、対象エンティティ、適用範囲、主担当・利用者とその判断を示す                                |
| 分類定義                 | ○    | 対象エンティティ、分類定義名、種別、正本参照、説明を表形式で特定する                                |
| 値の業務的意味と使い分け | ○    | 正本参照あり・スタンドアロン・動的分類の方式に応じて、選定条件と境界または管理規約を示す            |
| 関連仕様との関係         | 任意 | BDD・画面・業務ルール・状態定義などへの参照と、分類の利用先・変更影響を示す。概要等で明確なら省略可 |

### 5.1. 分類定義の要件

「定義項目」「内容」の 2 列の表に、次の項目を置く。複数の分類軸を扱う場合は、軸ごとに定義と説明の対応を識別できるようにする。

| 定義項目         | 内容                                                                                               |
| ---------------- | -------------------------------------------------------------------------------------------------- |
| 対象エンティティ | 分類される業務上の対象。BDD にある場合は論理名・物理名を合わせる                                   |
| 分類定義名       | 分類軸を表す論理名と属性名。エンティティ名だけで代用しない                                         |
| 種別             | 業務分類・コード表・動的分類のいずれか                                                             |
| 正本参照（SSOT） | スキーマのパスと定義位置、型のパスと識別子、動的分類の管理元、または「なし（スタンドアロン定義）」 |
| 説明             | その区分で分ける業務上の判断と目的                                                                 |

### 5.2. 値の業務的意味と使い分けの要件

| 定義方式       | 必須内容                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 正本参照あり   | 正本に対応する識別子を行のキーとして、各値の意味・選定条件・使い分けを記す。値だけの一覧や enum・union 型の転記は置かない |
| スタンドアロン | 値・分類名・表示名・説明と成立条件を定義する。表示名が分類名と同じ場合は同じであると分かる形で示す                        |
| 動的分類       | 値一覧を固定せず、管理元、作成・変更権限、命名規約、削除・アーカイブ時の扱いを示す。属性や参照関係の構造は BDD に委ねる   |

## 6. 記述ガイド

共通事項は上位のメタ情報標準・文書構成ガイド、共通の語義は用語集を正本とし、各章で再定義しない。以下の例は判断基準を示す部分例である。

### 6.1. 概要

- **判断基準**: 誰がどの場面で何を選ぶための分類かを示す。対象外の判断は正本となる仕様へ委ねる。
- **良い例**: 「起票者が、すでに起きた問題と未発生の懸念を分けて追跡するための分類を定義する。状態遷移は状態定義を参照する。」
- **悪い例**: 「登録項目の分類を適切に管理する。」目的・利用者・判断の境界が分からない。

### 6.2. 分類定義

正本は次の基準で選び、参照先のファイルと定義位置を確認する。スキーマと実装が併存する場合は許容値の正本を一つ指定し、他方は対応確認先として区別する。

| 参照方式       | 選定基準                                         | 正本参照欄の良い例                                                                           |
| -------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| スキーマ参照   | 許容値をスキーマで管理している                   | `schema_ref: docs/specdojo/schemas/v1/register-item-frontmatter.schema.yaml#/$defs/ItemType` |
| 型参照         | スキーマがなく、ソースの型で許容値を管理している | `type_ref: <path>#<TypeName>` の形で実在するパスと型識別子を示す                             |
| スタンドアロン | 実装に定義がなく、人が業務判断に使う区分である   | `なし（スタンドアロン定義）` とし、その区分を判断する主体を説明する                          |
| 動的分類       | 利用者が運用中に分類値を増減する                 | 管理元となる BDD のエンティティを参照し、値を確定するマスタの所在を示す                      |

- **判断基準**: 分類種別と参照方式は別に判断する。固定の業務分類・コード表は正本の有無で参照方式を選び、動的分類は固定 enum にせず管理元を参照する。
- **良い例**: 分類定義名を「分類（`item_type`）」とし、スキーマの `ItemType` を正本、CLI の検証定義を対応確認先として示す。
- **悪い例**: 属性を特定せず「登録項目」とだけ書く、または「ソースコード参照」とだけ書く。分類軸や参照先を解決できない。

### 6.3. 値の業務的意味と使い分け

#### 6.3.1. 正本参照あり

- **判断基準**: 正本の各値に業務上の説明が対応し、混同しやすい値を条件で区別できること。識別子は説明との対応付けに用い、許容値を独立して再定義しない。
- **推奨表**: `値`（正本に対応する識別子）、`分類名`（業務上の名称）、`業務上の意味と使い分け`（選定条件・隣接値との境界）。名称は関連 BDD・用語集と同じ対象を指すように合わせる。
- **良い例**: 「`issue` はすでに起きている問題。まだ起きていない懸念には `risk` を使う。」
- **悪い例**: 「`issue` は課題、`risk` はリスク。」名称の言い換えだけでは選定できない。

#### 6.3.2. スタンドアロン定義

- **判断基準**: 正本を CDT 自体が担うため、識別可能な値と判断条件を揃える。条件が重なる場合は優先順位や例外を明らかにする。
- **推奨表**: `値`（コード）、`分類名`（正式名称）、`表示名`（利用者向け名称）、`説明・成立条件`（選定条件）。
- **良い例**: 「`experimental`／試験商品／お試し: 店主が新規取扱を試す区分。入荷後30日間の売れ行きで定番化を判断する。」
- **悪い例**: 「`experimental`／その他／その他: 適宜使用する。」適用条件と判断主体を特定できない。

#### 6.3.3. 動的分類

- **判断基準**: 利用者が値を追加・変更できることを前提に、作成権限と既存参照の扱いを判断できる規約にする。件数の大小で固定 enum 化しない。
- **良い例**: 「店主がタグを追加する。使用済みタグは削除せずアーカイブし、新規付与だけを停止する。」管理元の属性定義は BDD を参照する。
- **悪い例**: 現在のタグを BDD の enum として列挙する。運用中に追加される値を表現できない。

### 6.4. 関連仕様との関係

- **判断基準**: 参照する文書と、どの属性・判断に分類を使うかを対にする。税率・状態遷移・承認・コマンド構文などの詳細は各正本へ委ねる。
- **良い例**: 「業務データ辞書の `item_type` に対応する。分類別の終端・承認者は状態定義を参照する。」文書名は実在する文書の wikilink として記述する。
- **悪い例**: 関連文書名だけを並べる、または状態遷移表や CLI オプション一覧を転記する。利用関係を示せないか、正本との二重管理になる。

### 6.5. 成果物の検証

1. **構造とメタデータ**: リポジトリの検査設定に従い Markdown・Frontmatter を検証する。期待結果は見出し・表の違反や未定義メタデータがないこと。カタログ管理下では ID・パス・rulebook 宣言との一致も確認する。
2. **参照と対応**: 正本のファイル・定義位置を解決し、各許容値に業務上の説明があり、正本にない値を許容していないことを照合する。CLI 等の検証値を併記する場合は正本と同じ集合か確認し、不一致は実行結果へ残す。
3. **業務判断と影響**: 混同しやすい値の条件、スタンドアロン分類の重複・漏れ、動的分類の権限・参照保持を確認する。変更時は BDD・画面・業務ルール・関連実装の利用箇所を辿り、意味や表示との不整合がないことを確認する。

## 7. 禁止事項

- **正本の再掲**: 値だけの一覧、enum・union 型、型制約、コマンド構文、状態遷移表の転記を置かない。説明表の識別子は「値の業務的意味と使い分けの要件」に従う。
- **判断できない説明**: 名称の直訳や「適切に選ぶ」だけで条件を済ませない。根拠のない値数の目安を分類種別・管理方式の必須条件にしない。
- **責務の混同**: 動的分類を固定 enum 化しない。分類の業務判断に寄与しない DDL・SQL・内部関数の詳細を混入しない。
- **共通規約違反**: 未定義の Frontmatter 項目、番号なし見出し、章番号末尾のピリオド欠落を使用しない。
