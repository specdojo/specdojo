# プロジェクト管理計画: 駄菓子屋きぬや 販売管理システム

## 1. 管理目的と適用方針

店主代表と家族利用者代表が同じ手順で販売・在庫・つけを記録・確認でき、日々の記録を無理なく続けられることを検証する。管理対象は初期リリースの準備から2週間の店頭試用終了までとし、中長期の効果測定は運用前に基準値を準備し、運用後の観測・比較を継続判断で後続作業へ引き継ぐ。

価値と単一店舗・タブレット1台の前提は [[specdojo:prj-overview-sample|プロジェクト概要]]、対象業務と期間は [[specdojo:prj-scope-sample|プロジェクトスコープ]]、判定条件は [[specdojo:prj-success-criteria-and-acceptance-criteria-sample|成功基準と受入条件]]（以下「成功条件」）、費用・参加負荷と見直し条件は [[specdojo:pm-organization-sample|組織定義]] を正本とし、成功条件の数値・測定方法を本書で再定義しない。

兼務体制で判断待ちと参加負荷を把握できるよう、統合表と判断ゲートによる軽量プロファイルを採用する。外部契約、有償運用、複数店舗化の提案時は、`PM` が費用・技術依存・責任への影響を整理し、人間の `PO` が個別計画を足す拡張プロファイルへの移行を判断する。

各条件の合否・測定方法は成功条件を正とする。SC-02〜SC-06 は初期受入の合否に混ぜず、測定期間が来る前に合格扱いにしない。

## 4. 正本・報告・見直し

### 4.1. 更新先と報告

`kinuya-` で始まる記録は未同梱の架空記録とする。未整備なら整備を先行タスクとし、口頭合意でゲートを通さない。

| 情報                         | 正本と整備                                                                                                                                                                    | 更新・報告契機                             | 主な確認者                |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ | ------------------------- |
| 目的・範囲・条件             | 「管理目的と適用方針」の正本                                                                                                                                                  | 基準変更時、ゲート前に `BA` が提示         | `PO`、`QE`                |
| 作業順序・Task owner・進捗   | `kinuya-schedule`（`PM`）。U-03 決定後に基準日を確定                                                                                                                          | 週次、節目、遅延・依存変更時               | `PM`                      |
| 成果物・主要判断の責任       | [[specdojo:pm-raci-sample\|RACI]]                                                                                                                                             | 成果物追加、承認責任変更時                 | `PM`、`PO`                |
| Role・実行主体・兼務         | [[specdojo:pm-roles-sample\|ロール定義]]、[[specdojo:pm-members-sample\|メンバー定義]]                                                                                        | 参加・離脱・交代、兼務負荷変化時           | `PM`、`PO`                |
| 課題・リスク・変更・決定     | [[specdojo:pm-issue-log-sample\|課題ログ]]、[[specdojo:pm-risk-register-sample\|リスク登録簿]]、[[specdojo:pm-change-request-log-sample\|変更要求ログ]]。決定は該当記録に付記 | 発生・状態変更時、判断期限前               | `PM`、判断する人間の Role |

承認責任は Schedule の `owner` でなく RACI を正とする。

### 4.2. 運用前の準備

`PM` は次の作業を `kinuya-schedule` に置く。在庫の無駄の定義は概要の「期待効果」と SC-05 に従う。

| 条件  | 先行作業と依存                                                                                    | 作業時間の仮見積もり   | 完了の証跡（`kinuya-trial-log`）                                             |
| ----- | ------------------------------------------------------------------------------------------------- | ---------------------- | ---------------------------------------------------------------------------- |
| SC-04 | `PO` が対象商品を確定 → `BA` が運用開始前1か月の日次欠品を採取 → `QE` が照合                      | `BA` 4時間、`QE` 1時間 | 対象商品・営業日別の記録、欠測の確認結果、照合日・確認者                     |
| SC-05 | `BA` が運用開始前1か月の廃棄・値引き・長期滞留の数量・金額を採取 → 月次集計と年換算 → `QE` が照合 | `BA` 4時間、`QE` 1時間 | 対象月の原記録、月次集計、年換算値と算定根拠、欠測の確認結果、照合日・確認者 |

_ASSUMPTION_: 時間は初期見積もりで、1か月の採取期間とは別に扱う。`PM` の依存・リスク整備は両条件で計1時間とし、M-04 の見積もりに含める。既存記録で対象月を確認できなければ、採取期間を確保して U-03 の候補日を組み直す。

`PM` は比較期間を失うリスクを条件 ID ごとに登録し、採取担当・期間の事前確保と週次の欠測確認で軽減する。基準値がそろわなければ `PO` が試用開始の延期か測定条件の変更を判断する。

### 4.3. 変更時の追従

目的、範囲、条件、上限、体制、外部条件が変わったら、`PM` が変更 ID に影響先を結び、担当・期限・確認担当付きの追従タスクを次の順で作る。追従は影響する作業の開始前に終える。

| 変更の例                           | 更新順序と担当                                                                                                       | 完了の確認                                            |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 在庫機能の追加や条件変更           | `PO` の範囲判断 → `BA` のスコープ・成功条件 → `DEV` の設計・実装影響 → `QE` の品質計画・試験 → `PM` の基準・Schedule | `QE` が条件 ID・対象版の再確認を照合し、`PO` が再判定 |
| 承認担当の交代、兼務での滞留       | `PM` が組織定義の見直しを起案 → `PO` が採用・使用可否を判断 → `PM` がロール・メンバー定義、RACI、Schedule を更新     | `QE` がゲートの判断者、RACI、引き継ぎ先を照合         |
| 上限・試用日・端末や接続条件の変更 | `DEV` が技術依存、`BA` が利用者影響、`PM` が費用・負荷を評価 → `PO` が判断 → 各正本と Schedule・基準へ反映           | `QE` が影響条件の再確認と旧版参照の解消を照合         |
