# プロジェクト管理計画: 駄菓子屋きぬや 販売管理システム

## 1. 管理目的と適用方針

店主代表と家族利用者代表が同じ手順で販売・在庫・つけを記録・確認でき、日々の記録を無理なく続けられることを検証する。管理対象は初期リリースの準備から2週間の店頭試用終了までとし、中長期の効果測定は継続判断で後続作業へ引き継ぐ。

価値と単一店舗・タブレット1台の前提は [[specdojo:prj-overview-sample|プロジェクト概要]]、対象業務と期間は [[specdojo:prj-scope-sample|プロジェクトスコープ]]、判定条件は [[specdojo:prj-success-criteria-and-acceptance-criteria-sample|成功基準と受入条件]]（以下「成功条件」）を正本とする。成功条件の数値・測定方法を本書では再定義しない。

兼務体制で判断待ちと参加負荷を把握できるよう、統合表と判断ゲートによる軽量プロファイルを採用する。外部契約、有償運用、複数店舗化を提案する場合は、`PM` が費用・技術依存・責任への影響を整理し、人間の `PO` が範囲変更と個別計画を追加する拡張プロファイルへの移行を判断する。

責任境界は [[specdojo:pm-organization-sample|組織定義]] に従う。AI Agent は草案、記録整理、実装、検証を支援し、費用・時間上限、範囲、優先順位、例外、受入、公開・継続は人間の `PO` が判断する。兼務でも作業結果と承認記録を分ける。

## 3. 判断ゲートとエスカレーション

| ゲート                     | 判断条件                                                                                                                                                                             | 判断材料                                                                | 起案・整理                          | 最終判断    | 証跡                                                            |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- | ----------------------------------- | ----------- | --------------------------------------------------------------- |
| 準備着手                   | U-01・U-02 が決定済みで、対象作業の支出・時間見込みが承認上限内。U-03 の候補日と担当の参加可能日が整合する                                                                           | 上限承認、参加者別見積もり、Schedule の依存・候補日                     | `PM`                                | 人間の `PO` | `kinuya-cost-and-effort-log` の承認記録と Schedule の候補日     |
| 初期リリース・店頭試用開始 | 成功条件 SC-01 と AC-01〜AC-04 の全条件が合格。M-03・M-04 が上限内で、実運用開始前の未決事項が解消している                                                                           | 条件 ID ごとの受入結果、対象版、支出・作業記録、未達・未決一覧          | `QE`、`PM`                          | 人間の `PO` | `kinuya-acceptance-record` の合否と公開可否の判断、根拠、判断日 |
| 店頭試用後の継続           | 成功条件 SC-02・SC-03 が合格し、保守・引き継ぎの担当と負荷を引き受けられる。SC-04〜SC-06 は所定時期の後続観測を割り当てる                                                            | 2週間の営業日別記録、追加操作時間、保守実績、利用者所感、後続観測タスク | `BA`、`PM`（`QE` が条件結果を照合） | 人間の `PO` | `kinuya-trial-log` の条件結果・継続／停止判断・改善先の課題 ID  |
| 重大変更・再開             | M-01〜M-09 の基準を変える場合、価値・条件 ID・支出・作業時間・継続負荷・試用日への影響と代替案を確認し、変更内容と再確認条件を承認できる。停止からの再開は是正・再確認の証跡がそろう | 変更要求、縮小／延期／中止案、影響条件と対象版、再計画                  | `PM`                                | 人間の `PO` | 変更要求ログの変更 ID・判断者・理由・判断日と追従タスク         |

SC-02〜SC-06 を初期受入の合否に混ぜず、測定期間が来る前に合格扱いにしない。各条件の合否・測定方法は成功条件を正とし、品質管理計画は確認方法と是正の運用に用いる。

必須条件の未達または証跡不足では、`QE` が条件 ID、対象版、不足材料、是正内容、再確認日を受入記録へ残し、`PM` が担当と依存を Schedule に追加する。人間の `PO` は該当ゲートを保留し、是正後の再判定で通過可否を決める。本例では必須条件を免除する例外を設けない。範囲・基準の変更が必要なら変更要求として先に承認し、旧条件の未達結果も保持する。

上限超過の見込み、主要操作不能、記録の不整合、個人情報・公開適性への重大な懸念があれば、担当 Role は影響する作業・利用を止めて `PM` へ報告する。`PM` は影響、保留対象、代替案、判断期限を整理し、次の支出・利用・公開より前に人間の `PO` へ判断を求める。再開は是正と再確認の証跡をそろえてから行う。

### 4.2. 変更時の追従

目的、範囲、成功条件、費用・時間上限、体制、外部条件が変わったら、`PM` は変更 ID に影響先を結び、次の順で追従タスクを作る。各タスクには担当 Role、依存先、見積もり、期限、確認担当を付ける。

| 変更の例                           | 更新順序と担当                                                                                                                               | 完了の確認                                                                      |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 在庫機能の追加や条件変更           | `PO` の範囲判断 → `BA` のスコープ・成功条件更新 → `DEV` の設計・実装影響確認 → `QE` の品質計画・試験更新 → `PM` の基準・Schedule 更新        | `QE` が変更 ID と条件 ID、対象版、再確認結果を照合し、`PO` がゲートを再判定する |
| 承認担当の交代、兼務での滞留       | `PM` が組織定義の見直しを起案 → 採用・使用可否変更は `PO` が判断 → `PM` がロール・メンバー定義、RACI、Schedule を順に更新                    | `QE` がゲートの判断者、RACI、未完了タスクの引き継ぎ先を照合する                 |
| 上限・試用日・端末や接続条件の変更 | `DEV` が技術依存、`BA` が利用者影響、`PM` が費用・負荷・依存を評価 → `PO` が変更を判断 → 各担当が正本を更新し、`PM` が Schedule と基準へ反映 | `QE` が影響条件の再確認と旧版参照の解消を確認する                               |

文書の置き換え・廃止は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、`PM` が参照元と移行期限を管理する。未完了の追従は課題 ID と担当 Role を付けて管理簿へ残し、影響する作業の開始前までに終える。
