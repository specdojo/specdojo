# 前提・制約・依存関係: 駄菓子屋きぬや 販売管理システム

本書は、駄菓子屋きぬやの初期リリース準備から店頭試用までに、作業の開始・保留・再判断に使う前提、制約、依存を整理する完成例である。未確認の条件と受領済みの判断を分け、各項目 ID から確認責任、影響作業、変更記録を追跡する。

## 1. 前提条件

対象業務と単一店舗の境界は [[specdojo:prj-scope-sample|プロジェクトスコープ]] の「対象業務」「スコープ外」を正とする。ここでは、それを実行する際に確認が必要な条件だけを登録する。

## 2. 制約事項

対象外と業務判断の境界は [[specdojo:prj-scope-sample|プロジェクトスコープ]] の「対象システム」「スコープ外」「境界の判断基準」へ委譲する。以下は [[specdojo:prj-charter-sample|プロジェクト憲章]] の「主要前提・制約」が結論だけを示す支出・公開情報の制約に、監視と逸脱時対応を補ったものである。憲章の GO / Not GO 判断ゲートは再登録しない。

| ID      | 内容                                                                                       | 適用範囲                       | 影響                                                                 | 監視・確認方法                                                                                               | 逸脱のトリガー                                                   | 所有者           | 対応方針                                                                                                                               |
| ------- | ------------------------------------------------------------------------------------------ | ------------------------------ | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| ACD-C02 | 費用上限は _UNDECIDED_: 管理計画 U-01 で店主代表が承認する。承認前に外部支出を開始しない。 | 機材購入、有償利用、外部契約   | 未承認の支出と継続費用が発生し、準備・開発の計画を維持できなくなる。 | 開発担当が購入・契約・有償利用の開始前に `kinuya-cost-and-effort-log` の上限・対象支出・承認証跡を照合する。 | 上限未承認、または対象支出の承認証跡がないまま着手しようとした。 | 開発担当（`PM`） | 着手を保留し、必要額・継続負担・無償代替を店主代表へ提示する。実施済みなら課題として影響と是正案を報告する。                           |

| ------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

## 4. 影響評価と対応方針

| 変化の種別       | 主な影響領域                           | 最初に確認すること                                                  | 一次対応・判断                                                                                   | 対応方針                                                                                     |
| ---------------- | -------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| 前提が崩れた     | 受入日程、記録品質、操作確認の有効性   | ACD-A01・A02 の変化が、どの操作確認・記録に及んだか                 | 開発担当が操作確認・試用結果、接続記録と影響作業を調べ、家族利用者代表へ店番への支障を確認する。 | 軽減案として確認日程・操作手順を見直す。受入・試用開始日の変更は店主代表が再判断する。       |
| 制約に抵触した   | 支出、公開適性、後戻り作業             | ACD-C02・C03 の抵触が未実施か実施済みか、影響する契約・公開物は何か | 開発担当が対象行為を止め、是正と影響確認を課題にする。                                           | 原因を除去し、承認証跡または公開前の再レビューをそろえる。再開・公開は店主代表が判断する。   |
| 依存先が変化した | 設計の確定、受入、店頭試用の開始・継続 | ACD-D01〜D04 の未成立部分、影響する対象版・条件 ID・作業            | 所有者が不足材料と回復見込みを特定し、開発担当が代替案と残作業の見積もりをまとめる。             | 代替策で軽減するか順序・期日・範囲を再判断する。店主代表の判断後に計画と受入対象を更新する。 |

作業順序・判断ゲートは [[specdojo:pm-plan-sample|プロジェクト管理計画]] を正とする。開発担当（`PM`）は変更記録から対象文書 ID、ACD 項目 ID、影響する条件 ID を結び、是正・再確認・再判断の順に `kinuya-schedule` へ担当 Role、依存先、見積もり、期限、確認担当を置く。

## 5. 監視・変更管理

### 5.1. 見直し契機と記録

開発担当（`PM`）は週次の進捗確認に加え、スコープ・憲章・受入条件の改訂、参加不可の申出、通信断・端末交換、支出・公開の提案、助言・決定の受領、各判断ゲートの準備開始時に本書を確認する。

変更記録には文書 ID と項目 ID、変化内容、影響する作業・条件 ID、一次対応者、判断者、判断根拠、対応状況、再確認時期、転送先の記録 ID を残す。ACD-C01 の廃止理由と参照への統合も同じ記録で追跡する。

本例では意思決定待ちの ACD-D03 をプロジェクト登録簿の `PJR-KN01` に登録した想定とする。`PJR-KN01` と `kinuya-project-register` は未同梱の架空の項目・記録名であり、実際の登録・承認の証跡ではない。`kinuya-schedule`、`kinuya-technical-dependency-log`、`kinuya-cost-and-effort-log`、`kinuya-acceptance-record` も未同梱で、[[specdojo:pm-plan-sample|プロジェクト管理計画]] の記録先を使う例である。実案件では各記録の整備を先行作業にし、証跡が参照できるまで成立扱いにしない。

### 5.3. 追従と責任

責任境界は [[specdojo:pm-organization-sample|組織定義]] に従う。開発担当（`PM`）が計画・Schedule・PJR の追従を管理し、`ARC` が文書構造・配置・命名・技術制約・参照の整合を支援、`QE` が受入条件と再確認結果を照合する。実行主体と兼務は [[specdojo:pm-members-sample|メンバー定義]] で管理する。専門支援を独立した Schedule の作業にする場合は、組織定義で `owner` の使用可否を見直す。

店主代表（人間の `PO`）が範囲・費用・公開・受入・運用継続を最終判断する。AI Agent に承認を委ねない。文書の置き換え・廃止と参照元への追従は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従い、開発担当（`PM`）が移行期限と未完了作業を追跡する。
