# 駄菓子屋きぬや 要求と仕様の対応（第 1 リリース）

## 1. 目的と適用範囲

本書は、仕様成果物の `relations.satisfies` から生成した派生ビューであり、表を手で直さない。2026 年度第 1 リリースで扱う会計・在庫・値引き・監査の要求と、それを充足する仕様の対応を示す。仕様がない要求を残したまま作り始めると、店主不在の店番で会計や在庫の記録が食い違っても気づけず、店主の記憶に頼る運用へ戻ってしまう。本書はその要求漏れと、どの要求にも結びつかない仕様漏れを仕様レビューの時点で見つけるために使う。

次の表は、本書を使う場面と、その場面で本書から確かめることの対応を示す。

| 使う場面                    | 使う人                     | 本書で確かめること                                              |
| --------------------------- | -------------------------- | --------------------------------------------------------------- |
| 第 1 リリースの仕様レビュー | 開発担当・同行レビュー担当 | 対応仕様が `なし` の要求、どの要求にも対応しない仕様            |
| 要求・仕様の変更判断        | 店主代表・開発担当         | 変更する要求 ID に結びつく仕様 ID と、充足状況が下がる要求      |
| 第 1 リリースの範囲の確認   | 店主代表                   | `充足` でない要求が会計・在庫・値引き・監査のどれに残っているか |
| ギャップの登録簿への転記    | 開発担当                   | 「ギャップと対応方針」の各行と、直す生成元の成果物              |

対象外は次のとおり。

- 次期リリースの要求（`req-r2-*`、つけ管理と仕入れ）: 第 1 リリースの範囲確認に使わず、要求一覧がまだ版を固めていないため。
- 非機能要求の数値目標（`nfr-*`）: 母集団とする要求一覧 `req-2026-r1` は機能要求だけを持ち、数値目標の充足は各 `nfr-*` で扱うため。`req-r1-004` のように非機能要求と関わる行は、ギャップに依存先の文書 ID を書く。

## 2. トレース対象の前提

- 要求の母集団（4 件）: 要求一覧 `req-2026-r1` が定める要求項目 `req-r1-001`〜`req-r1-004`。
- 仕様の抽出範囲: 会計・在庫・値引き・監査の領域にあるシステム化機能 `sf-*`、業務仕様 `bes-*`、外部 IF 仕様 `ifx-*`（7 件）。業務受入条件 `bac-*` は要求側の成果物であり、仕様として抽出しない。
- トレース単位: 1:N（1 要求に複数の仕様を対応させる）。
- 生成の手段と生成日: 生成コマンドがないため、rulebook の「生成の手順」による手作業で 2026-05-08 に生成した。
- 生成元の版: `main` の `7c41e9d`。
- 確認の手順: 同じ版で「生成の手順」をたどり、マトリクス・要求に対応しない仕様・サマリの件数が本書と一致することを照合する。差分があれば生成元を確かめ、本書を直さずに再生成する。

本書が参照する要求一覧と仕様文書は、いずれも未同梱の架空参照名である。

## 3. トレースマトリクス

次の表は、母集団の要求ごとに、その要求 ID を `relations.satisfies` に持つ仕様と充足状況の対応を示す。

| 要求ID     | 要求要約                         | 対応仕様ID                          | 充足状況 | ギャップ                                                                                                         | 備考                                                      |
| ---------- | -------------------------------- | ----------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| req-r1-001 | レジ会計を 90 秒以内で完了する   | sf-pos-checkout, bes-pos-operation  | 充足     | なし                                                                                                             | `sf-pos-checkout`: `ready`, `bes-pos-operation`: `ready`  |
| req-r1-002 | 在庫引当をリアルタイムで更新する | bes-stock-allocation, ifx-msg-stock | 一部充足 | _UNDECIDED_: 在庫メッセージ送信失敗時の再送条件と重複排除条件                                                    | `bes-stock-allocation`: `ready`, `ifx-msg-stock`: `draft` |
| req-r1-003 | キャンペーン値引きを適用する     | sf-discount-apply                   | 充足     | なし                                                                                                             | `sf-discount-apply`: `ready`                              |
| req-r1-004 | 監査ログを 1 年保持する          | なし                                | 未着手   | `bes-audit-log` が `relations.satisfies` に req-r1-004 を持たない。_UNDECIDED_: 保持先（依存先 `nfr-integrity`） | `bes-audit-log`: `draft`、`relations.satisfies` は空      |

次の表は、`relations.satisfies` が空か、母集団の要求 ID を 1 つも持たない仕様を示す。

| 仕様ID             | `relations.satisfies` の宣言 | ギャップ                                                                              |
| ------------------ | ---------------------------- | ------------------------------------------------------------------------------------- |
| bes-product-master | 空                           | 商品マスタの登録・改廃に対応する要求が `req-2026-r1` になく、要求漏れか対象外かが不明 |
| bes-audit-log      | 空                           | 監査ログの記録内容を定めるが、対応する req-r1-004 を宣言していない                    |

## 4. 充足状況サマリ

次の表は、トレースマトリクスから数えた充足状況ごとの件数を示す。合計は母集団の 4 件と一致する。

| 充足状況             | 件数 |
| -------------------- | ---- |
| 充足                 | 2    |
| 一部充足             | 1    |
| 未着手               | 1    |
| 合計                 | 4    |
| 要求に対応しない仕様 | 2    |

優先して解消する要求と理由は次のとおり。

1. `req-r1-004`: 監査ログを残せないと、販売記録の訂正や取消をあとから照合できず、店主不在の店番で起きた誤りを追えない。
2. `req-r1-002`: 在庫メッセージの再送条件が決まらないと、通信が途切れた会計で在庫が二重に減るか減らないままになり、人気商品の欠品につながる。
3. `bes-product-master`: 商品マスタは会計・在庫の前提であり、対応する要求がないまま第 1 リリースの範囲に入っている。

## 5. ギャップと対応方針

解消は本書でなく生成元の成果物で行う。次の表は、ギャップごとに直す成果物と、再生成した本書で解消と判定する条件の対応を示す。

| 対象               | ギャップ                       | 直す生成元の成果物と直し方                                                                                                                                   | 解消の判定条件                                                                      |
| ------------------ | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| req-r1-002         | 再送条件と重複排除条件が未決定 | `ifx-msg-stock` に送信失敗時の再送条件と重複排除条件を追記し、`ready` にする                                                                                 | 再生成で req-r1-002 が `充足` になり、ギャップが `なし` になる                      |
| req-r1-004         | 対応仕様がなく、保持先が未決定 | `nfr-integrity` で保持先を決めたうえで、`bes-audit-log` に保持方針を追記し、`relations.satisfies` に req-r1-004 を持たせる                                   | 再生成で req-r1-004 の対応仕様が `bes-audit-log` になり、`一部充足` 以上になる      |
| bes-product-master | 対応する要求がない             | 要求一覧 `req-2026-r1` に商品マスタの要求を追加し、`bes-product-master` の `relations.satisfies` に持たせる。対象外とするなら第 1 リリースの抽出範囲から外す | 再生成で母集団が 5 件になり、要求に対応しない仕様から `bes-product-master` が消える |

担当と期限は各行を PJR 登録候補として登録簿で追跡し、本書には持たない。実案件の PJR 個票は未同梱である。

## 6. 変更履歴と更新ルール

次のいずれかが起きたら、本書を直さずに「生成の手順」で再生成し、生成日と生成元の版を改める。再生成後は、「トレース対象の前提」の確認の手順で照合する。

- 要求一覧 `req-2026-r1` で要求項目が追加・削除された。
- 抽出範囲の仕様が追加された、または仕様の `relations.satisfies` が変わった。
- 対応仕様の `status` が変わった。

次の表は、生成ごとの版と、前回から充足状況が変わった要求の対応を示す。

| 生成日     | 生成元の版 | 前回から充足状況が変わった要求 ID | 契機                                          |
| ---------- | ---------- | --------------------------------- | --------------------------------------------- |
| 2026-05-08 | `7c41e9d`  | `req-r1-003`: `一部充足` → `充足` | `sf-discount-apply` の `status` を `ready` へ |
| 2026-04-24 | `e2b6f18`  | なし（初回生成）                  | 第 1 リリースの仕様の作成                     |
