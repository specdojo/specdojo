# リスク登録簿 サンプル

## 1. 概要

駄菓子屋きぬや 販売管理システム構築で、準備着手から2週間の店頭試用終了までに顕在化しうるリスクを、初期受入・店頭試用の期日と成功条件への影響で評価・対応・監視する。記録単位はリスク 1 件 1 行（`RK-NNN`）とし、毎週の見直しと兆候・期限超過の発生時に該当行を更新する。記載は 2026-04-09 時点である。

本書はプロジェクト登録簿を使わない単独のリスク登録簿の例である。登録簿を使う場合はリスクを `item_type: risk` の個票に書き、`register build` が個票から生成する `pm-risk-register.md` は直接編集しない。

次の表は、登録したリスクごとに、評価の結果と採る対応策、担当とステータスを示す。優先度とステータスは登録簿の `priority`・`item_status` の値で書く。

| リスクID | 内容                                                                                        | 発生確率 | 影響度 | 優先度   | 対応策                                                                 | 担当  | ステータス    |
| -------- | ------------------------------------------------------------------------------------------- | -------- | ------ | -------- | ---------------------------------------------------------------------- | ----- | ------------- |
| RK-001   | 下校後の来店集中で会計の記録が追いつかず、販売記録の漏れが出る                              | 中       | 高     | `high`   | 来店集中を模した連続会計を受入前に試し、記録が追いつかない操作を見直す | `DEV` | `in-progress` |
| RK-002   | 店主代表と家族利用者代表の参加可能日が合わず、初期受入の確認が遅れる                        | 高       | 中     | `high`   | 初期受入の確認日を候補日の確定時に2日分押さえ、両代表に了承を得る      | `PM`  | `open`        |
| RK-003   | 店頭のタブレット1台が故障・充電切れになり、その日の販売・在庫・つけを記録できない           | 低       | 高     | `medium` | 紙の記録票で代替し、復旧した営業日に入力する                           | `OPS` | `open`        |
| RK-004   | レシート文言の店主代表の確認が遅れ、受入対象の版が固まらない（2026-04-04 に課題へ移管済み） | 高       | 中     | `high`   | 課題 IS-002 で追跡する                                                 | `PM`  | `done`        |

## 3. 評価基準

### 3.1. 発生確率と影響度の判定条件

発生確率と影響度は、それぞれ次の条件で 3 段階に判定する。影響度は、遅れ・品質・後続成果物のうち最も重い観点で決める。

| 段階 | 発生確率の判定条件                                      | 影響度の判定条件                                                                                        |
| ---- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 高   | 兆候がすでに出ている、または同じ事象が準備中に起きた    | 店頭試用の開始が1週間以上遅れる、SC-01・SC-02 を満たせない、または受入済みの成果物の作り直しが要る      |
| 中   | 兆候はないが、前提条件の範囲で起こりうる                | 遅れが準備期間の予備（2 営業日）を超え1週間未満、または承認済みの受入条件（AC-01〜AC-04）の再確認が要る |
| 低   | 前提条件（端末1台・単一店舗など）が崩れたときだけ起こる | 遅れが予備の範囲に収まり、受入条件と後続成果物に影響しない                                              |

### 3.2. 優先度の対応表

優先度は、発生確率（行）と影響度（列）の組み合わせから次の表で決める。

| 発生確率 \ 影響度 | 高       | 中       | 低       |
| ----------------- | -------- | -------- | -------- |
| 高                | `high`   | `high`   | `medium` |
| 中                | `high`   | `medium` | `low`    |
| 低                | `medium` | `low`    | `low`    |

### 3.3. 各リスクの判定根拠

次の表は、各リスクの発生確率と影響度を判定条件のどれに当てはめたかを示す。

| リスクID | 発生確率の根拠                                                            | 影響度の根拠                                                                                      |
| -------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| RK-001   | 中: 来店集中は日常的に起こるが、連続会計の試行はまだ行っていない          | 高: 記録漏れが続くと SC-02（営業日の90%以上で記録が残る）を満たせず、店頭試用を延長することになる |
| RK-002   | 高: 両代表とも平日の日中は店番と仕事があり、準備中の打合せが2回延期された | 中: 確認日が1回ずれると予備の 2 営業日を超えるが、確認の手順と受入条件は変わらない                |
| RK-003   | 低: 端末1台の前提が崩れる故障・充電切れのときだけ起こる                   | 高: 停止日は販売・在庫・つけのすべてが記録できず、SC-02 の集計から外れる日が出る                  |
| RK-004   | 高: 店主代表の確認予定日が過ぎても確認の日程が決まっていなかった          | 中: 版の確定が遅れると AC-04 の照合をやり直すが、試用開始は予備の範囲で守れる見込みだった         |

### 3.4. 再評価の条件

次のいずれかが起きたら、該当リスクの発生確率と影響度を判定し直す。評価の変更と受容は `PO` が判断し、`PM` が判定根拠と変更案をまとめる。agent は判定根拠の整理にとどめる。

- モニタリングのトリガーに当たる兆候が出た。
- 対応の期限を過ぎた。
- 初期リリース・店頭試用の具体日、現金支出の上限、作業時間の上限が決まった、または変わった。
- 週次の見直しで、判定根拠に書いた事実が変わった。

## 4. 対応計画

次の表は、リスクごとの対応方針と、何を確かめたら対応を終えるかを示す。具体の対応は一覧の対応策を正とする。

| リスクID | 対応方針 | 期限                          | 完了条件                                                                                                          |
| -------- | -------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| RK-001   | 低減     | 2026-04-15                    | 連続会計の試行で _UNDECIDED_ 件を続けて記録し、販売記録の漏れが 0 件、1 件の会計確定が _UNDECIDED_ 秒以内に終わる |
| RK-002   | 低減     | 候補日の確定から 3 営業日以内 | 確認日 2 日分が Schedule に登録され、両代表がその日付を了承した記録が残る                                         |
| RK-003   | 受容     | 店頭試用終了まで監視          | 停止した営業日の記録が紙の記録票から復旧日に入力され、SC-02 の集計で欠けた営業日が 0 日である                     |
| RK-004   | 低減     | 2026-04-04（移管済み）        | 課題 IS-002 へ移管し、追跡を課題ログに任せた                                                                      |

RK-003 は `PO` が受容と判断した。許容する残存影響は、停止した営業日の追加操作時間が SC-03（1営業日 10 分以内）を超えうることであり、試用中は終えずに監視を続ける。受容はスコープと計画を変えないため決定記録には起票しない。

## 5. モニタリング

### 5.1. 監視周期と状態の更新

毎週の見直しで全リスクの兆候と期限を確かめ、兆候・期限超過はその場で該当行を更新する。ステータスは次の契機で変える。

| 契機                                                   | 更新後のステータス |
| ------------------------------------------------------ | ------------------ |
| 対応に着手した                                         | `in-progress`      |
| 対応が他者の回答・決定を待って進まない                 | `waiting`          |
| 完了条件を満たした、または課題・変更要求へ移管した     | `done`             |
| リスクの前提が誤りだった                               | `rejected`         |
| 受容して監視を続ける、または兆候待ちで対応に着手しない | `open`             |

### 5.2. 顕在化のトリガーと移管先

次の表は、リスクごとに何が起きたら顕在化とみなし、どこへ起票するかを示す。顕在化したら当日中に起票し、元のリスクを `done` にする。

| リスクID | 顕在化のトリガー                                      | 起票先                                       |
| -------- | ----------------------------------------------------- | -------------------------------------------- |
| RK-001   | 試行または試用中に販売記録の漏れが 1 件でも見つかった | 課題ログ。操作の変更が要るなら変更要求ログ   |
| RK-002   | 押さえた確認日 2 日とも両代表がそろわなかった         | 課題ログ。試用開始日を動かすなら変更要求ログ |
| RK-003   | タブレットが 2 営業日続けて使えない                   | 課題ログ。端末の追加購入は変更要求ログ       |
| RK-004   | 店主代表の確認予定日を過ぎても確認日が決まらない      | 課題ログの IS-002                            |

### 5.3. 見直し漏れと期限超過の連絡

週次の見直しが行われなかったとき、または対応の期限を過ぎたときは、担当が `PM` へ連絡する。`PM` は 2 営業日以内に該当リスクを再評価し、必要なら担当を割り当て直してステータスを更新する。`PM` 自身の見直しが行われなかったときは `PO` へ連絡する。
