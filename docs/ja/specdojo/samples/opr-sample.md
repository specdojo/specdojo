# 駄菓子屋きぬや 販売管理システム 運用手順

## 1. 概要

本書は、駄菓子屋きぬや 販売管理システムの恒常運用における共通手順と証跡規約の正本である。店番担当・運用／リリース管理（`OPS`: Operations / Release Manager）・開発（`DEV`: Developer）が行う作業の手順と残す証跡を定める。店主代表が不在の日も、家族の店番担当が同じ手順で販売・在庫・つけを記録し、異常時に同じ判断で連絡・切替できる状態を作る。

判断基準と目標値は [[specdojo:opd-index-sample|運用方針・設計（全体構成）]] に従い、本書は手順だけを書く。手順群の入口は [[specdojo:opr-index-sample|運用手順（全体構成）]] とする。分冊 `opr-<term>` は本書の証跡・優先度・承認の規約を参照し、差分の手順だけを書く。

次の表は、未決事項が本書のどの手順に影響し、決まるまでどう扱うかを示す。値が決まった時点で該当する章の完了条件を差し替える。

| 未決事項                                                                      | 決まるまでの手順上の扱い                                 | 影響する章                           |
| ----------------------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------ |
| _UNDECIDED_: オフライン時の記録方法                                           | 紙の販売控えに書き、復旧後に転記する                     | 障害対応手順                         |
| _UNDECIDED_: 目標復旧時間（RTO）・目標復旧時点（RPO）とバックアップの保管期間 | 翌営業日の開店までに前日閉店時点へ復元できれば合格とする | バックアップ確認・リストア手順、証跡 |
| _UNDECIDED_: 営業時間外の緊急連絡手段                                         | 営業時間外に気付いた異常は翌朝の開店前に連絡する         | 障害対応手順、アラート対応手順       |
| _UNDECIDED_: 監査ログ以外の証跡の保管期間                                     | 保管期間が決まるまでは削除しない                         | 証跡                                 |
| _UNDECIDED_: 変更の凍結期間（繁忙期の扱い）                                   | 凍結期間を置かず、閉店後であれば変更できるものとする     | 運用変更作業                         |

## 2. 手順適用範囲・前提

次の表は、本書の手順が対象とする範囲と、手順を行う前提を示す。

| 項目     | 内容                                                                                                                                                                                                        |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 対象     | 店頭のタブレット 1 台での販売・在庫・つけの記録、閉店後の日次締め、ホスティング環境の夜間バックアップ                                                                                                       |
| 対象外   | 複数店舗、電子商取引（EC）、本格会計、仕入れ先連携、キャッシュレス決済。仕入れの発注は現行の紙の手順のまま行う                                                                                              |
| 時間帯   | 営業時間 10:00〜18:00。日次点検は開店前（9:45 から）と閉店後、月次点検は毎月の最初の休業日                                                                                                                  |
| 必要権限 | 販売管理システムの記録は店番担当、点検の閲覧は `OPS` が行う。バックアップ取得・復元は `DEV` がホスティング環境の管理者権限で行う。アカウント管理はアカウント付与・剥奪手順 参照。共有のアカウントは使わない |
| 使用手段 | 本番のホスティング環境、復元と手順の模擬に使う検証用の環境、プロジェクトの課題管理、店内の点検ノート                                                                                                        |
| 連絡先   | 営業時間中は店内の電話で `OPS`、応答がなければプロジェクト責任者（`PO`: Project Owner）。営業時間外は店内の連絡帳（緊急連絡手段は概要参照）                                                                 |

## 3. 日次・週次・月次点検手順

次の表は、頻度ごとの点検と、点検を終えたと判定する条件を示す。週次の点検は置かず、週単位で見る項目は月次で扱う。

| 頻度             | 手順                                                                                                            | 実施者   | 完了条件                                                  | 証跡           |
| ---------------- | --------------------------------------------------------------------------------------------------------------- | -------- | --------------------------------------------------------- | -------------- |
| 日次（開店前）   | ログインし、前日の日次締めと夜間バックアップの成功表示を見る（所要 5 分）                                       | 店番担当 | 両方の成功表示がある。ない場合はアラート対応手順へ進んだ  | 日次点検の記録 |
| 日次（閉店後）   | 日次締めを実行し、販売記録の合計と数えた現金の合計を比べる                                                      | 店番担当 | 差が 0 円。差がある場合は原因と金額を日次締め記録に書いた | 日次締め記録   |
| 月次             | 日次締め記録・欠品記録・障害記録から重要業績評価指標（KPI）とサービスレベル目標（SLO）を集計する（所要 1 時間） | `OPS`    | 運用方針の KPI と SLO の全行に当月の値がある              | 月次点検の記録 |
| 月次             | 顧客の検索からつけ残高の表示までを 3 回計る                                                                     | `OPS`    | 3 回とも 1 分以内。超えた回があれば課題として登録した     | 月次点検の記録 |
| 月次（実施漏れ） | 月次点検の記録に当月分がないことを翌週の休業日に確かめ、残りの項目を行う                                        | `OPS`    | 遅れた項目と理由を記録し、`PO` へ報告した                 | 月次点検の記録 |

目標を下回った指標は、`OPS` が月次点検で `PO` へ報告し、課題としてプロジェクトの課題管理へ登録する。

日次締めで現金との差が残る場合は、店番担当が `PO` へ伝え、翌朝の開店前に `PO` が確かめる。

## 4. 障害対応手順

優先度の条件と停止の判断者は運用方針の体制・責任分界に従う。紙の販売控えへの切替と転記の詳しい手順は [[specdojo:opr-incident-sample|運用手順（障害対応）]] に従う。

店番担当は、気付いた時刻・画面の状態・優先度を障害記録に書いてから連絡する。次の表は、優先度ごとの初動の期限と、切り分けから復旧までの操作を示す。

| 優先度                                   | 初動目標                              | 切り分け（`DEV`）                                      | 一次対応（店番担当）                                                  | 復旧                                                                    | エスカレーション                                           |
| ---------------------------------------- | ------------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------- |
| P1（販売・つけのどちらかを記録できない） | 気付いてから 15 分以内に `OPS` へ連絡 | 店舗の通信回線、ホスティング環境、直近の変更の順に見る | つけの新規記録を止め、30 分で再開できなければ紙の販売控えへ切り替える | 販売・在庫・つけを各 1 件記録でき、紙の控えの転記を件数と金額で照合した | `OPS` が 15 分以内に応答しなければ `PO`。切替の判断は `PO` |
| P2（記録はできるが確認・締めができない） | 当日の閉店までに `OPS` へ連絡         | 該当機能の画面とデータの件数を見る                     | 記録を続け、できなかった確認を日次締め記録に書く                      | 該当機能が使え、当日分の確認をやり直した                                | 翌朝も直らなければ P1 として `PO` へ                       |
| P3（回避して記録を続けられる）           | 次の月次点検で `OPS` へ報告           | 月次点検で再現の条件を確かめる                         | 回避の操作を店内の連絡帳に書き、記録を続ける                          | 修正を運用変更作業の手順で適用した                                      | なし                                                       |

復旧後、`OPS` は原因・影響・再発防止を障害記録に追記し、月次点検で `PO` へ報告する。

## 5. アラート対応手順

自動の通知はホスティング環境の死活（営業時間中 5 分無応答）と夜間バックアップ（9:30 に前日の閉店後の成功記録なし）の 2 つで、通知先は `OPS` とする。次の表は、通知を受けてからの段階ごとの操作を示す。

| 段階     | 手順                                                                                                                                                                                                    | 完了条件                                                        | 証跡     |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- | -------- |
| 確認     | `OPS` が店番担当に電話し、記録できているか、成功記録が本当にないかを確かめる                                                                                                                            | 障害か誤検知かを決め、障害なら優先度を付けた                    | 障害記録 |
| 暫定対応 | 死活は P1 として障害対応手順へ、夜間バックアップは P2 としてバッチ再実行の手順へ進む                                                                                                                    | 該当する章の完了条件を満たした                                  | 障害記録 |
| 恒久対応 | `DEV` が原因を直し、運用変更作業の手順で適用する                                                                                                                                                        | 翌日の同じ監視で通知が出ない                                    | 変更記録 |
| 誤検知   | 死活は店番担当が 1 件記録でき、5 分後も応答があり、回復通知が届けば終了する。バックアップは実行ログが成功で、世代の取得日が前日の `closing_date` と一致すれば終了する。「誤検知」と原因を障害記録に書く | 死活の誤検知が月 3 件以上なら、閾値の見直しを課題として登録した | 障害記録 |

## 6. バックアップ確認・リストア手順

バックアップの自動取得は、閉店後に 1 日 1 回行う。確認・復元・演習は次のとおりとする。

- 確認: 店番担当が日次点検で、取得日時が前日の閉店後になっている成功表示を見る。表示がなければアラート対応手順の夜間バックアップへ進む。
- 復元: P1 でデータが失われ、`PO` が復元を決めた場合に `DEV` が行う。最新の成功したバックアップを本番へ戻し、紙の控えと日次締め記録から当日分を転記する。復元した前日の販売件数が日次締め記録と一致し、転記した件数・金額が紙の控えと一致すれば完了とし、障害記録に残す。
- 演習: `DEV` が月次点検で、前日のバックアップを検証用の環境へ戻し、前日の日次締めまでの販売件数を本番と比べる。`OPS` が件数の一致と、復元の開始から終了までの所要時間を確かめ、復元演習の記録に残す。一致しなければ P2 として扱う。
- 達成可否: RTO/RPO が決まるまでの判定は、概要の未決事項の表に従う。

## 7. バッチ再実行・失敗時対応

定期のバッチは夜間バックアップだけとする。日次締めは店番担当が操作し、失敗したらやり直す。

- 検知: 開店前の点検で前日の閉店後の成功記録がない、または実行ログが失敗で終わっている。
- 再実行: `DEV` は、同じ取得日の実行が終わっていることを確かめてから手動で取得を 1 回実行し、実行ログの `run_id` と結果を障害記録に書く。上限は自動取得を含めて 1 日 2 回、手動の再実行は 1 回までとする。
- 重複の防止: 同じ日付の取得は同じ世代を上書きするため、再実行しても世代は増えない。
- 上限到達時: 店番担当は P2 のまま記録を続ける。`OPS` が `PO` へ報告し、当日の閉店後の自動取得を待つ。翌朝も失敗なら `OPS` が P1 として `PO` へ上げる。

## 8. 運用変更作業

次の表は、変更の種類ごとの承認者と、適用・戻しの条件を示す。どの変更も、`DEV` が検証用の環境で販売・在庫・つけを各 1 件記録できることを確かめてから承認を求める。

| 変更種別                   | 承認者 | 実施条件                                     | 完了条件                                                  | ロールバック条件                           | 証跡                         |
| -------------------------- | ------ | -------------------------------------------- | --------------------------------------------------------- | ------------------------------------------ | ---------------------------- |
| アプリの版の更新           | `PO`   | 閉店後。営業時間中は P1 の復旧に必要な時だけ | 本番で販売・在庫・つけを各 1 件記録できた                 | 適用後の確認で 3 件のどれかを記録できない  | 変更記録（差分、承認、実施） |
| 商品マスタ・価格の一括変更 | `PO`   | 閉店後                                       | 翌朝の開店前に店番担当が 3 商品の価格を変更記録と照合した | 開店前の確認で変更記録と違う価格が見つかる | 変更記録（差分、承認、実施） |
| 記録に影響しない表示の修正 | `OPS`  | 閉店後                                       | 修正した画面で 1 件記録できた                             | 表示の崩れで記録の操作ができない           | 変更記録（差分、承認、実施） |

ロールバック条件に当たったら、`DEV` が直前の版または変更前の価格へ戻す。`DEV` は適用時と同じ確認を行い、戻した理由を変更記録に書く。記録の操作が変わる版の更新と価格の一括変更は、前日の閉店時に店内の掲示で店番担当へ周知する。記録に影響しない表示の修正は周知しない。

## 9. アカウント付与・剥奪手順

権限区分と、付与・剥奪・棚卸し・緊急権限の具体手順は [[specdojo:opr-access-control-sample|運用手順（権限・アカウント）]] に従う。通常の付与・剥奪は次の順に進め、各段階の日付を権限変更記録に残す。

1. 申請: `OPS` が、対象の役割と権限区分、使い始める日またはやめる日を書く。
2. 承認: `PO` が申請を見て付与・剥奪してよいかを決める。
3. 実施: `OPS` が付与するか、アカウントを無効にする。剥奪は店番をやめた日または保守作業が終わった日のうちに行う。
4. 検証・記録: `OPS` と本人が、付与なら申請した区分の操作だけができること、剥奪ならログインできないことを確かめ、結果を権限変更記録に書く。

棚卸し: `OPS` が月次点検で、有効なアカウントを店番の予定表・権限変更記録と照合し、分冊の棚卸しの合格条件を確かめる。差異は分冊の是正手順に従い、棚卸し記録に残す。

P1 の復旧で記録の訂正が要る場合は、分冊の緊急権限の手順に従い、`PO` の承認後に `OPS` が `DEV` の区分を一時的に引き上げる。失効と事後確認の結果を権限変更記録・棚卸し記録に残す。

## 10. 問い合わせ一次対応手順

問い合わせ窓口は `OPS` とする。店番担当は口頭または店内の連絡帳で問い合わせる。`OPS` は分類ごとに次のように回答・引継ぎを行う。

- 操作の質問: 店内の操作メモを見て当日の閉店までに答える（例:「つけの記録は顧客の画面の取り消しから当日分だけ消せます」）。操作メモにない操作は `DEV` へ引き継ぐ。
- 記録の訂正の依頼: `OPS` が日次締め記録を見て店番担当へ訂正を依頼し、翌営業日の開店までに結果を確かめる。締め済みの金額が変わる訂正は `PO` へ引き継ぐ。
- 機能の要望: 課題管理の要望の一覧に登録し、次の月次点検で `PO` が採否を決める。
- 障害にあたるもの: 障害対応手順の連絡先と期限で扱う。

`OPS` は回答後、分類・回答・引継ぎの有無を問い合わせ記録に書く。同じ操作の質問が月 2 回を超えたら、店内の操作メモに追記する。

## 11. 証跡

次の表は、各手順の証跡をどこに残し、どの識別子で照合するかを示す。

| 証跡種別       | 保存先                               | 保管期間                                  | 参照権限              | 最低限残す識別子                              |
| -------------- | ------------------------------------ | ----------------------------------------- | --------------------- | --------------------------------------------- |
| 日次点検の記録 | 店内の点検ノート（紙）               | _UNDECIDED_                               | 店番担当、`OPS`       | 点検日、点検した役割                          |
| 日次締め記録   | 販売管理システムの日次締めの画面     | _UNDECIDED_                               | 店番担当、`OPS`、`PO` | `closing_date`                                |
| 障害記録       | プロジェクトの課題管理               | _UNDECIDED_                               | `OPS`、`DEV`、`PO`    | `ticket_id`、優先度、発生時刻                 |
| 実行ログ       | ホスティング環境のバックアップの記録 | _UNDECIDED_: バックアップの保管期間と同じ | `OPS`、`DEV`          | `run_id`、実行日時                            |
| 変更記録       | プロジェクトの課題管理               | _UNDECIDED_                               | `OPS`、`DEV`、`PO`    | `ticket_id`、適用する版                       |
| 権限変更記録   | プロジェクトの課題管理               | _UNDECIDED_                               | `OPS`、`PO`           | `ticket_id`、権限区分、申請日・承認日・実施日 |
| 棚卸し記録     | プロジェクトの課題管理               | _UNDECIDED_                               | `OPS`、`PO`           | `ticket_id`、対象月、差異ごとの解消日         |
| 月次点検の記録 | プロジェクトの課題管理               | _UNDECIDED_                               | `OPS`、`PO`           | `ticket_id`、対象月                           |
| 問い合わせ記録 | 店内の連絡帳                         | _UNDECIDED_                               | 店番担当、`OPS`       | 受付日、分類                                  |
| 監査ログ       | 販売管理システムの監査ログ           | 1 年                                      | `OPS`、`PO`           | 操作日時、アカウント、操作の種類              |

欠品記録は日次締め記録と同じ `closing_date` で、復元演習の記録は月次点検の記録と同じ `ticket_id` で残す。未決の保管期間の扱いは、概要の未決事項の表に従う。

手順を新しく書いたときや改訂したときは、検証用の環境で手順を模擬する。各章の表にある完了条件を満たし、指定された証跡を残せることを確かめる。P1 の紙の控えへの切替、再実行の上限到達、ロールバックの分岐も 1 回ずつ模擬し、再実行の後もバックアップの世代が増えないことを確かめる。

手順の模擬結果は月次点検の記録に、確認日・確認環境・対象手順・`ticket_id`・合否を残す。
