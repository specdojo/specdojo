# 駄菓子屋きぬや 販売管理システム 総合テストカタログ 概要

## 1. 本ドキュメントの目的と適用対象

本書は、駄菓子屋きぬや 販売管理システムの初期リリースの総合テスト（ST）に適用する。対象別カタログ `stc-<term>` の分割基準・観点/条件・環境・合格基準を揃えるため、共通方針を定める。

[[specdojo:tsp-index-sample|テスト戦略・方針（TSP）]] の総合テストの範囲を、店頭業務がシステム全体で成立するかの確認へ具体化する。対象は、[[specdojo:bac-sample|業務受入条件（BAC）]] の BAC-01〜BAC-03 のシナリオ、在庫・つけの記録更新と確認、障害・回復、日次締めを含む性能とする。

在庫・つけは [[specdojo:prj-success-criteria-and-acceptance-criteria-sample|成功基準と受入条件]] の AC-05・AC-02、性能は [[specdojo:sac-sample|システム受入条件（SAC）]] の `SAC-PERF-01`〜`SAC-PERF-04` に対応させる。

ST が守る業務価値は、会計確定と販売記録・在庫減算の一致、在庫不足や入力不足で販売を確定しないこと、店主不在でも同じ手順で記録と引継ぎを終えられることである。これらが崩れると、ノートと記憶に頼る現状より記録が信用できなくなる。

ほかのテストレベルとの責任境界は次のとおりとする。

| レベル                                 | 本書との境界                                                                                                                                                                               |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 単体テスト（UT）・内部結合テスト（IT） | 金額・在庫の計算と、画面・記録サービス・データベース間の記録の一致の網羅は [[specdojo:itc-index-sample\|内部結合テスト]] までで確定済みとする。ST は業務シナリオを通した結果だけを確認する |
| 外部結合テスト（ET）                   | 印刷コマンド・保管サービスの契約（失敗・タイムアウト時の結果）は [[specdojo:etc-index-sample\|外部結合テスト]] に委ねる。ST は業務シナリオ中の代表的な成功/失敗だけを扱う                  |
| 受入テスト（AT）                       | 利用者が説明なしで操作できるかの判断は [[specdojo:atc-index-sample\|受入テスト]] に委ねる。ST は記録・状態の正しさと SAC の性能基準を判定する                                              |

個別ケースは本書に置かず、[[specdojo:stc-sample|総合テストカタログ 対象別]] 以下を正本とする。

## 2. テスト対象の括り方と分割基準

`<term>` は開始から完了までを1つの業務シナリオとして説明できる単位とする。BAC の受入シナリオを起点に、業務/価値境界→境界横断→データ境界→運用境界の順で判断した結果は次のとおり。

| `stc-<term>`          | 業務シナリオ（開始→完了）                                   | 根拠                               | 分割・統合の判断                                                                           |
| --------------------- | ----------------------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------ |
| `stc-cash-sale`       | 明細登録→会計確定→販売記録・在庫減算→レシート印刷           | BAC-01、受入条件 AC-01             | 確定前の取消と印刷失敗時の会計維持は同じ画面・記録サービス経路を通るため、別 term にしない |
| `stc-sale-hold`       | 在庫不足・入力不足の検知→未確定のまま停止→引継ぎメモ→再開   | BAC-02、BAC-03                     | 各2ケース程度で単独では薄く、「販売を確定しない」という同じ合否命題を持つため統合する      |
| `stc-stock-update`    | 入荷・棚卸・廃棄の登録→在庫更新→在庫表示と記録の照合        | AC-05、AC-02                       | 販売による減算とは開始条件が異なる在庫更新をまとめ、同じ在庫記録と表示で判定する           |
| `stc-credit-balance`  | つけ購入・入金の登録→常連顧客の検索→つけ残高と記録の照合    | AC-05、AC-02、SAC-PERF-03          | 扱うデータ（顧客・つけ残高）のライフサイクルが現金販売と異なるため分ける                   |
| `stc-record-recovery` | 応答欠落・保存失敗の検知→照合待ちの識別→記録の復元→業務再開 | TSP のスコープ（記録の保全・復元） | 運用手順と観測点（保管サービスの記録）が販売と異なるため運用境界で分ける                   |
| `stc-daily-close`     | 閉店後の日次締め開始→その日の記録の処理→翌日の開店前の完了  | SAC-PERF-04                        | 営業中の販売と異なり、その日の全記録と閉店から翌日の開店までの時間を前提とするため分ける   |

観点が15以上、またはケース表が60行以上の term は、データ境界で分割を再検討する。

## 3. 対象外・除外理由（共通）

ST の対象外とする範囲ごとに、除外理由、代替手段、ST で扱う例外条件を示す。

| 対象外（やらないこと）                         | 除外理由                                                        | 代替レベル/代替手段                                         | 例外（STで扱う条件）                                                                    |
| ---------------------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 代表負荷を超える長時間運転・限界負荷の性能測定 | 放課後ピークの代表負荷を超える量は初期リリースで発生しない      | 非機能要件（NFR）の性能測定記録。Architect（ARC）が実施する | SAC の代表負荷で、会計確定・つけ残高確認・日次締めを各主担当で測定する                  |
| 印刷コマンド・保管サービスの全障害パターン     | 契約の網羅は境界の責務で、ST で重ねると環境準備の費用が倍になる | ET（`receipt-print` 連携、保管サービスの契約観点）          | 用紙切れ・保存失敗・印字結果不明（30秒タイムアウト）の3種だけを業務シナリオ中で再現する |
| 画面の分かりやすさ・説明なしでの操作完了       | 記録と状態では利用者の理解を判定できない                        | AT（成功基準 SC-01・受入条件 AC-03）                        | なし                                                                                    |
| 端末の機種・ブラウザの網羅互換                 | 店頭端末は1台のタブレットに固定している                         | 前提外。端末を増やす時にスコープを改訂する                  | なし                                                                                    |
| 通信不能時の販売継続                           | TSP で未決であり、期待結果を定められない                        | なし（「メモ / 将来課題」で決定を待つ）                     | 決定後に `stc-record-recovery` へ観点を追加する                                         |

## 4. 観点の立て方（共通）

観点名は「名詞＋品質/振る舞い」とし、各 term は次の5系統から必要なものを立てる。

| 系統           | 本システムで保証すること                                     | 観点名の例                                     | 主に立てる term                                           |
| -------------- | ------------------------------------------------------------ | ---------------------------------------------- | --------------------------------------------------------- |
| 業務フロー成立 | 会計確定や在庫・つけの更新が記録と表示に一致して残る         | `販売確定成立`、`更新表示一致`                 | `stc-cash-sale`、`stc-stock-update`、`stc-credit-balance` |
| 例外時リカバリ | 在庫不足・入力不足・印刷失敗でも記録が欠けず次の手が分かる   | `未確定停止`、`会計維持`                       | `stc-sale-hold`、`stc-cash-sale`                          |
| データ整合性   | 同じ取引番号で二重に販売記録が作られない                     | `二重確定防止`                                 | `stc-cash-sale`、`stc-record-recovery`                    |
| 監視/運用観測  | 照合待ちの取引を取引番号で特定でき、復元後の記録と照合できる | `照合待ち識別`                                 | `stc-record-recovery`                                     |
| 代表的な非機能 | SAC の会計確定・つけ残高確認・日次締めの性能基準を満たす     | `会計確定応答`、`残高確認時間`、`日次締め完了` | `stc-cash-sale`、`stc-credit-balance`、`stc-daily-close`  |

「操作性が良いこと」のように条件を作れない観点は立てず、「対象外・除外理由（共通）」のとおり AT に委ねる。

## 5. 条件の立て方（共通）

条件の要素ごとに、差分の立て方と具体例を示す。

| 要素 | 本システムでの立て方                                        | 例                                                    |
| ---- | ----------------------------------------------------------- | ----------------------------------------------------- |
| 入力 | 購入数を在庫未満・在庫と同数・在庫超過の3値で代表させる     | 商品A（在庫5個）を2個・5個・6個                       |
| 状態 | 事前の在庫数、店番担当の役割、取引の確定状態で分ける        | 状態: 在庫5個、店番は家族利用者代表、取引は会計要求前 |
| 環境 | 外部インターフェースの状態はスタブの応答で1つずつ切り替える | 環境: プリンタ検証機が用紙切れを返す                  |
| 経路 | 成功・取消・停止・再開の分岐を1条件1経路にする              | 経路: 会計確定後に印刷が失敗し、会計は維持される      |

条件は次の順に追加する。

1. 代表シナリオ: BAC-01 の C-01
2. 重要分岐: 在庫と同数の C-02、取消
3. 重大例外: 二重確定、記録の欠落

入力×状態×環境の直積は作らない。在庫の判定は店番の役割で変わらないため、在庫超過は「店番が家族利用者代表」の状態だけで確認する。

## 6. 観点/条件の採用基準と対象別への分配方針（共通）

### 6.1. 採用基準（共通）

各観点は1つの合否命題、各条件は1つの差分を表す。採用する観点/条件には、次のいずれかを根拠として示す。

- 業務影響: 誤った販売記録・在庫数、つけ残高の誤表示、記録の欠落
- 不具合リスク: 確定状態の遷移（会計要求後の中断、印刷失敗）の欠落
- 上位仕様: BAC-01〜BAC-03、AC-01・AC-02・AC-05、TSP の出口条件（SAC-PERF-01〜SAC-PERF-04 を含む）

### 6.2. 対象別への分配方針（共通）

採用した観点/条件ごとに、主担当と従担当を次のとおり割り当てる。

| 観点/条件                                           | 採用理由                                            | 主担当 `stc-<term>`   | 従担当（任意）  | 備考                                                               |
| --------------------------------------------------- | --------------------------------------------------- | --------------------- | --------------- | ------------------------------------------------------------------ |
| `販売確定成立` / 在庫と同数の購入                   | BAC-01 の C-02。在庫0個の境界で減算漏れが起きやすい | `stc-cash-sale`       | なし            |                                                                    |
| `会計維持` / 印刷の用紙切れ                         | 会計を取り消すと現金と記録がずれる                  | `stc-cash-sale`       | なし            | 確定済みの会計を取り消さず、警告だけを出す                         |
| `二重確定防止` / 応答欠落後の再送                   | 二重記録は売上と在庫を同時に誤らせる                | `stc-record-recovery` | `stc-cash-sale` | 確定は販売側、照合待ちの識別は復元側で判定する                     |
| `更新表示一致` / 入荷・棚卸・廃棄の登録             | AC-05・AC-02。在庫の更新が表示に反映されること      | `stc-stock-update`    | なし            | 更新種別ごとに記録と表示を照合する                                 |
| `更新表示一致` / つけ購入・入金の登録               | AC-05・AC-02。つけ残高の更新が表示に反映されること  | `stc-credit-balance`  | なし            | 更新前後の残高をつけ記録と照合する                                 |
| `会計確定応答` / 60取引/時の負荷                    | TSP 出口条件の SAC-PERF-01                          | `stc-cash-sale`       | なし            | 基準は「メモ / 将来課題」の仮置き値。P99 も記録する                |
| `会計記録保全` / 同じ性能試行の60取引               | TSP 出口条件の SAC-PERF-02                          | `stc-cash-sale`       | なし            | 送信した取引番号と販売記録を照合し、欠落・重複がないことを判定する |
| `残高確認時間` / ピーク負荷での顧客検索から残高表示 | TSP 出口条件の SAC-PERF-03                          | `stc-credit-balance`  | なし            | 操作を含む全体の時間で判定し、残高表示の P95 も記録する            |
| `日次締め完了` / 性能試行で作ったその日の全記録     | TSP 出口条件の SAC-PERF-04                          | `stc-daily-close`     | なし            | SAC の暫定基準と測定回数に従う                                     |

主担当を複数置く場合は、1つに決められない理由を備考に書く。理由のない重複は認めない。

分割基準・対象外・共通カラム・環境前提・共通合格基準を改訂した場合は、本節の分配表から影響する `stc-<term>` を列挙する。列挙した対象のケース表・トレース表と `kinuya-ci-st` のテストコードを追従させる。

## 7. 総合テスト共通の境界/環境の扱い

### 7.1. 境界・環境の共通方針

各対象で再現性を保って実施・判定できるよう、共通の検証環境と証跡・責任を定める。

| 項目     | 共通方針                                                                                                                                                                                                                           |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 環境     | TSP の検証環境を ST 期間中は ST 専用とし、ST 開始時のアプリ版数と店舗設定を固定する。版数を変えた場合は P0 を全件再実行する                                                                                                        |
| データ   | 店舗データ領域 `kinuya-st` を使い、各ケースの開始時に `kinuya-test-data`（商品A 単価30円・在庫5個、架空の常連顧客1名）へ戻す。終了時に販売記録を削除し、残った領域は7日後に削除する。性能測定は次の例外に従う                      |
| 外部依存 | プリンタは店舗プリンタの検証機、保管サービスは検証用領域へ実接続する。用紙切れ・保存失敗・印字結果不明（30秒タイムアウト）・応答欠落は疑似応答スタブで再現する                                                                     |
| 画面操作 | 手順は「商品Aを2個登録して会計を確定する」の粒度にとどめ、画面のタップ順はテストコードに書く                                                                                                                                       |
| 観測点   | 画面表示に加え、販売記録・在庫記録・つけ記録・引継ぎメモ・保管サービスの保存記録で判定する。販売は取引番号、在庫は商品識別子、つけ残高は顧客 ID で照合する。性能測定の観測点は SAC・NFR に従う                                     |
| 証跡     | 継続的インテグレーション（CI）ジョブ `kinuya-ci-st` の run、ST レポート `kinuya-st-report`、手動ケースの画面キャプチャ（対象の照合キーが写る静止画を `kinuya-st-report` に添付）、照合キーつきの記録サービスのログ、印刷結果の記録 |
| 責任     | 環境とデータの準備は Developer（DEV）が行う。実施・証跡の照合・合否判定は Quality Engineer（QE）、例外承認は Project Manager（PM）が行う                                                                                           |

性能測定のデータ量・初期化の例外は SAC に従って対象別に記す。性能試行の記録は日次締めの測定終了まで保持してから削除する。

### 7.2. 共通合格基準

共通合格基準は TSP の総合テスト出口条件に沿って次のとおりとする。

| 優先度 | 対象                                                                                                                                                | 合格基準                                                                                     |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| P0     | 記録の欠落・誤り、販売の誤確定につながるケース、TSP 出口条件の必須ケース（BAC-01〜BAC-03、AC-05・AC-02 の更新・表示一致、SAC-PERF-01〜SAC-PERF-04） | 全件 Pass。1件でも Fail なら ST を完了しない                                                 |
| P1     | P0 に当たらない例外時の案内、つけ残高の表示、復元後の再開                                                                                           | 全件 Pass。Major の不具合で Fail を残す場合だけ、PM の例外承認と回避手順を課題ログに登録する |
| P2     | BAC-01〜BAC-03 に含まれない頻度の低い組合せ                                                                                                         | ST 期間内に80%以上を消化し、未消化分は受入テスト開始前までの実施計画を課題ログに登録する     |

性能は SAC の仮置き・暫定基準で出口判定に用いる。[[specdojo:nfr-performance-sample|性能要件]] の会計確定の P99 と商品検索の応答時間は値の記録のみとし、値の大小で合否を決めない。商品検索の測定は `stc-cash-sale` が担当する。優先度別の基準に加え、不具合の重大度と収束基準は TSP に従う。

## 8. ケース表の共通カラム

全 `stc-<term>` は次の順でカラムを並べる。1行は、条件と期待値の組が一意に決まる1テストを表す。`case_id` は `st-<term>-<perspective_key>-<nnn>` とし、`nnn` は010から10刻みで振る。

| カラム                 | 区分 | 書き方                                                         |
| ---------------------- | ---- | -------------------------------------------------------------- |
| `case_id`              | 必須 | 一度振った値は変えない。廃止したケースは欠番にし、再利用しない |
| 条件                   | 必須 | `入力:` `状態:` `環境:` `経路:` のうち差分の要点だけ           |
| 手順（最小）           | 必須 | 業務操作の粒度で3手順以内                                      |
| 期待値                 | 必須 | 観測点の値で Pass / Fail を判定できる文                        |
| 観測点（アサーション） | 推奨 | 期待値を確かめる記録・画面                                     |
| 環境/依存              | 推奨 | スタブの状態、データ領域                                       |
| トレース               | 推奨 | 対象別のトレース表の `TR-xx`                                   |
| 優先度                 | 推奨 | P0 / P1 / P2                                                   |
| 自動化                 | 推奨 | manual / automated / mixed                                     |
| 証跡                   | 推奨 | CI run、レポート、取引番号                                     |

期待値は、商品Aを2個・60円で会計確定する場合、「販売記録が1件（数量2・60円）でき、在庫が5個から3個になる」のように観測点と値を示す。「正常に処理される」とだけ書いたケースは認めない。条件・手順・トレース・証跡を含む記入例は [[specdojo:stc-sample|総合テストカタログ 対象別]] のケース表を参照する。

## 9. メモ / 将来課題

仮置き・未決の論点ごとに、影響する箇所、当面の扱い、確定時の見直し方針を示す。

| 論点                              | 影響（章・列）                       | 当面の扱い                                              | 確定時の見直し方針                                              |
| --------------------------------- | ------------------------------------ | ------------------------------------------------------- | --------------------------------------------------------------- |
| _ASSUMPTION_: 会計確定の応答基準  | 対象外の例外、共通合格基準の P0      | TSP の仮置き（60取引/時で応答の95%が2秒以内）で判定する | NFR 確定後に基準値を置き換え、`会計確定応答` の期待値を更新する |
| _UNDECIDED_: 通信不能時の販売継続 | 対象外、`stc-record-recovery` の観点 | 対象外とし、ST の合格を当該経路の合格とみなさない       | 決定後に観点と条件を追加し、分配表へ主担当を割り当てる          |
