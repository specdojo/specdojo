# 駄菓子屋きぬや 販売管理システム 総合テストカタログ 概要

## 1. 本ドキュメントの目的と適用対象

駄菓子屋きぬや 販売管理システムの初期リリースについて、総合テスト（ST）の対象別カタログ `stc-<term>` が同じ分割基準・観点/条件・環境・合格基準で書かれるよう、共通方針を定める。[[specdojo:tsp-index-sample|テスト戦略・方針]] の総合テストの範囲（BAC-01〜BAC-03 のシナリオ、つけ残高確認、障害・回復、性能）を、店頭業務がシステム全体で成立するかの確認へ具体化する。

ST が守る業務価値は、会計確定と販売記録・在庫減算の一致、在庫不足や入力不足で販売を確定しないこと、店主不在でも同じ手順で記録と引継ぎを終えられることである。これらが崩れると、ノートと記憶に頼る現状より記録が信用できなくなる。

| レベル | 本書との境界                                                                                                                                                                    |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| UT・IT | 金額・在庫の計算と、画面・記録サービス・DB 間の記録の一致の網羅は [[specdojo:itc-index-sample\|内部結合テスト]] までで確定済みとし、ST は業務シナリオを通した結果だけを確認する |
| ET     | 印刷コマンド・保管サービスの契約（失敗・タイムアウト時の結果）は [[specdojo:etc-index-sample\|外部結合テスト]] に委ね、ST は業務シナリオ中の代表的な成功/失敗だけを扱う         |
| AT     | 利用者が説明なしで操作できるかの判断は [[specdojo:atc-index-sample\|受入テスト]] に委ね、ST は記録と状態の正しさだけを判定する                                                  |

本書の維持は QE が担う。分割基準・対象外・共通カラム・環境前提・共通合格基準を改訂した場合、QE は「観点/条件の採用基準と対象別への分配方針（共通）」の分配表から影響する `stc-<term>` を列挙し、各担当（DEV）がケース表と `kinuya-ci-st` のテストコードを追従させる。個別ケースは本書に置かず、[[specdojo:stc-sample|総合テストカタログ 対象別]] 以下を正本とする。

## 2. テスト対象の括り方と分割基準

`<term>` は開始から完了までを1つの業務シナリオとして説明できる単位とする。BAC の受入シナリオを起点に、業務/価値境界→境界横断→データ境界→運用境界の順で判断した結果は次のとおり。

| `stc-<term>`          | 業務シナリオ（開始→完了）                                   | 根拠                               | 分割・統合の判断                                                                             |
| --------------------- | ----------------------------------------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------- |
| `stc-cash-sale`       | 明細登録→会計確定→販売記録・在庫減算→レシート印刷           | BAC-01、AC-01                      | 確定前の取消と印刷失敗時の会計維持は同じ画面・記録サービス経路を通るため、別 term にしない   |
| `stc-sale-hold`       | 在庫不足・入力不足の検知→未確定のまま停止→引継ぎメモ→再開   | BAC-02、BAC-03                     | 各2ケース程度で単独では薄く、「販売を確定しない」という同じ合否命題を持つため統合する        |
| `stc-credit-balance`  | 常連顧客の検索→つけ残高の表示→残高と記録の照合              | AC-02                              | 扱うデータ（顧客・つけ残高）のライフサイクルが販売と異なるため分ける                         |
| `stc-record-recovery` | 応答欠落・保存失敗の検知→照合待ちの識別→記録の復元→業務再開 | TSP のスコープ（記録の保全・復元） | 実施者が店主代表で、運用手順と観測点（保管サービスの記録）が販売と異なるため運用境界で分ける |

観点が15以上、またはケース表が60行を超えた term は、データ境界で分割を再検討する。

## 3. 対象外・除外理由（共通）

| 対象外（やらないこと）                     | 除外理由                                                        | 代替レベル/代替手段                                | 例外（STで扱う条件）                                       |
| ------------------------------------------ | --------------------------------------------------------------- | -------------------------------------------------- | ---------------------------------------------------------- |
| 長時間運転・限界負荷の性能測定             | 放課後ピークの代表負荷を超える量は初期リリースで発生しない      | NFR の性能測定記録（ARC が実施）                   | 会計確定の応答は代表値として `stc-cash-sale` で1回測定する |
| 印刷コマンド・保管サービスの全障害パターン | 契約の網羅は境界の責務で、ST で重ねると環境準備の費用が倍になる | ET（`receipt-print` 連携、保管サービスの契約観点） | 用紙切れと保存失敗の2種だけを業務シナリオ中で再現する      |
| 画面の分かりやすさ・説明なしでの操作完了   | 記録と状態では利用者の理解を判定できない                        | AT（SC-01・AC-03）                                 | なし                                                       |
| 端末の機種・ブラウザの網羅互換             | 店頭端末は1台のタブレットに固定している                         | 前提外。端末を増やす時にスコープを改訂する         | なし                                                       |
| 通信不能時の販売継続                       | TSP で未決であり、期待結果を定められない                        | なし（「メモ / 将来課題」で決定を待つ）            | 決定後に `stc-record-recovery` へ観点を追加する            |

## 4. 観点の立て方（共通）

観点名は「名詞＋品質/振る舞い」とし、各 term は次の5系統から必要なものを立てる。

| 系統           | 本システムで保証すること                                     | 観点名の例     | 主に立てる term                        |
| -------------- | ------------------------------------------------------------ | -------------- | -------------------------------------- |
| 業務フロー成立 | 会計確定で販売記録1件と在庫減算が同時に残る                  | `販売確定成立` | `stc-cash-sale`                        |
| 例外時リカバリ | 在庫不足・入力不足・印刷失敗でも記録が欠けず次の手が分かる   | `未確定停止`   | `stc-sale-hold`、`stc-cash-sale`       |
| データ整合性   | 同じ取引番号で二重に販売記録が作られない                     | `二重確定防止` | `stc-cash-sale`、`stc-record-recovery` |
| 監視/運用観測  | 照合待ちの取引を取引番号で特定でき、復元後の記録と照合できる | `照合待ち識別` | `stc-record-recovery`                  |
| 代表的な非機能 | 放課後ピーク相当で会計確定の応答が仮置き基準を満たす         | `会計確定応答` | `stc-cash-sale`                        |

「操作性が良いこと」のように条件を作れない観点は立てず、「対象外・除外理由（共通）」のとおり AT に委ねる。

## 5. 条件の立て方（共通）

| 要素 | 本システムでの立て方                                    | 例                                                    |
| ---- | ------------------------------------------------------- | ----------------------------------------------------- |
| 入力 | 購入数を在庫未満・在庫と同数・在庫超過の3値で代表させる | 商品A（在庫5個）を2個・5個・6個                       |
| 状態 | 事前の在庫数、店番担当の役割、取引の確定状態で分ける    | 状態: 在庫5個、店番は家族利用者代表、取引は会計要求前 |
| 環境 | 外部 I/F の状態はスタブの応答で1つずつ切り替える        | 環境: プリンタ検証機が用紙切れを返す                  |
| 経路 | 成功・取消・停止・再開の分岐を1条件1経路にする          | 経路: 会計確定後に印刷が失敗し、会計は維持される      |

代表シナリオ（BAC-01 の C-01）→重要分岐（在庫と同数の C-02、取消）→重大例外（二重確定、記録の欠落）の順に追加する。入力×状態×環境の直積は作らず、在庫超過は「店番が家族利用者代表」の状態だけで確認する（在庫の判定は店番の役割で変わらないため）。

## 6. 観点/条件の採用基準と対象別への分配方針（共通）

採用は1観点＝1合否命題、1条件＝1差分とし、次のいずれかを根拠に書けるものに限る。

- 業務影響: 誤った販売記録・在庫数、つけ残高の誤表示、記録の欠落
- 不具合リスク: 確定状態の遷移（会計要求後の中断、印刷失敗）の欠落
- 上位仕様: BAC-01〜BAC-03、AC-01・AC-02、TSP の出口条件

| 観点/条件                         | 採用理由                                            | 主担当 `stc-<term>`   | 従担当（任意）  | 備考                                           |
| --------------------------------- | --------------------------------------------------- | --------------------- | --------------- | ---------------------------------------------- |
| `販売確定成立` / 在庫と同数の購入 | BAC-01 の C-02。在庫0個の境界で減算漏れが起きやすい | `stc-cash-sale`       | なし            |                                                |
| `未確定停止` / 印刷の用紙切れ     | 会計を取り消すと現金と記録がずれる                  | `stc-cash-sale`       | `stc-sale-hold` | 引継ぎメモの書式は `stc-sale-hold` を参照する  |
| `二重確定防止` / 応答欠落後の再送 | 二重記録は売上と在庫を同時に誤らせる                | `stc-record-recovery` | `stc-cash-sale` | 確定は販売側、照合待ちの識別は復元側で判定する |
| `会計確定応答` / 60取引/時の負荷  | TSP の総合テスト出口条件                            | `stc-cash-sale`       | なし            | 基準は「メモ / 将来課題」の仮置き値            |

主担当を複数置く場合は、1つに決められない理由を備考に書く。理由のない重複は差し戻す。

## 7. 総合テスト共通の境界/環境の扱い

| 項目     | 共通方針                                                                                                                                                                            |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 環境     | TSP の検証環境を ST 期間中は ST 専用とし、ST 開始時のアプリ版数と店舗設定を固定する。版数を変えた場合は P0 を全件再実行する                                                         |
| データ   | 店舗データ領域 `kinuya-st` を使い、各ケースの開始時に `kinuya-test-data`（商品A 単価30円・在庫5個、架空の常連顧客1名）へ戻す。終了時に販売記録を削除し、残った領域は7日後に削除する |
| 外部依存 | プリンタは店舗プリンタの検証機、保管サービスは検証用領域へ実接続する。用紙切れ・保存失敗・応答欠落は疑似応答スタブで再現する                                                        |
| UI 操作  | 手順は「商品Aを2個登録して会計を確定する」の粒度にとどめ、画面のタップ順はテストコードに書く                                                                                        |
| 観測点   | 画面表示に加え、販売記録・在庫記録・引継ぎメモ・保管サービスの保存記録で判定する。照合のキーは取引番号とする                                                                        |
| 証跡     | CI ジョブ `kinuya-ci-st` の run、ST レポート `kinuya-st-report`、手動ケースの画面キャプチャ、取引番号つきの記録サービスのログ、印刷結果の記録                                       |
| 責任     | 環境とデータの準備は DEV、実施と証跡の照合は QE、合否判定は QE、例外承認は PM が行う                                                                                                |

共通合格基準は TSP の総合テスト出口条件に沿って次のとおりとする。

| 優先度 | 対象                                           | 合格基準                                                                                     |
| ------ | ---------------------------------------------- | -------------------------------------------------------------------------------------------- |
| P0     | 記録の欠落・誤り、販売の誤確定につながるケース | 全件 Pass。1件でも Fail なら ST を完了しない                                                 |
| P1     | 例外時の案内、つけ残高の表示、復元後の再開     | 全件 Pass。Major の不具合で Fail を残す場合だけ、PM の例外承認と回避手順を課題ログに登録する |
| P2     | 頻度の低い組合せ（取消後の再登録など）         | ST 期間内に80%以上を消化し、未消化分は受入テスト開始前までの実施計画を課題ログに登録する     |

## 8. ケース表の共通カラム

全 `stc-<term>` は次の順でカラムを並べる。`case_id` は `st-<term>-<perspective_key>-<nnn>` とし、`nnn` は010から10刻みで振る。

| カラム                 | 区分 | 書き方                                                         |
| ---------------------- | ---- | -------------------------------------------------------------- |
| `case_id`              | 必須 | 一度振った値は変えない。廃止したケースは欠番にし、再利用しない |
| 条件                   | 必須 | `入力:` `状態:` `環境:` `経路:` のうち差分の要点だけ           |
| 手順（最小）           | 必須 | 業務操作の粒度で3手順以内                                      |
| 期待値                 | 必須 | 観測点の値で Pass / Fail を判定できる文                        |
| 観測点（アサーション） | 推奨 | 期待値を確かめる記録・画面                                     |
| 環境/依存              | 推奨 | スタブの状態、データ領域                                       |
| トレース               | 推奨 | 対象別のトレース表の `TR-xx`                                   |
| 優先度                 | 推奨 | P0 / P1 / P2                                                   |
| 自動化                 | 推奨 | manual / automated / mixed                                     |
| 証跡                   | 推奨 | CI run、レポート、取引番号                                     |

対象別カタログでの記入例（`stc-cash-sale`）:

| `case_id`                        | 条件                                    | 手順（最小）                           | 期待値                                                              | 観測点（アサーション）   | 環境/依存                   | トレース | 優先度 | 自動化    | 証跡                               |
| -------------------------------- | --------------------------------------- | -------------------------------------- | ------------------------------------------------------------------- | ------------------------ | --------------------------- | -------- | ------ | --------- | ---------------------------------- |
| `st-cash-sale-flow-success-010`  | 入力: 商品A 2個 / 状態: 在庫5個         | 商品Aを2個登録し、60円で会計を確定する | 販売記録が1件（数量2・60円）でき、在庫が5個から3個になる            | 販売記録、在庫記録       | `kinuya-st`、プリンタ検証機 | TR-01    | P0     | automated | `kinuya-ci-st` の run、取引番号    |
| `st-cash-sale-print-failure-010` | 環境: 用紙切れ / 経路: 確定後に印刷失敗 | 会計を確定し、印刷失敗の警告を確認する | 販売記録1件と在庫減算が残り、警告に取引番号と「未印字」が表示される | 販売記録、画面、印刷結果 | 用紙切れスタブ              | TR-02    | P0     | mixed     | `kinuya-st-report`、画面キャプチャ |

期待値に「正常に処理される」とだけ書いたケースは、QE がレビューで差し戻す。
