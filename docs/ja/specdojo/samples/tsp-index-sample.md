# 駄菓子屋きぬや 販売管理システム テスト戦略・方針

## 1. 概要

駄菓子屋きぬや 販売管理システムの初期リリースについて、販売・在庫・つけの記録が欠けず、店主代表と家族利用者代表が同じ手順で照合できる品質を担保する。単一店舗・タブレット1台の店頭業務を、単体→内部結合→外部結合→総合→受入の順に確認する。各レベルの品質ゲートと、[[specdojo:bac-sample|現金販売の業務受入条件]] の BAC-01〜BAC-03、[[specdojo:prj-success-criteria-and-acceptance-criteria-sample|成功基準と受入条件]] の SC-01・AC-01〜AC-04 に対応する証跡で合否を判定する。

守る業務は、会計確定と販売記録・在庫減算の一致、在庫不足や入力不足で販売を確定しないこと、つけ残高を1分以内に確認できることの3つである。誤りが残ると、ノートと記憶に頼る現状より記録が信用できなくなり、店主不在の店番を任せられなくなる。

`kinuya-` で始まる参照名は未同梱の架空成果物である。経路 `PATH-01`〜`PATH-07` は [[specdojo:ifd-sample|情報流れ図]] の定義に従う。[[specdojo:sac-sample|システム受入条件]] と [[specdojo:nfr-index-sample|非機能要件]] は条件 ID が未整備のため、本書の非機能の基準は「メモ / 将来課題」の仮置きとして扱う。

### 2.2. 観点/条件設計の共通原則

| 項目     | 本プロジェクトでの適用                                                                                               | 例                                                                                           |
| -------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 定義粒度 | 1観点は「販売1件の確定で何が起きるか」の1命題とし、条件は在庫数・入力の有無など1つの差分で分ける                     | 観点「在庫以内なら販売を確定する」／条件「在庫5個・購入2個」／期待結果「在庫3個・記録1件」   |
| 分類     | 正常・境界・例外・状態に加え、店番交代時の引継ぎを「引継ぎ」として追加する。引継ぎは総合テストと受入テストで担保する | 境界: 在庫と同数の購入（BAC-01 の C-02）。例外: 在庫超過（BAC-02）。引継ぎ: 未確定の購入メモ |
| 判定軸   | 期待結果・観測点・合格条件を必ずそろえ、観測点は販売記録・在庫記録・引継ぎメモ・画面表示のいずれかとする             | 観測点「在庫記録」、合格条件「開始前との差分が販売数と一致すれば Pass、それ以外は Fail」     |

## 3. スコープ（対象/対象外）

対象:

- 現金販売の記録、確定前の取消、在庫不足・入力不足時の停止と引継ぎ（BAC-01〜BAC-03）
- 在庫数の確認、常連顧客のつけ残高の確認（AC-02）
- 会計確定後のレシート印刷と、印刷失敗時に会計を維持すること
- 記録の保全・復元と、応答欠落時の照合待ちの識別

対象外:

| 対象外の項目                                         | 委ねる先                                                       |
| ---------------------------------------------------- | -------------------------------------------------------------- |
| キャッシュレス決済、EC、仕入れ先とのシステム連携     | 初期リリースの対象外。プロジェクトスコープの改訂時に再判断する |
| プリンタ・ホスティング・保管サービス自体の可用性     | 各提供事業者の提供条件。障害時の業務継続は運用手順で扱う       |
| 通信不能時の販売継続                                 | 未決。「メモ / 将来課題」で決定後に総合テストへ追加する        |
| 運用開始後の欠品削減・在庫削減の効果（SC-04・SC-05） | 運用開始後の効果測定。テストの出口条件に含めない               |

## 4. テスト環境・テストデータ

| 環境区分 | 用途                       | 外部I/F の扱い                                                                                                                         |
| -------- | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 開発環境 | 単体テスト、内部結合テスト | 印刷と保管サービスはスタブ（外部I/F は原則スタブ）。内部結合テストでは記録サービスと DB を検証用に実接続し、単体テストではモックにする |
| 検証環境 | 外部結合テスト、総合テスト | 店舗プリンタの検証機と保管サービスの検証用領域を実接続する。本番 DB へは接続しない                                                     |
| 店舗端末 | 受入テスト                 | 本番相当の構成で実接続する。業務記録は受入用の店舗データ領域に分ける                                                                   |

外部I/F は、外部結合テストで導通と契約（印刷失敗・タイムアウト時の結果、保管失敗時の通知）を確認し、総合テストと受入テストでは主要シナリオ中のスモークまでを対象とする。応答欠落時の照合待ちの判定は内部経路（`PATH-02`）の故障であるため、遅延と無応答を再現できるスタブを使い内部結合テストで確認する。保全の取得（`PATH-04`）と復元の回復（`PATH-07`）は外部結合テストで確認し、復元の代表シナリオは総合テストでスモークまで確認する。

テストデータは、商品A（単価30円・在庫5個）を基準とする架空の商品・顧客を `kinuya-test-data` として共通化し、各テストの開始時に同じ状態へ戻す。実在の顧客名とつけ残高は使わず、受入テストでも架空の常連顧客で確認する。

## 5. 入口／出口条件（品質ゲート）

| テストレベル   | 入口条件（開始条件）                                               | 出口条件（完了条件）                                                                                                                     | エビデンス（根拠）                             | 判定者                 |
| -------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ---------------------- |
| 単体テスト     | 対象モジュールの設計がレビュー済みで、自動テストが CI で実行できる | 自動テストの失敗 0 件、計算・入力検証の境界条件の観点がすべて実装済み、Blocker・Critical・Major 0 件                                     | CI の実行結果                                  | DEV                    |
| 内部結合テスト | 単体テストの出口条件を満たす                                       | 記録の一致を確かめる観点の合格率 100%、Blocker・Critical 0 件、Major 2 件以下（各件の回避手順を QE が確認済み）                          | 内部結合テスト結果、DB 照合記録                | QE                     |
| 外部結合テスト | 内部結合テストの出口条件を満たし、検証機と検証用領域を使える       | 印刷・保管の契約観点（失敗・タイムアウトを含む）の合格率 100%、Blocker・Critical 0 件                                                    | 外部結合テスト結果、`receipt-print` の結果記録 | QE                     |
| 総合テスト     | 外部結合テストの出口条件を満たす                                   | BAC-01〜BAC-03 の全ケースが合格、ピーク1時間60取引の負荷で会計確定の応答 95% が2秒以内（仮置き基準）、Blocker・Critical 0 件、Major 0 件 | 総合テスト結果、性能測定記録                   | 判定: QE、例外承認: PM |
| 受入テスト     | 総合テストの出口条件を満たし、受入用データ領域を準備済み           | SC-01・AC-01〜AC-04 がすべて合格、Blocker・Critical・Major 0 件                                                                          | `kinuya-acceptance-record`                     | 判定: PO、照合: QE     |

総合テストで Major を残す場合に限り、PM が例外承認し、残課題を課題ログへ登録して受入テストの開始前に回避手順を両代表へ伝える。受入テストの出口条件には例外を設けない。

## 6. 自動化・回帰方針

- 会計計算、在庫引当、つけ残高計算は単体テストを自動化し、変更のたびに CI で全件を回帰する。架空の CI ジョブ `kinuya-ci-unit` で実行し、失敗が1件でもあれば merge しない。
- 販売記録と在庫・DB の一致、印刷失敗時の会計維持、応答欠落時の照合待ちは自動の回帰を必須とする。架空の CI ジョブ `kinuya-ci-sales-recovery` で実行し、記録サービス、印刷連携、保管サービス連携（記録の保全・復元を含む）のいずれかを変更した場合は merge 前に実行し、保全の取得と復元後の記録一致も回帰の範囲に含める。
- 画面の操作性と引継ぎメモの分かりやすさは手動で確認する。自動化しても利用者の理解は判定できないため、主要シナリオの探索テストで補う。

## 7. 不具合管理方針

| 重大度   | 判断観点                                 | 例                                                         |
| -------- | ---------------------------------------- | ---------------------------------------------------------- |
| Blocker  | テストを続けられない                     | 検証環境で販売画面を開始できない                           |
| Critical | 記録が欠ける・誤り、回避手段がない       | 会計確定後に販売記録が残らない、在庫が減らない             |
| Major    | 業務は続けられるが、回避手段の説明が必要 | 印刷失敗の警告が出ず、店番が控えの有無を確認する必要がある |
| Minor    | 記録と業務判断に影響しない               | 画面の文言の誤字                                           |

収束基準は、総合テストの最後の5営業日に Critical 以上の新規検出が 0 件であることとする。既知の不具合を残して次レベルへ進む場合は、「入口／出口条件（品質ゲート）」の例外承認に従う。
