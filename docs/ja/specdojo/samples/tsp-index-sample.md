# 駄菓子屋きぬや 販売管理システム テスト戦略・方針

## 1. 概要

駄菓子屋きぬや 販売管理システムの初期リリースについて、販売・在庫・つけの記録が欠けず、店主代表と家族利用者代表が同じ手順で照合できる品質を担保する。単一店舗・タブレット1台の店頭業務を、単体→内部結合→外部結合→総合→受入の順に確認する。各レベルの品質ゲートと、[[specdojo:bac-sample|現金販売の業務受入条件（BAC）]] の BAC-01〜BAC-03、[[specdojo:prj-success-criteria-and-acceptance-criteria-sample|成功基準（SC）と受入条件（AC）]] の初期受入の必須条件（SC-01・SC-07・SC-09・AC-01〜AC-05）に対応する証跡で合否を判定する。

守る業務は、販売・在庫・つけの記録と表示の一致、在庫不足や入力不足で販売を確定しないこと、つけ残高を1分以内に確認できることの3つである。誤りが残ると、ノートと記憶に頼る現状より記録が信用できなくなり、店主不在の店番を任せられなくなる。

`kinuya-` で始まる参照名は未同梱の架空成果物である。経路 `PATH-01`〜`PATH-07` は [[specdojo:ifd-sample|インフラ構成図]] の定義に従う。

性能は [[specdojo:sac-sample|システム受入条件（SAC）]] の `SAC-PERF-01`〜`SAC-PERF-04` と、[[specdojo:nfr-index-sample|非機能要件（NFR）]] の性能分冊（[[specdojo:nfr-performance-sample|性能要件]]）を総合テストの出口条件に接続する。会計確定の応答時間の正式な閾値は未確定のため、「メモ / 将来課題」の仮置き基準で判定する。

## 2. テストレベル一覧と観点/条件設計の共通原則

| -------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 単体テスト     | 金額・在庫・つけ残高の計算と入力検証、確定時の印刷要求が仕様どおりであること   | 会計計算、在庫引当、つけ残高計算、入力検証の各モジュール、印刷要求の回数と内容                                    | Developer（DEV）。自動テストで実施し、依存は「テスト環境・テストデータ」の方針で置き換える                    | 画面操作、DB の保存結果、外部I/F の実接続・契約確認                |
| 内部結合テスト | 画面・記録サービス・保全・復元処理と業務記録 DB の間で記録が欠けず一致すること | 店頭画面、販売・在庫・つけ記録サービス、保全・復元処理、業務記録 DB（`PATH-01`〜`PATH-03`・`PATH-04`・`PATH-07`） | DEV が実施し Quality Engineer（QE）が結果を照合。検証用 DB へ実接続し、レシート印刷はスタブにする             | 印刷コマンドと復元用保管サービスの契約確認は外部結合テストへ委ねる |
| 外部結合テスト | 自システム外の製品・サービスとの境界で契約どおり動くこと                       | `receipt-print` コマンド連携、復元用保管サービス（`PATH-05`・`PATH-06`。保全の転送と復元の読取）                  | DEV・QE。店舗プリンタの検証機と保管サービスの検証用領域を使う                                                 | 業務シナリオの網羅、プリンタ・保管サービス自体の可用性             |
| 総合テスト     | 店頭業務の主要シナリオがシステム全体で成立し、非機能基準を満たすこと           | BAC-01〜BAC-03、在庫・つけの記録更新と確認（AC-05・AC-02）、障害・回復、性能（日次締めを含む）                    | QE が実施し DEV が不具合を修正。本番相当環境で実接続する                                                      | 利用者の理解度・負担の判断                                         |
| 受入テスト     | 両代表が説明なしで主要業務を完了し、同じ記録を同じ結果で照合できること         | SC-01・SC-07・SC-09・AC-01〜AC-05 の代表シナリオと文書照合                                                        | Business Analyst（BA）が進行し、店主代表・家族利用者代表が操作する。DEV が文書照合を行い、QE が記録を照合する | 総合テストで合格した障害系・性能の再試験                           |

### 2.2. 観点/条件設計の共通原則

観点と条件を設計する際の定義粒度・分類・判定軸を、適用例とともに示す。

| 項目     | 本プロジェクトでの適用                                                                                                                                   | 例                                                                                           |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 定義粒度 | 1観点は対象処理の振る舞いについての1命題とし、条件は在庫数・入力の有無など1つの差分で分ける                                                              | 観点「在庫以内なら販売を確定する」／条件「在庫5個・購入2個」／期待結果「在庫3個・記録1件」   |
| 分類     | 正常・境界・例外・状態に加え、店番交代時の引継ぎを「引継ぎ」として追加する。引継ぎは総合テストと受入テストで担保する                                     | 境界: 在庫と同数の購入（BAC-01 の C-02）。例外: 在庫超過（BAC-02）。引継ぎ: 未確定の購入メモ |
| 判定軸   | 期待結果・観測点・合格条件を必ずそろえる。観測点はテストレベルに応じて、戻り値・依存の呼び出し・画面表示・販売/在庫/つけの記録・引継ぎメモ・ログから選ぶ | 観測点「在庫記録」、合格条件「開始前との差分が販売数と一致すれば Pass、それ以外は Fail」     |

## 3. スコープ（対象/対象外）

対象:

- 現金販売の記録、確定前の取消、在庫不足・入力不足時の停止と引継ぎ（BAC-01〜BAC-03）
- 入荷・棚卸・廃棄による在庫の更新、つけ購入・入金による残高の更新と、在庫数・つけ残高の確認（AC-05・AC-02）
- 会計確定後のレシート印刷と、印刷失敗時に会計を維持すること
- 記録の保全・復元と、応答欠落時の照合待ちの識別
- SAC の性能条件に従う会計確定・つけ残高確認・日次締めの性能測定

対象外の項目と、品質確認や判断を委ねる先を示す。

| 対象外の項目                                                   | 委ねる先                                                           |
| -------------------------------------------------------------- | ------------------------------------------------------------------ |
| キャッシュレス決済、電子商取引（EC）、仕入れ先とのシステム連携 | 初期リリースの対象外。プロジェクトスコープの改訂時に再判断する     |
| プリンタ・ホスティング・保管サービス自体の可用性               | 各提供事業者の提供条件。障害時の業務継続は運用手順で扱う           |
| 通信不能時の販売継続                                           | 未決。「メモ / 将来課題」で決定後に総合テストへ追加する            |
| 運用開始後に判定する成功基準（SC-02〜SC-06・SC-08・SC-10）     | 各成功基準の判定時期で効果を測定する。初期受入の出口条件に含めない |

## 4. テスト環境・テストデータ

### 4.1. 環境区分と用途

テスト環境ごとに、実施するテストレベルと外部I/F の扱いを示す。

| 環境区分 | 用途                       | 外部I/F の扱い                                                                                                                                                     |
| -------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 開発環境 | 単体テスト                 | DB はインメモリの Fake（状態を保持する代替実装）、記録サービスと保管サービスはスタブにする。印刷要求は回数と内容を検証するため、原則スタブの例外としてモックにする |
| 開発環境 | 内部結合テスト             | 記録サービスと DB は検証用に実接続し、印刷と保管サービスはスタブにする。遅延・無応答の確認では「I/F の確認範囲と代替方法」に従う                                   |
| 検証環境 | 外部結合テスト、総合テスト | 店舗プリンタの検証機と保管サービスの検証用領域を実接続する。本番 DB へは接続しない                                                                                 |
| 店舗端末 | 受入テスト                 | 本番相当の構成で実接続する。業務記録は受入用の店舗データ領域に分ける                                                                                               |

単体テストの依存の具体的な制御方法は [[specdojo:utc-index-sample|単体テストカタログ: 概要]] に従う。

### 4.2. I/F の確認範囲と代替方法

応答欠落時の照合待ちは、内部経路（`PATH-02`）の故障時に判定する。内部結合テストで、遅延と無応答を再現できるスタブを使って確認する。

保全の取得（`PATH-04`）と復元の回復（`PATH-07`）も業務記録 DB との内部経路であるため、内部結合テストで検証用 DB へ実接続して確認する。

外部I/F は、外部結合テストで導通と契約（印刷失敗・タイムアウト時の結果、保管失敗時の通知）を確認する。総合テストと受入テストでは、主要シナリオ中のスモークまでを対象とする。復元の代表シナリオは総合テストでスモークまで確認する。

### 4.3. テストデータ

テストデータは、商品A（単価30円・在庫5個）を基準とする架空の商品・顧客を `kinuya-test-data` として共通化する。各テストの開始時に同じ状態へ戻す。実在の顧客名とつけ残高は使わず、受入テストでも架空の常連顧客で確認する。

## 5. 入口／出口条件（品質ゲート）

各テストレベルの開始・完了条件と、合否判定に使う証跡・判定者を示す。

| テストレベル   | 入口条件（開始条件）                                                                         | 出口条件（完了条件）                                                                                                                       | エビデンス（根拠）                                                        | 判定者                                    |
| -------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- | ----------------------------------------- |
| 単体テスト     | 対象モジュールの設計がレビュー済みで、自動テストが継続的インテグレーション（CI）で実行できる | 自動テストの失敗 0 件、計算・入力検証の境界条件の観点がすべて実装済み、Blocker・Critical・Major 0 件                                       | CI の実行結果                                                             | DEV                                       |
| 内部結合テスト | 単体テストの出口条件を満たす                                                                 | 記録の一致を確かめる観点の合格率 100%、Blocker・Critical 0 件、Major 2 件以下（各件の回避手順を QE が確認済み）                            | 内部結合テスト結果、DB 照合記録                                           | QE                                        |
| 外部結合テスト | 内部結合テストの出口条件を満たし、検証機と検証用領域を使える                                 | 印刷・保管の契約観点（失敗・タイムアウトを含む）の合格率 100%、Blocker・Critical 0 件                                                      | 外部結合テスト結果、`receipt-print` の結果記録                            | QE                                        |
| 総合テスト     | 外部結合テストの出口条件を満たす                                                             | BAC-01〜BAC-03 の全ケースと `SAC-PERF-01`〜`SAC-PERF-04` が合格、AC-05 の更新結果が AC-02 の表示と一致、Blocker・Critical 0 件、Major 0 件 | 総合テスト結果、性能測定記録                                              | 判定: QE、例外承認: Project Manager（PM） |
| 受入テスト     | 総合テストの出口条件を満たし、受入用データ領域と操作メモを準備済み                           | SC-01・SC-07・SC-09・AC-01〜AC-05 がすべて合格、Blocker・Critical・Major 0 件                                                              | `kinuya-acceptance-record`（条件 ID・確認日・確認者・結果・証跡の保存先） | 判定: Project Owner（PO）、照合: QE       |

性能測定の前提・測定方法・合格基準は SAC の各条件に従う。会計確定の応答は記録サービスの要求受付から応答までとし、通信回線の遅延と印字時間を除く。会計確定の P99（`nfr-perf-002`）と商品検索の応答（`nfr-perf-004`）は、性能要件に従って値の記録のみとし、合否の閾値を設けない。

総合テストで Major を残す場合に限り、PM が例外承認する。その場合は残課題を課題ログへ登録し、受入テストの開始前に回避手順を店主代表と家族利用者代表へ伝える。受入テストの出口条件には例外を設けない。

## 6. 自動化・回帰方針

- 会計計算、在庫引当、つけ残高計算は単体テストを自動化し、変更のたびに CI で全件を回帰する。架空の CI ジョブ `kinuya-ci-unit` で実行し、失敗が1件でもあれば merge しない。
- 販売記録と在庫・DB の一致、印刷失敗時の会計維持、応答欠落時の照合待ちは自動の回帰を必須とする。保全の取得と復元後の記録一致も回帰の範囲に含める。記録サービス、印刷連携、保管サービス連携（記録の保全・復元を含む）のいずれかを変更した場合は、架空の CI ジョブ `kinuya-ci-sales-recovery` を merge 前に実行する。
- 画面の操作性と引継ぎメモの分かりやすさは手動で確認する。自動化しても利用者の理解は判定できないため、主要シナリオの探索テストで補う。

## 7. 不具合管理方針

不具合の重大度を、業務への影響と回避手段の有無で区分する。

| 重大度   | 判断観点                                 | 例                                                         |
| -------- | ---------------------------------------- | ---------------------------------------------------------- |
| Blocker  | テストを続けられない                     | 検証環境で販売画面を開始できない                           |
| Critical | 記録の欠落・誤りがあり、回避手段がない   | 会計確定後に販売記録が残らない、在庫が減らない             |
| Major    | 業務は続けられるが、回避手段の説明が必要 | 印刷失敗の警告が出ず、店番が控えの有無を確認する必要がある |
| Minor    | 記録と業務判断に影響しない               | 画面の文言の誤字                                           |

収束基準は、総合テストの最後の5営業日に Critical 以上の新規検出が 0 件であることとする。既知の不具合を残して次レベルへ進む場合は、「入口／出口条件（品質ゲート）」の例外承認に従う。

## 8. メモ / 将来課題

未確定の論点ごとに、影響する章・決定までの扱い・引き継ぎ先を示す。

| 論点                                     | 影響する章                         | 決定までの扱い                                                                                                              | 引き継ぎ先        |
| ---------------------------------------- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| _ASSUMPTION_: 会計確定の応答時間と処理量 | 入口／出口条件（総合テスト）       | NFR の会計確定の応答時間の閾値が未確定のため、放課後ピーク1時間60取引の負荷で会計確定の応答 95% が2秒以内を仮置き基準とする | `kinuya:pjr-i006` |
| _UNDECIDED_: 通信不能時の販売継続        | スコープ、テスト環境・テストデータ | 対象外として扱い、総合テストの合格をもって当該経路の受入とみなさない                                                        | `kinuya:pjr-i003` |

会計確定の仮置き基準では、単一端末で1分1取引を扱う負荷を仮定している。記録を後回しにしないため、応答待ちの許容時間を2秒と仮定する。この基準は、試用開始後の販売記録と店番担当の待ち時間の評価で見直す。
