# 移行テスト計画（移行リハーサル計画）: 駄菓子屋きぬや 販売管理システム

## 1. 概要（index）

商品ノートと常連客ノートを書き写した転記用の表を店頭タブレットへ取り込む移行（`mip-index`）を、切替日の前に 2 回リハーサルする。確かめるのは、取り込み・照合・動作確認が切替日の午前の臨時休業に収まること、つけ残高・件数・在庫数が元ノートと一致すること、移行後の端末で現金販売とつけ販売を記録できることの 3 点である。つけ残高を誤ると常連客への請求を誤って信用を失い、在庫数がずれると補充の判断を誤って欠品を招くため、本番の前に差異をなくしておく。

- 対象に含むもの: 商品台帳・現在庫・顧客台帳とつけ残高の取り込みと照合、取り込み後の動作確認、それらの所要時間。
- 対象に含まないもの: 最終棚卸の数え方、並行記録の 1 週間と正本切替（`otp-index` で確かめる）、移行しない過去の販売ノート・仕入ノート・つけ販売の明細。

## 2. リハーサル回数とスケジュール

切替日は第 1 回の前に仮置きし、第 2 回の結果を見て確定するか延期する（GO/NO-GO判断プロセス）。予定日は仮置きの切替日からの相対日で示す。

| 回数               | 予定日                                  | 目的                                                                                     | 完了条件                                                                               |
| ------------------ | --------------------------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 第 1 回            | 切替日の 10 日前（定休日の午前）        | 3 対象の取り込みから動作確認までを通しで行い、手順の抜けと手順ごとの所要時間を測る       | 全手順を最後まで実施し、手順ごとの所要時間と差異を結果報告に記入した（合否は問わない） |
| 第 2 回            | 切替日の 3 日前（定休日の午前）         | 第 1 回の是正を反映し、切替日の午前と同じ順序・同じ時刻の流れで行う                      | 合否基準のすべての項目が合格し、結果報告に GO/NO-GO 案を記入した                       |
| 追加（必要時のみ） | 切替日の 2 日前の閉店後まで（1 回まで） | 第 2 回で不合格だった項目について、原因を直したうえで第 2 回と同じ手順で通しを再実行する | 合否基準のすべての項目が合格した。上限を超えたら NO-GO とし、追加の回は設けない        |

- _ASSUMPTION_: 定休日は週 1 日あり、第 1 回と第 2 回はその午前に行う。来店客がいない時間に端末を使えるためである。
- _UNDECIDED_: 仮置きの切替日と定休日の曜日。第 1 回の予定日が決まらないため、店主代表が準備フェーズの開始前に決める。

## 3. テスト環境/データ準備

リハーサルは本番と同じ端末で行うが、本番の台帳には書き込まない。

| 項目             | 内容                                                                                                                                                                        |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 環境             | 店頭タブレット 1 台と販売管理システム。取り込み先はリハーサル用の保存先とし、本番の台帳と分ける                                                                             |
| 前提設定         | 移行作業フォルダ `migration/<run_id>/` が作れる、残高一覧と在庫一覧を印刷できる、端末の画面ロックが有効である                                                               |
| データセット ID  | `MTP-DS-R1`: 準備フェーズで読み合わせ済みの転記用の表の写し。`MTP-DS-R2`: 第 1 回の是正を反映した写し（追加の回も同じ ID を使い、直した行を備考欄に残す）                   |
| 在庫の照合元     | 前日の閉店後の商品ノートの記入から作った練習用の在庫記入表。リハーサルのために棚卸はしない                                                                                  |
| `run_id`         | `dmd-index` の規約（`DMD-YYYYMMDD-<term>-NN`）に従う。日付の部分でリハーサルと本番を区別する                                                                                |
| 初期化           | 各回の開始時に、リハーサル用の保存先の商品台帳・在庫・顧客台帳・つけ残高を空にする（洗い替え）                                                                              |
| 後始末           | 各回の終了時に、リハーサル用の保存先の台帳を空にする。取り込み用ファイル・ログ・照合表は `migration/<run_id>/` に残し、紙の照合表は店頭台帳保管棚の鍵付きの引き出しにしまう |
| データ準備の担当 | DEV。手順は `dmd-index` の移行手順と対象別の `dmd-<term>`（顧客台帳とつけ残高は `dmd-credit-data`）に従う                                                                   |

- _ASSUMPTION_: 販売管理システムは本番の台帳と分けたリハーサル用の保存先を持つ。持たない場合は、各回の後始末で本番の台帳を空にしたことを確かめる手順を追加する。

## 4. 検証観点（件数/差分/業務シナリオ）

取り込みのたびに次の表の観点をすべて確かめ、期待値を満たさない行を差異として結果報告に書く。許容差は `dmd-index` の検証の共通方針と同じ値を使う。

| 観点                              | 方法                                                                                                                       | 期待値                                                                     |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 件数照合（商品台帳・顧客台帳）    | 転記用の表の行数（除外欄を除く）と、取り込みログの投入件数を対象ごとに比べる                                               | 差分 0 件                                                                  |
| 件数照合（つけ残高）              | 転記用の表で残高が 0 円でない行の数と、つけ残高の投入件数を比べる                                                          | 差分 0 件                                                                  |
| 差分検知（サンプル）              | 元ノートの各ページから 1 行ずつ選び、画面に出る同じ記録のすべての項目と突き合わせる                                        | 差分 0。商品名・氏名の全角と半角、長音記号の違いだけは差分に数えない       |
| 差分検知（重要値: つけ残高）      | 印刷した残高一覧と元ノートのつけ欄の最終行を、全顧客について比べる                                                         | 顧客ごとの残高と合計の差異がともに 0 円                                    |
| 差分検知（重要値: 在庫数）        | 印刷した在庫一覧と練習用の在庫記入表を、全商品について比べる                                                               | 全商品で差異 0 個                                                          |
| 業務シナリオ（現金販売→取消）     | 店主代表が取り込んだ商品を 1 個現金販売し、販売記録を確かめてから取り消す                                                  | 販売記録が 1 件でき、取消の後に在庫数が販売前の数に戻る                    |
| 業務シナリオ（つけ販売→残高確認） | 家族利用者代表が残高のある顧客 1 人に 100 円のつけ販売を記録し、顧客を検索して残高を表示する                               | 残高が取り込み時の値より 100 円多い。顧客の検索から残高の表示まで 1 分以内 |
| 所要時間                          | 手順（書き出し・取り込み・照合・動作確認）ごとに開始と終了の時刻を移行作業の記録表に書き、取り込み直しの時間も別に記録する | 手順ごとの実測が残り、合否基準の所要時間と比べられる                       |

## 5. 合否基準

各回の結果は次の表で判定し、すべての項目が合格した回を合格とする。

| 項目           | 基準                                                                                                                      | 判定者 |
| -------------- | ------------------------------------------------------------------------------------------------------------------------- | ------ |
| 所要時間       | 3 対象の書き出し・取り込み・照合と動作確認の合計に、取り込み直し 1 回分を足した時間が、臨時休業の開始から正午までに収まる | OPS    |
| 件数差異       | 商品台帳・顧客台帳・つけ残高のいずれも 0 件                                                                               | DEV    |
| サンプルの差分 | 許容差（表記ゆれ）を除いて 0                                                                                              | QE     |
| つけ残高の差異 | 顧客ごとの残高と合計がともに 0 円                                                                                         | PO     |
| 在庫数の差異   | 全商品で 0 個                                                                                                             | PO     |
| 業務シナリオ   | 現金販売→取消、つけ販売→残高確認の 2 つがともに期待値どおり                                                               | PO     |
| 重大障害       | 0 件。取り込みが途中で止まり台帳が一部だけになる、本番の台帳へ書き込む、販売またはつけを記録できない、のいずれかを指す    | PO     |

- 判定者は件数を `mip-index` の成功条件と同じ役割にそろえ、つけ残高・在庫数は請求と補充に直結するため PO とする。
- _UNDECIDED_: 臨時休業の開始時刻。所要時間の基準が決まらないため、店主代表が第 1 回の実測を見て第 2 回の前までに決める。

## 6. 差異発生時の扱い（許容/修正/再実行）

差異は次の区分で扱い、判定者がその回の結果報告までに管理記録へ転記する。

| 区分                                                         | 扱い                                                                                                                            | 判定者 | 管理記録への転記                                            |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | ------ | ----------------------------------------------------------- |
| 許容差内（商品名・氏名の表記ゆれ）                           | 照合表に記録して合格とする。直す場合は次の回のデータセットに反映する                                                            | QE     | 転記しない                                                  |
| 許容差超（件数・残高・在庫・サンプルの差分、所要時間の超過） | 原因（書き写しの誤り、除外の誤り、手順の抜け）を特定して転記用の表か手順を直し、同じ回の中で別 `run_id` で 1 回まで取り込み直す | QE     | 差異と原因を `pm-issue-log` へ                              |
| 重大障害                                                     | その回を中止する。DEV が原因を切り分け、直るまで次の回を始めない                                                                | PO     | 障害を `pm-issue-log` へ、中止の判断を `pm-decision-log` へ |
| 原因が未解決のまま回を終えた差異                             | 次の回の開始前までに原因と直し方を決める。決まらなければ次の回を延ばす                                                          | QE     | `pm-issue-log` の課題を開いたままにする                     |

- 再実行の上限: 追加の回の回数と期限はリハーサル回数とスケジュールの表に従う。追加の回を行うかは PO が判断し、その判断を `pm-decision-log` へ転記する。

## 7. 結果報告フォーマット

結果は回ごとに次の項目で書き、報告先は店頭タブレットの `migration/rehearsal/` に置く回ごとの結果報告（`MTP-R<n>-report`）とする。本書には書き足さない。

| 項目        | 記載内容                                                                                          |
| ----------- | ------------------------------------------------------------------------------------------------- |
| 回数・日時  | 第何回か、開始と終了の日時、使ったデータセット ID と対象ごとの `run_id`                           |
| 結果        | 合否基準の項目ごとの合否と判定者、回としての合否                                                  |
| 差異        | 差異ごとの対象・内容・区分・原因・扱いと、転記した `pm-issue-log` の課題 ID                       |
| 所要時間    | 手順ごとの実測と `dmd-*` の見積との差、取り込み直しの有無と時間                                   |
| 証跡        | 照合表（`<run_id>-check-count`・`<run_id>-check-sample`・`<run_id>-check-value`）と動作確認の記録 |
| GO/NO-GO 案 | GO・条件付き GO・NO-GO のどれを提案するかと、その理由                                             |
| 未決事項    | 論点と、切替日の確定や当日の手順への影響                                                          |

## 8. GO/NO-GO判断プロセス

QE が第 2 回（追加の回を含む）の結果報告・差異一覧・所要時間を集約し、PO が営業後の週 1 回の判断の場で次の条件により判断する。急ぐ場合は店頭で判断してよい。判断の結果と理由は `pm-decision-log` へ記録する。

- GO: 合否基準のすべての項目が合格した。仮置きの切替日を確定し、`cop-index` の当日手順へ進む。
- 条件付き GO: 所要時間・件数・つけ残高・在庫数・重大障害が合格し、残った差異の原因と直し方が分かっていて、切替日の前日の読み合わせで直したことを確かめられる。条件と確認の期限を決定記録に書いて切替日を確定する。
- NO-GO: 重大障害が残る、再実行の上限を超えた、または所要時間が臨時休業に収まらない。切替日を延期し、PO が日程を決め直してリハーサルを計画し直す。
