# 駄菓子屋きぬや 商品販売機能仕様

## 1. 目的と概要

店主代表と家族利用者代表が、店頭のタブレットから現金販売を記録し、請求額・釣銭と在庫への反映結果を同じ取引で確認できるようにする。ノートへの転記漏れと暗算の誤りを減らし、店番が交代しても販売・在庫の記録を継続する。これは [[specdojo:prj-overview-sample|プロジェクト概要]] の「まず記録する」方針と、日々の記録を定着させる目標に対応する。

| 区分   | 範囲                                                                                                                                                    |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 対象   | 単一店舗の現金販売。商品・数量の登録と修正、税額・請求額・釣銭の提示、販売記録の確定、在庫反映結果の確認、レシート発行要求、確定前の取引中止            |
| 対象外 | つけ販売と精算、キャッシュレス決済、確定後の返品・値引訂正、補充判断・物理的補充、EC・複数店舗。つけ販売は業務領域 `P-04`、補充判断は `P-06` へ委譲する |

利用者は店主代表・家族利用者代表、設計入力として読む者は ARC・DEV、受入条件を確認する者は QE である。BA は業務境界、UX は表示と誤操作からの回復、OPS は障害時の照合方法を確認する。役割と兼務の正本は [[specdojo:pm-organization-sample|組織定義]] と [[specdojo:pm-roles-sample|ロール定義]] とする。

公開対象は店舗内の運用者と開発・レビュー担当であり、実顧客の情報や認証情報は含めない。人間の PO（店主代表）がスコープ・受入条件・公開可否を最終判断する。

## 2. 業務プロセス・画面との対応

業務境界は [[specdojo:cdfd-overview-sample|概念データフロー図（全体概要）]] の店頭販売 `P-03` と在庫確認 `P-05` に対応する。詳細 BPS `bps-sales-order-flow` は未作成のため、次表は領域単位の対応とし、処理ステップ ID の照合は未決事項 `Q-01` で追跡する。

| 根拠領域        | 本機能の責務                                                                             | 対応要件・入出力                             |
| --------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------- |
| `P-03` 店頭販売 | 購入商品と数量を受け、会計に使う明細と請求額を提示する                                   | `FR-01`・`FR-02`、商品情報・購入明細・請求額 |
| `P-03` 店頭販売 | 現金の受領確認を受け、販売を記録して完了可否を返す                                       | `FR-03`、預かり金・販売記録・会計結果        |
| `P-05` 在庫確認 | 販売による払出数量を渡し、反映結果を会計結果へ対応付ける。在庫の算出・補充要否は委譲する | `FR-03`、販売確定情報・在庫反映結果          |
| `P-03` 店頭販売 | 確定前の取引中止を受け、未確定の明細を破棄する                                           | `FR-04`、取引中止結果                        |

| 接点                                   | トリガー・受け渡し                                                           | 責務境界                                                                       |
| -------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| [[specdojo:uis-sample\|販売登録画面]]  | 商品追加・数量修正・会計確定・取引中止を受け、明細・金額・結果を返す         | 表示配置・入力形式・画面遷移は UIS、会計の確定可否は本機能が担う               |
| 在庫確認機能 `sf-inventory`            | 販売を識別する情報と払出数量を渡し、反映済み・未反映・結果不明の区別を受ける | 在庫更新は連携先、本機能は未反映・結果不明を販売完了と通知しない               |
| レシート出力 `ifx-cmd-receipt-printer` | 確定した販売の印字内容を渡し、印刷結果を受ける                               | 印刷失敗は販売確定と区別する。起動契約・再印刷手順は連携仕様と運用手順へ委ねる |

利用接点は GUI とし、CLI による会計は対象外とする。未作成の在庫連携・印刷契約は `Q-01` で詳細化する。

| 出力 | 会計結果、停止理由、取引中止結果、印字内容   | 本機能 / 店番担当・レシート出力             | 完了・保留・中止と印刷成否を識別できること         | [[specdojo:uis-sample\|販売登録画面]]、`ifx-cmd-receipt-printer`               | `FR-03`・`FR-04` |

売上記録と明細の管理単位は業務データ辞書を正本とし、データ項目・型・コード値を本書へ転記しない。未作成の税計算・連携契約と物理データの schema・版の確定は `Q-01` の対象とする。

### 3.2. 前提条件と事後条件

- 着手条件: 店番担当が販売権限で利用でき、商品台帳と店舗内の記録先へ接続できること。進行中の取引があればその取引を継続し、別の取引を重ねて開始しない。
- 事後条件: 正常完了時の記録・反映の保証は「通常処理」の `FR-03`、確定前の中止は `FR-04`、保留・失敗時の保持と回復条件は「例外・回復条件」に従う。印刷成否は会計結果と分けて判定する。

## 4. 処理要件・機能振る舞い

### 4.1. 通常処理

| 要件 ID | 開始条件                                         | 処理の責務・確定する結果                                                                                                                                     | 判断の正本                                                                     |
| ------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| `FR-01` | 販売取引で商品・数量を受けた                     | 商品と在庫を照合し、明細の追加・修正・削除に応じて表示を更新する。未登録商品や販売不可の数量は理由を返し、既存明細を維持する                                 | [[specdojo:uis-sample\|販売登録画面]] の入力条件                               |
| `FR-02` | 有効な明細がある                                 | 税計算の結果から税額・請求額を提示し、預かり金から釣銭を求める。明細が空、または預かり金が不足している間は確定を受け付けない                                 | `br-tax-calculation`、販売登録画面の会計条件                                   |
| `FR-03` | 店番担当が現金の受領を確認し、会計確定を要求した | 販売時の単価・数量を売上記録へ残し、在庫反映結果を照合する。両方を確認した後に販売完了を返し、レシート発行を要求する。完了済みの要求の再送では元の結果を返す | [[specdojo:bdd-sample\|業務データ辞書]]、`sf-inventory`、`ifx-api-store-sales` |
| `FR-04` | 確定前に取引中止の確認を受けた                   | 未確定の明細を破棄し、中止結果を返す。確定中・結果不明の取引は照合へ引き渡し、取消済みと扱わない                                                             | 販売登録画面、`stsd-sales-transaction`                                         |

商品の販売済みへの遷移は [[specdojo:stsd-sample|商品 ステータス定義]] を参照する。画面上の販売完了通知と、店番担当による釣銭・商品の手渡しは別であり、システムは顧客受領を推測しない。取引自体の状態・遷移は `stsd-sales-transaction` で詳細化する（`Q-01`）。

### 4.2. 例外・回復条件

| 条件                                             | 通知と保持する情報                                                                                             | 回復・再開条件                                                                                                                                   |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 未登録商品、数量不正、在庫不足                   | 対象商品と不成立の条件を通知する。拒否した変更を明細・販売記録・在庫に反映しない                               | 店番担当が商品または数量を修正し、`FR-01` で再照合する                                                                                           |
| 明細なし、預かり金不足・入力不正                 | 確定不可と理由を返し、有効な明細を維持する                                                                     | 明細追加または預かり金の補正後に `FR-02` から確認する                                                                                            |
| 保存・在庫反映が失敗、または応答が途絶え結果不明 | 完了通知を出さず、取引と停止位置、保存・反映状況を保持する。入力済みの情報を回復に使い、自動で別取引を作らない | OPS が同じ取引の販売記録と在庫を照合する。確定済みなら結果を再提示し、未完了なら未反映部分だけを再開する。照合できるまで再確定・中止を許可しない |
| 会計完了後の印刷失敗                             | 会計完了と印刷未完了を分けて通知し、確定済みの販売記録と印字内容を保持する                                     | 店番担当がプリンタの回復後に同じ販売の再印刷を要求する。売上・在庫を再更新しない                                                                 |

| 契約・互換性       | 画面、記録先、在庫連携、印刷先の契約を ARC が照合する。schema・版・再送契約の不一致があれば統合受入を保留する          | `Q-01`。業務データ辞書は論理定義、物理構造と公開契約は連携仕様・schema を正本とする                                |

## 6. 操作手順・コマンド参照

| 参照先                                | 種類     | 参照目的                                                                         |
| ------------------------------------- | -------- | -------------------------------------------------------------------------------- |
| [[specdojo:uis-sample\|販売登録画面]] | 画面仕様 | 商品登録・修正、預かり金確認、確定・中止の操作と入力形式                         |
| `opr-pos-operation`                   | 運用手順 | 店番交代時の確認、利用権限の設定、釣銭・商品の手渡し、印刷失敗時の再印刷         |
| `opr-sales-recovery`                  | 回復手順 | 取引結果不明時の記録・在庫の照合、部分失敗の再開、障害記録と代替運用への切替判断 |

一次対応は店番担当が行い、会計結果不明・記録不一致・再印刷不能は OPS に引き渡す。OPS は `opr-sales-recovery` で照合し、契約不一致・不具合なら ARC・DEV、営業継続への影響なら PM・PO へ報告する。未作成の運用手順は `Q-02` の承認条件とする。

仕様変更時は BA が業務対応、ARC・DEV が入出力・在庫連携・schema・画面への影響、QE が受入条件、OPS が運用手順への影響を確認する。PM は要件単位と受入条件を成果物カタログ・Schedule に接続し、進捗は実行結果、課題・変更判断は PJR・レビュー記録で追跡する。

### 7.2. 文書の完成判定と承認

文書検査は利用リポジトリの package・hook 設定に従い、Markdown 整形、Markdown lint、Frontmatter・参照検査の対象・コマンド・結果を実行記録に残す。適用検査のエラーがなく、主要要件と受入条件が対応し、カタログの完了条件を確認できることを文書の完成条件とする。

BA・ARC・DEV・QE・OPS は各合意対象と未充足条件をレビュー記録へ残す。PO は未決事項・未解決指摘と公開範囲を確認し、承認・保留・差し戻しを記録する。`Q-01`・`Q-02` の承認条件が未充足の間は `draft` を維持する。文書検査の成功、作業タスクの完了、機能受入、製品リリースはそれぞれ別に判断する。
