# 駄菓子屋きぬや 販売管理システム 運用手順（運用変更）

## 1. 概要

本書は [[specdojo:opr-sample|運用手順]]（`opr-index`）の運用変更作業を具体化する `opr-change` であり、証跡・優先度・承認の規約は `opr-index` に従う。駄菓子屋きぬや 販売管理システムのアプリの版の更新・商品マスタと価格の一括変更・表示の修正を、翌営業日の販売・在庫・つけの記録を止めずに適用し、問題があれば開店前に戻せる状態を作る。変更の承認者と戻す条件の基準は [[specdojo:opd-index-sample|運用方針・設計（全体構成）]] の変更管理に従い、本書は手順だけを書く。

次の表は、運用変更で未決の値が本書のどの手順に影響し、決まるまでどう扱うかを示す。値が決まった時点で該当する章の実施条件と完了条件を差し替える。

| 未決事項                                    | 決まるまでの手順上の扱い                                    | 影響する章         |
| ------------------------------------------- | ----------------------------------------------------------- | ------------------ |
| _UNDECIDED_: 変更の凍結期間（繁忙期の扱い） | 凍結期間を置かず、閉店後であれば変更できるものとする        | 手順適用範囲・前提 |
| _UNDECIDED_: ロールバック完了の目標時間     | 翌営業日の開店前の確認（9:45 から）までに戻せれば合格とする | 運用変更作業       |
| _UNDECIDED_: 変更記録の保管期間             | 変更記録を消さない                                          | 証跡               |

## 2. 手順適用範囲・前提

次の表は、本書の手順が対象とする変更と、手順を行う前提を示す。

| 項目     | 内容                                                                                                                         |
| -------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 対象     | 本番のアプリの版の更新、商品マスタ・価格の一括変更、記録に影響しない表示の修正、P1 の復旧に要る緊急の変更                    |
| 対象外   | 権限・アカウントの変更（[[specdojo:opr-access-control-sample\|アカウント付与・剥奪]]で扱う）、1 商品ずつの店頭での価格の修正 |
| 時間帯   | 閉店後（18:00 以降）に適用し、翌営業日の開店前の確認（9:45 から）までに完了または戻しを終える                                |
| 凍結期間 | 概要の未決事項の表に従う                                                                                                     |
| 必要権限 | 適用と戻しは `DEV` の管理者の権限、適用後の確認は店番担当の記録の権限で行う                                                  |
| 使用手段 | 本番のホスティング環境、検証用の環境、プロジェクトの課題管理（変更記録）、店内の掲示と操作メモ                               |
| 連絡先   | 適用中の異常は `DEV` から `OPS`、`OPS` が 15 分以内に応答しなければ `PO`                                                     |

手順を新しく書いたときや改訂したときは、検証用の環境でアプリの版の更新とロールバックを 1 回ずつ模擬し、変更記録の項目が運用変更作業の表のとおりに残ることを確かめる。結果は証跡の章の手順の確認の記録に残す。

## 3. 日次・週次・月次点検手順

`opr-index` 参照。変更の適用件数とロールバックの件数は、`opr-index` の月次点検で変更記録から集計する。

## 4. 障害対応手順

`opr-index` 参照。変更が原因の障害の扱いは、運用変更作業のエスカレーションの表に書く。

## 5. アラート対応手順

`opr-index` 参照。アラートの恒久対応で行う修正は、本書の運用変更作業の手順で適用する。

## 6. バックアップ確認・リストア手順

`opr-index` 参照。本書では、データの形が変わる版の更新の前に手動で取るバックアップだけを運用変更作業の手順に書く。

## 7. バッチ再実行・失敗時対応

本書の範囲外。変更の作業に定期のバッチは含まれないため。

## 8. 運用変更作業

### 8.1. 変更種別と承認・実施条件

次の表は、変更の種類ごとの承認者と、適用・完了・戻しの条件を示す。承認者と戻す条件は運用方針の変更管理と同じとする。

| 変更種別                   | 承認者 | 実施条件                                            | 完了条件                                                  | ロールバック条件                           | 証跡                         |
| -------------------------- | ------ | --------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------ | ---------------------------- |
| アプリの版の更新           | `PO`   | 閉店後。前日の閉店時までに事前周知を済ませた        | 本番で販売・在庫・つけを各 1 件記録し、取り消せた         | 適用後の確認で 3 件のどれかを記録できない  | 変更記録（差分、承認、実施） |
| 商品マスタ・価格の一括変更 | `PO`   | 閉店後。前日の閉店時に店内で掲示した                | 翌朝の開店前に店番担当が 3 商品の価格を変更記録と照合した | 開店前の確認で変更記録と違う価格が見つかる | 変更記録（差分、承認、実施） |
| 記録に影響しない表示の修正 | `OPS`  | 閉店後                                              | 修正した画面で 1 件記録できた                             | 表示の崩れで記録の操作ができない           | 変更記録（差分、実施）       |
| P1 の復旧に要る緊急の変更  | `PO`   | 営業時間中も可。`PO` が電話で承認し、後で記録に書く | P1 の復旧条件（`opr-index` の障害対応手順）を満たした     | 適用後も P1 の状態が続く、または悪化する   | 変更記録（差分、承認、実施） |

### 8.2. 影響の範囲の判定

変更を起票したら、`DEV` が次の表の確かめることを順に見て、影響の範囲と変更種別を決める。1 つでも「影響あり」なら、表示の修正として扱わず `PO` の承認を求める。

| 確かめること                                   | 影響ありとする条件                           | 決まること                         |
| ---------------------------------------------- | -------------------------------------------- | ---------------------------------- |
| 販売・在庫・つけの記録の画面や操作が変わるか   | 操作の手順・ボタンの位置・入力の項目が変わる | アプリの版の更新、事前周知が要る   |
| 保存する記録の形（項目の追加・削除）が変わるか | 記録の項目が増える・減る・意味が変わる       | 適用前の手動バックアップが要る     |
| 日次締めの金額や件数の計算が変わるか           | 締めの合計や差の出し方が変わる               | 翌朝の確認に日次締めの照合を加える |
| 商品の価格・名前が店頭の値札と変わるか         | 1 商品でも価格・名前が変わる                 | 商品マスタ・価格の一括変更         |

### 8.3. 適用の手順

1. 起票: `DEV` が変更記録を起票し、変更の目的、差分、影響の範囲の判定、戻し方を書く。
2. 検証: `DEV` が検証用の環境に適用し、販売・在庫・つけを各 1 件記録できることと、戻し方で元に戻せることを確かめ、結果を変更記録に書く。
3. 承認: 変更種別の表の承認者が、変更記録の差分・判定・検証の結果を見て適用してよいかを決め、日付とともに変更記録に書く。
4. 事前周知: 操作が変わる版は店内の操作メモを更新し、価格の一括変更は値札の差し替え一覧とともに、前日の閉店時に店内で掲示する。
5. 適用: `DEV` が閉店後に、データの形が変わる版なら手動のバックアップを取ってから適用し、適用の開始・終了の時刻と版を変更記録に書く。
6. 確認: `DEV` が変更種別の表の完了条件を確かめる。価格の一括変更は翌朝の開店前に店番担当が照合する。
7. 完了: 完了条件を満たしたら、`DEV` が変更記録を完了にする。満たさなければロールバックへ進む。

### 8.4. ロールバックとエスカレーション

ロールバック条件に当たったら、`DEV` は原因を調べる前に直前の版や変更前の価格へ戻す。戻した後に適用の確認と同じ操作をして、変更前と同じく記録できれば戻しの完了とし、戻した理由を変更記録に書く。データの形が変わる版で戻せない場合は、適用前の手動バックアップから復元する。

次の表は、戻しの途中で起きたことと、報告先・期限の対応を示す。

| 起きたこと                                       | 報告先           | 期限                   | その後の扱い                                      |
| ------------------------------------------------ | ---------------- | ---------------------- | ------------------------------------------------- |
| 戻しが完了した                                   | `OPS`            | 翌朝の開店前           | 原因を直した変更を、起票からやり直す              |
| 開店前の確認の時点で戻しが終わらない             | `OPS`、次に `PO` | 気付いてから 15 分以内 | P1 として `opr-index` の障害対応手順へ進む        |
| 戻した後も販売・在庫・つけのどれかを記録できない | `OPS`、次に `PO` | 気付いてから 15 分以内 | P1 として障害対応手順へ進み、変更記録に経緯を書く |

`OPS` は、月次点検で当月の変更件数・ロールバックの件数とその理由を `PO` へ報告する。

## 11. 証跡

次の表は、変更の各段階の証跡をどこに残し、どの識別子で照合するかを示す。

| 証跡種別         | 保存先                               | 保管期間           | 参照権限           | 最低限残す識別子                        |
| ---------------- | ------------------------------------ | ------------------ | ------------------ | --------------------------------------- |
| 変更記録         | プロジェクトの課題管理               | 概要の未決事項参照 | `OPS`、`DEV`、`PO` | `ticket_id`、変更種別、適用する版       |
| 差分             | プロジェクトのリポジトリ             | 概要の未決事項参照 | `OPS`、`DEV`、`PO` | `ticket_id` を書いた変更の識別子        |
| 承認の記録       | 変更記録の承認の欄                   | 変更記録と同じ     | `OPS`、`DEV`、`PO` | `ticket_id`、承認した役割、承認日       |
| 実施ログ         | 変更記録の実施の欄                   | 変更記録と同じ     | `OPS`、`DEV`、`PO` | `ticket_id`、開始・終了の時刻、確認結果 |
| 手動バックアップ | ホスティング環境のバックアップの記録 | `opr-index` 参照   | `OPS`、`DEV`       | `run_id`、`ticket_id`                   |
| 手順の確認の記録 | 月次点検の記録                       | `opr-index` 参照   | `OPS`、`PO`        | `ticket_id`、確認日、確認環境、合否     |

戻した変更も、完了した変更と同じ `ticket_id` で戻しの時刻と理由を実施ログに残す。
