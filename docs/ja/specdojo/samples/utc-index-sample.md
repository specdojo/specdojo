# 単体テストカタログ: 概要（駄菓子屋きぬや 販売管理システム）

## 1. 本ドキュメントの目的と適用対象

駄菓子屋きぬや 販売管理システムの初期リリースについて、対象別の単体テストカタログ `utc-<term>` の分け方・観点と条件の立て方・依存の扱い・ケース表の書き方をそろえる。[[specdojo:tsp-index-sample|テスト戦略・方針]] の単体テスト（会計計算、在庫引当、つけ残高計算、入力検証の各モジュール）を範囲とし、内部結合以降の確認は各レベルの `*c-index` で扱う。

本書で防ぐのは、会計金額・在庫減算・つけ残高の計算誤りが内部結合テストまで持ち越されることである。計算誤りが残ると販売記録と在庫が一致せず、店主代表が記録を信用できなくなる。

| 利用場面                  | 本書を使う判断                                                     |
| ------------------------- | ------------------------------------------------------------------ |
| `utc-<term>` の作成・追加 | 括り方・採用基準・依存の扱いを決める                               |
| `utc-<term>` のレビュー   | 分配の重複・期待値の判定可能性を照合する                           |
| 依存の扱いの例外          | 例外の根拠と依存の制御方法が本書の扱いに収まるかを判断する         |
| 観点の採用                | 業務影響を根拠に採用した観点が、守る業務と一致しているかを確かめる |

単体テストの合否は [[specdojo:tsp-index-sample|テスト戦略・方針]] の品質ゲートに従い、CI ジョブ `kinuya-ci-unit`（架空）の失敗 0 件と、境界条件の観点がすべて実装済みであることを DEV が判定する。

## 2. テスト対象の括り方と分割基準

`<term>` は責務境界で切り、同時に変更されやすい計算と状態更新を同じ単位に収める。初期リリースの括り方は次のとおりとする（各 `utc-<term>` は未同梱の架空成果物）。

| `utc-<term>`         | 責務のまとまり                                       | 依存の扱い                        | 括った理由                                               |
| -------------------- | ---------------------------------------------------- | --------------------------------- | -------------------------------------------------------- |
| `utc-sales-checkout` | 請求額・釣銭の計算と、会計確定時の在庫引当           | 商品・在庫リポジトリは Fake       | 金額と在庫減算は BAC-01 で同時に確定し、同時に変更される |
| `utc-sale-input`     | 商品・数量の入力検証と、不足時に未確定で保留する判定 | 依存なし（純関数）                | BAC-03 の停止判定だけを持ち、依存境界が他と異なる        |
| `utc-credit-balance` | つけの加算・入金後の残高計算                         | 顧客リポジトリは Fake、時刻は固定 | 残高は日付を伴い、時刻依存の扱いが会計と異なる           |

- 在庫不足の判定（BAC-02）は在庫引当と同じ在庫データを使うため `utc-sales-checkout` に含め、独立した term にしない。
- 1 term の観点が 15 以上、ケース表が 50 行以上になった場合は分割を検討する。
- 画面の部品（会計ボタン、数量入力欄）では切らない。画面の操作は総合テストで扱う。

## 3. 対象外・除外理由（共通）

| 対象外（やらないこと）                   | 除外理由                           | 代替レベル/代替手段                                            | 例外（UTで扱う条件）                                   |
| ---------------------------------------- | ---------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------ |
| 店頭画面の操作・表示                     | ロジック検証を逸脱する             | 総合テスト、受入テスト                                         | 金額表示の書式変換（例: 1200 → `1,200円`）の純関数のみ |
| 業務記録 DB への保存結果と照合           | 実接続が必要で、環境で結果が揺れる | 内部結合テスト（`PATH-01`〜`PATH-03`）                         | なし                                                   |
| `receipt-print` コマンドと保管サービス   | 外部要因で結果が揺れる             | 外部結合テスト（`PATH-05`・`PATH-06`）                         | 印刷要求データへの変換のみ                             |
| 会計確定の応答時間と放課後ピークの処理量 | 測定条件が単体の実行環境と異なる   | 総合テスト（性能測定）                                         | なし                                                   |
| 通信不能時の販売継続                     | 初期リリースで扱うか未決である     | どのレベルでも担保しない（決定まで受入は保留。決定後に再判断） | なし                                                   |

例外を適用する `utc-<term>` は、ケース表の `境界/依存` に適用した例外と依存の制御方法を書く。

## 4. 観点の立て方（共通）

観点は検討順に次の型で立て、名前は「名詞＋品質/振る舞い」とする。

| 観点の型               | 本システムでの観点名の例                 | 主な term                              |
| ---------------------- | ---------------------------------------- | -------------------------------------- |
| 業務ルールの正しさ     | `請求額計算の正しさ`、`在庫引当の正しさ` | `utc-sales-checkout`                   |
| 例外/エラー処理        | `在庫不足時の確定拒否`、`入力不足の検出` | `utc-sales-checkout`、`utc-sale-input` |
| 状態遷移               | `購入の未確定から確定への遷移`           | `utc-sale-input`                       |
| 契約/インタフェース    | `確定拒否時の戻り値とエラー種別`         | `utc-sales-checkout`                   |
| 非機能（UTの範囲のみ） | `残高計算の決定性`                       | `utc-credit-balance`                   |

`受領額60円のケース` のように条件そのものになっている名前は観点にせず、`釣銭計算の正しさ` へ統合する。

## 5. 条件の立て方（共通）

基準データは [[specdojo:tsp-index-sample|テスト戦略・方針]] の `kinuya-test-data`（商品A: 単価30円・在庫5個）とし、条件を入力・状態・環境の差分で立てる。

| 区分 | 本システムでの条件の例                                                 |
| ---- | ---------------------------------------------------------------------- |
| 入力 | 代表: 数量2。境界: 数量0・在庫と同数の5・在庫超過の6。異常: 商品未特定 |
| 状態 | 在庫5個・在庫0個、つけ残高0円・残高あり、購入が未確定・確定済み        |
| 環境 | 固定クロックの日付（月末・月初）、記録サービス Fake の保存失敗         |

条件は代表ケース（BAC-01 の C-01: 数量2・在庫5→3）、境界値（C-02: 在庫と同数の5）、重大例外（在庫超過で確定しない）の順に追加する。数量と在庫の全組合せは作らない。

## 6. 観点/条件の採用基準と対象別への分配方針（共通）

採用は「1観点=1合否命題」「1条件=1差分」とし、根拠は誤課金・欠品・誤更新につながる業務影響、または [[specdojo:bac-sample|現金販売の業務受入条件]] の明示要求に限る。分配は責務境界、依存境界、変更影響の順で決め、主担当を1つにする。

| 観点/条件                       | 採用理由                                       | 主担当 `utc-<term>`  | 従担当（任意）   | 備考                                     |
| ------------------------------- | ---------------------------------------------- | -------------------- | ---------------- | ---------------------------------------- |
| 在庫と同数の購入で在庫が0になる | BAC-01 の C-02。境界の欠落は欠品表示を誤らせる | `utc-sales-checkout` | なし             | 在庫が負にならないことも同じ観点で見る   |
| 在庫超過では販売を確定しない    | BAC-02。誤った確定は在庫の誤更新につながる     | `utc-sales-checkout` | `utc-sale-input` | 入力側は数量の形式だけを見て重複させない |
| 商品未特定・数量不明で保留する  | BAC-03 の C-03・C-04                           | `utc-sale-input`     | なし             | 引継ぎメモの内容は総合テストで確認する   |
| つけ残高の加算と入金後の残高    | つけ残高の誤計算は請求・入金の誤りにつながる   | `utc-credit-balance` | なし             | AC-02 への接続は「メモ / 将来課題」      |

分配結果は各 `utc-<term>` のケース表の `トレース` に BAC・AC の条件 ID を書いて追跡する。

## 7. 単体テスト共通の境界/依存の扱い

| 依存            | 本システムでの扱い                                         | 使い分け                                   |
| --------------- | ---------------------------------------------------------- | ------------------------------------------ |
| 業務記録 DB     | 商品・在庫・顧客リポジトリをインメモリの Fake に置き換える | Fake（状態を持ち、在庫の前後を比較できる） |
| 記録サービス    | 保存成功・保存失敗・タイムアウトを返す Stub                | Stub（失敗時の分岐を作る）                 |
| `receipt-print` | 印刷要求の送信回数と内容を検証する Mock                    | Mock（確定1回につき要求1回を検証する）     |
| 時刻            | 固定クロックを注入し、現在時刻を直接参照しない             | 月末・月初の日付で残高計算を固定する       |
| 取引番号の採番  | 採番器を注入し、固定の連番を返す                           | 期待値に取引番号を含めても結果が揺れない   |

非同期・並行性は、初期リリースの単体テスト対象が同期処理のみで、当てはまらない。並行処理を扱う確認は総合テスト（性能測定）に置く。

依存の扱いを変える場合は、変える `utc-<term>` に根拠を書き、本表を改訂する。

## 8. ケース表の共通カラム

各 `utc-<term>` は rulebook の定める10カラムを定められた順で置く（並びは後述の記入例のとおり）。本システムでは次の値の決め方を共通にする。

- `優先度`: 誤課金・在庫の誤更新につながるものを P0、つけ残高を P1、表示の書式変換を P2 とする。
- `自動化`: 単体テストはすべて `automated` とする。
- `証跡`: CI ジョブ `kinuya-ci-unit` の実行結果とテストコードの位置を書く。CI 未整備の間は「暫定: ローカル実行結果、CI 整備後に差し替え」と書く。

`utc-sales-checkout` の1行の書き方は次のとおりとする（`証跡` は CI 整備後の書き方で、整備前は上記の暫定表記にする）。

| `case_id`                                | 条件                                   | 手順（最小）   | 期待値                                               | 観測点（アサーション）        | 境界/依存           | トレース      | 優先度 | 自動化    | 証跡                        |
| ---------------------------------------- | -------------------------------------- | -------------- | ---------------------------------------------------- | ----------------------------- | ------------------- | ------------- | ------ | --------- | --------------------------- |
| `ut-sales-checkout-stock-allocation-020` | 入力: 商品A×5 状態: 在庫5個 環境: なし | 会計を確定する | 請求額150円の販売が1件確定し、在庫が5個から0個になる | 戻り値の請求額、Fake の在庫数 | 在庫リポジトリ Fake | BAC-01 / C-02 | P0     | automated | `kinuya-ci-unit` の実行結果 |
