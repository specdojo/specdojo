# ステークホルダー登録簿（サンプル）: 駄菓子屋きぬや販売管理システム

本書は、駄菓子屋きぬやの販売管理システム構築プロジェクトに関わる関係者を、[[specdojo:prj-overview-sample|プロジェクト概要]] の目的と初期公開指標から整理する例である。店主代表の判断事項、家族利用者と常連顧客への影響を明確にし、後続のコミュニケーション計画の入力とする。

意思決定・実行・利用・外部協力に関わる役割と、成果から影響を受ける集団を記載する。人物名、連絡先、顧客の氏名やつけ残高は扱わない。

## 1. 関係者一覧

次の表は、調整先となる役割・集団と、それぞれのプロジェクトへの関わり方を示す。Role code は採用済みの `PO` と `DEV` だけを使う。

| ID                     | 関係者       | 関与区分                | 所属/組織         | 対応 Role code | 主な責任                                                     | 備考                                                         |
| ---------------------- | ------------ | ----------------------- | ----------------- | -------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| `STH-SHOP-OWNER`       | 店主代表     | スポンサー / 意思決定者 | きぬや            | `PO`           | 目的、優先機能、初期公開の範囲と可否、最終的な業務判断を行う | 店番の主担当として毎営業日システムを使う                     |
| `STH-DEVELOPER`        | 開発担当     | 実行担当者              | きぬや（家族）    | `DEV`          | 要件整理から実装・動作確認までを行い、結果を店主代表に示す   | AI Agent の出力の採否も開発担当が確認する                    |
| `STH-TECH-MENTOR`      | 技術メンター | 外部協力者              | 外部（CoderDojo） | -              | データモデルと画面構造の設計方針に助言する                   | 設計方針の確定まで関与し、判断は行わない                     |
| `STH-FAMILY-USER`      | 家族利用者   | 利用者 / 影響受容者     | きぬや（家族）    | -              | 店主不在の店番日に販売・在庫・つけを記録・確認する           | 代表者が初期公開前の代表シナリオ試行に参加する               |
| `STH-REGULAR-CUSTOMER` | 常連顧客     | 影響受容者              | 店舗外（来店客）  | -              | つけで購入し、残高の確認を店頭で求める                       | 地域の子どもと近所の大人。顧客代表が期待の聞き取りに協力する |

## 2. 影響度/関心度分析

次の表は、各関係者の期待・懸念と、先へ進むために必要な合意を、影響度・関心度の根拠と対応付ける。

| ID                     | 関係者       | 影響度 | 関心度 | 主な期待                                               | 主な懸念                                             | 必要な合意                                                             | 評価根拠                                                               |
| ---------------------- | ------------ | ------ | ------ | ------------------------------------------------------ | ---------------------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `STH-SHOP-OWNER`       | 店主代表     | High   | High   | 販売・在庫・つけ残高を日常の操作だけで記録・確認できる | 操作が増えて日々の記録が続かなくなる                 | 目的、優先機能、初期公開の範囲、初期公開の可否                         | 方針・範囲・公開可否を直接判断し、店番で毎日使う                       |
| `STH-DEVELOPER`        | 開発担当     | Medium | High   | 優先機能と完了定義が決まってから設計・実装に入れる     | 初期公開範囲の変更で作り直しが発生する               | 優先機能ごとの完了定義と確認方法                                       | 成果物の品質と進捗を左右するが、範囲と公開可否は判断しない             |
| `STH-TECH-MENTOR`      | 技術メンター | Medium | Low    | 設計方針の案を受け取れば的確に助言できる               | 小規模店舗に対して過大な構成が選ばれる               | データモデルと画面構造の設計方針                                       | 設計方針に影響するが、日々の進行と運用には関与しない                   |
| `STH-FAMILY-USER`      | 家族利用者   | High   | Medium | 操作説明なしで、店主と同じ手順で記録・確認できる       | 操作に迷い、店番中につけの受付や記録ができない       | 代表シナリオ（販売記録・在庫確認・つけ残高確認）の試行結果と簡易手順書 | 試行結果が初期公開可否の判断材料になり、店主不在時の運営継続を左右する |
| `STH-REGULAR-CUSTOMER` | 常連顧客     | Medium | Medium | つけの記録が正確で、残高をその場で確かめられる         | 記録方法の切替で残高が食い違い、確認に時間を取られる | つけ残高の確認方法の変更内容と、氏名・残高を店内記録だけに置く扱い     | 来店時の体験とつけ管理の価値を受けるが、方針・範囲は判断しない         |

## 3. エンゲージメント方針

次の表は、各関係者の現状と目標の差分を、どの行動でどの判断の節目までに埋めるかを示す。初期公開の日付は _UNDECIDED_: 初期公開の計画で決定するため、期限は判断の節目で示す。

| ID                     | 関係者       | 現状                                                                             | 目標                                                                                           | 対応方針                                                                                                                           | 責任者 | 期限                                | 証跡                                    |
| ---------------------- | ------------ | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------ | ----------------------------------- | --------------------------------------- |
| `STH-SHOP-OWNER`       | 店主代表     | 販売・在庫・つけの記録をノートと記憶に頼っている                                 | 販売・在庫・つけの記録を毎営業日システムで行い、記録のある営業日が90%以上になっている          | 初期公開範囲の確定前に優先機能の判断を依頼し、代表シナリオの試行結果を示して初期公開の可否を判断してもらう                         | `DEV`  | 短期指標の判定時（運用開始後2週間） | Issue（判断記録）, Pull Request         |
| `STH-DEVELOPER`        | 開発担当     | 店主代表の要望を聞き取りながら、要件整理から実装までを一人で進めている           | 優先機能ごとの完了定義が店主代表と合意され、代表シナリオの必須タスクがすべて動作確認済みである | 優先機能ごとに完了定義と確認方法を Issue に書いて店主代表の合意を得てから実装し、結果を Pull Request で示す                        | `DEV`  | 初期公開の判断前                    | Issue, Pull Request                     |
| `STH-TECH-MENTOR`      | 技術メンター | 開発担当から相談を受けた設計について個別に助言している                           | データモデルと画面構造の設計方針への助言を終え、採否が記録されている                           | 設計方針の案を渡して助言を受け、採否の判断は開発担当と店主代表に残す                                                               | `DEV`  | 設計方針の確定まで                  | Issue（助言と採否）                     |
| `STH-FAMILY-USER`      | 家族利用者   | システムの操作経験がなく、店主不在時はつけの受付や在庫の問い合わせを保留している | 操作説明なしで代表シナリオを完遂し、重大な行き詰まりが0件である                                | 初期公開前の代表シナリオ試行に参加してもらい、結果を店主代表の初期公開判断に渡す。行き詰まった操作は手順書か画面を直して再試行する | `DEV`  | 初期公開の判断前                    | Issue（完了・所要時間・支援内容）       |
| `STH-REGULAR-CUSTOMER` | 常連顧客     | つけ残高をノートで管理され、本人の認識と食い違うと確認に時間がかかる             | つけの確認方法の変更を事前に知り、店主代表と家族のどちらに尋ねても同じ残高の回答を受けられる   | 記録方法を切り替える前に店頭で変更内容を告知し、残高の問い合わせには店主代表と家族が同じ手順で答える                               | `PO`   | 初期公開の前                        | Issue（告知文面、氏名・残高を含めない） |

## 4. コミュニケーション要件

次の表は、各関係者が判断・利用・協力に使う情報と、コミュニケーション計画へ渡す内容を示す。会議体と頻度はコミュニケーション計画で決める。

| ID                     | 関係者       | 情報要求                                               | 希望チャネル           | 合意・報告の必要性                                                 | 証跡要件                                     | コミュニケーション計画への反映                   |
| ---------------------- | ------------ | ------------------------------------------------------ | ---------------------- | ------------------------------------------------------------------ | -------------------------------------------- | ------------------------------------------------ |
| `STH-SHOP-OWNER`       | 店主代表     | 優先機能と初期公開範囲の選択肢、代表シナリオの試行結果 | 対面, Issue            | 初期公開範囲の確定と初期公開の可否を判断する                       | Issue に判断と理由を残す                     | 判断依頼: 初期公開範囲と初期公開の可否           |
| `STH-DEVELOPER`        | 開発担当     | 優先機能ごとの完了定義と店主代表の判断結果             | Issue, Pull Request    | 設計方針と実装結果を店主代表に報告し、完了定義の合意を得る         | Pull Request に完了定義との対応を残す        | 報告事項: 優先機能ごとの実装結果と完了定義の充足 |
| `STH-TECH-MENTOR`      | 技術メンター | データモデルと画面構造の設計方針案                     | チャット, Issue        | 設計方針の確定前に助言を受ける                                     | Issue に助言と採否を残す                     | 相談事項: 設計方針案と確定の見込み               |
| `STH-FAMILY-USER`      | 家族利用者   | 代表シナリオの手順と、画面・操作手順の変更点           | 簡易手順書, 対面       | 試行結果が店主代表の初期公開判断の前提になることを了解して参加する | Issue に完了・所要時間・支援内容を残す       | 参加依頼: 初期公開前の代表シナリオ試行           |
| `STH-REGULAR-CUSTOMER` | 常連顧客     | つけ残高の確認方法の変更内容と開始日                   | 店頭掲示, 店頭での説明 | 切替の前に告知し、残高の食い違いは店頭で確認する                   | Issue に告知文面を残し、氏名・残高を含めない | 告知事項: つけ確認方法の変更内容と開始日         |

## 5. 見直し条件

どの見直しでも、変更した関係者 ID の行を全章でそろえて更新し、コミュニケーション計画へ渡す内容が変わる場合は同じ Pull Request で計画にも反映する。次の表は、関係者・期待・合意対象を変える出来事と、その見直しの内容・責任者・承認者を示す。_TODO_: 運用開始後の定期見直しの周期は、短期指標の判定時に決める。

| 更新トリガー                                                 | 見直し内容                                                     | 見直し責任者 | 承認者 | 証跡                |
| ------------------------------------------------------------ | -------------------------------------------------------------- | ------------ | ------ | ------------------- |
| プロジェクトの目的やスコープを変更した                       | 関係者の追加・削除と、各関係者の必要な合意の見直し             | `PO`         | `PO`   | Issue, Pull Request |
| 初期公開の範囲または時期を変更した                           | 合意の期限、代表シナリオ試行の時期、告知の時期の見直し         | `DEV`        | `PO`   | Issue, Pull Request |
| 体制が変わった（開発担当の交代、外部協力者の追加・終了）     | 関与区分、対応 Role code、関与方針の責任者と期限の見直し       | `DEV`        | `PO`   | Pull Request        |
| 公開・利用方針が変わった（共有文書に載せる情報、店番の範囲） | 家族利用者・常連顧客の合意対象と証跡要件の見直し               | `DEV`        | `PO`   | Issue, Pull Request |
| 画面・操作手順またはつけの確認方法が変わった                 | 家族利用者・常連顧客の期待と懸念、試行と告知の要否の見直し     | `DEV`        | `PO`   | Pull Request        |
| 新しい関係者または利用者・影響受容者の集団が現れた           | 関係者一覧への登録と、同じ ID での各章の行の追加               | `DEV`        | `PO`   | Issue, Pull Request |
| 初期公開の判断前、短期指標の判定時                           | 各関係者の現状が目標に達したかと、残った差分の関与方針の見直し | `DEV`        | `PO`   | Pull Request        |
