# 駄菓子屋きぬや 販売管理システム 運用方針・設計（全体構成）

## 1. 概要（index）

初期リリース後の駄菓子屋きぬや 販売管理システムを、店主が不在でも店番担当が同じ判断で動かし続けるための運用方針の正本である。運用の目的は、販売・在庫・つけの記録を営業日ごとに欠かさず残し、店主代表の最終判断に必要な記録をそろえることとする。監視・障害対応・権限の差分は `opd-monitoring`・`opd-incident-management`・`opd-access-control` に分冊し、作業手順は `opr-*` に置く。

次の表は、`PO`（Project Owner）が決める運用上の未決事項と、決まるまでの扱いを示す。決まるまでは、該当する行の目標で達成・未達を判定しない。

| 未決事項                                                                      | 判断者 | 決まるまでの扱い                                                                   | 影響する章                     |
| ----------------------------------------------------------------------------- | ------ | ---------------------------------------------------------------------------------- | ------------------------------ |
| _UNDECIDED_: オフライン時の記録方法                                           | `PO`   | 通信できない間は紙の販売控えに書き、復旧後に開発担当（Developer、`DEV`）と転記する | 運用の範囲・前提、障害対応方針 |
| _UNDECIDED_: 営業時間内の稼働率の目標                                         | `PO`   | 停止の発生と時間を記録するだけとし、目標の達成・未達を判定しない                   | SLO・SLA・KPI                  |
| _UNDECIDED_: 目標復旧時間（RTO）・目標復旧時点（RPO）とバックアップの保管期間 | `PO`   | 毎日の閉店後にバックアップを取り、復元の確認は月次で行う                           | バックアップ・リストア方針     |
| _UNDECIDED_: 営業時間外の緊急連絡手段                                         | `PO`   | 営業時間外の障害は翌朝の開店前に連絡する                                           | 体制・責任分界、障害対応方針   |

## 2. 運用の範囲・前提

運用の対象は、店頭のタブレット 1 台で使う販売・在庫・つけの記録機能と、その記録を保存するホスティング環境とする。

| 項目               | 内容                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------ |
| 対象の機能         | 店頭販売の記録、在庫の確認と調整、つけ残高の記録と確認、閉店後の日次締め                         |
| 対象外             | 複数店舗、電子商取引（EC）、本格会計、仕入れ先連携、キャッシュレス決済、無人での会計             |
| 運用時間帯         | 営業時間 10:00〜18:00。日次締めとバックアップの確認は閉店後に行う                                |
| 店番担当           | 店主代表または家族利用者代表。どちらが店番でも同じ手順で記録する                                 |
| 前提とする外部要素 | 店舗の通信回線とホスティング環境。_ASSUMPTION_: 記録の正本はホスティング環境のデータベースに置く |

運用の判断は [[specdojo:prj-overview-sample|プロジェクト概要]] の目的と前提に従う。上位の非機能要件（[[specdojo:nfr-availability-sample|非機能要件 / 可用性]]・[[specdojo:nfr-operations-sample|非機能要件 / 運用]]）は、目標値が未決である。上位の目標値が決まった時点で、本書で `_UNDECIDED_` とした値を揃える。

## 3. SLO・SLA・KPI

SLO（サービスレベル目標）は運用側の数値目標、SLA（サービスレベル合意）は外部との約束を表す。KPI（重要業績評価指標）は改善の管理指標で、共通の期待効果をそのまま使う。判定者の `OPS` は Operations / Release Manager を指す。

次の表は、運用で追う指標と、達成・未達を判定する条件の対応を示す。

| 区分 | 指標               | 目標値                                                  | 測定期間 | 測定方法                                                                   | 証跡         | 判定者 |
| ---- | ------------------ | ------------------------------------------------------- | -------- | -------------------------------------------------------------------------- | ------------ | ------ |
| KPI  | 記録の継続         | 営業日の 90% 以上で販売・在庫・つけの記録がある         | 月次     | 日次締めで記録の有無を確かめた結果を集計する                               | 日次締め記録 | `PO`   |
| KPI  | つけ残高の確認時間 | 1 分以内                                                | 月次     | 顧客の検索から残高の表示までを月 3 回計る                                  | 月次点検記録 | `PO`   |
| KPI  | 人気商品の欠品     | 月間の欠品回数を導入前から 50% 減らす                   | 月次     | 同じ対象商品・除外条件で日次の欠品回数を月間集計し、導入前の基準値と比べる | 欠品記録     | `PO`   |
| SLO  | 営業時間内の稼働   | _UNDECIDED_                                             | 月次     | 店番担当が記録できなかった時間を障害記録に残し合計する                     | 障害記録     | `OPS`  |
| SLO  | 障害の一次連絡     | P1 は 15 分以内、P2 は当日の閉店まで、P3 は次の月次点検 | 月次     | 障害記録の発生時刻と連絡時刻の差を集計する                                 | 障害記録     | `OPS`  |
| SLA  | 外部との約束       | 対象外（外部の利用者・委託先と合意する約束がない）      | -        | -                                                                          | -            | -      |

欠品の基準値は、`PO` が運用開始前 1 か月に手書きで残した日次の欠品記録の合計とする。対象商品と除外条件は記録の開始前に固定し、来店数・仕入れ条件・季節要因も記録する。基準値が 0 回、記録が 1 か月そろわない場合、または季節要因で比較の扱いが未決の場合は、削減率を判定不能とし、`PO` が比較の扱いを見直す。月次点検では改善の経過を追い、成功の判定は [[specdojo:prj-success-criteria-and-acceptance-criteria-sample|成功基準と受入条件]] の SC-04 に従って運用開始後 6 か月目に行う。

目標を下回った月は、`OPS` が月次点検で `PO` へ報告し、原因と対策を課題としてプロジェクトの課題管理へ登録する。目標値そのものを変える場合は、変更要求として `PO` の承認を得る。

## 4. 体制・責任分界（RACI・当番・エスカレーション）

次の表は、運用の作業ごとに誰が実行し、誰が判断の責任を持つかを示す。`OPS` は組織定義で兼務先を決め、本書では兼務を問わない。

RACI は、Responsible（実行・R）、Accountable（説明責任・A）、Consulted（相談・C）、Informed（共有・I）の責任分担を表す。

| 作業                       | `PO` | `OPS` | `DEV` | 店番担当 | 補足                                           |
| -------------------------- | ---- | ----- | ----- | -------- | ---------------------------------------------- |
| 店頭での記録と異常の気付き | I    | A     | -     | R        | 異常は障害記録に書き、エスカレーション表に従う |
| 障害の切り分けと復旧       | I    | A     | R     | C        | 停止の判断は障害対応方針に従う                 |
| 業務の停止・再開の判断     | A    | R     | C     | I        | 紙の販売控えへの切替を含む                     |
| 変更の適用                 | A    | R     | R     | I        | 承認の範囲は変更管理に従う                     |
| 権限の付与・剥奪           | A    | R     | C     | I        | 棚卸しは権限・アカウント運用に従う             |

当番は営業時間中の店番担当とし、営業時間外の当番は置かない。店番担当は異常に気付いたら、次の条件で連絡する。

| 優先度 | 条件                                           | 連絡先           | 期限                   |
| ------ | ---------------------------------------------- | ---------------- | ---------------------- |
| P1     | 販売・つけのどちらかを記録できない             | `OPS`、次に `PO` | 気付いてから 15 分以内 |
| P2     | 記録はできるが、在庫の確認や日次締めができない | `OPS`            | 当日の閉店まで         |
| P3     | 表示の崩れなど、回避して記録を続けられる       | `OPS`            | 次の月次点検           |

P1 で `OPS` が 15 分以内に応答しない場合、店番担当は `PO` へ直接連絡する。紙の販売控えへの切替判断は「障害対応方針」に従う。

## 5. 監視・アラート方針（指標・閾値・通知先・初動）

自動の監視は、ホスティング環境の死活と閉店後のバックアップの結果に限る。店頭の異常は店番担当が気付いて連絡する。具体化は `opd-monitoring` に分冊する。

| 監視対象               | 閾値                                       | 通知先 | 初動                                                                     |
| ---------------------- | ------------------------------------------ | ------ | ------------------------------------------------------------------------ |
| ホスティング環境の死活 | 営業時間中に 5 分続けて応答がない          | `OPS`  | 店番担当に、記録を続けられているかを確認する。記録できなければ P1 とする |
| 閉店後のバックアップ   | 翌朝の開店時に前日の閉店後の成功記録がない | `OPS`  | P2 として `DEV` に再取得を依頼する                                       |
| 日次締めの差異         | 現金と販売記録の差が 1 円でもある          | `PO`   | 当日の販売記録を照合し、原因を日次締め記録に残す                         |

## 6. 障害対応方針（優先度・停止判断・周知）

優先度は体制・責任分界の表の条件で決める。具体化は `opd-incident-management` に分冊する。

- P1 に気付いてから 30 分たっても記録を再開できない場合、`PO` が紙の販売控えへの切替を決める。営業そのものは止めない。
- 紙の販売控えに切り替えた記録は、復旧後に店番担当が転記し、`DEV` が件数と金額を照合する。
- 来店客への周知は、会計の待ちが生じる場合だけ店頭で口頭で行う。つけ残高を確認できない間は、つけの新規記録を受けない。
- 障害が収まったら、`OPS` が原因・影響・再発防止を障害記録に残し、月次点検で `PO` へ報告する。

## 7. 変更管理（リリース・設定変更・承認・ロールバック）

次の表は、変更の種類ごとに承認が要るかと、戻す条件を示す。

| 変更の種類                         | 承認者 | 適用する時間帯 | ロールバックの条件                                                 |
| ---------------------------------- | ------ | -------------- | ------------------------------------------------------------------ |
| アプリの版の更新                   | `PO`   | 閉店後         | 適用後の確認で販売・在庫・つけのどれかを 1 件も記録できない        |
| 商品マスタ・価格の一括変更         | `PO`   | 閉店後         | 翌朝の開店前の確認で、価格が承認された変更記録と違う商品が見つかる |
| 権限・アカウントの変更             | `PO`   | 随時           | 店番担当が記録の画面に入れない                                     |
| 表示の文言など記録に影響しない修正 | `OPS`  | 閉店後         | 表示の崩れで記録の操作ができない                                   |

ロールバックは `DEV` が行い、戻した理由を変更記録に残す。営業時間中の変更は、P1 の復旧に必要な場合だけ `PO` の承認で行う。

## 8. バックアップ・リストア方針（RTO/RPO）

次の表は、記録の正本であるデータベースのバックアップと復元の方針を示す。

| 項目       | 方針                                                               |
| ---------- | ------------------------------------------------------------------ |
| 取得の頻度 | 毎日、閉店後の日次締めの後に 1 回                                  |
| RTO        | _UNDECIDED_: 決まるまでは翌営業日の開店までに復元する              |
| RPO        | _UNDECIDED_: 決まるまでは前日の閉店時点に戻ることを許す            |
| 保管期間   | _UNDECIDED_                                                        |
| 復元の確認 | 月次で、検証用の環境へ復元し、前日の販売件数と一致するかを確かめる |
| 確認者     | `OPS`。復元できなかった場合は P2 として扱う                        |

RPO を前日の閉店時点とする間は、当日分の記録は紙の販売控えと日次締め記録から転記して戻す。

## 9. 権限・アカウント運用（棚卸し・監査ログ）

アカウントは店番担当と `DEV` に限り、共有のアカウントは作らない。具体化は `opd-access-control` に分冊する。

次の表は、アカウントの付与・剥奪、棚卸し、監査ログの方針を示す。

| 項目               | 方針                                                               |
| ------------------ | ------------------------------------------------------------------ |
| 付与・剥奪の承認者 | `PO`                                                               |
| 剥奪の時期         | 店番をやめた日のうちに剥奪する                                     |
| 棚卸しの頻度       | 月次点検で、有効なアカウントと店番担当の一覧が一致するかを確かめる |
| 監査ログ           | ログイン、つけ残高の変更、価格の変更を残す。保管期間は 1 年        |

## 10. 定期運用方針（バッチ・点検）

次の表は、定期の作業ごとの周期・失敗時の扱い・確認者を示す。

| 作業                 | 周期                       | 失敗時の扱い                                                              | 確認者 |
| -------------------- | -------------------------- | ------------------------------------------------------------------------- | ------ |
| 日次締め             | 毎営業日の閉店後           | 差異が解けない場合は翌朝の開店前に `PO` が確かめる                        | `PO`   |
| 閉店後のバックアップ | 毎日、閉店後の日次締めの後 | 監視・アラート方針の閉店後のバックアップの行に従う                        | `OPS`  |
| 月次点検             | 毎月の最初の休業日         | KPI・SLO の集計、権限の棚卸し、復元の確認のどれかができなければ翌週に行う | `OPS`  |

## 11. 問い合わせ運用方針（窓口・分類・SLA）

窓口は `OPS` の 1 つとし、店番担当は口頭または店内の連絡帳で問い合わせる。

| 分類             | 例                             | 応答の目標                         |
| ---------------- | ------------------------------ | ---------------------------------- |
| 操作の質問       | つけの記録の消し方が分からない | 当日の閉店まで                     |
| 記録の訂正の依頼 | 前日の販売の数量を間違えた     | 翌営業日の開店まで                 |
| 機能の要望       | 欠品の多い商品を一覧で見たい   | 次の月次点検で `PO` が採否を決める |

障害にあたる問い合わせは、体制・責任分界のエスカレーション表で扱う。

次の表は、本書の方針を具体化する分冊と、手順を置く文書の対応を示す。

| 種別 | ドキュメントID            | 役割                                     | 状態 |
| ---- | ------------------------- | ---------------------------------------- | ---- |
| 方針 | `opd-monitoring`          | 監視の閾値と初動の具体化                 | 予定 |
| 方針 | `opd-incident-management` | 優先度ごとの停止判断と周知の具体化       | 予定 |
| 方針 | `opd-access-control`      | 付与・剥奪と棚卸しの具体化               | 予定 |
| 手順 | `opr-index`               | 日次締め・月次点検・復元確認の手順の入口 | 予定 |
| 手順 | `opr-incident`            | 紙の販売控えへの切替と転記の手順         | 予定 |
