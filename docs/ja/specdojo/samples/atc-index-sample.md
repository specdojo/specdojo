# 駄菓子屋きぬや 販売管理システム 受入テストカタログ 概要

## 1. 本ドキュメントの目的と適用対象

駄菓子屋きぬや 販売管理システムの初期リリースについて、店主代表と家族利用者代表が「店主不在でも同じ手順で販売・在庫・つけを記録して確認できる」と判断するための受入テスト（AT）の共通方針を定める。[[specdojo:tsp-index-sample|テスト戦略・方針]] の受入テストの範囲（SC-01・AC-01〜AC-04 の代表シナリオ）を、対象別カタログ `atc-<term>` の分割・観点・条件・環境・証跡へ具体化する。

AT で実現を確かめる価値は、ノートと記憶に頼らずに会計と在庫を記録できること、つけ残高を1分以内に確認できること、店番を交代しても未確定の購入を引き継げることである。記録と状態の正しさは [[specdojo:stc-index-sample|総合テストカタログ 概要]] で確定済みとし、AT は利用者が説明なしで業務を完了できるかを判定する。

| 文書                                    | 分担                                                               |
| --------------------------------------- | ------------------------------------------------------------------ |
| 本書                                    | 分割基準、対象外、観点・条件の立て方、環境・データ・証跡、合格基準 |
| `atc-<term>`                            | 対象ごとの観点・条件・ケース表。個別ケースの正本                   |
| 受入確認記録 `kinuya-acceptance-record` | ケース別の結果と証跡、受入全体の判定。合否の裏付け                 |

| 関係者（Role code） | 受入での責務                                                    |
| ------------------- | --------------------------------------------------------------- |
| 店主代表（PO）      | 受入全体の判定者。受入可・条件付き受入・保留・受入不可を決める  |
| 家族利用者代表      | 店主代表とともにケースを操作し、迷った点・質問を申告する        |
| 業務分析担当（BA）  | 実施を進行し、所要時間・質問・支援・誤操作を記録する            |
| 品質担当（QE）      | 証跡と期待値を照合し、集計結果を判定者へ渡す                    |
| 開発担当（DEV）     | 受入環境とデータを準備し、Fail の原因調査と修正版の再提供を行う |

### 1.1. 合格基準

| 優先度 | 意味                                                      | 集計条件                                                                                                      |
| ------ | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| P0     | SC-01・AC-01〜AC-04 に対応し、業務成果が成立する最短経路  | 全件 Pass。TSP の出口条件のとおり例外を設けず、1件でも Fail・未実施・判定保留があれば受入可にしない           |
| P1     | BAC-02・BAC-03 の停止と引継ぎ、確定前の取消などの重要分岐 | 全件 Pass で受入可。Fail は、回避手順を店主代表が実施でき、修正版の再試験日が決まっている場合だけ条件付き受入 |
| P2     | 取消後の再登録など頻度の低い経路                          | 90%以上 Pass。Fail は課題ログへ登録し、次回リリースまでの対応を決めたうえで受入可とする                       |

未実施と判定保留は Pass に数えない。修正版を受け取った場合は Fail のケースと、同じ `atc-<term>` の P0 全件を再試験してから再判定する。

### 1.2. 判定の流れ

| 段階        | 実施者 | 完了条件                                                                                 |
| ----------- | ------ | ---------------------------------------------------------------------------------------- |
| 1. 結果集計 | BA     | 全ケースの結果が優先度別に集計され、未実施・判定保留が件数で示されている                 |
| 2. 証跡照合 | QE     | 各ケースの期待値と証跡が一致し、AC-04 のとおり条件 ID・確認日・確認者を辿れる            |
| 3. 影響確認 | QE、BA | 残存する Fail・未決事項ごとに、業務影響と回避手順の有無が記録されている                  |
| 4. 判定記録 | PO     | 判定結果・理由・承認日・条件付き受入の条件が `kinuya-acceptance-record` に記録されている |

判定の記録には実施者と証跡確認者の nickname を残し、判定者がケース別の記録へ戻れるようにする。

## 2. 受入テスト対象の括り方と分割基準

`<term>` は利用者が業務の開始から完了まで続けて操作し、その場で受け入れるかを言える単位とする。受入判断の単位→業務成果の開始・完了条件→合意の責任境界→金銭影響のリスク境界の順で判断した結果は次のとおり。

| `atc-<term>`             | 業務成果（開始→完了）                                     | 根拠                 | 分割・統合の判断                                                                  |
| ------------------------ | --------------------------------------------------------- | -------------------- | --------------------------------------------------------------------------------- |
| `atc-cash-sale`          | 商品の登録→金額の提示→会計確定→レシートの受け渡し         | SC-01、AC-01、BAC-01 | 確定前の取消は同じ会計の中で起きる分岐のため、別 term にしない                    |
| `atc-sale-hold`          | 在庫不足・入力不足に気づく→未確定のまま止める→引継ぎ→再開 | BAC-02、BAC-03       | 各2ケース程度で、「販売を確定しない」という同じ判断を両代表が合意するため統合する |
| `atc-stock-credit-check` | 商品・常連顧客の検索→在庫数・つけ残高の確認               | SC-01、AC-02         | 金銭の授受がなく、つけ残高の照合責任を店主代表だけが負うため会計と分ける          |

ケースが50件を超えた term、または別の業務成果が混ざった term は分割を再検討する。

## 3. 対象外・除外理由（共通）

| 対象外（やらないこと）                     | 除外理由                                                   | 代替レベル/代替手段                     | 例外（ATで扱う条件）                                 |
| ------------------------------------------ | ---------------------------------------------------------- | --------------------------------------- | ---------------------------------------------------- |
| 金額・在庫・つけ残高の計算の網羅           | 計算の正しさは利用者の判断ではなく、記録で判定できる       | UT・IT・ST（`stc-cash-sale` ほか）      | 代表シナリオで表示された金額を両代表が現物と照合する |
| 印刷失敗・保存失敗・応答欠落の障害パターン | 障害の再現にはスタブが要り、店舗端末の構成を変えてしまう   | ET・ST（`stc-record-recovery`）         | なし                                                 |
| 会計確定の応答時間の測定                   | 受入は業務の成立の確認が目的で、測定条件をそろえられない   | ST・NFR の性能測定記録                  | 操作中に待たされたと申告した場合は所要時間を記録する |
| 運用開始後の効果（SC-02〜SC-06）           | 判定時期が運用開始後で、初期リリースの受入時に判定できない | 運用開始後の効果測定（店主代表が判定）  | なし                                                 |
| 通信不能時の販売継続                       | TSP で未決であり、期待結果を定められない                   | なし（「メモ / 将来課題」で決定を待つ） | 決定後の扱いは「メモ / 将来課題」に従う              |

## 4. 受入観点の立て方（共通）

観点名は「名詞＋成立/保証/整合」とし、各 term は次の系統から必要なものを立てる。

| 系統             | 本システムで受け入れる状態                                         | 観点名の例         | 主に立てる term                  |
| ---------------- | ------------------------------------------------------------------ | ------------------ | -------------------------------- |
| 業務成果の成立   | 説明なしで会計を確定でき、販売記録と在庫の減少を画面で確かめられる | `会計確定の成立`   | `atc-cash-sale`                  |
| 重要分岐         | 在庫不足・入力不足では確定せず、引継ぎメモで次の店番に渡せる       | `未確定停止の保証` | `atc-sale-hold`                  |
| 契約・データ整合 | 表示されたつけ残高が店主代表の手元の記録と一致する                 | `つけ残高の整合`   | `atc-stock-credit-check`         |
| 運用可能性       | 迷った操作を引継ぎメモと取引番号から店主代表が後で確認できる       | `取引照合の保証`   | `atc-cash-sale`、`atc-sale-hold` |
| AT で扱う非機能  | 残高確認が1分以内に終わる（共通サンプル文脈の期待効果）            | `残高確認の成立`   | `atc-stock-credit-check`         |

「使いやすいこと」のように合否命題にならない観点は立てず、所要時間・質問・支援・誤操作の記録で判定できる観点へ言い換える。

## 5. 条件の立て方（共通）

| 要素 | 本システムでの立て方                                  | 例                                             |
| ---- | ----------------------------------------------------- | ---------------------------------------------- |
| 入力 | 購入数を在庫未満と在庫超過の2値で代表させる           | 商品A（在庫5個）を2個・6個                     |
| 状態 | 操作する代表と、店番の交代の有無で分ける              | 状態: 店主不在で家族利用者代表が店番           |
| 環境 | 受入環境は1構成に固定し、外部依存の失敗は条件にしない | 環境: 店舗端末と店舗プリンタ（実機）           |
| 経路 | 確定・確定前の取消・停止と再開を1条件1経路にする      | 経路: 不足していた数量が分かり、販売を再開する |

代表（P0: 家族利用者代表が商品Aを2個販売する）→重要分岐（P1: 在庫超過、数量不明、確定前の取消）の順で追加する。在庫と同数の境界は ST で確定済みのため AT では作らない（障害経路は「対象外・除外理由（共通）」のとおり）。操作する代表×全経路の直積は作らず、店番の交代は `atc-sale-hold` の引継ぎ経路だけで確かめる。

## 6. 観点/条件の採用基準と対象別への分配方針（共通）

採用は1観点＝1合否命題、1条件＝1差分とし、根拠は SC-01・AC-01〜AC-04・BAC-01〜BAC-03 の条件 ID か、つけ残高の誤表示などの業務影響で示す。

| 観点/条件                                   | 採用理由                                         | 主担当 `atc-<term>`      | 従担当（任意）           | 備考                                          |
| ------------------------------------------- | ------------------------------------------------ | ------------------------ | ------------------------ | --------------------------------------------- |
| `会計確定の成立` / 家族利用者代表の店番     | SC-01・AC-01。店主不在の会計が初期リリースの目的 | `atc-cash-sale`          | なし                     |                                               |
| `未確定停止の保証` / 在庫超過の購入         | BAC-02。誤確定は在庫と売上を同時に誤らせる       | `atc-sale-hold`          | `atc-cash-sale`          | 再開後の会計の期待値は `atc-cash-sale` を参照 |
| `つけ残高の整合` / 常連顧客の残高確認       | AC-02。誤表示は顧客との信頼を損なう              | `atc-stock-credit-check` | なし                     |                                               |
| 主要操作の自力完了 / 説明なしの代表シナリオ | SC-01・AC-03。行き詰まりは受入不可に直結する     | `atc-cash-sale`          | `atc-stock-credit-check` | 測定記録は両 term とも同じ項目で残す          |

同じ観点を複数の term で主担当にしない。主担当を変える場合は、分配表と両 term のトレース列を同時に更新する。

## 7. 受入テストの環境/データ/外部依存の扱い（共通）

| 項目     | 共通方針                                                                                                                                                                |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 環境     | TSP の店舗端末（本番相当構成）を使う。ST の出口条件を満たしたリリース候補版のタグを受入開始時に固定し、版と実施期間を `kinuya-acceptance-record` に記録する             |
| データ   | 受入用の店舗データ領域 `kinuya-at` を使い、各ケースの開始時に `kinuya-test-data`（商品A 単価30円・在庫5個、架空の常連顧客1名）へ戻す。受入完了後に DEV が領域を削除する |
| 外部依存 | 店舗プリンタは実機に接続し、復元用保管サービスは検証用領域へ接続して本番の保管データに触れない。印刷結果は手元のレシート、保存結果は保管サービスの記録で確かめる        |
| 証跡     | 実施者・日時・版・ケース別結果、取引番号、画面キャプチャ、所要時間・質問・支援・誤操作の測定記録を残す。判定記録には証跡確認者（QE）と判定者（PO）を残す                |

実在の顧客名とつけ残高は使わない。準備したデータと異なる状態でケースを始めた場合、そのケースは判定保留とし、データを戻して再実施する。

## 8. ケース表の共通カラム

全 `atc-<term>` は次の順でカラムを並べる。`case_id` は `at-<term>-<perspective_key>-<nnn>` とし、`nnn` は010から10刻みで振り、一度振った値は変えない。

| 区分 | カラム                 | 書き方                                               |
| ---- | ---------------------- | ---------------------------------------------------- |
| 必須 | `case_id`              | 廃止したケースは欠番にし、再利用しない               |
| 必須 | 条件                   | `入力:` `状態:` `環境:` `経路:` のうち差分の要点だけ |
| 必須 | 手順（最小）           | 業務操作の意図が分かる粒度で3手順以内                |
| 必須 | 期待値                 | 利用者が画面や現物で観測して Pass / Fail を言える文  |
| 推奨 | 観測点（アサーション） | 画面表示、レシート、引継ぎメモ、取引番号             |
| 推奨 | 環境/依存              | データ領域と接続先                                   |
| 推奨 | トレース               | SC・AC・BAC の条件 ID                                |
| 推奨 | 優先度                 | 「合格基準」の P0 / P1 / P2                          |
| 推奨 | 実施形態               | manual / assisted / automated                        |
| 推奨 | 証跡                   | `kinuya-acceptance-record` の記録、画面キャプチャ    |

記入の形式例（`atc-cash-sale`）:

| `case_id`                        | 条件                                         | 手順（最小）                                     | 期待値                                                                                          | 観測点（アサーション）       | 環境/依存                 | トレース             | 優先度 | 実施形態 | 証跡                                       |
| -------------------------------- | -------------------------------------------- | ------------------------------------------------ | ----------------------------------------------------------------------------------------------- | ---------------------------- | ------------------------- | -------------------- | ------ | -------- | ------------------------------------------ |
| `at-cash-sale-sale-complete-010` | 入力: 商品A 2個 / 状態: 家族利用者代表が店番 | 商品Aを2個登録し、60円を受け取って会計を確定する | 説明なしで確定でき、レシートと販売一覧に同じ取引番号と合計60円が表示され、在庫が3個と表示される | レシート、販売一覧、在庫一覧 | `kinuya-at`、店舗プリンタ | SC-01、AC-01、BAC-01 | P0     | manual   | `kinuya-acceptance-record`、画面キャプチャ |

期待値を「正しく会計できること」とだけ書いたケースは認めない。
