# コミュニケーション計画: 駄菓子屋きぬや 販売管理システム

## 1. 方針と適用範囲

[[specdojo:pm-plan-sample|管理計画]] の判断ゲートと [[specdojo:prj-stakeholder-register-sample|ステークホルダー登録簿]] のコミュニケーション要件を、営業を妨げない判断依頼・確認・共有・告知へ具体化する。対象は準備着手から2週間の店頭試用終了までとし、定例会議は置かない。

- 店主代表 `STH-SHOP-OWNER` は登録簿のとおり `PO` を担う。本書では、機会の対象をステークホルダー ID、判断者を `PO` で書く。
- Issue・Pull Request・チャットの非同期の記録を基本とする。対面は、店主代表への判断依頼と受入結果の説明、家族利用者の試用準備、試用結果の聞き取り、常連顧客への店頭説明に限り、結果は当日中に Issue または指定の記録へ転記する。
- AI Agent は記録の整理、要約、告知文面の草案を支援する。合意・承認・公開・停止の判断は行わず、顧客の氏名・つけ残高・連絡先を入力しない。

## 2. コミュニケーション機会

登録簿の情報要求ごとの機会を示す。「判断ゲート」は管理計画の「判断ゲートとエスカレーション」のゲート名を指す。

| 対象・機会                                         | 伝える・確認する内容                                            | タイミング                                                                       | 手段                                                         | 責任  | 証跡                                             |
| -------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------ | ----- | ------------------------------------------------ |
| `STH-SHOP-OWNER` への判断依頼                      | 優先機能と初期公開範囲の選択肢、範囲・UI の変更、費用・時間上限 | 判断ゲート「準備着手」の前、判断ゲート「重大変更・再開」に当たる変更の起案時     | Issue に選択肢を書き、営業時間外の対面で説明する             | `PM`  | Issue の判断と理由、変更要求ログの変更 ID        |
| `STH-SHOP-OWNER` への進捗共有                      | 完了した作業、次の作業、ブロック、判断待ちの事項                | `kinuya-schedule` の週次確認時、各判断ゲートの判断依頼の前日、ブロック発生の当日 | `kinuya-schedule` の要約を Issue コメントに置く              | `PM`  | `kinuya-schedule` のタスク ID、課題ログの課題 ID |
| `STH-SHOP-OWNER` への実装結果の報告                | 優先機能ごとの実装結果と完了定義の充足                          | 優先機能ごとの Pull Request の作成時                                             | Pull Request に完了定義との対応を書き、Issue で要約を示す    | `DEV` | Pull Request の完了定義との対応                  |
| `STH-TECH-MENTOR` との設計相談                     | データモデルと画面構造の設計方針案、確定の見込み                | 設計方針の確定まで週1回                                                          | チャットで案を渡し、助言を Issue にまとめる                  | `DEV` | Issue の助言と採否                               |
| `STH-FAMILY-USER` への試用参加の依頼               | 代表シナリオの手順、画面・操作手順の変更点、困り事の伝え方      | 判断ゲート「初期リリース・店頭試用開始」の前、手順を変えた版の試用前             | 簡易手順書と短時間の対面実演                                 | `BA`  | Issue の完了・所要時間・支援内容                 |
| `STH-SHOP-OWNER` の受入確認                        | 条件 ID ごとの試験結果、未解決事項、公開可否                    | 判断ゲート「初期リリース・店頭試用開始」の前                                     | Issue に試験結果の要約を置き、対面で説明して判断を聞き取る   | `QE`  | `kinuya-acceptance-record` の合否・判断日        |
| `STH-REGULAR-CUSTOMER` への告知                    | つけ残高の確認方法の変更内容と開始日                            | つけの記録方法の切替開始日の前から開始日まで                                     | 店頭掲示と、問い合わせ時の店頭説明                           | `PO`  | Issue の告知文面（氏名・残高を含めない）         |
| `STH-SHOP-OWNER`・`STH-FAMILY-USER` への停止連絡   | 利用を止めた機能、紙のノートでの代替手順、再開の見込み          | 主要操作不能・記録の不整合で利用を止めた当日                                     | 営業時間内は店頭の口頭とチャット。営業時間外は未決事項を参照 | `PM`  | 課題ログの課題 ID                                |
| `STH-SHOP-OWNER`・`STH-FAMILY-USER` の試用結果確認 | 継続可否の材料、追加操作時間、改善候補                          | 判断ゲート「店頭試用後の継続」の前（試用終了日の後）                             | 対面の聞き取り                                               | `BA`  | `kinuya-trial-log` の営業日別記録と改善の課題 ID |

## 3. エスカレーション

いずれの条件も、次の支出・利用・公開より前に判断を求める。

| 条件                                                                                                 | 一次対応                                                                              | 最終判断 | 証跡                       |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | -------- | -------------------------- |
| 利用者価値または受入条件を登録簿・成功条件から判定できない                                           | `BA` が事実と選択肢を整理する                                                         | `PO`     | 課題ログ                   |
| 現金支出・作業時間が管理計画 M-03・M-04 の上限を超える見込み                                         | `PM` が縮小案と中止案を整理する                                                       | `PO`     | 変更要求ログ               |
| 受入条件の未達、または検証できない Agent 出力                                                        | `QE` が対象版と不足証跡を整理し、`PM` が是正を `kinuya-schedule` に置く               | `PO`     | `kinuya-acceptance-record` |
| 店頭試用中に主要操作が不能、または販売・在庫・つけの記録が食い違う                                   | 発見者が利用を止めて紙のノートへ切り替え、`PM` が停止連絡と代替案・再開期限を整理する | `PO`     | 課題ログ                   |
| 顧客情報・認証情報が公開資料・一般共有チャネル・Agent 入力に出た、または公開物に権利・内部事情の懸念 | 発見者が共有を止め、`QE` が影響範囲を確認し、`PM` が判断材料を整理する                | `PO`     | 課題ログ                   |
| 範囲・上限・試用日の基準を変える要求                                                                 | `PM` が影響と代替案を整理する                                                         | `PO`     | 変更要求ログ               |

## 4. 情報管理と公開

口頭や対面で決まった事項は `PM` が当日中に該当の管理記録へ転記し、変更を伴うものは変更要求ログへ起票する。

| 情報区分                               | 取扱い                                                                        | 記録先                                                                                                                                                  |
| -------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 判断・課題・リスク・変更               | 限定共有（プロジェクト関係者）。理由と次の行動を付ける                        | [[specdojo:pm-issue-log-sample\|課題ログ]]、[[specdojo:pm-risk-register-sample\|リスク登録簿]]、[[specdojo:pm-change-request-log-sample\|変更要求ログ]] |
| 進捗・作業結果                         | 限定共有（プロジェクト関係者）                                                | `kinuya-schedule`、Pull Request                                                                                                                         |
| 設計方針の相談                         | 限定共有（技術メンターを含む）。実データを含めず、架空の商品・顧客で示す      | Issue                                                                                                                                                   |
| 店頭告知                               | 公開（来店客）。変更内容と開始日だけを載せる                                  | Issue の告知文面                                                                                                                                        |
| 顧客の氏名・つけ残高・連絡先、認証情報 | 記録禁止。公開資料・一般共有チャネル・AI Agent の入力に含めない               | プロジェクトの記録には残さない                                                                                                                          |
| 公開する事例・画面                     | 公開。匿名化し、店舗運営に不要な内部事情を除く。`PO` の公開判断を経て公開する | `kinuya-acceptance-record` の公開可否                                                                                                                   |

## 5. 見直し条件と未決事項

参加者、判断ゲート、公開範囲、主な連絡手段が変わった場合に本計画を見直す。連絡の時期・判断経路・手段を変えたときは、次の対象も合わせて直す。

| 変えたこと               | 追従対象と更新する Role                                                                   | 反映の証跡                        |
| ------------------------ | ----------------------------------------------------------------------------------------- | --------------------------------- |
| 判断依頼・受入確認の時期 | 管理計画の判断ゲート（`PM`）、`kinuya-schedule` の確認・判断待ちタスク（`PM`）            | 変更要求ログの変更 ID とタスク ID |
| エスカレーションの判断者 | 本書のエスカレーションと RACI（`PM`）、管理計画の最終判断（`PM`）                         | 変更要求ログの変更 ID             |
| 連絡手段・チャネル       | チャットのチャネル設定と簡易手順書の連絡先（`DEV`）、本書のコミュニケーション機会（`PM`） | 課題ログの課題 ID                 |

- _UNDECIDED_: 営業時間外の緊急連絡手段。決まるまで、コミュニケーション機会の停止連絡は営業時間外の伝達先と手段が定まらず、翌営業日の開店前の店頭連絡で代える。判断ゲート「初期リリース・店頭試用開始」の前に `PO` が決定する。
- _UNDECIDED_: つけの記録方法の切替開始日。管理計画の U-03 が決まるまで、常連顧客への告知の掲示開始日が定まらない。U-03 の確定と同時に `PO` が決定する。
