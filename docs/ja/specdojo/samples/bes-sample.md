# 業務イベント: 店頭の現金会計の確定

駄菓子屋きぬやで、入力途中の取引や金額の確認を販売実績と混同しないため、一取引の現金会計が確定した事実を定義する。店主以外が店番しても、同じ境界で記録対象を判断できるようにする。

_ASSUMPTION_: 本例では単一店舗・一台のタブレットでの店頭現金販売を扱う。現金を受領してから会計を確定し、同じ取引を再表示しても別の会計確定とはしない。つけ販売、返品、取消、日次締めは別の出来事として扱う。

業務イベント一覧に対応付けるイベント名は「店頭の現金会計が確定した」、個別仕様 ID は `bes-cash-sale-confirmed` とする。上位一覧の文書 ID は `bes-index` として仮置きする。この仮置きの確認・照合は BA（業務分析担当）が担い、業務イベント一覧（BEL）の作成時（イベント処理とテスト設計への引き渡し前）に確定する。実案件での承認・公開に先立ち、一覧との対応確認を完了するか、未確定の制約事項として PO の承認を得て記録する。本書は完成記述の例であり、実案件での承認済み仕様を示すものではない。

## 1. 何が起きたか

一つの取引について、購入明細と請求金額を店番担当が確認し、現金の受領を確認したうえで会計を確定した。

- 一取引の確定につき一回発生する。一取引に複数の商品明細があっても、明細ごとには発生しない。
- 商品の追加、数量の修正、合計金額の表示だけでは発生しない。
- 確定後の控えの印字や在庫への反映は、この出来事を受けた後の業務で扱う。

定義を利用できると判断する基準は、「発生条件」の各場面から発生有無と回数を決められ、「事実データ」から同じ取引の明細と金額を対応付けられることである。実案件では、業務定義と公開可否の承認を人間の PO である店主代表が担い、開発担当が条件・データの対応を説明する。上位一覧 `bes-index` などの仮置き参照は、引き渡し前に BA が本登録先の ID と照合・確定することを原則とし、未解決のまま引き渡す場合は制限事項として PO が承認してレビュー結果に残す。承認時期はイベント処理とテスト設計へ引き渡す前とし、承認結果は対象案件のレビュー結果に記録する。

## 2. いつ

店番担当が現金の受領と釣銭を確認し、販売管理システムが対象取引の会計確定を記録した時点を発生時点とする。

- 顧客が現金を渡した時刻と、会計確定を記録した時刻を区別する。受領だけでは確定の成立を示さない。
- 発生時刻は個別取引の確定記録を基準にし、画面を参照した時刻や控えを再印字した時刻へ置き換えない。

発生時点は営業日による集計時点とは分ける。日次締めの確定時刻を、個別取引の会計確定時刻として用いない。

## 3. 誰が／何が

| 起点区分       | 確定を要求する主体 | 確定を記録する主体 | 主体ごとの責務                                                     |
| -------------- | ------------------ | ------------------ | ------------------------------------------------------------------ |
| 店主による店番 | 店主代表           | 販売管理システム   | 店主代表が明細・請求金額・現金の受領・釣銭を確認して確定を要求する |
| 家族による店番 | 家族利用者代表     | 販売管理システム   | 家族利用者代表が同じ確認を行い、確定を要求する                     |

- 本書では、上の二つの役割を業務上の「店番担当」と呼ぶ。誰が店番していても発生境界は同じである。
- 販売管理システムは、一取引の会計確定と発生時点を記録するシステムである。現金を受け取った事実の確認は店番担当が担う。
- 顧客は商品を購入して現金を渡す主体であり、システムへ会計確定を要求する主体ではない。

## 4. 発生条件

次の条件がすべて成立したときに発生する。

1. 対象は店頭の現金取引であり、会計がまだ確定していない（取引状態 `payment_status` が未確定 `unconfirmed`。仮置き ID `cdsd-order-status` / `bdd-sales-record`）。
2. 一件以上の商品明細があり、店番担当が購入内容と請求金額を確認している。
3. 受領金額が請求金額以上で、店番担当が受領と釣銭を確認している。
4. 店番担当の確定要求により、対象取引の会計確定が記録された。

金額計算と端数処理は販売金額の業務ルール `br-sales-amount`（[[specdojo:br-sample|販売金額計算の業務ルールサンプル]]）、確定後の控え・在庫反映は販売プロセス（仮置き ID `bps-sales-order-flow`）で扱う。本書ではそのロジックや手順を展開しない。

| 場面                                         | 発生有無・回数         | 判断根拠                             |
| -------------------------------------------- | ---------------------- | ------------------------------------ |
| 複数の商品明細を一つの取引として確定         | 一回                   | 明細数ではなく取引の確定が単位である |
| 合計表示後、受領金額が請求金額未満           | 発生しない             | 受領条件を満たしていない             |
| 現金を受領した後、確定前に入力内容を見直し中 | 発生しない             | 確定の記録がない                     |
| 会計確定の記録が成立する前に処理が停止       | 発生しない             | 受領済みでも確定の成立が確認できない |
| 確定済み取引の控えを再印字                   | 新たには発生しない     | 同じ確定済み取引の参照である         |
| 確定後に控えの印字が失敗                     | 確定時の一回のまま     | 印字は確定後の処理である             |
| つけでの購入を受け付ける                     | 本イベントは発生しない | 本例の現金取引の範囲外である         |

確定が記録されたか分からない場合に、現金の受領だけから発生済みと推定しない。事実の照合・復旧手順は販売プロセスへ委ねる。

## 5. 事実データ

項目名は業務上の論理名とする。型、値の形式、構造、保存形式は販売記録のデータモデル・schema（仮置き ID `bdd-sales-record` / `schema:sales-record`）で定義し、本書では重複定義しない。

| 項目         | 業務上の意味                                                             | 必要になる条件               |
| ------------ | ------------------------------------------------------------------------ | ---------------------------- |
| 取引番号     | 確定した一つの販売取引を識別する                                         | 常に必要                     |
| 会計確定時点 | 本書の「いつ」で定義した成立時点                                         | 常に必要                     |
| 確定担当     | 確定を要求した店番担当を識別する。役割だけでなく実際の担当をたどれる情報 | 常に必要                     |
| 商品明細     | 購入した商品と数量、および会計確定時点の販売金額の内訳                   | 常に必要                     |
| 請求金額     | 当該取引で顧客に請求した金額                                             | 常に必要                     |
| 受領金額     | 店番担当が受領を確認した現金の額                                         | 常に必要                     |
| 釣銭金額     | 当該会計で確認した釣銭の額                                               | 常に必要。釣銭なしも識別する |
| 支払区分     | 当該イベントが現金会計であることを示す情報                               | 常に必要                     |

### 5.1. 取引との対応の確認例

この例では、取引番号を会計確定と明細の対応に用いる。一括要求・並列要求は扱わないため、要求を束ねる識別子を追加しない。取引番号の採番規則はここでは定めない。

| 確認対象                           | 確認する事実                                                               |
| ---------------------------------- | -------------------------------------------------------------------------- |
| 取引 `TX-A` に二つの商品明細がある | 一回の確定に両明細が含まれ、どちらも `TX-A` の請求金額の根拠としてたどれる |
| 続けて別の取引 `TX-B` を確定する   | 二つの取引の明細・受領金額が混ざらず、確定はそれぞれ一回となる             |
| `TX-A` の控えを再印字する          | 同じ取引番号を参照し、新しい会計確定として数えない                         |

データモデルとの照合では、上の確認例に加えて、同じ取引の受領金額・釣銭金額も対応することを確認する。モデル上の物理項目名や保存単位が変わっても、この業務上の対応を維持する。
