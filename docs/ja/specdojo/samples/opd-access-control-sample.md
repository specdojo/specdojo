# 駄菓子屋きぬや 販売管理システム 運用方針・設計（権限・アカウント）

## 1. 概要（access-control）

本書は、[[specdojo:opd-index-sample|運用方針・設計（全体構成）]] の「権限・アカウント運用（棚卸し・監査ログ）」を具体化する分冊である。店主代表と家族利用者代表が交代で店番をし、店頭のタブレット 1 台を共用するため、誰がいつつけ残高や価格を変えたかを後から確かめられなければ、誤操作や不正な訂正を店主代表が判断できない。本書は権限区分、付与・剥奪の契機、棚卸しの合否、監査ログの記録対象、緊急権限を定める。前提とする目的と制約は [[specdojo:prj-overview-sample|プロジェクト概要]] に従う。

次の未決事項は `PO` が決める。決まるまでは、該当する行の扱いで運用する。

| 未決事項                                            | 判断者 | 決まるまでの扱い                                                           | 影響する節 |
| --------------------------------------------------- | ------ | -------------------------------------------------------------------------- | ---------- |
| _UNDECIDED_: `PO` に連絡がつかないときの緊急権限    | `PO`   | 緊急権限を使わず、紙の販売控えへ切り替えて `PO` の連絡を待つ               | 緊急権限   |
| _UNDECIDED_: 監査ログの保管先を記録の正本と分けるか | `PO`   | 記録の正本と同じホスティング環境に置き、監査ログの削除権限を誰にも付けない | 監査ログ   |

## 2. 権限・アカウント運用（棚卸し・監査ログ）

アカウントは 1 人 1 つとし、`opd-index` のとおり共有のアカウントは作らない。_ASSUMPTION_: 販売管理システムは利用者ごとのログインと、権限区分ごとの操作の制限、一定時間の無操作による自動ログアウトを備える。

### 2.1. 権限区分

`opd-index` は付与の対象を店番担当と `DEV` に限るだけで、操作の範囲を定めていない。次の表は、権限区分ごとの付与対象と、できる操作・できない操作の対応を示す（具体化）。

| 権限区分 | 付与対象                 | できる操作                                               | できない操作                                           |
| -------- | ------------------------ | -------------------------------------------------------- | ------------------------------------------------------ |
| 店番     | 店主代表、家族利用者代表 | 販売の記録、在庫の確認、つけの記録と残高の確認、日次締め | 価格・商品マスタの変更、つけ残高の訂正、アカウント管理 |
| 管理     | 店主代表（`PO`）         | 店番の操作に加え、価格・商品マスタの変更、つけ残高の訂正 | 監査ログの削除                                         |
| 運用     | `OPS`                    | アカウントの作成・停止・区分の変更、監査ログの閲覧       | 販売・つけの記録と訂正                                 |
| 保守     | 開発担当（`DEV`）        | 障害の調査に要る記録の閲覧、バックアップの確認           | 記録の変更（緊急権限を使う場合を除く）                 |

店主代表は店番と管理の両方を持つ。それ以外の人には 1 つの権限区分だけを付ける。

### 2.2. 付与・剥奪の契機

承認者は `opd-index` のとおり `PO` とし、`OPS` が操作する。次の表は、付与・剥奪の契機ごとに、何をいつまでに行うかを示す。

| 契機                                             | 行うこと                     | 期限                     | 差分の種類 |
| ------------------------------------------------ | ---------------------------- | ------------------------ | ---------- |
| 新たに店番に入る人が決まる                       | 店番の区分を付与する         | 最初の店番の前日まで     | 具体化     |
| 店番の予定表から外れて 3 か月たつ                | アカウントを停止する         | 棚卸しで見つけた当日     | 補足       |
| タブレットの紛失、パスワードの漏えいの疑いがある | 該当するアカウントを停止する | 気付いてから 15 分以内   | 補足       |
| 開発担当の保守作業が終わる                       | 保守の区分を外す             | 作業の終了を確かめた当日 | 具体化     |

付与・剥奪のたびに、`OPS` は申請日・対象の権限区分・承認者・実施日を権限変更記録に残す。承認の記録がない付与は、不正な付与として扱う。

### 2.3. 共用タブレットでのログイン

`opd-index` の「共有のアカウントは作らない」は、タブレットを共用する店では操作の記録者を分けるために次の扱いを要する（具体化）。

- 店番を交代するときは、前の店番担当がログアウトし、次の店番担当が自分のアカウントでログインする。
- 10 分操作がない場合は自動でログアウトする。会計の途中で離れても、別の人の名前で記録が残らないようにするためである。
- 交代時のログアウトを忘れた記録は、日次締めで店番担当が気付いた時点で日次締め記録に残し、`PO` が訂正の要否を決める。

### 2.4. 棚卸し

周期は `opd-index` のとおり月次点検で行い、本節は照合の対象と合否を定める（具体化）。実施者は `OPS` とする。

棚卸しでは、有効なアカウントの一覧を店番の予定表・権限変更記録と照合する。次の条件をすべて満たしたら合格とする。

| 確かめること                                               | 合格条件                                   |
| ---------------------------------------------------------- | ------------------------------------------ |
| 店番の予定表にない人の有効なアカウントが残っていない       | 0 件                                       |
| アカウントの権限区分が権限区分の表と一致する               | 不一致 0 件                                |
| すべての付与に権限変更記録の承認がある                     | 承認のない付与 0 件                        |
| 前回の棚卸し以降の緊急権限の使用に、事後の確認が済んでいる | 未確認 0 件                                |
| 見つけた差異の解消が棚卸し記録に残っている                 | 差異ごとに解消日と対応内容が記録されている |

不要なアカウントや区分の不一致は、`OPS` がその日のうちに停止・修正する。承認のない付与を見つけた場合は、`OPS` が直ちに停止し、当日中に `PO` へ報告して、原因と対策をプロジェクトの課題管理へリスクとして登録する。

月次点検ができなかった月は `opd-index` の定期運用方針のとおり翌週に行う。翌週も棚卸しができなければ、`OPS` が `PO` へ報告し、`PO` が実施日を決める（補足）。

### 2.5. 監査ログ

`opd-index` はログイン、つけ残高の変更、価格の変更を記録対象とし、保管期間を 1 年とする。本節は記録対象の追加と確かめ方を定める（具体化）。

- 記録対象に、アカウントの作成・停止・区分の変更と、緊急権限の開始・終了・その間の操作を加える。
- 各記録には、日時、アカウント、操作の種類、変更前と変更後の値を残す。
- 月次点検で `OPS` が、つけ残高の訂正と価格の変更の件数を数え、管理の区分を持つアカウント以外の操作が 0 件であることを確かめる。0 件でない場合は、承認のない付与と同じく `PO` へ報告する。
- 監査ログはどの権限区分からも削除できないようにする。

### 2.6. 緊急権限

緊急権限は、P1 の障害の復旧で記録を直す必要があり、通常の付与を待てないときに、`DEV` へ一時的に記録の変更を許す権限である。専用のアカウントは作らず、`DEV` のアカウントの区分を一時的に上げる。共有のアカウントを作らない方針と揃えるためである。

| 項目       | 方針                                                                                            |
| ---------- | ----------------------------------------------------------------------------------------------- |
| 使える場面 | `opd-index` の障害対応方針で P1 とした障害の復旧に、記録の変更が要る場合だけ                    |
| 承認       | `PO` の承認を得てから `OPS` が区分を上げる。`PO` の承認がない使用は認めない                     |
| 失効       | 付与から 24 時間、または `OPS` が復旧を確かめた時点の早い方で、区分を元に戻す                   |
| 延長       | 例外として、復旧が 24 時間で終わらない場合に限り `PO` が理由を記録して 1 回だけ 24 時間延ばせる |
| 事後の確認 | 終了後の次の営業日までに、`OPS` が監査ログで操作を確かめ、結果を `PO` へ報告する                |

_ASSUMPTION_: 区分を元に戻す操作は、販売管理システムの期限付きの権限変更で自動で行う。自動で戻せない場合は、`OPS` が失効の時刻に手で戻し、権限変更記録に残す。
