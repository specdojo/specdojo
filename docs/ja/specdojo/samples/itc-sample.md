# 内部結合テストカタログ: 会計確定（駄菓子屋きぬや 販売管理システム）

## 1. 概要（sales-checkout）

店頭操作端末からの会計確定の要求が、販売・在庫記録サービスを経て業務記録 DB に販売記録の保存と在庫減算を1トランザクションで確定するまでの縦スライス（`PATH-02`・`PATH-03`）。主要コンポーネントは記録サービスの会計確定ユースケース、販売・在庫の Repository、業務記録 DB である。

本書の `itc-<term>` は `itc-sales-checkout` であり、括り方・ケース表の共通カラムは [[specdojo:itc-index-sample|内部結合テストカタログ: 概要]] に従う。開発担当（DEV）がケースを追加しテストコードを実装する。同行レビュー担当（QE）がトレースと期待値の判定可能性をレビューし、全ケースの証跡がテストコードと CI run 番号へ辿れることを確認してから `ready` 化を店主代表（PO）へ諮る。

## 2. 責務（結合として保証）

- 確定した会計の販売記録1件と在庫減算を同じトランザクションで保存する（商品A×2: 販売記録1件、在庫5→3個）。
- 在庫と同数の購入で在庫を0個にし、負の在庫を保存しない。
- 在庫不足の会計を確定せず、エラー種別 `out-of-stock` を応答して販売・在庫の両テーブルを変更しない。
- 業務記録 DB が更新を拒否した場合にエラー種別 `checkout-failed` を応答し、販売記録・在庫とも確定前から差分を残さない。
- 確定済みと同じ取引番号の再送をエラー種別 `duplicate-transaction` で応答し、販売記録を二重に保存しない。
- 対象商品が特定できない購入・数量が不明な購入を保留（`pending-product`・`pending-quantity`）として応答し、販売記録を作らず在庫を変えない。

## 3. 対象外

- 対象外: つけ販売時のつけ残高の更新と照会（理由: 顧客と残高の集約が別 term の責務、代替: `itc-credit-balance`）。
- 対象外: 会計確定後のレシート印刷の成否（理由: `receipt-print` との実疎通が必要、代替: ET の `etc-receipt-print`）。
- 対象外: 請求額の計算と在庫引当の判定ロジック（理由: DB 実接続を要しない、代替: UT の [[specdojo:utc-sample|単体テストカタログ: 会計確定]]）。

## 4. 結合境界/依存/環境前提

- 入口: 記録サービスの会計確定ユースケース（入力は取引番号・購入明細・受領額）。出口: 確定結果またはエラー種別の応答と、業務記録 DB の販売・在庫テーブルの状態。
- 結合対象: 会計確定ユースケース＋販売 Repository＋在庫 Repository＋業務記録 DB。
- 依存の扱いは [[specdojo:itc-index-sample|内部結合テストカタログ: 概要]] の「内部結合テスト共通の境界/依存の扱い」に従い、外れる扱いはない。本 term では次を使う。

| 依存                     | 扱い                                                   | 再現性条件                                         |
| ------------------------ | ------------------------------------------------------ | -------------------------------------------------- |
| 業務記録 DB              | 実（マイグレーション適用済みのコンテナ DB）            | 各ケース開始時に `kinuya-test-data` を seed する   |
| `receipt-print` コマンド | Stub（成功を返す）                                     | 応答を成功に固定し、印刷結果を期待値に含めない     |
| 時刻                     | 固定クロック（`Asia/Tokyo`、営業日15:30）              | 販売記録の確定時刻を固定値で比較する               |
| DB の更新拒否            | 在庫テーブルへの更新拒否をテスト用トリガで発生させる   | 更新拒否ケースに限り設定し、ケース終了時に除去する |
| 取引番号の採番           | 実装の採番。再送ケースのみテストから同じ取引番号を指定 | 期待値は件数と差分で書き、採番値に依存しない       |

- 環境前提: `kinuya-it-compose` でコンテナ DB を起動し、CI ではジョブごとに `it_<CI run 番号>` のスキーマで分離する。1ケースのタイムアウトは30秒とし、失敗時は SQL・取引番号・リクエスト ID をテスト結果へ残す。
- 観測点: 応答の確定結果・エラー種別、販売テーブルの件数と内容、在庫テーブルの在庫数。
- _ASSUMPTION_: トランザクション分離レベルは `READ COMMITTED` とする。`kinuya-record-schema` の確定時に ARC が見直し、変わる場合は DEV が同時確定の観点を追加する。PJR への引き継ぎは itc-index 側の同じ論点に集約し、本書では起票しない。

## 6. テスト観点とケース

[[specdojo:itc-index-sample|内部結合テストカタログ: 概要]] の観点の型のうち、「結合 I/F の契約」は各観点の応答（確定結果・エラー種別）の期待値で担保し、独立した観点にしない。「状態遷移の整合性」は未確定のまま確定へ進まない保留の維持だけを「未確定の購入の保留」の観点で扱い、補完後の確定への遷移は扱わない。「依存障害時の挙動」は DB の更新拒否を「確定できない会計のロールバック」で扱い、未保存を成功と応答しないことを `it-sales-checkout-transaction-boundary-020` で確かめる。DB 停止・接続断は採用しない（理由: 検証用コンテナ DB の停止は CI の他ケースを巻き込み再現性を保てない、代替: ST の障害・回復）。「セキュリティ境界」は該当なし（単一店舗・端末1台）。
