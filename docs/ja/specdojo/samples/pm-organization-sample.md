# 組織定義: 駄菓子屋きぬや 販売管理システム

## 1. 組織モデル

単一店舗・タブレット1台で販売、在庫、つけの記録を続けるため、専門部署を設けない兼務体制とし、店主代表が人間の `PO` を担う。

| 責任領域         | 設計方針                                         | 最終判断 | 実行・確認                                   |
| ---------------- | ------------------------------------------------ | -------- | -------------------------------------------- |
| 価値・範囲       | 日々の記録を優先し、機能の追加と優先順位を決める | `PO`     | `PM`（判断案の整理）、`BA`（業務観点の相談） |
| 業務・利用者確認 | 店主以外も同じ手順で販売・在庫・つけを扱えるか   | `PO`     | `BA`                                         |
| 費用・参加負荷   | 費用と参加時間の上限を決め、超過する計画を見直す | `PO`     | `PM`                                         |
| 計画・調整       | 作業順序、進捗、課題・リスクを管理する           | `PM`     | `PM`                                         |
| 実現・設計       | 実装・データ設計と技術的な是正                   | `DEV`    | `DEV`                                        |
| 品質・受入       | 品質計画と試験結果から店頭試用の受入を決める     | `PO`     | `QE`                                         |
| 公開・継続       | 導入準備、障害時の引き継ぎ、利用継続の可否       | `PO`     | `PM`、`DEV`                                  |

家族利用者は `BA` の操作確認で意見を出し、内部 Role の承認責任は持たない。兼務しても作業結果と承認の記録は分ける。AI Agent は草案、整理、実装、検証を支援し、最終判断は対応する Role の人間が行う。

## 2. ロール・owner方針

| Role code | 採用／未採用 | `owner` 使用可否 | 判断理由・プロジェクトでの扱い                                       |
| --------- | ------------ | ---------------- | -------------------------------------------------------------------- |
| `PO`      | 採用         | 可               | 目的、上限、受入、公開・継続を店主代表が判断する                     |
| `PM`      | 採用         | 可               | 店頭試用までの作業順序と参加負荷を管理する。初期は兼務               |
| `BA`      | 採用         | 可               | 販売・在庫・つけの業務と、家族の店番時の確認を扱う                   |
| `DEV`     | 採用         | 可               | 実装・データ設計と修正を主導する                                     |
| `QE`      | 採用         | 可               | 記録漏れや残高誤りを実装とは別の観点で検証する                       |
| `ARC`     | 採用         | 不可             | 構成・データ管理方針の専門支援。設計作業は `DEV` が主導する          |
| `UX`      | 採用         | 不可             | 画面文言と操作説明の専門支援。利用者確認は `BA` が主導する           |
| `OPS`     | 採用         | 不可             | 導入・障害時対応・引き継ぎの専門支援。リリース準備は `PM` が主導する |

未採用の標準ロールと独自ロールはなし。使用可能な `owner` は「可」の5ロールで、初期 RACI の列もこの5ロールとする。専門支援3ロールの意見は主導ロールが作業結果へ取り込む。

## 4. 見直し条件

`PM` が週次の進捗確認と変更要求の受付時に確認する。Role や専任者を増やす前に、兼務の割り当てと作業順序の変更で足りるかを検討する。

| トリガー                                           | 確認すること                                               | 更新先                                                           | 判断者                                       |
| -------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------- | -------------------------------------------- |
| 参加・離脱・交代の申出                             | 担当できなくなる責任と引き継ぎ先                           | メンバー定義、RACI、Schedule。責任境界が変われば本書・ロール定義 | 再配置は `PM`、採用・`owner` 使用可否は `PO` |
| 兼務による作業・承認待ちで Schedule の期限を超えた | 止まったのが実作業か承認か、分担で解消できるか             | メンバー定義、RACI、Schedule。分離する場合は本書                 | 作業順序は `PM`、費用・参加時間上限は `PO`   |
| スコープ変更、成果物追加、専門支援の独立タスク化   | 業務・設計・確認範囲への影響、既存ロールで主導できるか     | 本書、ロール定義、メンバー定義、RACI、WBS、Schedule              | `PO`                                         |
| 店頭試用・公開の候補、運用範囲の変更               | 導入・復旧・引き継ぎの実施担当と人間の承認者に欠落がないか | 本書、RACI、メンバー定義、Schedule、ステークホルダー登録簿       | `PO`                                         |
| AI Agent の追加・削除、支援権限の変更              | 承認を委ねていないか、人間へ引き継げるか                   | agent 定義、本書、RACI、Schedule                                 | `PO`                                         |

採用・使用可否を変えたら、`QE` が使用不可ロールの `owner`、採用外の RACI 列、引き継ぎ先のないタスクが残っていないことを確かめて見直しを閉じる。
