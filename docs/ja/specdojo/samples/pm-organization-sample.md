# 組織定義: 駄菓子屋きぬや 販売管理システム

## 1. 組織モデル

単一店舗・タブレット1台で販売、在庫、つけの記録を続けるため、店主代表、開発担当、家族利用者が協働する小規模な兼務体制とする。店主代表が人間の `PO` を担い、専門部署を設けず、初期リリースと店頭試用に必要な責任を分ける。

| 責任領域         | 設計方針                                                   | 最終判断 | 実行・確認                                   |
| ---------------- | ---------------------------------------------------------- | -------- | -------------------------------------------- |
| 価値・範囲       | 日々の記録を優先し、機能の追加と優先順位を判断する         | `PO`     | `PM`（判断案の整理）、`BA`（業務観点の相談） |
| 業務・利用者確認 | 店主以外も同じ手順で販売・在庫・つけを確認できるか確かめる | `PO`     | `BA`                                         |
| 費用・参加負荷   | 費用と参加時間の上限を決め、超過する計画を見直す           | `PO`     | `PM`                                         |
| 計画・調整       | 作業順序、進捗、課題・リスクを管理する                     | `PM`     | `PM`                                         |
| 実現・設計       | 店頭端末での実装・データ設計と技術的な是正を判断する       | `DEV`    | `DEV`                                        |
| 品質・受入       | 品質計画と試験結果を確認し、店頭試用の受入を判断する       | `PO`     | `QE`                                         |
| 公開・継続       | 導入準備、障害時の引き継ぎ、利用継続の可否を判断する       | `PO`     | `PM`、`DEV`                                  |

「実行・確認」欄は内部 Role の分担を示す。家族利用者は `BA` が行う操作確認へ参加して意見を出し、内部 Role の承認責任は持たない。

同じ人間が複数ロールを兼務しても、作業結果と承認の記録を分ける。AI Agent は草案、整理、実装、検証を支援できるが、各領域の最終判断は対応する Role の人間が行う。

## 2. ロール・owner方針

採用判断と Schedule の `owner` 使用可否を次表に定める。Role の採用は専任者の配置を意味せず、実行主体と兼務は「正本と責任境界」のメンバー定義で管理する。

| Role code | 採用／未採用 | `owner` 使用可否 | 判断理由・プロジェクトでの扱い                                                           |
| --------- | ------------ | ---------------- | ---------------------------------------------------------------------------------------- |
| `PO`      | 採用         | 可               | 店舗の目的、上限、受入、公開・継続を店主代表が判断するため                               |
| `PM`      | 採用         | 可               | 店頭試用までの作業順序と参加負荷を継続して管理するため。初期は兼務とする                 |
| `BA`      | 採用         | 可               | 販売・在庫・つけの業務と、家族の店番時の確認を作業単位で扱うため                         |
| `DEV`     | 採用         | 可               | 実装・データ設計と修正を主導し、その技術的判断を引き受けるため                           |
| `QE`      | 採用         | 可               | 記録漏れや残高誤りを、実装作業とは別の確認観点で検証するため                             |
| `ARC`     | 採用         | 不可             | タブレット1台の構成・データ管理方針を検討する専門支援。初期の設計作業は `DEV` が主導する |
| `UX`      | 採用         | 不可             | 店主・家族向けの画面文言と操作説明を検討する専門支援。初期の利用者確認は `BA` が主導する |
| `OPS`     | 採用         | 不可             | 導入・障害時対応・引き継ぎを準備する専門支援。初期のリリース準備は `PM` が主導する       |

未採用の標準ロールおよび独自ロールは、いずれもなし。使用可能な `owner` は「可」の5ロールに限定する。

ロール定義の8ロールのうち、初期 RACI は作業と判断を主導する5ロールを列に持つ。専門支援3ロールの意見は、上表の主導ロールが作業結果へ取り込む。専門支援を独立したタスクへ分離する場合は、「見直し条件」に従い、`owner` 使用可否と RACI 列を更新してから Schedule に追加する。

## 4. 見直し条件

`PM` は週次の進捗確認と変更要求の受付時に、次表のトリガーを確認する。新しい Role や専任者を増やす前に、既存の兼務割り当てと作業順序の変更で対応できるか検討する。

| トリガー                                                           | 確認すること                                                                                                        | 更新先                                                               | 判断者                                                          |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------- |
| 参加・離脱・交代の申出を受けた                                     | メンバー定義と未完了タスクを照合し、担当不能な責任と引き継ぎ先を特定する                                            | メンバー定義、RACI、Schedule。責任境界が変わる場合は本書・ロール定義 | `PM` が再配置を判断。採用・`owner` 使用可否の変更は `PO` が判断 |
| 兼務による作業・承認待ちで Schedule の期限を超えた                 | 期限と待ち理由を確認し、実作業と承認のどちらが止まったか、分担で解消できるか確認する                                | メンバー定義、RACI、Schedule、課題管理簿。分離する場合は本書         | `PM` が作業順序を判断。費用・参加時間上限の変更は `PO` が判断   |
| スコープ変更、成果物追加、専門支援の独立タスク化を提案した         | `BA` が業務・利用者への影響、`DEV` と `ARC` が設計への影響、`QE` が確認範囲を調べ、既存ロールで主導できるか確認する | 本書、ロール定義、メンバー定義、RACI、WBS、Schedule、変更要求ログ    | `PO` が採用・`owner` 使用可否と範囲変更を判断                   |
| 店頭試用・公開の候補を提示した、または運用範囲を変える要求を受けた | 試験結果と導入・復旧・引き継ぎ手順を確認し、実施担当と人間の承認者に欠落がないか調べる                              | 本書、RACI、メンバー定義、Schedule、ステークホルダー登録簿           | `PO` が公開・継続を判断                                         |
| AI Agent の追加・削除または支援権限の変更を提案した                | 作成・検証の支援範囲と実行記録を確認し、承認を委ねていないか、人間へ引き継げるか調べる                              | agent 定義、本書、RACI、Schedule                                     | `PO` が委任範囲を判断                                           |

採用・使用可否の変更時は、`PM` がロール定義、メンバー定義、RACI、WBS、Schedule の影響箇所と担当 Role を特定し、更新順序・期限を追従タスクにする。文書の置き換え・廃止は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。`QE` が、使用不可ロールの `owner`、採用外の RACI 列、引き継ぎ先のないタスクが残っていないことを確認して見直しを閉じる。

未決事項は対応する管理簿または PJR に、担当 Role と転送先レコードを付けて残す。兼務による期限超過は [[specdojo:pm-issue-log-sample|課題管理簿]]、引き継ぎ不能の懸念は [[specdojo:pm-risk-register-sample|リスク登録簿]]、上限・範囲の変更は [[specdojo:pm-change-request-log-sample|変更要求ログ]] に分け、決定事項は `pm-decision-log.md`（本例では未整備）の代わりに同じ課題・変更要求の記録へ判断者と根拠を追記する。`PM` が期限と追従完了を確認し、未決の担当変更を前提に着手させない。
