# 駄菓子屋きぬや 販売管理システム 運用手順（バックアップ確認・リストア）

## 1. 概要

駄菓子屋きぬや 販売管理システムの夜間バックアップを確かめ、記録が失われたときに復元し、月次の演習で復元できることを確かめる手順を定める `opr-backup-restore` である。[[specdojo:opr-sample|運用手順]]（`opr-index`）の差分・具体化であり、証跡・優先度・エスカレーションの共通規約は `opr-index` に従う。目的は、タブレットや記録の正本に異常が起きても、販売・在庫・つけの記録を前日の閉店時点まで取り戻し、営業日の記録を途切れさせないことである。つけ残高を失うと常連客との精算ができなくなるため、つけの記録を含めて戻せることを演習ごとに確かめる。

次の表は、運用方針で未決の値が本書のどの手順に影響し、決まるまでどう判定するかを示す。値が決まった時点で、演習の判定基準の表と証跡の表を差し替える。

| 未決事項                                      | 決まるまでの手順上の扱い                                                                       | 影響する章                           |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------ |
| _UNDECIDED_: RTO（復元にかけてよい時間）      | 閉店（18:00）から翌日の開店前点検（9:45）までに、復元と照合を終えられれば合格とする            | バックアップ確認・リストア手順       |
| _UNDECIDED_: RPO（失ってよい記録の範囲）      | 前日の閉店時点の日次締めまでの記録が戻れば合格とし、当日分は紙の控えと日次締め記録から転記する | バックアップ確認・リストア手順       |
| _UNDECIDED_: バックアップの保管期間           | 世代を消さずに残す                                                                             | バックアップ確認・リストア手順、証跡 |
| _UNDECIDED_: 検証用の環境へ戻したデータの扱い | _ASSUMPTION_: 演習の終了時に、検証用の環境へ戻した顧客・つけのデータを消す                     | バックアップ確認・リストア手順       |

## 2. 手順適用範囲・前提

次の表は、本書の手順が対象とする範囲と、手順を行う前提を示す。

| 項目     | 内容                                                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 対象     | 記録の正本であるホスティング環境のデータベース（販売・在庫・顧客・つけ・日次締め）の夜間バックアップ、本番への復元、月次の復元演習 |
| 対象外   | タブレット本体の設定、店内の紙の点検ノート・連絡帳、プロジェクトの課題管理。紙の販売控えへの切替と転記は `opr-incident` で扱う     |
| 時間帯   | 確認は開店前点検（9:45 から）。本番への復元は閉店後、P1 で `PO` が決めた場合は営業時間中も行う。演習は月次点検の日に行う           |
| 必要権限 | 確認は店番担当の記録の権限、復元と演習は `DEV` の管理者の権限、演習結果の確認は `OPS` の閲覧の権限                                 |
| 使用手段 | ホスティング環境のバックアップの機能と実行ログ、検証用の環境、販売管理システムの日次締めの画面                                     |
| 連絡先   | `opr-index` の手順適用範囲・前提の連絡先に従う                                                                                     |

演習で検証用の環境を上書きするため、`OPS` は演習の前に、`DEV` が検証用の環境で運用変更の確認を進めていないことを確かめる。確認中であれば、演習をその確認の後に回す。

## 3. 日次・週次・月次点検手順

次の表は、バックアップに関わる点検と、点検を終えたと判定する条件を示す。週次の点検は置かない。

| 頻度           | 手順                                                                   | 実施者   | 完了条件                                                               | 証跡                           |
| -------------- | ---------------------------------------------------------------------- | -------- | ---------------------------------------------------------------------- | ------------------------------ |
| 日次（開店前） | 前日の閉店後の日時でバックアップの成功表示があるかを見る               | 店番担当 | 成功表示がある。ない場合は `opr-index` のアラート対応手順へ進んだ      | 日次点検の記録                 |
| 月次           | バックアップ確認・リストア手順の演習を行う                             | `DEV`    | 演習の判定基準の表の全行に結果があり、不合格の行はエスカレーションした | 復元演習の記録、月次点検の記録 |
| 月次           | 月次点検の記録で、前月の日次点検の成功表示が営業日の全日にあるかを見る | `OPS`    | 成功表示のない日について、障害記録の `ticket_id` が付いている          | 月次点検の記録                 |

演習を月次点検の日に行えなかった場合は、`opr-index` の月次の実施漏れの行に従い、翌週の休業日に行う。

## 4. 障害対応手順

`opr-index` 参照。優先度・初動目標・エスカレーションは `opr-index` の障害対応手順に従う。P1 で記録が失われ、`PO` が復元を決めた場合は、本書のバックアップ確認・リストア手順の復元へ進む。

## 5. アラート対応手順

`opr-index` 参照。夜間バックアップの通知（開店時に成功記録なし）の確認・暫定対応・誤検知の扱いは `opr-index` のアラート対応手順で完結しており、本書で変える点はない。

## 6. バックアップ確認・リストア手順

取得は夜間バックアップが閉店後の日次締めの後に自動で 1 日 1 回行い、同じ日付の取得は同じ世代を上書きする。確認・復元・演習は次のとおりとする。

### 6.1. 確認

- 実施条件: 毎営業日の開店前点検。
- 手順: 店番担当がバックアップの記録の画面で、前日の閉店後の日時と「成功」の表示を見て、日次点検の記録に書く。
- 完了条件: 成功表示がある。表示がない、または失敗の表示であれば、`opr-index` のアラート対応手順の夜間バックアップへ進む。

### 6.2. 復元

本番への復元は、記録が失われるか壊れて、`PO` が復元を決めた場合に `DEV` が行う。

1. `DEV` が障害記録の `ticket_id` に、復元を決めた時刻と戻す世代（最新の成功したバックアップ）を書く。
2. 店番担当が新しい記録を止め、紙の販売控えへ切り替える（`opr-incident`）。
3. `DEV` が戻す世代を本番へ復元し、開始と終了の時刻を障害記録に書く。
4. `DEV` が、復元したデータの販売件数・つけ残高の合計を、前日の日次締め記録の値と比べる。
5. 店番担当が紙の控えと日次締め記録から当日分を転記し、`DEV` が転記した件数と金額を照合する。
6. 店番担当が販売・在庫・つけを各 1 件記録できることを確かめ、記録を再開する。

完了条件は、手順 4 と手順 5 の値がすべて一致し、手順 6 の 3 件を記録できたこととする。一致しない場合は、1 つ前の世代で手順 3 からやり直すかを `PO` が決める。

### 6.3. 演習

`DEV` が月次点検の日に、前日のバックアップを検証用の環境へ復元し、本番と比べる。次の表は、演習で何を確かめ、何を満たせば合格とするかを示す。

| 確かめること                        | 測り方                                                       | 合格条件                                                                   |
| ----------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 販売の記録が戻る                    | 復元したデータと本番の、前日の日次締めまでの販売件数を比べる | 件数が一致する                                                             |
| つけ残高が戻る                      | 復元したデータと本番の、顧客ごとのつけ残高の合計を比べる     | 合計が一致する                                                             |
| 記録を失う範囲が目標に収まる（RPO） | 復元したデータの最新の販売記録の時刻を見る                   | 前日の日次締めの時刻以降である（RPO が決まるまで）                         |
| 復元の時間が目標に収まる（RTO）     | 復元の開始から、上の 2 行の照合を終えるまでの所要時間を計る  | 閉店から翌日の開店前点検までの 15 時間 45 分以内である（RTO が決まるまで） |
| 復元したデータで記録できる          | 検証用の環境で販売・在庫・つけを各 1 件記録する              | 3 件とも記録できる                                                         |

`DEV` は結果を復元演習の記録に書き、`OPS` が月次点検で全行の結果を確かめる。演習の後、検証用の環境へ戻したデータを概要の未決事項の表の扱いで片付ける。

### 6.4. 演習で目標を満たさないときの判断とエスカレーション

次の表は、演習の不合格の種類ごとに、誰へ上げ、誰が何を決めるかを示す。

| 不合格の種類                             | 一次の扱い                                                                    | エスカレーションの条件                 | 判断者と決めること                                                     |
| ---------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------- | ---------------------------------------------------------------------- |
| 販売件数またはつけ残高の合計が一致しない | P2 として障害記録に登録し、`DEV` が原因を調べ、同じ週の休業日に演習をやり直す | やり直しでも一致しない                 | `PO`。バックアップが当てにならない間、閉店後に紙の控えも残すかを決める |
| 最新の記録が前日の日次締めより前である   | P2 として障害記録に登録し、夜間バックアップの取得時刻と日次締めの順を確かめる | 翌月の演習でも同じ結果になる           | `PO`。取得の時刻や頻度を変える変更要求を出すかを決める                 |
| 所要時間が目標を超える                   | 超えた時間と、時間がかかった手順を復元演習の記録に書く                        | 2 か月続けて超える                     | `PO`。RTO の値または復元の手順の見直しを決める                         |
| 検証用の環境で記録できない               | P2 として障害記録に登録し、`DEV` が復元の手順を見直す                         | 手順を見直した後の演習でも記録できない | `PO`。本番の復元を手順どおりに行えるとみなすかを決める                 |

`OPS` はエスカレーションの条件に当たった月の月次点検で、復元演習の記録と障害記録の `ticket_id` を添えて `PO` へ報告する。`PO` の決定は月次点検の記録に残し、手順を変える場合は `opr-index` の運用変更作業に従う。

## 7. バッチ再実行・失敗時対応

`opr-index` 参照。夜間バックアップの失敗の検知・再実行の上限（1 日 2 回）・重複の防止は `opr-index` のバッチ再実行・失敗時対応で定めている。本書の確認で失敗を見つけた場合は、その手順へ進む。

## 8. 運用変更作業

`opr-index` 参照。RTO・RPO・保管期間が決まり、取得の頻度や保管の設定を変える場合は、`opr-index` の運用変更作業で「アプリの版の更新」と同じ承認者・実施条件で行い、変更後の最初の夜間バックアップの成功表示を完了条件に加える。

## 9. アカウント付与・剥奪手順

本書の範囲外。バックアップと復元に専用のアカウントは置かず、`DEV` の管理者のアカウントで行うため、付与・剥奪は `opr-index` のアカウント付与・剥奪手順で完結する。

## 10. 問い合わせ一次対応手順

`opr-index` 参照。「昨日の記録が消えた」など復元を伴いうる問い合わせは、`opr-index` の問い合わせ一次対応手順で障害にあたるものとして扱う。

## 11. 証跡

次の表は、本書の手順の証跡をどこに残し、どの識別子で照合するかを示す。参照権限は `opr-index` の証跡の表に従う。

| 証跡種別       | 保存先                               | 保管期間                                  | 参照権限           | 最低限残す識別子                                                         |
| -------------- | ------------------------------------ | ----------------------------------------- | ------------------ | ------------------------------------------------------------------------ |
| 日次点検の記録 | 店内の点検ノート（紙）               | _UNDECIDED_                               | 店番担当、`OPS`    | 点検日、点検した役割、成功表示の日時                                     |
| 実行ログ       | ホスティング環境のバックアップの記録 | _UNDECIDED_: バックアップの保管期間と同じ | `OPS`、`DEV`       | `run_id`、実行日時、世代の日付                                           |
| 障害記録       | プロジェクトの課題管理               | _UNDECIDED_                               | `OPS`、`DEV`、`PO` | `ticket_id`、復元した世代、開始・終了の時刻、照合の結果                  |
| 復元演習の記録 | プロジェクトの課題管理               | _UNDECIDED_                               | `OPS`、`DEV`、`PO` | 月次点検の記録と同じ `ticket_id`、演習日、所要時間、判定基準の各行の結果 |

復元演習の記録には、復元した世代の `run_id` を添え、どの取得を戻したかを実行ログと照合できるようにする。保管期間が決まるまでは証跡を消さない。
