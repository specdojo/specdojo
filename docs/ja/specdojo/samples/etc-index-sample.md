# 外部結合テストカタログ: 概要（駄菓子屋きぬや 販売管理システム）

## 1. 本ドキュメントの目的と適用対象

[[specdojo:tsp-index-sample|テスト戦略・方針]] の外部結合テストを根拠に、駄菓子屋きぬや 販売管理システムの対象別カタログ（`etc-<term>`）が共通で使う分割基準・観点と条件の立て方・外部依存境界・合格基準・証跡を定める。個別の観点・条件・ケースは `etc-<term>` に置き、本書には書かない。

外部結合テストで防ぐ業務リスクは次の3つである。いずれも店主代表が記録を信用できなくなり、店主不在の店番を任せられなくなる。

- 印刷の失敗・無応答を会計の失敗と誤認し、同じ販売を記録し直して売上と在庫が二重に動く。
- 印刷が二重に実行され、来店客にレシートを2枚渡して会計済みかどうかを店番が判断できなくなる。
- 転送が途中で失敗した復元用コピーを「復元できる」と通知し、障害時に販売・在庫・つけの記録を回復できない。

適用対象は外部結合テストのカタログ群（本書と `etc-<term>`）とする。画面・記録サービス・業務記録 DB の結合は [[specdojo:itc-index-sample|内部結合テスト]]、店頭業務のシナリオは [[specdojo:stc-index-sample|総合テストカタログ 概要]]、利用者による確認は [[specdojo:atc-index-sample|受入テスト]] で扱う。仕様の正本はカタログとし、テストコードと CI の実行記録は実装と実行結果の証跡として使う。

## 2. テスト対象の括り方と分割基準

「外部」は、開発担当が運用しない製品・サービスとの境界とする。[[specdojo:ifd-sample|インフラ構成図]] の経路のうち、店舗プリンタを動かす `receipt-print` コマンドと、提供事業者が運用する復元用保管サービス（`PATH-05`・`PATH-06`）が該当する。業務記録 DB（`PATH-03`・`PATH-04`・`PATH-07`）は開発担当が同じ環境で運用するため内部結合テストに置く。

| `<term>`         | 表示名                 | 外部 I/F・経路                       | 失敗モードの性質                           | 主担当 | 運用責任・確認者                                     |
| ---------------- | ---------------------- | ------------------------------------ | ------------------------------------------ | ------ | ---------------------------------------------------- |
| `receipt-print`  | レシート印刷連携       | `receipt-print` コマンド（店舗端末） | 用紙切れ・無応答。再実行すると二重印刷する | DEV    | 印刷障害の一次対応は店番担当、結果の照合は店主代表   |
| `backup-storage` | 復元用保管サービス連携 | `PATH-05`（転送）・`PATH-06`（読取） | 通信断・認証失敗。同じコピーなら再送できる | DEV    | サービスの障害は提供事業者、保管可否の判断は店主代表 |

2つの I/F は失敗モードと再送の可否が異なるため統合しない。今後、同じ `receipt-print` コマンドで印刷する帳票（つけの残高票など）が増えても、失敗時の扱いが同じなら `etc-receipt-print` に含める。観点が 15 を超えるか、ケース表が 50 行を超えた時点で分割を見直す。

## 3. 対象外・除外理由（共通）

| 対象外                                       | 除外理由                                                  | 代替                                         | 例外（外部結合テストで扱う条件）                                   |
| -------------------------------------------- | --------------------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------ |
| 本番の復元用保管領域への転送・読取           | 本番のコピーを上書き・削除すると、障害時に復元できない    | 保管サービスの検証用領域                     | なし。本番の復元手順の確認は運用手順の訓練として別計画で行う       |
| プリンタ機種・用紙サイズの網羅               | 店舗で使う機種は1台で、機種差は運用で吸収できる           | 店舗プリンタの検証機1台で確認する            | 機種を変更する場合に限り、変更後の機種で印刷の契約観点を再実行する |
| 保管サービス自体の可用性・SLA                | 提供事業者の責任範囲で、自システムから制御できない        | 提供事業者の提供条件と障害通知の確認（運用） | なし                                                               |
| 長時間の連続印刷・大量転送の負荷             | 放課後ピークでも印刷は1時間60件で、負荷は総合テストで測る | 総合テストの性能測定                         | 1回の転送サイズが検証用領域の上限を超える見込みが出た場合          |
| キャッシュレス決済、仕入れ先とのシステム連携 | 初期リリースのスコープ外                                  | なし（スコープ改訂時に再判断する）           | なし                                                               |

## 4. 観点の立て方（共通）

観点は「外部境界を跨いだときに何を保証するか」を名詞＋振る舞いで書き、`etc-<term>` の章立てに使う。次の型を上から検討し、該当しない型は `etc-<term>` に理由を1行で残す。

| 観点の型       | `etc-receipt-print` での観点名 | `etc-backup-storage` での観点名 |
| -------------- | ------------------------------ | ------------------------------- |
| I/F 契約の遵守 | 印刷結果の判別                 | 転送結果の判別                  |
| 認証・認可     | 該当なし（端末内コマンド）     | 保管先の認証失効時の停止        |
| 失敗モード     | 印刷失敗時の会計維持           | 転送失敗時の再送と完全性        |
| データ整合性   | 印刷の重複防止                 | 復元用コピーと記録の一致        |
| 監視・運用性   | 印刷障害の店番への通知         | 保管失敗の店主代表への通知      |

`印刷コマンド`（何を保証するか不明）や `終了コード 2`（条件の粒度）は観点名にしない。

## 5. 条件の立て方（共通）

条件は観点ごとに、代表（正常）→ 境界（タイムアウト・再送回数の上限）→ 重大例外（二重印刷・不完全なコピー）の順に追加する。1つの条件は入力・状態・環境のどれか1つだけを変える。

- 入力: 明細1件・明細最大件数（30件）のレシート、転送対象の記録が0件・通常量。
- 状態: 用紙あり・用紙切れ、保管先の資格情報の有効・失効、同じコピー識別子の転送済み・未転送。
- 環境: 成功・異常終了・無応答（タイムアウト）・遅延（上限の直前）。無応答と遅延はスタブで再現する。

全組合せは作らない。用紙切れと保管先の障害が同時に起きる組合せのように、業務影響が同じになる組合せは代表1件だけ残す。

## 6. 観点/条件の採用基準と対象別への分配方針（共通）

観点は1つの合否命題、条件は1つの差分として採用し、採用理由には業務影響か上位仕様の要求を書く。主担当は外部 I/F で決め、2つの I/F に跨るものは従担当として参照だけ置く。

| 観点/条件                                    | 採用理由                                               | 主担当 `etc-<term>`  | 従担当              | 備考                                     |
| -------------------------------------------- | ------------------------------------------------------ | -------------------- | ------------------- | ---------------------------------------- |
| 印刷失敗時の会計維持／印刷コマンドの無応答   | 会計を記録し直すと売上と在庫が二重に動く               | `etc-receipt-print`  | なし                | 販売記録が1件のままかを観測する          |
| 印刷の重複防止／警告後に店番が再印刷する     | レシート2枚で会計済みかを判断できなくなる              | `etc-receipt-print`  | なし                | 印刷要求の回数を観測する                 |
| 転送失敗時の再送と完全性／再送上限での失敗   | 不完全なコピーを復元可能と通知すると記録を回復できない | `etc-backup-storage` | なし                | 保管先のコピー件数と通知内容を観測する   |
| 保管失敗の店主代表への通知／営業中の転送失敗 | 通知が店番の会計操作を止めると販売を続けられない       | `etc-backup-storage` | `etc-receipt-print` | 通知中も印刷が動くことを従担当で参照する |

## 7. 外部結合テスト共通の境界/依存/環境の扱い

| 項目                   | 方針                                                                                                                                |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 実疎通とスタブの分担   | I/F 契約・認証・正常系は検証機と検証用領域へ実接続する。無応答・遅延・再送上限はスタブで再現し、実接続では起こさない                |
| 検証用領域が使えない時 | 提供事業者の障害で実接続できない日は、スタブで回帰を続け、実接続の観点を「未実施」と記録する。2営業日続く場合は QE が判定を保留する |
| 資格情報               | 保管先の検証用資格情報は CI の secret に置き、ログとテスト結果へ出力しない。本番の資格情報はテストで使わない                        |
| タイムアウト・再送     | `receipt-print` は応答待ち10秒・自動再送なし。保管サービスは応答待ち30秒・再送2回（間隔5秒・10秒）、同じコピー識別子で再送する      |
| テストデータの分離     | 検証用領域のコピーは `et-<CI run 番号>-` で始まる名前で保管し、各テストの終了時に自分の名前のコピーだけを削除する                   |
| 証跡                   | テスト結果に CI run 番号、コピー識別子（保管サービスの応答 ID）、印刷要求の相関 ID（販売記録の取引番号）を残す                      |

合格基準は数値か状態で書く。例: 「応答待ち10秒で打ち切り、販売記録が1件・印刷要求が1回のまま、店番に印刷失敗の警告を表示する」「再送2回で失敗した場合、保管先の `et-` コピーが不完全と記録され、店主代表に『復元できるコピーなし』と通知する」。「印刷が正常に動くこと」のように観測点のない基準は書かない。

## 8. ケース表の共通カラム

`etc-<term>` のケース表は、全 `<term>` で次のカラム順を使う。記入例は `etc-receipt-print` の観点「印刷失敗時の会計維持」（`perspective_key`: `failure-handling`）の1行である。

| カラム                 | 区分             | 記入例                                                              |
| ---------------------- | ---------------- | ------------------------------------------------------------------- |
| `case_id`              | 必須             | `et-receipt-print-failure-handling-010`                             |
| 条件                   | 必須             | 入力: 明細2件の会計確定。状態: 用紙あり。環境: 印刷コマンドが無応答 |
| 手順（最小）           | 必須             | 会計を確定し、印刷の応答を待つ                                      |
| 期待値                 | 必須             | 10秒で打ち切り、販売記録が1件のまま、印刷失敗の警告を表示する       |
| 観測点（アサーション） | 推奨（運用必須） | 販売記録の件数、印刷要求の回数、警告の表示                          |
| 境界/依存              | 推奨（運用必須） | 無応答スタブ、応答待ち10秒、自動再送なし                            |
| トレース               | 推奨（運用必須） | tsp の外部結合テスト出口条件（印刷失敗の契約観点）                  |
| 優先度                 | 推奨（運用必須） | P0                                                                  |
| 自動化                 | 推奨（運用必須） | automated                                                           |
| 証跡                   | 推奨（運用必須） | `kinuya-ci-sales-recovery` の CI run 番号、取引番号                 |

`case_id` は `et-<term>-<perspective_key>-<nnn>` とし、`nnn` は 010 から10刻みで振る。観点名を改めても `perspective_key` と `case_id` は変えず、廃止したケースは番号を欠番にして再利用しない。テストコードは `case_id` をテスト名に含め、CI の結果から対象ケースを検索できるようにする。
