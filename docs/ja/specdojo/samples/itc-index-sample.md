# 内部結合テストカタログ: 概要（駄菓子屋きぬや 販売管理システム）

## 1. 本ドキュメントの目的と適用対象

[[specdojo:tsp-index-sample|テスト戦略・方針]] の内部結合テストを根拠に、駄菓子屋きぬや 販売管理システムの対象別カタログ `itc-<term>` が共通で使う括り方・観点と条件の立て方・依存の扱い・ケース表の書き方をそろえ、品質・粒度・責任範囲を統一する。個別の観点・条件・ケースは `itc-<term>` に置き、本書には書かない。

適用対象は、[[specdojo:ifd-sample|インフラ構成図]] の店頭操作端末・販売・在庫・つけ記録サービス・業務記録 DB を結ぶ `PATH-01`〜`PATH-03` である（[[specdojo:tsp-index-sample|テスト戦略・方針]] の内部結合テストの範囲に合わせる）。保全の取得（`PATH-04`）と復元の回復（`PATH-07`）は外部結合テストの範囲とし、本書では扱わない。内部結合テストで防ぐ業務リスクは次の2つで、いずれも店主代表が記録を信用できなくなり、店主不在の店番を任せられなくなる。

- 会計確定の応答と DB の保存結果が食い違い、売上と在庫が二重に動く、または記録が欠ける。
- 在庫不足・入力不足の購入が DB 上で確定済みになり、在庫を誤って減らす。

| テストレベル   | 本システムでの責務                                                         | 内部結合テストとの分界                                           |
| -------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| UT（単体）     | 会計計算・在庫引当・つけ残高計算・入力検証のロジック                       | DB と記録サービスを Fake で置き換えた結果を、IT では実 DB で確認 |
| IT（内部結合） | 画面の要求・記録サービス・業務記録 DB の間の永続化とトランザクション境界   | 本書と `itc-<term>` の範囲                                       |
| ET（外部結合） | `receipt-print` コマンドと復元用保管サービス（`PATH-04`〜`PATH-07`）の契約 | IT では Stub で応答を制御し、実疎通しない                        |
| ST（総合）     | BAC-01〜BAC-03 の店頭業務シナリオ、障害・回復、性能                        | IT の合格を入口条件とする                                        |
| AT（受入）     | 店主代表・家族利用者代表による SC-01・AC-01〜AC-04 の確認                  | IT の結果を受入の判定に使わない                                  |
| 非機能テスト   | 放課後ピーク1時間60取引の応答時間                                          | IT では応答時間を合否にしない                                    |

| 関与者（Role）         | 本書を使う判断                                                      |
| ---------------------- | ------------------------------------------------------------------- |
| 開発担当（DEV）        | `itc-<term>` の作成・追加時に、括り方・依存の扱い・ケース表を決める |
| 同行レビュー担当（QE） | `itc-<term>` をレビューし、分配の重複と期待値の判定可能性を照合する |
| 技術メンター（ARC）    | 依存の扱いの例外と環境方針の変更を承認する                          |
| 店主代表（PO）         | 業務影響を根拠に採用した観点が、守る業務と一致しているかを確認する  |

## 2. テスト対象の括り方と分割基準

`<term>` は結合境界とデータ境界で切り、同じトランザクションで確定する記録を同じ単位に収める。初期リリースの括り方は次のとおりとする（各 `itc-<term>` は未同梱の架空成果物）。

| `itc-<term>`         | 結合のまとまり                                               | 経路                 | 括った理由                                                                       |
| -------------------- | ------------------------------------------------------------ | -------------------- | -------------------------------------------------------------------------------- |
| `itc-sales-checkout` | 会計確定の要求から販売記録の保存・在庫減算・未確定の保留まで | `PATH-02`・`PATH-03` | 販売記録と在庫減算は1トランザクションで確定し、BAC-01〜BAC-03 で同時に変更される |
| `itc-credit-balance` | つけの記録・入金と残高照会                                   | `PATH-02`・`PATH-03` | 顧客と残高の集約が販売と異なり、照会の一致を別に保証する                         |

- 在庫不足（BAC-02）と入力不足の保留（BAC-03）は会計確定と同じ在庫データを使うため、`itc-sales-checkout` に含め独立した term にしない。
- 保全の取得（`PATH-04`）と復元の回復（`PATH-07`）は tsp の定めで外部結合テストの範囲のため、term にしない。
- 画面資材の取得（`PATH-01`）は記録を持たないため term にせず、`itc-sales-checkout` の前提条件として扱う。
- 1 term の観点が 15 以上、ケース表が 50 行以上の場合は分割を検討し、分割は ARC が承認する。

## 3. 対象外・除外理由（共通）

| 対象外（やらないこと）                                   | 除外理由                                                                | 代替レベル/代替手段                                  | 例外（IT で扱う条件）                                   |
| -------------------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------- |
| `receipt-print` コマンドとの実疎通                       | 店舗プリンタの状態で結果が揺れる                                        | ET（`etc-receipt-print`）                            | なし。IT では Stub に置き換え、会計記録への影響だけ見る |
| 保全の取得、復元用保管サービスへの転送・読取、復元の回復 | 提供事業者の環境で結果が揺れ、本番コピーを壊しうる                      | ET（`etc-backup-storage`）、ST（復元の代表シナリオ） | なし。IT は `PATH-04`〜`PATH-07` を扱わない             |
| 店頭画面の表示・操作性                                   | 端末と利用者の理解に依存し、結合の合否にならない                        | ST、AT                                               | なし                                                    |
| 会計確定の応答時間と放課後ピークの処理量                 | 検証用 DB の性能は本番と異なる                                          | 非機能テスト（ST の性能測定）                        | なし                                                    |
| 通信不能時の販売継続                                     | 初期リリースで扱うか未決である。決定後に「メモ / 将来課題」で再判断する | ST                                                   | なし                                                    |

例外を適用する `itc-<term>` は、ケース表の `境界/依存` に適用した Stub と応答の種類を書く。

## 4. 観点の立て方（共通）

観点は「結合したときに何を保証するか」を名詞＋振る舞いで書き、`itc-<term>` の章立てに使う。次の型を上から検討し、該当しない型は `itc-<term>` に理由を1行で残す。

| 観点の型             | `itc-sales-checkout`              | `itc-credit-balance`       |
| -------------------- | --------------------------------- | -------------------------- |
| 結合 I/F の契約      | 確定結果とエラー種別の応答        | 残高照会の応答             |
| データ永続化の整合性 | 販売記録と在庫の一致              | つけ記録と残高の一致       |
| トランザクション境界 | 確定失敗時のロールバック          | 入金の二重計上防止         |
| 依存障害時の挙動     | DB 停止時に未保存を成功表示しない | DB 停止時の照会拒否        |
| 状態遷移の整合性     | 未確定から確定への遷移            | 該当なし（状態を持たない） |
| セキュリティ境界     | 該当なし（単一店舗・端末1台）     | 顧客ごとの残高の分離       |

`会計API`（何を保証するか不明）や `409応答`（条件の粒度）は観点名にしない。

## 5. 条件の立て方（共通）

基準データは [[specdojo:tsp-index-sample|テスト戦略・方針]] の `kinuya-test-data`（商品A: 単価30円・在庫5個）とし、条件は入力・状態・環境のどれか1つの差分で立てる。

| 区分 | 本システムでの条件の例                                                                        |
| ---- | --------------------------------------------------------------------------------------------- |
| 入力 | 代表: 商品A×2。境界: 在庫と同数の5・在庫超過の6・数量0。異常: 商品未特定、同じ取引番号の再送  |
| 状態 | 在庫5個・0個、つけ残高0円・残高あり、取引が未確定・確定済み、同じ在庫行を別取引がロック中     |
| 環境 | トランザクション分離レベル `READ COMMITTED`、固定クロック（月末23:59）、DB の更新拒否・接続断 |

条件は代表（BAC-01 の C-01: 在庫5→3）→ 境界（C-02: 在庫5→0、一意制約違反）→ 重大例外（二重計上・在庫の負値・記録の欠落）の順に追加する。数量と在庫の全組合せは作らない。

## 6. 観点/条件の採用基準と対象別への分配方針（共通）

採用は1観点=1合否命題、1条件=1差分とし、根拠は誤更新・欠損・二重計上につながる業務影響、または [[specdojo:bac-sample|現金販売の業務受入条件]] の明示要求に限る。分配は結合境界、データ境界、変更影響の順で決め、主担当を1つにする。

| 観点/条件                                        | 採用理由                                       | 主担当 `itc-<term>`  | 従担当（任意）       | 備考                                              |
| ------------------------------------------------ | ---------------------------------------------- | -------------------- | -------------------- | ------------------------------------------------- |
| 販売記録と在庫の一致／在庫と同数の購入           | BAC-01 の C-02。在庫の負値は欠品表示を誤らせる | `itc-sales-checkout` | なし                 | 販売記録1件・在庫0個を DB で観測する              |
| 同じ取引番号の再送で二重計上しない／一意制約違反 | 二重計上は売上と在庫を同時に狂わせる           | `itc-sales-checkout` | `itc-credit-balance` | つけ販売の再送は従担当で主担当の `case_id` を参照 |
| 確定失敗時のロールバック／DB の更新拒否          | 未保存を成功表示すると記録が欠ける             | `itc-sales-checkout` | なし                 | 応答と DB 差分の両方を観測する                    |

従担当の `itc-<term>` は、ケース表の `トレース` に主担当側の `case_id` を記して分配結果を追跡する。

## 7. 内部結合テスト共通の境界/依存の扱い

| 依存                       | 原則                                                                      | 例外と条件                                         |
| -------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------- |
| 業務記録 DB                | 本番と同じ製品・バージョンのコンテナ DB へ実接続する                      | なし                                               |
| マイグレーション・スキーマ | 全マイグレーションを適用してから実行し、NOT NULL・UNIQUE・FK を有効にする | なし                                               |
| `receipt-print` コマンド   | Stub で成功・終了コード異常・10秒無応答を返し分ける                       | 実疎通は ET で担保する                             |
| 時刻                       | 固定クロックを注入し、TZ は `Asia/Tokyo` に固定する                       | なし                                               |
| 取引番号の採番             | 実装の採番を使い、期待値には件数と差分だけを書く                          | 再送の条件に限り、テストから同じ取引番号を指定する |
| テストダブルの使い分け     | 応答固定で分岐を作るのは Stub、印刷要求の回数を検証するのは Mock          | 状態を持つ Fake は使わない（DB は実接続のため）    |

依存の扱いを変える `itc-<term>` は根拠を書き、ARC の承認を得てから本表を改訂する。合格基準は観測点を含む値で書く。例: 「DB が更新を拒否した場合、確定失敗を応答し、販売記録・在庫とも確定前と差分がない」。

## 8. テスト環境・データの共通方針

| 項目       | 方針                                                                                                                                                                                                                    |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 環境       | 開発環境の compose 定義（`kinuya-it-compose`、架空）で記録サービスとコンテナ DB を固定バージョンで起動する                                                                                                              |
| CI         | `kinuya-ci-sales-recovery`（架空）で実行し、記録サービス・スキーマ・印刷連携を変更した場合は merge 前に必須                                                                                                             |
| データ     | 各テストの開始時に `kinuya-test-data` を seed し、テストごとのトランザクションロールバックで独立させる。ロック競合・ロールバック検証など別接続やコミット済みデータが要る条件は、seed の再投入とスキーマ分離で独立させる |
| 並列実行   | CI のジョブごとに DB スキーマを `it_<CI run 番号>` で分け、相互干渉を避ける                                                                                                                                             |
| ログ・観測 | 失敗時に SQL・取引番号・リクエスト ID をテスト結果へ残す。つけの顧客名は架空でも出力せず顧客 ID で記録する                                                                                                              |

環境方針は全 `itc-<term>` で共通とし、対象ごとに DB 製品や分離レベルを変えない。変える必要が出た場合は ARC が本書を改訂してから `itc-<term>` へ反映する。

## 9. ケース表の共通カラム

`itc-<term>` のケース表は rulebook の定める10カラムを定められた順で置く。本システムでは次の値の決め方を共通にする。

- `case_id`: `it-<term>-<perspective_key>-<nnn>` とし、`nnn` は 010 から10刻みで振る。観点名を改めても変えず、廃止したケースは欠番にして再利用しない。テストコードは `case_id` をテスト名に含める。
- `優先度`: 二重計上・記録の欠落・在庫の誤更新につながるものを P0、つけ残高の照会を P1、通知内容を P2 とする。
- `自動化`: 内部結合テストはすべて `automated` とする。
- `証跡`: `kinuya-ci-sales-recovery` の CI run 番号とテストコードの位置を書く。

`itc-sales-checkout` の観点「販売記録と在庫の一致」（`perspective_key`: `persistence-integrity`）の1行の書き方は次のとおりとする。

| `case_id`                                     | 条件                                                        | 手順（最小）                     | 期待値                                                       | 観測点（アサーション）                 | 境界/依存                           | トレース      | 優先度 | 自動化    | 証跡                                      |
| --------------------------------------------- | ----------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------ | -------------------------------------- | ----------------------------------- | ------------- | ------ | --------- | ----------------------------------------- |
| `it-sales-checkout-persistence-integrity-020` | 入力: 確定済みと同じ取引番号で再送 状態: 在庫3個 環境: なし | 記録サービスへ会計確定を再送する | 重複エラーを応答し、販売記録は1件・在庫は3個のまま差分がない | 応答のエラー種別、販売記録件数、在庫数 | コンテナ DB 実接続、印刷は成功 Stub | BAC-01 / C-01 | P0     | automated | `kinuya-ci-sales-recovery` の CI run 番号 |

レビューでは、`case_id` の重複がないこと、必須4列が全行で埋まっていること、`ready` にする `itc-<term>` で推奨（運用必須）の6列が全行で埋まっていることを QE が確認し、1つでも満たさなければ不合格とする。

## 10. メモ / 将来課題

本書を `ready` にする前に、次の論点の当面の扱いを DEV と QE が確認し、PO が承認する。

| 論点                                                 | 内部結合テストへの影響                              | 当面の扱い                                                             | 担当・判断者                      | 報告先                  |
| ---------------------------------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------- | --------------------------------- | ----------------------- |
| _ASSUMPTION_: 分離レベル `READ COMMITTED` と同時確定 | 在庫行のロック競合の条件と期待値が変わる            | `kinuya-record-schema` の確定までは仮置きとし、確定後に条件を見直す    | ARC が確認、PO が承認             | PM へ決定事項として報告 |
| _UNDECIDED_: 通信不能時の販売継続                    | 未確定取引の照合の観点が増える                      | 対象外とし、`itc-sales-checkout` に保留後の再送の観点を追加しない      | BA が整理、PO が継続可否を判断    | PM へリスクとして報告   |
| `case_id` 重複と必須列の自動検査                     | レビューの確認漏れで不合格のまま `ready` になりうる | 検査ツールが整うまでは「ケース表の共通カラム」のレビュー確認で代替する | DEV が検査を整備、QE が結果を確認 | PM へ課題として報告     |
