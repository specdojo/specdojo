# 保管場所一覧（駄菓子屋きぬやの販売・在庫・記録管理）

## 1. 概要

店主代表と家族利用者代表（店番担当）が、店頭の現物商品・紙台帳・店舗タブレット内の電子ファイルの置き場所と処分基準を同じ根拠で判断できるよう、仕入・販売・在庫・締めに関わる保管場所一覧を定義する。検品前の入荷品と販売可能な商品の混在や、本部との照合に使う販売記録の控えと入力途中セッションファイルの誤削除を防ぐことを目的とする。

ロールの割り当ては [[specdojo:pm-members-sample|メンバー定義]] に従う。BA（開発担当）が日常の保管・清掃・処分の境界を整理し、店主代表が兼ねる OPS の専門支援（店頭運用・障害時の引き継ぎ）を取り込む。DEV（開発担当）が概念データストアおよび CLI の保存パスと整合させ、ARC（技術メンター）が構成に助言する。QE（同行レビュー担当）が検証手順と受入条件を確認し、PM（開発担当）が未決事項を管理台帳へつなぎ、店主代表が PO として保管方針と公開可否を最終判断する。店番の現場操作は店主代表と家族利用者代表（UX）が行う。

### 1.1. 対象範囲と隣接仕様との分担

対象範囲は [[specdojo:cdfd-overview-sample|概念データフロー図（全体概要）: 駄菓子屋きぬや販売管理]] の仕入・販売・在庫・締め領域で用いる物理保管場所および店舗タブレットのローカル保存領域とする。仕入記録は現行の仕入ノートを対象に含める。在庫記録は現行が店主の記憶で保管場所を持たないため一覧に載せず、システム化後の保管先を「確認事項と変更影響」で追跡する。

## 3. 削除・退避・復旧の判断基準

### 3.1. 削除・処分可否の3区分と運用判断

| 区分                                | 該当する保管場所                                                                                                                | 運用者（OPS・DEV）の判断基準と代替措置                                                                                                         |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `削除不可` / `処分不可`             | 売場棚、レジ釣銭準備箱・手提げ金庫、店頭台帳保管棚、母屋書庫、母屋金庫、外部退避媒体、`config/store-config.yaml`、`data/sales/` | 清掃や容量整理で消さない。商品は撤去品保留箱へ、旧年度の紙記録は母屋書庫へ、売上金は母屋金庫へ移す。電子記録の整理は保持期間の決定まで行わない |
| `条件付き削除可` / `条件付き処分可` | 検品場所、返品保管箱、撤去品保留箱、仮メモ挟み、`.session/current-tx.json`、`data/summary/`、`receipts/`                        | 一覧に書いた削除前条件（記録への反映・転記、PO の確定、CLI による終了、再生成手順の整備、月次締め確定）をすべて満たした場合だけ処分・削除する  |
| `削除可`                            | `tmp/`                                                                                                                          | 保守作業の終了後に削除してよい                                                                                                                 |

### 3.2. 場面別の対処と復旧手順

| 場面                                                       | 確認と対処手順                                                                                                                                                                                                                                                                                                                                                                                                                  | 担当・エスカレーション先                                               |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 会計要求前に再起動し、取引が残っている                     | `sales total` で残った明細を確認し、同じ取引を続けるか `sales cancel` で取り消す。`.session/current-tx.json` を手で削除しない                                                                                                                                                                                                                                                                                                   | 店番担当。解消しなければ DEV                                           |
| 会計要求後に再起動・応答欠落し、本部の受付結果が分からない | 取消、ファイル削除、新規取引での再登録をしない。PO が本部受付と `data/sales/` の記録を照合し、受付済みなら同じ取引を回復、未受付と確認できた場合だけ送信を再開する。照合・回復手順は未整備のため、確認できない取引は保留する                                                                                                                                                                                                    | OPS が会計を止めて PO・DEV へ連絡。PO が保留・回復を判断               |
| `data/summary/` を誤って削除した                           | 再生成手順の整備後は、対象日・基準時点を指定して集計元から `data/summary/` へ出力し直す。整備前は、受付済みの `data/sales/` の現金販売（結果不明は除く）と販売ノートの販売明細欄のつけ販売を合わせて手動集計し、日次締め記録の参照値と照合する。照合者・照合日・一致結果は日次締め記録の確認結果欄へ書き、本部の受付結果とは別の証跡として残す                                                                                  | OPS（店主代表）が再集計、QE が一致を確認。不一致なら PO が締めを再判断 |
| `config/store-config.yaml` が消失・破損した                | 会計を止める。DEV が外部退避媒体の最新世代を復元し、PO が店舗・税計算・本部接続の条件を確認する。CLI が「店舗設定不正」なしで起動し、表示条件が PO の確認値と一致すれば再開する。退避がない場合、DEV は設定の構造の正本 `kinuya-store-config-schema`（CLIS の未同梱の架空参照名）が提供されているときに限りそれに従い再作成する。提供されていなければ再作成せず会計を止めたまま PO へ報告する。どちらも PO の確認まで再開しない | OPS → DEV（復元）・PO（条件確認）                                      |
| `data/sales/` が消失・破損した                             | 新規会計を止める。DEV が外部退避媒体の最新世代を復元し、退避後の取引を PO が販売ノート・レシート控え・本部受付と照合して欠落を特定する。QE が取引番号の連続と日次締め記録の件数を照合する。退避がなければ推測で再作成せず、照合できない日は締めを保留する                                                                                                                                                                       | OPS → DEV（復元）・PO（照合と締め判断）・QE（一致確認）                |
| 売場で期限切れ・破損品を見つけた                           | 売場で捨てず撤去品保留箱へ移す。日次締めで店主代表が廃棄を確定し、廃棄数を在庫差異欄へ記入してから廃棄する                                                                                                                                                                                                                                                                                                                      | 店番担当（発見・移動）→ PO（廃棄確定）                                 |
| タブレットの空き容量が不足した                             | `tmp/` と条件を満たした `receipts/` だけを削除する。`data/sales/` と `data/summary/` は削除しない                                                                                                                                                                                                                                                                                                                               | OPS（削除）、DEV・PO（保持期間決定までの容量確保）                     |

### 4.2. 検証手順と受入条件

| 検証観点（ロール）                      | 確認内容・手順                                                                                                                                                                                                | 合格条件                                                                                                                       |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `[ARC・DEV]` 実装配置・CLI 仕様との一致 | タブレット内の各パスと役割を [[specdojo:clis-sample\|駄菓子屋きぬや 販売管理 CLI 仕様]] と照合する                                                                                                            | CLIS にないパスに `_ASSUMPTION_` が付き、進行中セッションと販売記録の控えが別ファイルであること                                |

| `[DEV・QE]` 受付結果不明の取引          | 本部の応答を欠落させて `sales complete` を実行し、続けて `sales cancel` を試す                                                                                                                                | `.session/current-tx.json` と `data/sales/` に結果不明として残り、取消は終了コード `2` で拒否される                            |
| `[OPS・QE]` 日次集計の再集計            | CDSD の照合例のうち現金販売108円を受付済みの `data/sales/` に、つけ販売216円を販売ノートの販売明細欄に用意し、結果不明の現金取引1件を加える。`data/summary/` を消して「場面別の対処と復旧手順」に従い作り直す | 販売2件・請求合計324円で元の売上IDの集合と一致し、結果不明の取引を含まない。照合の証跡が本部の受付結果と別に日次締め記録へ残る |
| `[BA]` 業務要求・データストアの網羅     | CDSD の5管理単位、全体概要の仕入記録・在庫記録、STSD の全状態と本書の一覧を照合する                                                                                                                           | 保管場所のない記録・状態が「確認事項と変更影響」で追跡されていること                                                           |
| `[OPS]` 削除可否・復旧判断の実効性      | 「保管場所一覧」と「削除・退避・復旧の判断基準」を用い、清掃・障害復旧・容量整理・返品の判断を模擬する                                                                                                        | 店主代表と店番担当が、消してよい場所、削除前条件、消失時の復旧経路と連絡先を迷わず判断できること                               |
| `[QE]` 文書品質・整合性検証             | 標準6列・必須章、章見出しの末尾ピリオド、wikilink の解決を確認し、整形・lint を実行する                                                                                                                       | `npx prettier --write`、`npm run lint:md`、`npm run lint:fm` がエラー0件で通過すること                                         |

PM は各行を区分どおりの管理台帳の種別で登録し、担当と判断時期を Schedule へ接続する。

公開および `status: ready` への昇格前に、BA・ARC・DEV・OPS・QE が受入条件を確認し、人間の PO（店主代表）が顧客情報の施錠保管と上表の未決事項の扱いを承認する。照合・回復契約と日次集計の再生成手順が整備されるまで、受付結果不明の取引の回復と日次集計の自動再生成は保留中の手順として扱い、それらに依存する運用開始を承認しない。agent は `status: draft` を維持する。
