# 保管場所一覧（駄菓子屋きぬやの販売・在庫・記録管理）

## 1. 概要

店主代表と家族利用者代表（店番担当）が、店頭の現物商品・紙台帳・店舗タブレット内の電子ファイルの置き場所と処分基準を同じ根拠で判断できるよう、販売・在庫・締めに関わる保管場所一覧を定義する。検品前の入荷品と販売可能在庫の混在や、タブレット内の確定売上記録と入力途中セッションファイルの誤削除を防ぐことを目的とする。

BA（同行レビュー担当）と OPS（家族利用者代表・店舗運営アドバイザー）が日常の保管・清掃・処分の境界を整理し、ARC（技術メンター）・DEV（開発担当）が概念データストアおよび CLI の保存パスと整合させる。QE（同行レビュー担当）が検証手順と受入条件を確認し、店主代表が PO として保管方針と公開可否を最終判断する。

### 1.1. 対象範囲と隣接仕様との分担

対象範囲は [[specdojo:cdfd-overview-sample|概念データフロー図（全体概要）]] の販売・仕入・在庫・締め領域で用いる物理保管場所および店舗タブレットのローカル保存領域とする。概念上の管理単位と更新責務は [[specdojo:cdsd-sample|概念データストア定義（駄菓子屋きぬやの販売と締め）]]、データ項目は [[specdojo:bdd-sample|業務データ辞書（駄菓子屋の販売管理）]]、商品の在庫状態遷移は [[specdojo:stsd-sample|状態遷移定義（駄菓子屋きぬやの商品在庫ライフサイクル）]]、CLI 操作とファイルパスは [[specdojo:clis-sample|CLI 仕様（駄菓子屋の販売管理 CLI）]] を正本として参照する。

## 2. 保管場所一覧

### 2.1. 店舗内の物理保管場所

| 保管場所                           | 置くもの                                                                     | 関連プロセス・操作                   | 共有の有無                                       | 寿命・管理頻度                                            | 削除・処分の可否と条件                                                                                                 |
| ---------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------ | ------------------------------------------------ | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 検品場所（店舗奥の荷受台）         | 納品直後の段ボール箱、検品前の入荷商品、納品伝票                             | 入荷荷受、入荷検品                   | 店舗内共有（荷受担当と店番担当が確認）           | 入荷当日の検品完了まで（原則当日中）                      | `条件付き処分可`。商品の破棄は不可。検品完了後、外箱は解体処分可、納品伝票は店頭台帳保管棚へ移動する                   |
| バックヤード（予備棚）             | 検品済みの予備在庫商品（外箱または小分け袋）                                 | 入荷検品、売場補充、月末棚卸         | 店舗内共有（店主代表・家族利用者代表が共有）     | 売場棚へ補充するまで（週次の補充確認・月末棚卸）          | `処分不可`。販売可能在庫のため勝手に廃棄しない。賞味期限切れ・破損発見時は返品保管箱へ移し、在庫記録を減算する         |
| 売場棚（店頭陳列棚・平台）         | 来店客が手に取る販売中商品、棚札                                             | 売場補充、店頭販売、日次賞味期限確認 | 店舗内公開（来店客・店番担当が常時参照）         | 販売成立または賞味期限前日まで（毎朝の開店前点検）        | `処分不可`。汚損・期限切れ商品は売場から撤去して返品保管箱へ移動する。棚札は取扱終了時に店主代表の確認後のみ撤去可     |
| 返品保管箱（バックヤード下段）     | 検品不合格品、売場から撤去した破損品・期限切れ商品                           | 入荷検品、期限切れ撤去、返品・廃棄   | 店舗内共有（売場と明確に分離した赤ラベル箱）     | 問屋への返品回収日または週次の廃棄確定日まで              | `条件付き処分可`。店主代表が返品または廃棄を確定し、仕入・在庫記録への反映を確認した後にのみ問屋返却または廃棄処分する |
| レジ釣銭準備箱・手提げ金庫         | 釣銭準備金、当日の現金売上、仮領収メモ                                       | 開店準備、店頭販売、日次締め         | 店舗内共有（営業中は店番担当、閉店後は施錠保管） | 営業開始から日次締め確定まで（毎日閉店時に精算）          | `処分不可`。日次締めで現金実査と販売集計の一致を店主代表が確認した後、売上金を母屋金庫へ移し、不要な仮メモのみ破棄する |
| 店頭台帳保管棚（施錠キャビネット） | 紙の商品台帳、顧客・つけ台帳、納品伝票綴り、日次締め記録・月次報告バインダー | つけ販売、日次締め、月次見直し       | 店舗内共有（店主代表・家族利用者代表のみ閲覧可） | 当年度＋過去3年間保管（年度末に旧年度分を母屋書庫へ退避） | `処分不可`。取引・未収金・税務の正本記録のため破棄しない。顧客情報を含むため来店客から見えない施錠棚に保管する         |

### 2.2. 店舗タブレット内の論理保管場所

| 保管場所                                                         | 置くもの                                                                             | 関連プロセス・操作                             | 共有の有無                                                 | 寿命・管理頻度                                            | 削除・処分の可否と条件                                                                                                        |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------- | ---------------------------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 店舗設定ファイル領域（`config/store-config.yaml`）               | 店舗コード、消費税率端数処理設定、データ保存先パス設定                               | CLI 初期設定、全コマンド実行時の設定読込       | 共有なし（店舗タブレット固有・設定バックアップ対象）       | 店舗運用期間中（恒久保持・設定変更時のみ更新）            | `削除不可`。削除すると全 CLI コマンドが起動不能になる。変更時は旧ファイルを退避したうえで開発担当または店主代表が更新する     |
| 取引セッション領域（`.session/current-tx.json`）                 | 入力途中の会計セッション状態（未確定の明細一覧・開始時刻）                           | `kinuya sale start`、`add`、`commit`、`cancel` | 共有なし（店舗タブレット固有の実行中状態ファイル）         | 1会計の開始から確定（`commit`）または取消（`cancel`）まで | `条件付き削除可`。会計確定・取消時に自動削除される。端末異常終了で残存した場合は、進行中の会計がないことを確認して削除可      |
| ローカル販売記録・日次集計領域（`data/sales/`・`data/summary/`） | 確定済みの売上記録・売上明細データ（`data/sales/`）、日次販売集計（`data/summary/`） | `kinuya sale commit`、`kinuya summary daily`   | 共有なし（店舗タブレット内正本・日次で外部メディアへ退避） | 売上記録は恒久保持（3年間）、日次集計は随時再生成可能     | `data/sales/` は `削除不可`（確定取引の正本）。`data/summary/` は `条件付き削除可`（削除しても `data/sales/` から再生成可能） |
| レシート出力・一時作業領域（`receipts/`・`tmp/`）                | 印字・画面提示用のレシート控えテキスト（`receipts/`）、一時作業ファイル（`tmp/`）    | `kinuya sale commit`、日次締め確認、保守作業   | 共有なし（端末ローカルの一時・控え領域）                   | `tmp/` はコマンド終了まで、`receipts/` は月次締め完了まで | `削除可`。`tmp/` は作業終了後に即時削除可。`receipts/` は月次締め完了後に削除可（必要時は確定した販売記録から再出力可能）     |

## 3. 削除・退避・復旧の判断基準

### 3.1. 削除・処分可否の3区分と運用判断

| 区分                                | 該当する保管場所                                                                          | 運用者（OPS・DEV）の判断基準と代替措置                                                                                             |
| ----------------------------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `削除不可` / `処分不可`             | バックヤード、売場棚、レジ金庫、店頭台帳保管棚、`config/store-config.yaml`、`data/sales/` | 日常清掃や容量整理で消してはならない。商品の撤去は返品保管箱への移動、旧台帳や過去年度売上の整理は母屋書庫・外部退避メディアへ移す |
| `条件付き削除可` / `条件付き処分可` | 検品場所（外箱・伝票）、返品保管箱、`.session/current-tx.json`、`data/summary/`           | 削除前条件（検品完了、店主代表の廃棄・返品承認、進行中会計なし、元売上記録の存在）を満たす場合のみ処分・削除する                   |
| `削除可`                            | `tmp/`、`receipts/`（月次締め確認後）                                                     | 作業完了または月次締め確定後に削除してよい。削除後に控えが必要な場合は `data/sales/` の確定売上から再出力する                      |

### 3.2. 場面別の対処と復旧手順

| 場面                                                 | 確認と対処手順                                                                                                                 | 担当・エスカレーション先                                      |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| 会計途中でタブレットが再起動し新規会計を始められない | 来店客との会計が継続中か確認する。やり直す場合は `kinuya sale cancel` を実行するか `.session/current-tx.json` を削除する       | OPS（家族利用者代表）。解消しない場合は DEV（開発担当）へ連絡 |
| 日次販売集計（`data/summary/`）を誤って削除した      | `data/sales/` の売上記録が残っていることを確認し、対象日を指定して日次集計コマンドを再実行して復元する                         | OPS（家族利用者代表）、QE（同行レビュー担当）が一致を確認     |
| 売場で賞味期限切れ・破損商品を発見した               | その場で捨てず売場棚から撤去して返品保管箱へ移す。日次締めで店主代表が確認し、在庫記録を更新したうえで廃棄または問屋へ返品する | OPS（発見・移動）→ PO（店主代表が処分確定）                   |
| タブレットの空き容量が不足した                       | `tmp/` と月次締め済みの `receipts/` を削除する。`data/sales/` は絶対に削除せず、年度末退避手順について DEV へ相談する          | OPS（一時領域削除）、DEV・PO（過去データの退避判断）          |

## 4. 関連仕様・実装配置との対応と検証

### 4.1. 概念データストア・関連仕様との対応

| 保管場所                                               | 対応する概念データストア・関連仕様                                                                                                                 | 整合確認のポイント                                                                               |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 検品場所、バックヤード、売場棚、返品保管箱             | [[specdojo:stsd-sample\|状態遷移定義（商品在庫ライフサイクル）]] の入荷検品待ち・保管中・販売中・返品待ち                                          | 状態ごとの物理配置が分離され、販売不可品（検品待ち・返品待ち）が売場棚に混在しないこと           |
| 店頭台帳保管棚                                         | [[specdojo:cdsd-sample\|概念データストア定義（販売と締め）]] の商品台帳・日次締め記録・月次報告、隣接領域の顧客・つけ台帳                          | 紙正本として保持する台帳と個人情報（顧客・つけ台帳）が施錠棚で保護されていること                 |
| `config/store-config.yaml`、`.session/current-tx.json` | [[specdojo:clis-sample\|CLI 仕様（販売管理 CLI）]] の設定ファイルおよび進行中セッション管理                                                        | 確定前の `.session/current-tx.json` が確定売上記録（`data/sales/`）と分離されていること          |
| `data/sales/`、`data/summary/`                         | [[specdojo:cdsd-sample\|概念データストア定義（販売と締め）]] の販売記録（正本）・日次販売集計（派生情報）、[[specdojo:bdd-sample\|業務データ辞書]] | 正本（`data/sales/`）が削除不可、派生集計（`data/summary/`）が再生成可能として区別されていること |

### 4.2. 検証手順と受入条件

1. **BA・OPS（業務網羅と運用判断）**: [[specdojo:cdsd-sample|概念データストア定義]] の5管理単位および [[specdojo:stsd-sample|状態遷移定義]] の在庫状態に対応する保管場所が漏れなく定義され、家族利用者代表が「消してよいもの／残すもの」を迷わず判別できること。
2. **ARC・DEV（CLI 仕様との配置一致）**: タブレット内の4領域のパスと役割が [[specdojo:clis-sample|CLI 仕様]] の入出力ファイル・終了時挙動と矛盾しないこと。
3. **QE（文書検査と照合）**: 標準6列・必須章の欠落がないこと、および `npx prettier --write`・`npm run lint:md`・`npm run lint:fm` がエラー 0 件で通過すること。

## 5. 確認事項と変更影響

| 論点・区分                                                        | 現在の判断・影響                                                                                             | 担当・判断時期・次の行動                                                                                                     | 追跡先候補                     |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| タブレット内 `data/sales/` の外部バックアップ媒体と世代数（未決） | `_UNDECIDED_`: 日次締め後に SD カードまたは USB メモリへ退避する方針だが、媒体の保管場所と保持世代数が未確定 | OPS・DEV が媒体候補とコピー手順を整理し、運用開始前に PO（店主代表）が保管場所（手提げ金庫または母屋金庫）と世代数を決定する | `specdojo:pjr-sales-storage`   |
| 紙の商品台帳・締め記録をタブレットへ完全移行する場合（変更影響）  | 店頭台帳保管棚の正本区分と `data/` 配下のファイル構成・バックアップ対象が変更になる                          | BA が [[specdojo:cdsd-sample\|概念データストア定義]] の正本区分を更新し、ARC・DEV が保存パス、OPS が退避手順を改訂する       | `specdojo:pjr-paper-to-tablet` |

公開および `status: ready` への昇格前に、BA・ARC・DEV・OPS・QE が上記の受入条件を確認し、人間の PO（店主代表）が顧客情報の施錠保管と未決バックアップ方式の扱いを承認する。agent は `status: draft` を維持する。
