# 駄菓子屋きぬや 販売管理システム 信頼性要件

## 1. 概要（対象・目的）

店頭での販売・つけの記録が失敗したり、同じ取引が二重に残ったりしないよう、記録処理の失敗と誤動作の許容度を定める。対象業務は店頭タブレット 1 台での販売記録（会計）、つけの記録と残高確認、在庫数の更新とする。

記録処理が失敗すると、次の業務影響が出る。基準値の厳しさは、この影響と、記録を営業日の 90% 以上で続けるというプロジェクトの初期目標（[[specdojo:prj-overview-sample|プロジェクト概要]]）から決める。

- 会計の記録が失敗すると客を待たせ、店番担当が紙に書き直す手間と転記漏れが生じる。
- つけの記録が二重に残る、または欠けると、残高の説明を誤り常連客の信頼を損なう。
- 販売記録の失敗が在庫数に反映されず、人気商品の欠品に気付けない。

停止をどこまで許すか、いつまでに復旧するかは [[specdojo:nfr-availability-sample|可用性要件]] で定め、本書では扱わない。本書は、システムが動いている間に記録処理が失敗しない・誤らない・一時的な不調から自動で回復することを対象とする。

## 2. 適用範囲・前提条件

要件の対象と除外を、次の表で定める。

| 区分             | 条件                                                                           | 障害率・成功率の集計での扱い                         |
| ---------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------- |
| 対象処理         | 会計（販売記録の登録）、つけの記録、在庫数の更新                               | 分母に含める                                         |
| 対象外の処理     | 日次締め、売上の集計表示、マスタ（商品・顧客）の登録                           | 含めない。失敗しても当日の取引の記録は失われないため |
| 対象時間帯       | _ASSUMPTION_: 営業日の 10:00〜18:00（可用性要件の対象時間帯と同じ）            | 含める                                               |
| 計画停止中       | 閉店後のアプリ更新・点検の時間                                                 | 含めない                                             |
| システム停止中   | 可用性要件で停止と数える時間（端末故障、ホスティング環境の停止など）           | 含めない。可用性要件の稼働率で扱う                   |
| 店頭の通信瞬断   | _ASSUMPTION_: 1 分未満で回線が戻る瞬断。頻度と影響は未確認（前提条件 ACD-A02） | 含める。自動回復の対象とする                         |
| 店番の操作取消し | 店番担当が会計の確定前に取り消した操作                                         | 含めない。失敗ではないため                           |

技術前提は次のとおりとする。外部依存の実績が分かるまで、基準値が実現できるかは判断できない。

- 店頭端末はタブレット 1 台、記録はホスティング環境のデータベースに置く単一構成とし、冗長化しない（_ASSUMPTION_）。
- 通信断が 1 分以上続く場合の店頭での記録方法は未決である（前提条件 ACD-D03）。決まるまでは可用性要件の停止として扱い、紙の販売控えで販売を続ける。
- ホスティング環境とデータベースの障害率は事業者の公表値がなく、_UNDECIDED_: 試用期間の実績から判断する。

## 3. 信頼性要件一覧

次の表は、要件ごとの指標と基準を示す。基準が未確定の要件は `_UNDECIDED_` とし、決まるまでの暫定の判定を備考に書く。

| id            | 内容                                                         | 指標                                                                                                                 | 基準                     | 備考                                                                                    |
| ------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- | ------------------------ | --------------------------------------------------------------------------------------- |
| `nfr-rel-001` | 会計の記録処理が失敗しない                                   | 障害率 = 失敗した会計処理件数 ÷ 全会計処理件数（暦月）。失敗は、確定操作の後に記録が残らなかった処理とする           | _UNDECIDED_: ○○% 以下    | 決まるまでは件数を記録するだけとし、達成・未達を判定しない                              |
| `nfr-rel-002` | 同じ取引が二重に記録されない                                 | 重複記録件数 = 同じ確定操作から 2 件以上作られた販売・つけの記録の件数（暦月）                                       | _ASSUMPTION_: 0 件       | 確定ボタンの連打、通信瞬断の後の再送でも 1 件だけ残ることを含む                         |
| `nfr-rel-003` | 通信の瞬断から自動で回復し、店番担当が操作をやり直さずに済む | 処理成功率 = 再試行を含めて記録できた会計・つけの処理件数 ÷ 瞬断中に確定した会計・つけの処理件数（試験・暦月）       | _ASSUMPTION_: 100%       | 1 分未満の瞬断に限る。再試行の回数・間隔は設計で決め、本書の基準にしない                |
| `nfr-rel-004` | アプリが営業中に異常終了しない                               | MTBF = 対象時間の合計 ÷ アプリの異常終了の回数（暦月）。異常終了は、操作中にアプリが閉じる、または応答しなくなる事象 | _UNDECIDED_: ○○ 時間以上 | 決まるまでは回数を記録するだけとする。異常終了の後の記録の再開は可用性要件の RTO で扱う |
| `nfr-rel-005` | 不正な入力値で記録を誤らない                                 | 不正値の受け付け件数 = 数量 0 以下・つけ残高を超える返済額など、検証規則に反する値で作られた記録の件数（試験）       | 0 件                     | 検証規則の一覧は詳細設計に置く。値の正しさの継続的な保証は完全性要件で扱う              |

## 4. 測定・検証方法

要件ごとに、どの方法で、いつ、どの Role code が判定するかを次の表で定める。

| id            | 方法             | 測定のしかた                                                                                                                           | 判定時期                             | 判定する Role code | 検証先                               |
| ------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ | ------------------ | ------------------------------------ |
| `nfr-rel-001` | 監視             | アプリが記録する会計処理のエラー件数と全件数を月次で集計する。店番担当が障害記録に残した「確定したのに残らなかった」件数を分子に加える | 月次の運用レビュー                   | `OPS`              | `sac-reliability`                    |
| `nfr-rel-002` | テスト・監視     | 受入前は確定ボタンの連打と確定直後の通信断を試験する。運用後は同じ時刻・金額・商品の記録を月次で抽出し、紙の控えと照合して重複を数える | 受入前の総合テスト、運用後は月次点検 | `QE`、`OPS`        | `stc-reliability`、`sac-reliability` |
| `nfr-rel-003` | テスト           | 検証用の環境で通信を 10 秒・30 秒・59 秒切り、その間に会計とつけを各 10 件確定して、回線が戻った後の記録件数を数える                   | 受入前の総合テスト                   | `QE`               | `stc-reliability`                    |
| `nfr-rel-004` | 監視             | アプリの異常終了の記録と、店番担当が障害記録に残した「アプリが閉じた」件数を合わせ、重なりは 1 回と数える                              | 月次の運用レビュー                   | `OPS`              | `sac-reliability`                    |
| `nfr-rel-005` | テスト・レビュー | 検証規則の一覧の各規則について、境界値と不正値を入力する試験を行う。規則の一覧と画面の入力項目の対応は設計レビューで確かめる           | 設計レビュー時、受入前の総合テスト   | `QE`               | `stc-reliability`                    |

測定結果は、指標が基準を満たせば pass、満たさなければ fail とする。基準が `_UNDECIDED_` の間の扱いは備考に従い、確定後は確定値で判定し直す。

基準未達・重大障害の扱いと、要件を見直す契機は次のとおりとする。

- fail となった要件は、要件 ID・測定期間・件数を課題として記録し、原因と対策を障害対応の運用手順に従って追う。
- `nfr-rel-002`・`nfr-rel-005` で 1 件でも誤った記録が見つかった場合は重大障害とし、該当取引を紙の控えで照合して直す。
- 次のいずれかが起きたときに、基準値と対象処理を見直す。2 か月続けて fail となったとき、通信断の頻度が分かったとき（前提条件 ACD-A02）、オフライン時の記録方法が決まったとき（前提条件 ACD-D03）、可用性要件の RTO・RPO を変えたとき。
