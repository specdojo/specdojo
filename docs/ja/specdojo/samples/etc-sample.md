# 外部結合テストカタログ: レシート印刷連携

## 1. 概要（`receipt-print`）

販売管理 CLI の会計確定（`sales complete`）が、店舗端末の外部コマンド `receipt-print` を起動して保存済みレシートを店舗プリンタで印刷し、その結果を判別する連携を対象とする。印刷が失敗・無応答でも会計を取り消さず、二重印刷を起こさずに店番へ次の手を示せることを、店舗プリンタの検証機とスタブで確かめる。

- 関連I/F: `receipt-print` の起動（入力 `receipts/receipt-YYYYMMDD-NNNN.txt`、stdout の結果 JSON、終了コード `0`・`1`・`2`・`5`）。

## 2. 責務

- 終了コードと結果 JSON を照合し、印字完了・送信前失敗・結果不明を区別して販売記録へ残す。
- 印刷が失敗・無応答・応答不正でも、確定済みの販売記録を1件のまま維持する。
- 応答待ち10秒で打ち切り、子プロセスを終了させ、不完全な stdout を結果に採用しない。
- 印刷要求を自動で再送せず、店番の再印刷は保存済みレシートだけで1回ずつ行う。
- 印刷失敗・結果不明を店番に警告し、取引番号と控えの場所を表示する。
- 印刷要求ごとに取引番号を相関 ID としてログへ出し、レシート本文は出さない。

## 3. 対象外

- 対象外: レシート本文の品名・税額・釣銭の正しさ（理由: 販売 CLI 内で生成し外部境界を跨がない、代替: IT の会計結合ケース）。
- 対象外: 復元用保管サービスへの転送の成否と通知内容（理由: 主担当は `etc-backup-storage`、代替: 同カタログの観点「保管失敗の店主代表への通知」）。本書は従担当として、通知表示中も印刷が動くことだけを確認する。
- 対象外: OS のデバイス権限の付与手順（理由: 端末の構築作業でありテストの合否に含めない、代替: 端末の構築手順書の確認）。権限がないときの判別（終了コード `5`）は本書で扱う。
- ET で扱う例外: 用紙切れは、検証機の用紙を抜いた状態で実機を使って再現する。用紙を戻せば元に戻り、費用は用紙1枚未満のため安全で、無応答のようにスタブへ寄せる必要がない。

## 4. 境界/依存/環境

| 項目         | 内容                                                                                                                                          |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 境界（入口） | `sales complete` が会計確定の後に `receipt-print` を子プロセスとして起動する（`shell: false`、stdin なし）                                    |
| 境界（出口） | `receipt-print` の終了コード、stdout の結果 JSON 1件、stderr の診断。プリンタへの印字データ送信                                               |
| 依存の扱い   | 正常・用紙切れ・権限不足・入力不正は検証機へ実接続する。無応答・応答 JSON の欠落・送信前ビジーは `receipt-print` スタブで再現する             |
| 観測点       | 販売記録 `data/sales/TX-YYYYMMDD-NNNN.json` の件数と印字状態、スタブ・検証機の印刷要求回数、店番への警告表示、ログの相関 ID                   |
| 認証         | 不要（USB 直結）。認可は OS のデバイス権限で、検証では権限を外したテスト用ユーザーで終了コード `5` を起こす                                   |
| タイムアウト | 応答待ち10秒、自動再送なし（`etc-index` の共通値）                                                                                            |
| テストデータ | 取引番号は `TX-<CI run 番号>-NNNN` とし、各テストの終了時に自分の番号の販売記録とレシートファイルだけを削除する。検証機の紙は印刷後に破棄する |
| 時刻依存     | 会計確定日をテスト用の固定日 `20261101` にし、レシートのファイル名を決定的にする                                                              |
| 秘密情報     | 秘密値はない。レシート本文はログとテスト結果に出さず、stderr の診断は保存前にパスの利用者名をマスクする                                       |

_UNDECIDED_: [[specdojo:ifx-cmd-sample|レシート印刷コマンド連携仕様]] は上限30秒・送信前ビジー時の自動再試行（最大3回）を定めており、`etc-index` の応答待ち10秒・自動再送なしと食い違う。本書は `etc-index` に従い、送信前ビジーも自動再送しない期待値にしている。両者の値が揃った時点で、ケース `et-receipt-print-failure-handling-020` の期待値を更新する。

## 7. 実行運用メモ

- 実行の場: `automated` のケースは `kinuya-ci-sales-recovery` で、印刷連携か販売 CLI の会計処理を変えた変更の merge 前に実行する。`manual` のケースは検証機の前で QE が実施し、紙面の写真を検証記録に残す。
- 実行制約: 検証機は1台のため印刷のケースは並列にしない。営業中の店舗プリンタは使わない。
- 後始末: 「境界/依存/環境」のテストデータの削除は、失敗したテストでも省かない。用紙切れのケースの後は用紙を戻し、テスト印刷を1回して検証機を元に戻す。
- 失敗時の再実行: 検証機の失敗は、プリンタの電源と USB 接続を確かめてから1回だけ再実行する。再実行でも失敗したら QE が不具合として起票し、同じ日に2回以上は繰り返さない。
- 変更時の見直し: `receipt-print` のメジャー版の更新（`>=2.0.0`）や終了コードの追加があれば、トレース表と「印刷結果の判別」のケースを更新する。
