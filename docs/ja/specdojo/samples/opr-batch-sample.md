# 駄菓子屋きぬや 販売管理システム 運用手順（バッチ再実行）

## 1. 概要

`opr-index` の差分・具体化として、定期のバッチである夜間バックアップが失敗したときの検知・再実行・上限到達時の扱いを定める。失敗を開店前の点検で見つけて当日のうちに取り直し、P1 で復元が要るときに前日の閉店時点へ戻せる状態を保つことが目的である。日次締めは店番担当の操作でありバッチではないため、本書では扱わない。証跡・優先度・承認の共通規約は [[specdojo:opr-sample|運用手順]]、判断基準は [[specdojo:opd-index-sample|運用方針・設計（全体構成）]] に従う。

次の表は、未決の値が本書のどの手順に影響し、決まるまでどう扱うかを示す。値が決まった時点で該当する章の完了条件を差し替える。

| 未決事項                                          | 決まるまでの手順上の扱い                                             | 影響する章                             |
| ------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------- |
| _UNDECIDED_: RTO/RPO とバックアップの保管期間     | 前日の閉店時点の世代が当日の閉店までに成功していれば合格とする       | バッチ再実行・失敗時対応、証跡         |
| _UNDECIDED_: 夜間バックアップの開始時刻と所要時間 | 開店前の点検で成功記録がなければ、実行中であっても失敗として扱う     | 障害対応手順、バッチ再実行・失敗時対応 |
| _UNDECIDED_: 営業時間外の緊急連絡手段             | 夜間の失敗通知は翌朝の開店前の点検で扱い、営業時間外には再実行しない | 手順適用範囲・前提                     |

## 2. 手順適用範囲・前提

次の表は、本書の手順が対象とする範囲と、再実行を行う前提を示す。

| 項目     | 内容                                                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 対象     | 記録の正本であるデータベースの夜間バックアップ（閉店後の日次締めの後に自動で 1 日 1 回）と、その手動の再実行                       |
| 対象外   | 日次締めのやり直し（`opr-index` の日次点検）、バックアップからの復元（`opr-index` のバックアップ確認・リストア手順）、仕入れの発注 |
| 時間帯   | 手動の再実行は、開店前の点検で失敗が分かってから当日の閉店まで。営業時間外には行わない                                             |
| 必要権限 | 再実行は `DEV` の管理者権限で行う。店番担当は成功表示の閲覧、`OPS` は実行ログの閲覧だけを使う                                      |
| 使用手段 | ホスティング環境のバックアップの記録と実行ログ、バックアップ取得のコマンド、プロジェクトの課題管理の障害記録、店内の点検ノート     |
| 連絡経路 | 店番担当が `OPS` へ、`OPS` が `DEV` へ再実行を依頼する。上限に達した場合は `OPS` が `PO` へ報告する                                |

_ASSUMPTION_: バックアップの取得はデータベースを読み取るだけで、取得中も店頭の販売・在庫・つけの記録を続けられる。これは「証跡」章の模擬で確かめ、記録が止まる場合は再実行の時間帯を閉店後に限る。

## 3. 日次・週次・月次点検手順

開店前の成功表示の確認と週次を置かない扱いは `opr-index` 参照。次の表は、本書が追加する月次の点検と、点検を終えたと判定する条件を示す。

| 頻度 | 手順                                                                     | 実施者 | 完了条件                                                                          | 証跡           |
| ---- | ------------------------------------------------------------------------ | ------ | --------------------------------------------------------------------------------- | -------------- |
| 月次 | 障害記録から当月の夜間バックアップの失敗・再実行・上限到達の回数を数える | `OPS`  | 失敗した日のすべてに `run_id` と再実行の結果がある                                | 月次点検の記録 |
| 月次 | 同じ原因の失敗が月 2 回以上あるかを確かめる                              | `OPS`  | 該当があれば恒久対応の課題を登録し、`PO` へ報告した。該当がなければその旨を書いた | 月次点検の記録 |

## 4. 障害対応手順

次の表は、夜間バックアップの失敗をどの優先度で扱い、どこまでを本書の手順で終えるかを示す。優先度の条件と初動目標は `opr-index` に従う。

| 優先度 | 本書で該当する条件                                                       | 対応                                                                  | 判断者 |
| ------ | ------------------------------------------------------------------------ | --------------------------------------------------------------------- | ------ |
| P1     | 上限に達した翌朝も成功記録がない、またはデータ不整合の可能性がある       | `opr-incident` へ切り替え、店番担当は紙の販売控えへの切替の判断を待つ | `PO`   |
| P2     | 開店前の点検で当日分の成功記録がない、または実行ログが失敗で終わっている | 店頭の記録を続け、「バッチ再実行・失敗時対応」の手順で取り直す        | `OPS`  |
| P3     | 本書の範囲外（バックアップの失敗は記録の復元に直結するため P3 にしない） | なし                                                                  | -      |

データ不整合の可能性とは、前日の日次締め記録で販売記録と現金の合計に説明できない差がある場合、または実行ログに取得中のデータベースのエラーが出ている場合を指す。

## 5. アラート対応手順

通知は「開店時に当日分の成功記録なし」の 1 つで、通知先は `OPS` とする。確認から恒久対応までの流れは `opr-index` に従い、本書の差分は次のとおりとする。

- 確認: `OPS` が実行ログで同じ取得日の `run_id` の結果を見る。成功で終わっていれば表示の遅れとして誤検知に進む。
- 暫定対応: 失敗であれば P2 として「バッチ再実行・失敗時対応」へ進む。
- 恒久対応: 再実行で直らない原因は、`DEV` が「運用変更作業」の手順で直す。
- 誤検知: 成功記録が表示され、世代の取得日が前日の `closing_date` と一致すれば、「誤検知」と原因を障害記録に書いて終える。

## 6. バックアップ確認・リストア手順

`opr-index` 参照。再実行で取り直した世代も通常の世代と同じく月次の復元演習の対象とし、本書では手順を追加しない。

## 7. バッチ再実行・失敗時対応

### 7.1. 失敗検知

- 店番担当が開店前の点検で、前日の閉店後の日時の成功表示がないことに気付き、日次点検の記録に書いて `OPS` へ連絡する。
- `OPS` がアラートの通知を受け、「アラート対応手順」の確認を行う。

どちらの経路でも、`OPS` は障害記録を P2 で起こし、`ticket_id` を `DEV` へ渡して再実行を依頼する。

### 7.2. 再実行の前提の確認

`DEV` は再実行の前に次の表をすべて確かめ、合格したら再実行の操作へ進む。

| 確かめること                       | 合格の条件                                                 | 合格しないとき                                         |
| ---------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------ |
| 同じ取得日の実行が終わっている     | 実行ログの最新の `run_id` が「失敗」で終わり、実行中がない | 実行中なら終わるまで待ち、成功すれば誤検知として終える |
| 当日の実行回数が上限に達していない | 自動の取得を含めて当日の実行が 1 回だけである              | 「再実行上限と上限到達時」へ進む                       |
| 失敗の原因が再実行で直る種類である | 実行ログのエラーが通信の切断や一時的な応答なしである       | 容量不足・認証の期限切れなどは「運用変更作業」で直す   |
| データ不整合の可能性がない         | 前日の日次締め記録の差が 0 円か、差の原因が書かれている    | P1 として `opr-incident` へ切り替える                  |

### 7.3. 再実行の操作

1. 入力を決める。取得日は前日の日次締めの `closing_date`、対象は販売管理のデータベースとする。
2. 取得のコマンドを 1 回実行する（例: `backup run --target sales-db --date <closing_date>`）。_ASSUMPTION_: ホスティング環境がこの形式の手動取得のコマンドを持つ。実際の引数は環境の手順書を正とし、本書には貼り付けない。
3. 出力された `run_id` と開始・終了時刻を障害記録に書く。
4. 店番担当に、取得の終了後に販売を 1 件記録できることを確かめてもらう。

### 7.4. 完了の条件

次の条件をすべて満たしたら、`OPS` が障害記録を完了にする。

- 実行ログで、再実行の `run_id` の結果が成功である。
- バックアップの記録に、取得日が前日の `closing_date` の世代が 1 つだけある。
- 世代に含まれる前日の販売件数が、前日の日次締め記録の販売件数と一致する。
- 再実行の後に、店番担当が販売を 1 件記録できた。

### 7.5. 再実行上限と上限到達時

上限は自動の取得を含めて 1 日 2 回とし、手動の再実行は 1 回までとする。上限を超える手動の取得は例外なく行わない。

- 上限到達時: P2 のまま店頭の記録を続け、当日の閉店後の自動の取得を待つ。`OPS` は上限到達を `PO` へ報告する。
- 翌朝も失敗: P1 として `PO` へ上げ、`opr-incident` に切り替える。
- 影響: 成功するまでの間に復元が必要になると、最新の成功した世代まで戻るため、それ以降の営業日の記録を日次締め記録と紙の販売控えから転記する必要がある。この間は月次の復元演習の対象世代も古くなる。

### 7.6. 重複の防止

同じ取得日の取得は同じ世代を上書きするため、再実行しても世代は増えない。取得はデータベースを読み取るだけで販売・在庫・つけの記録を書き換えないため、再実行による記録の重複は起きない。実行ごとに `run_id` が振られ、どの実行が成功した世代を作ったかを実行ログで追える。

## 8. 運用変更作業

`opr-index` 参照。再実行で直らない原因（容量不足、認証の期限切れ、取得の設定の誤り）の修正は、承認者・実施条件・ロールバック条件を含めて `opr-index` の運用変更作業に従う。修正後の確認は、翌朝の開店前の点検で成功表示があることとする。

## 9. アカウント付与・剥奪手順

`opr-index` 参照。再実行には `DEV` の管理者のアカウントを使い、バッチ専用のアカウントは置かない。

## 10. 問い合わせ一次対応手順

`opr-index` 参照。店番担当から「成功表示が出ていない」という問い合わせを受けた場合は、問い合わせではなく「失敗検知」として扱う。

## 11. 証跡

次の表は、本書の手順の証跡をどこに残し、どの識別子で照合するかを示す。保存先と参照権限は `opr-index` の証跡に合わせる。

| 証跡種別       | 保存先                               | 保管期間                                  | 参照権限           | 最低限残す識別子                                 |
| -------------- | ------------------------------------ | ----------------------------------------- | ------------------ | ------------------------------------------------ |
| 実行ログ       | ホスティング環境のバックアップの記録 | _UNDECIDED_: バックアップの保管期間と同じ | `OPS`、`DEV`       | `run_id`、取得日（`closing_date`）、結果         |
| 障害記録       | プロジェクトの課題管理               | _UNDECIDED_                               | `OPS`、`DEV`、`PO` | `ticket_id`、優先度、再実行の `run_id`、実行回数 |
| 日次点検の記録 | 店内の点検ノート（紙）               | _UNDECIDED_                               | 店番担当、`OPS`    | 点検日、成功表示の有無                           |
| 月次点検の記録 | プロジェクトの課題管理               | _UNDECIDED_                               | `OPS`、`PO`        | `ticket_id`、対象月、失敗と再実行の回数          |

本書を新しく書いたときや改訂したときは、検証用の環境で失敗した取得の再実行と上限到達までを模擬し、確認日・確認環境・模擬の `run_id`・合否を月次点検の記録に残す。模擬では、取得中に販売を 1 件記録できるかも確かめる。
