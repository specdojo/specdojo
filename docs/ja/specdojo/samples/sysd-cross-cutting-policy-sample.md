# 駄菓子屋きぬや 販売処理の横断ルール

## 1. 概要（適用範囲・優先順位）

店主代表と家族利用者代表が、通信や印字の失敗後も会計の確定状態を取り違えず店番を引き継げるよう、販売処理に共通する制約を定める。販売の記録継続と属人化の低減が目的であり、欠品削減や仕入れ判断の規則は本書では定めない。

対象は単一店舗・現金販売の CLI、ローカル取引保存、本部の商品照会・売上登録、外部レシート印刷コマンドとする。販売の操作・表示は [[specdojo:clis-sample|販売管理 CLI 仕様]] を参照する。つけ管理、キャッシュレス決済、複数店舗、無人会計、オフライン同期は対象外である。RDBMS のトランザクションは非該当だが、ファイルと本部受付の不整合は対象に含む。

_ASSUMPTION_: タブレット1台で店番担当が操作する学習用 CLI の設計例である。`kinuya-*` の契約・設定参照名は未同梱の架空正本とし、実運用の承認や実装済みを示さない。値・構文・構造はそれらの正本へ委ね、ここでは停止・保持・照合の判断を定める。

競合時は個人情報の保護、会計・受付状態の保存、回復可能性、処理速度の順で判断する。印字成功は会計確定の前提にしない。結果不明を成功や未受付へ読み替えない。

### 1.1. 利用・確認・承認責務

| Role・担当                | 合意・確認対象                                         |
| ------------------------- | ------------------------------------------------------ |
| ARC・技術メンター         | 外部連携と保存の境界、横断制約、例外の影響を確認       |
| DEV・開発担当             | 実装・設定・記録契約の整合と途中状態の照合を担当       |
| QE・同行レビュー担当      | 同じ取引の二重受付、時間切れ、保存失敗の期待結果を確認 |
| OPS・店舗運営アドバイザー | 店番交代時の照合・障害連絡・保存記録の扱いを確認       |
| PM                        | 未整備契約・受入作業の担当、依存、期限を追跡           |
| PO・店主代表（人間）      | 会計の保留・確定の業務判断と運用開始可否を最終承認     |

## 3. 各ルール詳細（ID単位）

### 3.1. scp-ERR-001: 失敗分類と利用者の次の手

- **Rule（MUST）**: 会計要求前の失敗は未実施、要求後の応答欠落は結果不明、確定後の印字失敗は警告として分ける。対象取引・保持記録・次の確認先を表示する。
- **Rationale（意図）**: 店番担当が同じ売上を登録し直したり、印字失敗を理由に会計を取り消したりしないため。
- **Scope（適用範囲）**: 明細追加、会計要求、ローカル保存、印字。
- **Enforcement（検証）**: K2 で送信前失敗は明細保持、送信後の無応答は照合待ち、印字失敗は会計維持を確認する。終了コードは CLI リファレンスを照合する。
- **Exception（例外）**: なし。原因を分類できなければ保留して店主代表へ渡す。
- **References（参照）**: [[specdojo:clis-sample|販売管理 CLI 仕様]] の「代表的な表示と利用者の次の手」、架空正本 `kinuya-cli-reference`。

### 3.2. scp-IDM-001: 受付照合と保存境界

- **Rule（MUST）**: 売上登録の再送前に、元の取引番号で本部受付とローカル記録を照合する。受付済みは記録を回復し、未受付を確認できた場合だけ同じ取引で再開する。照合不能なら保留する。
- **Rationale（意図）**: 通信切断後の二重会計と、受付済み売上の取消を防ぐ。
- **Scope（適用範囲）**: 本部売上登録、応答欠落、保存失敗後の回復。
- **Enforcement（検証）**: K2 で「本部受付済み・応答欠落」「未受付」「照合不能」を入力し、それぞれ記録回復・同一取引での再開・保留になることを確認する。新しい取引を作らない。
- **Exception（例外）**: 契約で重複排除が保証されても、本書の受入前に自動再送を追加しない。変更は店主代表の decision を必要とする。
- **References（参照）**: 架空正本 `ifx-api-kinuya-sales.yaml`、`kinuya-sales-record-schema`、`kinuya-recovery-procedure`。

### 3.3. scp-TIM-001: 連携の時間切れ

- **Rule（MUST）**: 商品照会・売上登録・印字に設定正本の時間上限を適用し、時間切れでは待機を打ち切る。印刷プロセスの終了を確認できない間は再起動しない。売上登録の時間切れを未受付と断定しない。
- **Rationale（意図）**: 操作を無期限に占有せず、遅れて完了する外部処理を重ねないため。
- **Scope（適用範囲）**: 本部 HTTP 連携と `receipt-print`。
- **Enforcement（検証）**: K2 で上限直前・到達時を注入する。照会は明細未追加、会計は照合待ち、印字は会計維持・印字状態不明となることを確認する。
- **Exception（例外）**: 上限値と停止方式の照合待ちは受入保留とする（Q-K1）。
- **References（参照）**: 架空正本 `kinuya-execution-policy` の `products.timeout_ms`、`sales.timeout_ms`、`print.timeout_ms`・`print.terminate_grace_ms`。印刷境界は [[specdojo:ifx-cmd-sample|印刷コマンド連携仕様]]。

### 3.4. scp-RET-001: 再試行の許可範囲

- **Rule（MUST）**: 商品照会の一時的な接続失敗・時間切れだけを、設定正本の回数・待機上限内で自動 retry する。認証拒否・入力不正・会計登録・印字には自動 retry を適用しない。別店舗や別の登録先への fallback は行わない。
- **Rationale（意図）**: 読取処理の回復と副作用の重複防止を両立させるため。
- **Scope（適用範囲）**: 商品照会、本部売上登録、印字。
- **Enforcement（検証）**: K2 で一時失敗は同じ照会を再試行、上限到達時は明細未追加で停止、認証拒否は再試行なし、売上登録・印字は手動照合へ進むことを確認する。
- **Exception（例外）**: 未登録商品は接続障害に分類しない。店番担当がコードを訂正する。
- **References（参照）**: 架空正本 `kinuya-execution-policy` の `products.retry.max_attempts`（初回を含む）・`products.retry.max_backoff_ms`。値の確定は Q-K1。

### 3.5. scp-LOG-001: 診断と監査

- **Rule（MUST）**: 接続・プロセス失敗の診断と、取引の開始・受付・保存・回復判断の監査を区別する。認証値・顧客氏名・生の通信本文を診断ログへ保存しない。
- **Rationale（意図）**: 店番交代時の照合を助け、個人情報を障害調査経由で拡散させないため。
- **Scope（適用範囲）**: CLI ログ、販売実績、照合記録。将来のつけ台帳は含めない。
- **Enforcement（検証）**: K3 で認証値を模した値の非記録、実行主体・時刻・取引・処理結果の追跡、保存不能時の警告を確認する。保持期間と閲覧範囲の受入は Q-K2 で行う。
- **Exception（例外）**: 調査目的でも無加工の秘密情報を保存しない。
- **References（参照）**: 架空正本 `kinuya-audit-record-schema`、`kinuya-log-policy`。

### 3.6. scp-TRC-001: 取引と外部処理の相関

- **Rule（MUST）**: 同じ取引番号から本部受付、ローカル控え、印字の要求と結果を追跡する。印字の試行は元の売上と区別し、外部側に共通 trace がなくても親の起動・終了を関連付ける。
- **Rationale（意図）**: 保留会計と未印字の控えを次の店番が取り違えないため。
- **Scope（適用範囲）**: 会計・保存・印字・再印刷の照合記録。
- **Enforcement（検証）**: K3 で異なる二取引と同一取引の印字再試行を追い、売上受付を再実行せず対象の控えだけへ到達できることを確認する。
- **Exception（例外）**: 印刷側の実紙面は記録だけで断定せず、店番担当が確認する。
- **References（参照）**: 架空正本 `kinuya-audit-record-schema`、[[specdojo:clis-sample|販売管理 CLI 仕様]] の引継ぎ操作。

### 3.7. scp-SEC-001: 認証情報の秘匿

- **Rule（MUST NOT）**: `KINUYA_API_KEY` の値を起動引数・画面・ログ・販売控えへ出さない。店舗設定ファイルへ保存しない。
- **Rationale（意図）**: 控えの共有やエラー報告から本部認証が漏れることを防ぐ。
- **Scope（適用範囲）**: 本部連携の起動、失敗表示、保存記録。
- **Enforcement（検証）**: K1 で未設定時は認証設定不足として停止し、設定済み時も表示・ログに値が現れないことを確認する。
- **Exception（例外）**: なし。認証設定の管理者は開発担当、実運用の権限承認者は店主代表とする。
- **References（参照）**: 架空正本 `kinuya-cli-reference` の認証設定、`kinuya-access-policy`。

### 3.8. scp-CFG-001: 設定の解決と反映

- **Rule（MUST）**: 店舗条件は起動時に `config/store-config.yaml` と schema の既定値から解決する。ファイル欠落時は既定値、不正内容なら停止する。認証は環境からだけ受け、CLI 指定や店舗設定で上書きしない。実行途中の設定変更は次の操作から反映する。
- **Rationale（意図）**: 隠れた設定上書きによる価格・接続先の混乱を防ぐ。
- **Scope（適用範囲）**: 店舗条件、本部接続、認証の初期解決。
- **Enforcement（検証）**: K1 でファイルなし・正当な設定・破損・認証欠落を与え、既定値採用・指定値採用・停止・停止をそれぞれ確認する。
- **Exception（例外）**: 不正設定を削除して既定値で回避する運用は採用しない。
- **References（参照）**: 架空正本 `kinuya-store-config-schema`、`kinuya-cli-reference`。具体値は転載しない。

### 3.9. scp-MOD-001: 会計と印字の境界

- **Rule（MUST）**: CLI は操作と表示、販売処理は受付と保存、印刷 adapter は保存済み控えの印字を担当する。印刷 adapter から売上登録を呼び出さず、印刷の失敗で確定済み会計を巻き戻さない。
- **Rationale（意図）**: 印字の復旧を会計の再実行から分離するため。
- **Scope（適用範囲）**: CLI・販売処理・保存・印刷 adapter 間の呼出し。
- **Enforcement（検証）**: K1 で境界の呼出し検査、K2 で印刷失敗を注入し、会計維持と控え保持、売上送信なしを確認する。
- **Exception（例外）**: 境界変更は技術メンターが影響を整理し、店主代表へ判断を依頼する。
- **References（参照）**: 架空正本 `kinuya-module-map`、[[specdojo:ifx-cmd-sample|印刷コマンド連携仕様]]。

## 4. 例外（DECリンク）

### 4.1. 例外の入口

承認済み例外はない。例外追加時は対象 Rule ID、理由・影響、期限、店主代表の判断、復帰条件を架空の決定簿 `kinuya-decision-log` で管理し、本書から接続する。通信不調や用紙切れだけで自動再送を許可しない。

### 4.2. 報告と追跡

| 事象                             | 記録先・種別                  | 報告・追跡責務                                              |
| -------------------------------- | ----------------------------- | ----------------------------------------------------------- |
| 二重受付・保存失敗等の実発生     | `kinuya-register` の issue    | 店番担当が対象取引を報告、開発担当が調査、PM が解消まで追跡 |
| 未確定契約による受入遅延の可能性 | 同登録簿の risk               | 技術メンターが影響提示、PM が依存・期限を追跡               |
| 自動再送等の方式変更             | 同登録簿の change と decision | 開発担当が案、同行レビュー担当が検証、店主代表が採否判断    |

## 6. 未決事項と公開前確認

### 6.1. 判断待ちと後続への影響

_UNDECIDED_: 契約と運用の受入は未了である。Q-K ID は論点 ID であり、発行済みチケットではない。PM が受入計画へ接続する。

| ID・作成対象                     | 判断者・担当                               | 判断期限         | 影響・当面の扱い                                               | 次アクションと解消条件                                                                                        |
| -------------------------------- | ------------------------------------------ | ---------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Q-K1: 本部受付契約・実行制約     | 技術メンター・開発担当が案、店主代表が判断 | K2 着手前        | 受付照合・時間上限・retry 値が未確認。通信失敗経路の受入を保留 | PM が issue と作業を起票。設定キー・値・単位と回復契約を整え、同行レビュー担当が境界・重複防止を確認          |
| Q-K2: 監視・保持・回復手順       | OPS が案、店主代表が判断                   | 店番交代の受入前 | 記録の確認間隔、保存期間、閲覧権限、連絡先が未確定             | PM が依存 risk を登録し、OPS が保留会計・未印字の検知と照合を実演、店主代表が運用負荷と留保範囲を判断         |
| Q-K3: 正本・検証 script と互換性 | 開発担当が整備、同行レビュー担当が確認     | 運用開始判断前   | 架空参照は未同梱。実装適合や検査成功を保証しない               | 正本と実行コマンドを実在する参照へ接続し、旧控え読込・実紙面・停止後の回復を検証。PM が実 ID と完了証跡を接続 |

### 6.2. 公開・昇格の判断条件

- 技術メンターと開発担当が全規則を実装・契約へ照合し、未確認を解消または対象外の理由付きで明示する。
- 同行レビュー担当と OPS が K1〜K3 の結果、失敗時の保持、秘密非記録、取引・印字の照合と次の店番への引継ぎを確認する。
- PM が判断待ちの担当・期限・作業依存・実 ID を接続し、人間の店主代表が運用開始可否を最終判断する。留保には範囲・期限・再確認責任を決定簿へ記録する。agent は `ready` に変更しない。
