# RACI: 駄菓子屋きぬや 販売管理システム

## 1. 適用方針

単一店舗・タブレット1台の販売・在庫・つけ記録の初期リリースと店頭試用の責任境界を示す。EC、複数店舗、本格会計、仕入れ先連携は初期スコープ外とし、定型作業や生成ビューは行にしない。

列は [[specdojo:pm-organization-sample|組織定義]] の主導ロールとする。専門支援の `ARC`、`UX`、`OPS` は列を省き、助言はそれぞれ `DEV`、`BA`、`PM` が取り込む。専門支援を独立タスク化するなら、先に組織定義を見直す。

記号は [[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] に従う。1 つの Role が `A` と `R` を兼ねる場合も、作業結果と判断の証跡を分けて残す。AI Agent は `R`・`C` の作業を支援できるが、`A` の判断は人間が行う。

## 2. 成果物別 RACI

成果物ごとに、対象 ID と各 Role の責任を示す。対象 ID は成果物カタログの ID（同じ種類が複数あるものは接頭辞）か、未同梱の架空のアプリ・記録の名前で書く。

| 成果物                                 | 対象 ID                                                                      | PO  | PM  | BA  | DEV | QE  |
| -------------------------------------- | ---------------------------------------------------------------------------- | --- | --- | --- | --- | --- |
| プロジェクト概要・スコープ・成功基準   | `prj-overview`・`prj-scope`・`prj-success-criteria-and-acceptance-criteria`  | A   | C   | R   | C   | C   |
| 組織定義・ロール定義・メンバー定義     | `pm-organization`・`pm-roles`・`pm-members`                                  | A   | R   | C   | I   | C   |
| 管理計画・コミュニケーション計画・RACI | `pm-plan`・`pm-communication-plan`・`pm-raci`                                | C   | A/R | C   | I   | C   |
| 利用者要求・操作設計                   | `bps-*`・`uis-*`                                                             | A   | C   | R   | C   | C   |
| 実装・データ設計                       | `sysd-index`・`bdd-*`・`kinuya-app` のコード                                 | C   | I   | C   | A/R | C   |
| 品質計画・試験結果                     | `pm-quality-management-plan`・`kinuya-st-report`・`kinuya-acceptance-record` | A   | C   | C   | C   | R   |
| リリース候補                           | `kinuya-app` の対象版タグ                                                    | A   | R   | C   | R   | C   |

## 3. 判断・プロセス別 RACI

判断・プロセスごとに、最終判断者と作業・相談の担当を示す。成果物行と重なる判断の範囲は表の後に書く。

| 判断・プロセス                 | PO  | PM  | BA  | DEV | QE  |
| ------------------------------ | --- | --- | --- | --- | --- |
| 価値、範囲、優先順位の判断     | A   | R   | C   | C   | C   |
| 費用・参加時間上限の判断       | A   | R   | C   | C   | C   |
| 作業順序、課題・リスク管理     | C   | A/R | C   | C   | C   |
| 利用者確認                     | A   | C   | R   | C   | C   |
| 受入・品質ゲート判定           | A   | C   | C   | C   | R   |
| 品質未達・例外要求への対応判断 | A   | C   | C   | C   | R   |
| 変更要求の採否                 | A   | R   | C   | C   | C   |
| リリース・試用後の継続判断     | A   | R   | C   | C   | C   |

- 作業順序、課題・リスク管理の `A` は進捗と調整を判断し、成果物の内容承認は各成果物行の `A` に残す。
- 品質計画・試験結果の行の `A` は確認範囲と結果を確かめ、リリース候補の行の `A` は準備完了を確かめる。利用開始の可否は本表の判断行で決める。
- 利用者確認では `BA` が店主・家族利用者の操作結果と意見を集め、内部 Role だけで代替しない。
- 品質未達では `QE` が不足する証跡と是正案を整理し、`PO` が保留と再判定を判断する。`PO` は [[specdojo:pm-plan-sample|管理計画]] の判断ゲートに従い、必須条件を免除しない。範囲・基準を変える場合は、先に変更要求を通す。

## 4. Schedule・実行主体との対応

### 4.1. 主担当と照合先

個別タスクの正本は、管理計画が示す `kinuya-schedule`（未同梱の架空記録）とする。担当の照合は人と組織の定義標準の「Schedule への担当展開」に従う。割り当て先の正本は、人間が [[specdojo:pm-members-sample|メンバー定義]]、agent が `.specdojo/agent-members.yaml` であり、本書へ複製しない。

対象作業ごとに、主担当と照合する RACI の行を示す。

| 対象作業                               | 主担当・`owner` | 対応する行と照合内容                       |
| -------------------------------------- | --------------- | ------------------------------------------ |
| 利用者要求・操作設計を作成する         | `BA`            | 成果物行の `R`。`UX` の助言を取り込む      |
| 実装・データ設計を承認する             | `DEV`           | 成果物行の `A/R`。作業結果と承認を別記録   |
| リリース候補の導入・引き継ぎを準備する | `PM`            | 複数 `R` のうち導入・復旧・引き継ぎの準備  |
| リリース候補の対象版を組み立てる       | `DEV`           | 複数 `R` のうち組み立てと技術的な是正      |
| リリース可否を承認する                 | `PO`            | 判断行の `A`。準備作業とは別の承認タスク   |
| 利用者要求・操作設計を技術レビューする | `DEV`           | 成果物行の `C`。作成とは別のレビュータスク |

### 4.2. 不一致時の更新先

不一致の原因ごとに、`PM` が更新する正本と確認を示す。`PM` はタスクの action と WBS の明示 `owner` を確かめ、作成か承認・レビューかを区別して修正先を決める。Schedule に入っている現在の担当を理由に主担当を選び直さない。

| 不一致の原因・具体例                                   | 更新する正本と確認                                                        |
| ------------------------------------------------------ | ------------------------------------------------------------------------- |
| 操作設計の作成タスクが `DEV`                           | タスク定義の正本（WBS の明示 `owner` か `kinuya-schedule`）を `BA` に直す |
| WBS の明示 `owner` は `BA`、展開結果が `DEV`           | 生成元・展開処理を直して再生成する。生成ビューは直接編集しない            |
| 合意した責任変更（専門支援の独立タスク化など）が未反映 | 組織定義を確かめ、本書を直してから WBS・Schedule へ反映する               |

原因や責任が未決の間は、担当変更を前提とする作業を保留する。

## 5. 見直し条件

次の変化が起きたら、対応する確認事項を確かめて本書を見直す。

| トリガー                                  | 確認すること                                                                 |
| ----------------------------------------- | ---------------------------------------------------------------------------- |
| 初期スコープ、成果物の統合・分割・廃止    | 各成果物から一つの行と `A`・主担当へ辿れるか、旧参照と後続タスクの付け替え先 |
| 採用 Role、専門支援の独立タスク化         | 組織定義と列・相談先の整合、WBS・Schedule の追従箇所                         |
| Schedule の担当変更・WBS 導入・タスク分割 | action と主担当の一致。直し方は「不一致時の更新先」に従う                    |
| 判断ゲートの変更、品質判定の滞留          | 判断行の `A` と材料を準備する `R`、相談先、判断期限への影響                  |
| 参加・離脱・兼務負荷・AI Agent 支援の変化 | 未完了タスクを引き受けられるか、人間の判断と作業の記録を分けられるか         |

次をすべて満たしたら見直しを終える。経緯や状態は本表へ蓄積しない。

- 各行の `A` と主担当が明確である。
- 組織・ロール・メンバー定義、WBS・Schedule、[[specdojo:pm-communication-plan-sample|コミュニケーション計画]] と整合している。
- 引き継ぎ漏れがない。
