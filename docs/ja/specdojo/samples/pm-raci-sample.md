# RACI: 駄菓子屋きぬや 販売管理システム

## 1. 適用方針

単一店舗・タブレット1台で販売、在庫、つけを記録する初期リリースと店頭試用を対象とする。業務・利用者確認、実装・データ設計、品質・受入、導入・継続の責任境界を示す。EC、複数店舗、本格会計、仕入れ先連携は初期スコープ外のため扱わず、日々の定型作業や生成ビューは独立した行にしない。

採用 Role と列の選択は [[specdojo:pm-organization-sample|組織定義]]、責務は [[specdojo:pm-roles-sample|ロール定義]] に従う。初期の主導ロールである `PO`、`PM`、`BA`、`DEV`、`QE` を列にする。専門支援の `ARC`、`UX`、`OPS` は独立列を省き、助言はそれぞれ `DEV`、`BA`、`PM` が取り込む。独立タスク化する場合は組織定義の見直しを先行させる。

記号の意味は [[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] に従い、各行の `A` は一つ、`R` は一つ以上とする。同じ人間が `A` と `R` を兼ねても、作業結果と判断の証跡を分ける。AI Agent は `R` または `C` の作業を支援できるが、各 `A` の最終判断は対応する Role の人間が行う。

## 2. 成果物別 RACI

| 成果物                                 | PO  | PM  | BA  | DEV | QE  |
| -------------------------------------- | --- | --- | --- | --- | --- |
| プロジェクト概要・スコープ・成功基準   | A   | C   | R   | C   | C   |
| 組織定義・ロール定義・メンバー定義     | A   | R   | C   | I   | C   |
| 管理計画・コミュニケーション計画・RACI | C   | A/R | C   | I   | C   |
| 利用者要求・操作設計                   | A   | C   | R   | C   | C   |
| 実装・データ設計                       | C   | I   | C   | A/R | C   |
| 品質計画・試験結果                     | A   | C   | C   | C   | R   |
| リリース候補                           | A   | R   | C   | R   | C   |

リリース候補の `R` は、導入・復旧・引き継ぎの準備を `PM`、対象版の組み立てと技術的な是正を `DEV` が主導する。品質計画・試験結果の `A` は確認範囲と結果を承認し、リリース候補の `A` は準備の完了を確認する。利用開始の可否は次表のリリース判断で決める。

## 3. 判断・プロセス別 RACI

| 判断・プロセス                 | PO  | PM  | BA  | DEV | QE  |
| ------------------------------ | --- | --- | --- | --- | --- |
| 価値、範囲、優先順位の判断     | A   | R   | C   | C   | C   |
| 費用・参加時間上限の判断       | A   | R   | C   | C   | C   |
| 作業順序、課題・リスク管理     | C   | A/R | C   | C   | C   |
| 利用者確認                     | A   | C   | R   | C   | C   |
| 受入・品質ゲート判定           | A   | C   | C   | C   | R   |
| 品質未達・例外要求への対応判断 | A   | C   | C   | C   | R   |
| 変更要求の採否                 | A   | R   | C   | C   | C   |
| リリース・試用後の継続判断     | A   | R   | C   | C   | C   |

作業順序、課題・リスク管理の `A` は進捗と調整を判断し、成果物の内容承認は各成果物行の `A` に残す。利用者確認では `BA` が店主・家族利用者の操作結果と意見を集め、内部 Role だけで利用者の確認を代替しない。

品質未達では `QE` が不足する証跡と是正・再確認案を整理する。[[specdojo:pm-plan-sample|管理計画]] の判断ゲートに従い、必須条件の免除は設けず、`PO` が保留と再判定を判断する。範囲・基準の変更が必要なら、変更要求として先に承認を得る。

## 4. Schedule・実行主体との対応

### 4.1. 主担当と照合先

作業順序・個別タスクの正本は、管理計画で整備先を示す `kinuya-schedule` とする。本例に未同梱の架空記録であり、`PM` が準備着手前に整備する。WBS を導入する場合は、WBS の明示 `owner` を先に確認する。未指定の作成作業は本表の主担当 `R` から展開する。`R` が一つならその Role、複数なら行の注記で示した担当範囲から決め、一意に決まらなければタスクを分割する。

| 対象作業                               | 主担当・`owner` | 対応する行と照合内容                           |
| -------------------------------------- | --------------- | ---------------------------------------------- |
| 利用者要求・操作設計を作成する         | `BA`            | 成果物行の `R`。`UX` の助言を取り込む          |
| 実装・データ設計を承認する             | `DEV`           | 成果物行の `A/R`。作業結果と承認を別記録にする |
| リリース候補の導入・引き継ぎを準備する | `PM`            | 複数 `R` のうち導入準備の主担当                |
| リリース候補の対象版を組み立てる       | `DEV`           | 複数 `R` のうち技術作業の主担当                |
| リリース可否を承認する                 | `PO`            | 判断行の `A`。準備作業とは別の承認タスク       |
| 利用者要求・操作設計を技術レビューする | `DEV`           | 成果物行の `C`。作成とは別のレビュータスク     |

承認・レビュー・外部待ちを別 Task / Milestone にする場合は、[[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] の「Schedule への担当展開」に従い、対象の `A` / `C` と照合する。通知だけの `I` を `owner` にしない。

人間の実行主体と兼務は [[specdojo:pm-members-sample|メンバー定義]]、agent は利用先の `.specdojo/agent-members.yaml` を正本とする。本書へ個人名・agent 名・割り当て一覧を複製しない。

### 4.2. 不一致時の更新先

`PM` は、対象タスクの action、WBS の明示 `owner` の有無、作成と承認・レビューの区別を確認してから、次表により修正先を決める。現在の Schedule の値だけを理由に主担当を選び直さない。

| 不一致の原因・具体例                                                        | 更新する正本と確認                                                                                                             |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 責任配置は有効だが、操作設計の作成タスクが `DEV` になっている               | タスク定義の正本を `BA` に修正する。WBS があればその明示 `owner`、Schedule を直接管理する本例では `kinuya-schedule` を更新する |
| WBS の明示 `owner` が `BA` だが、Schedule への展開結果が `DEV` になっている | WBS を保持し、Schedule の生成元・展開処理を修正して再生成する。生成ビューは直接編集しない                                      |
| 専門支援の独立タスク化など、合意した責任変更を本表が反映していない          | 組織定義の採用・使用可否を確認し、RACI の行・主担当を更新してから WBS・Schedule のタスク定義へ反映する                         |

原因や新しい責任が未決なら、`PM` が課題として担当 Role・判断期限・影響タスクを記録し、解決前は担当変更を前提とする作業を保留する。

## 5. 見直し条件

`PM` は週次の進捗確認と変更要求の受付時に、次表のトリガーと影響する行を確認する。

| トリガー                                         | 確認すること                                                                                                               |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 初期スコープまたは成果物の統合・分割・廃止       | 業務・技術・品質の確認範囲が欠けず、各成果物から一つの行と `A`・主担当へ辿れるか。旧参照と後続タスクの付け替え先も確認する |
| 採用 Role または専門支援の独立タスク化           | 組織定義の採用・`owner` 使用可否と列・相談先が整合するか。ロール・メンバー定義、WBS・Schedule の追従箇所を特定する         |
| Schedule の担当変更・WBS 導入・タスク分割        | action と主担当が一致するか、承認・レビューの例外かを確認し、「不一致時の更新先」に従って更新する                          |
| 受入・リリース・継続ゲートの変更、品質判定の滞留 | 判断行の `A` と材料を準備する `R`、相談先、判断期限への影響を確認し、管理計画・コミュニケーション計画へ反映する            |
| 参加・離脱・兼務負荷・AI Agent の支援範囲の変化  | メンバー定義と未完了タスクを照合し、実行・承認を引き受けられるか、人間の判断と作業の記録を分けられるか確認する             |

`PM` は影響する参照先、更新担当 Role、期限、依存関係を追従タスクにする。責任の見直しが完了する条件は、各行の `A` と主担当が明確で、組織・ロール・メンバー定義と WBS・Schedule、[[specdojo:pm-communication-plan-sample|コミュニケーション計画]] の担当・相談先が整合し、未完了タスクに引き継ぎ漏れがないことである。文書の置き換え・廃止は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。

発生済みの担当不能・承認待ちは [[specdojo:pm-issue-log-sample|課題管理簿]]、将来の引き継ぎ不能の懸念は [[specdojo:pm-risk-register-sample|リスク登録簿]]、範囲・上限・責任境界の変更要求は [[specdojo:pm-change-request-log-sample|変更要求ログ]] へ分ける。`PM` は担当 Role と転送先レコードを追跡し、決定は管理計画の方針どおり同じ記録に判断者・理由・判断日を付記する。経緯や状態を本表へ蓄積しない。
