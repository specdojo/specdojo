# RACI: 駄菓子屋きぬや 販売管理システム

## 1. 適用方針

単一店舗・タブレット1台の販売・在庫・つけ記録の初期リリースと店頭試用の責任境界を示す。EC、複数店舗、本格会計、仕入れ先連携は初期スコープ外とし、定型作業や生成ビューは行にしない。

列は [[specdojo:pm-organization-sample|組織定義]] の主導ロールとする。専門支援の `ARC`、`UX`、`OPS` は列を省き、助言はそれぞれ `DEV`、`BA`、`PM` が取り込む。独立タスク化するなら組織定義の見直しを先行させる。

記号は [[specdojo:people-and-organization-definition-standard|人と組織の定義標準]] に従う。`A` と `R` を兼ねても作業結果と判断の証跡を分ける。AI Agent は `R`・`C` の作業を支援できるが、`A` の判断は人間が行う。

## 2. 成果物別 RACI

| 成果物                                 | PO  | PM  | BA  | DEV | QE  |
| -------------------------------------- | --- | --- | --- | --- | --- |
| プロジェクト概要・スコープ・成功基準   | A   | C   | R   | C   | C   |
| 組織定義・ロール定義・メンバー定義     | A   | R   | C   | I   | C   |
| 管理計画・コミュニケーション計画・RACI | C   | A/R | C   | I   | C   |
| 利用者要求・操作設計                   | A   | C   | R   | C   | C   |
| 実装・データ設計                       | C   | I   | C   | A/R | C   |
| 品質計画・試験結果                     | A   | C   | C   | C   | R   |
| リリース候補                           | A   | R   | C   | R   | C   |

品質計画・試験結果の `A` は確認範囲と結果を、リリース候補の `A` は準備完了を確認する。利用開始の可否は次表で決める。

## 3. 判断・プロセス別 RACI

| 判断・プロセス                 | PO  | PM  | BA  | DEV | QE  |
| ------------------------------ | --- | --- | --- | --- | --- |
| 価値、範囲、優先順位の判断     | A   | R   | C   | C   | C   |
| 費用・参加時間上限の判断       | A   | R   | C   | C   | C   |
| 作業順序、課題・リスク管理     | C   | A/R | C   | C   | C   |
| 利用者確認                     | A   | C   | R   | C   | C   |
| 受入・品質ゲート判定           | A   | C   | C   | C   | R   |
| 品質未達・例外要求への対応判断 | A   | C   | C   | C   | R   |
| 変更要求の採否                 | A   | R   | C   | C   | C   |
| リリース・試用後の継続判断     | A   | R   | C   | C   | C   |

- 作業順序、課題・リスク管理の `A` は進捗と調整を判断し、成果物の内容承認は各成果物行の `A` に残す。
- 利用者確認では `BA` が店主・家族利用者の操作結果と意見を集め、内部 Role だけで代替しない。
- 品質未達では `QE` が不足する証跡と是正案を整理し、`PO` が保留と再判定を判断する。[[specdojo:pm-plan-sample|管理計画]] の判断ゲートどおり必須条件は免除せず、範囲・基準の変更は変更要求を先に通す。

## 4. Schedule・実行主体との対応

### 4.1. 主担当と照合先

個別タスクの正本は管理計画が示す `kinuya-schedule`（未同梱の架空記録）、照合は人と組織の定義標準の「Schedule への担当展開」に従う。割り当て先は人間が [[specdojo:pm-members-sample|メンバー定義]]、agent が `.specdojo/agent-members.yaml` を正本とし、本書へ複製しない。

| 対象作業                               | 主担当・`owner` | 対応する行と照合内容                       |
| -------------------------------------- | --------------- | ------------------------------------------ |
| 利用者要求・操作設計を作成する         | `BA`            | 成果物行の `R`。`UX` の助言を取り込む      |
| 実装・データ設計を承認する             | `DEV`           | 成果物行の `A/R`。作業結果と承認を別記録   |
| リリース候補の導入・引き継ぎを準備する | `PM`            | 複数 `R` のうち導入・復旧・引き継ぎの準備  |
| リリース候補の対象版を組み立てる       | `DEV`           | 複数 `R` のうち組み立てと技術的な是正      |
| リリース可否を承認する                 | `PO`            | 判断行の `A`。準備作業とは別の承認タスク   |
| 利用者要求・操作設計を技術レビューする | `DEV`           | 成果物行の `C`。作成とは別のレビュータスク |

### 4.2. 不一致時の更新先

`PM` は action、WBS の明示 `owner`、作成か承認・レビューかで修正先を決め、Schedule の現在値で主担当を選び直さない。

| 不一致の原因・具体例                                   | 更新する正本                                                              |
| ------------------------------------------------------ | ------------------------------------------------------------------------- |
| 操作設計の作成タスクが `DEV`                           | タスク定義の正本（WBS の明示 `owner` か `kinuya-schedule`）を `BA` に直す |
| WBS の明示 `owner` は `BA`、展開結果が `DEV`           | 生成元・展開処理を直して再生成する。生成ビューは直接編集しない            |
| 合意した責任変更（専門支援の独立タスク化など）が未反映 | 組織定義を確かめ、本書を直してから WBS・Schedule へ反映する               |

原因や責任が未決の間は、担当変更を前提とする作業を保留する。

## 5. 見直し条件

| トリガー                                  | 確認すること                                                                 |
| ----------------------------------------- | ---------------------------------------------------------------------------- |
| 初期スコープ、成果物の統合・分割・廃止    | 各成果物から一つの行と `A`・主担当へ辿れるか、旧参照と後続タスクの付け替え先 |
| 採用 Role、専門支援の独立タスク化         | 組織定義と列・相談先の整合、WBS・Schedule の追従箇所                         |
| Schedule の担当変更・WBS 導入・タスク分割 | action と主担当の一致。直し方は「不一致時の更新先」に従う                    |
| 判断ゲートの変更、品質判定の滞留          | 判断行の `A` と材料を準備する `R`、相談先、判断期限への影響                  |
| 参加・離脱・兼務負荷・AI Agent 支援の変化 | 未完了タスクを引き受けられるか、人間の判断と作業の記録を分けられるか         |

各行の `A` と主担当が明確で、組織・ロール・メンバー定義、WBS・Schedule、[[specdojo:pm-communication-plan-sample|コミュニケーション計画]] と整合し、引き継ぎ漏れがなければ見直しを終える。経緯や状態は本表へ蓄積しない。
