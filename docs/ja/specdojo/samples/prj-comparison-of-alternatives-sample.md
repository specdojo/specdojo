# 代替案比較: 駄菓子屋きぬや 販売管理システム

販売・在庫・つけの記録を店主代表以外の店番でも継続できるよう、解決方式を比較する。人間の `PO` が方式と試行対象を判断し、`PM` が未決事項と後続作業を計画へ渡すための完成例である。

## 1. 比較目的と前提条件

| 決定ID | 比較レイヤー           | 決定すること                        | 決定しないこと                     |
| ------ | ---------------------- | ----------------------------------- | ---------------------------------- |
| D-01   | 業務・システム解決方式 | P-01〜P-03 を改善する方式と試行対象 | 個別製品、開発手法、作業管理ツール |

根拠資料:

- [[specdojo:prj-scope-sample|プロジェクトスコープ]]: 販売・在庫・つけと簡易一覧を初期対象とし、EC、本格会計、仕入れ先連携、複数店舗管理を除外する。
- [[specdojo:prj-issues-and-approach-sample|プロジェクト課題と解決アプローチ]]: P-01 は記録不統一、P-02 は残高確認の負荷、P-03 は在庫過不足。記録手段と日次確認・引き継ぎを一式で比較する。
- [[specdojo:prj-assumptions-constraints-dependencies-sample|前提・制約・依存関係]]: タブレット1台、現行手順に近い操作、費用承認、通信断時の方針決定を成立条件とする。

_ASSUMPTION_: 本比較の期間評価では、準備着手の承認から2週間以内に試行候補を用意できることを目安とする。初期リリース日を確定したものではない。現金支出・参加者別作業時間の上限と具体日は [[specdojo:pm-plan-sample|プロジェクト管理計画]] の U-01〜U-03 で判断し、未承認の支出・作業を開始しない。

| 候補カテゴリ       | 候補に含める基準                                                 |
| ------------------ | ---------------------------------------------------------------- |
| 非システム対応     | 紙の記録と手順だけで P-01〜P-03 を改善できる                     |
| 汎用デジタルツール | 専用システムを構築せず、タブレットで記録・検索・集計できる       |
| 既存製品・サービス | 販売・在庫を既存機能で扱い、つけ管理を含む一式の運用を構成できる |
| 個別構築           | 店舗固有の手順と初期対象に合わせた最小機能を構築できる           |

外部候補は、[Google スプレッドシートの公式ヘルプ](https://support.google.com/docs/answer/6000292?co=GENIE.Platform%3DAndroid&hl=ja) でタブレットでの編集と書き出し、[Square の公式ヘルプ](https://squareup.com/help/jp/ja/article/8331-set-up-inventory-tracking) で販売に伴う在庫更新と商品情報の入出力を確認し、ALT-02・ALT-03 に含めた（資料確認日: 2026-11-13）。これはカテゴリの成立根拠であり、市場代表・店舗適合の証明ではない。端末の OS、費用、つけ管理、保管先・権限、全記録の取り出しは個別確認を残す。既存サービス案が残った時点で別レイヤーの製品比較へ進む。

## 3. 評価軸と評価基準

D-01 の全案に次の軸を適用する。`High` / `Middle` / `Low` は採択に有利な順で、費用・期間・リスク・負荷は小さい方を高くする。判定材料がない場合は「未判定」とし、中間評価で代用しない。

| 評価軸             | 判定基準（High / Middle / Low）                                                                                      | 根拠となる課題・制約               |
| ------------------ | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| 効果               | 記録統一・残高検索・在庫低下把握の3能力を同じ記録から提供 / 2能力 / 1能力以下                                        | P-01〜P-03                         |
| コスト             | 現金支出・参加者別作業時間がともに承認上限の80%以内 / ともに上限内だが一方が80%超 / 一方でも上限超。上限未決は未判定 | ACD-C02、管理計画 U-01・U-02       |
| 期間               | 試行候補の準備が7日以内 / 8〜14日 / 14日超。上限承認と参加可能日の確認後の見積もりを使う                             | 比較上の2週間の目安、管理計画 U-03 |
| リスク             | 誤記録・停止・移行漏れの全経路で照合・回復を検証済み / 対策と担当・確認条件があるが未検証 / 対策のない経路がある     | P-01・P-02、ACD-A02・D03           |
| 業務適合           | 両利用者が必須タスクを支援なしで完了 / 支援付きで完了 / 一つでも完了不能。操作性もこの軸で判定する                   | P-01、現行手順とタブレット1台      |
| 技術実現性         | 端末・移行・外部依存の成立を確認済み / 実現経路はあるが検証待ち / 成立しない依存がある                               | ACD-D01〜D04                       |
| データ移行・可逆性 | 元ノートとの全件照合と取り出し・紙への復元を検証済み / 方法を定義し検証待ち / 残高・履歴を復元する方法がない         | P-02、既存ノート                   |
| 運用・保守性       | 引き継ぎ・項目変更・回復を後任が単独で完了 / 手順はあるが支援を要する / 担当・手順を用意できない                     | P-01、小規模体制                   |

「業務適合」は利用者の手順・体制への適合を指し、継続運用と保守の負荷は「運用・保守性」にまとめる。

重み付け・加重合計は用いない。効果・業務適合に `Low` がある案は主方式から外し、残る案を効果、業務適合、リスクの順で比較して試行対象を選ぶ。正式採用は全軸が `Middle` 以上、未判定なし、受入・試用条件合格を必要とする。総合評価は、このゲートの充足状況で示す。

### 4.3. 比較試行の完了条件

- 入力と範囲: ALT-04 と ALT-01 に同じ架空の販売10件、入荷・在庫確認、つけ残高5件を用いる。`DEV` が候補版と操作メモをそろえ、`QE` が欠落・重複・残高差分と取り出し結果を照合する。
- 完了と判定: 全件一致、欠落・重複0件、両利用者が必須タスクを完了した時点で机上評価を更新する。未達は是正後に再確認し、期間・承認上限内に解消できなければ `PO` が試行中止または範囲縮小を判断する。通信断・紙への切り戻しは ACD-D03 の運用方針と追加受入条件が決まるまで実運用しない。
- 正式採用と記録: [[specdojo:prj-success-criteria-and-acceptance-criteria-sample|成功基準と受入条件]] の初期受入と2週間の試用継続条件を各段階で満たすことを確認する。`QE` は `kinuya-acceptance-record`、`BA` は `kinuya-trial-log` に D-01・案 ID・条件 ID・対象版・結果を残し、`PO` が採用・停止を判断する。成功条件の数値・測定方法は参照先を正とする。

## 6. 決定と見直し

D-01 の現時点の判定は「比較結果と採択理由」のとおり。最終判断は人間の `PO` が行い、AI Agent は調査・比較分析・検証を支援する。`BA` は業務影響、`ARC` は技術制約、`DEV` は実装・移行、`QE` は条件と証跡を確認し、`PM` が後続作業を管理する。

`PM` は上限・日程の決定、試行準備、初期受入、店頭試用、継続判断の順で `kinuya-schedule` に担当 Role・依存先・見積もり・期限・確認担当を置く。オフライン方針の判断待ちは既存の `PJR-KN01` へ接続する。`kinuya-` の記録名と `PJR-KN01` は管理計画・前提条件で用いる未同梱の架空記録であり、整備・承認済みの証跡ではない。

| 見直し契機・管理区分                                              | 記録先と次の判断                                                                                                                                               |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 試行・受入での不合格、2週間の記録継続・操作負担条件の未達（課題） | `PM` が [[specdojo:pm-issue-log-sample\|課題ログ]] に D-01・案 ID・是正担当・再確認期限を残し、`PO` が縮小・延期・停止を判断する                               |
| 移行漏れ、端末・通信障害、保守担当不在の兆候（リスク）            | `PM` が [[specdojo:pm-risk-register-sample\|リスク登録簿]] に対象案・兆候・軽減策を登録し、顕在化時は元の ID を付けて課題へ移す                                |
| 承認上限、範囲、利用者・端末、外部依存の変更（変更要求）          | `PM` が [[specdojo:pm-change-request-log-sample\|変更要求ログ]] に評価結果・影響・移行撤退方法を残し、該当カテゴリの全案を再比較する。特定製品を自動採用しない |

未決事項の判断は管理計画 U-01〜U-03 と `PJR-KN01`、採否・再評価の理由と判断者・判断日は該当する課題・変更要求へ付記し、独立した台帳へ二重転記しない。変更後は `PM` がスコープ、成功条件、設計・検証、Schedule への追従を計画し、次の影響作業の開始前に `QE` が整合を確認する。
