# 駄菓子屋きぬや 販売管理システムのオーケストレーター運用メモ

## 1. 目的と適用範囲

本書は、駄菓子屋きぬや 販売管理システム構築を扱う対話型オーケストレーターが、このプロジェクトで実行を組み、止まった実行を再開し、項目を close するときの運用メモである。

- 承認の聞き方や close の前の一般的な確かめ方は、配布するオーケストレーターの指示の本文に従う。本書は、店頭の端末 1 台と営業時間の制約から生じる事柄だけを加える。
- 記述は 2026-04-01 から 2026-04-15 の運用（初期リリースの準備）で起きたことに基づく。店頭の端末の台数か営業時間が変わったら書き直す。

`PJR-KN11` などの項目 ID と `kinuya-*` の記録は未同梱の架空の参照名で、記録先は [[specdojo:pm-plan-sample|プロジェクト管理計画]] に従う。

## 2. agent の使い分けと癖

難しさごとの既定の振り分けは `.specdojo/exec-defaults.yaml` の `routing` を正本とする。開発用の PC のメモリが足りないため、ローカル LLM の executor（`local-executor`）は easy の項目だけに使う。表に加えて、次の癖を踏まえて選ぶ。

| agent            | 癖・制約                                                               | 対応                                                                                 |
| ---------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `cloud-executor` | 使用量の上限に当たると、解除の時刻が出る                               | 実行のログで時刻を確かめ、待つか `cloud-light-executor` へ切り替える                 |
| `local-executor` | 編集できるのは `docs/`・`src/`・`tests/` の下だけ                      | 画面の設定ファイルなどほかの場所を触る項目は easy でも `cloud-light-executor` で流す |
| `local-executor` | 実際には変えていないのに「適用済み」と報告することがある（`PJR-KN12`） | result と差分を必ず照らす                                                            |
| `local-reporter` | 開発用の PC のローカル LLM が止まっていると、接続できずに止まる        | `--fallback-reporter-by cloud-reporter` を付けて流す                                 |

## 3. 実行の運び方

登録簿の項目は `exec run --register` で流す。複数件をまとめて流すときは、次の形で列を組む。

```bash
npx specdojo exec run --project kinuya --register <PJR-ID> --worktree \
  --join --if-busy wait --on-rate-limit fallback \
  --executor-by cloud-light-executor --fallback-executor-by cloud-executor \
  --reporter-by local-reporter --fallback-reporter-by cloud-reporter
```

- 列は 1 本にする。開発用の PC のメモリでは、売上記録の統合テストと文書サイトのビルドを並べると時間切れで落ちた（`PJR-KN13`）。
- 文書サイトのビルドは列の最後の 1 段として 1 回だけ流し、各項目の executor には流させない。
- 列の終わりを待って次を流すときは、待機のスクリプトを書かず `exec queue` で予約する。
- 個票の入力・完了条件には、変える対象の相対パスを書く。読むだけの文書はパスで書かず名前で書く。runner はパスを変更の範囲と推定し、同じパスを書いた項目を順番待ちにする。

## 4. 止まったときの再開

| 止まり方                                  | 原因の例                                     | 再開の仕方                                                                |
| ----------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------------- |
| 親の検証で、executor の実装の誤りで落ちた | import の抜け、lint の違反                   | `--resume --resume-from executor`                                         |
| 親の検証で、負荷で落ちた                  | 売上記録の統合テストの時間切れ               | 手元で同じテストを流し直して偶然かを確かめ、負荷が下がってから `--resume` |
| executor の段が failed で再開できない     | 使えないモデルを指していた、途中で止めた     | `--force-restart` で最初から流す                                          |
| 統合で `CONFLICT`                         | 並べた項目が同じ在庫の画面のファイルを変えた | worktree で両方の変更を残して手で解き、`--resume`                         |

- 再開の前に追加の指示を入れたいときは、plan を手で直さず `--resume-note` を使う。worktree の plan を直すと、統合の前に範囲外の変更として止まる。

## 5. close の前の確かめ方

- 売上・在庫・つけの記録の処理を変えた項目は、統合の後に `kinuya-test-data` の 1 営業日分を流し、つけ残高の合計が変更前と一致することを確かめてから close する。
- executor が `requires_human` と報告した検証は、オーケストレーターが自分で流す。例: タブレットの画面での表示の確認は、開発用の PC のエミュレーターで流し、画面の写しを個票に残した（`PJR-KN14`）。
- 文書だけを変えた項目では、記録の照合は要らない。

## 6. 保護された設定の扱い

- `.specdojo/`・`.agents/`・`package.json`・`AGENTS.md` は agent が書けない。範囲は `.specdojo/` の設定を正本とする。
- 変更が要る項目は、executor に変更案を個票の対応結果と報告の `handoff` に書かせる。オーケストレーターが利用者の承認を得て、feature ブランチで反映する。

## 7. 落とし穴

- 待機が自分自身を数える: `pgrep -f` のパターンで相手の run を探すと、待機のコマンドの文字列も一致して終わらない。プロセスの番号か `exec queue` で待つ。
- commit メッセージの本文は 1 行 100 文字以内にする（commitlint の `body-max-line-length`）。長い文は折り返す。

## 8. リリースの手順

店頭のタブレットへの入れ替えは、閉店後に行う。

1. 範囲の項目がすべて close されていることを登録簿で確かめる。close されていない項目があれば、次の版へ回すか待つかを店主代表（`PO`）に確かめる。
2. 各項目の個票の対応結果から「リリースノートに書く事項」を集め、`kinuya-release-notes` にまとめる。集めた件数と範囲の close の件数が一致したら次へ進む。
3. 開発用の PC で全件の検査を流し、すべて通ったら配布物を作る。
4. 閉店後にタブレットへ入れ替え、`kinuya-test-data` で販売・在庫・つけの記録を 1 件ずつ試す。どれかが通らなければ、前の版へ戻す。
5. 翌朝の開店前に、店主代表と販売の画面を確かめ、結果を `kinuya-acceptance-record` に残してリリースの項目を close する。

## 9. 店頭の端末との分担

- 営業時間中（10:00〜18:00）は、店頭のタブレットへ接続する検証を流さない。販売の画面が止まると店番が記録できなくなる。
- 夜間に長い列を流すときは、閉店後の入れ替えの作業と重ならないかを先に確かめる。
- _UNDECIDED_: 営業時間外にタブレットが通信できないときの検証の扱い。決まるまでは、タブレットに接続する検証を `requires_human` として残し、翌朝の開店前に流す。
