# プロジェクトスコープ: 駄菓子屋きぬや 販売管理システム

[[specdojo:prj-overview-sample|プロジェクト概要]] の期待効果（店主不在でも販売・在庫・つけを同じ手順で扱い、欠品と在庫の無駄を減らす）を受け、初期リリースで対象とする範囲と対象外を関係者が合意できるように境界を定める。

## 1. 対象業務

本プロジェクトでは、単一店舗の店頭販売を継続しやすくするため、販売記録、店頭在庫、常連顧客のつけ管理を対象とする。

- 駄菓子の店頭販売を記録する。
- 入荷、棚卸、廃棄を含む店頭在庫を管理する。
- 常連顧客の簡易情報とつけ残高を確認する。
- 日次の売上、在庫低下、つけ残高を確認する。

次の表は、対象業務に関わる利用者・関係者ごとに、どの場面で関わり、スコープに含めることで何が変わるかを示す。スコープの合意と変更の最終判断は店主代表が担い、責務を表す箇所では Role code の `PO` と書く。利用者影響と受入観点の整理は業務分析の Role `BA` が担い、家族利用者代表の操作確認の結果を取りまとめる。

| 利用者・関係者         | 関わる場面                                           | 利用者影響                                                             |
| ---------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------- |
| 店主代表（`PO`）       | 毎営業日の店番、仕入れ前の在庫確認、つけの受付       | 記憶とノートに頼らず、欠品しそうな商品とつけ残高をその場で確認できる   |
| 家族利用者代表         | 店主代表が不在の日の店番                             | つけの受付や在庫の問い合わせを、店主代表の戻りまで保留せずに対応できる |
| 開発担当               | 初期リリース前の試行、運用中の不具合と訂正依頼の受付 | 店頭で起きた問題を、同じ販売・在庫・つけ記録から確認できる             |
| 常連顧客（操作しない） | つけでの購入、つけ残高の問い合わせ                   | ノートの残高と本人の認識が食い違ったときの確認待ちが短くなる           |

## 2. 対象システム

次の表は、対象業務を支えるシステムと成果物ごとに、扱う内容と本プロジェクトが担う範囲の境界を示す。

| 対象                 | 内容                                                           | 境界                                                 |
| -------------------- | -------------------------------------------------------------- | ---------------------------------------------------- |
| 販売登録             | 商品選択、数量入力、支払い方法選択、販売記録                   | 店頭販売の記録までとし、会計処理は含めない           |
| 在庫管理             | 入荷登録、棚卸、廃棄・値引きの登録、在庫一覧、在庫低下の確認   | 店頭在庫までとし、仕入れ先との連携は含めない         |
| 顧客・つけ管理       | 常連顧客の登録、つけ残高の記録、残高確認                       | つけ管理に必要な最小情報だけを扱い、連絡先は持たない |
| 販売・在庫・つけ記録 | 各業務の正本となる記録                                         | 訂正手順を通じて更新し、生成レポートからは変更しない |
| 簡易レポート         | 日次売上一覧、在庫低下一覧、つけ残高一覧                       | 正本記録から生成し、集計値を直接編集しない           |
| 運用補助             | 店主代表と家族利用者代表が同じ手順を参照できる最小限の操作メモ | 操作の共通化までとし、個別の店番判断は店主代表が行う |

店頭で使うタブレット1台の用意と、運用開始前1か月のベースラインの手書き記録は、本書の対象システムに含めず、[[specdojo:prj-assumptions-constraints-dependencies-sample|前提・制約・依存関係]] で依存条件として扱う。

## 3. 対象期間

- 初期対象期間は、最小機能の初期リリースから、運用開始後2週間の記録継続を判定するまでとする。判定には [[specdojo:prj-success-criteria-and-acceptance-criteria-sample|成功基準と受入条件]] の SC-02（営業日の90%以上で販売・在庫・つけの記録が残る）を使い、判定の結果が出た時点で初期対象期間を終える。
- 初期リリース前は、店頭販売、在庫、つけ管理に必要な最小機能と操作メモの整備、店主代表と家族利用者代表による代表シナリオの試行を対象とする。
- 初期リリース後の2週間は、記録継続状況、不足機能、店主代表の操作負荷を確認し、次フェーズの改善候補を整理する。
- 運用開始後6か月・12か月で判定する中長期の効果（欠品削減、在庫適正化など）の確認は、初期対象期間に含めず継続改善として扱う。
- _ASSUMPTION_: 初期リリースと2週間の判定は、繁忙期（学校の夏休み期間）が始まる前に終える。
- 具体的な日付は _UNDECIDED_: 初期リリースの計画で決定する。

## 4. スコープ外

次の表は、初期リリースで扱わない対象ごとに、外す理由と後続で扱う条件を示す。

| 対象（Out）           | 理由                                                             | 補足                                             |
| --------------------- | ---------------------------------------------------------------- | ------------------------------------------------ |
| 複数店舗管理          | 単一店舗の運用定着を優先するため                                 | 運用定着後に次フェーズで検討する                 |
| EC サイトやネット注文 | 店頭販売の記録継続を優先するため                                 | 店舗運営への効果確認後に要否判断する             |
| 本格的な会計連携      | 初期は販売記録とつけ管理の責務に限定するため                     | 会計処理は既存手順で代替する                     |
| 仕入れ先システム連携  | 仕入れ判断の基礎データを蓄積する段階であり連携範囲が未確定       | 仕入れ改善の課題整理後に検討する                 |
| 仕入れ数量の自動提案  | 仕入れ数量は店主代表が判断し、システムは記録と確認を支援するため | 記録が蓄積し、中長期指標を判定した後に再検討する |
| 顧客の連絡先管理      | 顧客の個人情報を店内の最小限の記録にとどめるため                 | つけの督促は既存の対面のやり取りで行う           |
| 複雑なポイント制度    | 店頭手順を増やさず、店主代表が迷わず使えることを優先するため     | 必要性が明確になった段階で再検討する             |

オフライン時の運用を初期スコープに含めるかは _UNDECIDED_: 初期リリースの計画でオフライン時の運用方針を決めたときに、本書へ反映する。

## 5. 境界の判断基準

初期リリースでは、「店頭での販売・在庫・つけの記録が止まらないこと」を最優先とする。

迷った場合は、次の順で判断する。

1. 店主代表または家族利用者代表が日々使う業務を優先する。
2. 販売・在庫・つけ残高の記録継続に直接必要なものを優先する。
3. 店頭手順を複雑にする機能は初期スコープから外す。
4. 外部連携や高度な分析は、記録が安定した後の次フェーズで扱う。

例えば、在庫の廃棄登録は在庫の無駄を測る記録に直接必要なため 2. により含め、仕入れ数量の自動提案は 4. により次フェーズへ回す。

## 6. スコープ変更方針

次の表は、スコープを追加・削除・変更するときに、どこから提案し、何を評価し、誰が判断して、どこへ記録するかを示す。

| 項目     | 内容                                                                                                                                                                     |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 変更入口 | 店主代表、家族利用者代表、開発担当が課題一覧または変更要求ログへ提案する                                                                                                 |
| 影響評価 | 店頭手順、操作時間、初期リリース時期、データ移行、再説明の必要性を確認し、成功基準と受入条件、前提・制約・依存関係、課題と解決アプローチ、スケジュールの見直し要否を示す |
| 承認者   | 店主代表（`PO`）が最終判断する。`BA` は利用者影響と受入観点を整理して判断材料にする                                                                                      |
| 記録先   | 決定記録（DEC）、課題一覧、または変更要求ログへ、判断理由と影響範囲を残す                                                                                                |

記録先の書き方は [[specdojo:dec-sample|決定記録]]、[[specdojo:pm-issue-log-sample|課題一覧]]、[[specdojo:pm-change-request-log-sample|変更要求ログ]] の例に従う。

初期リリース前にスコープを追加する場合は、追加対象と同時に延期または除外する対象を示し、初期リリースの目的を維持できるかを確認する。例えば、つけ残高の月次集計を追加するなら、在庫低下一覧の表示条件の拡張を次フェーズへ延期し、繁忙期前の初期リリースに間に合うかを確認する。
