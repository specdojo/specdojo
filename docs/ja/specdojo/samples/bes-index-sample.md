# 業務イベント一覧: 駄菓子屋きぬや販売管理

駄菓子屋きぬやの店舗運営で、各プロセス領域を起動する業務上の出来事を一覧で定義する。対象は [[specdojo:cdfd-overview-sample|概念データフロー図（全体概要）]] の「プロセス領域」に挙げた仕入・販売・在庫・顧客・締めの 10 領域の起点イベントであり、領域 ID・領域名・起点イベントの文言は同書を正本とする。

[[specdojo:prj-overview-sample|プロジェクト概要]] の「まず記録する」方針に沿い、店主代表と家族利用者代表が、販売・入荷・つけをいつ記録するか同じ判断をできるようにする。購入の申し出と会計確定、納品と検品後の入荷記録を区別し、記録漏れや二重計上を防ぐための定義とする。

BA は本書を BPS・BR の入力、UX は UI 仕様の記録契機、QE はテスト仕様の発生・不成立条件の入口として使う。ARC・開発担当は個別 BES とデータモデルへの対応を確認し、人間の PO（店主代表）は対象範囲と未決事項の扱いを承認する。受けた後の手順は BPS、金額計算は [[specdojo:br-sample|販売金額計算の業務ルール]]、取引の状態は状態定義に委ねる。

_ASSUMPTION_: 事実データは、上位文書の「データストア」に挙げた記録の主な内容から、発生時点で観測できる情報を概念名で挙げた。データモデルとの対応は未照合であり、保管先の未確定とは別の確認事項として「未決事項と承認条件」で管理する。値・構文・構造はデータモデル・schema を正本とする。

## 2. 個別仕様への詳細化

| イベントID                  | 個別仕様                                                    | 詳細化する範囲                     | 詳細化の理由                                                                             |
| --------------------------- | ----------------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------- |

- `specdojo:bes-sample` は完成例の文書 ID であり、対応するイベント ID は `bes-cash-sale-confirmed` である。同書からも本一覧と対応行を参照する。
- `bes-credit-sale-requested` のうち上限内の申し出は、一覧の定義のまま扱う。上限超過の経路は個別仕様で境界を確定するまで、BPS・UI・テスト仕様の確定入力にしない。
- 未作成の個別仕様は文書 ID だけを仮置きし、作成時に BA が一覧の行と個別仕様の双方向の参照を設定する。

## 3. 未決事項と承認条件

### 3.1. 判断を残す論点

<!-- prettier-ignore -->
| 論点 | 現時点の扱い・影響 | 判断者・確認担当 | 次アクション・完了条件 | 解消の時期 |
| --- | --- | --- | --- | --- |
| 発注のない納品 | _UNDECIDED_: `bes-goods-delivered` に含めるかは未判断。現定義では発生せず、発注外納品の BPS・UI・テストが確定できない。 | BA が確認し、PO（店主代表）が判断する。 | BA が発注あり・なしの納品を店主代表に確認し、一覧に含めるか別の境界にするかを上位 CDFD と照合する。判断と影響先を記録して完了とする。 | 入荷検品 BPS の作成前 |
| つけ上限超過 | _UNDECIDED_: 申し出の受付と店主代表の承認のどちらで成立するかが未確定。当該経路の BPS・BR・UI・テストの判定に影響する。 | BA が整理し、PO（店主代表）が判断する。 | `bes-credit-sale-over-limit` を作成し、一覧との相互参照、上限内との境界、BR への参照を ARC・QE が確認して完了とする。 | つけ販売の設計への引き渡し前 |

| 事実データの照合 | _ASSUMPTION_: 販売記録・在庫記録・つけ台帳のデータモデルと未照合。発生時点で情報がそろわない場合、イベント処理・テストの入力が不足する。 | ARC が対応を確認し、BA・QE が業務上の意味と確認例を照合する。 | 全行の概念名をデータモデルへ対応付け、発生後の結果を含まないことを確認する。不足の解消または PO の制限事項承認を記録して完了とする。 | イベント処理・テスト設計への引き渡し前 |
| 一覧の範囲 | 10 領域の起点イベントだけを対象とする。値引き・取消・返品は内部の出来事として本一覧に含めず、全業務の対象外という意味にはしない。 | BA が網羅を確認し、PO（店主代表）が承認する。 | 起点イベントと有効行の対応を確認し、範囲の承認を記録する。追加の起点が必要なら先に上位 CDFD の範囲を見直す。 | 本書を確定入力として扱う前 |

判断と確認結果は本書と対象案件のレビュー結果に記録する。PM は、未決の境界、個別仕様の未作成、データ未照合を PJR 登録候補として PO へ報告し、該当する確認担当・判断時期・後続作業への影響を転記する。期限までに解消できなければ、PM が影響する設計作業を保留し、PO に制限事項としての受入可否を求める。

### 3.2. 確定入力としての受入条件

BA・ARC・QE は、次のすべてを満たすことを確認し、レビュー結果に証拠を残す。

- 上位 CDFD の 10 領域に有効な 10 行が対応し、出典のない行がない。必須 8 列に空欄がなく、廃止行を含めイベント ID の形式違反・重複が 0 件である。
- QE が、現金受領不足・明細確認中は現金会計の確定なし、確定後の再表示・再印字では追加の確定なしと判定できる。納品受取と検品後の入荷記録、閉店宣言と閉店時刻到来も区別できる。個別の判定例は個別 BES を参照する。
- 個別 BES の対応範囲と相互参照が一致し、上表の論点が解消または制限事項として承認され、PO（店主代表）が一覧の範囲を承認している。
- [[specdojo:bes-index-rulebook|業務イベント一覧 作成ルール]] の「検証と引き渡し」に従った静的検査で Markdown・Frontmatter のエラーが 0 件で、未解決指摘の扱いを QE が確認している。メタ情報の制約は同書の参照先を正本とし、sample の文書 ID とイベント ID を混同しない。

本例は業務判断を残した完成記述例であり、実案件の承認済み仕様ではない。現時点では上の条件を満たしていないため `status: draft` を維持し、人間の PO が承認するまで BPS・BR・UI・テスト仕様への確定入力にしない。

### 3.3. 改訂時の引き継ぎ

つけ上限超過の境界が決まった際は、BA が `bes-credit-sale-requested` の行と `bes-credit-sale-over-limit`、つけ販売の BPS・BR を照合し、UX が申出受付と承認の画面、QE が上限内・超過時の期待結果を更新する。ARC・開発担当は申出時点と承認時点で得られる情報をデータモデル・イベント契約と照合する。PM は未完の追従と引き渡し時期を PJR で管理し、PO が制限の解除を判断する。
