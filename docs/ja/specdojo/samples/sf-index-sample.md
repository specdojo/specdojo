# 駄菓子屋きぬや システム化機能一覧（全体構成）

本書は、駄菓子屋きぬや販売管理システムが店頭のタブレットで実現する機能の全体構成と一覧を定義する。各機能を業務プロセス領域と画面へ対応付け、機能分割・テスト対象の洗い出しと、個別機能仕様への入口として使う。

## 1. 目的と対象範囲

販売・在庫・つけ・締めの業務ごとにシステムが担う記録と確認の範囲を確定し、店主代表がスコープを承認でき、業務からの漏れと機能の重なりを一覧で判断できるようにする。これは [[specdojo:prj-overview-sample|プロジェクト概要]] の「まず記録する」方針と、店番が交代しても同じ手順で記録を続ける目標に対応する。

### 1.1. 対象の境界

| 区分   | 範囲                                                                                                                                         |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 対象   | 単一店舗の店頭タブレットで行う販売・つけ・在庫・締めの記録と確認。業務プロセス領域 `P-02`〜`P-10` のうち、システムが記録・算出・提示する部分 |
| 対象外 | 仕入先への発注（`P-01`）、補充・つけ上限・売価の最終判断、キャッシュレス決済、本格会計、EC、複数店舗、個別機能の入出力・振る舞いの詳細       |

販売・在庫・つけの日々の記録を先行し、補充依頼支援と月次集計の導入時期は `Q-03` で決める。一覧に載せた全機能を初期リリースに含むとはみなさない。通信不能時の営業継続方針はプロジェクト概要の未決事項に従い、本一覧でオフライン販売を保証しない。

### 1.2. 読者・確認責任・公開範囲

| Role | 本一覧の利用・確認責任                                                                               |
| ---- | ---------------------------------------------------------------------------------------------------- |
| BA   | 一覧を保守し、店主代表・家族利用者代表と業務の漏れと人間に残す判断を確認する                         |
| DEV  | 機能分割と画面・データ設計、実装範囲を確認する。ARC の専門支援を受けて販売・在庫の責務境界を照合する |
| QE   | 機能 ID をテスト対象に対応付け、参照と未決事項の欠落を確認する                                       |
| PM   | 参照先の整備と追従作業を成果物カタログ・Schedule に接続し、判断待ちを管理する                        |
| PO   | 人間の店主代表がスコープ、導入順序と公開可否を最終判断する                                           |

採用ロールと兼務は [[specdojo:pm-organization-sample|組織定義]]・[[specdojo:pm-members-sample|メンバー定義]]、作業と承認の分担は [[specdojo:pm-raci-sample|RACI]] を正本とする。初期の技術作業は DEV が主導し、ARC を独立した Schedule タスクの主担当にはしない。

公開対象は店舗内の運用者と開発・レビュー担当とする。本例には実顧客の情報、認証情報、非公開の接続先を含めない。外部公開する場合は BA が匿名化した版を用意し、PO が公開範囲を確認する。

### 1.3. 一覧の完成判定

次表は内容レビューの合格条件であり、確認済みの結果ではない。確認結果と未充足の条件は `kinuya-sf-review`（本例に未同梱の架空レビュー記録）へ残す。

| 確認担当          | 判定条件                                                                                           | 確認する証跡                                               |
| ----------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| BA                | `P-01`〜`P-10` の全10領域について、機能への割当てまたはシステム化しない理由がある                  | 概念データフロー図の領域表と本書「機能構成」・主一覧の対応 |
| DEV（ARC が支援） | 9件の機能 ID が一意で4領域の略号と一致し、販売・入荷から在庫への受け渡しと人間の判断が区別できる   | 主一覧と表後の責務境界、個別機能仕様・画面仕様の照合結果   |
| QE                | 主一覧の必須6列が埋まり、実在参照は解決でき、仮置きの参照は `Q-01`・`Q-03` で追跡されている        | 文書・参照の検査記録、機能 ID と後続テスト対象の対応       |
| PM                | 未決事項ごとに担当、判断時点、追跡先と保留する作業が特定されている                                 | 未決事項と、整備後の成果物カタログ・Schedule・課題記録     |
| PO                | 各担当の確認結果から対象範囲・人間の判断・公開範囲を確認でき、承認範囲に未合意の責務が残っていない | レビュー記録と承認対象の範囲、除外した範囲の追従先         |

文書検査の成功だけでは承認しない。`Q-01`〜`Q-03` が承認対象に影響する間は `draft` を維持し、PO が対象範囲を承認するまで当該範囲の設計・受入を保留する。機能自体の正常・例外・回復の試験条件は個別仕様と後続のテスト仕様で定義する。

## 2. 機能構成

業務プロセス領域の区分は [[specdojo:cdfd-overview-sample|概念データフロー図（全体概要）]] に従う。入荷の記録（`P-02`）は在庫数量を更新する処理のため、仕入ではなく在庫の領域に含める。

| 機能領域 | 略号  | 業務プロセス領域       | システムの責務                                                       | 人間に残す判断                       |
| -------- | ----- | ---------------------- | -------------------------------------------------------------------- | ------------------------------------ |
| 販売     | `POS` | `P-03`                 | 現金販売の明細・請求額・釣銭を提示し、販売を記録して在庫へ渡す       | 取引の中止                           |
| つけ     | `CRD` | `P-04`・`P-07`・`P-08` | 常連客とつけ上限を登録し、つけ販売と精算を記録して残高を提示する     | つけ上限の設定、上限超過時の販売可否 |
| 在庫     | `INV` | `P-02`・`P-05`・`P-06` | 入荷と販売を在庫へ反映し、補充基準を下回った商品と依頼数量を提示する | 補充依頼の承認                       |
| 締め     | `CLS` | `P-09`・`P-10`         | 当日の販売・入荷・在庫・つけを突き合わせ、差異と月次の集計を提示する | 締めの確定、売価・補充基準の見直し   |

仕入計画（`P-01`）はシステム化しない。仕入先とのシステム連携を初期リリースの対象外としたため、店主代表が補充依頼を基に発注する。

## 3. システム化機能一覧

| 機能 ID     | 機能名       | 概要                                                                                   | 業務プロセス仕様                               | 画面                                  | 個別仕様                                 |
| ----------- | ------------ | -------------------------------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------- | ---------------------------------------- |
| `SF-POS-01` | 店頭商品販売 | 商品と数量から請求額・釣銭を提示し、現金の受領確認を受けて販売を記録する               | `P-03` / `bps-sales-order-flow`                | [[specdojo:uis-sample\|販売登録画面]] | [[specdojo:sf-sample\|商品販売機能仕様]] |
| `SF-CRD-01` | つけ販売     | つけ上限と残高を確認して、つけでの販売を記録し、更新後の残高を提示する                 | `P-04` / `bps-credit-sale`                     | `uis-credit-sale`                     | 一覧行で要約                             |
| `SF-CRD-02` | 常連客登録   | 常連客の識別情報とつけ上限を登録・変更し、つけ販売の可否判定に使えるようにする         | `P-07` / `bps-customer-registration`           | `uis-customer`                        | 一覧行で要約                             |
| `SF-CRD-03` | つけ精算     | 支払額を受け付けてつけ残高を減らし、精算後の残高を提示する                             | `P-08` / `bps-credit-settlement`               | `uis-credit-sale`                     | 一覧行で要約                             |
| `SF-INV-01` | 在庫確認     | 販売と入荷を在庫数量へ反映し、商品ごとの現在庫を提示する                               | `P-05` / `bps-inventory-check`                 | `uis-inventory`                       | `sf-inventory`（作成候補、`Q-03`）       |
| `SF-INV-02` | 入荷記録     | 検品済みの商品と数量を入荷として記録し、在庫確認へ渡す                                 | `P-02` / `bps-receiving`                       | `uis-inventory`                       | 一覧行で要約                             |
| `SF-INV-03` | 補充依頼支援 | 補充基準を下回った商品と、発注単位に合わせた依頼数量を提示し、承認された依頼を記録する | `P-06` / [[specdojo:bps-sample\|補充依頼確定]] | `uis-inventory`                       | 一覧行で要約                             |
| `SF-CLS-01` | 日次締め照合 | 当日の販売・入荷・在庫・つけの記録を突き合わせ、差異を提示して締めの確定を記録する     | `P-09` / `bps-daily-closing`                   | `uis-closing`                         | 一覧行で要約                             |
| `SF-CLS-02` | 月次集計報告 | 月次の売上・欠品回数・つけ残高を集計し、見直しの判断材料として提示する                 | `P-10` / `bps-monthly-review`                  | `uis-closing`                         | 一覧行で要約                             |

- `uis-credit-sale` はつけ販売とつけ精算（`SF-CRD-01`・`SF-CRD-03`）にまたがる。`uis-inventory` は在庫の 3 機能にまたがる。
- `uis-closing` は日次締めと月次集計にまたがる。画面の数を機能数とせず、業務上の責務で行を分ける。
- `SF-POS-01`・`SF-CRD-01` と `SF-INV-02` は、販売の払出数量と入荷数量を `SF-INV-01` へ渡す。在庫の算出・反映は在庫確認、現金販売の完了通知は店頭商品販売が担い、在庫未反映・結果不明を販売完了とは通知しない。詳細な回復条件は [[specdojo:sf-sample|商品販売機能仕様]] を正とする。
- つけ上限超過時の販売可否、補充依頼の承認、締めの確定は店主代表に残す。システムは判断材料と判断結果を記録し、上限超過を自動承認する機能は数えない（`Q-02`）。
- 個別仕様の完成例は店頭商品販売を参照し、在庫確認は作成候補とする。カタログ登録が未確認のため、作成判断と登録を `Q-03` で追跡する。その他は一覧行の要約を正とし、詳細化が必要になった時点でカタログへ登録してから作成する。

画面配置・入力形式は画面仕様、入出力・振る舞い・機能の受入条件は個別仕様、値・物理構造はデータの正本・schema へ委ねる。通常利用の接点は GUI とし、別の操作例である販売管理 CLI をこの一覧の利用接点には含めない。

### 4.2. 再照合と申し送り

上流 BPS・画面の作成や改訂、機能の追加・廃止・統合、個別仕様の追加を受けて BA が該当機能 ID を再照合する。販売・在庫の境界変更では DEV が ARC の支援を受けて画面・データ設計・schema・実装への影響を、QE がテスト対象と受入条件への影響を特定する。OPS の運用手順への助言は PM が取り込む。影響しない参照先にも非該当の理由をレビュー記録へ残す。

判断待ちで後続作業が止まる場合は、BA が機能 ID、影響する成果物・タスクと再開条件を PM へ渡す。PM は課題を `kinuya-issue-log`、範囲変更を `kinuya-change-request-log`、追従作業を `kinuya-schedule` で追跡し、本書には対応する参照を残す。

廃止・統合時も機能 ID は再利用せず、旧 ID、理由、後継機能と参照元の付替え先をレビュー記録へ残す。文書の置き換え・廃止は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] に従う。公開後の参照切れは BA、技術境界の矛盾は DEV・ARC、計画への影響は PM、スコープ・公開範囲の変更は PO に引き継ぐ。
