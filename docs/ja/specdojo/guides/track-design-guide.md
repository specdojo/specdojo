# トラック設計ガイド

Track Design Guide

SpecDojoでは、関連する成果物の作成・更新と、それらを生み出す活動を作業系列ごとにまとめ、トラックとして管理します。

以下に、SpecDojoが想定する標準的なトラック構成を示します。トラックはフェーズではなく、相互に並行・反復して実行できます。表の順序は代表的な依存関係を示す一例であり、実際の実行順を固定するものではありません。

**対象読者**

- プロジェクトの作業系列を設計し、成果物の着手順・並行・反復を計画するプロジェクト責任者、計画担当者
- 担当する作業がどのトラックに属し、どの成果物を入力とするかを確認する成果物作成者

**この文書で分かること**

- SpecDojo が想定する標準トラックの構成と、各トラックが扱う範囲
- トラックとドメイン（`dct-<domain>.yaml`）・成果物カテゴリの対応関係
- 開発の進め方に応じた実行順序の組み立て方と、入力元より先に後続トラックへ着手する場合の留意点

**次に読む文書**

- 各成果物の目的・推奨ファイル名・記述規則への導線は [成果物リファレンス](../references/specdojo-deliverables-reference.md) を参照してください。
- トラックを実行タスクへ展開する方法は [Schedule設計ガイド](schedule-design-guide.md) を参照してください。

**この文書が扱わないこと**

- 個別成果物の目的、記述規則、Frontmatter 規約
- 文書の分類、ディレクトリ構成、ファイル名・ID の規則
- Schedule 上のタスク粒度、担当者、日付、依存関係の定義方法
- 要求・要件・仕様・設計・実装という記述内容の区別

## 1. 標準トラック構成

| id      | トラック                | 概要                                                   |
| ------- | ----------------------- | ------------------------------------------------------ |
| launch  | 立ち上げトラック        | プロジェクトの目的、範囲、前提および推進体制を定義する |
| tobe-rs | TO-BE要件・仕様トラック | 目指すTO-BE像と、その要件・仕様を定義する              |
| asis-rs | AS-IS調査・仕様トラック | 現行の業務・システムと、その課題・制約を明らかにする   |
| impact  | 影響調査トラック        | AS-ISとTO-BEの差分と影響を明らかにする                 |
| tobe-d  | TO-BE設計トラック       | TO-BEを実現する業務・システムを設計する                |
| qa-d    | 品質保証設計トラック    | 品質基準、受入条件および検証方法を設計する             |
| mig-d   | 移行設計トラック        | AS-ISからTO-BEへの移行を設計する                       |
| ops-d   | 運用設計トラック        | TO-BE移行後の運用を設計する                            |
| impl    | 実装トラック            | TO-BE設計に基づき、業務・システムを実装する            |
| test    | テストトラック          | 要件・仕様・設計への適合性を検証する                   |
| mig     | 移行トラック            | 移行設計に基づき、AS-ISからTO-BEへ移行する             |
| ops     | 運用トラック            | 移行後の業務・システムを運用し、継続的に改善する       |

## 2. トラックとドメイン・成果物カテゴリの関係

本章では、トラックがどのドメインの成果物カタログを対象とし、どの成果物カテゴリを扱うかを示します。個別成果物の目的・推奨ファイル名・記述規則への導線は [成果物リファレンス](../references/specdojo-deliverables-reference.md) を参照してください。

### 2.1. トラック・ドメイン・成果物の3層

トラック、ドメイン、成果物はそれぞれ扱う単位と正本が異なります。

| 層       | 単位                                   | 正本                                            |
| -------- | -------------------------------------- | ----------------------------------------------- |
| トラック | 関連する成果物と活動をまとめた作業系列 | 本書（標準構成）と `sch-strategy-<track>.yaml`  |
| ドメイン | 成果物カタログの管理単位               | `dct-<domain>.yaml`                             |
| 成果物   | 個別のドキュメント・定義ファイル       | 種別ごとの rulebook（一覧は成果物リファレンス） |

3層は Schedule 定義で接続します。`sch-strategy-<track>.yaml` は `track` でトラックを宣言し、`scope.catalogs` で対象とする `dct-<domain>.yaml` を指定します。つまりトラックが直接ぶら下げるのはドメインであり、個別成果物はドメインの成果物カタログ側で管理されます。生成の流れは [Schedule設計ガイド](schedule-design-guide.md) を参照してください。

### 2.2. トラック別の対応

各トラックが対象とするドメインと成果物カテゴリの標準的な組み合わせは次のとおりです。成果物カテゴリは [成果物リファレンス](../references/specdojo-deliverables-reference.md) の章タイトルに対応します。ドメイン名は例であり、実際の切り方はプロジェクトごとに決めます。

| id      | 想定ドメインの例                           | 主に扱う成果物カテゴリ                                 | 関与の仕方 |
| ------- | ------------------------------------------ | ------------------------------------------------------ | ---------- |
| launch  | `project-definition`、`project-management` | 立ち上げ、プロジェクト定義、プロジェクトマネジメント   | 定義する   |
| tobe-rs | `product-spec`                             | 業務仕様、外部I/F仕様、非機能要件                      | 定義する   |
| asis-rs | `product-change`、`product-spec`           | 現状定義、業務仕様（AS-IS）、外部I/F仕様（AS-IS）      | 定義する   |
| impact  | `product-change`                           | 影響調査、トレーサビリティ                             | 定義する   |
| tobe-d  | `product-spec`                             | アーキテクチャ、システム設計                           | 定義する   |
| qa-d    | `product-spec`                             | 業務受入条件、システム受入条件、テスト                 | 定義する   |
| mig-d   | `product-change`                           | 移行                                                   | 定義する   |
| ops-d   | `product-spec`                             | 運用                                                   | 定義する   |
| impl    | `product-spec`                             | システム設計（SSOTである定義ファイル・コードへの導線） | 実施する   |
| test    | `product-spec`                             | テスト                                                 | 実施する   |
| mig     | `product-change`                           | 移行                                                   | 実施する   |
| ops     | `product-spec`                             | 運用                                                   | 実施する   |

`関与の仕方` は、そのトラックが成果物を書き起こすのか、既存の成果物に従って作業するのかを表します。`定義する` トラックは成果物そのものが主な産物になります。`実施する` トラックは、対応する `定義する` トラックの成果物を入力として実行し、実行記録や更新結果を残します。テストは `qa-d` で観点・条件を定義して `test` で実施する、移行は `mig-d` で設計して `mig` で実行する、というように対になります。

### 2.3. ドメインの切り方

同じ成果物カテゴリが複数のトラックに現れるため、ドメインとトラックは1対1にはなりません。切り分けでは次を目安にします。

- 1つのトラックが複数のドメインを対象にしてよい。`sch-strategy-<track>.yaml` の `scope.catalogs` には複数の成果物カタログを指定できます。
- 1つのドメインを複数のトラックが参照してよい。例えば業務仕様のドメインは `tobe-rs` で作成し、`impl` や `test` では入力として参照します。
- AS-IS と TO-BE で同じ成果物種別を扱う場合は、ドメインまたは配置ディレクトリで区別し、同一カタログに混在させないようにします。
- ドメインは成果物カタログの管理単位なので、担当者と完了判断がまとまる粒度で切ると、Schedule への展開が素直になります。

## 3. トラックの標準的な実行順序

トラックはフェーズではないため、実行順序は開発の進め方によって変わります。ここでは代表的な2つの進め方について、どこから着手し、どこを並行させ、どこで区切るかの標準例を示します。実際の順序・日付・担当は `sch-track-<track>.yaml` が正本です。

進め方によらず、トラック間には次の情報の流れがあります。この表は、どのトラックの成果物を入力として使うかを示すものであり、着手順を固定するものではありません。

| トラック | 主な入力元トラック   | 受け取る情報                       |
| -------- | -------------------- | ---------------------------------- |
| すべて   | `launch`             | 対象範囲、推進体制、成果物カタログ |
| `impact` | `asis-rs`、`tobe-rs` | 現行の姿、目指す姿                 |
| `tobe-d` | `tobe-rs`            | 要件・仕様                         |
| `qa-d`   | `tobe-rs`            | 要件・仕様                         |
| `mig-d`  | `impact`、`tobe-d`   | 差分と対応方針、移行先の設計       |
| `ops-d`  | `tobe-d`             | 移行後の業務・システム構成         |
| `impl`   | `tobe-d`             | 設計                               |
| `test`   | `qa-d`、`impl`       | 観点・条件、検証対象               |
| `mig`    | `mig-d`、`test`      | 移行設計、検証結果                 |
| `ops`    | `ops-d`、`mig`       | 運用設計、移行結果                 |

`asis-rs` と `tobe-rs` の間には情報の流れを置きません。現行に引きずられた TO-BE を避けるため TO-BE を先に検討することも、現行の制約を早く把握するため AS-IS を先に調べることもできます。

### 3.1. アジャイル開発の場合

対象範囲を小さく区切り、`tobe-rs` から `test` までを1サイクルとして反復します。トラックは消えず、サイクルごとに扱う範囲だけが変わります。

| 段階         | 主に動くトラック             | 扱う範囲                                       |
| ------------ | ---------------------------- | ---------------------------------------------- |
| 立ち上げ     | `launch`                     | プロジェクト全体。以降のサイクルで随時見直す   |
| 各サイクル   | `asis-rs`、`tobe-rs`、`qa-d` | そのサイクルで扱う業務範囲に限定して調査・定義 |
| 各サイクル   | `tobe-d`、`impl`、`test`     | 同じ範囲を設計・実装・検証                     |
| リリース前   | `impact`、`mig-d`、`ops-d`   | 既存への影響、移行方式、運用方式               |
| リリース以降 | `mig`、`ops`                 | 移行実施と恒常運用。以降のサイクルと並行する   |

進め方の要点は次のとおりです。

- `launch` は最小限の範囲で先に通し、確定しない前提は `_UNDECIDED_` として残したままサイクルを始めます。
- `qa-d` は `tobe-rs` と同じサイクル内で進め、受入条件を仕様と同時に定義します。後追いにすると手戻りが大きくなります。
- `asis-rs` と `impact` は全体を先に調べ切らず、サイクルで扱う範囲だけを対象にします。
- 反復は Schedule 側で表現します。`sch-strategy-<track>.yaml` の `cycles` と `iterations` の意味は [Schedule設計ガイド](schedule-design-guide.md) の `phase_setsの反復` を参照してください。
- リリース後も `tobe-rs` 以降のサイクルは続くため、`ops` は他トラックと並行して動き続けます。

### 3.2. ウォーターフォール開発の場合

トラックをおおむね直列に並べ、区切りに判断ゲートを置きます。同じ段階に置いたトラックは並行して進められます。

| 段階           | 並行するトラック     | 段階末の判断材料                       |
| -------------- | -------------------- | -------------------------------------- |
| 立ち上げ       | `launch`             | 目的・範囲・体制が合意できているか     |
| 要件・仕様     | `asis-rs`、`tobe-rs` | TO-BE像と要件・仕様が固まったか        |
| 影響調査       | `impact`             | 差分と対応方針が明確になったか         |
| 設計           | `tobe-d`、`qa-d`     | 実現方式と受入条件が定まったか         |
| 移行・運用設計 | `mig-d`、`ops-d`     | 切替方式と運用方式が定まったか         |
| 実装           | `impl`               | 設計どおりに構築できたか               |
| テスト         | `test`               | 受入条件を満たしたか                   |
| 移行           | `mig`                | 本番切替が完了し、判定基準を満たしたか |
| 運用           | `ops`                | 安定稼働の完了条件を満たしたか         |

進め方の要点は次のとおりです。

- 段階の境界に GO/NOT GO の判断を置く場合は、`要件・仕様`（目指す姿が固まった時点）、`影響調査`（実現性と対応範囲が見えた時点）、`設計`（負荷と工期が見積もれる時点）の3点が代表的な候補です。
- 段階を直列にしても、`asis-rs` と `tobe-rs`、`tobe-d` と `qa-d` のように同じ入力を使うトラックは並行させたほうが待ち時間を減らせます。
- 判断ゲートは Schedule 側の `phase_gates` や `group_milestones` として展開します。トラックの区切りとゲートを1対1にする必要はありません。
- 後段のトラックほど前段の成果物に依存するため、前段で残した `_TODO_` や `_UNDECIDED_` は段階末までに解消しておきます。

### 3.3. 入力元より先に後続トラックへ着手する場合

`トラック間の情報の流れ` は依存の向きであって着手順ではありません。後続トラックから先に着手し、そこで分かったことをもとに入力元トラックの成果物を後から起こす進め方も選べます。既存プロダクトを扱う場合や、実現方式の不確実性が大きい場合はこちらが現実的です。

| 状況                                       | 先に着手するトラック              | 後から起こすトラック |
| ------------------------------------------ | --------------------------------- | -------------------- |
| 既存プロダクトに文書がない                 | `ops`、`impl`（現物・実績の確認） | `asis-rs`            |
| 実現方式に不確実性が大きい                 | `impl`（試作）                    | `tobe-rs`、`tobe-d`  |
| 期待する振る舞いのほうが先に合意できる     | `qa-d`（受入条件）                | `tobe-rs`            |
| 現場の運用実態から恒常運用の要件を固めたい | `ops`                             | `ops-d`              |

進め方の要点は次のとおりです。

- 後から起こす成果物も `dct-<domain>.yaml` に登録し、完了条件を持たせます。作らないと決めた場合は、その判断を記録に残します。
- 逆順で進めた区間は、最後に入力元と後続の整合を取る作業をタスクとして明示的に置きます。どちらを正本とするか決めないまま両方を更新すると、食い違いが残ります。
- Schedule の `depends_on` は実際の着手順に合わせて張ります。`トラック間の情報の流れ` をそのまま写すと、着手できないタスク順になります。
- 試作や現物確認を先に行う場合、その結果は入力にすぎません。後から起こす成果物は、確認結果をそのまま写すのではなく、目指す姿として書き直せているかを確認します。
