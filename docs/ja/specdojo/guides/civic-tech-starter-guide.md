# シビックテック入門ガイド

Civic Tech Starter Guide

資金と専門の人手が限られた小さなシビックテックのチームが、最初に使う 5 つの型（入門の型の組）と、「理解の負債」を減らすために何をどの順で残すかを示します。新しく作る場合と、すでに動いているシステムから始める場合の両方を扱います。

**対象読者**

- 当事者・市民・地域団体の参加者を含む、小さなシビックテックのチームの全員（プログラムを書かない人も含みます）
- そのチームで SpecDojo を使い始める進行役・開発者

**この文書で分かること**

- 理解の負債とは何か、なぜ型で減らせるか
- 最初に使う型の組と、ほかの型を後で足す目安
- 型の文書を agent に作らせ、人が確かめて決める流れ
- 新しく作る場合と既存のシステムから始める場合の、残す順番
- 確かめていない内容に付ける目印（`_ASSUMPTION_`・`_UNDECIDED_`）の使い方

**次に読む文書**

- 型の 4 つの種類（rulebook・recipe・sample・template）の使い分けは [[specdojo:kata-guide|実践の型活用ガイド]] を参照してください。
- 判断ややることの記録の付け方は [[specdojo:register-operation-guide|登録簿運用ガイド]] を参照してください。
- オーケストレーターとの対話の進め方は [[specdojo:orchestrator-operation-guide|オーケストレーター運用ガイド]] を参照してください。
- 既存のシステムから文書を起こす進め方（`retrofit`）は [[specdojo:ryu-guide|実践の進め方ガイド]] を参照してください。

## 1. 理解の負債と型

「理解の負債」は、作ったものについて「何のために、なぜこうしたか」が人の頭の中にしか残らず、その人が抜けると誰も引き継げなくなる状態です。少人数で人が入れ替わる活動では、前の担当者に聞けないことがよくあります。AI がプログラムを速く書くほど、理由の分からない部分も速く増えます。

型は「何をどんな形で書けばよいか」の決まりと見本です。型に沿った文書があれば、後から来た人や AI が、前の人に聞かなくても同じ場所から中身をたどれます。このガイドでは、次の 4 つの段で理解の負債を減らします。

| 段       | すること                                                           |
| -------- | ------------------------------------------------------------------ |
| 復元     | 既存のプログラムや断片的な記録から、agent が型に沿って文書を起こす |
| 確認状態 | 起こした内容のうち推測の部分に、agent が目印を付けて分ける         |
| 人の確定 | 推測の部分を、当事者や経験者が確かめて確定させる                   |
| 記録     | これから先の「なぜ」を、決めたその時に登録簿へ残させて失わない     |

プログラムから戻せるのは主に「何をしているか」です。当事者の困りごと、設計の理由、対象外にした判断などの「なぜ」は戻りません。AI がもっともらしく埋めると、分かったつもりの文書ができ、負債がかえって見えにくくなります。確認状態と人の確定の段は、これを防ぐためにあります。

## 2. 入門の型の組

最初は次の 5 つの型だけを使います。上から順に、プログラムを書かない人でも中身を話したり確かめたりできる型です。文書を書くのは agent で、人は `何をどの順で残すか` の流れで関わります。

| 順  | 型                   | 残すこと                                                           | プログラムを書かない人の関わり方                         | rulebook                                                                       |
| --- | -------------------- | ------------------------------------------------------------------ | -------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 1   | プロジェクト概要     | 誰のどんな困りごとを、何のために解くか                             | 困りごとと目的を自分の言葉で話し、書かれた内容を確かめる | [[specdojo:prj-overview-rulebook\|プロジェクト概要 作成ルール]]                |
| 2   | 課題と解決アプローチ | 困りごとの原因と、どの方針で解くか、何を選ばなかったか             | 方針が現場に合うかを確かめる                             | [[specdojo:prj-issues-and-approach-rulebook\|課題と解決アプローチ 作成ルール]] |
| 3   | ビジネスルール       | 制度や業務の決まり（計算・判定の条件、例外）と、その根拠           | 決まりと例外が正しいかを、根拠の資料や経験で確かめる     | [[specdojo:br-rulebook\|ビジネスルール 作成ルール]]                            |
| 4   | システム化機能一覧   | システムでできること（機能）の一覧と、どの困りごとに当たるか       | 足りない機能、要らない機能を指摘する                     | [[specdojo:sf-index-rulebook\|システム化機能一覧（全体構成）作成ルール]]       |
| 5   | プロジェクト登録簿   | 決めたこと（decision）、やること（todo）、聞きたいこと（question） | 決めたことの理由を話し、決定に同意する                   | [[specdojo:pjr-rulebook\|プロジェクト登録簿 作成ルール]]                       |

5 つに絞った理由は次のとおりです。

- 概要と課題と解決アプローチは、プログラムからは戻らない「なぜ」を持つ型です。人が抜ける前に書く価値が最も高いので先頭に置きます。
- ビジネスルールは、シビックテックで多い制度の計算や判定の正しさを、当事者と開発者が同じ表で確かめられる型です。業務の手順の型（業務プロセス仕様）より書く量が少なく、既存のプログラムから復元しやすいので、業務仕様の入口にします。
- 機能一覧は、作る人と使う人が「何ができるか」をそろえる最小の型です。機能ごとの詳しい仕様は後で足します。
- 判断の記録は、独立した文書ではなく登録簿の decision に残します。決定記録（`dec`）の型は非推奨で、登録簿が判断・やること・質問をまとめて持つためです。

## 3. 後で足す型の目安

次の型は最初は使いません。表の「足す目安」に当てはまる困りごとが実際に起きたときに、オーケストレーターに 1 つずつ起票を頼んで足します。

| 型                                                                                     | 足す目安                                                                                 |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| [[specdojo:gl-rulebook\|用語集]]                                                       | 同じ言葉が人によって違う意味で使われ、話がかみ合わないことがあった                       |
| [[specdojo:prj-stakeholder-register-rulebook\|ステークホルダー登録簿]]                 | 関わる団体や人が増え、誰に何を確かめればよいかが分からなくなった                         |
| [[specdojo:prj-scope-rulebook\|プロジェクトスコープ]]                                  | 「それもやるのか」という食い違いが出て、対象と対象外の線引きを書いておく必要が出た       |
| [[specdojo:prj-success-criteria-and-acceptance-criteria-rulebook\|成功基準と受入条件]] | 資金の出し手や協力団体に、何ができたら成功かを説明する必要が出た                         |
| [[specdojo:bps-rulebook\|業務プロセス仕様]]                                            | 業務の手順が複数の人や段にまたがり、ビジネスルールの表だけでは流れが伝わらない           |
| [[specdojo:bac-rulebook\|業務受入条件]]                                                | 当事者が「これで使える」と判断する条件を、作る前に決めておく必要が出た                   |
| [[specdojo:sf-rulebook\|システム化機能仕様]]                                           | 機能一覧の 1 行だけでは、作る人が入力・出力・例外で迷う機能が出た                        |
| [[specdojo:uis-rulebook\|画面仕様]]                                                    | 画面が増え、使う人と作る人で画面の項目や動きの理解が食い違った                           |
| [[specdojo:nfr-index-rulebook\|非機能要件]]                                            | 個人情報を扱う、止まると困る利用者がいるなど、速さ・安全・使いやすさの条件が必要になった |
| [[specdojo:mm-rulebook\|議事録]]                                                       | 会議で決めたことの経緯まで残したい。決めたこと自体は登録簿の decision で足ります         |

テストの型（受入テストカタログなど）や移行・運用の型は、プログラムの規模が大きくなり、作る人が複数になってから検討します。

## 4. 何をどの順で残すか

### 4.1. 基本の流れ

型の文書は、人が手で書かずに agent に作らせます。オーケストレーター（SpecDojo を操作する対話の AI）に頼むと、次の流れで進みます。

1. 利用者が、作りたい型の文書と材料（聞き取りのメモ、制度の資料、調べるプログラムの場所）をオーケストレーターに伝えます。
2. オーケストレーターが登録簿に todo を起票します。いくつもの型をまとめて作るときは、epic と子の todo に分けます。利用者は完了条件を確かめて起票を認めます。
3. オーケストレーターが `exec run` で agent に文書を作らせます。agent は型の rulebook に沿って書き、根拠を示せない内容に `_ASSUMPTION_`、決まっていない内容に `_UNDECIDED_` を付けます。
4. 人が結果を読んで確かめます。直しが要るときは直す点を完了条件に足して再実行させ、よければ close を指示します。

人の役割は次の 4 つです。書く作業は agent が受け持ちます。

| 役割       | すること                                                                                        |
| ---------- | ----------------------------------------------------------------------------------------------- |
| 話す       | 困りごと、目的、制度や現場の決まり、過去の経緯を、自分の言葉でオーケストレーターに伝える        |
| 確かめる   | agent が作った文書を読み、事実や現場と合っているかを確かめる                                    |
| 決める     | 方針を選び、todo や epic の close と文書の確定（`ready`）を指示する。確定は人だけが行う         |
| 目印を解く | `_ASSUMPTION_` の内容を確かめて外させ、`_UNDECIDED_` の内容を登録簿の decision で決めて外させる |

### 4.2. 新しく作る場合

1. 当事者が困りごとと目的を話し、プロジェクト概要を agent に作らせます。当事者が読んで確かめます。
2. 課題と解決アプローチを作らせます。選ばなかった方針とその理由も話し、文書に残させます。
3. 機能一覧を作らせます。各機能がどの困りごとに当たるかを書かせ、当たらない機能を作らないかは人が決めます。
4. 作り始める機能について、ビジネスルールを作らせます。根拠になる制度の資料の場所や、当事者の経験を材料として渡します。
5. 作りながら決めたこと・迷ったことは、その都度オーケストレーターに伝えて登録簿に残させます。決めたことは decision、まだ決められないことは question にします。

1 から 3 をまとめて始めるときは、次のように epic と子の todo に分けて起票させます。ID とファイル名は例です。

```chat
あなた: 子ども食堂の予約の仕組みを作ります。プロジェクト概要から機能一覧まで、最初の型の文書をまとめて作ってほしいです。材料は先週の聞き取りのメモ（notes/hearing.md）です。

オーケストレーター: 次のように epic と子の todo に分けて起票します。
  ・epic: 入門の型の文書をそろえる
  ・子の todo 1: プロジェクト概要を作る
  ・子の todo 2: 課題と解決アプローチを作る（1 の後に実行）
  ・子の todo 3: システム化機能一覧を作る（2 の後に実行）
  どの todo の完了条件にも、聞き取りのメモを材料にすることと、メモにない「なぜ」に `_ASSUMPTION_` を付けることを書きます。ビジネスルールは、作り始める機能が決まってから別の todo にします。起票してよろしいですか？

あなた: はい、お願いします。

オーケストレーター: epic PJR-AB12 と、子の todo PJR-CD34・PJR-EF56・PJR-GH78 を起票しました。PJR-CD34 から順に `exec run` で agent に作らせます。始めてよろしいですか？

あなた: 始めてください。

オーケストレーター: PJR-CD34 の実行が終わり、review になりました。プロジェクト概要に `_ASSUMPTION_` が 2 か所あります。当事者の方に確かめてもらい、結果を教えてください。

あなた: 1 つ目は合っていました。2 つ目の「対象を小学生に限る理由」は、会場の広さのためです。確かめたのは運営の田中さんで、今日です。

オーケストレーター: 2 か所の目印を外し、確かめた人と日付、2 つ目の理由を本文に書くことを完了条件に足して再実行します。終わったら PJR-CD34 を close し、PJR-EF56 に進みます。
```

子の todo がすべて終わったら、epic の close も人が指示します。epic の起票の仕方は [[specdojo:register-operation-guide|登録簿運用ガイド]] の `track の仕事を epic と子 todo で管理する` を参照してください。

### 4.3. 既存のシステムから始める場合（復元）

すでに動いているシステムがあり、作った人がいない、または理由が分からない場合は、プログラムから戻せるものと、人に聞かないと分からないものを分けて進めます。

1. プロジェクト概要は、今の参加者と当事者が話した内容から agent に作らせます。プログラムからは「なぜ」が戻らないため、概要は復元ではなく聞き取りから始めます。
2. ビジネスルールと機能一覧は、プログラムから復元させます。SpecDojo では、agent が実装を調べて文書を起こす進め方を `retrofit` と呼びます。起票のときに、調べるプログラムの場所をオーケストレーターに伝えます。
3. agent がプログラムで確かめられるのは「今こう動いている」ことだけです。「なぜそうするか」や「それで正しいか」には `_ASSUMPTION_` を付けさせます。
4. 目印の付いた内容を、当事者や経験者が確かめます。正しければ、確かめた人と日付を伝えて目印を外させます。今の動きが本来の意図と違うと分かったら、文書をプログラムに合わせず、直すかどうかを決めて登録簿の decision に残させます。
5. 課題と解決アプローチは、これから直す・足す方針が決まった時点で作らせます。
6. これより後は、新しく作る場合の 5 と同じく、決めたことをその都度登録簿に残させます。

調べるプログラムの場所を伝えると、オーケストレーターが `retrofit` の todo の起票を提案します。いくつもの型を復元するときは、新しく作る場合と同じく epic と子の todo に分けます。ID とパスは例です。

```chat
あなた: 給付の判定をしている今のプログラム（src/eligibility/ 配下）から、判定の決まりを文書に起こしてほしいです。作った人はもういません。

オーケストレーター: `retrofit` の todo「給付判定のビジネスルールを復元する」を起票します。完了条件には、src/eligibility/ を調べること、プログラムで確かめた「今こう動いている」ことだけを事実として書くこと、「なぜそうするか」と「それで正しいか」に `_ASSUMPTION_` を付けることを書きます。機能一覧も一緒に復元するなら、epic と子の todo 2 つに分けます。どちらにしますか？

あなた: 機能一覧も一緒にお願いします。

オーケストレーター: epic PJR-JK12 と、子の todo PJR-LM34（ビジネスルール）・PJR-NP56（機能一覧）を起票しました。PJR-LM34 から `exec run` で agent に作らせます。始めてよろしいですか？

あなた: 始めてください。
```

起票と実行のコマンドはオーケストレーターが使います。詳細は [[specdojo:command-reference|CLI コマンドリファレンス]] の `register add` と `exec run` を参照してください。

## 5. 確認状態の目印を使う

型に沿って書いた文書でも、確かめた内容と推測が混ざります。混ざったままにすると、後から読む人が推測を事実として受け取ります。そこで agent は、確かめていない内容の段落の先頭に次の目印を付けます。人は目印の付いた内容を確かめ、結果をオーケストレーターに伝えて外させます。

| 目印           | agent が付ける場面                                               | 外させるとき                                                           |
| -------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `_ASSUMPTION_` | 推測や仮置きで書いた。とくに、プログラムから「なぜ」を推し量った | 当事者や経験者が確かめた。確かめた人と日付を本文に書かせてから外させる |
| `_UNDECIDED_`  | 情報は足りているが、どれにするかを誰も決めていない               | 登録簿の decision で決めた。決定の個票を本文から参照させてから外させる |

agent が書いた文書では、目印は次のように見えます。

```markdown
_ASSUMPTION_: 申請の受付を月末で締めるのは、自治体の締め日に合わせたためと推測した。プログラムの日付判定からの推測で、担当者には未確認。

_UNDECIDED_: 世帯の人数に同居していない家族を含めるかは未決。PJR-XXXX の decision で決める。
```

使うときは次の点に気を付けます。

- 目印がないことは、確かめた証拠になりません。確かめた人と日付が本文にない内容は、確かめていない内容として扱います。
- 根拠の場所（資料・プログラム・聞き取り）を示せない部分に agent が `_ASSUMPTION_` を付けることは、オーケストレーターが起票のときに完了条件へ書きます。
- 文書の確定（`ready`）を指示しても、目印の付いた内容が確かめられたことにはなりません。確定を指示する前に、目印が残っていないかを人が見ます。
- 目印の書き方の規約は [[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] の `文脈の目印` を正本とします。

## 6. 全部の型を求めない

SpecDojo の進め方の考え方の 1 つに Sustainable Participation（無理のない参加）があります。お金だけでなく、参加する人の時間と続ける負担も費用として数え、要る文書だけを選んで分担するという考え方です。このガイドが入門の型の組を 5 つに絞り、ほかの型を困りごとが起きてから足すとしているのも、このためです。

- 5 つの型も、全部の章を一度に埋める必要はありません。分からない章は agent に `_ASSUMPTION_` や空欄の理由を書かせて残し、分かった人が後で話して埋めさせます。
- 型を足すのは、`後で足す型の目安` の困りごとが実際に起きたときです。将来要りそうだという理由だけでは起票を頼みません。
- 書く作業は agent に任せ、人の作業は `基本の流れ` の 4 つの役割に絞ります。そのうえで一人に集めないよう、当事者は話して確かめる、経験者は目印を解く、進行役はオーケストレーターへの依頼と close の指示をまとめる、開発者は復元した内容とプログラムとの対応を確かめる、というように分けます。
- 型を足すかどうか、やめるかどうかも、登録簿の decision に理由と一緒に残させます。後から来た人が、なぜこの型の組なのかをたどれます。
